Clean-Room Save Format Report: Castlevania - Byakuya no Concerto (Japan)

Release key: ACHJ-r0-e50df7b87f8523f6 | Game code: ACHJ | Header family: ACH | Community: comm-048

All findings below are derived exclusively from this workspace: ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and the real binary saves/cap-00-future-0.sav (plus its pre-computed hexdump in saves/hexdump_and_diffs.txt). No third-party game-specific sources were consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM

What is proven (code + byte evidence agree):

  • The save medium is flat-addressed SRAM (0x0E000000), not Flash or EEPROM — no Flash command-sequence bytes (0x5555/0x2AAA) or EEPROM/DMA3 (0x040000D4) access patterns exist anywhere in the 177 decompiled functions. All save I/O goes through a simple byte-copy driver.
  • A 16-byte ASCII magic/version stamp, "CASTLEVANIA1.00\0", lives at absolute save offset 0x0000. It is written by FUN_08000e98 and verified by FUN_08000f28, and it is the only non-zero content in the one .sav sample available (saves/cap-00-future-0.sav).
  • The boot path (FUN_08000800) checks this magic and, if it does not match, re-formats the save by calling the writer (FUN_08000e98), which bulk-copies a RAM buffer to SRAM in 0x1000-byte chunks before stamping the magic. This strongly indicates the magic doubles as a "is SRAM already formatted for this game/version" sentinel, and that the captured sample is a freshly-formatted, never-played save (header present, everything else 0x00).
  • A per-slot 1-byte bitflag field gates whether three 20-byte "file" records and one 76-byte "global config" record are loaded from SRAM into the RAM mirror, or skipped in favor of blank in-RAM defaults (FUN_08000ff8, consumed by FUN_0800b98c / FUN_0800ba4c).

What remains open (static-only or unresolved):

  • No checksum, CRC, sum, or XOR-style integrity routine was found anywhere in ghidra/decompiled.c. Either this title has no save checksum, or the checksum routine lies outside the 177 decompiled functions in this workspace (several callees — func_0x0801027c, func_0x080103ac, func_0x08010d44, func_0x080ba988 — are referenced only by call-site address and are not decompiled here).
  • The absolute SRAM byte offsets for the three file records, the global config block, and the validity-flag byte are all held in literal-pool constants (_DAT_0800b9e0, _DAT_0800ba84, _DAT_0800ba88, _DAT_0800ba8c, _DAT_08001024, etc.) whose resolved integer values are not printed by the decompiler in this workspace — only their use is visible. Their relative structure (strides, sizes, order) is solid; their absolute addresses are HYPOTHESIS.
  • Only one .sav sample is present in saves/ (the packet metadata references total_sav_files: 6, but only cap-00-future-0.sav is physically in this workspace), and it is blank/freshly-formatted. No sample with populated file-slot or config data was available to confirm field contents, byte order, or value ranges for anything beyond the magic string.
  • No states/*.ss paired save states are present in this checkpoint cohort, so none of the fuzzing predictions in §6 could be runtime-verified here.

2. Physical Media, Slot Geometry & Redundancy

  • Total save size: 32,768 bytes (32 KiB), consistent with the packet's declared SRAM 256K media (256 Kibit = 32 KiB).
  • SDK save tag: none detected in ROM (packet confirms SDK Save Tags in ROM: none); this is a hand-rolled/engine-specific SRAM driver, not an auto-detected SDK save library signature.
  • Active byte span observed in the sample: 0x0000–0x000F (16 bytes) only; everything else (0x0010–0x7FFF) is 0x00 fill.

  • Redundancy / mirroring: None observed. Each record is written/read exactly once per call; there is no A/B backup-copy pattern like the dual-bank schemes seen in some SDK save libraries.

  • Selection rule: Validity is gated purely by the 1-byte flag field via FUN_08000ff8 (one bit per slot/config, see §3), not by a sequence counter or checksum comparison between copies.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

  • FUN_080bcc58 (0x080bcc58) — raw byte-copy primitive. Sets an SRAM wait-control register (*_DAT_080bcc90 = *_DAT_080bcc90 & mask | 3, consistent with the GBA WAITCNT-style access-timing convention for SRAM/ROM regions) then copies param_3 bytes one at a time from param_1 to param_2. This is the literal SRAM bus driver — flat byte addressing, no command/latch sequence, confirming SRAM (not Flash, which requires 0xAA/0x55 unlock writes at 0x5555/0x2AAA, and not EEPROM, which requires serial-bit DMA3 transfers). Confidence: CONFIRMED_STATIC.
  • func_0x080bd178 / FUN_080bd178 (0x080bd178) — the actual read/write entry point used by every higher-level save function (src, dst, size, retries argument order, confirmed by tracing both directions — see 3.3). Decompiles only as an indirect jump-table trampoline (UNRECOVERED_JUMPTABLE) in this workspace, i.e. its body dispatches through a function pointer and Ghidra could not statically resolve the target. Functionally it behaves as the byte-copy transfer call. Confidence: CONFIRMED_STATIC (behavior inferred from all call sites; body itself unresolved).
  • FUN_080bcd7c (0x080bcd7c) — write-with-retry wrapper: calls FUN_080bcc58 (prep copy) then func_0x080bd178(src, dst, size, retries) up to 3 times, breaking out on a zero (success) return. This retry-on-failure pattern is standard defensive SRAM-write practice (guards against brown-out/bus-contention corruption during the write) and strongly implies func_0x080bd178's nonzero return means "write failed, try again." Confidence: CONFIRMED_STATIC.

3.2 Serialization / deserialization & checksum routines

  • No checksum, CRC, complement, or rolling-sum routine was found anywhere in ghidra/decompiled.c. A targeted search for accumulator-style byte-summation loops and for the strings "checksum"/"crc" (irrelevant here since the binary has no symbol table, but used as a sanity grep) returned nothing beyond the driver functions already documented.
  • There is no dedicated (de)serialization function distinct from the raw byte-copy driver — the "serialization" is simply a verbatim memory-image copy of the in-RAM struct to/from SRAM at fixed offsets. This is common for small, hand-rolled GBA save systems that don't use the official Nintendo SDK save library.
  • Conclusion: either (a) this title has no save-data integrity check at all and relies solely on the magic-string format sentinel plus the 1-byte validity-flag gate, or (b) a checksum routine exists in one of the un-decompiled callees (func_0x0801027c, func_0x080103ac, func_0x08010d44, func_0x080ba988) that this workspace's 177-function extraction did not include. Confidence: UNKNOWN — reported honestly rather than guessed.

3.3 Writer function and full traced caller chain

FUN_08000e98 (0x08000e98) — SRAM format/write function.

  • Body: bulk-copies a RAM source buffer to SRAM 0x0E000000 in 0x1000-byte chunks via FUN_080bcd7c(src, dst=iVar4+0xE000000, size=0x1000), looping while iVar4 <= iVar5 (iVar5 = _DAT_08000f20, an unresolved total-size constant — almost certainly 0x8000/32768, matching the observed .sav size). After the bulk copy, it writes the 15-byte magic ("CASTLEVANIA1.00") to SRAM offset 0x0000 via a final FUN_080bcd7c(src, 0xE000000, 0xF) call.
  • How mapped: located via the [MMIO-SEED] tag in ghidra/save_related_functions.c (direct 0x0E000000 SRAM literal) and cross-referenced in ghidra/decompiled.c:605-639.
  • Caller found (static, direct call in decompiled C, NOT present in callgraph.json's caller list for this address — callgraph.json reports callers: []): FUN_08000800 (0x08000800), at ghidra/decompiled.c:205-210:
  iVar3 = func_0x08000f28();
  if (iVar3 == 0) {
    func_0x08000e98();
  }

This is the boot-time format check: if the magic-verify function (FUN_08000f28) reports a mismatch (iVar3 == 0, i.e. SRAM does not currently hold a valid "CASTLEVANIA1.00" stamp — fresh/uninitialized/corrupted SRAM), the game immediately reformats the whole save region and re-stamps the magic. This is exactly the state captured in saves/cap-00-future-0.sav: magic present, payload zeroed — a save that has been through this format path but never through an actual in-game save.

  • FUN_08000800 itself has no statically-resolved caller (callgraph.json: callers: []); it is reached via the ROM's interrupt/reset or state-machine jump-table dispatch (consistent with the pervasive UNRECOVERED_JUMPTABLE pattern seen in nearly every function in this codebase), not a direct BL.
  • Confidence: CONFIRMED_STATIC for the format trigger logic; CONFIRMED_VERIFIED for the resulting on-disk state (byte-for-byte matches the observed sample).

FUN_08000f28 (0x08000f28) — magic/version verify (read) function.

  • Body: reads 15 bytes from SRAM 0x0E000000 into a RAM buffer via func_0x080bd178(0xE000000, pcVar3, 0xF, retries), then byte-compares against a 15-byte ROM literal (_DAT_08000f58) and returns 1 on exact match, 0 otherwise.
  • How mapped: second [MMIO-SEED] entry in ghidra/save_related_functions.c; full body at ghidra/decompiled.c:650-669.
  • Callers (from ghidra/callgraph.json, confirmed by direct call sites in ghidra/decompiled.c):
  • FUN_08000800 (0x08000800) — boot-time check described above (§3.3, FUN_08000e98 caller entry).
  • FUN_0800b98c (0x0800b98c) — per-file-slot loader, see below.
  • FUN_0800ba4c (0x0800ba4c) — global-config loader, see below.
  • Confidence: CONFIRMED_VERIFIED — both the writer and verifier agree on the exact 15/16-byte magic, and the actual .sav bytes match it exactly (see §4).

FUN_0800b98c (0x0800b98c) — per-file-slot SRAM→RAM loader, ghidra/decompiled.c:1544-1574.

void FUN_0800b98c(int param_1, int param_2) {
  piVar1 = _DAT_0800b9d8;                 // RAM mirror struct base pointer
  iVar2 = FUN_08000f28();                 // 1 = magic valid, 0 = invalid
  iVar3 = 0;
  if (iVar2 != 0) {
    iVar3 = FUN_08000ff8(param_1);        // 1 = slot param_1 marked "blank", 0 = slot has data
    if (iVar3 == 0) {
      // blank-init: zero the 4-byte header of the in-RAM record
      *(undefined4 **)iRam0800ba10 = &uStack_1c;   // stack-sourced 0 value
      *(int *)(iVar2 + 4) = *piVar1 + param_2*0x14 + 0x20;
      *(undefined4 *)(iVar2 + 8) = uRam0800ba14;
      uStack_1c = 0;
    } else {
      // real copy: SRAM record -> RAM mirror
      func_0x080bd178(param_1*0x3f8 + _DAT_0800b9e0,   // SRAM src: file `param_1`'s 1016-byte block
                       *piVar1 + param_2*0x14 + 0x20,   // RAM dst: struct + slot*20 + 0x20
                       0x14, *_DAT_0800b9dc);           // size 20 bytes, retry count
    }
  }
}
  • How each caller mutates the in-RAM save struct: the 20-byte record at RAM offset (struct_base + param_2*0x14 + 0x20) is either zeroed (blank/default file) or overwritten verbatim from SRAM offset (param_1*0x3F8 + base). param_1 selects which of the 3 SRAM file blocks to read; param_2 selects which 20-byte slot in the RAM mirror receives it (in the one caller found, these are always equal — see below).
  • Caller found: FUN_080041ac (0x080041ac), ghidra/decompiled.c:1507-1537:
  uVar3 = 0;
  do {
    func_0x0800b98c(uVar3, 0);
    if (*(short *)(iVar2 + 0x2a) != 0) {
      *(byte *)((int)param_1 + 0x11) |= (byte)(1 << (uVar3 & 0xff));
    }
    uVar3 = uVar3 + 1;
  } while ((int)uVar3 < 3);

This is a file-select-menu population loop: it calls FUN_0800b98c once per file index 0..2 (always with param_2 = 0, i.e. loading each candidate file into the same scratch RAM slot 0 for inspection), then checks an offset-0x2A field of that scratch struct and, if nonzero, sets the corresponding bit in a presence/availability bitmask at param_1+0x11. This is the save-file-select screen's "does file N exist, show its data" logic, not the in-game save-write path.

  • FUN_080041ac has no statically-resolved caller (callgraph.json: callers: [], and no direct call site found anywhere in ghidra/decompiled.c's text) — reached only via indirect/function-pointer dispatch (same jump-table pattern as elsewhere in this ROM), consistent with being a menu-system callback.
  • Confidence: CONFIRMED_STATIC (code path fully traced; never observed exercised in the available .sav sample, since that sample has no populated file records).

FUN_0800ba4c (0x0800ba4c) — global-config SRAM→RAM loader, ghidra/decompiled.c:1581-1599.

void FUN_0800ba4c(void) {
  piVar1 = _DAT_0800ba84;                 // RAM mirror struct base pointer
  iVar2 = FUN_08000f28();                 // magic valid check
  if ((iVar2 != 0) && (iVar3 = FUN_08000ff8(3), iVar3 != 0)) {
    func_0x080bd178(_DAT_0800ba8c, *piVar1 + 0x35c, 0x4c, *_DAT_0800ba88);
  }
}
  • Mirrors the file-slot loader exactly but with fixed slot index 3 (the 4th validity bit, reserved for global config rather than a per-file record), fixed RAM destination struct+0x35C, and fixed size 0x4C (76 bytes).
  • Caller found: FUN_080006d4 (0x080006d4), ghidra/decompiled.c:152-165, a large system boot-initialization routine that also calls audio/graphics/controller subsystem init functions (func_0x08000bfc, func_0x08011f04, func_0x08012768, func_0x0800e968, func_0x08010cdc, func_0x08014248, func_0x080158bc, func_0x0801615c) before finally calling FUN_0800ba4c() last. This firmly places global-config load as a one-shot, startup-time operation (load saved options/settings once at boot), not something repeated per frame or per menu visit.
  • FUN_080006d4 itself is called by FUN_08000668 relationship is actually reversed in callgraph.json (0x08000668.callers = ["0x080006d4"], i.e. FUN_080006d4 calls FUN_08000668); no further static caller of FUN_080006d4 was found, consistent with it being the ROM's cold-boot entry sequence.
  • Confidence: CONFIRMED_STATIC.

FUN_08000ff8 (0x08000ff8) — 1-byte validity-flag test, ghidra/decompiled.c:684-693.

void FUN_08000ff8(uint param_1) {
  byte abStack_c[4];
  func_0x080bd178(_DAT_08001024, abStack_c, 1, *_DAT_08001020);   // read 1 flag byte from SRAM
  return ~((int)(uint)abStack_c[0] >> (param_1 & 0xff)) & 1;      // inverted single-bit test
}
  • Reads a single flag byte from a fixed SRAM offset (_DAT_08001024, absolute value unresolved in this workspace) and returns the complement of bit param_1: 1 if that bit is clear (slot/config considered present/valid), 0 if set (slot/config considered blank/absent).
  • Callers: FUN_0800b98c (bit index = file number 0..2) and FUN_0800ba4c (bit index fixed at 3, the config slot). Both callers already documented above.
  • Given the observed sample is all-zero past offset 0x10, this flag byte reads as 0x00 in that sample, so every bit tests as clear → every slot (0,1,2) and the config slot (3) are reported present/valid by this bit-test alone — but FUN_0800b98c/FUN_0800ba4c only read the corresponding record in that case; they do not themselves re-validate its contents against the all-zero region, which is why the in-RAM mirror after boot in this sample would simply be all-zero file/config data rather than "no file" sentinel data. This is a subtlety worth flagging for the fuzzing plan in §6.
  • Confidence: CONFIRMED_STATIC for the bit-test logic; CONFIRMED_VERIFIED for its behavior against the actual sample's implied flag-byte value (0x00, consistent with the all-zero fill).

4.2 Checksum / integrity algorithm

No checksum or CRC mechanism was identified in ghidra/decompiled.c. No stored-checksum field, covered byte range, or accumulator loop exists in any save-related function traced in §3. The only two integrity gates present in this title are:

  1. The 16-byte magic/version string (format sentinel, §4.1).
  2. The single-bit-per-slot validity flag tested by FUN_08000ff8 (presence gate, §3).

Neither constitutes a cryptographic or arithmetic checksum over the payload bytes.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states are present in this checkpoint cohort (states/ is empty), so none of the following could be runtime-verified here. They are written as concrete, falsifiable mutation plans for the next capture round, once paired pre/post .ss states exist.

  1. Magic-corruption mutation (highest-confidence target, since this field is CONFIRMED_VERIFIED):
  • Mutate any single byte in 0x0000–0x000E (e.g. flip 0x0000 from 0x43 to 0x00).
  • No checksum repair needed (none exists).
  • Predicted effect: on next boot, FUN_08000f28's compare fails (iVar2 == 0) → FUN_08000800 calls FUN_08000e98, which reformats the entire 32 KiB region and rewrites the magic, destroying any file-slot/config data that may have existed. Observable via RAM: struct_base-relative file/config regions reset to the blank-init pattern; .sav bytes return to exactly saves/cap-00-future-0.sav's current content.
  1. Validity-flag-byte mutation (tests CONFIRMED_STATIC bit-gating logic):
  • Once the real SRAM offset of the flag byte (_DAT_08001024) is resolved by a live trace (watch the func_0x080bd178(_DAT_08001024, ...) call's source register at runtime), set bit 0 (file-0 flag) from 0→1.
  • Predicted effect: FUN_08000ff8(0) now returns 0 (blank) instead of 1 (present); the next call to FUN_0800b98c(0, 0) takes the blank-init branch instead of the SRAM-copy branch, so file-slot 0's 20-byte record in RAM is zeroed regardless of its actual SRAM bytes. This should be observable in the file-select menu (file 0 should display as empty/new-game even if its 20-byte record is non-zero).
  1. File-slot payload mutation (to resolve the HYPOTHESIS-rated 20-byte record layout):
  • Once a .sav sample with actual gameplay progress is captured, diff it byte-for-byte against saves/cap-00-future-0.sav within each 0x3F8-strided 20-byte window to identify which sub-fields change between a fresh file and a played one (likely candidates by genre convention: playtime, item/equipment flags, map/stage index, HP/stats — none of this is assumed here, all pending real byte evidence).
  • Mutate single bytes within an identified non-zero window and reload to observe in-game effects (e.g. displayed stage name, HP value, completion percentage on the file-select screen, which reads the offset-0x2A field per FUN_080041ac).
  • Predicted effect: since no checksum exists, arbitrary byte mutations within the 20-byte record should load without any "corrupted save" rejection — the only two gates (§4, §3) are the global magic and the per-slot flag bit, neither of which covers this record's payload. A successful counterfactual here (mutated byte loads and visibly changes something in-game with no corruption warning) would strengthen the "no checksum" conclusion in §3.2 to CONFIRMED_VERIFIED; a rejection/soft-lock would falsify it and point to an un-decompiled validation routine.
  1. Global-config block mutation (76 bytes at struct+0x35C):
  • Same approach as (3) applied to the fixed config block, loaded once at boot by FUN_0800ba4c via FUN_080006d4. Since this load happens only once at cold boot (not on every menu visit), the counterfactual must use a fresh power-on .ss state (not an in-session reload) to observe any effect.
  1. Fresh vs. restore matched-duration control:
  • Capture one .ss immediately after FUN_08000800's format path runs on genuinely blank SRAM (fresh), and one .ss after loading saves/cap-00-future-0.sav as-is (restore of an already-formatted-but-empty save). Both should be byte-identical in SRAM and behaviorally identical in-game, since the sample already represents the "freshly formatted" state — this is a negative control confirming the format path is idempotent and that cap-00-future-0.sav is not silently different from true factory-blank SRAM.
