1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven to CONFIRMED_VERIFIED standard:

  1. The medium is an 8 KiB EEPROM (EEPROM 64K in PACKET.md; 8192-byte .sav files; serial access through 0x0D000000 via DMA3 in FUN_080762e0 / FUN_08076360 / FUN_08076410).
  2. The populated save is two byte-identical 560-byte copies at raw .sav offsets 0x000 and 0x230 (70 EEPROM blocks of 8 bytes each). The rest of the 8192-byte image (0x460..0x1FFF) is the fill byte 0xFF; cap-00 is entirely 0xFF.
  3. Each copy ends, in the in-RAM serialization, with the 6-byte magic DIABLK followed by a 16-bit byte-sum checksum (sum of all preceding 552 bytes, modulo 65536, stored little-endian). In the raw EEPROM dump the final 8-byte block is byte-reversed (see §3.4), so the magic appears as ASCII KLBAID at raw offsets 0x22A and 0x45A, and the checksum bytes appear as 2C 0A at raw 0x228 / 0x458.
  4. The checksum was recomputed in Python over both copies of cap-01-future-1.sav and matches the stored value 0x2C0A in both copies (§4.3).
  5. The load path tries copy 0 first and falls back to copy 1 on EEPROM-read, magic, or checksum failure (FUN_0803cc8c → FUN_0803cce4). The save path writes copy 0 and then copy 1 from the same serialized buffer (FUN_0803cb3c → FUN_0803cbd0(0), FUN_0803cbd0(count)). There is no generation/sequence counter in the observed format: the two copies are identical and selection is order-based, not newest-wins.

What remains open (hence MEDIUM, not HIGH):

  • The absolute RAM address of the in-RAM save mirror (0x02xxxxxx/0x03xxxxxx) cannot be resolved: the decompilation references it only through unresolved ROM literal-pool symbols (_DAT_0803cbbc, _DAT_08070120, …) whose values are not present in this workspace. Field offsets below are therefore given as offsets within the 560-byte serialized save image ("logical / RAM-image offsets"), which are proven, plus the raw .sav transformation, which is also proven.
  • Gameplay semantics of most payload fields (which counter is money, which record is which character/item, etc.) are HYPOTHESIS/UNKNOWN. Only one payload writer could be tied to a field range with static certainty (FUN_0806fd78, §3.5, §5).
  • The top-level save/load entry points FUN_0803cb3c and FUN_0803cc8c have no static callers in ghidra/callgraph.json and no textual callers in ghidra/decompiled.c; they are presumably reached through an unrecovered jump table / function-pointer table (every function in this decompilation ends in an UNRECOVERED_JUMPTABLE call). Their trigger context (menu action, auto-save point) is therefore UNKNOWN.

2.2 PACKET probe results, reinterpreted

The PACKET.md profile lists 15 "active ranges" inside 0x000..0x45F and candidate checksum spans at 0x10C, 0x128, 0x33C, 0x358. Those are artefacts of splitting the two 560-byte copies at 0xFF runs, not separate fields: each copy is a single 560-byte serialized blob (§5), the 0xFF runs at logical 0x10C..0x12B etc. are in-blob padding (§5), and the true checksum sits in the final block of each copy (raw 0x228/0x458). The cold-reload probe mutated raw offset 0x10C and observed no integrity rejection and no revert-to-blank; that is consistent with this format — offset 0x10C lies in the covered region of copy 0, so a mutation there breaks copy 0's checksum, but the loader silently falls back to the intact copy 1 (FUN_0803cc8c), so no blank-revert is expected. Integrity protection exists, but it is redundancy-masked for single-copy corruption.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are Thumb code in ROM (0x08xxxxxx). The call graph in this workspace is sparse: most functions show no recovered callers/callees because every function tail-calls through an unrecovered jump table. Mapping method for each caller below: (a) direct func_0x… / FUN_… call sites found by text search in ghidra/decompiled.c; (b) edges in ghidra/callgraph.json; (c) where both are silent, that fact is stated rather than filled in.

3.1 Low-level hardware I/O driver (EEPROM serial via DMA3)

FUN_080762e0(src, dst, count) — DMA3 setup-and-wait — CONFIRMED_STATIC

  • Saves/clears an interrupt-enable global, programs three DMA-register globals via literal-pool pointers (*_DAT_08076350 = param_1 = source, *_DAT_08076354 = param_2 = destination, *_DAT_08076358 = param_3 & 0xFFFF | 0x80000000 = count with the DMA-enable bit 31 set — the standard DMA3 register block at 0x040000D4), then spins while the control register's busy bit (uVar2 & 0x8000 on the high halfword) is set, and restores the interrupt global.
  • This is the single choke point for all EEPROM transfers: called by FUN_08076360 (twice per read) and FUN_08076410 (once per write). Callers (callgraph + text): 0x08076360, 0x08076410.

FUN_08076360(block_addr, dst_u16x4) — EEPROM read one 8-byte block — CONFIRMED_STATIC

  • Bounds check: param_1 < *(ushort *)(cfg + 4) — the EEPROM config global's block-count field (1024 blocks on a 64-Kbit part; the exact config values are literal-pool data not present in this workspace, marked UNKNOWN).
  • Builds the read command bitstream on the stack: start bits 1, 1, then the block address, MSB-first, cfg[+8] bits wide (address-width byte of the same config global).
  • FUN_080762e0(bitstream, 0x0D000000, addr_bits + 3) sends it; FUN_080762e0(0x0D000000, bitstream, 0x44) receives 68 halfwords (64 data bits plus framing, each bit delivered as a 0/1 halfword).
  • Reassembles 4 × u16 MSB-first from the received bits and stores them in reverse word order (puVar6 = (ushort *)(param_2 + 6), decrementing) — the root of the per-block byte reversal documented in §3.4.
  • Returns 0 on success (non-zero/return-value global untouched on out-of-range address). Caller: FUN_080764ec (verify) and FUN_0803cce4 (bulk read; text call site at decompiled.c line 1635, an edge the JSON call graph missed — the graph lists no callees for 0x0803cce4).

FUN_08076410(block_addr, src_u16x4) — EEPROM write one 8-byte block — CONFIRMED_STATIC

  • Same bounds check. Expands the address and the 4 × 16 data bits into a halfword bitstream (each bit stored as the low bit of a halfword, shifting the source words out), prepends the write start/opcode bits (*puVar6 = 0; puVar6[-1] = 1 after the address field), and sends addr_bits + 0x43 halfwords to 0x0D000000 via FUN_080762e0 — i.e. framing + 64 data bits.
  • Then calls FUN_08076214 (EEPROM/DMA assist enable, §3.2), polls the EEPROM busy line (uRam0d000000 & 1) together with a completion flag global (*_DAT_080764e4), and calls FUN_0807629c (assist disable) before returning. Return value is 0 on success, non-zero (uRam080764e8 path) on timeout/busy-failure.
  • Callers: FUN_0803cbd0 only (text call site at decompiled.c line 1551; the JSON call graph correctly lists 0x08076410's callees but shows no caller for 0x0803cbd0 because 0x0803cbd0 itself has no recovered callers in the graph — see §3.3).

FUN_080764ec(block_addr, expected_u16x4) — EEPROM verify one block — CONFIRMED_STATIC

  • Reads the block back with FUN_08076360 into a stack buffer and compares all 4 halfwords against the expected data; returns 0 on match, 0x8000 on first mismatch. Caller: FUN_0803cbd0 (line 1569).

3.2 DMA/EEPROM assist helpers

Called from the boot function FUN_0800028c (line 38 — the only textual caller of any function in this section besides the intra-section calls). It initializes the descriptor object (fields +0 = a stack-linked cell, +4 and +8 from literal-pool values), calls the heap-init FUN_0803ce8c(base, 0x3F000), and clears a flag global. This anchors the whole save subsystem to console boot.

3.4 The per-8-byte-block reversal (why the raw file reads KLBAID)

The EEPROM layer transfers each 8-byte block as 64 serial bits and the read path reassembles the 4 halfwords in reverse word order (FUN_08076360), with the write path (FUN_08076410) performing the inverse expansion. The net, empirically exact, transformation between the in-RAM serialized image and the raw .sav bytes is:

Within each aligned 8-byte block, the raw file byte order is the reverse of the RAM byte order. Block order itself is preserved: RAM block n ↔ raw bytes 8n .. 8n+7 of the copy.

Verification (Python, §4.3): reversing each 8-byte block of copy 0 of cap-01 yields a RAM image whose final block is exactly 44 49 41 42 4C 4B 0A 2C = DIABLK + checksum 0x2C0A (little-endian), and whose byte-sum matches. The same holds for copy 1. In the raw file the last block therefore reads 2C 0A 4B 4C 42 41 49 44 (… 2C 0A 'K' 'L' 'B' 'A' 'I' 'D'). All field offsets in §5 are given in RAM-image (logical) offsets, with the raw offset derivable as: raw = copy_base + (logical & ~7) + (7 - (logical & 7)) per byte.

3.5 Payload writers (who mutates the RAM save struct before a flush)

Only one payload-mutating function in the decompiled set writes at offsets that land inside the 560-byte save image with the exact observed pattern:

FUN_0806fd78() — initialize four 28-byte records at save offset 0x1B4 — writer, CONFIRMED_STATIC for the code pattern, HYPOTHESIS for "its base pointer is the save mirror"

  • Loops i = 0..3, record stride 0x1C (28 bytes), source stride 0x18 (24 bytes) from a ROM data table (_DAT_08070124-based; the table itself is not in this workspace).
  • Per record (offsets relative to the record base at base + 0x1B4 + i*0x1C): zeroes a u32 at +0x00; copies u16s from the ROM entry to +0x04, +0x08, +0x0C, +0x10, +0x14 (source offsets +0, +4, +6, +8, +10, +12 in Ghidra's duplicated-store rendering — the decompiler emits each store twice through two algebraically equal base expressions; the distinct destination offsets are +0x04..+0x15); sets a u16 at +0x0C relative to the 0x1C0-anchored expression to 0 (the zero field observed at record +0x0E in two records — see §5 for the exact observed layout); ORs a flag constant (_DAT_08070128, value UNKNOWN) into the u16 at record +0x18; zeroes the u16 at record +0x1A.

No other function in the 89-function decompilation was found writing at save-image offsets 0x180/0x184 (the two 1 counters) or elsewhere in 0x000..0x227; those writers are outside the traced function set (UNKNOWN). 4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • In-RAM (written by FUN_0803c9b8, checked by FUN_0803ca54): 6 ASCII bytes DIABLK = 44 49 41 42 4C 4B at logical offset 0x228 (552) of each copy, i.e. the first 6 bytes of the final 8-byte block.
  • In the raw .sav (after the §3.4 per-block reversal): ASCII KLBAID = 4B 4C 42 41 49 44 at raw offsets 0x22A (copy 0) and 0x45A (copy 1). Verified present in cap-01-future-1.sav at exactly those offsets; absent (all-0xFF) in cap-00-future-0.sav.
  • Confidence: CONFIRMED_VERIFIED (code writes/checks DIABLK; bytes show the predicted reversed form at the predicted offsets in both copies).

4.2 Checksum algorithm (exact)

stored_u16_le  =  ( Σ byte[i]  for i in 0 .. 551 )  mod 65536
  • Algorithm class: sum8 accumulated into a 16-bit unsigned short (plain byte sum, no seed, no complement, no final XOR). In Ghidra's rendering, FUN_0803c9b8: *psVar2 = *psVar2 + (ushort)*pbStack_18; over (count-1)*8 bytes; FUN_0803ca54 recomputes identically into a short and compares with *(short *)(last + 6). Signedness of the accumulator is irrelevant modulo 65536 for the byte range involved.
  • Covered range: logical bytes 0x000..0x227 (552 bytes = the first 69 blocks) of the copy. The final block (magic + the checksum itself) is not covered.
  • Stored at: logical offset 0x22E (558), size 2, little-endian u16 in the RAM image. After the §3.4 reversal, its two bytes appear at raw copy offsets 0x228..0x229 in the order 2C 0A (high byte first), i.e. the raw bytes read big-endian equal the checksum value.
  • Error behaviour: magic mismatch → FUN_0803ca54 returns -3; checksum mismatch → -2; EEPROM read failure in bulk load → -1; any of these on copy 0 makes FUN_0803cc8c try copy 1. There is no correction, only fallback.
  • The candidate spans in PACKET.md (0x10C, 0x128, 0x33C, 0x358) are not checksums: 0x10C/0x33C-relative are inside the 0xFF padding field, and 0x128/0x358 are copy-relative zero regions. The single checksum per copy is at the offsets above. CONFIRMED_VERIFIED by elimination (only 0x2C0A satisfies the code-derived formula, §4.3) and by the code.

    ram = b''.join(raw[i:i+8][::-1] for i in range(0, 0x230, 8))   # undo §3.4 reversal
    stored = struct.unpack_from('<H', ram, 0x22E)[0]
    comp = sum(ram[:0x228]) & 0xffff
    print(slot, f"base={base:#x} raw_magic@{base+0x22a:#x}={raw[0x22a:0x230]}",
          f"ram_magic={ram[0x228:0x22e]} storedLE={stored:#06x}",
          f"computed_sum8={comp:#06x} match={stored == comp}",
          f"raw_prev_bytes={raw[0x228:0x22a].hex()}")
print("copies identical:", d[:0x230] == d[0x230:0x460],
      "tail 0x460.. all FF:", all(b == 0xff for b in d[0x460:]))
print("blocks per copy:", 0x230 // 8, "covered bytes:", (70 - 1) * 8)

Notes on the verification: because a byte-sum is permutation-invariant, the same 0x2C0A is obtained by summing the raw copy bytes 0x000..0x227 directly; the block-reversal step is what proves the DIABLK byte order and the little-endian storage, not the sum value. No other candidate algorithm (CRC16/CRC32, XOR, sum16) is implemented anywhere in the traced save code, and none is needed: the code-derived sum matches both copies exactly. The blank cap-00 correctly fails validation (no magic), which is the expected "no save" state, not corruption.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for any payload mutation (apply per copy, or the loader will silently use the other copy): (1) edit the logical image — i.e. raw bytes at copy_base + (logical & ~7) + (7 − (logical & 7)) per byte, or equivalently block-reverse the 560-byte copy, edit, and re-reverse; (2) recompute sum8 mod 65536 over logical 0x000..0x227; (3) store it little-endian at logical 0x22E (raw: byte-swapped pair at raw copy_base+0x228); (4) leave the magic bytes untouched; (5) to force the loader onto a specific copy, additionally corrupt the other copy's magic (e.g. zero raw 0x22A..0x22F of copy 0) so FUN_0803ca54 returns -3 and FUN_0803cc8c falls back. No paired .ss save states exist in this workspace (states/ is empty), so all predictions below are for cold-boot reload observation (title/continue UI, in-game status screens, and — if an emulator with a debugger is used — the RAM mirror after FUN_0803cc8c completes). The PACKET cold-reload harness (600 frames, thumbnails) is sufficient for the UI-level predictions.
