1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The save medium is byte-addressed SRAM, 32768 bytes (0x8000), accessed through a WAITCNT-gated 8-bit copy loop that matches the real GBA SRAM hardware contract.
  • There is a 64-byte (0x40) "profile header" record stored twice — at absolute offset 0x0000 (primary) and 0x6D40 (mirror) — and the two copies are byte-identical in both .sav samples. This is a straightforward whole-record redundancy/backup scheme, not two independent save slots.
  • The header's first 8 bytes are a sum32 checksum / one's-complement pair: u32 checksum at +0x00, u32 ~checksum at +0x04. The checksum formula was reverse-derived from decompiled code and then verified byte-for-byte against all four header copies present in the two .sav files (see §4 and the Python output below). All 4/4 match.
  • A 20-byte ASCII build/version magic string, "ZeroMissionEURver005", lives at header offset +0x1C and is present, unmodified, in all four header copies. Decompiled code (0x08073620) explicitly re-copies and re-compares this exact 20-byte span against a ROM-embedded constant on every slot validation pass.
  • The low-level SRAM write primitive (0x080052b0) and the save-slot validate/commit orchestrator (0x080734cc) were located and their call relationships traced through ghidra/decompiled.c and ghidra/callgraph.json.

What remains open / unverified (honestly flagged, not guessed):

  • The two .sav samples in this workspace capture only a title-screen / language-selection state — neither contains actual in-game progress (items, map, bosses). The individual sub-byte fields inside the 64-byte header (offsets 0x0C–0x1B) are confirmed as copy destinations in code, but their semantic meaning (which in-game value they hold) cannot be determined without a gameplay sample that varies them.
  • A second, larger per-slot payload region (0x1220 = 4640 bytes per slot, referenced by dispatcher id 0x0F) is addressed in code but its absolute offset inside the 32KB SRAM image could not be pinned down statically (the base pointer is runtime-resident, not a ROM constant) and is not visible in either .sav sample because no save-file slot was actually created.
  • A 128-byte region at 0x6DC0–0x6E3F contains structured binary + ASCII content ("o_SELECT_LANGUAGE", "ENDKEY_LANGUAGE_") that changed between the two captures, but no writer for this region was found anywhere in the 89-function decompiled corpus available in this workspace. It is reported as an unresolved hypothesis, not a confirmed field.
  • ghidra/callgraph.json is demonstrably incomplete: ghidra/decompiled.c shows 0x080734cc calling 0x08073620 three times by address (func_0x08073620(0/1/2)), yet callgraph.json lists callers: [] for 0x08073620 and does not list it as a callee of 0x080734cc. All caller-chain claims below were therefore built by reading decompiled.c directly and cross-checked against callgraph.json only where the two agree; disagreements are called out explicitly.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

  • 0x080052b0 — raw SRAM byte-copy driver (write primitive).
  void FUN_080052b0(undefined1 *param_1, undefined1 *param_2, int param_3)
  {
    *_DAT_080052e8 = *_DAT_080052e8 & (ushort)_DAT_080052ec | 3;   // WAITCNT-style wait-state bits set
    while (param_3 = param_3 + -1, param_3 != -1) {
      *param_2 = *param_1;      // single-byte copy — required by real SRAM's 8-bit bus
      param_1 = param_1 + 1;
      param_2 = param_2 + 1;
    }
  }

The & mask | 3 pattern against a global 16-bit register and the strictly byte-at-a-time copy loop match the documented GBA constraint that SRAM/cart RAM at 0x0E000000 must be accessed 8 bits at a time, and that access speed is commonly tuned via the WAITCNT register (0x04000204). This is CONFIRMED_STATIC against public hardware facts (no SRAM-specific semantics were taken from third-party research — only the generic, documented GBA bus behavior).

  • Caller: 0x08005384 (per callgraph.json and source).
  • 0x08005384 — write-with-retry wrapper.
  void FUN_08005384(undefined4 param_1, undefined4 param_2, undefined4 param_3, int param_4)
  {
    for (bVar1 = 0; bVar1 < 3; bVar1 = bVar1 + 1) {
      FUN_080052b0(param_1, param_2, param_3);   // write
      param_4 = FUN_08005320(param_1, param_2, param_3); // verify-like call
      if (param_4 == 0) break;
    }
  }

Retries the byte-copy up to 3 times, stopping early on a zero result from 0x08005320. 0x08005320's own body does not simply re-read param_1/param_2/param_3 in an obvious compare loop — it manipulates unrelated global pointers and calls func_0x0808b890, so its exact verification semantics are not fully resolved here; it is reported as "read/verify-adjacent, exact mechanism UNKNOWN" rather than claimed as a definite CRC/compare routine.

  • Caller: 0x0807443c (boot-time SRAM presence/pattern check, which also calls 0x0800524c).
  • 0x08000c58 — blank-init + conditional SRAM flush.
  void FUN_08000c58(void)
  {
    uVar1 = _DAT_08000c94;                                  // save EWRAM buffer address
    func_0x08003308(3, _DAT_08000c90, _DAT_08000c94, 0x8000, 0x10); // fill 32KB EWRAM buffer with pattern
    if (*_DAT_08000c98 == '\0') {
      func_0x08005384(uVar1, 0xe000000, 0x8000);            // flush whole 32KB buffer to real SRAM
    }
  }

This is the function that proves the exact media size: it flushes precisely 0x8000 (32768) bytes to the literal address 0xe000000, matching both the real GBA SRAM window and the exact size of every .sav file in saves/. CONFIRMED_VERIFIED (code target size == observed file size).

  • Caller: 0x080734cc.

3.2 DMA-queue copy/fill helpers (generic — reused outside save code too)

  • 0x08003238(channel, src, dst, len, unit) — queues a block copy through a software DMA-request structure (_DAT_08003268 + channel*0xc), polling a busy flag before/after. Used for 0x40-byte header staging copies inside the EWRAM save buffer in 0x080734cc. Also called from non-save graphics code (0x0807f4b0, 0x080808dc), so it is a generic engine primitive, not save-exclusive — flagged so as not to overclaim.
  • 0x08003308(channel, fill_value, dst, len, unit) — queues a block fill (source address fixed, so every destination byte receives fill_value). Used by 0x08000c58 to blank the 32KB EWRAM save mirror. Also called elsewhere (0x08004ba4, 0x0807475c, 0x08075148, 0x0807f5f4) for non-save purposes (e.g. VRAM/OAM/palette clears, per the unrelated 0x6000000/0x7000000/0x5000000 destinations seen in 0x080009f4).

3.3 Save-slot dispatcher

  • 0x08000c9c(id) — a generic id-keyed dispatcher (ids 0–0x10), most of whose ids jump through an unrelated function-pointer table (_DAT_08000d1c) and are not save-specific (it is shared by 0x080744dc, 0x08074e30, 0x08074edc, 0x08075148, which appear to be unrelated engine subsystems based on their surrounding code). Two ids are save-relevant and hard-coded, under a distinct "SRAM op mode" flag (*_DAT_08000cbc != 0):
  • id 0x0E → func_0x08003308(3, uRam08000ccc, iRam08000cd0, 0x8000, 0x10) — full 32KB buffer fill/stage op.
  • id 0x0F → func_0x08003308(3, uRam08000d00, *piRam08000d04 + *pcRam08000d08*0x1220 + 0x80, 0x1220, 0x10) — per-slot (0x1220-byte) stage op, slot index taken from *pcRam08000d08.
  • Callers (from callgraph.json): 0x080733e8, 0x08073438, 0x080734cc, 0x080744dc, 0x08074e30, 0x08074edc, 0x08075148. Only the first three are argued here to be save-related, based on their own decompiled bodies; the rest are out of scope for this report (no save-specific call pattern observed in them).

3.4 Save-slot validate/commit orchestrator

  • 0x080734cc — top-level slot validate-and-commit routine.
  1. Calls func_0x08073620(0), func_0x08073620(1), func_0x08073620(2) — validates up to 3 candidate header locations (checksum, complement, and 20-byte magic string; see §4).
  2. Depending on which validations pass, stages the winning/losing header via 0x08003238 (EWRAM-to-EWRAM 0x40-byte copy) and/or calls 0x08000c9c(0)/0x08000c9c(1)/0x08000c9c(2) to push a candidate into the active in-RAM mirror used for later flushing.
  3. If none of the three validated (iVar3 == 0), calls func_0x080736bc() (out of this workspace's 89-function set — not resolvable here; left as open question).
  4. Otherwise calls 0x08000c58 (blank-init path for the "losing" slot copy) followed by 0x08003238(3, _DAT_08073618, _DAT_0807361c, 0xc, 0x10) (a 12-byte metadata copy) and finally 0x08073438 to recompute and commit the checksum.
  • How each caller mutates the in-RAM struct before flush: every path above writes into the 64-byte header living at the address pointed to by _DAT_080734c0/_DAT_08073540 (an EWRAM, 0x02xxxxxx-class, pointer per the engine's own code — the literal numeric value of that pointer is not present as a ROM constant in decompiled.c, so it is described structurally rather than with a fabricated literal address).
  • This function itself has no caller visible anywhere in callgraph.json or decompiled.c — it is presumably invoked from a save-trigger (menu confirm, autosave point) outside the 89-function subset provided in this workspace. Flagged as an open question, not guessed.
  • **0x08073620(id)** — per-slot validator, called 3× from 0x080734cc (id=0,1,2) by direct address (func_0x08073620(...)), **not** reflected as an edge in callgraph.json` (methodology caveat noted in §1).
  void FUN_08073620(char param_1)
  {
    puVar1 = ...slot-base-selector-on-param_1...;      // picks one of 3 candidate header addresses
    uVar4 = sum of 16 x u32 words starting at puVar1;  // = sum over the full 64-byte header, INCLUDING the stored checksum+complement
    bVar6 = (*puVar1 != uVar4);                        // bit0: checksum mismatch
    for (i = 0; i < 0x14; i++)
      if (puVar1[0x1c+i] != _DAT_080736b8[i]) bVar6 |= 2;  // bit1: 20-byte magic-string mismatch vs ROM constant
    if (*puVar1 != ~puVar1[1]) bVar6 |= 4;              // bit2: checksum/complement pair mismatch
    return bVar6;
  }

This function is the save reader's integrity gate: a 0 result means "trust this header"; nonzero flags exactly which of the three checks failed. Since the summed window includes the checksum word and complement word themselves, and checksum + complement is always 0xFFFFFFFF (-1 mod 2^32) for any previously-valid header, the sum of the full 64 bytes mathematically collapses to checksum == sum(bytes 0x08..0x3F as 14 LE u32 words) - 1 — see §4 for the derivation and the verification run against real bytes.

  • 0x08073438 — checksum compute + header field writer (the actual "commit" step):
  void FUN_08073438(void)
  {
    puVar7[2]  (byte @+0x08) = 0x30;                 // constant
    puVar7+9   (byte @+0x09) = 0x31;                 // constant
    *(short*)(puVar7+10) (u16 @+0x0A) += 1;           // monotonic sequence/generation counter
    *(u16*)(puVar7+3) (u16 @+0x0C) = *_DAT_080734c4;  // copied from engine source record
    byte @+0x0E = source byte (+2 of source record)
    byte @+0x0F = 1;                                  // constant
    byte @+0x10 = 0x34;                               // constant
    byte @+0x11 = source byte
    byte @+0x12 = source byte
    byte @+0x13 = source byte
    u16  @+0x14 = source u16
    u32  @+0x18 = source u32
    bytes @+0x1C..+0x2F (20 bytes) = ROM constant "ZeroMissionEURver005"
    uVar3 = sum of 16 x u32 words starting at the header base (OLD bytes, pre-overwrite);
    header[+0x00] = uVar3;         // new checksum
    header[+0x04] = ~uVar3;        // new complement
    FUN_08000c9c(0);               // triggers the stage/flush path
  }

Caller: 0x080734cc only. Callee: 0x08000c9c.

3.5 Boot-time load path

  • 0x080733e8 — boot/init entry that: (a) loops up to 3× calling 0x0807443c while a flag byte is nonzero (SRAM presence/pattern self-test, built on 0x08005384→0x080052b0), (b) loops up to 3× calling 0x08000c9c(0xE) then 0x08000c9c(0xF) until the latter returns 0 (stage the full buffer, then the per-slot buffer), then (c) calls 0x080734cc (validate/select), 0x080744dc, 0x08074bb4, 0x08075148, 0x08074edc (the latter four are not argued here to be save-specific).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • Bytes: ASCII "ZeroMissionEURver005" (20 bytes / 0x14)
  • Offset: header +0x1C (absolute 0x001C for copy A, 0x6D5C for copy B)
  • Verified in code: yes — 0x08073438 writes it from a ROM constant (_DAT_080734c8) on every commit; 0x08073620 compares it against a different-but-equal-content ROM constant (_DAT_080736b8) on every validation.
  • Verified in .sav: yes — present byte-for-byte, identically, in both header copies of both cap-00-future-0.sav and cap-01-future-1.sav.

4.2 Checksum algorithm

  • Name: header_sum32
  • Algorithm: sum32_le with a one's-complement redundancy pair (custom, derived below)
  • Stored checksum: u32 little-endian at header +0x00
  • Stored complement: u32 little-endian at header +0x04 (always ~checksum mod 2^32)
  • Covered range (as executed by 0x08073438): the full 64-byte header [+0x00, +0x40), summed as 16 little-endian u32 words, before the new checksum/complement are written (i.e. the old checksum+complement values are part of the sum).
  • Derivation to a file-verifiable formula: because any previously-valid header always has words[0] + words[1] == 0xFFFFFFFF (mod 2^32), and the sum loop includes those two words unchanged, the formula collapses to a form that can be verified purely from the final, stored bytes:

checksum = ( sum_{i=2..15}( words[i] ) - 1 ) mod 2^32

i.e. sum of the 14 little-endian u32 words covering header bytes +0x08 through +0x3F, minus 1, modulo 2^32 — independent of whatever the previous checksum happened to be.

  • Endianness: little-endian throughout (matches ARM7TDMI default / GBA ABI).
  • Decompiled C proof: ghidra/decompiled.c:2743 (FUN_08073438) for the write path; ghidra/decompiled.c:2887 (FUN_08073620) for the read/validate path.

4.3 Python verification against the real .sav files

import struct

for fname in ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]:
    data = open(fname, "rb").read()
    for base in (0x0, 0x6d40):
        blk = data[base:base+0x40]
        stored_sum  = struct.unpack_from("<I", blk, 0)[0]
        stored_comp = struct.unpack_from("<I", blk, 4)[0]
        words = struct.unpack_from("<16I", blk, 0)
        sum_excl_checksum = sum(words[2:]) & 0xffffffff   # bytes +0x08..+0x3F
        computed = (sum_excl_checksum - 1) & 0xffffffff
        print(fname, hex(base),
              "stored=%08x" % stored_sum,
              "computed=%08x" % computed,
              "match=%s" % (stored_sum == computed),
              "complement_ok=%s" % ((~stored_sum & 0xffffffff) == stored_comp))

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav (or a fresh capture), then reloaded from the corresponding gameplay.ss/paired .ss save state per the project's mandatory paired-state convention, with before/after screenshots and RAM reads of the header's live EWRAM mirror.

  1. Checksum-only corruption (negative control for bit0).
  • Mutation: flip one bit in +0x00 (e.g. XOR 0x01) without touching +0x04.
  • Requires checksum repair: no (this is the corruption).
  • Predicted effect: 0x08073620 sets bit0 (and, since +0x04 is now inconsistent with the new +0x00, also bit2) on next validation of this slot id. If the mirror copy at 0x6D40 is still intact, predict the engine falls back to the mirror and the header's visible fields (sequence counter, magic string) stay unchanged after reload; if both copies are corrupted, predict a reinit via 0x08000c58 (fields reset / blanked).
  1. Magic-string corruption, checksum repaired (isolates bit1).
  • Mutation: change one ASCII byte inside +0x1C..+0x2F (e.g. 'Z' → 'z'), then recompute +0x00/+0x04 per §4.2 so the checksum/complement pair is internally consistent again.
  • Requires checksum repair: yes.
  • Predicted effect: 0x08073620 still sets bit1 (magic mismatch) even though bit0/bit2 are clean, because the comparison in 0x08073620 is a separate 20-byte memcmp against the ROM constant, independent of the checksum. This is the key falsifiable test distinguishing "checksum validates" from "version-string validates" as two genuinely separate gates.
  1. Sequence counter rollback.
  • Mutation: decrement +0x0A by 1 (or set to 0x0000), repair checksum.
  • Predicted effect: unknown/open — no code in this workspace was found comparing the two header copies' sequence numbers against each other to pick "most recent." If such comparison exists outside the 89-function subset provided here, predict the engine would now treat the mirror copy as newer; if no such comparison exists, predict no observable effect (counter is write-only telemetry).
  1. Debug/trace region zeroing (tests load-bearing vs. cosmetic).
  • Mutation: zero out 0x6DC0–0x6E3F entirely (no checksum involved — it is outside the header's checksum domain).
  • Predicted effect: unknown/open. If gameplay/UI is unaffected after reload, this supports the hypothesis that the region is a non-load-bearing debug/trace buffer. If any menu behavior changes, it is load-bearing and needs a dedicated follow-up trace.
  1. Reserved-tail mutation (+0x30–+0x3F).
  • Mutation: set all 16 bytes to 0xAA, repair checksum (they are inside the summed domain).
