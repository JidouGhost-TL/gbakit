1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code AND .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is serial EEPROM accessed at 0x0D000000 via DMA3 (0x040000D4 block). The EEPROM read/write bitstream builders are present and readable in the decompilation (FUN_0836a048 read, FUN_0836a0f8 write, FUN_08369fc8 DMA3 transfer).
  • The serialized save image is 144 bytes (0x90): a 136-byte payload (0x00-0x87) plus an 8-byte integrity block (0x88-0x8F), transferred as 18 EEPROM blocks of 8 bytes.
  • The integrity algorithm is an additive 32-bit byte sum over payload bytes 0x00-0x87, stored together with its bitwise complement. The formula was recomputed in Python against both real .sav files and matches exactly on both (Section 4).
  • A 16-byte header at 0x00-0x0F is compared word-by-word against a ROM template by the load/validate routine (FUN_080172e8). Both samples share bytes 0x00-0x03 (PS S) and 0x08-0x0F (000 A-TR); bytes 0x04-0x07 differ (00 00 00 00 vs PMID) and therefore cannot be part of a fixed magic.
  • Bytes 0x90-0x1FF of every 512-byte .sav are unused 0xFF fill. There is a single save copy; there is no backup slot, no mirroring, and no generation/sequence counter anywhere in the image or the code.
  • The cold-reload mutation probe in PACKET.md (mutation at offset 0x4, integrity_check_confirmed: true, save rewritten after mutation) is fully consistent with the code path FUN_0801262c (verify) → FUN_080172e8 (validate-or-rewrite) → FUN_080125b4 (recompute + rewrite).

Static-only (CONFIRMED_STATIC, code seen but not observable in the two .sav snapshots):

  • The exact identities of the block-transfer thunks 0x0836a3a0 / 0x0836a3ac (unrecovered jump-table stubs) as EEPROM write-block / read-block wrappers. Their call pattern (18 iterations, 8-byte stride, index 0..17) makes the role inference strong but the thunk bodies were not recovered.
  • The record sanitizer FUN_0801744c and record sorter FUN_0801760c, which operate on a same-shaped RAM structure. Their RAM base pointers are different literal-pool slots from the serializer's base, so their offsets are mapped onto the .sav layout as hypotheses, not proof. One sanitizer clamp conflicts with an observed .sav byte if applied to the saved image (see Section 5), so these functions may sanitize a working/display copy rather than the flushed struct itself.

Open / unknown:

  • The numeric RAM mirror address of the save struct. The decompilation only exposes ROM literal-pool slots that hold the pointer (0x08012628, 0x080126a4, 0x08017330, 0x080175f4/f8); the pointed-to EWRAM/IWRAM values are not present in the workspace files. All ram_addr entries are therefore null.
  • The semantics of payload fields beyond the header and checksum (record meanings at 0x10-0x27, settings bytes near 0x78-0x80, and the large zero region 0x28-0x87). The two snapshots differ in only 8 bytes, so almost no field semantics can be verified from data alone.
  • The ROM template bytes at 0x08017378 compared by FUN_080172e8 (the ROM itself is not in the workspace).

Geometry note: EEPROM on GBA is not memory-mapped as a linear array. The game transfers the image in 8-byte blocks (the EEPROM block size for this device class): the writer loops block indices 0..16 over the payload with an 8-byte pointer stride, then writes block 17 containing the two checksum words; the reader loops block indices 0..17. The .sav file is the emulator's linear dump of the EEPROM contents in block-address order, which is why file offsets equal serialized-struct offsets for the payload (proven by the checksum matching the raw file bytes in order).

Byte-order caveat (verified): the integrity block appears byte-reversed in the .sav relative to the little-endian RAM layout the code writes (Section 4). This is a property of the serial EEPROM transfer (the read builder FUN_0836a048 reassembles each block's four 16-bit words in reverse order), and it does not affect the payload checksum because addition is order-independent. It does mean a save editor must treat offsets 0x88-0x8F as reversed when patching a raw .sav.

3. Save Writer, Reader & Caller-Chain Architecture

Address-space summary: 0x080xxxxx functions are ARM code in the main ROM bank; 0x0836xxxx functions are Thumb code in a later ROM bank containing the EEPROM support library. DMA3 registers (0x040000D4 SAD, 0x040000D8 DAD, 0x040000DC CNT_L, 0x040000DE CNT_H) appear throughout the decompilation under Ghidra names uRam040000d4/d8/dc/de. WAITCNT (0x04000204) is never touched (0 matches), consistent with EEPROM not needing SRAM wait-state setup. No code touches 0x0E000000 (SRAM/Flash) and no Flash 0x5555/0x2AAA command sequence exists (0 matches each), ruling out SRAM/Flash save media.

3.3 Caller chains (how each caller was mapped, and how it mutates the RAM struct before flushing)

Mapping method: every chain below was traced by (1) taking the caller/callee edges from ghidra/callgraph.json, (2) reading the full body of each function in ghidra/decompiled.c (not just search hits), and (3) cross-checking argument flow (block index, base pointer, mode flags) at each call site. Where Ghidra lost a return value or a literal pointer value, that limitation is stated instead of guessed.

  1. Boot/init chain: FUN_08000368 → FUN_08000494 (hardware init, programs DMA3 once for a font/tile upload), FUN_0801195c (zeroes a 16-byte control block, then generic DMA3 FUN_08000d34 with length 0x1040), FUN_08011734 (starts a periodic DMA via FUN_08000cfc, length 7), FUN_08012578 (stores a u16 pair — likely EEPROM configuration, static-only). None of these write the save struct; they establish that the traced boot path reaches the game without an explicit save load, so the load must be triggered from an untraced caller of FUN_08016dbc/FUN_080172e8 via an unrecovered jump table. The call graph confirms FUN_080172e8, FUN_08017410, and FUN_08017054 have no recovered callers — their invocation is through indirect jumps Ghidra could not resolve.
  2. Load-or-initialize chain: FUN_08016dbc → FUN_080172e8 → (FUN_0801262c load+verify, header compare) or (FUN_080008b0 DMA + FUN_080125b4 rewrite). FUN_08016dbc first zeroes a field block, sets defaults (puVar1[8] = 1, byte at +0xF = 1), calls FUN_080172e8, and afterwards copies five fields out of the loaded struct area (iRam08016e80 + 0x68/0x6A/0x6C/0x78/0x79) into the live game struct (+0x1C, +0x19, +0x18, +0x10, +0xF). This is the one place where loaded save bytes demonstrably flow into gameplay state; the copied source offsets 0x68-0x79 fall inside the payload's otherwise-zero region, which is consistent with both snapshots having zeros there (a fresh/default profile). Confidence: CONFIRMED_STATIC for the copy mechanics, HYPOTHESIS for identifying iRam08016e80 with the serializer's base, since both are unrecovered literal pointers.
  3. Explicit save chain: FUN_08017054 → FUN_08016dbc (above) → FUN_08011990 (enqueues a DMA3 transfer descriptor via FUN_08000d34, length 0x48). FUN_08017054 itself has no recovered caller; it is a two-call sequencer, likely invoked per frame or on a state transition through a jump table.
  4. Dispatcher save path: FUN_08017410 (argument 0) → FUN_0801744c (sanitize: clamps record fields, counters, and mode bytes in the working struct) → FUN_0801760c (sorts the three 8-byte records by their +6 key) → FUN_080125b4 (recompute checksum, write 18 blocks). This is the only chain that mutates payload fields immediately before flushing: sanitization forces out-of-range bytes to defaults and sorting reorders the records at 0x10-0x27. Note the conflict flagged in Section 5: the sanitizer's record byte +1 clamp would rewrite the observed value 0xF4 at file offset 0x11, so either this chain was not the writer of the captured saves, or it sanitizes a different working copy than the flushed struct.
  5. Dispatcher load path: FUN_08017410 (argument non-zero) → FUN_0801262c only. No field mutation; failure (-1) is returned to the untraced caller.
  6. EEPROM library chains (Thumb bank): FUN_080125b4 → 0x0836a3a0 → (inferred) FUN_0836a0f8 → FUN_08369fc8 (DMA3 to 0x0D000000) + FUN_08369efc/FUN_08369f84; FUN_0801262c → 0x0836a3ac → (inferred) FUN_0836a048 → FUN_08369fc8; FUN_0836a1d4 → FUN_0836a048 (read-compare, no traced caller — likely the body behind 0x0836a3ac or a verify-after-write step). The (inferred) edges are the only non-proven links in the architecture; everything above and below them is directly decompiled.

How the in-RAM struct is mutated before flushing, summarized: gameplay-side writes land in the RAM struct during play (untraced jump-table callers); on save, FUN_0801744c clamps and FUN_0801760c sorts (dispatcher path only); FUN_080125b4 then derives the two checksum words from the final payload bytes and writes all 18 blocks. On load, FUN_0801262c fills the struct from EEPROM, FUN_080172e8 validates header + checksum, and FUN_08016dbc copies selected fields into live game state. No caller encrypts, compresses, or transforms payload bytes — the file image is a byte-for-byte dump of the RAM struct payload (proven by the raw byte sum matching).

4.2 Checksum algorithm (exact)

  • Algorithm: additive 32-bit byte sum (sum32, reported as sum16_le-family in the JSON enum sense: a plain unsigned byte sum kept in a 32-bit accumulator; values here fit in 16 bits).
  • Formula: sum = Σ data[i] for i in [0x00, 0x88), computed in RAM as the initial byte plus 0x87 (135) following bytes = 136 bytes total. complement = ~sum (bitwise NOT, 32-bit).
  • Covered range: file/struct offsets 0x00 inclusive to 0x88 exclusive (the whole payload, header included).
  • Stored offsets (RAM struct, little-endian u32 stores in code): sum at 0x88, complement at 0x8C.
  • Stored offsets (raw .sav): the 8-byte block is byte-reversed relative to RAM — offset 0x88 holds the complement as a big-endian u32, offset 0x8C holds the sum as a big-endian u32. Equivalently, .sav[0x88:0x90] == reverse(struct.pack('<I', sum) + struct.pack('<I', ~sum & 0xFFFFFFFF)), verified true on both files.
  • Decompiled proof (writer, FUN_080125b4): after the 17-block write loop, uVar6 = (uint)*pbRam08012628; iVar4 = 0x87; do { uVar6 += (byte)*next; } while (...) then *puVar7 = uVar6; *(uint *)((int)puVar8 + 5) = ~uVar6; followed by the block-17 write. (Verifier, FUN_0801262c): identical summation, then if ((uVar8 == *(uint *)(p + 1)) && (~uVar8 == *(uint *)(p + 5))) return 0; else return -1; (Ghidra renders the +0x88/+0x8C word pointers as byte offsets +1/+5 from the last payload byte pointer — the arithmetic is over the same two stored words).
  • Endianness note: the GBA CPU is little-endian and the code's RAM stores/comparisons are little-endian u32. The big-endian appearance in the file is produced by the serial EEPROM block transfer (see FUN_0836a048 reassembling words in reverse order). A save editor working on the raw .sav must use the big-endian/reversed form; a tool patching the RAM image must use little-endian at the same offsets.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for any payload mutation at offsets 0x00-0x87: recompute sum = Σ bytes[0x00:0x88] mod 2^32, then write big-endian ~sum at 0x88 and big-endian sum at 0x8C (equivalently write the byte-reversal of pack('<I', sum) + pack('<I', ~sum) into 0x88-0x8F). Mutations without this repair test the rejection path; mutations with repair test field semantics. No paired .ss save states exist in this workspace (states/ is empty per PACKET.md), so each test below names the observable to capture once states are available: the re-flushed .sav bytes, the loaded RAM struct, and the gameplay/UI state on cold reload.
