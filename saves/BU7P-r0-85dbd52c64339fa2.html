1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is a 512-byte EEPROM (EEPROM 4K = 4 Kbit), accessed as 64 blocks of 8 bytes through a serial DMA3 bitstream. Configured by FUN_0800b42c → FUN_08052124(4), read by FUN_080521ec, written by FUN_080522c0 via FUN_080522ac, verified by FUN_08052450, all on top of the DMA helper FUN_0805216c.
  • The 512 bytes tile exactly as: a 16-byte global header at 0x00, six 80-byte (0x50) profile slots at 0x10 + n·0x50, and a byte-identical header mirror at 0x1F0 (16 + 6·80 + 16 = 512). Both .sav files show this: only offsets 0x00–0x0F and 0x1F0–0x1FF are non-zero, they are identical within each file, and all six slots are all-zero in both samples.
  • The header magic is the 8 ASCII bytes 010EABGS at offset 0 of each header copy, present verbatim in both files and checked byte-by-byte (8 iterations) in FUN_08045874 after the checksum passes.
  • The integrity algorithm is a negated 16-bit sum: FUN_080457f4 sums len/2 16-bit words and every writer stores -sum in the last word of the record (header byte offset 0x0E, slot byte offset 0x4E), so a valid record sums to zero — which is exactly the test in FUN_08045780 / FUN_08045874. On the .sav file bytes this verifies as a big-endian-per-word sum (see §4 for the byte-lane discussion and the failing little-endian control).

Static-only (CONFIRMED_STATIC, code-proven, not observable in the samples):

  • The full writer/reader/repair architecture (§3), the 3-logical-profile × primary+backup slot pairing (physical slot i pairs with i±3), the boot-time load-or-rebuild flow, and the header field writers in FUN_0802d310 / unpacker FUN_0802d64c.
  • Slot payload byte 0–7 (an 8-byte descriptor unpacked by FUN_0802d670) and the slot checksum at slot+0x4E.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • Semantics of header bytes 8–13 (they are packed from a live game-state struct at offsets +0x15…+0x1B; byte 10 is an index < 6, plausibly a language index on this 6-language European build — unproven).
  • Almost everything inside a non-empty slot: both samples have all six slots zeroed, and the function that packs live gameplay state into the 80-byte slot buffer, func_0x0802d40c (called from FUN_08045690), is not present in the 280-function corpus. Slot payload bytes 8–77 are therefore UNKNOWN.
  • Absolute RAM addresses: every global is reached through a literal-pool _DAT_080xxxxx symbol whose stored value (a 0x02xxxxxx/0x03xxxxxx address) is not included in ghidra/decompiled.c, so RAM mirrors are identified by struct offset, not by address.
  • No caller exists in the corpus for the top-level entry points FUN_08045454 (save-system init) and FUN_0803d208 (header sync trigger); they are presumably invoked through function-pointer/state-machine tables that Ghidra left as UNRECOVERED_JUMPTABLE.

Slot address formula (from FUN_080457ac / FUN_080457d0): EEPROM offset = 0x10 + slot_index · 0x50, size 0x50. There are 3 logical profiles, each stored twice: logical profile p ∈ {0,1,2} lives at physical slot p (primary) and p+3 (backup). This pairing is explicit in FUN_080450c4 (writes p then p+3) and in FUN_08045288 (repairs slot i from slot i+3 or i−3).

Redundancy and selection rules

  • Header: two identical copies (0x00, 0x1F0). At boot, FUN_08045818 (via FUN_08045874(buf, block), EEPROM offset = block << 3) tries the primary (block 0 → 0x00) first: if its word-sum is zero and its first 8 bytes match the reference magic, it is accepted and copied over the RAM backup half (puVar1[4..7] = puVar1[0..3]). Otherwise the mirror is read into the RAM backup half (FUN_08045874(buf+4, 0x3E), 0x3E << 3 = 0x1F0); if that validates, a flag byte is set and the backup is copied back over the RAM primary (*puVar1 = puVar1[4], etc.). If neither validates, FUN_08045818 returns 0 and the caller rebuilds everything from scratch (§3).
  • Header write-back: FUN_08045360 reads both EEPROM copies, recomputes the RAM header checksum, and if the RAM header differs from either copy in any of its four 32-bit words it rewrites both copies from RAM (FUN_0800b3b4(0,…), then FUN_0800b3b4(0x1F0,…)). If both already match, it writes nothing.
  • Slots: every slot write goes to both copies (FUN_080450c4: FUN_080457d0(p), FUN_080457d0(p+3), then reads both back with FUN_080457ac). At boot, FUN_08045288 reads and checksum-validates all six physical slots (with one retry each); a slot whose checksum fails is repaired by copying its pair's EEPROM contents over it (read pair, write slot, mark valid, deserialize its descriptor), and slots that remain invalid get a zeroed 8-byte descriptor. There is no generation/sequence counter anywhere in the code or the samples: selection is purely "primary if valid, else backup; rewrite both on any mismatch". The only candidate counter-like header bytes (8 and 12) change in opposite directions (+3/−3) between the two samples, which is the behaviour of checksum-coupled or paired settings bytes, not of a monotonic generation counter (§5).
  • The cold-reload probe in the packet (mutation at 0x8, integrity_check_confirmed: true, save_rewritten_after_mutation: true, reverted_to_blank_on_mutation: false) is consistent with this design: a mutated header fails the load validation / RAM-compare and is rewritten from the surviving copy or RAM state rather than blanking the save.

3.3 ALL callers traced, and how each mutates the in-RAM structures before flushing

The in-RAM structures are: (a) the 32-byte header area (primary at +0, mirror at +16) reached as _DAT_080453f4 / _DAT_0804544c / _DAT_0804583c / _DAT_0802d364 in different functions (the literal-pool values are unavailable, but the functions only make sense as one shared buffer: FUN_0802d310 mutates it and immediately flushes it through FUN_08045360, and FUN_08045818 maintains exactly its two 16-byte halves); and (b) the save-manager struct whose +0x20 slot-buffer pointer, +0x24 descriptor array, +0x54 validity bytes, +0x5C cursor, +0x60 flag, +0x64/+0x68 usage stats are used consistently across FUN_080450c4–FUN_08045874. Absolute RAM addresses cannot be recovered from this corpus (ram_addr: null in the JSON).

  1. FUN_08045454 → FUN_08045818 → FUN_08045874 → FUN_0800b34c → FUN_080521ec → FUN_0805216c (boot header load; B+C). Mutates RAM only by loading: fills one or both 16-byte halves of the header area from EEPROM. No EEPROM write.
  2. FUN_08045454 → FUN_08045404 → FUN_0800b3b4 → FUN_080522ac → FUN_080522c0 → FUN_0805216c (+ verify FUN_08052450 → FUN_080521ec) (default header creation; B). Mutates the RAM header by copying the ROM template over it and overwriting byte 0x0E–0x0F with -sum, then flushes that exact 16-byte image to offsets 0x00 and 0x1F0.
  3. FUN_08045454 → FUN_080450c4(p, 1) → FUN_08045690(1) → FUN_080457d0(p), FUN_080457d0(p+3) (empty-profile creation; B+C). With flag = 1 the packer is skipped, so the RAM slot buffer stays all-zero and FUN_08045690 stores -sum = 0 at slot+0x4E: a fresh slot is 80 zero bytes — exactly what all six slots in both .sav samples contain. After write/read-back, FUN_080450c4 also writes the logical index into header byte 11 (low bit preserved).
  4. FUN_08045454 / FUN_0802d310 → FUN_08045360 → FUN_0800b34c / FUN_0800b3b4 (header flush; B+C). Mutates only the two checksum halfwords of the RAM header (+0x0E, +0x1E) before the word-compare and conditional rewrite of both EEPROM copies.
  5. FUN_0803d208 → FUN_0802d310 → FUN_08045360 (the only traced gameplay-side header writer; B+C). FUN_0803d208 first copies a byte from its own state struct (+8, checked < 6) into the shared state byte at +0x1B and applies it via FUN_0804b45c (a < 6-entry jump-table dispatcher, plausibly language selection). FUN_0802d310 then packs six state bytes into the RAM header (see the field table in §5 for the exact per-byte formulas), copies the primary half over the RAM mirror (puVar1[4..7] = puVar1[0..3]), brackets the flush with FUN_08049990/FUN_0804999c, and calls FUN_08045360, which recomputes the checksum and rewrites both EEPROM copies if anything changed. This chain is the writer responsible for the header differences between the two samples (bytes 8 and 12 change; §5).
  6. FUN_0802d5bc → FUN_0802d64c (header unpack; B). FUN_0802d64c is the exact inverse of FUN_0802d310's packing: state+0x19 ← header byte 9, state+0x18 ← byte 8, state+0x1A ← byte 13 >> 6, state+0x1B ← byte 10, state+0x15 ← (low byte of the halfword at header+0x0C). It never reads byte 11 — consistent with byte 11 being a write-side marker (validity/active-slot bits) rather than a settings byte. FUN_0802d5bc has no caller in the corpus.
  7. FUN_08045454 → FUN_08045288 → FUN_080457ac / FUN_08045780 / FUN_080457d0 / FUN_0802d670 → FUN_0804554c (boot slot load/repair; B+C). Mutates the shared 80-byte RAM slot buffer by loading each physical slot in turn, the validity bytes at manager+0x54+i, and the 8-byte descriptors at manager+0x24+i·8; writes EEPROM only when repairing a bad slot from its pair.
  8. Slot write path with live data: FUN_080450c4(p, 0) (only traced caller passes 1; a 0 caller is expected from gameplay but is outside the traced corpus) → FUN_08045690(0) → func_0x0802d40c() (missing function) packs live state into the RAM slot buffer through the +0x5C cursor, FUN_08045690 stamps the checksum at slot+0x4E, and the write/read-back/verify sequence of chain 3 flushes both physical copies.

Caller-mapping caveat: ghidra/callgraph.json agrees with the body-scan for the core edges (FUN_08045360, FUN_08045404, FUN_08045288, FUN_080450c4, FUN_0805216c, FUN_080521ec, FUN_08052450) but omits most func_0x… (tail-call-style) references, e.g. all callees of FUN_0800b34c, FUN_080457f4, FUN_08045818, and every caller of FUN_08045454, FUN_0803d208, FUN_0802d5bc. Those gaps are reported as open questions, not filled by guessing.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Bytes (both header copies, both files): 30 31 30 45 41 42 47 53 = ASCII 010EABGS at EEPROM offsets 0x00 and 0x1F0.
  • In code: FUN_08045874 compares the first 8 bytes of a freshly read header copy against a reference buffer, byte by byte, but only after the word-sum test passes; FUN_08045404 obtains the same 8 bytes by copying the 16-byte ROM template (_DAT_08045450) that is also the source of every default header. The literal template bytes are not present as text in ghidra/decompiled.c (they live behind a _DAT_ pointer), so the magic is verified_in_sav: true and verified-in-code by the compare/template-copy logic, not by a readable string literal. Confidence: CONFIRMED_VERIFIED for the byte value, CONFIRMED_STATIC for the exact code path.

Checksum — exact formula

From FUN_080457f4 (checksum core), FUN_08045404, FUN_08045360, FUN_08045690 (writers), and FUN_08045780 / FUN_08045874 (validators):

sum(buf, len)   = ( Σ buf[i]  for i in 0 .. len/2-1 )  mod 2^16     // buf[i] = i-th 16-bit word
stored          = (-sum with the stored field zeroed) mod 2^16
stored offset   = len - 2        // header: byte 0x0E; slot: byte 0x4E (80-byte record)
covered range   = the whole record, with the stored field treated as zero
validity test   = sum over the whole record (stored field included) == 0 (mod 2^16)

There is no seed, no complement beyond the two's-complement negation, no CRC table, and no second checksum function anywhere in the corpus. The same routine covers the 16-byte header (len = 0x10) and the 80-byte slot (len = 0x50, checksum at slot+0x4E, confirmed by FUN_08045690 zeroing +0x4E before summing and by FUN_08045780 validating the full 0x50).

Byte-lane caveat (important, and verified by the control test below): in the code the sum is over native (little-endian) halfwords read from RAM, but on the emulator .sav bytes the identity only holds when each 16-bit word is taken big-endian (i.e. the two bytes of each word swapped). The serial EEPROM driver explains the swap direction: FUN_080522c0 extracts write data LSB-first per halfword while FUN_080521ec reassembles read data MSB-first into reverse word order, so the EEPROM bitstream does not preserve the RAM byte-lane order that a plain SRAM dump would. The stored checksum halfword itself (09 09) is byte-palindromic in both samples, so it cannot distinguish the lanes on its own; the covered words can, and they decide unambiguously for the swapped interpretation (little-endian total is 0x00FE ≠ 0 on all four header copies). The file-level algorithm reported in save-format.json is therefore custom: sum of byte-swapped (file-order big-endian) 16-bit words, negated, stored at offset 14.

A second, weaker identity also holds on both samples — (-sum of bytes 0..8) mod 256 == byte 12 — but this is not reported as a separate checksum: no byte-sum routine exists in the code, and the identity is implied by the word-sum identity above plus the constant bytes (it constrains the same single degree of freedom that changed between the samples, byte 8 vs. byte 12, which carry equal weight 256 in the big-endian word sum). With only two samples differing in exactly those two bytes, a dedicated sum8 at byte 12 cannot be distinguished from the proven sum16 at byte 14; the code proves the latter and contains no trace of the former.

Checksum repair recipe (needed by §6): zero bytes 14–15 of a header copy, interpret the 16 bytes as eight big-endian u16 words, compute (-sum) mod 65536, store it big-endian at bytes 14–15; do the same for both copies at 0x00 and 0x1F0. For a slot: zero slot bytes 78–79, sum the 40 file-order big-endian u16 words, store the negation at slot+78, and write the result to both physical copies of the logical profile.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so every test below is phrased as: edit the .sav, cold-boot the ROM with that EEPROM image, and observe (a) the EEPROM image after boot (rewritten or not, and to what), (b) the title/options/profile UI, and (c) if a debugger is available, the RAM header area and the manager validity bytes at manager+0x54+i. The packet's existing probe already supplies the control result for test 1's no-repair variant: mutating offset 0x8 led to an integrity failure and a rewrite, not a blank save.

Checksum repair (from §4): zero bytes 14–15, sum the eight file-order big-endian u16 words, store (-sum) mod 65536 big-endian at bytes 14–15, and apply the identical edit to the mirror copy at 0x1F0 unless the test specifically targets copy selection. For slots, do the same over the 40 words of the 80-byte slot with the field at slot+78 zeroed, and write both physical copies (p and p+3) unless stated otherwise.
