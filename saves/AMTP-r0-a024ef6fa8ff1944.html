All findings below are derived only from these .sav bytes, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and standard GBA hardware facts (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000, WAITCNT 0x04000204). 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM-LOW.

What is proven (CONFIRMED_VERIFIED, matched against both static code and real .sav bytes):

  • The cartridge uses battery-backed SRAM, 32,768 bytes, accessed by raw byte-copy (no Flash sector-erase commands, no EEPROM DMA3 serial bitstream observed anywhere in the traced functions — consistent with plain SRAM, not Flash/EEPROM).
  • A 32-byte header/version block is present twice, byte-identical, at offset 0x0000 and offset 0x7100, in both samples. It decodes to a 4-byte opaque constant, an ASCII tag VF01, two flag/version bytes, and a 20-byte ASCII build string AGBMetroid_USVerE004.
  • A 128-byte block at 0x7040–0x70BF, sandwiched between the two header copies, is blank (all 0x00) in the first capture and populated in the second capture with a literal ASCII tag-delimited record: ...STARTKEYLANGUAGE + 1 payload byte (0x02) + ENDKEY_LANGUAGE_ + zero padding. This is the only region that differs between the two samples (39 bytes changed, all inside 0x7040–0x7066).
  • The GBA hardware-level SRAM write driver cluster (FUN_08004bf0/FUN_08004c54/FUN_08004cc4/FUN_08004d28) is identified and traced: raw byte-copy to/from 0x0E000000, wrapped in a write-then-read-back-verify retry loop (3 attempts).

What remains open (HYPOTHESIS / UNKNOWN):

  • The exact meaning of the 0x02 byte sandwiched inside the STARTKEYLANGUAGE…ENDKEY_LANGUAGE_ tag (plausibly a language-selection index, given the title region En,Fr,De,Es,It) is a hypothesis only — we have a single non-blank sample, so we cannot cross-validate the value against a different language selection.
  • The decompiled self-validating checksum writer/reader pair (FUN_0807eebc / FUN_0807f078) does not match the byte layout actually observed at 0x7040 in cap-01-future-1.sav (proven below in §4 by a failed invariant check). So the true checksum/integrity mechanism protecting the observed STARTKEYLANGUAGE block, if any, is UNKNOWN.
  • The opaque 4-byte constant at the start of each header copy (BE D7 A9 B9) is static across both samples; its purpose (fixed build-time magic vs. some other constant) is UNKNOWN.
  • Whether the 32KB SRAM image holds additional slots/fields that simply weren't touched by these two early checkpoints is UNKNOWN — only 3 of 32,768 bytes-worth of ranges are non-blank in either sample.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM addresses (0x08xxxxxx); all are flagged mode=thumb candidate only by Ghidra and contain UNRECOVERED_JUMPTABLE tail-call warnings, meaning the end of every function's control flow (and sometimes its true callers) is not fully statically recoverable. This caveat applies to every claim in this section.

3.3 How each caller mutates the in-RAM struct before flushing

Because every one of these functions is candidate only with unrecovered jump tables, Ghidra could not resolve the absolute addresses of the IWRAM/EWRAM mirror structs (they appear as _DAT_0807ef1c, puRam0807f040, etc. — globals Ghidra could not bind to a concrete 0x02xxxxxx/0x03xxxxxx address). What is visible:

  • FUN_0807eebc writes into its target buffer before checksumming: a byte at +0x02, a byte at +0x09, a byte at +0x0A copied from an external source, a flag byte at +0x0B, and a 20-byte block copied into +0x0C..+0x1F from a second external source (_DAT_0807ef24). These are plausibly: a two-digit text/version field (0x30='0', 0x31='1' literal ASCII digits), a copied status/flag byte, an "is-dirty" flag, and a 20-byte sub-record (player name, timer, or similar) — but none of this maps onto the actual 128-byte block we can see in the .sav files (see §4), so these are HYPOTHESIS, not verified mutation semantics.
  • FUN_0807ef28 mutates up to three local 3-word staging structures (puVar1/puVar4) by copying fields out of whichever slot status was good into a "working" struct, before calling FUN_08000c60 (full flush) and FUN_0807eebc (slot re-write). This is consistent with a "repair the save by majority vote across 3 redundant copies" pattern, but the exact in-RAM struct addresses are unresolved.

4.2 STARTKEYLANGUAGE / ENDKEY_LANGUAGE_ tag block (CONFIRMED_STATIC presence, HYPOTHESIS semantics)

Block at 0x7040–0x70BF (128 bytes), blank in cap-00-future-0.sav, populated in cap-01-future-1.sav:

1f 01 0a 99 f5 66 53 54 41 52 54 4b 45 59 4c 41 4e 47 55 41 47 45 02 45 4e 44 4b 45 59 5f 4c 41
4e 47 55 41 47 45 5f 00 00 ... (zero-padded to 128 bytes)

Decoded: 4 opaque bytes (1F 01 0A 99), 1 opaque byte (F5), ASCII "f", ASCII "STARTKEYLANGUAGE" (16 bytes, abs 0x7046–0x7055), one payload byte 0x02 (abs 0x7056), ASCII "ENDKEY_LANGUAGE_" (16 bytes, abs 0x7057–0x7066), then zero padding to the end of the 128-byte block.

This is a literal STARTKEY<name>…value…ENDKEY_<name>_ bracket — a pattern consistent with a generic in-house/SDK debug-dump macro that labels a named variable with start/end tags around its value, which this build appears to have left active. It brackets a single byte whose only plausible semantic link (given the title's En,Fr,De,Es,It region) is a language-selection index — 0x02 would be the third entry if 0-indexed (En=0, Fr=1, De=2, Es=3, It=4, i.e. German). This is a hypothesis: we have only one non-blank sample, so we cannot confirm the byte tracks the language selector rather than something else incidentally also named "LANGUAGE".

The 4 opaque bytes (1F 01 0A 99) and 1 opaque byte (F5) preceding the ASCII tag do not correspond to any offset covered by the traced FUN_0807eebc/FUN_0807f078 checksum pair's buffer layout (that pair expects its own checksum words at +0x00 and +0x04 of its buffer, and fixed bytes 0x30/0x31 at +0x02/+0x09 — none of which appear at these offsets). Their purpose is UNKNOWN.

4.3 Self-validating checksum pair (FUN_0807eebc / FUN_0807f078) — verified NOT to match the observed bytes

Algorithm as decompiled: for a 128-byte (32×u32) little-endian buffer, the writer (FUN_0807eebc) zeroes word 0, sets word 1 to 0xFFFFFFFF, then computes sum = Σ(all 32 words) (a plain 32-bit wrapping sum, no carry propagation beyond 32 bits) over the buffer including the just-zeroed/filled words 0–1, and finally stores word0 = sum, word1 = ~sum. Because x + ~x == 0xFFFFFFFF exactly for any 32-bit x, this creates a self-checking invariant: for a valid, unmodified buffer, re-summing all 32 words as stored (reader FUN_0807f078) must reproduce the stored word0 value, and separately word1 must always equal ~word0.

Python verification against the actual .sav bytes (saves/cap-01-future-1.sav, offset 0x7040):

word0 @ 0x7040 = 0x990a011f
word1 @ 0x7044 = 0x545366f5
~word0         = 0x66f5fee0   (expected to equal word1 if this writer produced this block)
identity holds (word1 == ~word0)?  False

Conclusion: the checksum algorithm traced in FUN_0807eebc/FUN_0807f078 does NOT describe the data actually present at 0x7040 in either sample. Either:

  1. this function pair's three redundant 128-byte candidate slots live at SRAM offsets our two early-game captures never populated (most likely — these are "future-0/1" checkpoint captures, plausibly very early in the game, and the STARTKEYLANGUAGE block may simply be a separate, smaller config write that happens before any real slot is ever serialized), or
  2. the 0x7040 block was produced by a writer outside the 88-function/5-seed trace set entirely.

No simple checksum (sum8/sum16/sum32 over the tag payload, with or without the 4-byte prefix, in either byte order) reproduces the stored prefix bytes 1F 01 0A 99 either (all combinations tested — see raw session output). The true integrity mechanism (if any) protecting the STARTKEYLANGUAGE block is UNKNOWN.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this packet's states/ directory (0 states shipped — "legacy checkpoint cohort"), so none of the following can be executed yet; this is a plan for the next capture round, to be run once paired pre/post .ss states are attached to future .sav snapshots for this release key.

  1. Language-byte hypothesis test (0x7056).
  • Mutation: flip 0x02 → 0x00, 0x01, 0x03, 0x04 in turn (covering all 5 EFIGS indices).
  • Requires checksum repair: unknown — no verified checksum covers this offset (see §4.3), so no repair step is currently defined. Record whether the game crashes/rejects the save on load, which is itself evidence for or against an unverified integrity check existing over this region.
  • Predicted effect (if hypothesis correct): in-game text language changes to match the new index on next boot/load. If the byte is unrelated, no visible effect, and the tag content may simply be re-written verbatim on next save (compare pre/post .sav bytes to see if the engine "heals" the value).
  1. Tag-prefix mutation (0x7040–0x7045, the opaque 4+1+1 bytes before STARTKEYLANGUAGE).
  • Mutation: zero all 6 bytes; separately, randomize them.
  • Predicted effect: if these bytes are a length/counter guarding the tag, the game should detect corruption and re-initialize or skip the block on load; if they are inert, no observable effect at all — either outcome is informative about whether an unverified writer actually checks them.
  1. Full-block corruption probe (0x7040–0x70BF, all 128 bytes).
  • Mutation: fill the entire block with 0xFF (restoring it to the "blank" cap-00 appearance) on a save captured from a state where the block was previously populated (cap-01-like state).
  • Predicted effect: tests whether the game can tolerate loss of this block entirely (e.g. falls back to a default language) or treats it as fatal corruption — this also indirectly tests the "which slot/offset does FUN_0807ef28's 3-way redundant checksum scheme actually protect" open question from §3–4, since if this block is one of those 3 candidate slots, the game's slot-repair logic (majority vote across the other 2) should kick in and visibly rewrite this block from a different in-RAM copy on the next save.
  1. Header-mirror divergence probe (0x0000–0x001F vs 0x7100–0x711F).
  • Mutation: corrupt only one of the two identical 32-byte header copies (e.g. flip the VF01 tag to VF00 at 0x0000 only, leaving 0x7100 intact), from a fresh/restore state.
  • Predicted effect: if a selection/fallback rule exists (per the open question in §2), the game should still boot normally using the intact copy, and ideally repair the corrupted one on next save. If no such rule exists, this is the first concrete evidence the two copies are not actually cross-validated at runtime.
  1. Full-save wipe regression control.
  • Mutation: overwrite the entire 32,768-byte image with 0xFF (matching the ROM's own fill byte) and boot.
  • Predicted effect: clean "no save data" first-boot state — this is the negative control confirming our fill-byte assumption and confirming none of the above probes accidentally depend on data outside the 3 active ranges identified in §2.

Each mutation above should be run from a matched-duration fresh boot and a matched-duration restore-from-state control, per the standing falsifiable-hypothesis/matched-duration-control requirement, with both pre- and post-mutation .ss states retained (bounded to the aggregate screenshot/state caps already in force for this project).
