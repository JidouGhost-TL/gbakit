1. Executive Summary & Overall Confidence

Overall Confidence: LOW–MEDIUM

What is proven (code + bytes agree):

  • The cartridge uses GBA EEPROM save media, accessed through the standard EEPROM-over-DMA3 serial protocol (0x0D000000 address-space port driven by DMA3 control register writes with the enable/busy bit, matching the generic SDK pattern seen in ghidra/decompiled.c).
  • The save file is exactly 512 bytes = 64 × 8-byte EEPROM blocks, consistent with a "4K" (64-block) EEPROM device and with the PACKET's declared media.
  • The real (non-blank) .sav snapshot (cap-01-future-1.sav) contains data in exactly 4 fixed-stride 16-byte "slot" regions, each slot built from two consecutive 8-byte EEPROM blocks, spaced 20 blocks (160 bytes) apart: blocks (0,1), (20,21), (40,41), (60,61). This stride/slot geometry is directly measured from the byte-level diff/hexdump evidence, not assumed.
  • cap-00-future-0.sav is uniformly 0xFF (factory-erased EEPROM state), confirming the baseline/blank state before any writes.
  • A 4-byte sequence 9F C2 3F 21 recurs byte-identically in the second block of 3 of the 4 slots (blocks 1, 21, 41). The 4th slot's second block (block 61) is still fully erased (0xFF×8), i.e. not yet written — this is strong evidence that a logical "slot save" is split into two independent, non-atomic 8-byte DMA3 writes (first block, then second/trailer block), and this capture caught the cartridge mid-sequence on the 4th slot.
  • Slot 0's first block differs from slots 1–3 and contains the byte sequence C0 DE 60 0D at offset 0x04–0x07 — a recognizable hex-speak constant (C0DE/600D) strongly suggestive of a deliberate magic/sentinel value, consistent with slot 0 functioning as a header/selector record distinct from the payload slots.

What is NOT proven (open / unverifiable with the given corpus):

  • No checksum or serialization routine was found anywhere in the 224-function decompiled trace. Only the low-level EEPROM bit-serial I/O driver (read/write/verify) is present (§3). The game-specific code that assembles the in-RAM save struct and decides what to write was not captured by the trace-guided extraction, and ghidra/callgraph.json confirms the EEPROM driver's top-level entry point (FUN_0802f69c) has zero traced callers in this function set.
  • The recurring trailer 9F C2 3F 21 cannot be a checksum of the preceding slot bytes under any ordinary algorithm, because the preceding 12 bytes differ between slot 0 (FF FF 00 01 C0 DE 60 0D 00 00 00 00) and slots 1–2 (00 00 6E 06 00 00 00 00 00 00 00 00) while the trailer stays constant (verified by brute-force sum8/sum32/CRC32/Adler32 checks in §4 — none matched). With only one non-blank sample available, the true meaning of this field cannot be determined; it is reported as an open question, not a verified checksum.
  • Field-level semantics (what 6E 06, the FF FF 00 01 header pair, etc. actually represent in-game) are hypotheses only — there is no corroborating second distinct non-blank save to triangulate against.
  • The EEPROM address bit-width constant (*_DAT_0802f4cc + 8 / *_DAT_0802f5cc + 8) that the driver uses to size its address field is a data value not resolved by the static decompile; it is inferred only indirectly from the 512-byte file size.

3. Save Writer, Reader & Caller-Chain Architecture

Only 5 functions touch the EEPROM port (0x0D000000) or its DMA3 plumbing anywhere in the 224-function decompiled corpus. All 5 are present in ghidra/save_related_functions.c / ghidra/decompiled.c, and form a single, self-contained, generic SDK-style EEPROM driver with no higher-level game-specific caller captured in the trace. This is a hardware/SDK I/O layer, not game-specific logic — safe to document as standard low-level driver behavior.

3.1 FUN_0802f3a0 — DMA3 raw bit-stream transfer primitive (CONFIRMED_STATIC)

void FUN_0802f3a0(undefined4 param_1, undefined4 param_2, uint param_3)
  • Writes param_1 → DMA3 source address register, param_2 → DMA3 destination address register, and (param_3 & 0xFFFF) | 0x80000000 → the combined 32-bit DMA3 control register (length in low 16 bits, enable bit set in bit 31, which is bit 15 of the 16-bit CNT_H half — the standard GBA DMA "start now" encoding).
  • Busy-waits on the upper 16 bits of the control register for the enable/busy bit (0x8000) to clear, i.e. polls for DMA completion.
  • This is the textbook GBA EEPROM-over-DMA3 bit-serial transfer primitive: EEPROM has no parallel data bus: every bit of an EEPROM command/address/data stream is transferred as one 16-bit DMA unit to/from 0x0D000000.
  • Callers (traced): FUN_0802f420, FUN_0802f4e4 (both call it twice each — once to push a bit-serialized request, once to pull back the bit-serialized response/ack).

3.2 FUN_0802f420 — EEPROM block READ (CONFIRMED_STATIC)

void FUN_0802f420(uint param_1, int param_2)
  • param_1 = EEPROM block address (masked to 16 bits).
  • Bounds-checks param_1 against a configured address width (*(ushort*)(*_DAT_0802f438 + 4)).
  • Serializes a READ command bit-by-bit into a stack bit-buffer: writes 0b1 (start bit) + 0b1 (read opcode bit) followed by the block address bits (MSB-first), sized by a configurable address-bit-width constant (*(byte*)(*_DAT_0802f4cc + 8)) — this bit-width constant, consistent with the observed 512-byte/64-block file size, would be 6 bits (2^6 = 64 blocks) for this title, though the constant's actual stored value was not resolved statically.
  • Transmits that bit-stream via FUN_0802f3a0(buffer, 0x0D000000, addrbits+3) (send request), then receives the 64-bit (+4 dummy/ack bits = 68 bits = 0x44) data response via FUN_0802f3a0(0x0D000000, buffer, 0x44).
  • Unpacks the returned bit-stream into 4×16-bit words at param_2 (the caller's output buffer), i.e. 8 bytes of EEPROM block data per call — confirming the 8-byte EEPROM block granularity used throughout §2.
  • Caller: FUN_0802f644 only.

3.3 FUN_0802f4d0 / FUN_0802f4e4 — EEPROM block WRITE (CONFIRMED_STATIC)

void FUN_0802f4d0(undefined2 param_1, undefined4 param_2)     // thin wrapper, param_3=1 ("wait")
void FUN_0802f4e4(uint param_1, ushort *param_2, char param_3) // actual writer
  • param_1 = block address, param_2 = pointer to 8 bytes (4×16-bit words) of block data to write, param_3 = wait-for-completion flag.
  • Serializes a WRITE command bit-stream: start bit 0, then the 64 data bits (MSB-first per 16-bit word, 4 words), then the block address bits, then a stop bit — sent via FUN_0802f3a0(buffer, 0x0D000000, addrbits + 0x43) (0x43 = 67 = 64 data bits + 2 framing bits + 1, matching the write-frame layout).
  • After issuing the write, if param_3 (wait flag) is set, busy-waits using a timer/cycle-delta loop (comparing against a hardware counter register pointed to by *_DAT_0802f5d0, with a timeout threshold of 0x88 = 136 units) for the EEPROM's internal write-cycle completion — this matches the real-world EEPROM write latency (a few ms) that must be waited out before the next operation.
  • Caller: FUN_0802f4d0 is called only by FUN_0802f69c; FUN_0802f4e4 has no traced caller other than FUN_0802f4d0.
  • This function operates on exactly one 8-byte block per call — direct structural proof for the torn-write evidence in §2 (a 16-byte slot requires two separate calls/DMA transactions, and a reset between them leaves the second block erased, exactly as observed for slot 3).

3.4 FUN_0802f644 — EEPROM write verify (read-back compare) (CONFIRMED_STATIC)

void FUN_0802f644(ushort param_1, short *param_2)
  • Calls FUN_0802f420 (read) for the same block address, then compares the 4×16-bit words just read against param_2 (the data that was supposedly just written). Returns 0x8000 on mismatch, 0 on match.
  • Caller: FUN_0802f69c only.

3.5 FUN_0802f69c — top-level "write block with retry+verify" entry point (CONFIRMED_STATIC, ORPHANED IN TRACE)

void FUN_0802f69c(undefined2 param_1, undefined4 param_2, uint param_3)
  • Loop (up to 3 attempts): call FUN_0802f4d0 (write+wait); if it reports success, call FUN_0802f644 (verify by read-back); break on verified success; otherwise retry.
  • This is the single logical "commit one 8-byte EEPROM block, with hardware write+verify retry" entry point of the whole save subsystem as captured.
  • ghidra/callgraph.json confirms this function has zero callers in the 224-function trace ('callers': []). This means **the game-specific logic that decides when to call this (on level-complete? on checkpoint? on quit?) and what 8-byte payload + which of the 64 block addresses to pass in was not part of the trace-guided extraction and is genuinely unknown** from this workspace. Any claim about why slots 0–3 are written in the observed pattern is therefore a hypothesis derived purely from the .sav byte evidence (§2), not from code.

3.6 RAM mirror / in-RAM save struct

No EWRAM (0x02xxxxxx) or IWRAM (0x03xxxxxx) addresses appear anywhere in the 5 EEPROM-touching functions above — the caller passes a raw stack buffer (param_2) directly into the driver. No in-RAM "save struct" global was identified in the trace; the struct almost certainly exists in the untraced caller of FUN_0802f69c, which is outside this workspace's 224-function extraction. This is reported as UNKNOWN rather than guessed.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature — C0 DE 60 0D (offset 0x04, slot 0 only)

  • Bytes (hex): c0de600d
  • Location: cap-01-future-1.sav offset 0x04–0x07, inside slot 0's first 8-byte block (FF FF 00 01 C0 DE 60 0D).
  • Verified in .sav: YES — present at that exact offset in the only non-blank sample.
  • Verified in code: NO — no decompiled function in this trace constructs or compares this literal constant; it is a value observed only in the binary save data.
  • Confidence: CONFIRMED_STATIC is too strong since it's not seen in code at all — correctly: HYPOTHESIS (byte-pattern recognition only, not code-traced). It is flagged because C0DE/600D is a well-known class of human-readable hex placeholder constant, making it a strong magic-signature candidate, but clean-room rules require stating plainly that no decompiled instruction was found that writes or validates it.

4.2 Candidate trailer field — 9F C2 3F 21 (offset +0x0C within each slot's second block)

  • Bytes (hex): 9fc23f21, found at absolute offsets 0x0C, 0xAC, 0x14C (slots 0, 1, 2 of cap-01-future-1.sav); slot 3's equivalent byte range (0x1EC) is still FF FF FF FF (unwritten).
  • Python verification performed against both real .sav files:
import zlib
data1 = open('saves/cap-01-future-1.sav','rb').read()
target = bytes.fromhex('9fc23f21')
slots = [(0x00,0x08), (0xa0,0xa8), (0x140,0x148)]
for base, base2 in slots:
    rec12 = data1[base:base+12]          # candidate "covered range"
    print(hex(base), rec12.hex(), '-> trailer', data1[base+12:base+16].hex())
# Result:
# 0x0   ffff0001c0de600d00000000 -> trailer 9fc23f21
# 0xa0  00006e060000000000000000 -> trailer 9fc23f21
# 0x140 00006e060000000000000000 -> trailer 9fc23f21
#
# sum8/sum16/sum32, zlib.crc32, zlib.adler32 of rec12 (and of just the
# preceding 4 zero bytes) were computed for every slot and NONE matched
# 0x9fc23f21 (big- or little-endian) for any candidate algorithm or byte range.
  • Result: NOT a verifiable checksum. The preceding 12 bytes differ between slot 0 (FF FF 00 01 C0 DE 60 0D 00 00 00 00) and slots 1–2 (00 00 6E 06 00 00 00 00 00 00 00 00), yet the trailer is byte-identical in all three. No ordinary checksum/CRC/sum/XOR algorithm over any contiguous byte range tested produces a value that varies with its input the way a real checksum must, while still landing on this constant for two different inputs — brute force across sum8, sum16(LE), sum32(LE), XOR8/16/32, CRC32 (zlib), and Adler32 confirms no match either.
  • Conclusion: This field is most plausibly a fixed signature/sentinel constant (e.g. a format-version tag, a save-structure-finalized marker, or a hard-coded ID baked in by the un-traced serializer) rather than a data-dependent checksum. Confidence: UNKNOWN for its true purpose; CONFIRMED_VERIFIED only for the raw observation that the byte sequence recurs identically at the 3 completed-slot offsets.
  • No checksum-computation loop (increment/XOR/shift-accumulate over a buffer) exists anywhere in the 224-function decompiled corpus — confirmed by manual inspection of all EEPROM-touching functions and a grep sweep of the full decompiled.c for the EEPROM port constant, which returns only the 3 driver call sites already covered in §3.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states were supplied in this workspace (states/ is empty), so the following plan specifies what to capture and test on a future run that does include paired pre/post save states, per the fuzzing methodology:

  1. Confirm block-write granularity (highest priority, directly testable).
  • Mutation: flip a single bit in block 60 (0x1E0) only, leave block 61 untouched, reload.
  • Predicted effect: if the driver treats blocks independently (per §3.3), the game should load the mutated block-60 data without re-validating against block 61's (still-erased) trailer, unless a higher-level (untraced) consumer detects the erased trailer and treats slot 3 as invalid/incomplete and falls back to slot 1 or 2. Either outcome is informative: it either proves block-level independence or proves the existence of an as-yet-unseen validity check tied to the 9F C2 3F 21 trailer.
  1. Probe the 9F C2 3F 21 trailer's role.
  • Mutation A: corrupt the trailer at 0x0AC–0x0AF (slot 1) only, keep slot 2 (its apparent duplicate) intact.
  • Predicted effect: if the trailer is a validity/checksum guard, the game should prefer slot 2 or flag slot 1 corrupted (observable via debug RAM flags, a corruption prompt, or silently falling back to slot 2's identical data — indistinguishable at the UI level without an in-RAM read, hence the need for a gameplay.ss state capture at the exact post-load point to inspect which slot's RAM mirror was actually loaded).
  • Mutation B: corrupt the trailer identically in both slot 1 and slot 2, leave slot 0's header trailer intact.
  • Predicted effect: if both backup copies are "invalid," behavior should diverge from Mutation A (e.g. hard reset to new-game, or silent accept if the trailer is not actually checked) — this directly tests whether the trailer is load-bearing at all, resolving the open question in §4.2.
  1. Probe the magic candidate C0 DE 60 0D.
  • Mutation: corrupt one byte of 0x04–0x07 in slot 0 only.
  • Predicted effect: if this is a real "save format valid" magic check, the game should treat the EEPROM image as blank/corrupt (behaving like cap-00-future-0.sav, i.e. starting a fresh game). If gameplay proceeds normally using slot 1/2 data regardless, the magic is scoped to slot 0 only (e.g. a profile-selector header) and not a whole-image validity gate.
  1. Probe the 0x002–0x003 candidate counter.
  • Mutation: increment 0x0003 from 01 to 02.
  • Predicted effect: if this is a generation/version counter consumed by a selection rule, behavior should be unaffected (counters are typically monotonic bookkeeping, not gameplay-visible) unless the counter is used to pick which of slots 1/2/3 is "newest" — in which case deliberately setting it to a value lower than a forged alternate counter elsewhere could be used to force the game to prefer a different backup slot, which would be strong structural proof of a generation-based selection rule.
  1. Establish a second non-blank sample (methodological priority above all byte mutations).
  • The single largest gap in this analysis is having only one non-blank .sav. Any two-run comparison (fresh game → first checkpoint; first checkpoint → second distinct checkpoint with a different observable game state, e.g. different level/score) would let every HYPOTHESIS field above be re-tested for whether it actually varies with game state, which is the only way to escalate the checksum/trailer/header fields past UNKNOWN.

All of the above require: (a) a gameplay.ss captured immediately after reload so in-RAM mirror state can be inspected, (b) checksum repair is not applicable until/unless a real checksum formula is found (§4.2 explicitly found none), so corrupted-field mutations should be applied raw and their behavioral effect observed rather than assuming a repair step is required.
