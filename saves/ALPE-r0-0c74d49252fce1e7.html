1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and real .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is a 512-byte EEPROM image. Both samples are exactly 512 bytes, the SDK tag is EEPROM_V122, and the low-level driver talks to EEPROM at 0x0D000000 through DMA3.
  • The first 32 bytes are a global header. On disk it starts with ASCII 30ABGROL. After undoing the EEPROM driver's per-8-byte-block byte reversal, the RAM header starts with LORGBA03.
  • The header integrity algorithm is a 16-bit additive checksum. The sum of the sixteen u16 words in the RAM header is 0x0000 in both samples. The stored checksum is at RAM offset 0x1E, which maps to file offset 0x18. Python computed 0xF515 / 0xF415 versus stored 0xF515 / 0xF415: exact match in both files.
  • Mutating file byte 0x16 changes RAM header byte 0x11. In the two samples that byte changes 0 -> 1 and the checksum word changes by the exact compensating amount. This also explains the packet probe: a mutation at 0x16 breaks the header sum, validation fails, and the game rewrites a blank/formatted save.

Static-only (CONFIRMED_STATIC):

  • Four 120-byte save slots are loaded after the header. Each slot is read as fifteen 8-byte EEPROM blocks and validated with the same sum-to-zero rule over sixty u16 words, plus a range check on the word at slot RAM offset 0x66.
  • The full caller chains for boot validation, header formatting, slot loading, and header flushing are traced below from direct func_0x... call sites in ghidra/decompiled.c, cross-checked against ghidra/callgraph.json where that graph captured the edge.

Open / hypothesis (HYPOTHESIS / UNKNOWN):

  • All four slots are all-zero in both samples, so no populated slot field beyond the validator word at RAM +0x66 can be named from bytes.
  • No direct slot-write call (FUN_08035838 with a slot start block) exists in the traced decompilation. The slot EEPROM writer is therefore not recovered. This is the main reason the overall rating is not HIGH.
  • Exact numeric RAM base addresses cannot be recovered from this export. Ghidra left every _DAT_... literal unresolved, so RAM mirrors are given as struct offsets, not as 0x02.../0x03... addresses.
  • The exact EEPROM block numbers for slots are not literal-recovered. Sequential blocks 4, 19, 34, 49 fit the geometry exactly and are labelled hypothesis.

EEPROM serialisation transform (critical for reading the .sav)

The EEPROM driver does not store RAM bytes in file order. Inside each 8-byte block, the read routine FUN_08045dbc reassembles sixteen 1-bit DMA samples at a time and stores the four resulting u16 values backwards (param_2 + 6, then decrementing). Combined with MSB-first bit assembly, the net file-to-RAM transform proven by the checksum is:

RAM byte at (block_base + i)  ==  file byte at (block_base + 7 - i),  for i in 0..7

In other words, reverse each 8-byte block to get the RAM image. Consequences verified in Section 4:

  • File magic 30ABGROL becomes RAM magic LORGBA03.
  • RAM checksum word at header +0x1E appears at file offset 0x18 as big-endian-looking bytes (F5 15 = RAM u16 0xF515).
  • RAM header byte +0x11 appears at file offset 0x16. This is exactly the packet's mutation-probe offset.
  • RAM header byte +0x10 appears at file offset 0x17.

Slot geometry in RAM is unaffected in size: each slot stays 120 bytes, only the byte order inside each 8-byte block changes.

3. Save Writer, Reader & Caller-Chain Architecture

How callers were mapped

Two evidence sources were combined:

  1. Direct call sites in ghidra/decompiled.c. Ghidra prints resolved direct calls as func_0x080...(...) inside the caller body. Every chain below was read from those bodies.
  2. ghidra/callgraph.json. Where present, it confirms the same edges (for example 0x08045dbc -> 0x08045d3c, 0x08045e6c -> {0x08045c70, 0x08045cf8, 0x08045d3c}, 0x08045f48 -> 0x08045dbc, 0x08035754 -> {0x0802abf4, 0x0802ac98, 0x0802ae10}).

ghidra/callgraph.json is incomplete for the save subsystem: most functions from 0x0803557c to 0x08035838 have empty caller/callee lists there, and almost every decompiled function ends in an UNRECOVERED_JUMPTABLE tail branch. Those tail branches hide callers that dispatch through function pointers or state tables. Where a caller is only reachable that way, this report says so instead of inventing an address. The top-level boot caller of FUN_0803557c and the menu caller of FUN_08025f88 are in that unknown set.

Caller chains

Chain A — boot validate, format if needed, load (CONFIRMED_STATIC). [unknown indirect boot caller] -> FUN_0803557c -> { FUN_08045bd0(4), FUN_08045c38(2), FUN_080357ac -> FUN_08035804(0,4) -> FUN_08045dbc -> FUN_08045d3c, [if invalid] FUN_08035754 -> FUN_08035838(0,0x40) -> FUN_08045e6c + FUN_08045f48, FUN_0803e9f8(header+0x10), FUN_080355c0 -> FUN_080356b8 -> FUN_08035804(slot_start,0xF) and FUN_08035628 -> FUN_08035730 }. RAM mutation before flush: only in the format branch, where the whole RAM header is replaced by the default template and its checksum word is recomputed. In the valid branch no header bytes are changed at boot; the byte at RAM +0x10 is read out and applied to the live settings global through FUN_0803e9f8, which also uses it as an index (value * 4) into a pointer table — consistent with a locale/language-style selector, but that meaning is a hypothesis.

Chain B — header flush after a settings change (CONFIRMED_STATIC). [unknown indirect caller] -> FUN_08025f88 -> FUN_0803e9f8(*(struct_at__DAT_08025fc0 + 8)), FUN_08035658, then if *(_DAT_08025fc4) == 0: FUN_0803dc34(0), FUN_08035670 -> FUN_08035838(0,4), FUN_0803dc34(saved_byte), FUN_0802b110(1); else FUN_0802b12c(...). How the RAM struct is mutated before flushing: FUN_08035658 first copies the live settings byte from FUN_0803ea18 (*_DAT_0803ea20) into header RAM +0x10 and sets header RAM +0x11 = 1. FUN_08035670 then zeroes and recomputes the checksum at +0x1E and writes the four header blocks only when the new checksum differs from the one already on EEPROM. The surrounding FUN_0803dc34(0) / restore pair and the final FUN_0803dca0(0x7A) look like a display/blanking guard around the slow EEPROM write; their exact UI role was not pursued because it does not change save bytes. The trigger condition behind *_DAT_08025fc4 is unresolved, so the gameplay event that calls FUN_08025f88 is unknown.

Chain C — checksum computation (CONFIRMED_STATIC). FUN_08035730(buf, byte_count) is called by FUN_08035628 (slots, 0x78), FUN_08035670 (header flush, 0x20), and inlined in equivalent open-coded loops inside FUN_08035754 and FUN_080357ac. No other checksum algorithm (CRC, XOR, byte sum) exists in the traced save code.

Missing chain — slot writer (UNKNOWN). Exhaustive text search of ghidra/decompiled.c finds only two FUN_08035838 call sites: (0, 0x40) in format and (0, 4) in header flush. No call writes fifteen blocks at a slot start, and no function recomputes a slot checksum before writing. Either the slot writer dispatches through an unrecovered jump table / function pointer not present in this export, or populated slots are written by code outside the 255 traced functions. This report does not invent one.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • File offset 0x00, 8 bytes: 33 30 41 42 47 52 4F 4C, ASCII 30ABGROL. Present identically in both samples.
  • RAM form after reversing the first 8-byte block: 4C 4F 52 47 42 41 30 33, ASCII LORGBA03.
  • Code proof: FUN_080357ac reads the header, and only in the sum-valid branch compares eight bytes one at a time against the constant behind iRam08035800. Any mismatch returns 0 (invalid). The constant bytes themselves are behind an unresolved literal, so the code side proves an 8-byte magic comparison exists at RAM header offset 0; identity with LORGBA03 follows from the verified serialisation transform and the file bytes.

Algorithm (exact)

FUN_08035730(buf, byte_count):
    s = 0  (s16 accumulator, arithmetic modulo 2^16)
    for i in 0 .. (byte_count/2 - 1):
        s = (s + u16_le(buf + 2*i)) mod 2^16
    return s

Header store (FUN_08035754 and FUN_08035670):
    header_u16[15] = (- sum of header_u16[0..15] with word 15 treated through the
                      same accumulation; equivalently -sum of words 0..14 when
                      word 15 starts zeroed) mod 2^16
    -- stored at RAM offset 0x1E, little-endian in RAM.

Header validate (FUN_080357ac):  sum of all 16 words == 0  AND magic matches.
Slot validate   (FUN_08035628):  sum of all 60 words over 0x78 bytes == 0
                                 AND 0x1F <= u16 at slot+0x66 <= 0x84.

There is no CRC, no XOR fold, no complement beyond the arithmetic negation above, no seed, and no byte-sum variant in the save code. The on-file appearance differs only because of the Section 2 block-reversal transform: summing the file header as big-endian u16 words also yields 0, and the stored file word at 0x18 reads 0xF515 / 0xF415 big-endian, matching the RAM little-endian checksum at +0x1E.

Worked sample arithmetic (RAM image):

  • cap-00-future-0.sav: words 4F4C 4752 4142 3330 0000 0000 FF07 00D4 0000 0000 0000 0000 0000 0000 0000 F515, sum 0x0000. Computed checksum -sum(words 0..14) = 0xF515, stored 0xF515.
  • cap-01-retained-3.sav: word 8 becomes 0x0100 (RAM byte +0x11 = 1), computed checksum 0xF415, stored 0xF415. The +0x0100 increase is exactly cancelled by the -0x0100 checksum change. This is the byte pair the packet lists as mutated ranges 0x16 and 0x18.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so predictions are stated for reloading the mutated .sav with a cold boot in an emulator. Repair always means: rebuild the RAM image (reverse each 8-byte block), set the target RAM byte, recompute header_u16[15] = (-sum of the other 15 words) & 0xFFFF (or the 60-word slot equivalent), re-apply block reversal, and write the file back.
