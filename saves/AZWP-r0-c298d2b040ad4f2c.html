1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (header, geometry, checksum, boot selection/repair logic, and default-score table are CONFIRMED_VERIFIED; most payload semantics are static-only or unknown).

Proven by both decompiled code and .sav bytes:

  • The cartridge save is a 32,768-byte SRAM image containing up to two byte-identical 1,028-byte (0x404) save blocks at file offsets 0x0000 and 0x4000.
  • Each block starts with magic MIW\0 (4D 49 57 00), a u32_le length field 0x404, and a u32_le additive checksum at +0x08 over all 257 u32_le words of the block with the checksum word zeroed. The checksum verifies on every valid block in both samples (Section 4).
  • Boot code validates block 0, falls back to block 1, repairs block 0 from block 1 when only block 1 is valid, creates defaults when both are invalid, and rewrites block 1 on every boot (Section 3). This exactly predicts the sample progression: cap-00 has only the 0x4000 copy, cap-01 has both copies.
  • A default-initialisation routine seeds eight 8-byte score records (indices 15–22) with values 50000, 10000, 100, 10000, 10000, 50, 30, 40, and those exact values appear at the predicted offsets in both samples.

Static-only / open:

  • The exact EWRAM/IWRAM address of the in-RAM mirror cannot be recovered from this export: Ghidra renders every literal-pool pointer as an unresolved _DAT_080xxxxx symbol with no value. All RAM addresses below are therefore null/unknown, not guessed.
  • The per-record type table used by the score updater, the meaning of header word +0x0C, the byte at +0x1FF, and all fields that are zero in the two (gameplay-free, default-only) samples remain unknown.
  • No gameplay caller of the save writer or score updater is present in the 269-function trace-guided corpus (see Section 3.4); only the boot-time caller chain was traced.

A note on the pre-extracted seed: ghidra/save_related_functions.c contains a single seed, FUN_080f5098, which is a software division/modulo helper (shift/subtract long division, calling a divide-by-zero trap func_0x080f4a8c). It has no callers, touches no SRAM/MMIO save address, and is a false positive from MMIO-pattern seeding. It plays no part in saving. The real save subsystem was found instead by following the 0x404-sized DMA fill, the u32-summing routine FUN_080004f4, and the boot function FUN_080001d4.

Redundancy model: this is a primary/backup pair with boot-time repair, not ping-pong/alternating writes and not newest-wins by counter. Copy 0 is the primary (validated first, and the repair target). Copy 1 is the backup (validated second) and is refreshed from RAM on every boot, which is why a first boot from blank SRAM produces exactly the cap-00 state (only copy 1 written, because the repair write to copy 0 is skipped when defaults were just created — see the chain in Section 3.3), and a second boot produces cap-01 (copy 0 repaired from the now-valid copy 1, then copy 1 rewritten with identical bytes).

Checksum weakness relevant to redundancy: because the checksum is a plain additive sum (Section 4), it detects accidental corruption but cannot distinguish copies by content age.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM addresses (0x08xxxxxx). The Ghidra export names two kinds of callees: FUN_080xxxxx (a body is present in decompiled.c and in callgraph.json) and func_0x080xxxxx (called but with its body inlined/absent from the corpus as a separate node — the wrapper functions below are reached this way). Caller mapping method: (a) callgraph.json callers/callees edges where present, (b) textual func_0x… / FUN_… call sites in decompiled.c, and (c) agreement of passed constants (size 0x404, offsets, default values) with .sav bytes. Where the export's call graph omits an edge for a func_0x… call, that is stated explicitly.

3.1 Low-level hardware I/O drivers (SRAM at 0x0E000000)

Write driver — FUN_080eeeb0(src_ram, dst_sram, len) (0x080eeeb0)

*_DAT_080eeee8 = *_DAT_080eeee8 & (ushort)_DAT_080eeeec | 3;   // WAITCNT (0x04000204): set SRAM wait bits
while (param_3 = param_3 + -1, param_3 != -1) {
  *param_2 = *param_1;  param_1 = param_1 + 1;  param_2 = param_2 + 1;  // byte-by-byte copy
}

A byte-at-a-time CPU copy is the canonical SRAM write (SRAM is byte-wide; 16/32-bit writes are unsafe), and the | 3 OR into a masked halfword register is consistent with configuring WAITCNT (0x04000204) SRAM wait states before access. Role: write. Sole traced caller: FUN_08000648. callgraph.json lists no callers for it because FUN_08000648 reaches it as func_0x080eeeb0.

Read driver — FUN_080eee4c(src_sram, dst_ram, len) (0x080eee4c)

*_DAT_080eee78 = *_DAT_080eee78 & (ushort)_DAT_080eee7c | 3;   // WAITCNT setup, as above
// copies a small code stub from ROM (_DAT_080eee80.._DAT_080eee84) onto the stack (uStack_90)
func_0x080f49c8(param_1, param_2, param_3, (int)&uStack_90 + 1);

Role: read (SRAM → RAM). It stages a copy routine on the stack — consistent with executing the actual byte-copy from RAM, a common SRAM-read idiom — and delegates to the external helper func_0x080f49c8(src, dst, len, stub), whose body is not in the corpus (HYPOTHESIS on the stack-stub mechanism; the SRAM→RAM direction is CONFIRMED_STATIC from the validator's usage). Sole traced caller: FUN_080005d4. No Flash command writes (0xAA/0x55 to 0x5555/0x2AAA) and no EEPROM/DMA3 (0x040000D4) save path exist anywhere in decompiled.c; the DMA helpers FUN_08001050 (DMA copy) and FUN_080010c4 (DMA fill) are used for graphics/RAM work and, in the case of FUN_080010c4, for zeroing the RAM mirror (Section 3.2), never with an SRAM destination in any traced call.

3.2 Serialisation, deserialisation, checksum, and default construction

Checksum — FUN_080004f4(buf, len) (0x080004f4): sums len >> 2 consecutive u32 words (iVar3 += *param_1++), returns the 32-bit sum. Callers (both in callgraph.json and in text): validator FUN_080005d4, writer FUN_08000648. Full algorithm and verification in Section 4.

Validator / deserialiser — FUN_080005d4(slot_sram_addr) (0x080005d4) returns 0 = valid, 1 = bad magic, 2 = bad checksum:

func_0x080eee4c(param_1, *_DAT_080005f4, _DAT_080005f8);        // SRAM -> RAM mirror, len = 0x404
iVar2 = func_0x08007c2c(*piVar1, _DAT_080005fc, 4);             // 4-byte compare vs "MIW\0"
if (iVar2 == 0) {
  iVar2 = FUN_080004f4(*piVar1, uVar3);                          // sum over full block (checksum word included)
  if (iVar2 + *(int *)(*piVar1 + 8) * -2 == 0) uVar3 = 0;        // valid iff total == 2 * stored
  else uVar3 = 2;
} else uVar3 = 1;

FUN_08007c2c (0x08007c2c) is the byte-compare helper (returns 0/1/-1 like memcmp/strcmp). The wrappers FUN_08000620 (0x08000620) and FUN_08000634 (0x08000634) each call FUN_080005d4 with one fixed slot address (*_DAT_08000630 / *_DAT_08000644 — unresolved literal-pool pointers to 0x0E000000 / 0x0E004000; the assignment of wrapper→offset is inferred from boot behaviour and sample order, Section 3.3).

Writer / serialiser — FUN_08000648(slot_sram_addr) (0x08000648):

*(undefined4 *)(iVar3 + 8) = 0;                                  // zero checksum word
uVar4 = FUN_080004f4(iVar3, _DAT_08000674);                      // sum over 0x404 bytes
*(undefined4 *)(iVar3 + 8) = uVar4;                              // store checksum at +0x08
func_0x080eeeb0(iVar3, param_1, uVar2);                          // RAM -> SRAM byte copy

Wrappers FUN_08000678 (0x08000678) and FUN_0800068c (0x0800068c) supply the two slot addresses. So every flush recomputes and embeds the checksum before the byte copy; there is no separate "erase" step (SRAM needs none) and no verify-after-write in traced code.

Default-save constructor — FUN_08000528 (0x08000528), called only from boot when both copies are invalid:

func_0x080010c4(0, iVar2, _DAT_080005bc, 0x20, 0x100);   // DMA-fill RAM mirror with 0 (0x404 bytes)
func_0x080f68b8(iVar2, _DAT_080005c0);                    // strcpy magic "MIW\0" to +0x00 (FUN_080f68b8 is strcpy)
*(undefined4 *)(iVar2 + 4) = uVar1;                      // +0x04 = 0x404 length
*(undefined4 *)(iVar2 + 8) = 0;                          // +0x08 checksum (recomputed later by writer)
*(undefined4 *)(iVar2 + 0xc) = _DAT_080005c4;            // +0x0C constant 00 00 1F 31 (bytes in .sav order)
*(byte *)(iVar2 + 0x20) |= 2;                            // byte at +0x20 gets bit 1 set (value 0x02 in .sav)
func_0x08008aa8(0xf, _DAT_080005c8);                     // record 15 <- 50000 (inferred constant, matches .sav)
func_0x08008aa8(0x10, _DAT_080005cc);                    // record 16 <- 10000
func_0x08008aa8(0x11, 100);                              // record 17 <- 100
func_0x08008aa8(0x12, uVar1 /*=_DAT_080005cc*/);         // record 18 <- 10000
func_0x08008aa8(0x13, uVar1);                            // record 19 <- 10000
func_0x08008aa8(0x14, 0x32);                             // record 20 <- 50
func_0x08008aa8(0x15, 0x1e);                             // record 21 <- 30
func_0x08008aa8(0x16, 0x28);                             // record 22 <- 40
func_0x08010bb4();                                       // clears a 6-byte global (context unknown)
*(undefined1 *)(iVar2 + _DAT_080005d0) = 1;              // byte at +0x1FF = 1 (offset inferred from .sav)

The two inferred constants (_DAT_080005c8 = 50000, _DAT_080005cc = 10000) are CONFIRMED_VERIFIED by the .sav bytes at the predicted record slots; the +0x1FF offset of the final store is CONFIRMED_VERIFIED the same way (it is the only non-zero byte in 0x100–0x3FF). FUN_080f68b8 (0x080f68b8) is a textbook strcpy, so the magic is stored as a C string at +0x00.

Score updater — FUN_08008aa8(index, value) (0x08008aa8): the only traced mutator of payload fields besides the constructor. For index < 0x1C (28) it addresses an 8-byte record at ram_mirror + index*8 + 0x20, reads a per-index type from a ROM table (*(int *)(index*4 + _DAT_08008aec) + 2), and:

  • type 1: maintains a descending top-3 u16_le list at record +2/+4/+6 — if value beats a slot, higher entries shift down and value is inserted at record +2 (as (ushort)param_2);
  • type 2: stores a u32_le at record +2 if it exceeds the current value (with clamping to _DAT_08008b68);
  • index == 99: a separate single-u16 high-score path at ram_mirror + 0x200 + idx*2 driven by a different index source.

In the default samples only the first slot of each seeded record is populated because the constructor inserts exactly one value per record into a zeroed table. How each record is updated in gameplay: a caller passes (record_index, new_value) and this function inserts it into the RAM mirror only; persistence happens whenever a later FUN_08000648 flush runs. No gameplay caller of FUN_08008aa8 is in the traced corpus — its only textual call sites are the eight constructor calls — so gameplay trigger contexts are UNKNOWN.

3.3 Boot caller chain (the fully traced chain)

FUN_080001d4 (0x080001d4, boot/init) executes, in order:

func_0x08000514();                 // *_DAT_08000520 = *_DAT_08000524  (pointer/context setup, HYPOTHESIS: installs RAM mirror pointer)
iVar3 = func_0x08000620();         // validate copy 0 (SRAM 0x0E000000) -> RAM mirror
if (iVar3 != 0) {
  iVar3 = func_0x08000634();       // validate copy 1 (SRAM 0x0E004000) -> RAM mirror
  if (iVar3 == 0) func_0x08000678();   // copy 1 valid: rewrite/repair copy 0 from RAM
  else func_0x08000528();              // both invalid: build defaults in RAM
}
func_0x0800068c();                 // unconditionally rewrite copy 1 from RAM

Mapping of wrappers to file offsets (inference, CONFIRMED_STATIC for the logic, HYPOTHESIS for which unresolved _DAT_ holds which absolute address — the behaviour + samples pin it down): the validator tried first and the repair target are the same copy, and the unconditional write is the other copy. cap-00 (blank → one boot) contains only the 0x4000 copy, so the unconditional writer FUN_0800068c targets file offset 0x4000; the repair writer FUN_08000678 therefore targets 0x0000, and correspondingly FUN_08000620 validates 0x0000 first and FUN_08000634 validates 0x4000. The second sample (another boot with no gameplay change) then adds the identical 0x0000 copy via the repair path and rewrites 0x4000 with identical bytes — exactly the observed cap-00 → cap-01 diff (1,028 bytes, all at 0x0000–0x0403).

Each validator call overwrites the whole RAM mirror with the SRAM image before checking it, so after boot the RAM mirror holds: copy 0 if it was valid, else copy 1 if valid (then copied back to copy 0), else fresh defaults. Every later field mutation happens in that RAM mirror; nothing in traced code writes SRAM except FUN_08000648's byte copy.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic: bytes 4D 49 57 00 = ASCII MIW\0 at block offset 0x00. Verified in code twice: written by strcpy (FUN_080f68b8) in FUN_08000528, compared over exactly 4 bytes by FUN_08007c2c(buf, magic_const, 4) in FUN_080005d4 (return 1 → reject). Verified in .sav: present at 0x0000 and 0x4000 in cap-01, at 0x4000 in cap-00; absent (all 0xFF) where no copy exists. The header word at +0x0C (bytes 00 00 1F 31, u32_le 0x311F0000) is a constant written by the constructor (_DAT_080005c4) but is never compared in traced code — it is not a second magic (CONFIRMED_STATIC that it is written; UNKNOWN semantics). The apparent ASCII SM at +0x08 is not a signature: it is the low half of the checksum value 0x6BD24D53 and changes with content.

Checksum algorithm (CONFIRMED_VERIFIED):

  • Routine: FUN_080004f4(buf, 0x404) — sum = Σ u32_le words, 257 words, arithmetic modulo 2³², little-endian, no seed, no complement, no final XOR.
  • Stored: u32_le at block offset 0x08, size 4.
  • Covered range: the entire block 0x00–0x403, with the stored word itself zeroed during computation (writer zeroes +0x08, sums, stores; reader sums the block as read and accepts iff total − 2·stored == 0, i.e. total == 2·stored).
  • There is no per-copy or secondary checksum, and no counter protected separately.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states were provided for this cohort (states/ is empty), so every test below is: patch a copy of a .sav, boot the ROM with that SRAM image, and observe (a) accepted/rejected/defaulted save, (b) on-screen scores/progress, and (c) whether boot rewrites either copy (diff the SRAM image after boot — the boot chain in Section 3.3 makes the file itself an observable). Checksum repair for any payload mutation: zero u32_le at block +0x08, sum all 257 u32_le words of the 0x404 block, store the sum at +0x08 (Python: struct.pack_into('<I', blk, 8, sum(struct.unpack('<257I', blk_zeroed)) & 0xFFFFFFFF)), and apply the same patch to both copies unless the test targets copy selection.
