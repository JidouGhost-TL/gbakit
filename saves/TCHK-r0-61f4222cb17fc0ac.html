All findings below are derived exclusively from ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, and the raw bytes of saves/cap-00-future-0.sav / saves/cap-01-future-1.sav (plus saves/hexdump_and_diffs.txt), cross-referenced only against public, generic GBA hardware behavior (EEPROM serial protocol over 0x0D000000 via DMA3 0x040000D4, BIOS IRQ masking conventions). 1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM-HIGH

What was proven (code + byte evidence agree):

  • The title uses a 6-bit-addressed, 8-byte-block EEPROM (block address < 0x40, i.e. 64 blocks × 8

bytes = 512 bytes of addressable save space), not the full 8 KiB that the generic EEPROM 64K media tag and the 8192-byte .sav container imply. The container is simply padded/oversized relative to what this ROM's driver ever addresses — only the first 0x200 (512) bytes are ever touched, exactly matching the tool's own "active range" observation (0x0001..0x0200).

  • Block 0 (file offset 0x00..0x07) holds a constant 8-byte validity/magic tag. It is byte-identical

in both capture snapshots and decodes, when the 7 content bytes are read back-to-front, to the ASCII text "EEPROM ". This is checked with a strcmp-style routine (FUN_0800ff1c) against a ROM-resident constant and auto-repaired (rewritten) on mismatch.

  • Block 1 (file offset 0x08..0x0F) holds an 8-byte mode/identity tag that is blank (0xFF×8,

i.e. factory-erased EEPROM) in cap-00 and becomes the reversed ASCII text "LCDUNIT" in cap-01. The byte-diff between the two capture files is exactly these 8 bytes — nothing else in either file differs. The writer that produces this transition (FUN_080003b4) and the full caller chain down to the DMA3 bit-serial EEPROM driver were traced statically.

  • There is no checksum, CRC, or additive integrity field anywhere in the traced save path. Integrity is

enforced purely by exact-match string comparison against fixed ROM constants, with the save engine reconstructing/rewriting the block whenever the comparison fails.

What remains open (static-only or unknown):

  • The exact ROM-resident string constants compared against (_DAT_0800021c, _DAT_08000234,

_DAT_0800024c, _DAT_08000264, _DAT_0800027c, and the block-0 magic _DAT_0800d164) are referenced only as data pointers in the decompilation — their literal byte contents are not present in the supplied .c/callgraph files, so we cannot prove which of the 5 candidate identity tags maps to which numeric mode index, beyond the one tag ("LCDUNIT") we can directly observe mutating into the .sav file. Only two capture snapshots are present, and only 1 of 64 possible 8-byte blocks is observed in a non-blank state beyond block 0, so blocks 0x02..0x3F remain UNKNOWN (never observed non-blank).

  • The precise bit-count breakdown inside the DMA3 bit-serial transfers (FUN_0800f78c calls with 9,

0x44, 0x49, 0x80000000-tagged lengths) is consistent with, but not independently provable beyond, the publicly documented GBA EEPROM read/write serial protocol (2 start bits + 6-bit address + 64 data bits + 1 stop bit for writes; 2+6+1 request / 4 dummy + 64 data bits response for reads). We rely on this generic, publicly-documented hardware protocol (not game-specific research) to interpret the bit counts.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3, 0x0D000000)

3.2 Verify-after-write wrapper

  • 0x0800fae8 — EepromWriteVerify(block, expected_data): calls FUN_0800f810(block, readback_buf)

(READ) into an uninitialized local, then compares the 4×16-bit words of readback_buf against expected_data word-by-word; returns 0x8000 on first mismatch, 0 if all 4 words match. Caller: FUN_0800d03c only (traced via ghidra/callgraph.json).

3.4 High-level callers: validity check, mode-dispatch, and mode-set — every traced caller

0x0800d130 — CheckAndRepairMagic() (top of the save subsystem; no static callers found in ghidra/callgraph.json — it is almost certainly invoked indirectly from the title's boot/init sequence via the same kind of indirect jumptable seen throughout this binary):

FUN_0800d0c4(0, buf)                       // read block 0 (validity tag) into buf
if (strcmp(MAGIC_CONST, buf) != 0) {       // FUN_0800ff1c
    build_tag(buf, MAGIC_CONST)             // FUN_0800fedc — formats the canonical tag into buf
    if (FUN_0800d03c(0, buf) != 0)          // write+verify block 0
        return 1;   // repaired/initialized
}
return 0;           // already valid, no repair needed

How mapped: direct body inspection; both read and write targets are block 0, matching the file offset (0x00) of the constant tag byte-identical across both .sav samples. The in-RAM struct mutated is the 8-byte stack buffer buf itself — this routine has no persistent RAM mirror beyond the stack; it is a pure validate-and-flush operation, not a cached-RAM-then-flush design.

0x080001e4 — ReadModeIndex(), called from 0x080001a0 (which gates on a hardware/BIOS condition (~*_DAT_080001cc & 0x3ff) == 0x300 before deciding whether to call it at all):

if (FUN_08000290() == 0) {                  // ROM header/title sanity check (unrelated to save; no EEPROM access)
    if (FUN_0800d130() == 1) return 3;       // magic was just repaired -> default mode index 3
    FUN_0800d0c4(1, buf);                    // read block 1 (mode/identity tag)
    if      (strcmp(TAG1, buf)==0) return 1;
    else if (strcmp(TAG2, buf)==0) return 2;
    else if (strcmp(TAG3, buf)==0) return 3;
    else if (strcmp(TAG4, buf)==0) return 4;
    else if (strcmp(TAG5, buf)==0) return 5;
    else return -1;                          // unrecognized tag
} else return 0;

How mapped: direct body inspection of FUN_080001e4; block index 1 passed to FUN_0800d0c4 matches file offset 0x08, exactly the offset of the observed "LCDUNIT" tag mutation. The five _DAT_* constants are the five known mode identities; their literal text is not present in the supplied decompilation (data section not dumped), so only the mapping mechanism is CONFIRMED_STATIC — the specific index↔string pairing beyond the one observed ("LCDUNIT") is UNKNOWN.

0x080003b4 — SetModeTag(mode_index) (the writer that actually produces the observed cap-00→cap-01 mutation):

void SetModeTag(int mode_index) {
    switch (mode_index) {
      case 1: build_tag(buf, _DAT_080003e0); break;
      case 2: build_tag(buf, uRam080003f0);  break;
      case 3: build_tag(buf, uRam08000400);  break;
      case 4: build_tag(buf, uRam08000410);  break;
    }
    status = FUN_0800d03c(1, buf);           // write+verify block 1
    if (status != 0) { ... drives on-screen UI feedback / further hardware test loop ... }
}

How mapped: direct body inspection; the only write target in this function is block 1 (FUN_0800d03c(1, buf)), and buf is populated exclusively by FUN_0800fedc from one of four candidate mode-name constants selected by param_1. This is the exact and only writer we traced for file offset 0x08..0x0F, and its invocation is consistent with the observed diff (blank→"LCDUNIT"). The subsequent code (FUN_0800bf0c, FUN_0800c554, polling on iRam08000444, writing puRam080004e0/puRam080004a0 structures) drives on-screen diagnostic UI/controller-state feedback for the aging-test harness and does

not touch EEPROM further — it is downstream UI, not additional save data.

RAM mirror note: no persistent EWRAM/IWRAM (0x02xxxxxx/0x03xxxxxx) staging structure for the save data was found anywhere in the traced functions. Every read/write wrapper operates directly on an 8-byte

stack buffer (auStack_10/auStack_94/buf) that is filled immediately before a single ReadBlock/ WriteAndVerifyBlock call and discarded on return. This is consistent with the small (512-byte), two-field nature of this title's save data — there is no larger in-RAM "save struct" to mirror.

4. Magic Signatures & Checksum / Integrity Algorithm

No checksum, CRC, sum, or XOR integrity field exists anywhere in the traced save path. Every integrity/validity check found in ghidra/decompiled.c is an exact-match string comparison (FUN_0800ff1c, a word-optimized strcmp) between the stored 8-byte block and a fixed ROM constant, with automatic reconstruction (not rejection) on mismatch — see §3.4.

Magic tag encoding (verified against both .sav files)

Both observed tags store their ASCII content byte-reversed, preceded by a 0x00 byte, inside an 8-byte block:

  • Block 0, bytes 0x00..0x07: 00 20 4D 4F 52 50 45 45. Bytes 0x01..0x07 reversed read as ASCII

"EEPROM " (trailing space). Identical in both .sav files.

  • Block 1, bytes 0x08..0x0F: 0xFF×8 in cap-00 (unwritten EEPROM); 00 54 49 4E 55 44 43 4C in

cap-01. Bytes 0x09..0x0F reversed read as ASCII "LCDUNIT".

This reversed-string layout is consistent with FUN_0800fedc's construction pattern: it invokes a formatting helper (func_0x08010050) to write the candidate tag into the buffer, then unconditionally sets the buffer's first byte to 0 (*apuStack_6c[0] = 0;) — i.e., the formatter writes the string right-to-left into the buffer and the wrapper null-terminates the "front" (lowest address) afterward, yielding the observed 00 + reversed-ASCII pattern.

Python verification (run against the actual .sav files in saves/)

Open questions to resolve with further evidence

  1. What are the literal ROM-constant strings at _DAT_0800021c, _DAT_08000234, _DAT_0800024c,

_DAT_08000264, _DAT_0800027c (the 5 mode-tag candidates in 0x080001e4) and at _DAT_080003e0, uRam080003f0, uRam08000400, uRam08000410 (the 4 writer-side candidates in 0x080003b4)? ghidra/callgraph.json, consistent with indirect/jumptable dispatch throughout this binary)? Tracing an actual emulator execution trace through the indirect call sites would confirm the boot-time ordering assumed in §3.4.

  1. Are blocks 0x02..0x3F ever written during longer play sessions of the aging/diagnostic test suite

(e.g. per-subsystem pass/fail logs)? Only 2 short capture snapshots were available in this packet; a longer multi-subsystem test run would be needed to observe this.

  1. Is the (~*_DAT_080001cc & 0x3ff) == 0x300 gate in 0x080001a0 a hardware revision/BIOS-version check
