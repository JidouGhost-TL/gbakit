1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (CONFIRMED_VERIFIED):

  • The save media is a 512-byte EEPROM (EEPROM 4K), accessed only as 8-byte blocks over DMA3 to the EEPROM window at 0x0D000000.
  • The physical layout is a 24-byte global header at offset 0x00, followed by three independent 160-byte save slots at 0x18, 0xB8 and 0x158, with the final 8 bytes at 0x1F8 unused.
  • The header starts with the 8-byte ASCII magic 4400ABGC at 0x00.
  • The header carries a negated sum-of-16-bit-words checksum at 0x16.

In .sav file domain the sum of the 12 big-endian words over 0x00..0x17 is exactly 0x0000 in both samples. The stored value 0x0100 (big-endian, file bytes 01 00) equals the negated sum of the other 11 words in both samples.

  • Both samples are factory-initialised saves.

Each slot contains only its first 8-byte block zeroed, exactly as the init code writes it, and all other slot bytes are erased 0xFF. No slot is valid in either sample.

  • The only difference between the two captures is a checksum-preserving pair: byte 0x0C increments 0x00 -> 0x01 and byte 0x10 decrements 0x10 -> 0x0F.
  • The PACKET cold-reload probe at offset 0xC (integrity failure, save rewritten) is consistent with the code-proven header validation.

What is proven only statically (CONFIRMED_STATIC):

  • The full writer/reader architecture: Nintendo EEPROM_V124 block driver, game read/write wrappers with verify-and-retry, header validate/create/flush functions, and slot load/validate functions (Section 3).
  • Slot validity is a zero word-sum over the full 160-byte slot (FUN_080327b4).

No valid slot exists in the samples, so the slot checksum's stored position is not byte-proven.

  • Header fields at RAM offsets +0x08..+0x0D and +0x11 are packed from a separate settings struct on save and unpacked on load (FUN_08020688 / FUN_08021390).

What remains open (HYPOTHESIS / UNKNOWN):

  • The internal field layout of a populated 160-byte slot.

No slot serializer and no slot checksum setter exists anywhere in the 307 traced functions. The slot writer is outside the traced set or behind an unrecovered indirect call.

  • The semantics of the paired counter-like fields at 0x0C and 0x10.
  • The absolute EWRAM/IWRAM addresses of the RAM save structs.

Ghidra _DAT_ symbols name only the ROM addresses of the pointer literals, not their values.

  • The exact RAM-to-file word byte-order conversion performed by the EEPROM serial layer (Section 4).

MEDIUM (not HIGH) is assigned because the physical media, header format and integrity algorithm are byte-verified, but the slot payload — the majority of the save's capacity — is unobserved in the samples and its writer was not traced.

Derivation from code, not just from the bytes:

  • FUN_0803242c validates a header of length 0x18 at offset 0, then in its init branch writes 8 bytes at iVar4 = 0x18, incrementing by 0xA0, for 3 iterations: 0x18, 0xB8, 0x158.
  • FUN_080327e0 loads slot n with byte offset (n * 0x14 + 3) * 8 = n * 160 + 24 and length 0xA0.
  • 24 + 3 * 160 = 504, leaving exactly one 8-byte block unused, which is 0xFF in both samples.

Both samples confirm the geometry byte-for-byte: non-0xFF content exists only at 0x00..0x1F (header plus slot 0's cleared first block), 0xB8..0xBF and 0x158..0x15F.

Redundancy, mirroring, generation counters, selection rule

  • There is no mirroring, no backup copy and no A/B generation scheme anywhere in the traced code.

Each region exists exactly once.

  • There is no generation or sequence counter used for slot selection.

The only counter-like change in the samples (bytes 0x0C/0x10 in the global header) is not read by any slot-selection code.

  • The header selection rule is fixed: offset 0, always, validated by word-sum plus 8-byte magic compare (FUN_080323d0).

Failure does not fall back to a copy; it triggers factory initialisation (FUN_0803284c plus slot clearing).

  • The slot selection rule is per-slot validity only.

FUN_08032744 tries each slot up to twice (FUN_080327e0 load, then FUN_080327b4 zero-sum check). The valid/invalid byte is kept at SaveManager + 0x28 + slot. Invalid slots have their 4-byte entry in a slot table zeroed (FUN_080285f0(slot * 4 + table, 0, 4)). Valid slots set SaveManager + 0x30 to the slot buffer pointer and SaveManager + 0x34 to 0, then func_0x080213b8(slot * 4 + table) registers the data.

  • Write reliability is provided at the block level instead: every written 8-byte block is read back and compared (FUN_08043788), with up to 3 attempts per block (FUN_0800a524).

Read blocks likewise retry up to 3 times (FUN_0800a4bc).

3. Save Writer, Reader & Caller-Chain Architecture

How callers were mapped

Two sources were cross-checked for every edge:

  1. callgraph.json (307 functions).
  2. Textual references in decompiled.c, including func_0x........ alias calls.

The callgraph is incomplete for this subsystem. It records no callers for 0x08043628, 0x08043788, 0x08043614, 0x0800a59c, 0x0800a5e4, 0x080327b4, 0x080327e0, 0x08032828 (as caller edges), 0x0803242c, 0x08021390 and 0x08026658. Those edges exist in the decompiled text as func_0x... calls, which the graph builder did not resolve. Every such edge below is marked "text-mapped". Conversely, every graph edge used below was confirmed in the text. Functions whose entry is reached only through a Ghidra UNRECOVERED_JUMPTABLE (indirect state dispatch) are marked "caller unresolved" rather than assigned an invented caller.

Layer 0 — DMA3 hardware driver

0x080434e4 — DMA3 transfer (CONFIRMED_STATIC)

void FUN_080434e4(undefined4 src, undefined4 dst, uint count)
  • Saves the halfword at *_DAT_08043544 and writes 0 to it (interrupt/DMA control save-and-disable).
  • Updates a control register: *_DAT_08043548 = *_DAT_08043548 & (ushort)_DAT_0804354c | *(ushort *)(*_DAT_08043550 + 6).
  • Programs three consecutive DMA3-family registers through _DAT_08043554 (source), _DAT_08043558 (destination) and _DAT_0804355c (control), storing count & 0xFFFF | 0x80000000 (enable bit 31).
  • Polls the high halfword of the control register until busy bit 0x8000 clears.
  • Restores *_DAT_08043544.

This is the only function that touches the DMA channel. Direction is determined by the caller: for EEPROM reads the destination/source pair is (stack buffer, 0x0D000000) then (0x0D000000, stack buffer).

Layer 1 — Nintendo EEPROM_V124 block driver (8-byte blocks)

0x0804349c — IdentifyEeprom / type select (CONFIRMED_STATIC)

  • Parameter 4 selects the first config structure pointer, 0x40 a second, any other value a third (and returns 1); recognised values return 0.
  • The game only ever passes 4 (via FUN_0800a59c), i.e. the 512-byte / 64-block device.
  • The config structure layout used by the readers/writers is: +4 = maximum block address (u16), +8 = serial address bit count (u8).

The struct contents are pointed to by _DAT_ literals not present in this workspace; the 64-block value is inferred from the media size.

0x08043564 — ReadEeprom block (CONFIRMED_STATIC)

void FUN_08043564(uint block_addr, int dest)
  • Masks the address to 16 bits and rejects it when >= *(u16 *)(config + 4).
  • Builds a serial command on the stack: the address is shifted out one bit at a time for config+8 bits, preceded by two 1 bits (start/read framing).
  • First DMA: FUN_080434e4(stack, 0x0D000000, config_bits + 3).
  • Second DMA: FUN_080434e4(0x0D000000, stack, 0x44) — 68 halfword bit samples, i.e. 64 data bits plus framing.
  • Reassembles four u16 values, each from 16 captured bit samples (uVar4 = uVar4 << 1 | *puVar5 & 1), and stores them to dest + 6, +4, +2, +0 (reverse word order).
  • Returns 0 on success.

0x08043628 — WriteEeprom block (CONFIRMED_STATIC)

void FUN_08043628(uint block_addr, ushort *src /* 4 words */, char wait_flag)
  • Same address range check as the reader.
  • Expands the four source words (64 bits) plus the address bits into a serial bitstream with framing bits 1, 0.
  • DMA: FUN_080434e4(stack, 0x0D000000, config_bits + 0x43).
  • Busy-wait: polls bit 0 of 0x0D000000 against a timer register (_DAT_08043714, wrap value 0xE4) with an accumulated timeout of 0x88; the loop repeats while wait_flag != 0.

0x08043614 — WriteEeprom with wait (CONFIRMED_STATIC, text-mapped)

Thin wrapper: return FUN_08043628(addr, data, 1);

0x08043788 — VerifyEeprom block (CONFIRMED_STATIC, text-mapped caller)

  • Reads the block back with FUN_08043564 into a stack buffer.
  • Compares the four s16 words against the supplied data.
  • Returns 0 on match, 0x8000 on first mismatch.

Layer 2 — Game EEPROM session and byte-range wrappers

0x0800a59c — EEPROM session begin (CONFIRMED_STATIC, text-mapped)

  • Saves two hardware registers via _DAT_0800a5c8/_DAT_0800a5d0 (WAITCNT family), writes a type value to one of them and clears the other.
  • Calls FUN_0804349c(4) and returns whether it returned 0.

0x0800a5e4 — EEPROM session end (CONFIRMED_STATIC, text-mapped)

Restores the two registers saved by FUN_0800a59c.

0x0800a4bc — EEPROM read bytes (CONFIRMED_STATIC)

void FUN_0800a4bc(uint byte_offset, uint byte_length, int dest)
  • Converts offset and length to blocks with >> 3.
  • Opens a session (FUN_0800a59c); if identification fails, returns 0.
  • For each block: calls FUN_08043564 (as func_0x08043564) with up to 3 retries while it returns non-zero; destination advances 8 bytes, block advances 1.
  • Closes the session (FUN_0800a5e4); returns 1 on success.

Callers (callgraph-confirmed): 0x08032364, 0x080323d0, 0x080327e0.

0x0800a524 — EEPROM write bytes with verify (CONFIRMED_STATIC)

  • Same block conversion and session handling.
  • For each block: func_0x08043614(block, src) (write with wait), then func_0x08043788(block, src) (verify), up to 3 attempts per block (text-mapped edges).
  • Returns 1 on success.

Callers (callgraph-confirmed): 0x08032364, 0x0803242c, 0x0803284c.

Layer 3 — Checksum core

0x08032828 — Sum16 (CONFIRMED_STATIC)

short FUN_08032828(short *data, uint byte_length)
{
    short sum = 0;
    for (n = byte_length >> 1; n != 0; n--) sum += *data++;
    return sum;
}

Sums byte_length / 2 signed 16-bit words with 16-bit truncation. Valid headers and (by validation code) valid slots sum to 0. Callers: 0x08032364 (header), 0x080327b4 (slot), both text-mapped; also open-coded as an identical loop in 0x080323d0 and 0x0803284c.

Layer 4 — Game save manager (header)

The save manager is a RAM struct (absolute address unresolved, see Section 5). Its first 24 bytes are the header image; offset +0x18 holds a pointer to a 160-byte slot buffer; +0x28..+0x2A holds per-slot valid bytes; +0x30/+0x34 hold slot-consumption pointers.

0x080323d0 — ValidateHeader (CONFIRMED_STATIC)

  1. FUN_0800a4bc(0, 0x18, header_RAM) reads the header.
  2. Sums the 12 words; if the sum is not 0, returns 0.
  3. Byte-compares the first 8 RAM bytes against the expected magic string at iRam08032428; any mismatch returns 0.
  4. Otherwise returns the read-success flag.

Caller: 0x0803242c (callgraph-confirmed).

0x0803284c — CreateDefaultHeader (CONFIRMED_STATIC, text-mapped)

  1. FUN_080289d8(header_RAM, ROM_template, 0x18) copies the 24-byte factory header.
  2. Sums the 12 words and stores -sum at header[11] (byte offset 0x16).
  3. FUN_0800a524(0, 0x18, ...) writes the header (third argument elided by Ghidra; contextually the header RAM).

Caller: 0x0803242c.

0x08032364 — FlushHeaderIfChanged (CONFIRMED_STATIC)

  1. Reads the current EEPROM header into a stack buffer (FUN_0800a4bc(0, 0x18, &stack)).
  2. Zeroes RAM header + 0x16, recomputes FUN_08032828(header, 0x18), stores -sum at +0x16.
  3. Compares RAM header against the EEPROM copy as six u32 values.
  4. If different, writes via FUN_0800a524(0, 0x18, header_RAM) and returns 1; otherwise returns 0.

Caller: 0x08020688 (text-mapped).

0x08020688 — PackSettingsAndFlushHeader (CONFIRMED_STATIC)

Copies fields from a separate settings struct into the header RAM, then flushes:

Caller: 0x08026658 (callgraph-confirmed). FUN_08026658 is a state/menu handler: in the relevant branch it sets a settings word to 0x14, clears another field, and calls FUN_08020688(). Its own caller is unresolved (indirect dispatch).

0x08021390 — UnpackHeaderToSettings (CONFIRMED_STATIC, reader)

Exact inverse of FUN_08020688: settings + 0x11 = header + 0x09, settings + 0x10 = header + 0x08, settings + 0x12 = header + 0x0D >> 7, settings + 0x13 = header + 0x0A, settings + 0x60 = header + 0x11. No textual or callgraph caller exists in the 307 functions (caller unresolved). The nearby FUN_08021374 initialises the same settings struct (+0x10 = 6, +0x11 = 6, +0x12 = 0, +0x13 = 0) after FUN_0801f17c() and is consistent with a defaults path.

Layer 5 — Game save manager (slots and init)

0x0803242c — SaveInit (CONFIRMED_STATIC, entry; caller unresolved)

  1. FUN_08028874(0xA0) allocates a zeroed 160-byte buffer (allocator that memsets via FUN_080285f0); stores it at SaveManager + 0x18.
  2. Calls the empty stub FUN_0800a4b4().
  3. FUN_080323d0() validates the header.
  4. On failure: FUN_0803284c() (create/write default header), FUN_08032494() (memset slot buffer to 0), then for slot = 0..2: FUN_0800a524(0x18 + slot * 0xA0, 8, slot_buffer) — only the first block of each slot is written.
  5. FUN_080384b0(*(u8 *)(SaveManager + 10)) applies header byte 10 as a table index (value 0 stores byte 0x2C, value 1 stores byte 0x2E elsewhere; semantics hypothesised as locale/language selection).
  6. FUN_08032744() loads all slots.

This function alone explains every non-header byte in both samples: the 8-byte zero blocks at 0x18, 0xB8 and 0x158.

0x08032494 — ClearSlotBuffer (CONFIRMED_STATIC, text-mapped)

FUN_080285f0(*(SaveManager + 0x18), 0, 0xA0) — RAM-only memset, not an EEPROM erase.

0x080327e0 — LoadSlot (CONFIRMED_STATIC, text-mapped)

FUN_0800a4bc((slot * 0x14 + 3) * 8, 0xA0, *(SaveManager + 0x18)).

0x080327b4 — ValidateSlot (CONFIRMED_STATIC, text-mapped)

Computes FUN_08032828(slot_buffer, 0xA0), stores (sum == 0) at SaveManager + 0x28 + slot, and returns it.

0x08032744 — LoadAllSlots (CONFIRMED_STATIC, text-mapped)

For slot = 0..2, with up to 2 load/validate attempts per slot: if the valid byte at SaveManager + 0x28 + slot is 0, zero the slot's 4-byte table entry; otherwise set SaveManager + 0x30 = slot_buffer, SaveManager + 0x34 = 0 and call func_0x080213b8(slot * 4 + table).

Caller: 0x0803242c (both a FUN_ reference and text-mapped).

What is missing

  • No slot serializer exists in the traced corpus.

An exhaustive textual search for FUN_0800a524/func_0x0800a524 finds only the header writes and the 8-byte slot-clearing writes. An exhaustive search for 0xA0 finds only the allocator, the buffer clear, LoadSlot and ValidateSlot. Therefore a populated slot's writer — and whoever recomputes a slot checksum before writing — is outside the 307 functions or behind an unrecovered indirect call. This is stated as a gap, not bridged by invention.

  • No function stores individually to header offsets +0x0C or +0x10.

Their observed change (Section 5) must be produced by code outside the traced set, or by a struct copy not visible in the decompilation.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic signature

OffsetBytes (hex)ASCIIVerified in codeVerified in .sav
0x0034 34 30 30 41 42 47 434400ABGCYes — FUN_080323d0 8-byte compare against the expected string at iRam08032428Yes — both samples

The literal expected string is a ROM/RAM pointer value (iRam08032428) in the decompilation, so the code-side characters cannot be read from the text alone. The identity is established jointly: the validator compares exactly 8 bytes after a successful checksum, and the only 8-byte ASCII string present at that position in both real saves is 4400ABGC. The PACKET save profile independently lists 4400ABGC as the sole ASCII magic string.

Header checksum — formula

covered range : file offsets 0x00 .. 0x17 inclusive (24 bytes, 12 words)
stored offset : file offset 0x16, 2 bytes
algorithm     : negated sum of 16-bit words (sum16 with two's-complement store)
validity rule : sum(all 12 words) mod 65536 == 0
store rule    : stored = (-sum(other 11 words)) mod 65536

Decompiled proof:

  • FUN_08032828 (0x08032828): sums byte_length >> 1 signed 16-bit words with 16-bit truncation.
  • FUN_080323d0: sVar2 += *psVar4 over 12 words starting at the header; the header is accepted only when sVar2 == 0 (followed by the magic compare).
  • FUN_0803284c: after copying the template, sums the 12 words and executes _DAT_08032888[0xb] = -sVar2 — signed-word index 11, i.e. byte offset 0x16.
  • FUN_08032364: *(u16 *)(header + 0x16) = 0; sVar2 = FUN_08032828(header, 0x18); *(s16 *)(header + 0x16) = -sVar2; then flushes if the header changed.

Endianness — an honest note

The code sums little-endian ARM s16 loads from the RAM image. The .sav file bytes verify only when the same 24 bytes are interpreted as big-endian u16 words:

  • Big-endian interpretation: sum = 0x0000 in both samples; stored 0x0100 matches the computed negation exactly.
  • Little-endian interpretation: sum = 0x02FD in both samples; stored 0x0001 does not match.

The transformation between the RAM image and the emulator's .sav file is performed by the EEPROM serial layer: both the read function (FUN_08043564, which stores reassembled words to dest + 6 .. dest + 0) and the write function (FUN_08043628, which expands words into an MSB-first serial bitstream) impose a word-level ordering that the decompiled text does not fully resolve into a byte-level rule. The magic, notably, reads as plain ASCII in file order, so no naive whole-file byte swap is claimed. What is claimed is exactly what was executed: in file domain the negated big-endian word-sum holds perfectly on both real samples (output below), and in code domain the negated word-sum store at +0x16 is explicit. Determining the precise RAM↔file byte permutation requires the paired emulator state or the ROM template bytes, neither of which is in this workspace. This is listed as an open question in save-format.json.

A secondary coincidence is explicitly not claimed as the algorithm: the plain byte-sum over 0x00..0x11 is also 0x00 mod 256 in both samples. The code contains no byte-sum over the header; the word-sum is the code-proven algorithm.

Slot checksum — what is and is not proven

Proven by code (CONFIRMED_STATIC): FUN_080327b4 sets a slot's valid flag exactly when FUN_08032828(slot_buffer, 0xA0) == 0, i.e. when the 80 signed words of the 160-byte slot sum to zero.

Not proven: the stored word's position inside the slot, and any file-domain endianness. By header analogy the candidate stored offset is slot_base + 0x9E (last word), but no traced function stores it, and both samples contain only cleared slots whose word-sum is 0xFFB4 ≠ 0 under either endianness (all slot words are 0x0000 or 0xFFFF, which are endian-symmetric, so the samples cannot distinguish). It is recorded as HYPOTHESIS in save-format.json and must not be treated as verified.

Key observations from this output:

  • Computed versus stored checksum matches on both samples (0x0100 = 0x0100).
  • The two changed bytes compensate exactly: word 6 gains 0x0100 (BE) while word 8 loses 0x0100 (BE), leaving the stored checksum unchanged.

The same compensation holds in little-endian byte terms (+1 at 0x0C, -1 at 0x10). Byte 0x10 is therefore data covered by the checksum, not the checksum itself — a common misreading that the diff alone would suggest.

  • Every slot's word-sum is 0xFFB4 ≠ 0, confirming via the game's own validity rule that all slots are empty.
  • The PACKET probe mutated offset 0xC, which is inside the covered range 0x00..0x15.

Any single-byte change there breaks the zero sum, so FUN_080323d0 rejects the header and FUN_0803242c rewrites a blank/factory save — exactly the reported reverted_to_blank_on_mutation and save_rewritten_after_mutation.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for all header mutations: after changing any byte in 0x00..0x15, recompute the header checksum in file domain and store it at 0x16 — interpret 0x00..0x17 as 12 big-endian u16 words, set the last word to (-sum(first 11 words)) mod 65536, and write those two bytes big-endian at 0x16. (If a future RAM capture resolves the RAM↔file byte permutation differently, apply the same negation in that domain instead; the file-domain rule above is the one verified on both samples.) No paired .ss save states were provided in this workspace (states/ is empty), so every prediction below is phrased for reloading the mutated .sav from a cold boot in the same emulator setup used for the PACKET probe, observing (a) whether the .sav file is rewritten, (b) the boot/UI result, and (c) where available the RAM valid bytes at SaveManager+0x28..0x2A.
