GBA Save Format Report — Harry Potter and the Prisoner of Azkaban (USA, Europe) (En,Fr,De,Es,It,Nl,Da)

Clean-room analysis. Sources used only: PACKET.md, saves/cap-00-future-0.sav, saves/cap-01-retained-3.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (220 functions), ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware facts stated in PACKET.md. No third-party game-specific material was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Save media is EEPROM, 8192 bytes total in the .sav image, transferred only through the serial EEPROM DMA3 path at 0x0D000000. No SRAM (0x0E000000) or Flash 0x5555/0x2AAA command code exists anywhere in ghidra/decompiled.c (grep for 0xe000000, 5555, 2aaa returns no hits; the only 0xd000000 references are in FUN_08049f8c and FUN_0804a050).
  • The 8192-byte EEPROM is partitioned exactly as: 16-byte header record (blocks 0–1), 40-byte global/profile record (blocks 2–6), then 3 save slots of 2712 bytes each (339 blocks each). 56 + 3 × 2712 = 8192, ending exactly at block 1024. Slot heads observed at file offsets 0x38, 0xAD0, 0x1568 differ by 0xA98 = 2712 bytes.
  • Header magic is the 8 ASCII bytes 100AOPPH at offset 0x00, checked byte-by-byte in FUN_0803c244.
  • Header integrity is a 16-bit additive zero-sum checksum (see §4). In .sav byte space it verifies as big-endian-word sum ≡ 0 (mod 65536) on both samples, including across the 2-byte inter-sample mutation, which is exactly compensating (0x09: ED→6D, 0x0F: 00→80).
  • Both samples are blank/formatted saves: header valid, global record all zero (trivially checksum-valid), each slot has only its first 16 bytes zero-written and the remaining 2696 bytes still erased (0xFF). Total non-0xFF bytes = 104 in each file, matching PACKET.md.

Static-only (CONFIRMED_STATIC, code seen but no populated .sav sample to verify against bytes):

  • The full writer/reader/checksum call chains in §3, the EEPROM 8-byte block read/write/verify drivers, the write-retry-3 policy, and the per-slot validity-flag handling in FUN_0803bc08.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • Slot payload layout beyond the 16-byte zeroed head: no populated slot exists in the corpus, so no slot field can be mapped.
  • The exact byte-length argument passed to the slot checksum call in FUN_0803c0a8 (the literal behind _DAT_0803c0d8 is not resolved in the decompilation; candidates are the full 2712-byte slot or a smaller prefix — see §4).
  • All RAM mirror addresses: Ghidra _DAT_0803xxxx literal-pool values are not present in the workspace files, so no 0x02xxxxxx/0x03xxxxxx address can be stated honestly.
  • Callers above FUN_0803bc9c and FUN_0803c114: neither callgraph.json nor the decompiled bodies contain a recovered call site (calls arrive through unrecovered jumptables / function pointers).

How the geometry was derived: FUN_0803c0dc(slot) reads from EEPROM block _DAT_0803c0f0 * slot + 7 for _DAT_0803c0f0 blocks, and the format loop in FUN_0803bc9c writes 2 blocks at block 7, stepping by _DAT_0803bd00, 3 times. The literal values behind those _DAT_ symbols are not in the workspace, but the .sav bytes fix them uniquely: non-0xFF islands sit at 0x38, 0xAD0, 0x1568 (stride 0xA98 = 2712 B = 339 blocks), and 7 blocks × 8 + 3 × 2712 = 8192 exactly. Any other stride fails to land on the observed islands or overflows the device. Geometry is therefore CONFIRMED_VERIFIED; the code-side literal identity (_DAT_0803c0f0 == _DAT_0803bd00 == 339) is CONFIRMED_STATIC inference from the shared formula shape.

Redundancy: there is no mirrored/backup copy of any record. Redundancy is instead:

  • Write-verify-retry: FUN_0804a280 retries write+verify up to 3 times per 8-byte block (see §3).
  • Header canonical-copy rewrite: FUN_0803c114 compares EEPROM header against the RAM canonical header (4×u32 compare) and rewrites EEPROM if different (returns 1 when it rewrote).
  • Boot re-format fallback: FUN_0803bc9c reformats header + global record + slot heads if header validation fails, and rewrites the global record alone if its checksum fails.
  • No generation/sequence counter was found in any record. The header payload words at 0x08–0x0D are the only candidate counter space; in the two samples they are identical except for the probe-mutated byte at 0x09, so no counter behaviour can be claimed (UNKNOWN).

Selection rule: all 3 slots are always read at boot (FUN_0803bc08 loops slots 0,1,2); each gets a validity flag at RAM save-struct +0x60 + slot×4 from the slot checksum. There is no "newest slot wins" logic in the recovered code — slots are independent, menu-facing entries, not rotating backups.

State of both samples: freshly formatted / blank-progress saves. Slot bodies are still 0xFF past byte 16, so these files prove the format/boot path, not gameplay progress fields.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

ghidra/callgraph.json is incomplete for this corpus: most of its 220 nodes have empty caller/callee lists because Ghidra could not recover the Thumb jumptable tails (WARNING: Could not recover jumptable, UNRECOVERED_JUMPTABLE) that terminate almost every function. Two evidence sources were therefore combined:

  1. callgraph.json edges where present (reliable where non-empty, e.g. the EEPROM seed cluster 0x08049f0c ← 0x08049f8c, 0x0804a050).
  2. Direct func_0x080…(...) call sites inside decompiled bodies in ghidra/decompiled.c (Ghidra emits these for calls whose target it did not name FUN_…). Every such site was enumerated with grep -n "func_0x0803c\|func_0x08049\|func_0x0804a" ghidra/decompiled.c. This recovers the whole save-manager layer that callgraph.json shows as callerless (e.g. FUN_0804a280 has callers: [] in JSON but is called at decompiled.c:5008 inside FUN_0803c348).

Any edge below is labelled with its source. Edges that exist in neither source are reported as unrecovered, not invented.

3.1 Low-level hardware I/O driver (EEPROM serial via DMA3)

All addresses are code addresses (0x08xxxxxx).

  • FUN_08049f0c(src, dst, count) — DMA3 transfer engine. Saves/restores an interrupt/DMA control register (*_DAT_08049f6c), programs DMA source (*_DAT_08049f7c = param_1), destination (*_DAT_08049f80 = param_2), and count/control (*_DAT_08049f84 = param_3 & 0xFFFF | 0x80000000, DMA enable bit 31), then spins while the DMA busy bit (0x8000 of the control high halfword) is set. This is the 0x040000D4-family DMA3 register block referenced via literal-pool pointers. Callers: FUN_08049f8c, FUN_0804a050 (both sources agree).
  • FUN_08049f8c(block, ram_ptr) — EEPROM read 8 bytes. Rejects block >= *(ushort *)(device_struct + 4) (device block count). Builds a read-command + address bitstream on the stack (address bits shifted out MSB-first, framed by 1,1 start bits), DMAs it to 0x0D000000 (length = address-bits + 3), then DMAs 0x44 = 68 halfwords back from 0x0D000000 (64 data bits + 4 dummy bits) and reassembles 4×u16, MSB-first (uVar4 = uVar4 << 1 | bit), storing them from ram_ptr + 6 downwards. Caller: FUN_0804a1b0 (verify) and FUN_0803c318 (block reader).
  • FUN_0804a050(block, ram_ptr, wait_flag) — EEPROM write 8 bytes. Serialises 4×u16 from ram_ptr plus the block address into a 130-byte stack bitstream (MSB-first), DMAs it to 0x0D000000 (length = address-bits + 0x43), then polls the EEPROM data line (uRam0d000000 & 1) with a timer-based timeout (0x88 tick budget measured against *_DAT_0804a13c) to wait out the internal write cycle; returns a timeout/error value when the budget expires. Caller: FUN_0804a248 only.
  • FUN_0804a1b0(block, ram_ptr) — verify: reads the block back via FUN_08049f8c into a stack buffer and compares 4×i16 against ram_ptr; returns 0x8000 on first mismatch, 0 on match. Caller: FUN_0804a280.
  • FUN_0804a248(block, ram_ptr) — write wrapper: if the device-type word *(int *)*_DAT_0804a270 != 0x200, forwards to FUN_0804a050(block, ram_ptr, 0); otherwise skips (returns the uninitialised success value). Caller: FUN_0804a280.
  • FUN_0804a280(block, ram_ptr) — write-with-verify, retry ×3: loops at most 3 times { FUN_0804a248 write; if ok, FUN_0804a1b0 verify; break on verify ok }. This is the only block-write entry point used above the driver. Caller: FUN_0803c348 (decompiled.c:5008; callgraph.json misses this edge).

There is no erase function (EEPROM needs none; 0xFF in the file is the emulator's never-written state, and the game never writes it — slot bodies stay 0xFF until gameplay writes them). There is no SRAM byte-copy and no Flash command sequence anywhere in the corpus.

3.2 Block serialisation layer

  • FUN_0803c318(start_block, block_count, ram_ptr) — multi-block read: calls FUN_0803c378 (bus setup), then loops FUN_08049f8c(block, ram_ptr) stepping block++, ram_ptr += 8, then FUN_0803c3a8 (bus restore). Call sites: FUN_0803c0dc (slot read), FUN_0803c114 (header read), FUN_0803c244 (header validate), FUN_0803c2e0 (global validate) — all via func_0x0803c318 references.
  • FUN_0803c348(start_block, block_count, ram_ptr) — multi-block write: same framing, looping FUN_0804a280(block, ram_ptr) (write+verify×3 per block). Call sites: FUN_0803bc9c (slot-head format), FUN_0803c114 (header rewrite), FUN_0803c204 (header format; Ghidra drops the 3rd argument in its rendering at decompiled.c:4869 but the parallel call at :4813 shows (0, 2, _DAT_0803c174)), FUN_0803c29c (global write).
  • FUN_0803c378() — bus setup before EEPROM access: saves WAITCNT-family state (*_DAT_0803c398 = *_DAT_0803c39c, *_DAT_0803c3a0 = (short)_DAT_0803c3a4, *puVar1 = 0) and calls FUN_08049ec4(0x40) (the param == 0x40 branch writes *_DAT_08049eec = _DAT_08049ef0, i.e. selects the slow EEPROM wait-state timing, cf. WAITCNT 0x04000204). Caller: both functions above.
  • FUN_0803c3a8() — bus restore: *_DAT_0803c3b4 = *_DAT_0803c3b8.

Helpers used by the managers (identified by body, CONFIRMED_STATIC): FUN_0802c4bc(dst, src, len) = memcpy, FUN_0802c450(ptr, value, len) = memset, FUN_0802c2ec(size) = zeroing malloc (aligns to 16, zeroes via FUN_0802c450), FUN_0802c26c(size) = malloc.

3.3 Checksum / validation routines

  • FUN_0803c1e0(short *buf, uint byte_len) — the sole checksum primitive: count = byte_len >> 1; sum = Σ buf[i] accumulated in an i16 (wraps mod 65536). Callers: FUN_0803c0a8, FUN_0803c114 (via func_0x0803c1e0).
  • FUN_0803c244() — header validate: FUN_0803c318(0, 2, buf); sums 8×i16 over the 16 bytes; if sum == 0, byte-compares the first 8 bytes against an expected 8-byte string (iRam0803c294 vs iRam0803c298, loop iVar3 < 8); returns 1 valid / 0 invalid. Caller: FUN_0803bc9c.
  • FUN_0803c2e0() — global-record validate: FUN_0803c318(2, 5, buf) (40 bytes at blocks 2–6); sums 20×i16; returns sum == 0. Caller: FUN_0803bc9c.
  • FUN_0803c0a8(slot) — slot validate: s = FUN_0803c1e0(*(save_struct + 0x38), _DAT_0803c0d8); stores (s == 0) as u32 at save_struct + 0x60 + slot×4; returns that flag. The length literal _DAT_0803c0d8 is unresolved (see §4). Caller: FUN_0803bc08.

3.4 Record managers (writers)

  • FUN_0803c204() — format header: memcpy 16-byte template (FUN_0802c4bc(_DAT_0803c23c, _DAT_0803c240, 0x10)), sums 8×i16 (template's checksum word starts zeroed), stores -sum at word index 7 (byte offset 0x0E, confirmed by the explicit +0xE form in FUN_0803c114), writes blocks 0–1 via FUN_0803c348(0, 2, …). Caller: FUN_0803bc9c (only when header invalid).
  • FUN_0803c114() — header sync: reads EEPROM header to stack, recomputes the RAM canonical header's checksum (zero word at +0xE, FUN_0803c1e0(buf, 0x10), store -sum at +0xE), compares RAM vs EEPROM as 4×u32; if equal returns 0, else writes RAM header via FUN_0803c348(0, 2, _DAT_0803c174) and returns 1. No caller recovered in either source (UNKNOWN caller; likely a save-trigger path reached by pointer).
  • FUN_0803c29c() — write global record: memcpy 40-byte template (FUN_0802c4bc(_DAT_0803c2d4, _DAT_0803c2d8, 0x28)), sums 20×i16 over the RAM struct window, stores -sum at struct + 0x36 (record offset 0x26 = last word of the 40-byte record whose EEPROM image starts at struct + 0x10), writes via FUN_0803c348(2, 5, struct + 0x10). Callers: FUN_0803bc9c (twice: format path and global-checksum-repair path).
  • FUN_0803bd2c() — clears the slot RAM buffer: memset *(save_struct + 0x38) to 0 for _DAT_0803bd44 bytes. Caller: FUN_0803bc9c format path.

3.5 Boot / orchestration chain (the main caller chain)

FUN_0803bc9c() — save-system boot init. Caller unrecovered (no edge in callgraph.json, no func_0x0803bc9c call site; reached via pointer/jumptable). Sequence, with how each step mutates RAM state before any flush:

  1. Allocates the save-struct's data buffer: *(save_struct + 0x38) = FUN_0802c2ec(_DAT_0803bcf8) (zeroed allocation; this pointer is the slot/global RAM work buffer used below).
  2. iVar2 = FUN_0803c244() — validate header (EEPROM → RAM stack/buffer, checksum + magic). No RAM mutation on success.
  3. If header invalid (iVar2 == 0): FUN_0803c204() (format+write header), FUN_0803c29c() (format+write global record), FUN_0803bd2c() (zero the RAM slot buffer), then writes a 16-byte zero head to each slot: loop block = 7; ×3 { FUN_0803c348(block, 2, *(save_struct + 0x38)); block += _DAT_0803bd00; } — this is exactly the 16 zero bytes observed at 0x38, 0xAD0, 0x1568, with the rest of each slot left 0xFF.
  4. iVar3 = FUN_0803c2e0() — validate global record; if invalid, FUN_0803c29c() rewrites it from template.
  5. FUN_08042588(*(byte *)(save_struct + 8) & 0x7F) — applies a locale/language index (this function stores the index and picks a decimal-separator glyph 0x20/0x2E/0x2C by range; the link from save-struct byte +8 to the header payload is HYPOTHESIS, see §5).
  6. FUN_0803bc08() — per-slot scan (below).

FUN_0803bc08() — slot scan, for slots 0,1,2: retries { FUN_0803c0dc(slot) (read whole slot: FUN_0803c318(339×slot + 7, 339, *(save_struct + 0x38)) per the geometry of §2); FUN_0803c0a8(slot) (checksum → validity flag at save_struct + 0x60 + slot×4) } until valid or retries exhausted (loop decrements iVar7 from 0, so at most 2 attempts). If the flag is 0 (invalid/empty): memsets 12 bytes at a per-slot menu struct (FUN_0802c450(puVar2 + slot×3 - 0x11, 0, 0xC)). If valid: records *(save_struct + 0x70) = *(save_struct + 0x38), clears save_struct + 0x74, and calls func_0x08021604(...) on the slot's menu entry. On the blank samples every slot's body is 0xFF, so under the full-slot-length checksum candidate every slot takes the invalid branch (full-slot sum = 0xFABC ≠ 0, §4).

FUN_0803bd04() — updates save-struct byte +8: byte = (old & 0x80) | (FUN_080425d8() & 0x7F) | 0x80 in effect (bit 7 always set, low 7 bits = current locale from FUN_080425d8(), a getter for *_DAT_080425e0). No caller recovered. It mutates only RAM; persistence would require a later FUN_0803c114/FUN_0803c204 header write (not observed in the recovered graph — HYPOTHESIS).

No other function in the 220-function corpus calls the block read/write layer. In particular there is no recovered gameplay "save game" writer that fills a slot body: within this workspace the only slot writes are the 16-byte zero heads in the format path. Slot-body writes either live in functions whose call edges Ghidra did not recover, or the corpus's trace-guided subset does not include the trigger path. This is stated as an open question, not filled in by guesswork.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

100AOPPH (bytes 31 30 30 41 4F 50 50 48) at file offset 0x00, size 8. Verified in code: FUN_0803c244 byte-compares the first 8 EEPROM-read bytes against an expected 8-byte string after the checksum passes. Verified in .sav: both samples start with exactly these bytes. Note the ASCII reads as 100AOPPH — plausibly a format/version tag (100A + OPPH?) — but any expansion is speculation and is not claimed.

4.2 Algorithm (from code)

Primitive FUN_0803c1e0(buf, byte_len): 16-bit wrapping sum of byte_len/2 signed 16-bit words. Writers store the two's-complement negation in the record's last word so that the whole record sums to zero; validators (FUN_0803c244, FUN_0803c2e0, FUN_0803c0a8) check sum == 0. No CRC, no XOR-fold, no seed, no complement beyond the negation. Covered ranges:

  • Header: bytes 0x00–0x0F, checksum stored at 0x0E–0x0F (word 7). Proof: FUN_0803c114 zeroes +0xE, calls FUN_0803c1e0(buf, 0x10), stores -sum at +0xE.
  • Global record: bytes 0x10–0x37 (40 B, EEPROM blocks 2–6), checksum at record offset 0x26 (file 0x36–0x37). Proof: FUN_0803c29c stores -sum at struct + 0x36 and writes struct + 0x10 for 5 blocks; FUN_0803c2e0 sums 20 words after FUN_0803c318(2, 5, …).
  • Slot: checksum call FUN_0803c1e0(*(save_struct + 0x38), _DAT_0803c0d8) — length literal unresolved in the workspace. Candidate A: full slot (2712 B). Candidate B: a prefix (e.g. the 16-B head). See verification below.

4.3 .sav-space byte order (important)

The game sums 16-bit words from its RAM buffer. In .sav file space the zero-sum identity holds only when words are read big-endian; the little-endian reading sums to 0x01FE on both files and is falsified. This is consistent with the drivers' MSB-first serial packing (FUN_08049f8c reassembles uVar4 = uVar4 << 1 | bit; FUN_0804a050 serialises MSB-first): the emulator's linear EEPROM image preserves the serial byte order, which swaps each RAM word's bytes in the file. Word order within a block cannot be distinguished by a sum and is not claimed. All verification below is therefore done in file space with >H words — the only space a .sav editor ever sees.

Interpretation:

  • Header checksum: CONFIRMED_VERIFIED on 2/2 samples. Stored (0x0A00, 0x0A80) equals computed -Σ(first 7 BE words) in both files.
  • The inter-sample diff is exactly compensating under this checksum: byte 0x09 (ED→6D, Δ −0x80 in BE word 4) and byte 0x0F (00→80, Δ +0x80 in the stored checksum word). This matches the PACKET.md cold-reload probe (mutation at 0x09, integrity check confirmed, save retained and not reverted to blank): the mutated file still passes FUN_0803c244's zero-sum, so the boot path in FUN_0803bc9c does not take the reformat branch. Who updated byte 0x0F (game checksum repair via a header rewrite, or the capture pipeline) cannot be distinguished from the workspace files — UNKNOWN; the checksum-preservation itself is verified arithmetic.
  • Global record checksum: verifies trivially (record is all zero; stored 0x0000, sum 0x0000). CONFIRMED_VERIFIED but weak evidence — an all-zero record passes any additive checksum. Its non-trivial proof rests on the code in FUN_0803c29c/FUN_0803c2e0 (CONFIRMED_STATIC for the formula).
  • Slot checksum: head-16 sum is 0x0000 (passes candidate B trivially, also all-zero), full-slot sum is 0xFABC ≠ 0 (fails candidate A — expected for an erased/empty slot, consistent with FUN_0803bc08 treating blank slots as invalid/empty). With only blank slots in the corpus, the length literal cannot be decided from bytes. HYPOTHESIS.

Checksum repair formula for editors (file space): stored_BE_word = (-sum(BE words of record with checksum word zeroed)) & 0xFFFF, written big-endian at the checksum offset; equivalently make the whole record's BE-word sum ≡ 0.
