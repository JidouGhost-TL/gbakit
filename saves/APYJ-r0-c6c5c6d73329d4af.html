1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM, asymmetric across layers:

  • HIGH / verified for the physical save media, block geometry, and the low-level

EEPROM hardware driver (write-with-verify-retry loop). This is proven both by the decompiled code and by direct arithmetic on the .sav byte layout.

  • MEDIUM (static-only) for the gross field boundaries of the 512-byte record

(magic string location, score-like table, two small-integer tables, a packed flag region, and an unwritten tail) — these are proven by byte-pattern analysis of the

only non-blank .sav sample, but not cross-checked against a second independent mutation, so field boundaries could be off by a few bytes at the edges.

  • LOW / open for the meaning of individual fields (score table semantics, the two

small-table codomains, the 2-byte values at 0x0C–0x0F and 0x1BE–0x1BF), and for checksum/integrity logic: no checksum, CRC, or sum/XOR routine was found anywhere in the 112-function decompiled corpus that touches this save buffer. The two candidate 16-bit values that could be a checksum (0x2E55 at 0x0C, 0x10A5 at 0x0E, 0x7EFF at 0x1BE) were tested against sum8/sum16/xor8/xor16 (both endiannesses) over every plausible covered range, and none matched. This is reported honestly as UNKNOWN, not asserted as a format fact.

  • The call chain above the hardware driver (i.e., what in-RAM struct is being

serialized, and what caller builds it before the final EepromWrite-style call) is not present in the traced callgraph — ghidra/callgraph.json shows the write-verify entry point 0x08023888 has "callers": []. The trace only captured the hardware I/O library in isolation; the game-specific "save manager" that populates the in-RAM buffer and triggers the flush is out of scope for this packet and remains an open question (see §6).

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K, matching the packet metadata (save_media_type) and

independently confirmed by the driver code (see §3): the block-address checks in FUN_08023754/FUN_080236a4 gate param_1 (the EEPROM block index) against a runtime-loaded bound, and the per-block payload is a fixed 64-bit (8-byte) bitstream (FUN_08023754 shifts out exactly 4 * 16 = 64 data bits per block, matching the EEPROM 8-byte/block protocol). 64 blocks * 8 bytes/block = 512 bytes, exactly the observed .sav file size.

  • Total .sav size: 512 bytes (both samples).
  • SDK save tags in ROM: none detected (per packet metadata).
  • Active (non-fill) byte ranges in the one populated sample (cap-01-future-1.sav,

fill byte 0x00):

  • 0x0000–0x01BF (448 bytes) — the primary record (magic, tables, flags).
  • 0x01DB–0x01FF (37 bytes) — a short tail region, itself mostly zero-filled with a

5-byte non-zero sub-field at 0x01DB–0x01DF, followed by bytes that are still 0xFF (the EEPROM blank/erased value) from 0x01E0 onward.

  • 0x01C0–0x01DA (26 bytes) is all 0x00, matching this sample's dominant fill

byte, so it is not flagged "active" by the byte-range tool, but it sits between two written regions and is therefore read as reserved/padding, not proof of emptiness. CONFIRMED_STATIC.

  • Slot/copy count: Only one candidate save record is visible across the two

samples (cap-00 is fully blank/erased 0xFF; cap-01 has the single record described above). There is no evidence of a second mirrored/backup copy inside the 512-byte space — the record plus its trailing padding/tail already consumes bytes 0x0000 through 0x01DF (480 of 512 bytes, i.e. EEPROM blocks 0–59 of 0–63). Blocks 60–63 (0x01E0–0x01FF) are 0xFF in both samples, i.e. never written in this 2-sample corpus.

  • Confidence: HYPOTHESIS. With only one non-blank sample we cannot rule out a

second profile/slot that simply was never created by this capture run, or that blocks 60–63 are written only under some condition not exercised here (see open questions, §6).

  • Mirroring / redundancy / generation counters: No second copy of the 448-byte

record is present anywhere in the 512-byte file, so there is no redundant mirrored copy to compare against for self-healing/rollback. No obvious sequence/generation counter field was identified (see §5 for the closest candidates, both low-confidence).

  • Selection rule: Not applicable / not observed — with a single record and no

second copy, there is nothing to "select between."

3. Save Writer, Reader & Caller-Chain Architecture

All addresses below come from ghidra/decompiled.c / ghidra/save_related_functions.c and are cross-checked against ghidra/callgraph.json. This is a generic GBA EEPROM hardware I/O library (DMA3 bit-serial protocol) — nothing about its internals is game-specific; it matches the well-known public shape of EEPROM read/write/verify helpers built on REG_DMA3 (0x040000D4) and the EEPROM data port at 0x0D000000.

3.1 Low-level hardware I/O driver

  • FUN_08023624(void *src, void *dst, uint count_and_flags) @ 0x08023624

(callers: 0x080236a4, 0x08023754). This is the raw DMA3 transfer primitive: it stashes a saved IRQ-enable word (_DAT_08023684), programs what are, by address-pattern and argument shape, the DMA3 source/destination/control registers (_DAT_08023694/_DAT_08023698/_DAT_0802369c, the third OR'd with 0x80000000, the DMA "enable" bit), then busy-waits on a status word until a "busy" bit (0x8000) clears before restoring the saved IRQ state. Both of its callers pass the EEPROM MMIO address 0xD000000 (i.e. 0x0D000000) as source or destination, which is the canonical GBA EEPROM data-port address — this is the strongest single piece of evidence that this function family is the EEPROM driver.

  • FUN_08023558(undefined2 *param_1) @ 0x08023558 (caller: 0x08023754).

Saves/restores an IRQ-mask bit (8 << *_DAT_080235d4, consistent with the DMA3-complete IRQ bit in REG_IE/REG_IF), then stores the 3-word argument block into a queue/handle structure and flips an "armed" flag (*puVar1 = 1). Read as

"arm/enable the EEPROM DMA completion interrupt for this transfer."

  • FUN_080235e0(void) @ 0x080235e0 (caller: 0x08023754). The inverse of

FUN_08023558: clears the queue/handle entry and the same IRQ-mask bit, i.e.

"disarm/disable the DMA completion interrupt."

  • FUN_080236a4(uint block, int out_buf8bytes) @ 0x080236a4 — MMIO seed.

(caller: 0x08023830). This is the EEPROM READ primitive: it bounds-checks block against a runtime block-count field, serializes a 2-bit "read" opcode plus the block address as a bitstream (one bit per ushort slot, loop count *(byte*)(...+8) — the EEPROM address width, 6 bits for 4Kbit/512-byte EEPROM), sends it to 0x0D000000 via two back-to-back FUN_08023624 calls (address-setup phase of length addr_bits+3, then a 68-cycle "turn-around + 64 data bits" read phase of length 0x44=68), then unpacks 64 serial bits into 4 big-endian 16-bit words (param_2[0..3]) — i.e. one 8-byte EEPROM block.

  • FUN_08023754(uint block, ushort *data8bytes) @ 0x08023754 — MMIO seed.

(caller: 0x08023888). This is the EEPROM WRITE primitive: same bounds check, then serializes a 2-bit "write" opcode, the block address, and the 64 data bits from data8bytes[0..3] into a single bitstream buffer, sends it in one FUN_08023624 transfer of length addr_bits + 0x43 (67) bits, arms the DMA IRQ via FUN_08023558, polls the EEPROM busy bit (uRam0d000000 & 1) until the write completes or a bail-out flag (*_DAT_08023828) is set, and disarms via FUN_080235e0.

  • FUN_08023830(ushort block, short *expected8bytes) @ 0x08023830. **Write

verification**: calls FUN_080236a4 to read back the just-written block into a 4-word local buffer, then compares all 4 words against expected8bytes; returns 0x8000 ("mismatch") on first differing word, 0 on full match.

  • FUN_08023888(ushort block, ushort *data8bytes) @ 0x08023888. The **top-level

"write with retry" entry point: loops up to 3 times, calling FUN_08023754 (write) then, if the write call itself didn't report failure, FUN_08023830 (verify); breaks out as soon as a write+verify cycle both report success. Returns the last status code. This is the actual save-flush API** that any higher-level game code would call once per 8-byte block to commit data to .sav.

Call-chain summary (bottom-up, as captured in ghidra/callgraph.json):

FUN_08023888  (write-with-retry, 3 attempts)
 ├─ FUN_08023754  (EEPROM write)
 │   ├─ FUN_08023624  (raw DMA3 transfer, dst=0x0D000000)
 │   ├─ FUN_08023558  (arm DMA-complete IRQ)
 │   └─ FUN_080235e0  (disarm DMA-complete IRQ)
 └─ FUN_08023830  (EEPROM read-back verify)
     └─ FUN_080236a4  (EEPROM read)
         └─ FUN_08023624  (raw DMA3 transfer, src=0x0D000000)

3.2 Serialization / deserialization & checksum routines

None found. The only numeric helper functions elsewhere in the 112-function decompiled corpus that are not part of the driver above are FUN_08023904 and FUN_08023a6c (software signed/unsigned integer division — standard compiler runtime helpers, __divsi3/__udivsi3-shaped, operating on arbitrary 32-bit operands with no relationship to the save buffer addresses) and FUN_08023ba4 (a generic word/byte memcpy). None of the traced functions contain a sum/XOR/CRC accumulation loop over the EEPROM data buffer. This means the serialization step (building the 448-byte in-RAM record and handing 8-byte chunks to FUN_08023888) and any checksum/integrity logic live entirely outside the traced function set — they were not captured by the trace that seeded this packet's Ghidra extraction.

3.3 Callers above the driver

ghidra/callgraph.json records "0x08023888": {"callers": [], "callees": [...]}. No caller of the top-level write-with-retry function, and no caller of FUN_08023830's sibling read path outside the verify loop, appears anywhere in the traced 112-function set. By elimination, every other decompiled function in this packet (the sprite/object-pool code at 0x0801e3e8–0x0801fd40, the "clear OAM descriptor pool" style helpers, etc.) was checked and does not touch the EEPROM MMIO addresses, DMA3 registers, or any of the FUN_08023xxx symbols — so none of them are, on this evidence, part of the save path. (In particular, FUN_0801fcd8's destination buffer for its own FUN_0801fee0 BIOS-CpuSet-style call is 0x07000000, which is GBA OAM, not SRAM/Flash/EEPROM — this function is unrelated to saving despite superficial "looks like a buffer flush" shape.)

Conclusion: the game-specific save-record builder and its caller(s) are not present in this packet's trace. This is reported as an explicit gap rather than guessed at.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • ASCII "1MOYUP" at file offset 0x02–0x07 (6 bytes), preceded by 2 bytes

(0x00–0x01: 01 00). Present in cap-01-future-1.sav and absent in the fully blank cap-00-future-0.sav (which is 0xFF for all 512 bytes).

Confidence: CONFIRMED_VERIFIED (directly observed in the real .sav bytes; independently corroborated by the packet's own ascii_magic_strings metadata). No code reference to this literal string was found in the traced decompilation (the serializer that would write it is outside the trace, per §3.3), so code-side confirmation is not available — the "verified" status here rests on direct byte observation, not on a decompiled string-compare.

4.2 Checksum / integrity algorithm

no byte-level match was found for any of the standard algorithms tried against the plausible stored-value candidates. Full verification performed in Python against saves/cap-01-future-1.sav:

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav, reloaded from the paired pre-save .ss state (not available in this packet's states/ directory — 0 states are present, so this plan assumes a future capture round that includes the required paired .ss states per project policy), with both

before and after observations recorded. No checksum repair step is included because no checksum algorithm was confirmed (§4.2); mutations are instead designed to (a) probe whether an undetected checksum exists at all, and (b) map field semantics independently of that question.

  1. Magic-string corruption probe. Flip one byte inside "1MOYUP" (e.g. 0x02:

0x31→0x30). Predicted effect if the magic is load-gating: game treats the slot as corrupt/new-game on next boot (visual delta on load, similar to the documented reverted_to_blank_boot signal already captured for blank EEPROM). If nothing changes, the magic is cosmetic/unused at load time — falsifies the "load-gating magic" hypothesis.

  1. Checksum-candidate round-trip probe. Independently flip one low bit in each of

the three UNKNOWN 16-bit candidates (0x0C, 0x0E, 0x1BE) one at a time, leaving everything else byte-identical, and reload. Predicted effect if any one is a real checksum: load is rejected/reset (observable via boot screenshot diff vs. an unmutated reload). Predicted effect if none are checksums: data loads unchanged and the flipped byte round-trips back out identically on next save — this is the direct falsification test for "no checksum exists" vs. "checksum exists but wasn't matched by the 5 ranges tried in §4.2."

  1. Score-table boundary probe. Zero out one 4-byte entry in the 0x010–0x0A7

table (e.g. entry at 0x010, currently 0x00000BB8=3000) and reload. Predicted observable: if this table is read/displayed (e.g. a records/ranking screen), the corresponding displayed value should become 0; if the table is write-only scratch state regenerated every boot, the value should silently revert on next save, which would falsify "persistent score record" in favor of "transient/derived data incidentally flushed to EEPROM."

  1. Index-table domain probe. Set one byte in the 0x0D0–0x19F array to a value

outside the observed 1–26 domain (e.g. 0xFF) and reload. Predicted effect if this is a bounded lookup index: visible corruption/garbage glyph or a game-side clamp/reset of that slot; if nothing visibly changes, the table is not actively read at the point tested, or is read with bounds-checking that silently discards the probe — either result narrows the hypothesis.

  1. Tail-field mutation probe. Flip 0x1DB (0x01→0x00) and reload. Predicted

effect if this is a "save exists" flag independent of the main 0x000 byte: no visible change (redundant flag) vs. observable "corrupt save" handling if it is load-gating on its own.

  1. Unwritten-block probe (counterfactual for §2's slot-count hypothesis). Write

non-0xFF, non-colliding sentinel bytes into blocks 60–63 (0x1E0–0x1FF) directly in the .sav file (bypassing the game), then boot. Predicted effect if those blocks are genuinely unused: no behavior change, and the next in-game save either leaves them untouched or overwrites them back to 0xFF/zero — this distinguishes "reserved-but-dead" bytes from "written only under an unexercised condition" (e.g. a second save slot or an unlockable mode).

  1. Fresh-vs-restore matched-duration control. Capture a third .sav snapshot

after an identical, timed sequence of actions from two different starting states (fresh blank EEPROM vs. restored cap-01), to obtain the second independent non-blank sample this packet lacks — required before any checksum hypothesis in §4.2 can be escalated from UNKNOWN to CONFIRMED_STATIC or ruled out definitively.

candidate fields identified, none confirmed (§4.2).
