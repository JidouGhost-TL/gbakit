2. Physical Media, Slot Geometry & Redundancy

  • Media kind: EEPROM (eeprom512 in the JSON deliverable). Evidence: SDK tag EEPROM_V124 at ROM offset 1269204 (per packet metadata); the only save-bus address used in the corpus is 0x0D000000, the GBA EEPROM bus; transfers are DMA3-driven serial bitstreams (FUN_0804c6dc, section 3.1), which is the EEPROM access method (EEPROM is not memory-mapped for direct byte access like SRAM at 0x0E000000). No Flash 0x5555/0x2AAA command sequence and no SRAM byte-copy save driver appear anywhere in the decompilation.
  • Total size: 512 bytes (4 Kbit). Proven two ways: (a) the .sav file is exactly 512 bytes; (b) FUN_0802458c (ghidra/decompiled.c:2295) loops uVar3 from 0 while < 0x40 (64 iterations), calling the 8-byte block reader FUN_0804c75c and advancing the destination by 8 each time — 64 x 8 = 512. This matches a 4-Kbit EEPROM organized as 64 individually addressed 64-bit blocks. It is not an 8-KB (64-Kbit, 1024-block) EEPROM: the caller never issues a block address >= 0x40.
  • SDK tag: EEPROM_V124 (ROM offset 1269204, supplied in packet metadata; the ROM itself is not in the workspace, so this is metadata-trusted, not re-verified from ROM bytes).
  • Active byte spans (in the sample): none, in the content sense. Python scan of sav-00-f1473.sav (section 4): 0x000-0x19F = 0x00 (416 B, the emulator backing-file background per hexdump_and_diffs.txt, which records background_fill=0x00), 0x1A0-0x1FF = 0xFF (96 B = EEPROM blocks 52-63). The pre-computed hexdump lists 0x01a0..0x0200 as the single "active range" only because 0xFF differs from the 0x00 background — it is a fill region, not save data. There are no magic bytes, no ASCII, and no non-fill bytes anywhere in the file.
  • Number of save slots/copies: 1. The traced loader (FUN_08024704 -> FUN_0802458c -> FUN_080247e4) reads exactly one 512-byte image starting at EEPROM block 0 and validates it once. No second image offset, no slot index parameter, and no slot-selection UI path is present in the traced functions.
  • Mirroring/redundancy: None traced. The image is read once into a RAM buffer and validated by a single checksum byte. There is no primary/backup pair, no duplicate payload copy inside the 512 bytes that the reader compares, and no fallback: on any block-read failure FUN_0802458c aborts to its post-read hook without calling the validator (section 3.3).
  • Generation/sequence counters: None traced. No field in the image is incremented, compared as a version, or used to choose between copies anywhere in FUN_080247e4 or its callers. Bytes 0x122-0x1FF are never read by the validator at all, so a counter hidden there cannot be excluded — but there is no evidence for one.
  • Selection rule: Not applicable — single image. Load succeeds or fails as a whole; validity is reported only as a boolean (RAM struct +0x23, section 5) computed from the checksum byte at 0x121.
  • Fill byte: 0xFF is the erased/untouched EEPROM cell value, observed in blocks 52-63 (0x1A0-0x1FF). The 0x00 region is the emulator's backing-file background, not evidence that the game wrote zeros — although a game-written zeroed payload cannot be distinguished from background in this sample, which is precisely why the checksum match in section 4 is vacuous.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are 0x08xxxxxx ROM addresses as named in the Ghidra corpus. How callers were mapped: (1) direct textual call sites FUN_xxxxxxxx(...) / func_0x...(...) in ghidra/decompiled.c were grepped; (2) each edge was cross-checked against ghidra/callgraph.json callers/callees; (3) edges present in the C text but absent in the JSON (because Ghidra emitted them as func_0x... indirect/jumptable calls, e.g. func_0x080247e4, func_0x0804c75c) are marked [C-text only]; edges in the JSON with no visible C call are marked [callgraph only]. Every function below terminates in an UNRECOVERED_JUMPTABLE tail call in the decompilation, so return-value and fall-through details are partially obscured — flagged where it matters.

3.1 Low-level hardware I/O driver

0x0804c6dc — DMA3 transfer engine (FUN_0804c6dc, decompiled.c:4150)

  • Role: read | write (generic DMA mover; the only mover used for the EEPROM bus).
  • What it does (decompiled proof): saves and zeroes *_DAT_0804c73c (an interrupt/DMA-control shadow), masks a control register via *_DAT_0804c740 & (ushort)_DAT_0804c744 | *(ushort *)(*_DAT_0804c748 + 6), then writes param_1 (source) to *_DAT_0804c74c, param_2 (destination) to *_DAT_0804c750, and param_3 & 0xffff | 0x80000000 (count + enable bit 31) to *_DAT_0804c754, then busy-waits on bit 0x8000 of the control high halfword before restoring the saved register. This register triple (source, destination, count|enable) with a busy poll is the DMA3 register block at 0x040000D4 per the packet's hardware spec; the individual register addresses themselves are behind unresolved _DAT_ literals, so the identification is by register pattern and order, marked CONFIRMED_STATIC.
  • Callers: 0x0804c75c only (callgraph + C text). Callees: none.

0x0804c75c — EEPROM single-block read, 8 bytes (FUN_0804c75c, decompiled.c:4181) [MMIO seed]

  • Role: read (one 64-bit EEPROM block). This is a reader only: both of its DMA calls receive from the EEPROM bus into a stack buffer; no data is ever DMA'd to 0x0D000000 except the command/address bitstream.
  • Protocol as decompiled: (a) param_1 (block address) is masked to 16 bits and bounds-checked against *(ushort *)(*_DAT_0804c774 + 4) — a device-descriptor block-count field (must be <= the caller's max 0x3F); out-of-range returns an error via the jumptable tail. (b) The address is shifted out MSB-first into a stack array of ushort bit cells (auStack_96), the count of address bits taken from descriptor byte +8 (6 bits for a 64-block/512-B EEPROM, by geometry). (c) Two header bits are forced to 1 (*puVar5 = 1; puVar5[-1] = 1) — the start bit and the read opcode bit(s) of the serial EEPROM command; the decompilation cannot resolve the exact opcode encoding beyond "two leading 1 bits", so the opcode is reported as observed bits, not named. (d) FUN_0804c6dc(auStack_98, 0xd000000, addr_bits + 3) DMAs the command+address bitstream to 0x0D000000. (e) FUN_0804c6dc(0xd000000, auStack_98, 0x44) DMAs 0x44 (68) halfword cells from 0x0D000000 back into the same stack buffer (dummy/start cells + 64 data bits). (f) The 64 data bits are reassembled MSB-first, 16 bits at a time, into 4 ushorts written backwards from param_2 + 6 — i.e. 8 bytes stored at param_2[0..8) in reverse halfword order relative to the serial stream.
  • Callers: none listed in callgraph.json (callers: []), but the C text shows the sole caller 0x0802458c calling it as func_0x0804c75c [C-text only]. Callees: 0x0804c6dc (callgraph + C text).
  • Returns: a status tested as sVar1 != 0 by the caller (non-zero = failure); the success value passes through the unrecovered jumptable, so the exact success code is UNKNOWN.

0x0804c694 — EEPROM type/configuration selector (FUN_0804c694, decompiled.c:4122)

  • Role: read-support (device identification/configuration; not a data mover).
  • What it does: branches on param_1: 4 writes one descriptor pointer (*_DAT_0804c6a8 = _DAT_0804c6ac), 0x40 writes another (*puRam0804c6bc = uRam0804c6c0), any other value writes a third and returns 1. The sole traced call passes 4 (FUN_0802457c), selecting the descriptor whose fields FUN_0804c75c then consults (block count at +4, address-bit count at +8). That the selected geometry is the 512-B one is corroborated by the caller's 0x40-block loop; the mapping of argument 4 to "4 Kbit" is a plausible reading of the value, stated here as hypothesis, while "selects the EEPROM descriptor used by the reader" is CONFIRMED_STATIC.
  • Callers: none in callgraph; C text shows sole caller 0x0802457c as func_0x0804c694(4) [C-text only].

Debunked seed: 0x0804cf54 is not a save function

ghidra/save_related_functions.c lists FUN_0804cf54 (decompiled.c:4340) as a seed, but its body is a signed division/remainder helper (sign normalization, shift-based long division, calls func_0x0804cf1c on divide-by-zero). It touches no MMIO, no 0x0D000000, and no save buffer. Its presence in the seed file is an MMIO-scan false positive. It is excluded from the save architecture and from save-format.json's driver list (mentioned there only via open_questions context in this report). The same caution applies to its sibling arithmetic helpers 0x0804ce88 / 0x0804d024 etc., which are runtime math, not integrity code — no CRC or checksum hides in them (they were read; they implement division/multiplication helpers).

3.2 Serialization / deserialization & checksum routines

0x080247e4 — Validator / deserializer (FUN_080247e4, decompiled.c:2356)

  • Role: deserialize | checksum (read-side only; it never writes EEPROM).
  • Inputs: param_1 = pointer to the 512-byte RAM image just read from EEPROM (a second argument is passed by the caller — param_3 of FUN_0802458c, value 1 from FUN_08024704 — but the decompiled signature takes one parameter, so the second argument's use is not recovered).
  • Exact behavior (decompiled proof, decompiled.c:2366-2382):
  1. *_DAT_08024854 = 0x53 ('S') — a byte store to an unresolved pointer, executed unconditionally before any validation. Because the destination literal is unresolved, this is not claimed as a magic-signature check or write into the save image; no byte of the .sav is compared against 0x53 anywhere. See section 4.1.
  2. *(RAM_struct + 0x22) = param_1[0] — EEPROM byte 0x00 is copied to the RAM save struct at offset +0x22 (struct base = value of _DAT_08024850, unresolved).
  3. FUN_0804e900(_DAT_08024858, param_1 + 4, 0x11c) — memcpy-style copy (section 3.2, next entry) of 284 bytes from EEPROM offset 0x04 to a RAM destination (unresolved literal _DAT_08024858, presumably inside/near the same RAM struct; its offset from the struct base cannot be recovered from the text corpus).
  4. Checksum recomputation: cVar3 (8-bit char) accumulates param_1[4] + param_1[5] + ... + param_1[0x11F] — see section 4.2 for the exact loop bounds and formula.
  5. 'Z' branch: if (*(char *)(RAM_struct + 0x22) == 'Z') *(char *)(RAM_struct + 0x22) = param_1[0x120]; — if the copied byte 0 equals 0x5A ('Z'), it is replaced in RAM by EEPROM byte 0x120. The EEPROM bytes themselves are not modified. Semantics (a sentinel meaning "take the real value from the extension byte") are hypothesis; the mechanics are CONFIRMED_STATIC.
  6. Validity flag: *(bool *)(RAM_struct + 0x23) = (param_1[0x121] == cVar3); — RAM struct +0x23 becomes the boolean "checksum matches".
  7. *_DAT_08024874 = *(undefined1 *)(RAM_struct + 0x22) — the (possibly 'Z'-substituted) byte 0 value is additionally published to a second unresolved global.
  • Callers: none in callgraph.json; C text shows sole caller 0x0802458c as func_0x080247e4(param_2, param_3) [C-text only], invoked only after all 64 block reads succeed.
  • **What it does not do:** it does not reject or re-read on checksum failure (it only records the boolean at +0x23); it does not read bytes 0x01-0x03 or 0x122-0x1FF for validation; it contains no magic comparison.

0x0804e900 — word-optimized memcpy (FUN_0804e900, decompiled.c:5089)

  • Role: deserialize (bulk copy primitive). Copies param_3 bytes from param_2 to param_1 in 16-byte unrolled word steps when both pointers are word-aligned, then word, then byte tail; returns the destination. Used by the validator for the 284-byte payload copy and by unrelated code elsewhere (0x08000878 region, 0x080480a0, 0x08048958) — a generic libc-style routine, not save-specific. Callers (save chain): 0x080247e4 [C-text only] (callgraph lists no callers for it at all).

How each caller mutates the in-RAM save struct before flushing: it does not — there is no flush. Every traced caller mutates only (a) the 512-byte staging buffer (0x08024704 zero-fills it; 0x0802458c fills it from EEPROM), and (b) the RAM save struct during load (0x080247e4 writes struct +0x22, struct +0x23, and the 284-byte payload destination). No caller writes gameplay state into the struct and then to EEPROM in this corpus. The RAM struct's concrete base address is unrecoverable (unresolved _DAT_08024850), so "RAM Mirror Addr" is null throughout section 5 — the offsets within the struct (+0x22, +0x23) are the recoverable facts.

3.4 The writer: absent from the corpus (explicit negative result)

The packet requires documenting the save writer. The honest finding is that no writer exists in the provided corpus:

  • Text search of all 5122 lines of ghidra/decompiled.c for the EEPROM bus address finds exactly two references, both in the read function FUN_0804c75c (0xd000000 as DMA destination for the command bitstream, and as DMA source for read-back). No function constructs a write bitstream (start + write opcode + address + 64 data bits), polls an EEPROM write-busy state, or DMAs payload data to 0x0D000000.
  • ghidra/callgraph.json contains no caller of 0x0804c6dc other than 0x0804c75c, and no other function whose callees include any EEPROM primitive.
  • ghidra/save_related_functions.c — the pre-extracted seed file built from MMIO references — contains the same reader chain plus the debunked arithmetic seed 0x0804cf54, and no writer.

Because the decompilation is trace-guided (154 functions actually executed in the recorded traces), the most likely explanation is that the save-writing code path was never executed during trace capture (consistent with the only .sav being blank and with sav-00-pre/sav-00-post bracketing a read/load event rather than a confirmed write). The writer's address, its serialization order, how it computes the stored checksum byte at 0x121 (presumably the same sum8, but that is hypothesis until a writer is observed), what it stores at bytes 0x01-0x03 and 0x120, and whether it writes the 0x1A0-0x1FF tail are all UNKNOWN. No writer address is invented anywhere in this report or in save-format.json (writers arrays name only functions with a textual call site / store in the corpus).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signatures

None. No byte or byte string in the 512-byte image is compared against a constant by any traced function. The validator FUN_080247e4 performs no header/magic test: it unconditionally copies byte 0 and the payload, then records only the checksum boolean. The two ASCII-looking constants in the validator are:

  • 0x53 ('S'): stored to an unresolved pointer (*_DAT_08024854 = 0x53), never compared against save data. It is not a magic signature and is not claimed as one in save-format.json (magic_signatures is empty).
  • 0x5A ('Z'): compared against the RAM copy of byte 0 (*(char *)(RAM_struct + 0x22) == 'Z') to trigger substitution from byte 0x120. This is a sentinel branch on one field, not a multi-byte magic. It is documented as a field (section 5), not as a signature.

In the sample .sav, no magic could be observed in any case: the file contains only 0x00 and 0xFF fill (section 4.3 output). verified_in_code=false, verified_in_sav=false for every candidate — hence the empty magic_signatures array rather than an invented one.

4.2 Checksum algorithm (exact)

  • Algorithm: sum8 — 8-bit additive checksum (sum of bytes modulo 256; the accumulator is a char, so wraparound is inherent).
  • Formula: computed = ( Σ byte[i] for i in [0x04, 0x120) ) & 0xFF, i.e. bytes 0x04 through 0x11F inclusive (284 bytes). No seed, no complement, no XOR, no CRC, no endianness (byte-wise).
  • Stored at: EEPROM offset 0x121 (289), 1 byte. Valid iff stored == computed; the result is written as a boolean to RAM struct +0x23. A mismatch does not abort the load in this function — the payload has already been copied to RAM before the comparison result is stored.
  • Decompiled proof (ghidra/decompiled.c:2370-2381, FUN_080247e4):
  func_0x0804e900(_DAT_08024858, param_1 + 4, 0x11c);   // copy 0x11C = 284 bytes from offset 4
  ...
  cVar3 = '\0';
  uVar5 = 4;
  do {
    cVar3 = cVar3 + param_1[(short)uVar5];
    uVar2 = (int)(short)uVar5 + 1;
    uVar5 = uVar2 & 0xffff;
  } while ((int)(uVar2 * 0x10000) >> 0x10 < 0x120);    // while next index < 0x120
  ...
  *(bool *)(iVar1 + 0x23) = param_1[0x121] == cVar3;   // stored byte vs computed sum8

Loop-bound check: the body executes for indices 4, 5, ..., 0x11F; after adding index 0x11F, uVar2 = 0x120, the condition 0x120 < 0x120 fails and the loop exits. The covered range is therefore exactly [0x04, 0x120) — the same 284 bytes that were just copied to RAM (0x11C = 284). Byte 0x120 and the stored byte 0x121 itself are not covered.

  • Functions: 0x080247e4 (compute + compare). No other checksum, CRC, XOR-fold, or sum over save data exists in the traced corpus (the arithmetic helpers 0x0804ce88/0x0804cf54/0x0804d024 family were read and are division/multiplication runtime, not integrity code).
  • Confidence: CONFIRMED_STATIC for the formula. It is deliberately not CONFIRMED_VERIFIED: the only sample is blank, so the "match" below is vacuous (see 4.3). Claiming verification from an all-zero payload would be dishonest — any sum, XOR, or CRC of zero bytes with a zero stored byte "matches".

  1. Computed vs stored: sum8[0x04:0x120) = 0x00; stored byte at 0x121 is 0x00; they are equal — but every input byte is 0x00, so this equality carries no evidential weight for the formula. This is recorded in save-format.json as match: true with confidence: CONFIRMED_STATIC, and the vacuity is disclosed here and in open_questions rather than hidden.
  2. The file's SHA-256 (2c467c76522d1982...) matches the value in saves/hexdump_and_diffs.txt, confirming the analyzed bytes are the corpus bytes.
  3. No alternative integrity value is present to cross-check: XOR-8, sum-16, etc. over the payload are all 0x0000 for the same vacuous reason and are not claimed as algorithms.
  4. A non-blank save (e.g. captured after a confirmed in-game write from the sav-00-pre/sav-00-post state pair, if a write can be induced) is required to promote this checksum to CONFIRMED_VERIFIED. The fuzzing plan in section 6 is designed to produce exactly that evidence.

6. Save Fuzzing & Counterfactual Verification Plan

Test harness: use the paired states states/sav-00-pre.ss (frame 1439) and states/sav-00-post.ss (frame 1473) as the load bracket, with states/gameplay.ss (frame 1094) and states/final.ss (frame 1795) as gameplay/UI baselines. For each mutation: patch the .sav, present it as the EEPROM image at cold load (the 0x08024704 path runs at load, per its position as an uncalled entry in the traced graph), reload from the pre-state, advance past frame 1473, and record (a) whether RAM struct +0x23 (checksum-valid bool) semantics change — observable indirectly via any "load succeeded / save data present" UI or gameplay divergence vs. the blank-boot baseline (the packet's cold-reload probe already establishes visual_delta_vs_blank_boot: true as an observable), (b) any crash/hang, and (c) the resulting .sav if the game rewrites it (which would also reveal the writer — capture and diff it before anything else).

Checksum repair (applies wherever marked): after mutating any byte in [0x04, 0x120), recompute sum8 = (Σ bytes[0x04..0x11F]) & 0xFF in Python and write it to offset 0x121. Mutations to offsets 0x00, 0x120, 0x121, and >= 0x122 do not require repair (outside the covered range) — that asymmetry is itself a testable prediction of the mapped formula.

Appendix B. Open Questions (also in save-format.json)

  1. Where is the EEPROM writer? It is absent from the 154-function trace-guided corpus (no write bitstream to 0x0D000000 exists in the decompilation). Its address, serialization, and stored-checksum computation are unknown.
  2. What are the semantics of byte 0x000, the 'Z' (0x5A) substitution from byte 0x120, and the unresolved 0x53 ('S') store in FUN_080247e4?
  3. What is the internal field structure of the 284-byte payload at 0x004-0x11F? No writer or per-field consumer was traced and the only sample is blank, so no sub-field can be mapped without fabrication.
  4. What are the concrete RAM addresses behind _DAT_08024850 (save struct base), _DAT_08024858 (payload destination), _DAT_08024874, and _DAT_08024854? The text decompilation leaves all literal-pool values unresolved, so RAM mirror addresses are reported as null.
  5. What consumes the checksum-valid boolean at RAM struct +0x23, and does it gate gameplay state, show an error, or silently ignore invalid saves? The validator only records the boolean.
  6. What are bytes 0x001-0x003, 0x122-0x19F, and the 0xFF tail at 0x1A0-0x1FF for? No traced code reads them; are they writer-only, reserved for a second structure, or unused?
  7. Can the sum8 checksum be promoted from CONFIRMED_STATIC to CONFIRMED_VERIFIED? The blank sample's match is vacuous (all-zero payload); a non-blank, game-written save is required.
  8. What do the pre/post-read hooks FUN_08024560/FUN_08024530 and the 0x0804c694(4) descriptor fields (block count at +4, address bits at +8) resolve to concretely, and what is the second argument passed to FUN_080247e4 by FUN_0802458c?
  9. Is the 0x1A0-0x1FF 0xFF region ever written by the game, or is it simply never-touched EEPROM cells?
