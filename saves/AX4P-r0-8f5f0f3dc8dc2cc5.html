1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  1. Physical medium is Flash 1M (131072 B), organised as thirty-two 0x1000-byte blocks, written/erased with the classic Flash command sequence (0xAA→0x0E5555-class address, 0x55→0x0E2AAA-class address, then command 0x90 ID / 0x80+0x30 sector-erase / 0xA0 byte-program / 0xB0 bank-switch / 0xF0 reset) — see FUN_080eaaf8, FUN_080eab1c, FUN_080eb1a0, FUN_080eb26c in save_related_functions.c and decompiled.c.
  2. Three block magics exist in the .sav files and are written by dedicated copy helpers immediately before checksumming: SMA4MWP0 (8 B, via the 8-byte copy FUN_0803b0dc), M3P0 (4 B) and S4CP (4 B, via the 4-byte copy FUN_0803b124).
  3. One single checksum algorithm covers every non-erased block: 16-bit truncated sum of all 4096 bytes with the stored checksum field itself zeroed, implemented by FUN_0803c0b8. Stored at block offset 0x08 in SMA4MWP0 blocks and at block offset 0x04 in M3P0/S4CP blocks. Verified in Python against every populated block: 18/19 blocks match in cap-01, 14/15 in cap-02, and the two “mismatches” match exactly once their still-erased (0xFF) trailing tail is treated as not-yet-programmed 0x00 — i.e. they are mid-write captures, not algorithm failures (Section 4).
  4. Block geometry and redundancy: one SMA4MWP0 block at file offset 0x00000 with a byte-identical mirror at 0x10000; six M3P0 blocks (three populated at 0x01000–0x03000, three empty templates at 0x11000–0x13000); a run of identical empty S4CP blocks starting at 0x06000, written 16-at-a-time by FUN_0803ecd8. Sector numbers in code (0, 0x10, table-driven <7/counter 0..5) map linearly onto these file offsets (sector × 0x1000), with sector 0x10 selecting the second 64 KiB Flash bank via FUN_080eaaf8.
  5. The master save-all orchestrator is FUN_0803d440: it runs the two default-initialisers, the SMA4MWP0 saver, three FUN_0803cd34(0|1|2) saves, three FUN_0803cdc0() saves, and finally the S4CP saver (FUN_0803ecd8 is called from it via an unresolved jumptable tail-call, shown as func_0x0803ecd8()).

What remains open / lower confidence:

  • The semantic meaning of almost every payload field (scores, lives, level-clear bits, inventory, etc.) is not proven. Both populated captures contain what is, by the code’s own defaults, a near-fresh game: SMA4MWP0 records are all in their 0xFF sentinel state, all three populated M3P0 files are byte-identical except slot index + checksum, and every observed S4CP payload is all-zero. There are no two captures with differing gameplay progress in this corpus, and there are no paired .ss states (0 states supplied), so field-level semantics cannot be differentially verified.
  • Numeric RAM mirror addresses are unrecoverable from the supplied decompilation (unresolved _DAT_ pool).
  • The exact dispatch semantics of the RAM-copied Flash polling routine behind FUN_080eb350/FUN_080eb354/FUN_080eb358/FUN_080eb35c (unrecovered jumptables) are inferred from argument order and the standard Flash API shape, not directly read.
  • The load/reader path is only partially present in the trace-guided function set: the read-transfer primitive FUN_080ead70 and a read-then-program wrapper FUN_0803afec exist, but no caller of FUN_0803afec appears in callgraph.json (calls via unrecovered jumptables/pointers are invisible to it), and no boot-time “verify magic → verify checksum → copy block into RAM struct” routine is in the 134-function corpus. The PACKET’s own cold-reload probe (integrity_check_confirmed: true, mutation at 0x1A) independently confirms a load-time integrity check exists; offset 0x1A lies inside the checksummed range, so any mutation there is consistent with rejection/repair by checksum failure alone.

Which copy is selected at load, and any generation counter: no generation/sequence counter field was found. Within each block the only monotonically varying bytes between otherwise identical copies are the M3P0 slot index (0,1,2) and the checksum that covers it. SMA4MWP0 primary and backup are identical, so a “pick the newer by counter” rule cannot operate on the observed bytes; the honest reading is fixed-address selection with checksum validation (try primary sector 0, fall back to backup sector 0x10 if magic/checksum fails), which is the standard pattern for this two-bank layout and is consistent with the PACKET cold-reload probe, but the actual load-side selection code is not in the supplied corpus (CONFIRMED_STATIC for the write side, HYPOTHESIS for the load-side fallback). Likewise the S4CP multiplicity (16 identical copies) suggests “first copy that passes magic+checksum wins” at load (HYPOTHESIS); no copy is distinguished by a counter in the observed bytes (all complete copies are byte-identical, checksum 0x011A).

Redundancy summary: SMA4MWP0 ×2 (cross-bank), M3P0 ×6 (3 + 3, in two differently-initialised groups), S4CP ×16 intended (identical empty payload in all observed complete copies). Every block is independently checksummed, so redundancy is at whole-block granularity.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two independent sources were cross-checked for every edge:

  1. ghidra/callgraph.json (134 nodes; static C calls + runtime direct-calls.json). In this corpus the graph records only a subset of edges — notably it lists FUN_0803b070’s callers as FUN_0803b190, FUN_0803b1a4, FUN_0803c308, FUN_0803ecd8, and FUN_0803afec/FUN_0803b070/FUN_0803af94 etc. as having the callees shown in the file.
  2. The bodies in ghidra/decompiled.c, which contain additional calls the graph omits because they go through func_0x… thunks or unrecovered jumptables (e.g. FUN_0803bc5c → FUN_0803b190/FUN_0803b1a4, FUN_0803d440 → func_0x0803ecd8(), FUN_0803afec → func_0x080ead70/func_0x080eaed4). Every caller claim below cites the decompiled body line, not just the graph.

A general caveat applies to the whole section: most functions end in (*UNRECOVERED_JUMPTABLE)() — Ghidra’s rendering of a Thumb tail-branch/jump-table the trace did not resolve. Callers reached only through such tails are invisible in both sources; “no callers in corpus” never means “never called”.

3.4 Block builders / savers and every caller

(a) SMA4MWP0 saver — FUN_0803bc5c

Chain (body-verified): FUN_0803af94() gate → guard: only if (status_byte & 2) == 0, and if counter_a < counter_b && flag == 1 then counter_a = counter_b (monotonic-counter merge into RAM, exact fields unresolved) → FUN_0803b418 → FUN_0803b0dc (8-byte magic) → *checksum_ptr = 0; *checksum_ptr = FUN_0803c0b8(0x1000) → FUN_0803b190 (sector 0) → FUN_0803b1a4 (sector 0x10).

  • FUN_0803b418: zeroes the 0x1000 staging buffer (FUN_08002d48(buf, 0x1000)), copies a 0x1C-byte header source into it (FUN_08002d68(buf, src, 0x1C)), then calls the field assembler FUN_0803b1b8.
  • FUN_0803b1b8 is the serialization routine for the SMA4MWP0 payload. How each caller mutates the in-RAM struct before flushing, as far as this function shows: it copies a 7-byte field, derives two bytes from bitfields of the live game struct ((byte & 0x3F) >> 2, a byte at +0x…), conditionally copies a byte through a pointer at game_struct + 0x3C40, copies fields of sizes 4, 2, 0x48, then 72 records of 0x15 bytes each (do { FUN_08002d68(dst, i*0x16 + src, 0x15); dst += 0x15; } while (i < 0x48) — note source stride 0x16, destination stride 0x15: one byte per record is dropped/repacked), then fields of sizes 0x15, 0x18, 0x20, 0x10, 0x1D, 0x20, 0x2B, 8, 9, 2, 0x92, 3, 0x0C, 5, three bytes unpacked from a u32 (big-endian order: >>16, >>8, >>0), several single bytes, and conditionally a 0x800-byte field if a pointer+flag check passes. All source/destination bases are unresolved _DAT_ pointers, so the RAM struct cannot be addressed numerically; the .sav-side result of this assembly is mapped in Section 5.
  • Callers of FUN_0803bc5c: FUN_0803d440 (graph + body). No other caller in the corpus.

(b) M3P0 savers — FUN_0803cd34 and FUN_0803cdc0, writer FUN_0803c308

Both: zero three staging areas (0x31C, 0x400, 0x400), copy a 4-byte field, store the distinguishing byte (param_1 = 0/1/2 in FUN_0803cd34; 0xFF plus a u16 constant in FUN_0803cdc0), then FUN_0803c91c → checksum FUN_0803c0b8(0x1000) stored after zeroing → FUN_0803c308().

  • FUN_0803cd34 additionally calls FUN_0803cb40 before FUN_0803c91c: it writes two u16 constants (4, 4), then for 8 entries copies 9 bytes ×4 from four table sources into the staging struct (offsets entry*0xE based), then for 8 more entries distributes one source byte to four mirrored offsets, writes 0x20/0 sentinel patterns, and sets two tail bytes 0x1F, 0x40. This is a structured sub-object (names/initials-class data) present only in group-A saves; its exact gameplay meaning is UNKNOWN.
  • FUN_0803c91c zeroes the 0x1000 buffer, sets a flag bit (| 2), copies 0x31C bytes from live_src + 0x820 into an intermediate, calls FUN_0803c6b0(0), copies the same 0x31C bytes again, calls FUN_0803c6b0(0x800). FUN_0803c6b0(param) expands the intermediate into the staging buffer at offset param as 8 groups (per-group byte counts read from a u16 table; each byte expanded with an OR of two source bytes). Net effect, verified in the .sav: the M3P0 block is two identical 0x800 halves (+0x000 and +0x800), differing only in the checksum halfword (stored only in the first half; zero in the second — 2 differing bytes total per block).
  • FUN_0803c308 is the selection-rule writer: it reads a u16 index from the RAM struct; if !(index & 0x8000) && index < 7 it writes the staging buffer to Flash sector table[index] (table of u16 at an unresolved _DAT_ base, entry stride 2 bytes) with error code 3, then — unless a status bit (& 8) is set — copies one byte from the struct into struct + table_offset + index (a per-index “saved/dirty” mark). Otherwise it raises FUN_0803af0c(3). Callers: FUN_0803cd34, FUN_0803cdc0 (graph + bodies). The counter that feeds this index is advanced by FUN_0803d440 (0,1,2,3,4,5 across its six M3P0 calls), which is why group A lands on sectors 1–3 and group B on sectors 0x11–0x13 under the sector = table[counter] mapping; the table contents themselves are behind an unresolved _DAT_, so the counter→sector table is CONFIRMED_STATIC in shape and CONFIRMED_VERIFIED in its net effect on the .sav layout.
  • Callers of FUN_0803cd34/FUN_0803cdc0: only FUN_0803d440 (cd34(0), cd34(1), cd34(2), cdc0(), cdc0(), cdc0()).

(c) S4CP saver — FUN_0803ecd8

FUN_0803af94() gate → if (status & 2) == 0: zero 0x1000 buffer → FUN_0803b124 (4-byte magic S4CP) → *checksum_ptr = 0 (note: it stores the pre-checksum byte bVar1 & 2, i.e. 0, into the checksum halfword first) → *checksum_ptr = FUN_0803c0b8(0x1000) → loop 16 times: FUN_0803b070(table[i], buf, err=6), table pointer += 2 halfwords (4 bytes) per iteration. Caller: FUN_0803d440 via unresolved tail (func_0x0803ecd8() at the end of its body); graph lists FUN_0803ecd8 with no callers for the same jumptable reason. In the observed saves every completed S4CP block has an all-zero payload, so this saver was captured writing the default/empty state; what non-empty S4CP payload fields look like is UNKNOWN.

(d) Master orchestrator — FUN_0803d440

If (status & 2) == 0 after the FUN_0803af94() gate, in order:

  1. FUN_0803b788 — default-initialiser A: zeroes a 0x1C area, copies an 8-byte constant, writes defaults into the live struct (u32 at +0x810 from a constant, bytes 3, 0, 0, 0, u32s 0, 0, bytes 0, 0xFF, 0, 0xFF at table-derived offsets).
  2. FUN_0803b834 — default-initialiser B (new-game reset): zeroes/scatters ~40 fields of the live struct (including u16 = 4 at one offset, 0xFF bytes, bitfield & 0xC3), then 72 records: each record gets a 0xFF head byte, 0x15 payload bytes zeroed (inner loop of 0x15 iterations — the decompiler renders the count as 0x14 down to -1), and a zero byte in a parallel array; afterwards zeroes fields of sizes 0x1D, 0x20, 0x10, 0x20, 0x2B, 0x18, 0x92, 0x800 and sets 5 bytes to 0xFF backwards from a pointer. This function is the reason the populated SMA4MWP0 records in the .sav are in the all-0xFF-sentinel default state.
  3. FUN_0803bc5c — save SMA4MWP0 (sectors 0 + 0x10).

4.2 Checksum algorithm (exact)

Decompiled proof, FUN_0803c0b8:

void FUN_0803c0b8(uint param_1) {          // param_1 is always 0x1000 at save call sites
  short sVar1 = 0;
  byte *pbVar2 = _DAT_0803c0e0;            // base of the 0x1000 RAM staging buffer
  for (param_1 &= 0xffff; param_1 != 0; param_1--)
    sVar1 = sVar1 + (ushort)*pbVar2++;     // byte-wise sum, truncated to 16 bits each step
  return sVar1;                            // (via unrecovered jumptable tail)
}

Writer pattern at all four call sites (FUN_0803bc5c, FUN_0803cd34, FUN_0803cdc0, FUN_0803ecd8):

*checksum_ptr = 0;                          // zero the field first
*checksum_ptr = FUN_0803c0b8(0x1000);       // then store sum over the whole block

Therefore, exactly:

  • Algorithm: sum16_le-family in storage, computed as a byte sum modulo 65536 (sum8 accumulated in a 16-bit short). Not XOR, not CRC, no seed, no final complement, no inversion.
  • Formula: stored_u16 = ( Σ_{i=0}^{4095} block[i], with block[stored_offset..stored_offset+1] taken as 0 ) mod 65536
  • Covered range: the entire 0x1000-byte block, including the magic (the magic copies run before the checksum at every call site) and including the second M3P0 half.
  • Stored offset / size: SMA4MWP0: offset 0x08, 2 bytes, little-endian. M3P0/S4CP: offset 0x04, 2 bytes, little-endian. In the duplicated second M3P0 half the field at +0x804 is left as 0x0000 (only the first half carries the checksum — verified: the two halves differ in exactly those 2 bytes).
  • Endianness: stored little-endian (GBA native); the summation itself is byte-order independent.

import struct
def repair(buf, block_off, coff):          # coff = 8 for SMA4MWP0, 4 for M3P0/S4CP

    c = sum(buf[block_off:block_off+0x1000]) & 0xFFFF
    struct.pack_into('<H', buf, block_off + coff, c)
