GBA Clean-Room Save Format Report — Tony Hawk's Pro Skater 3 (France) (AT3F-r0-6e6ba7257df4ba98)

All findings are derived only from this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (644 functions), ghidra/save_related_functions.c (8 functions), ghidra/callgraph.json, plus standard GBA hardware addresses given in PACKET.md. No third-party game-specific source was used. ROM bytes are not in the workspace, so Ghidra literal-pool symbols (_DAT_08021b10, iRam…, descriptor pointers) whose values live in ROM could not be resolved; every place that matters is flagged.

Terminology — raw vs. logical image. The single most important byte-level finding is that the raw .sav file is not in RAM order. Reversing every 8-byte block (logical[i:i+8] = raw[i:i+8][::-1]) turns gibberish into structured data (proof in §4). Offsets below are file offsets unless explicitly marked logical; block-aligned ranges coincide, intra-block offsets are mirrored within their 8-byte block.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Verified (code + .sav bytes agree):

  • Media is EEPROM, 8192 bytes (EEPROM 64K), file fill byte 0xFF. cap-00-future-0.sav is entirely 0xFF (blank/erased); cap-01-future-1.sav is the only populated sample (SHA-256 in §2).
  • The low-level driver is an EEPROM serial-over-DMA3 driver to 0x0D000000 (FUN_08049838 DMA3, FUN_080498b8 read-8B, FUN_08049968 write-8B, FUN_08049a44 verify, FUN_08049a9c write+verify ×3). No SRAM (0x0E000000) byte-copy and no Flash 0x5555/0x2AAA command sequence exists anywhere in decompiled.c (grep: 0 hits for 5555/2aaa/0e000000; 5 hits for d000000, all in the EEPROM driver).
  • The per-8-byte block reversal between the raw file and the RAM/logical image (read/write drivers repack bits into u16s in descending order). After reversal, block 0 reads THPS3\x1e, and skater names (Geoff Rowley, Elissa Steamer, …, Skater Perso) become readable ASCII at logical 0x1baa+.
  • A 6-byte magic + 32-bit additive checksum guard exists in FUN_080218bc: returns 0 = valid, 1 = bad magic, 2 = bad checksum; the write path re-stamps both and marks the bytes dirty for flushing.
  • Save/load is a single 0x2000-byte image held in a RAM save-manager struct, with a 0x80-byte dirty bitmap at struct+0x2000 (1 bit per image byte) and a loaded flag at struct+0x2080. Only dirty 8-byte EEPROM blocks are written (FUN_0800a564); the whole image is read on load (FUN_0800a7ac, length 0x2000).

Static-only (code proven, bytes not independently confirming):

  • Exact checksum formula shape (sum32_le, §4) — but its seed/addend, covered length, and stored offset are literal-pool constants not present in this workspace, and no simple candidate verifies against cap-01 (exact computed vs. stored values in §4). This is the main reason confidence is not HIGH.
  • Serializer record layouts (FUN_08021560 0x55-byte record, FUN_08021eec 9-byte field, the 0x66-stride record array in FUN_08022280).

Hypotheses / unknowns:

  • Internal field semantics of the 0x66-stride records at logical 0x14a8+ and the 24-byte name/score records at logical 0x1ba8+ (the serializer bodies func_0x08021208, func_0x0802171c, func_0x08021ec4, func_0x08022038, func_0x08022080 are called through unrecovered jumptables and are absent from both decompiled.c bodies and callgraph.json).
  • Absolute RAM base of the save-manager struct (all _DAT_/iRam bases unresolved), generation/sequence counters (none found), and any backup copy (none found — §2).

Corpus note from PACKET.md: the cold-reload/checksum probe already failed upstream (mGBA save_export: No bounded save payload), and states/ contains 0 paired save states, so no reload behaviour could be observed directly; §6 is a plan, not results.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3)

All addresses verified in ghidra/decompiled.c; line references are to that file.

  • FUN_08049838(src, dst, count) — DMA3 transfer primitive (decompiled.c:29540). Saves the DMA enable word, disables DMA, merges a channel-control halfword from desc+6, sets DMA3 source = param_1, dest = param_2, count = param_3 & 0xFFFF | 0x80000000 (enable), then polls the high halfword until bit 0x8000 (busy) clears, and restores the enable word. This is the 0x040000D4 DMA3 register block from PACKET.md; Ghidra renders the registers as _DAT_ pointers, so the literal 0x040000D4 string does not appear — the identification rests on the register-write pattern plus both callers passing 0x0D000000, the EEPROM window. Confidence: CONFIRMED_STATIC for "DMA3", CONFIRMED_VERIFIED for "only used for EEPROM here".
  • FUN_080498b8(block_addr, out_ptr) — EEPROM read one 8-byte block (decompiled.c:29571). Guards block_addr < *(u16*)(desc+4). Builds the read command on the stack: address bits are emitted MSB-first (loop over descriptor byte +8 = address-bit count), followed by two 1 start/read bits; DMAs addr_bits + 3 halfwords to 0x0D000000, then DMAs 0x44 (68) halfwords from 0x0D000000 back to the stack buffer, then repacks 64 data bits (uVar4 = uVar4<<1 | bit, 16 bits × 4) into 4 u16s written at out_ptr+6 descending. The descending/+6 repack is exactly why each 8-byte block appears byte-reversed in the raw .sav (§4). Returns 0 on success, a saved error value otherwise.
  • FUN_08049968(block_addr, data_ptr) — EEPROM write one 8-byte block (decompiled.c:29629). Mirror image: expands 4 u16 data words plus address bits MSB-first into a bit stack (stop bit 0, then 1), DMAs addr_bits + 0x43 halfwords to 0x0D000000, calls FUN_0804976c (write-enable/latch sequencing: sets control bit 8 << addr_bit_pos, copies the 3-halfword EEPROM descriptor), polls the EEPROM window/busy byte (uRam0d000000 & 1), then FUN_080497f4 (write-disable cleanup). Returns 0 on success.
  • FUN_08049a44(block_addr, expected_ptr) — verify (decompiled.c:29693). Reads the block back with FUN_080498b8 into a 4×s16 stack buffer and compares element-wise; returns 0 on match, 0x8000 on first mismatch.
  • FUN_08049a9c(addr, data, …) — write + verify, ≤3 retries (decompiled.c:29731). for (i<3) { if (FUN_08049968()==0 && FUN_08049a44()==0) break; }. This is the reliability/redundancy mechanism of the format.
  • FUN_0804976c / FUN_080497f4 (decompiled.c:29477/29515): EEPROM control-register set/clear helpers used only by the write path.
  • FUN_08049f60 (listed in save_related_functions.c): a software divide/modulo helper, not save I/O — it is a seed only by address proximity and is called by arithmetic code (FUN_08049b88). Explicitly excluded.
  • FUN_080496cc(param) and FUN_08049734(type, out) (decompiled.c:29434/29458): save-type/WAITCNT-style configuration consulted before transfers — FUN_0800a564 calls func_0x080496cc(0x40) and func_0x08049734(2, …) and aborts with -1 if the type check fails. Their register values are _DAT_-based and unresolved, so the exact EEPROM-size programming is CONFIRMED_STATIC for existence, UNKNOWN for values.

Bulk movers:

  • FUN_0800a7ac(buf, len) — bulk EEPROM → RAM read (decompiled.c:5120): for (block = 0; block < (len>>3); block++) { FUN_080498b8(block, buf); buf += 8; } (with the same FUN_080496cc(0x40) guard).
  • FUN_0800a564(image, bitmap) — dirty-block flush (decompiled.c:4955): FUN_0800a414 scans the bitmap for the first set bit → block index uStack_2c; writes func_0x08049a9c(block, block*8 + image); clears that byte's bit in the bitmap; FUN_0800a4bc advances to the next set bit; loops until the bitmap byte index reaches 0x80. Only dirty blocks ever touch the EEPROM — which is why a first save on a blank chip leaves most of cap-01 at 0xFF.
  • FUN_0800a648(bitmap_base, image, ptr, len) — dirty-bit setter (decompiled.c:5009): computes off = ptr - image and sets one bit per byte. Called by the header/checksum stamper (6 and 4 bytes) and by both record serializers (9 and 0x55 bytes).

3.2 Serialization, header & checksum

  • FUN_080218bc(struct, image, write_mode) — header + checksum validate/stamp (decompiled.c:17194). Detailed in §4. In read mode it only validates; in write mode, if validation fails (bad magic or bad sum), it writes the 6-byte magic, marks 6 bytes dirty, recomputes the sum, stores it little-endian at the (unresolved) stored offset, marks 4 bytes dirty, and recurses in read mode to self-verify. Callers: FUN_08021b20 (write mode) and FUN_08021e28 (read mode) — callgraph.json agrees (0x080218bc: callers [0x08021b20, 0x08021e28], callees [0x0800a648]).
  • FUN_08021560(out, src) — 0x55-byte record serializer (decompiled.c:17108): zero-fills 85 bytes, then packs fields from a live struct: src+0x00, (u32)src+0x24, (u32)src+0x04, (u32)src+0x08, src+0x64/0x65/0x66, (u32)src+0x68, (u32)src+0x6c, a 16-byte copy from src+0x83, a 17-byte copy from src+0xd3, four 8-byte copies from src+0xe4 + n*8, a u32 from src+0x104 stored at out+0x4a, a string copy FUN_08013480(out+0x51, src+0x11c), and src+0x108..0x10a at out+0x4e..0x50. This is a pack function only; the matching unpack is among the unrecovered func_0x… bodies (open question).
  • FUN_08021eec(_, out9, src9) (decompiled.c:17465): zero + copy a 9-byte field (name/id-sized). FUN_0802209c (decompiled.c:17492) is the same pattern for 6 bytes. FUN_08022114(a, b, len) (decompiled.c:17513): memcmp returning 1 = equal. func_0x0804a030(dst, src, len) is the memcpy counterpart (callgraph: no recovered body/callers — jumptable alias).

3.3 Caller chains — how each was mapped, and what each mutates in RAM before flushing

Mapping method, identical for every chain: (1) start from the three MMIO seeds in save_related_functions.c; (2) walk callgraph.json callers transitively; (3) confirm every edge by reading the body in decompiled.c, because the graph has two known gaps — func_0x08049a9c (called from FUN_0800a564 at decompiled.c:4991) appears in the graph as FUN_08049a9c with zero callers, and the func_0x08021208/0802171c/08021ec4/08022038/08022080/0804a030 serializers have no graph node and no body at all (unrecovered jumptable targets). Where graph and body disagree, the body wins and the discrepancy is noted.

Chain A — load (read) path. … → FUN_08021e98 → FUN_08021e28 → {FUN_0800a7ac → FUN_080498b8 → FUN_08049838 → 0x0D000000, FUN_080218bc}

  • FUN_08021e98 (decompiled.c:17445): one-shot guard — if its guard byte is 0, call FUN_08021e28(struct, image=struct) and set the guard. Callers (graph + bodies): FUN_08022198, FUN_08022254, FUN_08022280.
  • FUN_08021e28 (decompiled.c:17408): FUN_08000d30(1) (interrupt/DMA lock helper), FUN_0800a7ac(image, 0x2000), FUN_08000d30(0); on success runs FUN_080218bc(struct, image, 0) via its tail and stores the result, setting struct+0x2080 = (result==0); on read failure sets +0x2080 = 0 and an error word = 0xf. RAM mutation: the entire 0x2000-byte image is overwritten from EEPROM; no live-game field is touched in this function.
  • Deserializing callers then unpack image → live structs: FUN_08022198 → func_0x08021ec4(struct, arg, struct + iRam080221b8); FUN_08022254 → func_0x0802171c(struct, arg, struct + iRam08022274); FUN_08022280 → func_0x08021208 repeated with source stride 0x60 (param2 + 0x00/0x60/0xC0/0x120/0x180…) into destinations with stride 0x66 (struct + n*0x66 + iRam08022340), 4 per iteration, iVar4 = 1,5,9,13 (< 0x11), then func_0x08022080(struct, arg+0x660, …) and func_0x08022038(struct, arg+0x668, …). Because the unpack bodies are unrecovered, which live fields each record feeds is UNKNOWN; the 0x66 destination stride is the sole hard fact, and it matches the observed 0x66 record periodicity in the logical image (§5).

Chain B — save (write) path. FUN_080418d4 / (unnamed roots) → FUN_0802234c | FUN_08022450 → FUN_08021b20 → {FUN_080218bc(write), FUN_0800a564 → func_0x08049a9c → FUN_08049968/FUN_08049a44 → FUN_080498b8/FUN_08049838}

  • FUN_08022450(struct, src, flush_flag) (decompiled.c:17697): packs a live sub-struct into an 85-byte stack buffer with FUN_08021560, memcmps (FUN_08022114, len 0x55) against the image at struct + _DAT_080224cc; only if different: sets a dirty flag byte, func_0x0804a030 copies the 85 bytes into the image, FUN_0800a648(struct+0x2000, struct, image_ptr, 0x55) marks them dirty; then if flush_flag != 0, FUN_08021b20(struct, struct). RAM mutation before flush: exactly that 0x55-byte image record.
  • FUN_0802234c(struct, src, flush_flag) (decompiled.c:17657): same shape for a 9-byte field — FUN_08021eec copies 9 bytes, compare vs. image at struct + _DAT_080223c8, on difference memcpy + dirty flag + FUN_0800a648(...,9), optional flush.
  • FUN_080418d4(arg) (decompiled.c:26182, graph root, no callers): FUN_08041490(); FUN_08022254(global_struct, arg) (load + unpack one sub-struct); if that returns 0, FUN_08022450(global_struct, arg, 0) (serialize back, no immediate flush). This is a load-then-reserialize synchronisation entry point.
  • FUN_08021b20(struct, image) (decompiled.c:17271): the flush gate. If struct's dirty byte is set and a second flag byte is clear: emits a UI/status call (func_0x08021dd8), calls FUN_080218bc(struct, image, 1) (stamp magic/checksum into the image + dirty bits), spins delay loops (func_0x08044660 ×20 — presumably waiting out EEPROM/UI timing, semantics UNKNOWN), then FUN_0800a564(image, struct+0x2000). On success clears the dirty byte; on failure re-displays status and returns 1. RAM mutation before flush: header magic (6 B) + checksum (4 B) via FUN_080218bc, plus whatever Chains B-records already packed.

Chain C — reset. FUN_080224e8(struct) (decompiled.c:17737, graph root): FUN_0800a79c(struct+0x2000) → FUN_0800a72c zeroes the 0x80-byte bitmap; clears +0x2080/+0x2081/+0x2083, sets two flag words (1, 0, 0xFFFFFFFF). It calls no EEPROM writer — a "new game" reset only takes effect on the next Chain-B flush.

Non-save neighbours explicitly excluded: FUN_080492e0 (calls func_0x08049ae8, a BIOS/jumptable stub — graphics/sound decompression context), and the many func_0x08049ae0/4/8/c, func_0x080496xx software-interrupt wrappers throughout decompiled.c are BIOS SWI thunks (software_interrupt(0x5…0x13)), not save I/O, despite their 0x08049… addresses.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 The per-8-byte block reversal (verified)

The EEPROM drivers transfer data as a serial bitstream and repack it into u16s in descending stack order (FUN_080498b8: puVar6 = (ushort*)(param_2 + 6), decrementing; FUN_08049968: bit stack built by decrementing puVar6). Consequently the byte order the emulator dumps to .sav is the reverse of RAM order within each 8-byte EEPROM block. Python proof on the real files:

raw = open('saves/cap-01-future-1.sav','rb').read()
logical = b''.join(raw[i:i+8][::-1] for i in range(0, 8192, 8))
logical[0:6]        # b'THPS3\x1e'
logical[0x1baa:0x1bb6]  # b'Geoff Rowley'
# raw block 0 is: ff ff 1e 33 53 50 48 54  -> logical: 54 48 50 53 33 1e ff ff

Raw block 0 (FF FF 1E 33 53 50 48 54) is meaningless; reversed it is THPS3\x1e + two 0xFF. Dozens of skater names (Geoff Rowley, Elissa Steamer, Rune Glifberg, Bam Margera, Eric Koston, Andrew Reynolds, Jamie Thomas, Rodney Mullen, Chad Muska, Kareem Campbell, Steve Caballero, Tony Hawk, and the French custom name Skater Perso at logical 0x1FA3) appear only after reversal. Confidence: CONFIRMED_VERIFIED — code mechanism + readable text in bytes.

4.2 Magic signature

  • Logical: offset 0x0000, 6 bytes: 54 48 50 53 33 1E = ASCII THPS3 + 0x1E.
  • Raw file: offset 0x0002, 6 bytes: 1E 33 53 50 48 54 (the same block-0 reversal; file bytes 0x0000–0x0001 are the logical trailing FF FF).
  • Code proof: FUN_080218bc compares buffer bytes 0..5 against a 6-byte string at _DAT_080218e0 (do { iVar3++ } while (byte[iVar3] == magic[iVar3]), fail ⇒ result 1), and in write mode copies 6 bytes from the same string (_DAT_08021b1c) and marks 6 bytes dirty. The string's ROM bytes are not in the workspace, but the .sav bytes after reversal match a 6-byte compare exactly, including the non-ASCII 0x1E terminator/version-like byte. verified_in_code: true (length + position + write-back), verified_in_sav: true (bytes present in cap-01, absent in blank cap-00).
  • No other magic was found: no SDK tag, no second header, no EEPROM/Flash signatures in code or bytes.

4.3 Checksum — exact static formula, and honest verification result

Decompiled proof (FUN_080218bc, decompiled.c:17216–17227, repeated at 17244–17256 for stamping):

iVar5 = *param_2 + _DAT_08021b10 + param_2[1] + param_2[2];   // u32 words 0,2 + one extra term
piVar4 = param_2 + 3;
iVar3 = _DAT_08021b14;
do { iVar5 += piVar4[0] + piVar4[1] + piVar4[2] + piVar4[3];  // 4 x u32 LE per iteration
     piVar4 += 4; iVar3 -= 4; } while (iVar3 != 0);
stored = u32_le_at(param_2 + _DAT_08021b18);
if (iVar5 != stored) result = 2;                              // bad checksum
// write mode: store iVar5 LE at param_2 + _DAT_08021b18, mark 4 bytes dirty, re-validate

So the algorithm class is certain: sum32_le — an unweighted 32-bit (wrapping) sum of little-endian u32 words over the image buffer, stored as one u32 LE. It is not CRC, not XOR, not byte-sum (all loops are int*-typed). What is not resolvable from this workspace: the three literal-pool constants _DAT_08021b10 (the extra addend — possibly a fourth header word, a seed, or a Ghidra-misrendered buffer word), _DAT_08021b14 (loop trip count ⇒ covered range), and _DAT_08021b18 (stored byte offset). Their values are ROM data at 0x08021b10/14/18; no ROM is provided.

Python verification actually run against both real files (raw and logical-reversed forms, every plausible stored offset/candidate):

cap-01 logical (rev8): sum32_le(0..0x1FFB) = 0xc4d220da   candidate stored u32@logical 0x1FFC = 0x7ee72cda   match=False
cap-01 logical (rev8): sum32_le(all)       = 0x43b94db4   u32@logical 0x14A4 = 0x0000ffff                      match=False

        prefix/contiguous word range ending at/before it (except trivial 0x00000000/0xFFFFFFFF words)
cap-00: all 0xFF — no magic, checksum undefined; consistent with 'blank chip rejected by FUN_080218bc result 1'

Conclusion, stated plainly: the checksum is CONFIRMED_STATIC (formula shape proven in code), verified_on_samples: false. The likely stored-offset candidates from the byte profile (0x14A0 raw / 0x1FFC logical) do not satisfy the formula under any tested coverage, seed-free interpretation; with the ROM literal values missing, the covered range and addend cannot be pinned down, and inventing a seed to force a match would be fabrication. PACKET.md's own upstream probe (No bounded save payload) is consistent with this being genuinely unresolved upstream too. Anyone repairing a fuzzed save (§6) must therefore either recover _DAT_08021b10/14/18 from ROM, or let the game itself re-stamp (write mode re-stamps whenever validation fails — but note it only re-stamps on a save flush, after a load has already rejected the image; see §6 caveat).

6. Save Fuzzing & Counterfactual Verification Plan

Precondition caveat: states/ is empty — there are no paired .ss save states in this workspace, contrary to the plan template's assumption. Every test below therefore requires first capturing a save state in an emulator at the title/profile screen with cap-01 loaded, then swapping the .sav file, cold-resetting, and observing (a) whether struct+0x2080 behaviour (save-present UI) changes, and (b) the predicted field effect. Checksum repair caveat: because _DAT_08021b10/14/18 are unresolved (§4.3), no fuzzed save can currently be hand-repaired with certainty. Two repair strategies, in order: (1) recover the three literal values from ROM address 0x08021B10 (12 bytes) and implement §4.3 exactly; (2) exploit the game's own re-stamp — FUN_080218bc write mode re-stamps magic+checksum whenever validation fails, so if a mutated image can be forced through a save flush (FUN_08021b20) without a prior rejecting load, the game repairs it itself; whether any menu path does this is itself a testable prediction (P0).

All offsets below are raw file offsets; remember to mutate the logical byte — i.e. file offset block_start + (7 - (logical_off & 7)) within its 8-byte block.

Appendix — Method & Reproducibility

  • Callers were traced in ghidra/callgraph.json (transitive caller walk from the three MMIO seeds) and every edge was confirmed against a body in ghidra/decompiled.c; two graph gaps (the func_0x08049a9c alias showing zero callers, and the bodiless func_0x08021208/0802171c/08021ec4/08022038/08022080) are documented in §3.3.
  • Byte work was done in Python over the real files: SHA-256 of both saves, active-range extraction (agrees with saves/hexdump_and_diffs.txt), the per-8-byte reversal transform, ASCII extraction, 0x66/0x18 periodicity searches, and the checksum candidate sweep quoted in §4.3 (sum32_le, byte-sum, XOR, CRC32; raw and logical forms; all aligned stored offsets). The companion machine-readable summary is save-format.json in this directory, with the same confidence labels.
