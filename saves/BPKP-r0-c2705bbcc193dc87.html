Payback (Europe) (En,Fr,De,Es,It) — Clean-Room GBA Save Format Report

Release key: BPKP-r0-c2705bbcc193dc87. Game code BPKP. ROM SHA-256: c2705bbcc193dc872ac481ea9c98c8f96ebee0dbcbbe44322226f0eff60665f1.

All findings derive only from saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (56 functions), ghidra/save_related_functions.c (5 functions), and ghidra/callgraph.json in this workspace, plus standard GBA hardware addresses. No third-party game data was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is a 512-byte EEPROM (eeprom512). Total file size is 512 bytes in both samples.
  • Physical EEPROM word 0 (file 0x00..0x07) holds ASCII magic Payback..
  • Physical word 1 (file 0x08..0x0F) is a journalling header. Value FF FF FF FF FF FF FF FF means no pending transaction.
  • Physical words 2..5 (file 0x10..0x2F) are a 32-byte journal staging area.
  • Physical words 6..63 (file 0x30..0x1FF) hold 464 bytes of logical save data.
  • Game logical bytes are reversed inside each 8-byte EEPROM word relative to the .sav file. Logical offset L maps to file offset (6 + L//8)*8 + (7 - L%8).
  • There is no arithmetic checksum (sum, XOR, or CRC) over the save. Integrity uses the magic, the repeated journal header, per-field range validation on load, and EEPROM write read-back verification with retry.
  • Logical layout is fully sized. Offset 0 is a 1-byte validated selector. Offsets 1..4 are a 4-byte nibble-validated field. Offsets 5..268 are 11 identical 24-byte entries. Offsets 269..463 are 5 records of 39 bytes each. 269 + 5*39 = 464 = 0x1D0, matching the hard bound in the read and write functions.

Static-only facts (CONFIRMED_STATIC):

  • The low-level EEPROM serial driver, DMA3 helper, journalling writer, direct writer, reader, boot recovery routine, defaults writer, load validator, and menu writer were all traced in decompiled C. Their call graph edges match ghidra/callgraph.json, with one exception noted in section 3.
  • Exact numeric RAM mirror addresses cannot be recovered. Decompiled code references RAM through unresolved literal pools such as _DAT_080281c4 and _DAT_080281d8. Those symbols are ROM literal addresses, not the RAM values they point to.

Hypotheses and unknowns:

  • Semantic names for the 4-byte nibble field, the 11 entries, and the 18-byte record tails remain unknown. Their sizes, offsets, writers, readers, defaults, and validation rules are proven. Their gameplay meanings are not.
  • The defaults constants loaded from _DAT_08028090 and _DAT_08028094.._DAT_080280a8 are visible only as resulting bytes in the .sav files. Their ROM values were not separately provided.
  • No paired .ss save states exist in this workspace (states/ is empty). Section 6 is therefore a test plan, not an executed reload test.

The two samples differ in exactly 17 bytes. Every difference is explained by header creation and one journalling write of logical offset 0. See section 4.

There is one logical save, not multiple save slots at the physical level. The five 39-byte records inside the logical area are application records. They are not redundant copies of each other. In both samples all five records have flag 0 and 0xFF names and tails.

Byte reversal inside words

The EEPROM drivers expand each u16 into 16 serial bits, most-significant bit first, and reassemble received bits the same way (FUN_0807c474 lines with uVar4 = uVar4 << 1 | *puVar5 & 1, FUN_0807c538 bit expansion loops). The net effect seen in the .sav files is that the game's logical byte order is reversed within each 8-byte word.

Proof from bytes:

  • Logical offset 0 maps to file 0x37. In cap-00 it is 0xFF. In cap-01 it is 0x01. PACKET.md independently flags 0x37 as the mutation-probe and candidate-checksum offset. Section 4 shows it is a validated field, not a checksum.
  • The five record flags at logical 269, 308, 347, 386, 425 map to file 0x13A, 0x163, 0x18C, 0x1B5, 0x1DE. All five file bytes are 0x00 in both samples. Four of them appear as isolated non-0xFF bytes in saves/hexdump_and_diffs.txt. The fifth (0x13A) sits inside the large active range.
  • FUN_08027f90 writes single zero bytes at literal 0x134 (308) and 0x182 (386), plus three unresolved literals. The inferred full set 269, 308, 347, 386, 425 is an arithmetic progression with stride 39. It matches all five observed zero bytes.

Redundancy and selection rule

Redundancy is transactional, not mirrored slots:

  1. FUN_080277a4 (journalling writer) first writes the new words into staging words 2...
  2. It then writes journal header word 1 containing the destination word and block count repeated four times.
  3. It then writes the same words to their real destination words 6...
  4. It then clears word 1 to FF×8.
  5. At boot, FUN_08027c68 checks the magic. If the magic is valid and the journal header passes its repetition and range checks, it replays the staged words to their destination and clears the header. This recovers a write interrupted between steps 2 and 4.
  6. Every low-level write (FUN_0807c6f0) is verified by read-back comparison (FUN_0807c698) and retried up to 3 times.

Selection rule: there is nothing to select. Word 0 decides only whether the save exists. Word 1 decides only whether an interrupted journalling write must be replayed. The logical area is then read directly. No generation counter, sequence number, or A/B slot choice exists anywhere in the traced code or in the bytes. The repeated (destination, count) pairs in word 1 are a consistency check, not a generation counter. No counter field increments between the two samples. The only changed logical byte is offset 0 (0xFF to 0x01).

Active spans from PACKET.md map as follows. File 0x30..0x137 plus 0x13A..0x13F is the first 264-plus logical bytes (offsets 0..268 reversed per word, with three 0xFF payload bytes breaking the precomputed range). File 0x163, 0x18C, 0x1B5, 0x1DE are record flags 1..4. Record flag 0 at file 0x13A is inside the first span.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

FUN_0807c3f4 at 0x0807c3f4 — DMA3 helper.

  • Saves and clears a control word, merges a timing halfword, then stores param_1 as source, param_2 as destination, and param_3 & 0xFFFF | 0x80000000 as the DMA count-plus-enable word. It polls bit 0x8000 of the count word until clear, then restores the saved control word.
  • The register pointers are unresolved literal pools (_DAT_0807c454, _DAT_0807c464, _DAT_0807c468, _DAT_0807c46c). Their arrangement matches GBA DMA3 source (0x040000D4), destination (0x040000D8), and control (0x040000DC) as given in the task hardware spec. Exact numeric addresses are CONFIRMED_STATIC by pattern, not by a resolved literal.
  • Callers: FUN_0807c474 and FUN_0807c538 only. This matches ghidra/callgraph.json.

FUN_0807c474 at 0x0807c474 — EEPROM read of one 8-byte word.

  • Input param_1 is an EEPROM word address, masked to 16 bits and rejected if not below the descriptor word count. Input param_2 is an 8-byte output buffer (passed as int by Ghidra).
  • It pushes the address bits, most-significant bit first, into a stack bit array, appends two 1 bits, DMA-transfers address_bits + 3 halfwords from the stack to 0x0D000000, then DMA-transfers 0x44 (68) halfwords back from 0x0D000000. It reassembles 4 u16 values by shifting in one bit at a time and stores them in reverse word order into the output buffer.
  • Callers in code: FUN_080277a4 (read-modify-write), FUN_08027a2c (read-modify-write), FUN_08027b6c (reader), FUN_08027c68 (boot recovery), FUN_0807c698 (verifier). ghidra/callgraph.json lists only FUN_0807c698. The other edges use the unresolved-indirect-call form func_0x0807c474 and were mapped by reading every call site in ghidra/decompiled.c. That is how each caller in this section was mapped: direct textual search for func_0x0807c474, func_0x0807c6f0, func_0x0807c524, and func_0x0807c538 across the full decompilation, cross-checked against ghidra/callgraph.json.

FUN_0807c538 at 0x0807c538 — EEPROM write of one 8-byte word.

  • Inputs are a word address, a u16* 8-byte source buffer, and a wait flag. It expands the 64 data bits, then the address bits, then the bits 0 and 1, into a stack bitstream, and DMA-transfers address_bits + 0x43 halfwords to 0x0D000000.
  • If the wait flag is non-zero, it polls the low bit of 0x0D000000 and a timer-like counter (wrapping at 0xE4, giving up after 0x88 accumulated ticks) to wait for write completion.
  • Sole caller: FUN_0807c524. This matches ghidra/callgraph.json.

FUN_0807c524 at 0x0807c524 — write wrapper. It calls FUN_0807c538 with wait flag 1 and returns its low 16 bits. Sole caller: FUN_0807c6f0.

FUN_0807c698 at 0x0807c698 — write verifier. It re-reads the word with FUN_0807c474 and compares all 4 u16 values against the intended buffer. It returns 0 on match and 0x8000 on the first mismatch. Sole caller: FUN_0807c6f0.

FUN_0807c6f0 at 0x0807c6f0 — verified EEPROM word write.

  • Loop of at most 3 attempts: call FUN_0807c524 to write, and if that returns 0, call FUN_0807c698 to verify. Break on verified success. Return the last status.
  • Callers in code: FUN_080277a4 (staging, header, destination, header-clear writes), FUN_08027a2c (direct writes), FUN_08027c68 (recovery replay and first-boot writes). ghidra/callgraph.json lists these edges.

FUN_0807c3ac at 0x0807c3ac — EEPROM init. Called once as FUN_0807c3ac(4) by FUN_08027c68. It writes one of three descriptor locations depending on whether the argument is 4, 0x40, or anything else, and returns 0 or 1. The descriptor fields it selects are the ones later read as word count (+4) and address-bit count (+8).

There is no SRAM byte-copy driver and no Flash 0x5555/0x2AAA command sequence anywhere in the 56 decompiled functions. The only save-media address used is 0x0D000000 (EEPROM via DMA3). All other func_0x0807c7f4 / func_0x0807c7f8 / func_0x0807c800 / func_0x0807c804 / func_0x0807c808 / func_0x0807c80c calls are unresolved indirect calls with no EEPROM operands. They are graphics and system helpers, not save I/O.

3.2 Serialization, deserialization, and integrity routines

FUN_08027b6c at 0x08027b6c — logical reader (deserialize).

  • Signature: FUN_08027b6c(byte_offset, dst, byte_count). It rejects negative offsets and any range ending past 0x1D0 (464). There is no per-call length cap beyond the range check.
  • It converts the byte offset to a starting EEPROM word (offset >> 3) + 6 and an intra-word byte position offset & 7. For each touched word it calls FUN_0807c474 into a 9-byte stack frame (data at +1) and copies out only the requested bytes. It returns 0 on success and 0xFFFFFFFF on a bad range or driver error.
  • Sole caller in the traced set: FUN_08028134. See section 3.3.

FUN_08027a2c at 0x08027a2c — direct logical writer (serialize, no journal).

  • Signature mirrors the reader. It rejects ranges past 0x1D0 and counts above 0x18 (24) or below 1.
  • For each touched word it read-modify-writes: FUN_0807c474 the current word, splice in the new bytes, then FUN_0807c6f0 the merged word back to the same destination word (offset >> 3) + 6 + index. No staging and no journal header are involved.
  • Sole caller: FUN_08027f90 (defaults writer). A failure in any word aborts with 0xFFFFFFFF.

FUN_080277a4 at 0x080277a4 — journalling logical writer (serialize with crash recovery).

  • Same range rules as FUN_08027a2c: end offset at most 0x1D0, count 1..24 (0x18). The 24-byte cap bounds a transaction to at most 4 EEPROM words, which is exactly the staging capacity of words 2..5. The cap is therefore structural, not arbitrary.
  • Phase 1 (stage): for each touched destination word, read-modify-write the merged word into staging word 2 + index via FUN_0807c6f0.
  • Phase 2 (arm): build an 8-byte header in stack bytes uStack_4c..uStack_45 as four repeats of (start destination word, touched-word count) and write it to word 1 via FUN_0807c6f0. In driver buffer order the bytes are [dest, count, dest, count, dest, count, dest, count].
  • Phase 3 (commit): write each staged word to its real destination word 6 + (offset >> 3) + index via FUN_0807c6f0.
  • Phase 4 (disarm): overwrite word 1 with FF×8 via FUN_0807c6f0.
  • Callers: FUN_08028134 (repairs) and FUN_080294c4 (selector commit). Both are detailed in section 3.3.

FUN_08027c68 at 0x08027c68 — boot probe, journal recovery, and first-boot creation.

  • Calls FUN_0807c3ac(4), then reads word 0 with FUN_0807c474. In driver buffer order it compares the 8 bytes against ., k, c, a, b, y, a, P at stack offsets bStack_28 down to bStack_21. That is the file-order string Payback. reversed, confirming the per-word reversal in section 2.
  • If the magic matches: it reads word 1. It takes dest = bStack_28 and count = bStack_27 (driver buffer order) and requires all of: 6 <= dest <= 62, 1 <= count <= 4, and the remaining six bytes repeat the same (dest, count) pair three more times. If all checks pass, it copies each staging word 2 + i to destination word dest + i with FUN_0807c474 + FUN_0807c6f0, then clears word 1 to FF×8. If the header is FF×8 or otherwise invalid, it does nothing and returns success. A partially valid header is ignored, not replayed.
  • If the magic does not match: it clears word 1 to FF×8, calls FUN_08027f90 to write all defaults, sets the stack bytes to the magic pattern, writes word 0 (file Payback.) via FUN_0807c6f0, and returns success.
  • Any driver error at any step aborts to the return with the error status. No caller in the traced set. It is a boot entry point.

There is no checksum routine. No function in the save cluster sums, XORs, or CRCs save bytes. The integrity routines are exactly: the magic compare, the journal header repetition and range check, the per-field validation in FUN_08028134, and the write verify-and-retry in FUN_0807c6f0 / FUN_0807c698.

3.3 All callers, how each was mapped, and how each mutates the save

Mapping method for every caller below: (1) textual search of ghidra/decompiled.c for each driver and serializer name, including the func_0x… unresolved-indirect spelling; (2) cross-check against ghidra/callgraph.json; (3) read the full body of each calling function to determine which bytes it changes and with what values. Where the callgraph and the decompiled text disagree, the decompiled text wins and the disagreement is stated.

FUN_08027f90 at 0x08027f90 — defaults writer and post-init sequencer.

  • How mapped: sole caller is FUN_08027c68 (magic-missing branch). It is also the only caller of FUN_08027a2c in the whole decompilation.
  • How it mutates the save: it writes through FUN_08027a2c only. It never touches words 0, 1, or the staging area directly.
  • FUN_08027a2c(1, &uStack_14, 4) with uStack_14 = _DAT_08028090: writes the 4-byte default at logical 1..4. Observed logical bytes 10 45 98 76 in both samples.
  • Loop iVar4 from 0 to 10 (11 entries): writes six 4-byte defaults (_DAT_08028094, _DAT_08028098, _DAT_0802809c, _DAT_080280a0, _DAT_080280a4, _DAT_080280a8) at logical iVar4*0x18 + 5, +9, +13, +17, +21, +25. That is 11 entries of 24 bytes at logical 5..268. Observed: all 11 entries identical, each 20 a1 07 e0 40 42 0f e0 60 e3 16 e0 80 84 1e e0 a0 25 26 e0 c0 c6 2d e0 in logical byte order.
  • uStack_14 = 0, then five 1-byte writes of 0 at logical _DAT_080280ac, 0x134 (308), _DAT_080280b0, 0x182 (386), _DAT_080280b4. The two resolved literals and the observed zero bytes fix the full set as 269, 308, 347, 386, 425 (stride 39). These are the five record flags. The three unresolved literals are inferred, and that inference is marked in the field map.
  • Logical offset 0 is not written here. Names and record tails are not written here. They remain 0xFF on a fresh save, which both samples show.
  • After the save writes, it calls FUN_08027f4c, then performs non-save hardware setup (writes to 0x04000000-range registers via uRam04000000, calls FUN_080731d8, FUN_080732ac, func_0x0807c7f8, FUN_08077f44, FUN_0806c61c, FUN_080294c4, FUN_0806c778, FUN_08025b58, FUN_08027f04). Those calls do not touch EEPROM. FUN_080294c4 is a menu loop (see below); its presence here means the defaults path falls into the same menu flow.
  • It does not read the save. It blindly overwrites offsets 1..268 and the five flags.

FUN_08028134 at 0x08028134 — load, validate, repair, and apply.

  • How mapped: no caller in the traced set and no callgraph caller. It is an entry point, most plausibly reached from a menu or boot flow outside the 56 traced functions. It is the sole caller of FUN_08027b6c and one of two callers of FUN_080277a4.
  • It begins with FUN_08027f04 (copies four constant halfwords and words into RAM through literal-pool pointers; no EEPROM access; treated as a settings-apply helper, CONFIRMED_STATIC).
  • Read 1: FUN_08027b6c(0, _DAT_080281c4, 1) reads logical offset 0 (language or locale selector; the title ships En, Fr, De, Es, It, and the valid range is 0..4) into a RAM halfword. If the value is greater than 4, it replaces it with a default from uRam08028414 and repairs the save with FUN_080277a4(0, puVar2, 1). It then indexes a 20-byte-stride string table with the value and picks a RAM pointer depending on a string compare (FUN_08077d78). The in-RAM struct field is the halfword at _DAT_080281c4. Its numeric RAM address is unrecoverable (literal pool).
  • Read 2: FUN_08027b6c(1, &uStack_20, 4) reads logical 1..4 as a u32. It splits the word into 8 nibbles and stores them as 8 halfwords at _DAT_080281d8[0..7], masking each extraction with (u16)_DAT_080281c0. It validates all 8: if any nibble is greater than 9, or equals 2, or equals 3, the whole field is considered corrupt. On corruption it loads 8 replacement halfwords from ROM constants (uRam080283bc and neighbours, packed back into uStack_24) and repairs with FUN_080277a4(1, &uStack_24, 4). On success the 8 halfwords remain in RAM as the live decoded field. Observed value in both samples: u32 0x76984510, nibbles (least significant first) 0,1,5,4,8,9,6,7. All valid. No repair fires.
  • Read 3 (record flags and names): loop iVar18 from 0 to 4. It reads 1 byte at logical iVar18*0x27 + 0x10D (269 + 39·i). If the byte is greater than 2, it zeroes it and repairs with FUN_080277a4(that offset, &bStack_19, 1). It stores the byte into a RAM array at _DAT_080283d0 + i. If the byte is 0, it writes a 0 byte into a RAM name buffer at i*0x14 + _DAT_080283cc and does not read the name. If the byte is non-zero, it reads 20 bytes at logical i*0x27 + 0x10E into that RAM buffer and scans for a 0 terminator. If none of the 20 bytes is 0, it zeroes the RAM flag byte and the first RAM name byte and repairs the flag with FUN_080277a4(i*0x27 + 0x10D, &bStack_19, 1) where bStack_19 is false (0). Observed: all five flags are 0, so no name is ever read and this repair never fires on the samples. The flag semantics 0 = empty are proven. The meanings of flag values 1 and 2 are unknown.
  • Read 4 (entry table references): nested loops iVar7 0..10 and iVar18 0..5 read 4 bytes at logical (iVar7*6 + iVar18)*4 + 5 — that is, every 4-byte field of the 11×24-byte entry table written by FUN_08027f90. For each field it splits off the top nibble (uStack_28 >> 0x1C) as a record reference and the low 28 bits (& _DAT_080283dc) as a value. It mirrors the reference byte into a RAM array and the value into a RAM u32 array. Repairs:
  • If the reference is below 5 but the referenced record's RAM flag byte is 0 (empty), it sets the reference to 0xF (15) and repairs with FUN_080277a4(field_offset, &uStack_28, 4).
  • Else if the reference is between 5 and 13 inclusive, it sets the reference to 0xE (14), computes a replacement value from two ROM constants and the column index, and repairs the same way.
  • References 0xE and 0xF need no repair. Observed: every entry field has top nibble 0xE. No repair fires. 0xE therefore means a default or unlinked state. The exact distinction between 0xE and 0xF is unknown.
  • It ends with FUN_08027f4c (settings-apply helper). The infinite outer loop with iVar7 wrapping past 10 is a Ghidra loop-recovery artefact around the final FUN_08027f4c call, not save logic.
  • Net mutation behaviour: FUN_08028134 is read-mostly. It writes only to fix out-of-range bytes, and always through the journalling writer FUN_080277a4. On both samples it would perform zero writes.

FUN_080294c4 at 0x080294c4 — interactive menu that commits logical offset 0.

  • How mapped: called by FUN_08027f90 (with (*_DAT_08028128, 0)) and internally by FUN_0806c82c-adjacent flows. In the save cluster it is the second caller of FUN_080277a4. The bulk of the function is text and sprite rendering (FUN_08028c08, FUN_08029198, FUN_08028ac4) and input handling through param_1 button bytes. Those callees do not touch EEPROM.
  • The single save mutation: when the confirm path is taken (param_1+2, +3, +4 byte pattern with the debounce flag set), it stores the current selection index into the halfword at _DAT_08029a70, then calls FUN_08027f04, then FUN_080277a4(0, psVar13, 1) — a journalling write of 1 byte at logical offset 0 — then FUN_08027f4c. It then re-derives a RAM pointer from the new value via a 20-byte-stride table compare.
  • This is the writer that changed logical offset 0 from 0xFF to 0x01 between the two samples. The staged staging-word residue in cap-01 (word 2 equals word 6) is the fingerprint of this journalling write. See section 4.

FUN_08027f04 at 0x08027f04 and FUN_08027f4c at 0x08027f4c — settings-apply helpers.

  • Both copy constant halfwords and words from ROM literal pools into RAM locations named by other literal pools. Neither reads or writes EEPROM. Callers: FUN_08028134 (start and end), FUN_08027f90 (FUN_08027f4c after defaults, FUN_08027f04 at the end), FUN_080294c4 (around the offset-0 commit). ghidra/callgraph.json agrees. They plausibly publish loaded save values into live game RAM. Which RAM fields they set cannot be determined without the literal values. Functions explicitly excluded after reading them:

They call only unresolved graphics helpers and FUN_08027f04 / FUN_08027f4c in duplicated epilogue patterns at the sites found by the search above. They never call an EEPROM function.   • FUN_0802555e and FUN_0802557c are thin wrappers over FUN_08022e0a and FUN_08023014. FUN_08025b58 toggles a bit in a 0x04000000-range register. None touch EEPROM.

Caller-chain summary (entry to EEPROM):

  • Boot and recovery: FUN_08027c68 → FUN_0807c474 / FUN_0807c6f0 → FUN_0807c524 → FUN_0807c538 → FUN_0807c3f4 → DMA3 → 0x0D000000. First boot additionally runs FUN_08027c68 → FUN_08027f90 → FUN_08027a2c → FUN_0807c474 / FUN_0807c6f0.
  • Load and repair: FUN_08028134 → FUN_08027b6c → FUN_0807c474 → FUN_0807c3f4. Repairs go FUN_08028134 → FUN_080277a4 → FUN_0807c474 / FUN_0807c6f0.
  • Menu commit: FUN_080294c4 → FUN_080277a4 (1 byte at logical 0).
  • Defaults: FUN_08027f90 → FUN_08027a2c (direct, no journal).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Bytes (file order): 50 61 79 62 61 63 6B 2E, ASCII Payback., at file offset 0x00, EEPROM word 0.
  • Verified in code: FUN_08027c68 compares the driver-buffer bytes against this string reversed. It also writes the same pattern on first boot.
  • Verified in .sav: present in cap-01-future-1.sav. Absent (all FF) in cap-00-future-0.sav, which is the pre-creation or interrupted-creation state. The defaults are already present in cap-00, so cap-00 was captured after FUN_08027f90 ran but before or without the final word-0 write, or the header was later erased. The code path writes word 1 clear, then defaults, then word 0, in that order.

There is no arithmetic checksum

No save function computes a sum, XOR, or CRC over save bytes. The name FUN_0807c9c8 was checked: it is a signed division routine (it negates negative operands, performs shift-and-subtract division, and restores the sign). It is called with gameplay values, never with save buffers. No other candidate exists in the 56 functions.

The candidate byte flagged by PACKET.md at file 0x37 is not a checksum. File 0x37 is logical offset 0 (see the reversal mapping in section 2): the selector byte validated by FUN_08028134 (> 4 triggers a repair write) and committed by FUN_080294c4 through FUN_080277a4. Mutating it to an out-of-range value forces a repair-and-rewrite on load. Mutating it within 0..4 silently changes the selection. Both behaviours match the probe result in PACKET.md (integrity_check_confirmed: true, save_rewritten_after_mutation: true, visual_delta_after_mutation: false is not explained by this byte alone and remains a probe observation).

The actual integrity algorithm (journal header)

  • Stored location: EEPROM word 1, file 0x08..0x0F, 8 bytes.
  • Idle value: FF FF FF FF FF FF FF FF. Any transaction in progress replaces it.
  • Armed value (driver buffer order): [dest_word, block_count, dest_word, block_count, dest_word, block_count, dest_word, block_count], written by FUN_080277a4 phase 2 and read back by FUN_08027c68.
  • Validation in FUN_08027c68, exact: let A be buffer byte 0 and B be buffer byte 1. Replay only if 6 <= A <= 62, 1 <= B <= 4, and buffer bytes 2..7 equal A, B, A, B, A, B in buffer order. That is, all four A copies agree, all four B copies agree, the destination lies inside the logical word range, and the count fits the 4-word staging area.
  • Covered range: the transaction it describes. Staging words 2..2+B-1 (file 0x10..) are copied to destination words A..A+B-1 (file A*8..). After replay, or after a successful commit, word 1 is reset to FF×8.
  • This is a repetition-consistency check, not a function of the payload bytes. Corrupting the payload in staging or at the destination is not detected by it. Payload protection at write time is instead the read-back compare in FUN_0807c698, retried 3 times by FUN_0807c6f0. Payload protection at load time is the per-field validation in FUN_08028134 (section 3.3), which repairs only the fields it checks.
  • Note on coverage limits in FUN_08027c68's replay: the candidate set is read with separate FUN_0807c474 + FUN_0807c6f0 pairs (with extra unrolled pairs when (count & 3) requires them). A power loss during replay can leave word 1 armed and a prefix of destinations updated. The next boot replays again. Replay is idempotent because staging is never modified by replay.
