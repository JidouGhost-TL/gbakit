1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (physical layout and integrity model: high; payload field semantics: LOW).

Verified by both code and .sav bytes:

  • Physical medium is SRAM at 0x0E000000, total image size 32,768 bytes (SRAM 256K = 256 Kbit), SDK tag SRAM_V112, fill/erased byte 0xFF.
  • Exactly one contiguous save record is written: SRAM offset 0x0000, length 0x6D8 = 1,752 bytes. The writer FUN_0800036c calls func_0x08015174(RAM_struct, 0x0E000000, 0x6D8) and the reader FUN_08000418 calls func_0x08015110(0x0E000000, RAM_struct, 0x6D8).
  • Offset 0x00 holds a 4-byte little-endian magic C6 66 F0 89 (u32_le 0x89F066C6). The writer stores it unconditionally (*puVar1 = _DAT_08000414 in FUN_0800036c, ghidra/decompiled.c:25) before writing; the reader branches on *piVar1 != _DAT_080004a0 (FUN_08000418, ghidra/decompiled.c:56). Both unresolved _DAT_ literals are inferred to be the same constant because the observed .sav bytes at 0x00..0x03 are exactly c6 66 f0 89 in the only non-blank sample.
  • There is no arithmetic checksum (no sum/XOR/CRC) in the writer, reader, or either low-level driver in the decompilation. Integrity on write is a byte-for-byte verify-after-write: FUN_0800036c calls func_0x080151e4(RAM_struct, 0x0E000000, 0x6D8) after FUN_08015174 and forwards its result uVar3 to the unrecovered jumptable continuation (ghidra/decompiled.c:31-36). Integrity on load is the magic comparison only, within the evidence available.
  • cap-00-future-0.sav is entirely 0xFF (blank/erased). cap-01-future-1.sav differs in exactly the 1,752 bytes 0x0000..0x06D7; inside that record only the 4 magic bytes are non-zero and all other 1,748 bytes are 0x00. Bytes 0x06D8..0x7FFF remain 0xFF. This is a freshly initialised/blank-progress record, not a progressed game save.

Static-only facts:

  • The RAM struct tail fields at struct offset 0x6D0 (u32, index 0x1B4 as a u32*) and probably 0x6D4 (u8, low byte of index 0x1B5) are copied between globals and the struct by both writer and reader.
  • The exact RAM base address of the struct is not recoverable from this packet: Ghidra left it as unresolved literals _DAT_080003ec (writer) and _DAT_0800049c (reader). No 0x02xxxxxx/0x03xxxxxx address is asserted anywhere in this report or JSON.

Hypotheses / unknowns (LOW confidence):

  • Semantic subdivision of payload bytes 0x04..0x6CF (1,740 bytes). Every payload byte is 0x00 in the sole non-blank sample, and no other decompiled function reads or writes the SRAM struct, so no unit/progress/score field can be named honestly.
  • Whether the 0x6D0 dword or 0x6D4 byte is a generation counter, settings word, or other global. They are 0 in the fresh record and only their copy direction is proven.

What remains open: progressed-save samples (needed to map payload), resolved _DAT_ literal pool values (needed for RAM addresses and exact global identities), and recovery of the unrecovered jumptable dispatchers that invoke FUN_0800036c/FUN_08000418.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (method)

Three independent routes were used and cross-checked:

  1. Textual func_0x........() references inside ghidra/decompiled.c — the only reliable edges for the save seeds, because ghidra/callgraph.json lists 0x0800036c and 0x08000418 with empty callers/callees arrays. The callgraph appears to record only FUN_→FUN_ edges; calls written as func_0x08015174(...) etc. are absent from it. This discrepancy is reported, not papered over.
  2. ghidra/callgraph.json edges for the rest of the 57 functions (17 edges total; enumerated in §3.5) to determine whether any non-seed function can reach a save driver. None can: no listed edge targets 0x0800036c, 0x08000418, 0x08015110, 0x08015174, or 0x080151e4.
  3. Constant search over decompiled.c for 0xE000000, 0x6D8, Flash/EEPROM constants (see §2). Only the two seed functions and the three FUN_080151xx drivers mention SRAM at all.

Both seed functions end in UNRECOVERED_JUMPTABLE indirect jumps (Ghidra could not recover the jump tables at 0x080003ea/0x08000498), and both have zero callers in the callgraph. They are therefore state-machine continuations / dispatch targets whose invoking context is not present in this packet; their trigger context is honestly recorded as unknown rather than invented.

3.3 Serializer / writer: FUN_0800036c (ghidra/decompiled.c:6)

Step-by-step (line numbers in ghidra/decompiled.c):

  1. func_0x08014338() (line 14) — guard/lock entry. FUN_08014338 (:1264) checks *piVar2 + _DAT < 2, adds +10 to the same global word, zeroes two halfwords, and calls func_0x080150e0 (BIOS SWI wrapper, FUN_080150e0:1648 is software_interrupt(0xB)). Its mirror FUN_08014384 (:1294) subtracts 10 and writes 0xB600 halfwords. These two bracket the SRAM write as a matched lock/unlock pair (most plausibly sound/interrupt suppression while SRAM timing is altered); neither touches save payload bytes.
  2. Header field updates in the RAM struct puVar1 = _DAT_080003ec (line 15):
  • puVar1[0x1B4] = *_DAT_080003f0 (line 16) — copies a global u32 into struct offset 0x1B4*4 = 0x6D0.
  • *(undefined1*)((int)puVar1 + _DAT_080003f8) = *_DAT_080003f4 (line 17) — copies a global byte into a struct byte offset held in an unresolved literal; the matching reader offset is 0x6D4 (see §3.4), so 0x6D4 is the probable offset (HYPOTHESIS for the writer side, CONFIRMED_STATIC for the reader side).
  • *puVar1 = _DAT_08000414 (line 25) — stores the magic constant at offset 0x00, unconditionally, immediately before flushing. This proves the magic is a constant, not a computed checksum: no accumulation over the struct occurs anywhere in the function.
  1. The intervening puVar2 writes (lines 18–24, 27–30) repeatedly write three words through _DAT_080003fc and spin while a word's sign bit is set. Through unresolved literals this cannot be resolved definitively; the three-word src/dst/control pattern with a busy-wait is consistent with DMA3 (0x040000D4/D8/DC) register pokes used elsewhere by this SDK, but because the literal is unresolved this is recorded as an unresolved DMA-like setup, not as the save transfer itself — the actual save transfer is unambiguously the byte loop in FUN_08015174.
  2. func_0x08015174(_DAT_080003ec, 0xE000000, 0x6D8) (line 31) — flush RAM struct → SRAM 0x0E000000, 1,752 bytes.
  3. uVar3 = func_0x080151e4(puVar1, 0xE000000, 0x6D8) (line 32) — verify-after-write.
  4. func_0x08014384() (line 33) — lock release; then the unrecovered jumptable is called with uVar3 (lines 36), i.e. the verify result selects the next state.

Callers of FUN_0800036c: none in callgraph.json, none textual in decompiled.c. It is reached only through the unrecovered dispatch mechanism. No other function in the corpus mutates the RAM save struct before a flush; the only pre-flush mutations that exist anywhere are the three header stores in steps 2 above, performed by the writer itself.

3.4 Deserializer / reader: FUN_08000418 (ghidra/decompiled.c:45)

  1. func_0x08015110(0xE000000, _DAT_0800049c, 0x6D8) (line 54) — read SRAM 0x0E000000 → RAM struct piVar1, 1,752 bytes.
  2. Magic gate (lines 56–61): if (*piVar1 != _DAT_080004a0) — if u32_le[0x00] != magic, it seeds auStack_c[0] = 0 and writes three pointer words through _DAT_080004a4 (same unresolved three-word DMA-like pattern as the writer). No re-write to SRAM occurs in this branch within the visible code, and no payload field is individually cleared in visible code; the branch is recorded as the invalid/blank-save initialisation path whose full effect is inside the unresolved pointer writes.
  3. Tail exports (lines 62–63), executed regardless of the magic branch:
  • *_DAT_080004ac = piVar1[0x1B4] — struct u32 at offset 0x6D0 → global.
  • *_DAT_080004b0 = (char)piVar1[0x1B5] — low byte of the u32 slot at offset 0x1B5*4 = 0x6D4 → global byte. (Ghidra models the struct as int*, so the saved field is the byte at 0x6D4; bytes 0x6D5..0x6D7 are never separately accessed.)
  1. Further unresolved three-word pointer writes (lines 64–74), sign-bit busy-wait, then unrecovered jumptable called with 0 (line 77).

Callers of FUN_08000418: none in callgraph.json, none textual. Symmetrically to the writer, only the magic word and the two tail fields are ever extracted from the loaded struct by any code in this corpus. No function in decompiled.c reads payload bytes 0x04..0x6CF from the struct — that is the central limitation of this packet and the reason payload semantics are UNKNOWN.

4.2 Checksum: none — proof and Python verification

Claim: there is no arithmetic checksum field anywhere in the 1,752-byte record. Three independent proofs:

  1. Code proof (writer): FUN_0800036c performs exactly three payload-affecting stores before flushing — magic constant at 0x00, global u32 at 0x6D0, global byte at (probably) 0x6D4 — and no loop over the struct. A checksum cannot be computed by code that never reads the payload.
  2. Code proof (drivers): FUN_08015174 is a pure copy loop; FUN_08015110/FUN_080151e4 delegate to the unrecovered FUN_0801528c trampoline with only (src, dst, len, stack) arguments and no accumulator visible. The reader's only post-load test is the magic equality at FUN_08000418:56.
  3. Byte proof: in cap-01, every byte after the magic is 0x00. Any stored checksum of that payload would have to sit in a zero byte/word, while the computed candidates below are (mostly) non-zero or would force the field to equal a value it does not hold; and the sole non-zero field (offset 0) is provably the constant magic (§3.3 step 2), not data-derived — on a zeroed payload a data-derived field changing would still have to be produced by a loop that does not exist.

Integrity actually used: magic equality on load + verify-after-write byte comparison on save (FUN_080151e4, result forwarded to the state dispatcher). This detects a blank/corrupt header and a failed SRAM write; it does not detect in-place payload corruption after a successful write. Fuzzing (§6) exploits exactly this.

6. Save Fuzzing & Counterfactual Verification Plan

Prerequisites: use copies of cap-01-future-1.sav; no checksum repair is needed for any target (no checksum exists — §4). There are no paired .ss save states in this packet (states/ is empty), so each test is: patch the .sav, cold-boot the ROM with that SRAM image, and observe (a) whether the magic gate accepts the record, (b) the RAM struct after FUN_08000418 runs, and (c) visible UI/gameplay change. A progressed save (any payload byte non-zero) should be captured first if obtainable, because on the current all-zero payload most payload mutations are only detectable in RAM, not on screen.
