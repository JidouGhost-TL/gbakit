GBA Clean-Room Save Format Report — Bratz (USA) (En,Fr,Es)

Release key: A2RE-r0-fb4811eac43aa876 · ROM SHA-256: fb4811eac43aa8763d7ebae1ef8296bcbc71da9623331990a42c6209d1c7e93f · Game code: A2RE

All findings derive only from this workspace: sav-00-f1402.sav, decompiled.c, save_related_functions.c, callgraph.json, and standard GBA hardware addresses given in the packet. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + bytes agree):

  • The save medium is a 512-byte EEPROM (packet tag EEPROM_V122, file size 512). Only EEPROM read paths exist in the traced corpus.
  • There are 3 save slots of 32 bytes at EEPROM offsets 0x00, 0x20, 0x40, plus one global block of 312 bytes at EEPROM offset 0x60 (block 12). Total addressed space is 408 of 512 bytes.
  • The per-slot integrity algorithm is a seeded byte sum: sum8 over slot bytes 0x00..0x1B, stored as u32_le at slot offset 0x1C. This is proven by the reader code in FUN_08011794. The global block uses the same shape: sum8 over 308 bytes, stored u32_le at file offset 404 (FUN_0800a328).
  • The sample save has exactly one non-blank region: slot 0 (0x00..0x1F). Slots 1–2, the global block, and the tail are all 0xFF.

Not proven / open (stated plainly):

  • The checksum seed constants are unresolved. Readers load the seed from literal-pool words (_DAT_08011b98 for slots, _DAT_0800a730 for global) whose values are not present anywhere in this workspace. With seed = 0, the sample slot 0 does not verify: computed 0x000001FC vs stored 0x00000000. The seed that would make slot 0 verify is 0xFFFFFE04, but deriving a seed from the sample is fitting, not proof. The checksum is therefore CONFIRMED_STATIC for formula/range/storage, not CONFIRMED_VERIFIED.
  • No EEPROM write function exists in the 237 traced functions. There is no write-bitstream builder, no serializer, and no checksum-store anywhere in decompiled.c. The likely writer callees (func_0x0800cdec, func_0x08006d74) are called from the main state machine but were never traced/decompiled. Every writer claim in this report is marked accordingly.
  • No magic signature is checked by any traced code. Byte 0x41 at offset 0 is a masked field byte (& 7 = 1), not a verified magic.
  • Two of the three MMIO seeds in save_related_functions.c (0x080256ee, 0x0802fa44) are false positives: register-block initializers / garbled audio-DMA code with no EEPROM traffic. Only the 0x0802dbb8 / 0x0802dc38 cluster is save I/O.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

callgraph.json contains only FUN_→FUN_ direct edges (237 nodes). The decompiled C also calls the same addresses through Ghidra's unresolved thunk spelling func_0x080XXXXX. I mapped callers by address equality: func_0x0802dc38 at a call site is FUN_0802dc38. This matters because the callgraph lists FUN_0802b9ac callees as only 0x08024938, silently dropping its func_0x0802dc38 and func_0x0802fa44 calls; the C text is authoritative. Conversely, several func_0x… targets (e.g. func_0x0802e5a4, the 9-byte copy) have no FUN_ body in the corpus at all and are treated as untraced.

3.2 Low-level hardware I/O driver

FUN_0802dbb8(src, dst, count) — DMA3 transfer engine (decompiled.c:7927).

*_DAT_0802dc28 = param_1;                       // DMA3 SAD  (inferred 0x040000D4)
*_DAT_0802dc2c = param_2;                       // DMA3 DAD  (inferred 0x040000D8)
*_DAT_0802dc30 = param_3 & 0xffff | 0x80000000; // DMA3 CNT: count + enable bit 31
while ((cnt_high & 0x8000) != 0) { /* poll busy */ }

The three literal-pool pointers are not resolved in the corpus; the SAD/DAD/CNT assignment is inferred from the packet's DMA3 base 0x040000D4 and the canonical register order, and from the save/restore of a control word in *_DAT_0802dc18. Confidence: CONFIRMED_STATIC for "this programs a DMA channel and polls bit 15 of its control high halfword"; the exact 0x040000D4/D8/DC mapping is a hardware-spec inference.

FUN_0802dc38(block, ram_ptr) — EEPROM read one 8-byte block (decompiled.c:7958).

  • Rejects block >= *(u16*)(type_struct + 4) (EEPROM block count).
  • Builds a bitstream on the stack: address bits MSB-first (count from *(byte*)(type_struct + 8)), preceded by two 1 bits (read header), then:
  • FUN_0802dbb8(bitstream, 0x0D000000, addr_bits + 3) — DMA to the EEPROM window.
  • FUN_0802dbb8(0x0D000000, bitstream, 0x44) — DMA from the EEPROM window, 68 halfwords (4 dummy + 64 data bits).
  • Unpacks 64 bits into 4 u16s at ram_ptr + 6, +4, +2, +0 (descending). Returns 0 on success via the (unrecovered) tail jump; the only caller tests != 0 as failure.

FUN_0802b9ac(eeprom_block, ram_ptr, byte_len) — EEPROM bulk read (decompiled.c:7775).

  • Calls func_0x0802da4c(4) first (bus-config helper; with argument 4 it copies one literal-pool word to another — exact register unresolved, treated as EEPROM bus setup, HYPOTHESIS).
  • Loops i while byte_len >> 3 > i: func_0x0802dc38(eeprom_block + i, ram_ptr + i*8). Length is therefore rounded down to whole 8-byte blocks.
  • If a sound-context global (*_DAT_0802ba2c) is active, it wraps the transfer with func_0x0802fa44() / FUN_08024938() (audio quiesce/restore; FUN_08024938 is a display/audio register builder, not save logic).

There is no EEPROM write, erase, or busy-poll-after-write function in the corpus. No function builds a write bitstream (header 10), no function DMAs data to 0x0D000000 except the read-address phase inside FUN_0802dc38, and no Flash 0x5555/0x2AAA or SRAM 0x0E000000 sequence exists anywhere (0 occurrences). The writer side is genuinely missing from the traced set — see §3.5.

3.3 Serialization / deserialization & checksum routines

FUN_08011794(base, slot) — slot load + validate + unpack (decompiled.c:1117). This is the deserializer.

  1. buf = base + 0x44 + slot*0x20; func_0x0802b9ac(slot << 2, buf, 0x20).
  2. sum = _DAT_08011b98; for (i = 0; i < 0x1C; i++) sum += buf[i]; (seed unresolved).
  3. Valid iff *(i32*)(base + 0x60 + slot*0x20) == sum (slot offset 0x1C).
  4. On failure: clear the unpacked RAM fields to defaults (same defaults as FUN_08010226), zero the 9-byte field at base+0x30 and the whole slot buffer (via FUN_0802e10c, a zero-fill), then retry (max 3 reads). Returns 1 = valid, 0 = invalid after retries (return value via unrecovered jumptable; callers ignore it).
  5. On success: unpack buf into the RAM struct (exact bit mapping in §5).

FUN_0800a328(base, unused) — global block load + validate (decompiled.c:595).

  1. buf = base + 0xB0; func_0x0802b9ac(0xC, buf, 0x138).
  2. sum = _DAT_0800a730; for (i = 0; i < 0x134; i++) sum += buf[i]; (seed unresolved).
  3. Valid iff *(i32*)(base + 0x1E4) == sum. On failure zero the 312-byte buffer and retry (3 attempts). No field unpacking happens here — consumers read base + 0xB0 … directly (no such consumer offsets were found in the corpus beyond this reader, so global field semantics are UNKNOWN).

FUN_08010226(base) — RAM defaults / "new game" reset (decompiled.c:635). Zeroes the same fields the slot unpacker writes and sets *(u32*)(base+0xC) fields to constants (+0x40, +0x2E00 after masking, i.e. field values 4 and 0x17=23 in the bits 4–8 and 9–14 lanes). It does not touch EEPROM. Note the sample's bytes 3 (=4) and 2 (=0x17) numerically echo these defaults, but they sit in different lanes than the reader's map (reader takes bits 4–8 from file byte 4, bits 9–14 from file byte 5); I do not claim the sample encodes the defaults.

Zero-fill helpers. FUN_0802e10c(ptr, len) and FUN_0802e0c4(ptr, len) (decompiled.c:8822) write only zero bytes (word-optimized memset-0). func_0x0802e5a4(dst, src, n) is the untraced copy used for the 9-byte field; its (dst, src, 9) shape at decompiled.c:1198 is the only evidence for direction.

3.4 ALL traced callers (complete chains)

Chain A — boot/load (fully traced):

FUN_080145da (root, no callers; auStack_340[824] on stack)
 ├─ FUN_0800019c(auStack)            — struct init; also calls func_0x080256ee (non-save register init)
 └─ FUN_080119d2(auStack)            — main state machine
     ├─ FUN_080119a2(base)           [decompiled.c:1317]
     │    └─ FUN_08011794(base, slot) ×3   — load+validate+unpack each slot
     │         └─ func_0x0802b9ac → FUN_0802dc38 → FUN_0802dbb8 (DMA3/EEPROM)
     │    └─ FUN_08010226(base)      — apply RAM defaults after loading
     └─ FUN_0800a328(base)           [decompiled.c:1318] — load+validate global block
          └─ func_0x0802b9ac(0xC, base+0xB0, 0x138) → same EEPROM chain

How each caller mutates RAM before/after the flush points: FUN_080145da creates the zeroed-ish 824-byte state struct on the stack and passes it down; FUN_080119d2 calls the two loaders before any gameplay handler, so all save-derived fields are populated before the state machine dispatches. FUN_080119a2 additionally zeroes base+0xA4+slot*4 after each slot load. Neither writes EEPROM.

Chain B — gameplay mutation of the save-derived RAM fields (traced handlers, EEPROM flush untraced):

  • FUN_080119d2 itself reads/writes the bitfields at base+8 / base+0xC throughout its switch (e.g. (param_1[2] & 0x1FFFF) >> 0x10 as a mode index), tests slot occupancy via base + slot*0x20 + 0x4B, and in its slot-management branch calls FUN_08010226(base) (reset fields), then the untraced func_0x0800cdec(base, slot) and func_0x08006d74(base, slot) (decompiled.c:2283). These two are the prime writer candidates: right place (slot context), right arguments (struct + slot index), absent bodies. Unproven.
  • func_0x08010770(base) (decompiled.c:2239) runs when at least one slot is occupied; func_0x08010298(base) (decompiled.c:2254) runs in the "no occupied slot" branch. Either could contain the flush; both are untraced.
  • Defined handlers FUN_080112dc, FUN_08006bfe, FUN_08006cd8 receive the same base pointer from FUN_080119d2 (lines 1327–1329) and mutate gameplay fields, but contain no EEPROM, checksum, or slot-buffer (+0x44) references. They are not writers as far as the corpus shows.

Chain C — non-save seed functions (traced and dismissed):

  • FUN_080256ee (decompiled.c:5101): bitfield init of a register struct; called as func_0x080256ee from FUN_0800019c only. No DMA/EEPROM.
  • FUN_0802fa44: decompiler reports "Control flow encountered bad instruction data" and overlapping instructions; its readable fragments touch 0x04000084, 0x04000100, 0x040000C4/D0 (audio/timer/DMA status area) and call FUN_0802c9f4/FUN_0802dbb8 with garbage operands. Treated as an audio-DMA routine corrupted in decompilation — excluded from the save architecture. FUN_0802c9f4 / FUN_0802cae0 (version-string check param_4 != 0x38, vtable alloc) belong to the same audio/library cluster.

3.5 Writer architecture (what can and cannot be said)

The serializer that packs base+8/base+0xC bitfields back into the 32-byte slot image, computes the seeded sum, stores it at +0x1C, and issues EEPROM writes is not in this workspace. Any report claiming a writer address would be inventing it. The falsifiable candidates, by call-site context only, are func_0x0800cdec and func_0x08006d74 (slot-indexed, called immediately after FUN_08010226 in the new-slot flow), with func_0x08010770 / func_0x08010298 as secondary candidates. See §6 for how to prove or kill each candidate with the paired save states.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic signatures

None. No traced function compares any save byte against a constant signature. The slot loader validates only the seeded sum; the global loader likewise. Byte 0 of the sample (0x41, 'A') is consumed as & 7 (= 1) by the unpacker. Listing it as a magic would be a guess, so magic_signatures in save-format.json is empty and the 0x41 observation is recorded as a field value.

Checksum formula (from decompiled C)

Slot checksum — decompiled.c:1145:

iVar4 = _DAT_08011b98;                                  // seed: VALUE NOT IN CORPUS
for (uVar3 = 0; uVar3 < 0x1c; uVar3++)
    iVar4 = (uint)*(byte *)(iVar1 + uVar3) + iVar4;     // sum8, u32 wraparound
bVar5 = *(int *)(slot_base + 0x60) != iVar4;            // stored u32_le at slot+0x1C
  • Algorithm: sum8 with a 32-bit seed, little-endian storage. Covered range: slot bytes 0x00..0x1B (28 bytes). Stored at slot offset 0x1C, size 4.
  • Global checksum — decompiled.c:622: identical shape, seed _DAT_0800a730 (also not in corpus), covered 0x00..0x133 of the global block (308 bytes), stored u32_le at file offset 96 + 308 = 404.

Interpretation, without varnish:

  • With seed 0 the sample slot 0 fails its own reader's check (0x1FC ≠ 0). Three mutually exclusive explanations remain: (a) the true seed is 0xFFFFFE04 — possible but unfalsifiable here and numerically ugly; (b) this snapshot's slot 0 is genuinely invalid and would be zeroed on load (the file was captured at frame 1402, paired with pre/post states at frames 1368/1402, so it may predate the first successful flush); (c) the emulator's .sav byte order within each 8-byte EEPROM block differs from the RAM buffer order the checksum runs over (the reader unpacks u16s in descending order, +6,+4,+2,+0). I tested order permutations (identity, u16-reversed-per-block, byte-swapped, fully reversed): sum8 over the full 28 bytes is permutation-invariant, so no permutation rescues a seed-0 match, and no CRC32/CRC16/XOR variant tested matched the 0x71CD5B07 word at 0x18 either. Explanation (c) therefore cannot fix the checksum, only field offsets.
  • Blank slots 1–2 and the blank global block also fail (computed 0x1BE4 / 0x132CC vs stored 0xFFFFFFFF), which is exactly what erased EEPROM should do: the loaders zero them and move on. This consistency supports the formula while leaving the seed open.
  • Verdict: formula, range, and storage are CONFIRMED_STATIC; on-sample verification is FAILED with the only seed available (0) and INDETERMINATE for the true seed. The required seed 0xFFFFFE04 is reported as a hypothesis to test (§6), never as a finding.

6. Save Fuzzing & Counterfactual Verification Plan

Reload method for every test: write the mutated .sav, cold-boot from the paired states (sav-00-pre.ss frame 1368 → let the game pass the frame-1402 save point → compare against sav-00-post.ss frame 1402 and final.ss frame 1868), and watch (a) whether the slot survives FUN_080119a2 validation, (b) RAM fields at base+0x08, base+0x0C, base+0x28, base+0x2C, base+0x30, (c) title/file-select UI.
