GBA Save Format Report — Charlie and the Chocolate Factory (USA) (En,Fr,Es,Nl) (BCFE-r0-908aa26aa73dfd4e)

Clean-room derivation from saves/*.sav, decompiled.c, save_related_functions.c, and callgraph.json only. No third-party game data was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Verified by both code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM, 512 bytes total, accessed as 64 blocks of 8 bytes through DMA3 to 0x0D000000.
  • One logical save struct of 0x124 (292) bytes sits at EEPROM block 0 / struct offset 0x000.
  • Integrity is a magic word at struct 0x11C plus an 8-bit byte-sum stored at struct 0x120.
  • On saves/sav-01-f1374.sav both checks reproduce exactly: magic constant 0x5A5A5A5A, checksum stored 0x00000479 = computed 0x00000479.
  • The reader is FUN_0803a8b0 at 0x0803a8b0, wrapped by FUN_0803ab28 at 0x0803ab28.

Static-only (CONFIRMED_STATIC):

  • The EEPROM read driver FUN_08045d40 (0x08045d40), DMA3 helper FUN_08045cc0 (0x08045cc0), EEPROM-type select FUN_08045c78 (0x08045c78), and struct-clear FUN_0803abc8 (0x0803abc8) are identified from decompiled code.
  • Their literal pool values (_DAT_0803a93c, _DAT_0803a938, DMA register pointers) are not resolved in the supplied Ghidra text, so exact RAM addresses are not claimed.

Open / not in corpus:

  • No EEPROM write driver and no save-serializing writer function is present in the 102 supplied functions. Only the read path was traced. The writer is inferred by symmetry in §3 and §6, not quoted.
  • No caller of the load wrapper 0x0803ab28 and no caller of the clear routine 0x0803abc8 is present in callgraph.json (both show empty caller lists; every function ends in an unrecovered jumptable tail-call, so upstream edges are missing).
  • Semantics of payload fields at struct 0x08–0x10 are unknown. Both samples are an early/default save and are byte-identical there.
  • saves/sav-00-f1325.sav is a partially written image: payload blocks are present, magic/checksum blocks are still erased 0xFF. It fails validation by design and must not be treated as a valid save.

Byte-order transform (critical): the EEPROM serial read in FUN_08045d40 stores each 8-byte block into RAM in reverse order (it writes u16s from param_2 + 6 downwards, MSB-first). Therefore the in-RAM struct B is obtained from the raw .sav file by reversing every 8-byte block:

B = b''.join(raw[i:i+8][::-1] for i in range(0, 512, 8))

Struct byte at offset o lives at raw file offset (o & ~7) + (7 - (o & 7)). All offsets in §5 are struct offsets unless stated. The byte-sum in §4 is permutation-invariant, but the magic and stored-checksum locations are only correct after this transform — which is itself strong evidence the transform is right.

Selection rule: there is only one candidate copy. On boot/load the game reads all 64 blocks, then accepts the copy only if both integrity checks in §4 pass. If either fails, FUN_0803a8b0 sets the invalid flag (*_DAT_0803a958 = 1), leaves the live RAM struct untouched, and returns the failure value. If both pass, it copies the 292-byte staging buffer over the live RAM struct with FUN_08046028 (memcpy) and sets the valid flag (*_DAT_0803a934 = 1).

Write-completeness evidence: sav-00 (frame 1325) contains payload blocks 0–1 and zero blocks 2–4, with everything from struct 0x28 onward still 0xFF, including the magic/checksum blocks. sav-01 (frame 1374) contains the complete struct through 0x123. So between frames 1325 and 1374 a save flush completed the struct. The flush writes blocks in ascending order (inferred from the partial image), so an interrupted flush leaves a torn, invalid save — consistent with the absence of a backup copy being a real data-loss risk.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O

FUN_08045cc0 at 0x08045cc0 — DMA3 transfer helper (role: read/write primitive).

*_DAT_08045d30 = param_1;                              // DMA3 source (inferred 0x040000D4 SAD)
*_DAT_08045d34 = param_2;                              // DMA3 dest   (inferred 0x040000D8 DAD)
*_DAT_08045d38 = param_3 & 0xffff | 0x80000000;        // DMA3 count + enable (inferred 0x040000DC CNT)
while ((uVar2 & 0x8000) != 0) { uVar2 = *puRam08045d3c; }  // poll DMA busy

It also saves/clears a control register (*_DAT_08045d20) and programs a wait-state value (*_DAT_08045d24, masked with *(ushort *)(*_DAT_08045d2c + 6)). Register addresses are inferred from the standard GBA DMA3 map and the literal 0x0D000000 operand at the call site; the supplied decompilation does not resolve the _DAT_ literal-pool values, so this mapping is CONFIRMED_STATIC for the pattern, not address-verified.

FUN_08045d40 at 0x08045d40 — EEPROM block read (role: read). This is the sole MMIO seed in save_related_functions.c.

  • Rejects addresses >= *(ushort *)(*_DAT_08045d58 + 4) (device block count from the config struct chosen by FUN_08045c78).
  • Builds a serial bitstream on the stack: two 1 start bits, then the block address MSB-first over *(byte *)(*_DAT_08045dec + 8) address bits.
  • FUN_08045cc0(auStack_98, 0xd000000, addr_bits + 3) sends the read command/address to EEPROM at 0x0D000000.
  • FUN_08045cc0(0xd000000, auStack_98, 0x44) clocks back 68 halfword transfers (dummy bit + 64 data bits + slack).
  • Unpacks 64 bits MSB-first into 4 × u16 at param_2 + 6, +4, +2, +0 — hence the per-block byte reversal in §2.
  • Returns 0 on success; on out-of-range address it returns the uninitialized default uRam08045d5c, which the caller treats as failure.

FUN_08045c78 at 0x08045c78 — EEPROM config select (role: serialize support). With argument 4 it installs one config struct (*_DAT_08045c8c = _DAT_08045c90); 0x40 installs another; anything else installs a third and returns 1. FUN_0803a8b0 always calls it with 4, matching a 4-Kbit (512-byte) EEPROM geometry: 64 blocks, 6 address bits. The two other geometries are never selected by the save path in the corpus.

No SRAM byte-copy loop (0x0E000000) and no Flash 0x5555/0x2AAA command sequence exists anywhere in decompiled.c. That negative result rules out SRAM/Flash writers in the traced code and corroborates EEPROM-only media.

3.2 Serialization / deserialization

FUN_0803a8b0 at 0x0803a8b0 — save reader + validator + deserializer (role: deserialize, checksum). Decompiled proof (abridged):

*_DAT_0803a934 = 0;
func_0x08045c78(4);                                   // select 512B EEPROM config
for (uVar5 = 0; uVar5 < 0x40; uVar5++) {              // 64 blocks x 8B = 512B

    if ((uVar2 & 0xffff) != 0) goto LAB_0803a946;     // any block failure -> invalid

FUN_0803ab28 at 0x0803ab28 — load wrapper (role: deserialize). Its entire body is a call to FUN_0803a8b0. callgraph.json confirms the edge 0x0803ab28 -> 0x0803a8b0 and lists no callers for 0x0803ab28.

FUN_0803abc8 at 0x0803abc8 — save-struct clear (role: serialize support). It memsets 0x124 bytes to 0 via FUN_08046110 (memset). Its target pointer (_DAT_0803abdc) is a different literal-pool entry than the reader's staging pointer, so whether it clears the staging buffer, the live RAM struct, or a third copy cannot be proven from the text. Size equality (0x124) makes "same struct family" CONFIRMED_STATIC; identity of the buffer is a hypothesis. callgraph.json lists no callers.

Writer (missing from corpus). No function in decompiled.c calls an EEPROM write primitive, computes the §4 byte sum for storing, or writes struct word 0x47/0x48. The func_0x… external-call census contains exactly one EEPROM data function (0x08045d40) and one config function (0x08045c78). Therefore the serializer/writer — which must exist, because sav-01 gained valid magic+checksum blocks between frames 1325 and 1374 — was not captured in this trace-guided corpus. By symmetry with the reader it must: (1) call FUN_08045c78(4); (2) set struct word 0x47 = word0 ^ 0x5A5A5A5A; (3) zero word 0x48, sum 292 bytes, store the sum at 0x48; (4) bit-bang each 8-byte block to 0x0D000000 with a write command (opcode bits differ from read; not observed). Any more specific writer claim would be fabrication, so none is made.

4. Magic Signatures & Checksum / Integrity Algorithm

There is no ASCII magic string. Integrity uses two u32_le words at the end of the 292-byte struct.

Magic signature (struct offset 0x11C, size 4):

stored_magic = struct_u32_le[0x00] XOR 0x5A5A5A5A

The constant 0x5A5A5A5A is _DAT_0803a93c in FUN_0803a8b0; its value is not printed in the decompilation but is recovered from the .sav bytes below and matches on the valid sample. Struct word 0x00 is therefore a per-save key/seed word: in both samples it is 0xCE40CC1C, giving stored magic 0x941A9646. It is not a counter — it does not change between the partial and completed images of the same save.

Checksum (struct offset 0x120, size 4, stored u32_le; algorithm sum8 zero-extended):

checksum = sum(struct_bytes[0x000 .. 0x123] with bytes[0x120..0x123] treated as 0)   (mod 2^32, byte-wise)
covered range: struct 0x000..0x123 inclusive (292 bytes), including the magic word at 0x11C

Decompiled proof is the loop quoted in §3.2: uVar2 = (byte)*puVar4 + uVar2 over 0x124 iterations after zeroing puVar1[0x48], compared against the saved uVar6 = puVar1[0x48]. No CRC, XOR-fold, complement, or seed is used beyond the zeroed field itself.

Python verification (script run in this workspace as /tmp/verify_bcfe.py; re-runnable):

import struct, hashlib
def rev8(d): return b''.join(d[i:i+8][::-1] for i in range(0, len(d), 8))
for fn in ["saves/sav-00-f1325.sav", "saves/sav-01-f1374.sav"]:
    raw = open(fn, 'rb').read(); B = rev8(raw)
    w0, w47, w48 = (struct.unpack_from('<I', B, o)[0] for o in (0, 0x11c, 0x120))
    buf = bytearray(B[:0x124]); buf[0x120:0x124] = b'\0' * 4
    print(fn, f"w0=0x{w0:08x} magic=0x{w47:08x} w0^magic=0x{w0^w47:08x}",
          f"stored=0x{w48:08x} computed=0x{sum(buf):08x} match={sum(buf)==w48}")

Interpretation: sav-01 is a fully valid save (CONFIRMED_VERIFIED for both algorithms). sav-00 correctly fails both checks because its magic/checksum EEPROM blocks were still erased 0xFF at capture time; its computed sum 0xF9F7 includes those 0xFF bytes and is not a meaningful alternative checksum. This also falsifies raw-order (non-reversed) parsing: without rev8, the stored words at 0x11C/0x120 are 0x00000000/0xFFFFFFFF and nothing matches.

6. Save Fuzzing & Counterfactual Verification Plan

General repair procedure for every mutation below: apply the mutation to the struct image, recompute word 0x11C = word0 ^ 0x5A5A5A5A (only if word 0x00 changed), zero bytes 0x120–0x123, set byte-sum over 0x000–0x123 into 0x120 as u32_le, then map back to a .sav file with the per-8-byte-block reversal (raw[i:i+8] = struct[i:i+8][::-1]). Load with the paired save state (states/sav-01-pre.ss / sav-00-pre.ss identity: frame 1325, d39a989c4c1f00e5) and cold-reload. The packet's probe already confirms saves survive cold reload with a visual delta versus blank boot, so a rejected fuzzed save should visibly fall back to the no-save/default flow, and an accepted one should reach the loaded state.
