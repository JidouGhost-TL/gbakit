1. Executive Summary & Overall Confidence

Overall confidence: LOW.

This clean-room pass had two inputs — a trace-guided Ghidra decompilation of 27 functions (ghidra/decompiled.c) and a single .sav capture (saves/cap-00-future-0.sav) — and neither contains any evidence of save I/O:

  • ghidra/save_related_functions.c reports 0 MMIO seed functions found (no

hits anchored on SRAM/Flash/EEPROM/DMA3 access patterns), and 0 functions after expanding 2-hop callers / 1-hop callees from those seeds. The trace that fed the decompiler simply never touched save hardware.

  • All 27 functions present in ghidra/decompiled.c were individually read and

cross-checked against ghidra/callgraph.json. They decompose into exactly two disjoint clusters with zero cross-cluster call edges and zero edges reaching any address in the GBA save-hardware ranges (0x0E000000 SRAM/Flash, 0x0D000000 EEPROM, 0x040000D4 DMA3, 0x5555/0x2AAA Flash command bytes):

  • An 18-function audio/streaming cluster built around the BIOS

software_interrupt(0xC) call (CpuFastSet), consistent with a sound-buffer mixing/streaming engine operating purely on EWRAM/IWRAM buffers.

  • A 9-function software floating-point library (pack/unpack, add/sub,

multiply, divide, compare, int→float, 64-bit multiply helper) — again, no pointers into cartridge save space.

  • The one .sav sample available, saves/cap-00-future-0.sav (32,768 bytes),

is byte-for-byte 0xFF — confirmed independently in this session with a Python pass (see §4) and consistent with saves/hexdump_and_diffs.txt, which reports 0 active (non-fill) byte ranges. There is no written save data to reverse-engineer structurally; at best this sample proves the blank/erased state of the backing store.

  • states/ is empty — no paired .ss save states exist yet to run dynamic

(RAM-write-triggered) verification.

What is proven: the blank-fill convention (0xFF) and size (32,768 bytes) of the one capture on disk; that the 27 functions reachable from the supplied trace are unrelated to save I/O.

What remains completely open: the actual save media type, slot/redundancy layout, magic bytes, checksum algorithm, and field map. None of these can be derived from the current evidence. This report documents that negative result precisely, rather than fabricating or guessing a field map, per the clean-room rule against unverified claims.

3. Save Writer, Reader & Caller-Chain Architecture

No save-hardware I/O driver, serialization/deserialization routine, or checksum routine was found among the traced functions. This section documents the methodology used to rule each of the 27 functions out, per the packet's requirement to account for every function.

3.1 Method

  1. Searched ghidra/save_related_functions.c — it declares 0 MMIO seeds and 0

total functions (seed functions are anchored on known SRAM/Flash/EEPROM/DMA3 access instruction patterns; none fired on this trace).

  1. Grepped ghidra/decompiled.c case-insensitively for sram, eeprom,

flash, dma, 0x0d000000, 0x0e000000, 0x040000d4, checksum, crc, 0x5555, 0x2aaa — zero matches.

  1. Read all 27 function bodies directly and classified every memory reference

and BIOS call by address range. No reference falls in 0x02xxxxxx (EWRAM)

as a save mirror with a corresponding periodic flush to 0x0Dxxxxxx/0x0Exxxxxx; all 0x02xxxxxx/0x03xxxxxx-style struct accesses seen are local object/channel state for the audio engine (see 3.2), not a save-record staging buffer.

  1. Cross-checked the resulting two clusters against ghidra/callgraph.json:

18 functions have caller/callee edges only to each other (audio cluster), 9 functions have edges only to each other (float-library cluster), and there are 0 edges between the two clusters and 0 unresolved external addresses pointing at save hardware.

3.2 Cluster A — Audio/stream engine (18 functions, not save-related)

FUN_08117fe4 is a thin wrapper around software_interrupt(0xC) — the GBA BIOS CpuFastSet call, a DMA-accelerated fixed-size memory copy/fill used across the GBA SDK ecosystem for bulk EWRAM/IWRAM transfers (generic, publicly documented BIOS behavior, not game-specific). It is called from FUN_0811904c and FUN_081192e8, which in turn are driven by FUN_08118f7c/FUN_08119224 and FUN_08119480, all of which manipulate an in-RAM structure's offsets (param_1 + 0x14/0x1c/0x20/0x24/.../0x8c/0x8d) that look like double-buffer read/write cursors and an end-of-stream flag — i.e. a streaming audio-channel mixer advancing through a sample/sequence buffer each frame. FUN_081185cc/FUN_08118630/FUN_0811950c compute elapsed time/position using FUN_0811e0a8/FUN_0811db9c (see cluster B) to convert tick counts to fixed/float ratios — consistent with tempo or playback-rate math, not save-field math. FUN_0811d348/FUN_0811d408/FUN_0811d550 manage a small ring/queue of per-voice counters. None of this cluster ever constructs or inspects a magic number, a checksum, or an address in 0x0D000000–0x0E00FFFF.

Caller-chain verdict: this cluster is a sound-engine component. It is documented here (not silently dropped) to satisfy the "every function" requirement, but it is explicitly ruled out as a save writer/reader — it never touches cartridge save address space, and nothing it does propagates to the .sav buffer.

3.3 Cluster B — Software floating-point library (9 functions, not save-related)

FUN_0811d944 (unpack an IEEE-754-shaped undefined4 into a {class, sign, exponent, mantissa} record), FUN_0811d88c (pack that record back into a float-shaped undefined4, including rounding and the 0xff NaN/Inf class), FUN_0811d9c0 (add/sub on unpacked operands), FUN_0811db3c (multiply: unpack, multiply, repack), FUN_0811db9c (divide: unpack, 64×64 divide via FUN_0811e1d8, repack), FUN_0811ddec/FUN_0811dfd0 (ordering compare, with -1 sentinel for "incomparable"), FUN_0811e0a8 (signed int → float), and FUN_0811e1d8 (branch-free 32×32→64 unsigned multiply with a linear term, used as the divide's inner primitive). This is a textbook software float library, almost certainly linked in to support non-FPU arithmetic elsewhere in the title (e.g. the audio engine's tick→time conversions in 3.2). It has no concept of a save buffer, a save slot, or a checksum.

Caller-chain verdict: ruled out as save-related for the same reason — no reference to save address space, no magic/checksum construction.

3.4 Conclusion for Section 3

There is currently no identified:

  • low-level hardware I/O driver (SRAM byte-copy / Flash 64K/128K command

sequence / EEPROM DMA3 bitstream),

  • serialization/deserialization routine, or
  • checksum/integrity routine

in the supplied trace. The 0x08xxxxxx function table required by the packet template is therefore empty by evidence, not by omission — see io_driver_functions: [] in save-format.json. The true save-write/read path exists in the ROM (the SRAM_F_V103 SDK tag proves the title links save support) but was not captured by whatever trace seeded this decompilation batch (consistent with the standing guardrail that trace-seeded discovery can miss code paths that were never executed during capture — e.g. the player never saved/loaded during the session that produced this trace).

4. Magic Signatures & Checksum / Integrity Algorithm

None found. No candidate magic bytes or checksum/CRC routine exists in ghidra/decompiled.c (see the grep in §3.1, step 2), and the one .sav sample has no non-fill bytes to search for a magic signature in the first place.

6. Save Fuzzing & Counterfactual Verification Plan

Because no field, magic, or checksum is mapped yet, fuzzing targets cannot be specified at the byte-offset level with any justified prediction. The falsifiable next steps, in order, are:

  1. Produce a non-blank capture. Record a fresh gameplay session that

actually performs an in-game save, with the mandated paired .ss states (sav-00-pre.ss before the save menu commits, sav-00-post.ss immediately after) plus gameplay.ss/final.ss. Compare sav-00-pre.ss RAM against sav-00-post.ss RAM to locate the in-RAM save staging struct by diffing EWRAM/IWRAM, independent of any code trace.

  1. **Re-run trace-guided MMIO-seed extraction against that new session's

execution trace.** The current ghidra/save_related_functions.c found 0 seeds because the captured trace never executed save code; a trace that spans the actual save button press should surface the real SRAM/Flash/EEPROM driver functions and let ghidra/callgraph.json be regenerated with genuine save-caller edges.

  1. **Diff the new non-blank .sav against this session's all-0xFF

baseline** (saves/cap-00-future-0.sav) byte-by-byte to get the first real candidate active byte ranges, magic-byte candidates (fixed values repeated across independent saves), and checksum candidates (bytes whose value tracks a sum/XOR/CRC of neighboring bytes).

  1. Counterfactual once a field is hypothesized: mutate one candidate byte

in a copy of the .sav, reload from the matching pre-save .ss state with the mutated file mounted as battery save, and observe whether the title (a) accepts it silently, (b) visibly reflects the mutated value in-game, or (c) resets/rejects it — the last case is positive evidence of an integrity check whose covered range and algorithm can then be bisected by repeating with single-bit flips at different offsets.

  1. Preserve this all-0xFF capture and this report as the documented

starting point — it is a legitimate negative result (confirms blank/erased state, rules out 27 functions), not a failed run to discard.

No mutation is proposed against the current sample because every byte is identical (0xFF); mutating a blank/fill region produces no falsifiable prediction about real save semantics.
