Save Format Report — Koukou Juken Advance Series Eijukugo Hen - 650 Phrases Shuuroku (Japan) (A53J)

Clean-room derivation from saves/*.sav, ghidra/decompiled.c (58 functions), ghidra/save_related_functions.c, and ghidra/callgraph.json only, plus standard GBA hardware addresses. No third-party game-specific sources were used.

1. Executive Summary & Overall Confidence

Overall confidence: LOW (with HIGH confidence on the narrow physical/media facts below).

Proven by both code and .sav bytes (verified): the game uses 32 KiB SRAM at 0x0E000000; a dedicated writer (0x08000488) flushes a RAM struct to SRAM with a byte-copy driver (0x08016eb4) and a read-back/verify helper, and a reader (0x08000588) loads SRAM into RAM and gates on the first 32-bit word. In the corpus, cap-00-future-0.sav is a fully erased (0xFF) image and cap-01-future-1.sav is a freshly initialised save: one populated span at 0x0000–0x1767 whose only non-zero bytes are the 4-byte header 63 C8 D0 1A (0x1AD0C863 LE), plus an isolated 12 zero bytes at 0x180C–0x1817.

Not proven (open): the exact value of the expected header constant in code, the RAM mirror base address and every literal-pool field offset (all appear as unresolved _DAT_0800xxxx in the trace-guided decompilation), the exact write length(s), any checksum beyond the first-word compare (standard sum/XOR/CRC hypotheses were tested in Python and rejected), the subdivision of the 5,988-byte all-zero payload, slot redundancy, and the callers/triggers of the save functions (the callgraph records no callers for them). Any report claiming phrase-by-phrase fields, a CRC, or dual slots from this corpus would be fabricating: the only populated save contains no progressed game state at all.

The 12-byte span at 0x180C after a 164-byte 0xFF gap must not be called a "backup slot": it is all zero, has no header of its own, and no code constant 0x180C/0x1818 was recovered. It may be a second small struct, sparse tail fields of one struct, or the remainder of a longer flush — all hypotheses.

Geometry arithmetic: main span 0x1768 = 5,992 B = 4 B header + 5,988 B payload. 5,988 does not divide cleanly by 650 phrases (5,988 / 650 ≈ 9.21), so even a per-phrase record size cannot be inferred.

3. Save Writer, Reader & Caller-Chain Architecture

Only 2 of the 58 decompiled functions touch save media; both are the MMIO seeds in ghidra/save_related_functions.c. All other functions operate on VRAM (0x06000000), palette/OAM-style records, audio/division helpers (0x08016ffc is a software divide), or BIOS SWIs (0x08016e20 = SWI 0x0B, 0x08016e24 = SWI 0x05) and are not save code. There is no Flash command sequence (0x5555/0x2AAA unlock, erase/program) and no EEPROM-over-DMA3 (0x040000D4) anywhere in the decompilation — consistent with SRAM media.

Low-level hardware I/O drivers

  • 0x08016eb4 — SRAM write (byte copy). Sets a WAITCNT-style register (*_DAT_08016eec & mask | 3, the standard SRAM wait-state setup) then while (len-- != -1) *dst++ = *src++;. This is the classic Nintendo SRAM byte-wise write (SRAM is 8-bit only, hence no 16/32-bit copies). Role: write. Caller: 0x08000488 only (by call site; the callgraph does not record these helper edges because the helpers are func_-prefixed library stubs).
  • 0x08016e50 — SRAM read wrapper. Builds a stack guard/canary, then calls func_0x08016fcc(SRAM_addr, RAM_addr, len, guard) — the Nintendo-style ReadSram/VerifySram core. Caller: 0x08000588.
  • 0x08016f24 — SRAM verify/read-back wrapper. Identical shape to 0x08016e50; called by the writer immediately after 0x08016eb4, i.e. write-then-verify. Caller: 0x08000488.
  • 0x08016fcc — transfer core (unrecovered). Present only as an UNRECOVERED_JUMPTABLE stub, so its exact copy/compare semantics are CONFIRMED_STATIC for existence and HYPOTHESIS for behaviour. This stub is also the largest single hole in the analysis (it could in principle hide a checksum pass — see Section 4).

Writer: 0x08000488

Sequence: FUN_08016078() (guard/critical-section helper that also appears before the SRAM-timing change in FUN_08015f8c) → a series of stores into the RAM save struct (base _DAT_08000538, a literal-pool pointer whose numeric value is not resolved in this decompilation): fields at +_DAT_0800053c, +_DAT_08000544, repeated 3-word records through a second pointer puVar2, and fields at struct-relative +0x3C and +0x10C → busy-wait on a DMA/status sign bit → func_0x08016eb4(RAM_base, 0x0E000000, _DAT_08000584) (length is again an unresolved literal) → func_0x08016f24(RAM_base, 0x0E000000, len) verify → FUN_080160c4() (restores the 0xB600 timing registers undone by FUN_08016078) → indirect jump-table exit.

How its callers were mapped and how it mutates the struct: it has no callers in ghidra/callgraph.json ("0x08000488": {"callers": [], "callees": []}) and none in the C (it ends in an unrecovered jump table, i.e. it is itself a state-machine fragment reached by indirect dispatch). Therefore no caller chain into gameplay code can be honestly traced from this workspace, and the pre-flush stores above are the only struct mutations attributable to it — with their byte offsets unrecoverable because every offset is a literal-pool _DAT_ value. Naming specific RAM addresses (0x02xxxxxx/0x03xxxxxx) or field offsets would be invention.

Reader / validator: 0x08000588

Sequence: func_0x08016e50(0x0E000000, RAM_base, len) loads SRAM into the same kind of RAM struct → validity gate: if (*RAM_base != _DAT_08000664) the save is treated as invalid and sanitised by OR-ing a mask (_DAT_08000670) over 0x29 halfwords (loop iVar6 = 0x28; do { ... } while (-1 < iVar6), i.e. 41 entries) at two struct offsets (+_DAT_08000674, +_DAT_08000678) → further field restores at +_DAT_08000680 / -4 → jump-table exit.

This first-dword compare is the only integrity/validity check in the entire decompilation. Its expected value is an unresolved literal, so we cannot prove from code alone that the expected value equals the observed 0x1AD0C863 — that equality is a hypothesis (Section 4), albeit the natural one: the word sits at offset 0, is the only non-zero data in a freshly written save, and is exactly what a first-word magic is for.

How callers were mapped (method): (1) took the 2 MMIO seeds from save_related_functions.c; (2) searched all 58 functions in decompiled.c for 0x0E000000, the three helper addresses, and Flash/EEPROM signatures (none); (3) cross-checked every edge in callgraph.json (58 nodes; the save seeds are isolated nodes); (4) accepted only literal call sites in C as edges where the JSON is silent. The negative result (no gameplay callers recoverable) is a property of the trace-guided, jump-table-fragmented decompilation, not evidence that the game never calls these functions.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic candidate: offset 0x0000, 4 bytes 63 C8 D0 1A (0x1AD0C863 little-endian; u16 halves 0xC863, 0x1AD0). Verified in .sav: yes (Python, below). Verified in code: no — FUN_08000588 compares the first word against _DAT_08000664, whose value the decompilation does not resolve. Confidence: HYPOTHESIS. There are no ASCII magic strings (PACKET profile: ascii_magic_strings: [], confirmed by the byte census: the file contains only 0x00, 0xFF, and the 4 header bytes).

Checksum: none found, and the obvious ones are disproven. No sum/XOR/CRC loop exists in the 58 functions. Because the payload after offset 4 is entirely 0x00, any plain sum or XOR over it is 0x00, while CRCs are fixed functions of the zero-run length; none equals the header word or either half:

Conclusion: the stored word does not function as a standard checksum of the observed payload (stored 0x1AD0C863 vs every computed value above: no match, on either sample; cap-00 is blank). It is best explained as a magic/ID word checked by 0x08000588. A custom checksum inside the unrecovered 0x08016fcc stub cannot be excluded — that is an explicit open question, and the fuzzing plan (Section 6) tests it. In save-format.json this is recorded as one checksum entry with algorithm: "unknown", match: false on both samples, confidence UNKNOWN — not dressed up as verified.

Decompiled proof of the only integrity gate (ghidra/decompiled.c, FUN_08000588):

func_0x08016e50(0xe000000, _DAT_0800065c, _DAT_08000660);   // ReadSram -> RAM

  /* sanitise: OR mask over 0x29 halfwords at two struct offsets */

and of the write path (FUN_08000488): func_0x08016eb4(_DAT_08000538, 0xe000000, _DAT_08000584); uVar4 = func_0x08016f24(puVar1, 0xe000000, uVar4); with FUN_08016eb4 being the byte loop while (param_3 = param_3 + -1, param_3 != -1) { *param_2 = *param_1; ... }.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save-states ship in this workspace (states/ is empty), so predictions are stated for reload in an emulator from a modified .sav (cold boot), which is the available equivalent. No checksum repair is required by any step unless a step reveals a hidden checksum — that discovery is itself a target.

  1. Header validity (offset 0x0000, 4 B). Flip 0x63→0x62. Prediction if it is the 0x08000588 magic: save rejected/sanitised (the 41-halfword OR-mask path), game boots as new game and re-writes an initialised save. If the save loads normally, the first-word compare is not the (sole) gate or _DAT_08000664 is not this word.
  2. Payload sweep (offset 0x0004, 1 B at a time across 0x0004–0x1767). Set one byte to 0x01 per boot. No checksum repair (none proven). Prediction: exactly one phrase state / score / setting changes per relevant offset, subdividing the payload; wholesale rejection at some offset reveals a hidden checksum covering it (then re-examine 0x08016fcc).
  3. Mid-payload corruption (offset 0x0800 = 0xFF). Prediction: silent acceptance if integrity is header-only; rejection localises a payload checksum and bounds its covered range by binary search.
  4. Secondary span (0x180C–0x1817, 12 B). (a) Restore to 0xFF; (b) write incrementing pattern 00 01 02 …. Prediction: loss/change of one specific setting or progress element implicates this span as a real struct; no observable change in either direction marks it padding/unused.
  5. Gap fill (0x1768–0x180B, 164 B → 0x00). Prediction: no gameplay change if the reader consumes ≤0x1768 or a sparse struct; any change proves the read length exceeds the normally written span.
  6. Blank-image control (all 0xFF, = cap-00). Prediction: boot treats it as no save (first word 0xFFFFFFFF fails the compare), initialises RAM, and the next flush reproduces the cap-01 pattern — confirming cap-01 is the game's own initialised image rather than player progress.
  7. Progressed-save capture (not a mutation). Play one phrase to completion, dump .sav, diff against cap-01. Prediction: a small, localised non-zero cluster inside 0x0004–0x1767 — the first real field. This single capture would raise the whole report's confidence more than any static re-reading.

Appendix: Method & Limitations

Files inspected in full: PACKET.md, ghidra/save_related_functions.c (2 seeds), ghidra/callgraph.json (58 nodes), ghidra/decompiled.c (58 functions, 1,888 lines), saves/hexdump_and_diffs.txt, and both .sav binaries via Python (hashlib, byte/range census, sum/XOR/CRC16/CRC32/Adler tests quoted in §4). SHA-256: cap-00 2d864c0b789a4321…, cap-01 839139b74049f509… (full values in the analysis transcript; prefixes match hexdump_and_diffs.txt). PACKET metadata mentions 6 corpus files / "total_sav_files: 6", but only 2 .sav files exist on disk; conclusions are drawn from those 2. Dominant limitations: unresolved literal-pool _DAT_ values (RAM base, lengths, expected header, field offsets), the unrecovered 0x08016fcc core and jump-table dispatch (no gameplay callers), and the absence of any progressed save. Confidence would move to MEDIUM/HIGH with: literal-pool resolution or a ROM-side re-dump, one progressed .sav, and the fuzzing results above.
