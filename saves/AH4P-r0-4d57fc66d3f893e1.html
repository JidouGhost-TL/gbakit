Clean-Room Save Format Report — Shrek: Hassle at the Castle (Europe) (AH4P)

Release key: AH4P-r0-4d57fc66d3f893e1 · ROM SHA-256: 4d57fc66d3f893e1ab94ef2f6a302f5843b2bce90051b386793e4f98a1871424

All findings below are derived exclusively from the files in this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and standard public GBA hardware specs (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000, WAITCNT 0x04000204). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_STATIC, cross-checked against .sav bytes where possible):

  • The save medium is EEPROM 4K (512-byte file, 64× 8-byte serial blocks), accessed through a standard 2-/3-bit-opcode EEPROM bitstream driver clocked over DMA3.
  • A complete, address-verified low-level driver chain exists: raw DMA3 transfer → bit-serializer read/write → write-with-read-back-verify (×3 retries) → generic byte-stream EepromWrite/EepromRead wrappers → two small wrapper functions (FUN_08009548 write, FUN_0800959c load) that are the only two callers of the generic wrappers in the decompiled corpus.
  • The in-RAM/in-save struct is exactly 80 bytes (0x50), built field-by-field through ~20 tiny getter/setter accessor functions whose byte offsets are provable by direct pointer arithmetic in ghidra/decompiled.c. This gives us a byte-exact field map for the entire active save region (0x00–0x4F), matching the tool's auto-detected active range exactly.
  • A 12-byte magic/version tag at offset 0x00 and a stored 4-byte field at offset 0x0C that is computed and written immediately before every save by a dedicated summation routine (FUN_08009374) — i.e., a checksum-shaped field, both structurally and behaviorally.

Not proven / open:

  • The exact checksum algorithm's byte interpretation does not reproduce the stored value in the one populated sample we have (cap-01-future-1.sav). Section 4 shows the Python verification: both big-endian and little-endian 32-bit-word interpretations of the summed fields produce 0x000002ea, but the stored field is 0x30313052 / 0x52303130. This is reported as an unresolved discrepancy, not papered over — see open questions.
  • Semantic meaning of the four header fields and the three repeated 16-byte "slot" records (what game concept they track) is unknown — only their byte offsets, accessor functions, and init-time default values are proven from code. We only have one non-blank sample, so distinguishing "always this value" from "mutated during the one captured playthrough" is not possible yet.
  • No RTC, no second save slot/copy, no CRC table was found — absence-based claims are weaker than presence-based ones and should be re-checked if more .sav or .ss samples become available.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K, confirmed by the .sav file size (512 bytes = 64 × 8-byte serial blocks) and by the EEPROM-specific bitstream driver at 0x08032dd4/0x08032e84/0x08032fb8 (see §3), which reads/writes 8-byte (4-halfword) blocks addressed by a small block index, not the byte-addressed SRAM/Flash model.
  • SDK save tag in ROM: none detected (per packet metadata).
  • Active save payload: a single contiguous 0x50 (80-byte) region at EEPROM byte offset 0x00–0x4F (blocks 0–9). This is proven directly: the two high-level wrapper calls (FUN_08009548→func_0x0801fa40, FUN_0800959c→func_0x0801fbb4) both pass the literal size argument 0x50.
  • Remaining 432 bytes (blocks 10–63) are unused by any function reachable from the traced save-writer/reader entry points in this corpus. We found no second copy, no backup/primary mirror pair, and no generation/sequence counter distinguishing multiple save slots. This is a static-only, absence-based finding — it cannot be fully excluded that another untraced code path uses the remaining EEPROM space, since only 170 of the ROM's functions were decompiled.
  • Redundancy / selection rule: none found. There is exactly one slot (offset 0, size 0x50); no primary/backup pair, no slot-selection index.
  • Generation/sequence counter: none identified as such. The repeated 3×16-byte "slot" records (§5) could theoretically serve a rotating-slot purpose, but nothing in the traced code treats them as alternates of the same logical record — all three are unconditionally written with the same literal values at init time (see §5), so they read as three parallel fixed records, not a ring buffer.
  • Cold-reload probe: the packet's own probe (save_preserved_on_load: true, visual_delta_on_load: false, reverted_to_blank_boot: false) is consistent with a single stable slot that survives reload without being reset — i.e., consistent with (but does not by itself prove) the single-slot model derived from code.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses below are from ghidra/decompiled.c / ghidra/save_related_functions.c; call edges are cross-checked in ghidra/callgraph.json.

3.1 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3)

0x08032d54Raw DMA3 transfer primitive. FUN_08032d54(src, dst, count\|0x80000000) programs a DMA3-style transfer (count field OR'd with an enable/start bit) and busy-waits on a status halfword until the transfer completes. Lowest-level MMIO building block; everything else is built on it.CONFIRMED_STATIC2 callers: 0x08032dd4, 0x08032e84.
0x08032c88 / 0x08032d10IRQ-mask / DMA-enable toggle pair. Both manipulate a bitmask via 8 << n (classic GBA interrupt/DMA-enable-bit pattern) around a small FIFO-queue push (0x08032c88, called before a transfer) and pop/clear (0x08032d10, called after).CONFIRMED_STATICOnly called from 0x08032e84, i.e. only on the write path.
0x08032dd4EepromRead(block_num, out_ptr4halfwords). Builds a read-request bitstream (opcode + 6-bit block address), sends it via 0x08032d54 to 0xD000000, then clocks out 68 response bits and reassembles them into 4 halfwords (8 bytes) at out_ptr. Bounds-checks block_num against a config value at (*_DAT_08032dec)+4 (max block count — the driver is parameterized for both 4K/64K EEPROM variants; the address-bit-width field (*_DAT_08032e80)+8 is 6 for this title's 4K config).CONFIRMED_STATIC1 caller: 0x08032f60 (verify). Also called directly from 0x0801fa40/0x0801fbb4 (see §3.2).
0x08032e84EepromWrite(block_num, in_ptr4halfwords). Serializes a write-opcode + block address + the 4 input halfwords (64 data bits) + stop bit into a bitstream via 0x08032c88/0x08032d54, writes it to 0xD000000, then busy-waits on the EEPROM "ready" bit (uRam0d000000 & 1) before calling 0x08032d10 to release.CONFIRMED_STATIC1 caller: 0x08032fb8.
0x08032f60Write-verify. Calls EepromRead on the just-written block and compares all 4 halfwords byte-for-byte against the buffer that was supposed to be written; returns 0x8000 on mismatch.CONFIRMED_STATIC1 caller: 0x08032fb8.
0x08032fb8EepromWriteVerified(block_num, buf) — writes via 0x08032e84, then verifies via 0x08032f60, retrying the whole write+verify up to 3 times before giving up. This is the actual save-commit primitive used by the game.CONFIRMED_STATICNo static callers inside the seed set; its only caller found in the wider corpus is 0801fa40 (§3.2), confirmed by direct text search of ghidra/decompiled.c.

3.2 Generic byte-stream wrappers (block-splitting layer)

AddrRoleConfidence
0x0801fa40WriteSaveBytes(handle, byte_offset, src_ptr, length). Converts a byte offset/length into EEPROM block numbers (byte_offset >> 3), handles unaligned partial blocks by first reading the existing block (0x08032dd4) and merging in the new bytes, then commits each 8-byte block via 0x08032fb8 (write+verify+retry). Both are generic byte-range helpers with no game-specific knowledge; they do not know what the save struct's fields mean, only how many bytes to move.

3.3 Game-side save writer / reader entry points (the only two traced callers)

AddrRoleConfidence
0x08009548 (FUN_08009548)Top-level save writer. FUN_08009548(buf): computes the checksum over buf via FUN_08009374(buf), stores it into buf+0xC via FUN_080094cc, then calls func_0x0801fa40(handle, 0, buf, 0x50) to flush exactly the 80-byte struct to EEPROM offset 0. On success it also fires a sound/UI feedback call (func_0x08033000, generic sound-driver API — unrelated to save logic, see §3.4).CONFIRMED_STATIC
0x0800959c (FUN_0800959c)Top-level save loader. FUN_0800959c(buf): calls func_0x0801fbb4(handle, buf, 0, 0x50) to read the 80-byte struct from EEPROM offset 0 into buf, then validates it via FUN_080094e0(buf) (checks the 12-byte magic AND recomputed-vs-stored checksum, §3.4/§4). If either the EEPROM transfer or the validation fails, it calls FUN_080092ec(buf) to reset the struct to hard-coded defaults (same defaults as described in §5) rather than leave a half-read/corrupt buffer in play.CONFIRMED_STATIC

How callers mutate the in-RAM struct before flushing: the write path (0x08009548) does not itself write any field except the checksum at +0xC — every other field (magic, header A–D, slot records) must already have been populated earlier by gameplay code through the dedicated accessor functions in §5 (e.g. FUN_08009420, FUN_08009438, …), which were only traced as far as FUN_080092ec (the default-initializer) and FUN_08009374 (the checksum reader) in this corpus; no other gameplay call sites into those accessors were found among the 170 decompiled functions. This means: we have proof of the struct layout and of the default-initialization values, but not of which in-game events update the header/slot fields during normal play — that remains an open question (§6/open_questions).

3.4 Non-save-related functions excluded from the chain

func_0x08033000, func_0x08033110, FUN_08033034, FUN_08033110 and friends are a generic sound/dialog-feedback driver (indirect-call-through-function-pointer pattern used for playing jingles/SFX on save success or failure) reused all across the ROM — confirmed by checking that func_0x08033xxx call sites appear throughout unrelated code far outside the save call chain (e.g. lines 1167, 1835, 2008 in decompiled.c, nowhere near any EEPROM/SRAM MMIO access). They are not part of the save-format itself and were deliberately excluded from the field map.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic / version tag

  • Offset: 0x00, size 12 bytes.
  • Mechanism: FUN_080092ec (default-initializer) copies exactly 12 bytes from a ROM constant pointer (_DAT_08009310) into the struct; FUN_080094e0 (validator) copies the same-length ROM string from _DAT_08009518 into a stack buffer and compares the first 12 bytes against the struct's first 12 bytes, treating a mismatch as "save corrupt/absent."
  • Observed in .sav: cap-01-future-1.sav bytes 0x00–0x0B = 45 56 5f 4b 45 52 48 53 00 00 03 65 = ASCII "EV_KERHS" + 00 00 03 65. This matches the packet's auto-detected ascii_magic_strings: ["EV_KERHS", ...] exactly.
  • Confidence: CONFIRMED_STATIC for the copy/compare mechanism and offsets (proven in code); CONFIRMED_VERIFIED that this exact byte string is present in the one non-blank sample. We do not have the ROM itself in this workspace, so we cannot re-derive the source string bytes from ROM data directly — only from the decompiled copy-length (0xD→12 effective) and the .sav observation, which agree.

4.2 Checksum field

  • Offset: 0x0C, size 4 bytes. Writer: FUN_080094cc(buf, value) → *(u32*)(buf+0xC) = value. Reader: inferred (by offset symmetry with the writer, and by the validator's use pattern) to be func_0x080094c8(buf); this reader's body is not present in the 170 decompiled functions in this corpus, so its existence is inferred rather than directly observed — flagged as a gap.
  • Computation: FUN_08009374(buf), called immediately before every write (FUN_08009548) and recomputed on every load for comparison (FUN_080094e0). The decompiled algorithm is a plain running sum (unsigned 32-bit addition, no masking beyond natural overflow):
  1. Sum the 12 raw magic bytes (buf[0..0xB]) as individual unsigned bytes.
  2. Add the four 32-bit header fields at buf+0x10, +0x14, +0x18, +0x1C.
  3. Add all twelve 32-bit fields of the three 16-byte slot records at buf+0x20..+0x4F.
  4. Return the 32-bit sum (checksum field itself, buf+0xC, is correctly excluded from the sum).
  • Covered range: 0x00–0x0B (byte-wise) + 0x10–0x4F (word-wise); excludes 0x0C–0x0F (itself).
  • Confidence of mechanism/location: CONFIRMED_STATIC — the code unambiguously computes and stores a sum-like value into this field on every save, and recomputes/compares it on every load. This is checksum-shaped behavior proven from code.
  • Confidence of exact formula/endianness: UNVERIFIED — does not reproduce the stored value. See the Python verification below.

Python verification (run against the actual .sav files in saves/):

=== saves/cap-00-future-0.sav (size=512) ===
block[0:0x50] all-0xFF (blank slot): True

=== saves/cap-01-future-1.sav (size=512) ===
block[0:0x50] all-0xFF (blank slot): False
magic[0:0xC] = b'EV_KERHS\x00\x00\x03e' hex: 45565f4b4552485300000365
stored checksum field [0xC:0x10] = 30313052  as u32 BE: 0x30313052  as u32 LE: 0x52303130
  decompiled-formula sum8(magic)+sum32(BE header+slots) = 0x2ea  == stored(BE)? False  == stored(LE)? False
  decompiled-formula sum8(magic)+sum32(LE header+slots) = 0xb0002df  == stored(BE)? False  == stored(LE)? False
  alt: plain byte-sum of whole 0x50 block minus checksum field = 0x2ea

Interpretation: regardless of 32-bit word endianness assumption, the literal sum of the fields FUN_08009374 is proven (from code) to add up produces 0x2ea, not the stored 0x30313052/0x52303130. Three honest explanations, none provable from this workspace alone:

  1. cap-01-future-1.sav was captured at a point where the struct was not yet checksummed/flushed consistently (e.g., mid-write or from a different capture mechanism than the traced FUN_08009548 path).
  2. The checksum sum legitimately overflowed/accumulated across more fields or more precision than the four header + twelve slot words traced here (e.g. uninitialized stack bytes beyond buf+0x4F, or a wider accumulator reused across multiple save-struct instances not captured in this corpus).
  3. Offset 0x0C–0x0F is not actually the checksum result for this build/path, despite FUN_080094cc's offset matching — i.e. our accessor-offset mapping for this one field could be wrong despite being internally consistent with every other accessor in the struct.

This is recorded as the single most important open question — do not treat the checksum algorithm as solved; only its shape (sum-based, 4-byte, pre-write, offset 0x0C) is solid.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav (the only populated sample), ideally paired with the mandated pre/post .ss save states for the harness that produced it (none are present in states/ for this legacy cohort — flag this as missing instrumentation for the next capture round).

  1. Magic corruption (offset 0x00, 1 byte flip, e.g. 0x45→0x44). Predicted effect: FUN_080094e0 magic compare fails on next load → FUN_0800959c calls FUN_080092ec, resetting the whole struct to defaults (magic restored to "EV_KERHS\x00\x00\x03\x65", header A–D back to 0,1,0,0, all three slot records back to 0,3,0,0). Observable: next save-write after boot should re-flush these exact default bytes — verifiable by diffing the resulting .sav against the documented defaults. No checksum repair needed to trigger the reset (that's the point of this test — the corrupted-but-unrepaired checksum will also legitimately fail).
  2. Checksum-field-only corruption (offset 0x0C-0x0F, e.g. zero out to 00 00 00 00), magic left intact. Predicted effect: if the true checksum algorithm is sum-based as traced, the recomputed checksum will differ from the (now-wrong) stored value and the load path should behave identically to case 1 (reset to defaults) — this is a direct test of whether FUN_08009374's output is actually consulted on load as we believe, independent of resolving the exact formula.
  3. Checksum repair attempt using the traced formula. Compute sum8(magic) + sum32_LE(header+slots) and sum32_BE(...) variants, write each candidate into 0x0C-0x0F in turn over an otherwise-untouched copy, and observe which one (if either) the game accepts as valid on load without resetting. This directly resolves the open question in §4.2 experimentally rather than by further static analysis.
  4. Header Field A mutation (offset 0x10, flip 00 00 00 01→00 00 00 00), checksum not repaired. Predicted effect: load should reset to defaults (checksum mismatch), unless the real checksum algorithm does not cover this field — if the save instead loads successfully with Field A changed but no reset, that falsifies our "Field A is checksum-covered" claim in §4.2's algorithm and narrows the real formula.
  5. Slot-record field-0 mutation across all three records simultaneously (offsets 0x20, 0x30, 0x40: 00 00 00 03→00 00 00 00), checksum repaired per whichever formula survives test 3. Predicted effect (if accepted): a gameplay-observable change in whatever the three parallel slot records represent — since all three were observed to carry the same value in the one sample, flipping all three together maximizes the chance of a visible, correlated in-game effect (e.g. a HUD counter, unlock state, or per-level flag shared across 3 instances) rather than a silent one.
  6. Fresh-vs-restore matched-duration control. Boot once from a factory-fresh EEPROM (all 0xFF, like cap-00-future-0.sav) and once from a restored cap-01-derived state, run an identical input script for an identical frame count, and diff the resulting .sav bytes. This separates "value changed because of what we did" from "value changes every boot regardless" for every field marked UNKNOWN semantics in §5.
  7. Protocol negative: truncate the save file to 79 bytes (drop last byte of slot 2). Predicted effect: this cannot occur on real EEPROM hardware (fixed 8-byte block granularity) but is useful to test emulator/tooling robustness — not a game-behavior prediction, a tooling-robustness check.

Open Questions

  • Checksum formula does not reproduce the stored value in the only populated sample (§4.2) — needs experimental resolution via fuzzing test 3 above, or a second naturally-occurring populated .sav sample for cross-checking.
  • Semantic meaning of header Fields A–D and the three 16-byte slot records is entirely unknown; we have one data point of "defaults vs. one mutated sample," which is not enough to separate "this field is per-save-session volatile" from "this field is a stable gameplay counter."
  • The checksum reader accessor (func_0x080094c8) is inferred by offset symmetry, not directly observed in the decompiled corpus — its body should be re-decompiled/added to a future save_related_functions.c extraction if possible.
  • No code path writing to EEPROM blocks 10–63 (bytes 0x50-0x1FF) was found, but only 170 functions were decompiled; this is an absence-based claim and could be wrong if the full ROM were analyzed.
  • No RTC-backed fields, multi-slot selection, or backup-copy mechanism were found — consistent with a simple single-slot EEPROM title, but again absence-based.
