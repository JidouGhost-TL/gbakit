1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (header / magic / checksum / geometry / default-name: HIGH; EEPROM flush writer and post-name profile semantics: unresolved).

Proven (code + .sav bytes agree)

  1. Media is EEPROM, 512 bytes total. The ROM carries the SDK tag EEPROM_V124, the only save-bus address literal in the entire decompilation is 0x0D000000 (EEPROM), and the loader FUN_08778000 reads exactly 0x40 (64) blocks of 8 bytes = 512 bytes before validating. Both .sav files are exactly 512 bytes. There is no SRAM window (0x0E000000), no Flash command sequence (0x5555 / 0x2AAA), and no other 0x0D000000 reference in the 85 functions.
  2. Magic driv. In RAM order the first four bytes are 64 72 69 76 = ASCII driv (u32 LE 0x76697264). FUN_08778000 compares *_DAT_087780c0 against the constant iRam087780c4 and writes that same constant back when (re)initialising the struct. In the file the block appears byte-reversed as 76 69 72 64 = vird at file offset 0x04.
  3. Checksum is a plain 8-bit byte sum (sum8) accumulated in a 32-bit integer. FUN_08778000 sums exactly 0x1F8 (504) bytes starting at RAM offset 8 and compares the total with the u32 LE stored at RAM offset 4. Python verification (Section 4.3): on sav-01-f1157.sav stored 0x000002F0 (752) exactly equals the computed sum over the full covered range; on sav-00-f1119.sav it equals the sum over the written prefix and differs over the full range only because the unwritten tail still holds erased 0xFF bytes (Section 4.4).
  4. Default profile name saveA. At RAM offset 0x80 the image holds 73 61 76 65 41 20 20 20 = saveA␣␣␣, followed by bytes 0x20, 0x80 and zeros. The orphan initializer FUN_0800289c writes precisely this pattern — a u32 constant, then 0x41 (A), three 0x20, one more 0x20, then 0x80, then long zero runs — so the u32 constant is save (u32 LE 0x65766173). This is a byte-exact match between code and both .sav files.
  5. Single copy, no redundancy, no generation counter. Both snapshots have byte-identical active bytes (0x00..0x90); the only differences are erased-vs-zero fill in the never-written tail. There is no second slot, backup, sequence counter, or timestamp anywhere in the 512 bytes.

Static-only (code seen, no .sav corroboration possible)

  • The DMA3 primitive FUN_087787c8, the EEPROM block reader FUN_08778848, and the EEPROM configuration helper FUN_08778780 are identified by their MMIO behaviour (Section 3). Their Ghidra _DAT_ register pointers are unresolved symbols, so no absolute DMA/EEPROM register address beyond the literal 0x0D000000 can be quoted.
  • The absolute RAM base of the save struct (_DAT_087780c0) is an unresolved pointer in the decompilation; only struct-relative offsets are known. ram_addr is therefore null in save-format.json.

Unknown / open

  • No EEPROM write (flush) function exists in the corpus. An exhaustive search (Section 3.5) found no EEPROM write-opcode builder, no second 0x0D000000 user, no SRAM/Flash path. The function that persists the RAM struct to EEPROM was either not executed during the traced run or not included in the 85-function decompilation. All "writers" below are therefore RAM-struct writers unless explicitly called an EEPROM writer (none is).
  • The caller of FUN_0800289c was not traced (call graph lists no callers); its destination is mapped to RAM +0x80 by the byte-exact default pattern, not by a traced call.
  • Profile bytes after the name and two flag bytes are all zero in the only sample, so their semantics are unknown.
  • Why sav-00's tail is 0xFF while sav-01's is 0x00 (late flush vs. emulator backing-store behaviour) cannot be decided from the corpus (Section 2.4).

GBA EEPROM addressing note (hardware fact): a 512-byte EEPROM is organised as 64 blocks of 8 bytes with a 6-bit block address; the reader builds the read command as two leading 1 bits plus the address bits (the *puVar5 = 1; puVar5[-1] = 1; in FUN_08778848), DMA-writes addr_bits + 3 bit cells to 0x0D000000, then DMA-reads 0x44 (68) bit cells (dummy + 64 data bits) back and re-packs them into 4 halfwords (8 bytes) per block.

2.2 Slot geometry

There is exactly one 512-byte structure and it occupies the whole EEPROM:

Region (RAM offsets)SizeContent
0x00..0x088 BHeader: magic driv (4 B) + stored checksum u32 LE (4 B)
0x08..0x80120 BCovered by checksum; all zero in both samples (reserved / unused)

File offsets equal RAM offsets at region granularity; only the byte order inside each 8-byte block is reversed (2.3). The active (non-fill) span reported by hexdump_and_diffs.txt is 0x00..0x90 (144 B) for sav-00; for sav-01 the same bytes are the only non-zero content.

2.3 File ↔ RAM transform (8-byte block reversal)

The .sav image is not in RAM byte order. Reversing the byte order inside every 8-byte block converts file → RAM, and this is the only transform that makes the data intelligible:

  • File block 00 00 02 f0 76 69 72 64 → RAM 64 72 69 76 f0 02 00 00 = driv + checksum 0x000002F0 (LE).
  • File block at 0x80: 20 20 20 41 65 76 61 73 → RAM 73 61 76 65 41 20 20 20 = saveA␣␣␣.
  • File block at 0x88: 00 00 00 00 00 00 80 20 → RAM 20 80 00 00 00 00 00 00.

This matches the reader's re-packing logic in FUN_08778848: bits are shifted in MSB-first (uVar4 = uVar4 << 1 | *puVar5 & 1) and the four recovered halfwords are stored to descending addresses (puVar6 = param_2 + 6, decrementing), i.e. the serial bitstream order is the reverse of RAM order at block granularity. Confidence: CONFIRMED_VERIFIED — two independent ASCII strings (driv, saveA) plus the LE checksum all become correct simultaneously, in both files; no other simple transform (byte-swap per halfword, bit reversal, word reversal) achieves this.

All offsets in save-format.json are file offsets; the field evidence states the corresponding RAM offset. To edit a save: reverse each 8-byte block → edit in RAM order → recompute the checksum → re-reverse each block.

2.4 Redundancy, counters, selection rule

  • Copies / slots: one. No duplicate header exists at 0x100 or anywhere else; bytes 0x90..0x200 contain no second driv/save signature in either byte order.
  • Mirroring: none.
  • Generation / sequence counter: none. The active 144 bytes are identical between frame 1119 and frame 1157; nothing increments.
  • Selection rule: not applicable (single copy). Validity selection is: magic must equal the driv constant and the byte sum must match; on failure the loader retries the full read up to 4 times and then reinitialises the RAM struct (Section 3.4). There is no fallback copy to select.
  • Snapshot delta: the only change between the two .sav files is tail fill 0xFF → 0x00 at 0x90..0x200 (368 bytes, per hexdump_and_diffs.txt). Because the checksum stored (752) equals the sum with a zero tail, the RAM image the game checksummed had zeros there. The sav-00 tail therefore represents EEPROM cells that had not yet been flushed (still erased) when the first snapshot was taken, or emulator backing-store fill; the corpus cannot distinguish these. The cold-reload probe in PACKET §1 (save_preserved: true) was presumably run against the later, zero-tail state, which passes validation exactly.

3. Save Writer, Reader & Caller-Chain Architecture

Addressing note: two function clusters exist. The 0x0800xxxx / 0x082xxxxx functions are ARM code in the main binary image; the 0x0877xxxx / 0x087dxxxx / 0x087exxxx functions are a Thumb overlay/cluster. Only the functions below touch the save. Every other function in the 85-function corpus was inspected and excluded (3.6).

3.1 Low-level hardware I/O driver

FUN_087787c8 (0x087787c8) — DMA3 transfer primitive — role: write (bus transfer)

Signature: void FUN_087787c8(undefined4 param_1 /*src*/, undefined4 param_2 /*dst*/, uint param_3 /*count*/).

Decompiled behaviour (identical in save_related_functions.c and decompiled.c):

  1. Saves and clears an interrupt/DMA control global (*_DAT_08778828).
  2. Programs the DMA channel: *_DAT_0877882c = *_DAT_0877882c & (ushort)_DAT_08778830 | *(ushort *)(*_DAT_08778834 + 6);
  3. *_DAT_08778838 = param_1; *_DAT_0877883c = param_2; — source and destination registers (DMA3 SAD/DAD, 0x040000D4 region; exact registers are unresolved _DAT_ symbols).
  4. *_DAT_08778840 = param_3 & 0xFFFF | 0x80000000; — transfer count with bit 31 set = DMA enable (CNT register).
  5. Busy-waits while bit 15 (0x8000) of the control halfword remains set, then restores the saved control value and returns through an unrecovered jumptable (tail-call epilogue).

Callers (call graph): only 0x08778848 (×2 per block read). Callees: none.

FUN_08778780 (0x08778780) — EEPROM/DMA configuration select — role: support

void FUN_08778780(short param_1): branches on the argument — 4 writes one configuration global (*_DAT_08778794 = _DAT_08778798), 0x40 writes another (*puRam087787a8 = uRam087787ac), anything else writes a third and returns 1. This is the SDK EEPROM-library setup that selects the EEPROM size/address-width profile before transfers. Called by FUN_08778000 with argument 4 before every load attempt. Static-only identification; the concrete register values are unresolved symbols.

FUN_08778848 (0x08778848) — EEPROM 8-byte block read — role: read

Signature: void FUN_08778848(uint param_1 /*block address*/, int param_2 /*RAM destination*/). Marked [MMIO-SEED] in save_related_functions.c; it is the only function in the corpus referencing the EEPROM window 0x0D000000.

Behaviour:

  1. param_1 &= 0xFFFF; rejects addresses >= *(ushort *)(*_DAT_08778860 + 4) (the configured block count — 64 for a 512 B EEPROM).
  2. Builds the serial read command in the stack bit-buffer auStack_96[67]: writes the address bits MSB-first below the buffer top (count from *(byte *)(*_DAT_087788f4 + 8) = address-width field), then sets the two leading bits *puVar5 = 1; puVar5[-1] = 1; (EEPROM read opcode).
  3. FUN_087787c8(auStack_98, 0x0D000000, addr_bits + 3) — DMA-writes the command bitstream to the EEPROM serial line.
  4. FUN_087787c8(0x0D000000, auStack_98, 0x44) — DMA-reads 68 bit cells back.
  5. Re-packs: from auStack_96 + 3, four times it shifts 16 bits in MSB-first (uVar4 = uVar4 << 1 | *puVar5 & 1) and stores each halfword to descending addresses starting at param_2 + 6. Result: one 8-byte block in RAM, with the block's bytes in reverse serial order (the origin of the file↔RAM transform in 2.3). Returns 0 on success (via the unrecovered jumptable tail).

Callers: callgraph.json lists none, but ghidra/decompiled.c shows FUN_08778000 calling it (as the unresolved alias func_0x08778848) 64 times in a loop. Mapping method: the decompiler failed to resolve the indirect/aliased call target inside FUN_08778000, so the static graph lost the edge, while the trace-guided decompilation body preserves the call sites. The decompiled body is taken as authoritative for this edge; the graph edge 0x08778848 → 0x087787c8 is present and agrees.

3.2 Serialization / deserialization & checksum

FUN_08778000 (0x08778000) — load, validate, (re)initialise — roles: read + deserialize + checksum

Signature: void FUN_08778000(void). No callers in the corpus (it is an entry point, presumably boot-time). This is the save-system core:

  1. *pbRam087780bc = 0; — zero the retry counter.
  2. Loop (up to 4 attempts):

a. func_0x08778780(4); — configure EEPROM. b. func_0x08778848() × 0x40 (64) — read all 64 blocks (512 B) into the RAM struct at _DAT_087780c0. (Register-passed arguments were lost by the decompiler; the count 0x40 and the geometry are explicit.) c. If *_DAT_087780c0 != iRam087780c4 (magic mismatch), break out to the failure path. d. Sum 0x1F8 (504) bytes from _DAT_087780c0 + 8; if iVar2 == _DAT_087780c0[1] (stored u32 at +4), return — save is valid. e. Increment the retry counter; loop while counter != 4.

  1. Failure path: *_DAT_087780c0 = iRam087780c4; (write the magic) and zero 0x1FC (508) bytes starting at _DAT_087780c0 + 4 — i.e. it fabricates a blank, valid-by-construction struct in RAM (magic + zero checksum field + zero payload, whose byte sum is 0, matching the zeroed stored checksum). It does not itself write EEPROM (no writer exists in the corpus).

The magic constant iRam087780c4 is unresolved in the Ghidra text, but the .sav bytes pin it: RAM-order 64 72 69 76 = driv (u32 LE 0x76697264).

3.3 Caller chains (complete)

Chain A — boot load & validate (the only EEPROM chain): FUN_08778000 → FUN_08778780(4); FUN_08778000 → FUN_08778848 ×64 → FUN_087787c8 ×2 per block (command write to 0x0D000000, then data read). Trigger: game boot / save load. RAM mutation: fills the whole 512 B struct, then either leaves it (valid) or the failure path rewrites the header magic and zeroes +4..+512. Mapping method: decompiled bodies; callgraph.json corroborates 0x08778848 → 0x087787c8 and the absence of any other EEPROM edge. (FUN_08778000 itself is absent from callgraph.json's keys — a graph-coverage gap, noted for honesty.)

Chain B — blank-save fabrication: FUN_08778000 (failure path, after 4 failed attempts or magic mismatch) → writes magic constant at +0, zeroes 508 bytes at +4. Trigger: blank/corrupt EEPROM. RAM mutation: produces the zeroed default struct whose stored checksum (0) matches its zero payload sum.

Chain C — default profile creation: (untraced caller) → FUN_0800289c(save_struct + 0x80) → writes saveA␣␣␣, flags 0x20, 0x80, zeroes the remainder of the record. Trigger: presumably new-profile/default creation; not observed in the trace. RAM mutation: exactly the bytes seen at RAM 0x80..0x90 in both saves. Mapping method: byte-pattern identity (3.2), since the call edge is missing.

Writer chain — missing: see 3.5. No chain from any game-logic function to an EEPROM write exists in the corpus. Consequently, no function can be honestly named as the one that mutates gameplay fields and flushes them; the RAM-side mutator for Chain C is FUN_0800289c, and the flush step is an open question.

3.5 Exhaustive writer search (negative result)

Searches run over ghidra/decompiled.c (all 85 functions) and ghidra/save_related_functions.c:

  • 0x0D000000: only the two DMA calls inside FUN_08778848 (a read: command bits 1,1 + address, then a read-back). No write-opcode (0,1 / write-enable) bit pattern is built anywhere.
  • 0x0E000000 (SRAM/Flash window), 0x5555, 0x2AAA (Flash commands): zero hits.
  • Byte-sum loops (iVar += (uint)*ptr form): only FUN_08778000. No second checksum, CRC, XOR, or complement routine exists in the corpus.
  • All remaining 0x087dxxxx/0x0877xxxx functions were read; they are audio/JPEG/graphics code (3.6), none references the save struct base or the EEPROM window.

Conclusion: the EEPROM flush writer is not in the workspace corpus. Any report claiming a writer address would be fabricating it. This caps overall confidence at MEDIUM.

4.2 Checksum algorithm (exact)

  • Algorithm: sum8 — plain unsigned byte sum, accumulated in a 32-bit integer (no masking per step, no complement, no seed, no XOR). Stored as u32 little-endian.
  • Formula: stored = Σ byte[i] for i in [8, 512) over the RAM-order image (equivalently over file bytes [8,512), since the block reversal is a permutation and the sum is permutation-invariant — but the stored field itself must be read in RAM order).
  • Covered range: RAM +0x08 .. +0x200 (504 bytes, 0x1F8), i.e. everything except the 8-byte header.
  • Stored at: RAM +0x04, size 4 bytes (u32 LE). In the file this appears block-reversed at file offset 0x00 as bytes 00 00 02 F0.
  • Decompiled proof (FUN_08778000, ghidra/decompiled.c):
pbVar3 = (byte *)(_DAT_087780c0 + 2);        /* RAM +8 */
iVar2 = 0; iVar5 = 0x1f8;                    /* 504 bytes */
do { iVar2 = iVar2 + (uint)*pbVar3; iVar5 = iVar5 + -1; pbVar3 = pbVar3 + 1; } while (iVar5 != 0);
if (iVar2 == _DAT_087780c0[1]) { return; }    /* stored u32 at RAM +4 */

preceded by the magic gate if (*_DAT_087780c0 != iRam087780c4) break;.

4.4 Interpretation of the sav-00 full-range mismatch

Both files store 752. That value equals the byte sum of the written prefix [8, 0x90) in both files, and the full-range sum [8, 512) in sav-01 (zero tail contributes nothing). In sav-00 the full-range sum is 94592 (0x17180) because the 368 never-written tail bytes are still erased 0xFF. The game computed 752, so the RAM image it summed had zeros in the tail — consistent with a freshly zeroed RAM struct (Chain B) whose tail blocks had not yet been flushed to EEPROM when sav-00 was snapshotted 38 frames earlier, and had been by sav-01 (or with emulator fill behaviour). The algorithm itself is CONFIRMED_VERIFIED (decompiled formula + exact match on sav-01 + prefix match on both); the sav-00 tail state is flagged as an open question rather than silently forced to fit.

6. Save Fuzzing & Counterfactual Verification Plan

General repair procedure for every mutation below (unless stated otherwise): decode the .sav by reversing each 8-byte block, apply the edit in RAM order, recompute sum8 over RAM [8, 512) and store it as u32 LE at RAM +4, re-encode by reversing each 8-byte block again, then cold-boot from the paired states (states/sav-00-pre.ss frame 1055 / sav-01-pre.ss frame 1119) with the mutated EEPROM and observe. A mutation is only attributable to the edited field if the repaired save is accepted (no reinitialisation) while the unrepaired twin is rejected.
