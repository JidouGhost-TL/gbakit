1. Executive Summary & Overall Confidence

Overall confidence: HIGH for the physical format, EEPROM transport, block-reversal mapping, both magics, and both integrity checksums; LOW for the gameplay semantics of the sparse payload fields.

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  1. The save is a single 512-byte EEPROM image made of 64 blocks of 8 bytes, transferred one block at a time through DMA3 to/from the EEPROM bus at 0x0D000000.
  2. Each 8-byte block appears byte-reversed in the .sav file relative to the RAM image (see §4). This is not a conjecture: applying the reversal makes the ASCII magics readable (mobile21, 0.05) and makes both independent checksums match exactly on cap-01, a double coincidence that is not credibly accidental.
  3. Magic 1 is the 8 ASCII bytes mobile21 at RAM 0x00–0x07, checked by FUN_08007268 via FUN_080072a4.
  4. Magic 2 / format version is the 4 ASCII bytes 0.05 at RAM 0x08–0x0B, checked by FUN_080072a4.
  5. Checksum 1 at RAM 0x1F8 is a plain modulo-2^32 sum of the 126 little-endian u32 words covering RAM 0x000–0x1F7 (FUN_08007320). On cap-01 (RAM-decoded): computed 0x1bb6dfd0 = stored 0x1bb6dfd0.
  6. Checksum 2 at RAM 0x1FC is the conditional-negation sum of the same 126 words (FUN_08007358). On cap-01 (RAM-decoded): computed 0x762fd3c6 = stored 0x762fd3c6.
  7. Save path recomputes both checksums into RAM +0x1F8/+0x1FC, writes all blocks, then read-back-verifies every block; load path reads all blocks and validates magic 1, magic 2, checksum 1, checksum 2 in that order, with retry-up-to-3 wrappers on both save and load.

Static-only (CONFIRMED_STATIC): the DMA3 register programming, EEPROM serial framing, write-enable/teardown helpers, error-code values, and retry counts are read directly from the decompilation but cannot be re-executed from the corpus alone.

Unknowns / hypotheses (HYPOTHESIS / UNKNOWN): the gameplay meaning of the payload at RAM 0x40–0x57, 0x80–0x9F, and the large zero regions; every direct gameplay writer that mutates payload fields in RAM before a save (no such writer is identifiable in the corpus — see §3.4); the literal RAM base address of the save struct (Ghidra _DAT_* literal-pool values were not exported, so the absolute 0x02xxxxxx/0x03xxxxxx address is unrecoverable from these files); and the EEPROM descriptor values (address-bit width and block count) behind the type-3 descriptor, although 64 blocks × 8 B is independently proved by the 512-byte file and the read/write loops.

The blank snapshot cap-00 (all 0xFF) is the erased/invalid state: both magics and both checksums fail on it, exactly as the validator would require before rejecting it.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

All EEPROM traffic goes through three functions in the 0x08059f54–0x0805a2xx cluster. These are classic Nintendo-style EEPROM access routines: EEPROM is not memory-mapped for data; address and data are clocked serially through the single data line at 0x0D000000, and DMA3 is used to move the pre-built bit-frame between a stack buffer and that address.

FunctionRoleKey behaviour (decompiled proof)
FUN_0805a020(src, dst, count)DMA3 transfer primitiveSaves and clears an interrupt-enable register, programs DMA3 source (*_DAT_0805a090 = param_1), destination (*_DAT_0805a094 = param_2), and control/count (*_DAT_0805a098 = (count & 0xFFFF) \| 0x80000000, i.e. DMA enable bit 31), then busy-waits on bit 0x8000 of the DMA control high halfword until the transfer completes, and restores the saved register. The register block reached through the _DAT_0805a08x pointers is the DMA3 register group at 0x040000D4 (SAD/DAD/CNT), per standard GBA hardware mapping. Callers: FUN_0805a0a0, FUN_0805a158 only.
FUN_0805a0a0(addr, dst_ram)EEPROM read of one 8-byte blockBounds-checks addr < *(u16*)(descriptor + 4). Builds a read frame on the stack: the address bits (MSB-first, count = descriptor byte at +8), preceded by start/read bits (*puVar5 = 1; puVar5[-1] = 1). DMAs the frame to 0x0D000000 with count addr_bits + 3, then DMAs 0x44 (68) halfword samples back from 0x0D000000 into a 67-u16 stack buffer. Reassembles 4 u16 values (16 low-bit samples each, uVar4 = (uVar4 << 1) \| (*puVar5 & 1)) and stores them to dst_ram + 6, +4, +2, +0 in that descending order — the origin of the u16-order component of the block reversal in §4. There is no SRAM byte-copy driver and no Flash 0x5555/0x2AAA command sequence anywhere in the corpus: no function references 0x0E000000, 0x5555, or 0x2AAA save-bus patterns. The only save-bus address in the decompilation is 0x0D000000 (EEPROM), consistent with the EEPROM 4K media line.

3.2 Serialization / deserialization & checksum routines

There is no separate serialization layer: the RAM save struct is the EEPROM image, copied block-by-block with no packing, compression, or byte-order conversion other than the serial framing inside the drivers (whose net file-level effect is the §4 block reversal).

Functions in this codebase return through unrecovered jumptables (UNRECOVERED_JUMPTABLE tail calls), which is why the top-level wrappers show no callers in the JSON: their callers are game-state dispatch code whose edges Ghidra did not recover. That gap is stated, not papered over — no caller above FUN_080071d4 / FUN_08007244 is claimed anywhere in this report.

Save chain — FUN_080071d4 → FUN_0800712c (write-all + verify):

  1. FUN_080071d4 (retry wrapper): calls FUN_0800712c and retries while it returns non-zero, up to 3 attempts (while (iVar2 < 3 && (iVar1 = FUN_0800712c(...), iVar1 != 0))).
  2. FUN_0800712c (save-all):

  • FUN_08059f1c(3, &local) selects the EEPROM descriptor; on failure the function reports error 5 and writes nothing.
  • Write loop: for block = 0 .. count-1, FUN_0805a158(block, base + block*8) — the whole 512 B struct goes to EEPROM blocks 0–63 in order.
  • Verify loop (only if every write succeeded): for block = 0 .. count-1, FUN_0805a23c(block, base + block*8) re-reads and compares; the first mismatch aborts with a non-zero result, which the wrapper retries.
  1. Per block, FUN_0805a158 → FUN_0805a020 (DMA3 frame out) → FUN_08059f54 (write-enable) → ready-poll on 0x0D000000 bit 0 → FUN_08059fdc (teardown).

Trigger context: not recoverable from the corpus (no caller above the retry wrapper). By position and behaviour it is the game's explicit save operation; when in gameplay it fires is UNKNOWN.

Load chain — FUN_08007244 → FUN_080071f0 + FUN_080072a4 (read-all + validate):

  1. FUN_08007244 (retry wrapper): up to 3 attempts of { FUN_080071f0 (read-all); if that succeeds, FUN_080072a4 (validate) }; stops at the first fully successful attempt.
  2. FUN_080071f0 (read-all): FUN_08059f1c(3, &local) (failure → error 5), then for block = 0 .. count-1, FUN_0805a0a0(block, base + block*8) fills the entire RAM struct from EEPROM. It performs no field-level parsing — deserialization is this verbatim block copy, and all interpretation happens in the validator and in later (untraced) gameplay readers.
  3. FUN_080072a4 (validator), in strict order:
  • FUN_08007268() compares RAM 0x00–0x07 against the ROM magic → mismatch returns 1.
  • Compares RAM 0x08–0x0B against a 4-byte ROM string (proved to be 0.05) → mismatch returns 2.
  • FUN_08007320() recomputed vs *(u32*)(base + 0x1F8) → mismatch returns 3.
  • FUN_08007358() recomputed vs *(u32*)(base + 0x1FC) → mismatch returns 4.
  • All pass → returns 0 (valid save).
  1. FUN_080070b4 / FUN_08059eb4(4) sit near this cluster at boot but have no traced edge into the load chain; no claim is made about them beyond §3.1.

Cold-boot context from the packet probe: the emulator probe (save_preserved_on_load: true, reverted_to_blank_boot: false) is consistent with cap-01 passing FUN_080072a4 and with cap-00 (blank) being the no-save state the game would reject and treat as empty.

3.4 How each caller mutates the in-RAM save struct before flushing

  • FUN_0800712c mutates exactly two fields: RAM 0x1F8 (checksum 1) and RAM 0x1FC (checksum 2), recomputed fresh on every save. Nothing else in any traced save/load function writes the struct except FUN_080071f0/FUN_0805a0a0, which overwrite the entire struct with EEPROM contents on load.
  • The magics at RAM 0x00–0x0B are not written by any traced function. Their initialisation (presumably when a new game is created, by code that copies a ROM default image or stamps the strings directly) is outside the recovered corpus: UNKNOWN, and deliberately not guessed.
  • Likewise, no gameplay writer of any payload field (RAM 0x10–0x1F7) was found. The corpus's callgraph is truncated above the two retry wrappers (§3.3), and because the Ghidra export omits _DAT_* literal values, the struct's absolute RAM address cannot be cross-referenced against other functions' pointer constants. Every payload-field “Writers” entry in §5 is therefore honestly UNKNOWN (with the load path as the only proven writer of the RAM copy). Any report claiming specific gameplay writers from this corpus would be fabricating them.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 The 8-byte block reversal (read this first — everything else depends on it)

The raw .sav bytes do not directly resemble the code's view of the save. At file offset 0x00 the raw bytes are 31 32 65 6c 69 62 6f 6d (12elibom) and at 0x0C they are 35 30 2e 30 (50.0) — both are reversals of plausible strings within their 8-byte blocks. The decompiled reader explains the mechanism: FUN_0805a0a0 stores its 4 reassembled u16s to dst+6, +4, +2, +0 (descending), and FUN_0805a158 builds its serial frame in descending stack order; the emulator's EEPROM byte packing preserves that serial order, so each 8-byte block lands in the file reversed relative to RAM.

Empirical rule (verified, §4.3): RAM image = .sav with every consecutive 8-byte block reversed. Equivalently RAM[i] = sav[(i & ~7) | (7 - (i & 7))]. Under this transform cap-01 begins mobile21 + 0.05, and both checksums verify. Without it, neither magic is readable and neither checksum matches under any tested interpretation (identity, 16/32-bit byte swaps, bit reversal, XOR-0xFF, block-order reversal — all tested and rejected before the block reversal matched both checksums simultaneously).

4.3 Checksums — exact algorithms and Python verification

Both checksums cover the 126 u32 little-endian words at RAM 0x000–0x1F7 (504 bytes; word indices 0–125). The stored fields at RAM 0x1F8/0x1FC are exactly one word past the covered range, so there is no self-reference. All arithmetic is modulo 2^32.

Checksum 1 — plain sum (FUN_08007320), stored at RAM 0x1F8 (u32_le):

int acc = 0;
for (int *p = base; p < base + 0x7E; p++) acc += *p;   // signedness irrelevant mod 2^32

Checksum 2 — conditional-negation sum (FUN_08007358), stored at RAM 0x1FC (u32_le):

uint acc = 0;
for (uint *p = base; p < base + 0x7E; p++) {
    uint x = *p;
    if (x <= acc) x = -x;   // unsigned compare; negation mod 2^32
    acc += x;
}

This second algorithm is order-dependent, not commutative: it penalises non-increasing word sequences by negating the word before adding. It is a genuinely different function of the data from checksum 1 (it is not a checksum of checksum 1), so the pair detects some edits a single sum would miss — although, as §6 notes, both are still trivially repairable by anyone who knows the formulas, which is every reader of this report.

Decompiled-C proof anchors: FUN_08007320 loops piStack_c < _DAT + 0x7E accumulating iStack_4 + *piStack_c; FUN_08007358 has the identical 0x7E bound with the if (uVar1 <= uStack_8) uVar1 = -uVar1; step. FUN_0800712c stores their results to base + 0x1F8 / base + 0x1FC before writing; FUN_080072a4 recomputes and compares against those exact offsets (errors 3 and 4).

Verification script (exactly the script run against the corpus; save it as /tmp/verify.py and run python3 /tmp/verify.py from the workspace root to reproduce):

import struct, hashlib
def ram_image(raw): return b''.join(raw[i:i+8][::-1] for i in range(0, len(raw), 8))
def cksum2(words):
    acc = 0
    for x in words:
        u = x
        if u <= acc: u = (-u) & 0xffffffff
        acc = (acc + u) & 0xffffffff
    return acc
for fn in ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]:
    raw = open(fn, 'rb').read(); ram = ram_image(raw)
    w = struct.unpack('<126I', ram[:504])
    s = sum(w) & 0xffffffff; c = cksum2(w); st = struct.unpack('<2I', ram[504:512])
    print(f"{fn}: sha256={hashlib.sha256(raw).hexdigest()}")
    print(f"  RAM[0:8]={ram[0:8]!r} RAM[8:12]={ram[8:12]!r} RAM[12:16]={ram[12:16].hex()}")
    print(f"  checksum_sum32_le[0:504] computed=0x{s:08x} stored@RAM0x1F8=0x{st[0]:08x} match={s==st[0]}")
    print(f"  checksum_condneg[0:504]  computed=0x{c:08x} stored@RAM0x1FC=0x{st[1]:08x} match={c==st[1]}")

Checksum repair procedure for editors/fuzzers: decode the file with the block reversal, edit RAM-image bytes, recompute both checksums over RAM 0x000–0x1F7, store them little-endian at RAM 0x1F8/0x1FC, then re-apply the block reversal to produce the .sav file. In raw-file terms the two stored u32s occupy the final block reversed: file bytes 0x1F8–0x1FF are 76 2f d3 c6 1b b6 df d0 in cap-01, i.e. checksum 2's bytes in reverse followed by checksum 1's bytes in reverse — never patch those file offsets as if they were plain little-endian fields.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test: (a) work on a copy of cap-01; (b) decode the 8-byte block reversal, mutate RAM-image offsets, repair both checksums (§4.3), re-encode — except in the tests whose point is to omit a step; (c) no .ss save states exist in this cohort, so “reload prediction” means cold-booting the emulator with the mutated .sav (the packet probe's protocol: 600 frames, check save_preserved_on_load / blank-boot behaviour and screenshot delta), or, if states become available, loading a state saved at a title/continue screen and then triggering the game's load path. Expected validator outcomes reference FUN_080072a4 error codes (§3.3): a rejected load is retried 3× by FUN_08007244 and then treated as no-valid-save.
