1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is 32 KiB SRAM (SRAM 256K), image length 0x3420 bytes, fill 0xFF.
  • A 16-byte ASCII magic KING OF SWING EU sits at file offset 0x3400 and is compared as 4× u32 words on load.
  • Integrity is a 32-bit byte-sum (sum8 accumulated in a 32-bit int) over [0x0000, 0x341C), stored little-endian at 0x341C. It matches both samples exactly (Section 4).
  • The image contains 4 byte-identical copies of a 0xD00-byte block plus a 32-byte global trailer. There is no per-copy checksum and no generation/sequence counter.
  • On validation failure the loader restores a default buffer via DMA3 and rewrites a blank/default save — exactly matching the PACKET cold-reload probe (mutation at 0x341B → reverted to blank, save rewritten).

Static-only (CONFIRMED_STATIC): the loader FUN_086d26f4 / writer FUN_086d5bf8 structure, the SRAM read/write thunks FUN_089feaa8 / FUN_089feab4, and the DMA restore path.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN): the gameplay semantics of every payload field (no function in the 76-function corpus reads or writes individual payload fields), the RAM mirror address of the save buffer (held in unrecovered literal-pool pointers), the copy-selection rule among the 4 replicas, and all gameplay-triggered save callers (absent from callgraph.json; entry is via unrecovered jumptables).

Geometry, verified in Python on both samples: the four blocks at 0x0000, 0x0D00, 0x1A00, 0x2700 (each 0xD00 bytes) are byte-identical (SHA-256 prefix 2240efd0e33a for every block in both files; pairwise diff = 0 bytes). The only bytes that differ between cap-00-future-0.sav and cap-01-future-1.sav are 0x341B (payload) and 0x341C..0x341D (the resulting checksum) — so the replicas do not diverge even across captures.

Redundancy model: replication without per-copy integrity. Because the single global checksum covers all four copies together, corrupting any one copy invalidates the whole image; the redundancy therefore protects only against a hypothetical per-copy reader that this corpus does not contain, or is an artefact of serialising a RAM region that already holds 4 copies. Which copy (if any single one) is authoritative on load cannot be determined from code or samples — the loader validates the image as one blob. This is an open question (Section 6 tests it).

3. Save Writer, Reader & Caller-Chain Architecture

Only two functions in the 76-function decompilation touch save media. Two other DMA3 "seed" functions were examined and ruled out.

3.1 Low-level hardware I/O

  • FUN_089feaa8 — SRAM read thunk. Body is an unrecovered jumptable ((*pcRam089feab0)()), but its sole call site passes (0x0E000000, ram_buffer, length), i.e. source = SRAM base 0x0E000000. (CONFIRMED_STATIC from call-site argument order.)
  • FUN_089feab4 — SRAM write thunk, same pattern; sole call site passes (ram_buffer, 0x0E000000, total_length, end_pointer) and its return value is checked for error by the writer.
  • No Flash 0x5555/0x2AAA command sequence and no EEPROM DMA3 serial bitstream exists anywhere in the corpus (grep over decompiled.c for 0x0E000000, 0x040000D4/DC/DE hits only the functions listed here plus the ruled-out graphics DMA below). The media is plain byte-wide SRAM; no WAITCNT (0x04000204) manipulation is present in the save path.

Ruled out (MMIO seeds in ghidra/save_related_functions.c that are not save I/O):

  • FUN_0841c8b0 — DMA3 streamer writing to VRAM 0x0600E000 with stride 0x800; graphics tile upload.
  • FUN_086ead58 — DMA3 chunk copy (0x20-byte units, uRam040000dc = 8) into IWRAM 0x03000A00; palette/work-RAM copy.
  • FUN_0841c710, FUN_0841cb58/cbc8, FUN_0841cc40/ccb8 — display/window helpers using the same DMA registers.

3.2 Loader / validator — FUN_086d26f4 (0x086d26f4)

Decompiled proof (ghidra/decompiled.c:1868-1927):

  1. Clears uRam030002b3 = 0 (busy/error flag) and state uRam03000002 = 0.
  2. func_0x089feaa8(0x0E000000, pbRam086d27bc, uRam086d27c0) — reads the image from SRAM into the RAM buffer. (Buffer pointer and lengths are literal-pool values at 0x086D27BC..0x086D27CC, unrecovered by Ghidra; their values are inferred from .sav geometry in Section 4.)
  3. Compares 4 × int32 (piRam086d27c4 vs piRam086d27c8, loop at lines 1887–1895) — a 16-byte header compare, matching the 16-byte magic at 0x3400. On any mismatch it jumps to the failure label.
  4. Sums uRam086d27cc bytes from the buffer (iVar6 += *pbVar4, lines 1896–1906) and compares against *(int *)(pbVar4 + 1) — the int32 immediately after the summed range (lines 1907). This is the checksum verify.
  5. Success: if the two bytes at pcRam086d27d0 are equal, copies that byte to cRam030004bb and dispatches through an unrecovered jumptable with argument pbVar4 + 5 (one past the stored checksum — i.e. the end-of-image pointer). The byte copied to 0x030004BB is plausibly a validated mode/slot byte; its exact source offset is unrecovered.
  6. Failure (LAB_086d2784): programs DMA3 (0x040000D4 = default-data source uRam086d27d4, 0x040000D8 = buffer, 0x040000DC = length>>2, 0x040000DE = 0x8400 enable), calls the writer FUN_086d5bf8 to persist the restored default image, sets game state uRam03000002 = 0x1C, and dispatches onward.

3.3 Writer / serialiser — FUN_086d5bf8 (0x086d5bf8)

Decompiled proof (ghidra/decompiled.c:1932-1967):

  1. iVar4 = iRam086d5c44 (total image length), pbVar2 = pbRam086d5c40 (buffer).
  2. Sums the first total - 4 bytes into iVar5 (lines 1949–1957).
  3. Stores it with *(int *)(pbVar6 + 1) = iVar5 — i.e. at buffer + total - 4, the last 4 bytes of the image (line 1958).
  4. func_0x089feab4(buffer, 0x0E000000, total, pbVar6 + 5) writes the whole image to SRAM; a non-zero return sets the error flag uRam030002b3 = 0xFF (lines 1959–1962).
  5. Returns via unrecovered jumptable.

There is no separate serialiser: the RAM buffer is the on-media image (byte-for-byte copy both ways). Consequently every payload field's file offset equals its offset inside the RAM buffer; only the buffer's base address is unknown.

3.4 Caller chains (how each caller was mapped)

ghidra/callgraph.json (76 nodes) lists no callers for FUN_086d26f4, FUN_086d5bf8, FUN_089feaa8, or FUN_089feab4, and the decompiled bodies end in unrecovered jumptables. Mapping therefore rests on direct call sites inside the decompiled C, cross-checked against the callgraph:

How each caller mutates the in-RAM save struct before flushing: no caller that mutates individual payload fields exists in this corpus. The only RAM mutations by traced code are: the loader clearing 0x030002B3/0x03000002, copying one validated byte to 0x030004BB, the DMA default-restore overwriting the whole buffer, and the writer recomputing the checksum at buffer+0x341C. Gameplay code that updates the records/flags arrays and invokes FUN_086d5bf8 was not captured by the trace-guided decompilation — every statement about which gameplay event updates which field would be invention, so field writers/readers in Section 5 are listed as the loader/writer pair only. The unrelated traced chains that do exist in the callgraph (e.g. 0x085C4F70 → 0x0800058C → 0x08000508, 0x086BF5B0 → 0x086B969C, the 0x089Fxxxx thumb chains) never reference 0x0E000000, the DMA save path, or the flags above, and were verified as non-save (input/graphics/gameplay helpers).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic: 16 bytes at 0x3400: 4B 49 4E 47 20 4F 46 20 53 57 49 4E 47 20 45 55 = ASCII KING OF SWING EU. Verified in both .sav files and in code (4-word compare, FUN_086d26f4, decompiled.c:1887-1895). Note the magic is in the trailer, not a header — it sits after all four data copies.

Checksum (exact formula):

stored_u32_le @ 0x341C  ==  sum( image[0x0000 .. 0x341B] )   # unsigned byte sum, 32-bit accumulator
covered range: [0, 0x341C)   stored offset: 0x341C, size 4, little-endian

Code proof: writer sums total-4 bytes and stores at buffer+total-4 (decompiled.c:1949-1958); reader sums 0x341C bytes and compares to the following int32 (decompiled.c:1896-1907). With total 0x3420, both descriptions coincide. No seed, no complement, no CRC, no XOR — a plain additive sum. (Algorithm enum in save-format.json: sum32_le, since the accumulator and stored value are 32-bit.)

Python verification output (run in this workspace against the real files):

cap-00-future-0.sav  sum[0:0x341C]=0x0007086f  stored@0x341C=0x0007086f  match=True
cap-01-future-1.sav  sum[0:0x341C]=0x00070770  stored@0x341C=0x00070770  match=True

Cross-check from the inter-sample diff: the only payload byte that changes between the captures is at 0x341B (0xFF → 0x00, Δ = −255), and the stored checksum changes by exactly −255 (0x7086F → 0x70770, with the borrow visible in bytes 0x341C..0x341D). The PACKET probe's single-byte mutation at 0x341B necessarily breaks this sum, which is why the loader rejected and rewrote the save — that probe confirms integrity coverage of 0x341B but does not by itself prove the byte has gameplay meaning.

Rejected alternatives (tested, do not match): sum over [0,0x3400), sum including the magic, sum over the full 0x3420, and any 16-bit truncation — the stored values match only the [0,0x341C) 32-bit sum on both files.

6. Save Fuzzing & Counterfactual Verification Plan

Checksum repair for every test below (unless stated): recompute sum(image[0:0x341C]) in Python and store it as u32 LE at 0x341C, e.g. struct.pack_into('<I', img, 0x341C, sum(img[:0x341C]) & 0xFFFFFFFF). Reload from the paired save state after each mutation and observe UI/gameplay/RAM (0x030002B3 error flag, 0x03000002 state, 0x030004BB).

#MutationChecksum repair?Predicted observable
1Flip one byte at 0x341C (checksum itself), no repairNoLoad rejects; blank/default save rewritten; state 0x1C. Reproduces the PACKET probe result and confirms checksum position
2Corrupt one magic byte at 0x3400YesStill rejected (magic compare runs before/independent of sum); blank save rewritten. Distinguishes magic from checksum failure if RAM state differs
3Toggle 0x341B (0xFF↔0x00)YesAccepted silently ⇒ padding/uninitialised byte; any UI/mode change ⇒ real flag. Resolves the UNKNOWN field
4Set record 0 scores (0x0304..0x0310) to 60, 120, 180 in copy 0 onlyYesIf first level's best-times display changes, copy 0 is authoritative; if not, repeat in all 4 copies — together these identify the copy-selection rule
5Same as #4 but in copy 3 onlyYesChange ⇒ last-copy-wins; no change ⇒ first-copy or all-copies-compared rule
6Zero one 8-byte record at 0x0100 in all 4 copiesYesA level/item locks (or unlocks) if the flags array hypothesis holds; no visible change weakens it
7Change 0x00F9 (and replicas) 0x02 → 0x00/0x01/0x03YesLanguage/mode/version UI change if the byte is a mode selector
8Change 0x00C0 bytes 60 60 in all copiesYesAudio/settings change if it is a volume/settings pair; otherwise inert constant
9Write 0x00 over 0x3420..0x342F (outside image)NoNo effect predicted; any effect falsifies the 0x3420 image-length derivation
10Zero the entire records array (0x0300..0xBFF, all copies)YesAll best-times/scores cleared while unlocks persist if the records hypothesis holds; a blank-save reset instead would mean the array is validated semantically

Appendix: Method & Limitations

  • Geometry was derived by Python analysis of both .sav files (period detection, per-block SHA-256, byte diffs) and cross-checked against the writer/reader loop arithmetic (total-4 covered bytes, stored int32 after the covered range).
  • Literal-pool values (buffer address, read length, covered length 0x341C, total 0x3420, DMA default-data source) were not recovered by Ghidra (pbRam086d27bc-style placeholders); the numeric values above are inferred from .sav geometry and fit both samples and both code paths exactly, but are labelled accordingly where they are not directly read from code.
  • states/ contains no paired save states for this cohort, so Section 6 is a plan, not executed results.
  • Functions FUN_089feaa8/FUN_089feab4 are jumptable thunks; their SRAM read/write roles are inferred from their sole call sites' argument order (0x0E000000 as source for read, destination for write).
