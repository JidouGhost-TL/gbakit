1. Executive Summary & Overall Confidence

Overall confidence: LOW (for a complete field-level format) — MEDIUM for the physical media, size, reader chain and header layout, LOW for payload semantics, writer behaviour and integrity.

What was proven by both code and .sav bytes:

  • The save medium is a 512-byte EEPROM (4 Kbit) image. The only EEPROM data-path function found, FUN_0802c87c at 0x0802c87c, performs serial EEPROM reads through DMA3 to/from 0x0D000000; its bulk caller FUN_0802100c at 0x0802100c loops over exactly 0x40 (64) blocks of 8 bytes = 512 bytes. Both .sav files are exactly 512 bytes, fill byte 0xFF.
  • A complete reader chain exists in the traced code: boot/init FUN_080222f8 (0x080222f8) → EEPROM timing setup FUN_0802103c/FUN_0802c684 and object construction FUN_0800c2ac (0x0800c2ac) → loader/validator FUN_0801239c (0x0801239c) → bulk read FUN_0802100c → block read FUN_0802c87c → DMA3 driver FUN_0802c7fc (0x0802c7fc).
  • The first 16 bytes form a header with a duplicated 32-bit value 0x62D00D60 (raw bytes 60 0D D0 62) at offsets 0x04 and 0x0C, a 0xFFFF sentinel at 0x08, and a one-dword validity comparison in FUN_08019a6c (0x08019a6c). The duplicated value is byte-identical in both snapshots.
  • The only gameplay-visible payload bytes beyond the header and zeros are single bytes 0x03 at 0x1D and 0x05 at 0x1F (equivalently big-endian-looking u16 values 3 and 5 at 0x1C/0x1E). Everything from 0x20 to the end of the active span is 0x00; the remainder of the chip is erased 0xFF.

What remains open (why not HIGH/MEDIUM overall):

  • No EEPROM write (flush) function exists in the decompiled corpus. FUN_0802c7fc is the only function that touches 0x0D000000, and its only caller is the reader FUN_0802c87c. The writer therefore either lies in an un-traced code gap (notably 0x080120B4–0x0801239C, between the tiny FUN_080120ac and FUN_0801239c, and the unrecovered tail/entry points 0x08012358, 0x080123E4, 0x080123F0 inside/near the loader) or was never executed during the trace-guided capture. This is stated as a finding, not filled in by guessing.
  • No checksum/CRC/sum/XOR algorithm was found in code, and none validates against the .sav bytes. Exhaustive Python search (below, §4) over byte-windows, sum8/sum16/sum32 (byte and word sums, both endiannesses), XOR, CRC-32, Adler-32, CRC-16/CCITT, FNV-1a and per-block word/byte-reversal transforms found no non-self-referential match to the stored dword. Integrity, as far as the traced code shows, is the single-dword comparison in FUN_08019a6c plus the duplicated header dword.
  • Absolute RAM addresses are not recoverable from decompiled.c. Ghidra literal-pool values (_DAT_0800c330, _DAT_08019a48, _DAT_08019a7c, _DAT_08019a80, …) are named but their values are not present in the corpus. Only relative offsets are proven: the EEPROM image lands at (save-object) +4, and the 8-byte header copy lands in a global pointed to by _DAT_08019a48.
  • Payload semantics (what the 3 and 5, and the zero fields, mean in gameplay) are hypotheses, because both snapshots were taken 34 frames apart during early boot/title flow (sav-00-pre=frame 990, post=1024; sav-01-pre=1024, post=1058) with no gameplay progression between them.
  • states/ contains only *.ss.identity.json metadata (frames/SHA-256), not reloadable .ss binaries, so no counterfactual reload was performed in this workspace; §6 is a plan for when the paired states are available.

Confidence vocabulary used below: CONFIRMED_VERIFIED = proven by decompiled code and .sav bytes; CONFIRMED_STATIC = proven by decompiled code / callgraph / text call-site only; HYPOTHESIS = consistent with bytes and code but not proven; UNKNOWN = no evidence.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (methodology)

Two sources were cross-checked, because they disagree in an instructive way:

  1. ghidra/callgraph.json records only direct FUN_-style calls. For the save cluster it contains exactly: 0x0802c7fc ← 0x0802c87c, 0x0802c87c ← (none), 0x0802100c ← (none), 0x0801239c ← (none), 0x0800c2ac ← 0x080222f8, 0x0802103c ← 0x080222f8, 0x08019a3c ← 0x08019a4c.
  2. ghidra/decompiled.c additionally contains func_0x… aliases emitted at tail-call / unrecovered-jumptable sites (every save-cluster function ends in (*UNRECOVERED_JUMPTABLE)(…)). A regex parse of all 225 function bodies for (FUN_|func_0x)(080[0-9a-f]+)\( recovers the edges the callgraph misses, e.g. FUN_0802100c is called by FUN_0801239c, which is called by FUN_0800c2ac. Every caller claim below cites which source proves it. Where the two disagree, the decompiled text is the stronger evidence (it is the actual call site); the callgraph absence is explained by Ghidra treating the transfer as an indirect jump, not a call.

Three addresses used by FUN_0800c2ac — 0x08012358, 0x080123E4, 0x080123F0 — have no FUN_ body in the corpus at all. 0x080123E4/0x080123F0 lie inside the address span of FUN_0801239c (0x0801239C–0x080123FC) and are most plausibly internal entry/tail points of the loader; 0x08012358 lies in the un-decompiled gap 0x080120B4–0x0801239C. They are reported as unrecovered entry points, not invented functions.

3.2 Low-level hardware I/O driver

FUN_0802c7fc (0x0802c7fc) — generic DMA3 transfer (the only 0x0D000000 toucher)

  • Callers: 0x0802c87c only (callgraph and text agree).
  • Behaviour (from the body in ghidra/save_related_functions.c / decompiled.c:6890): saves and clears a global enable word (*_DAT_0802c85c), programs WAITCNT-style register (*_DAT_0802c860 = *_DAT_0802c860 & (ushort)_DAT_0802c864 | *(ushort *)(*_DAT_0802c868 + 6) — mask + a per-media timing field at config +6, consistent with WAITCNT 0x04000204 SRAM/EEPROM waitstate setup), then writes source (*_DAT_0802c86c = param_1), destination (*_DAT_0802c870 = param_2), and count/control (*_DAT_0802c874 = param_3 & 0xffff | 0x80000000, enable bit 31 set), then busy-polls the high halfword of the control register (while ((uVar2 & 0x8000) != 0)) and restores the saved enable. The three consecutive register pointers (…86c/…870/…874) match the DMA3 SAD/DAD/CNT layout at 0x040000D4/D8/DC from PACKET.md. Absolute register values cannot be confirmed because the _DAT_ literal values are absent from the corpus — CONFIRMED_STATIC for the DMA3 identification, not VERIFIED.
  • It is direction-agnostic: the caller passes (src,dst,count) in either order, so this one driver serves both the EEPROM request-write and the data-read phases. There is no separate SRAM byte-copy loop, no Flash 0x5555/0x2AAA command sequence, and no erase routine anywhere in the 225 functions — consistent with EEPROM media and inconsistent with SRAM/Flash alternatives.

FUN_0802c87c (0x0802c87c) — EEPROM single-block (8-byte) serial read

  • Callers: FUN_0802100c only (text call site decompiled.c:2656; callgraph lists it as a root because the call is via the func_ alias).
  • Signature/behaviour: FUN_0802c87c(uint block_addr /*masked &0xffff*/, int out_buf).
  • Bounds check: if (param_1 < *(ushort *)(*_DAT_0802c894 + 4)) — the EEPROM config struct's field at +4 is the block count (must be ≥64 for the observed chip; the caller's loop proves 64 is used).
  • Builds a serial request bitstream on the stack (auStack_96[67] halfwords, one bit per halfword): address bits are emitted MSB-first in a loop counted by *(byte *)(*_DAT_0802c928 + 8) (address-width field at config +8; 6 bits for a 64-block chip, value not in corpus), preceded by two 1 bits (*puVar5 = 1; puVar5[-1] = 1; — start + read-opcode framing per the standard EEPROM serial protocol; the exact opcode encoding is HYPOTHESIS from bit pattern alone).
  • FUN_0802c7fc(auStack_98, 0xd000000, addr_bits + 3) — DMA-writes the request bitstream to the EEPROM bus.
  • FUN_0802c7fc(0xd000000, auStack_98, 0x44) — DMA-reads 0x44 = 68 halfwords back (64 data bits + framing/dummy bits).
  • Unpacks: starting at auStack_96 + 3, it gathers 16 bits at a time (uVar4 = uVar4 << 1 | *puVar5 & 1), four times, storing each u16 to descending addresses (puVar6 = (ushort *)(param_2 + 6), then puVar6 += -1). Consequence for the field map: within each 8-byte block, the RAM image produced by this routine has its four u16 words in reverse order relative to the serial bit order. Whether the emulator .sav byte order already compensates for this (so .sav offset == RAM offset) cannot be proven from the corpus; the field map in §5 therefore reports raw .sav offsets as primary and flags the possible per-block u16-reversal as an open transform (see §4.3 and open questions).
  • Returns 0 on success (uVar3 = 0 inside the bounds-pass branch); on out-of-range it returns the pre-loaded global uRam0802c898 (non-zero error sentinel, exact value not in corpus).

EEPROM timing/config setup: FUN_0802103c (0x0802103c) → FUN_0802c684 (0x0802c684)

  • FUN_0802103c does exactly func_0x0802c684(4) and tail-returns. Caller: FUN_080222f8 (callgraph and text).
  • FUN_0802c684(short mode): with mode == 4 it performs *_DAT_0802c698 = _DAT_0802c69c (other modes 0x40/other write different globals) and returns a flag via the jumptable. Interpreted as selecting the EEPROM waitstate/timing profile (mode 4) before any EEPROM access — CONFIRMED_STATIC for the call and the conditional store; the register identity is HYPOTHESIS (literal values absent).

3.3 Bulk reader / deserialization

FUN_0802100c (0x0802100c) — read whole EEPROM into RAM

  • Callers: FUN_0801239c only (text, decompiled.c:1217: func_0x0802100c(param_1 + 4)).
  • Loop: do { sVar1 = func_0x0802c87c(uVar2 & 0xffff, param_1); param_1 += 8; uVar2++; if (0x3f < uVar2) break; } while (sVar1 == 0); then tail-returns (sVar1 == 0). I.e. it fills the destination with up to 64 consecutive 8-byte blocks (512 bytes), stopping early on the first block error, and reports overall success as its return value (consumed as a truth value by the loader). This function is the serialization boundary on the read side: EEPROM offset N maps to RAM byte dest + N, with dest = save_object + 4.

FUN_0801239c (0x0801239c) — loader + header validator (save-manager method)

  • Callers: FUN_0800c2ac only (text, decompiled.c:660: func_0x0801239c(_DAT_0800c330); the argument is the global save-object pointer whose value is not in the corpus).
  • Step-by-step (body at decompiled.c:1207):
  1. iVar3 = func_0x0801d780() — fetch a current-context id (FUN_0801d780 returns *_DAT_0801d788).
  2. func_0x0801d9dc() — if a flag global is set, clear it, call FUN_0802a2d0 and clear two globals (teardown of a previous context; not save-data mutation).
  3. uVar1 = func_0x0802100c(param_1 + 4) — the flush-in: whole EEPROM → RAM at param_1+4.
  4. if (iVar3 != *_DAT_080123e0) func_0x0801d69c(iVar3); — if the fetched id differs from a stored global, (re)initialise that context via FUN_0801d69c (see §3.5).
  5. func_0x08019a3c(param_1 + 4) — copy the first 8 bytes of the freshly loaded image into the validation global (see §3.4).
  6. cVar2 = func_0x08019a6c(); if (cVar2 != '\0') func_0x08019a4c(); — if the header test fails, overwrite the validation global with ROM constants (FUN_08019a4c). Note carefully: this repairs the global copy, not the EEPROM and not the loaded buffer — no write-back occurs here.
  7. Tail-returns uVar1 (the bulk-read success flag from step 3), not the validity result. Validity is re-tested by the caller.

FUN_0800c2ac (0x0800c2ac) — object constructor / top-level save consumer

  • Callers: FUN_080222f8 only (callgraph and text; invoked during boot/task setup and its result registered via FUN_08015a24(auStack_1c, result, 1)).
  • How it mutates RAM before/around the load (body at decompiled.c:639): it initialises its own game object first — *param_1 written twice from ROM constants, sub-object constructed at param_1+1 by FUN_0800dea0 (which itself calls FUN_0800d970 to set defaults including param_1[8] = 3, list/array fields, etc.), *(undefined1 *)(param_1 + 0x27) = 0, param_1[0x29] = 4, param_1[0x2a] = param_1[0x2b] = 0, a 2-byte field at param_1 + 0x3e zeroed by FUN_080120ac, the global back-pointer *_DAT_0800c32c = param_1 stored, list insertion via FUN_08015c2c(param_1), param_1[0x30] = 0. Only then does it load the save:
  • cVar2 = func_0x0801239c(_DAT_0800c330) — load EEPROM image (into the global save object, a different object from param_1).
  • If load succeeded (cVar2 != 0): re-test validity with FUN_08019a6c().
  • Valid branch (== 0): func_0x080123fc(uVar1, puVar3) — apply the loaded save to the game object (puVar3 = param_1 + 1). FUN_080123fc (0x080123fc) itself only calls FUN_08019a84(param_2), and FUN_08019a84 (0x08019a84) is an empty stub (return;). So in the traced code the "apply" step is a no-op placeholder — the real field-by-field deserialization must live in unrecovered code (jumptable targets) or the game reads the RAM image at save-object+4 directly. CONFIRMED_STATIC for the stub; deserialization semantics UNKNOWN.
  • Invalid branch (!= 0): func_0x080123e4(uVar1) (unrecovered), func_0x0801241c(uVar1), func_0x080123f0(uVar1, puVar3) (unrecovered), func_0x08012358(uVar1) (unrecovered). Of these only FUN_0801241c (0x0801241c) is decompiled: it writes a single ROM constant dword (FUN_08019aac: *p = _DAT_08019ab4) at offsets *param_1, *param_1 + 100, *param_1 + 200, *param_1 + 300 — i.e. it resets four same-typed fields spaced 100 bytes apart in the save object (plausibly four sub-records/counters) to a default. This is the defaults-initialisation path taken on first boot / corrupt save, and it mutates RAM only in the traced code.
  • It never calls any EEPROM write. Whatever persists the defaults to the chip is outside the corpus.

3.4 Header validation helpers

FUN_08019a3c (0x08019a3c) — copy 8-byte header to validation global

  • Callers: FUN_0801239c and FUN_08019a4c (callgraph + text).
  • Body: puVar1 = _DAT_08019a48; uVar2 = param_1[1]; *_DAT_08019a48 = *param_1; puVar1[1] = uVar2; — copies exactly two u32s (8 bytes) from the argument to the global. Used both to snapshot the loaded header (from save-object+4) and to install constant headers (from a stack pair in FUN_08019a4c).

FUN_08019a6c (0x08019a6c) — one-dword validity test

  • Callers: FUN_0801239c, FUN_0800c2ac (text; callgraph lists none — tail calls).
  • Body: return (-(*_DAT_08019a7c ^ _DAT_08019a80) | *_DAT_08019a7c ^ _DAT_08019a80) >> 0x1f; — computes the XOR of one dword in the validation global with one ROM constant and reduces it to a boolean (0 iff the XOR is 0, i.e. iff the dword equals the constant; the expression is the compiler's branchless != 0 idiom, returned as the sign bit). This is the entirety of the integrity/magic checking found in the corpus. Which of the two header dwords is compared (offset 0x00 or 0x04 of the image) depends on whether _DAT_08019a7c points at the global's first or second word — unresolvable from the corpus. §4 evaluates both readings against the bytes.

FUN_08019a4c (0x08019a4c) — install default header into validation global

  • Callers: FUN_0801239c only (text + callgraph via FUN_08019a3c edge).
  • Body: builds a stack pair uStack_c = _DAT_08019a64; uStack_8 = _DAT_08019a68; and calls FUN_08019a3c(&uStack_c). So the "known-good" header is two ROM dwords. If the compared dword is header word 1 (image offset 0x04), the expected constant _DAT_08019a80 and one of these defaults should equal 0x62D00D60; if it is word 0, the expected value should be 0x00000000. Both are consistent with the observed bytes; the corpus cannot distinguish them (see §4).

FUN_08019aac (0x08019aac) — single-dword default store

  • Callers: FUN_0801241c only (text). Body: *param_1 = _DAT_08019ab4;. A one-constant reset primitive used four times by the invalid-save branch.

3.5 Context (re)initialisation reached from the loader

FUN_0801d69c (0x0801d69c)

  • Callers: FUN_0801239c (conditional, when the context id changed) and FUN_0800d7c4 (0x0800d7c4, text: func_0x0801d69c(*_DAT_0800d808) after allocating a new sub-object via FUN_0801f8c0).
  • Behaviour relevant to saves: it is not a save writer. It guards on a state global (*_DAT_0801d73c), tears down (FUN_0802a2d0) when active, then populates a descriptor struct (_DAT_0801d750): clears byte at +0x38 (puVar2 + 0xe as bytes — struct-field offsets in the decompilation are in undefined4 units in places; reported here as written), stores the id at puVar2[0xc], a ROM pointer at puVar2[0xb], zeroes a u16 at byte-offset 0x12, sets u16 fields (value 2 at puVar2+4 as undefined2, and two shorts from ROM constants), calls FUN_080285a0(puVar2) and FUN_08028ca4(puVar2), and on success sets state globals and calls FUN_0801d820(0x100) / FUN_08029c70(0xffffffff, …). It mutates RAM game state that may later be serialized by the missing writer, but no field-level mapping from this struct to .sav offsets is provable. CONFIRMED_STATIC for the mutations; save relevance HYPOTHESIS.

FUN_080222f8 (0x080222f8) — boot / main-loop (root)

  • Callers: none (root in both sources).
  • Save-relevant sequence: func_0x0802d7c8(), FUN_08021894(), func_0x08027df0(), func_0x080225c8(), FUN_0801da70() (resets a block of globals to 0/0x100 defaults), FUN_08020f00() (sets a bit | 0x40 in a control global), FUN_0802103c() (EEPROM timing setup, §3.2), then object/task registration (FUN_08015b90, FUN_08015a24 with results of FUN_0801f868, FUN_0800788c, FUN_0800c2ac — the last being the save consumer of §3.3), FUN_08015bbc(_DAT_08022364), and the main loop (FUN_080101bc poll, FUN_080159fc/d4, …). So EEPROM setup and save load happen once, early in boot, before the main loop — matching the snapshot timing (first .sav appears between frames 990 and 1024).

3.6 The writer: negative result (exhaustive)

The following were searched across all 225 decompiled bodies and the callgraph: the literal 0xd000000 (2 hits, both in FUN_0802c87c), FUN_0802c7fc call sites (1 caller), any second caller of FUN_0802c87c/FUN_0802100c, any loop packing bits MSB-first from a RAM buffer toward 0x0D000000 (the write-side mirror of the reader's unpack), any Flash 0x5555/0x2AAA sequence, and any SRAM copy at 0x0E000000. None exist in the corpus. The EEPROM write driver (which by symmetry with the reader would build a ~addr_bits + 66-bit write bitstream and DMA it to 0x0D000000) is absent. Candidates for its location, in order: (a) the un-decompiled gap 0x080120B4–0x0801239C adjacent to the loader; (b) the unrecovered entry points 0x08012358/0x080123E4/0x080123F0; (c) code never executed during the trace-guided capture (e.g. a "save game" menu action not performed before frame 1058 — consistent with the snapshots showing only boot-time defaults and zero-extension). The observed .sav contents (valid header already present at first snapshot) prove something wrote the header before frame 1024 in the emulator run, but that writer is not in the provided Ghidra corpus. All writer-dependent claims below are therefore UNKNOWN/HYPOTHESIS, and no writer address is fabricated in save-format.json (the driver entries list only functions actually present).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature (duplicated header dword)

Raw header bytes (both files, identical):

Offset  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
       00 00 00 00 60 0D D0 62 FF FF 00 00 60 0D D0 62
  • Stored value (little-endian u32): 0x62D00D60 at offset 0x04, repeated verbatim at offset 0x0C. Bytes are not printable ASCII (60 0D D0 62 = ` `, CR, Ð, b`) — it is a binary magic/ID, not a string tag. No ASCII magic (e.g. game-code string) exists anywhere in the active span.
  • Verification in .sav: verified — present at both offsets in both files (Python output in §4.4).
  • Verification in code: partial / static-only. The only validation primitive, FUN_08019a6c (0x08019a6c), compares exactly one dword of the 8-byte header copy (installed by FUN_08019a3c, 0x08019a3c) against a ROM constant _DAT_08019a80:
// FUN_08019a6c (0x08019a6c) — decompiled.c
return (-(*_DAT_08019a7c ^ _DAT_08019a80) | *_DAT_08019a7c ^ _DAT_08019a80) >> 0x1f;

Exact formula: valid ⇔ (*_DAT_08019a7c XOR _DAT_08019a80) == 0, branchlessly reduced to a 0/1 (sign-bit) result. Callers: FUN_0801239c (on failure it calls FUN_08019a4c to install the two ROM default dwords _DAT_08019a64/_DAT_08019a68 into the validation global) and FUN_0800c2ac (0 → apply-loaded branch FUN_080123fc; non-zero → defaults branch). Because the corpus does not contain the literal values of _DAT_08019a7c (which word of the global it points at) or _DAT_08019a80 (the expected constant), two readings remain:

  • Reading A (compared word = image offset 0x04): expected constant = 0x62D00D60; the duplicated dword is the magic, and its copy at 0x0C is redundancy (only one copy is actually tested by this function; any test of the second copy would be in unrecovered code).
  • Reading B (compared word = image offset 0x00): expected constant = 0x00000000; the test merely checks the first dword is zero, and 0x62D00D60 is an unchecked ID/version field.

Reading A is rated more likely (a non-trivial constant is the usual reason for such a test, and FUN_08019a4c installs two non-stack-default dwords, suggesting at least one is non-zero), but it is not proven. Confidence: CONFIRMED_VERIFIED that the duplicated bytes exist in .sav; HYPOTHESIS that 0x62D00D60 is the compared magic; CONFIRMED_STATIC that the comparison formula above is the only integrity test in the traced code.

4.2 Checksum: exhaustive negative result

No sum, XOR, CRC, complement or seeded-checksum routine referencing the save buffer, the header copy, or the EEPROM image exists in the 225 decompiled functions (the only arithmetic test is §4.1). To avoid asserting absence from code reading alone, the stored dword was also tested computationally against the actual bytes (§4.4): every contiguous byte window inside 0x00–0x70 not overlapping the header fields, under sum8, sum16, sum32 (byte sums), little-/big-endian u16-word and u32-word sums, XOR-8/16/32, CRC-32 (binascii.crc32), Adler-32, CRC-16/CCITT-FALSE, FNV-1a-32, and the same set after per-8-byte-block transforms (reverse bytes, reverse u16 words, swap u32 halves — the transforms suggested by the reader's unpacking in FUN_0802c87c). No window/algorithm/transform produced 0x62D00D60 (the only hits were trivial self-references where the window contained the stored dword itself, and low-byte coincidences …& 0xFF == 0x60, both excluded as non-evidence). 4.3 Byte-order caveat (reader transform)

FUN_0802c87c stores the four unpacked u16s of each block to descending RAM addresses. If the .sav file byte order is the serial/EEPROM order rather than the post-unpack RAM order, then the in-RAM field layout is the per-block u16-reversed transform of the file: under that transform the header becomes D0 62 60 0D 00 00 00 00 | D0 62 60 0D 00 00 FF FF … and the 0x1C region becomes 00 05 00 03 …. Neither transform produces a more "magic-like" header than the raw reading (raw gives the same dword value 0x62D00D60 twice as LE u32; reversed gives 0x0D6062D0 twice), and mGBA-style EEPROM dumps conventionally store bytes in the game's logical address order. The field map (§5) therefore uses raw .sav offsets, and the transform is carried as an open question (§7). Fuzzing at the .sav level (§6) is unaffected: mutate file bytes, let the game's own reader transform them.

6. Save Fuzzing & Counterfactual Verification Plan

Prerequisites: use the paired save states as reload points — sav-00-pre (frame 990, state SHA e0980fb7…, = gameplay.ss) → sav-00-post (frame 1024, a2e84544…) for the first save appearance, and sav-01-pre (frame 1024) → sav-01-post/final (frame 1058, 4a82a075…) for the zero-extension. Workspace caveat: states/ currently contains only *.ss.identity.json metadata, not the .ss binaries; obtain the actual state files matching those SHA-256 prefixes before executing this plan. For every mutation: (1) copy the .sav, apply the byte edit, (2) checksum repair = none required beyond the header rule in step (3) — no CRC exists (§4.2); (3) unless the mutation is itself a header test, keep 0x04 and 0x0C equal and, under Reading A, equal to 60 0D D0 62; (4) cold-boot (do not load a state taken after the save was already read into RAM — the loader runs at boot in FUN_080222f8; states at frame ≥1024 may already hold the RAM image at save-object+4, so prefer booting the ROM with the mutated .sav attached, or use sav-00-pre (frame 990) if it predates the FUN_0800c2ac load in that run — verify by checking whether sav-00 appears without mutation in the control run); (5) run a control (unmutated .sav) and a blank control (all-FF .sav) side by side; the packet's cold-reload probe (save_preserved: true, visual_delta_vs_blank_boot: true) predicts the unmutated control differs visually from blank boot. Observe: title/continue UI, defaults vs. loaded behaviour, and — if a debugger is available — the RAM image at save-object+4 and the validation global copy after FUN_08019a3c, plus which branch of FUN_0800c2ac executes (valid FUN_080123fc vs. invalid defaults path). "Repair" for payload mutations: none; if the game rejects the file, re-apply the mutation with header dwords restored as in (3) to isolate whether rejection was header- or payload-driven.

7. Open Questions

  1. Where is the EEPROM write driver and its callers? Absent from the corpus (§3.6). Prime suspects: gap 0x080120B4–0x0801239C, unrecovered entries 0x08012358/0x080123E4/0x080123F0, or code unexecuted during capture. Without it, flush triggers (menu, checkpoint, auto-save), write granularity, and whether the header is rewritten on every save are all unknown.
  2. Which header dword does FUN_08019a6c compare, and what is the constant _DAT_08019a80? (Reading A vs. B, §4.1.) Resolvable instantly if literal-pool values (_DAT_08019a48/…a64/…a68/…a7c/…a80, _DAT_0800c330) are ever dumped; resolvable behaviourally by fuzz tests F1/F2.
  3. Absolute RAM address of the save object / image (save-object base; image at base+4). All _DAT_ literal values are missing from decompiled.c; only relative offsets are proven. This also blocks mapping FUN_0801241c's +0/+100/+200/+300 resets to file offsets (test F10).
  4. Does any code cross-check the duplicated dword (0x04 vs 0x0C) or test 0x08/0x0A? No such code in the corpus; test F3/F4.
  5. Per-block byte order: does the .sav byte order equal the post-unpack RAM order, or is each 8-byte block u16-reversed in RAM by FUN_0802c87c (§4.3)? Affects RAM-side field offsets (not file offsets); resolvable by dumping RAM after load.
  6. EEPROM config struct values: block-count field (+4, must be ≥64), address-width field (+8, expected 6), WAITCNT timing field (+6), and the return sentinel uRam0802c898. Consistent with 64×8=512 B but the exact values are not in the corpus.
  7. Semantics of the (3, 5) pair at 0x1C–0x1F and of the zero payload (0x10–0x57), and what gameplay progression changes them. Both snapshots predate any gameplay divergence; later saves are needed.
  8. What wrote the 0x58–0x5F / 0x65–0x67 zero blocks between frames 1024–1058, and is that a save-flush, an EEPROM-space initialisation, or emulator EEPROM backing-store behaviour? The sub-block change at 0x65 is not whole-block aligned.
  9. Is FUN_080123fc's apply step really a stub, with deserialization done by direct reads of the RAM image elsewhere (no traced consumers of image fields beyond the header were found), or does the unrecovered jumptable hide the real apply code?
  10. Are there save-related functions among the 225 that were not recognised because they never touch 0x0D000000 in the traced path (e.g. a serializer that only mutates the RAM image at save-object+4, to be flushed by the missing writer)? A serializer of that shape would be indistinguishable from ordinary game-object code in this corpus; the FUN_0801241c/FUN_08019aac reset pattern is the only concrete lead.
