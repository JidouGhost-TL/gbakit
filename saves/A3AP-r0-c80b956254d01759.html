1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven (code + byte-level verification against the real .sav):

  • The complete low-level EEPROM I/O stack: bitstream read/write primitives, a generic DMA3 transfer helper, an IRQ-disable/restore wrapper, a write-with-readback-verify routine, and two retry-wrapped "bulk record" read/write entry points.
  • Two distinct checksum algorithms are implemented in the save-validation code, and both were verified byte-for-byte against the actual .sav file (see §4). This is the strongest result in this report.
  • The EEPROM's 8192-byte address space is organized into fixed-size, 8-byte "records" (consistent with a 1024-record / 64 Kbit EEPROM), and the capture shows a clear, reproducible primary/backup redundancy pattern: every structure that is checksum-protected exists twice, byte-identical, at a fixed offset apart.
  • The top-level boot sequence: FUN_08002418 (RAM/BIOS init) unconditionally calls func_0x080fc2d8, which is the save-subsystem's "validate everything, repair on mismatch" entry point, confirming all of this logic runs once at boot/title before any gameplay.

What remains open (HYPOTHESIS / UNKNOWN):

  • The exact semantic meaning of several fixed/constant-looking fields (e.g. the 0x00004E20 field in the file-slot header, and the 4-byte prefix 00 03 09 94 preceding the "0PYA" tag in each per-slot level-data block). These values did not match any checksum/complement/XOR formula tested against the bytes around them, and only one .sav sample is present in this workspace, so no cross-sample diffing was possible to separate "constant" fields from "variable" ones.
  • The internal layout of the 768-byte per-file-slot level/progress data beyond its first 8-byte tag header; the Ghidra decompilation of FUN_080fbdf0/FUN_080fc180 shows byte/halfword copies and clears into a 0x300-byte RAM buffer but the per-field semantics (per-level completion flags, coin counts, etc.) are not exposed by the pointer-aliased (_DAT_*) Ghidra output available here.
  • Whether the "global config" 8-byte record (offset 0x10/0x20) represents sound/options settings, a "last played file" pointer, or something else — only its checksum mechanics are confirmed, not its payload semantics.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM, addressed in 8-byte records by the low-level driver (FUN_0813249c/FUN_0813254c/FUN_08132628/FUN_08132680). The supplied .sav is 8192 bytes = 1024 records of 8 bytes, consistent with a 64-Kbit EEPROM (EEPROM 64K as declared).
  • Written extent: Only records 0–319 (byte offsets 0x0000–0x09FF) contain any non-zero/non-erase content in the sample; all bytes from 0x0A00 to the end of the file (0x1FFF) are 0x00. Bytes inside the written extent that have never been touched read back as 0xFF (the classic EEPROM "erased" value), while bytes past the written extent read back as 0x00 in this capture — most likely an artifact of how the emulator/capture tool materializes a never-allocated backing file, not a real hardware distinction. Confidence: CONFIRMED_STATIC (byte observation); the 0x00-vs-0xFF distinction's cause is HYPOTHESIS.

How the slot geometry was mapped (confidence: CONFIRMED_STATIC for the stride, CONFIRMED_VERIFIED for the byte-identity of each primary/backup pair): FUN_080fc2d8 (the master boot-time validator, §3) loops exactly 3 times calling FUN_080fbdf0 once per iteration — the literal 3 loop bound matches the 3 observed 768-byte file-slot regions. FUN_080fbdf0 copies a 0x300-byte (768-byte) RAM buffer out via FUN_080fb1ec/FUN_080fb290, matching the 768-byte slot stride measured directly in the file (0x400-0x100 = 0x300, 0x700-0x400 = 0x300). Within each 768-byte slot, the primary/backup split at the halfway point (+0x180 = 384) was found empirically: every slot's first 8 bytes at offset +0 and +0x180 are byte-identical (0003099430505941 in all 6 cases, verified in Python), and the same primary/backup byte-identity holds for the global-config record (0x10≡0x20) and the file-header record (0x80≡0xC0).

Selection rule: Not directly observable from a single static capture (no divergent primary/backup pair exists in this sample to show which one "wins"). From the code in FUN_080fb3ac and FUN_080fb85c (§3), the rule is: read the primary copy, validate its checksum; if invalid, read the backup copy and validate; if the backup is valid, copy it into the primary slot (self-healing). If both fail checksum, the code falls through to re-initializing the record from a fixed default and rewriting both copies. Confidence: CONFIRMED_STATIC (proven by code control flow; not exercised against a corrupted sample in this workspace).

4.2 Checksum Algorithm A — "6+2" one's-complement sum16 (global config record)

  • Formula: stored_checksum (2 bytes, big-endian, at record offset 0–1) == (0xFFFF − sum(payload_bytes[2..8])) & 0xFFFF
  • Covered range: bytes 2–7 of the 8-byte record (6 payload bytes).
  • Stored location: bytes 0–1 of the same record.
  • Code proof: FUN_080fb5f0 (decompiled.c lines ~1770–1799) computes uVar2 = sum(pbVar3[0..5]) then stores ~uVar2 — a 16-bit one's complement — immediately before calling FUN_080fb318 to flush. FUN_080fb3ac performs the mirror-image check on read (lines ~1649–1763).
  • Python verification (run against saves/cap-00-future-0.sav):
Record @ 0x10: fe c8 01 01 01 01 da 59
  payload[2:8]        = 01 01 01 01 da 59
  stored checksum      = 0xFEC8   (bytes[0:2], big-endian)
  computed checksum     = (0xFFFF - sum(payload)) & 0xFFFF = 0xFEC8
  MATCH
Record @ 0x20 (backup): identical bytes to 0x10 -> MATCH

Confidence: CONFIRMED_VERIFIED.

4.3 Checksum Algorithm B — self-referential additive sum16 (file-slot-table header record)

  • Formula: stored_checksum (2 bytes, big-endian, at record offset 14–15) == sum(all 24 bytes of the record, with bytes 14–15 temporarily set to 0) & 0xFFFF
  • Covered range: the full 24-byte record (with the checksum field itself zeroed during computation — a standard "self-inclusive" checksum pattern).
  • Stored location: bytes 14–15.
  • Code proof: FUN_080fb7dc (decompiled.c lines ~1917–1951) explicitly zeroes *(short *)(iVar1 + _DAT_080fb84c) = 0; then sums all 24 bytes (bVar6 < 0x18 loop) and stores the sum back into that same halfword. FUN_080fb85c performs the matching validation on read.
  • Python verification:
Record @ 0x80 (primary): 30 50 57 4d 33 41 4d 53 00 00 4e 20 00 00 02 a9 00 00 00 00 00 00 00 03
  stored checksum (bytes[14:16], BE) = 0x02A9
  computed (sum of all 24 bytes, bytes[14:16] zeroed) = 0x02A9
  MATCH
Record @ 0xC0 (backup): identical bytes -> MATCH

Confidence: CONFIRMED_VERIFIED.

4.4 Per-file-slot level-data checksum (FUN_080fbc6c)

  • Formula (code-level only): plain additive 16-bit sum over 0x78 (120) halfwords (240 bytes) of a staged RAM buffer, no complement.
  • Status: the summed region is a RAM-side staging buffer assembled by FUN_080fb20c/FUN_080fb1ec from parts of the 768-byte EEPROM slot plus fixed constants; it is not a contiguous 240-byte span of the raw .sav file, so it could not be verified directly against saves/cap-00-future-0.sav bytes with the tools available in this workspace (no RAM/emulator trace capturing the assembled buffer is present in states/, which is empty for this release).

Confidence: CONFIRMED_STATIC (algorithm proven from code) but NOT verified against file bytes — flagged as an open item in §6/open_questions.

4.5 Unidentified constant-looking fields

  • 0x0088 (and its backup 0x00C8): 00 00 4E 20 (= 20000 decimal, big-endian) — tested against every checksum/XOR/complement hypothesis over every other span in the 24-byte record; no match found. Byte-identical between primary and backup, so either a true constant (version/build tag) or a field that has simply never changed in this single sample.
  • 0x0100 (and the 5 other slot-header starts): 00 03 09 94 preceding the "0PYA" tag — same treatment, same result (no match found).

Confidence: HYPOTHESIS/UNKNOWN — see §6 for the counterfactual test that would resolve this (vary gameplay state, re-capture, diff).

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of saves/cap-00-future-0.sav, loaded into the emulator from the paired gameplay.ss/pre-save .ss states once those are captured for this release (the states/ directory is currently empty for this checkpoint — no paired .ss states are available yet in this workspace, so none of the predictions below have been empirically run; this is a plan, not a result).

  1. Global config checksum repair test (validates Algorithm A, §4.2)
  • Mutation: flip one bit in payload byte 0x0012 (e.g. 0x01 → 0x03) without touching the checksum at 0x0010–0x0011.
  • Checksum repair: recompute (0xFFFF − sum(bytes[0x12:0x18])) & 0xFFFF and write it (big-endian) to 0x0010–0x0011.
  • Predicted effect (unrepaired): FUN_080fb3ac detects the mismatch on next boot, falls back to the backup record at 0x0020 (still valid/unmutated), and silently restores 0x0010 from it — i.e. the mutation should be invisible after one boot cycle unless the backup (0x0020) is mutated identically.
  • Predicted effect (both copies mutated identically, checksum repaired): no visible behavior change is predicted unless byte 0x0012 is proven to correspond to a visible setting (e.g. sound on/off, text language) — currently unknown; this is itself a secondary test of what the field controls.
  1. File-slot header tamper + both-copies-corrupt test (validates the redundancy/repair policy of §2 and Algorithm B)
  • Mutation: corrupt the checksum field at 0x008E-0x008F on both the primary (0x0080) and backup (0x00C0) records (e.g. zero them).
  • Predicted effect: FUN_080fb85c fails validation on both copies and takes the "rebuild from scratch" path (FUN_080fb674 + FUN_080fb7dc) — predict the file-select screen either shows all 3 slots as "new/empty" or the game visibly re-initializes the slot table on next boot. This is the clearest externally-observable counterfactual in this report.
  1. Per-slot tag corruption test (tests whether "0PYA" at 0x0104 is load-bearing or decorative)
  • Mutation: corrupt 0x0104–0x0107 (the "0PYA" ascii bytes) in the File Slot 0 primary copy only, leave the backup at 0x0284 intact.
  • Predicted effect: on boot, FUN_080fbdf0 should detect the primary/backup mismatch (via FUN_080fbc6c's additive checksum over the staged buffer) and silently restore Slot 0's primary from its backup — i.e. no visible change, serving as a direct test of whether the tag bytes are included in the FUN_080fbc6c checksum span.
  1. Unidentified constant-field mutation (resolves the 0x0088/0x0100 open questions from §4.5)
  • Mutation: change 0x0088–0x008B from 00 00 4E 20 to some other value in both primary and backup copies, with the Algorithm B checksum correctly repaired.
  • Predicted effect: unknown by design — this is an information-gathering mutation. If the game boots normally with no visible difference, the field is likely a build/version stamp. If the game detects an "invalid version" and force-rebuilds the slot table (same visible signature as test 2), the field is a guarded version/magic check not caught by the additive checksum alone.
  • Required follow-up: capture a second independent .sav from a different playthrough/session to see whether this field (and the 0x0100 00 03 09 94 field) ever actually varies — this cannot be determined from the single sample available in this workspace.
  1. Protocol negative — out-of-range record write
  • Not a byte mutation but a code-level observation worth stating as a negative test: FUN_0813249c/FUN_0813254c both bounds-check the record index against a stored record-count constant before touching the bus (if (param_1 < *(ushort*)(...))), so a save file artificially extended beyond the 1024-record (8192-byte) boundary should be silently ignored by the read/write primitives rather than causing an out-of-bounds bus access — a fresh/restore-repeat control worth confirming empirically once .ss states exist for this release.
