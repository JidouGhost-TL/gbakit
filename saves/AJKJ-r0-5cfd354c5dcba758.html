Clean-Room Save Format Report — Jikkyou World Soccer Pocket 2 (Japan)

AJKJ-r0-5cfd354c5dcba758 · ROM SHA-256 5cfd354c5dcba7583a954bfb04d28145ced4ccc0a441dcb3b694c039bae583aa

All findings below are derived exclusively from the files in this workspace (saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c) plus public GBA hardware facts (EEPROM mirror at 0x0D000000, DMA register layout SAD/DAD/CNT, EWRAM 0x02000000, IWRAM 0x03000000). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: LOW–MEDIUM.

What is proven:

  • The ROM contains a complete, self-consistent low-level EEPROM access driver (7 functions, addresses 0x08084ba4–0x08084ed4) built on top of a generic DMA-transfer primitive. This driver performs read, write, and write-with-read-back-verify-and-retry (up to 3 attempts) against the EEPROM MMIO mirror at 0x0D000000.
  • Exactly one of the two supplied .sav snapshots (cap-01-future-1.sav) differs from a fully-erased (0xFF-filled) EEPROM image. The diff is a single contiguous 84-byte span at file offset 0x1004–0x1057.
  • That span's internal layout is highly regular: it decomposes cleanly into eleven 8-byte blocks (0x1004, 0x100C, 0x1014, 0x101C, 0x1024, 0x102C, 0x1034, 0x103C, 0x1044, 0x104C, 0x1054), of which only the first block and two interior blocks carry non-zero payload.

What is not proven and remains open:

  • No caller of the top-level write/verify entry point (FUN_08084ed4) exists anywhere in the 266-function traced corpus. The code that actually decides when to save, what game state to serialize, and where that state lives in EWRAM/IWRAM before the flush is completely absent from this workspace. Every RAM-mirror address, field semantics, and "writer/reader caller chain" claim below this point is therefore a hypothesis derived purely from static byte-pattern inspection of the .sav files, not from decompiled logic.
  • No checksum, CRC, or magic-signature routine was found anywhere in the traced 266 functions. No candidate checksum byte could be verified against the payload (see §4).
  • Only 2 .sav samples exist, one of them fully blank. This is insufficient to distinguish "fixed-format field" from "coincidental value" for any byte in the active range.
  • states/ contains zero paired save states for this checkpoint cohort, so no RAM-to-.sav correlation via live memory inspection was possible.

Caveat on "64K": classic GBA 64 Kbit EEPROM is addressed in 1024 blocks of 8 bytes starting at file offset 0. The observed active span starts at 0x1004, i.e. 4 bytes into the 8-byte block that begins at 0x1000 (block index 512 of 1024). This is consistent with "only the tail 4 bytes of block 512 are non-erased" rather than a block-size mismatch — see §5 for the block-by-block breakdown.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Confirmed low-level I/O driver (hardware-adjacent, CONFIRMED_STATIC)

All seven functions below are present verbatim in ghidra/save_related_functions.c / ghidra/decompiled.c. Confidence is CONFIRMED_STATIC: the control-flow and register-layout reasoning below is sound, but Ghidra did not resolve any of the _DAT_* globals to named MMIO symbols (no literal 0x040000d4/0x0d000000 DMA register strings appear anywhere in the corpus other than one status-bit test), so the exact DMA channel (3 vs. another) is inferred, not read from a symbol name.

AddrRoleEvidence
0x08084c70 FUN_08084c70(src, dst, cnt)Generic DMA kick-off + busy-wait. Writes src→SAD-equivalent global, dst→DAD-equivalent global, cnt\|0x80000000→CNT-equivalent global (bit31 of the combined 32-bit word = bit15 of the high half = the real GBA DMA "enable" bit), then polls a 16-bit status word at +2 for bit 0x8000 to clear. This is structurally identical to a DMA SAD/DAD/CNT_L/CNT_H register triplet with the hardware enable bit, matching the public GBA DMA register layout.ghidra/decompiled.c:7961
0x08084cf0 FUN_08084cf0(param_1, param_2) [MMIO-SEED]EEPROM block READ. Builds a bit-serial read-request stream into a stack buffer, DMAs it out to 0xD000000 (via FUN_08084c70(..., 0xd000000, ...)), then DMAs 68 halfwords back in from 0xD000000, and finally unpacks 4×16-bit words of real data by shifting in one bit per received halfword (uVar4 = uVar4<<1 \| *puVar5&1, 16 iterations × 4 words = 64 bits = 8 bytes). Produces exactly one 8-byte EEPROM block per call.ghidra/decompiled.c:7992; constants 0x44=68 matches request-stream+turnaround+64-bit payload framing used by the real EEPROM serial protocol
0x08084da0 FUN_08084da0(param_1, param_2) [MMIO-SEED]EEPROM block WRITE. Packs the 8-byte buffer at param_2 plus the 10/14-bit block address param_1 into a bit-serial write-request stream, DMAs it to 0xD000000 (FUN_08084c70(..., 0xd000000, *addr+0x43)), wraps the transfer in FUN_08084ba4/FUN_08084c2c (see below), then busy-waits on the EEPROM "ready" bit at 0xD000000 (uRam0d000000 & 1) before returning.ghidra/decompiled.c:8050
0x08084ba4 FUN_08084ba4(param_1)Enter critical section / enqueue DMA request. Links a small 3-field descriptor (copied from param_1[0..2]) into what reads as a circular pending-transfer queue, and sets a "busy"/"armed" flag to 1. 3.2 The missing link: no traced caller mutates a RAM save struct

This is the single most important negative finding of this analysis. ghidra/callgraph.json reports "0x08084ed4": {"callers": [], ...}, and an exhaustive grep of every one of the seven save-driver addresses across the full ghidra/decompiled.c (266 functions) confirms zero other function references 0x08084ed4, 0x08084da0's caller set beyond 0x08084ed4, etc. Additionally:

  • None of the 266 decompiled functions reference any EWRAM (0x02xxxxxx) or IWRAM (0x03xxxxxx) literal address — i.e. there is no visibility at all, anywhere in this workspace, into where the in-RAM save struct lives or how it is populated.
  • 209 of the 266 functions (79%) are marked Could not recover jumptable — they are indirect-branch veneers/thunks whose real target Ghidra could not statically resolve from the trace. The function that calls into FUN_08084ed4 almost certainly exists only as one of these unresolved indirect-jump targets, i.e. it was never actually executed during whatever trace seeded this decompilation, or it was executed but through a branch Ghidra couldn't follow.

Conclusion: the "serialization" and "what triggers a save" layers cannot be documented from code in this packet. §5's field map is therefore built bottom-up from the raw .sav bytes only, with explicit HYPOTHESIS/UNKNOWN confidence, not top-down from a traced writer.

4. Magic Signatures & Checksum / Integrity Algorithm

No checksum, CRC, or magic-signature computation routine was found in ghidra/decompiled.c. All 266 functions were inspected; none contain an accumulation loop (running sum/XOR/rotate) over a buffer of plausible save-record length. This is consistent with §3.2: the serialization layer that would contain such a routine is not present in the traced corpus.

Python verification was still performed against the only non-blank sample, to rule out an externally-known trivial checksum coincidentally matching:

$ python3
data1[0x1004:0x1058]  # 84-byte active span
sum8  (sum & 0xff)      = 0x6d   (109)
sum16 (full sum)        = 109
xor8  (running xor)     = 0x67

No byte within the 84-byte span, nor the 4 bytes immediately preceding (0x1000–0x1003, still 0xFF/erased) or following (0x1058–0x105B, still 0xFF/erased), equals 0x6d, 0x67, or their one's/two's complements. No candidate stored checksum byte exists in this sample. Either: (a) the checksum (if any) covers a different range not captured in this 84-byte delta (e.g. a separate "directory" block elsewhere in the 8192-byte EEPROM that was not touched between the two captures and therefore invisible to the diff), or (b) this title does not checksum this particular record, relying solely on the hardware write-verify-retry in FUN_08084ed4 (§3.1) for integrity, or (c) a checksum exists but is computed over values not yet present (this may be a "new game, first save" record, see §5).

Confidence: UNKNOWN. No magic signature (ASCII or binary) was found either — ascii_magic_strings in the PACKET.md profile is empty, and no repeating binary tag (e.g. a 2–4 byte constant repeated across blocks) appears in the active span.

6. Save Fuzzing & Counterfactual Verification Plan

No .ss save states are present in this checkpoint cohort (states/ is empty), so the plan below is written to be executed once paired pre/post save states are captured for this title, per the standing paired-.ss requirement.

  1. Header/tag field test (0x1004–0x1007).
  • Mutation: flip to 00 00 00 00 and, separately, to FF FF FF FF.
  • Repair: none known (no checksum found, §4) — write back raw.
  • Predicted effect: if this is a record-presence/version tag, the game should treat the save as absent/corrupt and fall back to new-game on next boot; if it is inert data, no observable change. Capture gameplay.ss immediately after the title-screen "Continue" prompt renders to distinguish.
  1. Paired counter test (0x1023/0x102B last bytes).
  • Mutation: increment each independently (02→03), then both together, then set to FF.
  • Predicted effect: if these back a visible counter/stat, a specific on-screen number should change by a matching amount; if they're an enum/flag, expect either no visible change or a mode switch. Run as two separate single-byte mutations (not combined) to avoid conflating two fields.
  1. Zero-padding boundary test (0x1008–0x101F, 0x102C–0x1057).
  • Mutation: fill with 0x55 pattern.
  • Predicted effect: if truly unused padding, zero observable effect and the hardware write-verify-retry (FUN_08084ed4) will happily re-save it unchanged; if live fields currently at their default value, expect UI/behavior changes. This test is the most direct way to falsify the "padding" hypothesis in §5.
  1. Erased-region boundary probe (0x1058–0x105F, 0x0FFC–0x1003).
  • Mutation: write a distinctive non-0xFF marker just outside the currently-observed active span on both sides.
  • Predicted effect: if the true record boundary is wider than 84 bytes but was simply all-zero/unused in this particular capture, a future legitimate save should overwrite the marker; if the marker survives untouched across a fresh save, the true record boundary is narrower than assumed or located elsewhere.
  1. Protocol negative (hardware layer).
  • Corrupt a single bit in the just-written block before the title's own read-back verify would run (requires emulator-level MMIO hook on 0x0D000000), to confirm FUN_08084ed4's retry loop actually fires 3 times and that a persistently-failing write surfaces as a distinguishable in-game error state rather than silent data loss. This directly tests the one mechanism in §3.1 that is CONFIRMED_STATIC, elevating it toward CONFIRMED_VERIFIED.
  1. Multi-sample collection (prerequisite for everything above).
  • Capture at least 3–5 non-blank .sav snapshots differing in known, controlled ways (e.g. different match scores, different save slots if the menu offers more than one) with paired .ss states, specifically to break the current 1-real-sample limitation that makes every row in §5 a HYPOTHESIS.
