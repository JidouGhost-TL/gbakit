1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM (structural layout and media type are byte-exact HIGH confidence; checksum algorithm is code-proven but numerically under-determined by this single all-zero sample; per-field gameplay semantics inside each save slot are UNKNOWN — no non-blank sample exists in this workspace).

Proven (verified against both decompiled C and the actual .sav bytes):

  • The save image is a flat SRAM image, not Flash or EEPROM (no 0x5555/0x2AAA Flash command

sequences, no EEPROM/DMA3 bitstream code anywhere in the 253-function corpus).

  • A 16-byte global header beginning with the ASCII magic "DRACULA AGB" (11 bytes) followed by 5 padding

bytes, located at file offset 0x0000.

  • Eight fixed-size save "slots" of 0x3D0 (976) bytes each, placed contiguously starting at file offset

0x0010, for a total active region of 0x10 + 8*0x3D0 = 0x1E90 (7824) bytes. This arithmetic reproduces the corpus-reported active range (0x0000–0x1E8F, 7824 bytes) exactly, byte for byte.

  • Every byte at file offset 0x1E90 and beyond in the sample is 0xFF (SRAM erase/fill value), confirming

the remaining 32768 - 0x1E90 = 5168 bytes of the 32 KiB (256 Kbit) SRAM chip are untouched.

  • Each 976-byte slot reserves a single checksum byte at local offset +9 (i.e. file offsets 0x0019,

0x03E9, 0x07B9, 0x0B89, 0x0F59, 0x1329, 0x16F9, 0x1AC9), computed by an 8-bit additive "sum-excluding-self" routine.

Open (not provable from this workspace):

  • The semantic purpose of the 8 slots (distinct in-game save files vs. internal redundancy/wear copies vs.

per-area records) — the only sample available is a freshly-initialized, all-zero save, so no slot ever diverges from any other slot.

  • The exact length of the checksum coverage range (_DAT_080104bc, a ROM data constant not captured in

this decompilation dump) and the layout of in-slot gameplay fields (HP, position, inventory, etc.).

  • The exact 16-byte expected-header comparison constants used by the mismatch test in 0x08010158.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Methodology note (important, affects confidence throughout this section)

ghidra/callgraph.json reports empty callers and callees arrays for every function in the save subsystem described below (0x08010158, 0x08010250, 0x0801026c, 0x08010320, 0x08010490, 0x080c2f88, 0x080c3060, 0x080c3100), even though ghidra/decompiled.c plainly shows these functions calling each other. Every one of these functions ends its body with the pattern:

/* WARNING: Could not recover jumptable at 0x0xxxxxxx. Too many branches */
/* WARNING: Treating indirect jump as call */
(*UNRECOVERED_JUMPTABLE)();

This is the most likely explanation for the missing callgraph edges: these routines are reached through an indirect/tail-call dispatch (a jump table or task-trampoline) that Ghidra's static analysis could not resolve into a direct BL, and the trace-derived direct-calls.json runtime overlay evidently did not observe this code path being exercised either (the capture for this release contains no paired .ss states — states/ is empty for this cohort — so there is no runtime trace to confirm the real top-level caller).

Consequently, all caller/callee relationships below were mapped manually, by literal cross-referencing of func_0x########(...) / FUN_########(...) call-site text and address labels inside ghidra/decompiled.c — not by trusting ghidra/callgraph.json edges, which are empty for this entire subsystem. This is explicitly flagged per function below.

3.2 Seed candidates evaluated and ruled out

ghidra/save_related_functions.c flagged 0x08005e80, 0x08007b3c, 0x08010158, 0x08016238, 0x0806a7ac, 0x0806bcd8, and 0x080c36e4 as "MMIO-seed" or 2-hop candidates. A full-corpus search of ghidra/decompiled.c for GBA save/cart-I/O markers (0xe000000/0x0e000000 SRAM base, 0xd000000 EEPROM base, DMA3 control 0x040000d4, Flash unlock bytes 0x5555/0x2aaa, WAITCNT 0x04000204) found exactly one hit, inside 0x08010158 (*_DAT_080101f0 = 0xe000000;). The other six seeds (0x08005e80 jump-table dispatch over a sprite/OAM-like list, 0x08007b3c a small lookup-table read, 0x08016238 a spatial proximity/collision scan over linked actor records, 0x0806a7ac a 2-argument event-dispatch trampoline, 0x0806bcd8 a large state machine resembling enemy-AI / room-transition logic, 0x080c36e4 a signed 32-bit division routine) contain no SRAM/Flash/EEPROM address literals and are therefore classified UNKNOWN / not save-related — they are retained here only to document that they were checked and excluded, per the clean-room honesty requirement.

3.3 Function-by-function trace

0x08010158 — Header check & full-save (re)initialization orchestrator (role: write entry point / repair)

  • Sets a global pointer to the literal SRAM base address: *_DAT_080101f0 = 0xe000000;.
  • Calls 0x08010250() to read the current 16-byte header out of SRAM into a RAM scratch buffer.
  • Compares 3 fields of the header-in-RAM (*_DAT_080101f4, _DAT_080101f4[1], masked _DAT_080101f4[2])

against three "expected" constants (_DAT_080101f8, iRam080101fc, uRam08010200/uRam08010204).

The literal values of these expected constants are ROM data-section bytes not present in this decompilation dump — the exact expected header bitpattern cannot be stated, only that a mismatch triggers the branch below.

  • On mismatch, it writes the literal ASCII bytes 44 52 41 43 55 4c 41 20 41 47 42 ("DRACULA AGB",

11 bytes) one byte at a time into the header buffer, calls 0x0801026c() (header write+verify), then loops uVar3 from 0 to 7 calling 0x08010320(uVar3) once per slot — i.e. re-initializing the entire 16-byte header plus all 8 save slots whenever the header fails its sanity check.

  • How mapped: direct text read of the function body in ghidra/decompiled.c lines ~3235–3280; callgraph

edge absent (see §3.1).

  • RAM struct mutated: the header RAM mirror at _DAT_080101f4 (bytes 0–10 set to the magic string).

0x08010250 — Header read helper (role: read)

  • Single statement: func_0x080c2f88(*_DAT_08010264, _DAT_08010268, 0x10); — reads/transfers exactly 16

bytes, matching the header size established in §2.

  • How mapped: text search for the only caller of this exact 0x10-length transfer, 0x08010158.

0x0801026c — Header write+verify retry loop (role: write / checksum-adjacent integrity loop)

  • Runs for (uVar4 = 0; uVar4 < 10; uVar4++) { FUN_080c3060(write); if (FUN_080c3100(verify) == 0) break; }

— writes the 16-byte header buffer to SRAM and immediately reads it back for comparison, retrying up to 10 times until the verify call reports success (0).

  • Mutates a fallback/failure RAM flag (piRam080102e8 family) only if all 10 attempts fail.
  • How mapped: sole caller found by text search is 0x08010158.

0x08010320(param_1 = slot_index 0..7) — Per-slot checksum + write + verify (role: serialize / checksum / write)

  • Computes iVar6 = *_DAT_08010364 + (param_1 & 0xff) * 0x3d0 + 0x10; — the SRAM-mirror address of slot

param_1.

  • Calls 0x08010490(puVar8) to compute the slot's checksum byte and stores the result at local offset +9

of the slot buffer ((&stack0xfffffff9)[iVar1] = uVar3;).

  • Runs the same write+verify retry pattern as 0x0801026c, but with length 0x3d0 (976 bytes) instead of

16: for (uVar5 = 0; uVar5 < 10; uVar5++) { FUN_080c3060(write, 0x3d0); if (FUN_080c3100(verify, 0x3d0)==0) break; }.

  • How mapped: sole caller found by text search is the 8-iteration loop inside 0x08010158.
  • RAM struct mutated: slot buffer bytes [0..0x3cf] of slot param_1, specifically byte +9 (checksum).

0x08010490 — Checksum computation (role: checksum)

cVar1 = 0;
for (uVar2 = 0; uVar2 <= _DAT_080104bc; uVar2++) cVar1 += *(char *)(param_1 + uVar2);
return cVar1 - *(char *)(param_1 + 9);
  • Sums bytes [0.._DAT_080104bc] (inclusive; upper bound is an uncaptured ROM data constant — **UNKNOWN

exact length) of the slot buffer, including whatever stale value currently sits at byte +9, then subtracts that same byte back out. The net effect: the returned value is the 8-bit sum of every byte in the covered range except** byte +9, regardless of what was previously stored there — a standard "additive checksum with self-exclusion" construction. The caller (0x08010320) stores this result at byte +9.

  • How mapped: sole caller found by text search is 0x08010320.

0x080c3060 — Raw byte-wise copy primitive (role: write, low-level I/O driver)

*_DAT_080c3094 = *_DAT_080c3094 & (ushort)_DAT_080c3098 | 3;   // IRQ-mask-style guard, 2-bit set
while (iStack_c-- != -1) *puStack_10++ = *puStack_14++;         // plain 1-byte-at-a-time copy
  • This is the actual hardware I/O driver for SRAM: a byte-granular copy loop (no 16/32-bit accesses),

exactly as required because GBA SRAM only supports 8-bit bus transactions. Used for both the 16-byte header write (0x0801026c) and the 976-byte slot write (0x08010320).

  • How mapped: both callers found by text search (0x0801026c, 0x08010320); no callgraph edge recorded.

0x080c3100 — Raw byte-wise verify/compare wrapper (role: read / integrity check)

  • Same IRQ-guard pattern as 0x080c3060, then delegates to the opaque, non-decompiled routine

0x080c31e8(param_1, param_2, param_3, iStack_10) and returns its result (0 presumably = match, matching the if (iVar4 == 0) break; success condition seen in both 0x0801026c and 0x08010320).

  • How mapped: both callers found by text search (0x0801026c, 0x08010320); no callgraph edge recorded.

0x080c31e8 — Opaque low-level transfer/compare primitive (role: unknown, likely final read-back/compare)

  • Ghidra could not decompile a body for this address in this dump (UNRECOVERED_JUMPTABLE stub only). Its

exact semantics (byte compare vs. re-copy vs. BIOS call) are UNKNOWN; only its call signature and position in the retry loop are provable.

4.2 Checksum algorithm

  • Algorithm: custom 8-bit additive "sum excluding self" (not CRC, not XOR, not two's-complement sum).
  • Formula: stored_byte[+9] = (Σ byte[i] for i in [0, N]) mod 256, where the sum in the decompiled code

literally includes the stale byte at +9 and then subtracts it back out (net: sum of all other bytes in range [0, N]). N = _DAT_080104bc, a ROM constant not captured in this decompilation dump (exact value UNKNOWN).

  • Stored offset: local slot offset +9 (one checksum byte per 976-byte slot; 8 independent checksums,

no header-level or whole-file checksum was found).

  • Endianness: N/A — single byte.
  • Decompiled C proof: 0x08010490 (quoted in full in §3.3) plus its only caller 0x08010320.

4.3 Python verification against the real .sav file

Only one .sav sample exists in this workspace, and its slot bodies are entirely zero-filled (a freshly initialized, never-played save). This makes the checksum trivially satisfied for any candidate value of N (the sum of an all-zero range is 0 regardless of range length), so this sample can verify the location and resting value of the checksum byte, but cannot distinguish the exact coverage length N. This limitation is stated explicitly rather than concealed.

$ python3 - <<'EOF'
data = open('saves/cap-00-future-0.sav','rb').read()
for i in range(8):
    slot_start = 0x10 + i*0x3d0
    chk_off = slot_start + 9
    slot_body = data[slot_start:slot_start+0x3d0]
    computed = (sum(slot_body) - slot_body[9]) & 0xff   # sum over whole slot, excluding byte+9
    stored   = data[chk_off]
    print(f"slot {i}: stored=0x{stored:02x} computed(any N<=0x3cf)=0x{computed:02x} match={stored==computed}")
EOF
