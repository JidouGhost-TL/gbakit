Release key: AP8P-r0-041d521127619163 · ROM SHA-256: 041d5211276191639362c024d6e4037e9007c30be38ca5570a8be4dc6aeac579

All findings below are derived exclusively from this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and standard public GBA hardware facts (EEPROM bus at 0x0D000000 via DMA3 0x040000D4, SRAM/Flash at 0x0E000000, EWRAM 0x02000000, IWRAM 0x03000000). 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_VERIFIED — code and raw .sav bytes agree):

  • Save media is EEPROM 4K (512 bytes), driven by the classic GBA bit-serial EEPROM protocol over the DMA3 bus (0x0D000000/0x040000D4).
  • The raw .sav file stores each 8-byte (64-bit) EEPROM sector in byte-reversed order relative to the in-RAM/CPU byte order. Reversing any 8-byte sector's bytes recovers the true in-RAM content. This was verified directly: reversing file bytes 00 00 64 65 73 75 6e 55 yields the ASCII string "Unused\0\0".
  • A 3-slot save-select structure exists: 3× 8-byte header sectors (file offsets 0x00, 0x08, 0x10) followed by 3× 160-byte body regions (file offsets 0x18, 0xB8, 0x158).
  • The first byte of each body (after un-reversing), found at file offsets 0x1F, 0xBF, 0x15F, is a slot status marker: 0xD8 = "slot empty/uninitialized" (the value every slot in our sample holds); the boot-time scan code treats 0x27 as "slot has data".
  • A large fraction of each 160-byte body (bytes 40–159 of the 160-byte buffer) is not written from meaningful save data — it is uninitialized/leftover stack content, because the initializer function allocates only a 40-byte local buffer but instructs the write routine to flush 160 bytes. This was confirmed both in the decompiled C (buffer size vs. write length mismatch) and in the raw bytes (the leftover region is byte-identical across all three slots, as expected for stale stack content captured by the same call site on three successive loop iterations).

Open / not yet proven:

  • Whether any checksum/CRC protects the save data. Exhaustive per-sector and per-block sum8/xor8/complement tests against the only "odd" trailer bytes we found (0x41, 0x5A, 0x73, 0xD8) did not produce a reliable, cross-slot-consistent formula (see §4). The low-level "verify" step (FUN_08032edc) is a write-confirmation read-back, not a payload checksum. We have no evidence of a payload checksum anywhere in the traced code; this is treated as UNKNOWN, not disproven.
  • Semantics of nearly every body field beyond the status-marker byte — we only have two samples, both representing an empty/freshly-initialized state (cap-00: EEPROM in erased 0xFF state before first boot; cap-01: all-3-slots-blank-initialized state after first boot), no sample of actual gameplay data exists in this workspace.
  • Resolution of most _DAT_* global pointers to concrete absolute RAM/ROM addresses (the Ghidra output leaves them as unresolved globals), so exact RAM mirror addresses for the save struct are UNKNOWN.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K, 512 bytes total, addressed as 64 sectors × 8 bytes (6-bit sector address), matching GBA's standard EEPROM bus protocol (serial DMA3 bitstream to/from 0x0D000000, command codes 0x2 (read) / 0x3 (write) framed with start/stop bits — see §3).
  • Background fill: cap-00-future-0.sav is uniformly 0xFF — the EEPROM-erased state, present before the game ever writes to it.
  • Slot layout (all offsets are file offsets; the body of this report distinguishes file-byte-order from CPU-byte-order per §3):

  • Redundancy: No mirrored/backup copy was found — each of the 3 "slots" is an independent save-game record (classic multi-save-file selection), not a redundant copy of the same data. There is no evidence of a separate checksum/generation-counter slot distinct from the per-slot header+body pair.
  • Generation/sequence counters: CONFIRMED_STATIC only — see field map row for offset 0xE9/0x189 (a monotonically-stepping byte: 0x00, 0x04, 0x08 across slots 0/1/2) which looks structurally like a per-slot index/sequence tag baked in at init time rather than a live save-generation counter; no live mutation was observed (we have no "before vs after a real save" pair).
  • Selection rule: FUN_080281d8 (see §3) iterates slot indices 0..2 at boot, reading the first body byte of each slot; a slot is presented as "has data" only if that byte equals 0x27; otherwise the slot is (re)written blank via FUN_08022680. No explicit "most-recent slot wins" logic was observed — selection is presentation-only (menu flags), not an active/backup failover scheme.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Hardware I/O driver layer (bit-serial EEPROM over DMA3)

  • 0x08032cd0 — DmaXfer(src, dst, ctrl): Generic DMA3 transfer primitive. Disables then restores an interrupt-mask-like flag (_DAT_08032d30), programs DMA3 source/dest/control registers (the param_3 | 0x80000000 pattern is the DMA "enable" bit), then busy-waits on bit 15 of the control word (DMA busy flag) before returning. This is the common low-level primitive used by both read and write paths.
  • 0x08032d50 — EepromReadSector(sector, dst[4 x u16]) [MMIO seed]: Builds a read-request bitstream (sector address shifted into a stack bit-array), issues it via DmaXfer with destination 0xD000000 (EEPROM bus) and a command-length of "address-bits + 3", then issues a second DmaXfer from 0xD000000 reading back 0x44 (68) bits, and unpacks the 4×16-bit words of sector data out of the returned bitstream. This is the classic "EEPROM READ" bit-serial command.
  • 0x08032e00 — EepromWriteSector(sector, src[4 x u16]) [MMIO seed]: Same pattern but assembles a write bitstream (2-bit write opcode + 6-bit sector address + 64 data bits), and after programming the output DMA (DmaXfer(..., 0xD000000, len+0x43)), it calls 0x08032c04 then polls uRam0d000000 & 1 (classic "EEPROM busy" ready-bit poll) before calling 0x08032c8c. This is the classic "EEPROM WRITE" command sequence.
  • 0x08032c04 / 0x08032c8c: Small wrapper pair bracketing the write's busy-poll; from the field writes (*_DAT_08032c84 = 0, flag toggling) these look like an interrupt-mask save/restore or a "busy flag" set/clear pair around the hardware wait-loop, not checksum logic.
  • 0x08032edc — EepromReadVerify(sector, expected[4 x u16]): Calls EepromReadSector into a local 4×u16 buffer, then compares word-by-word against expected; returns 0 on an exact match, 0x8000 on mismatch. This is a write-confirmation read-back, not a data-integrity checksum — it only ever compares the just-written bytes against themselves.

All four of these are confirmed by the call-graph (ghidra/callgraph.json) to only call each other (08032d50→08032cd0, 08032e00→{08032c04,08032c8c,08032cd0}, 08032edc→08032d50), and have no traced callers inside the 292-function decompilation set — their only observed callers are the func_0x08032xxxx(...) call sites inside ghidra/decompiled.c that the Ghidra pass could not attribute back through its own call-graph builder (indirect/THUMB-interworking calls). We located those real callers manually by text search (§3.2).

3.2 Mid-level sector-block read/write (the actual save API)

Found by grepping ghidra/decompiled.c for literal func_0x08032d50/e00/edc call sites (lines 3540–3607), since the auto-generated call-graph missed these indirect calls:

  • 0x0800df48 — ReadEepromBlock(startSector, buf, len): Loops over len bytes 8 at a time, calling EepromReadSector directly into the caller's buffer, then EepromReadVerify against what was just read (a defensive double-read, not a checksum), advancing the sector index each iteration. Handles a non-multiple-of-8 tail via an 8-byte stack scratch buffer.
  • 0x0800dfb8 — WriteEepromBlock(startSector, buf, len): Same loop shape but calls EepromWriteSector then EepromReadVerify for each 8-byte chunk (write-then-confirm), with the same tail-handling via an 8-byte scratch buffer merged from old+new data for partial trailing sectors.
  • 0x0800deb8(handle) / 0x0800defc(handle): Bracket every block read/write call pair we found (see call sites below). From the field pattern (*_DAT_...def0 |= 1 on entry, &= 0xfe on exit, plus a func_0x08011b50/68/0801216c pair) these behave as an acquire/release "save-system busy" lock — most likely guarding against reentrant EEPROM access (e.g., during VBlank) rather than doing any data transformation.

Both 0x0800df48 and 0x0800dfb8 are CONFIRMED_STATIC save I/O primitives (hardware-fact-grounded): they are the only functions in the decompiled set that drive the EEPROM sector read/write seeds directly, and their sector-stepping loop structure exactly matches EEPROM-4K's 8-byte sector geometry.

3.3 Game-level callers (how the in-RAM save struct gets flushed)

Traced via ghidra/callgraph.json callers of 0x0800df48 / 0x0800dfb8:

  • 0x08022680 — InitBlankSaveSlot(slotIndex) (callee of 0x080281d8 only):
  1. Calls FUN_0800deb8 (acquire save lock).
  2. Zeroes a 40-byte local stack buffer (undefined4 auStack_48[10]), then sets byte 0 of that buffer to 0xD8 — this is the literal origin of the "slot empty" marker.
  3. Copies an 8-byte global template (*_DAT_080226f8) into a second local buffer.
  4. Calls WriteEepromBlock(slotIndex*20 + 3, auStack_48, 0xA0) — writes the 160-byte body, even though only the first 40 bytes of auStack_48 were ever initialized. Bytes 40–159 of every freshly-initialized body are therefore whatever happened to be on the stack at that call site (verified: those bytes are byte-identical across slots 0/1/2 in cap-01-future-1.sav, which is exactly what stale-stack reuse across three successive loop iterations of the same call site would produce).
  5. Calls WriteEepromBlock(slotIndex, auStack_20, 8) — writes the 8-byte header, containing the template copied in step 3 (observed as "Unused" once un-reversed).
  6. Calls FUN_0800defc (release save lock).
  • 0x080281d8 — ScanAndInitSaveSlots(), called once by 0x08029098 (a title/boot-flow function): loops slot = 0..2:
  • Reads the slot's first body word via ReadEepromBlock(slot*20+3, ...).
  • If that word's low byte == 0x27 → marks the slot "has data" (flag=1) for the save-select UI.
  • Else if that low byte != 0xD8 → calls InitBlankSaveSlot(slot) (i.e., anything that isn't already the recognized "empty" sentinel gets stomped back to blank — a self-healing/format-on-corruption behavior).
  • Else (byte == 0xD8) → leaves the slot alone, flag =0 ("no data").
  • Also reads the 8-byte header via ReadEepromBlock(slot, ...) into a per-slot RAM record and renders save-select menu text/icons for that slot (FUN_08009244 calls with string-table indices 0x14, 0x28, 0xB4).
  • This is how every RAM mutation we can prove is driven: the only confirmed write trigger in this workspace is the boot-time slot-scan/auto-format path, not an in-gameplay "Save Game" menu action (no such caller was found pointing at 0x0800dfb8/0x08022680 other than this one).
  • 0x08028364 — ReadSlotHeaderAndCompare(sector, namePtr): Reads one 8-byte header via ReadEepromBlock and compares it against namePtr using FUN_08034adc, a generic word-optimized strcmp/memcmp (confirmed by its code shape — no save-specific logic). Used to check whether a slot's stored name matches an expected string; not a checksum routine. This function currently has no traced caller in the call-graph.
