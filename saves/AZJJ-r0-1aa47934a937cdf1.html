  • Release key: AZJJ-r0-1aa47934a937cdf1
  • Game code / header family: AZJJ / AZJ
  • ROM SHA-256: 1aa47934a937cdf13b2536ad35d391262202d53f8797db11335fc43f12374596
  • Workspace inputs: saves/cap-00-future-0.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (110 functions), ghidra/callgraph.json, ghidra/save_related_functions.c

All findings below are derived exclusively from the bytes of saves/cap-00-future-0.sav and the trace-guided decompilation in ghidra/. No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: LOW–MEDIUM.

What is proven (code + bytes agree):

  • The title uses a 512-byte (4Kbit) EEPROM, accessed through a classic GBA EEPROM bit-serial driver that performs its I/O via DMA3 to 0x0D000000.
  • The EEPROM is organized into 64 addressable 8-byte blocks; the driver reads the configured address width from a runtime config struct rather than hard-coding it.
  • Only the first 14 of 64 blocks (bytes 0x00–0x6F) are non-blank in the captured sample; blocks 14–63 (bytes 0x70–0x1FF) are untouched EEPROM fill (0xFF).

What remains open / unverified:

  • No caller of the EEPROM write or read entry points exists anywhere in the 110-function decompiled set or callgraph.json. The actual save-manager code that fills the 8-byte block buffers, decides when to save, and (if present) computes any checksum was not captured by this trace and is completely absent from this workspace.
  • Because of that gap, every interpretation of the block-0 "magic" bytes, the block-1 header fields, and the ten 8-byte "record" blocks is a byte-pattern HYPOTHESIS, not a code-verified fact.
  • An exhaustive brute-force search (sum8/16, xor8/16, crc32 over nine plausible byte ranges) found no checksum algorithm that reproduces any 16- or 32-bit value sitting in the header. The integrity/checksum mechanism, if any, is UNKNOWN.
  • Only one .sav sample exists in this workspace (saves/ contains a single binary, despite the packet metadata mentioning six total captures elsewhere in the corpus), and states/ is empty for this checkpoint cohort. Without a second differing sample or paired .ss save states, field semantics and checksum formulas cannot be empirically confirmed from this workspace alone.

Slot / redundancy structure (HYPOTHESIS): Blocks 2–6 (0x10–0x37) and blocks 7–11 (0x38–0x5F) each hold five 8-byte entries whose first 7 bytes are byte-for-byte identical pairwise (block2≡block7, block3≡block8, block4≡block9, block5≡block10, block6≡block11); only the 8th byte of each entry differs. This is consistent with a dual-copy / generation-stamped redundancy scheme common to EEPROM save systems (write the same logical record twice with an incrementing tag byte so a power-loss mid-write can be detected), but:

  • No selection-rule code was found (no caller reads/compares the two copies).
  • The trailing tag byte sequence across blocks 2–11, in address order, is 00,04,08,09,0c,10,14,18,1c,20 — mostly +4 increments but with one irregular +1/+3 step at blocks 5–6. This is not a clean arithmetic counter, so the "generation counter" reading is only a plausible guess, not a confirmed mechanism.

Blocks 12 (0x60) and 13 (0x68) do not match the 5-entry record pattern and are unclassified.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Hardware I/O driver (confirmed by code)

FUN_080492b4 (0x080492b4) — raw DMA3 transfer primitive

  • Signature: void FUN_080492b4(src, dst, count_with_flag)
  • Disables/restores IME, sets DMA3 source/dest/count registers, sets bit 0x80000000 (DMA enable) on the count register, then busy-polls the DMA channel's control-register high half until bit 0x8000 (busy) clears.
  • This is the generic "kick a DMA3 transfer and wait" primitive used by both the EEPROM read and write routines below. It is standard GBA hardware I/O (DMA3 is the mandated channel for EEPROM serial access), not game-specific.
  • Callers (from callgraph.json): 0x08049334, 0x080493f8 — both confirmed by direct call-site inspection in decompiled.c lines 3934–3935 and 4026.

FUN_08049334 (0x08049334) — EEPROM block WRITE

  • Signature: void FUN_08049334(uint block_addr, int data_ptr)
  • Bounds-checks block_addr against a configured maximum (*(ushort*)(cfg+4)).
  • Serializes, MSB-first, into a bit buffer: a 2-bit write opcode (1,1), then N address bits (N = *(byte*)(cfg2+8), the configured address width), then 64 data bits taken from the caller's 8-byte buffer.
  • Calls FUN_080492b4 twice: once to DMA the command+address bitstream out to 0x0D000000, once more (0x44 = 68 half-words) to drive the serial clock, matching the documented GBA EEPROM write-cycle shape (2 start bits + address bits + 64 data bits + 1 stop bit).
  • Callers found: none. Neither callgraph.json nor any grep of decompiled.c shows a function that calls FUN_08049334. The real save-manager that assembles the 8-byte record and invokes this write was not part of the 110-function trace.

FUN_080493e4 (0x080493e4) — blocking EEPROM read wrapper

  • One line: FUN_080493f8(param_1, param_2, /*retry=*/1).
  • Callers found: none.

FUN_080493f8 (0x080493f8) — EEPROM block READ

  • Signature: void FUN_080493f8(uint block_addr, ushort *out_buf, char retry_forever)
  • Builds a 2-bit read opcode (0,1) + address bits, DMAs the request out via FUN_080492b4, then polls the EEPROM-ready line at 0x0D000000 (bit 0) with a software timeout (accumulates elapsed ticks and gives up past 0x88), retrying the whole wait loop if retry_forever is set and the timeout elapsed.
  • Returns 0 on success, or an error code (uRam08049520) on timeout when not retrying forever.
  • Callers found: none (FUN_080493e4 calls it, but nothing calls FUN_080493e4 either).

3.2 Caller-chain gap (honest disclosure)

Both the write path (FUN_08049334 ← ??) and the read path (FUN_080493e4/FUN_080493f8 ← ??) are dead ends in this workspace: callgraph.json lists "callers": [] for all three entry points, and no indirect/jump-table reference to their addresses appears anywhere in decompiled.c. This means:

  • We cannot show which RAM struct (0x02xxxxxx EWRAM or 0x03xxxxxx IWRAM) is serialized into each 8-byte block.
  • We cannot show when a save is triggered (menu save, auto-save, pause-save, etc.).
  • We cannot show whether a checksum is computed before the write or validated after the read, because the function that would do so is not in this decompiled set.

This is the single largest gap in this analysis and should be the top priority for a follow-up trace/decompilation pass (capture a save-triggering playthrough segment specifically).

3.3 Other functions inspected and ruled out

ghidra/save_related_functions.c flagged 0x0804a3f0 as an [MMIO-SEED] candidate alongside the two real EEPROM functions. Inspection of its full decompilation (lines 4195–4241 of decompiled.c) shows it is a generic unsigned 32-bit division routine (restoring-division shift/subtract loop calling func_0x080496c0 on divide-by-zero) with zero MMIO or hardware-register references. This is a false positive in the seed-selection heuristic and is explicitly excluded from the save architecture below. Two sibling division routines, FUN_0804962c (signed division) and FUN_08049fcc (unsigned division), are the same compiler-runtime pattern and are likewise unrelated to saving.

FUN_08049220, FUN_08049224, FUN_0804923c, FUN_08049240, FUN_08049244, FUN_08049248 are one-line GBA BIOS software_interrupt() wrappers (SWI 0x0C CpuFastSet, 0x0B CpuSet, 0x12 LZ77UnCompVram, 0x11 LZ77UnCompWram, 0x01 RegisterRamReset, 0x05 VBlankIntrWait). These are standard runtime-library stubs, not save-specific, and are listed here only for completeness/noise disclosure.

FUN_0804926c (0x0804926c) branches on a selector value (4, 0x40, else) and wires one of three function-pointer globals (*_DAT_08049280, *puRam08049294, *puRam080492ac). This shape matches a save-media driver dispatcher (SRAM vs. EEPROM vs. Flash installer), which would explain how FUN_08049334/FUN_080493f8's config-pointer dereferences (cfg+4, cfg+8) get populated at boot — but no code or byte evidence ties the specific values 4/0x40 to "EEPROM", so this remains an open hypothesis, not a finding.

4.2 Header field at 0x08

Bytes 0x08–0x0B = 00 10 00 00. Interpreted little-endian 32-bit: 0x00001000 = 4096. This equals the EEPROM's capacity in bits (4Kbit = 4096 bits = 512 bytes), which is suggestive of a self-describing "device/format tag" written once at save-file creation — but this is pattern-matching, not code-proven.

4.3 Checksum / integrity algorithm — UNKNOWN

Bytes 0x0C–0x0F = 90 9b 09 9b are the only remaining candidate "integrity-looking" field (two u16-sized sub-values, 0x9b90 and 0x9b09 little-endian). 6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist for this legacy checkpoint cohort (states/ is empty per the packet). All plans below are untested hypotheses pending a capture run that supplies the mandatory pre/post save-state pairs; each entry specifies the mutation, whether a checksum repair step is needed (unknown — no formula was confirmed), and the observable prediction.

  1. Offset 0x00, 1 byte — flip 0x34→0x35 in the magic. No checksum repair known. Prediction: if the loader validates this literal, reload should fall back to a blank/default save (reverted_to_blank_boot=true); if unchanged bytes still load normally, the magic is not validated at boot and is purely incidental/decorative.
  2. Offset 0x08, 4 bytes — change 00 10 00 00 (4096) to 00 00 00 00. Prediction: tests whether this is a hard device/format validation constant; a mismatch should either be ignored or force reinitialization.
  3. Offset 0x0C, 4 bytes — flip all bits of 90 9b 09 9b. Prediction: since no checksum formula was confirmed (§4.3), this tests whether the field is checked at all — if the save still loads cleanly with visual_delta_on_load=true unchanged, it is inert data, not a checksum.
  4. Offset 0x12, 2 bytes — change record A0's big value field a1 20 to 00 00. Prediction: if this value is rendered in-game (e.g., a displayed statistic tied to record A0), the on-screen value should visibly change; if gameplay is unaffected, the field is unused/reserved.
  5. Offset 0x38, 8 bytes — zero out the entire B0 record (duplicate of A0 at 0x10). Prediction: if dual-copy redundancy is real, the game should silently recover using the still-intact A0 copy; if the save is instead flagged corrupt, the "copies" are not functioning as independent redundancy.
  6. Offset 0x60, 8 bytes — mutate bytes 2–3 (01 2c) of the unclassified block 12 record. Prediction: observe for any UI/gameplay change to determine this block's role, since it has no twin to compare against.
  7. Offset 0x70, 16 bytes — write non-0xFF garbage into the first currently-blank block (block 14). Prediction: if the game only ever touches blocks 0–13, no effect should be observed; if additional save slots exist but are simply unused in this sample, this may surface as new in-game state or corruption, which would reveal unused save capacity.

Each mutation should be applied to a copy of saves/cap-00-future-0.sav, reloaded from a fresh emulator boot, and compared frame-by-frame against the unmodified baseline using the same cold-reload/checksum-probe methodology already used to produce the packet's Cold-Reload / Checksum Probe metadata, so that save_preserved_on_load, visual_delta_on_load, and reverted_to_blank_boot can be re-measured per mutation.
