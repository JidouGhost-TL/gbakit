1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The title uses EEPROM save media accessed exclusively through the GBA DMA3 serial EEPROM protocol at 0x0D000000 / 0x040000D4. No SRAM (0x0E000000) or Flash (0x5555/0x2AAA command-sequence) code paths exist anywhere in the 154 traced functions.
  • The EEPROM is organized as 4 fixed-size 128-byte slots (16× 8-byte EEPROM blocks each), which sum exactly to the reported 512-byte (4K/"EEPROM 4K") device size.
  • A complete driver → mid-level → high-level call chain for both read and write was traced via ghidra/callgraph.json from the raw DMA3 bit-shifter up to two top-level entry points (FUN_0801fdf0 = load-all, FUN_0801fb74 = save/tick).
  • A sum16 checksum with a secondary 32-bit "magic/version" gate protects the per-slot contents (offsets 0x02–0x7F), proven directly from the decompiled validator FUN_0801f9e4.
  • Against the one non-blank .sav sample (cap-01-future-1.sav), the checksum stored at offset 0x00 is self-consistent with the sum of bytes 0x02–0x7F under the formula derived from the code, once an additive seed constant is solved for (Python-verified below).

What remains open (explicitly not claimed as proven):

  • The exact numeric value of the checksum seed constant (_DAT_0801fa9c) and the "magic" mask/expected-value pair (_DAT_0801faa0/_DAT_0801faa4) are not resolvable from this trace-limited decompilation — they live in ROM .data that was not included in the packet. We solved the seed algebraically from the one real sample (0x8BF1) but could not cross-validate it against a second independent non-blank sample, since the only other .sav (cap-00-future-0.sav) is fully blank (0xFF×512).
  • The write-side checksum routine (FUN_0801fb74) uses a different, hard-coded seed literal (0x13) over the same byte range. Reconciling the write-side and read-side seed constants algebraically implies a different relationship than the one solved from real data; this discrepancy is flagged as an open question, not resolved by invention.
  • The precise gameplay semantics of individual bytes inside each 128-byte slot (high-score fields, player initials, option flags, etc.) are hypotheses based on byte-pattern/ASCII observation only, not on any symbol or label.
  • RAM mirror addresses (0x02xxxxxx/0x03xxxxxx) for the save buffer are unknown — all buffer-base pointers (_DAT_0801fa90, _DAT_0801f7e8, etc.) are themselves ROM-resident pointer variables whose resolved runtime values are not present in this trace-guided decompilation.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Algorithm (from FUN_0801f9e4, decompiled.c lines 4015–4058)

For a given slot buffer S (128 bytes, base = *_DAT_0801fa90 + table[slot] + _DAT_0801fa98):

  • Checksum field: u16 little-endian at S[0x00:0x02].
  • Covered range: S[0x02:0x80] (126 bytes) — summed as unsigned bytes, truncated to 16 bits after every addition (equivalent to a plain mod-65536 running sum).
  • Read-side validation formula:
  valid_checksum := sum16(S[0x02:0x80]) == (u16_le(S[0x00:0x02]) + SEED_R) & 0xFFFF

where SEED_R = _DAT_0801fa9c, a ROM-resident constant not resolvable from this trace-limited decompilation.

  • Secondary "magic"/version gate: u32_le(S[0x2C:0x30]) & MASK == EXPECTED, where MASK = _DAT_0801faa0 and EXPECTED = _DAT_0801faa4 (both unresolved constants). Both the checksum test and the magic test must pass (they're OR'd in the failure condition: checksum_bad || magic_bad ⇒ reset).
  • Reset-to-default behavior (on either check failing): zero S[0x02:0x80] (126 bytes), then set:
  • S[0x2D] = 0x6B ('k')
  • S[0x2E] = 0x6D ('m')
  • S[0x2F] = 0x63 ('c')
  • S[0x00:0x02] = u16_le(S[0x2D] + S[0x2E] + 0x76) = u16_le(0x14E) = bytes 4E 01.

Note: the default-path checksum write uses a different, simplified formula (S[0x2D] + S[0x2E] + 0x76) than the general read-side validation formula (sum16(S[0x02:0x80]) == stored + SEED_R). We verified algebraically that these two formulas do not reconcile with a single small constant: solving for SEED_R from the default-reset state gives sum16(default-reset buffer) - 0x14E = (0x6B+0x6D+0x63) - 0x14E = 0x13B - 0x14E = -0x13 ≡ 0xFFED, which does not match the SEED_R = 0x8BF1 solved from the real captured save (§4.2). This is flagged as an open question — either (a) the freshly-reset default record is expected to fail its own checksum again on the very next validation pass (a "self-healing idempotent reset" that simply keeps resetting until a real save occurs), or (b) the write-side literal 0x13 in FUN_0801fb74 and the default-path 0x76 constant serve different purposes than assumed here. We do not claim a resolution — this needs a .ss state capture immediately after a deliberate factory-reset trigger to settle (see §6).

blk = open('saves/cap-01-future-1.sav','rb').read()[:128]

6. Save Fuzzing & Counterfactual Verification Plan

All mutations assume starting from a copy of cap-01-future-1.sav loaded into a paired pre/post .ss state per the mandatory save-state policy. Every mutation that touches the checksum-covered range (0x02–0x7F) requires checksum repair to avoid simply exercising the reset-to-default path (which is also a valid, separate test case below).

Checksum repair script (for any mutation inside 0x02–0x7F, assuming SEED_R = 0x8BF1 holds):

def repair(blk: bytearray, seed=0x8bf1):
    new_sum = sum(blk[2:128]) & 0xffff
    stored = (new_sum - seed) & 0xffff
    blk[0] = stored & 0xff
    blk[1] = (stored >> 8) & 0xff
    return blk
