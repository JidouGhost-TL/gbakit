SAVE-FORMAT-REPORT — Koukou Juken Advance Series Eitango Hen - 2000 Words Shuuroku (Japan)

Release key A52J-r0-f6f06dd3e06b749b · Game code A52J · ROM SHA-256 f6f06dd3e06b749b0a3f47334c04e1f87a64b69ecadee8945173fbfb9b9083c4

Clean-room: every claim below derives only from saves/, ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, PACKET.md, and standard GBA hardware addresses. No third-party game data was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + bytes agreeing):

  • Save media is SRAM at 0x0E000000, 32,768 bytes (256K). Only two functions in the 57-function corpus touch 0x0E000000: FUN_08000484 writer and FUN_08000584 reader. SDK tag in PACKET.md: SRAM_V112.
  • No Flash command sequence (0x5555/0x2AAA), no EEPROM/DMA3 (0x0D000000, 0x040000D4) anywhere in the corpus. Search of ghidra/decompiled.c returned zero hits for those patterns.
  • The writer stamps a constant into dword 0 of the RAM struct before flushing, and the reader compares dword 0 against a constant after loading. The only non-zero dword in the populated save is e4 2b 51 6e at offset 0.
  • saves/cap-00-future-0.sav is fully erased (0xFF × 32,768). saves/cap-01-future-1.sav differs in exactly one contiguous span 0x0000–0x477F plus a 12-byte island at 0x4890–0x489B.

Open / not proven:

  • All _DAT_080005xx/_DAT_080006xx literal-pool values are unresolved symbolic names in the decompilation. The RAM struct base address, the exact copy length, and the exact magic constant were never read as numbers.
  • The payload 0x0004–0x477F is all 0x00 in the only populated sample. Its internal field layout is therefore unmapped.
  • No checksum routine was found, and no standard checksum matches the stored bytes. A checksum outside the traced corpus cannot be excluded.
  • Neither seed function has any caller in ghidra/callgraph.json or ghidra/decompiled.c. Trigger context is unknown.
  • states/ is empty. No reload or fuzz prediction has been executed.

Geometry derivation. Python diff of the two real files (script in §4):

diff ranges: [('0x0', '0x477f'), ('0x4890', '0x489b')] count 18316

The written span ends exactly at 0x4780. Both seed functions independently reference that offset in the RAM struct: the writer sets puVar2[1] = puVar1 + 0x11e0 (decompiled.c:34) and the reader sets puVar4 = (ushort *)(piVar1 + 0x11e0) (decompiled.c:79). piVar1/puVar1 are int *, so +0x11e0 words is +0x4780 bytes. That the flush length (_DAT_08000580 / _DAT_08000660) equals 0x4780 is an inference from the byte boundary plus this code reference — labelled HYPOTHESIS wherever it matters, because the literal length itself is unresolved.

The 12 zero bytes at 0x4890–0x489B sit inside otherwise untouched 0xFF SRAM. No traced function writes there. It is recorded as an anomaly, not as a slot: 12 bytes cannot be a copy of an 18 KB image, and there is no header, magic, or reader reference for it.

Redundancy verdict: single-copy save. If the one copy fails its dword-0 check, the reader initialises defaults in RAM (see §3). There is no fallback copy to select.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two sources were cross-checked, and they disagree — this is stated plainly:

  • ghidra/callgraph.json (57 keys) records no callers and no callees for either seed: "0x08000484": {"callers": [], "callees": []}, same for 0x08000584. Its only edges are in unrelated clusters (e.g. 0x08012a48 → 0x08010bac/0x08010c3c, the 0x08014xxx audio cluster).
  • ghidra/decompiled.c bodies use Ghidra's unresolved-call spelling func_0x080xxxxx, which a regex extraction ((?:func_|FUN_)(0x080[0-9a-f]+)) maps to the same addresses as the FUN_080xxxxx definitions. All chains below come from the bodies, not the callgraph.

Both seeds end in (*UNRECOVERED_JUMPTABLE)(...) — a tail dispatch Ghidra could not recover. They are reached from an unrecovered jump/state table. No entry caller exists in this corpus for either seed. Any menu/boot trigger named below is a hypothesis.

The remaining 50 functions were classified to prove they are not save code: 0x080109e4–0x08010d0c display/OAM setup (0x06000000, 0x05000000 writes), 0x08012a48 background setup, 0x08013374–0x08013438 text/script rendering, 0x080138f4–0x08015670 the M4A-style audio cluster (constants 0xB600, 0x96, 0x50-stride channel structs), 0x08015b38 SWI 0x0B (CpuSet), 0x08015b3c SWI 0x05 (VBlankIntrWait), 0x08015d14 integer division. None touches 0x0E000000.

3.3 Writer: FUN_08000484

Chain: FUN_08000484 → FUN_08014d90 → FUN_08015bcc → FUN_08015c3c → FUN_08014ddc → UNRECOVERED_JUMPTABLE(verify_result).

How it mutates the RAM struct before flushing (decompiled.c:15-45):

  1. func_0x08014d90() — pre-write helper (see §3.5 caveat).
  2. *puVar1 = _DAT_0800057c — stamps dword 0 of the struct (base puVar1 = _DAT_08000534) with a literal-pool constant. This is the magic write.
  3. *(base + _DAT_08000538) = *_DAT_0800053c and *(base + _DAT_08000540) = *_DAT_08000544 — two further field stores; numeric offsets unresolved.
  4. A series of stores through a second pointer puVar2 = _DAT_08000548 referencing base, base + _DAT_08000564, base + _DAT_08000564 + 0x3c, and base + 0x4780 (word 0x11e0). Whether puVar2 is part of the save struct or a separate descriptor list cannot be resolved.
  5. func_0x08015bcc(_DAT_08000534, 0xe000000, _DAT_08000580) — byte-copy RAM → SRAM.
  6. uVar4 = func_0x08015c3c(puVar1, 0xe000000, uVar4) — verify; result passed to the tail dispatch.
  7. func_0x08014ddc() — post-write helper.

3.4 Reader: FUN_08000584

Chain: FUN_08000584 → FUN_08015b68 → FUN_08015ce4, then tail dispatch.

How it mutates the RAM struct after loading (decompiled.c:69-120):

  1. func_0x08015b68(0xe000000, _DAT_0800065c, _DAT_08000660) — SRAM → RAM.
  2. if (*piVar1 != _DAT_08000664) — dword-0 validity check. On mismatch (fresh/corrupt): a 68-iteration loop (iVar6 = 0x43 down to 0) ORs _DAT_08000670 into u16 entries at RAM+0x4780 and at RAM+_DAT_08000674 — default flag arrays. Note 0x4780 is exactly the inferred end of the persisted image, so these may be RAM-only state re-derived at load.
  3. On either path it then copies fields out: *_DAT_08000678 = *(base + _DAT_0800067c), *_DAT_08000680 = *(base + _DAT_0800067c - 4), and further descriptor stores through piVar2 = _DAT_08000668 referencing base+4, base+_DAT_08000698, base+_DAT_08000698+0x3c, base+0x4780.
  4. (*UNRECOVERED_JUMPTABLE)(0).

3.5 Shared helpers — honesty caveat

FUN_08014d90 and FUN_08014ddc bracket the writer's SRAM access, but both are also called from the audio cluster (FUN_08014ca4, FUN_08014c00) and manipulate 0xB600 constants and a ±10 counter. They are not proven save logic; they may be sound/system guards quiescing audio around SRAM access, or trace artefacts. They are listed in save-format.json with that caveat and no stronger claim.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Offset 0, size 4, bytes e4 2b 51 6e, LE value 0x6E512BE4. No ASCII content.
  • In code: writer stamps *base = _DAT_0800057c (decompiled.c:36); reader tests *base != _DAT_08000664 (decompiled.c:72).
  • In bytes: dword 0 is the only non-zero dword in cap-01.
  • Confidence CONFIRMED_STATIC: the stamp/check pattern at offset 0 is proven in code and the value is observed in the save, but the two literal-pool constants are unresolved, so their equality with each other and with 0x6E512BE4 is inferred, not read.

Checksum: none found

No arithmetic loop over the save payload exists in any of the 57 decompiled functions. The only candidate stored value, dword 0, behaves as a constant (stamped from a literal, compared to a literal) — not as a computed value. Python verification against the real file:

Open questions

  1. Numeric values of every _DAT_ literal in both seeds: RAM base, copy length, magic constants, OR-default value, second default-array offset. This single gap caps overall confidence at MEDIUM.
  2. Internal layout of 0x0004–0x477F: needs a save with real gameplay progress (non-zero payload).
  3. Entry callers / trigger states for FUN_08000484 and FUN_08000584 (unrecovered jump tables; zero callers in both graph sources).
  4. Existence of any checksum outside the traced 57 functions.
  5. Origin of the 12 zero bytes at 0x4890–0x489B.
  6. True role of FUN_08014d90/FUN_08014ddc on the save path (shared with the audio cluster).
  7. Whether the RAM array at +0x4780 is persisted or RAM-only.
