All findings below are derived only from the workspace corpus: the two 512-byte .sav binaries in saves/, ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware facts stated in PACKET.md. 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (core on-disk format: HIGH; individual gameplay-field semantics: LOW–MEDIUM).

Proven by both decompiled code and .sav bytes (verified):

  • The save medium is EEPROM, 512 bytes total (EEPROM 4K in the packet), accessed as 8-byte (4×u16) serial blocks through DMA3 to the EEPROM window at 0x0D000000.
  • The emulator .sav file is not a direct byte image of the in-RAM save buffer. Each 8-byte EEPROM block is stored byte-reversed in the file: logical (RAM) offset r maps to file offset (r & ~7) + (7 - (r & 7)). Undoing that reversal is required before any field, magic, or checksum interpretation.
  • The logical image is an 8-byte global/config record followed by three profile slots of 160 bytes (0xA0) each, at logical offsets 8, 168 (0xA8), and 328 (0x148), ending exactly at 488 (0x1E8). The remaining file bytes (0x1E8–0x1FF) are 0xFF (unwritten/erased EEPROM).
  • Each profile carries a u32 header word at +0x00 and a CRC-16 (poly 0x1021, MSB-first, init 0x0000, no reflection, no final XOR — i.e. CRC-16/XMODEM with zero seed) over profile bytes +0x00..+0x9B, stored little-endian at +0x9C. This was verified in Python against all three slots in both files (6/6 match; see §4).
  • Header magics (logical, little-endian u32): global record 0xC0DE611D, occupied profile 0xC0DE612D, empty/initialised profile template 0x3F219ED2. The empty template has a valid CRC (0x0FF8) but is treated as empty by the validator because its header differs from the occupied-profile value expected by the validation routine.

Static-only (code-proven, not directly observable in the two samples):

  • The full writer/reader/caller architecture in §3, including the write-if-dirty flush with read-back verification and up-to-3 write+verify retries.
  • Profile field writers/readers in FUN_080226dc (game state → profile) and FUN_080228a8 (profile → game state). Field offsets are code-proven; what each field means in gameplay terms (which getter in the FUN_08014exx/FUN_080149xx families corresponds to which game concept) is not recoverable from this corpus alone.

Hypotheses / unknowns (explicitly not proven):

  • Exact gameplay semantics of most profile payload fields (names below are structural, not semantic).
  • The exact value of the EEPROM block-count global dereferenced in FUN_0800a850/FUN_0800a8d0 (*_DAT_0800a880 / *_DAT_0800a908). The corpus shows at least 61 blocks (488 bytes) are meaningful; whether the driver transfers 61 or 64 blocks is unresolved (see §2).
  • The absolute EWRAM address of the save buffer. All *_DAT_080xxxxx values in the decompilation are ROM literal-pool addresses whose pointed-to RAM addresses are not present in the corpus, so RAM mirrors are given as offsets from the save-buffer base, not absolute 0x02xxxxxx addresses.
  • Whether the occupied-profile header 0xC0DE612D is slot-independent (only slot 0 is occupied in the samples, so a slot-dependent variant cannot be excluded — see §5).

A note on the packet's mutation probe: the probe mutated file offset 0xC, reported integrity_check_confirmed: true, save_rewritten_after_mutation: true, and a visual delta. File 0xC maps under the block-reversal to logical offset 0x0B, i.e. the most-significant byte of profile 0's header word, which is both magic-checked and CRC-covered. That is exactly the behaviour expected if the header+CRC validation in FUN_08022bb4 fails and the slot is re-initialised/rewritten — corroborating the code analysis.

Redundancy and selection rules:

  • There is no mirroring or backup copy: each profile exists exactly once. Integrity relies on the per-profile header word plus CRC-16 (§4), and on the write path verifying each EEPROM block after writing (FUN_0803b2c4, §3).
  • There is no generation/sequence counter spanning slots. The only counter-like field is the global record byte at logical +4 (value 0x01 in both samples), which FUN_080314c4 increments (via FUN_0800026a(value + 1, 0x18), i.e. an increment reduced with modulus-like helper bound 0x18) before flushing. With both samples showing 0x01, the modulus and exact semantics remain HYPOTHESIS.
  • Slot selection is by explicit index, not by scanning for the newest valid copy: FUN_080191fc(index) returns profile_base + index * 0xA0, and callers iterate indices 0..2 (FUN_08028f60 loop while (iVar2 + 1 < 3); FUN_080191a0 loop over *param_1 = 3 slots).
  • On load (FUN_080191a0), each slot is validated (FUN_08022be4 → FUN_08022bb4); a slot that fails header or CRC validation is re-initialised in RAM to the empty template (FUN_08022c04: zero-fill, empty header 0x3F219ED2, freshly computed CRC). The same treatment applies to the global record (FUN_08022c3c check, FUN_08022c50 re-init). Empty-template slots therefore remain "invalid" to the occupied-header check by design — that is how an empty slot is represented. This distinction (empty header vs. occupied header) is CONFIRMED_STATIC from the three distinct header-writing routines (FUN_08022c04, FUN_080226dc, FUN_08022c50) and CONFIRMED_VERIFIED for the byte values.
  • Transfer-length open question: FUN_0800a8d0 (load) and FUN_0800a850 (flush) loop over a block count stored in a global (*_DAT_0800a908 / *_DAT_0800a880) whose value is not in the corpus. 61 blocks covers everything meaningful; 64 blocks would also copy the trailing 24 bytes (RAM garbage / 0xFF) harmlessly. The report and JSON therefore record the meaningful length (488) and flag the exact count as unknown rather than guessing.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

ghidra/callgraph.json (314 nodes) records only direct FUN_ calls. The EEPROM routines are mostly reached through Ghidra's func_0x........ alias form, which the callgraph omits — e.g. FUN_0803b164 and FUN_0803b31c appear as orphans (no callers) in the JSON. Every chain below was therefore built by combining (a) callgraph edges, (b) textual func_0x........(...) references in ghidra/decompiled.c, and (c) the pre-extracted seed file ghidra/save_related_functions.c. Line citations are to ghidra/decompiled.c unless stated otherwise.

Hence the §2 mapping. There is no SRAM (0x0E000000) or Flash (0x5555/0x2AAA) code anywhere in the corpus — searches for those constants return no save-related hits.

3.5 Serialization: game state ↔ profile (FUN_080226dc / FUN_080228a8)

FUN_080226dc(profile, game_state) (decompiled.c:3836) builds a profile in RAM:

  • profile[1] (+0x04) ← FUN_08014e14(game), profile[2] (+0x08) ← FUN_08014e10(game) — both only when FUN_08014e04(game) == 0; FUN_08014e14 itself selects between game offsets +0x14/+0x1E8 based on game +0x28, FUN_08014e10 reads game +0x18.
  • profile[3] (+0x0C) ← FUN_08014bd8(game) = game u32 at +0x20; profile[4] (+0x10) ← FUN_08014e08(game) = game u32 at +0x30.
  • FUN_08022b10(profile, game) fills the region starting at profile+0x14 (reads 5 groups × up to 15 entries, decompiled.c:4124–4162).
  • Bytes +0x28..+0x2F ← FUN_080149b8(game, 0..7); bytes +0x30..+0x39 ← FUN_08014994(game, pair 0..4, 0/1); bytes +0x3A..+0x3B ← FUN_08014978(game, 0/1) (decompiled.c:3862–3905 approx.).
  • Bytes +0x3C,+0x3D ← FUN_08022a38(profile): values derived from func_0x08029ab4()/func_0x08029ab0() shifted >> 4 (decompiled.c:4011–4017). In cap-01 both are 0x0C.
  • Block +0x44, 6 units ← FUN_08001e48(game + 0xC, profile + 0x44, 6) (copy helper).
  • Block +0x60, 14 units ← FUN_08007214(FUN_08014bd0(game) = game + 0x19C, profile + 0x60, 0xE).
  • Finally writes the occupied header (*profile = magic, decompiled.c:3907 approx.) and the CRC at +0x9C via FUN_08022bf0.

FUN_080228a8(profile, game_state) (decompiled.c:3913) is the exact reverse: it pushes profile u32s +0x04/+0x08/+0x0C/+0x10 back through FUN_08014db0/FUN_08014dac/FUN_08014bdc/FUN_08014dd8, copies +0x44 back to game+0xC (FUN_08001ea4), replays the +0x28..+0x3B bytes through func_0x080149c4/func_0x080149a4/func_0x08014984 setters, restores the +0x60 block via FUN_08007238(..., profile + 0x60, 0xE), calls FUN_08022a6c (the inverse of the +0x14 region filler) and FUN_08022a14 (pushes +0x3C/+0x3D back out, shifted << 4).

The in-RAM struct that gets mutated before flushing is therefore: the save struct's global record (counter byte via FUN_08022c34) and the selected 160-byte profile inside the save struct's profile array. FUN_080191fc(slot) provides the pointer; FUN_080226dc rewrites the whole profile and recomputes its CRC; FUN_08018fa0 → FUN_0800a850 then writes only the EEPROM blocks whose contents differ from what is already stored.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 The block-reversal (read this first)

Raw .sav bytes do not verify under any standard checksum until each 8-byte block is reversed. Working in the logical image (file block-reversed) makes header, fields, and CRC all line up with the decompiled offsets. All offsets in §4–§5 are logical unless explicitly marked "file".

4.3 Checksum algorithm

  • Algorithm: CRC-16, MSB-first, polynomial 0x1021, initial value 0x0000, no input/output reflection, no final XOR (CRC-16/XMODEM parameters with zero seed). Name in JSON: crc16 (formula detailed there).
  • Code proof: FUN_08031520(seed, data, len) at decompiled.c:5368 implements crc = (crc << 8) ^ table[((crc >> 8) ^ byte)] with the table at _DAT_080315ec; all profile call sites pass seed = 0 and len = 0x9C: FUN_08022bb4 (decompiled.c:4178), FUN_08022bf0 (decompiled.c:4204, used by both FUN_08022c04 and FUN_080226dc after writing the header).
  • Covered range: profile bytes +0x00 through +0x9B inclusive (156 bytes), i.e. header and all payload, excluding the CRC itself.
  • Stored at: profile +0x9C, u16 little-endian (logical). Bytes +0x9E..+0x9F are outside the CRC and are 0x0000 in all samples.
  • File locations of the stored CRC (for hex-editor use): slot 0 → file bytes 0xA2–0xA3 (byte-swapped by the block reversal: logical F8 0F appears as file 0F F8); slot 1 → file 0x142–0x143; slot 2 → file 0x1E2–0x1E3. These match the packet's "candidate checksum spans" at 0xA2/0x142/0x1E2.

4.4 Python verification output (actual run in this workspace)

Script (run as python3 /tmp/verify.py; logic reproduced in the JSON evidence and §6):

def ram_image(raw):  # undo per-8-byte-block reversal
    out = bytearray(len(raw))
    for i in range(0, len(raw), 8):
        out[i:i+8] = raw[i:i+8][::-1]
    return bytes(out)

def crc16(data, init=0):  # poly 0x1021, MSB-first, no xorout
    c = init
    for b in data:
        c ^= b << 8
        for _ in range(8):
            c = ((c << 1) ^ 0x1021) & 0xFFFF if c & 0x8000 else (c << 1) & 0xFFFF
    return c

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this corpus (states/ is empty), so the plan below is written to be executed as soon as states are captured. Every mutation is specified in logical offsets; the repair procedure converts back to file form.

Universal checksum-repair procedure: (1) byte-reverse each 8-byte block of the .sav to obtain the logical image; (2) apply the mutation at the logical offset; (3) if the mutation touches any profile byte in +0x00..+0x9B, recompute CRC-16 (poly 0x1021, init 0, MSB-first) over that profile's 156 covered bytes and store it u16le at profile+0x9C; (4) re-reverse each 8-byte block and write the .sav; (5) boot from the paired save state, letting FUN_080191a0 load and validate, and observe UI, gameplay state, and (if a debugger is available) the save buffer in RAM and subsequent EEPROM rewrite activity (FUN_0800a850 writes only dirty blocks, so an unexpected rewrite is itself a signal).

Controls and pass criteria: every fuzz boot must be paired with an unmodified-file control boot from the same save state. A prediction counts as confirmed only if (a) the CRC/header validation outcome matches (slot accepted vs. re-initialised), and (b) the observed RAM/UI delta is confined to the predicted path. Mutations F1 and F2 need no save state to sanity-check offline: the repaired/failed CRCs can be re-verified with the section 4 Python before booting.

Open questions carried into fuzzing: gameplay semantics of the FUN_08014exx/FUN_080149xx fields; unit size of the +0x44 6-unit copy; entry semantics of the +0x14 table region and +0x60 block; whether the occupied header varies by slot; the global counter's exact modulus; the driver's true block count (F8); and the absolute EWRAM base of the save buffer (recoverable from a debugger during any fuzz boot).
