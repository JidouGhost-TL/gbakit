1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven to HIGH confidence, by both decompiled code and the real .sav bytes:

  • The save medium is a 512-byte EEPROM (EEPROM 4K, SDK tag EEPROM_V124, see §2), accessed as 64 blocks of 8 bytes through a serial bitstream clocked out/in by DMA3 to 0x0D000000 in FUN_08047484, FUN_08047504 and FUN_080475c8.
  • The file layout is a 16-byte global header at 0x00, followed by three contiguous 160-byte save slots at 0x10, 0xB0, 0x150, and 16 unused bytes at 0x1F0. This geometry is derived arithmetically from the block arguments in FUN_08017f30 (slot*0x14+2 blocks, 0x14 blocks), FUN_08018064 / FUN_08017fa8 (blocks 0–1 = header), and FUN_080178a0 (slot start blocks 2, 22, 42, step 0x14), and it matches the non-0xFF spans of both samples exactly.
  • The 8-byte magic 7800OGEL at offset 0x00, and the 16-bit additive header checksum at offset 0x0E (sum of the eight big-endian-interpreted words ≡ 0 mod 65536; stored word is the two's-complement negation of the sum of the other seven). The exact Python verification against both files is in §4: computed 0xFF80 = stored 0xFF80 in both samples; the little-endian interpretation was tested and fails in both, so the byte order claim is falsified-tested, not assumed.
  • The complete low-level writer/reader/verify chain and the header load/create/flush chain (§3), including the fact that both available samples are in the "blank-initialised" state: header valid, and only the first 8 bytes of each slot ever written (all zero), with the remaining 152 bytes of each slot still at the 0xFF fill. Consequently all three slots fail the game's own slot-validity sum (0xFFB4 ≠ 0, §4) and would be treated as empty/invalid on load.

What remains open, and why the overall grade is not HIGH:

  • No full-slot writer was found in the corpus. The only traced writes to slot EEPROM space are the one-block blanking writes in FUN_080178a0. No traced function calls the multi-block writer with a 20-block count for a slot. The gameplay writer that serialises a populated 160-byte slot, and therefore the slot's internal field layout and the exact stored-checksum offset inside a slot, are unknown from this corpus. The trace-guided 294-function corpus presumably only contains code executed during the captures.
  • Both samples are blank-state saves. No populated slot exists to map gameplay fields (progress, studs, characters, etc.) against. Every slot-payload field beyond "first block is zero in blank state" is UNKNOWN.
  • The semantics of header bytes 0x08 and 0x0C, the only two bytes that differ between the samples, are not written by any traced function other than the default-template copy. They are reported as observed values with HYPOTHESIS/UNKNOWN semantics (§5).
  • The numeric RAM base of the save-manager struct cannot be recovered (see method note). RAM offsets within the struct are recovered; absolute RAM addresses are not.
  • There are no paired .ss save states in this workspace (states/ is empty), so §6 is a plan, not executed results. The PACKET.md cold-reload probe (mutation at 0x8 ⇒ integrity failure ⇒ save rewritten) is consistent with, and independently corroborates, the checksum in §4, but it is probe metadata, not a test run here.

FUN_08047c5c, listed as an MMIO seed in ghidra/save_related_functions.c, is a false seed: it is an integer divide/modulo helper (called as func_0x08047c5c(uVar5, _DAT_080173ac) from FUN_0801731c), touches no MMIO, and has no save role. It is excluded from the architecture below.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM addresses (0x08xxxxxx). "How mapped" states the evidence for each edge: CG = edge present in ghidra/callgraph.json, TXT = callee address literal present in the caller's body in ghidra/decompiled.c. The callgraph omits most func_0x... edges (e.g. it lists no callees for FUN_0801811c), so TXT is the primary evidence and CG is corroboration where present.

3.1 Low-level hardware I/O driver

FUN_08047484 — DMA3 transfer engine

Signature: FUN_08047484(src, dst, count). It saves an interrupt/DMA-enable halfword (*_DAT_080474e4), clears it, programs the DMA3 registers through the _DAT_080474f4 (source), _DAT_080474f8 (destination) and _DAT_080474fc (control/count) pointers with count & 0xFFFF | 0x80000000 (DMA enable bit 31), applies a WAITCNT-related mask/or from *_DAT_080474f0 + 6, then busy-waits while bit 0x8000 of the control high halfword is set, and restores the saved enable value. One of the two addresses at every call site is 0x0D000000, the GBA EEPROM serial data register/window. Callers (CG + TXT): FUN_08047504, FUN_080475c8. This is the standard Nintendo EEPROM-library DMA routine: the EEPROM is a 1-bit serial device, so each DMA halfword carries one serial bit in its LSB.

FUN_08047504 — EEPROM read one block (8 bytes)

Signature: FUN_08047504(block_index, ram_dst). Behaviour:

  1. Masks the block index to 16 bits and bounds-checks it against the device block count at descriptor+4; on failure it returns the non-zero default uRam08047520 (error).
  2. Builds the read command bitstream on the stack: two 1 bits (start bit + read opcode MSB-first) followed by the block-address bits, most-significant bit first, count = byte at descriptor+8.
  3. FUN_08047484(stack, 0x0D000000, addr_bits + 3) sends the command; FUN_08047484(0x0D000000, stack, 0x44) clocks back 0x44 = 68 halfwords (dummy bits plus 64 data bits).
  4. Reassembles four u16 words MSB-first from the received LSBs and stores them to ram_dst .. ram_dst+7 (store pointer starts at ram_dst+6 and decrements — word order within the block is handled by the library's bit ordering; see the byte-order discussion in §4).
  5. Returns 0 on success.

Callers: FUN_08047728 (CG + TXT) and FUN_0801811c (TXT; CG omits this edge).

FUN_080475c8 — EEPROM write one block (8 bytes) + write-complete wait

Signature: FUN_080475c8(block_index, ram_src, wait_flag). It expands the four source u16s and the block address into a serial bitstream terminated by 0, 1 (start + write opcode), sends addr_bits + 0x43 halfwords (start + 2 opcode bits + address + 64 data bits) to 0x0D000000 via FUN_08047484, then polls the EEPROM data line (uRam0d000000 & 1) with a timeout accumulated from a timer register (*_DAT_080476b4, wrap 0xE4, limit 0x88) until the device signals write completion; with wait_flag != 0 it waits for an additional cycle. Returns 0 on success, a non-zero library value on timeout. Callers: only via the wrapper FUN_080475b4 (TXT).

FUN_080475b4 — write-block wrapper

Calls func_0x080475c8(param_1, param_2, 1) — i.e. always requests the write-complete wait. Caller: FUN_08018198 (TXT).

FUN_08047728 — EEPROM verify one block

Reads the block back with FUN_08047504 into a 4-word stack buffer and compares all four u16s against the source buffer. Returns 0 on match, 0x8000 on first mismatch. Caller: FUN_08018198 (TXT).

FUN_0804743c — EEPROM access-mode set , FUN_08018220 — enter EEPROM access , FUN_0801826c — leave EEPROM access

FUN_08018220 saves a WAITCNT-class global (*_DAT_0801825c = *_DAT_08018260), writes a saved-state halfword, zeroes the control global, and calls FUN_0804743c(4), whose param == 4 branch stores a constant through _DAT_08047450 — consistent with selecting the EEPROM wait-state/addressing mode before a burst of serial transfers. FUN_0801826c restores the saved global. Every multi-block transfer (§3.2) is bracketed by this pair. The exact register fields cannot be resolved further because the _DAT_ values are not in the workspace (CONFIRMED_STATIC for the bracketing role, UNKNOWN for the exact bit fields).

There is no SRAM byte-copy driver, no Flash 0x5555/0x2AAA command sequence, and no erase function anywhere in the save path; those alternatives from the packet template do not apply to this title. EEPROM "erase" is simply overwriting, and the only erase-like operation is the zeroing of slot first blocks in FUN_080178a0.

3.2 Multi-block transfer wrappers

FUN_0801811c — read N blocks

Signature: FUN_0801811c(start_block, block_count, ram_dst). Calls FUN_08018220, then per block calls FUN_08047504(block, dst), retrying a failing block while a counter starting at 3 has not run out (up to 4 attempts per block), advancing dst += 8, block += 1. Calls FUN_0801826c and returns last_error == 0 as a boolean (1 = success). Callers (TXT): FUN_08017f30, FUN_08017fa8, FUN_080180b4. CG lists no callers/callees for this function — the edges are text-only, which is stated here rather than silently relying on the graph.

FUN_08018198 — write N blocks with verify

Same loop shape, but each block is written with FUN_080475b4 and immediately verified with FUN_08047728; the block is retried while verify/write fails and the retry counter lasts. Callers (TXT): FUN_080178a0 (count 1 per slot — blanking), FUN_08017fa8 (count 2 — header), FUN_08018064 (count 2 — header). No caller passes a slot-sized count of 20. That absence is the basis for the "no traced full-slot writer" finding in §1.

3.3 Checksum, serialisation and save-manager layer

The save manager is a RAM struct reached through several literal-pool pointers (_DAT_0801790c, _DAT_08017a00, _DAT_08017f2c, _DAT_08017f6c, _DAT_08018024, _DAT_080180ac, _DAT_080180f0). Their offsets are used identically (+0x10 slot-buffer pointer, +0x14 descriptors, +0x2C validity array), so they are treated as aliases for one manager object; whether they are literally the same pointer value cannot be proven from the workspace. Offsets below are offsets from that manager base. The first 16 bytes of the manager are the header's RAM mirror — proven by FUN_08017fa8, which checksums, compares and writes exactly those 16 bytes as EEPROM blocks 0–1.

FUN_08018028 — sum16

FUN_08018028(ushort *p, uint byte_len): sums byte_len >> 1 consecutive u16 words, masking to 16 bits after each addition (uVar1 = *param_1 + uVar1 & 0xFFFF). Returns the 16-bit sum. This is the only checksum routine in the save path; there is no CRC, XOR-fold, or complement table anywhere in the traced save functions. Callers (CG + TXT): FUN_08017ee8, FUN_08017fa8, FUN_08018064, FUN_080180b4.

FUN_08018064 — create default header and write it

Copies a 16-byte ROM template (_DAT_080180b0, source of the 7800OGEL magic and default field values) into the header mirror with the memcpy FUN_08013828, computes sVar2 = FUN_08018028(mirror, 0x10), stores *(short*)(mirror + 0xE) = -sVar2, and writes blocks 0–1 with FUN_08018198(0, 2, mirror). Caller: FUN_080178a0 (TXT) on the invalid-header path. Note it does not explicitly zero offset 0x0E before summing, unlike FUN_08017fa8; the stored result is still correct in both observed files (§4), which implies the template's checksum field contributes consistently — the template bytes themselves are not in the workspace, so this detail is CONFIRMED_STATIC for the algorithm and UNKNOWN for the template contents beyond the magic.

FUN_080180b4 — validate header on load

Reads blocks 0–1 into the header mirror (FUN_0801811c(0, 2, mirror)). Returns 0 (invalid) if the read fails or FUN_08018028(mirror, 0x10) != 0. Otherwise byte-compares the first 8 mirror bytes against the ROM constant at pcRam08018118 (the magic) and returns 1 only if all 8 match. Caller: FUN_080178a0 (TXT).

FUN_08017fa8 — flush header if changed

  1. Reads the current EEPROM header into a 16-byte stack buffer: FUN_0801811c(0, 2, &stack). If that read fails, returns failure without writing.
  2. Mutates the RAM mirror: *(u16*)(mirror + 0xE) = 0, then *(short*)(mirror + 0xE) = -FUN_08018028(mirror, 0x10).
  3. Compares the mirror against the stack readback as four u32s; if identical, skips the write (returns success).
  4. Otherwise writes blocks 0–1 with FUN_08018198(0, 2, mirror) (which itself write-verifies each block).

This is the only traced writer of a checksummed save region, and the only traced function that mutates header fields before flushing: it mutates exactly one field, the checksum at +0xE. No traced caller of FUN_08017fa8 mutates any other header byte first — which is why the 0x08/0x0C delta between samples (§5) cannot be attributed to a traced writer.

Caller (CG + TXT): FUN_0802c960, which executes FUN_0801bd2c(); FUN_08017fa8(); FUN_0801bd50();. FUN_0801bd2c and FUN_0801bd50 are one-line wrappers around func_0x08044420 / func_0x080443f0, neither of which is among the 294 decompiled functions, so their role (plausibly a lock/unlock or sound/task bracket) is UNKNOWN. FUN_0802c960 itself has no callers in the callgraph and no textual caller; its trigger context (menu exit, autosave point, etc.) is UNKNOWN.

FUN_080178a0 — save-manager initialisation / load orchestrator

  1. Allocates the shared slot buffer: *(manager + 0x10) = FUN_080135d0(0xA0) (heap allocator; FUN_080135d0 aligns, calls the heap in FUN_08013538, and zero-fills via FUN_080137a0).
  2. iVar3 = FUN_080180b4() — validate header (§3.3).
  3. If invalid: FUN_08018064() (create + write default header), FUN_08017948() (zero the 160-byte slot buffer in RAM), then for each slot n = 0,1,2: FUN_08018198(2 + 0x14*n, 1, slot_buffer) — writes one zeroed block at each slot's start. This exactly produces the observed sample state.
  4. Reads the selector byte *(u8*)(manager + 10) — i.e. header file offset 0x0A — passes it to FUN_0801d04c, and copies it to a global byte at _DAT_08017910 + _DAT_08017914. FUN_0801d04c stores it through _DAT_0801d07c and indexes a table with param * 4, consistent with a current-profile/slot index (HYPOTHESIS).
  5. Calls FUN_08017eac() to load all slots.

FUN_080178a0 has no callers in the callgraph and no textual caller in the corpus; it is reached through an unrecovered jumptable/function-pointer path. Boot-time init is the natural reading, labelled HYPOTHESIS for the trigger, CONFIRMED_STATIC for the body.

FUN_08017948 — zero slot buffer

FUN_080137a0(*(manager + 0x10), 0, 0xA0) — memsets the shared slot buffer to zero. (FUN_080137a0 is a byte-value fill routine.) Callers (CG records FUN_08017f30; TXT shows the call in FUN_08017948's own definition and its use from FUN_080178a0): used on the blank-initialisation path before the one-block slot writes.

FUN_08017f30 — load one slot into the shared buffer

First zero-fills the shared buffer (FUN_08017948();, corroborated by the callgraph edge 0x08017f30 → FUN_08017948), then calls FUN_0801811c(slot*0x14 + 2, 0x14, *(manager + 0x10)): reads the slot's full 20 blocks into the shared heap buffer, overwriting whatever slot was there before. Caller: FUN_08017eac (TXT).

FUN_08017ee8 — slot validity flag

Computes sVar2 = FUN_08018028(*(manager + 0x10), 0xA0) over the just-loaded slot buffer and writes *(u32*)(manager + 0x2C + 4*slot) = (sVar2 == 0). So each slot carries the same sum-to-zero integrity rule as the header, over its full 160 bytes. Caller: FUN_08017eac (TXT).

FUN_080179c0 — post-load per-slot activation

If *(manager + 0x2C + 4*slot) == 0 (invalid): memsets the 8-byte descriptor at manager + 0x14 + 8*slot to zero. Else: stores *(manager + 0x3C) = *(manager + 0x10), *(manager + 0x40) = 0, and calls func_0x0802c164(manager + 0x14 + 8*slot). 0x0802c164 is not among the 294 decompiled functions, so what activation does with the descriptor is UNKNOWN. Caller (CG + TXT): FUN_08017eac.

FUN_08017eac — load all slots

For slot = 0,1,2: FUN_08017f30(slot); FUN_08017ee8(slot); FUN_080179c0(slot);. Caller: FUN_080178a0 (TXT). Because the slot buffer is shared, after this loop the buffer holds slot 2's data; per-slot state survives only in the descriptors at manager+0x14 and validity flags at manager+0x2C.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • File offset 0x00, 8 bytes: 37 38 30 30 4F 47 45 4C = ASCII 7800OGEL, present identically in both samples.
  • Verified in code: FUN_080180b4 byte-compares the first 8 bytes of the EEPROM-read header mirror against the ROM constant at pcRam08018118 and rejects the header unless all 8 match; FUN_08018064 installs those bytes from the ROM template at _DAT_080180b0. The constant bytes themselves are not reproduced in the decompiled text, so the code-side verification is CONFIRMED_STATIC (comparison exists, length 8, against a ROM constant) and the sav-side value is CONFIRMED_VERIFIED. Note the reversed-looking OGEL: that is the byte order as stored and as compared; no byte-swap is applied by the validation code, so 7800OGEL is the on-media signature, not a display artefact to be "corrected" to LEGO.

4.2 Header checksum — exact algorithm

From FUN_08018028 (sum), FUN_08017fa8 and FUN_08018064 (store), FUN_080180b4 (validate):

  • Algorithm: 16-bit additive sum (sum16), two's-complement negation on store. No seed, no final XOR, no CRC.
  • Covered range: the entire region including the stored word — file bytes 0x00–0x0F for the header (8 words). Validation succeeds iff sum(words) & 0xFFFF == 0.
  • Store procedure (FUN_08017fa8, verbatim logic): set word at offset 0x0E to 0, compute s = sum16(region), store (−s) & 0xFFFF at offset 0x0E.
  • Stored offset/size: file offset 0x0E, 2 bytes.
  • File byte order: big-endian per 16-bit word. The decompiled sum operates on RAM u16s loaded from the mirror; the EEPROM driver assembles received bits MSB-first (FUN_08047504). When the 16 file bytes are interpreted as eight big-endian u16s, the rule holds exactly on both samples; interpreted as little-endian it fails on both (total 0x01FE ≠ 0, computed negation 0x7F01 ≠ stored 0x80FF). The endianness claim is therefore verified at the file level, and the RAM-level statement is: the checksum sums the eight u16 words of the 16-byte mirror as assembled by the EEPROM read routine, in the order that makes the on-media bytes big-endian per word. A residual caveat: the driver's intra-block word ordering (stores start at dst+6 and decrement in FUN_08047504) means a block-internal word permutation cannot be distinguished by an additive checksum (addition is commutative) or by the byte-wise magic compare if the ROM constant is stored in the same permuted order. File offsets in §5 are therefore the authoritative coordinate system; RAM-mirror offsets are stated as file-offset-equivalent, which is exactly how FUN_08018064/FUN_08017fa8/FUN_080180b4 treat the mirror (template memcpy, +0xE store, 8-byte compare).

4.3 Slot checksum — exact algorithm (static)

FUN_08017ee8 applies the identical routine to a slot: FUN_08018028(slot_buffer, 0xA0) == 0 is the validity condition, i.e. the sum of the slot's 80 words must be 0 mod 65536. By analogy with the header, a writer must store the negated sum of the other 79 words in one word of the slot, most plausibly the last word (slot offset 0x9E), but no traced slot writer exists, so the stored offset inside the slot is HYPOTHESIS (last word) and the sum rule itself is CONFIRMED_STATIC. On the blank samples every slot sums to 0xFFB4 ≠ 0 (four zero words from the blanked first block + 76 words of 0xFFFF: −76 mod 65536 = 0xFFB4), so all three slots are invalid/empty under the game's own rule — verified numerically below.

The two-sample delta (byte 0x08: 04→03, i.e. word-4 high byte −1 = −0x0100; byte 0x0C: 00→01, i.e. word-6 high byte +1 = +0x0100) nets to zero, so the same stored checksum remains correct in both files — consistent with a header flush through FUN_08017fa8 recomputing the checksum after both fields changed (or with the fields having been written as a compensating pair). It also explains the PACKET.md probe: a single-byte mutation at 0x8 without that compensation breaks the sum, FUN_080180b4 rejects the header, and the game rewrites a blank save — matching integrity_check_confirmed: true, reverted_to_blank_on_mutation: true.

Write-verify is the second integrity layer: every block written through FUN_08018198 is read back and compared word-for-word by FUN_08047728, with retries. There is no redundancy copy to fall back to; a block that cannot be written/verified after retries simply makes the multi-block call return failure.

6. Save Fuzzing & Counterfactual Verification Plan

No .ss save states exist in this workspace, so none of these tests could be executed here. Each test starts from a copy of cap-00-future-0.sav, boots it, and observes (a) whether the save is accepted, rewritten, or blanked, (b) the resulting .sav bytes, and (c) any RAM/UI change. "Repair checksum" for the header means: set bytes 0x0E–0x0F to (−sum of the other seven big-endian words) & 0xFFFF, big-endian. For a slot it means the candidate repair: set the slot's last two bytes (base+0x9E) to (−sum of the other 79 big-endian words) & 0xFFFF — labelled as testing the §5 hypothesis, since the slot stored offset is unproven.
