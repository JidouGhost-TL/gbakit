3.0 How callers were mapped (method)

  2. Cross-checked against ghidra/callgraph.json (152 entries).   3. 3.3 Top-level save manager: FUN_08010968 (0x08010968)

Signature: FUN_08010968(undefined4 sram_base, undefined4 ram_buffer, undefined4 size) — the only function that binds the triple together. Called exactly once in the corpus:

// FUN_0801cf54 (game/system init)
FUN_08010968(0xe000000, _DAT_0801d130, 0x8000);   // SRAM 0x0E000000, RAM mirror (value unresolved), 32768 bytes

Step-by-step (decompiled body, ghidra/save_related_functions.c lines 45–90 and ghidra/decompiled.c):

  1. Bind descriptor: puVar1 = _DAT_08010a08; *puVar1 = sram_base; puVar1[1] = ram_buffer; puVar1[2] = size; The descriptor is a ≥ 0x13A-byte work struct (fields touched up to +0x139).
  2. Load: func_0x08010a94(); — SRAM→RAM transfer + verify (§3.2).
  3. Validate magic: iVar4 = func_0x0801bf30(_DAT_08010a0c, puVar1 + 4); — strcmp(expected_rom_string, descriptor+16). descriptor+16 is byte offset 0x10 (pointer arithmetic on undefined4*: +4 words). The ROM expected string is not in the workspace, but the .sav bytes prove its value is MINIMONI_V1009 (see §4; CONFIRMED_VERIFIED by bytes + copy direction in step 4).
  4. First-boot init (only if strcmp != 0, i.e. blank/corrupt/wrong save):
  • Registers a callback/state struct: *(undefined2 **)_DAT_08010a10 = auStack_24 (=0); *(ptr)(_DAT_08010a10+4) = puVar1; *(ptr)(_DAT_08010a10+8) = _DAT_08010a14;
  • Writes magic into RAM: func_0x0801befc(expected, puVar1 + 4); (strcpy to descriptor+16).
  • Zeroes three descriptor bytes: *(u8)(puVar1 + 0x4e) = 0 → byte offset 0x138; *(u8)((int)puVar1 + 0x139) = 0; *(u8)(puVar1 + 0x2a) = 0 → byte offset 0xA8.
  • Clears six u16 slots: for (i=0..5) func_0x08010b10(i, 0); where FUN_08010b10(idx, val) writes *(u16*)((idx&0xff)*2 + _DAT_08010b24 + 0x102) = val (array base unresolved).
  1. Mark valid/dirty (unconditional): re-binds the triple, then *(undefined2 *)(puVar1 + 3) = 1; — u16 flag at descriptor byte offset 0x0C set to 1. Interpreted as "save present/initialized" flag in RAM; whether it also triggers the missing flush is UNKNOWN.
  2. Returns through an unrecovered jump table (state-machine dispatch; the true continuation — plausibly including the write-back — is not visible).

How the in-RAM struct is mutated before any flush: On blank media the only mutations proven by code are: magic string at descriptor+16, zeroing of +0xA8/+0x138/+0x139, clearing of 6×u16 array entries, and flag +0x0C = 1. No other save-field writers exist in the save path. All other FUN_0801cf54 callees (below) mutate a different struct (_DAT_0801d10c, the general game-state block) or display/audio state — they do not touch the SRAM descriptor, and conflating them with save fields would be an error. They are listed for completeness of the caller chain, with their actual (non-save) effects stated.

3.4 The missing flush — write-back gap (critical honesty note)

cap-01-future-1.sav contains the magic at 0x00 over a 0x00 (not 0xFF) background. Erased SRAM reads 0xFF (proven by cap-00). Therefore, between the two captures, something wrote at least the magic — and, if the 0x00 background came from the same write, the whole 32 KiB zeroed mirror — to SRAM. Yet:

  • FUN_08010968's traced body calls only the read wrapper, never FUN_08010a1c.
  • FUN_08010a1c has zero callers in both ghidra/decompiled.c (text search: only its own header + definition) and ghidra/callgraph.json (callers: [] — in fact the entry is absent from callgraph callees entirely; the function exists in decompilation but is unreachable in the traced graph).

Possible resolutions, in order of likelihood given the pervasive UNRECOVERED_JUMPTABLE tails (nearly every function ends in one — this ROM uses a state-machine/jump-table style Ghidra could not resolve):

  1. The flush is invoked from an untraced state reached via a jump-table tail (e.g. the tail at the end of FUN_08010968 itself, or a later gameplay state that sets the +0x0C flag and dispatches to FUN_08010a1c). Most likely.
  2. The emulator harness zero-filled SRAM before the init write of the header block, so only a partial write occurred. Cannot be distinguished from (1) with the given samples.
  3. FUN_08040cf8 direction is reversed (write, not read), making FUN_08010a94 itself the flush. Argued against by argument order vs. the visible FUN_08040d5c loop, but not disprovable while FUN_08040e74 remains a stub. Retained as a live alternative; fuzzing test F-06 (§6) discriminates it.

Consequence for this report: Every "writer" attribution beyond first-boot init is marked CONFIRMED_STATIC or HYPOTHESIS. No gameplay writer chain is claimed, because none exists in the evidence.

4.2 Checksum / integrity algorithm

Finding: there is no stored checksum, CRC, or hash anywhere in the save format as evidenced. Integrity consists of exactly two mechanisms, neither of which stores a computed value in the image:

  1. Magic compare (§4.1) — rejects blank/corrupt images at load.
  2. SRAM verify-compare (FUN_08040dcc, called by both wrappers after every transfer) — byte-for-byte comparison of RAM mirror vs. SRAM contents at transfer time. This detects transfer errors; it writes nothing to the image.

Decompiled proof (absence): The complete save path (FUN_08010968, FUN_08010a94, FUN_08010a1c, FUN_08040cf8, FUN_08040d5c, FUN_08040dcc, FUN_0801bf30, FUN_0801befc, FUN_08010b10) contains no loop that accumulates a sum/XOR/CRC over the save buffer and no store of a computed value into the buffer. The only accumulation loops in the corpus belong to unrelated graphics/task code. The verify routine's result is used only as a branch condition (if (iVar3 != 0) → error-string copy), never written into the image.

Formula fields (as required, stated negatively and precisely):

  • Algorithm: unknown — more precisely, none / not present. No formula, seed, covered range, or stored offset exists to report.
  • Covered range: N/A. Stored offset/size: N/A (no stored bytes).
  • The JSON deliverable therefore carries "checksums": [] with the reasoning recorded in open_questions, rather than inventing an entry. (Schema permits an empty list; a fabricated custom entry would violate clean-room honesty.)

Combined with the code-side absence, the honest conclusion is no stored checksum (CONFIRMED_VERIFIED for these samples; a checksum that only appears in populated saves cannot be ruled out metaphysically, but there is zero code evidence for one — see fuzzing test F-05).

5. Complete Field Map Table

5.1 Mapping model (read before the table)

Two structures must not be conflated:

  • SRAM descriptor / work struct (base = value of _DAT_08010a08, absolute address unresolved): holds {sram_addr @+0x00, ram_buffer @+0x04, size @+0x08, flag @+0x0C, string @+0x10, …}. Its +0xA8/+0x138/+0x139 bytes and the 6×u16 array (via FUN_08010b10, base _DAT_08010b24 + 0x102) are RAM-side fields.
  • File image / RAM mirror (base = value of _DAT_0801d130, absolute address unresolved): the byte-for-byte image transferred by the 0x8000-byte copy. File offset 0x00 is its first byte.

If the RAM mirror base equals descriptor+16, descriptor offsets map to file offsets by file = desc − 0x10 (so +0xA8→0x98, +0x138→0x128, +0x139→0x129, flag +0x0C would fall before the image and never be stored). If the mirror is a separate buffer, only the string's presence at file offset 0 is proven and the other descriptor fields have no file offset at all. The workspace cannot decide between these models (literal-pool values missing). The table therefore gives file offsets only where bytes prove them, and lists RAM-descriptor fields separately with UNKNOWN file mapping. This is the maximum honest precision.
