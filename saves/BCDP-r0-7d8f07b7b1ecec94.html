1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (format structure, geometry, driver and checksum: effectively HIGH; per-field gameplay semantics and the emulator byte-order transform: MEDIUM — see below).

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • The game uses a 512-byte EEPROM (EEPROM 4K = 4 Kbit). Exactly one 72-byte (0x48) save image is read from and written to EEPROM byte offset 0. There are no slots, no backup copy, no generation counter and no ASCII magic.
  • Integrity is a seeded byte-sum: stored_u32le = (0x12345678 + sum of all 72 image bytes with the checksum field zeroed) & 0xFFFFFFFF, stored little-endian in the last 4 bytes of the image (RAM offset +0x44). This reproduces the stored value in cap-01-future-1.sav exactly (computed 0x1234627B = stored 0x1234627B); the blank cap-00-future-0.sav correctly fails the check, which is the code path that manufactures the defaults seen in cap-01.
  • The complete writer/reader chain was traced from the game state machine down to the DMA3 EEPROM serial driver at 0x0D000000.

Static-only (CONFIRMED_STATIC, code-proven, not independently observable in the two snapshots): exact EEPROM wire protocol details, the device-type selection, write-verify retry behaviour, and every caller trigger in §3.

Hypotheses / unknowns (HYPOTHESIS/UNKNOWN): the gameplay meaning of most persisted words (only their copy paths and a few sentinel/clamp behaviours are code-visible); whether the .sav file's per-8-byte-block byte reversal (see §2) is an emulator packing artefact or the true EEPROM cell order — the checksum sum is invariant under that permutation, so the checksum verdict does not depend on resolving it; the numeric RAM address of the heap-allocated game object (only the global pointer cell is visible in decompilation).

Corpus limits: only 2 snapshots, of which 1 is blank (all 0xFF) and 1 is a valid early save. There are no paired .ss save states in this workspace (states/ is empty), so §6 is a plan, not an executed result. PACKET.md §1's cold-reload probe (integrity_check_confirmed: true, mutation at 0x0 produced a visual delta, save preserved on load) is consistent with the checksum + load behaviour derived here, but was not re-executed.

File layout vs. RAM layout (byte-order transform)

The decompiled serialize/deserialize code (FUN_0801ef34/FUN_0801ee34) works on a 72-byte RAM staging buffer whose last word (+0x44) is the checksum and whose words at +0x30/+0x34 receive the small integers 7 and 8 on the default path. In the .sav file, the word 12 34 62 7B sits at file offset 0x40, not 0x44, and the small integers appear as 00 00 00 08 / 00 00 00 07. Reversing each 8-byte EEPROM block maps file ↔ RAM exactly and consistently:

  • file block 8 12 34 62 7B 00 00 00 00 → RAM +0x40 = 0x00000000, RAM +0x44 = 0x1234627B (little-endian checksum — matches the code offset and endianness);
  • file block 6 00 00 00 08 00 00 00 07 → RAM +0x30 = 7, +0x34 = 8 (exactly the loader's default constants, in the code's order);
  • file blocks 0/2/4 (00 00 00 00 FF FF FF FF) → RAM record first words 0xFFFFFFFF (the loader's default "empty record" word).

This is consistent with the MSB-first serial bit order of the EEPROM driver (FUN_08029a2c builds its DMA source buffer backwards; FUN_08029968 reconstructs words MSB-first) combined with how the emulator packs serial bits into the .sav file. It is labelled HYPOTHESIS at the transform level: the alternative (file is the literal RAM image, checksum is big-endian at 0x40) contradicts the decompiled offsets/endianness and turns the +0x30/+0x34 fields into 0x08000000/0x07000000, which the game code treats as small integers everywhere. All field offsets in §5 are given in both domains. The checksum itself is a plain byte sum and is identical in both domains.

Defaults manufactured by the loader on checksum failure (FUN_0801ee34, decompiled lines 4745–4755): staging buffer zeroed (FUN_0802a284, a memset), then +0x30 = 7, +0x34 = 8, +0x40 = 0x000000FF, and the first word of each of the 3 records (+0x00, +0x10, +0x20) set to 0xFFFFFFFF. The valid snapshot matches this default state except that +0x40 is 0 instead of 0xFF — explained by FUN_080221cc (lines 5616–5625): on first boot the game sees object field +0x6C == 0xFF, rewrites it to 0 and immediately saves. cap-01-future-1.sav is therefore best explained as the first-boot defaulted-then-saved image. This is an inference from code + bytes, not a directly observed boot.

How callers were mapped: (a) direct edges in callgraph.json; (b) textual FUN_/func_0x references in decompiled.c — necessary because several real calls are emitted as func_0x08029674-style tail/jumptable calls that the callgraph records as "no callers" for the EEPROM high-level wrappers (e.g. FUN_08029674 and FUN_0802971a show callers: [] in the graph but are called textually from FUN_0801ef34 line 4866 and FUN_0801ee34 line 4741); (c) constant tracking (0x48 length, offset 0, device type 0) at each call site. 4. Magic Signatures & Checksum / Integrity Algorithm

Magic signatures

There is no ASCII magic and no constant magic word in the save image. PACKET.md reports ascii_magic_strings: [], and no constant-compare against the image exists in FUN_0801EE34 other than the checksum. The bytes 12 34 62 7B at file offset 0x40 look magic-like but are the checksum value itself for this particular (nearly-empty) image: 0x12345678 + 0xC03 = 0x1234627B. On any other image content those 4 bytes will differ. The value 0x12345678 is the checksum seed, not stored magic.

Checksum algorithm (exact)

  • Function: FUN_0800AA6A mode 0 (decompiled lines 2999–3025), called from FUN_0801EE34 (line 4744) and FUN_0801EF34 (line 4864) with (0, buf, 0x48, _DAT_0801F0D4).
  • Formula: acc = seed; for i in 0..71: acc = (acc + buf[i]) & 0xFFFFFFFF — an 8-bit byte sum accumulated in 32 bits (equivalently sum8 extended to 32 bits; not CRC, not XOR, no complement, no final negation).
  • Seed: _DAT_0801F0D4 is an unresolved ROM constant in the decompilation. Solving stored − sum(image with checksum zeroed) on the valid snapshot yields exactly 0x12345678, the canonical test seed — this is treated as the seed value, verified on the sample below.
  • Covered range: the full 72-byte image, RAM offsets 0x00–0x47 inclusive, with the 4 checksum bytes treated as 0. In the loader this is explicit: stored = *(u32*)(buf+0x44); *(u32*)(buf+0x44) = 0; computed = sum(buf, 0x48, seed). In the saver the fresh staging buffer's +0x44 word is still zero at compute time (the buffer is newly allocated; note the code does not explicitly zero it — allocator behaviour is an assumption, see Open Questions).
  • Stored at: RAM image offset +0x44, size 4, little-endian u32. In the .sav file domain (per-8-byte-block reversal, §2) those 4 bytes appear at file offset 0x40 in big-endian-looking order (12 34 62 7B).
  • Decompiled C proof (verbatim logic):
// FUN_0800aa6a (0x0800AA6A), mode 0 branch:

do {

6. Save Fuzzing & Counterfactual Verification Plan

No .ss save states exist in this workspace, so the reload oracle is: boot the ROM with a mutated .sav, let FUN_0801EE34 run, and observe (a) whether defaults were manufactured (records 0xFFFFFFFF, singles 7/8, selector 0xFF→ first-boot flow), (b) the RAM mirror (obj+0x18…, obj+0x5C…0x6C via the global at *_DAT_0801F0DC), and (c) visible UI/gameplay deltas. Checksum repair for any mutation in RAM offsets 0x00–0x43: recompute stored = (0x12345678 + Σ 72 bytes with checksum word = 0) & 0xFFFFFFFF, write it little-endian at RAM +0x44, then apply the per-8-byte-block reversal to obtain file bytes (or equivalently compute the sum directly on file bytes — the sum is identical — and place the 4 checksum bytes reversed into file block 8's first half). General repair snippet (RAM domain, then transform to file domain):

import struct
img = bytearray(ram_image_72_bytes)          # RAM domain
struct.pack_into('<I', img, 0x44, 0)
struct.pack_into('<I', img, 0x44, (0x12345678 + sum(img)) & 0xFFFFFFFF)
sav = bytearray(512)
for b in range(9):                            # per-8-byte-block reversal
    sav[b*8:b*8+8] = img[b*8:b*8+8][::-1]
sav[0x48:] = b'\xFF' * (512 - 0x48)

Open Questions

  1. Gameplay names for singles A–E, the 3 records' word1–3, and each bit of the +0x38 bitflags — no string/UI evidence in the corpus names them; the "language index" reading of the selector (5 values, 5 title languages) is plausible but unproven.
  2. Record word0 width contradiction: loader default stores 0xFFFFFFFF (u32) while FUN_080221CC compares/increments it as if 0xFF-sentinel small-int. F6 resolves this empirically.
  3. The .sav block-reversal transform is inferred from code offsets + default constants + checksum placement jointly; F10's second half is the decisive test. (The checksum verdict itself does not depend on it.)
  4. _DAT_0801F0D4 (seed cell) and all _DAT_ pointer contents are unresolved ROM constants in the decompilation; the seed value 0x12345678 is recovered arithmetically from the valid sample, not read from ROM.
  5. FUN_0801EF34 computes the checksum over a fresh heap buffer without explicitly zeroing +0x44 first; correctness relies on the allocator returning a zeroed/fresh word there (or on the word's prior value being 0 in practice). One valid sample cannot distinguish these.
  6. Helper bodies called with pointers to persisted fields (func_0x08020152, func_0x08020c70, func_0x0802148a, func_0x08020716, func_0x0801f512, func_0x0801fa78, func_0x08021080, func_0x08020a9a) are absent from the 248-function set; their reads/writes of the mirror are mapped only by call-site context (C3/C4/C8).
  7. FUN_0800AA6A mode 1 (via func_0x0800552c) is unused by the save path and unidentified; the EEPROM device-type-1 (8192-byte) path is dead code for this title as far as the corpus shows.
  8. Only one valid snapshot exists; field value ranges, progression maxima (0xC/0xD clamps suggest 13–14 steps) and bit assignments need the §6 experiments or more captures to confirm.
