Save Format Report — Hoshi no Kirby: Yume no Izumi Deluxe (Japan)

Release key: A7KJ-r0-4d306911d2d7bad5 | Game code: A7KJ | Header family: A7K ROM SHA-256: 4d306911d2d7bad548aaffe13b1d30670a3fd97f9f9d760c247cd2ae3c431c36

1. Executive Summary & Overall Confidence

Overall confidence: LOW.

What is proven (from the raw .sav bytes only, in saves/cap-00-future-0.sav):

  • The 32,768-byte save image contains exactly six 116-byte "active" (non-0xFF) byte ranges, each starting on a 256-byte (0x100) stride: 0x0200, 0x0300, 0x0400, 0x0500, 0x0600, 0x0700.
  • All six active ranges are byte-for-byte identical, including a common 4-byte trailer 65 B9 86 CA.
  • Everything else in the 32 KB image is the uniform fill byte 0xFF (erase/blank state).

What is not proven, and remains open:

  • ghidra/save_related_functions.c reports 0 MMIO save-bus seed functions found anywhere in the 98 trace-guided decompiled functions (ghidra/decompiled.c), and a full-text search of that file for SRAM/Flash/EEPROM/DMA3/checksum/CRC-related keywords and string literals ("save", "Save", "SAVE") returns zero matches. The Ghidra trace that produced this packet simply never executed or captured any save-writer/reader code path for this title.
  • As a direct consequence, no function address, caller chain, checksum routine, or RAM-mirror address in this report can be backed by decompiled code. Every structural claim below is derived exclusively from static inspection of the one available .sav binary, which is why overall confidence is LOW rather than MEDIUM/HIGH.
  • Because only a single .sav snapshot exists (total_sav_files: 6 in the packet metadata refers to the corpus-wide capture count, but only one binary, cap-00-future-0.sav, is actually present in saves/), no byte ever changed across samples (mutated_byte_count: 0), so there is no empirical way to distinguish "this byte is written by gameplay" from "this byte is a fixed compile-time constant" from a single static image.

2. Physical Media, Slot Geometry & Redundancy

  • Declared media: SRAM 256K (per packet metadata; no SDK save tags were detected in the ROM to corroborate this, and the Ghidra trace contains no SRAM-region (0x0E000000) accesses to confirm it directly).
  • Total save image size: 32,768 bytes (0x8000), consistent with a 256 Kbit (32 KB) SRAM/battery-backed-RAM part.
  • Observed slot/copy layout: Six candidate "slots" or "records," each occupying a 256-byte (0x100) region, with only the first 116 bytes (0x00–0x73 relative) of each region populated and the remaining 140 bytes left at the blank fill value 0xFF:

  • Region 0x0000–0x01FF (512 bytes): entirely 0xFF in the one available sample — either unused, or a header/global-config area that has never been written in this capture.
  • Region 0x0800–0x7FFF (the remaining ~31 KB): entirely 0xFF — unused in this capture.
  • Redundancy / selection rule: UNKNOWN. Two competing hypotheses fit the evidence equally well and cannot be distinguished from a single static, all-identical sample:
  1. The six 116-byte blocks are six independent save/record slots (e.g., per-sub-game high-score or file records) that happen to all hold the same freshly-initialized default state.
  2. The six blocks are one logical record replicated six times for wear-leveling/corruption redundancy, with a "pick the valid copy" selection rule that cannot be observed because no copy currently differs and no reader code was traced.

There is no decompiled selection/voting routine to confirm either hypothesis, and no byte-level evidence (e.g., a sequence/generation counter that increments between copies) favors one over the other. This is recorded as HYPOTHESIS in the field map.

  • Generation/sequence counters: None observed. The 4-byte field at relative offset 0x08–0x0B inside each block is 00 00 00 00 in every one of the six identical copies — consistent with either an unused reserved field or a counter still at its initial value of zero; cannot be distinguished with one sample.

3. Save Writer, Reader & Caller-Chain Architecture

No save writer, reader, serialization, checksum, or hardware-I/O function could be identified.

  • ghidra/save_related_functions.c explicitly states: "0 MMIO seeds, 0 total with 2-hop callers + 1-hop callees." This file is the pre-filtered seed list the trace-guided decompilation pipeline uses to find functions that touch SRAM (0x0E000000), Flash command sequences (0x5555/0x2AAA), or EEPROM DMA3 bitstream (0x040000D4)/WAITCNT (0x04000204) MMIO. An empty seed list means the runtime trace that drove this decompilation never executed any instruction touching those address ranges.
  • A manual sweep of all 98 functions in ghidra/decompiled.c (3,833 lines) for the literal address ranges 0x0E0000xx/0x0D0000xx, the strings SRAM/sram/EEPROM/eeprom/FLASH/flash/checksum/crc, and the magic/trailer byte pattern 99999999/ca86b965/65b986ca found zero occurrences. 0x74 appears once (ghidra/decompiled.c:3053, *(undefined4 *)(iVar3 + 0x74) = _DAT_080ce0c0;) but this is a struct-field store inside an unrelated function with no connection (by callgraph or by value) to the save region's active-byte length of 0x74; it is almost certainly coincidental and is not claimed as save-related.
  • ghidra/callgraph.json contains 98 function nodes with caller/callee edges, but since none of the 98 functions are save-I/O candidates (per the seed list above), tracing this graph cannot surface a save caller chain — there is nothing in it to trace to.
  • Conclusion: This report cannot name a single 0x08xxxxxx save writer, reader, or checksum function with any confidence, static or verified. All function-level fields in save-format.json (io_driver_functions, caller_chains) are left empty, and all RAM-mirror addresses (0x02xxxxxx/0x03xxxxxx) in the field map are marked UNKNOWN.
  • Why this matters for future work: this packet's trace capture needs to be re-run with a playthrough that actually triggers an in-game save (e.g., via the pause/save menu) before any code-level save architecture claims can be made for this title. The current decompilation evidently only covers boot/menu/gameplay code paths that never reach the save routine.

  • Conclusion: 65 B9 86 CA is recorded as an unverified candidate magic/checksum trailer, confidence HYPOTHESIS. Two explanations remain open and are indistinguishable from one static sample:
  1. It is a fixed hard-coded magic constant written identically into every freshly-initialized record (most consistent with it being bit-for-bit identical across all six slots, and with no simple checksum formula reproducing it).
  2. It is a computed checksum/CRC using an algorithm not tested here (e.g., a non-standard/table-driven CRC, a checksum seeded with a non-zero initial value, or one covering a different byte range than guessed) that, coincidentally, produces the same result on all six slots because the covered payload is itself identical in all six slots.
  • No code-level proof is possible per Section 3 (zero save-related functions traced), so this cannot be elevated past HYPOTHESIS without a re-trace that captures the actual save-write instruction stream, or without a second .sav sample in which the payload differs so the trailer can be observed changing in response.
