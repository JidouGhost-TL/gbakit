Clean-Room Save Format Report — Diddy Kong Pilot (Unknown) (Proto) (2003)

Release key: RARE-r0-08c9b79d4a16ade4 · Header family: RAR (RARE) · Community: comm-002 ROM SHA-256: 08c9b79d4a16ade44d036dd837d9577881202a5424990839f86551139d421bdf

All findings below are derived exclusively from the files in this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/callgraph.json, and ghidra/save_related_functions.c, cross-checked with standard GBA hardware addresses (EEPROM bus 0x0D000000, DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000).

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_VERIFIED / CONFIRMED_STATIC):

  • The title uses EEPROM 4K (512-byte, 64×8-byte block) backup media, matching the SDK tag

EEPROM_V122@8703148 and the two 512-byte .sav samples in saves/.

  • A low-level 6-function EEPROM driver cluster (FUN_08032680 … FUN_08032958) implements the

classic GBA serial-EEPROM bitstream protocol via DMA3, with distinct read / write / verify entry points.

  • A single higher-level save manager (FUN_0801d55c load/validate, FUN_0801d384 build-default-

record, FUN_0801d2ec write-dirty-blocks-and-verify, FUN_0801d4ec zero-init, FUN_0801d698 force-rebuild-and-flush) drives that driver in 8-byte block units — exactly the EEPROM 4K block granularity.

  • A 4-byte ASCII magic "ERAR" at file offset 0x04 and a constant marker byte 0x16 at file

offset 0x1C are byte-for-byte verified in both .sav samples and have a matching code-level origin (an explicit 4-byte magic-constant copy and an explicit 0x16 literal write) in FUN_0801d384.

  • There is exactly one save slot/copy — the active region is a single contiguous span

(0x04–0x100), with no second magic-duplicated region, no alternating A/B slot, and no generation counter distinguishing multiple copies.

Open / not proven (HYPOTHESIS / UNKNOWN):

  • A running 8-bit subtract-accumulate loop in FUN_0801d384 looks like a checksum routine, but

Python verification against both real .sav files does not match any offset/endianness combination tried against the two observed mutated spans (0x13 and 0xF8–0xF9). It may apply to an entirely different, non-persisted scratch structure, or cover a byte range we have not correctly reconstructed from the decompiled pointer arithmetic. The cold-reload probe in PACKET.md reports "integrity_check_confirmed": false and "reverted_to_blank_on_mutation": false, which is consistent with no enforced checksum on this field actually gating load, or the probe's mutation offset not being covered by whatever check exists.

  • Byte-level correlation of three code-written fields (struct+0x1b hardcoded 0x16,

struct+0x1c..0x1d, struct+0x1e) to file offsets has a ±1-byte residual ambiguity: the decompiler itself flags "Globals starting with _ overlap smaller symbols at the same address" for this binary, and the hardcoded 0x16 write at decompiled offset 0x1b does not land on the real constant byte (file 0x1C) when struct-offset is mapped 1:1 to file-offset. We trust the observed byte (0x1C == 0x16, constant across all samples) over the exact source line attribution.

  • With only 2 .sav samples and 0 paired .ss save states in this packet, no field's semantic

meaning (score, time, level, flags) can be claimed — only its structural role (magic, constant marker, mutating counter-like byte/word) is supported by evidence.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level EEPROM bitstream driver (hardware I/O layer)

All six functions live in a tight 0x0803_2680–0x0803_2990 cluster and were pre-seeded in ghidra/save_related_functions.c as MMIO-adjacent candidates. Confirmed roles from the decompiled bit-serialization logic and DMA3 destination constant 0xd000000 (EEPROM bus, GBA-standard 0x0D000000 with the top nibble truncated by the 24-bit address bus):

0x0803274cRaw DMA3 bit-serial transfer primitiveFUN_0803274c(src, dst, bitcount)Programs DMA3 control registers (_DAT_080327b8 region) and busy-waits on a status bit (while ((uVar2 & 0x8000) != 0)) — this is the generic "clock N bits over the EEPROM serial line" helper shared by read/write/verify
0x080327ccEEPROM Read (8-byte record)FUN_080327cc(block, dst[4]×u16)Serializes a 6-bit "READ" opcode + 6-bit block address via FUN_0803274c(..., 0xd000000, ...), then clocks 68 (0x44) bits back from 0xd000000 and unpacks 4×u16 into dst

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature "ERAR" — CONFIRMED_VERIFIED

  • Offset: file 0x04–0x07 (4 bytes)
  • Bytes: 45 52 41 52 → ASCII ERAR
  • Decompiled origin: FUN_0801d384, line param_1[1] = *(undefined4 *)(iVar8 + 0x1c); — a

4-byte copy from a fixed ROM-constant source into the record being built.

  • Python verification:
$ python3 -c "
a=open('saves/cap-00-future-0.sav','rb').read()
b=open('saves/cap-01-future-1.sav','rb').read()
print(a[4:8], b[4:8])
"
b'ERAR' b'ERAR'

Identical in both samples — verified.

4.2 Marker byte 0x16 — CONFIRMED_VERIFIED (byte), CONFIRMED_STATIC (exact source line, ±1 byte)

  • Offset: file 0x1C (1 byte), constant 0x16 in both samples.
  • Decompiled origin: FUN_0801d384 contains a literal *(undefined1 *)((int)param_1 + 0x1b) = 0x16;

and FUN_0801d55c's validity gate reads *(char *)((int)_DAT_0801d628 + 0x1b) == '\x16'. Mapping decompiled struct-offset 0x1b 1:1 onto file-offset lands one byte short of the real constant (file 0x1b is always 0x00; file 0x1c is always 0x16). Given Ghidra's own warning about overlapping globals in this binary, we treat this as a benign ±1-byte decompiler slip and trust the directly observed, invariant file byte.

  • Python verification:
$ python3 -c "
for f in ['saves/cap-00-future-0.sav','saves/cap-01-future-1.sav']:
    d=open(f,'rb').read()
    print(f, hex(d[0x1b]), hex(d[0x1c]))
"
saves/cap-00-future-0.sav 0x0 0x16
saves/cap-01-future-1.sav 0x0 0x16

4.3 Candidate checksum loop in FUN_0801d384 — HYPOTHESIS (NOT verified against real bytes)

Decompiled code (reproduced from ghidra/decompiled.c lines ~2888–2895):

iVar8 = 0;
uVar6 = 0;
do {
  iVar7 = ((uVar6 & 0xffff) - (uint)*(byte *)((int)param_1 + iVar8)) * 0x10000;
  iVar8 = iVar8 + 1;
  uVar6 = iVar7 >> 0x10;
} while (iVar8 < 0xfe);
*(short *)((int)param_1 + 0xfe) = (short)((uint)iVar7 >> 0x10);

This is a 16-bit running-subtraction accumulator over the first 254 (0xfe) bytes of the record, with the final 16-bit value stored immediately after (+0xfe/+0xff). This pattern strongly resembles a checksum/integrity field, but it operates on param_1, a caller-supplied scratch buffer whose relationship to the persisted 512-byte EEPROM image is not proven 1:1 — FUN_0801d384 is only ever used to build a default record (on first-run / erase), not on every save.

Python verification attempted against the real .sav files (treating file offset 0x00 and 0x04 as candidate bases for the 254-byte range, both little- and big-endian at the stored offset):

saves/cap-00-future-0.sav base=0 computed=0x1fe0 stored(LE)=0xffff stored(BE)=0xffff  -> NO MATCH
saves/cap-00-future-0.sav base=4 computed=0x1de2 stored(LE)=0x0000 stored(BE)=0x0000  -> NO MATCH
saves/cap-01-future-1.sav base=0 computed=0x20df stored(LE)=0xffff stored(BE)=0xffff  -> NO MATCH
saves/cap-01-future-1.sav base=4 computed=0x1ee1 stored(LE)=0x0000 stored(BE)=0x0000  -> NO MATCH

(Bytes at file 0xFE/0xFF and 0x102/0x103 are both inside the all-zero unused tail, which is itself evidence this checksum target offset does not correspond to a meaningful location in the persisted 512-byte image.) Conclusion: no checksum/CRC over the persisted .sav bytes could be confirmed with the available 2 samples. This is consistent with the packet's own cold-reload probe ("integrity_check_confirmed": false).

4.4 Observed mutating spans — HYPOTHESIS (counters, not verified as checksums)

Only 3 bytes differ between the two .sav samples:

If 0xF8:0xF9 is read big-endian as a single 16-bit value, it moves 0x1EB0 → 0x1FA0, a delta of exactly +0xF0 (240) — numerically identical to the magnitude of the nibble that cleared at 0x13 (0xF0 → 0x00 = −240). This is circumstantial (2 samples is not enough to establish causality) but is flagged as the most promising fuzzing lead in §6.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of a valid .sav, with the matching sav-XX-pre.ss emulator save state reloaded immediately before injecting the mutated .sav, and a fresh sav-XX-post.ss captured after the next in-game save/load cycle, per the paired-save-state requirement. This packet currently ships 0 .ss files, so these are unexecuted, planned tests.

  1. Validity-gate negative test — flip file offset 0x1C from 0x16 to any other byte (e.g.

0x00) and reload. Prediction: if FUN_0801d55c's validity gate is actually reached and enforced, the game should take the "rebuild defaults" branch (FUN_0801d4ec→FUN_0801d384→ FUN_0801d2ec), silently rewriting the save to a fresh default record and losing all progress in the 0x08–0xF9 span. This directly tests §4.2's marker-byte hypothesis and would also retroactively validate (or falsify) the struct-offset mapping ambiguity noted there.

  1. Magic-corruption test — flip one byte of "ERAR" at 0x04-0x07 (e.g. 0x04: 0x45→0x00).

Prediction: same rebuild-defaults behavior as test 1, since the validity check is a logical AND of the magic compare and the marker byte.

  1. 0x13 nibble-pair fuzzing — set 0x13 to 0xFF (both nibbles saturated, matching the

neighboring 0x12 byte's constant 0xFF) and separately to 0x00. Prediction: if this is a per-slot counter/flag nibble pair as hypothesized in §3.2/§5, expect an observable change in whatever UI element or RAM-mirrored state array indexes slot 11 of the 12-byte block — compare RAM at the (currently unknown) EWRAM mirror address across both mutations via an .ss diff.

  1. 0xF8-0xF9 counter-carry test — write 0x1E 0xB0 (cap-00's value) then advance gameplay

by the smallest possible observable unit (e.g. one frame / one menu tick) and capture the resulting bytes. Prediction: per §4.4, if these two bytes truly track the nibble cleared at 0x13, incrementing play by the same unit that produced the original cap-00→cap-01 transition should reproduce the identical +0x01 / -0x10 byte delta and the matching 0xF0 clear at 0x13. A mismatch falsifies the circumstantial checksum-adjacent-counter link.

  1. No-checksum-repair control — since §4.3 found no verifiable checksum formula, mutate an

arbitrary byte in the currently-UNKNOWN span 0x20–0xF7 (e.g. 0x50: 0xFF→0x00) without attempting any repair write, then cold-boot. Prediction, per the packet's own probe data (reverted_to_blank_on_mutation: false, save_rewritten_after_mutation: false): the save should load without being flagged corrupt or rewritten, further corroborating that no whole-save checksum is enforced at load time — only (at most) the 0x04/0x1C validity gate.

  1. EEPROM verify-failure injection — if save-state tooling allows intercepting the DMA3

write path, force FUN_08032958 (EEPROM verify, 0x08032958) to return 0x8000 (mismatch) on one block during a FUN_0801d2ec flush. Prediction: per the decompiled logic, a non-zero OR-accumulated return code (iVar6) from the write loop causes the subsequent read-back verify loop to be skipped entirely (if (uVar4 == 0) { ...verify... }), which would be an important, currently unconfirmed reliability gap worth confirming experimentally.
