Corpus used (nothing else): PACKET.md, saves/sav-00-f990.sav (512 B, SHA-256 f0bd9d7c453b044b25fc1192c0072b70c70223b5e8fefeae12a2f47121ad4c20), saves/hexdump_and_diffs.txt, states/*.identity.json (identity metadata only; no state binaries in workspace), ghidra/decompiled.c (160 functions), ghidra/save_related_functions.c (13 functions), ghidra/callgraph.json (160 entries). Addressing convention used throughout this report. Two byte domains must not be conflated:

DomainMeaning
Logical / RAM serialized imageThe 424-byte buffer iVar3 built by the reader at 0x0800a198. Offsets written L+0x…. This is the domain of all decompiled offsets (iVar3 + 0x1a6, uStack_38 * 8 + iVar3, …).
Raw .sav fileThe 512 bytes on disk. Offset written F+0x…. Conversion: for logical offset x, raw offset is (x & ~7) \| (7 - (x & 7)) — i.e. every 8-byte EEPROM block is byte-reversed between disk and RAM (proven in §4).

Ghidra placeholder names such as iRam0800a54c / puRam08007630 are literal-pool locations in ROM (0x0800xxxx), not the numeric RAM values stored there. The workspace contains no ROM binary and no value-resolving pass, so absolute EWRAM/IWRAM numeric addresses of the profile globals cannot be recovered from this corpus. Where this report says "RAM mirror", it gives the exact struct offset and the literal-pool site that references the base, and marks the numeric base UNKNOWN. That is a corpus limitation, not an omission in the search: every 0x02xxxxxx/0x03xxxxxx candidate was looked for; the decompilation contains none for the save profile array (searching decompiled.c for resolved 0x02/0x03 data addresses returns only unresolved iRam0800…/puRam0800… placeholders).

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (core format proven; writer body and sub-field semantics partly outside the traced corpus).

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • The save is a single 424-byte serialized image (0x1A8) inside a 512-byte EEPROM, read in 53 blocks of 8 bytes by the reader at 0x0800a198, with each 8-byte block byte-reversed between the raw .sav file and the RAM buffer.
  • The only checksum in the entire 160-function decompilation is the one in 0x0800a198: low bytes of the 211 little-endian u16s before the checksum slot, summed modulo 256, plus 7. It verifies exactly on the real sample: computed 0xA3, stored 0xA3 (§4, with control experiment).
  • Layout arithmetic closes exactly: 4 × 0x44 serialized profile records (0x000–0x10F) + 15 × 10 repeated second-section records (0x110–0x1A5) + 2-byte checksum slot (0x1A6–0x1A7) = 0x1A8; EEPROM blocks 53–63 (F+0x1A8–0x1FF, 88 bytes) are all 0xFF (never written).
  • On checksum failure (or when called with param_1 != 0) the reader discards the EEPROM image and copies ROM-resident defaults into the RAM profile globals; on success it calls the external unpacker 0x08009168. There is no magic signature, no backup copy, no generation counter in the image.

Static-only (CONFIRMED_STATIC): the full reader flow and RAM profile struct layout (0x60 bytes/slot, 4 slots); the name-entry writer trigger at 0x0800f648 calling the external flush 0x08009944; all caller chains in §3; the fact that the two pre-extracted "save seeds" are not save functions at all (generic VRAM/palette DMA, §3.1).

Unknown / hypothesis (HYPOTHESIS/UNKNOWN): the body of the save writer (0x08009944) and unpacker (0x08009168) — both are called but not present in the 160 traced functions; the exact pack mapping between the 96-byte RAM profile struct and the 68-byte serialized record; semantics of most individual fields (the single sample is a near-blank/new-profile image with almost all gameplay fields zero); the numeric RAM base addresses (unresolved literal pools, see above); what FUN_08000a8c/FUN_08000ac0 install around the EEPROM read.

Sample limitation is material: one .sav, taken at frame 990 (sav-00-f990), apparently right after profile creation. Fields that are zero here may be counters/scores that only move in gameplay; §6 is designed to resolve them.

Geometry note on the block reversal: GBA EEPROM transfers are serial and the SDK/emulator representation stores each 64-bit block big-endian on disk, while the game builds a little-endian RAM buffer. The corpus itself proves the reversal is real and per-8-bytes, not global: reversing the whole 424 bytes or swapping only u16s fails the checksum (control in §4), reversing each 8-byte block passes it exactly, and under that transform the sample becomes structured (4-fold 0x44 periodicity and ASCII-bearing records) instead of noise.

3.3 Reader chain (fully traced)

0x0800681c (main, entry; no callers)
  └─ func_0x0800a198(0)                      [textual edge, decompiled.c:1296; executed at the top of every outer main-loop iteration]
       ├─ func_0x08042a94(4)                 [library probe/configure]
       ├─ FUN_08022554(0x1a8) → iVar3        [heap alloc, 424 B; FUN_08022554 is the allocator, decompiled.c:2759]
       ├─ FUN_08000a8c()                     [bracket open; callgraph edge]
       ├─ 53 × func_0x08042aac(i, iVar3 + i*8), i = 0..52   [EEPROM block reads → RAM image]
       ├─ FUN_08000ac0()                     [bracket close; callgraph edge]

       ├─ pass && param_1==0 → func_0x08009168(iVar3)      [unpack to RAM globals]
       ├─ fail || param_1!=0 → ROM-default copy (below)    [no EEPROM write-back; image is simply not trusted]

Default-copy branch (the "factory reset" path, decompiled.c:1639-1678): for each of 4 slots at slot * 0x60 in the RAM profile array it copies u16 @+0x00; 12 × u32 @+0x04…; 12 × u16 @+0x34…; u16 @+0x4C, +0x4E, +0x50, +0x52; u8 @+0x54; 7 × u8 @+0x56…+0x5C (name). Then for 5 entries at stride 0xC in a second RAM struct it copies three u32-sized fields at +8… and three 7-byte arrays. Source pointers are ROM-side literal-pool references (suffix …a550/…a860/…a868… vs destination …a54c/…a85c/…a864… in Ghidra's naming — distinct literal slots, consistent with ROM→RAM copy). This branch is also the ground truth for the RAM struct layout used in §5.

Other callers of the reader's callees (so they are not mistaken for save code): FUN_08000a8c/FUN_08000ac0 have no other callers in callgraph.json. FUN_08022554/FUN_080224a8 are the general heap allocator/free used all over the game (e.g. 0x0800322c, 0x08003488, title code).

Is 0x08009944 called anywhere else? Corpus-wide textual search: exactly one call site (decompiled.c:2071). Gameplay progress (§3.5) mutates RAM profiles, but no further 0x08009944 call is visible — either the external session functions of §3.5 call it themselves (their bodies are outside the corpus), or progress is flushed at a point the trace did not reach. This is stated as an open question in §6/save-format.json, not assumed.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic signatures: none. No constant byte string is compared anywhere in the reader (its only validation is the checksum below), and no ASCII/header string exists in the used image: logical 0x000–0x10F is binary profile data, and the repeated 20 49 50 53 00 59 00 00 00 00 records at L+0x110… (§5) are data defaults (identical in all 15 records, never tested by code), not a signature. Reporting them as "magic" would be fabrication; save-format.json therefore has an empty magic_signatures list.

Checksum — exact algorithm (from ghidra/decompiled.c:1627-1632):

cStack_39 = '\0';
for (uStack_40 = 0; uStack_40 < 0xd3; uStack_40 = uStack_40 + 1) {
  cStack_39 = cStack_39 + *(char *)(uStack_40 * 2 + iVar3);
}
FUN_08001db4(uRam0800a540, cStack_39 + 7U, *(ushort *)(iVar3 + 0x1a6) & 0xff);   // log site
if (((*(ushort *)(iVar3 + 0x1a6) & 0xff) == (ushort)(byte)(cStack_39 + 7U)) && (param_1 == '\0')) { … }

In words: view the logical image as 212 little-endian u16s. Sum the low byte only of u16[0..210] (i.e. logical bytes 0x000, 0x002, …, 0x1A4) modulo 256 (char accumulator), add 7, truncate to a byte. Compare against the low byte of u16[211] at logical 0x1A6 (its high byte at 0x1A7 is ignored by the comparison and is 0x00 in the sample). Covered logical range: even bytes of 0x000–0x1A5; stored at logical 0x1A6 (= raw file F+0x1A1 after block reversal). No seed other than the +7, no complement, no CRC, no XOR — a plain sum8 + 7. (char signedness is irrelevant modulo 256.)

Python verification against the real sample (run in this workspace; logical image = raw file with each 8-byte block reversed):

Reproduction (exact code executed):

d = open('saves/sav-00-f990.sav','rb').read()          # 512 bytes
ram = b''.join(d[i:i+8][::-1] for i in range(0, 424, 8))  # logical image
computed = (sum(ram[i*2] for i in range(0xd3)) + 7) & 0xff
stored = ram[0x1a6]

The control line is the falsification test: without the per-8-byte reversal the same formula yields 0x4A ≠ 0x59, so the reversal is not cosmetic — it is the on-disk encoding. Conversely the reversal is independently motivated by the reader's 8-byte block structure (uStack_38 * 8 + iVar3, 53 iterations) and by the structured content it reveals (§5). Confidence: CONFIRMED_VERIFIED (formula read from code and matched on bytes, with a failing control).

Note on the tail subfields (L+rec*0x44+0x34…+0x43): with one near-blank sample, any finer split (e.g. calling +0x3B's 0x80 a flag byte, or +0x3D the name) would be guessing from a single data point. They are therefore mapped as one 16-byte tail field here, with the two candidate correspondences (three 01 00 pairs ↔ RAM +0x4C/+0x4E/+0x50; 0x41 ↔ glyph-coded name) recorded as hypotheses to be settled by §6, and mirrored that way in save-format.json.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test below. (1) Work in the logical domain: decode ram = per-8-byte-reverse(raw[0:424]), mutate logical bytes, recompute the checksum, re-encode raw[0:424] = per-8-byte-reverse(ram), keep raw[424:512] = 0xFF. (2) Checksum repair is: ram[0x1A6] = (sum(ram[i*2] for i in range(0xD3)) + 7) & 0xFF (leave ram[0x1A7] at 0). Note the trap: mutating a byte at an odd logical offset does not change the checksum (only even offsets are summed), so "no repair needed" cases below are real predictions, not sloppiness. (3) Reload procedure: write the mutated .sav, cold-boot from sav-00-pre.ss (frame 1), let the game pass the frame-990 point matching sav-00-post.ss, and compare profile-select screen, RAM profile array (slot × 0x60 fields known from §5), and whether a subsequent legitimate profile creation rewrites the image (which would expose the writer's byte layout directly). (4) Always run the unmutated verified image as control: it must load (checksum 0xA3).
