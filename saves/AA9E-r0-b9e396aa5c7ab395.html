  • Clean-room basis: only the files above plus standard GBA hardware addresses

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree, i.e. verified):

  • The save medium is a 512-byte EEPROM (4 Kbit) image. The only save-bus driver in the

corpus, FUN_080e8488 at 0x080e8488, talks to the EEPROM bus at 0x0D000000 through DMA3 programmed by FUN_080e8408 at 0x080e8408. This matches the packet metadata EEPROM 4K and SDK tag EEPROM_V124.

  • A sequential loader, FUN_080e7654 at 0x080e7654, reads exactly 0x1A8 (424) bytes —

53 consecutive 8-byte EEPROM blocks — into a RAM buffer. Both .sav files are non-erased over exactly 0x000..0x1A7 once complete, and bytes 0x1A8..0x1FF are 0xFF in both files.

  • One integrity algorithm is proven end-to-end (Section 4): byte 0x00 must equal the

ones-complement (~, modulo 256) of the 8-bit sum of bytes 0x01..0x1A7. It verifies on sav-01-f1828.sav (stored 0x00, computed 0x00) and

fails on sav-00-f1723.sav (stored 0x00, computed 0xBD). The failing sample is therefore either an incomplete/intermediate EEPROM image or an image the boot validator would reject and reinitialise; this report does not hide that result.

  • Two ASCII byte strings are present at identical offsets in both samples:

AMOT at 0x88 and IIAA at 0x94. They are verified in the .sav bytes only; no code in the corpus compares them, so they are not proven magic signatures.

Static-only (decompiled code, no direct .sav confirmation):

  • The boot/load and validation flow in FUN_080ce3cc (0x080ce3cc), the bit-field unpacker

FUN_080ce710 (0x080ce710), and the deserialiser FUN_080ce8d0 (0x080ce8d0), including a table of 16 records with an 8-byte stride starting at save offset 0x0C and explicit trailer reads at 0x19A..0x1A7 (Section 5).

  • Default-initialisation writes in FUN_080ce3cc that run when the EEPROM read fails or

the checksum does not match.

Open / unknown (stated plainly):

  • No EEPROM write (program) driver exists in the corpus. The only bus function is a

read: it DMAs an address/command bitstream to 0x0D000000, then DMAs 0x44 halfwords back. No function DMAs a 64-bit data payload to the EEPROM, and no other literal 0x0D000000 reference exists in the decompilation. Consequently every field's .sav writer is unattributed, no slot-writing or generation-counter logic can be proven, and "how each caller mutates the RAM struct before flushing" can only be answered for the load/default paths that were traced, not for a flush path.

  • No absolute RAM mirror address can be given. Ghidra left every relevant pointer as

an unresolved _DAT_080xxxxx literal-pool symbol (for example _DAT_080ce474, _DAT_080e7670, _DAT_080e8534); their target values are not in the corpus. Fields below therefore carry ram_addr: null and are located relative to the save-buffer base.

  • The exact numeric bound _DAT_080ce544 of the checksum loop is unresolved. The covered

range 0x01..0x1A7 is inferred because (a) the loader length is exactly 0x1A8, (b) the loop increments one byte at a time starting at buffer+1, and (c) that exact range verifies on sav-01 and fails on sav-00. See Section 4.

  • sav-00 failing the checksum, and the purpose of the dense regions at

0x98..0xB7, 0xC0..0xDF, and 0x148..0x177, remain hypotheses (Sections 5–6).

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two sources were cross-checked:

  1. The call graph (221 nodes). It records the edge

0x080e8488 -> 0x080e8408 and callers: [0x080e8488] for 0x080e8408, but it records

no callers and no callees for 0x080ce3cc, 0x080ce710, 0x080ce8d0, 0x080e7654, or 0x080e8488. This is because those calls go through Ghidra's func_0x08xxxxxx pseudo-names and unrecovered jumptables (WARNING: Could not recover jumptable), which the graph builder did not resolve.

  1. Textual func_0x08xxxxxx(...) call sites in the decompilation,

which recover exactly the edges the graph misses. Each chain below cites the line of the call site so the mapping is auditable. Line numbers refer to the decompilation in the workspace.

Any caller not reachable by either method is reported as "no caller in corpus", never guessed.

3.2 Low-level hardware I/O driver

FUN_080e8408 (0x080e8408) — DMA3 transfer primitive

  • Role: generic DMA3 copy used by the EEPROM driver. It saves and clears an interrupt-related

halfword (*_DAT_080e8468), masks a control register (*_DAT_080e846c & (ushort)_DAT_080e8470 | *(ushort *)(*_DAT_080e8474 + 6)), then writes source to *_DAT_080e8478, destination to *_DAT_080e847c, and param_3 & 0xFFFF | 0x80000000 (DMA enable, bit 31) to *_DAT_080e8480, and spins while the busy bit (0x8000 of the high halfword) is set. By the standard GBA map these are DMA3SAD 0x040000D4, DMA3DAD 0x040000D8, DMA3CNT 0x040000DC; the literal register addresses are DAT-unresolved in the corpus, so the identification is by register-write pattern and order, labelled CONFIRMED_STATIC.

  • Callers (callgraph + text): only FUN_080e8488 (two call sites, lines 8575–8576).

FUN_080e8488 (0x080e8488) — EEPROM 8-byte block read (the sole MMIO seed)

  • Signature: FUN_080e8488(uint block_address, int dest_buffer).
  • It masks the address to 16 bits and rejects it if >= *(ushort *)(*_DAT_080e84a0 + 4)

(an EEPROM block-count limit whose literal value is unresolved).

  • It builds a serial bitstream on the stack (auStack_96[67], one bit per halfword):

the address bits (count = byte at *_DAT_080e8534 + 8), preceded by two 1 bits (start + read-opcode pattern), then DMAs address_bits + 3 halfwords from the stack to the EEPROM bus 0x0D000000 via FUN_080e8408(auStack_98, 0xd000000, ...) (line 8575).

  • It then DMAs 0x44 (68) halfwords from 0x0D000000 back to the stack (line 8576)

and repacks 64 data bits, 16 at a time, into four halfwords written to dest+6, dest+4, dest+2, dest+0 (reverse halfword order). Net effect: one 8-byte EEPROM block lands at dest[0..7]. It returns 0 on success and the sentinel uRam080e84a4 on an out-of-range address.

  • Callers: none in the call graph; textually exactly one —

FUN_080e7654 (line 8042, func_0x080e8488(*piVar1, param_1)).

  • Write counterpart: absent. A program operation would need a start/write-opcode

bitstream (1,0 pattern), a 64-bit data phase DMA'd to 0x0D000000, and a busy-wait; no such function, and no second 0x0D000000 literal, exists in the corpus. All "writer" attributions below are therefore negative findings, not omissions of this report.

3.3 Sequential reader (deserialisation front end)

FUN_080e7654 (0x080e7654) — read length bytes from consecutive EEPROM blocks

  • Loop (lines 8024–8058): if length == 0, return 1 (success); otherwise

result = FUN_080e8488(*block_counter, dest); on non-zero return 0 (failure); else (*block_counter)++, dest += 8, length -= 8.

  • Callers: none in the call graph; textually exactly one — FUN_080ce3cc (line 292):

func_0x080e7654(_DAT_080ce474, 0x1a8), i.e. read 424 bytes into the save buffer.

3.4 Load, validate, default-initialise: FUN_080ce3cc (0x080ce3cc)

Entry point of the save system. It has no caller in the corpus (call graph: no callers; no textual func_0x080ce3cc call site) and is presumably reached from boot code outside the 221 traced functions or via an unrecovered jumptable. Its flow:

  1. Calls func_0x080e7290() (FUN_080e7290, line 290) — a pre-load hardware/system

initialisation routine (calls FUN_080e83c0(4), FUN_080e6014(), FUN_080e3b68()); it does not touch EEPROM and is not save-specific.

  1. ok = FUN_080e7654(save_buffer, 0x1A8) (line 292).
  2. Read-failure branch (ok == 0): copies a default block into the buffer with the

BIOS CpuSet wrapper func_0x080e8380 (SWI 0x0B, FUN_080e8380 at 0x080e8380), applies the default field writes listed in §3.5, then calls FUN_080ce710(), FUN_080ce8d0(), and FUN_080e763c() (a flag-setting routine: FUN_080e5574() plus two = 1 stores).

  1. Read-success branch (ok != 0): runs the checksum of Section 4 over the buffer.
  • On match: sets the valid flag *puRam080ce574 = 1 — and, notably, does not call

the unpackers in this decompiled branch; any later unpack must happen in a caller outside the corpus.

  • On mismatch: copies defaults over the buffer (func_0x080e8380), applies the same

default field writes, calls FUN_080ce710() and FUN_080ce8d0(), and clears the state word *_DAT_080ce560 = 0.

3.5 Default field writes in FUN_080ce3cc (both failure paths)

These are the only proven "mutations of the in-RAM save struct" in the corpus. Offsets are buffer-relative; puVar1/puVar4 are the buffer base in the two branches.

  • byte[1] = byte[1] & 0xFC | 0x01; byte[6] = byte[6] & 0x1F | 0x20
  • u16[2] = (mask & u16[2]) | 0x0200; u32[0] = (mask & u32[0]) | 0x20000
  • byte[12] = 0x10; byte[13] = byte[14] = byte[15] = byte[16] = 0xFF
  • byte[20] = 0x11; byte[21] = byte[22] = byte[23] = byte[24] = 0xFF
  • u32[8] = (mask & u32[8]) | 0x8000 (buffer offset 0x08)
  • u32[0x8C] = *source_u32; byte[0x90] = (byte)(source_u32[1]) — a 5-byte copy whose

source is a DAT-unresolved constant/struct outside the buffer.

Caution: these defaults do not byte-match the observed .sav header (observed byte[1] = 0x20, byte[6] = 0x01, byte[12] = 0x00). Therefore either the defaults are later transformed by the (absent) serialiser/bit-packer before being written, or puVar1's base is a working-RAM struct that is not byte-identical to the EEPROM image. This mismatch is why header-field semantics below are capped at HYPOTHESIS even where the offsets are code-proven.

3.6 Unpackers called by the load path

FUN_080ce710 (0x080ce710) — bit-field unpack of header bytes 0x00..0x05

Reads the save buffer (puVar3) and writes a different RAM struct (puVar2). It extracts, among others: byte[1] & 3, (byte[2] & ...), (u32[0] & 0x3FFFF) >> 10, (u16[2] & 0x3FF) >> 2, byte[3] bit fields (& 7, & 0x1F, >> 5), and (u16[4] & 0x1FFF), (u32[4] & 0x1FFFFF) >> 13. It proves bytes 0x00..0x05 are a packed header, not plain scalars; individual game meanings are unknown. Callers: textual only, FUN_080ce3cc (three func_0x080ce710 sites corpus-wide include its own callees); no call-graph edges.

FUN_080ce8d0 (0x080ce8d0) — main deserialiser into working RAM

With src = save buffer (iVar10) and dst = working struct (iVar9):

  • 16 records, 8-byte stride, from src+0x0C: for record i (0..15),

u32 dst_entry[+8] = (u32)(byte)src[0x0C + 8i], and each signed byte src[0x0C + 8i + 1 .. +4] becomes either -1 (if the byte is -1/0xFF, a sentinel) or value << 11 in four separate dst arrays (stride 0x1C per entry). The remaining 3 bytes of each record (+5..+7) are not consumed here.

  • Four bulk copies of lengths 9, 180 (0xB4), 40 (0x28), and 40 (0x28) bytes

between DAT-unresolved absolute pointers. Their lengths are proven; their save-buffer offsets are not recoverable from the corpus, so they are not assigned to offsets in the field map (doing so would be fabrication). They do prove sizeable contiguous regions of the image are copied verbatim into RAM.

  • Header bit-fields: bytes src[7], src[8], src[9], src[10], src[11] are

disassembled bit-by-bit into dst flag bytes, a u16 at dst+0x2CC ((src[8] & 0x7F) << 2 | src[7] >> 6), and a pointer computed as byte_value * 0x1C + base, i.e. one header byte indexes a 28-byte record table.

  • Trailer: u16 dst[0x1D8] = u16 src[0x19A], u16 dst[0x1DA] = u16 src[0x19C],

u32 dst[0x1D4] = u32 src[0x1A0], u32 dst[0x1D0] = u32 src[0x1A4] (note the 0x1A0/0x1A4 order swap).

Callers: textual only, FUN_080ce3cc (twice: read-failure and checksum-failure branches).

3.7 Caller chains (complete for the corpus)

  • Chain A (load/validate/default):

`[entry outside corpus] -> FUN_080ce3cc (0x080ce3cc) -> FUN_080e7654 (0x080e7654)

-> FUN_080e8488 (0x080e8488) -> FUN_080e8408 (0x080e8408, DMA3 to 0x0D000000). Side calls: FUN_080e7290, FUN_080ce710, FUN_080ce8d0, FUN_080e763c, SWI wrappers FUN_080e8380 (CpuSet, SWI 0x0B) and, elsewhere, FUN_080e837c (CpuFastSet, SWI 0x0C).   • Chain B (writer): does not exist in the corpus. No caller mutates the save struct

"before flushing", because no flush function was traced. Any report claiming a writer address from this corpus alone would be inventing it. The writer presumably lives in functions never executed during the trace-guided capture (the packet's cold-reload probe shows a save does persist at runtime, so a writer exists in the full ROM — it is simply not among these 221 functions).

3.8 Other searched-and-rejected driver families

  • SRAM/Flash: no 0x0E000000, 0x5555, 0x2AAA, or WAITCNT (0x04000204) reference in

the decompilation. Rejected.

  • Other DMA3 users: FUN_080e8408 is called only by FUN_080e8488. No second save driver.
  • FUN_080e8a6c/FUN_080e8ad0 (end of the decompilation) are RAM memcpy/memset helpers

(word/byte copies and byte fills), not save I/O; they never reference 0x0D000000.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Checksum — exact formula

  • Name: eeprom_image_sum8_complement
  • Stored location: byte offset 0x00, size 1 byte.
  • Covered range: byte offsets 0x01..0x1A7 inclusive (423 bytes; the whole loaded

image except the checksum byte itself). The exclusive end 0x1A8 equals the loader length in FUN_080ce3cc.

  • Formula: stored == (~(sum of all covered bytes mod 256)) & 0xFF, equivalently

stored == (0xFF - (sum mod 256)), equivalently (stored + sum) & 0xFF == 0xFF. It is an 8-bit additive sum with ones-complement, little-endian-independent (byte-wise), seed 0, no XOR key, not a CRC.

  • Decompiled proof (FUN_080ce3cc, read-success branch): starting with

bVar2 = 0, the loop starting at the buffer base pre-increments a byte pointer and adds each signed char into bVar2 (which wraps modulo 256 as a byte), iterating while uVar5 <= _DAT_080ce544; the test is if ((byte)*_DAT_080ce548 == (byte)~bVar2). The unresolved bound _DAT_080ce544 is the one gap: the covered end was pinned to 0x1A7 by the loader length plus the byte verification below, not by reading the literal out of the corpus.

  • Recompute/repair rule (for fuzzing): after mutating any byte in 0x01..0x1A7, set

byte[0] = (~sum(bytes[1..0x1A8])) & 0xFF (Python slice end 0x1A8).

Interpretation:

  • sav-01-f1828.sav is a verified-valid image under this algorithm.
  • sav-00-f1723.sav is not valid as dumped: its bytes 0xB8..0x1A7 are still erased

(0xFF), and summing them gives 0x42/~0xBD. Either that snapshot caught the EEPROM before a later write completed the region and the checksum (frame 1723 precedes the frame-1828 save), or it is an image the boot validator would reject and replace with defaults. Both samples share bytes 0x01..0xB7 except offsets 0x07 and 0x0E, whose changes (+0x40, -0x40) cancel in the sum — consistent with normal field updates that do not by themselves invalidate or repair a checksum.

  • No other integrity field was found: no second stored sum, CRC, or XOR field is compared

anywhere in the corpus, and brute-forcing plain/~/negated sum8 over every prefix 1..N produced only the N = 0x1A7 match on sav-01 (plus chance matches on sav-00 at unrelated prefixes, as expected for a 1-byte check value).

4.3 Magic signatures

  • AMOT at 0x88 (41 4D 4F 54) and IIAA at 0x94 (49 49 41 41): present identically

in both samples, hence verified in .sav. No instruction in the corpus loads or compares these constants (a literal search for AMOT/IIAA/their little-endian word forms finds nothing), so they are not verified in code and are classified HYPOTHESIS as signatures. Alternatives that cannot be excluded: player/profile names or codes stored as text, or coincidental ASCII inside record data — note 0x88 lies inside the span the record table of FUN_080ce8d0 would cover (0x0C + 8*15 + 4 = 0x88), so the "name/signature" reading and the "record byte" reading conflict; only fuzzing (Section 6) can separate them.

  • There is no header magic at offset 0x00: offset 0x00 is the checksum, and the

following header bytes are packed bit-fields (Section 3.6), not a constant signature. A blank/erased image is detected by checksum failure, not by a missing magic.

6. Save Fuzzing & Counterfactual Verification Plan

Base image for all tests: sav-01-f1828.sav (the only checksum-valid sample). Paired states: reload from sav-01-pre.ss / sav-00-post.ss (frame 1723) and sav-01-post.ss / gameplay.ss (frame 1828), with final.ss (frame 1877) as the post-gameplay reference. Unless a test says otherwise, apply the mutation, repair the checksum (byte[0] = (~sum(bytes[0x01..0x1A7])) & 0xFF, Python: d[0] = (~sum(d[1:0x1A8])) & 0xFF), cold-reload, and compare (a) whether the game accepts or discards/defaults the save, (b) menu/profile/deck state against the unmodified control, and (c) the next .sav the game writes after any in-game save action, byte-diffed against the input.

Controls (run first):

  • C0 — unmodified reload. Reload sav-01 unchanged. Prediction: accepted, no reset to

defaults. This reproduces the packet's cold-reload probe (save_preserved: true).

  • C1 — checksum byte corruption, no repair. Set byte[0x00] ^= 0xFF. Prediction from

FUN_080ce3cc: checksum mismatch → defaults are installed, the valid flag path is not taken, and the previous progress is lost/defaulted. If the save instead loads normally, the Section 4 algorithm or covered range is wrong.

  • C2 — covered byte corruption, no repair. Flip one bit at 0x100 without repairing.

Same prediction as C1. Together C1/C2 prove the stored byte and the covered range are causally linked, not coincidentally equal on one sample.

  • C3 — unused-tail mutation, no repair needed. Write 0x00 over 0x1A8..0x1FF.

Prediction: no observable change and no rejection, because the loader never reads past 0x1A8 and the checksum excludes the tail. Any behavioural change falsifies the loader-length claim.

Field-identification tests (all with checksum repair):

  • F1 — header bit-fields (0x01..0x06). Mutate one bit at a time in 0x01, then

0x02, then 0x06. Prediction: if FUN_080ce710's unpacking feeds profile/options state, exactly the corresponding menu/profile attribute changes while other state is untouched. A change in an unexpected subsystem maps that bit by counterfactual.

  • F2 — the changing byte (0x07). Set 0x07 from 0xA7 back to sav-00's 0x67

(and separately 0x0E from 0x80 back to 0xC0; note the pair sum cancels, but repair anyway). Prediction from FUN_080ce8d0: flag bytes and the * 0x1C record-table index derived from byte 0x07 change; watch whichever UI/gameplay mode those flags gate. Reverting both should reproduce the frame-1723 (sav-00) state if these are progress fields.

  • F3 — record sentinel (0x0D, record 0 byte +1). Set 0x0D to 0xFF, then to

0x02. Prediction: with 0xFF, the corresponding deserialised slot becomes -1 (absent/empty); with 0x02 it becomes 0x02 << 11 = 0x1000 in RAM. Observe whether a visible entry (card/deck slot) disappears or changes. Repeat at 0x15 (record 1) to confirm the 8-byte stride: the same class of entry should move by one slot.

  • F4 — record value byte (0x0C, record 0 byte +0). Increment 0x0C. Prediction:

the zero-extended byte stored by FUN_080ce8d0 changes for entry 0 only; a count/ID change in the first entry, with entries 1..15 untouched, confirms record semantics.

  • F5 — AMOT test (0x88). Change one letter (AMOT → BMOT). Two outcomes

separate the hypotheses of Section 4.3: if acceptance or displayed text changes and no record-15 behaviour moves, it is a name/signature; if instead the 16th record's +4 value (scaled << 11 in RAM) changes behaviour and nothing textual moves, it was record data all along. Also try erasing 0x88..0x8B to 0xFF: a name field should show blank/default text, a sentinel byte should make that record component "absent".

  • F6 — IIAA test (0x94). As F5, one letter at a time. Independent behaviour change

would promote it from HYPOTHESIS; no change keeps it as (possibly cosmetic) text data.

  • F7 — dense late region (0x148..0x177). Zero the whole range, then mutate single

bytes at 0x160 (the ASCII-like 2589… run) and 0x148. Prediction: if this is text/code data, the corresponding screen shows altered characters or a rejected code; if it is packed numeric data, a counter/stat changes instead. The result decides the charset question raised in the field map.

  • F8 — trailer fields (0x19A, 0x1A7). Set u16[0x19A] to 0x0001; separately set

byte 0x1A7 from 0x07 to 0x00. Prediction from FUN_080ce8d0: the working-RAM words at dst+0x1D8 / dst+0x1D0 change on load; observe which persistent attribute (count, unlock, timer) follows. This also resolves whether 0x1A7's 0x07 is a big-endian-looking low value or the high byte of 0x07000000.

  • F9 — sav-00 resurrection test. Take sav-00-f1723.sav, repair its checksum to the

computed 0xBD without changing anything else, and reload. Predictions: (a) if the game now accepts sav-00's state, the checksum was the only blocker and sav-00 was a complete but stale-checksum image; (b) if it accepts but shows defaults, the erased 0xB8..0x1A7 region is load-critical; (c) if it still rejects, a second validation exists outside the traced code. Each outcome is decisive for a different open question.

  • F10 — write-path discovery (addresses the biggest gap). From a reloaded valid save,

perform one minimal in-game change (one menu/option toggle), trigger the game's own save, and diff the resulting .sav against the input at 8-byte block granularity. Prediction: whole EEPROM blocks (multiples of 8 bytes) change, byte 0x00 changes to the recomputed complement, and the changed blocks identify which fields that action owns. Repeating with different single actions substitutes for the missing writer function and converts UNKNOWN/HYPOTHESIS rows into observed mappings.

Negative/robustness tests:

  • N1 — truncation/extension. Reload a 424-byte truncated file and a 1024-byte

zero-padded file. Prediction: the emulator/game behaviour is driven by the first 0x1A8 bytes; any difference isolates emulator EEPROM-size handling, not game logic.

  • N2 — all-erased image. All 0xFF (512 B). Prediction: read succeeds at the bus

level (EEPROM reads erased cells as 0xFF), the computed complement does not equal the stored 0xFF, and the game installs defaults — the "new game" path of FUN_080ce3cc. An all-0x00 image should behave differently (its checksum byte 0x00 vs computed ~0x00 = 0xFF also fails, by a different value), confirming the validator distinguishes content, not just blankness.

  • N3 — double mutation with repair at two offsets. Mutate 0x07 and 0x148

together with a single repair. Prediction: both F2 and F7 effects appear together, confirming fields are independent bytes under one checksum rather than an interleaved/ECC layout (which would corrupt neighbouring fields).

Every test above is executable with the paired .ss states in states/ and a byte editor or a short Python mutation script using the repair one-liner in Section 4.1. No test requires knowledge outside this workspace.
