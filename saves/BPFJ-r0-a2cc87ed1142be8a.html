1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM-LOW.

What is proven:

  • The cartridge uses an EEPROM 4K device (512 bytes), confirmed by the corpus save-profile metadata and by the fact that both .sav files are exactly 512 bytes.
  • cap-00-future-0.sav is entirely 0xFF (factory-blank EEPROM). cap-01-future-1.sav has exactly 408 bytes (0x000–0x197) of non-0xFF data, with the remaining 104 bytes (0x198–0x1FF) staying 0xFF. This gives us one clean "before → after first save" pair, but only one populated sample, which caps how confidently any field can be generalized.
  • The low-level EEPROM hardware I/O driver (DMA3-driven serial bitstream read/write/verify/retry) is fully decompiled and its internal call graph is closed (verified in ghidra/callgraph.json and ghidra/decompiled.c).
  • A 16-bit big-endian additive checksum candidate at offset 0x190 reproduces the exact stored bytes for the one populated .sav, over a precisely-bounded byte range (0x02A–0x18F), verified by direct Python computation (Section 4).

What is NOT proven (open/unknown):

  • No caller chain exists in the traced 109 functions from any game-logic function into the EEPROM driver. FUN_08067774 (write) and FUN_0806792C (write-verify-retry) both show "callers": [] in ghidra/callgraph.json. This means the trace-guided decompilation captured the generic hardware driver but not the game-specific serialization/deserialization code that builds the 512-byte buffer shown in the hexdump. No "writer calls driver" edge is directly observable in the evidence provided.
  • No checksum-computation routine was found among the 109 decompiled functions, so the checksum candidate in Section 4 is sav-verified but not code-verified (schema confidence HYPOTHESIS, not CONFIRMED_VERIFIED).
  • The large repeating tagged-chunk region (0x02A–0x18F) has an obvious syntactic structure (length-prefixed 3-byte tags + numeric fields, appearing twice in different orderings) but its semantic meaning is unknown — this report deliberately does not guess game-specific meaning (e.g. what the chunks represent) since that would violate clean-room rules without decompiled serializer code to back it up.
  • With only one populated sample, no field-level "this byte changes, that byte doesn't" differential evidence exists — the entire 408-byte region flips from 0xFF in one single write event, so we cannot yet separate "always-written" fields from "conditionally-written" fields. This is flagged as a required follow-up (Section 6).

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (fully traced, closed call graph)

All addresses below are confirmed via ghidra/decompiled.c and cross-checked against ghidra/callgraph.json. This is the generic EEPROM serial-bitstream driver that any GBA EEPROM-backed title uses; it is standard-hardware-pattern code, not a game-specific discovery.

3.2 Caller chain into game logic — UNTRACED

This is the most important honest gap in this report: ghidra/callgraph.json lists "callers": [] for both 0x08067774 and 0x0806792c. A full-text search of all 109 functions in ghidra/decompiled.c for FUN_08067774 and FUN_0806792c turns up only their own definitions and the internal edges listed above — no other function in the available decompilation calls into this driver.

Conclusion: the trace-guided decompilation seed set captured the generic EEPROM hardware driver in isolation, but the game-specific save-serialization function(s) that build the 408-byte buffer (header string, chunk table, checksum) and invoke FUN_0806792c once per 8-byte block are outside the 109 traced functions. We cannot claim any caller-chain mapping for "how the in-RAM save struct gets flushed" beyond the driver itself. This must be re-run with a wider or differently-seeded Ghidra trace (seeded from the EEPROM driver entry points themselves, tracing upward instead of relying on the existing downward seed) before this gap can be closed.

3.3 In-RAM save struct

No 0x02xxxxxx (EWRAM) or 0x03xxxxxx (IWRAM) address was observed as an argument to FUN_0806792c or FUN_08067774 within the traced functions, because no caller was traced at all (3.2). The location, size, and layout of any in-RAM mirror of the save struct is UNKNOWN from the available evidence.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Header bytes (not a classic ASCII magic, but a fixed-format string)

Offset 0x000–0x00F (16 bytes) decodes as 8× big-endian 16-bit code units, each with a zero high byte — i.e. a fixed-width string encoded one ASCII byte per 16-bit slot:

00 4F 00 59 00 55 00 50 00 32 00 30 00 30 00 46
→ "O" "Y" "U" "P" "2" "0" "0" "F"  (reading low byte of each pair)

This is verified in the .sav file (byte-exact) but not verified in code (no serializer function was found that writes this literal string — see 3.2). Confidence: CONFIRMED_STATIC is not applicable since there's no code backing; this is CONFIRMED_VERIFIED only as "these bytes are present in the one real .sav sample" — the generating function is unknown. It is not claimed to be a conventional "magic number" in the sense of a fixed constant checked at load time, since no load-time comparison code was found.

4.2 Checksum candidate — Python-verified against the real .sav

Algorithm: 16-bit big-endian additive checksum (sum of all 16-bit big-endian words in the covered range, truncated mod 0x10000).

Covered range: 0x02A–0x18F inclusive (358 bytes, 179 words).

Stored location: 0x190–0x191, interpreted big-endian (i.e. byte 0x190 is the checksum's high byte).

Verification script and exact output (run against saves/cap-01-future-1.sav):

import struct
data = open('saves/cap-01-future-1.sav','rb').read()

def sum16be(b):
    s = 0
    for i in range(0, len(b) - (len(b) % 2), 2):
        s += struct.unpack('>H', b[i:i+2])[0]
    return s & 0xffff

computed = sum16be(data[0x2a:0x190])
stored   = struct.unpack('>H', data[0x190:0x192])[0]
print(f"computed=0x{computed:04x} stored=0x{stored:04x} match={computed == stored}")

Output:

computed=0x5f1d stored=0x5f1d match=True

A brute-force scan over every (start, end) window pair in [0x0, 0x190] found that **start=0x2A, end=0x190, big-endian 16-bit sum is the only window whose checksum matches the stored value (adjacent-byte windows 0x2C, 0x20, 0x10, 0x0 as start, and 0x18C/0x18E/0x192/0x194/0x198 as end, were all tried and do not** match — see raw search output retained in this session). This precisely pins the covered range.

Why big-endian (MSB-first) is plausible on hardware grounds: the EEPROM driver (FUN_080676b0, Section 3.1) explicitly packs and unpacks each 16-bit word bit-by-bit, MSB first, and writes/reads words in descending pointer order. A checksum generated by code that walks the same in-RAM buffer the same way the serial driver does would naturally produce a big-endian-looking sum. This is a plausible, hardware-consistent explanation but is not itself proof of a specific checksum function — no such function was found in the 109 decompiled functions.

Confidence: HYPOTHESIS. It is .sav-verified (byte-exact, uniquely-bounded match) but not code-verified (no decompiled checksum routine). Per the clean-room honesty rule, this cannot be elevated to CONFIRMED_VERIFIED, which requires both code and .sav proof.

Important caveat: with only one populated sample, a single matching window cannot fully rule out coincidence, although the uniqueness of the exact-boundary match (only 0x2A..0x190, no other tested window matches) is reassuring. This must be confirmed with a second independently-generated save (different in-game state) per Section 6.

4.3 No other checksums/magics found

  • No CRC16/CRC32 (zlib polynomial) match was found over any tested window.
  • No XOR-based checksum match was found.
  • No second magic/signature was found anywhere else in the 408-byte active range.

6. Save Fuzzing & Counterfactual Verification Plan

Given the single-populated-sample limitation (Section 1), the highest-value next steps are:

  1. Second independent save sample (different in-game state).
  • Mutation: None needed — just capture a second, different, legitimately-produced save (e.g. different progress/options than cap-01).
  • Predicted effect: If the 0x02A–0x18F → 0x190 checksum relationship (Section 4.2) is real, the new sample's checksum at 0x190 will also match a fresh sum16be(data[0x2A:0x190]) computation. If it's coincidence, it likely will not.
  • Requires checksum repair: No (this is a read-only comparison, not a mutation).
  1. Single-byte mutation inside the chunk table, checksum left stale.
  • Mutation: Flip one byte inside 0x02A–0x18F (e.g. 0x30 → 0x31 at offset 0x2B) without updating 0x190–0x191.
  • Requires checksum repair: Yes — recompute sum16be over 0x02A–0x18F and write the new value at 0x190 (big-endian) to test whether the game accepts a repaired checksum, vs. leaving it stale to test whether the game rejects/resets the save on a checksum mismatch (this is the real test of whether 0x190 is actually read/enforced at load time).
  • Predicted effect: With a correct checksum repair, gameplay should load normally with the mutated byte's effect visible wherever that chunk-table entry is actually consumed (currently unknown — this is exactly what the mutation should reveal). With a stale (unrepaired) checksum, if 0x190 is truly validated at load, expect a reset-to-blank or an error/retry state; if nothing changes, 0x190 is not actually validated as a load-time gate and is more likely a different kind of counter.
  1. Zero out 0x192–0x197. (Already zero in the one sample — mutate to non-zero instead.)
  • Mutation: Write non-0x00 bytes into 0x192–0x197.
  • Requires checksum repair: Unknown — first determine whether this range is inside or outside any checksum coverage (current evidence says outside, since the verified checksum range stops at 0x18F).
  • Predicted effect: If this is genuinely unused reserved space, no observable effect. If it's a secondary counter not yet exercised by the one sample, expect either corruption-handling behavior or a visible counter change next time the game writes a save.
  1. Wipe 0x198–0x1FF from 0xFF to 0x00, then reload.
  • Mutation: Fill the declared-unused tail with 0x00 instead of 0xFF.
  • Requires checksum repair: No (this range is outside the active/checksummed range as currently understood).
  • Predicted effect: No observable effect if truly unused EEPROM space; any visible effect would falsify the "408 bytes active, rest unused" boundary claimed in Section 2.
  1. Upstream caller-chain re-trace (not a .sav mutation, but required to close the open items in Section 3.2).
  • Re-run the Ghidra trace seeded from 0x0806792c and 0x08067774 as entry points, tracing callers upward (rather than the current downward seed from an assumed MMIO address), to find the actual game-specific save-serialization function(s) and any in-RAM save struct address.
  • Predicted effect: Should surface at least one 0x08xxxxxx function that calls 0x0806792c in a loop (once per 8-byte EEPROM block, 51 times for the observed 408-byte payload) and that references an EWRAM/IWRAM buffer matching the header+chunk-table layout in Section 5.

All of the above should be executed against paired pre/post .ss emulator save states per the standing project rule (not available for this legacy checkpoint cohort — states/ is currently empty), so that RAM-level before/after effects can be inspected directly rather than inferred solely from .sav bytes.
