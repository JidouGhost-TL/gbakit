GBA Save Format Reverse-Engineering Report — Harry Potter and the Sorcerer's Stone (USA, Europe) (En,Fr,De,Es,It,Nl,Pt,Sv,No,Da)

Release key: AHRE-r0-9532eeccbeeb09e3. Game code AHRE, header family AHR. ROM SHA-256 9532eeccbeeb09e36706b53a362239f9db59935799b62d089e93f9d5381058d8. Engine/SDK community comm-004.

Corpus inspected: PACKET.md, cap-00-future-0.sav, cap-01-future-1.sav, hexdump_and_diffs.txt, decompiled.c (201 functions, 7,808 lines), save_related_functions.c (5 functions), and callgraph.json (201 nodes, 57 direct edges).

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes:

  • The save medium is serial EEPROM accessed through DMA3 at 0x0D000000, not byte-wide SRAM at 0x0E000000 and not Flash command sequences at 0x5555/0x2AAA.
  • The low-level driver transfers EEPROM data in 8-byte (64-bit) blocks: FUN_080375c0 reads one block and FUN_08037670 writes one block.
  • The retained image is exactly 512 bytes in both captures, matching EEPROM 4K (4 Kbit) in the packet metadata and the SDK tag EEPROM_V122.

Proven on the .sav side plus the behavioral cold-reload probe, but not located as a routine in the 201-function decompilation:

  • An 8-byte ASCII signature Q00ABGPH sits at offset 0x00 in both captures.
  • A one-byte additive integrity value sits at offset 0x08. It equals the bitwise NOT of the 8-bit byte sum of the covered bytes. It matches both captures. Mutating offset 0x08 in the probe caused the save to be treated as blank and rewritten, which independently confirms an integrity gate at that offset.

Static-only or unresolved:

  • No function in the decompiled set contains the literal Q00ABGPH, the constant 0x51, or an identifiable byte-sum checksum loop. The checksum computation and magic comparison therefore were not located in code. They may live outside the 201 traced functions, in a data-driven routine, or behind an unresolved indirect call.
  • FUN_080375c0 and FUN_08037670 have no callers in callgraph.json. 158 of 201 functions have no recorded caller and there are only 57 direct edges, while the decompilation contains 254 UNRECOVERED_JUMPTABLE indirect-tail warnings. The serialization layer and gameplay callers that feed the EEPROM driver are therefore not resolvable from this corpus. Any claim naming them would be fabrication, so this report names the driver layer exactly and marks the upper chain open.
  • No RAM mirror address (0x02xxxxxx/0x03xxxxxx) can be given. The Ghidra export leaves every _DAT_08037xxxx literal unresolved, and the decompilation contains no 0x020/0x030 address literal. The EEPROM type-config structure pointer is likewise unresolved.
  • Only offsets 0x00–0x0F are non-fill in either capture. Everything from 0x10 to 0x1FF is 0x00. Field semantics beyond the 16-byte header block are unknown, not zero-value gameplay fields.

EEPROM geometry note. A 4-Kbit EEPROM organized as 64 × 64-bit needs 6 address bits. The driver takes the address-bit count from its config struct (cfg+8) and rejects addresses >= *(u16 *)(cfg+4). 3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

FUN_08037540 — DMA3 transfer primitive. Role: read/write transport for both directions.

  • It saves and clears a wait/state register, programs the DMA source (*_DAT_080375b0 = param_1) and destination (*_DAT_080375b4 = param_2), then writes the control word *_DAT_080375b8 = param_3 & 0xffff | 0x80000000. Setting bit 31 enables the channel. It polls the high halfword until bit 15 (0x8000) clears, then restores the saved register.
  • The register block reached through _DAT_080375b0/_DAT_080375b4/_DAT_080375b8 is the DMA3 register set (DMA3SAD/DMA3DAD/DMA3CNT, hardware base 0x040000D4) by layout and behavior. The literal addresses are unresolved in the export, so the mapping is by register order and the standard GBA map, confidence CONFIRMED_STATIC for the DMA3 role.
  • Callees: none. Callers: FUN_080375c0 and FUN_08037670, proven in callgraph.json.

FUN_080375c0 — EEPROM block read (param_1 = block address, param_2 = output buffer). Role: read.

  • It masks the address to 16 bits and returns an error value unless param_1 < *(u16 *)(cfg+4) (block count).
  • It builds the read command bitstream MSB-first in a stack array: the address bits, then two 1 bits (*puVar5 = 1; puVar5[-1] = 1), i.e. the EEPROM read opcode.
  • It DMAs addr_bits + 3 halfwords from the bitstream to 0x0D000000, then DMAs 0x44 (68) halfwords back from 0x0D000000. The extra halfwords are the command/address echo and dummy bit the EEPROM protocol returns before the 64 data bits.
  • It repacks 64 received bits MSB-first into four u16 values and stores them at param_2 + 6, +4, +2, +0. The payload is therefore one 8-byte block. Word order in RAM is the reverse of wire order at halfword granularity.
  • Callers: none in the callgraph. Callees: FUN_08037540.

FUN_08037670 — EEPROM block write (param_1 = block address, param_2 = u16 * source of 4 halfwords = 8 bytes). Role: write.

  • Same address range check against *(u16 *)(cfg+4).
  • It serializes the four u16 payload words into 64 single-bit halfwords, appends the address bits, then writes the start/opcode bits 0 then 1 (*puVar6 = 0; puVar6[-1] = 1), i.e. the EEPROM write opcode.
  • It DMAs addr_bits + 0x43 halfwords to 0x0D000000 (start bit + 2 opcode bits + address bits + 64 data bits), calls FUN_08037474, then busy-polls the EEPROM data line (uRam0d000000 & 1) and a status byte (*_DAT_08037744) until the internal write cycle completes, and finally calls FUN_080374fc.
  • Callers: none in the callgraph. Callees: FUN_08037474, FUN_080374fc, FUN_08037540.

FUN_08037474 — interrupt/DMA state setup helper. Role: support (serialize transport setup).

  • It copies a handler/state pointer pair, clears and then sets a flag word, computes a channel mask (8 << channel), stores three halfwords from its argument into a register-shadow struct, and sets the active flag to 1. It ends in an unresolved indirect jump.
  • Callers: FUN_08037670 only. Callees: none direct.

FUN_080374fc — interrupt/DMA teardown helper. Role: support.

  • It clears the flag word, zeroes the same halfword pair FUN_08037474 populated, clears the channel bit with & ~(8 << channel), and restores the saved handler word.
  • Callers: FUN_08037670 only. Callees: none direct.

Excluded candidates. FUN_080373b4, FUN_080373b8, FUN_080373cc, and FUN_080373d0 are BIOS software_interrupt stubs (SWI 6, SWI 6 with return, SWI 0x15, SWI 0x14) in the same address cluster. They are not save code. FUN_080377e4 and FUN_08037c28 operate on a 0x13c-byte-plus heap struct with counters at +0xC2/+0xC3 and pointer tables at +0x118–+0x128. Nothing ties them to the 512-byte EEPROM image, so they are not claimed as save serializers.

3.2 Serialization, deserialization & checksum routines

The only serialization proven in code is at block granularity: the EEPROM write driver serializes 4× u16 (8 bytes) per call and the read driver deserializes 64 wire bits into 4× u16 per call. A whole-image serializer that walks 64 EEPROM blocks, prepends Q00ABGPH, updates the byte at 0x0E, and computes the checksum at 0x08 was not found among the 201 decompiled functions:

  • Q00ABGPH, Q00, 0x51, and every checksum keyword have zero hits in decompiled.c.
  • Neither EEPROM block function is called by any other decompiled function, so the loop that would call the driver 64 times (or twice, for blocks 0–1) is absent from the traced set.
  • Every decompiled function ends through an unresolved indirect tail (UNRECOVERED_JUMPTABLE), so register-indirect calls (BX) to the driver cannot be recovered from this export even where they exist in the ROM.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

OffsetBytes (hex)ASCIIIn .savIn code
0x00, size 851 30 30 41 42 47 50 48Q00ABGPHYes, identical in both capturesNot found as a literal or constructed constant in the 201 functions

The signature occupies exactly EEPROM block 0 (bytes 0x00–0x07), which is consistent with a header written by one block-write call. Whether the game compares all 8 bytes on load is HYPOTHESIS: the bytes are stable across both captures and the probe's blank-revert proves an integrity gate exists, but the comparison routine itself was not located.

4.2 Checksum formula

  • Stored offset: 0x08 (first byte of EEPROM block 1). Size: 1 byte.
  • Algorithm: sum8 complement. stored = (~(sum of covered bytes)) & 0xFF, equivalently stored = 0xFF - (sum & 0xFF), equivalently (sum + stored) & 0xFF == 0xFF.
  • Covered range proven: every byte from 0x00 through 0x0F except the stored byte itself. Byte 0x0E is proven covered by the differential pair (see below). Because bytes 0x10–0x1FF are 0x00 in both captures, a whole-image cover (0x00–0x1FF except 0x08) produces identical values and cannot be excluded. The minimal proven cover is 0x00–0x0F excluding 0x08.
  • Not the algorithm: two's-complement negation (-sum) is off by one on both files (0xED/0xEC vs stored 0xEC/0xEB). XOR-8 gives 0x0D/0x0C. CRC-16/MODBUS over the covered bytes gives 0x5D48/0xCD49, unrelated to the stored byte. A 16-bit sum has no matching stored halfword (u16 at 0x08 is 0x00EC/0x00EB, i.e. the checksum byte plus a zero high byte).

Differential proof. Between the two captures only two bytes change: 0x08: 0xEC → 0xEB (delta −1) and 0x0E: 0x00 → 0x01 (delta +1). A one-byte increase inside the covered range decreases ~sum8 by exactly one. That lockstep is the signature of the additive complement and it places 0x0E inside the covered range. The behavioral probe agrees: corrupting offset 0x08 made the loader reject the image (integrity_check_confirmed: true, reverted_to_blank_on_mutation: true).

Decompiled C proof: none available in this corpus. No byte-sum loop over a save buffer exists in the 201 functions. The formula is verified empirically on the real binaries and behaviorally by the mutation probe; the implementing routine remains unlocated. Confidence for the formula on these samples is high; confidence that the cover stops at 0x0F is low (zero tail is indistinguishable).

import pathlib
for f in sorted(pathlib.Path('saves').glob('*.sav')):

    print(f.name, f"stored=0x{d[8]:02x}", f"computed=0x{computed:02x}", "match:", computed == d[8])

6. Save Fuzzing & Counterfactual Verification Plan

There are no paired .ss save states in this corpus (states/ is empty), so each test below is written for a cold reload of the mutated .sav in the emulator. Every mutation that touches a covered byte needs the checksum repaired first, or the loader's known reject-and-blank behavior will mask the field effect. Repair is always: data[8] = (~sum(data[i] for i in range(len(data)) if i != 8)) & 0xFF. Whether the cover is 16 bytes or the whole image does not change the repaired value while the tail stays zero; if a test writes beyond 0x0F, repair over the whole image.

Predictions are stated so each one can fail. Tests 2–3 isolate the signature check from the checksum check. Tests 7–8 resolve the covered-range ambiguity that the all-zero tail makes undecidable from the current captures. Test 9 establishes the from-blank write set, which bounds how much of the 512-byte image the game ever initializes.

Open questions

  • Which routine computes the ~sum8 checksum and compares Q00ABGPH, and which gameplay callers invoke the EEPROM read/write wrappers? The traced 201 functions contain neither, and the callgraph's indirect tails are unrecovered.
  • What is the RAM base address and layout of the save struct that the block drivers copy to and from?
  • Does the checksum cover stop at 0x0F, or does it run over the whole 512-byte image?
  • What does the u16_le candidate at 0x0E count, and what are bytes 0x09–0x0D and 0x0F for?
  • Are blocks at 0x10–0x1FF ever written in longer play, and if so, what fields do they hold?
  • What are the literal EEPROM config values (block count at cfg+4, address bits at cfg+8) that the stripped _DAT_ pool would have provided?

Method note

Every claim above was derived only from the workspace corpus and standard GBA hardware addresses. File bytes were read with Python pathlib and compared byte-by-byte; checksum candidates (~sum8, -sum8, XOR-8, CRC-16/MODBUS, sum16) were all computed against both real captures, and only ~sum8 matches. Function claims were cross-checked between [callgraph.json edges and textual FUN_ call sites in decompiled.c. Where the corpus is silent — callers of the EEPROM drivers, the checksum routine, RAM addresses — this report says so instead of inventing a chain.
