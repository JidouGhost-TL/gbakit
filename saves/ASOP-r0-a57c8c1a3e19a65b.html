All findings derive only from this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (81 functions), ghidra/save_related_functions.c (7 functions), ghidra/callgraph.json, plus standard GBA hardware addresses. No third-party game-specific sources were used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • Media is Flash 512K (64 KiB, 0x0E000000), erased fill 0xFF, SDK tags: none detected.
  • The save struct is 0x430 (1072) bytes, stored at the start of a Flash sector, starting with the ASCII magic PIRO (50 49 52 4F, LE u32 0x4F524950).
  • Integrity is a sum32: the LE u32 at struct offset 0x42C equals the sum (mod 2³²) of the 267 LE u32 words at offsets 0x000–0x428. Verified exactly on cap-01-future-1.sav (stored = computed = 0xD24D4116; see §4).
  • The low-level driver is a classic Flash command-sequence driver (unlock 0xAA@0x5555 / 0x55@0x2AAA, autoselect 0x90, reset 0xF0, erase 0x80/0x30, byte-program 0xA0), with wait/poll code relocated to RAM via FUN_080991c4.
  • Load (FUN_08012ca8), save (FUN_08012d98), checksum (FUN_08012fc4), and factory-default init (FUN_0803cd34) are all identified, and the default-init function byte-for-byte explains the only populated sample (flags 0x19=1, 0x1A=1, ten 0x20-filled records with 0xFF at +8).

Open / static-only (CONFIRMED_STATIC, HYPOTHESIS, UNKNOWN):

  • The live struct's RAM base is unknown: every _DAT_08012xxx/_DAT_0803cxxx literal-pool value is unresolved in this Ghidra output, so no 0x02xxxxxx/0x03xxxxxx mirror address can be honestly claimed.
  • FUN_08012d98 (save) has no caller in the 81-function corpus, so the gameplay trigger that saves is unknown.
  • Semantics of the 216×u32 array at 0x020 (all 36000) and of the 10×16 B records at 0x384 are structural only.
  • The sector ring bound is ambiguous (save wraps at 9, load scans <10); only sector 0 is populated in the samples.

Sample corpus: cap-00-future-0.sav is fully erased (65536× 0xFF, SHA-256 71189f7f…); cap-01-future-1.sav has exactly one valid struct in sector 0 (4086 non-0xFF bytes, SHA-256 cfe0626b…). There are no paired .ss states in this workspace (states/ is empty), so §6 predictions cannot be executed here.

Geometry detail. FUN_08012ca8 first reads sector 0 (func_0x080992ac(0,0,buf,0x430), line 1594). If the magic matches and FUN_08012fc4 agrees with the stored dword, a flag byte is cleared (line 1599). It then loops sector indices while < 10 (lines 1607–1619), reading each sector's 0x430 bytes, breaking on the first magic mismatch, and recording each checksum-valid sector into *_DAT_08012d74. Finally, if a valid sector was recorded it re-reads that sector into the live struct and returns 1 (lines 1621–1628); otherwise it returns 0. In cap-01, sector 1 is erased (0xFFFFFFFF magic), so the scan breaks immediately and sector 0 is selected — consistent with the bytes.

FUN_08012d98 writes the incremented sector byte: next = current + 1, wrapping to 0 when the incremented value equals 9 (lines 1679–1694), storing it at line 1703 and programming that sector at line 1704. This reads as a wear-levelling ring of 9 sectors (0–8), while the load scan's < 10 bound would also admit sector 9. The discrepancy cannot be resolved from the samples (only sector 0 exists); it is listed as an open question rather than smoothed over.

Two anomalies are reported, not explained away: (1) sector 0's tail 0x430–0xFFF is 0x00, not the erased 0xFF, although the program size is only 0x430 — this is not produced by any traced write and is most likely emulator Flash-backing behaviour; (2) PACKET's "active ranges" split at every 0xFF byte inside the records (offsets 0x38C, 0x39C, …), which is exactly the record +8 marker byte, not separate regions.

3. Save Writer, Reader & Caller-Chain Architecture

How callers were mapped. ghidra/callgraph.json only records calls to functions Ghidra named FUN_*. Calls written as func_0x080xxxxx(...) in ghidra/decompiled.c (thunks/stubs and the Flash core) do not appear as callgraph edges — e.g. FUN_08012fc4, FUN_080992ac, and FUN_080993cc show empty caller lists in the JSON while being textually called at lines 1594–1704. Every chain below therefore combines (a) callgraph edges, (b) textual func_/FUN_ call sites with line numbers, and (c) the pre-extracted seed file. Where a body is an unrecovered jumptable, that is stated.

3.1 Low-level Flash hardware driver (all CONFIRMED_STATIC unless noted)

  • FUN_08098f4c — Flash identify. Calls FUN_080991c4 to stage wait code, writes 0xAA/0x55 then 0x90 (autoselect) to the unresolved unlock addresses (standard 0x0E005555/0x0E002AAA pattern; only 0x0E000000 appears as a literal, line 3272), reads two ID bytes via stub func_0x08099b50, then writes 0xAA/0x55/0xF0 (reset) and returns (id1 & 0xFF) << 8 | (id2 & 0xFF). Caller: FUN_08098fe4.
  • FUN_08098fe4 — Flash init / vendor select. Sets WAITCNT SRAM bits (| 3, line 3299), calls identify, then walks a vendor table (_DAT_0809900c): an entry with byte +0x28 == 0 is the default/fallback, an entry whose short +0x28 equals the chip ID is a match (return flag 0 vs 1). It copies five dwords plus entry+0x14 into the flash-parameter globals (_DAT_08099060…_DAT_08099074) that later supply the sector-size shift (+8/+0x1C reads in FUN_080992ac/FUN_080993cc/FUN_08099540). Caller: boot FUN_080003ec.
  • FUN_0809909c — Flash config selector. If param_1 <= 3, stores the byte, computes byte*4 + table, and writes a table dword to *param_2 (lines 3336–3340). Called from boot with (1, _DAT_08000864) when identify returns 0. Exact role (interrupt/timing profile) is unresolved.
  • FUN_080991c4 — Relocate wait/poll code. Copies a code template from ROM (_DAT_080991e0 ^ 1, Thumb) into a RAM/stack buffer and stores buffer+1 through _DAT_080991dc. Required because the Flash array cannot be read while programming/erasing. Callers: FUN_08098f4c, FUN_08099540 (and textually inside the read/write wrappers' stack staging).
  • FUN_080992ac — ReadFlash(sector, offset, dest, size). WAITCNT |3, stages the template on the stack, then func_0x08099b48(0x0E000000 + offset + (sector << shift), dest, size, stack+1) (line 3452). Argument order (flash source first) is the read signature. Callers: FUN_08012ca8, FUN_08012d98.
  • FUN_080993cc — ProgramFlash(sector, src, size). Same staging, then func_0x08099b48(src, 0x0E000000 + (sector << shift), size, stack+1) (line 3483) — RAM source first, the write signature. Caller: FUN_08099484.
  • FUN_08099484 — Program with verify, retry ≤ 3. Each attempt: func_0x08099b44(sector, src, *DAT) (verify stub); if 0, FUN_080993cc(sector, src, size); break when both return 0 (lines 3502–3506). Caller: FUN_08012d98.
  • FUN_08099540 — EraseFlashSector(sector). Guard sector < 0x10 (line 3534 — this is the 16-sector proof). Unlock 0xAA/0x55, command 0x80, unlock again, 0x30 at the sector address 0x0E000000 + (sector << shift) (lines 3540–3546), wait via FUN_080991c4 + core func_0x08099b48(2, sectorAddr, 0xFF, …), restore WAITCNT. No caller in the corpus; the erase step of a save most likely hides inside the unrecovered stub func_0x08099b40 called at FUN_08012d98 line 1695 (its 0 return gates stamping/programming).
  • FUN_080995dc — Program single byte. Unlock 0xAA/0x55, command 0xA0, *param_2 = *param_1, core func_0x08099b48(1, param_2, *param_1, …) (lines 3571–3576). No caller in the corpus.
  • FUN_080990d4 / FUN_0809917c manipulate interrupt-enable style bits (8 << shift) around a Flash-related register block; no save-path caller was traced, so they are listed for completeness, not claimed as save functions.
  • Stubs 0x08099b44 (verify), 0x08099b48 (transfer/wait core), 0x08099b50 (read ID byte), 0x08099b3c/0x08099b40 (jumptable thunks) have unrecovered bodies. Their roles are inferred from call-site argument order only.

Not save code: FUN_08096da8–FUN_080985a8 sit between the game code and the Flash driver in address order but operate on 0x50-stride channel structs and are the sound engine; FUN_08006a6dc/FUN_0806ad44/FUN_0805423c/FUN_080034cc/FUN_08004158 are sprite/gameplay code. They are excluded deliberately.

3.2 Serialization, load, save, defaults

  • FUN_08012fc4 — checksum. acc = Σ *(s32*)(base+off) for off = 0,4,… while off <= bound (lines 1729–1734). See §4.
  • FUN_08012ca8 — load / deserialize. As §2: sector scan, magic compare (*buf == _DAT_08012d04, lines 1595/1611), checksum compare (*stored == FUN_08012fc4(buf), lines 1597–1599/1612–1614), keep last valid, re-read into the live struct (uRam08012d94, line 1626), return 1; else return 0. Sole traced caller: FUN_0803cbc0 (callgraph edge + line 1798).
  • FUN_08012d98 — save / serialize. (1) Dedup: if a current sector byte (*_DAT_08012de4 != -1) exists, read that sector into a fresh 0x430 allocation (func_0x08006a88(0x430) allocator, line 1662) and byte-compare it against the live struct; if identical, free and return 0 without writing (lines 1663–1677). (2) Compute next sector (wrap at 9, lines 1679–1694). (3) Gate on stub func_0x08099b40(next, …) == 0 (line 1695; plausibly erase). (4) Stamp magic *_DAT_08012e94 = _DAT_08012e98 (line 1698), compute and store the checksum at struct + _DAT_08012e9c (lines 1699–1701), record the next-sector byte (line 1703). (5) FUN_08099484(sector, struct, checksum_offset + 4) — i.e. program exactly 0x430 bytes with up to 3 verify retries (line 1704). No caller exists in the 81 functions or the callgraph — the trigger is an open question.
  • FUN_0803cd34 — factory defaults. Called by FUN_0803cbc0 (line 1800) when load returns ≠ 1. It DMA/CpuSet-stages a template (descriptor writes at lines 1858–1865, 1889–1892), zeroes struct+0x08…0x0F (4×u16, lines 1867–1873) and struct+0x18, writes struct+0x420 = _DAT_0803cdf4 (line 1865; the sample shows 50000 there), sets bytes +0x19 = 1, +0x1A = 1, +0x1B = 0, +0x1C = 0 (lines 1893–1896), zeroes struct+0x428 (line 1897), and fills the ten records: 8× 0x20 at struct+0x384+i*0x10 and 0xFF at struct+0x38C+i*0x10 for i < 10 (lines 1874–1888). Every one of these writes is visible verbatim in cap-01.

3.3 Caller chains (complete, as far as the corpus reaches)

  1. Boot → Flash init: FUN_080003ec (main init) → func_0x08098fe4() (line 195) → FUN_08098f4c identify; if the result is 0, func_0x0809909c(1, _DAT_08000864) (line 197), else a flag bit 0x100 is set (line 200). This chain touches no save-struct fields; it configures the flash-parameter globals and WAITCNT before any save I/O.
  2. Game-state init → load: FUN_0803cbc0 → FUN_08012ca8() (line 1798) → FUN_080992ac + FUN_08012fc4. On failure (ret != 1) → FUN_0803cd34() defaults (line 1800), which mutates the live struct's header bytes, record area, and +0x420/+0x428 as above. On success (ret == 1) it branches on live-struct flag bits 0x200 / 0x100 / 0x1000 to mode entry points including FUN_0806a6dc(1) (lines 1802–1817) — that is how loaded data steers the initial game mode, but the flag dword's offset cannot be named because the literal base is unresolved.
  3. Save (entry unknown): FUN_08012d98 → FUN_080992ac (dedup read) → FUN_08012fc4 (stamp) → FUN_08099484 → FUN_080993cc, gated by stub 0x08099b40 (probable erase, cf. standalone FUN_08099540). Before flushing, this chain mutates only three things: struct +0 (magic), struct +0x42C (checksum), and the global current-sector byte. All gameplay mutations of struct fields happen in code outside this corpus — no writer of the 0x020 array, the record values, or the header flags (other than factory defaults) exists among the 81 functions. That absence is a finding, not an oversight: it bounds what this trace can claim.
  4. Erase (entry unknown): FUN_08099540 → FUN_080991c4. Included because sector erase is a required step of every Flash save; its connection to chain 3 is via the unrecovered stub, hence HYPOTHESIS for the linkage, CONFIRMED_STATIC for the function itself.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic. Offset 0x000, 4 bytes 50 49 52 4F = ASCII PIRO, LE u32 0x4F524950. Verified in code: FUN_08012ca8 compares the first dword of every candidate sector against a literal (lines 1595, 1611) and FUN_08012d98 stores a literal to offset 0 before checksumming (line 1698); the literal values themselves are unresolved _DAT_ entries, so the identification of that literal with PIRO rests on the .sav bytes — which show PIRO at offset 0 of the only valid sector and nowhere else. Verified in sav: yes (cap-01 sector 0; cap-00 blank).

Checksum (CONFIRMED_VERIFIED).

  • Algorithm: sum32_le — plain u32 addition, no seed, no complement, no XOR/CRC.
  • Formula: stored = Σ_{i=0}^{266} LE_u32(base + 4i) (mod 2³²), i.e. bytes [0x000, 0x42C).
  • Stored at: offset 0x42C, size 4, LE. The stored dword itself is excluded.
  • Decompiled proof: FUN_08012fc4 (lines 1722–1738) accumulates *(int*)(param_1 + uVar1), uVar1 += 4, while uVar1 <= _DAT_08012fe4. The bound literal is unresolved; 0x428 is inferred (last covered dword). Because offsets 0x420–0x42B in the sample contribute only one non-zero dword at 0x420, any bound in 0x420–0x428 gives the same sum on this sample — the exact bound is therefore CONFIRMED_VERIFIED for the covered range [0,0x42C) as a byte range, with the bound-literal caveat noted.
  • Cross-proof of the stored offset: FUN_08012d98 stores the sum at struct + _DAT_08012e9c (lines 1700–1701) and programs that_offset + 4 bytes (line 1704); the read size is 0x430, so offset + 4 = 0x430 gives offset 0x42C, matching the .sav.

6. Save Fuzzing & Counterfactual Verification Plan

No .ss states exist in this workspace, so each test is specified as: mutate a copy of cap-01-future-1.sav, reload in an emulator with that .sav, and observe. Unless stated otherwise, "repair" means recomputing sum32 over [0,0x42C) and writing it LE at 0x42C (one line: struct.pack_into('<I', d, 0x42C, sum(struct.unpack_from('<267I', d, 0)) & 0xFFFFFFFF)).

  1. Magic kill (offset 0x000, 4 B): change PIRO→XIRO, with repair. Prediction: sector rejected on the magic compare before checksum (FUN_08012ca8 lines 1595/1611); with no other valid sector, factory defaults (FUN_0803cd34) appear — observable as reset options/records. Falsifies magic-first ordering if the save still loads.
  2. Checksum kill (offset 0x42C, 4 B): increment the stored dword, no other change. Prediction: checksum compare fails, sector skipped, defaults loaded. If the game instead boots the mutated data, the compare at lines 1597–1614 is not on the boot path.
  3. Array probe (offset 0x020, 4 B): set the first array dword 36000 → 12345, repair. Prediction: if the array holds displayed times/scores, exactly one UI value changes after reload; no visible change reclassifies the array as template/padding.
  4. Header flag probe (offset 0x019, 1 B): 1 → 0, repair. Prediction: a default-on option/mode differs on reload (factory init sets this byte to 1). Repeat independently for 0x01A.
  5. Record name probe (offset 0x384, 8 B): write TEST (0x20-padded) into record 0, repair. Prediction: the name appears in any ranking/records screen if these are name entries; no appearance anywhere downgrades the records to unused/hypothesis.
  6. Record value probe (offset 0x420, 4 B): 50000 → 99999, repair. Prediction: the last record's displayed value changes if record +12 is a score/time.
  7. Selection-rule test (offset 0x1000, 1072 B): copy the valid sector-0 struct verbatim into sector 1, no repair needed (checksum travels with the copy). Prediction per §2: load keeps the last valid sector, so sector 1 wins; then corrupt only sector 0's magic — the game should still load from sector 1. Loading defaults instead falsifies the scan/last-valid mapping.
  8. Ring test: from a booted valid save, force an in-game save (once its trigger is found) and diff the .sav. Prediction: a new valid struct appears at sector 1 (0x1000) with repaired checksum, sector 0 untouched — confirming next-sector writes and giving a second sample to disambiguate the 9-vs-10 wrap and the checksum bound (0x420–0x428).
  9. Tail test (offset 0x430, 3024 B): fill sector 0's tail with 0xFF. Prediction: no behavioural change, because only 0x430 bytes are ever read; any change falsifies the read-size mapping.
  10. Truncation counterfactual: zero bytes 0x424–0x42B are already zero, so instead set 0x428 = 1 without repair, then separately with repair. Without repair the sector must be rejected if 0x428 is inside the summed range; acceptance without repair would move the checksum bound below 0x428 and resolve the open bound question.

Appendix: Method & Limitations

  • Callgraph caveat: ghidra/callgraph.json omits every func_0x… call (thunks/stubs), so all chains were re-derived textually from ghidra/decompiled.c line numbers and only then cross-checked against the graph. The graph's sole recorded save-chain edge is 0x0803cbc0 → 0x08012ca8, plus 0x08098fe4 → 0x08098f4c, 0x08099484 → 0x080993cc, 0x08099540 → 0x080991c4.
  • Literal-pool caveat: no _DAT_ value is resolved anywhere in this decompilation, so vendor-table contents, the sector-size shift value, the checksum bound literal, and all RAM addresses are inferred from call-site structure and the .sav bytes — and labelled as such wherever used.
  • The 81 functions are trace-guided, not the whole ROM: absence of a caller/writer in this corpus (notably for FUN_08012d98) means "not traced here", never "does not exist".
