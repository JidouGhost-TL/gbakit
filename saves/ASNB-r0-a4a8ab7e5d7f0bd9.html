1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

The on-disk format is proven to a high standard; the code that produces it is not identified in the traced corpus. Those two halves must not be conflated.

Proven (verified by both .sav bytes and internal arithmetic consistency)

  • The 32 KiB image is a single sequential chain of 11 chunks starting at 0x0000. Every chunk is a 12-byte header + payload: 4-byte ASCII magic, u16_le at +4, u16_le record_size at +6, u16_le record_count at +8, u16_le checksum at +10, then record_size * record_count payload bytes. For all 11 chunks the sum offset + 12 + record_size*record_count lands exactly on the next chunk's magic, and the final chunk (OPTS) ends at 0x7EDF.
  • The integrity algorithm is a plain 8-bit byte sum (sum8) modulo 65536, stored little-endian at header +10, covering payload bytes only. It verifies 33/33 (11 chunks × 3 files), including the four non-trivial values WSLU=0x063C, LINE=0x0ED7, SEAS=0x0BF1, OPTS=0x0200. CRC32, XOR, sum16_le/be and header-inclusive variants were computed and ruled out (see §4 for full output).
  • There is no second copy, mirror, backup slot, or generation counter: each of the 11 magics occurs exactly once per file, and the three files are byte-identical except for one byte at 0x7FFC.
  • The two pre-extracted "MMIO seed" functions in save_related_functions.c are false positives: FUN_08050930 / FUN_08050a78 are signed/unsigned modulo compiler-runtime routines, not save I/O (see §3).

Static-only / hypothesis

  • Chunk-name semantics (BATT=batting records, PITC=pitching, WBAT/WPIT=weekly variants, WSLU, LINE=lineup, SEAS=season, SERI=series, CARD, OPTS=options, STAT) are inferred from the ASCII magics and record geometry only.
  • The header u16 at +4 is 1 for single-blob chunks (including STAT) and 0 for the four 16-byte record arrays. Its meaning (version / flags / is-array) is unresolved.
  • SEAS payload is byte-for-byte identical to the first 2,748 bytes of LINE, and WSLU payload to the first 500 bytes of LINE. Aliased RAM sources vs. a shared ROM default template cannot be distinguished from these samples.

Unknown / open

  • The true serializer, deserializer, and SRAM byte-copy driver were not found among the 562 trace-guided functions. decompiled.c contains zero literals for 0x0E000000, 0x040000D4, 0x04000204, any chunk magic, or any chunk payload size; literal pools surface as unresolved _DAT_080xxxxx placeholders and most calls are unrecovered indirect jumps absent from callgraph.json. Consequently no RAM mirror address can be honestly assigned to any field.
  • The single varying byte at 0x7FFC (in the unused 0xFF tail) is provably not a deterministic checksum of the rest of the file. This conflicts with a naive reading of the PACKET mutation probe; see §2 and §6.

Geometry

The chain occupies almost the entire SRAM: 32,479 of 32,768 bytes. There is no room for a second full copy, and none is present — a search for each magic (STAT BATT PITC WBAT WPIT WSLU LINE SEAS SERI CARD OPTS) returns exactly one offset per file. Redundancy, if any, would have to be per-chunk, and no chunk is duplicated either. Integrity therefore rests entirely on the per-chunk sum8 (and magic) checks; a single corrupted payload byte invalidates at least its chunk.

The 0x7FFC byte — a discrepancy that must be stated plainly

PACKET reports a mutation probe at 0x7FFC with integrity_check_confirmed: true and reverted_to_blank_on_mutation: true. Our three retained captures contradict the simplest interpretation of that claim:

  • The files differ only at 0x7FFC: 0x08 (cap-00), 0x80 (cap-01), 0xB0 (cap-02). Every chunk byte, header, and checksum is identical.
  • 0x7FFC lies 289 bytes past the end of the chunk chain (0x7EDF), inside a sea of 0xFF. No chunk covers it.
  • A deterministic checksum of the remaining bytes would be constant because the remaining bytes are constant. It is not: sum(rest) & 0xFF = 0x68 and xor(rest) = 0x3E in all three files, while the byte itself takes three different values.

Conclusion: 0x7FFC is either uninitialised SRAM garbage sampled at capture time, a tick/random-derived value, or evidence of a whole-image integrity mechanism more subtle than a file checksum (e.g. the game rewrites SRAM on load for unrelated reasons, making the probe's "save rewritten" observation ambiguous). §6 includes a decisive fuzz target for this byte. It is classified UNKNOWN, not as a checksum.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 What the hardware driver must look like (GBA ground truth)

On GBA, SRAM at 0x0E000000 is an 8-bit-wide bus: saves are written with byte loads/stores (or a BIOS/DMA copy configured for byte transfers), typically after setting WAITCNT SRAM wait states (0x04000204). Flash (64K/128K 0x5555/0x2AAA command sequences) and EEPROM (serial bitstream via DMA3 at 0x040000D4) leave very different code fingerprints. None of those fingerprints — no 0x0E000000, 0x0D000000, 0x040000D4, 0x04000204, 0x5555/0x2AAA command pattern, or EEPROM/FLASH/DMA string — appears in decompiled.c (verified by case-insensitive search: 0 hits for each; the 59 SRAM hits are Ghidra dummy names like psRam08012688, i.e. unresolved pointers, not hardware references). Combined with PACKET's SRAM 256K media observation, the driver is an SRAM byte-copy whose base pointer is held in a literal pool that Ghidra did not resolve.

3.2 The seeded functions are compiler runtime, not save I/O (verified)

ghidra/save_related_functions.c seeds FUN_08050930 and FUN_08050a78 as "MMIO seeds". Reading the bodies disproves that:

3.4 Caller chains that were traced and excluded

  • Boot / main loop: FUN_08036ec0 (callgraph root, 13 callees) calls FUN_08000e24 (early init: SWI copy, subsystem inits) and loops through FUN_080112cc, FUN_08000f50, FUN_0802951c (×0x16), FUN_0800d698(1), FUN_0800d698(2). Bodies read: this is the game-state dispatch and text/score rendering path (FUN_0800d698 → FUN_0800d43c → FUN_0800d198/FUN_0800cff8 draws glyphs). A boot-time save load plausibly hangs off FUN_08000e24, but no chunk, magic, or checksum logic exists in its traced body. How each caller mutates the in-RAM save struct: unobservable — no traced caller writes a proven save-struct field, because the struct's RAM address is unresolved.
  • Text rendering: FUN_0802951c → FUN_0800d698 → FUN_0800d43c → FUN_0800cff8/0800d198. Excluded: glyph rasterisation, no persistence.
  • Representative memcpy caller: FUN_0801a518 copies 0x19-byte string templates to the stack and writes tiles. Excluded; the other three memcpy callers are a debug-string ring (FUN_0803840c), a sound/input sequencer (FUN_0803c6bc), and a texture/resource loader (FUN_0804b9c4, whose recsize*count + +0xC descriptor arithmetic is a useful reminder that this engine reuses 12-byte descriptor idioms outside saves).

3.5 Reconstructed writer/reader (hypothesis, constrained by §4 proof)

The .sav bytes alone force this shape, whoever implements it:

  1. Writer: iterate a fixed 11-entry descriptor table (magic, +4 field, record size, count, RAM source pointer). For each entry: emit 12-byte header, copy record_size*count bytes from RAM to SRAM 0x0E000000 + running_offset, compute sum8 over the payload, store it at header +10. Advance running_offset by 12 + record_size*count.
  2. Reader: walk the same chain from offset 0; for each chunk verify the magic and recompute sum8; copy payload to the chunk's RAM destination. On mismatch, reject (PACKET probe: blank/rewrite behaviour).
  3. In-RAM mutation before flush: gameplay code mutates the RAM buffers (records in BATT/PITC, blobs for LINE/SEAS/OPTS, …); the writer itself only serialises and checksums. No traced function can be named as a mutator — this is an explicit gap, not a filled one.

4.2 Exact checksum formula

stored_u16le(chunk_header + 10) = ( Σ payload[i]  for i in [0, record_size*record_count) ) mod 65536
  • Algorithm class: sum8 (additive, 8-bit elements, 16-bit accumulator, little-endian store). Seed 0. No final XOR, complement, or byte reflection.
  • Covered range: payload only — header bytes (including the magic) and all other chunks are excluded. Including the header breaks every non-zero chunk.
  • Ruled out by direct computation on every chunk: CRC32 (low/high half), CRC-16-style bytewise accumulation via crc_hqx, XOR-8, XOR-16, sum16_le, sum16_be. Only sum8 matches the non-zero chunks; the seven all-zero payloads match trivially under any zero-preserving sum and were not used as discriminators.

4.3 Python verification (executed in this workspace)

Verification script (run against the real binaries; identical logic is embedded in the generation of save-format.json):

import pathlib, struct
for f in sorted(pathlib.Path("saves").glob("*.sav")):
    d = f.read_bytes(); off = 0
    while True:
        magic = d[off:off+4]
        v, rec, cnt, chk = struct.unpack_from("<HHHH", d, off+4)
        payload = d[off+12 : off+12 + rec*cnt]
        comp = sum(payload) & 0xFFFF
        print(f.name, magic.decode(), f"@0x{off:04x}",
              f"stored=0x{chk:04x} computed=0x{comp:04x} match={comp==chk}")
        off += 12 + rec*cnt
        if magic == b"OPTS": break

4.4 Magic signatures

All 11 magics are verified in .sav (exactly one occurrence each, at the chained offsets in §5) and none is verified in code: the ASCII strings never appear in decompiled.c, consistent with a ROM descriptor table referenced through unresolved _DAT_ pointers. verified_in_code is therefore false in save-format.json — an honest negative, not an omission.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule: after mutating any payload byte(s) in chunk C, recompute sum(payload_C) & 0xFFFF and store it little-endian at header_C + 10 — unless the experiment deliberately tests checksum enforcement, in which case leave the stale checksum in place. Work on copies of cap-02-retained-3.sav; reload each mutant cold and record (a) blank-vs-loaded boot, (b) any save rewrite after boot, (c) the affected screen (options / lineup / season / stats), and (d) a RAM dump if a paired save-state is available.
