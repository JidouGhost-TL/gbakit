1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM

Proven (verified by decompiled code AND .sav bytes — CONFIRMED_VERIFIED)

  1. The save medium is SRAM at 0x0E000000, 32 KiB (SRAM 256K). The formatter writes the entire chip in four 0x2000-byte verified-write chunks (0x0E000000, 0x0E002000, 0x0E004000, 0x0E006000) from a zeroed RAM mirror. No Flash command sequence (0x5555/0x2AAA) and no EEPROM/DMA3 (0x040000D4, 0x0D000000) reference exists anywhere in ghidra/decompiled.c or ghidra/save_related_functions.c (grep: zero hits).
  2. A 15-byte ASCII magic 020322_DM7_KCEJ is stored at file offset 0x01 and is written by code (FUN_08005ecc, length 0xF) and validated by code (FUN_08005ee4, byte-by-byte compare of 15 bytes read from SRAM against a ROM string).
  3. The integrity value is a 16-bit byte-sum (sum16). FUN_0801fffc accumulates s16 += (u8)*p++ over a RAM buffer. Recomputed in Python over payload copy A sav[0x10:0x401E], the sum is 0x112E, exactly matching the u16-LE stored at 0x401E — and the identical value stored at 0x7FFE for copy B (see §4 for the overlap caveat and full output).
  4. The payload exists in two byte-identical copies (A at 0x0010, B at 0x3FF0, each 0x400E bytes), differing only at the two bytes where copy A's checksum physically overlaps copy B's payload (see §2).
  5. Byte 0x0000 is a status/commit byte that the formatter cycles 1 → 2 → 3 → 0 while writing copy A, copy B, and the header, leaving 0 (committed) in the observed save. The validator FUN_08005a84 requires this byte to be < 3.

Static-only (CONFIRMED_STATIC — in code, not observable in the two samples)

  • The writer/validator call architecture in §3, including the exact state-decoding table of FUN_08005a84 and the default-value initializers called by FUN_08005d30 (e.g. constants 0x640, 0x48, 1, a 40×u16 list copy, a 0x385-byte table copy).
  • The verified-write retry semantics (copy + compare, up to 3 attempts) of FUN_08034230 / FUN_08034094.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN)

  • Semantic labels for payload sub-fields (card-collection counts, a 40-entry card-ID list, currency-like counters). Only two snapshots exist — one completely erased (0xFF) and one populated — so no gameplay delta can be correlated with any field. All semantics are inferred from byte shapes and initializer constants only.
  • Numeric RAM mirror addresses. Every pointer in the decompilation is an unresolved _DAT_0800xxxx literal-pool symbol; this Ghidra export does not include the literal values. Therefore no field can be bound to a concrete 0x02xxxxxx/0x03xxxxxx address from the available evidence. save-format.json honestly records ram_addr: null for all fields.
  • Seven leaf functions are missing from the 174-function decompilation (they appear only as func_0x… calls and have no callgraph.json node): 0x08005dd8, 0x08005e34, 0x08005e5c, 0x08005c3c, 0x08005c64, 0x08005b08, 0x08005be4, plus 0x08020310. Their roles below are inferred from call sites and naming proximity, never from their bodies.
  • The exact covered length constant of FUN_0801fffc (a _DAT_ bound) and the destinations/lengths inside FUN_08005ba4 / FUN_08005bc4 are unresolved for the same literal-pool reason. The covered range in §4 is pinned empirically by the .sav verification, not by the constant.

Why not HIGH: the checksum, magic, medium, and geometry are verified, but field semantics, RAM addresses, slot-selection semantics, and the loader path rest on static inference and a single populated sample.

0x7FFE  └  checksum B: u16-LE, same value as checksum A
0x8000  end of SRAM

Facts and caveats:

  • Two copies, stride 0x3FE0, deliberately overlapping. Copy B begins 0x2E bytes before copy A ends. Consequently the two checksum-A bytes at 0x401E–0x401F are physically also payload bytes +0x2E/+0x2F of copy B. A byte-for-byte comparison of the two payloads (Python, §4) shows they are identical at every one of the 0x400E positions except those two overlapped bytes. This is not corruption: the writer computes the checksum once from the RAM payload struct (before any SRAM checksum write) and stores that one value at both 0x401E and 0x7FFE, so on disk copy B "contains" copy A's checksum in its overlap window while its own stored checksum still encodes the pristine RAM payload.
  • No generation/sequence counter was found. Neither copy carries an incrementing counter in the observed save: byte 0x0000 is a phase/commit flag (final value 0), and no other header field differs between copies. Copy preference therefore cannot be counter-based; it is validity-based (next bullet). Confidence: CONFIRMED_STATIC for the absence in code paths traced; a counter inside the un-decoded payload cannot be excluded (UNKNOWN).
  • Selection rule (static inference). FUN_08005a84 returns a state in {0,1,2,3} from three validity inputs — magic OK (FUN_08005ee4), status byte < 3 (func_0x08005dd8), and two per-copy integrity results (func_0x08005e34, func_0x08005e5c, bodies missing). FUN_08005b44 dispatches on that state: 2 → func_0x08005c3c(), 3 → func_0x08005c64() (both missing; interpreted as the per-copy loaders/repairers). The boot dispatcher FUN_08020258 treats state 0 as "no valid save" and falls through to the formatter FUN_08005c98 when its sub-dialog also returns 0. Which numeric state maps to copy A vs. copy B cannot be proven without the missing loader bodies: HYPOTHESIS.
  • Redundancy role. Copy A is labelled primary and copy B backup in save-format.json solely because A shares the header block (status + magic at 0x00) and is written first (phase byte 1 precedes A's chunk write, 2 precedes B's). The validator gives no proven priority; this labelling is HYPOTHESIS.
  • Cold-reload probe (PACKET): the populated save survived reload (save_preserved_on_load: true, visual delta on load), consistent with both copies + checksums validating at boot.

3.3 The formatter / save creator — FUN_08005c98

Sole static caller: FUN_08020258. Exact sequence (all steps visible in ghidra/decompiled.c and duplicated in ghidra/save_related_functions.c):

  1. uVar2 = *_DAT_08005d28 (RAM mirror base, unresolved), zero-fill a mirror field via func_0x08033f2c(stack_zero, uVar2, _DAT_08005d2c).
  2. Flush the mirror to the whole SRAM with four verified writes: func_0x08034230(uVar2, 0x0E000000, 0x2000), …0x0E002000…, …0x0E004000…, …0x0E006000…. At this point SRAM is a zero image (this is also why an interrupted format leaves a zeroed, magic-less chip that the validator rejects).
  3. FUN_08005d30() — initialise the in-RAM save struct to new-game defaults (see §3.5).
  4. FUN_08020028() — pack the scattered RAM fields into the contiguous payload image.
  5. uVar1 = func_0x0801fffc() — compute sum16 over the packed payload.
  6. FUN_08005d84() status =1; FUN_08005ba4() flush chunk A; FUN_08005dfc(uVar1) store checksum A; FUN_08005da0() status =2; FUN_08005bc4() flush chunk B; FUN_08005e18(uVar1) store checksum B (same value); FUN_08005dbc() status =3; FUN_08005ecc() write magic; FUN_08005d68() status =0 (commit).

Interpretation (CONFIRMED_STATIC for the sequence; semantics HYPOTHESIS): this is the create/format path for a new save, not a general "save progress" routine — no other SRAM writer exists in the corpus, so routine gameplay saving either re-uses the FUN_08005ba4/FUN_08005bc4 + checksum-writer tail through unrecovered jumptable callers, or was not captured by the trace-guided decompilation. The in-RAM struct is mutated (step 3 defaults, or by gameplay) before the pack step (FUN_08020028) and checksum step; the on-disk mutation order is strictly: whole-chip zero flush → copy A → checksum A → copy B → checksum B → magic → committed status. A power loss mid-sequence leaves a detectable state: status 1/2/3, a missing/stale magic, or a copy whose checksum fails — all inputs to FUN_08005a84.

4.2 Checksum algorithm

  • Algorithm: sum16 — plain additive sum of unsigned bytes, truncated to 16 bits. No seed, no complement, no XOR folding, no CRC polynomial.
  • Formula: stored_u16le = ( Σ byte[i] for i in covered_range ) mod 65536
  • Covered range (copy A): file offsets [0x0010, 0x401E) — i.e. the entire 0x400E-byte payload, excluding the 16-byte header (status + magic) and excluding the stored checksum itself. Copy B uses the identical payload bytes at [0x3FF0, 0x7FFE).
  • Stored offsets / size: u16 little-endian at 0x401E (copy A) and 0x7FFE (copy B), written by FUN_08005dfc / FUN_08005e18 from the single value returned by FUN_0801fffc.
  • Endianness: stored little-endian (2E 11 = 0x112E); the accumulator in code is a signed short, whose bit pattern is identical to the unsigned sum mod 65536.
  • Why the header is excluded: it could not be otherwise — in FUN_08005c98 the checksum is computed from the RAM payload (FUN_08020028 pack output) before the magic is written to SRAM, and summing the on-disk header (0x00 + magic ASCII) would give 0x14FA ≠ 0x112E. The Python check below confirms the header-excluded range is the one that matches.

Decompiled proof (FUN_0801fffc, abridged):

sVar3 = 0;                                   // short accumulator
pbVar1 = (byte *)*_DAT_08020020;             // payload base (literal unresolved)
uVar2 = 0;
do { sVar3 = sVar3 + (ushort)*pbVar1; pbVar1++; uVar2++; }
while (uVar2 <= _DAT_08020024);              // count = bound+1 bytes (literal unresolved)
return sVar3;

6.3 Checksum repair recipe (exact)

The writer computes one value from the RAM payload and stores it at both checksum offsets. To repair a mutated file so both copies validate under that model:

import struct
d = bytearray(open('mutated.sav','rb').read())
# 1) make the logical payload copies identical (copy A at 0x10 is the reference)
d[0x3FF0:0x7FFE] = d[0x10:0x401E]
# 2) compute sum16 over copy A payload and store it at both checksum offsets
s = sum(d[0x10:0x401E]) & 0xFFFF
struct.pack_into('<H', d, 0x401E, s)
struct.pack_into('<H', d, 0x7FFE, s)
# 3) ensure the committed status
d[0x00] = 0x00
open('mutated.sav','wb').write(d)

Note the deliberate ordering: step 1 copies A's payload over B including the window at 0x401E, and step 2 then writes checksum A over those two bytes — reproducing exactly the on-disk overlap artifact of §2/§4.3 (a naive verifier summing copy B raw will then read stored + 0x3F; that is expected, cf. §4.3). If a future loader is found to sum copy B raw instead, repair B independently as sum(d[0x3FF0:0x7FFE]) stored at 0x7FFE after step 1 — F3/F4/F7 discriminate which model the loader uses.

6.4 Verification script actually executed for this report

The output quoted in §4.3 was produced in this workspace by:

python3 /tmp/verify_save.py

where /tmp/verify_save.py computes both file hashes, locates the magic, evaluates sum16 over [0x10,0x401E) and [0x3FF0,0x7FFE) (raw and RAM-view), diffs the two payload copies byte-by-byte, and prints the candidate scalar fields (0x814, 0x83C, 0x422, 0x3CE, 0x3D2). Its full logic is: sum(d[a:b]) & 0xFFFF compared against struct.unpack_from('<H', d, stored_offset)[0]. Re-running it against any future mutated save (before repair) is the fastest oracle for whether a mutation touched covered bytes: the computed value must move by exactly the byte delta, and the stored value must not.
