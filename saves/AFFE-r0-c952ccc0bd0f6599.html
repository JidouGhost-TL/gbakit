Final Fight One (USA) — Clean-Room GBA Save Format Report

  • Release key: AFFE-r0-c952ccc0bd0f6599, Game code: AFFE / AFF
  • ROM SHA-256: c952ccc0bd0f65990db2c6ad0f309484d790691fcbdbae23d2cb29af4aa27989
  • Corpus: sav-00-f1157.sav (512 B), decompiled.c (172 functions), callgraph.json, save_related_functions.c
  • Method: only workspace files plus standard GBA hardware addresses from the packet were used. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Verified by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM, 512 B total in the file, read in 8-byte blocks via DMA3 to 0x0D000000.
  • There are two 256-byte slots. Slot 0 at file offset 0x000 is populated; slot 1 at 0x100 is all 0xFF in this sample and therefore fails validation.
  • Each slot is validated by a magic word plus a 16-bit additive checksum. The checksum was recomputed in Python and matches exactly (Section 4).
  • Only the first 0x74 (116) bytes of a validated slot are copied into the live RAM struct. The rest of the slot is 0xE5 padding except the trailer at logical 0xFC..0xFF.
  • Five 6-byte ASCII names (CODY , HAGGAR, GUY , A-CODY, A-GUY ) are recovered only after reversing each 8-byte EEPROM block, exactly as the EEPROM reader reconstructs words.

Static-only (CONFIRMED_STATIC):

  • The full reader/validator/selector call chain at 0x08045958, 0x0804599c, 0x08045a58, 0x08045820 (Section 3).
  • The selector rule comparing the first u16 of the two candidate buffers with a < 0x40 window.

Open / not proven:

  • No EEPROM write function exists in the 172 traced functions. The writer was not executed during the trace that produced decompiled.c. One unresolved external, func_0x0804576c, is called from FUN_08045820 after a flag byte is set to 0xFF and is the only in-corpus candidate for a flush/save routine; its body is absent, so it is a hypothesis, not a finding.
  • Absolute EWRAM/IWRAM addresses of the staging and live buffers are not recoverable from the text: Ghidra left every pointer as an unresolved _DAT_080xxxxx literal-pool entry. All RAM references below are therefore given as offsets from the slot/staging buffer base, with ram_addr: null in save-format.json.
  • Semantics of most numeric fields (scores vs. stage/character IDs vs. options) are hypotheses. Byte values, offsets, and ASCII are verified; meanings are not.
  • Only one .sav sample exists, so cross-save variation, the generation-counter behaviour, and slot-1-as-primary behaviour cannot be observed directly.

Address derivation in FUN_08045958(int slot): uVar2 = slot << 0x15; each iteration passes uVar2 >> 0x10 (= slot*32 + block_index) to func_0x0806b280 and adds 0x10000. So the EEPROM address unit is one 8-byte block, slot 0 occupies units 0–31 and slot 1 units 32–63, i.e. 64 units × 8 B = 512 B, consistent with a 4-Kbit EEPROM and a 6-bit block address (the address-bit count itself is read from an unresolved config byte at *_DAT_0806b334 + 8 in FUN_0806b280, so the exact bit count is static-unresolved).

Byte-order transform (critical): the .sav file stores each 8-byte block reversed relative to the game's RAM image. Reversing every 8-byte block of file slot 0 yields the logical/RAM image used everywhere below ("logical offset"). This is proven two independent ways in Section 4: (a) the RAM-image u16LE sum is 0x00420000, low 16 bits zero, as FUN_0804599c requires; (b) readable names CODY, HAGGAR, GUY appear only in the reversed image. The equivalent raw-file statement is sum(u16BE over file[0:256]) & 0xFFFF == 0. Conversion: logical_offset = (sav_offset & ~7) + (7 - (sav_offset & 7)) within a slot, and vice versa.

Selection rule (FUN_08045a58, paraphrased):

ok0 = (FUN_08045958(0)==0 && FUN_0804599c()==0);
if (ok0) { memcpy(live, staging, 0x74); have = true; }
ok1 = (FUN_08045958(1)==0 && FUN_0804599c()==0);
if (ok1) {
  if (!have || (ushort)(*staging_first_u16 - *live_first_u16) < 0x40)
      memcpy(live, staging, 0x74);   // slot 1 wins
  have = true;
}
if (have) FUN_080457a8();  // apply live struct
return have ? 0 : -1;

So a valid slot 1 replaces slot 0 unless slot 0 was valid and the first-u16 difference is >= 0x40, in which case slot 0 (already in live) is kept. If neither slot validates, the function returns 0xFFFFFFFF and no copy occurs. In this sample only slot 0 validates, so slot 0 is the active copy and slot 1 is an erased backup.

There is no separate global-config copy: the 0x74-byte live struct (records plus the config tail at logical 0x54..0x73) is the single payload shared by both slots.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two sources were cross-checked. callgraph.json only records edges Ghidra resolved as FUN_080xxxxx; calls emitted as func_0x080xxxxx (unresolved/thunk targets) are missing from it. Example: the callgraph lists FUN_08045820 callees as only 0x0800a880, 0x0804568c, but the decompiled text shows it also calls func_0x08045a58() and func_0x0804576c(). Every func_0x… reference in decompiled.c was therefore extracted with Python and merged with the callgraph before drawing any chain. Conversely the callgraph confirms FUN_0806b200's only caller is FUN_0806b280, and FUN_08045958's only resolved caller is FUN_08045a58.

3.2 Low-level hardware I/O driver

FUN_0806b200(src, dst, count) at 0x0806b200 — DMA3 driver (in save_related_functions.c and decompiled.c):

saved = *_DAT_0806b260; *_DAT_0806b260 = 0;                       // suspend DMA3
*_DAT_0806b264 = *(ushort*)(*_DAT_0806b26c+6) | *_DAT_0806b264 & mask;
*_DAT_0806b270 = src; *_DAT_0806b274 = dst;                      // DMA3 SAD/DAD (0x040000D4 block)
*_DAT_0806b278 = (count & 0xFFFF) | 0x80000000;                  // CNT: enable
while (*(ushort*)(cnt+2) & 0x8000) {}                             // poll busy
*_DAT_0806b260 = saved;                                          // restore

The exact register addresses are unresolved _DAT_ literals; assignment to the 0x040000D4 DMA3 block follows the packet's hardware spec and the src/dst/count ordering. Only caller: FUN_0806b280.

FUN_0806b280(eeprom_block_addr, ram_dst) at 0x0806b280 — EEPROM read of one 8-byte block:

  1. Rejects addr >= *(ushort*)(cfg+4) (device block limit), returning non-zero.
  2. Builds a bitstream on the stack: two leading 1 bits, then the address bits MSB-first (count from *(byte*)(cfg+8)).
  3. FUN_0806b200(bitstream, 0x0D000000, addr_bits+3) — DMA the command/address bits to the EEPROM window.
  4. FUN_0806b200(0x0D000000, bitstream, 0x44) — DMA back 68 halfwords (4 dummy bits + 64 data bits), each halfword carrying one bit in bit 0.
  5. Reconstructs four u16s MSB-first (uVar4 = uVar4<<1 | *puVar5 & 1, 16 bits each) and stores them descending at ram_dst+6, +4, +2, +0. This descending store plus MSB-first packing is exactly why each 8-byte file block is reversed in the RAM image.

There is no EEPROM write counterpart in the corpus: no function sends a write opcode (the two leading bits here are both 1, the read command), sends 64 data bits to 0x0D000000, or polls an EEPROM busy bit. FUN_0806b588 / FUN_0806b4f0 in the seed file are signed divide/modulo helpers, and FUN_08000270 is a 32-byte-block memcpy; none touches EEPROM. This is consistent with a trace-guided decompilation (172 functions actually executed around boot/load at frames 1106–1157 per states); a save triggered later in gameplay would not be captured.

3.3 Serialization, deserialization & checksum routines

  • Deserialization (EEPROM → RAM): FUN_08045958(slot) at 0x08045958. Brackets the transfer with FUN_0800a868() / FUN_0800a874(), which call func_0x0806a2c0 / func_0x0806a33c (sound/DMA pause–resume wrappers, via FUN_0806b0ac = SWI 0x0B helper) — EEPROM DMA3 is suspended from audio DMA while reading. Loops 32 blocks into the staging buffer at base + block*8; returns 0 on success, 0xFFFFFFFF if any block read fails.
  • Validation: FUN_0804599c() at 0x0804599c (Section 4).
  • Selection + commit to live struct: FUN_08045a58() at 0x08045a58 (Section 2), using FUN_0806b7d8(dst, src, 0x74) (memcpy, at 0x0806b7d8) and then FUN_080457a8().
  • Apply: FUN_080457a8() at 0x080457a8 calls FUN_0800b9ac(ptr), which writes four u16s from a table indexed by four bytes at ptr — i.e. it consumes the freshly loaded struct (plausibly palette/ranking-graphics setup). It does not write EEPROM.
  • Serialization (RAM → EEPROM): absent (see §3.2). The checksum writer side is likewise absent; only the validator proves the formula.

4. Magic Signatures & Checksum / Integrity Algorithm

Validator FUN_0804599c at 0x0804599c, decompiled proof:

undefined4 FUN_0804599c(void) {
  if (*_DAT_080459ac == _DAT_080459b0) {          // (a) magic gate
    uVar3 = 0;
    puVar4 = _DAT_080459ac - 0x7E;               // ushort* : -126 words
    iVar2 = 0x7F;
    do { uVar3 += *puVar4; puVar4++; iVar2--; } while (-1 < iVar2);  // 128 words
    uVar1 = 0;
    if ((uVar3 & uRam080459d4) != 0) uVar1 = 0xFFFFFFFF;             // (b) sum gate
  } else uVar1 = 0xFFFFFFFF;
  return uVar1;
}

Pointer arithmetic fixes the layout uniquely: starting 126 words before the gated word and summing 128 words must cover a 256-byte slot exactly, so the gated word is word 126 at logical offset 0xFC, the sum covers words 0–127 (logical 0x00..0xFF), and word 127 at 0xFE is free to be the checksum word. The mask literal uRam080459d4 is unresolved in the text; the only natural value consistent with the sample is 0x0000FFFF (the accumulated sum is 0x00420000, so a mask containing bit 17 or bit 22 would fail — see below).

Exact algorithm:

  • Magic: u16LE at logical 0xFC must equal 0x55A6 (RAM bytes A6 55; .sav file bytes 55 A6 at file offset 0xFA within slot 0's last block). No ASCII magic exists anywhere in the slot; the names in §5 are payload, not signatures. verified_in_code rests on the gate structure (the constant itself is an unresolved literal), verified_in_sav on the observed word — hence CONFIRMED_STATIC for the constant, with the value itself observed in the sample.
  • Checksum: stored_u16LE @ logical 0xFE == (-(sum of u16LE words 0..126)) & 0xFFFF, equivalently sum of all 128 u16LE words & 0xFFFF == 0. Covered range: logical 0x000..0x0FF (the whole 256-byte slot, including padding and trailer). Endianness: little-endian words in the RAM image; on the raw file this is exactly a big-endian word sum. There is no seed, complement beyond the two's-complement negation, CRC, or XOR — it is a plain additive sum16.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for every mutation below: edit the logical image, recompute word 127 as (-sum(u16LE words 0..126)) & 0xFFFF, store it little-endian at logical 0xFE, keep word 126 = 0x55A6, then map back to the file by reversing each 8-byte block (equivalently, edit file bytes and check sum(u16BE file slot) & 0xFFFF == 0). Reload by cold-booting from the paired states: use sav-00-pre.ss (frame 1106, before the save appears) versus sav-00-post.ss / gameplay state (frame 1157) as the unmutated control; the packet's cold-reload probe (save_preserved: true) is the baseline expectation.

10Slot 1 only: copy valid slot 0 into file 0x100..0x1FF, erase slot 0 to 0xFFAlready validGame loads the same data from slot 1, proving slot geometry/addressing (slot*32 blocks). Then corrupt slot 1's magic: total no-save behaviour
11Live-struct boundary: mutate logical 0x73 (last copied byte) vs. 0x74 (first non-copied byte), each with repairYes0x73 mutation may show a (config) effect after load; 0x74 mutation must show none, testing the 0x74 memcpy length in FUN_08045a58
12Counterfactual writer hunt: set flag 0x6B = 0xFF in the live path is already test 5; separately, during gameplay from the frame-1157 state, change an option/record in RAM and watch for EEPROM writes to 0x0D000000 with a write opcoden/aAny observed write identifies the missing writer (candidate 0x0804576c); its address-bit count and data-bit order must match FUN_0806b280's read protocol. Absence of writes on option changes would mean saving is triggered elsewhere (e.g. game-over/ranking entry)

Negative controls: mutating any byte without checksum repair (tests 7–9) must always invalidate the slot; if a mutated-but-unrepaired slot still loads, the validator model in §4 is wrong and the FUN_0804599c reading must be revisited. All predictions are stated before looking at gameplay outcomes, per the clean-room rules.
