Clean-Room Save Format Report: Polarium Advance (USA) [BIIE-r0-f03f192ea9ceb7dd]

1. Executive Summary & Overall Confidence

Overall Confidence: LOW–MEDIUM.

What was proven directly from ghidra/decompiled.c + ghidra/save_related_functions.c, cross-checked byte-for-byte against saves/cap-00-future-0.sav:

  • The ROM contains a complete, generic Flash hardware-access driver (manufacturer/device-ID probe, bank-select for ≥1 Mbit parts, sector erase with 3-try retry, byte-program with 3-try retry, chip-ID dispatch table). This driver talks to the GBA's parallel Flash/SRAM window at 0x0E000000 using the standard 0xAA→0x5555, 0x55→0x2AAA unlock handshake — never via EEPROM's DMA3 serial bitstream (0x040000D4) and never via a plain WAITCNT-gated SRAM byte-copy. This is strong, verified evidence the save medium is parallel Flash, consistent with the packet's declared Flash 512K (64 KiB) media type.
  • The single .sav sample is byte-identically structured with the automated profiler's active_ranges: every non-0xFF byte in the 65536-byte file falls inside the 8 declared active spans (verified independently with Python in this session) — there is no undocumented live data elsewhere in the file.
  • Two small metadata blocks (0x3F94 and 0x6D88+0x6D94) are byte-for-byte identical to mirror copies located exactly +0x9000 bytes later (0xCF94, 0xFD88+0xFD94). This is a verified structural fact, not a hypothesis.
  • A third metadata block (0x9DA8, tag ROY) has no +0x9000 mirror — a +0x9000 mirror would land at 0x12DA8, outside the 64 KiB file, so no backup copy is physically possible for that block. This asymmetry is noted as an open question, not resolved.
  • What was not found anywhere in the 133-function decompiled corpus: any checksum, CRC, XOR, or sum routine; any reference to the 0x0E000000 Flash window outside the 10 pre-seeded save-bus functions; any function that assembles the 104-byte records seen in the .sav file. The serialization/checksum layer that decides what goes into the save buffer is simply absent from this decompilation slice. All claims about field meaning (as opposed to field byte layout) below are therefore HYPOTHESIS at best.
  • The one available .sav file is a pristine, unplayed, factory-initialized save (mutated_byte_count: 0 per the packet's own profiler, and confirmed here — all 100 stage-record slots across the three large blocks are byte-identical copies of a single 104-byte template). No gameplay-mutated sample exists in this workspace, so no checksum could be verified against a changed value — there is nothing to recompute against, and the automated profiler independently found zero candidate checksum/counter spans.

Everything below distinguishes CONFIRMED_VERIFIED (proven by code AND bytes), CONFIRMED_STATIC (proven by code OR bytes alone), and HYPOTHESIS/UNKNOWN.

3. Save Writer, Reader & Caller-Chain Architecture

All 10 functions below come from ghidra/save_related_functions.c (the pre-seeded MMIO-adjacent set) and are cross-referenced against ghidra/callgraph.json. No caller outside this 10-function cluster was found — every entry point's callers list in the callgraph is empty, and several functions end in (*UNRECOVERED_JUMPTABLE)(...), i.e. Ghidra could not statically recover an indirect call/return target. This means the actual game logic that decides when to erase/write a save, and what bytes to put in the in-RAM buffer before flushing, is not reachable from this decompiled slice — it is called indirectly (function-pointer dispatch table, see FUN_0802e7d8 below) from code outside the 133-function set.

3.1 Hardware ID probe / dispatch init — FUN_0802e7d8 (entry, no static callers)

Sets a control register bitfield (*_DAT_0802e7f8 = ... | 3), then calls the ID-probe FUN_0802e2fc, then walks a table at _DAT_0802e800 of records (stride 0x14/20 bytes, with a short chip-ID at offset 0x28 relative to the record... as decompiled) looking for a match to the probed ID, falling back to the default (first with a zero byte at +0x28). On match/fallback it populates 6 function-pointer globals (_DAT_0802e854.._DAT_0802e868) from the matched record's fields and tail-calls through UNRECOVERED_JUMPTABLE. This is a classic Flash-chip dispatch-table initializer (install the read/write/erase/etc. function pointers appropriate to the detected chip), not a save-data writer itself.

3.2 Chip ID probe — FUN_0802e2fc [MMIO-SEED] (caller: FUN_0802e7d8)

Writes the Flash unlock handshake 0xAA → *_DAT_0802e324 (bank 0x5555), 0x55 → *_DAT_0802e328 (bank 0x2AAA), then 0x90 (autoselect/ID-entry command) to the first address. Busy-waits a software delay loop. Reads back manufacturer ID via func_0x0802ec5c(_DAT_0802e370) and device ID via func_0x0802ec5c(0xE000000). Then issues the Flash reset/exit sequence 0xAA/0x55/0xF0/0xF0 to a second unlock-pair address, delays again, and tail-calls through an unrecovered jump table with (manufacturerID<<8 | deviceID). CONFIRMED_STATIC: this is the standard parallel-Flash "read manufacturer+device ID" sequence, addressed at 0x0E000000 (confirmed: func_0x0802ec5c(0xE000000) literal).

3.3 Latency-sensitive block copy — FUN_0802e4ec (caller: FUN_0802e968)

Copies a run of undefined2 (halfword) units from a source computed from _DAT_0802e50c to the caller-supplied buffer, length derived from (_DAT_0802e510 - _DAT_0802e50c). Used as a scratch-buffer snapshot (likely to preserve code/data that must run from fast RAM while Flash commands are in flight, since Flash reads are not available during erase/program). Generic driver plumbing, not save-field-specific.

3.4 Sector erase — FUN_0802e968 [MMIO-SEED] (no static callers recorded)

Guarded by (param_1 & 0xFFFF) < 0x10 (i.e. only sector indices 0–15 are valid — consistent with a 64 KiB Flash chip organized as sixteen 4 KiB sectors). Issues 0x80/0xAA/0x55/<sector_addr>:0x30 — the standard Flash sector-erase command — after snapshotting via FUN_0802e4ec, then calls func_0x0802ec54(2, puVar7, 0xFF, *_DAT_0802e9ec) (a generic low-level primitive, body not in this corpus) to poll for erase completion, and sets a status register bitfield.

3.5 Byte/word program primitives — FUN_0802e550, FUN_0802e61c, FUN_0802e6b4 [MMIO-SEEDs]

All three share the same shape: optional bank-select via the external func_0x0802e2d8 when the detected chip reports size 0x20000 (128 KiB — i.e. this driver is written generically for both 64 KiB and 128 KiB Flash parts, even though this title's declared media is 64 KiB/512 Kbit), a halfword copy loop into a stack buffer, then a tail-call into func_0x0802ec54(...) with an address computed as (sector_or_offset << shift) + 0xE000000 — i.e. the actual byte-program MMIO write, whose low-level body is not in the decompiled set (likely a BIOS-adjacent or inlined-elsewhere routine). These differ only in parameter order/count, suggesting they are specializations for "write N bytes at offset" vs. "write page" call shapes.

3.6 Write-with-retry wrappers — FUN_0802e74c → FUN_0802e61c, FUN_0802e790 → FUN_0802e6b4

Both retry up to 3 times: call a generic low-level primitive func_0x0802ec50(...)/compare, and only invoke the corresponding program primitive (§3.5) if the generic path reports non-zero, breaking out on success. This is the write-verify-retry layer standard in commercial Flash SDK drivers of this era. No caller of FUN_0802e74c/FUN_0802e790 is present in the decompiled corpus.

3.7 Signed division w/ div-by-zero trap — FUN_0802ed1c [MMIO-SEED, listed but NOT save-specific]

A textbook restoring binary-division algorithm (__divsi3-style compiler runtime support), calling func_0x0802ed18() (not decompiled) on division by zero. This function was included in the seed set presumably because its address range is adjacent to the Flash driver cluster, but its logic is a generic arithmetic runtime routine, not a save I/O function. Flagged here explicitly so it is not mistaken for save logic.

3.8 What is missing (and why confidence is capped at LOW–MEDIUM)

No function in ghidra/decompiled.c or ghidra/save_related_functions.c:

  • assembles a 104-byte stage record, the HAG/SHO/ROY metadata blocks, or the +0x9000 mirror copy,
  • computes any running sum/XOR/CRC over save bytes,
  • calls FUN_0802e74c, FUN_0802e790, FUN_0802e7d8, or FUN_0802ed1c from a traceable address.

The caller chain stops at the hardware driver boundary. We can state with confidence how bytes would physically reach Flash, but not which game-logic routine decides what those bytes are, nor whether/how a checksum is computed — because that code is not present in this decompiled slice.

4. Magic Signatures & Checksum / Integrity Algorithm

No checksum or CRC algorithm could be identified or verified.

  • The automated profiler's candidate_checksum_or_counter_spans_hex is empty for this release.
  • No decompiled.c function references the 0x0E000000/Flash window other than the 10 functions in §3, and none of those 10 perform summation/XOR/CRC arithmetic over a buffer.
  • The only .sav sample available is an unmutated factory-default save (all three large record blocks are 100% identical copies of one 104-byte template; mutated_byte_count: 0). There is no second (post-gameplay) sample to diff against, so even a black-box/statistical checksum search has nothing to correlate against.

6. Save Fuzzing & Counterfactual Verification Plan

Since no .ss paired save states exist in this workspace (states/ is empty for this legacy checkpoint cohort) and the only .sav sample is pristine, the following plan describes what a future round with live emulator save states should test. All mutations should be applied to a copy of saves/cap-00-future-0.sav, with before/after hashes recorded, then loaded in-emulator from a gameplay.ss/final.ss pair per the standing paired-state requirement.

  1. Mirror-write confirmation — Flip one byte inside 0x3F94–0x3FFF (e.g. the tag byte at 0x3F94), boot, enter and exit the in-game save screen without saving, then re-dump SRAM. Prediction: if the game treats 0xCF94 as an independent backup that only syncs on explicit save, the mirror will diverge after the flip and only one side will change; if the game treats it as a cold-start sanitize pass, both may reset to defaults. This directly tests the +0x9000 redundancy mechanism described in §2/§4.
  2. Stage-record write locus — Clear/complete the first puzzle stage in-game, save, and diff against cap-00-future-0.sav. Prediction: exactly one of Block A/B/C's first 104-byte record will change from the all-zero template to a non-zero value; this will immediately disambiguate "A/B/C are redundant copies" vs. "A/B/C are distinct tables" (§2) — if more than one block changes identically, redundancy is confirmed; if only one changes, distinct tables is confirmed.
  3. Field-boundary mutation — Mutate only +0x0A–+0x0D (the candidate score/time u32) of the first stage record to 0xFFFFFFFF, reload. Prediction: if this is a best-time field, UI should show an implausible/garbage time or trigger a sanitize-on-load reset to default; if the save reload instead crashes or shows corruption across multiple stages, the field boundaries assumed here are wrong.
  4. Checksum-repair probe (negative control) — Because no checksum routine was found, flip an arbitrary byte in an active record region (not the tags) and reload with no recomputation of anything. Prediction: if the game accepts the mutated save without any corruption warning or silent revert, this is positive evidence that no checksum exists for that region, strengthening §4's conclusion. If the game instead rejects/resets the save, a checksum or validity check exists somewhere not yet located, and the search in §3/§4 should be repeated against a larger decompiled function set.
  5. ROY-block asymmetry probe — Since 0x9DA8 has no +0x9000 mirror, mutate a byte in 0x9DA8–0x9FFF only, reload, and check whether the game silently accepts it (supporting "single-copy, unmirrored table") or detects/resets it (supporting an as-yet-unlocated separate integrity mechanism for this specific block).
  6. Fresh-vs-restore matched control — Run two matched-duration sessions: (a) fresh boot → save immediately with no play, (b) fresh boot → play stage 1 → save. Diff both resulting .sav files against cap-00-future-0.sav and against each other to isolate exactly which bytes the "no-op save" path touches (candidate: initialization of the HAG/SHO/ROY tags) versus which bytes only change after real gameplay (candidate: Block A/B/C records).

Open Questions

  • What routine (outside this decompiled 133-function set) actually assembles save records and invokes the §3 driver? It is reached only via an unrecovered indirect jump table, so static analysis here cannot find it.
  • Is there a checksum/CRC anywhere in the title's save path, or does it rely solely on the chip-level write-verify-retry in §3.6 for integrity? No evidence either way.
  • Do Blocks A, B, C represent three redundant full copies, three difficulty/world-specific stage tables, or something else? The differing record counts (35/35/30) argue against simple full-copy redundancy but are not conclusive.
  • What do the HAG/SHO/ROY 3-letter tags mean, and why is ROY unmirrored while HAG/SHO are mirrored at +0x9000?
  • Is the 0x6D98 value (0x00000007) a counter, a flag, or a default game parameter? No code reference was found to confirm either way.
