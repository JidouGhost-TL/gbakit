All findings below are derived only from saves/*.sav, ghidra/decompiled.c (278 functions), ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware addresses. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (header, media geometry, flash drivers and both checksums are HIGH/verified; most sector-0 payload semantics are LOW/unknown).

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is Flash 512K (64 KiB file), SDK tag FLASH512_V131, base 0x0E000000, 4 KiB sectors. Only sectors 0–4 (0x0000–0x4FFF) are used; 0x5000–0xFFFF is erased 0xFF in both samples.
  • Magic URBZ0011 at file offset 0x00, compared byte-by-byte (8 bytes) in FUN_0804d694 and present in both .sav files.
  • Header checksum: 16-bit little-endian word-sum over 0x00–0x17 must equal 0x0000; the stored word at 0x0E is the two's-complement negation of the sum of the other 11 words. Verified numerically on both samples (Section 4).
  • Per-sector checksum for sectors 1–4: the same word-sum over the whole 0x1000 sector must equal 0x0000, checked by FUN_0804d9b4. In both samples sectors 1–4 are all-zero, so this passes trivially (weak verification — see open questions).
  • The PACKET cold-reload probe (mutation at 0x0B → save rejected/re-initialised) is fully explained: byte 0x0B lies inside the header checksum cover, so any single-byte header mutation breaks the zero-sum (reproduced in Python, Section 4).

Static-only (CONFIRMED_STATIC): the full load/save caller chains (Section 3), the language byte at 0x0A, the sector-valid flags at 0xCC–0xCF, and the stream cursor at 0xD4.

Unknown / hypothesis: semantics of almost all sector-0 payload bytes at 0x18–0xFFF beyond observed pointer-like values. No backup/mirror copy and no generation counter were found (byte 0x0B is a flag written as literal 1, not an increment — see Section 2). There is no integrity cover over the sector-0 payload (0x18–0xFFF): the header checksum covers only 0x00–0x17.

3. Save Writer, Reader & Caller-Chain Architecture

Addressing note: Ghidra _DAT_080xxxxxx symbols are literal-pool pointers whose target values are not recovered in this decompilation, so absolute RAM mirror addresses (0x02xxxxxx) cannot be honestly stated. Struct-relative offsets (+0x0A, +0xCC, …) are exact as decompiled. Every function below ends in an UNRECOVERED_JUMPTABLE indirect jump in the decompilation; callers/callees were therefore mapped by combining ghidra/callgraph.json with a textual FUN_/func_0x reference scan of ghidra/decompiled.c (the callgraph alone under-reports edges through those trampolines — e.g. it lists no callers for 0x0806b61c, while the text shows FUN_0800d7b4 calling it).

3.3 Game-level save system (0x0804d6xx–0x0804da48)

Checksum core — FUN_0804da24: s16 sum = 0; for (i = len>>1; i; i--) sum += *ptr++; return sum; (16-bit wrap). Callers: FUN_0804d624, FUN_0804d9b4.

Load / init (entry) — FUN_0804d6f0 (no static caller; reached via unrecovered jump-table/state dispatch):

  1. Allocates a 0x1000 buffer (FUN_08032e48, malloc+memset) and stores the pointer at struct +0x18.
  2. FUN_0800d7a4() identifies the flash chip.
  3. FUN_0804d694 reads the 24-byte header (FUN_0800d7b4(0, 0x18, struct)), requires FUN_0804da24-style sum of 12 words == 0, then compares 8 bytes against a second (ROM template) copy — the URBZ0011 check.
  4. On failure: FUN_0804da48 creates a fresh header (Section 4), FUN_0804d764 zeroes the buffer (FUN_08032fac = memset), and sectors 0x1000–0x4000 are written from the zeroed buffer — i.e. blank re-initialisation, exactly the probe outcome.
  5. FUN_0804d938 loads sectors 1–4 (below).
  6. FUN_08061a80(*(u8*)(struct+10)) applies the persisted language byte (Section 3.4).

Sector 1–4 loader — FUN_0804d938, for slot = 0..3 (entry stride 0x2C):

  • Retries (up to 2 attempts in the decompiled loop) FUN_0804d9e4(slot) = read (slot+1)*0x1000, 0x1000 into the +0x18 buffer, then FUN_0804d9b4(slot) sets *(bool*)(struct + 0xCC + slot) = (FUN_0804da24(buffer, 0x1000) == 0).
  • Invalid: the 0x2C RAM entry is memset to 0 (FUN_08032fac).
  • Valid: stream cursor globals are reset (struct+0xD4 = buffer, struct+0xD8 = 0) and FUN_08023e3c deserialises the block into the entry (Section 3.4).

Save / flush trigger — FUN_0802e5f8 (no static caller; jump-table dispatched):

  1. FUN_08061a80(*(struct2 + 0xC)) — switch current language from another struct field.
  2. FUN_0804d74c — mutates the in-RAM save struct before flush: *(u8*)(struct+0x0A) = FUN_08061afc() (current language global, FUN_08061afc) and *(u8*)(struct+0x0B) = 1.
  3. FUN_0805ba4c() → FUN_08068398 (pre-flush hook; clears bits in two globals — semantics unknown, possibly sound/timer).
  4. FUN_0804d624 — flush sector 0: reads the on-flash header back to the stack (FUN_0800d7b4(0,0x18,stack)), zeroes RAM word at +0x0E, stores *(s16*)(struct+0x0E) = -FUN_0804da24(struct, 0x18), compares the RAM struct against the read-back copy, and if different writes the whole sector (FUN_0800d800(0, 0x1000, struct)). Honest caveat: the decompiled compare loop counts 0x400 iterations against a 0x18-byte stack buffer, which cannot be literally correct; the compare extent (header-only vs. full sector) is a decompiler artefact and is marked CONFIRMED_STATIC for the flow, UNKNOWN for the exact extent. Either way, the mutated fields from step 2 (0x0A, 0x0B, checksum 0x0E) are exactly the bytes that differ in the header between the two samples.
  5. FUN_0805ba58() → FUN_08068368 (post-flush hook, unknown semantics), then a scene/state call (FUN_080333b8(3) or FUN_080333c8(5,2,0)).

Header creation — FUN_0804da48: memcpy (FUN_08033018, FUN_08033018) of a 24-byte template into the struct, sum of 12 words computed inline, struct_u16[7] = -sum (byte offset 0x0E), then sector-0 write via the flash FUN_0800d800(0, 0x1000, …). This proves the magic and default header bytes exist as a ROM template in code, not just in the .sav.

3.4 Serialisation / stream reader (sectors 1–4 → RAM entries)

  • FUN_0804d800 (game stream-copy, distinct from the flash wrapper at 0x0800d800): maintains cursor at struct+0xD4 and a state word at struct+0xD8 (if > 0, cursor is advanced by 1 and the state cleared — an alignment/skip step), then memcpy(dst, cursor, n); cursor += n;. This is a sequential deserialiser over the sector buffer. No symmetric serialiser was found in the traced set — the sector 1–4 writer is an open question (Section 6 of the JSON); sector 0 is written as a raw struct dump, so sectors 1–4 may likewise be raw dumps of another RAM image and this reader may serve a different (e.g. preview/header) purpose.
  • FUN_08023e3c deserialises one 0x2C entry: 1 byte to a global, then 4 B → entry+0x00, 6 B → entry+0x04, 3 B → entry+0x0C (with sign-extension of bit 23: if (v & 0x800000) v |= 0xFF000000), 16 B → entry+0x10, then FUN_08048d8c unpacks 5 packed bytes into 10 fields at entry+0x20 offsets {0,2,5, 1,6, 3,9, 4,7, 8} (bit-fields of widths 1/2/5, 3/5, 4/4, 3/5, 5 bits — needs/motives-style nibble stats is a hypothesis only, not asserted).
  • FUN_08061a80: stores its argument to a global byte and, if < 6, dispatches through a 6-entry table — six locales matching the title's (En,Fr,De,Es,It,Nl). This is why header byte 0x0A is identified as the language id. Callers: FUN_0804d6f0 (load), FUN_0802e5f8 (save trigger), FUN_08061a60.

How each caller was mapped: (1) start from the three MMIO seeds in ghidra/save_related_functions.c; (2) take callers/callees from ghidra/callgraph.json; (3) repair missing edges with a textual scan for FUN_080…/func_0x080… in ghidra/decompiled.c (needed because most functions exit via unrecovered jump tables); (4) read each candidate body in full before assigning a role. Chains terminate at FUN_0804d6f0 and FUN_0802e5f8, which have no static callers — they are reached through the game's unrecovered state dispatch, and no caller is invented for them.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Bytes 55 52 42 5A 30 30 31 31 = ASCII URBZ0011 at offset 0x00, size 8.
  • In code: FUN_0804d694 compares 8 bytes of the RAM header against a template copy after the checksum passes; FUN_0804da48 installs that template with a 24-byte memcpy. Verified in both .sav files. Confidence: CONFIRMED_VERIFIED.

Checksum algorithm (one core, two uses)

Core (FUN_0804da24):

short FUN_0804da24(short *p, uint len) {   // len in bytes
  short s = 0;
  for (uint n = len >> 1; n != 0; n--) s += *p++;
  return s;                                // sum16_le, modulo 2^16
}
  • Header checksum: covered range 0x00–0x17 (24 bytes, 12×u16_le), stored as u16_le at 0x0E (word index 7). Writer sets the word to 0, sums, stores -sum (FUN_0804d624; creator does the equivalent inline in FUN_0804da48). Validator requires the total, including the stored word, to be 0x0000 (FUN_0804d694). Formula: stored = (-Σ other 11 words) mod 65536; equivalently Σ all 12 words ≡ 0 (mod 65536). No seed, no XOR/CRC, no complement beyond negation — this is sum16_le with two's-complement store.
  • Sector 1–4 checksum: same core over the full 0x1000 bytes (FUN_0804d9b4 requires FUN_0804da24(buffer, 0x1000) == 0). No separate stored field was located inside those blocks; for an all-zero block the sum is trivially 0. Where the compensating word lives in a non-empty block is unknown (no writer traced), so this use is CONFIRMED_STATIC in code and only weakly verified on samples.

Open questions

  1. Which function writes non-empty sectors 1–4, and where does the compensating checksum word live inside such a block? No serialiser symmetric to FUN_08023e3c was found in the 278 decompiled functions.
  2. What are the four 0x2C records (sectors 1–4) semantically — households, districts, or something else? Both samples have them empty.
  3. Semantics of sector-0 payload regions 0x300, 0x34A, 0x610, 0x70C, 0x730 (pointer/code-shaped, populated only in cap-01).
  4. Exact compare extent in FUN_0804d624 (decompiler artefact: 0x400 iterations vs. 0x18-byte stack buffer) — does a flush happen only when the header changes, or when any sector-0 byte changes?
  5. Index→language mapping for byte 0x0A (only 0 = En is consistent with the samples' provenance; the other five assignments are untested).
  6. Meaning of header constants 0xFF80 at 0x08 and 0xFFFF at 0x12, and of the pre/post-flush hooks FUN_08068398/FUN_08068368.
  7. Absolute RAM base of the save struct: _DAT_ literal-pool targets are unrecovered, so struct-relative offsets are proven but the 0x02xxxxxx base is not.
