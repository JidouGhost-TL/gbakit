1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte-level agreement):

  • The save medium is EEPROM, 8192 bytes total, addressed in 8-byte blocks (1024 blocks), matching the packet's EEPROM 64K tag.
  • The EEPROM image is organized as three 768-byte (0x300) slot records at byte offsets 0x000, 0x300, 0x600, plus a single 8-byte global metadata block at byte offset 0x900 (EEPROM block 0x120).
  • A per-slot checksum at relative offset 0x0F is proven, byte-for-byte, against both .sav files and all three slot copies: it is the bitwise one's complement of an 8-bit sum over the whole 768-byte record. This directly contradicts the literal text of the Ghidra decompilation (which renders the store as an arithmetic negation) — see Section 4 for the discrepancy and the proof.
  • The low-level EEPROM read/write/verify driver chain (FUN_0806bc1c / FUN_0806bcd4 / FUN_0806bdb8 / their DMA3 helpers) is fully traced and its block-address arithmetic exactly reproduces the slot layout measured in the real .sav files.

What remains open (see Section 6 and open_questions in save-format.json):

  • No checksum/validity verification call was traced anywhere in the load path — only the save path computes/writes the checksum. Whether the game ever rejects a corrupted slot on load is unproven and is the top fuzzing priority.
  • The semantic meaning of most payload bytes (the 240-byte flag table and the 480-byte stage/record table) is unproven; only their byte/word structure is proven, from the checksum routine's loop bounds.
  • True callers of the four save-cluster entry points could not be statically resolved: every function in this ROM region ends in an indirect (*UNRECOVERED_JUMPTABLE)() call, so the engine appears to dispatch tasks through a function-pointer table rather than ordinary BL instructions, which defeats simple static-callgraph caller extraction.
  • Only two capture samples were available, and all three slot copies were byte-identical in both — so slot redundancy semantics (independent save files vs. primary/backup copies) could not be exercised.

This geometry is derived directly from the two reader/writer loops:

  • FUN_08002930(slot_index) (save+verify) and FUN_08002a50(slot_index) (load) both iterate uVar2 from 0 to 0x5F (96 iterations), calling the EEPROM driver at block address uVar2 + slot_index*0x60, with the destination/source RAM pointer advancing by 8 bytes each iteration. 96 blocks x 8 bytes = 0x300 bytes, and slot_index*0x60 blocks = slot_index*0x300 bytes — exactly the 0x000/0x300/0x600 spacing measured in the files.
  • FUN_08002e3c (write) / FUN_08002eac (read) both use the single fixed block address 0x120 (= 0x900/8), matching the one EEPROM block (0x900-0x907) that is the only byte range that differs between the two capture samples (see saves/hexdump_and_diffs.txt, lines 76-84: all 8 bytes flip from 0xFF to 0x00).

Redundancy: Cannot be confirmed from the available samples. All three slot records are byte-identical to each other in both .sav files, so it is impossible to tell from this data alone whether slots 0/1/2 are three independently selectable save files (most likely, given they are addressed by an explicit slot_index parameter) or a primary/backup/tertiary redundancy scheme for a single logical save. No generation/sequence counter distinguishing the three copies was found. This is listed as an open question.

Selection rule for the global meta block: FUN_08002eac reads the block and inspects the u16 at its relative offset +6 (absolute file offset 0x906-0x907). If that value is 1 or 2, it is written into *puRam08002ef4 (believed to be an "active slot" indicator); any other value (including the 0x0000 observed in both current samples) takes the "no active slot" branch and clears *_DAT_08002ee0. Neither sample currently exercises the 1/2 branch, so this selection rule is CONFIRMED_STATIC (proven in code) but its real-world trigger is still a HYPOTHESIS.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (EEPROM serial DMA3 bitstream)

All I/O to the save medium goes through 0x0D000000 via DMA3 (0x040000D4), consistent with standard GBA EEPROM access. Six functions form this layer (all seeded from ghidra/save_related_functions.c and fully reproduced in ghidra/decompiled.c):

AddrName (assigned)RoleCallers tracedNotes
0x0806bb9cEEPROM_DMA3_XFERread/write primitive0x0806bc1c, 0x0806bcd4Lowest-level primitive. Takes a source/dest pair and a block-count-derived control word, drives DMA3 against 0x0D000000, busy-waits on a ready bit. Shared by both directions; direction is determined entirely by which operand is the EEPROM address.
0x0806bc1cEEPROM_READ_BLOCKread0x0806bdb8Serializes an address into the GBA EEPROM read-request bitstream, issues it via two EEPROM_DMA3_XFER calls, then deserializes the 4 returned 16-bit words into the caller's 8-byte destination buffer (param_2[0..3], written high-to-low).
0x0806bcd4EEPROM_WRITE_BLOCKwrite(none traced — see 3.3)Serializes address + 4 source words (param_2[0..3]) into the write bitstream, shifts it out via EEPROM_DMA3_XFER, calls EEPROM_WRITE_STROBE to commit, then polls bit 0 of 0x0D000000 until the chip reports ready. Classic EEPROM write-with-busy-poll pattern.
0x0806bdb8EEPROM_VERIFY_BLOCKread+compare(none traced)Calls EEPROM_READ_BLOCK into a local stack buffer, then compares all 4 words against the caller-supplied expected buffer (param_2). Returns 0 on exact match, 0x8000 on the first mismatch. This is the "verify" half of every write-then-verify pair in this ROM.
0x0806baf4EEPROM_WRITE_STROBEwrite (helper)0x0806bcd4Issues the write-commit/strobe sequence; only ever called from EEPROM_WRITE_BLOCK.
0x0806bb58EEPROM_WRITE_TEARDOWNwrite (helper)0x0806bcd4Clears an internal queue-head pointer and an interrupt-enable bit at the end of a write; only ever called from EEPROM_WRITE_BLOCK.

No Flash (0x5555/0x2AAA command sequence) or SRAM byte-copy code was found anywhere in ghidra/decompiled.c's 87 functions — consistent with the packet's declared media type of EEPROM 64K.

3.3 All callers traced, and how each caller mutates the in-RAM save struct before flushing

This is the central limitation of this analysis: ghidra/callgraph.json records essentially zero direct callers for the four save-cluster entry points (0x08002930, 0x08002a50, 0x08002e3c, 0x08002eac all show "callers": [], except 0x08002ac8 which shows exactly one — 0x08002e3c). The reason is visible directly in the decompiled source: every single function in this 87-function corpus ends with

/* WARNING: Could not recover jumptable at 0x0...  Too many branches */
/* WARNING: Treating indirect jump as call */
(*UNRECOVERED_JUMPTABLE)(...);

This means the real calling convention for this engine is an indirect, function-pointer/task-table dispatch (every function "returns" by jumping through a table rather than via ordinary BL/BX LR), which is invisible to a static BL-based callgraph. How each traced caller mutates RAM before flushing:

  • FUN_08002930 (save+verify a slot): For uVar2 = 0..0x5F, calls EEPROM_WRITE_BLOCK(uVar2 + slot_index*0x60, iVar3) where iVar3 starts at _DAT_0800299c and advances by 8 bytes each iteration — i.e. it streams a 768-byte RAM buffer (base address unresolved from these files, since _DAT_0800299c is a literal-pool reference whose resolved value isn't present in the decompiled text) out to EEPROM 8 bytes at a time. If any block write fails (sVar1 != 0), it aborts immediately to the cleanup label. On success, it then re-reads and verifies all 96 blocks via EEPROM_VERIFY_BLOCK. The RAM struct itself is not mutated by this function — it is the source of the flush, implying some other, untraced caller fills it in before this is invoked.
  • FUN_08002a50 (load a slot): Symmetric 96-block loop using EEPROM_READ_BLOCK into a RAM buffer at _DAT_08002a90 (address unresolved). This populates the RAM mirror from EEPROM; it does not call ComputeRecordChecksum or CompareMagicStruct anywhere in its body — i.e., no checksum/magic verification was traced on load (see Section 6, this is the single most important open question for fuzzing).
  • FUN_08002e3c (write global meta block): Zeroes two u16 fields in a RAM struct (_DAT_08002e94-relative), copies one u16 from an external global (_DAT_08002ea0) into a third field, sets a flag byte at +0xE to 1, calls ComputeRecordChecksum (the only directly-traced BL edge among this cluster), then writes only an 8-byte slice of that larger struct (base _DAT_08002e94 + _DAT_08002e98) out to EEPROM block 0x120, verifying the write afterward. Because ComputeRecordChecksum needs the full 768-byte record to run its loops, the struct it operates on here must be larger than the 8 bytes actually persisted — the fate of the rest of that struct is unresolved (Section 6).
  • FUN_08002eac (read global meta block): Reads EEPROM block 0x120 into a RAM buffer at _DAT_08002edc, then branches on the u16 at +6 of that buffer (== 1 or == 2 -> write it into *puRam08002ef4; otherwise -> zero *_DAT_08002ee0). This is the clearest and most directly actionable field discovered: a global "active slot selector" gate.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Header bytes (relative offset 0x00-0x0D, 14 bytes)

Identical 14-byte sequence observed at the start of all three slot records in both samples:

41 4d 52 45 42 4d 4f 42 d2 00 32 58 41 4d
A  M  R  E  B  M  O  B  .  .  2  X  A  M

FUN_08002a94 compares a struct's first 14 bytes against a constant (_DAT_08002abc) and additionally requires byte +0xE to be 0x00. Byte +0xE of this header region is actually 0x2D (part of the 15th/16th bytes 2d 4e = "-N", which lie just past the 14-byte compared region), so this specific check is not satisfied by the observed slot layout — meaning either FUN_08002a94 validates an unrelated in-RAM structure, or the validity bit lives somewhere this analysis has not located. This is flagged HYPOTHESIS, not confirmed, precisely because the code's own stated precondition fails against the real bytes.

As a purely observational (non-code-driven) note: reading the first 8 bytes in reverse byte order yields BOMBERMA, and the 6 bytes at relative offset 0x0A-0x0F reversed yield N-MAX2; concatenated (BOMBERMA + N-MAX2 = BOMBERMAN-MAX2) this resembles a byte-reversed encoding of the title given in this release's own packet metadata ("Bomberman Max 2"). This is offered only as a plausible, falsifiable hypothesis about why this constant exists (e.g. a reversed title string used as a cartridge/profile signature) — it is not verified against any code path, since the comparison target _DAT_08002abc's literal value could not be resolved from the files in this workspace.

4.2 Checksum algorithm (relative offset 0x0F, 1 byte) — verified against real bytes

FUN_08002ac8 (ghidra/decompiled.c lines ~513-565) computes, for a 768-byte (0x300) record param_1:

  1. Zero byte param_1[0x0F].
  2. Sum (8-bit accumulator, mod 256) bytes param_1[0x00..0x0D] (14 bytes).
  3. Sum bytes param_1[0x0E] and param_1[0x0F] (the latter is now 0).
  4. Sum bytes param_1[0x10..0x1F] and param_1[0x20..0x2F] (32 bytes, two interleaved 16-byte ranges).
  5. Sum bytes param_1[0x30..0x11F] (240 bytes, iterated as 5 chunks of 48 interleaved even/odd bytes).
  6. Sum every little-endian u16 word in param_1[0x120..0x2FF] (30 rows x 8 words = 480 bytes).
  7. Store the result into param_1[0x0F].

Decompiler discrepancy, caught by byte-level verification: step 7 is rendered in the decompiled C as:

*(char *)(param_1 + 0xf) = -(char)sVar1;

i.e. an arithmetic two's-complement negation of the low byte of the sum. Computing this literally against both real .sav files produces 0x4F for every one of the 6 slot copies, but the actual stored byte in every case is 0x4E — a constant off-by-one. Testing the bitwise one's complement (~sum & 0xFF, i.e. NOT rather than arithmetic negate) instead reproduces the stored byte exactly in all 6 cases. This is reported as a probable Ghidra NEG/MVN misdecompilation (ARM/Thumb's "negate" and "bitwise-NOT" instructions are easy to conflate when the decompiler can't see the exact opcode), not as a semantic hypothesis — it is proven by direct byte comparison.

Python verification run against the real files in this workspace:

def raw_sum8(buf):
    b = bytearray(buf)
    b[0xf] = 0
    s = 0
    for i in range(0xe):
        s += b[i]
    for i in range(2):
        s += b[0xe + i]
    for i in range(0x10):
        s += b[0x20 + i] + b[0x10 + i]
    for u4 in range(5):
        for u3 in range(0x18):
            iVar2 = u3 * 2 + u4 * 0x30
            s += b[iVar2 + 0x31] + b[0x30 + iVar2]
    for u4 in range(0x1e):
        for u3 in range(8):
            off = 0x120 + u3 * 2 + u4 * 0x10
            s += b[off] | (b[off + 1] << 8)
    return s & 0xff

Confidence: CONFIRMED_VERIFIED. All 6 available samples (2 files x 3 slots) match exactly under the one's-complement formula and none match under a literal reading of the decompiled negation.

Caveat: because both samples carry byte-identical slot payloads (Section 2), this result only proves the formula against a single underlying content value (raw_sum=0xB1 in every case). No sample with a different payload was available to additionally confirm the formula generalizes across varying content — this is listed as a fuzzing target (Section 6) rather than assumed.

6. Save Fuzzing & Counterfactual Verification Plan

Caveat on current workspace state: the states/ directory for this cohort is empty — no paired .ss pre/post save states are currently available here, so none of the following mutations could be executed and observed in this session. They are written up as a concrete, falsifiable plan for the next round that does capture paired .ss states, per fuzzing_targets in save-format.json.

  1. Checksum enforcement probe (highest priority). Corrupt only slot_record_0[0x0F] (the checksum byte) to an arbitrary wrong value, leave every payload byte untouched, reload from a pre-save .ss. Prediction: because no verify-on-load call was traced from FUN_08002a50, the slot should load with no visible rejection — if the game instead shows a corruption warning or resets the slot, that disproves this report's load-path analysis and reveals an untraced validation call. Falsifiable either way.
  2. Flag-table mutation with correct checksum repair. Flip one 0x0000 -> 0x0001 word inside slot_record_0[0x30..0x11F] (e.g. relative 0x60), recompute and rewrite the checksum using the verified one's-complement formula (Section 4.2), reload. Prediction: some discrete unlock/clear-state UI element should change state, if this region is in fact a flag table as hypothesized. A second identical trial without repairing the checksum isolates whether the checksum is enforced independently of payload validity.
  3. Global slot-selector probe. Set global_meta_block word at absolute offset 0x906 to 0x0001, then in a separate trial to 0x0002 (no checksum involved, since this 8-byte block has none). Prediction: FUN_08002eac's branch condition should trigger, changing which slot the title/continue screen treats as active, versus the 0x0000 baseline currently observed in both samples.
  4. Validity-byte probe. Set slot_record_0[0x0E] from the observed constant 0x2D to 0x00 (the value CompareMagicStruct requires for "valid"), repair the checksum, reload. Prediction: if CompareMagicStruct actually gates this struct's validity, behavior should change (e.g. slot now reads as valid/invalid where it didn't before); no observable change would support this report's hypothesis that CompareMagicStruct validates a different, untraced structure.
  5. Cross-content checksum regeneralization. Because both current samples share byte-identical slot payloads (raw_sum=0xB1 in every case), capture at least one .sav with genuinely different gameplay progress and re-run the Section 4.2 verification script against it, to confirm the one's-complement formula generalizes beyond the single content value tested here.
  6. Slot independence probe. Make a change only to slot_record_1 (e.g. via a "save to slot 1" in-game action if exposed) and confirm slot_record_0/slot_record_2 remain untouched, to resolve the open redundancy-vs-independent-files question from Section 2.

All mutation trials should retain the original pre-mutation .sav/.ss pair (per the standing fresh/restore-repeat and holdout-preservation requirements) so each result is a reproducible A/B rather than a one-shot destructive edit.
