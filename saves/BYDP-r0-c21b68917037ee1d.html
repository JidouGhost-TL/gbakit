2.2 Byte geometry (verified against both .sav files)

Derivation, step by step:

  1. Byte 0x0000 is 0xEE in both files. The writer FUN_08019504 writes single bytes 0x03, 0x01, 0x02, and finally 0xEE to the same address 0x0E000000 at successive stages of the write; 0xEE is the last write, so it is the resting value (Section 3.2). The reader FUN_08019c70 special-cases 0xEE as the "valid" sentinel value (Section 3.3).
  2. Bytes 0x0001–0x000F are the 15-byte ASCII string YDBTE_0000_KCEJ in both files. The writer writes a 15-byte block immediately after the first sentinel write; the validator FUN_08019cb4 reads 15 bytes and compares them against a ROM string (Section 4.1).
  3. The remaining non-zero bytes form two clusters with identical content: the payload head at 0x0010… and its twin at 0x4008… (Python-verified: the full 16,374-byte ranges 0x10–0x4005 and 0x4008–0x7FFD are byte-identical in both files). Two 2-byte values sit exactly between/after them: at 0x4006 and at 0x7FFE, equal to each other in each file (0xFD59 / 0xFDF8 little-endian). Section 4 proves these are the checksums of the preceding data ranges, which fixes the data length at 0x3FF6 by adjacency: checksum A immediately follows data A, data B immediately follows checksum A, checksum B immediately follows data B, and checksum B ends exactly at the end of the 32 KiB SRAM.
  4. There is no second sentinel or second magic for copy B. Bytes 0x4000–0x4005 are simply the zero tail of copy A's data. The header (sentinel + magic) is global, not per-copy.

2.3 Slots, copies, redundancy, counters, selection rule

  • Save slots: There is exactly one logical save slot. It is not split into multiple game slots anywhere in the file: one global header, one payload, duplicated once. (In save-format.json this is modelled as slot_0 = copy A region 0x0000–0x4007 including header, and slot_0_backup = copy B region 0x4008–0x7FFF; they are copies of one slot, not independent slots.)
  • Redundancy: Full dual-copy redundancy of the 16,374-byte data block plus its checksum. The writer serialises the RAM struct once (gather into one buffer, one checksum computation in FUN_08019504), then writes that same buffer and the same 2-byte checksum twice, to two different SRAM destinations, in one save operation.
  • Generation / sequence counters: None found. The two copies are byte-identical in both samples, including the checksum. There is no per-copy counter, timestamp, or "newer copy" marker anywhere in the non-zero bytes, and the writer code contains no increment-before-write of any header field. The only per-write changing value is the 4-byte field at data offset 0x00, and it is identical in both copies, so it cannot serve as a copy-generation discriminator either.
  • Selection rule (what is proven): On load, both copies are validated independently (magic and sentinel globally; checksum per copy) and the results are OR-combined into one status byte by FUN_08019c10 (Section 3.3). Status 0x00 means sentinel 0xEE, magic OK, copy A checksum OK, copy B checksum OK. Two entry points, FUN_08019628 and FUN_08019a9c, dispatch through a jumptable indexed by that status byte.
  • Selection rule (what is NOT proven): Which jumptable handler runs for "copy A bad / copy B good" (status 0x02) versus the reverse (status 0x01), and whether the good copy is copied over the bad one, loaded directly, or the save is discarded. The jumptables were not recovered by Ghidra (UNRECOVERED_JUMPTABLE at 0x08019646 / 0x08019ab6). Any "the game falls back to the valid copy" statement is therefore a hypothesis; the fuzzing plan in Section 6 is designed to settle it. The corpus cold-reload probe is consistent with active repair: mutating offset 0x10 (inside copy A data) was confirmed as an integrity-check hit, and the save was rewritten after mutation rather than reverted to blank — but the probe alone does not show whether copy B was the restore source.
  • Transient write states: During a save, byte 0x0000 cycles 0x03 → (magic) → 0x01 → (data A + checksum A) → 0x02 → (data B + checksum B) → 0xEE. A power loss mid-save therefore leaves sentinel 0x03, 0x01, or 0x02, which FUN_08019c70 maps to distinct non-valid status codes (0x40/0x20/0x10) — an intentional incomplete-write detector. See Section 3.2.

2.4 Active (non-zero) byte spans

Per-file Python enumeration (identical span layout in both files; only values at 0x10–0x13, 0x4006, 0x4008–0x400B, 0x7FFE differ):

0x00–0x18, 0x1C, 0x1E–0x20, 0x2C, 0x36, 0x4006–0x4010, 0x4014, 0x4016–0x4018, 0x4024, 0x402E, 0x7FFE–0x7FFF — 50 non-zero bytes total. This is an explicit corpus limitation.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

Two evidence sources were combined, because neither is complete alone:

  1. ghidra/callgraph.json (combined static C + runtime direct-calls.json): gives explicit callers/callees edges, e.g. 0x08019504 ← {0x08019b84, 0x08032d30}, 0x08019c44 ← {0x08019cfc, 0x08019d54}, 0x0803da98 ← {0x0803dbc0}, 0x08032d30 → {0x08019504, 0x080320a0, 0x08032984, 0x08032a0c, 0x08032b34, 0x08032b9c, 0x08032c7c}.
  2. Textual func_0x080xxxxx references inside ghidra/decompiled.c bodies: many library/trampoline functions end in an UNRECOVERED_JUMPTABLE tail-call, so the call graph records empty callees for them even though the body text plainly calls helpers (example: FUN_08019504 has callees: [] in the graph, but its body calls func_0x08019b94, func_0x080358dc, func_0x08019c44, and func_0x08019c04 nine times). Every chain below was traced in the body text and cross-checked against the graph; where the two disagree, the body text wins and the discrepancy is noted.

A consequence: functions reached only through the unrecovered jumptables (e.g. FUN_08035944, the scatter/deserialise routine, which has no textual caller) can be placed in a chain only as "jumptable-dispatched, exact entry unproven". Those placements are labelled HYPOTHESIS wherever they occur.

All _DAT_080xxxxx / iRam… / uRam… symbols are unresolved literal-pool placeholders in this corpus: the numeric RAM/ROM value stored at that ROM address was not recovered. Where a function's SRAM destination is one of these symbols, the on-SRAM offset asserted in this report is inferred from the .sav geometry and then verified by the checksum proof (Section 4), not read out of the code. That inference chain is stated explicitly each time.

3.2 The writer: FUN_08019504 (0x08019504)

FUN_08019504 is the sole save writer. Callers (call graph): 0x08019b84 and 0x08032d30 — both traced in Section 3.5. Its exact sequence (decompilation lines 368–459):

  1. func_0x08019b94() — clears the status/result record (FUN_08019b94 zeroes a dword and a byte at _DAT_08019bc0; the same record the writer later stores its result code into).
  2. uVar1 = _DAT_08019548 — the contiguous save buffer (RAM, address unresolved). func_0x080358dc(uVar1) serialises it: FUN_080358dc walks a table of (src_ptr, len) pairs at _DAT_08035940 and copies each RAM segment into the buffer in order, until a pair whose pointer is 0. This gather table — not any single struct — is the real definition of the in-RAM save layout, and its contents are the corpus's biggest gap.
  3. uStack_1a = func_0x08019c44(uVar1, _DAT_0801954c) — computes the checksum over the buffer; _DAT_0801954c is the buffer length (numeric value unresolved in code; 0x3FF6 inferred from .sav geometry, Section 2.2, and confirmed by the Section 4 proof).
  4. Then nine verified writes via func_0x08019c04, each storing its return code into *_DAT_08019550, aborting to a distinct error code on the first non-zero return:

On full success the final code is 0x0A. The code is stored as *(undefined1 *)(piVar3 + 1) = uVar4 where piVar3 = _DAT_08019550 — i.e. a status record holding (last write result, overall save result 0x0A–0x13).

Design reading (verified by the .sav resting state): the sentinel at offset 0x0000 acts as a write-progress marker. It is 0xEE only when a save completed all nine steps; 0x03, 0x01, and 0x02 each mean "died during stage N". The magic is written before either data copy, so a torn save can have valid magic but stale/torn data — which is exactly why each copy carries its own checksum and is validated separately.

Load entry points (both call FUN_08019b94 to clear the status record, then FUN_08019c10, then dispatch):

  • FUN_08019628 (0x08019628): if (status & 0xFF) > 0x22, writes 0x21 to *(iRam08019830 + 4) and returns; otherwise calls jumptable[status] ((**(code **)(status*4 + _DAT_08019648))()).
  • FUN_08019a9c (0x08019a9c): if (status & 0xFF) < 0x24, calls jumptable[status] (iRam08019ab8 table); otherwise writes 0 to *(_DAT_08019b70 + 4) and returns.

The two thresholds (0x23 vs 0x24 valid-status ceilings) and the two different out-of-range actions suggest two distinct load contexts (for example a boot-time load and an in-game load/continue), but which is which cannot be determined from this corpus — HYPOTHESIS. What is certain is that the per-status handlers (including the presumably-happy path at status 0, the one-copy-bad paths, and the no-save path) live in those unrecovered jumptables.

                        └─ (HYPOTHESIS) status-0 handler: FUN_08035944(validated_buffer)
                           scatters the buffer into the live RAM struct via table _DAT_080359a8

How the readers mutate RAM: the validators themselves are read-only toward SRAM but write two RAM buffers: FUN_08019cfc leaves copy A's 16,374 bytes in the buffer at _DAT_08019d34, FUN_08019d54 leaves copy B's in _DAT_08019d8c (as a side effect of checksumming — the read destination is the checksum input). A downstream handler therefore already has a fully materialised copy in RAM and needs only the FUN_08035944 scatter to make it live. Neither validator writes to SRAM; there is no code in the corpus that repairs a corrupt copy in place at load time (any repair must happen via a later full FUN_08019504 save — consistent with the cold-reload probe observing "save rewritten after mutation").

It matters to the save format only because it shares the FUN_080359ac field-refresh; it is not a save writer.
  • FUN_0803d8e8, FUN_08018f3c, FUN_08018f88, FUN_0801909c and the 0x080191xx/0x080192xx cluster: display/background initialisation, unrelated to saves.
  • The 0x080325xx–0x08032cxx cluster other than FUN_08032d30's chain: scene/presentation helpers reached from FUN_08032450; no save-bus access.

4.2 Checksum algorithm — exact formula

Checksum core, FUN_08019c44 (0x08019c44), decompiled (lines 627–647):

void FUN_08019c44(byte *param_1, uint param_2)
{
  uint uVar1 = 0;
  uint uVar2 = _DAT_08019c6c;              // seed (literal, value not printed)
  if (param_2 != 0) {
    do {
      uVar2 = uVar2 - *param_1 & 0xffff;  // subtract each byte, 16-bit wrap
      param_1 = param_1 + 1;
      uVar1 = uVar1 + 1 & 0xffff;
    } while (uVar1 < param_2);
  }
  (*UNRECOVERED_JUMPTABLE)(uVar2);        // return value in r0
}

That is, over the covered byte string B[0..n):

checksum = (SEED − Σ B[i]) & 0xFFFF
  • Algorithm class: sum16-family (negated byte sum), equivalently the 16-bit one's-complement of the byte sum when SEED = 0xFFFF. It is not a CRC, not XOR, and not a plain additive sum.
  • Seed: _DAT_08019c6c, not printed in the corpus. Python verification below pins it uniquely: only SEED = 0xFFFF reproduces the stored values; SEED = 0 (plain two's-complement negation) is off by exactly 1 on every copy in every file. The seed is therefore asserted as 0xFFFF with CONFIRMED_VERIFIED-by-verification status (the arithmetic leaves no other candidate: stored + Σ covered ≡ SEED (mod 65536) evaluates to 0xFFFF on all four copy/file combinations independently).
  • Endianness of the stored value: little-endian u16. In the writer it is stored from the 2-byte stack variable uStack_1a (func_0x08019c04(&uStack_1a, …, 2), ARM little-endian); in the readers it is compared against auStack_10[0] as a single u16. In the files: 59 FD = 0xFD59, F8 FD = 0xFDF8.
  • Covered range (copy A): save offsets 0x0010–0x4005 inclusive (16,374 bytes, 0x3FF6), i.e. everything from the 4-byte leading field through the payload tail, excluding sentinel, magic, and the checksum itself.
  • Covered range (copy B): save offsets 0x4008–0x7FFD inclusive (16,374 bytes).
  • Stored offsets: copy A at 0x4006 (immediately after covered range A), copy B at 0x7FFE (immediately after covered range B, ending at EOF).
  • Functions: computed by FUN_08019c44; invoked on the write path once by FUN_08019504 (the single result is written to both copies) and on the read path by FUN_08019cfc (copy A) and FUN_08019d54 (copy B).
  • Caveat on covered length: the code's length argument (_DAT_0801954c / _DAT_08019d40 / _DAT_08019d98) is an unresolved literal, so 0x3FF6 is inferred from checksum adjacency (Section 2.2), not read from code. Any shorter "true" length that stops inside the trailing zero region would produce the identical sum and is therefore indistinguishable by checksum alone; the adjacency + dual-copy packing argument is what makes 0x3FF6 the reported figure. Confidence stays CONFIRMED_VERIFIED because both stored checksums sit exactly where this length predicts and both verify.

4.3 Python verification against the real .sav files (executed in this workspace)

Verification script (run verbatim; also re-run at delivery time):

import struct
for fn in ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]:
    d = bytearray(open(fn, "rb").read())
    sentinel = d[0]; magic = bytes(d[1:16])
    A = bytes(d[0x10:0x4006]); B = bytes(d[0x4008:0x7FFE])
    sA = struct.unpack_from("<H", d, 0x4006)[0]
    sB = struct.unpack_from("<H", d, 0x7FFE)[0]
    cA = (0xFFFF - sum(A)) & 0xFFFF; cB = (0xFFFF - sum(B)) & 0xFFFF
    print(fn)
    print(f" sentinel=0x{sentinel:02x} magic={magic!r} match={magic == b'YDBTE_0000_KCEJ'}")
    print(f" copyA stored=0x{sA:04x} computed=0x{cA:04x} match={sA == cA} "
          f"copyB stored=0x{sB:04x} computed=0x{cB:04x} match={sB == cB} A==B:{A == B}")
    sent_code = {0xEE: 0, 2: 0x10, 1: 0x20}.get(sentinel, 0x40)
    status = sent_code | (0 if magic == b"YDBTE_0000_KCEJ" else 4) \
             | (0 if cA == sA else 2) | (0 if cB == sB else 1)
    print(f" simulated FUN_08019c10 status=0x{status:02x} (0=fully valid)")

Negative controls executed in the same session (all correctly rejected, proving the formula is not a tautology):

  • SEED = 0 ((−Σ) & 0xFFFF): gives 0xFD5A / 0xFDF9 — off by one on every copy. Rejected.
  • Checksum over sentinel+magic+data, over magic alone, over the 4-byte leading field alone, and over payload-without-leading-field: none reproduces the stored values on both files. Only "leading field + full payload to the adjacency boundary, seed 0xFFFF" matches all four (file × copy) combinations.
  • Between-file differential: the byte-sum of the 4-byte leading field changes by −159 between the two captures and the stored checksum changes by exactly +159 (mod 65,536) while the remaining payload sum is unchanged (11 in both files) — an independent confirmation that the leading field is inside the covered range and that the formula's sign is as stated.

The corpus probe result is consistent with this: a mutation at 0x10 (first covered byte of copy A) was confirmed by the game as an integrity failure, and the response was a rewrite of the save (FUN_08019504 on a later save trigger), not a revert to blank.

Notes on the table's limits (read before citing any payload row):

  1. No RAM mirror address is asserted for any field. Every RAM pointer on the save path sits behind an unresolved _DAT_080xxxxx literal in this corpus. The only RAM addresses that are certain are the SRAM window itself (0x0E000000 + offset) and the functional roles of the buffer symbols (_DAT_08019548 write buffer, _DAT_08019d34 / _DAT_08019d8c read buffers).
  2. No payload sub-field boundary is code-derived. The 0x01-byte groupings above come from byte enumeration of two near-blank saves, not from writer code. The gather table in FUN_080358dc is the authoritative field definition and it was not recovered; a progressed save (or the ROM literal pool) is required to promote any HYPOTHESIS row.
  3. The pre-save refresh in Chain W1 (12-byte copy by FUN_0801aed8, 12+10-byte copies by FUN_08032e4c, flag bytes 1/2 via FUN_080320a0/FUN_080320ac) and the confirm-time choice store in Chain W2 (FUN_080320a0) provably mutate RAM bytes that the gather then serialises, but their destination save offsets are exactly what the missing table would provide. They are therefore recorded as writer-side facts in Section 3.5, not as field rows.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test: work on a copy of a known-good .sav (cap-00-future-0.sav); keep the other copy byte-identical unless the test says otherwise; after each mutation, boot/load and record (a) whether the save is accepted, (b) the simulated FUN_08019c10 status, (c) any SRAM rewrite (diff the .sav after one save trigger), and (d) the visible UI/game state. There are no paired .ss save states in this corpus (states/ is empty), so "reload" means a cold boot with the mutated .sav in place — the same protocol as the corpus cold-reload probe.

Checksum repair procedure (needed by every "accepted-mutation" test): for the copy you edited, recompute s = (0xFFFF − Σ covered bytes) & 0xFFFF over 0x10–0x4005 (copy A) and/or 0x4008–0x7FFD (copy B) and store s little-endian at 0x4006 and/or 0x7FFE. Reference implementation verified against both corpus files:

import struct
d = bytearray(open("mutated.sav", "rb").read())
for start, end, store in [(0x10, 0x4006, 0x4006), (0x4008, 0x7FFE, 0x7FFE)]:
    struct.pack_into("<H", d, store, (0xFFFF - sum(d[start:end])) & 0xFFFF)
open("mutated.sav", "wb").write(d)
