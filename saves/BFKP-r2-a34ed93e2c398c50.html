1. Executive Summary & Overall Confidence

Overall confidence: LOW (driver layer: CONFIRMED_STATIC/CONFIRMED_VERIFIED; game-field layer: HYPOTHESIS/UNKNOWN).

Proven (code + bytes):

  • The save medium is EEPROM, 512 bytes total (eeprom512, PACKET "EEPROM 4K" = 4 Kbit). Access is serial via DMA3 to 0x0D000000, exactly as implemented by FUN_08036800/FUN_08036880/FUN_08036944 in save_related_functions.c.
  • The EEPROM transfer unit is 8 bytes (4× u16): the read routine unpacks 64 data bits, the write routine packs 64 data bits. There are thus 64 addressable blocks (addr 0..63) if the full 512 B is used.
  • cap-00-future-0.sav is a fully erased image (512× 0xFF, SHA-256 9f56cda75fefeab90f6fa5d5ddc9601544b121732c5ecccab32e631060453a5d); cap-01-future-1.sav is an initialized, almost-empty image (507× 0x00, only 5 nonzero bytes, SHA-256 7eb73968d59482c2d0b240db8163d8e676fb57a1ba0208cfed727be28e93130e). Both were verified byte-by-byte in Python (Section 4).
  • No magic signature and no checksum/integrity routine exists in the traced code set, and no candidate checksum explains the .sav bytes consistently (Section 4). PACKET metadata agrees: ascii_magic_strings: [], candidate_checksum_or_counter_spans_hex: [], sdk_tags: none.

Open / not proven:

  • The ultimate callers of the EEPROM read/write routines are absent: ghidra/callgraph.json lists callers: [] for both 0x08036880 and 0x08036944, and both exit through an UNRECOVERED_JUMPTABLE. Therefore the in-RAM save struct address (0x02xxxxxx/0x03xxxxxx), serialization order, slot-selection rule, and every game-semantic field updater are unknown. The remaining 32 decompiled functions (heap allocator FUN_0803a5c0/FUN_0803ea0c family, audio/graphics helpers FUN_0802e*, memset/memcpy-like FUN_0800014e/FUN_08000160/FUN_08041f04) contain no EEPROM/0x0D000000 references and are not save code.
  • Only one progressed sample exists and it is 99% zeros, so the field map (Section 5) is necessarily sparse: 5 nonzero bytes are mapped as hypotheses, everything else is UNKNOWN payload/padding.
  • states/ is empty, so no RAM-vs-EEPROM correlation was possible.

This LOW rating is the honest consequence of a truncated caller chain plus a near-blank progressed save; upgrading it requires a progressed .sav with substantial nonzero content and/or decompilation of the indirect-jump callers.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level DMA3 driver — FUN_08036800 (0x08036800)

Generic DMA3 engine used for EEPROM transfers, in save_related_functions.c / ghidra/decompiled.c:809:

void FUN_08036800(undefined4 param_1, undefined4 param_2, uint param_3) {
  uVar1 = *_DAT_08036860; *_DAT_08036860 = 0;                       // save & mask interrupts
  *_DAT_08036864 = *_DAT_08036864 & mask | *(ushort *)(*_DAT_0803686c + 6);
  *_DAT_08036870 = param_1;                                          // DMA3 SAD  (0x040000D4)
  *_DAT_08036874 = param_2;                                          // DMA3 DAD  (0x040000D8)
  *_DAT_08036878 = param_3 & 0xffff | 0x80000000;                    // DMA3 CNT: count + enable (0x040000DC)
  while ((CNT >> 16 & 0x8000) != 0) { /* poll busy */ }
  *_DAT_08036860 = uVar1;                                            // restore interrupts
}

The exact DAT_ target addresses are not resolved in the decompilation, but the register pattern (source, dest, count | 0x80000000 enable, busy-poll on the high halfword) is uniquely DMA3 per the GBA spec addresses in PACKET.md (0x040000D4 block). Both EEPROM routines call it with one endpoint literally 0xd000000 (EEPROM window 0x0D000000).

3.2 EEPROM reader — FUN_08036880 (0x08036880)

Signature: FUN_08036880(uint addr, int destRAM). Behavior (decompiled.c:840–891):

  1. Bounds-check: if (addr < *(ushort *)(desc + 4)) — descriptor +4 is the device block count; out-of-range reads silently return an error value (uRam0803689c) via the unrecovered jumptable tail.
  2. Builds the address bitstream MSB-first on the stack: for desc[+8] (address-bit count) iterations it stores addr and shifts right, walking the buffer downward; then writes two 1 halfwords — the EEPROM read opcode header 11 (plus start bit semantics).
  3. FUN_08036800(stackBuf, 0x0D000000, addrBits + 3) — clocks out header+address.
  4. FUN_08036800(0x0D000000, stackBuf, 0x44) — clocks in 68 halfwords = 64 data bits + 4 dummy bits, per the standard EEPROM read frame.
  5. Unpacks 64 bits MSB-first (uVar4 = uVar4 << 1 | *p & 1) into 4× u16, stored downward from destRAM + 6 — i.e. 8 bytes at destRAM+0..7 in little-endian word order.

Each call therefore reads exactly one 8-byte EEPROM block into RAM. There is no looping over blocks, no checksum verification, and no magic comparison in this routine.

3.3 EEPROM writer — FUN_08036944 (0x08036944)

Signature: FUN_08036944(uint addr, ushort *srcRAM, char waitFlag). Behavior (decompiled.c:898–981):

  1. Same bounds-check against descriptor +4.
  2. Packs 4× u16 from srcRAM (8 bytes) bit-by-bit MSB-first (16 iterations per word), then the address bits, into a stack bitstream; prepends 0 then 1 — the EEPROM write opcode header 10.
  3. FUN_08036800(stackBuf, 0x0D000000, addrBits + 0x43) — clocks out 2 opcode + address + 64 data (+ stop) bits.
  4. Busy-wait: polls uRam0d000000 & 1 (EEPROM ready bit read back through the data line) using a timer register (*_DAT_08036a30, wrap 0xe4) with timeout 0x88 ticks; the waitFlag (param_3) controls whether it loops until ready.

Each call writes exactly one 8-byte EEPROM block from RAM. No erase routine is needed (EEPROM is byte/block writable, unlike Flash); no 0x5555/0x2AAA Flash command sequence or SRAM 0x0E000000 access exists anywhere in the decompiled set — confirming EEPROM-only storage.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic signatures: none. No ASCII string, constant byte sequence, or header comparison appears in any save-related function, and both .sav images contain no ASCII (PACKET: ascii_magic_strings: []). magic_signatures in save-format.json is therefore empty — verified in code (verified_in_code: n/a) and in bytes.

Checksum: none identified — and that is a positive finding about this corpus, not an omission. Specifically:

  • No function in the 35-function decompilation computes a sum/XOR/CRC over a buffer and stores or compares it; the only loops over save data are the bit pack/unpack loops in the two EEPROM routines.
  • The EEPROM routines transfer caller buffers verbatim (bit-packed) with no integrity field added, stripped, or checked, and no failure path other than the address bounds-check.

Python verification against the real .sav files (executed in this workspace):

Candidate-checksum tests, all rejected as unproven:

  • Stored byte = sum8 of the rest of its region: region 0 gives 0x08, which matches byte +14 only if byte +7 is excluded and byte +14 is the stored value — but regions 1–3 then require stored 0x00 at +14 with byte +7 = 0x01 unexplained by any sum (their payload sum is 0x00, so +7 cannot simultaneously be a sum and 0x01). A single coincidental match on a near-zero buffer (where almost any additive checksum is 0 or the payload's lone byte) is not verification.
  • Whole-image sum16/xor/crc stored somewhere: no nonzero byte in cap-01 equals 0xff08, 0xf5, or 0xbe9dd84f in any obvious encoding (the image's only values are 0xfc, 0x08, 0x01).
  • Complement/check-digit at +7: 0xFC is the two's-complement negation of 0x04 (region 0's sum8), which is suggestive, but regions 1–3 would then store -0x01 = 0xFF, not 0x01. Inconsistent — rejected.

Conclusion: formula, covered range, and stored offset are all UNKNOWN; confidence UNKNOWN in save-format.json. Either the game genuinely has no integrity check (plausible for a children's title with flag-byte saves, and consistent with PACKET's probe accepting the sparse image on cold reload), or the checker lives in the untraced caller. Section 6 gives the mutations that decide between these.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save-states exist in this workspace (states/ is empty), so each test is: patch a copy of cap-01-future-1.sav, boot the ROM with it, and observe (a) whether the image is accepted, rewritten, or reverts to blank/default boot (compare against PACKET's baseline: cap-01 is save_preserved_on_load: true), (b) title/load-screen UI, (c) any EEPROM write-back — re-dump the .sav after boot and diff; a write-back reveals exactly which blocks the loader touches via FUN_08036944. Checksum repair: none is currently known — every target below is run without repair first, precisely because rejection-vs-acceptance is the experiment that proves or kills the checksum hypothesis. If a mutation is rejected, repeat it while also adjusting the Section 4 candidate bytes (+7, +14) and note which combination is accepted.

RAM-side predictions (for when save-states are available): because FUN_08036880 deposits each block at a caller-chosen RAM pointer with no transformation beyond bit-unpacking, the RAM mirror of file offset X should be byte-identical to the .sav at X once the base is found.
