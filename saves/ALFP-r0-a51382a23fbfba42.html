1. Executive Summary & Overall Confidence

Overall Confidence: LOW–MEDIUM.

What is proven (code + .sav bytes agree):

  • The title uses a 64Kbit (8192-byte) EEPROM, accessed as 1024 individually-addressed 8-byte ("double-word") blocks over the serial EEPROM bus at 0x0D000000, driven via DMA3 register programming at 0x040000D4/0x040000D8/0x040000DC. This is confirmed both by the decompiled driver code (loop bound 0x2000 bytes in 8-byte steps = 1024 × 8B = 8192B) and by the .sav files themselves (exactly 8192 bytes each).
  • A full read ("load") path and a full write ("save") path exist as distinct top-level routines (FUN_08021904 load, FUN_08021974 save), each driving the low-level per-block read/write/verify primitives.
  • Across the two provided .sav snapshots, only the first 8 bytes (block 0) of the 8192-byte EEPROM were ever written; every other byte in both files is the erased/unwritten fill value 0xFF. This is a directly observed, verified fact from saves/hexdump_and_diffs.txt and raw hex inspection.

What remains open / unverified:

  • The exact field layout and semantics of the 8 written bytes (offsets 0x0–0x7) could not be confirmed. A candidate Adler-32-style checksum routine (FUN_080219ee) exists in the decompiled code, but it has no traced caller in ghidra/callgraph.json, and no byte-order/offset/window combination of it over the observed data reproduces the stored first 4 bytes (12 62 56 87). The checksum hypothesis is therefore not verified and is reported as such below.
  • Only 2 samples, differing in only 8 bytes, are available. This is far too little data to determine slot count, redundancy/mirroring, or the meaning of fields beyond block 0 with any confidence. No second save slot or backup copy was observed, but absence of evidence is not evidence of absence here — later blocks may simply be unused at this early point in the playthrough that produced these captures.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM, 64Kbit = 8192 bytes total (saves/*.sav are both exactly 8192 bytes). No SDK save-type ASCII tag (EEPROM_V###, SRAM_V###, FLASH_V###) was detected anywhere in the traced code or workspace ROM metadata (SDK Save Tags in ROM: none detected per PACKET.md).
  • Addressing granularity: The EEPROM driver addresses the chip in 8-byte ("double-word") blocks. FUN_08021904 (load) iterates block indices 0..1023 (iVar4 stepping by 8 up to 0x2000), confirming 1024 total addressable blocks × 8 bytes = 8192 bytes, matching the 64Kbit EEPROM geometry exactly.
  • Active data span observed: Only block 0 (file offset 0x0000–0x0007) has ever been written in either sample. All of 0x0008–0x1FFF reads back as 0xFF (erased NAND/EEPROM state) in both captures.
  • Slots / copies: No second written region was observed in either .sav, so no redundant/backup copy or mirrored slot could be confirmed. Given only block 0 is populated, it is not possible to distinguish "this game has exactly one save slot and we're seeing it partially filled early on" from "this game has multiple slots elsewhere in the EEPROM that are simply still blank in these two captures." Status: UNKNOWN, not ruled out.
  • Generation / sequence counters, selection rule: Not observed. No second generation of block 0 was captured (only 1 write event is visible across the 2 samples), so a generation-counter or ping-pong selection scheme cannot be confirmed or refuted.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses below are thumb-mode functions in the main ROM (0x08xxxxxx), taken from ghidra/decompiled.c and ghidra/save_related_functions.c, cross-checked against ghidra/callgraph.json.

3.1 Low-level hardware I/O driver (EEPROM serial bus via DMA3)

AddrRoleHow identified
0x08021efcDMA3 register programmer + busy-wait. Takes (src, dst, control), writes them to three adjacent 32-bit MMIO-shaped globals (_DAT_08021f6c/_DAT_08021f70/_DAT_08021f74, consistent with DMA3SAD/DMA3DAD/DMA3CNT at 0x040000D4/D8/DC), sets the DMA "start" bit (\| 0x80000000) in the control write, then spins on bit 15 of the control-register mirror (uVar2 & 0x8000) until DMA3 clears its busy flag. This is the textbook GBA EEPROM bit-serial DMA pattern. Disables/restores IE briefly around the transfer (see 3.2).Address-window correlation (this is the only function in the seed set that programs 3 sequential 32-bit "registers" and busy-waits a hardware-shaped flag bit) plus standard DMA3 register layout knowledge.
0x08021f7c [seed]EEPROM single-block READ. Builds a serial bit-stream in auStack_96 encoding a 2-bit READ opcode + the block address (bit-width taken from a global byte at *_DAT_08022028+8, consistent with the SDK's 6-bit vs 14-bit address-width selector for 4Kbit vs 64Kbit EEPROM) + a stop bit, DMAs it out via FUN_08021efc(..., 0xd000000, ...) (writing to the EEPROM bus address 0x0D000000), then issues a second DMA3 (FUN_08021efc(0xd000000, auStack_98, 0x44)) to read back 64 serial bits (0x44 = 0x40 data bits + 0x4 dummy bits — the GBA EEPROM read protocol), and finally de-serializes those 64 bits into the 4×16-bit (8-byte) output block pointed to by param_2.Bit-packing/unpacking pattern matches the documented GBA EEPROM read sequence (address-out, 4-bit dummy, 64-bit data-in) 1:1; confirmed by direct inspection of ghidra/save_related_functions.c lines 98–154.
0x0802202c [seed]EEPROM single-block WRITE. Symmetric to the read path: packs a WRITE opcode + block address + the 64 data bits of param_2 (the 8-byte caller buffer) + a stop bit into auStack_2e, DMAs the combined bitstream out to 0x0D000000 via FUN_08021efc, then calls FUN_08021e30 (disable interrupts / arm busy-poll, see 3.2) and busy-waits the EEPROM "ready" bit (uRam0d000000 & 1) before calling FUN_08021eb8 (re-enable).Same reasoning: opcode+address+64-bit-payload packing, followed by the EEPROM write-busy poll loop, is the standard GBA EEPROM write sequence.
0x08021e30Helper invoked only by 0x0802202c, immediately before the write-busy poll. Clears/arms IRQ-related globals and chains into a jump table (BIOS Intr-style wait primitive). Classified as an interrupt-state guard around the EEPROM write-busy wait, not a save-data mutator.Call-site only inside 0x0802202c; callgraph confirms single caller.
0x08021eb8Helper invoked only by 0x0802202c, immediately after the busy-wait resolves. Restores the IRQ-related state saved/cleared by 0x08021e30.Same as above (paired disable/enable).

3.2 Mid-level block write-with-verify

AddrRole
0x08022108Read-back verify. Reads one block via FUN_08021f7c into a local 8-byte stack buffer, then compares it word-by-word against the caller's param_2 buffer; returns 0x8000 (fail) on first mismatch, 0 on full match.
0x08022160Write-with-retry wrapper (no traced caller in ghidra/callgraph.json — this appears to be an exported save-system entry point called from game code not present in the decompiled set). Loop up to 3 times: call FUN_0802202c (write block), and if the implicit post-write status is non-zero, call FUN_08022108 (verify); stop retrying once a write+verify succeeds (param_3 == 0). This is the block-level "write, verify, retry up to 3×" primitive that the high-level save routine (3.3) calls once per 8-byte block.

3.3 High-level save/load entry points and caller chains

AddrRoleCaller-chain mapping
0x08021904Load-all / deserialize. Selects EEPROM backup type via func_0x08021d90(0x40) (the 0x40 branch of that dispatcher is the only one that sets up the EEPROM-specific function-pointer pair, matching the EEPROM 64K media tag in PACKET.md). Allocates an 8192-byte (0x2000) RAM buffer via the heap allocator FUN_0801f53c, stores its pointer in *_DAT_08021a48, then loops iVar4 from 0 to 0x2000 in steps of 8, calling func_0x08021f7c(iVar4>>3, buf+iVar4) for each of the 1024 blocks — i.e. reads the entire 8192-byte EEPROM into a single contiguous RAM mirror buffer, byte-for-byte, block by block. No per-field parsing happens inside this function; it is a raw bulk copy.No caller found in the traced decompilation set (ghidra/callgraph.json lists 0x08021904 with "callers": []). This function must be invoked from game-logic code outside the 74-function trace window (e.g. a title-screen/continue-menu load routine not captured by the seed expansion). This is the single confirmed deserialization entry point for the whole save file.
0x08021974Save-all / serialize (partial-range capable). Takes a RAM source pointer region (param_2 offset + param_3 address + param_4 byte count), sets up a DMA/transfer descriptor (*_DAT_08021a50, etc.), then loops iVar3 from 0 to param_4 in steps of 8, calling func_0x08022160(blockIndex, srcPtr+iVar3) — i.e. writes an arbitrary caller-specified byte range of the RAM mirror out to EEPROM, 8 bytes (one block) at a time, using the write-verify-retry primitive. Because param_4 (byte count) is caller-supplied, this same function can be used both for "flush the whole 8KB" and for "flush just a small changed region" (e.g. just block 0), which is consistent with the observed .sav evidence: only block 0 (8 bytes) was ever actually written in the two captured snapshots, implying the caller invoked this routine with a small param_4 (≈8) rather than the full 8192.No caller found in the traced set ("callers": [] in ghidra/callgraph.json). Must be invoked from an un-traced game-logic save routine (e.g. an autosave-on-event hook). This is the confirmed serialization entry point; the specific game-event caller(s) are UNKNOWN from this evidence.
0x080219d6Sets up the same transfer-descriptor fields as the tail of 0x08021974 but contains no write loop of its own — it only programs *_DAT_08021a50, piVar1[1], the 16-bit length, and the 0x8400 control word, then returns. Read as a "prepare descriptor, defer the actual DMA to a caller-driven pump" variant, i.e. likely used when the write is driven incrementally from a VBlank/async pump elsewhere, rather than inline like 0x08021974. Role: HYPOTHESIS — static-only, unverified against any .sav delta (no byte evidence distinguishes it from 0x08021974's inline path).No caller or callee edges recorded in ghidra/callgraph.json.

3.4 In-RAM save mirror

The in-RAM copy of the save data is not a fixed static address — it is a heap-allocated buffer (FUN_0801f53c(0x2000), an EWRAM-backed linked-list allocator rooted near 0x02000000, confirmed by the allocator's own pointer arithmetic using the 0x2000000-based free-list walk at ghidra/decompiled.c:400-455). Its address is stored in the global *_DAT_08021a48 and is only resolved at runtime, so no fixed EWRAM/IWRAM address can be given for "the save struct in RAM" from static analysis alone. This is the field each writer mutates before 0x08021974 flushes the relevant byte range to EEPROM. No code path mutating specific byte offsets within that 8192-byte RAM buffer was captured in this trace window (the game logic that sets individual save fields lies outside the 74-function seed set), so field-level writers inside the RAM buffer are UNKNOWN; only the bulk flush call (0x08021974) and bulk load call (0x08021904) are confirmed.

3.5 Functions in the seed set that are not part of the save path (ruled out)

For completeness/honesty: the seed expansion (2-hop callers / 1-hop callees from the two MMIO seeds) pulled in several functions that, on inspection, are unrelated utility code sharing nearby ROM addresses, not save-system logic:

  • 0x0801f53c family (0x0801f3ac, 0x0801f406, 0x0801f454, 0x0801f5c0, 0x0801f6f8, 0x0801f744, 0x0801f7a4, …): a generic EWRAM heap allocator/deallocator (malloc/free-style linked free list), used by many systems including the save loader, but not save-specific itself.
  • 0x08020c70–0x08021088, 0x080211d6–0x080211f0, 0x0802106a, 0x08021080: DMA-driven tile/background buffer streaming code (copies between 0x02000000-region buffers using func_0x08023ba0/func_0x08023b7c), i.e. graphics streaming, not save I/O. (FUN_0802106a/FUN_08021080 are reused as generic "program DMA control word" / "disable DMA" helpers that also happen to be called from the save path — see 3.3 — but their own definitions are graphics-DMA-shaped, not save-shaped.)
  • 0x0802130c, 0x0802135a, 0x080217f4: sprite/image buffer allocation using the same generic heap allocator; width×height math, not save fields.
  • 0x080218ac: a self-referential xorshift-style PRNG/state-mixer (uVar3-uVar2 return), unrelated to save I/O.

4. Magic Signatures & Checksum / Integrity Algorithm

No magic signature bytes or ASCII tags were found. PACKET.md's pre-computed ascii_magic_strings is empty, and direct hex inspection of both .sav files confirms no fixed/recognizable magic byte pattern — the only non-fill bytes in either file are the 8 bytes at offset 0x0000–0x0007 in cap-01-future-1.sav.

4.1 Candidate checksum routine: FUN_080219ee (static-only, unverified)

uint FUN_080219ee(byte *param_1,int param_2)
{
  ...
  uVar4 = 1;                 // A = 1          (Adler-32 "sum1" init)
  iVar5 = 0;                 // B = 0          (Adler-32 "sum2" init)
  while (0 < param_2) {
    ... for each byte in current chunk:
      uVar4 = bVar1 + uVar4;   // A = A + byte
      iVar5 = iVar5 + uVar4;   // B = B + A
    uVar4 = func_0x080283a0(uVar4);  // periodic mod reduction (compiler reciprocal-multiply mod)
    iVar5 = func_0x080283a0(iVar5);
  }
  return iVar5 << 0x10 | uVar4;     // (B << 16) | A
}

This is structurally identical to the Adler-32 algorithm (A initialized to 1, B initialized to 0, B += A each byte, periodic modulo reduction via FUN_080283a0, final packing (B<<16)|A). FUN_080283a0 itself (ghidra/decompiled.c:2872-2879) is a classic compiler-generated "multiply-by-reciprocal" modulo-constant implementation — the actual modulus constant lives in ROM data (uRam080283bc/iRam080283c0) that is not resolvable from the decompiled C alone, so the modulus (standard Adler-32 uses 65521) is assumed, not proven.

Verification performed (Python, against saves/cap-01-future-1.sav):

stored bytes[0:4]            = 12 62 56 87   (LE u32 = 0x87566212, BE u32 = 0x12625687)
Adler-32(bytes[4:8]=00 04 06 04)   = 0x0020000f
Adler-32(bytes[4:0x10])            = 0x24740807
Adler-32(bytes[4:0x200])           = 0x658df626
Adler-32(bytes[4:0x2000])          = 0x8a53f626
Adler-32(bytes[0:0x200], w/ bytes[0:4] zeroed) = 0x6591f626
CRC-32(bytes[4:8])                 = 0x777a145f
sum8/sum16/sum32(bytes[4:8])       = 0x04 / 0x000e / 0x0000000e

None of these candidate windows/algorithms reproduce the stored value 0x87566212 / 0x12625687. Additionally, FUN_080219ee has no traced caller or callee edge in ghidra/callgraph.json — it is not demonstrably wired into the load/save path captured in this trace at all.

Conclusion: the checksum/integrity-algorithm hypothesis is UNVERIFIED. We cannot confirm that offset 0x0–0x3 is a checksum, nor (if it is) what it covers or what algorithm computes it. It is reported in §5 as HYPOTHESIS only, on the strength of its high apparent entropy relative to the plausible small-integer values at offset 0x4–0x7, not on any matching computation.

6. Save Fuzzing & Counterfactual Verification Plan

Because only block 0 (8 bytes) has ever been observed written, all fuzzing should start there. No paired .ss save states were provided in states/ for this release (states/ is empty per PACKET.md §2 — "0 states"), so none of the following can currently be executed as "mutate .sav → reload emulator state → observe" without first capturing fresh gameplay.ss/pre/post .ss pairs for this title; the plan below documents what to run once such states exist.

  1. Checksum-field falsification test. Flip a single bit in 0x0000 (e.g. 0x12 → 0x13) while leaving 0x0004–0x0007 untouched, reload from a paired pre-load .ss, and observe whether the game (a) silently accepts the save, (b) resets the 8-byte block to a default, or (c) throws a corrupt-save warning. A reaction in (b)/(c) would be the first real evidence that 0x0000–0x0003 is validated (checksum or otherwise); no reaction supports it being ordinary data, falsifying the checksum hypothesis in §4.
  2. Payload-field isolation test. Independently mutate each of 0x0004, 0x0005, 0x0006, 0x0007 by ±1 and reload, logging any observable change in HUD/menu state, to begin assigning semantics to these 4 bytes without assuming them in advance.
  3. Checksum-recompute test. If test 1 shows the game does re-derive and overwrite 0x0000–0x0003 after being given corrupted bytes plus unmodified 0x0004–0x0007, capture the game-written replacement value and re-attempt the Adler-32 (and other) formula matches from §4 against that freshly observed pair — this is the strongest way to pin the algorithm once more write events are captured.
  4. Unused-region write test. Mutate a currently-0xFF byte at 0x0008 to a non-0xFF value, reload, save again, and check whether the game's next write to the EEPROM touches/overwrites that byte (via a fresh hexdump diff) — this tests whether block 1+ is simply unused at this point in the game or structurally dead space.
  5. Full-buffer flush trigger. Play further into the game (past whatever event triggers additional EEPROM writes) and recapture .sav snapshots to determine whether later gameplay eventually populates 0x0008 onward, which would validate or refute the "only block 0 used so far" reading of the current 2 samples.

All mutation tests must preserve the original unmodified .sav/.ss files (do not overwrite originals) and record both the before/after hexdumps per the workspace's existing hexdump_and_diffs.txt convention.

7. Known Unknowns / Open Questions

  • Is offset 0x0–0x3 actually a checksum? If so, over what byte range, with what algorithm/modulus, and in what endianness is it stored? (FUN_080219ee is a structural Adler-32 candidate but is unverified and has no traced caller.)
  • What do the 4 bytes at offset 0x4–0x7 represent semantically?
  • Does this title use more than one save slot / a backup copy elsewhere in the 8192-byte EEPROM? Not observed in either sample; cannot be ruled out.
  • Is there a sequence/generation counter governing slot selection? Not observed (only a single write event visible).
  • Which specific game-logic call sites invoke the confirmed entry points 0x08021904 (load) and 0x08021974 (save)? Both have zero traced callers in ghidra/callgraph.json, meaning the relevant game-event hooks lie outside this 74-function trace window.
  • What is the role of 0x080219d6 (descriptor-setup-only variant) relative to 0x08021974 — a deferred/async write path, or dead/unused code?
