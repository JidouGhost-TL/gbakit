  • Methodology: All findings below were derived strictly from saves/cap-00-future-0.sav, saves/cap-01-future-1.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (129 functions), ghidra/save_related_functions.c (7 pre-extracted MMIO-adjacent functions), ghidra/callgraph.json, and standard documented GBA hardware behavior (SRAM/Flash bus at 0x0E000000, Flash command protocol, EWRAM/IWRAM address ranges). 1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven (code + .sav bytes together, or .sav bytes alone with no code claim attached):

  • The save media is GBA Flash 512K (64 KiB), addressed through the 0x0E000000 flash bus window, with a 16×4096-byte sector layout. This is proven both by the hardware FUN_080605b0 sector-erase routine (which only accepts sector indices 0..15, i.e. 0x1000-byte sectors across a 64 KiB device) and by the .sav files themselves, which are exactly 65536 bytes and whose only non-blank (0xFF-fill) data sits exactly on 0x1000-aligned sector boundaries.
  • The save uses a two-sector, sequence-counted, ping-pong ("A/B") redundancy scheme: sector 0 (0x0000-0x0FFF) and sector 1 (0x1000-0x1FFF) each hold an independent, byte-identical copy of the save record except for one 4-byte field at record offset 0x08, which is a monotonically-incrementing generation/sequence counter (1 in the sector-0 copy, 2 in the sector-1 copy in the two-snapshot sample we have). This is proven directly by diffing cap-00 against cap-01: cap-01's sector-1 body is byte-for-byte identical to its sector-0 body except for that single counter byte.
  • The record begins with an 8-byte ASCII magic signature "SONIC_PB", confirmed identically in both sectors of both capture files.
  • A 20-entry × 16-byte default high-score table (named entries, descending scores) is present and repeats 3-4 times within the record, almost certainly once per pinball table/board. This is a structural, byte-level finding; the semantic claim ("one table per pinball board") is a hypothesis, not proven.

What remains open / unresolved:

  • No caller of the flash write/erase driver was found anywhere in the 129-function decompiled corpus. ghidra/callgraph.json shows FUN_08060420 (driver init) and FUN_080605b0 (sector erase+program) have zero recorded callers. This means the actual game-logic function that assembles the in-RAM save struct, decides which sector to write, bumps the sequence counter, and invokes the flash driver is not present in this workspace and cannot be clean-room traced beyond what the raw .sav bytes themselves reveal.
  • No checksum or CRC was found. Every standard algorithm tried (sum8, sum16-LE, XOR8, XOR16, CRC32, two's-complement) was checked against the only candidate trailer bytes (the final 2 bytes of each 4096-byte sector, offset 0x0FFE-0x0FFF) and none matched; moreover those trailer bytes are identical in the gen-1 and gen-2 copies even though the body changed, which actively disproves the hypothesis that they are a checksum over the sector body. The save format appears to rely on the two-sector redundancy scheme alone (always keep one older, previously-committed-good copy) rather than on payload integrity verification.
  • The precise meaning of most header fields (bytes 0x0C-0x23) and of the score-table "slot 4" anomaly (see §5) are unmapped and marked HYPOTHESIS/UNKNOWN.

Supporting trampolines referenced by the above but not recovered by Ghidra (register-indirect jump tables that could not be resolved to static targets): 0x0806089c (the actual byte-program-and-verify loop), 0x080608a4 (ID-byte read), 0x08060890, 0x08060894, 0x08060898, 0x080608cc (further polymorphic driver entry points). These are almost certainly per-vendor flash driver implementations selected by 0x08060420's dispatch table, but their bodies are opaque in this corpus. func_0x0805ff20 (bank-select helper invoked by 0x08060198/0x080602fc) is referenced but has no definition anywhere in ghidra/decompiled.c — it is outside the 129-function trace window.

3.2 Serialization / deserialization & checksum routines

None were found. No function in ghidra/decompiled.c or ghidra/save_related_functions.c builds, walks, or validates the "SONIC_PB"-prefixed record structure, and no checksum/CRC computation touching flash-bus addresses was located. See §4 for the negative checksum-verification result.

3.3 Callers — what was actually traceable

Per ghidra/callgraph.json, every one of the 7 flash-driver functions above has either zero recorded callers, or callers that are themselves other flash-driver functions (0x0805ff44 ← 0x08060420; 0x08060134 ← 0x080605b0). 0x08060420, 0x080605b0, 0x08060198, 0x080602fc, and 0x080612a0 all show "callers": [].

How this was mapped: we queried ghidra/callgraph.json for the callers array of each of the 7 seed addresses, then cross-referenced every other function body in ghidra/decompiled.c (all 129) via grep for literal references to these 7 addresses (as FUN_<addr> call sites or func_0x<addr> symbol references) — none were found outside the seed set itself. We also scanned the higher-level game-logic functions reachable from the only two "root-like" functions in the graph with no callers of their own (0x08006ef4, a large boot/init routine, and 0x08029018/0x080298a8, which turned out to be VRAM/BG-tile decompression routines writing to 0x06000000 — graphics, not save-data) and found no path from them to the flash driver.

Conclusion: the complete game-logic caller chain that decides when to save, assembles the in-RAM struct, and invokes 0x08060420/0x080605b0 is not present in the traced 129-function window. This is a genuine, honestly-reported gap — not an oversight in this analysis. Any claim about "how a caller mutates the in-RAM save struct before flushing" (as the packet's §3 requests) is UNKNOWN for this corpus; the only mutation evidence we have is the result visible in the two .sav snapshots (the sequence counter increment at offset 0x08), not the code that produced it.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • Bytes: 53 4F 4E 49 43 5F 50 42 = ASCII "SONIC_PB"
  • Offset: 0x0000 of each sector (absolute 0x0000 and 0x1000)
  • Verified in code: No — no function was found that writes or compares this literal string (it is presumably written by game logic not present in this trace, or burned once at save-file creation).
  • Verified in .sav: Yes — present, identical, at the start of every active sector in both capture files.
  • Confidence: CONFIRMED_VERIFIED (bytes only; writer function UNKNOWN)

4.2 Checksum/integrity algorithm — NEGATIVE RESULT (no algorithm identified)

The only candidate integrity-looking field is the final 2 bytes of each 4096-byte sector (0x0FFE-0x0FFF / 0x1FFE-0x1FFF), which are non-zero (0x01, 0x39) in an otherwise all-zero tail region. Python verification against the actual .sav bytes:

$ python3 - <<'EOF'
import struct, zlib
data0 = open("saves/cap-00-future-0.sav","rb").read()
data1 = open("saves/cap-01-future-1.sav","rb").read()
for label, s in [("cap00 sector0 (gen=1)", data0[0:0x1000]),
                 ("cap01 sector0 (gen=1, unchanged)", data1[0:0x1000]),
                 ("cap01 sector1 (gen=2, new)", data1[0x1000:0x2000])]:
    body = s[:0xffe]
    tail = struct.unpack_from('<H', s, 0xffe)[0]
    sum8 = sum(body) & 0xff
    sum16 = sum(struct.unpack_from('<%dH' % (len(body)//2), body)) & 0xffff
    xor8 = 0
    for b in body: xor8 ^= b
    crc32 = zlib.crc32(body) & 0xffffffff
    print(f"{label}: stored_tail16_LE=0x{tail:04x} sum8=0x{sum8:02x} sum16=0x{sum16:04x} xor8=0x{xor8:02x} crc32=0x{crc32:08x}")
EOF

cap00 sector0 (gen=1): stored_tail16_LE=0x3901 sum8=0xc8 sum16=0x69e2 xor8=0x58 crc32=0xe9c164f6
cap01 sector0 (gen=1, unchanged): stored_tail16_LE=0x3901 sum8=0xc8 sum16=0x69e2 xor8=0x58 crc32=0xe9c164f6
cap01 sector1 (gen=2, new): stored_tail16_LE=0x3901 sum8=0xc9 sum16=0x69e3 xor8=0x5b crc32=0xd8c6b887

Finding: none of sum8 (low byte), sum16-LE, XOR8, or CRC32 (full or truncated) of the sector body matches the stored trailer value 0x3901 (LE) / 0x0139 (BE) in either generation. Critically, the trailer bytes are identical across both generations even though the body's only other difference (the sequence counter) did change the body's sum/XOR/CRC — this is direct, reproducible evidence from the actual bytes that the trailer is not a checksum of the sector body under any of the tested formulas. It is most plausibly either (a) a checksum over a narrower, not-yet-identified sub-range that happens to exclude the counter byte, (b) an unrelated small counter/flag field coincidentally sitting at the sector's last 2 bytes, or (c) leftover non-game data. This is reported as UNKNOWN, not asserted as a solved checksum.

Covered byte range: N/A (no algorithm confirmed). Stored offset: 0x0FFE (2 bytes, candidate only). Confidence: UNKNOWN.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss emulator save states were provided in this packet (states/ is empty for this legacy checkpoint cohort), so the following plan is written to be executed once such states exist (per the standing instruction that every .sav capture must have paired pre/post .ss states going forward), and is deliberately scoped to falsifiable, single-variable mutations.

  1. Confirm the sequence-counter semantics (highest confidence target).
  • Mutation: load cap-01-future-1.sav (sector0 counter=1, sector1 counter=2), then set sector0's counter field (0x0008, 4 bytes LE) to 0x00000003.
  • Checksum repair: none required (no checksum identified).
  • Prediction: if our model is correct, the game should treat sector 0 (now counter=3) as the authoritative copy on next boot, since it is the numerically higher sequence value, even though it is physically the "older" sector slot. If the game instead keeps using sector 1, the "highest counter wins" hypothesis is falsified in favor of a simpler "last-written-physical-slot" rule.
  1. Confirm magic-signature gating.
  • Mutation: corrupt the first byte of "SONIC_PB" at offset 0x0000 in both sectors (e.g., change 0x53 → 0x00).
  • Prediction: if the magic is checked on boot, the game should treat the save as absent/corrupt and fall back to a factory-default boot (matching the reverted_to_blank_boot flag semantics referenced in the packet's cold-reload probe). If the game loads anyway, the magic is cosmetic/unused for validation.
  1. Confirm the high-score table boundaries (one table per board vs. shared defaults).
  • Mutation: change a single score value inside the 0x230-0x36F block (e.g., set the "SEG" entry's score from 1,000,000,000 to 1) and leave the 0x370-0x4AF and 0x4B0-0x5EF duplicate blocks untouched.
  • Prediction: if each 320-byte block is an independent per-board table, only one board's leaderboard UI should reflect the change; the other two (and the 4th, divergent block) should remain at 1,000,000,000. If all four boards show the change, the blocks are actually read through a single shared pointer/alias rather than four independent structures.
  1. Probe the "4th table" anomaly.
  • Mutation: toggle the divergent field at 0x0728-0x072B (currently 0x00000001) between 0, 1, and a large value.
  • Prediction: if this is a "games played" or "credits" counter rather than a genuine high-score entry, UI elements showing play-count/credits should change proportionally, while no high-score board changes. If a high-score board does reflect it, our "4 boards" hypothesis for the triple-duplicated block is wrong and this is actually a real 4th leaderboard whose top entry has simply never been beaten.
  1. Probe the 0x0FFE-0x0FFF trailer field.
  • Mutation: flip each bit of the 2-byte trailer independently (16 single-bit-flip variants) on a sector that is otherwise untouched.
  • Prediction: given §4.2's negative checksum result, we predict no observable effect on gameplay/UI in most variants (supporting "unused/leftover data"). Any observed effect (refusal to load, visual glitch, etc.) would be a significant, surprising finding warranting a full re-investigation of this field as a disguised validation value.
  1. Protocol negative — confirm absence of EEPROM/SRAM behavior.
  • Control: attempt to read/write the save region through the EEPROM DMA3 bitstream protocol (0x0D000000 + 0x040000D4) instead of the Flash byte-bus protocol (0x0E000000).
  • Prediction: this should fail/produce no effect, since all seed evidence (FUN_0805ff44, FUN_080605b0, etc.) points exclusively at the Flash command protocol at 0x0E000000. This is a matched-duration negative control validating that media-type identification (Flash 512K) is correct and not a misclassified EEPROM device.

All fuzzing targets above require no checksum repair step, since no checksum/CRC algorithm was confirmed to exist in this save format (§4.2).
