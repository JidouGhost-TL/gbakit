1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What is proven:

  • The title uses the GBA EEPROM 4K serial interface exclusively (DMA3-driven bit-stream protocol at 0x0D000000/0x040000D4); no SRAM/Flash command sequences (0x5555/0x2AAA) appear anywhere in the decompiled corpus.
  • A complete low-level driver chain exists and was traced end-to-end: bit-serializer → DMA3 command issue → busy-poll → write-then-read-back verification → 3-attempt retry wrapper.
  • A fixed, byte-exact record table (51 × 8-byte records = 408 bytes) starting at file offset 0x10 is independently confirmed purely from the raw .sav bytes (identical layout, identical values, in both snapshots) — each record is a 4-byte big-endian numeric field followed by a 4-byte ASCII-ish tag field. This is unrelated to any external research; it falls directly out of inspecting the two provided binaries.
  • The overall active/non-zero region of the file (0x0000–0x01A8, 424 bytes) matches exactly: 16 header bytes + 408 record bytes = 424.

What remains open:

  • The exact algorithm (if any) behind the three single bytes at offsets 0x0B, 0x0D, 0x0F that moved by the same delta (+5) between the two captures. No checksum/sum/xor routine found in the decompiled set reproduces these three bytes from any tested byte range (see §4). They are most likely independent counters (e.g. elapsed-time or play-count fields), not a classical checksum, but this is unresolved.
  • Which specific caller(s) populate the 51-record score table before it is flushed to EEPROM. The caller-chain seed set (ghidra/save_related_functions.c) only covers the hardware I/O driver and the two generic "task" state machines (FUN_0801b518, FUN_0801b684); the game-logic function(s) that write individual record bytes are outside the provided 111-function decompilation window.
  • Whether the generic 12-byte "stamp" builder/verifier pair (FUN_0801b8c0/FUN_0801b914, §3.3) is actually the mechanism guarding this specific 512-byte save, or a generic SDK utility used for an unrelated sub-block. The byte layout at file offset 0 does not cleanly match the stamp's expected magic(6)+version_u16(0x0100)+sum16+xor16 shape (see §4 for the alignment attempts that failed).
  • The entry points into the EEPROM subsystem (FUN_0801b518/FUN_0801b684) have no statically-recorded callers in ghidra/callgraph.json. They are almost certainly invoked indirectly through a function-pointer task-scheduler slot that Ghidra's static analysis could not resolve — this is explicitly called out wherever it matters below rather than papered over.

The packet's own mutation_probe (probe_offset_hex: 0xB, integrity_check_confirmed: false, reverted_to_blank_on_mutation: false) is consistent with everything found here: mutating the single byte at 0x0B did not trigger any visible rejection, and this report independently shows that the only decompiled "integrity" check (FUN_0801b914) validates only a 6-byte magic + 2-byte version field and never re-derives the sum16/xor16 fields on load.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level EEPROM/DMA3 I/O driver (hardware tier)

All addresses below are from ghidra/save_related_functions.c / ghidra/decompiled.c.

  • FUN_08024504 (0x08024504) — generic DMA3 transfer primitive. Loads a global "DMA busy" flag, programs what are structurally the DMA3 source address, destination address, and control-word globals (_DAT_08024574 = src, _DAT_08024578 = dst, _DAT_0802457c = count-with-enable-bit | 0x80000000), then busy-polls a status half-word until the top bit (0x8000, "DMA in progress") clears, restores the busy flag, and tail-calls an unresolved jump table. This is the textbook shape of a GBA DMA3-driven EEPROM bit-stream pump (serial clocking of one bit per DMA unit through 0x0D000000). Confidence: CONFIRMED_STATIC.
  • FUN_08024584 (0x08024584, flagged MMIO-SEED in the seed file) — EEPROM READ command + bit-unpack. Builds a bit-serialized "read" request (a leading 1,1 start-of-command marker followed by the bit-reversed 6-bit (4K EEPROM) record address) into a 67-entry stack bit buffer, sends it via two FUN_08024504 calls — first writing the 3+2-bit command/address prefix, then reading back 0x44 (68) bits from 0x0D000000 — and finally reassembles 4 little-endian-packed 16-bit words from the trailing 64 bits (8 bytes) of the response into param_2. Confidence: CONFIRMED_STATIC (classic 4K-EEPROM read protocol: 2-bit opcode 11, 6-bit address, 64 dummy/data bits).
  • FUN_08024634 (0x08024634, flagged MMIO-SEED) — EEPROM WRITE command + bit-pack. Serializes the 64-bit record payload (param_2, 4×16-bit words) followed by the 6-bit record address into a bit buffer with a 1,0 start-of-command marker, sends the full 0x43(67)-bit command+data stream via FUN_08024504, then calls FUN_08024438 (sets up a second transfer descriptor / re-arms interrupt dispatch) and busy-polls the 0x0D000000 MMIO ready bit before calling the teardown routine FUN_080244c0. Confidence: CONFIRMED_STATIC (classic 4K-EEPROM write protocol: 2-bit opcode 10, 6-bit address, 64 data bits, then EEPROM-busy poll).
  • FUN_08024710 (0x08024710) — write-verify (read-back-compare). Calls FUN_08024584 (read) into a 4-word local buffer, then compares all 4 words against the param_2 buffer the caller expected to have just written; returns 0x8000 on any mismatch, 0 on full match. Confidence: CONFIRMED_STATIC.
  • FUN_08024768 (0x08024768) — write-with-retry orchestrator, the top of the hardware tier. Loops up to 3 times: call FUN_08024634 (write); if the write "failed" (non-zero return) call FUN_08024710 (verify-by-readback); break the loop if the record is confirmed good. Returns the final status to its caller. Confidence: CONFIRMED_STATIC.
  • FUN_08024438 / FUN_080244c0 — small MMIO/interrupt-controller housekeeping pair invoked immediately around the write bit-stream (FUN_08024438 re-arms a second DMA/transfer descriptor and sets an enable flag; FUN_080244c0 tears it down and restores the previous mask). Confidence: CONFIRMED_STATIC, role (arm/disarm) inferred purely from the mirrored field writes.
  • FUN_08024398 / FUN_08024400 — generic interrupt-vector get/set helpers (dispatch on a mode selector 4 / 0x40 / other), used by the task-setup layer below to install a completion callback. Confidence: CONFIRMED_STATIC for mechanism, role as "vector install" is a structural inference from the 3-way if/else dispatch shape, not from any external documentation.

Caller-chain mapping method: ghidra/callgraph.json lists FUN_08024438/FUN_080244c0/FUN_08024504 as called only from FUN_08024634; FUN_08024584 called only from FUN_08024710; FUN_08024634/FUN_08024710 called only from FUN_08024768. This was cross-checked line-by-line against the call sites visible in ghidra/decompiled.c (e.g. FUN_08024634 body literally contains FUN_08024438(_DAT_08024704); and FUN_080244c0();) — the JSON graph and the C source agree exactly for this cluster.

3.2 Task-level state machines (middle tier)

Two sibling cooperative state machines drive the hardware tier one 8-byte record at a time:

  • FUN_0801b518 (0x0801b518) — EEPROM READ task. A switch-like dispatch on a persistent state byte:
  • state 0x65 (101, initial): on the very first tick, calls FUN_0801b914 (the "stamp" verifier, §3.3) against the just-populated header buffer; on failure sets an error code (4), on success proceeds and sets the task's exit state to 900 (done/aborted).
  • state 1: calls FUN_0801b440 (per-transfer setup, below) then advances to state 100.
  • state 100: the main read loop — repeatedly calls func_0x08024584 (the hardware read primitive, §3.1) for each successive record index until the configured record count is reached, then advances to 11.
  • state 11/900: terminal states.

Confidence: CONFIRMED_STATIC for the control flow; the call to FUN_0801b914/func_0x0801b914 at line 2129 of decompiled.c is present in the source but is not reflected as a caller edge in ghidra/callgraph.json (the static graph only lists FUN_0801b440/FUN_0801b4c4 as callees of 0x0801b518). This is flagged explicitly as a tool blind spot rather than silently relied upon.

  • FUN_0801b684 (0x0801b684) — EEPROM WRITE task, structurally the mirror of the read task: state 0x65 initial setup, 1→100 setup via FUN_0801b440, state 100 loops calling func_0x08024768 (the hardware write-with-retry primitive, §3.1) once per record, 0xb(11)→"last record, finalize via FUN_0801b514" (a no-op stub in this binary) then transitions through state 100 again, 900 abort.

Confidence: CONFIRMED_STATIC.

  • FUN_0801b440 (0x0801b440) — per-transfer setup: copies the transfer-descriptor fields (base pointer, record count, byte stride) into the active transfer-state globals, zero-initializes/records swap fields, then installs a completion callback via func_0x08024398(4) and registers record-count metadata via func_0x08024400(2, ...). Confidence: CONFIRMED_STATIC.
  • FUN_0801b4c4 (0x0801b4c4) — inverse of FUN_0801b440: copies the active transfer-state fields back out into the caller's descriptor and clears/reinitializes it, i.e. transfer teardown. Confidence: CONFIRMED_STATIC.

Important caller-chain caveat: per ghidra/callgraph.json, neither FUN_0801b518 nor FUN_0801b684 has any recorded caller anywhere in the 111-function corpus. Given the cooperative state-machine shape (a persistent state byte advanced one tick per invocation, explicit 900 "abort" / terminal states), these two functions are almost certainly entries in a function-pointer task table driven by a generic OS/task scheduler (invoked indirectly, e.g. (*task_table[slot])()), which static Ghidra analysis cannot resolve into a direct-call edge. This workspace does not contain the scheduler or the in-game trigger (menu action, auto-save hook, etc.) that enqueues these tasks — that remains an open question (see §6).

3.3 Generic "stamp" (magic+version+dual-checksum) helper pair

  • FUN_0801b8c0 (0x0801b8c0) — builds a 12-byte header into a caller-supplied buffer: memcpy (via func_0x08024b74, a generic bulk-copy routine) of 6 literal bytes from ROM constant _DAT_0801b90c into offsets [0:6]; writes the 16-bit literal 0x0100 at [6:8] (a version/format number); computes an additive 16-bit signed-word checksum over a 500-byte buffer (FUN_0801b958, sum += *word++, 250 iterations) and stores the result at [8:10]; computes a 16-bit XOR-word checksum over the same 500-byte buffer (FUN_0801b980, x ^= *word++, 250 iterations) and stores the result at [10:12]. Confidence: CONFIRMED_STATIC for the algorithm; UNKNOWN whether/where it is actually invoked to produce bytes inside this specific 512-byte .sav (see §4 — no clean byte-offset alignment was found).
  • FUN_0801b914 (0x0801b914) — the matching verifier: re-derives the same 6 literal bytes from _DAT_0801b948 and compares them against the first 6 bytes of the candidate buffer; if they match, additionally requires the 16-bit field at offset [6:8] to equal 0x0100; returns 1 only if both checks pass. Crucially, it never reads or recomputes the sum16/xor16 fields — those two checksum words, even if present, are write-only from this function's perspective. Confidence: CONFIRMED_STATIC.
  • FUN_0801b958 (additive sum16) and FUN_0801b980 (XOR16) are themselves tiny, generic, and reusable; they are not inherently save-specific, but they are only referenced (per decompiled.c) from inside FUN_0801b8c0.

4.3 Checksum/counter verification attempts against 0x0B/0x0D/0x0F — tested, inconclusive

The packet's own cold-reload probe flags 0x0B as a "candidate checksum or counter" byte and reports integrity_check_confirmed: false. The following Python verification was run against both .sav files to test every checksum routine actually present in the decompiled corpus (FUN_0801b958 additive sum16, FUN_0801b980 XOR16, and generic sum8/XOR8) over every plausible byte window:

def sum16(data):               # mirrors FUN_0801b958 (signed 16-bit accumulate)
    total = 0
    for i in range(0, len(data), 2):
        v = struct.unpack_from('<h', data, i)[0]
        total = (total + v) & 0xFFFF
    return total

def xor16(data):                # mirrors FUN_0801b980
    x = 0
    for i in range(0, len(data), 2):
        x ^= struct.unpack_from('<H', data, i)[0]
    return x

Result: scanning every start offset in [0, 32) and every window length in {496, 500, 508} for sum16/xor16, and every start offset in [0, 16) with multiple end offsets for sum8/xor8, produced only matches that are self-referential (the candidate "stored" byte/word lies inside the summed window, so the match is a tautology of the arithmetic rather than evidence of a real checksum) or trivially explained by the 88-byte all-zero tail. No non-trivial checksum formula was found that reproduces the observed +5/+5/+5 deltas at 0x0B/0x0D/0x0F from the record table or header bytes.

Conclusion: these three bytes are most consistent with three independent counters that happened to advance by the same amount (5) between the two capture points (e.g. three different units/granularities of the same underlying elapsed-time or tick value, since 0x0C and 0x0E — the bytes interleaved between them — stayed constant). This is reported as a HYPOTHESIS; the generic SDK "stamp" checksum pair in §3.3 does not explain these bytes (12-byte stamp model does not align with the observed 16-byte header / 0x10-aligned record table start — see §4.4).

4.4 Why the FUN_0801b8c0/FUN_0801b914 stamp does not cleanly map onto this file

If the 12-byte stamp (magic[6]+version_u16(0x0100)+sum16+xor16) were written starting at file offset 0x00, bytes [6:8] would need to equal 0x0100. The actual bytes at [6:8] are 50 54 ("PT", part of the DTOPT ASCII run) — not 0x0100 under either endianness. Shifting the hypothesized alignment to start at offset 0x03 (where the ASCII clearly begins) likewise fails: bytes [9:11] (00 00) do not encode 0x0100 either. No offset in [0, 16) produces a 6-byte run matching a null/ASCII-terminated magic and a following 0x0100 version word simultaneously. This stamp pair is therefore CONFIRMED_STATIC as code that exists and is called from the read task, but UNKNOWN/not applicable as the mechanism guarding the bytes actually observed in these two .sav files. It may guard a different save region not exercised by this capture, or a build-time-disabled code path.

4.5 Record-table checksum

No record-level (per-8-byte) checksum field was identified; all 51 records in both snapshots are byte-identical, and no decompiled function was found that computes a checksum restricted to an 8-byte stride.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below are concrete, byte-offset-targeted, and designed to be run against the EEPROM-backed .sav and reloaded from a fresh boot (or from the .ss save states once a paired pre/post capture exists for this release — none are present in states/ for this legacy checkpoint cohort yet, per §2 of the packet).

  1. Header counter isolation (0x0B/0x0D/0x0F)
  • Mutation: set only 0x0B to an arbitrary value (e.g. 0xFF), leave 0x0D/0x0F untouched.
  • No checksum repair needed (no verified checksum covers this byte, per §4.3).
  • Prediction: if 0x0B is a free-standing counter unrelated to 0x0D/0x0F, the game should load normally with only whatever UI/behavior is driven by this specific counter changed (if any is visible at all — the packet's own probe found visual_delta_after_mutation: false, so the most likely observable outcome is no visible effect, which would itself be useful confirmation that this byte is inert/cosmetic metadata, not a save-corruption guard).
  • Counterfactual: repeat with 0x0D alone, then 0x0F alone, to determine whether the three bytes are read independently or only as a correlated set.
  1. Magic signature corruption
  • Mutation: flip one byte inside 0x03-0x07 (e.g. 0x03: 0x44→0x45, breaking "DTOPT" to "ETOPT").
  • Prediction based on FUN_0801b914: if this magic check genuinely gates this save region, the read task should detect the mismatch and transition to its error state (4) rather than its normal accept path — this should be observable as a reset-to-default / "corrupted save" state rather than silently loading the mutated bytes. If, instead, the game loads normally with the table intact, that is strong evidence this magic/stamp pair (§4.4) does not actually gate this 512-byte region, resolving the open question in §4.4 definitively either way.
  • No checksum repair applicable (no verified checksum exists for this region).
  1. Record-table score mutation with surrounding-byte stability check
  • Mutation: change the score field of one interior record, e.g. offset 0x60-0x63 (first byte of the DLG-tagged record) from 00 98 96 80 to 00 00 00 01.
  • Prediction: if a high-score/table UI exists, the displayed value for that entry should change to reflect the new 32-bit big-endian value; this both validates the big-endian, 4-byte-score field hypothesis and the field's screen-visible consumer.
  • Counterfactual: also mutate only the tag bytes (0x64-0x67, e.g. "DLG"→"ZZZ") in isolation to confirm the tag field is independently consumed (name display) from the score field.
  1. Terminator-record boundary test
  • Mutation: overwrite the final record's all-zero tag ("DOP"/0x00000000 score at 0x1A0-0x1A7) with a non-zero score and a 3-letter tag.
  • Prediction: if this record is a genuine list terminator (sentinel), the table-reading code (not present in the provided decompilation window) may either (a) ignore it as an 11th entry past whatever count is actually used, or (b) treat it as a valid new high score if the true table length is larger than assumed. Either outcome narrows down the true record count per block, which this report could not determine from static code alone.
  1. Anomalous first-record (0x10-0x17) isolation
  • Mutation: change only the trailing 01 01 01 00 bytes at 0x14-0x17 to 00 00 00 00.
  • Prediction: distinguishes whether this is consumed as a 3-flag options/config record (expected: a settings change visible in-game) versus being dead/unused padding carried over from a shared record-writer routine (expected: no observable change), directly resolving the HYPOTHESIS flag in §5 for this record.

Every mutation above should be paired with: (a) a SHA-256 of the mutated file before reload, (b) a screenshot/visual-delta capture immediately after reload (as the packet's existing cold-reload probe already does), and (c) a second save-and-reload cycle to check whether the game's own write-back silently "repairs" the mutated byte back to an expected value (which would itself prove an active validator exists even though none was conclusively located in the static code for this specific region).
