Yu-Gi-Oh! - Reshef of Destruction (USA) — Clean-Room GBA Save Format Report

Release Key: AY8E-r0-b64014de39862621 · ROM SHA-256: b64014de3986262114d7c6797bf92b97938d8bf2464f2b96071b3b41c25f4b8f

1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

Proven (code + .sav bytes agree): SRAM 256K media (32,768 bytes), the 15-byte magic 021024_DM8_KCEJ at file offset 0x01, a four-way 8 KiB (0x2000) blocked write layout driven by FUN_0800af68, byte-wise verified SRAM writes with three retries (FUN_080588c4 → FUN_080587a0 + memcmp FUN_0805aac4), and a magic-compare reader (FUN_0800b194). The blank snapshot cap-00-future-0.sav is uniformly 0xFF; the initialized snapshot cap-01-future-1.sav is zero-filled except the magic and two 0xFFFF u16 words at 0x401E and 0x7FFE.

Open: no dedicated sum/CRC checksum loop exists anywhere in the 169-function decompiled corpus, so the two 0xFFFF words cannot be proven to be checksums; all Ghidra _DAT_ address constants are unresolved placeholders, so absolute RAM mirror addresses (0x02xxxxxx/0x03xxxxxx) cannot be named; several callees (FUN_0800b088, FUN_0800b0e4, FUN_0800b10c, FUN_0800ace8, FUN_0800adc4, FUN_0803525c) are referenced but absent from ghidra/decompiled.c. Gameplay-field semantics (duelist struct offsets) are static-only inferences from RAM-side code, never observed non-zero in a .sav sample. Only 2 of the 6 corpus .sav files are present in this workspace, and states/ is empty, so no reload behaviour could be observed directly.

2. Physical Media, Slot Geometry & Redundancy

  • Total size: 32,768 bytes (256 Kbit) in both samples; PACKET media SRAM 256K, SDK tag SRAM_F_V102.
  • Erased/blank state: 0xFF fill (cap-00-future-0.sav, SHA-256 2d864c0b…). Initialized state: 0x00 dominant fill (cap-01-future-1.sav, SHA-256 65b153d2…, only 19 non-zero bytes).
  • Blocking: FUN_0800af68 writes one 0x2000-byte RAM image to four SRAM destinations 0x0E000000, 0x0E002000, 0x0E004000, 0x0E006000 via FUN_080588c4. File offsets therefore form four 8 KiB blocks at 0x0000, 0x2000, 0x4000, 0x6000.
  • Redundancy: during (re)initialization all four blocks receive the identical image (mirroring/zero-fill). In cap-01 only block 0 carries the header magic; blocks 1–3 are all-zero except 0xFFFF words at 0x401E (block 2, +0x1E) and 0x7FFE (block 3, +0x1FFE). Whether the four blocks later diverge into independent slots or stay mirrored copies cannot be decided from a single initialized sample.
  • Generation/sequence counters: none verified. FUN_0800af68 cycles the header byte at SRAM+0 through values 1 → 2 → 3 → 0 interleaved with u16 and magic writes, which looks like a commit-phase marker that ends at 0 (matching cap-01 byte 0 = 0x00), not a persistent counter.
  • Selection rule: FUN_0800ac64 classifies the existing save into values 0–3 (combining a type byte < 3 from FUN_0800b088 with bits from FUN_0800b0e4/FUN_0800b10c) and FUN_08035444 branches on it; the exact copy-selection rule is UNKNOWN because those byte-reader callees are missing from the corpus.

All SRAM access in the corpus funnels through one verified-write primitive; grep finds exactly five literal 0xE000000 references, all in the FUN_0800af68 cluster.

  2. Write the image to all four SRAM blocks (0x2000 each) via FUN_080588c4.
  3. FUN_0800aff0 builds fresh defaults in RAM (calls FUN_0800759c, FUN_08008cac — 0x321-byte struct copy, FUN_0801da58, FUN_0801d6c0 — sets a field to 0x640, FUN_0801d724 — 0x48, FUN_08020168, FUN_0802712c, FUN_0802d9f0, FUN_08026f3c, FUN_080561fc, FUN_080554ec, FUN_08055fd0, FUN_0801fb44, FUN_08048cb8).
  4. Header commit sequence directly on SRAM: FUN_0800b050 writes marker 1 at SRAM+0; FUN_0800b0ac writes a u16; FUN_0800b06c writes marker 2 at SRAM+0; FUN_0800b0c8 writes the same u16 value again; FUN_0800b1e4 writes marker 3; FUN_0800b17c writes the 15-byte magic; FUN_0800b034 writes marker 0 (final state).

Caller chains (from ghidra/callgraph.json + decompiled bodies)

  • FUN_08035444 (top dispatcher, no callers in graph): calls FUN_0800ac64; if no valid save → FUN_080354c0 (title/menu loop calling FUN_08035488, FUN_08034f60, FUN_080353b0, FUN_08035020); if still no save → FUN_0800af68 (create new) then FUN_080354a8; else load path FUN_0800ace8 + FUN_0800adc4 + FUN_080354a8 + FUN_08024588 (last three bodies missing from corpus).
  • FUN_0800ad24 (no callers): dispatches on FUN_0800ac64 result 2/3 to missing FUN_0800ae1c/FUN_0800ae70 — likely per-type load variants.
  • RAM-struct mutators before flush: the duel/gameplay functions FUN_08005d1c, FUN_0800604c, FUN_080064f4, FUN_08006764, FUN_0800683c, FUN_08006958, FUN_08006b40, FUN_08006c60, FUN_08006e84, FUN_08007068, FUN_08007350 (grouped by FUN_080075b0, itself called by FUN_0800aff0) mutate the player/duelist struct in RAM at relative offsets +0x00..+0x09 (bytes), +0x0E/+0x1C/+0x1E (name/id u16s), +0x32 (mode/state u16, values 2/3/5/6 observed in code), +0x16A (progress u16), +0x16C/+0x16E (i16 positions). Mapping method: each function's _DAT_ pointer dereferences were cross-checked across all 169 bodies; identical relative offsets recur in ≥6 independent functions, so they are fields of one shared RAM struct that FUN_08008cac/FUN_0802d9f0 copy wholesale (0x321 bytes) and that the 8 KiB SRAM image mirrors. How each caller mutates the struct: byte fields are incremented/wrapped against per-mode limits, +0x32 transitions between states 2/3/5, +0x16A is reset to 0 on state changes and compared against FUN_0805d1fc (strlen-like) thresholds in FUN_08006764/FUN_0800683c.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic: 021024_DM8_KCEJ (15 ASCII bytes) at file offset 0x01, written by FUN_0800b17c (FUN_080588c4(..., 0xf)) and validated by FUN_0800b194. Verified in both code and cap-01-future-1.sav bytes.

Integrity in code is write-verify, not a stored checksum: FUN_080588c4 copies, then memcmps (FUN_0805aac4), retrying 3 times. No sum/XOR/CRC loop over save data exists in the corpus, so no checksum formula can be claimed as proven.

The only candidate stored integrity words are u16 0xFFFF at 0x401E and 0x7FFE in cap-01. Python verification (script /tmp/verify_sav.py, run in this workspace):

saves/cap-01-future-1.sav 32768 sha256=65b153d227854b9340e124d97d3faf2e1d43dfad8dadd679e82979d478fa6bca
  magic@0x01: b'021024_DM8_KCEJ'
  byte0: 0x0  u16@0x401E: 0xffff  u16@0x7FFE: 0xffff
  block2 covered sum16: 0x0 ones-complement: 0xffff
  block3 covered sum16: 0x0 ones-complement: 0xffff
  block0 sum16: 0x3cd xor8: 0x33 crc32: 0xa9a457a2

Stored 0xFFFF equals the one's complement of the sum16 of the (all-zero) covered bytes — but that is trivially true for any complement scheme over empty data, and equally consistent with an erased/uninitialized sentinel or the FUN_0800b0ac/FUN_0800b0c8 u16 value. Verdict: HYPOTHESIS, not verified. Block 0 has no candidate stored checksum at all (its would-be trailer bytes are 0x0000, matching none of sum16 0x03CD, its complement 0xFC32, XOR8 0x33, or CRC32 0xA9A457A2).

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss states exist in states/, so each test reloads the mutated .sav cold and observes boot/UI/RAM. Repair rule if the 0xFFFF words prove to be one's-complement sum16 checksums: recompute stored = (~sum16(covered bytes)) & 0xFFFF; if boot ignores them, they are sentinels and no repair is needed — the first test decides this.
