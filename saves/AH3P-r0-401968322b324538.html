All findings below are derived exclusively from ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, the two real .sav files in saves/, and standard public GBA hardware facts (SRAM/Flash at 0x0E000000, EEPROM via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM-HIGH.

What was proven (code + byte-level cross-check, CONFIRMED_VERIFIED):

  • The save medium is plain SRAM, not Flash or EEPROM: the decompiled code never emits the

Flash 0x5555/0x2AAA command-byte sequence and never touches the EEPROM DMA3 control register (0x040000D4); the only save-space literal present is the raw SRAM base 0xE000000 (ghidra/decompiled.c:249,284). This matches the packet's declared SRAM 256K media.

  • The 32768-byte .sav file is a byte-exact duplication of two 16384-byte (0x4000) halves:

data[0:0x4000] == data[0x4000:0x8000] holds for both sample files (verified in Python, see §2). This matches the dual-write loop in FUN_0800078c (ghidra/decompiled.c:235-241, 256-263), which writes every byte to both addr and addr+0x4000 in the same iteration.

  • A 51-entry, 220-byte-stride (0xDC) record table occupies 0x142C..0x3FFF (exactly ending

at the mirror boundary). Each record is an 8-byte header (u32 payload length, u8 table id, u8 index, u16 checksum) followed by a 128-byte payload. The checksum of all 51 records in both sample .sav files was independently recomputed in Python using the exact algorithm of FUN_0800044c and matched the stored value in all 102 cases (51 records × 2 files) — see §4 for the full verification run.

  • The literal ASCII header "HAMUTARO3\0\0\0AH3P" followed by a build-timestamp string

("Apr 16 200319:20:08") is present at offset 0x0000 in both sample files.

What remains open / unresolved (CONFIRMED_STATIC or HYPOTHESIS):

  • The exact RAM/SRAM addresses behind most _DAT_* globals in ghidra/decompiled.c are not

resolved to numeric literals (Ghidra emitted them as unnamed data symbols with no accompanying symbol/map file in this workspace). This means several caller chains (table ids 1–3 written via the same checksum writer as table id 4, and the separate FUN_080011b4 writer) are proven structurally in code but their destination offsets inside the real .sav could not be independently located/verified against the sample bytes.

  • The "ten-plus" small isolated byte/word regions outside the verified roster table

(0xEE-0xF6, 0x3E6-0x3E7, 0x6B8-0x6C0, 0xB84, 0xD98-0xDA4, 0xDC2-0xDCA) look like plain gameplay counters/stats. None of them match the header shape (len|tableid|idx|chk) of the verified record format, and they are not demonstrably checksum-protected — this is consistent with the packet's own cold-reload probe, which mutated offset 0x6BE and recorded "reverted_to_blank_on_mutation": false" / "integrity_check_confirmed": false".

  • A ROM-resident "blank/default save" template, and a corruption-recovery path that stamps an

ASCII "Clr" tag into a staging buffer, are visible in FUN_0800078c but were never exercised in either sample file (both samples already contain a valid primary save), so this path is CONFIRMED_STATIC only — not observed in practice.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O

No Flash command bytes (0x5555/0x2AAA) or EEPROM DMA3 bitstream code were found anywhere in ghidra/decompiled.c. All save I/O is raw 8-bit SRAM byte load/store, consistent with the packet's declared SRAM 256K media. The two primitives used throughout:

  • FUN_080ec144 (0x080ec144, ghidra/decompiled.c:4892-4906) — raw interrupt-masked byte

copy:

  void FUN_080ec144(undefined1 *param_1,undefined1 *param_2,int param_3)
  {
    *_DAT_080ec17c = *_DAT_080ec17c & (ushort)_DAT_080ec180 | 3;  // disable IRQs (IME/IE-style)
    while (param_3 = param_3 + -1, param_3 != -1) {
      *param_2 = *param_1;
      param_1 = param_1 + 1;
      param_2 = param_2 + 1;
    }
  }

This is the actual SRAM write primitive: single-byte stores, exactly matching the GBA SRAM hardware requirement (8-bit bus only, no 16/32-bit or DMA access). It is only called from FUN_0800078c after a mismatch is detected (see 3.2), confirming it is the real "commit to SRAM" step, not a general-purpose memcpy used elsewhere in gameplay code. Role: write. Caller: 0x0800078c (via 0x080ec26c, see callgraph edge 080ec144 -> callers: [080ec26c], ghidra/callgraph.json).

  • func_0x080ec26c / func_0x080ec2b8 — not present among the 126 decompiled bodies

(external/BIOS-adjacent runtime helpers); both are used exclusively as equality tests (callers test == 0 for "match") over fixed byte ranges (0x10, 0xDC+8, 0x8000 bytes), matching the classic memcmp-style signature (dst, src, len[, extra]). func_0x080ec26c is additionally used as the write-verify retry gate: FUN_0800078c's blank-format loop stages a full buffer, calls func_0x080ec26c(iVar7, 0xe000000, 0x8000) against the real SRAM base, and

loops again if the comparison fails (} while (iVar7 != 0);) — i.e. "stage → commit via byte-copy loop → verify by comparing against 0xE000000 → retry until equal". Role: read (verification compare), CONFIRMED_STATIC.

3.2 Serialization / checksum routine

FUN_0800044c (0x0800044c, ghidra/decompiled.c:87-106):

void FUN_0800044c(ushort *param_1,uint param_2)
{
  uint uVar1 = 0;
  for (; 1 < param_2; param_2 = param_2 - 2) {
    uVar1 = uVar1 + *param_1;
    param_1 = param_1 + 1;
  }
  if (param_2 != 0) {
    uVar1 = uVar1 + (byte)*param_1;
  }
  uVar1 = (uVar1 & _DAT_08000488) + (uVar1 >> 0x10);
  /* tail-call via jump table */
  return ~((uVar1 & _DAT_08000488) + (uVar1 >> 0x10)) & 0xffff;
}

This is a classic Internet-checksum-style, one's-complement 16-bit sum: sum the buffer as little-endian 16-bit words, fold any trailing odd byte in as a plain byte add, fold the 32-bit accumulator's carry into the low 16 bits (twice), then return the bitwise complement masked to 16 bits. _DAT_08000488 is 0xFFFF in effect (standard carry-fold mask). Role: checksum, CONFIRMED_VERIFIED (byte-for-byte match against real .sav data, see §4).

Full traced chain, every hop confirmed via ghidra/callgraph.json and manual read of ghidra/decompiled.c:

How each caller mutates the in-RAM struct before flushing: FUN_08000ff4 is the only function observed to populate the 8-byte record header + 128-byte payload (piVar3, a scratch buffer obtained from func_0x0800ae6c) before the checksum is computed and the record is copied out. The three table id 1/2/3 singleton invocations execute the same code path with param_2=0 fixed, so they are structurally proven writers but their destination tables (_DAT_08001084/_DAT_08001088-equivalent for those ids) are unresolved symbols in this workspace — their exact byte offsets in the real .sav were not independently located, so they remain CONFIRMED_STATIC rather than CONFIRMED_VERIFIED.

A second, structurally similar writer, FUN_080011b4 (0x080011b4, ghidra/decompiled.c:731-800), is called from 0x08000744 for parameters 2 and 3. It also compares two backup candidates via func_0x080ec2b8/FUN_0800044c and copies the winner with func_0x080ec2b4 (a plain, non-interrupt-masked copy, distinct from FUN_080ec144). Because it never references the literal SRAM base 0xE000000 internally, whether it participates in the .sav file at all (versus writing into an IWRAM/EWRAM-only shadow structure) is an

open question — see §6.

3.4 Format-recovery ("Clr" tag) path — CONFIRMED_STATIC, not observed in samples

The else branch of FUN_0800078c (triggered only when neither existing candidate backup compares equal — i.e. first boot or corrupted save) stages a fresh buffer and stamps the ASCII bytes 0x43,0x6c,0x72 ("Clr") at buffer offset +9 (and the mirrored +0x4009):

*(undefined1 *)(iVar7 + 9) = 0x43;    // 'C'
*(undefined1 *)(iVar7 + 0xa) = 0x6c;  // 'l'
*(undefined1 *)(iVar7 + 0xb) = 0x72;  // 'r'

In both real sample files, bytes 0x0009-0x000B are 00 00 00 (the three null bytes padding "HAMUTARO3" before "AH3P" begins at 0x0C). This confirms the "Clr"-stamping path was

not exercised when either sample .sav was produced — both already carried a previously initialized, valid save, so the game took the "compare existing candidates, pick a winner" branch instead of the "format blank" branch. This is a correctly CONFIRMED_STATIC (code-proven) finding that is explicitly not corroborated by sample bytes, and should not be over-claimed.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic / version string (CONFIRMED_VERIFIED)

Offset 0x0000, both sample files, identical bytes:

000000: 48 41 4d 55 54 41 52 4f 33 00 00 00 41 48 33 50  HAMUTARO3...AH3P
000010: 41 70 72 20 31 36 20 32 30 30 33 31 39 3a 32 30  Apr 16 200319:20
000020: 3a 30 38 00 00 00 00 00 00 00 00 00 00 00 00 00  :08.............

"HAMUTARO3" (9 bytes, NUL-padded to 12) is the internal title/series tag; "AH3P" (4 bytes) is the GBA header game code baked into the save as a cross-check; "Apr 16 200319:20:08" is a build/link timestamp string, almost certainly compiled into the ROM's default/blank save template and copied verbatim the first time the save is initialized (the template source itself was not located among the 126 decompiled functions — Ghidra shows it only as an opaque _DAT_* pointer, consistent with it being .rodata, not disassembled code).

No code in ghidra/decompiled.c was found to construct this string byte-by-byte; it is therefore CONFIRMED_VERIFIED as a static, invariant signature (proven identical across both samples) but its writer function is HYPOTHESIS (inferred to be a memcpy of a ROM-resident template, never isolated in the extracted function set).

4.2 Checksum algorithm — CONFIRMED_VERIFIED

Algorithm: one's-complement 16-bit checksum (see §3.2, FUN_0800044c). Covered range: the full record (8-byte header with the 2-byte checksum field temporarily zeroed, + 128-byte payload = 136 bytes), per record. Stored at: header offset +6 (2 bytes, little-endian), inside each of the 51 roster records.

Python verification output, run against both real .sav files in saves/:

import struct

def chk(buf):
    u, n, i = 0, len(buf), 0
    while n > 1:
        u += struct.unpack_from('<H', buf, i)[0]
        i += 2; n -= 2
    if n != 0:
        u += buf[i]
    u = (u & 0xffff) + (u >> 16)
    u = (u & 0xffff) + (u >> 16)
    return (~u) & 0xffff

base, stride = 0x142C, 0xDC
for fname in ['saves/cap-00-future-0.sav', 'saves/cap-01-future-1.sav']:
    data = open(fname, 'rb').read()
    matches = 0
    for idx in range(51):
        off = base + idx * stride
        rec = bytearray(data[off:off + 136])
        stored = struct.unpack_from('<H', rec, 6)[0]
        rec[6] = rec[7] = 0
        matches += (chk(bytes(rec)) == stored)
    print(fname, 'matches:', matches, '/ 51')

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of a paired .ss-backed .sav (none are currently present in states/ for this legacy checkpoint cohort — this plan assumes future captures will include paired pre/post save states), then reloaded and observed in mGBA.

  1. Checksum-protected roster record tamper (predicts rejection/repair).
  • Mutate one byte inside a roster record payload, e.g. 0x142C + 0x08 (record 0, payload byte

0), leaving the stored checksum at 0x142C+0x06 unchanged.

  • Prediction: if the game actually validates this checksum at load (not yet observed —

only inferred from the write-side code), the record should either be treated as corrupt (reset to a default "Ham-Ham" state) or silently ignored; if the game does not validate on load, the tampered byte should persist and manifest as a visibly wrong hamster stat/name/location in-game.

  • Required checksum repair (counterfactual control): recompute via the exact FUN_0800044c

algorithm (§4.2) over the 136-byte record with the checksum field zeroed, write the result at +0x06, and verify the same mutated payload byte is now accepted without any fallback/reset behavior — isolating "checksum enforced" from "byte simply unused".

  • Repeat identically on the mirrored copy at offset + 0x4000 to rule out the mirror being

used as the authoritative copy during a mismatch.

  1. Mirror-desync fuzz (tests redundancy/selection logic).
  • Flip one bit at 0x142C+0x08 but leave 0x542C+0x08 (the +0x4000 mirror) untouched,

producing a deliberately desynchronized pair.

  • Prediction: per §2, no generation counter was found, so the expected outcome is that the

game either (a) silently uses the primary 0x0000-based window and never notices the mismatch until the next save-and-mirror cycle overwrites it again, or (b) a comparison path we have not yet located detects the mismatch and triggers the 0x0800078c "format blank" branch. Observing which outcome occurs will resolve the current open question in §3.1/3.4.

  1. Non-record counter tamper (0x06BE, 0x0B84).
  • Decrement/increment 0x06BE and 0x0B84 independently (not in the observed lockstep of

-1/+1) and reload.

  • Prediction: since the packet's own cold-reload probe already found

"reverted_to_blank_on_mutation": false" for 0x06BE, no corruption-recovery behavior is expected; the counterfactual to test is whether the visible game state (e.g. an on-screen day counter, hunger/step meter) changes proportionally — this would confirm the field's semantic meaning, which is currently only HYPOTHESIS.

  1. Blank-format path trigger (tests the never-observed "Clr" tag, §3.4).
  • Corrupt both mirror halves identically (so the primary/backup equality compare in

FUN_0800078c fails for all three candidate sources) by, e.g., zeroing bytes 0x0000-0x0023 in both the 0x0000 and 0x4000 copies.

  • Prediction: this should force the game down the previously-unexercised blank-format

branch, and the resulting fresh save should show the "Clr" tag at offset 0x0009-0x000B and a freshly-rebuilt header/roster table — directly confirming or refuting §3.4's CONFIRMED_STATIC hypothesis with real bytes for the first time.

  1. Fresh-vs-restore matched-duration control.
  • Run two otherwise-identical sessions of equal frame length, one starting from a fresh/blank

save and one restoring the existing cap-00/cap-01 save, mutating nothing. Diff the resulting .sav files byte-for-byte against each other and against the two provided samples.

  • Prediction: only the already-identified mutating bytes (0x06BE, 0x0B84, and their

+0x4000 mirrors) and any newly-identified time/step counters should differ; any additional byte-level divergence is a signal of an unmapped field worth a follow-up targeted mutation test.
