Clean-Room Save Format Report: Mother 1+2 (Japan) — A2UJ-r0-fd444702f465698e

All findings below are derived exclusively from this workspace: the two .sav binaries in saves/, the trace-guided decompilation in ghidra/decompiled.c (158 functions), ghidra/callgraph.json, ghidra/save_related_functions.c, and standard/public GBA hardware specs (SRAM 0x0E000000, Flash, EEPROM via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000, WAITCNT 0x04000204). No third-party game-specific wiki, decompilation, or cheat-table was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

A small, 16-byte "selection" record (magic "MOTSEL12") is fully verified: its magic bytes, its additive checksum algorithm, its mirrored (×2) redundancy layout, its exact writer function (FUN_0801278c), its exact validator/reader functions (FUN_080125b0 read-side, FUN_080124c4 caller with mirror fallback), and its on-disk bytes in saves/cap-01-future-1.sav all agree byte-for-byte with a Python re-implementation of the checksum formula (§4). This is the only region of the 32 KB SRAM image that differs from the blank/erased state across the two supplied snapshots, so it is the only region that can be CONFIRMED_VERIFIED.

A second, much larger record format (magic "MOT2", record size 0x7C0 = 1984 bytes, same additive-checksum family) is CONFIRMED_STATIC only: its validator (FUN_0801256c) and its mirrored-slot reader (FUN_08012460) are fully decompiled and self-consistent, and very likely hold the actual game-progress save, but neither supplied .sav file contains non-erased bytes outside the 32-byte 0x7F00–0x7F1F window, so this format's physical offset, full field layout, and its writer function cannot be verified against real bytes — they remain HYPOTHESIS/UNKNOWN.

Every low-level byte-copy "driver" function that both of the above call through (FUN_080f482c, FUN_080f4890, FUN_080f4900, FUN_080f49a8) is explicitly flagged by the decompiler itself ("Globals starting with _ overlap smaller symbols at the same address" / "Could not recover jumptable") as unreliable in its recovered body. The call sites (argument count, argument ordering, and argument sizes matching record sizes) are trustworthy evidence; the

internal mechanics shown (loop bounds, the exact hardware register touched) are not asserted as fact — they are flagged HYPOTHESIS, consistent only in shape with the standard GBA "set wait-state bits, then access SRAM" idiom.

ghidra/callgraph.json resolved zero static call edges for every function this report discusses (all entries queried returned {"callers": [], "callees": []}). All caller/callee chains below were established by manually reading argument addresses and global symbol names in ghidra/decompiled.c, not from the callgraph. This is stated explicitly in §3 for every chain.

2. Physical Media, Slot Geometry & Redundancy

  • Media: SRAM, 32,768 bytes (32 KB / 256 Kbit) — both supplied .sav files are exactly

32768 bytes, matching the packet's declared SRAM 256K media tag. Standard GBA SRAM is mapped at 0x0E000000 and is only byte-addressable (8-bit bus); no literal 0x0E000000 constant appears anywhere in the 158-function decompiled corpus, so the exact CPU-side base address is

not independently verified here — it is the standard mapping for this media kind.

  • No SDK save-library tags detected in the ROM (per packet metadata); the save code appears

to be a bespoke, hand-rolled driver (see §3).

  • Observed non-erased region: only 0x7F00–0x7F1F (32 bytes) differs from the

all-0xFF erased state in either supplied .sav. Everything else in the 32 KB image is 0xFF in both files (confirmed by exhaustive Python scan, see §4).

  • Slot/copy geometry — small "selection" record (CONFIRMED_VERIFIED):
  • Record size: 16 bytes (0x10).
  • Two identical, fully mirrored copies: 0x7F00–0x7F0F and 0x7F10–0x7F1F.
  • Verified byte-for-byte identical in cap-01-future-1.sav.
  • Selection rule (read path, FUN_080124c4): try mirror A first (copy SRAM→RAM via

FUN_080f482c, validate via FUN_080125b0); if invalid, try mirror B; if both invalid, report failure (*param_1 = 0xFFFFFFFF). This is a simple "primary, then backup" fallback, not a round-robin/newest-wins scheme — there is no sequence counter in this record.

  • Write path (FUN_0801278c): builds the record once in a RAM scratch buffer, computes the

checksum, then writes it to both mirror destinations in turn, each via a write (func_0x080f4890) immediately followed by a verify/read-back-and-retry loop (func_0x080f4900, up to 5 attempts) — a write-verify-retry idiom consistent with SRAM's reputation for unreliable writes on some cartridges/emulators.

  • Slot/copy geometry — large "MOT2" record (CONFIRMED_STATIC):
  • Record size: 0x7C0 = 1984 bytes.
  • Reader FUN_08012460 computes two destination offsets from a caller-supplied slot index

iVar4: mirror A at iVar4 * 0xF80 + base, mirror B at (iVar4*2 + 1) * 0x7C0 + base (base = _DAT_080124b4/iVar1, an un-resolved global in this corpus). This is again a "try A, else try B" fallback with no visible sequence/generation counter field in the validator.

  • Not observed in either supplied .sav — this slot's absolute SRAM offset therefore

cannot be cross-checked against real bytes and is UNKNOWN.

  • No writer function for this record was found among the 158 extracted functions — **UNKNOWN /

open question** (see §6).

3.2 Small "selection" record ("MOTSEL12") — CONFIRMED_VERIFIED chain

Writer: FUN_0801278c(param_1) (ghidra/decompiled.c:1393)

puVar1 = _DAT_080127cc;                 // RAM scratch buffer for the 16-byte record
*_DAT_080127cc = 0x4d; puVar1[1]=0x4f; puVar1[2]=0x54; puVar1[3]=0x53;
puVar1[4]=0x45; puVar1[5]=0x4c; puVar1[6]=0x31; puVar1[7]=0x32;   // "MOTSEL12"
*(undefined4*)(puVar1+0xc) = param_1;   // offset 0xC: caller-supplied 4-byte field
*(undefined4*)(puVar1+8)   = 0;         // offset 8: zero the checksum field before summing
uVar3 = func_0x0801296c(puVar1,0x10);   // sum all 16 bytes (checksum field currently 0)
*(undefined4*)(puVar1+8)   = uVar3;     // store the sum back into the checksum field
// ... then write puVar1 to BOTH mirror destinations, each via func_0x080f4890
//     write + func_0x080f4900 verify/retry (up to 5 attempts), to _DAT_080127d4 and _DAT_08012800

param_1 is passed in by this function's caller. No caller of 0x0801278c exists among the 158 extracted functions — the value of param_1 actually used in production code is therefore unknown; the only observed instance (0x00000000) comes from the .sav byte evidence itself, not from tracing a caller. This is noted as an open question in §6.

Checksum primitive: FUN_0801296c(ptr,len) (ghidra/decompiled.c:1442) — a plain additive loop, iVar1 += *ptr++ for len iterations, returned as a 32-bit (unbounded, non-modulo) sum. No XOR, no CRC polynomial, no seed — the simplest possible checksum.

Validator/reader: FUN_080125b0(void) (ghidra/decompiled.c:1353), operating on buffer _DAT_080125e8:

if (bytes[0..7] == "MOTSEL12") {
    iVar4 = *(int*)(bytes+8);         // read stored checksum
    bytes[8..11] = 0;                 // zero it in place
    iVar3 = func_0x0801296c(bytes, 0x10);  // recompute sum over all 16 bytes
    return (iVar4 == iVar3) ? 0 /*OK*/ : 1 /*checksum mismatch*/;
} else {
    return 2; // bad magic
}

This is the exact inverse of the writer's checksum construction — proof that 0x080125b0 is the matching reader for records built by 0x0801278c.

Reader caller / mirror-fallback: FUN_080124c4(param_1) (ghidra/decompiled.c:1281):

*param_1 = 0xFFFFFFFF;
func_0x080f482c(_DAT_080124f8, _DAT_080124fc, 0x10);   // copy mirror A into RAM buffer
if (func_0x080125b0() != 0) {                           // validate mirror A
    func_0x080f482c(_DAT_08012500, uVar2/*=_DAT_080124fc*/, 0x10); // copy mirror B
    if (func_0x080125b0() != 0) { return 1 /*both failed*/; }
}
*param_1 = *(undefined4*)(iRam08012514 + 0xc);          // success: return the 0xC field
return 0;

How this caller was mapped: it calls func_0x080125b0() by literal name match with zero arguments (consistent with the validator's void signature operating on the fixed global buffer _DAT_080125e8), and its copy sizes (0x10) and destination global (_DAT_080124f8) match the record size and scratch-buffer convention used by the writer side. This is how it mutates no save bytes (it is read-only) but populates the in-RAM mirror iRam08012514 from whichever SRAM mirror validated successfully.

3.3 Large "MOT2" record (0x7C0 bytes) — CONFIRMED_STATIC chain (no .sav byte evidence)

Validator: FUN_0801256c(void) (ghidra/decompiled.c:1314), operating on buffer _DAT_0801258c:

if (bytes[0..3] == "MOT2") {
    iVar4 = *(int*)(bytes+4);          // stored checksum
    bytes[4..7] = 0;                   // zero it
    iVar3 = func_0x0801296c(bytes, 0x7c0); // sum the WHOLE 1984-byte record
    return (iVar4==iVar3) ? 0 : 1;
} else return 2;

Same checksum family as the small record (func_0x0801296c), but magic is only 4 bytes ("MOT2") and the checksum field sits at offset 4 instead of 8, covering the entire record rather than just a 16-byte header.

Reader / mirror-fallback caller: FUN_08012460(void) (ghidra/decompiled.c:1246):

iVar1 = _DAT_080124b0;                               // source struct base
iVar4 = *(short*)(_DAT_080124b0 + 10);               // slot index, read from offset 10 of source struct
func_0x080f482c(iVar4*0xf80 + _DAT_080124b4, _DAT_080124b0, 0x7c0);  // copy mirror A -> RAM
if (func_0x0801256c(iVar4) != 0) {                   // validate mirror A
    func_0x080f482c((iVar4*2+1)*0x7c0 + _DAT_080124b4, iVar1, 0x7c0); // copy mirror B -> RAM
    if (func_0x0801256c(iVar4) != 0) { return 0 /*both failed*/; }
}
*(short*)(iVar1 + 8) = (short)_DAT_080124b8;
return 1; // success

How this caller was mapped: it calls func_0x0801256c(iVar4) by literal name, with the slot index as argument (matching the validator's implicit per-slot buffer selection), and its copy length (0x7c0) matches the record size asserted by the validator and by the init routine below.

No writer for this record exists among the 158 extracted functions. It mutates the in-RAM struct at iVar1 + 8 (a 2-byte field) on success, copying from global _DAT_080124b8 — the meaning of this field is UNKNOWN (likely a "last slot loaded OK" flag or cached value, but unverified).

Init: FUN_08012444(void) (ghidra/decompiled.c:1233):

*_DAT_08012454 = 0x7c0;          // record size constant, confirms 0x7C0 elsewhere
*_DAT_08012458 = _DAT_0801245c;  // base pointer setup

Confirms 0x7C0 as a named constant independently of the validator/reader, reducing the risk that 0x7c0 is a coincidental literal.

Important correction to the packet's pre-computed profile: the packet's ascii_magic_strings field reports "MOTSEL127" (9 characters) for the active range. This is a naive printable-ASCII-run scan. The decompiled code proves the true magic is only the first

8 bytes, "MOTSEL12"; the 9th byte (0x37, ASCII '7') is actually the low byte of the 32-bit checksum field (0x00000237) and only looks like a printable magic character by coincidence. This is called out explicitly so the distinction between tool-generated heuristic metadata and code-verified fact is not lost.

Checksum algorithm — small "selection" record (CONFIRMED_VERIFIED)

  • Algorithm: plain unsigned additive sum (sum32), implemented by FUN_0801296c:

checksum = Σ byte[i] for i in 0..len-1, no modulo/wraparound masking observed, no seed, no XOR, no CRC polynomial, no bit rotation.

  • Covered range: the full 16-byte record (offset 0x0–0xF), **with the 4-byte checksum

field itself (offset 0x8–0xB) temporarily zeroed** during the summation (both in the writer FUN_0801278c and the validator FUN_080125b0 — proven identical on both sides).

  • Stored offset / size: offset 0x8, 4 bytes, little-endian (ARM/Thumb native word store).
  • Endianness: little-endian (GBA ARM7TDMI native).

Python verification against the actual .sav files (script run in this workspace):

import struct
def verify(path):
    data = open(path,'rb').read()
    for off in (0x7f00, 0x7f10):
        rec = data[off:off+16]
        magic = rec[0:8]
        stored_chk = struct.unpack_from('<I', rec, 8)[0]
        zeroed = bytearray(rec); zeroed[8:12] = b'\x00\x00\x00\x00'
        computed = sum(zeroed)
        print(off, magic, hex(stored_chk), hex(computed), stored_chk==computed)

pattern, but over 0x7C0 (1984) bytes with the checksum field at offset 0x4–0x7 (not 0x8).

  • Cannot be verified against real bytes — this region is not present (still 0xFF-filled) in

either supplied .sav. Confidence: CONFIRMED_STATIC (code-only).

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav (the only sample with a live record), loaded as a .sav paired with an emulator save state, since this workspace's states/ directory is empty for this legacy checkpoint cohort (no paired .ss files were supplied — this is itself an open item; see below). All offsets are absolute file offsets.

  1. Checksum-field corruption, no repair (negative control).
  • Mutation: flip one bit in 0x7F08 (e.g. XOR 0x01) in mirror A only, leave mirror B intact.
  • Requires checksum repair: No (this is the corruption test).
  • Predicted effect: FUN_080124c4's mirror-A validation (FUN_080125b0) returns 1

(checksum mismatch); it should fall through to mirror B, which still validates, and the game should behave exactly as if nothing were corrupted (silent self-heal via redundancy). This tests the "primary fails, backup succeeds" path with zero game-visible symptom — the key observable is that the next write should rewrite mirror A to match (since the writer always writes both), which can be confirmed by re-dumping the .sav after one more save event.

  1. Checksum-field corruption in BOTH mirrors (true failure injection).
  • Mutation: corrupt 0x7F08 and 0x7F18 identically (e.g. set both to 0x00000000).
  • Requires checksum repair: No.
  • Predicted effect: both mirror validations fail; FUN_080124c4 returns failure

(*param_1 = 0xFFFFFFFF). Observable prediction: whatever UI consumes this "selection" value should fall back to a default (likely "no selection" / slot-picker shown), since no valid record exists. If the game instead crashes or silently proceeds with garbage, that would falsify the "selection record, soft-fail design" hypothesis.

  1. Magic-byte corruption (bad-magic path, return code 2).
  • Mutation: change 0x7F00 from 0x4D ('M') to any other byte, in mirror A only.
  • Requires checksum repair: No (magic check happens before checksum check and short-circuits).
  • Predicted effect: identical observable behavior to test 1 (silent fallback to mirror B) —

this distinguishes "bad magic" (return 2) from "bad checksum" (return 1) at the code level, but both should be externally indistinguishable via gameplay, since FUN_080124c4 only checks != 0, not the specific error code. If gameplay does distinguish these two cases, that falsifies this reading of the caller.

  1. Field 0x7F0C (the unidentified param_1 field) sweep, with checksum repair.
  • Mutation: set 0x7F0C–0x7F0F (and the matching mirror 0x7F1C–0x7F1F) to 0x00000001,

0x00000002, 0x00000003, etc., one value per test run.

  • Requires checksum repair: Yes — recompute

sum(bytes[0:16] with bytes[8:12]=0) after each mutation and write the new sum (little-endian) into 0x7F08/0x7F18.

  • Predicted effect: this is the key falsifiable test for the 0x7F0C field's semantics. If it

selects a save slot / character / difficulty, the title screen or load menu should visibly change its default selection or highlighted entry when reloading from a save state taken at the title screen. If no observable change occurs for any tested value, that is evidence this field is unused/reserved in the shipped game logic reachable from this entry point, which would narrow (not confirm) the HYPOTHESIS in §5.

  1. Fresh vs. restore repeat (determinism control).
  • Procedure: from a blank SRAM (cap-00-future-0.sav), trigger whatever in-game action produced

cap-01-future-1.sav's write twice in a row (fresh boot each time), and diff the two resulting .sav files byte-for-byte.

  • Predicted effect: if the write is purely deterministic (no RNG/timestamp in this record), the

two resulting files should be byte-identical, confirming there is no hidden counter/seed field this report missed. Any difference would directly falsify the "fully mapped, 16 fixed-meaning bytes" claim in §5 and point at an unmapped dynamic field.

  1. Large "MOT2" record discovery probe (addresses the biggest open gap).
  • Procedure: since no writer was found in this corpus and the record was never observed

non-erased, the only clean-room way to locate it is a controlled gameplay capture: perform an in-game action expected to trigger a "real" game save (not just the title-screen selection captured here), then re-dump SRAM and diff against the blank baseline, exactly as was done to produce cap-01-future-1.sav for the small record.

  • Predicted effect: a new non-erased range of exactly 0x7C0 bytes (or two ranges, 0x7C0

apart per the mirror-offset formula in §3.3) should appear, beginning with ASCII "MOT2" and containing a valid sum32 checksum at offset +4 per §4's algorithm. This is the single highest-value next capture for closing this report's largest UNKNOWN region.

Open questions carried to §6 explicitly (not resolved by this corpus):

  • Real-world value range and semantic meaning of the 0x7F0C field (writer's param_1); no

  • Absolute SRAM offset of the "MOT2" large record (base global _DAT_080124b4 unresolved).
  • Full byte-level field layout of the large record's 1976-byte payload (0x8–0x7BF).
  • Exact hardware register touched by the &mask|3 idiom in FUN_080f482c/FUN_080f4890

(structurally consistent with WAITCNT SRAM wait-control bits, but not literally confirmed — no literal 0x04000204 constant appears in this corpus).

  • No paired .ss emulator save states were supplied for this release (states/ is empty for this

legacy checkpoint cohort), so the fuzzing plan above cannot be executed from this workspace as-is — it requires a follow-up capture that includes paired pre/post save states.
