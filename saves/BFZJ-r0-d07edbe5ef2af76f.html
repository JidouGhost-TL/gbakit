  • Release Key: BFZJ-r0-d07edbe5ef2af76f
  • Game Code / Header Family: BFZJ / BFZ
  • ROM SHA-256: d07edbe5ef2af76fcea3e56ff735b6892ca8f0b0d6a0cde0e7cccd23821812bd
  • Analysis method: Clean-room — derived exclusively from ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, the .sav binary in saves/, and standard public GBA hardware facts (SRAM/Flash at 0x0E000000, EEPROM at 0x0D000000, EWRAM 0x02000000, IWRAM 0x03000000, WAITCNT 0x04000204). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM-HIGH

The save image uses flat-addressed SRAM (byte-addressable, no bank-switching, no DMA3/EEPROM serial protocol), organized as a set of independently-checksummed records, each written twice — a primary copy and a byte-identical backup copy offset +0x4000 later in the 32 KiB image. This was proven by:

  • Reverse-engineering the single checksum routine (FUN_0803afc0, a simple unsigned byte-sum) and the single generic write-with-verify-retry routine (FUN_0803b0a4), which every save-writer in the game calls.
  • Reproducing that checksum algorithm in Python and matching it exactly against 5 independent records (the global header, the ranking table, both per-car-profile slots, and a currently-all-zero record) in the one available .sav sample, including their +0x4000 backup mirrors.
  • Cross-checking three specific byte values that the decompiled init code writes as hard-coded constants (offset+0x20 = 1, offset+0xac = 5) against the exact same byte positions in the real .sav file — all three matched.

What remains open: the exact in-SRAM location and checksum boundary of one large (9,216-byte / 0x2400) record (likely a ghost-data/rankings-adjacent table, written by FUN_0803b968), the exact size of a small record at absolute offset 0x0D00, the precise bit-field semantics of the per-car-profile flag byte, and all gameplay-level semantic labels (which car/course/time a given byte represents). Only one .sav sample was available for this packet (the packet metadata lists 6 captures, but only cap-00-future-0.sav is present in saves/), so no cross-save diffing was possible to disambiguate semantics — this caps the semantic-field confidence at HYPOTHESIS even where structure is CONFIRMED.

2. Physical Media, Slot Geometry & Redundancy

  • Media: SRAM, 256 Kibit (32,768 bytes / 0x8000). No SDK save-identifier tag strings were found in the ROM.
  • Addressing: All save I/O is flat byte-addressed memory copy (FUN_08066bd4 / FUN_08066c44, simple for loops doing *dst++ = *src++), not EEPROM DMA3 bitstream and not Flash 0x5555/0x2AAA command sequences. This is consistent with battery-backed SRAM at 0x0E000000 mapped directly into the CPU address space.
  • Redundancy scheme: The universal writer FUN_0803b0a4 always performs two writes: one at the caller-supplied SRAM address, and one at address + 0x4000. The universal "preferred reader" FUN_0803b040 reads the primary copy, verifies its embedded checksum, and — only if that checksum fails — falls back to the copy at address + 0x4000. This is a classic primary/backup redundancy scheme spanning the two 16 KiB (0x4000) halves of the 32 KiB SRAM chip.
  • Verified in the sample: every record checked (global header, ranking table, slot 0, slot 1) has byte-identical primary and backup copies 0x4000 apart, and both independently satisfy the checksum. See Section 4 for the Python proof.
  • Slots: There are exactly 2 per-car-profile "slot" records (FUN_0803b770/FUN_0803b830, parameter 0/1), each 0xB0 (176) bytes, located at 0x0BA0 and 0x0C50 in the primary half. No slot-selection/active-slot index field was identified in the traced functions — slot index is always passed explicitly by the caller (0 or 1), so slot selection appears to be driven by game-mode state that lies outside the save-related call tree captured in this packet.
  • Generation/sequence counters: none found. The redundancy mechanism is pure checksum-validated A/B replication, not a rotating generation counter — there is no "newest wins" sequence number; the backup is only consulted when the primary's checksum is wrong.

3.2 Serialization / record I/O (the two universal primitives)

  • FUN_0803b0a4(ram_buf, sram_addr, size) — the one save-writer in the game. Computes FUN_0803afc0(ram_buf, size) and stores it as a little-endian u32 at ram_buf[0..3], then calls FUN_08066ca8(ram_buf, sram_addr, size) twice: once at sram_addr, once at sram_addr + 0x4000. Every record-specific writer below is a thin wrapper around this one function with a fixed (ram_buf, sram_addr, size) triple.
  • FUN_0803b040(sram_addr, out_buf, size) — the one save-reader with fallback. Reads sram_addr into out_buf via func_0x08066b70, checks out_buf[0] == FUN_0803afc0(out_buf, size); if the checksum is wrong, re-reads from sram_addr + 0x4000 and checks again; returns failure only if both copies fail.
  • FUN_0803b178 — plain unchecksummed byte copy (for loop), used only for the per-entry packing inside the ranking table (Section 3.4) and for the two 1-byte "getter" accessors FUN_0803bd20/read helpers — it moves bytes between RAM structures, never touches SRAM checksums itself.

Higher-level orchestrators, confirmed by direct call-site inspection:

  • FUN_0803ba04 (0x0803ba04, "format/init everything") — unconditionally calls FUN_0803b148, FUN_0803b34c (→b250+b2e4), FUN_0803b4f8 (→b364+b488), FUN_0803b830(0), FUN_0803b830(1), FUN_0803b9ec (→b938+b968), FUN_0803b920 (→b868+b8a8). This writes every single record once, from scratch — a full-save factory reset.
  • FUN_0803ba34 (0x0803ba34, no static callers — invoked via an unresolved function pointer, almost certainly at boot/title) — reads the global header via FUN_0803b108; if that record is invalid, it calls FUN_0803ba04 (full reset, above). If it is valid, it individually re-validates each of the other 7 records via unresolved external stub calls (func_0x0803b208, func_0x0803b318, func_0x0803b4c0, func_0x0803b7d0(0/1), func_0x0803b8e4, func_0x0803b9a4 — these are 1-hop-outside the extraction window and were not decompiled in this packet) and, for any record found invalid, re-initializes only that record's RAM copy (calling the matching *_250/*_364/*_634/*_868/*_938 init routine) — notably it does not call the corresponding _0a4 writer for the two car-profile slots directly; instead it calls an unresolved func_0x0803bdf8(idx), which could not be decompiled from this packet's extraction window.

3.4 Ranking/name table internal packing (confirmed structurally, semantics unconfirmed)

  • FUN_0803babc / FUN_0803bc14 (0x0803babc / 0x0803bc14) are a matched encode/decode pair implementing a 6-bit character pack: 8 ASCII characters (each stored as char - 0x20, i.e. values 0–63) are bit-packed into 6 bytes (48 bits = 8×6 bits), little-endian bit order. This is a standard space-saving technique for name/initials entry fields; I treat "this stores an 8-character string" as CONFIRMED_STATIC (the algorithm is unambiguous), but which gameplay field it represents (driver name, car name, etc.) is HYPOTHESIS.
  • FUN_0803d7b0 (0x0803d7b0) builds, per outer-loop index 0..0x2d (46 iterations), a 64-byte (0x40) RAM record consisting of 5 inner entries of 12 bytes each (5×12=60) plus 2 trailing bytes + 2 zero-padding bytes. Each 12-byte inner entry = 6-byte packed name (via FUN_0803babc) + 2-byte field (copied verbatim from source +0xA..+0xB) + 1 byte (+0xC) + 1 byte (+0xD) + 2 zero bytes. This matches the math exactly: 0x1c (ranking table start) + 0x4 (checksum) + 46*0x40 = 0xBA0, which is exactly the address where the first car-profile slot begins — i.e., the table's size and the next record's start address agree to the byte, which is strong structural corroboration.
  • FUN_0803bd20/FUN_0803bd68/FUN_0803bec8 are read-only accessors (not writers): FUN_0803bd20 decodes one 6-byte packed name back to 8 ASCII characters for UI display; FUN_0803bd68/FUN_0803bec8 fetch single bytes (+0xC, +0xD) from an unrelated structure base — these look like simple settings getters, not save-record readers (they do not call FUN_0803b040), so I have not attributed them to any specific save record.

3.5 Car-profile slot internals (FUN_0803b634, confirmed byte-exact against the sample)

FUN_0803b634(idx) operates on base = sram_mirror_ptr + idx*0xB0 + 0xBA0 and performs, in order:

  1. *(u8)(base+4) &= 0xFE then &= 0xF1 then &= 0x8F; |= 0x10 — three sequential bit-clear/set operations on a single flag byte at +4 (final effect: clears bit 0, clears bits 1–3, clears bits 4–6 and sets bit 4).
  2. *(u16)(base+4) &= mask; |= 0x100 — re-touches the same 2 bytes as a 16-bit field, setting bit 8 (i.e., bit 0 of byte +5).
  3. *(u8)(base+5) &= 0xE3; |= 0x0C — clears bits 2–4 of byte +5, sets bits 2–3.
  4. Zeroes three 8-byte arrays at +0x20, +0x28, +0x30.
  5. Sets *(u8)(base+0x20) = 1.
  6. Sets *(u8)(base+0xAC) = 5, *(u8)(base+0xAD) = 0, *(u8)(base+0xAE) = 0.

Every one of these hard-coded constants was verified against the real .sav file (Section 4.3): byte +0x20 reads 0x01 in both slots, byte +0xAC reads 0x05 in both slots. This is about as strong as clean-room static-to-dynamic correlation gets without an emulator trace.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Algorithm

u32 checksum(u8 *record, u32 size) {
    u32 sum = 0;
    for (u32 i = 4; i < size; i++)
        sum += record[i];          // unsigned byte accumulation, no carry masking beyond u32 wrap
    return sum;                      // stored little-endian at record[0..3]
}
  • Type: sum8-style unsigned byte accumulation into a 32-bit field (not sum16/32, not XOR, not CRC, no seed, no two's-complement). Decompiled proof: FUN_0803afc0, ghidra/decompiled.c:1603-1618.
  • Covered range: every byte of the record except its own first 4 bytes (the stored checksum field), i.e. [record_base+4, record_base+size).
  • Stored offset: always the first 4 bytes of the record (record_base+0..3), little-endian.
  • Scope: per-record (not a single whole-save checksum) — there are at least 6 independently-checksummed records.

4.2 Python verification against saves/cap-00-future-0.sav

import struct
data = open("saves/cap-00-future-0.sav", "rb").read()

def checksum(buf, size):
    s = 0
    for i in range(4, size):
        s += buf[i]
    return s & 0xFFFFFFFF

def check(name, off, size):
    buf = data[off:off+size]
    stored = struct.unpack_from("<I", buf, 0)[0]
    computed = checksum(buf, size)
    print(f"{name}: off=0x{off:x} size=0x{size:x} stored=0x{stored:08x} computed=0x{computed:08x} match={stored==computed}")

check("global_header",        0x0000, 8)
check("config2",              0x0008, 0x14)

4.4 Record at absolute offset 0x0D00 — size unresolved

The writer FUN_0803b8a8 flushes a record at base+0xD00 whose size comes from an unresolved literal (_DAT_0803b8d8), and in this sample the entire region from 0x0D00 through at least 0x0D08–0x1C00 reads as all-zero (checksum of an all-zero buffer is trivially 0, so this is consistent with — but does not prove — any size up to the start of whatever record follows it). Confidence: HYPOTHESIS for size; CONFIRMED_STATIC for existence/role (a small record flushed via the universal writer, with one payload byte zeroed by its init routine at +0xD04).

4.5 Large 9,216-byte (0x2400) record — location unresolved

FUN_0803b968 flushes exactly 0x2400 bytes via the universal writer, proven in code. I attempted to locate it in the sample by brute-force: scanning every 4-byte-aligned offset in the primary 16 KiB half for a 0x2400-byte window whose first 4 bytes equal the sum-checksum of the remaining 0x23FC bytes. This scan found no unique non-trivial match (the only non-zero "hit" at offset 0x0C50 is a false positive — it coincides with the already-confirmed slot-1 checksum because all bytes past slot1+0xB0 are zero in this sample, so a checksum over any larger zero-padded window from that same start trivially reproduces the same sum). The large non-zero tail span observed at 0x361C..0x4008 (mirrored at 0x761C..0x8000) is the best structural candidate for this record's populated tail, but I could not confirm its exact start address or checksum boundary against this single sample. Confidence: HYPOTHESIS (size is CONFIRMED_STATIC from code; offset/checksum boundary is UNKNOWN).

4.6 Magic signature summary

No ASCII magic strings exist anywhere in the active save ranges (confirmed by the packet's own byte-level profiling: ascii_magic_strings: []). The closest analogue to a "magic" value is the global-header 4-byte payload 3D 52 2F 36 (offset 0x0004), which FUN_0803b108 compares against a fixed in-ROM constant (iRam0803b13c) to decide whether the whole save needs a factory reset — functionally a format/version tag, not a text signature. The specific expected constant value in ROM was not resolved in this extraction window.

6. Save Fuzzing & Counterfactual Verification Plan

No .ss emulator save states were provided in this packet (states/ is empty), so the following plan is written for the next round, to be run against the paired pre/post .ss states this project's harness requires for every .sav capture:

  1. Checksum-rejection boundary test. Flip a single bit anywhere in 0x0021–0x0B9F (inside the ranking table payload, away from the checksum field) without repairing the checksum at 0x001C. Predicted effect: on next boot, FUN_0803b108's equivalent reader for this record (unresolved stub func_0x0803b318) should detect the mismatch and the FUN_0803b250-based reset path should fire, restoring the table to its zeroed default — observable as the ranking/name UI reverting to blank entries. Mutate, then reload from the paired pre/post .ss states to compare RAM state before vs. after the detected corruption.
  2. Checksum-repaired mutation test (byte-exact plant). Recompute and rewrite the checksum at 0x001C after mutating one packed-name entry's 6 bytes (e.g. entry 0, 0x0020–0x0025) to a different 6-bit-packed ASCII string. Predicted effect: the record now passes validation, and if the UI reads this table for display (as hypothesized), the displayed name/initials at that table position should change — the first semantic confirmation of the ranking-table hypothesis.
  3. Slot flag-byte sweep. With slot 0's checksum repaired after each change, individually toggle each bit of 0x0BA4 (the +4 flag byte) and re-run. Predicted effect: since 3 of its bits are forced by FUN_0803b634 on every re-init, only bits outside those forced masks (bit values not touched by the 0xFE/0xF1/0x8F|0x10 sequence) should survive a reset — this will empirically pin down which bits are "live" settings vs. always-reset housekeeping bits, something static analysis alone cannot resolve.
  4. Fresh-vs-restore matched-duration control. Capture one .sav+paired .ss after a fresh, untouched boot (global header should be the "first valid" state) and a second after deliberately corrupting and letting the game auto-reset (FUN_0803ba04 path). Predicted effect: post-reset bytes at 0x0BC0/0x0C70/0x0CFC should read 01/01/05 identically to this sample (confirming these are reset-time constants, not gameplay-accumulated values) while the ranking table and the unresolved 0x2400 record should read all-zero (confirming they are not touched by the per-slot reset path, only by the full FUN_0803ba04 factory reset).
  5. 0x0D00 record size probe. Deliberately write non-zero bytes at increasing offsets past 0x0D00 (0x0D08, 0x0D20, 0x0D80, …) with a valid recomputed checksum at each candidate size, reload, and observe at which size the game's unresolved reader (func_0x0803b8e4) stops accepting the record as valid (i.e., starts resetting it) — this directly resolves the open "exact size" question in Section 4.4 without needing to recover _DAT_0803b8d8's literal value.
  6. 0x2400-record location probe. Write a small, easily-recognizable non-zero marker (e.g. repeating 0xAA) with a correct checksum at each of several candidate base addresses derived from Section 4.5 (starting with 0x1C08), reload, and check via RAM inspection at runtime (or via a second save-and-diff cycle) whether the marker survives FUN_0803b968's validation — this is the most direct way to resolve the still-unconfirmed location of the largest record in the save.
  7. Protocol negative — truncated/zero-length save. Load a .sav truncated to less than 0x8000 bytes (e.g. only the primary 16 KiB half present) and confirm the game either pads/rejects gracefully or triggers the full FUN_0803ba04 reset path, exercising the backup-fallback logic (FUN_0803b040) under a worst-case missing-backup condition.
