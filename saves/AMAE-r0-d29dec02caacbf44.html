Save Format Report — Super Mario Advance (USA, Europe) [AMAE]

Release key: AMAE-r0-d29dec02caacbf44 · ROM SHA-256: d29dec02caacbf449e2a93c6042258b0669542e102eb0e6fd0eb92a5411e0244

All findings below are derived exclusively from this workspace: the single .sav sample in saves/, the trace-guided Ghidra decompilation in ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, and standard public GBA hardware facts (EEPROM bus at 0x0D000000 via DMA3 0x040000D4, BIOS SWI numbers, EWRAM/IWRAM layout).

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The save media is a 512-byte / 4Kbit serial EEPROM accessed through DMA3 bit-serial I/O at 0x0D000000, addressed in 8-byte "sectors" (6-bit sector index, 0–63). This matches the declared EEPROM 4K media exactly (512 bytes = 64 sectors × 8 bytes).
  • An ASCII magic signature "EAMA" lives at file offset 0x04–0x07.
  • A 16-bit little-endian checksum at file offset 0x02–0x03 is the exact sum-of-bytes (mod 0x10000) of the 16-byte block at offset 0x10–0x1F. This was independently recomputed in Python against the real .sav bytes and matches exactly (0x00A8 stored == 0x00A8 computed).
  • The save format implements primary/backup mirrored redundancy: the 16-byte block at 0x10–0x1F is byte-for-byte duplicated at 0x98–0xA7, confirmed identical in the sample.
  • The low-level EEPROM read/write/verify driver functions and the mid-level sector read/write-verify wrapper functions and the top-level boot-time validator/repair orchestrator were all traced and are documented in Section 3.

What remains open / unverified (only one sample, most of the file is still zero-filled / never written):

  • The semantic meaning of the two non-zero 16-bit values in the checksummed block (0x4E20=20000 and 0x2710=10000 at offsets 0x12–0x13/0x16–0x17) is unknown — clean-room rules forbid guessing from any external wiki/decomp.
  • Three further 40-byte mirrored groups (sectors 4–8/21–25, 9–13/26–30, 14–18/31–35, i.e. file ranges 0x20–0x47/0xA8–0xCF, 0x48–0x6F/0xD0–0xF7, 0x70–0x97/0xF8–0x11F) exist in the code (same read/verify/checksum pattern, same mirrored-pair architecture) but are entirely zero in this sample, so their individual per-group checksum storage offsets could not be byte-verified — only structurally inferred from the decompiled control flow.
  • Region 0x120–0x1FF is raw erased EEPROM (0xFF) and is never addressed by any sector index reachable from the traced code — it is unused/unformatted space, not a corrupted field.

Redundancy/selection rule (traced in FUN_08026c30, the boot-time validator): for each mirrored group, both copies are read and a live sum-of-bytes checksum is computed for each. If the two live sums disagree, whichever copy's live sum still matches the group's previously-accepted/stored checksum is treated as authoritative and is copied over the stale copy (write+verify via FUN_08026a30); if neither copy's checksum is self-consistent, an error bitmask (bStack_15) records a hard failure for that group and an external fatal/error-report call (func_0x080287f8) is made instead of silently continuing. This is a classic "self-healing mirrored pair" scheme, not a simple single-slot-with-generation-counter scheme — no sequence/generation counter field was found.

3. Save Writer, Reader & Caller-Chain Architecture

Methodology note (important, clean-room evidence caveat)

ghidra/callgraph.json is restricted to the 2-hop neighborhood around the two MMIO seed functions (0x080b6ac0, 0x080b6b78) and reports "callers": [] for both, and only one caller apiece for their shared helper 0x080b6a40. This under-reports the true caller graph. ghidra/decompiled.c contains 90 functions, including the real mid-level sector read/write wrappers and the top-level boot-time validator, which do call these MMIO seeds (via the func_0x08xxxxxx call syntax used for calls outside the currently-decompiling function's immediate block). The full chain below was reconstructed by manually grepping decompiled.c for every func_0x080b6ac0, func_0x080b6b78, func_0x080b6c5c call site and reading the enclosing function bodies — this is the only way the true architecture becomes visible; callgraph.json alone would have hidden it.

Layer 1 — Raw EEPROM bus driver (hardware, 0x0D000000 / DMA3)

AddrRoleNotes
0x080b6a40DMA3 transfer primitive. Programs the DMA3 source/dest/count-and-control registers (via unnamed MMIO-shadow globals), sets the "start" bit (0x80000000), then busy-waits on the DMA3 control register's busy bit (0x8000).Generic GBA hardware driver — this is the standard CPU-driven bit-serial DMA3 EEPROM handshake, not game-specific.
0x080b6ac0EEPROM READ, one 8-byte sector. Bounds-checks param_1 (sector index) against a device-size table, bit-packs the 6-bit address into a request bitstream, issues it via two FUN_080b6a40 calls (request burst of 0x44=68 bits), then unpacks the 64-bit response into 4×u16 words at param_2. Returns 0 on success.DMA3 request opcode embeds 0x30000 (read command).
0x080b6b78EEPROM WRITE, one 8-byte sector. Same address bit-packing, then packs 64 data bits (param_2, 4×u16) ahead of the address bits, issues a 0x430000-tagged burst, then busy-waits on bit 0 of the EEPROM data line (uRam0d000000 & 1) for write-complete, bracketed by FUN_080b6998/FUN_080b69fc (see below).DMA3 request opcode embeds 0x430000 (write command) — differs from read only in the top command bits, as expected for 4Kbit-EEPROM protocol.
0x080b6c5cEEPROM VERIFY = read-back + compare. Calls FUN_080b6ac0 into a 4-word stack buffer, then compares all 4 words against the caller-supplied expected buffer (param_2); returns 0x8000 on any mismatch, else 0.Used exclusively as the "verify after write" step.

0x080b6960Device/bank size-table probe: validates param_1 ∈ [0,3], looks up a size entry.Used only by the size-detect gate below, not per-sector I/O.

Layer 3 — Boot-time save validator / repairer (top-level orchestrator)

FUN_08026c30 is the entry point that ties everything together at boot/load time:

  1. Calls FUN_0802687c (size-detect guard).
  2. Reads the header sector-pair (FUN_08026934(0, …, 2) → bytes 0x00–0x0F).
  3. If the header is blank (first boot), performs an initial populate-and-write sequence for a small RAM record (16-byte sum accumulated, RTC-looking fields, not yet correlated to a stored file offset in this sample) and bails to the fatal handler on failure.
  4. For Group A (sector 2/sector 0x13, each count 2): reads both copies via FUN_08026934, sums 16 bytes of each with a running u16 accumulator (sStack_1e/sStack_1c), compares each sum against the previously-cached expected checksum; whichever copy disagrees gets rewritten from the other via FUN_08026a30. If neither live sum matches the cached value and the two copies also disagree with each other, individual field-level checksums are taken (same sum-of-16-bytes algorithm) and a bitmask (bStack_15) tracks which half failed; on unrecoverable disagreement it calls func_0x080287f8 (fatal/alert handler) and aborts via goto SUB_08027d8c.
  5. Repeats the identical read→sum→compare→repair pattern for Group B (sector 4/sector 0x15, count 5, 40-byte sum loop 0x28 iterations), Group C (sector 9/sector 0x1a, count 5), and Group D (sector 0xe/sector 0x1f, count 5) — each accumulating into the shared error bitmask bStack_15 at successively higher bit positions (0x04/0x08, 0x10/0x20, 0x40/0x80).
  6. If the header itself needed repair (cStack_1f != 0), rewrites the header sector-pair via FUN_08026a30(0, …, 2).
  7. If bStack_15 != 0 (any group hard-failed), stores the bitmask into a RAM status byte and calls func_0x080287f8.

How each caller mutates the in-RAM save struct before flushing: every write path above only ever calls FUN_08026a30, and the data buffer passed to it is always a RAM pointer (uRam08027xxx family) that was just populated either by (a) the sibling "good" copy's read buffer (straight copy-repair, no field edits) or (b) a locally-summed/zeroed scratch struct during first-boot initialization. No other gameplay code path outside this file was found to directly call the write-verify layer (Layer 2) with the two-hop trace available — meaning at the trace depth available in this workspace, in-RAM save-field writes by day-to-day gameplay logic were not captured; only the boot-time integrity-check/repair path is proven to reach the hardware writer.

Layer 4 — Per-slot runtime loader

AddrRoleNotes
0x08028190Loads one of the mirrored 40-byte groups into live RAM at runtime (sector index taken from a lookup table indexed by param_1), sums 40 bytes (0x28 iterations) and compares against a stored checksum; on mismatch falls back to the backup-copy sector index (same lookup table, offset +3) and re-validates; calls func_0x08028764 (fatal handler) if both fail.Distinct from the boot-time validator (FUN_08026c30) — this looks like an on-demand "activate slot N" loader (e.g. per file-select or per-level), using the same sum-of-bytes checksum algorithm.

Functions seen but confirmed not save-related

FUN_0804261c calls func_0x080b68a8, which is BIOS SWI 0x0F (ObjAffineSet) — this is sprite affine-matrix math, unrelated to save I/O, and is excluded from the field map despite being near the MMIO-seed address range in the ROM.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic signature

  • Offset: 0x04–0x07
  • Bytes: 45 41 4D 41
  • ASCII: "EAMA"
  • Verified in code: Yes — this is the literal content read into the header sector-pair that FUN_08026c30 treats as the "is this save blank or populated" gate.
  • Verified in .sav: Yes — present verbatim in saves/cap-00-future-0.sav.

Checksum — Group A (CONFIRMED_VERIFIED)

  • Algorithm: sum-of-bytes, 16-bit accumulator, no special seed, no carry-out wraparound beyond mod 0x10000 (checksum = (Σ byte_i) mod 0x10000), little-endian storage.
  • Covered range: 0x10–0x1F (16 bytes, Group A primary copy).
  • Stored offset: 0x02–0x03 (2 bytes, LE).
  • Decompiled proof: ghidra/decompiled.c lines ~1869–1874 (FUN_08026c30): sStack_1e = sStack_1e + (ushort)*(byte *)(iRam08027258 + i) looped 16 times (bStack_20 < 0x10), then compared against *(short *)(iRam080272b0 + 4).
  • Python verification (run against the real file in this workspace):
data = open("saves/cap-00-future-0.sav","rb").read()
block = data[0x10:0x20]                 # 16-byte Group A primary copy
checksum = sum(block) & 0xFFFF          # sum-of-bytes mod 0x10000
stored   = data[0x02] | (data[0x03] << 8)   # u16 LE at 0x02-0x03

>>> block.hex()
'00004e20000027100000000000000003'[:32]   # 00 00 4e 20 00 00 27 10 00 00 00 00 00 00 00 03
>>> hex(checksum)
'0xa8'
>>> hex(stored)
'0xa8'
>>> checksum == stored
True
  • Mirror consistency (also run against the real file): data[0x10:0x20] == data[0x98:0xa8] → True. Group A's primary copy (sectors 2–3) and backup copy (sectors 19–20) are byte-for-byte identical in this sample.

Checksums — Groups B / C / D (CONFIRMED_STATIC only)

The identical read→sum(40 bytes)→compare→repair pattern is used for Group B (covered 0x20–0x47, compared against a cached field at a RAM offset iRam080276ac+6), Group C (covered 0x48–0x6F, RAM offset +8), and Group D (covered 0x70–0x97, RAM offset +10). The algorithm (sum-of-bytes mod 0x10000) is proven identical by code inspection, but the exact in-file byte offset of each group's stored checksum could not be verified because every byte in these ranges is 0x00 in the only available sample — a zero sum trivially equals a zero stored checksum, so this sample cannot distinguish "checksum field correctly at offset X" from "checksum field elsewhere, both coincidentally zero." A second sample with Groups B/C/D populated is required to pin down their stored offsets with the same confidence as Group A.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of saves/cap-00-future-0.sav, reloaded from a paired pre-save .ss state per the project's mandatory paired-state policy, and observed for the predicted effect. (No .ss states are present in this particular states/ directory for this legacy checkpoint cohort — this plan should be re-run once paired states exist for this release.)

  1. Checksum-break test (highest-value, directly falsifies/confirms §4).
  • Mutation: flip any single bit in 0x10–0x1F (e.g. 0x12 ^= 0x01) without updating 0x02–0x03.
  • Requires checksum repair: no (intentionally left broken).
  • Predicted effect: on next boot, FUN_08026c30's live sum of 0x10–0x1F no longer matches stored 0x02–0x03; since the backup copy at 0x98–0xA7 is untouched and still matches, the engine should auto-repair the primary copy from the backup (overwrite 0x10-0x1F back to the backup's bytes) rather than crash or report fatal corruption. Observable via re-reading the .sav after the game writes back, and via the RAM status/error bitmask if inspectable in a debugger.
  1. Dual-corruption test (fatal-path confirmation).
  • Mutation: break the checksum relationship in both copies simultaneously — e.g. flip a bit in 0x12 (primary) AND a different bit in 0x9A (backup), such that neither 16-byte sum matches 0x02-0x03 and the two copies also disagree with each other.
  • Requires checksum repair: no.
  • Predicted effect: bStack_15 error bitmask gets a Group-A failure bit set, func_0x080287f8 (fatal/alert handler) is invoked. Observable as an in-game error/corruption message or forced "save deleted/reset" behavior, distinct from test 1's silent auto-heal.
  1. Checksum-repair round-trip test.
  • Mutation: change 0x12–0x13 to a new value, then recompute and write the correct 16-bit sum-of-bytes into 0x02–0x03 using the Python formula in §4, and also update the backup copy at 0x9A–0x9B + its own group checksum relationship to match (keep primary and backup identical).
  • Requires checksum repair: yes (this is the repair step).
  • Predicted effect: the engine accepts the save as valid with no repair/fatal path taken, and the new value should be observable in-game if 0x12-0x13 controls any visible counter/threshold — this is also the only safe way to probe the semantic meaning of 0x12-0x13/0x16-0x17 without violating the "don't guess" rule: change it, reload, and observe what differs.
  1. Magic-byte corruption (blank-save-detection test).
  • Mutation: zero out 0x04–0x07 (destroy "EAMA").
  • Requires checksum repair: no.
  • Predicted effect: FUN_08026c30's blank-save gate should treat the file as uninitialized and re-run its first-boot populate-and-write path, producing a freshly zeroed/defaulted header + Group A on next save, effectively resetting progress tied to that block.
  1. Populate-and-verify test for Groups B/C/D (resolves the open §4 gap).
  • Action: find or create a save state where gameplay actually populates 0x20–0x11F (e.g. further into the game than this capture), capture a fresh .sav, and re-run the Python checksum search (sum-of-16/40-bytes mod 0x10000 against every plausible 2-byte field near each group) to pin down the exact stored-checksum offsets for Groups B, C, D the same way Group A was confirmed here.
  1. Unused-region boundary test.
  • Mutation: write non-0xFF garbage into 0x120–0x1FF.
  • Requires checksum repair: no.
  • Predicted effect: no observable effect at all, since no traced sector index ever reaches this region — this is a negative/falsification control to confirm the region truly is dead space and not a currently-undiscovered fifth group.
