1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The save medium is EEPROM, accessed through a DMA3 serial-bitstream driver at 0x0D000000 (standard GBA EEPROM protocol: read/write opcode bits shifted out via 16-bit DMA transfers), not SRAM/Flash. The driver functions, their 8-byte block looping wrappers, and their unique call sites were fully traced.
  • The save image is built from a single 476-byte (0x1DC) primary structure that is read wholesale on load and written wholesale (with per-8-byte-block write+verify) on save. This constant appears identically in both the loader and the writer and matches the packet's independently-measured mutated_byte_count: 476 almost exactly (472 contiguous bytes 0x000-0x1D7 + a disjoint 4-byte span 0x1DC-0x1DF, see §4).
  • A 10-entry record table (stride 0x2C = 44 bytes) is built/reset by a dedicated routine, with two further sub-fields per record: a packed 2-bit array (52 slots across 13 bytes) and a mixed-radix packed byte (three 0–6 values packed as a + b*6 + c*36). This exactly matches the periodicity (~0x28–0x30) that the packet's own active_ranges_hex scan already observed empirically in the raw bytes.
  • A 5-entry, 4-byte-stride "slot" table at struct offset 0x1C8 is written by a dedicated routine, each entry encoded as base_value*10 + (index % 10). This matches the exact byte offsets (0x1C8, 0x1CC, 0x1D0, 0x1D4, 0x1D8) the packet's hexdump shows, and the encoding model is independently confirmed against the real .sav bytes (see §4).
  • The candidate checksum span the packet flagged (0x1DC-0x1DF) is outside the 476-byte block that the traced loader reads and the traced writer writes. This is a concrete, code-proven explanation for why the packet's own mutation probe at that offset found integrity_check_confirmed: false / no revert / no rewrite — the mutated byte is simply never touched by the only read/write path this trace covers.

What remains open / unproven:

  • The exact absolute file offset of the 10-record table's start, and the per-record internal byte layout beyond the two sub-fields above, because the record-array base pointer is an unresolved _DAT_* RAM symbol in the decompilation (no memory map was supplied).
  • Whether struct offset 0x08 (a 4-byte field written from a routine that sums a 116-entry ROM table, and checked on load against the same sum) is a true per-save corruption checksum or a build/version compatibility stamp — we cannot evaluate the ROM constant table contents from this workspace, so the "formula" is proven in code but its expected value is not independently verifiable from the .sav bytes alone.
  • Whether the apparent magic string "imanoK" (bytes 0x02-0x07, which read backward as "Konami") is actually enforced by the traced strcmp-style check, because that check is called with a pointer to byte offset 0 of the struct (which is 0x00 0x00), not offset 2 — see §4 for the exact ambiguity and why it may make the check a no-op in practice.
  • All concrete field meanings (what the 10 records and 5 slots represent in gameplay terms — e.g. per-course best times/scores) are not asserted; only their mechanical shape (offsets, stride, encoding) is backed by code, and the two available .sav samples look like synthetic/mutated test fixtures (classification: multi_state_mutated_save) rather than organic gameplay saves, so no field has been observed cycling through plausible real gameplay values.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Hardware I/O driver layer (EEPROM, DMA3 bitstream)

All of these are in ghidra/save_related_functions.c, the pre-extracted MMIO seed set, cross-referenced against ghidra/decompiled.c for their real call sites.

3.3 Save-level reader/validator and writer, and their callers

Caller-chain mapping method: ghidra/callgraph.json gives static caller/callee edges for every address; I walked from the four MMIO seeds outward (1–2 hops) to find FUN_08002b7c/FUN_08002be4, then from those to their sole statically-known callers, FUN_08018bd4 and FUN_08018c2c. I then grepped decompiled.c directly for every remaining literal/func_0x… reference to each address to catch any indirect-call site the static graph might have missed (none were found beyond the graph's edges). Neither FUN_08018bd4 nor FUN_08018c2c has a statically resolved caller in callgraph.json — both are reached only through UNRECOVERED_JUMPTABLE indirect calls (Ghidra's marker for an unrecovered function-pointer dispatch), the same pattern seen on every function in this trace set. This is consistent with a save task being invoked through an engine-level event/task dispatcher rather than a direct call, but it means the in-game trigger condition for load/save (title screen, pause menu, end-of-run, etc.) could not be identified from this workspace — only the mechanics of the load/save routines themselves.

FUN_08018bd4 — Save LOADER / validator

If either sanity check fails, FUN_08018ae0 overwrites that same struct in place with hardcoded defaults (it does not immediately write that default struct back to EEPROM — the next real FUN_08018c2c call will persist it).

This means the specific call site(s) that update the struct during actual gameplay (scoring a trick, finishing a run, etc.) were not found in this 154-function trace — only the "rebuild + flush" path was. The per-record clamps (max 99, max 5/6) are the only concrete evidence of what ranges the real fields can take.

3.4 Checksum/magic comparison helpers

AddrRole
0x08018b98 (FUN_08018b98)Byte-for-byte compare loop that returns 1 on first mismatch, 0 if it runs to a matching '\0' terminator — i.e., this is a plain strcmp, not a hash/CRC.
0x08018bb4 (FUN_08018bb4)Sums 116 (0x74) consecutive 4-byte signed integers starting at a fixed ROM/RAM address _DAT_08018bd0 and returns the 32-bit sum. This is not a function of the save bytes at all — it sums a constant table, so (barring undiscovered aliasing) it produces the same value every time it's called in a given ROM build. It therefore behaves as a build/content version stamp, compared against the previously-stored stamp at struct +0x08, rather than a classic per-save corruption checksum.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 The "imanoK" / "Konami" string (struct offset 0x02–0x07)

cap-01-future-1.sav bytes 0x00–0x07: 00 00 69 6d 61 6e 6f 4b → ASCII "\x00\x00imanoK". "imanoK" read backward spells "Konami" — purely a byte-level observation about this sample, stated without importing any external research.

The loader's only string-shaped check is FUN_08018b98(dest, _DAT_08018c28), called with dest = the exact same pointer used as the destination of the 476-byte bulk read (i.e., struct offset 0, not offset 2). Two readings are possible from the static trace alone, and the workspace does not contain enough information to pick one with certainty:

  1. If _DAT_08018c28 (the ROM-resident expected string) also begins with 0x00: the strcmp loop's first comparison (*param_1 != *param_2) succeeds trivially, and its second check (*param_1 == '\0') is also immediately true, so the function returns 0 ("match") without ever inspecting bytes 2–7. Under this reading, the "imanoK" bytes are present in the struct but are not actually enforced as a magic signature by this check — any save with a leading 0x00 byte passes.
  2. **If _DAT_08018c28 resolves to a string that does not start with 0x00** (e.g., the pointer is bound at link time to the literal "imanoK" and the two leading 0x00 bytes are a separate 2-byte field that merely precedes it in the struct, with the strcmp pointer arithmetic not shown in this trace being dest+2): the check would be a real magic-string gate.

Confidence: CONFIRMED_STATIC for the code shape (a plain strcmp), HYPOTHESIS for which reading is correct. We could not resolve _DAT_08018c28's pointee bytes from this workspace (it is an external/ROM data symbol with no accompanying .rodata dump), so Python verification against the .sav bytes can only confirm what is stored, not what the ROM expects:

stored bytes[0:8] = 00 00 69 6d 61 6e 6f 4b

4.2 The struct+0x08 field — checksum/version stamp

  • Algorithm: sum32(table[0..115]) where table is a fixed, 116-entry, 4-byte-signed-int ROM array at address _DAT_08018bd0 (FUN_08018bb4). This is a sum32, not XOR/CRC, with no explicit endianness swap (native ARM little-endian accumulation).
  • Covered range: the ROM constant table — not any range of the save file itself. This is the most important and most falsifiable claim in this report: the "checksum" the loader checks is independent of what's in EEPROM except at the single comparison point.
  • Stored offset: struct byte offset 0x08, size 4 bytes, little-endian (confirmed by *(int*)(struct+8) = FUN_08018bb4() in the writer and *(int*)(iVar1+8) != FUN_08018bb4() in the loader — both use a 4-byte int dereference at +8).
  • Decompiled C proof: ghidra/decompiled.c lines 2999-3021 (FUN_08018bb4), line 3045 (loader comparison), line 3126-3127 (writer store).
  • Python verification against the real .sav:
stored value @ struct+0x08 (cap-01-future-1.sav) = 1  (bytes: 01 00 00 00, little-endian)

We cannot independently recompute the expected sum, because the 116-entry ROM table (_DAT_08018bd0) lives in ROM code/data this workspace does not expose as raw bytes (only as an unresolved symbol in the decompilation). Confidence: CONFIRMED_STATIC for the formula and storage location; UNKNOWN for whether 1 is a value that formula can actually produce — this is explicitly flagged as an open question rather than asserted either way.

4.3 The packet's flagged candidate span 0x1DC–0x1DF

  • Finding: this span is proven, by direct constant-matching against the decompiled code, to lie outside both the 476-byte (0x1DC) read performed by FUN_08018bd4 and the 476-byte write performed by FUN_08018c2c. Both operations cover byte range [0x000, 0x1DC) — i.e., bytes 0x000–0x1DB inclusive — and neither touches 0x1DC–0x1DF.
  • Python verification:
>>> len(open("saves/cap-01-future-1.sav","rb").read()[0x0:0x1DC])

  • This is a code-grounded explanation for the packet's own cold-reload mutation probe result (probe_offset_hex: 0x1DC, integrity_check_confirmed: false, reverted_to_blank_on_mutation: false, save_rewritten_after_mutation: false): mutating a byte at 0x1DC cannot trigger the loader's integrity-failure path (which can only fire from the magic compare or the +0x08 stamp compare, both inside [0,0x1DC)), and cannot be clobbered by the writer's next flush (which only touches [0,0x1DC) too) — both observed behaviors are exactly what the traced code predicts for a mutation at that specific offset. Confidence: CONFIRMED_STATIC (the offset arithmetic is exact and literal-for-literal) combined with CONFIRMED_VERIFIED for the packet's independently-collected runtime behavior matching this prediction.
  • What 0x1DC–0x1DF (and the rest of the 0x1D8–0x1FF tail) actually is remains UNKNOWN — it is read by neither of the two traced I/O paths, so nothing in this workspace writes or validates it either. It may be dead EEPROM space, or written by a code path outside the 154-function trace.
