1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (static decompilation + cross-checked control flow, consistent with the observed .sav byte layout):

  • The title uses the GBA SDK's generic 4-backend save library (FUN_080302e4 selects backend type 0–3; both save call sites pass 3, i.e. EEPROM), backed by a classic EEPROM bit-serial DMA3 driver (FUN_08030468/FUN_08030518/FUN_080305f4/FUN_080303e8, guarded by IME-style critical-section helpers FUN_0803031c/FUN_080303a4).
  • There is exactly one save record in the traced code: a 24-byte (0x18) structure written by FUN_0800dce0 and read by FUN_0800dddc. This matches the Save Profile Summary's single active range 0x0000–0x0017 (24 mutated bytes) out of the 512-byte capture window.
  • The first 2 bytes are a checksum field (computed by FUN_0800d9cc, a byte-wise sum+XOR accumulator) covering the remaining 22 bytes (offsets 0x02–0x17), checked against a fresh recomputation on load before the rest of the record is trusted.
  • Offset 0x02 is a second gate value, compared on load against a fixed RAM constant; offset 0x04 is an index fed into a base + index*8 table-selector call; offsets 0x08–0x0C are a raw 5-byte array mirrored byte-for-byte between save and RAM; offset 0x10 is a bit-packed byte holding four 2-bit status codes that are unpacked through a reverse lookup table on load.

What remains open / unverified:

  • The exact checksum algorithm, while fully decompiled, could NOT be reproduced against the one available non-blank .sav sample (computed 0xA5 vs. stored 0x02 — see §4). Only one real save sample exists in this workspace (the other is an all-0xFF blank), so there is no second data point to disambiguate a transcription/attribution error from a genuinely different algorithm. This caps the field-map's checksum confidence at CONFIRMED_STATIC, not CONFIRMED_VERIFIED.
  • Byte offset 0x17 (the last byte of the 24-byte record) is 0xD2 in the real sample but is never written by the only traced writer function FUN_0800dce0 (which memsets the full 24 bytes to 0 and then writes only offsets 0x00–0x10). This is flagged as an unresolved anomaly (§5, §6) rather than silently reconciled.
  • Semantic meaning of individual fields (what the 8–12 byte array or the 4 packed status codes represent in gameplay terms) is not derivable from this workspace alone — RAM mirror addresses are unresolved ROM literal-pool pointers (Ghidra could not resolve the pointed-to EWRAM/IWRAM symbol names), so all semantic labels below are explicitly marked HYPOTHESIS.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K-class device (SDK tag EEPROM_V122@275928), accessed through the generic AGB-style save-library dispatcher FUN_080302e4(type, &descriptor) with type bounds-checked to 0..3 (4 backend types: almost certainly SRAM / Flash 64K / Flash 128K / EEPROM, selected per-title at link time). Both save call sites in this ROM hard-code type = 3.
  • Capture window: 512 bytes retained per the capture harness; only the first 24 bytes (0x0000–0x0017) are ever touched by the traced save/load code. The remaining 488 bytes stay at the EEPROM's erased/unprogrammed fill value 0xFF in both samples — there is no evidence in the traced code of any second record, slot, or backup copy living elsewhere in the 512-byte window.
  • Slots/copies: One logical record, no redundancy, no mirroring, no generation/sequence counter beyond the single checksum+gate pair at offsets 0x00/0x02. There is no "select newest of N copies" logic anywhere in the traced call graph — FUN_0800dce0/FUN_0800dddc always operate at absolute EEPROM offset 0.
  • Selection rule: N/A (single slot). Validity rule on load is: stored_checksum == recompute(bytes[2:24]) AND bytes[2:4] == <fixed RAM constant> (FUN_0800dddc, see §3/§4). If either check fails, the loader takes the "fail" path (func_0x08024290(); return 0;) without touching any gameplay state.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Hardware I/O driver layer (EEPROM, bit-serial via DMA3)

All addresses below were extracted from ghidra/save_related_functions.c (the pre-seeded MMIO functions) and cross-referenced in ghidra/decompiled.c / ghidra/callgraph.json.

AddrRoleNotes
0x080303e8DMA3 transfer + busy-wait helperSets up a transfer descriptor (param_1=source, param_2=dest, param_3=count\|0x80000000 enable bit) at the pointer held in _DAT_08030460 (the DMA3 control register region, 0x040000D4+), then polls bit 0x8000 of the following halfword until clear. This is the generic "kick DMA3 and wait" primitive shared by both read and write paths. Wrapped by an IME-style disable/enable pair (0x0803031c saves+disables, 0x080303a4 restores) so the bit-banged EEPROM protocol runs with interrupts masked. Callers: 0x08030468, 0x08030518.
0x08030468EEPROM read primitiveSerializes a 14-bit DMA-style read request (address param_1 shifted into a bit-stream buffer), issues it via two 0x080303e8 DMA3 calls to 0x0D000000 (EEPROM data port), then deserializes 64 bits read back from uRam0d000000 into 4×16-bit words written to param_2 (destination buffer), MSB-first per the inner uVar4 = uVar4<<1 \| bit unpack loop. Reads exactly one 8-byte EEPROM "page". Callers: 0x080305f4.
0x08030518EEPROM write primitiveSerializes address+64-bit data (param_2, 4×16-bit words) into a 1-prefixed write-command bit-stream, issues it via 0x080303e8 to 0x0D000000, then polls the EEPROM busy flag (uRam0d000000 & 1) with a timeout guarded by _DAT_080305ec, and calls the IME-restore helper 0x080303a4 at the end. Writes exactly one 8-byte page. No direct static caller recorded in callgraph.json (likely reached through an indirect/jump-table call not resolved statically), but is the only function in the corpus that performs a 64-bit EEPROM write sequence, so its role is unambiguous from the decompiled body itself.
0x080305f4EEPROM write-verifyCalls 0x08030468 to read back the page just written at param_1 and compares all 4 words against the expected data at param_2; returns 0 on match, 0x8000 on mismatch. This is the read-after-write integrity check wrapped around every write.
0x0803031c / 0x080303a4IME-style critical-section enter/exitSave/clear and restore an interrupt-enable-like global around the EEPROM bit-banging sequence inside 0x08030518.

3.2 Block-level driver (device-agnostic, selects EEPROM backend)

3.3 Top-level record Save/Load (the actual game-facing API)

Writer — 0x0800dce0 ("WriteSaveRecord")

puVar2 = _DAT_0800dd68                       // 24-byte RAM staging buffer
memset(puVar2, 0, 0x18)                      // func_0x080386e4 == memset
puVar2[offset 0x02..0x03] = *_DAT_0800dd6c   // u16 "gate/version" value
puVar2[offset 0x04..0x05] = *_DAT_0800dd70   // u16 index/selector
puVar2[offset 0x06]       = *_DAT_0800dd74   // u8
puVar2[offset 0x07]       = *_DAT_0800dd78   // u8
puVar2[offset 0x08..0x0C] = memcpy(5 bytes from _DAT_0800dd88)  // raw 5-byte array
puVar2[offset 0x0D]       = *_DAT_0800dd80   // u8
puVar2[offset 0x0E]       = *_DAT_0800dd84   // u8
puVar2[offset 0x0F]       = *_DAT_0800dd7c   // u8
puVar2[offset 0x10]       = pack4x2bit(_DAT_0800dd8c[0..3])  // status byte
uVar4 = FUN_0800d9cc(puVar2+2, 0x16)         // checksum over bytes [2,24)
puVar2[offset 0x00..0x01] = uVar4
FUN_08003730(0, 0x18)                        // write+verify to EEPROM

Reader — 0x0800dddc ("ReadSaveRecord")

psVar1 = _DAT_0800de88                       // 24-byte RAM staging buffer
FUN_08003798(0, 0x18)                        // read from EEPROM into psVar1
sVar4 = FUN_0800d9cc(psVar1+2, 0x16)         // recompute checksum over bytes [2,24)
if (sVar4 == psVar1[offset 0x00..0x01]) {
    if (psVar1[offset 0x02..0x03] == <fixed RAM constant uRam0800de8c>) {
        FUN_080032b0(psVar1[offset 0x04..0x05])         // index -> base+index*8 selector
        *puRam0800de90 = psVar1[offset 0x06]
        func_0x08002978(psVar1[offset 0x07])            // byte passed to a config/setter routine
        *puRam0800de94 = psVar1[offset 0x0F]
        *puRam0800de98 = psVar1[offset 0x0D]
        *puRam0800de9c = psVar1[offset 0x0E]
        unpack4x2bit(psVar1[offset 0x10]) -> 4x u16 lookup -> RAM array iRam0800dea0
        memcpy(iRam0800dea8, psVar1+8, 5)               // raw 5-byte array restored
        return 1  // success
    }
}
return 0  // checksum or gate mismatch -> abort, no state touched

How each caller mutates the in-RAM struct before flushing: both 0x0800dce0 and 0x0800dddc operate on a dedicated 24-byte scratch buffer (_DAT_0800dd68 for write, _DAT_0800de88 for read — two distinct ROM literal-pool addresses, so likely two separate fixed RAM buffers rather than one shared one, though this cannot be confirmed without resolving the literal-pool targets). The writer populates every field from already-live gameplay RAM globals (_DAT_0800dd6c.._DAT_0800dd8c) immediately before computing the checksum and flushing — i.e., the struct is built fresh on every save call rather than being incrementally maintained. The reader does the inverse: it only writes gameplay RAM (puRam0800de90..iRam0800dea8, plus a call into 0x080032b0 and func_0x08002978) after both the checksum and the offset-0x02 gate value pass, so a corrupt/foreign EEPROM image cannot partially corrupt live state.

All callers found: callgraph.json records no static callers for 0x0800dce0 or 0x0800dddc (their callers are reached by an indirect/jump-table call that Ghidra could not statically resolve — consistent with the "UNRECOVERED_JUMPTABLE" warnings throughout the surrounding functions and the notion of a save/load menu dispatch table). No other function in the 181-function trace references the EEPROM-type-3 block driver (0x08003730/0x08003798) or the 24-byte staging buffers, so within this workspace's trace coverage this is the single, exclusive save/load path for the title — there is no evidence of a second record format or an alternate writer.

4. Magic Signatures & Checksum / Integrity Algorithm

No fixed ASCII/byte magic signature exists in the traced code — ascii_magic_strings in the Save Profile Summary is empty, and neither 0x0800dce0 nor 0x0800dddc compare against a literal byte string. The closest thing to a signature is the offset-0x02 gate value, which is a 16-bit value compared against a fixed RAM constant (uRam0800de8c) rather than a compile-time ROM literal, so its expected value cannot be read directly out of the decompiled code.

Checksum algorithm — decompiled from FUN_0800d9cc(param_1, param_2):

uVar2 = param_2 - 1;        // param_2 = 0x16 (22) at both call sites -> uVar2 = 21
iVar4 = 0;                  // carry
pb = param_1 + param_2 - 2; // last-1 byte of the covered range
uVar3 = uVar2;
do {
    uVar2 = uVar2 + buf[pb] + iVar4;
    iVar4 = uVar2 >> 8;                 // carry out of the add
    uVar2 = (uVar2 & 0xff) ^ buf[pb+1]; // XOR with the *next* byte, then truncate
    pb -= 1;
    uVar3 -= 1;
} while (uVar3 > 0);
return (short)uVar2;         // single byte 0-255, stored as u16 with high byte 0

This is a custom byte-wise sum+XOR accumulator with carry propagation, run backwards from the high end of the covered range toward the low end, called as FUN_0800d9cc(struct+2, 0x16) — i.e. it is declared to cover bytes [0x02, 0x18) (22 bytes, offsets 0x02–0x17 inclusive), stored at struct[0x00..0x01] (high byte always 0 given the algorithm's &0xff truncation).

Python verification against the real .sav sample (saves/cap-01-future-1.sav):

buf[0:24] = 02 00 00 01 01 29 00 ee 00 00 00 2d 32 28 1e 23 00 00 00 00 00 00 00 d2
stored checksum (bytes 0-1, LE)      = 0x0002
recomputed via FUN_0800d9cc(buf+2,0x16) = 0x00A5
MATCH: False

Script and trace (reproduced verbatim):

data = open('saves/cap-01-future-1.sav','rb').read()
buf = data[:24]
param2 = 0x16
start = 2
uVar2 = param2 - 1          # 21
iVar4 = 0
pb = start + param2 - 2     # 22
uVar3 = uVar2
while True:
    uVar2 = uVar2 + buf[pb] + iVar4
    iVar4 = uVar2 >> 8
    uVar2 = (uVar2 & 0xff) ^ buf[pb+1]
    pb -= 1
    uVar3 -= 1
    if not (uVar3 > 0):
        break
# uVar2 == 0xa5
# buf[0], buf[1] == 0x02, 0x00  -> stored == 0x0002

Result: the recomputed checksum (0xA5) does NOT match the stored value (0x02). A brute-force sweep over every (start, length) sub-range of the 24-byte record (both the traced backward direction and a forward variant) found no sub-range reproducing 0x0002 other than degenerate near-all-zero ranges unrelated to the actual call site's fixed arguments (struct+2, 0x16). Plain sum8/xor8 over [2:24) (0xB3/0x1F) also do not match.

Root-cause hypothesis (not provable from this workspace): offset 0x17 (the very last byte of the record, value 0xD2) is covered by the checksum's declared range but is never written by the only writer function traced (0x0800dce0 writes only offsets 0x00–0x10; the preceding memset(puVar2,0,0x18) would leave it 0x00). If the checksum was originally computed when offset 0x17 was 0x00 (as the writer's own logic implies it must have been at that moment) and the captured EEPROM byte at 0x17 was mutated afterward by some other, untraced code path, the mismatch would be fully explained. This cannot be confirmed with only one non-blank sample in this workspace — see §6 (open questions / fuzzing plan).

Confidence: checksum presence, storage offset, and covered range: CONFIRMED_STATIC (clearly decompiled, used symmetrically by both writer and reader). Exact algorithm correctness against real data: unverified (HYPOTHESIS) — flagged, not concealed.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss emulator save states are present in this workspace (states/ is empty for this legacy checkpoint cohort), so all mutation targets below are specified as offset/value plans to run against a freshly captured gameplay session with paired pre/post .ss states, per the standing instruction that every .sav capture must have paired save states for save-writer tracing.

Checksum repair procedure for all rows above: recompute FUN_0800d9cc-equivalent over bytes [0x02,0x18) of the mutated buffer (backward accumulator, sum+carry then XOR-with-next-byte, per §4's pseudocode) and write the low byte of the result to 0x00, 0x00 to 0x01, before flashing the mutated 24-byte record back to EEPROM offset 0 and reloading. Caveat: because the stock game's own checksum does not currently reproduce under this formula (§4), checksum-repaired mutations should be validated by observing whether FUN_0800dddc's checksum-compare branch is taken at all (e.g. via emulator breakpoint on 0x0800dddc+checksum-compare, or by comparing pre/post .ss RAM state) rather than by assuming the repaired checksum will be accepted.
