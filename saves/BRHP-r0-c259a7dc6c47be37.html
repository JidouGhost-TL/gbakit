1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (physical layout and integrity algorithm: HIGH / verified; gameplay semantics of most payload bytes: LOW / unknown).

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is a 512-byte EEPROM (EEPROM 4K, i.e. 4 Kbit). The .sav files are exactly 512 bytes, fill byte 0xFF.
  • Exactly one logical save blob exists. It occupies EEPROM blocks 10–35 inclusive (26 blocks × 8 bytes = 208 bytes, 0xD0), i.e. file offsets 0x50–0x11F. Every other byte of both captures is the erased fill 0xFF (blocks 0–9 and 36–63 are untouched).
  • The blob is serialized through a byte-reversal per 8-byte EEPROM block: the RAM image is recovered by reversing the 8 bytes of each block (block order is preserved). This is proven three independent ways (see §3.4): the reset-header pattern 01 01 01 FF, the repeated sentinel 0x0228, and the checksum all only line up in the block-reversed RAM domain, never in raw file order.
  • Integrity is a 32-bit XOR checksum: stored_u32le(RAM+0) = XOR(u32le words at RAM+4 … RAM+207) XOR 0xABCD1234. It verifies exactly on both captures (full Python output in §4).
  • A secondary sentinel check requires a big-endian-assembled value 0x0228 at RAM offsets +0x44 (bytes 02 28 in RAM, 28 02 in file order at 0x92). The same pair repeats at RAM +0x84 and +0xC4, but only the first is explicitly re-validated on load.
  • On any validation failure the loader rebuilds a blank/default blob and flushes it back to EEPROM. This explains the packet's cold-reload probe: mutating file offset 0x50 (RAM byte +7 after block reversal) breaks the XOR, the save is rejected, and a blank save is rewritten — integrity_check_confirmed: true, reverted_to_blank_on_mutation: true.

Static-only (CONFIRMED_STATIC, code seen, not observable in the two captures):

  • The complete EEPROM driver stack (DMA3 bitstream I/O, read/write/verify, 3-attempt write-and-verify, EEPROM-type identification selecting the 4-Kbit descriptor) and the pack/unpack (serialize/deserialize) routines that translate between the 208-byte blob and three 0x11C-byte in-RAM game-state records.
  • The save writer is reached in the traced code only from the loader's failure path and from the blank-reset routine; the reader has no recovered caller. Normal gameplay save triggers are not present in the trace-guided call graph (see §3.5 for why: almost every function ends in an UNRECOVERED_JUMPTABLE indirect jump, and the call graph drops the func_0x… pseudo-call edges, so several real edges had to be recovered by grepping the decompilation text).

Unknown / hypotheses (HYPOTHESIS / UNKNOWN):

  • The absolute RAM address of the 208-byte blob and of the three 0x11C-byte records: every pointer in the decompilation is an unresolved _DAT_080… literal, so no 0x02xxxxxx/0x03xxxxxx address can be honestly quoted.
  • The gameplay meaning of nearly all payload bytes. The two captures differ in exactly one payload byte (RAM +7: 0xFF → 0x00), so almost every field is observed only at 0/default values.
  • The exact identity of the constant compared against the 0x0228 sentinel on load (a dereferenced pointer *piRam0801cf14 in the decompilation) — its value is inferred as 0x0228 from the init/pack writers and the .sav bytes, not read from ROM.
  • An anomaly at blob byte +0x35, which the reader forces to 0 before checksumming and the writer forces to 0 after flushing (see §5, note N3).

Byte-reversal note (applies everywhere below): a RAM blob offset r maps to file offset 0x50 + (r // 8) * 8 + (7 - (r % 8)). File ranges for multi-byte RAM fields are therefore the same block span, with bytes reversed inside each 8-byte block. All "RAM offset" values below are blob-relative; all "file offset" values are .sav offsets.

Observed content summary (both captures): in RAM domain the blob is almost entirely zero. The only non-zero RAM bytes are the checksum word (RAM +0..+3), header bytes 01 01 01 + FF/00 (RAM +4..+7), and the three sentinel pairs 02 28 (RAM +0x44/+0x45, +0x84/+0x85, +0xC4/+0xC5). In file domain these appear at 0x54–0x57 (checksum, reversed), 0x50–0x53 (header, reversed), and 0x92–0x93, 0xD2–0xD3, 0x112–0x113 (sentinels, reversed) — exactly the active ranges and the 28 02 repeats in saves/hexdump_and_diffs.txt.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

ghidra/callgraph.json alone is incomplete for this binary: it lists the EEPROM wrappers 0x0805c7ac/0x0805c7c0/0x0805c7d4 and the high-level save functions with few or no edges, because the decompiler emits inter-function references as func_0x… pseudo-calls and terminates almost every function with an UNRECOVERED_JUMPTABLE indirect jump. I therefore mapped callers by (a) reading callgraph.json, and (b) grepping ghidra/decompiled.c for every func_0x<addr> / FUN_<addr> occurrence and reading each calling function in full. Every chain below cites the exact decompiled line(s) where the call appears. Where the two sources disagree, the decompilation text wins and the discrepancy is noted.

3.1 Low-level hardware I/O driver (EEPROM over DMA3)

  • FUN_08063308 (0x08063308) — DMA3 transfer primitive. Saves and clears an interrupt-enable global (*_DAT_08063368), programs a WAITCNT-related register from a type descriptor (*_DAT_0806336c … | *(ushort *)(*_DAT_08063374 + 6)), writes source (*_DAT_08063378 = param_1), destination (*_DAT_0806337c = param_2), and DMA3 control/count (*_DAT_08063380 = param_3 & 0xffff | 0x80000000, i.e. count | DMA-enable at the 0x040000D4 DMA3 register block per the packet's hardware map), then busy-waits on the DMA busy bit (uVar2 & 0x8000) and restores interrupts. Callers: FUN_08063388, FUN_0806344c (both in callgraph.json and decompilation).
  • FUN_080632c0 (0x080632c0) — EEPROM type identification / descriptor select. Argument 4 selects one descriptor (*_DAT_080632d4 = _DAT_080632d8), 0x40 a second, anything else a third (and returns 1). The selected descriptor supplies the two parameters the bitstream functions need: max block count at descriptor +4 (compared against the block address) and address-bit count at descriptor +8. For this title it is invoked exactly once, with argument 4 (4-Kbit ⇒ 64 blocks of 8 bytes ⇒ 6 address bits), via the wrapper chain in §3.2. The .sav size (512 B) corroborates the 4-Kbit descriptor.
  • FUN_08063388 (0x08063388) — EEPROM read one block: FUN_08063388(block, out_ptr) (the decompiled prototype shows the two arguments; the seed file lists it as an MMIO seed). It rejects block >= *(descriptor+4), builds the read-command bitstream on the stack (address bits shifted out MSB-style into descending stack halfwords, terminated by two 1 start bits), DMAs it to 0x0D000000 (length = address-bits + 3), then DMAs 0x44 (68) halfwords back from 0x0D000000, and reassembles four u16 words bit-by-bit (uVar4 = uVar4 << 1 | *puVar5 & 1, 16 bits each), storing them into param_2 + 6 while decrementing the destination pointer — i.e. words are delivered in reverse word order with reversed bit assembly, which is the code-level origin of the per-block byte reversal observed in the .sav files. Returns 0 on success (initial uRam080633a4 value on out-of-range).
  • FUN_0806344c (0x0806344c) — EEPROM write one block: FUN_0806344c(block, in_ptr, wait_flag). Symmetric to the read: expands each of the four source u16s into 16 stack halfwords (descending), appends the address bits and the 0, 1 start-bit pair, DMAs address_bits + 0x43 halfwords to 0x0D000000, then polls the EEPROM busy line (uRam0d000000 & 1) with a timer-derived timeout (accumulated delta compared against 0x88, tick source *_DAT_08063538 wrapping at 0xE4); if wait_flag != 0 it loops until the busy line releases. This is the classic EEPROM write-cycle wait.
  • FUN_08063438 (0x08063438) — thin wrapper: FUN_0806344c(block, ptr, 1) (write with wait). Only caller: FUN_08063604.
  • FUN_080635ac (0x080635ac) — EEPROM verify one block: reads the block with FUN_08063388 into a stack buffer and compares the four i16 words against the caller's buffer; returns 0x8000 on first mismatch, 0 on match.
  • FUN_08063604 (0x08063604) — write-and-verify with retry: up to 3 attempts of FUN_08063438 (write) followed, if the write reported success, by FUN_080635ac (verify); returns the final status. This is the function the high-level writer ultimately calls per block.
  • Division helpers FUN_08063680 (signed divide), FUN_080637e8 (unsigned divide), FUN_08063860 (modulo) sit immediately after the EEPROM driver and are used by the pack routine (division by 0x3C = 60). They are not save-integrity functions; FUN_08063860 was listed as an MMIO seed in ghidra/save_related_functions.c but its body is pure arithmetic with no MMIO access — a seed false positive.
  • FUN_08069334 (0x08069334) appears in callgraph.json and in ghidra/save_related_functions.c as a caller of FUN_08063388. Reading the body shows a large graphics/tile-allocation routine whose tail (from uVar17 = uRam080635cc onward) contains a second, spliced fragment that calls FUN_08063388(iVar9, psVar19) and compares four i16s exactly like FUN_080635ac. This is a Ghidra function-boundary merge artefact: the EEPROM-verify fragment is real code, but its attribution to the graphics routine's entry point and trigger context is unreliable. It is recorded as CONFIRMED_STATIC for the call itself and UNKNOWN for context.

3.2 SDK-style EEPROM wrappers

These three tiny wrappers are the bridge between game code and the driver. Their decompiled prototypes show only one argument because the remaining arguments arrive in registers that the unrecovered-jumptable return path discards; the true arity is visible at the call sites.

  • FUN_0805c7ac (0x0805c7ac) → FUN_080632c0(size): identify EEPROM. Called once as func_0x0805c7ac(4) at the end of FUN_0801cd44 (decompiled line 2400).
  • FUN_0805c7c0 (0x0805c7c0) → FUN_08063604(block, ptr): write-and-verify one block. Called in the writer loop as func_0x0805c7c0(sVar3, puVar7) (line 2452).
  • FUN_0805c7d4 (0x0805c7d4) → FUN_08063388(block, ptr): read one block. Called in the reader loop as func_0x0805c7d4(sVar4, puVar7) (line 2497).

callgraph.json records no callers/callees for these three wrappers; the edges above come solely from grepping the decompilation. Any analysis using the call graph alone would conclude the EEPROM is never accessed from game code — that conclusion would be wrong.

3.3 High-level save functions

  • FUN_0801cd98 (0x0801cd98) — save writer (flush). Sequence: four calls to FUN_08061c48 (a wrapper over FUN_080570b8; context unclear, likely display/system sync — treated as opaque), two calls to FUN_0800ac34 (frame/interrupt sync busy-wait that increments counters; also called between block writes), clears/sets three status globals (*_DAT_0801ce30 = 0, *_DAT_0801ce34 = 1, *puVar2 = 1 where puVar2 aliases the first), FUN_0800ac80(0) (stores 0 to a global — mode setter), then FUN_0801c7f0() to pack game state into the blob (see below), recomputes the XOR checksum over blob words 1–51 and stores it at blob word 0 (*_DAT_0801ce38 = uVar4 ^ _DAT_0801ce3c), then writes 26 blocks: for (block = 10; block < 36; block++) { FUN_0800ac34(); func_0x0805c7c0(block, ptr); ptr += 8 bytes; }. After the loop it writes 0 to blob byte +0x35 in RAM (not re-flushed — see note N3). Callers (call graph + grep agree): FUN_0801ce40 (validation-failure path) and FUN_0801d08c (reset). No other caller exists in the traced code.
  • FUN_0801ce40 (0x0801ce40) — save reader (load + validate). Sequence: four FUN_08061c48 calls, status-globals setup mirror of the writer, FUN_0800ac80(0), func_0x0801dd20() (clears a flag byte at stride 0x1C over 5 entries of some table, then sets the first to 1), func_0x0801d280(0) (no-op at argument 0; at argument 1 it would reinitialise several subsystems), reads 26 blocks from block 10 into the blob with func_0x0805c7d4 interleaved with FUN_0800ac34, calls func_0x0801d260(0) (no-op at 0), forces blob byte +0x35 = 0, recomputes the XOR checksum over words 1–51 and compares: if (*blob != (xor ^ CONST) || ((byte)blob_word[0x11] * 0x100 + blob[0x45]) != *piRam0801cf14) { func_0x0801d08c(); FUN_0801cd98(0); }, then unpacks with FUN_0801ca80(). Callers: none recovered (no call-graph caller, no func_0x0801ce40 reference anywhere) — it is an entry reached through the unrecovered indirect dispatch, most plausibly at boot/title initialisation. That context is HYPOTHESIS.
  • FUN_0801d08c (0x0801d08c) — reset to blank/default and save. Zeroes the 208-byte blob (func_0x0806570c(...,0,0xd0) — FUN_0806570c is the memset at 0x0806570c), zeroes three 0x11C-byte game-state records (+0, +0x11C, +0x238), sets blob bytes +4 = 1, +5 = 1, +6 = 1, +7 = 0xFF, then calls FUN_0801cd98(0). Note the reader's failure path calls FUN_0801d08c() (which itself flushes) and then FUN_0801cd98(0) again — a redundant double flush exactly as decompiled. Callers: FUN_0801ce40 only (plus its call-graph edge is missing; found by grep at line 2517).
  • FUN_0801cd44 (0x0801cd44) — default-blob initialiser / EEPROM identify. Memsets a 0x11C-byte record and the 208-byte blob to 0, writes the sentinel pair at blob +0x44/+0x45, +0x84/+0x85, +0xC4/+0xC5 from a single global value (high byte first: *(blob+0x44) = (uVar4 >> 8), *(blob+0x45) = (byte)uVar4, …, i.e. the 0x0228 value corroborated by the captures), and finishes with func_0x0805c7ac(4) (identify EEPROM 4K). Callers: none recovered anywhere. It may run before the traced window or through indirect dispatch; HYPOTHESIS.
  • FUN_0801c7f0 (0x0801c7f0) — pack / serialize: translates the three 0x11C-byte game-state records into the blob. Called only by the writer FUN_0801cd98 (line 2436 / call graph agree). Per record i (source stride 0x11C, blob stride 0x40, blob base R = i*0x40): four 3-byte fields at R+0x08..R+0x13 extracted from source u32s at record offsets +4, +8, +0xC, +0x10 (each emitted as byte-at-+2, then >>8 byte, then low byte — a 24-bit big-endian-style extraction); a byte at R+0x14 copied from source offset +0x118; twelve bytes at R+0x15..R+0x20 bit-packed MSB-first from 96 single-valued source bytes starting at record +0x14 (b0*-128 + b1*64 + b2*32 + b3*16 + b4*8 + b5*4 + b6*2 + b7); twelve more bytes at R+0x21..R+0x2C bit-packed the same way from a second source array; three bytes at R+0x2D..R+0x2F derived from the source record's first u32 divided by 60 (func_0x080637e8(*src, 0x3c), capped against a global), emitted as q >> 10, q >> 2, and a byte combining q's low 2 bits with 5 bits of another source byte (& 0x1f); a 31-bit bitfield at R+0x30..R+0x33 assembled bit-by-bit (bit n = src_byte[n] & 1) and stored little-endian; a second 31-bit bitfield at R+0x34..R+0x37; and the sentinel pair rewritten at R+0x44/+0x45 from the same global as FUN_0801cd44 (for i = 2 this lands at blob +0xC4, the last sentinel). So before every flush the pack routine mutates the blob at R+0x08..R+0x37 and R+0x44/+0x45 for all three records; it does not touch blob bytes +4..+7, R+0x00..R+0x07 (except via the previous record's sentinel at R+0x44 overlapping the next chunk's +4/+5), R+0x38..R+0x43, or the tail +0xC6..+0xCF.
  • FUN_0801ca80 (0x0801ca80) — unpack / deserialize: exact inverse of FUN_0801c7f0. Called only by the reader FUN_0801ce40 after successful validation (line 2520). It reconstructs each 0x11C-byte record: the four 24-bit fields are reassembled as byte0*0x10000 + byte1*0x100 + byte2 into record offsets +4, +8, +0xC, +0x10; the byte at record +0x118 comes from blob R+0x14; the two 12-byte packed arrays are expanded bit-by-bit (>>7 … &1) back into byte arrays; the time value is rebuilt as (b0x2D*0x400 + b0x2E*4 + (b0x2F >> 6)) * 0x3C into record word 0, with (b0x2F >> 1) & 0x1f written to another record byte; and the two 31-bit fields are expanded back into 31 single bytes each.
  • Supporting: FUN_0806570c memset (used by init/reset), FUN_0800ac34 frame-sync busy-wait, FUN_0800ac80 global mode store, FUN_08061c48→FUN_080570b8 opaque sync wrapper, FUN_0801dd20/FUN_0801d260/FUN_0801d280 state initialisers (argument-0 paths taken during load).

3.4 Why the RAM image is the per-block byte reversal of the file (proof)

  1. Reset pattern: FUN_0801d08c writes blob bytes +4,+5,+6,+7 = 01,01,01,FF. Capture cap-00 has, in block-reversed RAM domain, bytes +4..+7 = 01 01 01 ff exactly; in raw file order those bytes sit at 0x53,0x52,0x51,0x50, i.e. reversed. Capture cap-01 differs only at RAM +7 (00), matching a single payload-byte change.
  2. Sentinel: init/pack write 02 at +0x44 and 28 at +0x45. Block reversal maps RAM +0x44 → file 0x93 and +0x45 → file 0x92; the captures contain 0x93=02, 0x92=28. In raw order the pair reads 28 02 at 0x92, which would make the init code's byte order inexplicable.
  3. Checksum: the XOR formula (§4) verifies on both captures only in the block-reversed domain; in raw file order the same computation yields 0x9edede60/0x9edede9f against stored file words 0x010101ff/0x01010100 — no match.
  4. Driver code: both FUN_08063388 (read) and FUN_0806344c (write) build/consume the EEPROM bitstream with descending stack halfwords and store recovered words into param_2 + 6 decrementing — reversed word/bit assembly at exactly 8-byte (4-word) granularity, consistent with the empirical reversal.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Sentinel ("magic")

  • RAM blob offsets +0x44/+0x45 (file 0x93/0x92), repeated at +0x84/+0x85 (file 0xD3/0xD2) and +0xC4/+0xC5 (file 0x113/0x112): RAM bytes 02 28, file bytes 28 02.
  • Writers: FUN_0801cd44 (init, blob-absolute offsets) and FUN_0801c7f0 (pack, at record*0x40 + 0x44 for each of 3 records — which is why the third lands at +0xC4, past the second record's nominal stride).
  • Reader check (FUN_0801ce40): (byte)blob_word[0x11] * 0x100 + blob[0x45] != *piRam0801cf14 → reject. blob_word[0x11] is the u32 at RAM +0x44; its low byte is 0x02, so the compared value is 0x0228. Only the first sentinel is checked; the other two are protected only by the XOR checksum.
  • Verified in code: yes (three writer sites, one reader site). Verified in .sav: yes, 02 28 in RAM domain in both captures at all three offsets. It is a version/format sentinel, not ASCII magic; there are no ASCII magic strings in the blob (PACKET.md: ascii_magic_strings: []). Confidence: CONFIRMED_VERIFIED for value/location; the compared constant's ROM identity is CONFIRMED_STATIC-inferred (0x0228).

4.2 Checksum

  • Algorithm: XOR-32 with key (custom). Formula, all arithmetic on little-endian u32 words of the block-reversed RAM image:

blob_u32le[0] = ( blob_u32le[1] XOR blob_u32le[2] XOR … XOR blob_u32le[51] ) XOR 0xABCD1234

  • Stored: blob word 0 (RAM +0x00..+0x03; file bytes 0x57,0x56,0x55,0x54 after per-block reversal, i.e. file block 0x54..0x57 read in reverse). Stored size 4 bytes.
  • Covered: blob words 1–51 = RAM +0x04..+0xCF (204 bytes; the entire blob except the checksum word). In file terms: offsets 0x50..0x11F except the four checksum bytes at 0x54..0x57.
  • Decompiled proof:
  • Writer FUN_0801cd98: uVar4 = 0; uVar6 = 2; puVar5 = blob; do { puVar5++; uVar4 ^= *puVar5; bVar1 = uVar6 < 0x34; uVar6++; } while (bVar1); *blob = uVar4 ^ _DAT_0801ce3c; — the loop XORs words 1–51 (51 iterations, uVar6 running 2…0x34), then stores the XOR folded with a constant. That constant's value is not printed by the decompilation; it is recovered from the captures below as 0xABCD1234, identical for both files, which is itself the proof that the constant is a fixed XOR key and not data-dependent.
  • Reader FUN_0801ce40: identical loop, then if (*blob != (uVar5 ^ _DAT_0801cf10) || sentinel != expected) { reset; save; }.
  • The change between captures is fully explained by this formula: only payload word 1 changes (0xFF010101 → 0x00010101, i.e. RAM byte +7: FF → 00); the XOR delta is 0xFF000000; the stored word changes 0x54CC3B37 → 0xABCC3B37; and 0x54CC3B37 XOR 0xABCC3B37 = 0xFF000000. Exact agreement.

4.3 Python verification (executed in this workspace)

Script:

import pathlib, struct, functools, hashlib
for p in sorted(pathlib.Path('saves').glob('*.sav')):
    b = p.read_bytes(); raw = b[0x50:0x50+0xD0]
    ram = b''.join(raw[i:i+8][::-1] for i in range(0, 0xD0, 8))  # undo per-block reversal

          f"stored=0x{w[0]:08x} xor(w1..51)=0x{x:08x} xor^0xABCD1234=0x{x^0xABCD1234:08x} "
          f"match={w[0]==x^0xABCD1234} sentinel=0x{ram[0x44]*256+ram[0x45]:04x} hdr={ram[4:8].hex()}")
