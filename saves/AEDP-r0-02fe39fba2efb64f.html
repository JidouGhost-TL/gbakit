Carrera Power Slide (Europe) (En,Fr,De,Es,It,Nl) — Clean-Room GBA Save Format Report

Release key: AEDP-r0-02fe39fba2efb64f · Game code AEDP · ROM SHA-256 02fe39fba2efb64f19834398f0622e9f74286a09a0aff6e4b4bb35925bab1098

Offset convention (critical). All offsets in this report and in save-format.json are logical EEPROM byte offsets, unless explicitly labelled "file offset". The emulator .sav file does not store logical bytes linearly: each 8-byte EEPROM block is byte-reversed in the file. The mapping is: `` file_offset = (logical_offset & ~7) | (7 - (logical_offset & 7)) logical_byte[i] = file_byte[(i & ~7) | (7 - (i & 7))] ` Evidence: only under this transform does logical byte 0 become the 0x17 magic checked in code, and only under this transform do both integrity values (Section 4) verify on both samples. In raw file order, byte 0 is 0x00 and no checksum verifies. This reversal is consistent with the 64-bit serial EEPROM transfer assembled/disassembled bit-by-bit in FUN_080190e8 / FUN_08019198 and the 8-byte block handling in FUN_08002528 / FUN_080025e4`. It is proven empirically (magic + two independent checksums, 2/2 samples), regardless of whether the reversal originates in the game's bit-packing or in the emulator's EEPROM dump convention.

1. Executive Summary & Overall Confidence

Overall confidence: HIGH for the physical layout, the two-layer integrity scheme, and the writer/reader architecture. MEDIUM/LOW for the semantic meaning of individual payload bit-fields and for multi-slot geometry (see below).

What was proven by both decompiled code AND .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM, 512 bytes total, accessed as 64 blocks of 8 bytes via DMA3 to 0x0D000000.
  • A single-file header at logical offsets 0–2: magic 0x17 at offset 0, big-endian additive sum16 at offsets 1–2.
  • One 68-byte record at logical offsets 3–70: a little-endian raw CRC-32 at record offset 0 (logical 3–6) over a 64-byte packed payload at record offset 4 (logical 7–70).
  • Both checksums recompute exactly on both saves/cap-00-future-0.sav and saves/cap-01-future-1.sav (Section 4, with Python output). The PACKET cold-reload probe (mutation at file offset 0x45 → reverted to blank, save rewritten) is fully explained: file 0x45 is logical 0x42 (record byte 63, a packed payload byte), so mutating it breaks both the CRC-32 and the outer sum16.
  • The complete call chain boot-init → load/unpack → (on failure) defaults → pack → flush, and format-on-missing-magic.

What remains open (HYPOTHESIS / UNKNOWN):

  • Semantic names of the ~35 packed sub-fields inside the 64-byte payload. The packer (FUN_08015590) and unpacker (FUN_08015b74) are exact bit-level mirrors, so field boundaries are statically recoverable, but no string/label evidence in the workspace names what each field means in gameplay terms (times, unlocks, options, etc.).
  • Exact slot stride and maximum slot index. Only slot 0 is ever used by traced callers and only one record exists in the samples. The init argument 0x54 (84) passed by FUN_080029b0 to FUN_08002830 is a hypothesis for a per-slot allocation/stride, not proven.
  • Whether the outer sum's covered range includes logical byte 71 (the byte after the record). Byte 71 is 0x00 in both samples, so including or excluding it does not change the sum; the block loop in FUN_0800271c sums whole 8-byte blocks and therefore probably includes it.
  • Numeric RAM addresses of the save struct. The decompilation loads the struct base through ROM literal pointers (_DAT_08015984, _DAT_08015e00, …) whose target values are not present in the C text, so ram_addr is honestly null in save-format.json.

Method: every function cited below was read in ghidra/decompiled.c; caller/callee edges were cross-checked against ghidra/callgraph.json and against func_0x… runtime calls in the C text (the callgraph omits several runtime/indirect edges, e.g. FUN_080029b0 → FUN_08015b74); all checksum claims were verified by executing Python against the real .sav binaries (Section 4). No third-party game-specific source was used.

Slots / copies. Traced code supports an indexed record space: the writer FUN_08002798(buf, slot) and reader FUN_080028e0(buf, slot) compute EEPROM_offset = stride * slot + 3, where stride is a ROM-literal global (*_DAT_08002820 / *_DAT_08002934, value not recovered from the C text). The special slot value 0x400 means "next slot": the writer stores last_slot + 1 (*_DAT_08002818 + 1) and the reader likewise reads last_slot + 1. A global maximum index (_DAT_0800281c / _DAT_08002930) bounds the slot. However:

  • The only slot ever passed by a traced caller is 0 (FUN_08015590 → FUN_08002798(puVar10, 0); FUN_08015b74 → FUN_080028e0(_DAT_08015e00, 0)).
  • Both .sav samples contain exactly one non-zero record (logical 3–70); logical 71–511 are zero. There is no mirror/backup copy in the observed images: no second magic, no duplicated payload, no generation/sequence counter anywhere in the file. Confidence: CONFIRMED_VERIFIED for "one active copy in samples", CONFIRMED_STATIC for "indexed API exists", HYPOTHESIS for any multi-slot use.
  • Hypothesis (unproven): FUN_080029b0 calls FUN_08002830(0x54). 0x54 = 84 is in the valid range checked by the callee (1 ≤ param ≤ 0x1FF) and would fit 512 / 84 = 6 slots with 16 bytes slack per slot beyond the 68-byte record. The decompiled body of FUN_08002830 stores the argument to a global and later returns func_0x0801f6dc(_DAT_080028c0, *piVar1) — FUN_0801f6dc is the compiler's signed-division helper — consistent with a "capacity / size" computation, but the dividend global's value is not in the C text. This is recorded as an open question, not a fact.

Selection rule (as traced). At boot, FUN_080029b0 initialises the EEPROM (FUN_08002830(0x54)), then loads slot 0 (FUN_08015b74). If the inner CRC-32 fails (function returns 0), it installs defaults (FUN_08015e40) and immediately re-saves (FUN_08015590). There is no "pick newest of two copies" logic in any traced function; redundancy is therefore none observed — integrity failure leads to defaults + rewrite, matching the PACKET probe (reverted_to_blank_on_mutation: true, save_rewritten_after_mutation: true, save_preserved_on_load: true for the unmutated case).

Generation/sequence counters. None found. No byte in the header or record is incremented as a generation counter by any traced writer: the only bytes that changed between the two samples are the two integrity fields and two packed payload bytes (record bytes 62–63, logical 65–66). The payload byte at logical 0x15 (record byte 18, value 0x02 in both) and bytes at logical 0x0E–0x0F (0x08 0x10) are constant across samples and are candidates for mode/flags fields, not counters.

Mapping method for every edge below: (a) direct FUN_… calls in ghidra/decompiled.c, (b) func_0x… runtime calls in the same text (these are real calls the static callgraph missed), (c) ghidra/callgraph.json edges. Where (b) and (c) disagree, the decompiled text was trusted and the discrepancy is noted.

Chain A — boot / cold load (entry FUN_080029b0, no callers in callgraph; it is an entry point).

How it mutates RAM before flushing: FUN_080029b0 itself only sets five status globals (*_DAT_080029fc = 1, *_DAT_08002a00 = 1, *_DAT_08002a04 = 5, *_DAT_08002a08 = 1, *_DAT_08002a0c = -1) on the failure path. The actual save fields are written by FUN_08015e40 (defaults, §3.3) and then serialised by FUN_08015590. 4. Magic Signatures & Checksum / Integrity Algorithm

4.0 Magic signature

  • Bytes: 0x17 (single byte, no ASCII magic exists in either sample — consistent with PACKET's ascii_magic_strings: []).
  • Logical offset: 0 (file offset 0x07 due to block reversal).
  • Code proof: written by FUN_080026cc (auStack_10[0] = 0x17; FUN_080025e4(0, auStack_10, 8)), checked by FUN_08002830 (if (acStack_18[0] == '\x17') … else format).
  • Sample proof: logical byte 0 = 0x17 in both samples (file byte 0x07 = 0x17 in both hexdumps).
  • Confidence: CONFIRMED_VERIFIED.

4.1 Outer integrity — additive sum16 (big-endian store)

  • Algorithm: 16-bit wrapping sum of unsigned bytes (sum16, stored big-endian — the schema's sum16_le does not describe it, so save-format.json uses custom with this detail).
  • Formula: stored_u16_BE at logical 1..2 == (Σ byte[i] for i in covered range) & 0xFFFF.
  • Covered range: logical 3..70 inclusive proven (68 bytes = the whole record, including the inner CRC bytes at 3–6). Logical byte 71 inclusion is unresolved (zero in both samples; the block loop in FUN_0800271c sums whole blocks and likely includes it — including it does not change either sample's sum).
  • Stored offset/size: logical 1, 2 bytes, big-endian.
  • Decompiled proof: computation in FUN_0800271c (iVar1 = b[0]+b[1]+b[2]+b[3]+b[4] for the unaligned first read at offset 3, then 8-byte block sums from offset 8); store in FUN_08002798:
  iVar3 = FUN_0800271c();
  uStack_10 = (undefined1)((uint)iVar3 >> 8);   // high byte first → big-endian
  uStack_f  = (undefined1)iVar3;
  iVar3 = FUN_080025e4(1, &uStack_10, 2);        // write at logical offset 1, length 2

Validation-side: FUN_08002830 recomputes FUN_0800271c() when the magic is present. Honesty note: the precise stored-vs-computed comparison expression is not cleanly recovered — the decompilation renders it as if ((uVar5 & uRam080028bc) == 0xffffffff) goto fail;, which as written only clearly rejects the -1 read-failure sentinel. The store + recompute + sample match are verified; the exact comparison opcode is CONFIRMED_STATIC at reduced confidence. The observed reject-on-corruption behaviour is independently proven by the inner CRC path (§4.2) and by the PACKET probe.

  • Order of operations (writer): record is flushed first, then the sum is recomputed from EEPROM (FUN_0800271c reads back through FUN_08002528), then the 2 sum bytes are written. A power loss between the two writes leaves a stale sum — see fuzzing plan.

4.2 Inner integrity — raw CRC-32 (no final XOR), little-endian store

  • Algorithm: CRC-32, reflected, polynomial 0xEDB88320 (proven by verification; the literal _DAT_08016e54 is not in the C text), initial value 0xFFFFFFFF, no final XOR — i.e. zlib.crc32(data) ^ 0xFFFFFFFF. This is not standard zlib CRC-32 output; implementations must use the raw form.
  • Formula: stored_u32_LE at logical 3..6 == crc32_raw(payload), where the per-byte step is FUN_08016e3c((byte ^ crc) & 0xFF) followed by crc = (crc >> 8) ^ step_result — the standard table-driven form with the table generated bitwise.
  • Covered range: logical 7..70 inclusive (the 64-byte payload, record bytes +4..+67). Proven exactly: neighbouring ranges (63 or 65 bytes, shifted windows) do not match on either sample.
  • Stored offset/size: logical 3, 4 bytes, little-endian (*puVar3 == uVar8 comparison in FUN_08015b74 is a native little-endian u32 load; the verified byte order is LE).
  • Decompiled proof: writer loop in FUN_08015590:
  uVar11 = 0xffffffff;
  do { uVar12 = func_0x08016e3c((*(byte *)(iVar4 + 4 + uVar15) ^ uVar11) & 0xff);
       uVar11 = uVar11 >> 8 ^ uVar12; uVar15++; } while (uVar15 < 0x40);
  *_DAT_08015b70 = uVar11;   // record offset 0

Reader loop in FUN_08015b74 is identical and ends with bVar9 = *puVar3 == uVar8; gating all unpacking.

  • Confidence: CONFIRMED_VERIFIED.

4.3 Python verification output (executed in this workspace)

Script (run as /tmp/verify.py; the same logic is reproducible from this report):

import pathlib, struct, hashlib
def logical(d):
    o = bytearray()
    for i in range(0, len(d), 8): o += d[i:i+8][::-1]
    return bytes(o)
def crc_raw(data, poly=0xEDB88320):
    crc = 0xFFFFFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ poly if crc & 1 else crc >> 1
    return crc & 0xFFFFFFFF
# per file: magic=d[0]; sum16: struct.unpack(">H", d[1:3]) vs sum(d[3:71]) & 0xFFFF

6. Save Fuzzing & Counterfactual Verification Plan

All mutations are specified in file offsets (what you edit in the .sav), with the logical offset in parentheses. "Repair" means recomputing the integrity fields in logical space, then mapping each byte back to its file offset (file = (logical & ~7) | (7 - (logical & 7))). No paired .ss states exist in this workspace (states/ is empty), so predictions are stated as observable boot/UI/RAM outcomes to check on first reload; where a save-state becomes available, also watch the RAM struct pointed to by the reader's base pointer.
