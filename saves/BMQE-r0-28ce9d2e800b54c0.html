Clean-Room Save Format Report: Magical Quest 3 Starring Mickey & Donald (USA) (En,Fr,De)

Release key: BMQE-r0-28ce9d2e800b54c0 · Game code: BMQE / header family BMQ · Community: comm-040 ROM SHA-256: 28ce9d2e800b54c0f6a580e2193c23f80b6e2567890bb9048901a3ff8f163d6c

All findings below are derived exclusively from ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and the two .sav snapshots and diff log in saves/. No third-party game-specific documentation was consulted.

1. Executive Summary & Overall Confidence

Overall Confidence: LOW-MEDIUM.

What is proven:

  • The title uses EEPROM save media, accessed exclusively through the GBA serial EEPROM bus (0x0D000000) driven by DMA3 bit-transfers. No SRAM (0x0E000000) or Flash bank-select (0x5555/0x2AAA) code paths exist anywhere in the 241 decompiled functions — this independently corroborates the packet's "Observed Save Media": "EEPROM 4K" tag.
  • A complete, generic 6-function EEPROM driver cluster was traced: raw DMA3 bit-transfer primitive → block read → block write → write-then-read-back verify → write/verify/retry(×3). This is a standard SDK-style EEPROM access library (consistent with the comm-040 shared-engine tag), not game-specific logic.
  • Exactly one 8-byte region of the 512-byte .sav (offset 0x180–0x187, i.e. EEPROM block index 0x30) is non-blank across the two captured snapshots; its value is reproducibly derived from the hardware driver's I/O word size (one EEPROM block = 8 bytes = 4×u16).

What remains open / unresolved (and is the reason confidence is capped at LOW-MEDIUM rather than HIGH):

  • No caller of the write/retry entry point (FUN_081190ec) or of the raw write primitive (FUN_08118f34) exists anywhere in the traced 241-function corpus (confirmed by exhaustive search of ghidra/callgraph.json, section 3.3). This means the actual game-logic function that decides when to save and what in-RAM struct (0x02xxxxxx/0x03xxxxxx) feeds the 8-byte payload is not present in this workspace and cannot be clean-room derived from the available decompilation. It is an UNKNOWN, not an assumption.
  • Only two .sav snapshots exist (one all-0xFF blank, one with a single written block), and zero paired .ss save states are present in states/. This is insufficient to distinguish a real "checksum algorithm" from simple field duplication, or to test counterfactual mutations against a live emulator session. All byte-level semantics beyond the raw hex are therefore HYPOTHESIS, not verified.
  • No ASCII magic string, version tag, or slot-selector byte was found anywhere in the 512-byte save image.

3. Save Writer, Reader & Caller-Chain Architecture

All six functions below live in a single contiguous code region (0x08118da0–0x08119138) and were extracted as the "save-related" seed cluster in ghidra/save_related_functions.c. Addresses, roles and the exact evidence for each role are given below.

3.1 Low-level hardware I/O driver

FUN_08118df0 (0x08118df0) — raw DMA3 serial-bit transfer primitive.

  • Writes param_1 (source) and param_2 (dest) into two MMIO-adjacent globals (_DAT_08118e60, _DAT_08118e64), then writes param_3 & 0xffff | 0x80000000 into a third global (_DAT_08118e68) — the 0x80000000 set bit is the DMA enable bit pattern, and the struct layout (src ptr, dst ptr, count|enable) matches the GBA DMA3 register triplet DMA3SAD/DMA3DAD/DMA3CNT_H (0x040000D4/0x040000D8/0x040000DC) addressed indirectly through pointer globals.
  • Busy-waits on bit 15 (0x8000) of a status halfword before returning — the DMA "busy" bit.
  • Callers (confirmed via callgraph.json): 0x08118e70 (read path), 0x08118f34 (write path). No other caller exists in the 241-function set.
  • Role: shared low-level transfer primitive used by both the EEPROM read and write block functions to shift bits across the serial EEPROM bus at 0x0D000000.

3.2 EEPROM block read / write / verify functions

FUN_08118e70 (0x08118e70) — EEPROM block READ.

  • Bound-checks param_1 (block address) against *(ushort*)(*_DAT_08118e88 + 4) (max block count for this EEPROM size — consistent with EEPROM 4K's 64-block ceiling).
  • Serializes a "READ" command bit (1) + the block address bits into a local stack bitstream, then calls FUN_08118df0 twice: once to clock out the read-request bitstream, once to clock in 0x44 (68) response bits over the EEPROM bus.
  • Unpacks the response into 4 big-endian ushort halfwords, written to the caller-supplied param_2 buffer (offsets +0,+2,+4,+6).
  • Caller: 0x08119094 only (confirmed in callgraph.json).
  • Role: READER — the only function in this workspace that pulls an 8-byte block out of EEPROM into RAM.

FUN_08118f20 (0x08118f20) — thin wrapper: func_0x08118f34(param_1, param_2, 1).

  • Caller: 0x081190ec only.
  • Role: WRITE entry point (fixed "wait-for-ready" flag = 1).

FUN_08118f34 (0x08118f34) — EEPROM block WRITE (raw hardware).

  • Packs the caller-supplied 4×ushort payload (param_2[0..3]) plus the block address (param_1) MSB-first into a serial bitstream, then calls FUN_08118df0 once to clock addr_width + 0x43 bits out over the bus.
  • Afterward polls the EEPROM "ready" status bit (uRam0d000000 & 1) in a timeout loop (accumulates elapsed ticks in uStack_18, compared against threshold 0x88) before returning — this is the hardware write-completion wait, not an application-level checksum loop.
  • Callers: 0x08118f20 only (per callgraph.json; note save_related_functions.c's header comment says "callers: none" because that extraction only looked at the 2-hop/1-hop seed window and did not include 0x08118f20 in its listing — callgraph.json is authoritative and shows the real edge).
  • Role: WRITER — the only function that pushes an 8-byte block from RAM into EEPROM.

FUN_08119094 (0x08119094) — write-verify (read-back-and-compare).

  • Calls FUN_08118e70 to read back the block just written into a local stack buffer, then compares each of the 4 halfwords against the original param_2 payload. Returns 0 on full match, 0x8000 on first mismatch.
  • Caller: 0x081190ec only.
  • Role: INTEGRITY CHECK — this is the only integrity mechanism found anywhere in the traced code (see section 4 — there is no stored checksum field).

FUN_081190ec (0x081190ec) — write/verify/retry entry point.

  • Loop up to 3 times: write via FUN_08118f20, then if the write call itself reports success, verify via FUN_08119094; break on clean verify.
  • Callers: NONE found in the 241-function decompiled corpus (confirmed by exhaustive scan of every function's callees list in ghidra/callgraph.json — section 3.3 below).
  • Role: highest-level save-writer entry point visible in this workspace. It is the natural "SaveBlock()" analogue, but the game-logic call site that invokes it is outside the traced function set.

3.3 Caller-chain mapping method and result

Mapping method: for every one of the 241 functions keyed in ghidra/callgraph.json, we searched its callees array for each of the six save-cluster addresses (0x08118df0, 0x08118e70, 0x08118f20, 0x08118f34, 0x08119094, 0x081190ec). Result (verified by direct Python traversal of the full dict, not just the pre-extracted seed file):

0x08118e70 -> 0x08118df0
0x08118f34 -> 0x08118df0
0x08119094 -> 0x08118e70
0x081190ec -> 0x08119094
0x081190ec -> 0x08118f20

No other function in the corpus calls into this cluster. Consequence: we cannot identify, from this workspace, which game-state struct in EWRAM (0x02xxxxxx) or IWRAM (0x03xxxxxx) is read to build the 8-byte payload passed into FUN_08118f20/FUN_081190ec, nor what in-game event (menu save, checkpoint, level-complete, boot-time EEPROM presence test) triggers it. This is reported as an explicit UNKNOWN, not inferred or guessed.

4. Magic Signatures & Checksum / Integrity Algorithm

No ASCII magic string and no stored software checksum/CRC field were found anywhere in the 512-byte save image or in the traced decompiled code.

  • No ASCII run of printable bytes exists in either .sav file (the only non-blank bytes are the 8 at 0x180–0x187, and none are printable ASCII as a run).
  • No sum/XOR/CRC accumulation loop over a save buffer exists anywhere in the 241 decompiled functions. The only "integrity" logic found is the hardware read-back-and-compare + 3× retry implemented by FUN_08119094/FUN_081190ec (section 3.2) — this is a transport-reliability mechanism (defends against a failed EEPROM write), not a stored, software-computed checksum that could be verified against file bytes.

Python verification performed directly against saves/cap-01-future-1.sav (the only non-blank sample):

block bytes (0x180-0x187): 0002000000000002
as 4x u16 big-endian:      (2, 0, 0, 2)
halfword[0] == halfword[3]: True
XOR of all 8 bytes:         0
sum8 mod 256:                4
cap-00-future-0.sav:        all 512 bytes == 0xFF (fully blank)

Interpretation (HYPOTHESIS, not verified — only one non-blank sample exists): the first and last big-endian u16 of the 8-byte block are both 0x0002, and the middle 4 bytes are 0x00000000. This is consistent with either:

  1. A simple duplicate-value redundancy pattern (the same 16-bit value written at both block-start and block-end, letting a reader detect corruption by direct equality rather than an arithmetic checksum), or
  2. Two independent fields that coincidentally share the value 2 (e.g. a slot index and a format/version tag), with the middle field(s) legitimately zero.

With a single non-blank sample it is not possible to distinguish these two hypotheses, and no sum/XOR/CRC formula can be "confirmed" from one data point — any formula with the right number of free parameters fits one sample trivially (e.g. XOR-of-all-bytes == 0 is true here, but true for any symmetric pattern and proves nothing). No checksum entry is reported as CONFIRMED in save-format.json; the checksums array is empty, and this ambiguity is carried into the field map (section 5) and fuzzing plan (section 6) as the top open question.

Open Questions

  1. What game-logic function calls FUN_081190ec (or FUN_08118f20 directly), and what EWRAM/IWRAM struct supplies its 4-halfword payload? (Outside the traced 241-function corpus — section 3.3.)
  2. Is block address 0x30 (0x180/8) hard-coded, or could other blocks be used for additional save slots never exercised in the two available captures?
  3. Are the two matching 0x0002 halfwords a redundancy pair, or two independently-valued fields that happen to coincide at 2? (Section 4 — needs more non-blank samples with differing values to resolve.)
  4. Is there any integrity mechanism beyond the hardware write-verify-retry (e.g., a checksum computed in RAM before the write that this driver-level trace cannot see)? Needs live-session fuzzing per section 6 once paired .ss states exist.
  5. What does the 2 value represent semantically (counter, boolean flag ×2 copies, slot marker, version tag)? Cannot be determined without either more .sav samples spanning different in-game states, or the untraced caller function.
