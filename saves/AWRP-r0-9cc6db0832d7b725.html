Clean-Room Save Format Report: Advance Wars (Europe) (En,Fr,De,Es) — AWRP-r0-9cc6db0832d7b725

All findings below are derived exclusively from the files in this workspace: ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and the real .sav binary in saves/, cross-checked against standard public GBA hardware behavior (Flash/SRAM bus at 0x0E000000, BIOS SWI numbering). No third-party game-specific wiki, decompilation project, or walkthrough was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + bytes agree):

  • The title uses a generic Flash-based object/sector store (not a hand-rolled single-struct save), built from a small set of low-level hardware routines plus a directory/allocator layer sitting on top of it.
  • The save media is Flash, sector size 0x1000 (4096 bytes), matching the GBA-standard SST-style command sequences (chip-ID entry/exit, 4KB sector erase) found in the MMIO seed functions.
  • Every stored "object" in the store begins with a small header whose byte at relative offset +5 is a hard-coded constant 0x09, and whose bytes at relative offset +6/+7 form a sum-and-ones’-complement pair (byte[+7] == 0xFF - byte[+6]). Both properties are independently confirmed in ghidra/decompiled.c (FUN_0801ab60) and in the real .sav file at offset 0xF005–0xF007 (09 D9 26, where 0xD9 + 0x26 == 0xFF).
  • The init call chain from boot to the first directory scan is fully traced: FUN_08038b48 → FUN_0801ab24 → FUN_0801b384/FUN_0801b674 → FUN_0801b150/FUN_0801b3a8/FUN_0801ab60.

What is not proven (open / HYPOTHESIS):

  • The exact byte range the sum8 checksum covers. A static-code trace shows the sum is computed over a runtime-resolved pointer/length pair (_DAT_0801aef8, _DAT_0801aef4) whose values are not visible without a live trace, so the covered span could not be reproduced byte-for-byte from the static sources alone (see §4 for the verification attempt and its result).
  • The semantic meaning of nearly all gameplay-relevant fields (money, unit/map progress, campaign flags, etc.). Only structural/container-level facts are confirmed; no game-specific field has been semantically identified.
  • Whether the two ASCII fragments found in the save ("wars" at 0xF000, "Advance" at 0xF372) are the same logical field, two different fields, or save-slot/version-label text — their presence is confirmed, their meaning is not.

2. Physical Media, Slot Geometry & Redundancy

  • Media: Flash, 512 Kbit (65,536 bytes total), matching the packet's save_media_type: "Flash 512K" and the observed .sav file size (65536 bytes).
  • No SDK save tag string was found anywhere in ghidra/decompiled.c or ghidra/save_related_functions.c — consistent with the packet's SDK Save Tags in ROM: none detected.
  • Sector size: 0x1000 (4096 bytes) is used throughout the allocator layer (FUN_0801b3a8, FUN_0801babc, FUN_0801bb14, FUN_0801bb74 all multiply/divide a sector index by 0x1000). 65536 / 4096 = 16 sectors — matches the 0x10 (16) loop bound seen in FUN_0801b3a8's "mark free/erase" scan (while (iVar4 < 0x10), ghidra/decompiled.c:3471) and the param_1 < 0x10 guard in the raw hardware erase routine FUN_0807a9dc (ghidra/save_related_functions.c:191).
  • Slot/redundancy model: This is not a simple "slot 0 / slot 1 mirrored backup" scheme. It is a wear-leveled flash object store: the allocator (FUN_0801ab60) scans all 16 sectors for free/stale entries, can relocate an object to a new sector, and marks the old sector's slot invalid (ghidra/decompiled.c:3449-3453, *puVar10 = 0xff; marking a slot byte "erased/free"). There is no evidence of a fixed "primary vs backup" pair of whole-save mirrors; redundancy (if any) is at the level of individual objects being relocated on write, not whole-save duplication.
  • Only ~1.4 KB of the 64 KB chip is actually used in the sample save (0xF000–0xF56A, plus 2 bytes at 0xFFFE). The rest is the Flash erased-fill value 0xFF. This means the store's directory/object area is anchored near the top of the address space (0xF000–0xFFFF), not the bottom — all 16 "logical sectors" referenced by the allocator are almost entirely blank in this capture, i.e. only a small fraction of the store's total sector budget is populated for this title/profile.
  • Selection rule: Not resolved. The directory-scan/erase logic (FUN_0801b150/FUN_0801b3a8/FUN_0801b674, ghidra/decompiled.c:3368-3478) walks a 16-entry table comparing per-slot validity and timestamp/sequence-like markers, but the comparison operands (*pbVar7, *(char*)(uVar9 + _DAT_0801b320)) are opaque globals whose concrete meaning could not be pinned down statically. Treat as HYPOTHESIS: "most-recently-written valid object wins."

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (MMIO seeds, ghidra/save_related_functions.c)

All MMIO-seed functions bottom out in func_0x0807bf10/0807bf14/0807bf18/0807bf1c, which are themselves unresolved indirect-jump-table trampolines (ghidra/decompiled.c:7616-7665). Sibling functions in the same address range resolve directly to BIOS software interrupts, e.g. FUN_0807a184 → software_interrupt(0x0B) (BIOS CpuSet), FUN_0807a19c → software_interrupt(0x11), FUN_0807a1a8 → software_interrupt(0x15) (ghidra/decompiled.c:7061-7086). This strongly suggests the 0807bf1x family are BIOS-call wrappers too (most likely CpuSet/CpuFastSet-style block copy for the Flash program path), but their exact SWI numbers were not directly observable in the extracted sources — HYPOTHESIS, not verified.

3.2 Allocator / directory layer (generic flash object store, 0x0801axxx–0x0801cxxx)

  • FUN_0801ab24 (ghidra/decompiled.c:2960-2977) — save-system init. Stores 5 parameters into globals (device/geometry descriptor pointers) then calls FUN_0801b384() (chip-ID probe wrapper, itself calling func_0x0807a2bc) and FUN_0801b674(0) (directory rebuild entry point).
  • FUN_0801b674 (ghidra/decompiled.c:3730+) — directory rebuild dispatcher; callees per ghidra/callgraph.json are 0x0801b150, 0x0801b3a8, 0x0801b4ac.
  • FUN_0801b150 / FUN_0801b3a8 (ghidra/decompiled.c:3368-3478) — directory scan: iterates all 16 sector slots, calls FUN_0801ba74 (slot-select) + FUN_0801b3a8 (per-slot validity probe, itself calling FUN_0801b42c), and on an invalid/orphaned slot marks it free (*pbVar7 |= 4, *puVar10 = 0xff) and clears a per-slot RAM mirror word (*(undefined4*)(uVar9*4 + iRam0801b328) = 0). A second pass (uVar9 > 0xf) sweeps all 16 slots again clearing stale "busy" flags.
  • FUN_0801ab60 (ghidra/decompiled.c:2984-3253) — the write/allocate routine. For a given object index (unaff_r9), it:
  1. Builds a free-slot candidate list (abStack_70) and sorts candidates by a priority value at _DAT_0801acac.
  2. Splits the caller's buffer into _DAT_0801acb0-sized chunks (first chunk shortened by 0x10 if this is the very first fragment for the object), building a chunk table (aiStack_f0).
  3. For each chunk, in reverse order, stages a record header at a pointer puVar2:
  • +0x00..+0x04: left unset by this function (must be filled earlier/elsewhere — not resolved here); in the .sav sample these bytes hold the ASCII tag "wars" + one extra byte 0xAA for the first stored object.
  • +0x05: hard-coded constant 0x09.
  • +0x06: sum-of-bytes checksum bVar5, accumulated over a runtime-resolved range [_DAT_0801aef8 .. _DAT_0801aef8+_DAT_0801aef4] (ghidra/decompiled.c:3199-3204).
  • +0x07: ones' complement of +0x06 (~bVar5).
  • +0x08: 4-byte copy of a global object/session counter *_DAT_0801ae20.
  • +0x0c: packed byte = (chunk_index*0x10) + (chunk_count-1).
  • +0x0d: the caller-supplied "mode" byte (uStack_4c, originally param_1 & 0xff).
  • +0x0e: 16-bit chunk offset.
  • +0x14: 16-bit chunk length.
  • +0x52..: the chunk's payload bytes, copied from the caller's source buffer.
  1. Also toggles an "erase marker" pair at an offset-dependent location using the literal bytes 0x55/0xAA depending on a flag at +0x40 of the per-slot table (ghidra/decompiled.c:3127-3137) — this is a free/used marker convention for the slot table itself, distinct from the per-record checksum pair.
  2. Calls FUN_0801babc(slot) then FUN_0801bb14(slot, header_ptr) to commit/verify the record.
  • FUN_0801babc (ghidra/decompiled.c:3882-3904) — write dispatcher: if a "real hardware" flag (*_DAT_0801bae0 == 1) is set, calls the hardware page-write path (func_0x0807bf14); otherwise writes into a RAM-shadowed 4 KB sector buffer (func_0x0801bbb0). This two-path design (hardware vs. RAM-shadow) is a generic engine feature (likely supporting a debug/emulated-flash build mode) and is not itself game-specific.
  • FUN_0801bb14 (ghidra/decompiled.c:3911-3942) — read-back/compare dispatcher: hardware path calls func_0x0807a808 directly (bank-addressed read, see §3.1); RAM-shadow path does a byte-by-byte memcmp-style loop against the 4 KB shadow buffer.
  • FUN_0801bb74 (ghidra/decompiled.c:3949-3964) — program/erase dispatcher: hardware path calls func_0x0807a6a8 (bank-addressed burst write); RAM-shadow path calls a plain buffer copy (func_0x0801bbb0).

            │    └─ FUN_0801b3a8()       // per-slot validity probe
            │         └─ FUN_0801b42c()

This chain is derived from direct call-site reads in ghidra/decompiled.c (lines 5173-5219, 3730+, 3368-3478) combined with ghidra/callgraph.json entries for 0x0801ab24, 0x0801b674. How mapped: every arrow above is a literal FUN_xxxx(...) call expression found in the decompiled C, not an inference from the (sparse) callgraph alone — the callgraph's indirect-jump-table gaps (UNRECOVERED_JUMPTABLE) meant most of this had to be reconstructed by reading call sites directly rather than trusting callgraph.json in isolation.

In-RAM mutation before flush: FUN_0801ab60 is the only confirmed point where the in-RAM record staging buffer (puVar2, a local/global scratch buffer — exact RAM address not resolved, likely EWRAM/IWRAM scratch passed by the caller) is mutated field-by-field before being handed to FUN_0801babc→hardware/shadow write. No other caller of the write path was found in the extracted sources; the single confirmed entry point into the allocator's write side is FUN_0801ab60, called from FUN_0801b150 (ghidra/decompiled.c:3396). The actual gameplay code that decides what data to save and when (e.g. end-of-turn, menu "Save Game") was not present in the 247-function extraction and could not be traced — this is an explicit open question (§6 / open_questions).

4.2 Checksum algorithm

Algorithm (from code, FUN_0801ab60, ghidra/decompiled.c:3199-3206):

byte sum = 0;
for (i = 0; i <= _DAT_0801aef4; i++)
    sum += *(byte*)(i + _DAT_0801aef8);
record[+0x06] = sum;        // stored checksum
record[+0x07] = ~sum;       // stored as one's-complement guard byte

This is a classic sum8 + one's-complement guard-byte pair (the complement byte lets a reader detect a torn/partial write by checking stored_sum + stored_complement == 0xFF, without needing to know the original covered range).

What is independently verified against the real .sav file (saves/cap-00-future-0.sav):

data = open('saves/cap-00-future-0.sav','rb').read()
assert data[0xF005] == 0x09                      # hard-coded header constant
assert data[0xF006] + data[0xF007] == 0xFF        # sum8 / complement pair
# -> data[0xF005] = 0x09, data[0xF006] = 0xD9, data[0xF007] = 0x26
# -> 0xD9 + 0x26 = 0xFF  ✔ CONFIRMED

Output: both assertions pass. 0xF005 == 0x09 matches the hard-coded constant the code always writes at relative offset +5. 0xF006/0xF007 (0xD9/0x26) satisfy the sum/complement invariant exactly.

What could NOT be verified: the exact byte range the sum covers. _DAT_0801aef8 (start pointer) and _DAT_0801aef4 (inclusive end index) are runtime-resolved globals with no fixed value visible in the static decompilation. An exhaustive brute-force search of every contiguous byte range inside the active save region (0xF000–0xF56A, excluding the two checksum bytes themselves) was run:

# brute force: all (start,end) pairs in [0xF000, 0xF56A), sum8 excluding 0xF006/0xF007
# target = 0xD9 (the stored sum byte)
# result: 1153 of ~67,000 candidate ranges reproduce 0xD9 — far too many to
# single out the "real" one without a runtime trace or a second sample .sav
# with different content to differentially test range boundaries.

Conclusion: the checksum mechanism (sum8 + complement, header offset +5/+6/+7) is CONFIRMED_VERIFIED. The checksum's exact covered byte range is UNKNOWN and requires either (a) a second .sav sample with different payload content to differentially narrow the range, or (b) a live memory trace of _DAT_0801aef8/_DAT_0801aef4 at the moment FUN_0801ab60 runs (see §6, fuzzing plan item 1).

No CRC16/CRC32/XOR-16 or other algorithm was found anywhere in the extracted save-path functions; sum8+complement is the only integrity mechanism present in ghidra/decompiled.c's save-write path.

4.3 End-of-chip marker

Bytes at 0xFFFE-0xFFFF: 00 55 (preceded by a long run of 0xFF). No code in the extracted sources references this location directly. HYPOTHESIS: could be an end-of-flash sentinel/version byte pair, or simply incidental non-blank leftover data from a prior write; not resolved.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of saves/cap-00-future-0.sav, loaded into a paired pre/post .ss save-state pair per the project's mandatory paired-state convention, so RAM-side effects can be inspected alongside the on-disk bytes.

  1. Pin down the checksum's covered range (resolves the biggest open question in §4.2).
  • Mutate a single byte deep inside the suspected payload region, e.g. 0xF04C (01 → 02), without touching 0xF006/0xF007.
  • Reload. If the title screen shows a "save corrupted" message, re-generates the file, or silently ignores the mutated byte, that tells us whether 0xF04C is inside or outside the checksum's covered span.
  • Repeat with mutations progressively closer to 0xF008 and progressively further toward 0xF56A to binary-search the covered range boundary.
  • Predicted effect if in range: corruption detected (reload falls back to new-game / shows an error). Predicted effect if out of range: save loads normally but the mutated byte's own (currently unknown) effect becomes visible.
  1. Checksum-repair mutation test.
  • Flip a payload byte, then recompute sum8 over each of the top 5 candidate ranges from the §4.2 brute-force list and patch 0xF006/0xF007 accordingly for each candidate.
  • Whichever repaired variant reloads cleanly identifies the true covered range. This is the single most decisive, cheap experiment available.
  1. Header +5 constant removal/corruption.
  • Mutate 0xF005 from 0x09 to another value (e.g. 0x00 or 0xFF), leaving the checksum pair untouched.
  • Predicted effect: if 0x09 is validated on load (e.g. as a record-type tag), the save should be rejected/ignored even though the sum8/complement pair is still internally consistent — this would confirm +5 is a second, independent integrity gate, not just an incidental constant.
  1. "wars" / "Advance" tag mutation.
  • Change 0xF000-0xF003 from "wars" to another 4-byte ASCII value (recomputing 0xF006/0xF007 only if range experiment #1/#2 shows these bytes are in-range).
  • Predicted effect: if this is a displayed save-slot label, the change should be visible on the in-game load/select screen; if it's an internal format tag, the save may be rejected instead.
  1. 0xF420-0xF52F sparse-table bit flip.
  • Flip one of the repeating 00 bytes in the FF FF FF 00 stride pattern to FF (making that 4-byte slot fully blank) and, separately, flip one FF to 00 elsewhere in the same stride.
  • Predicted effect: if this is an allocated-object bitmap, one direction should make the game treat a previously valid slot as empty (e.g. a mission/profile disappearing from a list), while the other should have no effect (already-blank semantics) or trigger an allocator error on next save.
  1. 0xF530-0xF56A high-entropy tail region.
  • Zero the entire region and reload.
  • Predicted effect: if this is itself a secondary checksummed block, expect a corruption/fallback response; if it's cosmetic (e.g. a cached thumbnail/RNG seed with no validation), expect normal load with at most a visual anomaly.
  1. 0xFFFE-0xFFFF end marker.
  • Overwrite 00 55 with FF FF (making the whole chip appear uniformly erased past 0xF56A) and reload.
  • Predicted effect: if this is a real end-of-store sentinel, expect altered directory-scan behavior (e.g. treating the store as "freshly erased"); if incidental, expect no change.
  1. Fresh-vs-restore control. For every mutation above, also run the unmutated file through an identical load/reload cycle first, to establish a matched-duration baseline before attributing any observed behavior change to the mutation itself (protocol-negative control, per project testing standards).

All outcomes — including "no observable effect" — must be recorded; none of the above should be treated as confirmed semantics until the predicted-vs-observed result is logged.
