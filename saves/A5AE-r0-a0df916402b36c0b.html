Offset convention (read first). The .sav file does not store the EEPROM contents in RAM byte order. Within each 8-byte EEPROM block, the file bytes are the reverse of the logical (RAM) byte order. This is not an assumption: it is the only per-block permutation (tested: raw LE, raw BE, 2-/4-/8-byte reversals) under which the decompiled checksum in FUN_08156508 verifies against the real file (Section 4). Throughout this report, logical offset = offset in the RAM-order image obtained by reversing each 8-byte block of the file; raw offset = offset in sav-00-f1492.sav as-is. Logical↔raw mapping inside a block: raw = block_base + (7 - (logical - block_base)). Block bases (0x000, 0x008, …, 0x100, …) are identical in both images.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree — CONFIRMED_VERIFIED)

  1. Physical media is a 512-byte EEPROM image (4 Kbit; the packet's "EEPROM 4K" is kilobits). The single sample is exactly 512 bytes, erased fill is 0xFF, and the only validated save structure is read as 8-byte EEPROM blocks (Section 2, 3).
  2. A 24-byte validated structure exists at logical offset 0x100 (EEPROM blocks 32–34, read as blocks 32–47). Its integrity algorithm is a seed-7 additive 16-bit sum over 11 little-endian u16 words, stored in word 11 at logical 0x116. Computed and stored values both equal 0x000D on the sample — an exact match (full Python trace in Section 4).
  3. The deserializer FUN_08156508 (0x08156508) is fully mapped: on checksum success it copies the low bytes of words 0–5 into a 6-byte RAM array, words 6/7/8/9/10 into individual RAM bytes; on checksum failure it installs defaults (array=[1,0,0,0,0,0], two bytes =2); on read error it calls the un-decompiled func_0x0816ab68. The sample is a genuine near-initial save, not the failure fallback: it differs from the defaults in words 8 and 9 (Section 5).
  4. No magic signature exists in either active span, and none is checked in code (no string literals at all in decompiled.c).
  5. The three pre-extracted "save-bus" DMA3 seeds are false positives. FUN_08155800, FUN_0815feb0, and FUN_081658c8 all write DMA3 registers (0x040000D4/D8/DC), but none targets the EEPROM window 0x0D000000; one demonstrably targets VRAM (0x06001800). They are graphics DMA, not save I/O (Section 3.1).

Static-only (CONFIRMED_STATIC — in code, not observable in the sample)

  • The bracketing helpers FUN_0816a924 / FUN_0816a998 and the block-read helper FUN_0816ab08(0x10, 2) around the load; the failure-default values; the read-error path to 0x0816ab68.

Open / hypothesis (HYPOTHESIS / UNKNOWN)

  • The save writer does not exist in the traced corpus. No function computes the seed-7 sum and stores it, no function writes EEPROM blocks, and no code anywhere touches 0x0D000000 (EEPROM), 0x0E000000 (SRAM/Flash), the Flash 0x5555/0x2AAA command addresses, or WAITCNT (0x04000204) — grep-verified over all 65 functions. The writer, the true low-level EEPROM serial/DMA3 bitstream driver, and all in-game mutation callers (level completion, options changes, …) were never executed during the traced frames (≤1620, boot/title only, per states/), so they were never decompiled.
  • The 16-byte structure at logical 0x000 (words [3,0,0,0,0,0,3,0xFFFF]) has no reader, writer, or checksum in the corpus. It is a hypothesis-grade second block (Section 2, 5).
  • Semantic names of all fields are unknown. Only their types, sizes, RAM destinations (as Ghidra literal-pool symbols, whose target values are not recoverable from the decompiled text), and observed values are known. All gameplay meanings suggested below are labelled hypotheses.
  • RAM mirror addresses are unknown. decompiled.c references RAM only through ROM literal-pool symbols (iRam0815665c, puRam08156660, … at ROM 0x081566xx); the pointer values stored at those ROM addresses are not present in the corpus, so no 0x02xxxxxx/0x03xxxxxx address can be honestly assigned. Fields below use ram_addr: null with the literal symbol recorded as evidence.

Why not HIGH: one of two active blocks, the entire write path, and all field semantics remain unproven. Why not LOW: media, geometry of the main block, its checksum, its deserializer, and its defaults are byte-exact verified against the real save.

Timing evidence from states/

sav-00-pre.ss (frame 1458) differs from sav-00-post.ss/gameplay.ss (frame 1492, identical hashes 3604704ce8c6e173), and the packet probe reports save_preserved: true. The 512-byte image above therefore existed by frame 1492 and survived a cold reload. This is consistent with both blocks being written once early (first-boot formatting/initialisation) and then only read — which also explains why no writer appears in a trace that ends at frame 1620: any later writer (e.g. on level completion) was never exercised.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O drivers — and the three DMA3 false positives

A grep over all 65 decompiled functions finds zero references to 0x0D000000 (EEPROM), 0x0E000000 (SRAM/Flash), 0x5555, 0x2AAA, or 0x04000204 (WAITCNT). The only save-adjacent MMIO in the corpus is DMA3 (0x040000D4 = DMA3SAD, 0x040000D8 = DMA3DAD, 0x040000DC = DMA3CNT), used by exactly the three pre-extracted seeds. None of them can be the EEPROM driver, because a GBA EEPROM transfer must use DMA3 with one endpoint at 0x0D000000 and a bit-serial length (9/17-bit command + data), and none does:

Conclusion: the true EEPROM serial driver (DMA3 ↔ 0x0D000000) and any SRAM byte-copy / Flash command-sequence driver are absent from the traced corpus. This game is EEPROM-only per the packet and the 512-byte sample; there is no evidence of SRAM or Flash support in code or data.

3.2 The verified reader / deserializer chain (Slot B)

FUN_08156508 (0x08156508) — load + validate + deserialize (the only proven save function)

No caller in callgraph.json (reached indirectly — via a function-pointer/jump table, as are most top-level functions in this corpus; the graph lists it with callers: []). Its body, mapped line-by-line:

3.2.1 FUN_0816ab08 (0x0816ab08) — EEPROM block-read helper

Signature from the caller: FUN_0816ab08(count=0x10, page=2) returns char (0 = success). Body: for i in 0..count-1, calls the indirect thunk func_0x0817faf0(block_index = i + page*16, dest) with dest advancing by 8 bytes per block, returning the first non-zero result immediately. With (0x10, 2): blocks 32–47, 128 bytes into the RAM buffer. The 8-byte stride and 6-bit-range block numbering (32–47 of 64) are exactly GBA EEPROM addressing (each EEPROM address selects 8 bytes). The thunk at 0x0817faf0 is a one-instruction indirect jump ((*pcRam0817faf8)()) whose target — the actual per-block EEPROM/DMA3 routine, almost certainly in the untraced library region alongside FUN_0817f4b0 — is not in the corpus. How mapped: argument arithmetic in FUN_08156508 + stride/return-value behaviour here; the per-block transfer itself is CONFIRMED_STATIC for its interface, UNKNOWN for its implementation.

3.3 Bracketing helpers

  • FUN_0816a924 (0x0816a924), called immediately before the read: clears DISPCNT bit 12 (uRam04000000 &= 0xEFFF), calls FUN_0817d738 (sound-engine init, which calls FUN_0817d6dc + func_0x0817e004), copies a two-word value into a RAM struct (puRam0816a988), calls func_0x0817facc(3, struct+6), then sets *puRam0816a990 = 0, *puRam0816a994 = 1.
  • FUN_0816a998 (0x0816a998), called immediately after the read: sets DISPCNT bit 12 (|= 0x1000, OBJ enable), writes 3 to 0x04000200 (REG_IE), restores pointer fields (puRam0816a9fc, puRam0816aa00 = 1, …).

These two look like a suspend/resume pair around the EEPROM access (display/sound/interrupt state saved, then restored) — a common pattern because EEPROM DMA3 transfers must not be interrupted by other DMA. Their exact purpose is HYPOTHESIS; that they bracket every Slot B load is CONFIRMED_STATIC. Neither mutates any save field.

3.4 Serialization / writer — absent

No traced function: (a) computes the seed-7 sum except FUN_08156508 itself (verification only — it never stores the result), (b) assembles u16 words from the RAM byte fields, (c) calls any EEPROM-write counterpart of FUN_0816ab08, or (d) touches 0x0D000000. The only candidate is the un-decompiled func_0x0816ab68 (0x0816ab68), called from FUN_08156508 only when the read itself returns an error — plausibly "format/initialise EEPROM" or "write defaults", but with no body available its role is UNKNOWN. Likewise, no in-game caller that mutates the RAM fields (puRam08156660 array, puRam08156668/70/74, puRam0815666c) before a flush was traced: within decompiled.c those literal symbols are written only by FUN_08156508. Other functions referencing the same RAM addresses would use different literal-pool symbols, and the target values needed to join them are not in the corpus — so mutation callers are honestly unmapped, not absent from the game.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signatures

None. Neither active span contains an ASCII or constant magic: Slot B logical bytes are 01 00 00 00 … 02 00 02 00 … 01 00 … 0D 00 (small integers, no header), Slot A is 03 00 … 03 00 FF FF. Code-side, decompiled.c contains no string literals and no multi-byte constant comparison against the save buffer — validity rests entirely on the checksum below. magic_signatures in save-format.json is therefore an empty list. The 0xFFFF word 7 of Slot A is erased-fill, not a magic (it is the untouched second half of EEPROM block 1).

4.2 Checksum algorithm (Slot B) — exact

From FUN_08156508 (decompiled.c lines 380–389):

uVar12 = 7;                                   // seed
uVar11 = 0;
do {
    iVar1 = uVar11 * 2;
    uVar11 = uVar11 + 1 & 0xff;
    uVar12 = (int)(((uint)*(ushort *)(buf + iVar1) + (uVar12 & 0xffff)) * 0x10000) >> 0x10;
} while (uVar11 < 0xb);                       // 11 words: buf+0x00 .. buf+0x14
if ((uint)*(ushort *)(buf + 0x16) == (uVar12 & 0xffff)) { /* valid */ }
  • Algorithm: sum16_le — additive sum of little-endian u16 words, seed = 7, truncated to 16 bits each iteration (the *0x10000 >> 0x10 idiom is a 16-bit truncation with sign extension; the final & 0xffff comparison makes it equivalent to mod-65536 addition for all inputs here).
  • Covered range: logical 0x100–0x115 inclusive (words 0–10, 22 bytes).
  • Stored at: word 11, logical offset 0x116 (2 bytes, LE 0x000D). In raw file bytes, block-reversal places these at raw 0x110–0x111 as 00 0D (raw LE word 0x0D00).
  • Endianness: words are LE in the logical (RAM) image; the file image is per-8-byte-block reversed (Section 2 convention). There is no complement, XOR, CRC, or final negation.

6. Save Fuzzing & Counterfactual Verification Plan

Reload method for every test: place the mutated sav-00-f1492.sav alongside the emulator, restore sav-00-pre.ss (frame 1458, pre-save) or cold-boot, advance past frame 1492, and observe (a) title/continue UI, (b) level/character select state, (c) the RAM fields if a debugger is attached (watch the targets of literals 0x08156660/64/68/6C/70/74 — resolve the pointer values from ROM at runtime, since they are not in the corpus), and (d) whether the game rewrites the .sav (which would reveal the untraced writer and let it be traced). All offsets below are raw file offsets (what an editor must change); checksum repair is specified in logical terms with the exact raw bytes to write.

Checksum repair procedure (needed by tests F2–F5): reverse each 8-byte block of the mutated file to get the logical image; compute acc = (7 + sum(words 0..10)) & 0xFFFF at logical 0x100; store acc as LE at logical 0x116; reverse each 8-byte block back. Reference implementation:

import struct
d = bytearray(open('sav-00-f1492.sav','rb').read())
L = bytearray(b''.join(bytes(d[i:i+8][::-1]) for i in range(0,512,8)))
# ... mutate L at logical offsets ...
acc = 7
for i in range(11): acc = (acc + struct.unpack_from('<H', L, 0x100+i*2)[0]) & 0xffff
struct.pack_into('<H', L, 0x116, acc)
out = b''.join(bytes(L[i:i+8][::-1]) for i in range(0,512,8))
open('sav-00-f1492.sav','wb').write(out)
