1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Structure and integrity are proven to a high standard. Field semantics are mostly unproven. Both samples are near-blank, so most payload bytes are zero in every observed state.

Proven by both code and .sav bytes:

  • The save medium is byte-serial EEPROM accessed at 0x0D000000 through DMA3.
  • The physical file is 512 bytes.
  • One save image starts at EEPROM block 0.
  • The game writes 176 bytes (0xB0) and reads back only 144 bytes (0x90).
  • The logical (in-RAM) image is not byte-identical to the physical EEPROM file.

Each 8-byte EEPROM block is stored byte-reversed relative to the logical image.

  • Logical offset 0x00 holds signature 0x1234 (little-endian u16).
  • Logical offset 0x8C holds 0x000B in both samples.
  • Logical offset 0x8E is a writer-stamped validity signature.

It is 0x0000 in the cleared save and 0x9797 in the committed save.

  • There is no stored data checksum (no sum, XOR, or CRC over the payload) in the save path.

Integrity is two signatures plus per-block read-back verification after writing.

  • Mutating physical 0x88 in the probe reverted the save.

Physical 0x88 is the high byte of the logical 0x8E validity signature. That probe result matches the code path exactly.

Still open:

  • Exact RAM addresses of the save buffers and game-state structs.

The Ghidra export names literal-pool slots (_DAT_08015ff8, _DAT_080004c4, …) but does not export their values, so no 0x02xxxxxx/0x03xxxxxx address can be stated honestly.

  • Gameplay meaning of logical fields at 0x02, 0x04, 0x08, and the 125-byte blob at 0x0C..0x88.

They are zero in both samples.

  • Why the writer emits 0xB0 bytes while the reader consumes 0x90.

The trailing 0x20 bytes are written but never read by any traced reader.

2. Physical Media, Slot Geometry & Redundancy

Media

  • SDK tag in ROM (per packet): EEPROM_V124@524712.
  • Observed media label: EEPROM 4K, i.e. 4 Kbit = 512 bytes.
  • Both .sav files are exactly 512 bytes.
  • cap-00-future-0.sav SHA-256: 11979f0a06cd18e38e53e05eafa20cf19270d398d17f0749a82a9ea3aae875a7
  • cap-01-future-1.sav SHA-256: 5f822d15e513657134f7cd80fcd9181bcd5ca3b75fd963729eb60f4cb5104a8b
  • Fill byte outside the written image is 0xFF.

Bytes 0xB0..0x1FF are 0xFF in both files (336/336 bytes verified in Python).

Geometry

  • EEPROM is transferred in 8-byte (64-bit) blocks.
  • Bulk write length: 0xB0 = 176 bytes = 22 blocks, EEPROM block addresses 0..21.
  • Bulk read length: 0x90 = 144 bytes = 18 blocks, EEPROM block addresses 0..17.
  • Physical active range in the files: 0x00..0xAF.
  • Logical valid range: 0x00..0x8F.

The reader stops at 0x90, which is exactly the end of the 0x8E signature.

  • Logical 0x90..0xAF is written, never read, and zero in both samples.

Treat it as buffer slack / reserved, not as a second slot.

Logical ↔ physical mapping (verified)

Within each 8-byte block, physical order is the reverse of logical order:

physical_offset = block_base + (7 - (logical_offset mod 8))
block_base      = logical_offset & ~7

Equivalently: reverse every consecutive 8-byte group of the .sav to obtain the logical RAM image, and vice versa.

Two independent fields prove this mapping:

  1. Logical 0x00..0x01 becomes physical 0x06..0x07 = 12 34, giving logical LE u16 0x1234 — the value the writer stamps and the reader compares.
  2. Logical 0x8C..0x8D becomes physical 0x8A..0x8B = 00 0B, giving logical LE u16 0x000B — exactly the default (*(u16 *)(struct + 8) = 0xB) that FUN_080003d4 writes and FUN_08015f98 copies to save offset 0x8C.

A naive direct-offset reading misplaces both: it would put a fake magic at physical 0x06 and a fake field at physical 0x8A/0x8B. All offsets in the field map below are logical unless labelled physical.

Slots, copies, counters, selection

  • One slot only. Every traced bulk read and write uses EEPROM address 0:
  • Load: FUN_08015f84 → FUN_08015df4(0, buffer, 0x90).
  • Save: FUN_08015f98 / FUN_0801600c → FUN_08015eb8(buffer, 0, 0xB0).
  • No backup copy, mirror slot, or A/B ping-pong was found in code or bytes.
  • No generation/sequence counter was found.

No traced writer increments any save field. Logical 0x8C = 0x000B is constant across both samples and is set as a literal default, so it is not a counter.

  • Selection rule (there is only one candidate, so this is a validity rule, not a slot choice):
  1. Read 144 bytes.
  2. If logical u16[0x00] != 0x1234, zero the read buffer (FUN_08015df4).
  3. At boot, if logical u16[0x8E] != <expected signature>, discard, write a cleared save via FUN_0801600c, and reload (FUN_08000408).
  4. If u16[0x8E] matches, copy the 125-byte blob at logical 0x0C..0x88 into the RAM blob.

3. Save Writer, Reader & Caller-Chain Architecture

How callers were mapped

Two sources were cross-checked:

  • ghidra/callgraph.json (119 nodes).
  • Textual call sites in ghidra/decompiled.c (FUN_… / func_0x… calls with line numbers).

The callgraph is incomplete for the high-level save functions. For example it lists FUN_08015eb8 with callees [], while decompiled.c:4735/4745 shows it calling the EEPROM write and verify functions (as func_0x08018854 / func_0x080189c8 stubs), and it lists FUN_08015f98/FUN_0801600c with no recorded caller for the former beyond the graph edge that does exist. Where the two disagreed, the textual call site in decompiled.c was treated as authoritative and the callgraph as corroboration. Unrecovered jumptables (UNRECOVERED_JUMPTABLE) hide some dispatch, so root functions with no static caller are identified as state-machine/table entries, not as dead code.

Low-level hardware I/O

FUN_08018724 — DMA3 transfer to/from EEPROM (0x0D000000)

void FUN_08018724(undefined4 param_1 /*src*/, undefined4 param_2 /*dst*/, uint param_3 /*count*/)
{
  uVar1 = *_DAT_08018784; *_DAT_08018784 = 0;                 // save & clear IRQ/DMA ctrl
  *_DAT_08018788 = *_DAT_08018788 & (ushort)_DAT_0801878c
                 | *(ushort *)(*_DAT_08018790 + 6);           // DMA control bits
  *_DAT_08018794 = param_1;                                   // DMA3 source (0x040000D4 family)
  *_DAT_08018798 = param_2;                                   // DMA3 dest
  *_DAT_0801879c = param_3 & 0xffff | 0x80000000;             // DMA3 count + enable

  *_DAT_08018784 = uVar1;                                     // restore
}

This is the only function that moves bits between RAM and 0x0D000000. Callers: FUN_080187a4, FUN_08018868 (callgraph agrees).

FUN_080187a4 — EEPROM read one 8-byte block

  • Signature: FUN_080187a4(uint block_addr, int out_buf).
  • Bounds check: block_addr < *(u16 *)(eeprom_type + 4).
  • Builds the serial address bitstream on the stack (address bits shifted out MSB-first, then start bits 1,1).
  • Sends it with FUN_08018724(stack, 0x0D000000, addr_bits + 3).
  • Clocks data back with FUN_08018724(0x0D000000, stack, 0x44) (68 halfword transfers = 64 data bits + turnaround).
  • Reassembles four u16 words bit-by-bit (uVar4 = uVar4 << 1 | *puVar5 & 1) and stores them in reverse word order (puVar6 = (ushort *)(param_2 + 6), decrementing).

Together with the emulator's bit packing this produces the verified per-8-byte reversal between the logical image and the .sav file.

FUN_08018868 — EEPROM write one 8-byte block; FUN_08018854 — wrapper

  • FUN_08018868(uint block_addr, ushort *in_buf, char wait_flag).
  • Expands each of the 4 input u16s into 16 serial bit cells, prepends the block address bits and start/stop cells (*puVar6 = 0; puVar6[-1] = 1).
  • Sends addr_bits + 0x43 cells via FUN_08018724(stack, 0x0D000000, …).
  • Then waits for the EEPROM programming cycle: it polls 0x0D000000 & 1 and a timer (_DAT_08018954), accumulating elapsed ticks and bailing out when the total exceeds 0x88.

That 0x88 is a timeout tick count, not a save offset and not a checksum constant. Do not confuse it with physical probe offset 0x88.

  • FUN_08018854(param_1, param_2) is a thin wrapper: func_0x08018868(param_1, param_2, 1).

FUN_080189c8 — write-verify (read-back compare)

  • FUN_080189c8(ushort block_addr, short *expected).
  • Reads the block back with FUN_080187a4(block_addr, stack[4]).
  • Compares all 4 shorts; returns 0x8000 on first mismatch, 0 on success.
  • Note: FUN_08015eb8 calls it as func_0x080189c8(uVar4, param_1) using the block index as address.

That is only correct because every caller passes EEPROM base 0. It would verify the wrong blocks for a non-zero base; with base 0 it is exact.

False seeds excluded

  • FUN_08018b34 (listed as an MMIO seed in save_related_functions.c) is a signed remainder routine (__modsi3-style). It touches no MMIO and no save data.
  • FUN_08018a9c is the matching signed divide, FUN_08018a60/08018a64 are indirect-jump stubs, and FUN_08018d3c is a word-copy/memcpy-style routine used for RAM copies (e.g. FUN_08001384 line 658), not for EEPROM I/O.
  • FUN_080186c8 is SWI 0x0B (CPU set / interrupt helper) used by unrelated init code.

     │    └─ copy 125 bytes read_buf+0x0C → RAM blob (iRam08000550)
     └─ else
          ├─ func_0x0801600c() → FUN_08015eb8(image, 0, 0xB0)   write cleared save

How mapped: FUN_08000408 body at decompiled.c:152-166; callgraph confirms 080010e8 → 08000408 and 08000408 → 080003d4. RAM mutation in this chain: defaults are installed before the load, and the loaded blob overwrites the blob only when the 0x8E signature passes. If it fails, the cleared image (validity 0) is written back, so the next boot takes the same branch and keeps the default (zero) blob — matching cap-00, which is exactly a cleared-save image that nevertheless carries the 0x1234 header because FUN_08015eb8 stamps it unconditionally.

How mapped: callgraph 08001b5c → 08001384; textual call at decompiled.c:652. Chain D — clear-save triggers

  • Boot invalid-signature path: FUN_08000408 → FUN_0801600c (Chain A).
  • No other static caller of FUN_0801600c exists in the export.

A user-facing "delete save" entry, if any, would have to arrive through an unrecovered jumptable and cannot be claimed.

The literal-pool values (_DAT_08015f80, _DAT_08015eb4, _DAT_08016008, _DAT_080004c8) are not exported as numbers. Their equality with the observed 0x1234 / 0x9797 is inferred from the .sav bytes plus the stamp/compare code shape, and is labelled accordingly in the field map. The 0x9797 byte palindrome means this one field cannot by itself distinguish byte order; 0x1234 and 0x000B carry the byte-order proof.

There is no data checksum — proof

Three independent lines of evidence:

  1. Code: neither serializer computes anything over the payload.

FUN_08015f98 copies fields and loads the 0x8E value from a literal ((short)_DAT_08016008). There is no accumulation loop, table CRC, or XOR fold anywhere in FUN_08015f98, FUN_0801600c, FUN_08015eb8, or FUN_08015df4. The only load-side tests are the two signature compares above. The only other integrity mechanism is read-back verification in FUN_080189c8, which compares EEPROM content against RAM and stores nothing.

  1. Counterfactual in the samples: the payloads of the two files are byte-identical except at logical 0x8E..0x8F.

Any data-dependent checksum over the same payload would have to take the same value in both files. The stored values differ (0x0000 vs 0x9797), and the difference tracks the writer path (clear vs serialize), not the data.

  1. Numeric verification: every standard candidate computed over the logical image fails to reproduce 0x9797 (see output below).

Therefore the correct classification for the checksums entry in save-format.json is a custom two-signature validity scheme, not sum8/sum16/crc. Anyone editing a save does not need to repair a checksum; they must preserve/restore the two signatures (see §6).

def derev(d):
    out = bytearray(len(d))
    for i in range(0, len(d), 8):
        b = d[i:i+8]; out[i:i+len(b)] = b[::-1]
    return bytes(out)
for name in sorted(p.name for p in pathlib.Path('saves').glob('*.sav')):

Probe corroboration

Packet probe: mutation at physical 0x88, integrity_check_confirmed: true, reverted_to_blank_on_mutation: true, save_rewritten_after_mutation: true, visual_delta_after_mutation: false. Physical 0x88 maps to logical 0x8F, the high byte of the 0x8E validity signature. Corrupting it makes Chain A take the invalid branch: cleared save written (save_rewritten_after_mutation), gameplay state remains the zero defaults (visual_delta_after_mutation: false on an already-blank profile). This is fully consistent with the code and inconsistent with a payload-checksum reading, under which a mutation at a payload byte would have been the natural probe target.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test:

  • Work on a copy of cap-01-future-1.sav (the committed save). Keep cap-00 as the cleared-save reference.
  • Mutate physical offsets in the file. Convert with: physical = (logical & ~7) + (7 - (logical & 7)).
  • No checksum repair exists or is needed. The only repair is signatures: logical 0x00 = 0x1234 (physical bytes @ 0x06..0x07 = 12 34) and, for a save that should be accepted as committed, logical 0x8E = 0x9797 (physical @ 0x88..0x89 = 97 97).
  • Reload from a paired emulator state / cold boot and observe: (a) whether the file is rewritten, (b) whether it reverts to the cap-00 cleared pattern, (c) RAM blob contents, (d) any gameplay/UI change.

Open questions

  • Exact RAM addresses behind _DAT_08015f94, _DAT_08015ff8, _DAT_08015ffc, _DAT_08016000, _DAT_08016004, _DAT_080004c4, and iRam08000550. Resolving the literal pool (e.g. from the ROM or a fuller Ghidra export) would pin every ram_addr in the field map.
  • Whether _DAT_08016008 and _DAT_080004c8 are literally 0x9797 in ROM, or whether 0x9797 is derived from a RAM variable at stamp time. The decompiled shape (constant load) favours a literal.
  • Gameplay semantics of save fields 0x02, 0x04, 0x08, 0x8C, and the internal layout of the 125-byte blob. Both samples are zero there; a progressed save is needed.
  • Why the image buffer / write length is 0xB0 when the logical format is 0x90. Possibilities: fixed SDK buffer size, reserved expansion, or an unobserved second reader.
  • The gameplay trigger names for FUN_08001384 (committed-save state) and FUN_0800e3e8 (game-state mutator). Both are reached through unrecovered dispatch in this export.
  • Whether FUN_080186dc(0x40) also probes for EEPROM presence/type at runtime (its register writes are unexported), which would matter for behaviour on 8 Kbit parts.
