Release key B8QE-r0-55c61cd0ab12c4c8 · Game code B8QE / header family B8Q · ROM SHA-256 55c61cd0ab12c4c8e1cd4f7888f8f54e0f977816b17b789ef0706b319c495cae · Community comm-006

All findings below derive only from the workspace corpus: PACKET.md, the two binaries in saves/, decompiled.c, save_related_functions.c, and callgraph.json, plus standard GBA hardware addresses supplied in the packet. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • The medium is a 512-byte (4 Kbit) EEPROM, SDK tag EEPROM_V124, erased/fill byte 0xFF.
  • The file is one 24-byte global header at 0x00–0x17 followed by two independent 240-byte slots at 0x18–0x107 and 0x108–0x1F7, with 8 unused trailing bytes at 0x1F8–0x1FF.
  • The header starts with the 8-byte ASCII magic 1100ABGP. The code compares exactly those 8 bytes on load.
  • The integrity algorithm is a negated 16-bit additive checksum: the sum (mod 2^16) of all twelve u16 words in a block, including the stored checksum word, must be zero. The stored word is at the last two bytes of the block and equals (-sum_of_all_preceding_words) & 0xFFFF. On the physical EEPROM image the words must be read big-endian (MSB first), which is the serial EEPROM representation; both sample files verify exactly, and the natural little-endian reading is rejected (it yields 0x01FE, not zero). See §4 for the reproduction output.
  • Both captured slots are blank/invalid: each contains only its 8-byte zeroed clear marker and 0xFF elsewhere, and each fails the same sum-to-zero test (0xFF8C). There is therefore no populated gameplay payload in this corpus to map.

Static-only (CONFIRMED_STATIC, from code but not observable in a populated sample):

  • The full EEPROM driver stack (DMA3 serial transfer, read, write, verify, retry, type identification) and the header/slot manager functions and their caller chains (§3).
  • The slot checksum uses the identical sum-to-zero primitive over 120 u16 words, stored at slot offset +0xEE.
  • The boot init path rewrites a default header and clears both slots when the header fails validation.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • The semantics of header bytes 0x08–0x15 (except that 0x0C and 0x10 are the only bytes that changed between captures, in a checksum-preserving +1/−1 pair). No populated slot exists, so all slot payload fields at offsets 0x20 onward are unknown.
  • Exact RAM mirror addresses: Ghidra left every global as an unresolved _DAT_…/iRam… symbol, so no 0x02xxxxxx/0x03xxxxxx address can be stated honestly. The RAM structures are identified by the functions that own them (§3, §5).
  • The direct caller of the boot entry FUN_0802b82c: no direct call exists in the 288-function corpus or callgraph; it is reached indirectly (every function ends in an UNRECOVERED_JUMPTABLE, so indirect/state-table dispatch is invisible to this corpus).

Why not HIGH: the header, geometry, driver, and checksum are verified, but there is no valid populated slot sample, so the actual gameplay payload layout is completely unobserved.

Geometry proof:

  • Header size 0x18: FUN_0802b7d0 and FUN_0802bc4c read/write exactly 0x18 bytes at EEPROM offset 0 and sum 12 u16 words (0xC iterations).
  • Slot size 0xF0 and stride: FUN_0802bbe0(param) reads at EEPROM offset param * 0xF0 + 0x18 for 0xF0 bytes; FUN_0802b82c writes the clear marker at 0x18 and then 0x18 + 0xF0 = 0x108; FUN_0802b82c also allocates the slot RAM buffer with FUN_08025028(0xF0).
  • Slot count = 2: the loader FUN_0802bb44 loops slot indices 0 and 1 only (if (1 < uVar7) exit after the second iteration). 0x18 + 2*0xF0 = 0x1F8, leaving exactly the observed 8 trailing bytes; a third slot cannot fit.
  • Observed bytes match the geometry exactly: the only non-0xFF regions are 0x00–0x1F (header plus slot 0's 8-byte clear marker; bytes 0x14–0x15 are 0xFF inside the header's sentinel word) and 0x108–0x10F (slot 1's clear marker).

Redundancy and selection rules:

  • No mirroring or backup copy exists. There is a single header and two independent gameplay slots; no duplicate header, no A/B generation pair, and no copy-selection-by-sequence logic anywhere in the traced code.
  • The header is protected by rewrite-if-different, not by a backup: FUN_0802b764 recomputes the header checksum in RAM, compares all 24 bytes (6 u32 compares) against EEPROM, and rewrites EEPROM only when they differ.
  • The two slots are alternative save games, not redundant copies of each other. At boot, FUN_0802bb44 loads each slot independently, validates its checksum, and marks a per-slot validity flag (descriptor byte at slot-descriptor +0x2C); an invalid slot's 8-byte descriptor is zeroed, a valid slot is adopted. Selection is therefore per-slot validity, never newest-wins.
  • Generation/sequence counters: none found. No field is incremented on each save or compared across copies. The only values that changed between the two captures are header bytes 0x0C (0x00 → 0x01) and 0x10 (0x10 → 0x0F), a coupled +1/−1 pair that preserves the header checksum (see §4); whether either is a counter is a hypothesis, not a generation mechanism (nothing in code compares them across copies).
  • Write reliability is provided at the driver level instead of by redundancy: writes are verified by read-back compare (FUN_080413c4) with up to 3 additional retries in FUN_08012768, and reads likewise retry up to 3 times in FUN_08012700.

3. Save Writer, Reader & Caller-Chain Architecture

Every function below is Thumb code in the 0x08xxxxxx ROM image. Two tracing methods were used and are stated per chain: (a) direct func_0x…/FUN_… call sites in decompiled.c, and (b) the callers/callees edges in callgraph.json. Both agree wherever the callgraph has edges. The callgraph is incomplete by construction: every function terminates in an unrecovered jump table, so indirect calls are missing from it; where the two disagree, the decompiled call site wins. RAM globals appear only as unresolved _DAT_0802xxxx symbols (the literal pointer values were not recovered), so RAM mirrors are named by their owning function, not by address.

How each caller mutates the in-RAM save struct before flushing:

  • FUN_0801d720 is the only gameplay-side header mutator in the corpus. Before calling FUN_0802b764, it copies fields from a second RAM object (behind _DAT_0801d790) into the header struct (behind _DAT_0801d78c): struct bytes +8 and +9 from source +0x24/+0x25, byte +10 from source +0x27, byte +11 set to constant 1, byte +13 merged as (old & 0x7F) | (source_byte(+0x26) << 7), byte +17 from source +0x48, and the u16 at +12 conditionally OR-ed with flag 0x400 when the source word at +0x14 has bit 0x400 set. It also calls FUN_08035098/FUN_080350a4 around the flush (outside the save corpus). Because the EEPROM image stores each u16 MSB-first (§4), RAM byte offsets +12/+13 and +16/+17 correspond to .sav bytes 0x0D/0x0C and 0x11/0x10 respectively if the pair is treated as one u16; treated as individual bytes, the mutated .sav bytes 0x0C and 0x10 are the high bytes of those two words. The exact byte-vs-word correspondence cannot be resolved further from this corpus (the RAM pointer literals are unrecovered), so §5 records both mappings and marks semantics as hypotheses.
  • FUN_08022f5c, the sole caller of FUN_0801d720 (callgraph edge and textual call site agree), reaches it on one branch of a state dispatch: it copies a mode byte into the source object (+0x27), calls FUN_08037570 (mode set), and when a status word masked with 0xFFFFFF7F is not 7 it sets state fields (+8 = 2, +0xC = 0, +0x10 = 2, +0x14 = 0x10), calls FUN_0802551c(2, 0, 0xC) and FUN_0802d8f0(0x3F), then FUN_0801d720. It is a menu/state transition handler; its own caller is not in the corpus.
  • No function in the corpus writes a populated slot: the only slot EEPROM writes are the 8-byte clear markers in FUN_0802b82c. A gameplay slot-save function either was not traced into this 288-function corpus or dispatches indirectly to FUN_08012768 with a slot offset; this is stated as an open question rather than guessed.
  • Header template initialisation in FUN_0802bc4c mutates RAM by memcpy from ROM, then writes the checksum word at +0x16 (_DAT_0802bc88[0xB] in u16 indexing) before the EEPROM write; FUN_0802b764 does the same at byte offset +0x16 after zeroing it first. Both produce the identical sum-to-zero invariant.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Offset 0x00, 8 bytes, ASCII 1100ABGP (31 31 30 30 41 42 47 50).
  • Verified in sav: present identically in both samples.
  • Verified in code: FUN_0802b7d0 compares the first 8 bytes of the loaded header against an 8-byte ROM template, but only after the checksum passes; FUN_0802bc4c writes that template (via the ROM default header) when initialising. A header failing either test is treated as blank and reinitialised by FUN_0802b82c. This matches the packet's cold-reload probe: mutating byte 0x0C (checksum-covered) caused the save to be reverted/rewritten as blank.

Checksum formula

covered block      : header 0x00–0x17 (12 words) or one slot (120 words)
word interpretation: u16, big-endian in the .sav image (MSB-first serial EEPROM order);
                     equivalently the little-endian u16 array in RAM
stored field       : last word of the block — header offset 0x16, slot offset +0xEE
formula            : stored = (-(sum of all preceding u16 words)) mod 2^16
validity rule      : (sum of ALL u16 words in the block, including stored) mod 2^16 == 0

Decompiled proof:

  • Primitive FUN_0802bc28: sVar1 = 0; for (n = param_2 >> 1; n; n--) sVar1 += *param_1++; — a plain 16-bit additive sum, no seed, no complement step, no CRC polynomial, no XOR.
  • Store side, FUN_0802bc4c: after copying the template and summing its 12 words, _DAT_0802bc88[0xB] = -sVar2; — word index 11 = byte offset 0x16. FUN_0802b764 does the same at byte offset +0x16 after first zeroing that word, then compares the whole block.
  • Check side, FUN_0802b7d0 (header, inline 12-word sum, requires sVar2 == 0 before the magic compare) and FUN_0802bbb4 (slot, FUN_0802bc28(buf, 0xF0) == 0).

Endianness: the code sums RAM u16 values (little-endian CPU). In the .sav image the same test only passes when the words are read big-endian, because the EEPROM driver clocks data MSB-first (FUN_080411a0 reassembles each word by shifting received bits in from the LSB side; FUN_08041264 expands each word MSB-first). Reading the samples little-endian gives 0x01FE for both headers — a clean rejection of the LE interpretation, not a near miss.

Interpretation of the inter-sample diff: byte 0x0C is the high byte of header word 6 (0x0000 → 0x0100) and byte 0x10 is the high byte of word 8 (0x1005 → 0x0F05). The +0x0100 and −0x0100 changes cancel, so the checksum word (0x0100) and the sum-to-zero invariant are unchanged between captures. This is precisely why the packet's profile flags 0x0C and 0x10 as a coupled candidate span: they are two halves of one checksum-preserving update, not two independent checksums. It also confirms the checksum covers the whole header: a lone mutation at 0x0C (the packet's probe) breaks the sum (0x0100 ≠ 0) and the game discards the save.

Slot checksum status: both slots in both files are invalid (0xFF8C), consistent with the boot code path that wrote only their 8-byte zero clear markers onto erased (0xFF) EEPROM. Their stored last word reads 0xFFFF (erased), while a valid blank-payload slot would require 0x0073 given the current preceding words.

6. Save Fuzzing & Counterfactual Verification Plan

No emulator save states (states/ is empty) accompany this corpus, so every test below is specified as: patch the .sav, repair the checksum where stated, cold-boot, and observe. "Repair" always means recomputing the negated sum-to-zero word of the affected block: for the header, stored@0x16 = (-sum of BE u16 words 0..10) & 0xFFFF, stored big-endian; for a slot, the same over its 119 preceding words at slot offset +0xEE. Predictions follow from FUN_0802b82c/FUN_0802b7d0/FUN_0802bb44: a header failing checksum or magic is replaced by the default header and both slots are re-cleared (first 8 bytes zeroed); a slot failing its checksum is marked invalid and its descriptor zeroed while the other slot is unaffected.

RAM-side confirmation for tests 2–5 (when a debugger or save state is available): after boot, the header RAM struct (the object read by FUN_08012700(0, 0x18, …) in FUN_0802b7d0) must contain the patched words in little-endian form — i.e. .sav bytes 0x0C–0x0D appear byte-swapped in RAM. Observing that swap directly would close the one remaining static-only link (the unrecovered _DAT_ pointer values) and pin the RAM mirror address.

Open questions

  • What are the semantics of header bytes 0x08–0x15, in particular the coupled 0x0C/0x10 pair and the 0xFFFF word at 0x14?
  • Where is the gameplay slot-write function (populate payload, compute slot checksum at +0xEE, call FUN_08012768 at a slot offset)? It is absent from the 288-function corpus; a valid populated slot sample or a wider trace is required.
  • What are the literal RAM addresses behind the _DAT_0802b7c0/_DAT_0802b800/_DAT_0802bc88 header struct and the save-manager global (+0x18 slot buffer, +0x34 active pointer)? Recovering the pointer literals from ROM would convert every "unresolved" RAM mirror above into an address.
  • Who calls FUN_0802b82c (boot init) and FUN_08022f5c (state dispatch)? Both are reached indirectly; the jump tables were not recovered.
  • What does FUN_0801e358 (per-valid-slot post-load hook, called by FUN_0802bb44) do with the adopted slot buffer? Its body is outside the corpus and it likely defines which payload fields are consumed first.
