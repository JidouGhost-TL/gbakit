1. Executive Summary & Overall Confidence

Overall Confidence: LOW–MEDIUM

What was proven (code + byte evidence agree):

  • The save medium is battery SRAM mapped at 0x0E000000, 32768 bytes (32 KB), fill byte 0x00.
  • A 16-byte ASCII tag, byte-identical to CASTLEVANIA2-010, occupies file offset 0x0000-0x000F in both sample .sav files, and a dedicated 16-byte compare routine (FUN_08001094) exists in code whose structure (read 16 bytes from 0x0E000000, byte-compare loop) matches this exactly.
  • A single byte at file offset 0x1AFC is the only other byte that differs from the 0x00 fill value across the two capture snapshots (0x00 → 0x01), and this same offset is flagged by the automated cold-reload mutation probe (probe_offset_hex: 0x1AFC) as not protected by any detectable integrity check (integrity_check_confirmed: false).
  • A systematic Python search (Section 4) found no sum8/xor8/sum16 checksum over any plausible byte range of either .sav file that matches any candidate "stored checksum" byte — consistent with the probe's negative finding. We conclude no checksum/CRC is present on the observed region of this save, at least not one derivable from these two low-entropy samples.

What remains open / unproven:

  • The exact absolute SRAM offsets of the two "sub-record" fields touched by FUN_080137cc/FUN_08013930 (reader, offset +0x60) and FUN_080138fc/FUN_08013930 (writer/reader pair, offset +0x4D0) cannot be resolved to file offsets, because the base-address constants they add to (_DAT_08013808, _DAT_08013970, _DAT_0801392c, _DAT_08013804, _DAT_0801396c) are opaque DAT_* globals whose literal values are not present in ghidra/decompiled.c.
  • The semantic meaning of the mutated byte at 0x1AFC (counter? flag? boss/chapter progress?) is not determinable from code, because no traced function in ghidra/decompiled.c/ghidra/callgraph.json resolves a literal address or struct-relative offset equal to 0x1AFC (file offset 6908). It is an observation-only fact (two snapshots, one byte delta), not a code-traced field.
  • Only 2 .sav snapshots and 0 paired .ss save states are available in this cohort (states/ is empty — "legacy checkpoint cohort"), so no RAM-mirror cross-reference or live-memory confirmation was possible. All conclusions rest on static decompilation + static byte diffing only.

Given the extremely low non-fill byte count (17 max observed non-zero bytes across both files) and the complete absence of paired save states, this report documents a verified magic signature and I/O driver architecture, but a largely unmapped payload — hence LOW–MEDIUM overall confidence rather than HIGH.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver pair

Two primitive routines form the bottom of every save access in this binary. Both operate on plain byte ranges at 0x0E000000 with no Flash command bytes (0x5555/0x2AAA) and no DMA3 (0x040000D4) programming anywhere in ghidra/decompiled.c, which is the clean-room basis for classifying the media as SRAM, not Flash or EEPROM.

  • FUN_080da7c0 @ 0x080DA7C0 — READER. Declared with no visible body in decompiled.c (void FUN_080da7c0(void) with an unrecovered jump table at its tail), but every call site passes 4 arguments in the pattern (media_addr, ram_dest_ptr, size, bank):
  • func_0x080da7c0(0xe000000, pcVar3, 0x10, *_DAT_080010c0) — read 16 bytes from SRAM base into RAM (FUN_08001094, decompiled.c:415).
  • func_0x080da7c0(_DAT_08001120, abStack_10, 1, *_DAT_0800111c) — read 1 status byte (FUN_080010e4, decompiled.c:446).
  • func_0x080da7c0(_DAT_08013808, *piVar1 + 0x60, 4, *_DAT_08013804) — read a 4-byte sub-field (FUN_080137cc, decompiled.c:793).
  • Direction is proven by FUN_08001094: the destination (pcVar3) is immediately byte-compared against a ROM constant, which only makes sense if the SRAM contents were just copied into pcVar3 — i.e. media→RAM.
  • FUN_080d82dc @ 0x080D82DC — WRITER with read-back verify, up to 3 retries:
  void FUN_080d82dc(undefined4 param_1,undefined4 param_2,undefined4 param_3,int param_4)
  {
    byte bVar1;
    for (bVar1 = 0; bVar1 < 3; bVar1 = bVar1 + 1) {
      FUN_080d81b8(param_1,param_2,param_3);                         // raw byte-copy to SRAM
      param_4 = func_0x080da7c0(param_1,param_2,param_3,*_DAT_080d8318); // read back & compare
      if (param_4 == 0) break;                                        // success -> stop retrying
    }
    (*UNRECOVERED_JUMPTABLE)(param_4);
  }

(ghidra/decompiled.c:3193-3212). Call sites confirm the argument order is (ram_src, media_dest, size[, bank]):

  • func_0x080d82dc(*piVar3 + _DAT_08001084, iVar4 + 0xe000000, 0x1000) — bulk 4KB-chunk write of the whole buffer to 0x0E000000+iVar4 (FUN_08001004, decompiled.c:379).
  • func_0x080d82dc(*piVar3 + _DAT_08001084, 0xe000000, 0x10) — re-stamp the 16-byte magic after a full restore (FUN_08001004, decompiled.c:391).
  • func_0x080d82dc(abStack_10, uVar1, 1) — single status-byte write (FUN_080010e4/FUN_08001124, decompiled.c:448,470).
  • func_0x080d82dc(*piVar1 + 0x4d0, uVar2, 4) — 4-byte field commit (FUN_080138fc, decompiled.c:816).

FUN_080d81b8 (the actual byte-copy primitive underneath FUN_080d82dc) is itself not resolved in this excerpt (listed as a callee with no body shown), but its call pattern (param_1,param_2,param_3 = same 3-arg shape as the writer) is consistent with a straight memcpy-to-SRAM.

Confidence: CONFIRMED_STATIC for the read/write role assignment and retry/verify behavior (proven purely from argument-usage patterns across multiple call sites — internally consistent and unambiguous). Not independently confirmed against live RAM/SRAM bus traces (none are available in this workspace).

3.2 Magic-signature verifier

  • FUN_08001094 @ 0x08001094 (ghidra/decompiled.c:404-431):
  void FUN_08001094(void) {
    uVar4 = 1;
    pcVar3 = (char *)(*_DAT_080010b8 + _DAT_080010bc);
    func_0x080da7c0(0xe000000, pcVar3, 0x10, *_DAT_080010c0);   // read 16 bytes from SRAM base
    iVar2 = 0x10;
    pcVar1 = _DAT_080010c4;                                      // ROM-resident reference constant
    do {
      if (*pcVar3 != *pcVar1) { uVar4 = 0; break; }               // byte-by-byte compare
      iVar2--; pcVar3++; pcVar1++;
    } while (0 < iVar2);
    (*UNRECOVERED_JUMPTABLE)(uVar4);                              // returns boolean match result
  }

This reads 16 bytes from SRAM offset 0 and compares them byte-for-byte against a 16-byte constant pointed to by _DAT_080010c4. CONFIRMED_STATIC: the structure (16-byte SRAM-base compare, boolean return) unambiguously matches a magic-signature check. The literal value of _DAT_080010c4 is not printed anywhere in ghidra/decompiled.c (it is an opaque data reference), so the code alone does not prove it equals "CASTLEVANIA2-010". However, both sample .sav files independently contain exactly that ASCII string at exactly SRAM offset 0, with exactly the 16-byte length the routine checks — so combining code + bytes, this is CONFIRMED_VERIFIED as the magic-signature location/length/content; the constant-table identity assumption is the one residual inferential step.

3.3 Caller chains over the magic check and bit-flag gate

Three status-bit primitives share one SRAM byte, bit 6:

  • FUN_08001164(param_1) @ 0x08001164 — TEST bit param_1: reads 1 byte via func_0x080da7c0, returns ~(byte >> bit) & 1 (decompiled.c:482-493).
  • FUN_080010e4(param_1) @ 0x080010e4 — SET bit param_1: read byte, OR in 1<<bit, write back via func_0x080d82dc (decompiled.c:438-453).
  • FUN_08001124(param_1) @ 0x08001124 — CLEAR bit param_1: read byte, AND out ~(1<<bit), write back (decompiled.c:460-475).

These three are called exclusively with the literal argument 6 in every observed caller, i.e. they all operate on bit 6 of a single status byte.

Caller chain A — read-gated by bit 6, reads field at RAM_struct+0x60:

FUN_080137cc (0x080137cc)
 ├─ calls FUN_08001094()            // magic check must return non-zero
 └─ if magic OK: calls FUN_08001164(6)   // bit 6 of status byte must test true
     └─ if both true: func_0x080da7c0(_DAT_08013808, *piVar1 + 0x60, 4, *_DAT_08013804)

(ghidra/decompiled.c:781-799). No caller of FUN_080137cc itself is present in ghidra/callgraph.json ("callers": []) — it is an entry point not reached by any other traced function in this excerpt (likely called from un-decompiled higher-level game-state code, or is itself a vblank/menu-table-dispatched handler).

Caller chain B — read-gated by bit 6, reads field at RAM_struct+0x4D0:

FUN_08013930 (0x08013930)
 ├─ calls FUN_08001094()
 └─ if magic OK: calls FUN_08001164(6)
     └─ if both true: func_0x080da7c0(_DAT_08013970, *piVar1 + 0x4d0, 4, *_DAT_0801396c)

(ghidra/decompiled.c:829-847). Same "none" caller status in the callgraph.

Caller chain C — transactional writer, commits field at RAM_struct+0x4D0:

FUN_080138fc (0x080138fc)
 ├─ FUN_080010e4(6)                               // SET bit 6 — "write in progress" guard
 ├─ func_0x080d82dc(*piVar1 + 0x4d0, uVar2, 4)     // commit 4 bytes RAM -> SRAM, with verify/retry
 └─ FUN_08001124(6)                               // CLEAR bit 6 — commit complete

(ghidra/decompiled.c:806-822). This set→write→clear bracket is the classic single-bit "dirty"/"transaction in progress" journal pattern used to detect a save interrupted mid-write (e.g. by sudden power loss): on the next boot, chain B's read of this same bit 6 can distinguish "field was committed cleanly" from "field write was interrupted," although with only static code we cannot prove which boolean state (set vs. clear) chain B interprets as "valid" beyond the literal ~(bit)&1 test already shown.

How these callers mutate the in-RAM struct before flushing: in all three chains, the RAM-resident struct pointer is piVar1 (_DAT_08013800/_DAT_08013928/_DAT_08013968, three distinct global pointer slots that — absent further decompilation — may or may not alias the same struct instance). FUN_080138fc is the only function in this excerpt that computes new field content before flushing: it captures uVar2 = _DAT_0801392c (an opaque constant/global, not a computed value) and immediately writes it out — i.e. in this trace window, the 4-byte field's value comes from a global, not from arithmetic on gameplay state. The actual gameplay-state mutation of that global is outside the 115 decompiled functions in this workspace.

3.4 Full-save restore / re-stamp path

FUN_08001004 @ 0x08001004 (ghidra/decompiled.c:359-397, no traced callers in ghidra/callgraph.json) performs a bulk restore: it copies the full save region from 0x0E000000 into a RAM buffer in 0x1000-byte chunks (loop bound _DAT_0800108c), using func_0x080d82dc's own internal read-back (note: here func_0x080d82dc is called with the SRAM address as the second argument, i.e. used as a bulk copy primitive, not strictly "write" — this is the one call site where the generic nature of the low-level routine is visible), then overwrites the final 0x10 bytes of the RAM buffer with a 16-byte constant from _DAT_08001090 and writes that 16-byte region back to SRAM offset 0. This is consistent with a first-boot/corrupt-save initializer that (re-)stamps the magic signature after populating/restoring the rest of the buffer. CONFIRMED_STATIC; not observed firing in either sample .sav (both already contain a valid magic, so this path's "blank-to-initialized" transition is not evidenced in our 2 samples).

4.2 Checksum / integrity algorithm — NONE FOUND (exhaustively checked)

No checksum, XOR, or CRC routine was found anywhere in ghidra/decompiled.c's 115 functions (no loop accumulating a running sum/XOR over a byte range with a single stored result was identified; FUN_08001194 is an unrelated OAM/affine-sprite decompression routine, not a save checksum, despite superficially resembling an accumulator loop).

This was independently cross-checked by brute-force arithmetic against the two real .sav files — testing sum8 and xor8 over every plausible covered range (0x00–0x10, 0x10–0x1AFC, 0x00–0x1AFC, and neighboring end-offsets) against every plausible "stored checksum" byte near the one active mutation site:

This negative result is corroborated by the PACKET's own automated mutation probe at this exact offset: "integrity_check_confirmed": false, "reverted_to_blank_on_mutation": false, "save_rewritten_after_mutation": false — i.e. flipping this byte and reloading did not trigger any observable save-rejection/repair behavior, which is exactly what "no checksum covers this byte" predicts.

Confidence: CONFIRMED_VERIFIED that no checksum is detectable from the current evidence. This is not proof that no integrity mechanism exists anywhere in the save (e.g. it could cover a region that happens to be all-zero fill in both of our low-entropy samples, which would be invisible to a byte-diff search), but within the observed active ranges, no checksum formula fits.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-00-future-0.sav or cap-01-future-1.sav, loaded from the paired .ss save state once this checkpoint cohort has paired states available (states/ is currently empty for this release; re-run this cohort's capture harness with paired .ss states before executing this plan, per the standing paired-save-state requirement).

  1. Magic signature corruption (negative control).
  • Mutation: flip one byte anywhere in 0x0000-0x000F (e.g. 0x0000: 0x43 -> 0x00).
  • No checksum repair needed (none exists per §4.2).
  • Predicted effect: FUN_08001094 returns 0 (mismatch) on next load; both gated readers (FUN_080137cc, FUN_08013930) will refuse to read their fields (iVar3 stays 0). Observable prediction: game should treat the save as absent/corrupt and likely trigger the FUN_08001004 bulk-restore/re-stamp path, OR present a "no save data" state at boot. If instead the game silently loads as if nothing changed, that disproves the magic check's gating role entirely and should be flagged as a falsified hypothesis.
  1. Status bit 6 forced set (transactional-flag probe).
  • Mutation: cannot be done confidently from file bytes alone, since the absolute offset of the status byte is UNKNOWN (§5). This mutation requires first locating the byte via a live RAM-write breakpoint on FUN_080010e4/FUN_08001124 in an emulator with debugging, then mutating the corresponding .sav byte once the real SRAM offset is known.
  • Predicted effect once located: forcing bit 6 set before boot should make FUN_080137cc/FUN_08013930's gate condition (magic_ok && FUN_08001164(6)) evaluate true even without a prior FUN_080138fc write, causing the two 4-byte fields to be read and applied to the RAM struct on boot — observable only if those fields visibly affect gameplay/UI state. If forcing the bit produces no visible change, the fields may be read into struct locations outside the sampled HUD/gameplay observation window used by this cohort's capture harness.
  1. 0x1AFC byte mutation (direct re-run of the existing probe, extended).
  • Mutation: set 0x1AFC to 0x02, 0xFF, and 0x00 in three separate copies (beyond the already-tested 0x00->0x01).
  • No checksum repair needed (none exists).
  • Predicted effect per the existing packet probe (reverted_to_blank_on_mutation: false, save_rewritten_after_mutation: false): the save should load normally regardless of value, with no integrity rejection. If a value like 0xFF instead does cause a visible difference (e.g. UI counter overflow/wrap, or a boolean flag flipping some other visible state), that is new information about this byte's semantic range that the original two-sample diff could not reveal (since only 0x00→0x01 was ever observed).
  • Counterfactual: if 0xFF crashes or soft-locks the game, this byte is more likely an array index / enum than a free-running counter.
  1. Bulk-region all-0xFF fill (media-type sanity re-check).
  • Mutation: fill the entire 0x0010-0x7FFF region (currently all-zero in both samples) with 0xFF.
  • Predicted effect: since no checksum exists, the game should load without any rejection. Watch specifically for whether FUN_08001004's bulk-restore path triggers (it would, if the game has its own independent "is this blank" heuristic distinct from the magic check) — if the save is silently reset to blank/default despite having a valid magic signature, that would reveal an additional, currently-untraced validity check elsewhere in the ROM that wasn't captured in this 115-function excerpt.
  1. Structural falsification check (counterfactual for the whole report).
  • If none of the mutations above produce any observable difference across repeated fresh-boot and mid-session reloads, the dominant alternative hypothesis is that this save cohort's capture harness never exercises the gameplay states that read/write offsets +0x60/+0x4D0/status-bit-6 at all (consistent with their near-total 0x00 fill in both real samples), and a longer, more varied capture session (not just 2 snapshots) is required before this field map can advance past HYPOTHESIS/UNKNOWN confidence.
