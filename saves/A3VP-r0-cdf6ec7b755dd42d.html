1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (verified):

  • The save medium image is a 64 KiB Flash dump whose only used area is ten 4 KiB slots at 0x0000–0x9FFF; everything else is 0xFF fill.
  • Every slot begins with the 8-byte ASCII magic SONIC_PB, followed by a 64-bit generation counter. The writer is a ring buffer: each flush increments the counter and writes slot (counter − 1) % 10. This is directly observed: cap-00 contains only slot 0 (counter 1); cap-01 adds slot 1 (counter 2), byte-identical to slot 0 except the counter byte at +0x08. The loader scans all ten slots and picks the valid one with the greatest counter.
  • The integrity check is degenerate: FUN_08049718 sums only the first 4 bytes of the slot ('S'+'O'+'N'+'I' = 0x0139) and stores that 16-bit sum big-endian at 0xFFE/0xFFF. It matches all three slot instances in the corpus (Python verification in §4). Payload bytes 0x04–0xFFD are not checksummed at all.
  • The default/factory save built by FUN_080494c8 (magic, counter = 1, value at +0x14 = 100, seven config u16s at +0x18, flag bytes at +0x30, settings u16s at +0xCC/+0xCE/+0xD0) matches the observed bytes exactly, and the four high-score tables at +0x22C (4 × 20 entries × 16 bytes, scores 1,000,000,000 down to 50,000,000 with names SON/TAI/KNU/AMY/CLA…/SEG) match FUN_08030e88's default-table generator.

Static-only (code read, no direct byte proof beyond consistency): the Flash command sequences (autoselect ID, sector erase, byte program, 1M bank-switch path), the erase/write retry loops, and the load-time field mirroring into a working RAM struct.

Unknown / hypothesis: the absolute RAM base address of the save struct (Ghidra _DAT_ literal-pool values are symbolic in this corpus, so only struct-relative offsets are proven), the gameplay semantics of most payload fields, the exact role of the byte at 0x72C, and whether the 4-byte checksum loop bound is intentional design or a decompilation artifact (it fits both the validator code and all samples, but it authenticates almost nothing — §6 provides a decisive fuzz test).

Selection-rule quirk (static-only): in FUN_08048dcc the running best is kept as uVar11 = (ushort)auStack_70[slot*2], i.e. the counter's low word truncated to 16 bits, and a candidate is forced when its high word (+0x0C) is non-zero. Behaviour for counters above 0xFFFF is therefore not a clean 64-bit maximum — this is a code-reading hypothesis, untestable with counters 1–2 in the corpus.

Erase geometry: FUN_080605b0 accepts a sector index < 0x10 and addresses it as 0x0E000000 + (index << shift), where shift comes from the identified chip's config table (byte at entry +8, installed by FUN_08060420). With 4 KiB slots this is consistent with 4 KiB Flash sectors, but the shift value itself lives behind an unresolved _DAT_ pointer, so "4 KiB erase sector" is CONFIRMED_STATIC, not byte-verified.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

ghidra/callgraph.json is incomplete for this subsystem: most save calls go through func_0x0806xxxx / func_0x0805fxxx indirect trampolines that Ghidra left as UNRECOVERED_JUMPTABLE, so the JSON lists, for example, only 0x08048d94, 0x0803a098, 0x08002f14 as callees of FUN_08048dcc. Every chain below was therefore mapped by (a) reading the explicit func_0x080XXXXX(...) call sites and field writes in the ghidra/decompiled.c body of each function, (b) cross-checking each resolved edge against callgraph.json (all resolved edges agree), and (c) verifying the resulting field layout byte-for-byte against the .sav images with Python. Functions at 0x08060890–0x080608a4 are one-instruction trampolines into RAM-copied driver code and are treated as unresolved (their roles are inferred from call sites only).

3.2 Low-level Flash I/O driver (all at 0x0E000000)

  • FUN_0805ff44 — Flash autoselect / ID read. Writes 0xAA to the 0x5555-scaled address and 0x55 to the 0x2AAA-scaled address (via _DAT_ pointers), issues 0x90 (autoselect), reads the manufacturer/device bytes through the FUN_080608a4 byte-read trampoline at 0x0E000000, then issues 0xF0 (reset) twice. Returns (id_byte_1 << 8) | id_byte_0. It first copies its helper into a 64-byte stack buffer via FUN_08060134, the standard pattern for executing code while the Flash array is in ID mode. Caller: FUN_08060420 only (callgraph-confirmed).
  • FUN_08060420 — IdentifyFlash / select chip config. Sets WAITCNT bits (| 3), calls FUN_0805ff44, then walks a chip-descriptor table comparing the ID against the short at entry +0x28; on a match (or on the empty-name terminator entry) it copies the descriptor's fields +0x00…+0x14 into driver globals — including the sector-address shift byte at descriptor +8 that FUN_08060198/FUN_080602fc/FUN_080605b0 later use. This is how one driver supports both 512K and 1M parts.
  • FUN_08060198 — ReadFlash(index, offset, dst, len). Sets WAITCNT | 3; if the identified chip size is 0x20000 (Flash 1M) it bank-switches with FUN_0805ff20 and reduces the index to its low nibble; otherwise the address is 0x0E000000 + (index << shift) + offset. The copy itself runs through the RAM-resident FUN_0806089c trampoline after the routine is staged on the stack. Callers (from C bodies): FUN_08048dcc (ten times, len = 0x1000) and FUN_080492e4.
  • FUN_080602fc — WriteFlash(index, src, len). Mirror image of the reader: same WAITCNT handling, same 1M bank-switch check, address 0x0E000000 + (index << shift), copy via FUN_0806089c. Callers: FUN_080492e4 and FUN_08049640, always with len = 0x1000 — i.e. a whole slot struct is flushed verbatim, so disk offsets equal RAM-struct offsets.
  • FUN_080605b0 — EraseSector(index). Only for index < 0x10. Full unlock sequence 0xAA → 0x55 → 0x80 → 0xAA → 0x55 → 0x30 at the sector address, routine staged via FUN_08060134, completion polled through FUN_0806089c(2, addr, 0xFF, …). No resolved callers in the corpus (reached via trampolines); it is the only erase primitive the sector-write paths can use.
  • FUN_0806064c — ProgramByte. Unlock 0xAA → 0x55 → 0xA0, then *dst = *src byte program via FUN_0806089c. No resolved callers in the corpus.
  • FUN_08060134 — stage driver code to RAM/stack. Copies the halfword range between two _DAT_ bounds into the caller's buffer and records buffer + 1 (Thumb) as the entry point. Callers: FUN_0805ff44, FUN_080605b0.
  • FUN_08060008 — select Flash type/size. For param ≤ 3 stores the type index and a derived table pointer. Callers: FUN_080492e4 (param = 3) and FUN_08049640; its return value gates the erase/write retry loops, so it behaves as a "driver ready / verify" gate — exact semantics static-only.
  • FUN_0805feb4 — SWI 0x0B (CpuSet) wrapper, used as the memcpy for high-score entries and small field copies in FUN_08048dcc/FUN_080494c8.

3.3 Serialisation, checksum, and the save/load state machine

  • FUN_08049718 — checksum (see §4). short result; loops while (uVar2 < 4) summing bytes from the pointer stored in *_DAT_08049738 (the RAM save-struct base). Callers: the loader, the default builder, and the flush routine.
  • FUN_080494c8 — build default save struct in RAM. Zeroes the struct, copies the 8-byte magic template to +0x00, sets counter +0x08 = 1, +0x0C = 0, +0x14 = 100, config u16s at +0x18… = 8, 1, 0x20, 1, 0x200, 0x100, 2, flag bytes +0x30…+0x35 = 1,1,0,1,0,0, settings +0xCC = +0xCE = +0xD0 = 1 (plus a fourth u16 write through an unresolved _DAT_ offset with no observed counterpart), zeroes the working high-score area, calls FUN_08030e88 to generate the default tables, copies them working +0x1E0 → save +0x22C, then computes the checksum and stores it big-endian (high-byte store first-seen at the higher _DAT_ offset, low byte at the struct-end offset). Every one of these values is present verbatim in both .sav files.
  • FUN_08030e88 — default high-score generator. For 4 tables × 20 entries at working-struct +0x1E0 + table*0x140 + entry*0x10: writes a 64-bit score decreasing from a base constant (observed: 1,000,000,000 − 50,000,000 × entry) and the name bytes 'S','O','N',… at entry +8/+9/+10. The observed tables (SON 1e9, TAI 950M, KNU 900M, AMY 850M, CLA 800M, …, SEG 50M, identical in all 4 tables) match this generator; the on-disk copy sits at +0x22C (see §3.4).
  • FUN_08049640 — flush / save-now (the writer entry point). Increments the 64-bit counter at +0x08/+0x0C (with carry when lo wraps), recomputes the checksum via FUN_08049718 and stores it at 0xFFE/0xFFF, computes the target slot as (counter − 1) mod 10 using the 64-bit divide/mod helper FUN_08060ef4, then, gated by FUN_08060008, retries up to 3 times: erase via FUN_08060898 trampoline and, on success, FUN_080602fc(slot, struct_base, 0x1000). Callers (callgraph-confirmed): FUN_080498f0, FUN_08049d4c.
  • FUN_08048dcc — load / validate (the reader entry point). Calls FUN_08048d94 (zeroes the RAM struct, then FUN_08060420 IdentifyFlash). It then reads each of the 10 slots with FUN_08060198(i, 0, buf, 0x1000), marks a slot valid only if the first 8 bytes equal SONIC_PB and FUN_08049718() equals the stored big-endian u16 assembled as CONCAT11(byte[0xFFE], byte[0xFFF]), records each valid slot's counter pair, and selects the greatest (with the u16-truncation quirk of §2). If no slot is valid it calls FUN_080492e4 to initialise. Otherwise it re-reads the winning slot and deserialises: high scores save +0x22C → working +0x1E0 (8 bytes per entry via FUN_0805feb4), +0x14 to a RAM variable, 6 bytes from +0x30, 4 bytes from +0x36, 16 bytes from +0x3A (three separate RAM destinations), settings +0xCC → working+0x80, +0xCE → working+0x82, a further u16 via an unresolved offset (candidate +0xD2) → working+0x6E0, then FUN_0803a098 for config and FUN_08049d4c for any pending flush.
  • FUN_080492e4 — initialisation / new-save. Selects Flash type FUN_08060008(3, …), touches all 10 slots through the FUN_08060894 trampoline (erase/verify — unresolved), builds the default struct with FUN_080494c8, and writes slot 0 with the same erase + FUN_080602fc(0, …, 0x1000) retry pattern as the flush routine. Called from FUN_08048dcc when no valid slot exists.
  • FUN_0803a098 — config deserialiser. If its guard flag is clear it installs the defaults 8, 1, 0x20, 1, 0x200, 0x100, 2 into the working struct; otherwise it loads seven u16s from save +0x18…+0x24. Called by FUN_08048dcc (callgraph-confirmed).
  • FUN_08049d4c — pending-value flush. If save +0x11 ≠ 0 and the value returned by FUN_0805dbd8 qualifies (≤ a RAM threshold), it writes that value to save +0x14, clears +0x11, and calls FUN_08049640. Called by FUN_08048dcc; caller of FUN_08049640 (callgraph-confirmed).
  • FUN_080498f0 — save trigger. Copies working +0x6E0 to a +0x72C field, then either returns 1 (suppressed by a flag) or calls FUN_08049640. Caller of FUN_08049640 (callgraph-confirmed).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic. SONIC_PB (hex 53 4F 4E 49 43 5F 50 42) at slot offset 0x00, 8 bytes. Verified in code: FUN_080494c8 copies an 8-byte template to +0x00 and FUN_08048dcc byte-compares 8 bytes per slot. Verified in .sav: present at file offsets 0x0000 (both files) and 0x1000 (cap-01 only). The PACKET profile's second string 9SONIC_PB is the same signature preceded by the counter byte 0x09 in a string scan, not a separate magic.

Checksum — exact algorithm (as decompiled).

// FUN_08049718 (ghidra/decompiled.c)
short FUN_08049718(void) {
  byte *pbVar3 = (byte *)*_DAT_08049738;   // RAM save-struct base
  short sVar1 = 0; ushort uVar2 = 0;
  do { sVar1 += (ushort)*pbVar3; pbVar3++; uVar2++; } while (uVar2 < 4);
  return sVar1;
}
  • Formula: (slot[0] + slot[1] + slot[2] + slot[3]) & 0xFFFF — a plain 16-bit byte sum over only the first 4 bytes ('S'+'O'+'N'+'I' = 0x53+0x4F+0x4E+0x49 = 0x0139). No seed, no complement, no CRC, no XOR.
  • Covered range: slot bytes [0x000, 0x004) only. Bytes 0x004–0xFFD are not covered.
  • Stored at: slot 0xFFE (high byte) / 0xFFF (low byte) — big-endian. Proof: both writers (FUN_080494c8, FUN_08049640) store (char)(checksum >> 8) at the higher _DAT_ offset and (char)checksum at the struct-end offset, and the validator (FUN_08048dcc) reassembles with CONCAT11(byte_at_higher_offset, byte_at_end).
  • Honesty note: a checksum over the first 4 magic bytes is degenerate (it can only fail if the magic itself is already corrupt, which the separate 8-byte compare also catches). Two alternative contiguous ranges (0x002–0x006 and three ranges inside the score tables) coincidentally also sum to 0x0139 on these samples because of repeated score bytes; the code's explicit uVar2 < 4 loop starting at the struct base is what selects [0,4). Confidence is nevertheless CONFIRMED_VERIFIED on the combined code + bytes evidence, and §6 item 3 gives a mutation that distinguishes the hypotheses at runtime.

6. Save Fuzzing & Counterfactual Verification Plan

General notes: there are no paired .ss save states in this corpus (states/ is empty), so every test below is specified as: patch the .sav, cold-boot the ROM with that image, and observe (a) which slot the loader selects (inferable from the next save's counter/slot), (b) RAM via emulator watchpoints on the save/working structs once their base is located by searching EWRAM/IWRAM for SONIC_PB after boot, and (c) UI (high-score screens, any value fed by +0x14). Checksum repair, where needed, is only ever: recompute sum(slot[0:4]) & 0xFFFF and write it big-endian at 0xFFE/0xFFF — payload edits need no repair, which is itself the key prediction of §4.

  1. Counter/selection test (offset 0x008, size 4). In cap-01, set slot 1's counter lo to 0xFFFFFFFF (hi stays 0). No checksum repair. Prediction: the loader still selects slot 1 (greatest counter); then set slot 0's counter to 0x00010000 with slot 1 at 0x0000FFFF to expose the (ushort) truncation quirk — if the loader picks slot 1, the quirk reading is wrong and selection is a clean comparison.
  2. Checksum rejection/fallback test (offset 0xFFE, size 2). Zero the checksum in slot 1 only. Prediction: slot 1 is rejected, the loader falls back to slot 0 (counter 1) instead of reinitialising, and the next in-game save writes counter 2 into slot 1 again.
  3. Magic-vs-checksum separation test (offset 0x000, size 1) — the decisive §4 test. Change slot 1's 'S' to 'X' and repair the checksum to the new 4-byte sum (0x58+0x4F+0x4E+0x49 = 0x013E, stored 01 3E). Prediction: the slot is still rejected (independent 8-byte magic compare), proving the checksum covers only the magic prefix; if instead the slot loads, the covered range is larger than the decompiled loop suggests and §4 must be revised. Control: corrupt one payload byte (e.g. 0x100) with no repair — prediction: the slot still loads, confirming payload is uncovered.
  4. Value field test (offset 0x014, size 4). Set +0x14 from 100 to 9999 in the newest slot. No repair. Prediction: whatever consumes the RAM variable loaded from +0x14 in FUN_08048dcc shows 9999; a RAM watchpoint on that variable identifies the consumer and the field's semantics.
  5. High-score test (offset 0x22C, size 4; name at 0x234, size 3). Set table 0 rank-1 score to 0xFFFFFFFF and its name to ZZZ. No repair.
