Orientation warning (read first). Every offset in this report is a logical offset — the offset in the 512-byte RAM buffer the game builds when it reads the EEPROM (FUN_080235b4 → FUN_080237a0). The .sav file on disk is not in logical order: the EEPROM read driver stores each 8-byte block byte-reversed (see §3.1), so a logical offset L lives at file offset (L & ~7) | (7 - (L & 7)). Example: the first magic byte is logical 0x000 but file offset 0x007. This transform is proven, not assumed: it makes both magic bytes land exactly where the decompiled code checks them and makes the checksum verify on the completed save (§4), while naive file order fails the checksum (0x61 vs stored 0x60).

What was proven (code + bytes agree):

  1. The save medium is a 512-byte (4 Kbit) EEPROM (EEPROM_V124), read and written as 64 blocks of 8 bytes through DMA3 to/from 0x0D000000.
  2. There is one single save record, logical size 0x173 (371) bytes, at offset 0x000 of the EEPROM image. There is no backup copy, no second slot, no mirroring, and no generation/sequence counter (§2).
  3. Integrity is a double 'W' (0x57) magic at logical 0x000 and 0x171, plus an 8-bit additive checksum at logical 0x172 covering logical 0x000..0x170. Verified byte-exactly on sav-01-f1647.sav (§4).
  4. The two .sav snapshots capture one write in progress: sav-00 (frame 1613) is a prefix-written, currently-invalid image; sav-01 (frame 1647) is the completed, valid image (§2.3).

What remains open: the EEPROM write path and serializer (0x08023624, SDK EEPROM-write), the trigger that requests a save, all payload sub-field meanings, and every absolute RAM address.

2. Physical Media, Slot Geometry & Redundancy

2.1 Media

  • Kind: EEPROM, 4 Kbit = 512 bytes (eeprom512 in the JSON deliverable). Both .sav files are exactly 512 bytes (sav-00 SHA-256 prefix 1d8d48acc920dd38, sav-01 prefix d788dbcffd1373fe).
  • SDK tag in ROM: EEPROM_V124 (at ROM offset 1046920 per the packet) — Nintendo's EEPROM driver, V124.
  • Bus: serial EEPROM at 0x0D000000, accessed only via DMA3 (registers based at 0x040000D4). There is no SRAM (0x0E000000 byte-copy) or Flash (0x5555/0x2AAA command) code anywhere in the corpus: the strings/constants 0x0E000000, 0x5555, 0x2AAA never appear in ghidra/decompiled.c; the only save-media constant is 0xd000000 in FUN_08049504.
  • Organization: 64 blocks × 8 bytes. The read driver is invoked once per block with a block index 0..0x3F and an 8-byte destination stride (FUN_080235b4 loop, §3.3).
  • Erased state: 0xFF per byte (idle/erased EEPROM bits are 1). The pre-computed dump calls 0x00 the "background fill" because most of the file is 0x00, but the unwritten tail of sav-00 is 0xFF, i.e. truly erased, whereas the 0x00 regions have been actively written with zero bits.

2.3 The two snapshots are one write, caught in progress

Paired state metadata: sav-00 was captured at frame 1613 (sav-00-pre 1579 → sav-00-post 1613); sav-01 at frame 1647 (sav-01-pre = frame 1613 = sav-00-post → sav-01-post 1647 = final.ss). The byte diff is exactly 200 bytes, all 0xFF → 0x00 except two:

  • file 0x118..0x14F, 0x157, 0x178..0x1FF: erased 0xFF in sav-00, written 0x00 in sav-01;
  • file 0x175..0x176: 0xFF → 0x60, 0x57 — i.e. logical 0x172 (checksum 0x60) and logical 0x171 (second 'W' magic) appear only in the completed image.

Interpretation (HIGH confidence): the writer flushes the 512-byte RAM image to EEPROM block-by-block in ascending order. At frame 1613 the flush had completed roughly the first 35 blocks (file/logical 0x000..0x117 are already final), while blocks from file offset 0x118 upward still held erased 0xFF. By frame 1647 the flush finished, including the trailer at logical 0x171/0x172 and the zero tail. Two consequences:

  1. sav-00 is an invalid save if loaded as-is — its stored checksum byte is still erased 0xFF while the computed sum over its (partially erased) body is 0x27. This is the expected mid-write state, not corruption.
  2. There is no atomicity or redundancy: a power loss mid-flush leaves exactly this kind of torn, checksum-failing image, and the loader has no backup to fall back to (§3.4, §6).

Note also that logical 0x150..0x16F (file blocks 42–45) remains 0xFF in both images, inside the checksummed payload. So the RAM image itself legitimately contains an erased-looking 0xFF field region; it is payload data (meaning unknown), not unwritten media.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

FUN_08049484 (0x08049484) — DMA3 transfer engine

void FUN_08049484(undefined4 param_1 /*src*/, undefined4 param_2 /*dst*/, uint param_3 /*count*/)
{
  uVar1 = *_DAT_080494e4;
  *_DAT_080494e4 = 0;                                              // disable (DMA/IRQ control via literal)
  *_DAT_080494e8 = *_DAT_080494e8 & (ushort)_DAT_080494ec
                 | *(ushort *)(*_DAT_080494f0 + 6);                // WAITCNT (0x04000204) |= timing from table+6
  *_DAT_080494f4 = param_1;                                        // DMA3 SAD (0x040000D4)
  *_DAT_080494f8 = param_2;                                        // DMA3 DAD (0x040000D8)
  *_DAT_080494fc = param_3 & 0xffff | 0x80000000;                  // DMA3 CNT (0x040000DC): count + enable
  while ((*(ushort *)((int)_DAT_080494fc + 2) & 0x8000) != 0) {}   // poll CNT_H enable bit until done
  *_DAT_080494e4 = uVar1;                                          // restore
  (*UNRECOVERED_JUMPTABLE)();
}
  • One caller only: FUN_08049504 (twice). Role: synchronous DMA3 copy between a RAM buffer and the EEPROM window 0x0D000000, with WAITCNT bits adjusted from a ROM timing table (the standard EEPROM wait-state setup).
  • Because every _DAT_ is an unresolved literal, the exact register addresses above are identified from the GBA hardware map (DMA3 0x040000D4, WAITCNT 0x04000204) plus access pattern (SAD/DAD/CNT triple, 0x80000000 enable bit, busy-poll on the high halfword). Confidence: CONFIRMED_STATIC for the DMA3 identification.

Consequences, all verified against the .sav bytes:

  • The function returns 0 on success; FUN_080235b4 aborts the whole load on any non-zero return.
  • Because the four u16s are stored in reverse order at dest+6,+4,+2,+0, each 8-byte block appears byte-reversed between the physical EEPROM/file image and the game's RAM buffer. This is exactly the transform stated in the orientation warning, and it is what makes the magic/checksum verify (§4).
  • The geometry constants (block count at config+4, address-bit count at config+8) come from an SDK configuration structure whose literal value Ghidra did not resolve. For a 512-byte EEPROM they must be 64 and 6 respectively; the observed file size and the 0..0x3F caller loop corroborate this. Confidence: CONFIRMED_STATIC, corroborated by the binaries.
  • There is no EEPROM write, erase, or verify function in the decompiled corpus at all. The SDK write routine that must sit next to this read routine was not trace-recovered (address range 0x080495xx–0x080497xx contains only runtime helpers in the corpus). This is the single largest gap in the corpus (see §3.5).

FUN_08049894 and FUN_080499dc (two of the three "MMIO seeds" in ghidra/save_related_functions.c) are not save functions: both are signed/modulo software-runtime helpers that call the division-by-zero handler func_0x08049890 when param_2 == 0. Likewise FUN_080497fc is signed division. They were seeded only because they sit in the same ROM region; they play no role in saving. FUN_08049a9c is a word-optimized memcpy, used by the deserializer.

3.2 Serialization / deserialization & checksum routines

FUN_080237a0 (0x080237a0) — deserialize + validate (the core of the format)

Called by FUN_080235b4 (the callgraph lists no caller because the call goes through the unresolved-jumptable convention used throughout this binary, but the call func_0x080237a0(param_2,param_3) is explicit in FUN_080235b4's body). param_1 is the 512-byte read buffer; a second argument (1, passed down from FUN_08023824) is accepted and ignored.

void FUN_080237a0(undefined1 *buf)
{
  *(undefined4 *)(S + 0x88) = 0;                       // valid_flag = 0
  *(undefined1 *)(S + 0x83) = *buf;                     // hdr = buf[0]
  memcpy(M, buf + 1, 0x170);                            // payload -> RAM struct M
  cVar3 = 0;                                            // char (int8) accumulator
  for (uVar4 = 0; uVar4 < 0x171; uVar4++)
      cVar3 = buf[uVar4] + cVar3;                       // sum8 over buf[0..0x170]
  if (*(char *)(S + 0x83) == 'W')
      *(char *)(S + 0x83) = buf[0x171];                 // hdr = second magic byte
  if (buf[0x172] == cVar3)
      *(undefined4 *)(S + 0x88) = 1;                    // checksum ok -> valid_flag = 1
}

Where S = _DAT_08023800 and M = _DAT_08023804 are two unresolved literal-pool pointers (save-manager struct base and payload destination; whether M == S + 4 or a separate struct cannot be determined from the corpus — see §5 notes).

Semantics:

  • The payload (logical 0x001..0x170) is always copied into RAM, even if the checksum then fails; only the valid_flag at S+0x88 records the verdict. Any consumer must check S+0x88 (and the derived boolean at S+0x83, below) before trusting the payload — whether all consumers do is not observable in the corpus.
  • The first magic byte is not compared directly. Instead S+0x83 = buf[0]; if that equals 'W' it is replaced by buf[0x171]. The caller then tests the result (§3.3), producing a net double-magic check: the derived byte equals 'W' iff buf[0] == 'W' && buf[0x171] == 'W'.
  • The checksum is a plain sum-8 (addition modulo 256; the char accumulator's signedness is irrelevant mod 256). Covered range is inclusive 0x000..0x170 (369 bytes), i.e. it includes the first magic byte and all payload bytes, but not the second magic byte or the stored checksum itself.

Writer-side serialization — 0x08023624 (NOT in corpus)

The save-side counterpart — which must stamp 'W' at logical 0x000 and 0x171, compute the same sum-8 into logical 0x172, and flush 64 blocks through the (also missing) SDK EEPROM-write routine — is func_0x08023624, referenced exactly once, as an unresolved external in FUN_0802388c. It was not decompiled. Everything about the writer beyond its existence, its trigger state machine (§3.5), and the final on-disk byte image is inference from the reader + the .sav bytes, and is labelled as such in §5/§6.

How each caller was mapped. (i) ghidra/callgraph.json gives 0x08023824 → {0x080235a4, 0x080235b4} and 0x08049504 → {0x08049484}; (ii) the func_0x08049504(uVar3, iVar5) and func_0x080237a0(param_2, param_3) calls are explicit in FUN_080235b4's decompiled body even though the callgraph's callee list for 0x080235b4 is empty (the binary's pervasive UNRECOVERED_JUMPTABLE tail-call convention hides most edges from the static graph — every function in the corpus ends with one); (iii) FUN_080235a4's body is a single call func_0x0804943c(4). FUN_0804943c(short) branches on 4 / 0x40 / other and stores different table values, returning 0/1 — consistent with an SDK "select EEPROM type/size" helper where 4 denotes the 4-Kbit part; this identification is HYPOTHESIS (the literal targets are unresolved), but the argument value 4 matches the observed 512-byte media.

How the chain mutates the in-RAM save struct before/after reading. Before reading, FUN_08023824 zeroes S+0x83 (derived save-present byte), S+0x84 (load-completed flag), and S+0x88 (valid flag). After a fully successful read+validate it sets S+0x84 = 1 unconditionally (note: S+0x84 means "the EEPROM read completed", not "the save is valid" — validity is S+0x88, and presence is the booleanized S+0x83). The two vestigial-looking arguments (0xff into FUN_080235b4, 1 forwarded to FUN_080237a0) are accepted and ignored by the callees; plausibly a slot index / flags word from a more general SDK-adjacent API — UNKNOWN.

FUN_080485d0 / FUN_08048634 bracket the EEPROM access and adjust a counter by +10/-10 and poke 0x400/0xb600-valued registers via literals. Because EEPROM transfers commandeer DMA3, a quiesce/restore of the game's audio/DMA state is the natural reading, but with literals unresolved this remains HYPOTHESIS; what is certain is only that every load is bracketed by this pair.

Callers of FUN_08023824: none in callgraph.json and none in the C text. Given the binary-wide tail-call/jumptable style, the load entry is almost certainly reached through a function-pointer table (e.g. a title-screen / boot state machine such as FUN_08023a30, which dispatches through *(short*)(param+0x38)*4 + table). Naming a specific caller would be fabrication; the trigger context is therefore recorded as "boot/title load, exact caller not recovered" (UNKNOWN).

3.4 What the loader does with a torn/blank EEPROM

  • Blank/erased chip: buf[0] = 0xFF ≠ 'W' → S+0x83 booleanizes to 0; sum over erased bytes ≠ stored 0xFF (in general) → S+0x88 = 0. Result: "no save".
  • Mid-write torn image (sav-00 as captured): buf[0] = 'W' but buf[0x171] = 0xFF, checksum fails → S+0x83 = 0, S+0x88 = 0. Result: payload bytes were still memcpy'd into RAM but are flagged invalid.
  • Completed image (sav-01): both magics 'W', checksum matches → S+0x83 = 1, S+0x88 = 1.

Evidence and limits:

  • FUN_0802388c (0x0802388c) is in the corpus and reads/writes the same save-manager struct offsets (+0x82, +0x8c) used by the load chain. Its two-phase shape — arm a 0x7a (122) countdown, stage a copy with CpuSet, then on the next phase invoke the flush — is characteristic of a deferred EEPROM save (wait for a quiet moment, then perform the slow serial write). Calling it a "per-frame poll" is HYPOTHESIS; that it is the save trigger/flush path is CONFIRMED_STATIC (it is the only corpus function that invokes 0x08023624, and 0x08023624 is the only unrecovered function invoked with save-struct arguments).
  • The first argument to 0x08023624 is the byte at S+0x82 — adjacent to the load chain's S+0x83 save-present byte. A plausible role is "slot/index or dirty flag byte", UNKNOWN.
  • How the writer mutates the in-RAM struct before flushing: not directly observable. By symmetry with the reader and from the final byte image, the serializer must (a) copy the payload struct into the 512-byte image at logical 0x001..0x170, (b) stamp 'W' at 0x000 and 0x171, (c) compute sum-8 over 0x000..0x170 into 0x172, (d) zero (or leave zeroed) 0x173..0x1FF, and (e) write all 64 blocks in ascending order — step (e)'s ordering is proven by the sav-00 mid-write snapshot (§2.3); steps (a)–(d) are proven as net effects by the verified final image, but the code performing them was not recovered.
  • Default/new-game initializers: FUN_08000638 and FUN_080234b0 each zero-initialize a large RAM struct containing a 0x15 × 3-byte array region and 1-valued flag bytes, and FUN_080234b0 additionally iterates 3 entries of stride 0x54. These are the only corpus functions whose struct footprint is compatible with the 368-byte payload, and FUN_080234b0 writes the value 0x0032 at the struct start — matching the payload's first bytes 32 00 (logical 0x001..0x002). It is therefore a HYPOTHESIS (not proven, because the _DAT_ bases 0x0800074c / 0x08023590 / 0x08023804 cannot be shown equal) that one or both initialize the save payload struct (e.g. at new-game / factory-default time), with three 0x54-byte sub-records (plausibly three party/character slots — semantics unknown). No caller for either function appears in the callgraph.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magics

  • Magic A: logical offset 0x000, byte 0x57 = ASCII 'W'. Checked in FUN_080237a0 (*(S+0x83) = buf[0]; if (== 'W') …) and re-checked in FUN_080235b4.
  • Magic B: logical offset 0x171 (369), byte 0x57 = 'W'. Substituted into S+0x83 by FUN_080237a0 when Magic A matches; the net loader-visible result is the boolean S+0x83 = (buf[0]=='W' && buf[0x171]=='W').
  • There is no ASCII header string, no game-code stamp, and no version field checked by any code in the corpus. (Logical 0x001 = 0x32 '2' is suggestive of a version/sub-format byte — the default initializer FUN_080234b0 writes 0x0032 at its struct start — but no code compares it; HYPOTHESIS.)

4.2 Checksum

  • Algorithm: sum8 — 8-bit additive sum (mod 256). Decompiled proof (FUN_080237a0):
cVar3 = '\0';
uVar4 = 0;
do {
  cVar3 = param_1[(short)uVar4] + cVar3;
  uVar2 = (int)(short)uVar4 + 1;
  uVar4 = uVar2 & 0xffff;
} while ((int)(uVar2 * 0x10000) >> 0x10 < 0x171);
...
if (param_1[0x172] == cVar3) { *(undefined4 *)(iVar1 + 0x88) = 1; }
  • Formula: stored == (Σ buf[i] for i in 0x000..0x170) & 0xFF. The loop runs while the index is < 0x171, i.e. it sums 369 bytes inclusive of both ends — including Magic A ('W') and every payload byte, excluding Magic B and the stored checksum.
  • Stored at: logical 0x172 (370), 1 byte. (File offset 0x175.)
  • No seed, no complement, no XOR fold, no CRC polynomial anywhere in the reader path; the writer-side computation is presumed identical but its code (0x08023624) was not recovered.

Reading of the result:

  • sav-01 verifies perfectly: both magics 'W', computed sum 0x60 = stored 0x60. This single byte-exact triple coincidence (2 magic positions + checksum, under a transform derived independently from the driver code) also retroactively proves the per-block byte-reversal transform: computing the sum in naive file order gives 0x61 ≠ 0x60.
  • sav-00 fails exactly as a mid-write image must: Magic A is already written (0x57), but Magic B and the checksum byte are still erased 0xFF, and the body sum (0x27, over a body whose tail blocks are still 0xFF) cannot match. The loader would set S+0x83 = 0, S+0x88 = 0 ("no valid save") for this image.
  • The checksum covers the payload's internal 0xFF region (logical 0x150..0x16F) — those bytes are part of the summed RAM image in both snapshots, confirming they are payload, not media defects.

6. Save Fuzzing & Counterfactual Verification Plan

General method: mutate the .sav file, then cold-boot (or reload from the paired save states sav-01-pre.ss/sav-01-post.ss, frames 1613/1647) and observe (a) title/continue UI, (b) the RAM save-manager flags if a debugger is available (S+0x83 present, S+0x84 loaded, S+0x88 valid — locate S by watching which RAM the 0x170-byte payload copy lands in), and (c) any gameplay state restored from the payload. Unless stated, start from sav-01-f1647.sav (the only valid image). Remember the block-reversal: to change logical offset L, edit file offset (L & ~7) | (7 - (L & 7)). Checksum repair (needed whenever logical 0x000..0x170 changes): recompute sum8 over the logical image bytes 0x000..0x170 and store it at logical 0x172 = file offset 0x175 (see the Python in §4.3; apply mutations in logical space, then re-serialize each 8-byte block reversed into file space).
