1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven to CONFIRMED_VERIFIED (code + both .sav files agree, with computed-vs-stored output in §4):

  • Physical media is byte-addressed SRAM at 0x0E000000, retained as a 32768-byte (256 Kbit) file, fill byte 0x00 in both samples (packet SDK tag SRAM_V112, §2).
  • Layout is a 40-byte (0x28) header at file offset 0x0000, followed by 0x800-byte (2048-byte) physical blocks, with two logical data blocks actually used by the traced wrappers: logical block 1 at 0x0800 backed up at 0x2800, and logical block 2 at 0x1000 backed up at 0x3000 (§2, §3).
  • Magic is the 6-byte sequence 33 31 31 30 61 00 ("3110a\0") at offset 0x00, compared byte-for-byte in FUN_08001a44 (§4).
  • Integrity is one custom 16-bit checksum per physical block, stored as a u16_le array in the header at 0x06 + 2*physical_block. The algorithm acc = ((acc + byte) & 0xFFFF) ^ 0xFFFF over all 2048 bytes reproduces every non-header stored checksum in both files exactly (blocks 1, 2, 5, 6 and all zero blocks; §4). One mathematically unresolvable bit in the XOR constant is disclosed in §4.3.
  • Primary and backup copies are byte-identical in cap-01 (block1 == block5, block2 == block6); the writer always writes both, the reader tries primary then backup, with no generation/sequence counter anywhere in the header (§2).
  • Logical block 2's live struct is exactly 0x4A0 bytes = 8 records × 0x94 bytes, proven independently by the DMA length 0x4A0 in FUN_080149e0/FUN_08014a10 and by the 0x94 record stride/repeated name field in the bytes (§5).

Static-only (CONFIRMED_STATIC, code explicit, samples cannot corroborate):

  • Boot/erase/load/save entry behaviour, fallback-to-backup and erase-all-on-double-failure, write-with-verify retry (3 attempts), and that a backup hit is not written back to the primary (§3).
  • Exact RAM mirror addresses. ghidra/decompiled.c renders every buffer pointer as an unresolved literal-pool symbol (_DAT_0800xxxx); the values at those ROM addresses are not in this workspace. EWRAM/IWRAM addresses (0x02xxxxxx/0x03xxxxxx) therefore cannot be honestly named and are recorded as null/UNKNOWN throughout. Inventing them would violate the packet's clean-room rule.

Open (HYPOTHESIS/UNKNOWN):

  • Gameplay semantics of almost every intra-block field. Two samples (one blank-ish, one early-game) cannot show progression. CP932/Shift-JIS name strings and one ASCII "725" string are reported as decoded byte facts, with semantic labels marked HYPOTHESIS.
  • Top-level triggers. Every entry wrapper (FUN_08001a44, FUN_08007e34, FUN_08007e4c, FUN_08014a40, FUN_08008394) has no caller in either callgraph.json or a textual scan of decompiled.c; the corpus ends every function in an UNRECOVERED_JUMPTABLE tail-dispatch, so the invoking game-state is UNKNOWN (§3.4).
  • Whether physical blocks 3, 4, 7–15 are ever used by code outside the 200-function corpus. In-corpus, only logical blocks 1 and 2 have wrappers, plus factory-initialise touching all 16 indices.
  • Checksum XOR constant bit 15 (§4.3) and the reader's exact returned-code consumption by the unrecovered dispatch.

Cold-reload probe context from the packet (not re-derivable from workspace files): mutating offset 0x8 (first checksum entry) gave integrity_check_confirmed: true, visual_delta_after_mutation: true, but reverted_to_blank_on_mutation: false and save_rewritten_after_mutation: false — consistent with §3: a primary-checksum failure silently falls back to the identical backup rather than erasing or rewriting.

Mapping rule from code (both directions): primary SRAM offset = logical * 0x800 + 0x0E000000, backup = (logical + 4) * 0x800 + 0x0E000000, valid for logical < 0x10 (FUN_08001a9c, FUN_08001b5c). The generic functions accept 0–15, but the only wrappers in the corpus instantiate logical 1 (FUN_080072fc/FUN_08007310) and logical 2 (FUN_08014a10/FUN_080149e0). Physical block 0 doubles as the header page; it is never loaded as game data by a wrapper.

2.3 Slots, copies, selection — no generation counter

  • Logical slots used: 2 (block 1, block 2). They are saved/loaded together by the "all" wrappers (§3.4); there is no evidence of player-visible multiple save files — the two blocks are two different data structures, not two player slots. slots_and_copies in save-format.json therefore lists the header page, the two logical slots with their backups, and the reserved remainder, rather than inventing "slot_0/slot_1" game files.
  • Redundancy: exactly 2 copies per logical block (primary + +4-block backup), written with identical bytes in the same call (FUN_08001b5c calls the verified writer twice before updating the header). Verified in cap-01: block1 == block5 and block2 == block6 byte-for-byte.
  • Selection rule (reader, FUN_08001a9c): load primary; if its header checksum ≠ recomputed checksum, load backup into the same RAM buffer; if backup verifies, accept it (buffer silently holds the backup copy — no repair write to the primary occurs in this function); if both fail, call factory-init FUN_080019ec (erases/rebuilds the whole save), zero the caller's RAM buffer, and report failure.
  • Generation/sequence counters: none. Header bytes 0x14..0x27 are zero in the populated sample; there is no timestamp, no write counter, and no "newer copy wins" logic anywhere in the reader — primacy alone decides. This matches the packet's mutation probe: a corrupted primary checksum does not blank or rewrite the save, because the backup serves the load.
  • Header checksum-table role: one u16 per physical block, so a backup's entry necessarily duplicates its primary's value whenever the copies are identical (0x16C8 appears at 0x08 and 0x10; 0x0734 at 0x0A and 0x12 in cap-01). The table is a property of the header page, rewritten on every block write (§3.3).
  • Reserved space: physical blocks 3, 4, 7–15 (20480 bytes, 62.5% of the file) and the header tail 0x28..0x7FF are zero in both samples. Factory-init (FUN_080019ec) does iterate indices 0–15 through the block writer, which for indices ≥ 12 addresses (index+4)*0x800 ≥ 0x8000, beyond the 32768-byte retained SRAM — behaviour there (mirror/wrap/ignored) is UNKNOWN from this workspace and immaterial in practice since the result is all-zero in both samples.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (method)

Two independent sources were cross-checked for every edge, because neither is complete alone:

  1. ghidra/callgraph.json (200 nodes, callers/callees). It records FUN_-style direct calls (e.g. FUN_080072fc → FUN_08001b5c appears indirectly via the wrapper listing) but omits most SRAM-library edges.
  2. Textual scan of ghidra/decompiled.c for FUN_080xxxxxx( / func_0x080xxxxxx( tokens per function body, then building the reverse (caller) index. This recovers edges callgraph.json drops — e.g. FUN_080019ec → func_0x08001b5c, FUN_08007e34 → func_0x08014a10, FUN_08001b5c → func_0x0800545c, FUN_0800545c → FUN_08005388/FUN_080053f8. Where the two sources disagree, the textual body wins (it is the actual code), and the disagreement is noted.

A third, systematic limitation applies to the whole corpus: every function ends in (*UNRECOVERED_JUMPTABLE)(...), a state-machine tail-dispatch Ghidra could not recover. The value passed (e.g. uVar3 in FUN_08001a44) is produced in a register for that dispatch, which is why several "void" functions below are described as reporting a code rather than returning one. Inbound edges from that dispatch are exactly what is missing for the top-level entries in §3.4 — this is stated as UNKNOWN, not papered over.

RAM mirror addresses are likewise limited: buffer identities below are named by their (unresolved) literal-pool symbols, e.g. _DAT_0800730c. The same logical buffer recurs under different symbols in different functions (block-1 buffer: _DAT_0800730c in FUN_080072fc, _DAT_08007320 in FUN_08007310; block-2 buffer: _DAT_08014a08/_DAT_08014a3c in FUN_080149e0/FUN_08014a10; header buffer: _DAT_08001a3c/_DAT_08001a8c/_DAT_08001b34/_DAT_08001be8). Equality of the pointed-to values is inferred from identical roles/sizes, and is labelled HYPOTHESIS where it matters — the addresses themselves are UNKNOWN in this workspace.

4.2 Checksum algorithm — exact formula

Decompiled proof, writer FUN_08001b5c (reader FUN_08001a9c is character-identical):

uVar7 = 0;
uVar5 = 0;
do {
    uVar4 = (*(byte *)(param_2 + uVar5) + uVar7) * 0x10000 ^ _DAT_08001be4;
    uVar7 = uVar4 >> 0x10;
    uVar5 = uVar5 + 1 & 0xffff;
} while (uVar5 <= _DAT_08001be0);
*(undefined2 *)((param_1 + 4) * 2 + _DAT_08001be8 + 6) = (undefined2)(uVar4 >> 0x10);
*(undefined2 *)(param_1 * 2 + _DAT_08001be8 + 6)       = (undefined2)(uVar4 >> 0x10);

Reading the arithmetic as 32-bit C: ((acc + byte) * 0x10000 ^ K) >> 0x10 discards K's low 16 bits and the sum's bits above 16, so with KH = K >> 16 the recurrence, seed, and storage are exactly:

acc_0     = 0
acc_{i+1} = ((acc_i + data[i]) & 0xFFFF) ^ KH ,  i = 0 .. 2047
stored    = acc_2048 as u16_le at file offset 0x06 + 2*physical_block
covered   = the block's full 2048 bytes (file block_start .. block_start+0x7FF)
byte order= ascending offset; sum is unsigned byte addition; endianness only affects storage (LE)
  • Covered length: the loop runs while (index <= bound) from 0. The bound symbols (_DAT_08001b2c/_DAT_08001be0) are unresolved literal-pool values in this workspace; 2048 iterations (bound 0x7FF) is the unique length consistent with the 0x800 transfer size and with verification below — a 2047-iteration variant produces different per-block candidate constants for blocks 1 and 2 (no common KH), while 2048 yields a common constant for both (§4.3). Covered-range confidence: CONFIRMED_VERIFIED by elimination + verification, with the bound literal itself CONFIRMED_STATIC-unresolved.
  • Stored offsets: writer stores at header-RAM +6+2*slot and +6+2*(slot+4), i.e. one table indexed by physical block. In the file: block 1 → 0x08, block 2 → 0x0A, block 5 (backup 1) → 0x10, block 6 (backup 2) → 0x12. Reader compares against the same table entries. Confidence: CONFIRMED_VERIFIED.
  • Not a sum16 (block sums are 0x3522/0x4028 ≠ stored), not CRC16/CRC32 (no polynomial shift-register in the code; the recurrence is add-then-XOR), not XOR-fold. Algorithm enum for the JSON: custom.

4.3 The one unresolved bit (read before reimplementing)

Brute-forcing KH over all 65536 values against block 1 alone (2048 iterations, numpy-vectorised over KH) gives exactly two survivors, 0x7FFF and 0xFFFF; both also satisfy block 2, both backup blocks, and every zero block. Their trajectories differ only at every second step, always by exactly 0x8000, and re-converge on the next byte; because the covered length (2048) is even, the final stored value is identical. Therefore the .sav evidence in this workspace cannot distinguish KH = 0xFFFF from KH = 0x7FFF, and the low 16 bits of the code constant _DAT_08001be4/_DAT_08001b30 are provably irrelevant (shifted out). This report adopts KH = 0xFFFF (complement form, the natural reading of an XOR-with-all-ones constant) and marks the checksum CONFIRMED_VERIFIED for the covered data with that disclosed equivalence: any editor that uses 0xFFFF will produce files this game accepts — the equivalence is functional, not just empirical: random 2048-byte blocks also checksum identically under both constants (verified in this workspace) because the covered length is fixed and even. Bit 15 of the true ROM constant is therefore operationally meaningless for this format and remains UNKNOWN from .sav evidence; only the ROM literal-pool value (_DAT_08001be4/_DAT_08001b30, not in this workspace) could name it, and no mutation of a 2048-byte block ever can (see F14). Reimplementations must use the full 2048-byte recurrence — shortening the range silently changes results (e.g. truncating at the last nonzero byte does not reproduce the stored values; trailing zeros still toggle the accumulator).
