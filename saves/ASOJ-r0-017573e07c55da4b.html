All findings below are derived exclusively from the files present in this workspace (saves/*.sav, ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json) plus standard, publicly documented GBA hardware behavior (Flash cart I/O at 0x0E000000, EEPROM/DMA3, memory map). 1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven:

  • The cartridge uses a Flash 512K (64KB) save chip at 0x0E000000, driven by a

standard AMD/SST-style command-sequence Flash driver (chip-ID autoselect, 4KB sector erase, single-byte program, multi-byte program-with-verify-retry). This driver is fully present in ghidra/decompiled.c and matches the generic GBA Flash hardware protocol byte-for-byte (0xAA/0x55 unlock + 0x90/0xF0/0x80+0x30/0xA0 command bytes), independent of any game-specific knowledge.

  • The two real .sav samples in saves/ show a blank-flash boot (cap-00, all 0xFF)

followed by a post-save capture (cap-01) whose first 0x1000 bytes contain a 4-byte ASCII magic "PIRO", a 216-entry table of an identical 4-byte filler value, ten identical 16-byte blank records, and one distinct 32-byte trailer record. This layout was reconstructed and independently verified in Python directly against the binary (saves/cap-01-future-1.sav).

What remains open:

  • The higher-level serialize/build routine that actually assembles the "PIRO"

payload and calls into the Flash driver is not present in the 86-function decompilation set handed to this packet (the seed-extraction was hop-limited to the Flash transport layer). Consequently we cannot show RAM-mirror addresses, nor the exact caller instruction, for any field in the payload.

  • Nearly every traced function in the Flash driver ends in an UNRECOVERED_JUMPTABLE

indirect call (Ghidra could not resolve a computed jump table), so static caller edges into the Flash driver are almost entirely absent from ghidra/callgraph.json. The real dispatcher (very likely an SDK-style flash_command[] function-pointer table indexed by an opcode) is outside the provided decompilation.

  • No checksum, CRC, or integrity field was found — neither in the traced Flash

driver code nor as a numerically-consistent byte range in the .sav data (verified with sum8/xor8/sum16 sweeps below). This is reported as UNKNOWN, not assumed absent.

  • Only one non-blank sample exists, captured from what looks like a first/default save

(all record fields are at default/blank values). No field has yet been observed with a non-default value, so field semantics beyond structural shape are HYPOTHESIS.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses below come from ghidra/decompiled.c / ghidra/save_related_functions.c. This is a classic GBA Flash command-sequence driver (AMD/SST-style 0xAA/0x55 unlock bytes), a generic hardware pattern, not game-specific code.

3.1 Low-level hardware I/O driver functions

Shared low-level primitives (bodies are themselves UNRECOVERED_JUMPTABLE thunks — likely BIOS/SWI wrappers resolved only at link/runtime):

  • func_0x08099854 — byte compare/verify.
  • func_0x08099858 — generic N-byte write/poll transport (address, data, count, scratch).
  • func_0x08099860 — generic byte read.
  • 0x080997e8 — software_interrupt(0x0B) (BIOS CpuSet, used for the bank-switch copy).
  • 0x08099824 — software_interrupt(0x05) (BIOS VBlankIntrWait/Halt-class SWI, used for erase timing).

No EEPROM (0x0D000000/DMA3 0x040000D4) or raw SRAM byte-copy pattern was found — only the Flash command-sequence pattern targeting 0x0E000000, consistent with the packet's Observed Save Media: Flash 512K metadata.

3.2 Serialization / deserialization & checksum routines

Not present in the provided decompilation. The 86 functions available are limited to the Flash transport layer above plus one unrelated subsystem (see note below). No function in ghidra/decompiled.c references the ASCII bytes "PIRO", the repeated table filler 0x00008CA0, or the 0xC350 trailer value, so the routine(s) that build the in-RAM save image before handing it to the Flash driver could not be located or traced. This is explicitly UNKNOWN, not assumed to not exist.

3.3 Caller-chain mapping, using ghidra/callgraph.json

Static callers recovered for the Flash driver cluster are limited to the three internal edges below (everything else terminates in an unresolved indirect jump):

0x08098cf4 (chip detect/select) --calls--> 0x08098c5c (chip ID autoselect)
0x08099250 (sector erase)       --calls--> 0x08098ed4 (bank-switch copy helper)
0x08099194 (write+verify+retry) --calls--> 0x080990dc (multi-byte program, retry path)

ghidra/callgraph.json reports zero callers for every other Flash-driver function (0x08098fbc, 0x08099250 itself, 0x080992ec, and all of the func_0x080998xx thunks). This is not an artifact of incomplete search depth — decompiled.c shows the

reason: essentially every public entry point in this cluster ends in /* WARNING: Could not recover jumptable ... Too many branches */ followed by (*UNRECOVERED_JUMPTABLE)(...). The real game-side call sites almost certainly invoke this driver through a computed function-pointer table (an SDK-style flash_driver_opsopcode dispatch), which Ghidra's static analysis cannot resolve into caller edges. We therefore cannot show how any specific caller mutates an in-RAM save struct before flushing — that mutation happens upstream of the traceable code in this packet.

Unrelated cluster, explicitly excluded: ghidra/callgraph.json also contains a densely-connected cluster (0x0806a708 → 0x080535c8, 0x08053640, 0x08054208, 0x0806a6b0 → 0x08052878, plus 0x08001588/0x080034cc/0x08004158/0x08006b54) that manipulates 0x03000000-range IWRAM buffers with fixed sizes 0x1140/0x500/ 0x200 and 0x30-byte-stride channel records — the address space and record shapes are consistent with an audio/sound-mixer subsystem, not save data, and it never touches 0xE000000/0x0D000000/SRAM. It is noted here only to document that it was examined and ruled out, per the packet's "every relevant function" requirement.

Checksum / integrity algorithm

Result: UNKNOWN — no checksum/CRC field was identified.

No candidate checksum routine exists in the available decompilation (see §3.2), and no byte range in the populated region (0x0000–0x041F) numerically matches a plausible self-contained checksum of any neighboring data under the common encodings tested. Verification performed directly against saves/cap-01-future-1.sav:

$ python3 - <<'EOF'
d = open("saves/cap-01-future-1.sav", "rb").read()
def sum8(b):  return sum(b) & 0xff
def xor8(b):
    x = 0
    for c in b: x ^= c
    return x
def sum16le(b):
    s = 0
    for i in range(0, len(b) - 1, 2):
        s += int.from_bytes(b[i:i+2], "little")
    return s & 0xffff

print("sum8  (0x000-0x420):", hex(sum8(d[0:0x420])))
print("xor8  (0x000-0x420):", hex(xor8(d[0:0x420])))
print("sum16 (0x000-0x420):", hex(sum16le(d[0:0x420])))
print("sum8  (0x000-0x1000):", hex(sum8(d[0:0x1000])))
print("xor8  (0x000-0x1000):", hex(xor8(d[0:0x1000])))
EOF

Output:

sum8  (0x000-0x420): 0x50
xor8  (0x000-0x420): 0x4
sum16 (0x000-0x420): 0x4e98
sum8  (0x000-0x1000): 0xd7
xor8  (0x000-0x1000): 0x5f

None of these computed values appear anywhere else in the file as a plausible stored checksum (no byte or 16-bit field in the populated region equals 0x50, 0x04, 0x4e98, 0xd7, or 0x5f, nor their byte-swapped/complemented forms). This does not prove the absence of a checksum (a second, independent sample with differing payload bytes would be required to rule a cumulative-sum/CRC scheme in or out with certainty), but no evidence for one currently exists. Flagged UNKNOWN per the clean-room honesty requirement, not asserted as "no checksum."

7. Open Questions

  1. What code builds the "PIRO" payload, the 216×0x00008CA0 table, and the

10-record block? It is not present in the provided 86-function decompilation.

  1. What is the real caller of the Flash driver (the resolved target of the

UNRECOVERED_JUMPTABLE dispatches)? Almost certainly an indexed function-pointer table outside the extracted function set.

  1. Is there a checksum/CRC at all? Only one real sample exists; a second sample with

different payload bytes is required to test any cumulative-sum/CRC hypothesis with confidence.

  1. What do the two distinct trailer values (0x0000C350 = 50000, 0x4016, 0xD24C

at 0x0420/0x042C/0x042E) represent? No corroborating code was found.

  1. Is the 0xFF byte at +0xC of each 16-byte record a per-slot "unused" flag, a

string terminator, or something else? All 10 observed records are identical, so no contrastive evidence exists yet.

  1. Why are 10 identical records present — is 10 a meaningful count (e.g. a fixed-size

ranking/roster table), or an artifact of this specific capture? Cannot be determined from a single sample.
