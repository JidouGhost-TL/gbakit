1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven:

  • The EEPROM 4K hardware I/O stack (bit-serial DMA3 transfer primitive, 8-byte-sector read function, 8-byte-sector write-with-busy-poll function, and the bus-arbitration/lock wrapper pair) is fully decompiled and present in this workspace, and its sector-level behavior is consistent with the raw byte layout actually observed in both .sav samples.
  • The high-level "save block" API (full 512-byte block read/write, each going through an IRQ/audio-lock wrapper) is traced end-to-end from the low-level EEPROM sector loop up to the save-manager functions that call it.
  • A 3-record "slot table" (3 × 12-byte records) occupies file offset 0x00–0x23, immediately followed by a 4-byte generation/checksum field at 0x24–0x27 and a 1-byte flags field at 0x28. This structural layout is CONFIRMED_STATIC by code and CONFIRMED_VERIFIED against both .sav samples (sentinel/zero values line up exactly with what the init/commit code would produce).
  • A generic Fletcher/Adler-style two-running-sum checksum function (FUN_0800acb0) and a generic unsigned-modulo division routine (FUN_080115c4) were decompiled, and FUN_080115c4 was verified in Python to be bit-exact with a % b for arbitrary unsigned operands, including the canonical Adler-32 modulus 65521.
  • A 176-byte ascending test/calibration byte-fill (0x00..0xAF, written at logical offset 0x29..0xD8 by the save-table "cold init" path, FUN_08037f70) was matched byte-for-byte against the physical bytes recovered from both .sav files, once a per-8-byte-EEPROM-sector permutation is applied. 176 of 184 bytes in the region match the derived formula exactly; the 8 non-matching bytes are fully explained as expected incomplete-final-sector / first-sector boundary effects (see §4).

What remains open:

  • The exact numeric checksum modulus (_DAT_0800acf0) and seed (_DAT_0800acbc), and the ROM string constant parsed by the generic atoi-style helper FUN_080100ac, are data-segment values not present in this workspace (only decompiled code and two .sav files were provided — no ROM/.gba binary or data dump). The checksum formula is proven from code; its numeric behavior could not be verified against a real non-zero stored checksum because both captured .sav samples still have an all-zero, never-committed checksum field (record 0's status byte is 0x00 in both — i.e. neither sample ever ran the "finalize" branch that writes the checksum).
  • The low-level EEPROM "write single sector" function (func_0x0801594c), called from the write-loop wrapper FUN_0800ac1c, is referenced by address but its body is not present in this workspace's decompilation (only its sibling read function FUN_0801589c and the raw DMA3 primitive FUN_0801581c were extracted as MMIO seeds). Its behavior is inferred by symmetry with FUN_0801589c/FUN_08015960, not directly proven.
  • The semantic meaning of the 176-byte region at 0x29–0xD8 is a test/calibration fill pattern, not real gameplay data (both samples are identical in this region and match exactly the "cold-init ascending fill" branch of FUN_08037f70). No conclusions about actual gameplay save fields (inventory, level progress, etc.) can be drawn from these two samples — they appear to be freshly-initialized/never-played saves.

2. Physical Media, Slot Geometry & Redundancy

  • Media type: EEPROM 4K (512 bytes total addressable via 6-bit sector index × 8 bytes/sector = 64 sectors × 8 bytes = 512 bytes). SDK tag observed in corpus metadata: EEPROM_V124@1365908.
  • Bus: Standard GBA EEPROM access pattern — serial bit-stream DMA3 transfers through REG_DMA3SAD/DAD/CNT (0x040000D4+), addressing the EEPROM I/O window at 0x0D000000.
  • File size as captured: 512 bytes (matches 4K EEPROM exactly).
  • Active (non-fill) data window: file offset 0x00–0xDF (224 bytes). Bytes 0xE0–0x1FF (288 bytes) are 0xFF fill, i.e. never written by the traced code — the game only uses the first 28 of the 64 available 8-byte sectors.
  • Slots / copies: One single-generation save table is present — no redundant/backup mirror copy was found inside the active 224-byte window. The table consists of:
  • 3 fixed-size 12-byte "slot" records at offsets 0x00, 0x0C, 0x18 (see §5).
  • One 4-byte generation/checksum field at 0x24.
  • One 1-byte flags field at 0x28.
  • One 176-byte payload/fill region at 0x29–0xD8 (observed, in both samples, to be the "cold-init ascending calibration fill," not gameplay data).
  • Generation / sequence counter: The 0x24–0x27 field doubles as a generation counter + checksum (see §4); in both available samples it is still 0x00000000 (table never finalized/committed).
  • Selection rule: FUN_08037f70 reads the single table (there is only one; no slot-selection logic was found) and decides whether to keep or reinitialize it purely based on whether the stored value at +0x24 matches a freshly recomputed seed + checksum(record0). There is no multi-copy "pick the newest valid copy" logic of the kind seen in some SRAM save formats — this title relies on checksum-triggered full reinitialization instead of redundancy.

3.5 How each caller mutates the in-RAM save struct before flushing

  • FUN_08037f70 (cold path) directly memsets RAM at structBase+0x00..0x23 to zero, writes structBase+0x24 (checksum) and structBase+0x28 (flags), and byte-fills structBase+0x29..0xD8, before calling WriteSaveBlock. This is a full-table RAM mutation, confirmed in code.
  • FUN_08038088 mutates only one 12-byte slot record's two 4-byte fields (packing several 1-byte RAM counters into "field B" and copying a 4-byte RAM counter verbatim into "field A"), and only touches the checksum field +0x24 when its param_2 finalize flag is set. This is a partial, single-slot RAM mutation.
  • Both callers ultimately call the same WriteSaveBlock (FUN_08037eb8), which always rewrites the full 512-byte EEPROM image (size=0x200) — there is no partial/sector-only commit path in the traced code.

4. Magic Signatures & Checksum / Integrity Algorithm

No fixed ASCII/byte magic signature was found in the active 0x00–0xDF window of either sample (the apparent "magic strings" 6543210/, :987FEDCBA, etc. reported in the corpus metadata are an artifact of the calibration byte-fill described below being misread as ASCII — they are not a real signature; see the formula-vs-bytes verification below).

4.1 Checksum algorithm — FUN_0800acb0

uint FUN_0800acb0(byte *param_1, int param_2)
{
  uVar1 = _DAT_0800acf0;                 // modulus M (data value, not in this workspace)
  iVar3 = 0;                             // running "sum1"
  iVar4 = _DAT_0800acbc;                 // running "sum2", seeded from a data value
  while (param_2 != 0) {
    iVar3 = iVar3 + 1 + (uint)*param_1;  // sum1 += 1 + byte   (Adler-style "+1 per byte")
    param_1 = param_1 + 1;
    iVar4 = iVar4 + iVar3;               // sum2 += running sum1
    param_2 = param_2 - 1;
  }
  iVar3 = func_0x080115c4(iVar3, _DAT_0800acf0);  // sum1 %= M
  uVar2  = func_0x080115c4(iVar4, uVar1);          // sum2 %= M
  return iVar3 << 0x10 | uVar2;          // combined = (sum1 % M) << 16 | (sum2 % M)
}

This is structurally identical to the classic Fletcher-16/Adler-32 two-running-sum checksum family: sum1 = (Σ(1+byte)) mod M, sum2 = (Σ running-sum1) mod M, combined as sum1<<16 | sum2. FUN_080115c4 (the modulus operator used here) was verified below to be exactly a % b.

Covered range (as called): FUN_0800acb0(*piVar6, 0xC) — exactly 12 bytes, the first slot record only (file offset 0x00–0x0B), not the whole table. The combined result is added to FUN_080100ac(romStringConstant, 0, 10) (a decimal string-to-integer parse of a ROM data constant — generic libc-style atoi/strtol, not game-specific) and the sum is stored as a plain 32-bit little-endian integer at file offset 0x24.

Stored offset: 0x24, size 4 bytes, little-endian, int32.

Covered byte range: 0x00–0x0B (first 12-byte slot record).

4.4 The 176-byte "ascending fill" region — verified permutation match

The reset/init branch of FUN_08037f70 contains:

uVar5 = 0;
do {
  *(char *)(iVar1 + 0x29 + uVar5) = (char)uVar5;
  uVar5 = uVar5 + 1 & 0xff;
} while (uVar5 < 0xb0);

This writes a plain ascending byte counter 0, 1, 2, …, 175 at logical offsets 0x29..0xD8. Both .sav samples are byte-identical in the 0x28–0xDF window (184 bytes), and show a value pattern that does not match a plain linear counter at face value — but does match it exactly once a per-8-byte-EEPROM-sector permutation (consistent with the halfword-reversal behavior proven in FUN_0801589c/FUN_08015960, §3.1) is applied:

def predicted_byte(abs_offset):          # abs_offset in [0x28, 0xDF]
    B = (abs_offset - 0x28) // 8         # sector index, relative to 0x28
    p = abs_offset % 8                   # position within the 8-byte EEPROM sector
    return (8*B + 6 - p) if p < 7 else (8*B - 1)

# Verified against saves/cap-00-future-0.sav and saves/cap-01-future-1.sav (identical in this window):
# 176 of 184 bytes match predicted_byte() exactly.
# The 8 non-matches are:
#   - offset 0x2F (first sector, position 7): actual 0x07, formula predicts a wrap-around (-1 & 0xff = 0xFF).
#     This is the one sector where there is no "previous sector" to carry a byte from — a boundary
#     clamp, not a formula failure.
#   - offsets 0xD8-0xDE (7 bytes): actual 0xFF (fill/never-written), formula predicts 0xB0-0xB6.
#     The fill loop stops at uVar5=175 (0xAF), so the final sector (0xD8-0xDF) only ever receives
#     the one "carried-over" byte at its position-7 slot (0xDF = 0xAF, verified to match), and its
#     other 7 positions were genuinely never written -> correctly still fill-byte 0xFF.

Result: both exceptions are fully explained by sector-boundary effects, not formula errors. This is strong, reproducible evidence that:

  1. Both captured .sav files are in the "cold-init, never finalized" state produced by FUN_08037f70's reset branch — i.e. these are not real played-through saves, but freshly-initialized (or test/calibration) EEPROM images.
  2. The raw bytes in a .sav dump for this title reflect physical EEPROM sector order, not the logical byte order the game code writes in — any future byte-level mapping work on this title's save format must account for this 8-byte-sector permutation before interpreting offsets as "logical" game data.

The previously-reported "ASCII magic strings" (6543210/, NMLKJIHGVUTSRQPO, etc., from the corpus metadata) are simply this permuted ascending-byte-counter pattern happening to fall in the printable ASCII range — not a real magic signature.

6. Save Fuzzing & Counterfactual Verification Plan

No .ss save states were provided in states/ for this release (packet notes "0 states… none for this legacy checkpoint cohort"), so the following plan is written for the next capture round that does include paired .ss states, using the field map above.

  1. Checksum-field mutation (offset 0x24-0x27):
  • Mutation: flip any single bit in the stored 32-bit value (currently 0x00000000) to a non-zero value, keeping record 0 (0x00-0x0B) unchanged.
  • Requires checksum repair: yes, once a real non-zero checksum has been observed — need seed and modulus M recovered first (see open question in §1).
  • Predicted effect: on next boot, FUN_08037f70's comparison stored != seed+checksum will be true, forcing the cold-reset branch — i.e. the game should treat the save as corrupt and silently reinitialize it (zeroing all 3 slot records and rewriting the ascending fill + flags). This is directly observable via RAM inspection of structBase+0x00..0x28 immediately after the next save-load, or by reloading a .ss taken right after the title screen.
  1. Record 0 "field A"/"field B" mutation (offset 0x04-0x0B):
  • Mutation: change 0x00FFFFFF to 0x00000000 in either field.
  • Requires checksum repair: yes, if the checksum field is ever non-zero in the sample used (not needed for the current all-zero samples, since the checksum comparison would still trivially fail either way given it's already in the never-finalized state).
  • Predicted effect: changes the value FUN_0800acb0 computes over record 0, which (once +0x24 is non-zero/finalized in a future sample) should change the stored checksum on the next finalize-commit. This directly tests the checksum's 12-byte coverage boundary (record 0 only vs. all 3 records).
  1. Flags byte mutation (offset 0x28):
  • Mutation: set each of the 4 low bits individually (0x01, 0x02, 0x04, 0x08) and observe via RAM dump of the 4 destination byte flags that FUN_08038300 writes.
  • Requires checksum repair: no (flags byte is outside the checksummed 12-byte range).
  • Predicted effect: each bit should toggle exactly one of 4 independent RAM byte flags on load — a strong, cheaply falsifiable test of the bit-unpack mapping proven in §3.4.
  1. Record 2 "field B" mutation (offset 0x20-0x23, the one field proven to actually change across saves):
  • Mutation: zero all 4 bytes, or set the top byte (bit 24-31, hypothesized frame/tick index) to 0xFF.
  • Requires checksum repair: no (record 2 is not part of the checksummed 12 bytes).
  • Predicted effect: since this field's packing/unpacking is fully proven in FUN_08038088 but its gameplay meaning is not, the counterfactual here is purely mechanical: confirm that on next FUN_08038088 commit, the game correctly re-derives the same packed value from its own RAM counters (i.e. the mutation should be silently overwritten on the next commit rather than causing a corruption/crash), falsifying or confirming that this field is pure derived/transient state rather than authoritative save data.
  1. Fill-region mutation (offset 0x29-0xD8):
  • Mutation: overwrite the full 176-byte region with 0xFF.
  • Requires checksum repair: no (outside the checksummed range).
  • Predicted effect: since no reader of this region was found in the traced code, the prediction is a protocol negative — the game should show no observable behavior change after reload. If any observable effect does occur, that falsifies the "cold-init test fill, never read back" hypothesis in §4.4 and would indicate an untraced reader exists outside this workspace's decompilation window.
  1. Fresh vs. restore matched-duration control:
  • Capture one .ss immediately after a genuine in-game save (not just booting to title) to obtain a sample where record 0's status byte is non-zero and the 0x24 checksum field is finally non-zero. Diff that sample against the two cold-init samples here to (a) numerically solve for the unknown modulus/seed via the now-known checksum formula, and (b) determine whether the 0x29-0xD8 region is overwritten with real gameplay data or left as the calibration fill forever (testing whether that region is genuinely dead/unused past first boot).
