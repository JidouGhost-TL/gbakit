1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + .sav bytes agree):

  • The save medium is EEPROM, organized as 64 blocks of 8 bytes (512 bytes total), matching the EEPROM-4K bus protocol implemented by the traced driver functions.
  • There is a fixed 4-byte ASCII "format stamp" at file offset 0x04-0x07. The literal bytes 'N','G','D','K' are written by the format/erase routine FUN_080038d0. In the real .sav, this field appears byte-reversed as "KDGN" (4b 44 47 4e) — and this reversal is explained and proven by the low-level EEPROM write driver's own bitstream-construction logic (see §4).
  • The candidate per-save checksum routine FUN_080037c8 (len + byte-sum) is proven, by exhaustive brute force over every possible length, to be incapable of producing the byte pattern actually stored at offset 0x04-0x07 in the available sample — its maximum possible output (0x1F800) is roughly 10,000× smaller than the stored value (0x4E47444B). This is a rare case where a negative result is itself a verified finding: it rules out the obvious "offset 4-7 is the live checksum" hypothesis for this specific capture.

What remains open / unverified:

  • The exact value and meaning of the 4-byte word at offset 0x00-0x03 (compared against a ROM/IWRAM constant we cannot read from decompiled C alone).
  • Whether the "real" checksummed commit path (FUN_08003920) ever executed in either of the two supplied .sav snapshots, or whether both snapshots only reflect the one-time blank-EEPROM formatting pass.
  • The purpose of a single non-zero EEPROM block (block #37, file offset 0x128-0x12F) inside an otherwise fully zero-filled progress struct — no writer was traced to this specific block.
  • Only 2 actual .sav files were available (one fully-erased, one post-boot), which is too few samples to empirically distinguish a true live checksum from a static format constant with full certainty; the reasoning above is sound but would benefit from a deliberate in-game save action and a second checksum sample.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 The "KDGN" field is a reversed format stamp, not an ASCII magic literal and not the live checksum

File offset 0x04-0x07 in cap-01-future-1.sav reads 4b 44 47 4e → ASCII "KDGN". Two competing explanations were tested:

  1. Hypothesis A — it is FUN_080037c8's checksum output, computed over the 293-byte payload starting at offset 8.
  2. Hypothesis B — it is FUN_080038d0's hard-coded format stamp ('N','G','D','K'), stored byte-reversed because of how the low-level EEPROM writer serializes data.

Python verification (actual output):

offset 0x00-0x03 (hdr1) raw bytes: 00000125 -> LE32 0x25010000
offset 0x04-0x07 (hdr2) raw bytes: 4b44474e -> ASCII KDGN

--- Hypothesis test: hdr2 == FUN_080037c8(payload[:L]) = L + sum(bytes) for any L in 0..504 ---
max achievable checksum value for L=504: 129024 (0x1f800)
stored hdr2 as uint: 1313293387 (0x4e47444b)
matching lengths found: [] => IMPOSSIBLE, checksum formula cannot produce stored value

--- Counter-test: FUN_080038d0 hardcoded magic-stamp bytes [0x4e,0x47,0x44,0x4b] (N,G,D,K) ---
stamp as written by code (forward RAM order): 4e47444b NGDK
stamp reversed byte order:                    4b44474e KDGN
matches stored hdr2 bytes exactly: True

Conclusion (CONFIRMED_VERIFIED): Hypothesis A is disproven outright — 0x4E47444B (~1.31 billion) exceeds the maximum possible 32-bit output of len + Σbytes for any payload of 0-504 bytes (max 0x1F800 ≈ 129,024) by roughly four orders of magnitude, for every candidate length. Hypothesis B is confirmed exactly: the stored bytes are the precise byte-reversal of the literal stamp FUN_080038d0 writes (N,G,D,K → K,D,G,N).

Root cause of the reversal (CONFIRMED_STATIC from code): FUN_0803d92c (the raw EEPROM block writer used only by the unverified format path) builds its output bitstream into a stack buffer using a pointer that decrements on every store (puVar5 = puVar5 + -1), i.e. it serializes the 4 source halfwords starting from the last word toward the first. This is the standard GBA EEPROM write pattern (address bits + data bits shifted out MSB-first per bit, buffer built backwards so the final DMA3 transfer streams it forward), and it is exactly what produces a reversed byte order in the EEPROM cell relative to the RAM template's natural left-to-right byte order.

4.2 Header word 0 (offset 0x00-0x03) — magic/version constant

FUN_08003960 compares this word against *_DAT_080039b0, a value stored via pointer indirection in ROM/IWRAM whose literal contents are not visible anywhere in the supplied decompiled.c text (no ROM binary was provided in this workspace, consistent with the clean-room scope). We cannot independently verify the expected value. The observed stored bytes are 00 00 01 25.

Hypothesis (not proven): bytes 0x02-0x03, read as 0x0125 = 293 decimal, are suggestively identical to the 0x125-byte struct-length constant used in three other places in the code (the FUN_08029eb0 corruption-recovery zero-fill loop, an earlier default-init zero-fill loop, and the len arguments passed into FUN_08003960/FUN_08003920 from both entry points). This would make offset 0x00-0x03 a packed {reserved:u16, structSize:u16} version/layout tag rather than a save-counter. This is flagged HYPOTHESIS in the field map — a second .sav sample with a different struct version, or a ROM binary read at *_DAT_080039b0's referenced address, would confirm or refute it.

4.3 Checksum algorithm — proven by code, not exercised in these samples

// FUN_080037c8 (clean-room transcription from ghidra/decompiled.c)
int Checksum8(byte *data, int len) {
    int acc = len;
    for (int i = 0; i < len; i++) acc += data[i];
    return acc;   // 32-bit wraparound, no CRC/complement
}

This is unambiguous in the decompiled code and is called from both the commit path (FUN_08003920) and the verify path (FUN_08003960) with matching semantics (write time: checksum computed over the about-to-be-written payload; load time: checksum recomputed over the just-read payload, compared to the stored word). However, as shown in §4.1, this formula cannot have produced the bytes actually present at offset 0x04-0x07 in the one populated sample we have. The most defensible reading is that FUN_08003920 never actually ran in the captured session — only the one-time FUN_080038d0 format pass did (consistent with the short 600-frame / ~3-second cold-reload probe in the packet metadata, which shows no explicit in-game save action). This checksum is therefore rated CONFIRMED_STATIC (the algorithm is certain from code) but has zero verified samples — it should be the first target of the fuzzing plan in §6.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below are designed to be applied to a .sav loaded from a paired pre-save .ss state, then reloaded, with the post-load .ss state and on-screen/RAM behavior compared against predictions.

  1. Force the real checksum path to execute. Perform an actual in-game save action (not just boot), capture the resulting .sav, and recompute Checksum8(payload[8:8+0x125]) in Python. Prediction: the new offset 0x04-0x07 value should differ from "KDGN" and should exactly equal 0x125 + Σ(payload bytes). This single test would resolve the central open question in §1.
  2. Corrupt the format stamp only (flip one bit at offset 0x07), reload without touching anything else. Prediction: since no reader of this field was traced, gameplay should be unaffected; if it does cause a visible reformat/reset, that proves an as-yet-untraced magic check exists.
  3. Blank the header word 0 (0x00-0x03 → FFFFFFFF) while leaving the payload intact, reload. Prediction: FUN_08003960 should return code 2 (magic mismatch). Per the traced code, only return code 1 has an explicit recovery branch in FUN_08029eb0 — this test should reveal whether code 2 is handled elsewhere (e.g. triggers a full FUN_080038d0 reformat) or causes a stall, which this packet's traced functions cannot determine.
  4. Toggle EEPROM block #37 (0x128-0x12F) between all-zero, all-0xff, and its current mixed pattern, reload each time. Prediction: resolves the unknown_block_0x25_marker field — a gameplay/UI change indicates a live field; no change indicates a static template artifact.
  5. Single-byte mutation inside the payload (e.g. offset 0x10) without repairing the header checksum, reload. Prediction (requires checksum repair to avoid reset): FUN_08003960 recomputes the checksum over the mutated payload, finds it doesn't match the stale stored header checksum, returns 1, and FUN_08029eb0 zero-fills and rewrites the entire struct — i.e. the mutation is not preserved; the save instead resets to defaults. To make a payload edit stick, the checksum at offset 0x04-0x07 must be recomputed as 0x125 + Σ(mutated 293 bytes) and written back in the matching byte order determined by test 1.
  6. Matched-duration control: repeat the cold-reload probe (boot → wait 600 frames → compare) with the unmodified original .sav twice, to confirm the "fully deterministic, no autosave-on-boot" baseline before attributing any mutation's effect to the mutation itself rather than to run-to-run nondeterminism.
