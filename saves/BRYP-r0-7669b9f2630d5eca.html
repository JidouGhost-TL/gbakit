GBA Save Format Report — Rayman - Hoodlums' Revenge (Europe) (BRYP)

Clean-room analysis. Sources used only: saves/*.sav (2 × 512 B), saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware addresses from PACKET.md. No third-party game data was used.

Release: BRYP-r0-7669b9f2630d5eca, game code BRYP, ROM SHA-256 7669b9f2630d5eca543be5bc29ea0e2c81fd0557a1231079978854d432eeb95a.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (core format: HIGH; field semantics beyond headers: LOW).

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM, 512 bytes total, accessed as 64 blocks of 8 bytes via DMA3 to 0x0D000000.
  • One contiguous logical image of 504 bytes at EEPROM offset 0: a 104-byte global/config record followed by four 100-byte save slots. The final 8 bytes (504..511) are unused (0xFF).
  • Each record starts with a u16_le byte-sum checksum and a magic byte 'G' (0x47) at offset +2.
  • The checksum formula, covered ranges, magic, record sizes/offsets, and the per-8-byte-block byte reversal between the physical .sav file and the logical RAM image were all verified in Python against both real saves: 10/10 checksums match (1 global + 4 slots × 2 files).
  • Cross-file evidence: the only difference between the two saves is logical global byte +4 (0x06 → 0x01, delta −5) and the global checksum low byte changes by exactly −5, independently confirming checksum coverage.

Static-only (CONFIRMED_STATIC, code seen, not exercised by a populated save):

  • Slot/global initialization values and the load-time validate-or-reinitialize logic.
  • EEPROM write/verify/retry behaviour and read-back memcmp after every write.
  • Readers/writers listed in §3.

Unknown / hypothesis (HYPOTHESIS / UNKNOWN):

  • Semantics of global bytes +3..+7, the six 16-byte sub-entries in the global record, and all slot payload bytes +3..+99. Both samples contain freshly initialized, otherwise empty saves (all payload bytes are 0x00), so no populated field can be named honestly.
  • The numeric RAM mirror address. Ghidra shows the buffer only through unresolved literal-pool pointers (e.g. _DAT_08025df4, _DAT_08025d50); without the ROM bytes the 0x02xxxxxx/0x03xxxxxx value cannot be read from this workspace. The buffer is proven contiguous (see §3), only its base address is unknown.
  • Gameplay callers that mutate slot/global payload and invoke the flush functions outside the traced init/load paths. No such direct callers exist in callgraph.json or in the 223 decompiled functions (see §3.4).

2.1 Logical layout (RAM image / EEPROM logical offsets)

0x000  Global/config record   104 bytes (0x68)
0x068  Slot 0                 100 bytes (0x64)
0x0CC  Slot 1                 100 bytes
0x130  Slot 2                 100 bytes
0x194  Slot 3                 100 bytes
0x1F8  (end of used image, 504 bytes)
0x1F8..0x1FF  Unused, 0xFF (one whole 8-byte block)

Proof: FUN_08025e50 flushes the global record with FUN_08034eb4(0, 0x68, buf, 2). FUN_08025e74(slot) flushes with FUN_08034eb4(slot_base - (global_base - 0x68), 100, slot_ptr, 2), i.e. EEPROM offset 0x68 + slot*100, length 100. FUN_08025dd8 loads 0x1F8 = 104 + 4*100 bytes in one read. These three independent call sites agree exactly.

2.2 Physical .sav encoding (block byte reversal)

The emulator .sav file is not the logical byte stream. Within each aligned 8-byte block, bytes are reversed:

logical_offset  ->  physical_offset = (logical & ~7) | (7 - (logical & 7))

This comes from the serial EEPROM bitstream packing/unpacking in FUN_0803c5ac (read: 4 × u16 reconstructed MSB-first into descending u16 slots) and FUN_0803c670 (write: each u16 expanded MSB-first). It was not assumed: applying this transform makes all 10 record checksums and all 5 'G' magics verify (§4); direct, 16-bit-swap, 4-byte-reverse, and word-reverse transforms all fail.

Consequences for the raw file:

  • Global header logical bytes CB 01 47 00 06 FF 7F 00 appear physically as 00 7F FF 06 00 47 01 CB.
  • Each empty slot shows 0x47 at physical slot_logical_start+5 (its magic, logical +2 after block remapping) and at the byte holding its checksum low byte (logical +0, value 0x47 because an empty slot sums to 0x47), e.g. slot 0 at physical 0x6D/0x6F, slot 3's checksum byte at physical 0x1F3-area boundaries as listed in hexdump_and_diffs.txt.

2.3 Redundancy, counters, selection rule

  • Copies: exactly one copy of the global record and one copy of each slot. No backup/mirror copy and no A/B ping-pong was found in code or in the 512-byte image.
  • Generation/sequence counters: none. No monotonically increasing field is written by any traced save function; the only varying byte between the two samples is global +4 (semantics unknown, §5).
  • Selection rule (load, FUN_08025dd8):
  1. Read 504 bytes. If the EEPROM read itself fails, return failure (0).
  2. If global magic != 'G' or global checksum mismatches → reinitialize everything (FUN_08025cc4: fresh global + all 4 slots, each flushed).
  3. Else, for each of the 4 slots independently: if slot magic/checksum mismatches → reinitialize that slot only (FUN_08025d64, which flushes just that slot).
  • Write-side redundancy: every block write is verified by read-back compare (FUN_0803c7d0), retried up to 3 times at block level (FUN_0803c828), up to 8 attempts per block at range level (FUN_08034b90/FUN_08034cd4), and a full-range write is followed by a read-back + memcmp (FUN_080446b0) in FUN_08034cd4. Integrity is therefore per-record checksum + write-verify, not duplication.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM 0x08xxxxxx. FUN_08042c08/FUN_08042c0c are unrecovered-jumptable library stubs used as memcpy-style copies; func_0x… names in the decompilation denote the same addresses.

3.4 What was not found (honest gap)

Exhaustive text search of all 223 functions finds the byte 0x47/'G', the checksum function FUN_080388cc, and the flush functions referenced only at the call sites above. FUN_08025e50, FUN_08025e74, FUN_08025dd8, and FUN_08025f08 have no direct callers in the callgraph. Therefore, in this traced corpus, no gameplay function is observable mutating slot/global payload and then flushing. The likely explanations, in order: (1) gameplay writers call the flush functions through function pointers / unrecovered jumptable tail-calls that Ghidra did not resolve into the graph; (2) payload mutation code was not trace-reached and is absent from the 223 functions. Either way, naming any specific gameplay mutator from this workspace would be fabrication, so none is named. This is the main reason overall confidence is MEDIUM rather than HIGH.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • One magic byte per record: 'G' = 0x47 at logical offset +2 of the global record and of every slot.
  • Code proof: init writes *(byte*)(buf+2) = 0x47 in both FUN_08025cc4 and FUN_08025d64; load tests (char)puVar5[1] == 'G' (second u16, low byte = byte +2) in FUN_08025dd8 for global and each slot.
  • Save proof: after the §2.2 block-reversal transform, byte +2 is 0x47 in all 5 records in both files (physically scattered, e.g. global at physical 0x05, slot 0 at physical 0x6D). There is no multi-byte ASCII signature; the PACKET's empty ascii_magic_strings is explained by the reversal hiding the single-byte magic.

4.2 Checksum algorithm (exact)

stored_u16_le(record+0) = ( Σ_{i=0}^{N-1} (u8)record[2+i] ) & 0xFFFF
global: N = 0x66 = 102  -> covers logical bytes 2..103 inclusive, stored at logical 0..1
slot:   N = 0x62 =  98  -> covers logical bytes 2.. 99 inclusive, stored at logical 0..1
  • Algorithm class: plain additive sum8 accumulated into a wider integer, truncated to u16_le on store. No seed, no complement, no XOR, no CRC, no final-byte exclusion beyond the 2 stored bytes themselves (the covered range starts at +2, i.e. it includes the magic byte — which is why an empty slot's checksum is exactly 0x47).
  • Code proof (FUN_080388cc): iVar2 = 0; do { iVar2 += *(byte*)(param_1 + uVar1); } while (...) with call sites FUN_080388cc(buf+1_as_u16_ptr, 0x66) = byte pointer buf+2, and *puVar = uVar2 storing the low 16 bits (FUN_08025e50, FUN_08025e74, validated identically in FUN_08025dd8).
  • Stored offsets (logical): global 0x00, slots 0x68, 0xCC, 0x130, 0x194 (each record +0). Physical file offsets of the stored low byte follow §2.2 (e.g. global checksum low byte at physical 0x07, high byte at 0x06).

6. Save Fuzzing & Counterfactual Verification Plan
