Save Format Report — The Lord of the Rings, The Third Age (USA, Europe) (En,Fr,De,Es,It) [B3AE-r0-721d5d0339f4c97a]

1. Executive Summary & Overall Confidence

Overall Confidence: LOW

This release's trace-guided Ghidra decompilation (ghidra/decompiled.c, 268 functions, address range 0x08000778–0x0804e434) contains zero references to EEPROM/SRAM/Flash MMIO (0x0D000000, 0x0E000000, DMA3 0x040000D4), and ghidra/save_related_functions.c confirms 0 MMIO seed functions and 0 candidate functions were found by the automated save-driver search. ghidra/callgraph.json contains the same 268 functions with no entries in the save-I/O address neighborhood.

The ROM's declared SDK save tag is EEPROM_V124@10527748 (decimal file offset), which resolves to ROM address 0x08A0A404 — far outside the traced/decompiled function range (max traced address 0x0804e434). In other words: the actual EEPROM read/write driver was never executed during trace capture and is therefore completely absent from this workspace's static evidence. No writer, reader, serialization, or checksum routine can be cited by address for this release.

What was proven, strictly from the single .sav binary in saves/:

  • The file is exactly 512 bytes, fully consistent with a 4 Kbit (eeprom512) EEPROM device — the SDK tag name (EEPROM_V124) is consistent with this media kind, though code-level confirmation is absent.
  • Of the 64 possible 8-byte EEPROM "lines" in a 512-byte EEPROM, only 2 lines are non-blank (not 0xFF): line 0–2 region (bytes 0x00–0x1F, actually lines 0, 1, 2 are non-blank and line 3 is a specific sentinel pattern) and line 28 (bytes 0xE0–0xE7). All other 60 lines are 0xFF-filled (erased/never-written EEPROM state).
  • Byte-reversing the first 8 bytes (33 31 30 30 45 41 33 42 → 42 33 41 45 30 30 31 33) decodes as ASCII "B3AE0013" — i.e., this release's own game code (B3AE) followed by "0013". This is a strong structural observation but its purpose (identity/version stamp vs. coincidental artifact of how the capture tool serialized the EEPROM line) is a hypothesis, not a verified fact, because no writer code is available to confirm it is deliberately written by the game in reversed order rather than being a dump-tooling artifact.
  • An identical 8-byte pattern FF 00 00 00 00 00 00 00 occurs at both offset 0x18 (end of the populated block) and offset 0xE0 (otherwise isolated inside the blank region). This repetition is suggestive of a sentinel/terminator or secondary-slot marker, but with only one .sav sample this cannot be distinguished from coincidence.
  • No checksum, CRC, or integrity algorithm could be confirmed. A brute-force scan (documented in Section 4) over every plausible sum8/XOR8 combination inside the populated bytes produced 1,888 spurious "matches" — an expected result when testing an underdetermined system against a single data point, not evidence of a real checksum.

Bottom line: this packet's static evidence is centered entirely on one raw .sav snapshot with no corroborating decompiled save-I/O code. Every semantic claim below is explicitly marked HYPOTHESIS or UNKNOWN unless it is a direct, literal observation of the bytes themselves (CONFIRMED_VERIFIED is reserved here for "this is what the bytes literally contain," not "this is what the field means").

3. Save Writer, Reader & Caller-Chain Architecture

No save-related functions are present in this workspace's decompiled corpus.

  • ghidra/save_related_functions.c explicitly reports 0 MMIO seeds, 0 total functions (header comment: "0 save-bus/EEPROM/DMA3 MMIO seed functions ... 0 total with 2-hop callers + 1-hop callees").
  • A manual re-verification was run against ghidra/decompiled.c for the literal strings eeprom, sram, flash, dma3, 0x040000d4, 0x0d00, 0x0e00, checksum, 0x5555, 0x2aaa (case-insensitive) — zero matches.
  • ghidra/callgraph.json was loaded and enumerated: it contains exactly the same 268 function addresses as decompiled.c (range 0x08000778–0x0804e434), confirming the callgraph does not extend into the save-I/O region of the ROM.
  • The SDK save tag EEPROM_V124 is located at ROM address 0x08A0A404 per the packet's declared file offset (10527748 decimal = 0xA0A404, plus the 0x08000000 ROM base). This address is >750 KB past the highest traced function (0x0804e434), meaning the trace-capture session that produced this decompilation never executed the save subsystem (no save/load UI action was triggered during the capturing playthrough, or the save routine lives in a code region the tracer didn't cover).

Consequence: there is no hardware I/O driver, no serialization/deserialization routine, no checksum function, and no caller chain that can be cited by address for this release. Any claim of "function X writes field Y" would be fabricated and is explicitly withheld. The io_driver_functions and caller_chains arrays in save-format.json are empty for this reason, and this is itself a reportable finding (missing trace coverage), not an omission.

Required next step to raise confidence: re-run (or request re-run of) trace-guided decompilation after driving the emulator through an explicit in-game save action, specifically to capture execution at/near ROM offset 0xA0A404 (0x08A0A404), then re-extract save_related_functions.c seeds from the resulting trace.

4.1 Candidate magic signature

Offset 0x00, 8 bytes, raw: 33 31 30 30 45 41 33 42 (ASCII "3100EA3B").

Byte-reversed: 42 33 41 45 30 30 31 33 → ASCII "B3AE0013" — exactly this release's game code (B3AE) followed by the literal digits "0013".

raw bytes      : 33 31 30 30 45 41 33 42
as ASCII       : 3 1 0 0 E A 3 B
byte-reversed  : 42 33 41 45 30 30 31 33
reversed ASCII : B 3 A E 0 0 1 3

This is a direct, literal observation (CONFIRMED_VERIFIED as a byte pattern). Its interpretation — a deliberate game-written identity/compatibility stamp — is a HYPOTHESIS, with an explicit competing hypothesis also recorded: the reversal could be an artifact of how the capture tool serialized a single 8-byte EEPROM "line" into the .sav file (e.g., bit/byte order chosen by the emulator's EEPROM backend), rather than something the game itself wrote in reverse. No code is available to adjudicate between these two explanations.

verified_in_code: false (no writer function traced). verified_in_sav: true (literal bytes present).

4.2 Checksum / integrity algorithm

No checksum algorithm could be confirmed or even proposed with any confidence. Two independent obstacles:

  1. No checksum/CRC function exists anywhere in the traced decompiled code (Section 3).
  2. Only one .sav sample exists in saves/. A checksum hypothesis requires at least two independent save states (ideally with a deliberately mutated field) to distinguish a real checksum from coincidence. With n=1, the system is massively underdetermined.

To make this concrete, the following brute-force verification was run in Python against the one available .sav file, testing every single byte within the populated region as a candidate "stored checksum" against every possible contiguous sub-range (excluding itself) as the "covered range," using both 8-bit additive sum and 8-bit XOR:

data = open('saves/cap-00-future-0.sav','rb').read()
active = list(range(0,0x20)) + list(range(0xE0,0xE8))

def sum8(b): return sum(b) & 0xff
def xor8(b):
    v = 0
    for x in b: v ^= x
    return v

found = []
for i in range(32):
    stored = data[active[i]]
    for start in range(32):
        for end in range(start + 1, 33):
            rng = bytes(data[active[k]] for k in range(start, end) if active[k] != active[i])
            if not rng:
                continue
            if sum8(rng) == stored:
                found.append(('sum8', active[i], start, end))
            if xor8(rng) == stored:
                found.append(('xor8', active[i], start, end))

print("candidate matches found:", len(found))

Output:

candidate matches found: 1888

1,888 "matching" (position, algorithm, range) triples were found. This is the expected behavior of a badly underdetermined search (32 candidate stored-byte positions × hundreds of candidate ranges × 2 algorithms, tested against a single sample) and is not evidence of a real checksum — it is evidence that single-sample checksum recovery is not meaningful here. No specific one of these 1,888 coincidences is reported as a finding.

Conclusion: checksums in save-format.json lists this attempt with confidence: UNKNOWN and an explicit note that the match count reflects search-space size, not a verified algorithm. A real checksum cannot be confirmed until either (a) decompiled checksum code is captured by a future trace, or (b) at least 2–3 additional .sav samples (ideally from controlled, deliberately-mutated-and-corrected gameplay) are available for cross-sample differencing.
