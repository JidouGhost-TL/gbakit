Release key: BLYX-r0-135e13f36b883066 · Game code BLYX · ROM SHA-256 135e13f36b8830662130d7b6019714e876e16a384afd9a4533a7bce1fd2305d5

Clean-room derivation: only saves/*.sav, ghidra/decompiled.c (273 functions), ghidra/callgraph.json, ghidra/save_related_functions.c, and standard GBA hardware facts were used. No third-party game-specific source was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (verified):

  • The save medium is a 512-byte EEPROM (EEPROM 4K, 4096 bits) accessed as 64 blocks of 8 bytes through DMA3 to 0x0D000000.
  • The EEPROM layout is: a 16-byte header at blocks 0–1 (file offset 0x00–0x0F), then three 160-byte slots at blocks 2–21, 22–41, 42–61 (file offsets 0x10–0xAF, 0xB0–0x14F, 0x150–0x1EF). Blocks 62–63 (0x1F0–0x1FF) are unused/erased.
  • The header carries the ASCII magic 7500EUSA at offset 0x00–0x07, validated byte-by-byte in code.
  • The integrity algorithm is a 16-bit additive sum: the sum of all eight u16 words of a checksummed region must be 0 (mod 65536), with the last word stored as the negated sum of the preceding words. This verifies exactly on both real .sav files for the header (see §4 for Python output).
  • Both corpus saves are blank/initialized saves: every slot contains only the 8-byte zero prefix written by the blank-save initializer, with the remaining 152 bytes still in the erased 0xFF state. No populated gameplay slot exists in the corpus.

Static-only (code-proven, not byte-proven): the EEPROM read/write/verify driver behavior, retry counts (3 attempts per block), the slot-validity rule (slot sum over 0xA0 bytes must be zero), and the boot-time blank-save creation path.

Open / unknown: the semantics of header bytes 0x08–0x0D, every field inside a populated 160-byte slot, the RAM mirror addresses (Ghidra _DAT_ pointer values are not present in the corpus, so no 0x02xxxxxx/0x03xxxxxx address can be honestly assigned), the full slot-payload writer (no caller flushing a complete 20-block slot was found in the corpus), and any generation/selection counter (none was found; selection appears to be by per-slot validity flag only).

Redundancy and selection:

  • There is no mirrored/backup header copy and no mirrored slot copy in the image. The only redundancy is the per-block write-verify retry (write, read back, compare, up to 3 attempts, FUN_08039c30 calling FUN_08051224 then FUN_08051398) and the analogous 3-attempt read retry in FUN_08039bb4.
  • There is no generation/sequence counter anywhere in the code paths traced. The only candidate counter-like bytes are header offsets 0x0C–0x0D (see §5), and nothing in the corpus compares them to choose between copies, because there are no copies to choose between.
  • Slot selection at load is by validity flag, not recency: FUN_08039988(slot) computes the slot sum and stores a boolean (sum == 0) at manager-struct offset 0x20 + slot*4; FUN_08039474(slot) then consumes that flag (populating a per-slot pointer/state at +0x14 + slot*4 when valid, zeroing 4 bytes there when invalid). Which valid slot the game then presents as "continue" is decided outside the traced functions and remains unknown.
  • Blank-save creation (FUN_0803935c, when header validation fails): writes a fresh header, zeroes the 160-byte RAM slot buffer (FUN_080393fc, memset over 0xA0 bytes), and writes only the first 8-byte block of that zeroed buffer to each slot start (FUN_08039c30(2,1,…), (22,1,…), (42,1,…)). This exactly matches both corpus files: each slot is 8 × 0x00 followed by 152 × 0xFF (never-written EEPROM cells retain the erased state). This is a strong code↔bytes cross-confirmation of the geometry.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two evidence sources were combined, because neither is complete alone:

  1. ghidra/callgraph.json records only a subset of edges (e.g. it lists no callers for FUN_08039bb4/FUN_08039c30 at all).
  2. The decompiled text in ghidra/decompiled.c contains explicit func_0x080… / FUN_080… call sites, which were extracted for every function body to build a text-based caller map. Every chain below was confirmed in the function bodies themselves, not just in the graph.

Ghidra could not recover the tail-call jumptables (UNRECOVERED_JUMPTABLE in nearly every function), so functions whose only references would be through those tables appear caller-less in both sources. Those cases are flagged explicitly rather than guessed.

RAM addresses: the decompilation references all globals through unresolved _DAT_080xxxxx literal-pool symbols whose target values are not in the corpus. Therefore no honest 0x02xxxxxx/0x03xxxxxx mirror address can be given; §5 records struct-relative offsets instead and save-format.json uses ram_addr: null.

3.2 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3)

  • FUN_080510f4(src, dst, count) — DMA3 transfer primitive. It saves and clears an interrupt/DMA control register (*_DAT_08051154), programs a WAITCNT-related register (*_DAT_08051158), stores source (*_DAT_08051164) and destination (*_DAT_08051168), then writes count & 0xFFFF | 0x80000000 (DMA enable) to the DMA control register (*_DAT_0805116c) and busy-waits on its busy bit (0x8000 of the upper halfword). Callers pass 0x0D000000 (the GBA EEPROM window) as one endpoint. This is the only function that touches the EEPROM bus.
  • FUN_08051174(block_addr, ram_ptr) — EEPROM read one 8-byte block. It rejects block_addr >= *(u16*)(cfg+4), expands the address MSB-first into a bit array on the stack, issues two FUN_080510f4 DMA transfers against 0x0D000000 (command length = address-bits + 3; data length 0x44 = 68 halfword bit-cells), then packs the received bits MSB-first into 4 u16 words stored at ram_ptr. Returns 0 on success (nonzero error value otherwise, propagated from the config-error path).
  • FUN_08051238(block_addr, ram_ptr, wait_flag) — EEPROM write one 8-byte block. It expands the 4 u16 data words plus the address into a serial bit array and DMA-writes address-bits + 0x43 bit-cells to 0x0D000000, then polls the EEPROM busy line (uRam0d000000 & 1) with a timer-based timeout (accumulated tick delta threshold 0x88). This MSB-first serial packing is why each u16 appears byte-swapped (big-endian) in the raw .sav image relative to RAM word order — see §4.
  • FUN_08051224(block_addr, ram_ptr) — write wrapper: calls FUN_08051238(addr, ptr, 1) (wait-for-completion enabled) and returns its status.
  • FUN_08051398(block_addr, ram_ptr) — verify: reads the block back via FUN_08051174 into a stack buffer and compares all 4 u16 words against ram_ptr; returns 0 on match, 0x8000 on mismatch.
  • FUN_080510ac(mode) — bus timing setup: mode 4, 0x40, or other selects among three WAITCNT/timing register writes. Called with 4 from FUN_08039cb8 before every EEPROM session.
  • FUN_08039cb8() / FUN_08039d04() — EEPROM session begin/end: save/restore the bus-control registers around a transfer session and invoke FUN_080510ac(4). Both block readers/writers below wrap their loops in this pair.
  • FUN_08051824 — listed as an MMIO seed in ghidra/save_related_functions.c but is actually an unsigned division/modulo helper (shift-subtract algorithm, calls func_0x080517a8 on divide-by-zero). It has no callers, no MMIO access, and no save role; it is a seed false positive and is excluded from the save architecture.

Support helpers used by the save layer: FUN_0800c2bc (memcpy), FUN_0800c234 (memset), FUN_0800c064 (zeroing allocator: aligns size to 16, allocates via FUN_0800bfcc, zeroes the block).

3.3 Block transfer layer

  • FUN_08039bb4(block_addr, block_count, ram_ptr) — read block_count consecutive 8-byte blocks starting at block_addr into ram_ptr (advancing ram_ptr += 8, addr += 1 per block). Each block is retried up to 3 times until FUN_08051174 returns 0. Returns success boolean (last_status == 0). Wrapped in FUN_08039cb8()/FUN_08039d04().
  • FUN_08039c30(block_addr, block_count, ram_ptr) — write + verify the same geometry: per block, FUN_08051224 (write) then FUN_08051398 (read-back compare), up to 3 attempts per block until verify passes. Returns success boolean. Same session wrappers.

3.4 Checksum / serialization routines

  • FUN_08039ac0(u16* ptr, u32 byte_count) — the sole checksum primitive: sums byte_count >> 1 consecutive u16 words, keeping the running total modulo 0x10000 (uVar1 = *param_1 + uVar1 & 0xffff). No seed, no final XOR/complement inside the function; callers negate the result when storing (see §4).
  • Header fix-up appears identically in two writers: zero the u16 at header +0x0E, compute FUN_08039ac0(header, 0x10), store its negation (-sum) at +0x0E. Validation is the dual: the sum over the full 16 bytes must be exactly 0.

How each caller mutates the in-RAM save data before flushing — exhaustively, from the bodies:

  • FUN_08039afc: replaces the entire 16-byte RAM header with the ROM template, then overwrites only +0x0E with the negated checksum. No other header byte is touched.
  • FUN_08039a48: touches only +0x0E (zero, then negated sum). All other header bytes (0x08–0x0D included) must already have been mutated by code outside the corpus before this flush; no such mutator was found.
  • FUN_0803935c (blank path): zeroes the whole 160-byte slot buffer in RAM, of which only the first 8 bytes are ever flushed per slot.
  • No traced function mutates any populated slot payload byte, because no populated-slot writer exists in the corpus. This is stated as an open question rather than filled in.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Bytes 0x00–0x07 = 37 35 30 30 45 55 53 41 = ASCII 7500EUSA, present identically in both .sav files.
  • Verified in code: FUN_08039b4c compares the first 8 read-back bytes byte-by-byte against a constant (pcRam08039bb0); the constant's bytes are not in the corpus, but the comparison length (8) and position (header start) match the observed magic exactly. Verified in sav: yes, both files.

Checksum formula (exact)

  • Primitive (FUN_08039ac0(ptr, byte_count)): sum = (Σ u16[i]) mod 65536 over byte_count/2 words. Plain additive sum16; no seed, no XOR, no CRC, no complement inside the primitive.
  • Storing (writers FUN_08039afc, FUN_08039a48): zero the u16 at stored offset, then stored = (−sum) mod 65536 over the region including the zeroed stored word.
  • Validating (FUN_08039b4c for the header; FUN_08039988 for slots): the region is valid iff the sum over the full region, stored word included, equals 0.
  • Header instance: covered range file 0x00–0x0F (16 bytes, 8 words), stored word at file 0x0E–0x0F.
  • Slot instance: covered range = the slot's full 160 bytes (0xA0, 80 words); validity rule proven in code (FUN_08039988). The stored word's position inside the slot is inferred as the final word (slot offset +0x9E, by analogy with the header's last-word placement); no slot-checksum writer exists in the corpus to prove it, so this is HYPOTHESIS.
  • Endianness / file byte order: in RAM the sum is over native (little-endian) u16 words. The EEPROM wire format packs bits MSB-first (FUN_08051238/FUN_08051174), so in the raw .sav image each u16 appears with its high byte first. Verification against the files must therefore sum big-endian-interpreted word pairs. Both worked examples below use exactly that and match; the equivalent little-endian file interpretation fails (sums 0x01FE/0x02FE ≠ 0), which is itself evidence for the MSB-first packing reading of the driver.

One subtlety in FUN_08039afc: unlike FUN_08039a48, it does not explicitly zero +0x0E before summing — it sums the freshly copied template (including whatever the template holds at +0x0E) and stores the negation. For the resulting header to validate (total sum 0), the ROM template's +0x0E word must be 0. The template bytes are not in the corpus; this is consistent-but-unproven, and the two real blank headers both validate, which supports it.

Reading of the result:

  • Header: stored word 0xFF80 equals the computed negated sum of the other seven words, and the total sum is 0x0000, in both files. Header checksum: CONFIRMED_VERIFIED.
  • The two files differ only at 0x08 (0x00→0xFF) and 0x0C (0x00→0x01). In big-endian word terms those deltas are +0xFF00 and +0x0100, which cancel modulo 65536 — so the unchanged stored checksum is arithmetically consistent with both files having been flushed through the re-checksumming writer FUN_08039a48. (It also means these two samples alone cannot prove the checksum covers bytes 0x08/0x0C; the code sum over 0x10 bytes proves coverage, the bytes prove the formula.)
  • Slots: sum 0xFFB4 ≠ 0 → invalid/empty, exactly as expected for blank-initialized slots (8 zero bytes + erased 0xFF remainder). No valid-slot sample exists to verify the slot checksum end-to-end; slot checksum confidence is therefore CONFIRMED_STATIC for the algorithm/rule and HYPOTHESIS for the stored-word position.
  • This also matches the PACKET cold-reload probe: a single-byte mutation at 0x08 breaks the header sum (no compensating change), the header is rejected, and the game rewrites a blank save — the observed integrity_check_confirmed behavior.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so every test below is phrased as: patch the .sav, repair checksums where noted, cold-boot, and observe the title/file-select UI plus (where an emulator debugger is available) the manager-struct validity flags at +0x20 + slot*4. Predictions follow strictly from the traced code.

  1. Header checksum break (control). Flip one bit at 0x08 in cap-01 with no repair. Prediction: header sum ≠ 0 → FUN_08039b4c returns 0 → FUN_0803935c recreates a blank header and rewrites slot prefixes; game boots as blank/no-save. (Already probe-confirmed per PACKET; retest as the harness control.)
  2. Magic break with checksum repair. Change 0x00 37→38, then recompute: sum the eight big-endian file words with word 7 zeroed, store the negated sum big-endian at 0x0E.
