1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (header subsystem HIGH; slot payload semantics LOW because both samples contain only blank/invalid slots).

What was proven (verified, code + bytes):

  1. Media is EEPROM, 512 bytes total (EEPROM 4K = 4 Kbit), accessed as 64 blocks of 8 bytes through the serial EEPROM port 0x0D000000 driven by DMA (FUN_08041b14 writes the 0x80000000-flagged DMA control word; FUN_08041b94/FUN_08041c58 build MSB-first serial bitstreams). No SRAM/Flash path exists in the corpus: no 0x0E000000, 0x5555, or 0x2AAA token occurs anywhere in ghidra/decompiled.c (grep count 0), and no SDK save tag string was detected in the ROM per PACKET.md.
  2. Layout is one 40-byte global header at EEPROM offset 0x00 plus three independent 152-byte slots at 0x28, 0xC0, 0x158, plus a 16-byte never-addressed tail at 0x1F0. Slot base formula is proven arithmetically from FUN_0802f410: (slot * 0x13 + 5) * 8 = slot * 152 + 40.
  3. Integrity is a signed 16-bit additive checksum (FUN_0802f460): the sum of all signed little-endian i16 words of a record, in the in-RAM representation, must be 0. The header checksum word is stored at RAM offset 0x0E (halfword index 7) as the negated sum of the other words, proven in FUN_0802ef20 and FUN_0802f484 and numerically verified on both .sav files (computed == stored, total == 0).
  4. The .sav file byte order is not the RAM byte order: within each 8-byte EEPROM block the file stores bytes reversed relative to RAM. This transform is proven two independent ways (Section 4): (a) it makes the header i16 sum exactly 0 on both samples, while a direct little-endian file sum gives 254; (b) the blank-slot writer in FUN_0802efe8 sets RAM bytes 0, 1, 2 cumulatively to 0xFF before writing slots 0, 1, 2, and the files show 0xFF at block-relative file offsets 7; 7,6; 7,6,5 respectively.
  5. Magic is the 8 ASCII bytes 300ABG2I at file offset 0x00 (RAM-domain I2GBA003 after the block-reversal transform). It is present in both samples and is checked in code by the 8-byte compare loop in FUN_0802ef8c together with the zero-sum test.

What remains open:

  • Slot payload field semantics: both samples contain only blank slots (all 0x00/0xFF, checksums non-zero = invalid). No populated/gameplay slot sample exists in this corpus, and no non-blank slot writer call site exists in ghidra/decompiled.c (only header writes and the blank-slot writer call FUN_0800cb88). The per-slot serializer/deserializer beyond the checks in FUN_0802f37c/FUN_0802f3e4 and the unresolved callee func_0x0801b788 (called, but its body is not among the 270 decompiled functions and it has no ghidra/callgraph.json node) is therefore unknown.
  • Absolute RAM mirror addresses: every save buffer is reached through an unresolved literal-pool pointer (_DAT_0802ef7c, _DAT_0802efbc, _DAT_0802f4c0, *(global + 0x28), …). The ROM literal values are not in this corpus, so no 0x02xxxxxx/0x03xxxxxx address can be honestly named. Offsets within each buffer are proven; base addresses are UNKNOWN.
  • The exact EEPROM chip-type descriptor (the struct dereferenced as *_DAT_08041bac + 4 = capacity in blocks, + 8 = address-bit count in FUN_08041b94/FUN_08041c58) is static-only; 6 address bits for 64 blocks is inferred from the 512-byte media, not read from the descriptor bytes.
  • Semantics of header RAM bytes 0x08..0x0D beyond "one counter-like byte at RAM 0x0B changed between the two captures" (Section 5).

Cold-reload probe context from PACKET.md is consistent with these findings: mutating file offset 0x8 (the high byte of the header checksum in file order) was confirmed to break integrity, the game reverted to a blank save and rewrote it, and the save was preserved on load. That is exactly the FUN_0802ef8c → FUN_0802efe8 failure path (Section 3).

2.3 Redundancy, counters, selection rule

  • No mirroring/backup copy exists. There is exactly one header and one copy of each slot. ghidra/callgraph.json and a full-text search of ghidra/decompiled.c show EEPROM accesses only at byte offsets 0, 0x28 + slot * 0x98 (read size 0x98, blank-write size 0x90). No second header address, no A/B generation pair, and no sequence/generation counter used for copy selection was found.
  • Selection rule is by explicit index, not by recency. FUN_0802f37c iterates slot = 0, 1, 2 in order, reads each with FUN_0802f410(slot), validates each with FUN_0802f3e4(slot), and records a per-slot validity bool at *(global + 0x50 + slot). There is no newest-wins comparison and no counter comparison anywhere in the save stack.
  • Header counter-like byte: the only byte that changed between the two captures inside the header (apart from its checksum compensation) is RAM byte 0x0B / file byte 0x0C, 0x00 → 0x01 (Section 5). It is not used for slot selection; its gameplay meaning is UNKNOWN. There is no evidence of a generation counter in any slot (slots are byte-identical between captures).
  • Failure behaviour (redundancy substitute): if the header fails magic or checksum at boot, FUN_0802efe8 does not fall back to a backup; it recreates a default header (FUN_0802f484), zeroes the shared 0x98 scratch buffer (FUN_0802f058), and blanks all three slots. This matches the PACKET.md mutation probe ("reverted to blank on mutation", "save rewritten after mutation").

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

  1. Seeds: ghidra/save_related_functions.c names two MMIO seeds, 0x08041b94 (EEPROM read-block) and 0x08041c58 (EEPROM write-block), both hitting 0x0D000000, plus their DMA helper 0x08041b14 and verify wrapper 0x08041db8.
  2. ghidra/callgraph.json was queried programmatically for callers/callees of every seed and of the mid-level wrappers. Note: the callgraph's callees lists are incomplete for the mid-level layer (e.g. 0x0800cb20 lists callees: [] although its body calls func_0x08041b94), because most functions end in unrecovered jumptables. Edges were therefore confirmed by full-text search of ghidra/decompiled.c for FUN_0800cb20(, FUN_0800cb88(, func_0x08041b94, func_0x08041c44, func_0x08041db8, and each manager function name. Every edge reported below was seen in a function body, and callgraph agreement/disagreement is stated per edge.
  3. Address arithmetic was evaluated symbolically: FUN_0800cb20/FUN_0800cb88 take (byte_offset, byte_length, RAM buffer); FUN_0802f410's expression (param_1 * 0x13 + 5) * 8 was expanded for slots 0–2.
  4. RAM-field mutations "before flushing" are reported only where a caller body visibly writes through a pointer immediately before calling FUN_0802ef20 (header flush) or a FUN_0800cb88 write. Where the base pointer is an unresolved _DAT_ literal, that limitation is stated instead of inventing an address.

3.4 Game-level save managers and every caller chain

Chain A — Boot validation and (re)initialisation: FUN_0802efe8

  • FUN_0802efe8 (no callers in ghidra/callgraph.json; it is a boot-path root in this corpus — its caller is outside the 270-function set or reached indirectly):
  1. buf = FUN_080284b8(0x98); *(save_global + 0x28) = buf — allocates the shared 152-byte scratch buffer. RAM mutation: installs the buffer pointer into the save-global struct at +0x28; the numeric base of save_global is an unresolved _DAT_0802f03c literal (UNKNOWN).
  2. FUN_0800cb18() — no-op.
  3. ok = FUN_0802ef8c() — header validation (Chain B).
  4. If ok == 0: FUN_0802f484() (write default header, Chain D), FUN_0802f058() (FUN_0802861c(*(save_global + 0x28), 0, 0x98) — zero the scratch buffer), then for slot = 0..2: buf[slot] = 0xFF; FUN_0800cb88(0x28 + slot * 0x98, 0x90, buf). RAM mutations before each flush: the buffer is all-zero except a cumulative 0xFF marker — byte 0 set before slot 0's write, bytes 0–1 before slot 1's, bytes 0–2 before slot 2's. This is the exact pattern observed in the .sav files after the block-reversal transform (file-relative 0xFF at 7; 7,6; 7,6,5). Only 0x90 bytes are written, leaving slot+0x90..+0x97 erased.
  5. FUN_0803c464(*(u8 *)(save_global + 10)) — dispatches on a manager byte (index < 6 checked inside FUN_0803c464; six languages in the title make a language-index reading plausible but hypothesis, and the byte belongs to the manager struct, not proven to be a header field).
  6. FUN_0802f37c() — load/validate all slots (Chain E).

Chain B — Header validation: FUN_0802ef8c

  • Callers: 0x0802efe8 only (callgraph agrees).
  • FUN_0800cb20(0, 0x28, hdr_buf) reads the 40-byte header into the buffer behind _DAT_0802efbc (unresolved base). It then sums 20 × i16 with an inlined copy of FUN_0802f460; iff the sum is 0 it byte-compares 8 bytes between two unresolved addresses (iRam0802efe0 vs iRam0802efe4 in Ghidra naming, loop iVar3 = 0..7). One side is the header start (magic candidate), the other the expected pattern (ROM template candidate); the literal values are not in the corpus, so the expected bytes are identified from the .sav side as 300ABG2I (file order). Returns the read success flag ANDed with these checks via the code_r0x0802efb6 failure exit. RAM mutation: none (validation only; writes only its local sum).

Chain C — Header flush (read-modify-compare-write): FUN_0802ef20

  • Direct callers found by body search: FUN_0801bcb4 (below). ghidra/callgraph.json lists callers: [] for 0x0802ef20 — this edge is callgraph-missing, body-confirmed (func_0x0802ef20() at decompiled line 4242). This discrepancy is reported deliberately: the callgraph alone would orphan the header writer.
  • Behaviour: reads the current EEPROM header to a stack buffer (FUN_0800cb20(0, 0x28, &iStack_30)); zeroes the RAM header's checksum word (*(u16 *)(hdr + 0xE) = 0), recomputes s = FUN_0802f460(hdr, 0x28), stores *(i16 *)(hdr + 0xE) = -s; compares RAM header vs EEPROM stack copy as 10 × u32; only if they differ writes it back with FUN_0800cb88(0, 0x28, hdr) and returns 1 (0 = unchanged/read-failed). This is a change-suppressing flush: unchanged headers cause no EEPROM wear.
  • Caller FUN_0801bcb4 (callers: 0x08024198, callgraph agrees) mutates RAM fields before flushing: through two unresolved base pointers it copies setting bytes between a source and destination struct — dst[9] = src[5], dst[8] = src[4], dst[0xD] = (dst[0xD] & 0x7F) | (src[6] << 7), dst[0xB] = 1, dst[10] = src[7] — bracketed by FUN_0803ac14()/FUN_0803ac20() (lock/unlock wrappers over FUN_0803e8d8/FUN_0803e8a8), then calls FUN_0802ef20(). Whether dst is the header RAM buffer itself cannot be proven (base literal unresolved; offsets 8–13 also overlap the field range discussed in Section 5, so a header-settings interpretation is CONFIRMED_STATIC for the copy operations, HYPOTHESIS for "these bytes are EEPROM header bytes"). The inverse shuffle FUN_0801bc94 (dst[5] = src[9], dst[4] = src[8], dst[6] = src[0xD] >> 7, dst[7] = src[10], called by FUN_0801bbdc which also zeroes two buffers and sets *(u16 *)(p + 2) = 1, *q = 0x2A) is the matching unpack direction and supports a packed-settings interpretation.
  • Caller FUN_08024198 (no callgraph callers; body-confirmed caller of FUN_0801bcb4 at line 4699): copies a manager byte to +7, if it is < 6 calls FUN_0803c464(that byte) (language-like dispatch, hypothesis), branches on a joypad/state mask ((*_DAT_080241e4 & 0xFFFFFF7F) == 7), sets manager fields +8, +0xC, +0x10, +0x14, calls FUN_080307d0(0x10, 0x28)/FUN_080307e8(0x10, 0) or FUN_080289ac(2, 0, 8), then FUN_0801bcb4() → Chain C flush. Net effect: an options/language-style change is packed and the header is flushed if changed.

Chain D — Default header creation: FUN_0802f484

  • Callers: 0x0802efe8 only (body-confirmed).
  • FUN_08028688(hdr_dst, hdr_template, 0x28) copies a 40-byte ROM template (source _DAT_0802f4c4, unresolved — the template bytes are not in the corpus; the resulting on-EEPROM bytes are known from the samples), sums 20 × i16 (inlined FUN_0802f460 copy), stores the checksum as hdr_dst[7] = -sum (halfword index 7 = byte offset 0x0E, consistent with Chain C; the template's word 7 must be 0 for the result to be valid, as it is in the samples), then FUN_0800cb88(0, 0x28, hdr_dst) writes+verifies it. Note the decompiled call text is FUN_0800cb88(0, 0x28) with the buffer argument folded into the _DAT_ globals by the decompiler; the two-explicit-argument rendering is a Ghidra artefact, the length/offset are unambiguous.

Chain E — Slot loading: FUN_0802f37c → FUN_0802f410 / FUN_0802f3e4

  • FUN_0802f37c (no callgraph callers; called by FUN_0802efe8): for slot = 0..2, with a 12-byte-per-slot descriptor array (iVar4 += 0xC):
  1. FUN_0803ac14() (lock), ok_read = FUN_0802f410(slot), FUN_0803ac20() (unlock). FUN_0802f410(slot) = FUN_0800cb20((slot * 0x13 + 5) * 8, 0x98, *(save_global + 0x28)) — reads the full 152-byte slot into the shared scratch buffer.
  2. If read ok: ok_sum = FUN_0802f3e4(slot) = s = FUN_0802f460(*(save_global + 0x28), 0x98); *(bool *)(save_global + 0x50 + slot) = (s == 0); return s == 0. RAM mutation: writes the per-slot validity bool at manager +0x50 + slot.
  3. If valid and *(char *)(save_global + 0x50 + slot) != 0 (same byte just written — in practice the valid branch): *(save_global + 0x58) = *(save_global + 0x28), *(save_global + 0x5C) = 0, then func_0x0801b788(descriptor_slot) — the slot deserialiser/expander. Its body is absent from ghidra/decompiled.c's 270 functions and from ghidra/callgraph.json; what it expands the 152 bytes into is UNKNOWN.
  4. If valid but that byte is 0: FUN_0802861c(descriptor_slot, 0, 0xC) — zeroes the 12-byte descriptor (empty-slot record).
  • There is no slot-write counterpart to FUN_0802f410 in the corpus: the only FUN_0800cb88 call sites in all of ghidra/decompiled.c are the header flush (FUN_0802ef20), the default header (FUN_0802f484), and the blank-slot loop (FUN_0802efe8). A gameplay "save game to slot N" writer either lives outside the 270 functions, is reached through an unrecovered jumptable, or reuses the header flush path with computed arguments not present in this decompilation. This is the report's largest open item (Section 6, fuzzing target F6, is designed to expose it at runtime).

4.2 Checksum algorithm (exact)

  • Core routine: FUN_0802f460 (ghidra/decompiled.c lines 6516–6536):
void FUN_0802f460(short *param_1, uint param_2) {
  short sVar1 = 0;
  param_2 = param_2 >> 1;
  if (param_2 != 0) {
    do { sVar1 = sVar1 + *param_1; param_1++; param_2--; } while (0 < (int)param_2);
  }
  return sVar1;   // wrapping signed 16-bit sum of little-endian i16 words
}
  • Formula: S(record) = Σ_{i=0}^{n/2-1} i16_le(RAM_record[2i..2i+1]) (mod 2^16, signed wrap). A record is valid iff S(record) == 0.
  • Stored field (header): RAM offset 0x0E (halfword index 7, 2 bytes, little-endian in RAM). Writers zero it, sum the record, and store the negation (FUN_0802ef20: *(u16 *)(hdr+0xE) = 0; s = FUN_0802f460(hdr, 0x28); *(i16 *)(hdr+0xE) = -s; — lines 6308–6310; FUN_0802f484: hdr[7] = -sVar2 after the same inlined sum — line 6560).
  • Covered ranges: header = RAM record bytes 0x00..0x27 (40 B, 20 words, checksum word included in the validation sum); slot = RAM record bytes 0x00..0x97 (152 B, 76 words) in FUN_0802f3e4. The slot's own checksum-word position is not identified by any writer in the corpus (hypothesis: also index 7 by symmetry with the header; see §6 F5).
  • Endianness in the file: because of the §4.3 transform, the header checksum appears in the file at offset 0x08 as two bytes that read as the RAM value in big-endian file order (20 F6 / 1F F6). In file terms: stored_file_u16be(0x08) == -(sum of the other 19 RAM words).
  • Seed/complement variants ruled out: no XOR-fold, CRC, or complement pass exists in the save stack; the only arithmetic is the additive sum and its negation. A direct little-endian sum over raw file bytes gives 254 for both headers (not 0), and a raw byte-sum gives 766 — both rejected by the samples; the RAM-domain sum gives exactly 0 (below).

4.3 The file↔RAM byte-order transform (proven)

Within each 8-byte EEPROM block, file byte b (0–7) is RAM byte 7-b of that block. Evidence:

  1. Checksum closure: applying the reversal and then the §4.2 sum makes both headers sum to exactly 0 and makes stored == -sum(others). Without it (raw LE file sum) both headers sum to 254 — invalid under FUN_0802ef8c, contradicting the PACKET.md probe result that these saves load and are preserved.
  2. Blank-slot markers: FUN_0802efe8 sets scratch RAM byte k to 0xFF immediately before writing slot k (k = 0,1,2, cumulative, buffer otherwise zero, write length 0x90). Observed file 0xFF positions relative to each slot are {7}, {6,7}, {5,6,7} — i.e. RAM bytes {0}, {0,1}, {0,1,2} under reversal, in order. Three independent slots match with zero free parameters.
  3. Driver consistency: FUN_08041b94 stores the four reconstructed u16s in reverse word order (param_2+6 first) and shifts bits MSB-first, and FUN_08041c58 serialises in the matching order — a reversed-within-block RAM layout is exactly what such a serialiser produces against an emulator dump that packs the serial stream linearly (static consistency; the empirical proofs are 1–2).

Consequence for tooling: any editor must transform RAM_block[j] = file_block[7-j] (and inversely) before interpreting fields, checksums, or RAM offsets. All RAM offsets quoted in this report are record-relative and identical numerically to EEPROM record offsets; only intra-block byte order differs.

4.4 Python verification against the real .sav files (executed)

Script (run in this workspace as /tmp/verify_save.py; logic reproduced here in full):

import struct, hashlib
files = ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]
def to_ram(d):
    out = bytearray()
    for i in range(0, len(d), 8):
        out += d[i:i+8][::-1]          # reverse bytes within each 8-byte block
    return bytes(out)
def s16sum(buf):
    s = 0
    for (v,) in struct.iter_unpack("<h", buf):
        s = ((s + v) & 0xffff)
        if s >= 0x8000: s -= 0x10000
    return s
# per file: header RAM words, sum, stored word 7 vs -sum(others); per slot: RAM sum & file 0xFF offsets

6. Save Fuzzing & Counterfactual Verification Plan

General repair procedure (needed by every mutation below that touches a checksummed record). To repair the header after editing file bytes: transform the 40-byte header to RAM order (RAM[j] = file_block[7-(j mod 8)] + block_base per 8-byte block), set RAM word 7 (bytes 0x0E..0x0F) to 0, compute S = Σ i16_le over the 20 words with signed 16-bit wrap, store -S little-endian at RAM 0x0E, transform back (same reversal), and confirm the whole-record RAM sum is 0 with the §4.4 script before booting. To attempt slot repair (hypothesis H-slot, §5): the same procedure over 152 bytes with the checksum word assumed at SLT+0x0E; if the game still rejects the slot, repeat with the checksum word at each other word index in turn (76 candidates) — acceptance at exactly one index proves its position. No paired .ss save states exist in this workspace (states/ is empty, PACKET.md §2), so every prediction below is phrased for cold-boot reload of the mutated .sav (the PACKET.md probe methodology: boot screenshot vs loaded screenshot, plus whether the file is rewritten). Emulator-side, also watch the shared scratch buffer and validity bools if a debugger is available; without .ss files, file-rewrite and title/menu behaviour are the observables.
