1. Executive Summary & Overall Confidence

Overall confidence: HIGH.

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is an 8 KiB EEPROM (EEPROM 64K), accessed as 8-byte blocks through a serial bitstream at 0x0D000000 via DMA3 (FUN_0804a7d0 at 0x0804a7d0, seeding 0x040000D4-family DMA registers per the packet's hardware map).
  • Only the first 512 bytes (0x000–0x1FF) of the 8192-byte .sav image are ever used: one 64-byte header chunk at 0x00, followed by seven 64-byte data chunks at 0x40, 0x80, 0xC0, 0x100, 0x140, 0x180, 0x1C0. Each chunk carries a 60-byte (0x3C) RAM struct plus 4 zero pad bytes on EEPROM.
  • Within every 8-byte EEPROM block, the raw .sav byte order is the reverse of the in-RAM byte order. This is a direct consequence of the MSB-first bit-building loops in the writer FUN_0804a900 (0x0804a900, stack pointer decrementing) and reader FUN_0804a850 (0x0804a850, destination pointer starting at param_2 + 6 and decrementing), and it is empirically confirmed: reversing each 8-byte block of cap-01-future-1.sav turns byte 0 into the ASCII magic 'N' (0x4E) checked by the loader, turns the garbled 00 42 4D 53 runs into the ASCII name "SMB\0", and turns e8 03 00 00 into the little-endian score 1000.
  • Integrity is a CRC-16/CCITT-FALSE (polynomial 0x1021, init 0xFFFF, MSB-first, no reflection, no final XOR) implemented by FUN_08041c38 (0x08041c38), used twice: (a) over header bytes 0x00–0x37, stored little-endian at header offset 0x38; (b) per data chunk over its 60 data bytes, with the seven CRCs summed into a 32-bit aggregate stored at header offset 0x34. Both values verify exactly on cap-01-future-1.sav (Section 4).
  • The factory-default initializer FUN_08008da4 (0x08008da4) explains essentially every non-checksum byte observed in the populated save, including the three set bits (1, 11, 31) of the progress/unlock bitfield at header offset 0x08, set via FUN_0800988c (0x0800988c).
  • The populated save is a defaults save: every one of the 35 high-score entries (7 chunks × 5 entries × 12 bytes) still holds the template name "SMB\0" and the template score (1000 in chunks 0–3, 50 in chunks 4–6). No gameplay-earned score is present in either sample.

Still open (HYPOTHESIS / UNKNOWN, Section 5–6):

  • The concrete RAM addresses of the header struct and the seven data structs. The decompilation references them only through unresolved literal pools (_DAT_08008f44, the pointer tables _DAT_08008f48 / _DAT_08009038); the literal values are not present in the workspace, so ram_addr is reported as null rather than guessed.
  • The exact gameplay callers that insert new high scores into the 12-byte entries, and the caller of the save routine FUN_08008f5c. Both are invisible in callgraph.json because the trace-guided decompilation leaves most indirect jumps as UNRECOVERED_JUMPTABLE; FUN_08008f5c, FUN_08008da4, FUN_08041cf4, FUN_08041d90, and FUN_08041c38 all show zero recorded callers even though their callees and internal behavior are fully visible. This is a limitation of the extraction, not evidence the code is dead — the populated .sav could only have been produced by this writer chain.
  • The semantics of header bytes 0x15–0x33 beyond the fields explicitly written by FUN_08008da4, and of the per-entry third word (always 0 in the sample).

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (EEPROM serial via DMA3)

  • FUN_0804a7d0 (0x0804a7d0) — DMA3 transfer primitive. Saves/restores an interrupt-enable word, programs DMA source (param_1), destination (param_2), and control param_3 & 0xFFFF | 0x80000000 (enable bit), then spins while the busy bit (0x8000 of the control high halfword) is set. Called by both the read and write bitstream routines with destination/source 0x0D000000 (the EEPROM serial window). Confidence: CONFIRMED_STATIC (MMIO seed; register addresses themselves are behind literal pools, identified from the 0x0D000000 immediates and the packet's 0x040000D4 DMA3 map).
  • FUN_0804a850 (0x0804a850) — EEPROM read one 8-byte block. If block_addr < *(u16*)(chip_config + 4): builds the read command bitstream (two 1 bits, then addr_bits address bits MSB-first, where addr_bits = *(u8*)(chip_config + 8)), DMAs addr_bits + 3 halfwords to 0x0D000000, DMAs 0x44 halfwords back from 0x0D000000, then extracts 64 data bits into 4 u16s, writing them backwards from param_2 + 6 — the origin of the in-block byte reversal. Returns 0 on success.
  • FUN_0804a900 (0x0804a900) — EEPROM write one 8-byte block. Expands the 4 input u16s into 64 bits MSB-first (again building the stack bitstream backwards), prepends two 1 bits (write opcode) and the address bits, appends a 0 bit, DMAs addr_bits + 0x43 halfwords to 0x0D000000, calls FUN_0804a704 (bus/interrupt setup helper at 0x0804a704), polls the EEPROM busy line (0x0D000000 & 1) and a status flag, then calls FUN_0804a78c (0x0804a78c, teardown helper).
  • FUN_0804a9dc (0x0804a9dc) — verify: re-reads the block via FUN_0804a850 and compares all 4 u16s; returns 0x8000 on any mismatch.
  • FUN_0804aa34 (0x0804aa34) — write-with-retry: up to 3 attempts of FUN_0804a900 + FUN_0804a9dc until verify passes; returns the final status.
  • FUN_0804a704 / FUN_0804a78c — small setup/teardown helpers used only by the write path (they manipulate a control register by 8 << chip_index); exact register identity is behind literal pools, so their role is stated functionally. Confidence: CONFIRMED_STATIC for the call relationship, HYPOTHESIS for the exact registers.
  • Not save-related despite appearing in the seed file: FUN_0804ab48 (0x0804ab48) and FUN_0804ac90 (0x0804ac90) are signed/unsigned division-remainder helpers (also FUN_0804aab0, FUN_0804ac18); they were swept in as MMIO-seed neighbours and have no EEPROM role.

3.2 Mid-level wrappers

  • FUN_08041cf4 (0x08041cf4) — EEPROM read bytes (byte_offset, dst, length). Only acts when the current save device type == 3 (EEPROM, set by FUN_08041e44). Loops in 8-byte blocks: block address (offset & 0x7FFFF) >> 3, calls FUN_0804a850; handles a trailing partial block by reading into a scratch u16[4] and copying out byte-wise. Returns 1 on success.
  • FUN_08041d90 (0x08041d90) — EEPROM write bytes (byte_offset, src, length). Same gating and block loop, calling FUN_0804aa34 per block; on a status with bit 0x8000 set it flags error state 7 and returns 0.
  • FUN_08041e44 (0x08041e44) — device init: called at boot as FUN_08041e44(3, 4) from FUN_08035420; for type 3 it selects the EEPROM chip configuration (FUN_0804a664 at 0x0804a664, FUN_0804a6cc at 0x0804a6cc) and records type << 7-style geometry used by the wrappers.
  • FUN_08041c38 (0x08041c38) — CRC-16 (Section 4).
  • FUN_08041cac (0x08041cac) — zeroes five driver state words before device init at boot; support routine, no save-data role.

3.3 Serialization / deserialization & integrity

  • FUN_08008ec4 (0x08008ec4) — load / deserialize. Reads header (offset 0, len 0x3C) into the header RAM struct, computes its CRC-16 over 0x38 bytes; then for i = 0..6 reads chunk 0x40 + 0x40·i (len 0x40) into a stack buffer, memcpy's 0x3C bytes into RAM struct table[i], and accumulates CRC16(struct, 0x3C). Returns 1 iff read-ok ∧ header[0] == 'N' ∧ header CRC matches word at header+0x38 ∧ accumulated sum equals word at header+0x34; else 0.
  • FUN_08008f5c (0x08008f5c) — save / serialize. Waits for VBlank (FUN_0804a640, SWI 5 wrapper). Temporarily clears header+0x04 (restored at the end, so the on-disk value is whatever it held — see field map), zeroes header+0x34, then for each of the 7 structs: adds CRC16(struct, 0x3C) into header+0x34, copies the struct into a 64-byte stack buffer with bytes 60–63 zeroed, and writes it at 0x40 + 0x40·i (len 0x40). Finally sets header+0x32 = 0, stores CRC16(header, 0x38) at header+0x38, writes the header (offset 0, len 0x3C, i.e. 8 EEPROM blocks including pad), restores header+0x04, and returns the AND of all write statuses.

3.4 Caller chains — how each caller was mapped

Mapping method: (1) direct textual func_0x… / FUN_… call sites in ghidra/decompiled.c; (2) cross-checked against ghidra/callgraph.json callers/callees; (3) where the two disagree, the decompiled body wins, because the callgraph demonstrably omits calls made through the func_0x… spelling and through unrecovered jumptables (e.g. it records zero callers for FUN_08041c38 although FUN_08008ec4 and FUN_08008f5c both call it in the C text).

Chain A — boot / load (fully traced). FUN_08035420 (0x08035420, main boot/task function; no recorded callers, it is an entry) → func_0x08041cac() (clear driver state) → FUN_08041e44(3, 4) (select EEPROM) → FUN_08008ec4() (load) → FUN_08041cf4 → FUN_0804a850 → FUN_0804a7d0 → 0x0D000000. How FUN_08035420 mutates/consumes the save structs: it stores the load result inverted into game-state byte +0x6D (*(iVar10 + 0x6D) = (cVar7 == 0) — i.e. "save invalid" flag). If load failed, it writes header+0x33 = 0 (via *_DAT_080355e0 + 0x33) and game-state +0x85 = 0; if load succeeded, it copies the persisted byte header+0x33 into game-state +0x85 (*puVar12 = *(undefined1*)(*piRam08035714 + 0x33)). So header byte 0x33 is a persisted setting that is force-cleared whenever the save is rejected. RAM mirror: game-state struct pointer and header pointer are literal-pool values not present in the workspace, hence null in the JSON.

Chain B — save (traced internally; entry caller not recoverable). FUN_08008f5c → FUN_08041d90 → FUN_0804aa34 → {FUN_0804a900 → FUN_0804a7d0, FUN_0804a704, FUN_0804a78c; FUN_0804a9dc → FUN_0804a850}. FUN_08008f5c has no caller in callgraph.json and no textual call site in decompiled.c; its caller must dispatch through an unrecovered jumptable/function pointer. Mutations it performs on the in-RAM header before flushing: header+0x34 := Σ CRC16(chunk_i), header+0x32 := 0, header+0x38 := CRC16(header, 0x38), and header+0x04 is cleared only for the duration of the write and restored afterwards.

Chain C — factory defaults (traced internally; entry caller not recoverable). FUN_08008da4 → FUN_0800988c(1), FUN_0800988c(0x0B), FUN_0800988c(0x1F) (set unlock bits 1, 11, 31) and → FUN_08009900 (0x08009900, a ROM table lookup table[block]) per block to pick one of four ROM entry templates, copying 5 × 12-byte entries into each of the 7 RAM structs. Like Chain B, no caller is recorded; the trigger is inferred to be "load rejected / first boot", because FUN_08035420 reacts to load failure in exactly the state this function initializes, and because a save produced from these defaults matches cap-01-future-1.sav byte-for-byte after CRC computation. Mutations: header bytes 0x00='N', +0x01=3, +0x02=3, +0x03=1, +0x04=0, +0x05=0, +0x06=1, +0x07=3, +0x08..+0x20 := 0 (then bits set), +0x15=0, +0x16=0, +0x24 (u32) = 0, +0x28..+0x2F := 0, +0x30=5, +0x32=1 (later cleared to 0 by the saver), +0x33=0; each chunk filled with template entries (name, default score, 0).

Chain D — in-game progress bit writer. FUN_0800988c(bit) sets bit bit (bit < 100) in the header bitfield at header+0x08 + (bit >> 3) |= 1 << (bit & 7). Its only traced callers are the three calls in FUN_08008da4; gameplay callers that set further bits are not recoverable from the callgraph (same jumptable limitation) and are marked HYPOTHESIS in the field map.

Untraced writers (honest gap). No other function in the decompilation was found writing the header struct (via +0x32/+0x33/+0x34 patterns), the chunk pointer tables, the "SMB" template, or the constants 1000/50 as score initializers outside Chain C. Score-insertion during gameplay therefore remains UNKNOWN at the function level; Section 6 gives a fuzzing plan to identify it dynamically.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • Single-byte magic 'N' (0x4E) at RAM/file offset 0x00 of the header chunk. Written by FUN_08008da4 (*(undefined1*)*piVar7 = 0x4E), checked by FUN_08008ec4 (*pcVar6 != 'N'). In the raw file it appears at file offset 0x07 because of the in-block reversal (03 01 00 00 01 03 03 4E …). Verified in code: yes. Verified in .sav: yes (cap-01), and its absence (0xFF) correctly invalidates cap-00.
  • Secondary quasi-signature: the ASCII bytes "SMB\0" (53 4D 42 00) at the start of every one of the 35 score entries (entry offset +0). In raw file order each appears as 00 42 4D 53 at the tail of an 8-byte block. This is the default entry name copied from ROM templates by FUN_08008da4; it is not checked by the loader, so it is a content signature, not a validity magic. (Clean-room note: SMB plausibly abbreviates the game title, but that expansion is not provable from the workspace and is not relied on.)
  • No other ASCII strings, and no SDK save tag, exist in either sample (PACKET.md §1: ascii_magic_strings: [] for the raw byte view, explained by the reversal).

4.2 Checksum algorithm (exact)

Decompiled proof, FUN_08041c38 (0x08041c38):

uVar1 = _DAT_08041c6c;                       // initial value (see below)
for (; param_2 != 0; param_2 = param_2 + -1) {
  uVar1 = (uVar1 << 8 ^ *(ushort *)((uVar1 >> 8 ^ (uint)*param_1) * 2 + _DAT_08041c70)) & 0xffff;
  param_1 = param_1 + 1;
}

This is the table-driven MSB-first CRC-16 form crc = (crc << 8) ^ table[((crc >> 8) ^ byte)]. The table at _DAT_08041c70 and the init literal at _DAT_08041c6c are ROM values not printed in the workspace, so the polynomial/init were identified by exhaustive trial of the standard CRC-16 catalogue against the real save (Section 4.3): the unique catalogue match on both the header CRC and the 7-block aggregate is CRC-16/CCITT-FALSE: poly 0x1021, init 0xFFFF, refin=false, refout=false, xorout 0x0000. (The runner-up MSB-first forms — XMODEM init 0x0000, AUG-CCITT init 0x1D0F, GENIBUS, and all reflected 0x8005/0x8408 forms — were computed and fail; values in the verification script output were checked for XMODEM 474a, KERMIT 510c, ARC ed58, MODBUS e192, etc., none matching.)

Two stored values, both computed by the saver FUN_08008f5c and checked by the loader FUN_08008ec4:

NameFormulaCovered range (RAM order)Stored atStored size/type
header_crcCRC-16/CCITT-FALSEheader bytes 0x00–0x37 (56 bytes)header 0x38u16 LE (written as u32, high half zero)

Note the ordering inside FUN_08008f5c: the aggregate at 0x34 is summed before the header CRC is computed, and header+0x32 is zeroed before the header CRC — so the header CRC covers the final stored aggregate and the zeroed 0x32. There is no per-chunk stored CRC and no checksum over the 4 pad bytes (they are zero and outside the 0x3C coverage).

6. Save Fuzzing & Counterfactual Verification Plan

General repair procedure after any mutation (offsets below are RAM-order; translate to raw file offsets by reversing each 8-byte block: within a block, RAM byte k lives at raw offset block_start + (7 - k)):

  1. Mutate the target bytes in the reversed (RAM-order) view, or equivalently mutate raw bytes with the reversal applied.
  2. Recompute CRC16/CCITT-FALSE (poly 0x1021, init 0xFFFF) of the mutated chunk's 60 bytes; update the aggregate: header.u32@0x34 = old_aggregate - old_chunk_crc + new_chunk_crc (for header mutations, the aggregate is unchanged).
  3. Zero header@0x32 (already 0 in any valid save), recompute CRC-16 over header 0x00–0x37, store it LE at header@0x38.
  4. Re-apply the per-8-byte-block reversal to produce the raw .sav, keep total size 8192, and leave bytes 0x200+ as 0x00.
  5. Reload from the paired save state / cold-boot and observe the predictions. (No .ss files ship in this workspace — states/ is empty — so each test needs a fresh boot with the mutated .sav in place; the PACKET.md cold-reload probe shows the harness retains .sav bytes across load.)
