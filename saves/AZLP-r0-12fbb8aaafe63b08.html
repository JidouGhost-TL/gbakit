All findings below are derived exclusively from ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and the real save binary saves/cap-00-future-0.sav in this workspace, cross-checked with standard public GBA hardware specs (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The cartridge uses a 64Kbit (8192-byte) EEPROM, accessed exclusively through a DMA3 serial-bitstream driver chain rooted at 0x0813700c/0x0813708c/0x0813713c/0x08137218/0x08137270.
  • The EEPROM is organized as two byte-for-byte identical 4096-byte halves (0x0000-0x0FFF primary, 0x1000-0x1FFF backup/mirror). This is proven directly from the .sav bytes (full-half comparison) and matches the redundant dual-bank write/verify logic in FUN_08068784/FUN_08068610.
  • A 4-byte sentinel, byte pattern 54 49 4E 49 (ASCII "TINI"), appears at six fixed offsets in each half (0x40, 0x50, 0x60, 0x70, 0x90, 0xB0). This is simply the little-endian encoding of the 32-bit constant 0x494E4954, which read big-endian spells "INIT" — i.e. a classic "slot initialized" magic word, byte-swapped by the GBA's little-endian stores.
  • There is a verified boot-time / repair call chain: FUN_0801180c(slot) (slots 0,1,2) → FUN_080685cc/FUN_080685f8 (bank-1 / bank-2 status check, via FUN_08068884) → on failure, FUN_08068730(slot) (rewrite both banks from the RAM mirror) or FUN_0801164c(slot) (zero + reformat the RAM-side slot struct). The same repair primitive FUN_08068730 is also invoked from FUN_080686a8, which validates the global/options slot (index 3) and cascades repair to slots 0,1,2 if slot 3 is corrupt in both banks.
  • A single capture (saves/cap-00-future-0.sav) is an "initialized but never played" save: only the identification/sentinel bytes above have been written; no gameplay-progress payload exists in this sample.

What remains open / not provable from this single sample:

  • The per-field checksum/integrity algorithm referenced by FUN_08068af0 (two's-complement-style u16+u16==0x10000 check, with an alternate bitmask-compare branch) cannot be exercised: it operates on slot payload regions that are still all 0xFF in this capture. A full byte-level scan for a matching u16 pair found zero candidates (verification run in §4).
  • The exact ROM-resident constants _DAT_08068b04, _DAT_08068b14, uRam08068b08, _DAT_08068b40 that FUN_08068af0 compares against are not present in the decompiled excerpt provided, so the precise comparison values are unresolved (UNKNOWN).
  • The human-readable meaning of the large scrambled ASCII block at offset 0x00 ("T KNIL AAP EHT OS 4 & TS46,SDROWTF4SS%") is only partially decodable: individual substrings reverse cleanly to recognizable English fragments (KNIL→LINK, EHT→THE, SDROW→WORDS), but no single whole-string or per-word reversal rule reproduces a complete, self-consistent phrase from the bytes we have. This is reported as a HYPOTHESIS, not a confirmed decode.
  • No gameplay-slot (player save file) payload has ever been written in the available sample, so fields beyond the six sentinel tags and the one populated 16-byte table block at 0xE0 are UNKNOWN.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (EEPROM serial DMA3 bitstream)

All physical EEPROM access funnels through one primitive:

  • FUN_0813700c(src, dst, count) — raw DMA3 transfer. Disables/restores the global interrupt-enable flag (_DAT_0813706c), programs DMA3 source (_DAT_0813707c=src), destination (_DAT_08137080=dst), and count|enable (_DAT_08137084 = count & 0xffff | 0x80000000), then busy-polls the DMA control register (*(ushort*)(*_DAT_08137078+6), bit 0x8000) until the transfer completes. This is the textbook GBA DMA3-driven EEPROM bit-serial transfer pattern (EEPROM is addressed one bit per DMA "unit" at 0x0D000000).

Built on top of it:

  • FUN_0813708c(param_1, param_2) [MMIO-SEED] — EEPROM READ of one 8-byte block. Builds a 2-bit "READ" command + address bitstream in a stack buffer sized by an address-bit-width field read from a descriptor (*(byte*)(*_DAT_08137138+8), 6 or 14 bits depending on EEPROM size — here 14, since this is the 64Kbit/1024-block variant), sends it via FUN_0813700c(stack, 0x0D000000, bits+3), then reads back 0x44 (68) bits via FUN_0813700c(0x0D000000, stack, 0x44) (4 dummy bits + 64 data bits), and unpacks them MSB-first into 4 × 16-bit words at param_2+6, param_2+4, param_2+2, param_2.
  • FUN_0813713c(param_1, param_2) [MMIO-SEED] — EEPROM WRITE of one 8-byte block. Builds a 2-bit "WRITE" command + address bits + the 64 data bits taken from param_2 (4 words), sends the whole stream via FUN_0813700c(stack, 0x0D000000, bits+0x43), calls FUN_08136f40 (interrupt-mode setup / a jump-table-driven helper that overlaps a global dispatch structure — exact semantics HYPOTHESIS, but it always precedes the busy-wait), then polls uRam0d000000 & 1 (the EEPROM busy bit, standard behavior: write cycle takes ~10 ms) until clear or until _DAT_08137210 signals timeout, and finally calls FUN_08136fc8 (cleanup/re-arm, mirror image of FUN_08136f40).
  • FUN_08137218(param_1, param_2) — READ + COMPARE: calls FUN_0813708c into a 4-word stack buffer and compares all 4 words against param_2 (the data that was supposed to have been written); returns 0x8000 on any mismatch, else 0. This is the write-verify step.
  • FUN_08137270(param_1, param_2) — top-level "write with retry": loops up to 3 times calling FUN_0813713c (write) then FUN_08137218 (verify); breaks on first clean verify, otherwise retries. This is the only EEPROM write entry point used by everything above it; it has no callers in the static graph but is reached indirectly through func_0x08137270 from FUN_08068c3c (see below) — resolved via text search of ghidra/decompiled.c, not the callgraph JSON alone.

3.2 Block-level read/write/verify wrappers (8-byte-block loops over arbitrary length)

  • FUN_08068bf8(param_1, param_2, param_3) — loops FUN_0813708c (read-only, no verify) over ceil(param_3/8) 8-byte blocks starting at EEPROM block index param_1>>3[wait: param_1 & 0xffff) >> 3], copying into RAM at param_2. Fails fast (returns success=1/0) and is itself called with param_2/param_2+8 and param_2+0x1000/param_2+0x1000+8 variants by FUN_08068a30 and FUN_08068884 (see §3.3) — this is where the "try primary, then fallback-within-half" redundancy is implemented on the read side.
  • FUN_08068c3c(param_1, param_2, param_3) — loops FUN_08137270 (write+verify+retry) over the same 8-byte blocks; on a failing block it performs one extra corrective write using a fallback buffer (uRam08068c70) before reporting overall failure. This is the write counterpart.
  • FUN_08068c8c(param_1, param_2, param_3) — loops FUN_08137218 (read+compare only, no write) — a pure verify pass used to decide whether a rewrite is needed without mutating EEPROM.

3.3 Caller chain and in-RAM mutation before flush

  • FUN_08068b4c(param_1, param_2, param_3) — the per-"half" write dispatcher. param_1 bit 0 → write half A (param_2/param_2+8 fallback) via FUN_08068c3c; bit 1 → write half B (param_2+0x1000/param_2+0x1000+8) via FUN_08068c3c. Called by:
  • FUN_08068730(slot) — repair primitive: fetches the slot's table row via FUN_08068bdc(slot|4) and FUN_08068bdc(slot), then calls FUN_08068b4c(3, ..., src=_DAT_08068780) twice (once per candidate address field in the row) — i.e. it flushes whatever is currently sitting in the fixed RAM source address _DAT_08068780 straight to EEPROM, for both halves. This is how a corrupted slot gets "healed": the RAM struct for that slot (populated earlier by gameplay code or zeroed by FUN_0801164c) is blindly re-flushed.
  • FUN_08068784(param_1, param_2) — the general "commit RAM buffer param_2 to slot param_1" writer: computes a running checksum over the RAM source via FUN_08068578 (summed into sStack_1c, negated into sStack_1a — see §4), then writes half A (verify via FUN_08068c3c, with the puVar5[2] != uRam08068880 sentinel-compare guarding a fallback), then half B similarly. Invoked as func_0x08068784(7, param_1) by FUN_08068610(param_1), the public "SAVE" entry point.
  • FUN_08068610(0x3000000) is called directly from FUN_08011294 (a small IWRAM byte-setting mutator at 0x08011294, clamping cRam03000005 to the range [2,6]→2) whenever that setting changes — i.e. a global option byte living in IWRAM at 0x03000000 is persisted to EEPROM slot encoded by the low 3 bits of the address argument (0x3000000 & 7 == 0) on every change. This is a concrete, traced example of "RAM mutation → flush" for the global/options slot.
  • FUN_08068884(param_1, param_2) mirrors FUN_08068784 but for loading: reads half A via FUN_08068bf8, runs an integrity check via func_0x080689e0 (not in the provided seed set — only its call site is visible), and on success calls func_0x08136e44(&uStack_24, param_2, *puVar4>>2 | 0x5000000) to copy the validated data into the live RAM struct (address 0x05000000-tagged argument is almost certainly a mis-decompiled/overlapping symbol for an EWRAM/struct pointer, not literal PRAM — flagged HYPOTHESIS). Called as func_0x08068884(7, param_1) from FUN_08068624(param_1), the public "LOAD" entry point.
  • FUN_080685cc(slot) / FUN_080685f8(slot) — thin wrappers that call func_0x08068884(slot) / func_0x08068884(slot|4) to get a tri-state status (0=blank/never written, 1=valid, -1/2=corrupt) for half A and half B respectively, without necessarily copying data into the live struct (argument list differs from the full-load call). Both are called from FUN_0801180c(slot), the boot-time per-slot validator for slot ∈ {0,1,2}:
  • status -1 (both halves bad, or contradictory) → FUN_08068730(slot) (blind re-flush of current RAM defaults to both EEPROM halves).
  • status 0 (slot never initialized) → FUN_0801164c(slot) (zero a 0x40-byte and a 0x10-byte RAM struct for the slot via FUN_0800bb2c (memset-style), set two flag bytes at struct offset 0x24/0x25 to 1 — these two 01 01 bytes match the first two bytes of the populated 0xE0 table block in the real .sav).
  • status 1 (valid) → fall through, no repair/reformat needed.
  • FUN_080686a8(void) — the global-slot consistency check, called independently of the per-save-file boot loop: fetches table row 3, verifies both halves via FUN_08068c8c, and if both halves fail, cascades FUN_08068730(2), FUN_08068730(1), FUN_08068730(0) (repair all three player slots) before repairing slot 3 itself via two FUN_08068c3c calls. This indicates slot 3 is treated as authoritative/foundational for slots 0-2 (plausibly a shared checksum seed, language/region flag, or file-table index that the player slots depend on).

All of the above is CONFIRMED_STATIC (read directly from ghidra/decompiled.c control flow and cross-checked against ghidra/callgraph.json caller/callee lists). The semantic labels ("player slot", "options slot", "boot validator") are inferences from structure and naming context, not from any external documentation, and are marked HYPOTHESIS in the field map where the label itself (not just the existence of the field) is asserted.

4.2 Checksum/integrity algorithm

Two candidate integrity mechanisms were located in code, neither of which could be exercised against real non-sentinel data because the only available sample has not had any gameplay data written to it.

(a) FUN_08068af0 — table-row validity/complement check:

undefined4 FUN_08068af0(ushort *param_1)
{
  uVar2 = *(uint *)(param_1 + 2);              // 32-bit field at byte offset +4
  if (uVar2 == _DAT_08068b04) {                // compares against an unresolved ROM constant
      if ((uint)*param_1 + (uint)param_1[1] == 0x10000)   // u16[0] + u16[1] == 0x10000  (two's-complement pair)
          return 2;
      return 0;
  } else {
      uVar1 = (uVar2 <= _DAT_08068b04) ? uRam08068b08 : _DAT_08068b14;
      if (uVar2 == uVar1 && (param_1[1] & *param_1) == _DAT_08068b40)
          return 1;
      return 0;
  }
}

This is a two-branch validator: branch 1 checks that the first two 16-bit words of an 8-byte EEPROM block sum to exactly 0x10000 (i.e. word[1] is the 16-bit two's-complement negation of word[0] — a classic checksum = -value integrity pair), gated by a 32-bit tag field at +4 matching an unresolved constant _DAT_08068b04. Branch 2 performs a bitwise AND equality check against another unresolved constant _DAT_08068b40, gated by the tag field matching one of two other unresolved globals. The three comparison constants (_DAT_08068b04, _DAT_08068b14/uRam08068b08, _DAT_08068b40) are not defined anywhere in the provided ghidra/decompiled.c/ghidra/callgraph.json excerpt — they live in a ROM data region outside the supplied trace, so their numeric values are UNKNOWN.

(b) FUN_08068578-based running sum (seen inlined in FUN_08068784):

sStack_1c = FUN_08068578(&uStack_18, 4);      // checksum seed over a 4-byte constant block
sStack_1c = sVar4 + FUN_08068578(param_2, *puVar5);  // + checksum over the payload buffer
sStack_1a = -sStack_1c;                        // store negated sum alongside

FUN_08068578 itself is not in the extracted seed set, so its internal algorithm (straight sum vs. CRC vs. XOR) is UNKNOWN; what is visible is that the result and its negation are both computed and presumably stored as a value/complement pair — structurally consistent with the u16+u16==0x10000 check in FUN_08068af0.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of saves/cap-00-future-0.sav, loaded via the paired pre/post .ss save states once a boot-time load has been captured (no .ss states exist yet in states/ for this release — this is a prerequisite action, not yet performed).

  1. Sentinel corruption (single slot, single half):
  • Mutation: flip one byte of the slot-0 sentinel at 0x0040 (e.g. 54→00), leaving 0x1040 intact.
  • Requires checksum repair: No (no checksum covers this region per current evidence; purely a magic-compare).
  • Predicted effect: On next boot, FUN_0801180c(0) → FUN_080685cc(0) should report half-A invalid while FUN_080685f8(0) (half B) still reports valid → expect no visible gameplay change, but FUN_08068730(0) should fire and silently rewrite 0x0040 back to 54 49 4E 49 from the (intact) in-RAM/half-B state. Observable via a post-boot .sav diff showing the byte self-healed.
  1. Sentinel corruption (both halves of one slot):
  • Mutation: flip the same byte at both 0x0040 and 0x1040.
  • Predicted effect: Both FUN_080685cc(0)/FUN_080685f8(0) report failure → status -1 path → FUN_08068730(0) rewrites both halves from whatever default/zeroed struct is in RAM at boot (likely producing a "new file" / blank-slate player file rather than self-healing prior progress, since no valid source remains). This is the key experiment to determine whether full dual-corruption is recoverable or destructive.
  1. Global slot (index 3) dual corruption — cascade test:
  • Mutation: corrupt both 0x0070 and 0x1070.
  • Predicted effect per FUN_080686a8: triggers FUN_08068730(2), FUN_08068730(1), FUN_08068730(0) in addition to repairing slot 3 — i.e. corrupting only the global slot should cause all three player slots to be rewritten too. This is a strong, falsifiable, counterintuitive prediction worth testing first.
  1. Trailing tail-value mutation at 0x0026-0x0027 (AC DB):
  • Mutation: change AC DB → 00 00, both halves.
  • Requires checksum repair: Unknown — this is exactly the candidate field the checksum scan in §4 failed to validate against any neighboring pair, so this experiment doubles as a checksum-location probe.
  • Predicted effect: if this is in fact a checksum/counter consumed somewhere outside the traced functions, expect either a visible load failure (text block treated as corrupt) or no effect (if it is inert/unused in this build). Either outcome narrows the hypothesis.
  1. TF4S/KNIL tag swap at 0xE4/0xEA:
  • Mutation: swap the two 4-byte tags' positions.
  • Predicted effect: if these are independent identifiers (game-mode tag vs. reversed-word tag) consumed by distinct, unrelated checks, expect no crash but possibly a different reported "mode" on boot (if any UI surfaces it) or silent ignoring; if they are checked as a pair, expect FUN_08068af0-style validation to fail and trigger repair.
  1. Baseline/control — re-save without mutation:
  • Fresh/restore repeat: load cap-00-future-0.sav unmodified, let the title-screen boot sequence run to completion, and re-dump EEPROM. Predicted effect: byte-identical output (no incidental re-randomization), establishing the negative control for all mutation experiments above.

Each experiment above has a concrete, observable, falsifiable prediction and a matched non-mutated control (#6), per the project's experimental-design requirements. None of these have been executed yet — this section is a plan, not a result.
