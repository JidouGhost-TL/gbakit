1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven (code + .sav bytes agree):

  • The save medium is battery-backed SRAM, accessed through two generic hardware I/O driver routines (FUN_080006a4 write, FUN_080006e4 read) that both OR the caller-supplied offset with 0xE000000, placing them squarely in the GBA SRAM/Flash address window 0x0E000000.
  • Bytes 0x00–0x27 (40 bytes) of the single .sav sample contain a non-blank, structured region; everything from 0x28 to the end of the 32768-byte file is the SRAM open-bus fill value 0xFF.
  • A 32-byte fixed identification string occupies 0x00–0x1F, followed by two 4-byte "stamp" fields at 0x20 and 0x24. This exactly matches the byte ranges that the decompiled writer function (FUN_08000358) and reader/validator function (FUN_080002e0) operate on.
  • No arithmetic checksum, XOR, or CRC loop exists anywhere in the 214 decompiled functions available (grep -c "+=" over the whole file returns zero hits). Integrity is enforced by (a) an exact memcmp of the 32-byte magic string and (b) small range checks on the two 4-byte stamp fields, not by a traditional checksum.

What remains open:

  • We have only one .sav sample, and it is a "cold" / freshly-created save (both stamp fields are 0, and everything past offset 0x28 is unwritten 0xFF). We cannot yet observe how the stamp fields change after real gameplay saves, nor where actual farm/calendar/inventory data lives in the remaining 32728 bytes.
  • The RAM-side source/destination buffers for the writer/reader (_DAT_08000398, _DAT_08000354, _DAT_0800039c, etc.) are ROM-resident pointer/literal-pool symbols whose dereferenced RAM target addresses are not resolvable from the decompiled excerpts in this workspace — their EWRAM/IWRAM addresses are UNKNOWN.
  • No caller was found anywhere in the 214-function corpus for the writer entry point FUN_08000358 or the stamp-accessor FUN_080003a0; both are presumably invoked by higher-level menu/game-state code that is outside the current decompilation slice.
  • ghidra/callgraph.json reports empty callers/callees for the two low-level MMIO seed functions (0x080006a4, 0x080006e4) even though ghidra/decompiled.c plainly shows them being called from FUN_080002e0/FUN_08000358/FUN_080003a0. This is a known tool limitation (both seeds have "Could not recover jumptable" warnings), so caller lists below were reconstructed by manual text search, not solely from the callgraph.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O drivers (SRAM byte I/O)

FUN_080006a4 @ 0x080006a4 — SRAM WRITE driver (write-with-verify-retry)

void FUN_080006a4(undefined4 param_1,uint param_2,undefined4 param_3,int param_4)
{
  ...
  *_DAT_080006e0 = 0;
  if (param_4 != 0) {
    iVar1 = func_0x080d38d4(param_3,param_2 | 0xe000000);   // param_2 = SRAM offset, OR'd with base 0x0E000000
    bVar2 = iVar1 == 0;
    if (!bVar2) { func_0x08000728(param_1,0x100); }
  }
  (*UNRECOVERED_JUMPTABLE)(bVar2);
}

param_2 | 0xe000000 is the unambiguous tell that this driver addresses the GBA SRAM/Flash window. It delegates to FUN_080d38d4 (0x080d38d4), which performs up to 3 write+verify-readback retries:

void FUN_080d38d4(...) {
  for (bVar1 = 0; bVar1 < 3; bVar1 = bVar1 + 1) {
    FUN_080d3800(param_1,param_2,param_3);   // raw byte copy (the actual store to SRAM)
    param_4 = FUN_080d3870(param_1,param_2,param_3); // read-back + memcmp-style verify
    if (param_4 == 0) break;                 // 0 == match == success, stop retrying
  }
}

FUN_080d3800 is a plain byte-by-byte copy loop (*param_2 = *param_1; param_1++; param_2++;), and FUN_080d3870 copies into a stack buffer and (per its structure) feeds a verification path through func_0x080d3918 — a generic SDK byte-copy/verify primitive, not game-specific.

FUN_080006e4 @ 0x080006e4 — SRAM READ driver (plain copy, no retry)

void FUN_080006e4(undefined4 param_1,undefined4 param_2,uint param_3,int param_4)
{
  *_DAT_08000708 = 0;
  if (param_4 != 0) {
    func_0x080d379c(param_3 | 0xe000000,param_2);   // param_3 = SRAM offset, OR'd with base 0x0E000000
  }
  (*UNRECOVERED_JUMPTABLE)(param_4 != 0);
}

Delegates to FUN_080d379c (0x080d379c), a stack-buffer copy that forwards into func_0x080d3918, mirroring the read half of the same generic SRAM-access primitive family (FUN_080d3800/FUN_080d3870/FUN_080d3948 memcmp/FUN_080d3918).

Both 0x080006a4 and 0x080006e4 are marked "candidate only" with "Could not recover jumptable — too many branches" in Ghidra, and ghidra/callgraph.json lists zero callers/callees for both, even though their callers are visible in ghidra/decompiled.c (see §3.2). This is a static-analysis gap in the available callgraph, not evidence that these functions are unused.

3.2 Serialization / Validation & Caller Chains

Writer entry point — FUN_08000358 @ 0x08000358 (ghidra/decompiled.c lines 43–67)

void FUN_08000358(undefined4 param_1)
{
  func_0x080006a4(param_1,0,_DAT_08000398,0x20);   // write 32B magic/header to SRAM offset 0x00
  puVar1 = _DAT_0800039c;
  if (*_DAT_0800039c == 0) {                        // only proceed if the header write reported success
    uStack_10 = (uint)*_DAT_0800039c;                // reuse the (0 == success) status value AS the data
    func_0x080006a4(param_1,0x20,&uStack_10,4);      // write 4B stamp A to SRAM offset 0x20
    if (*puVar1 == 0) {
      func_0x080006a4(param_1,0x24,&uStack_10,4);    // write the SAME 4B value as stamp B to SRAM offset 0x24
    }
  }
}

How mapped: traced directly from the decompiled source text; ghidra/callgraph.json has no caller entries for 0x08000358 itself, so the game-logic trigger (menu "Save" command, etc.) is outside the 214-function corpus provided. The mutation sequence on the in-RAM save image is: (1) the header bytes, already assembled in RAM at _DAT_08000398 prior to this call, are flushed verbatim to SRAM 0x00; (2) the write-status code itself (0 on success) is written into SRAM at 0x20 and 0x24 as a post-write confirmation stamp — this call does not itself construct the header or recompute any checksum, it is a pure flush routine.

Reader/validator — FUN_080002e0 @ 0x080002e0 (ghidra/decompiled.c lines 2–40)

void FUN_080002e0(undefined4 param_1)

  func_0x080006e4(param_1,auStack_34,0,0x20);         // read 32B header from SRAM 0x00 into local buffer

How mapped: traced directly from decompiled source; confirmed as a real edge in ghidra/callgraph.json ("0x080002e0": {"callers": ["0x080003a0"], ...}). This function performs no RAM mutation — it is read-only and produces a boolean validity verdict in a register (uVar3), consumed by its caller.

Stamp accessor — FUN_080003a0 @ 0x080003a0 (ghidra/decompiled.c lines 70–95)

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

Offset 0x00, length 32 bytes (the exact span read/written/compared by FUN_08000358/FUN_080002e0/FUN_080d3948):

hex:      47 42 41 96 71 8f ea 95 a8 8c ea 82 cc 53 52 41
          4d 83 43 83 81 81 5b 83 57 20 30 30 30 30 00
ascii:    G  B  A  .  q  .  .  .  .  .  .  .  S  R  A  M
          .  C  .  .  .  [  .  W     0  0  0  0  .

Decoded as mixed ASCII/Shift-JIS, this is the literal text string:

"GBA牧場物語のSRAMイメージ 0000" (+ 1 trailing NUL to fill 32 bytes)

i.e. "GBA [Bokujou Monogatari / Harvest Moon] no SRAM imēji" ("GBA Harvest Moon's SRAM image"), followed by a 5-digit ASCII decimal counter field whose first four digits ("0000") fall inside this 32-byte span and whose fifth digit ("0") plus further padding falls just past it (byte 0x20 onward, see field map). This is a well-known convention on GBA-era Japanese titles: an embedded human-readable save-type/version stamp used for auto-detection by flashcarts/emulators and sanity-checking by the game itself. It was decoded directly from the original .sav bytes in this workspace — no external reference was consulted.

This observed string differs from the corpus-metadata SDK tag SRAM_V113@7715160; that literal substring was not found anywhere in the 40-byte active region of the sample. It may exist elsewhere in ROM outside the excerpts provided in this workspace (open question).

  • verified_in_code: true — FUN_08000358 writes exactly this 32-byte span from a RAM buffer to SRAM 0x00, and FUN_080002e0 memcmps exactly this span against a fixed template (_DAT_08000354).
  • verified_in_sav: true — present verbatim in saves/cap-00-future-0.sav bytes 0x00-0x1F.

4.2 Checksum / integrity algorithm

No arithmetic checksum (sum, XOR, CRC, complement) was found. A full-text search of all 214 decompiled functions in ghidra/decompiled.c for accumulation idioms (+=, byte-summation loops) returned zero matches. Integrity is instead enforced by two independent mechanisms, both confirmed in FUN_080002e0:

  1. Exact magic-string match — func_0x080d3948(auStack_34, _DAT_08000354, 0x20) is a memcmp-style byte-equality check (see FUN_080d3948 disassembly: byte/word-wise compare returning the first differing byte's signed difference, 0 if equal) over the 32-byte header against a fixed in-ROM template. Any single bit flip in the header fails validation.
  2. Range-bounded stamp fields — the reader additionally requires (stampA & 3) == stampA (i.e. stampA ∈ {0,1,2,3}) and stampB < 2 (i.e. stampB ∈ {0,1}). These are not checksums of the header; they are plausibility bounds on two small status/echo values written by the save routine itself.

Python verification against the actual .sav file (saves/cap-00-future-0.sav):

$ python3 - <<'EOF'
data = open('saves/cap-00-future-0.sav','rb').read()
hdr32 = data[0:0x20]
print('header (shift_jis):', hdr32.decode('shift_jis', errors='replace'))
stampA = int.from_bytes(data[0x20:0x24], 'little')
stampB = int.from_bytes(data[0x24:0x28], 'little')
print('stampA =', stampA, ' (stampA & 3) == stampA ->', (stampA & 3) == stampA)
print('stampB =', stampB, ' stampB < 2         ->', stampB < 2)
print('bytes 0x28..end all 0xFF ->', all(b == 0xff for b in data[0x28:]))
EOF

header (shift_jis): GBA牧場物語のSRAMイメージ 0000
stampA = 0  (stampA & 3) == stampA -> True
stampB = 0  stampB < 2         -> True
bytes 0x28..end all 0xFF -> True

Since no fixed "expected header" byte-for-byte template beyond our own decode is available in this workspace (the in-ROM comparison constant _DAT_08000354 is referenced but its literal bytes are not present in the decompiled excerpts), the verification above demonstrates self-consistency: the sample's header is well-formed ASCII/Shift-JIS text and both stamp fields independently satisfy the exact range predicates the decompiled reader enforces. This is the strongest verification achievable from a single cold sample; a second, post-gameplay-save sample is required to test whether a deliberately corrupted header or out-of-range stamp is actually rejected at runtime (see §6).

Overall checksum confidence: CONFIRMED_STATIC for "no arithmetic checksum exists / integrity = magic-match + range-check", CONFIRMED_VERIFIED for "the sample's header text and stamp values currently satisfy those exact predicates."

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of a save that has first been through one real in-game save (so that stamp fields are populated by the real game rather than by this report's assumptions), then reloaded from the paired pre-save .ss state so the exact RAM contents at the moment of load are known.

  1. Header corruption (offset 0x00, 1 byte flip, e.g. 0x47→0x48)
  • Mutation: flip a single byte inside the 32-byte magic/header span.
  • Requires checksum repair: no (no checksum exists), but this will fail the memcmp in FUN_080002e0.
  • Predicted effect: on next load, FUN_080002e0 returns "invalid" (uVar3 = 0); the game should treat the save as absent/corrupt and behave as it does when SRAM is freshly erased (e.g. offer "new game" rather than "continue", or silently reset progress). No crash is expected since the check is a simple boolean gate.
  1. Stamp A out-of-range (offset 0x20, write 0x00000004)
  • Mutation: set the 4-byte LE value at 0x20 to 4.
  • Requires checksum repair: no.
  • Predicted effect: (4 & 3) == 4 is False (since 4 & 3 == 0), so validation fails exactly like case 1, even though the header itself is untouched. This isolates and confirms the stamp-A range check independently of the header memcmp.
  1. Stamp B out-of-range (offset 0x24, write 0x00000002)
  • Mutation: set the 4-byte LE value at 0x24 to 2.
  • Requires checksum repair: no.
  • Predicted effect: 2 < 2 is False, validation fails, isolating the stamp-B check independently of header and stamp A.
  1. Stamp A/B boundary values (offset 0x20=3, offset 0x24=1)
  • Mutation: set stamp A to the maximum in-range value (3) and stamp B to 1, leaving the header intact.
  • Predicted effect: validation should still pass (3 & 3 == 3, 1 < 2), proving these are genuinely inclusive-range checks rather than exact-equality-to-zero checks, and testing whether the game's behavior differs when stamp values are nonzero (e.g. does it pick a different internal save-slot index, consistent with the open hypothesis that stamp A is a mod-4 slot/generation selector rather than a pure 0/1 success echo?).
  1. Region-discovery sweep (offset 0x28 onward)
  • Mutation: in small aligned chunks (4 or 8 bytes at a time), toggle bytes across the currently-unmapped 0x28–0x7FFF region on a save taken after some real farm progress has been made, and diff against the pre-mutation .sav/.ss pair.
  • Requires checksum repair: unknown — contingent on whether gameplay data in this region has its own (as-yet unobserved) per-record checksum, which cannot be ruled out since this report's checksum analysis only covers the 40-byte header region actually exercised by the 214 traced functions.
  • Predicted effect: observable changes in on-screen stats (money, day/season counters, character stats) pinpoint field offsets for round-two mapping; this is the primary recommended next step, since the current corpus contains zero traced functions touching this 32728-byte region.
