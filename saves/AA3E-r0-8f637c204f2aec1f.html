1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree)

  • The save image is a 32,768-byte SRAM image containing 11 contiguous chunks that tile offsets 0x0000..0x7F4F with no gaps and no overlap. Every chunk has a 12-byte header {magic[4], u16 version/flag, u16 block_size, u16 block_count, u16 checksum} followed by block_size * block_count payload bytes.
  • The per-chunk integrity algorithm is a 16-bit byte-sum over the payload only, implemented in FUN_0802eae0 (0x0802eae0) and stored little-endian at header offset +10. Python re-implementation matches the stored value for all 11 chunks in both samples (22/22) — including the non-trivial checksums LINE=0x9586, SEAS=0x05C9, OPTS=0x0200, CARD=0x003F, WSLU=0x000E.
  • The low-level SRAM driver, chunk verifier, chunk writer, single-record reader, and single-record writer were all located in the decompilation and cross-checked against the on-disk layout (Section 3, Section 4).
  • Boot behaviour matches the packet probe: on load every chunk is verified; a chunk that fails magic/shape/checksum validation is rewritten from RAM (FUN_0802ea38 → FUN_0802eb00 / FUN_0802ec10). This is the mechanism behind "reverted to blank / save rewritten after mutation".

Static-only (code seen, bytes cannot confirm)

  • Descriptor-table semantics beyond the file-visible fields: each of the 11 ROM descriptors is 20 bytes (5 × u32); fields +0/+4/+8/+12 are visible in the file headers, but field +16 (RAM record stride used by the writer via func_0x08044018) and all RAM mirror base addresses are referenced only through unresolved _DAT_ literal-pool symbols in the trace-guided decompilation. No concrete 0x02xxxxxx/0x03xxxxxx mirror address can be stated honestly.
  • The two pre-extracted "MMIO seed" functions in ghidra/save_related_functions.c (0x080440e8, 0x08044230) are signed/unsigned divide/modulo runtime helpers, not save code. The seed heuristic produced false positives; the real save stack sits at 0x0802e8xx–0x0802efxx + 0x080435xx–0x080436xx and was found by tracing byte-loop/checksum shapes and textual func_0x… call sites, not by the seed file.

Open / unresolved (stated plainly)

  • The byte at 0x7FFC (0x60 in cap-00-future-0.sav, 0xE0 in cap-01-retained-3.sav) is not explained. It lies outside the chunk area (chunks end at 0x7F50), the chunk areas of both files are byte-identical (same SHA-256 prefix), and no traced function reads or writes that offset. It therefore cannot be a deterministic checksum over the chunk content (identical content would give an identical value). The two values differ only in bit 7 (0x60 vs 0xE0; low 7 bits 0x60 in both), which suggests a toggled flag/generation bit on a base value, SRAM residue, or a check value salted by state outside the image — all hypotheses, none proven. The packet probe reports that mutating 0x7FFC reverted the game to blank; that observation is not reproduced by any code path visible in this workspace and is flagged as an open question in Section 6 rather than silently absorbed into a checksum claim.
  • Only two .sav samples exist and both are the same blank/default state (all statistic tables are zero). Field semantics inside the LINE/SEAS/WSLU/CARD blobs (schedule grids, ID ramps, charset tables) are therefore labelled HYPOTHESIS/UNKNOWN, not confirmed gameplay meanings.
  • ghidra/decompiled.c is a trace-guided subset (364 functions), not the full ROM. Gameplay-time writers beyond the traced boot/record paths may exist outside the trace; absence of a caller in this corpus is not proof of absence in the ROM.

Slots, copies, mirroring, generation counters

  • There are no save slots and no mirrored/backup copies. The image is a single linear sequence of 11 named chunks. No duplicate chunk, no A/B bank, and no per-slot header exists anywhere in the 32 KiB.
  • There is no generation/sequence counter inside the chunk area. Headers contain magic, version/flag, block size, block count, and payload checksum only (Section 5). Nothing increments between the two samples inside 0x0000..0x7F4F (the chunk areas are byte-identical).
  • Selection rule: there is nothing to select. At boot, FUN_0802ea38 walks all 11 descriptors in order, computes each chunk's SRAM offset by accumulation (offset[0]=0; offset[n+1]=offset[n]+12+block_size*block_count), verifies each chunk independently, and rewrites only the failing chunk from RAM (FUN_0802ec10). Validity is therefore per-chunk, not per-image: corrupting one chunk costs that chunk, not the whole save — with the caveat that the packet's cold-reload probe mutated the out-of-area byte 0x7FFC and still observed a blank revert, which this per-chunk model does not explain (open question Q1, Section 6).
  • Redundancy is limited to (a) the per-chunk checksum, (b) write-with-verify (up to 3 attempts, FUN_08043688), and (c) boot-time rewrite-from-RAM of invalid chunks. There is no second copy to fall back to; "recovery" means resetting the chunk to whatever the RAM image currently holds (defaults at boot).

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How functions were mapped (method)

  1. The ghidra/save_related_functions.c seeds (0x080440e8, 0x08044230) were inspected first and rejected: both are shift/subtract division helpers (signed modulo / unsigned division runtime), with no memory I/O. Treating them as save code would have been a false lead.
  2. ghidra/decompiled.c was split into its 364 functions. Byte-loop shapes were searched (byte */undefined1 * dereference loops with an accumulator), which surfaced FUN_0802eae0 — a textbook byte-sum — plus strcpy-family false positives at 0x080438d4/0x08043974/0x08043794 (rejected: NUL-terminated string copies, no length/checksum semantics).
  3. Callers of the checksum were traced textually. Ghidra emits two call spellings: FUN_… (resolved, present in ghidra/callgraph.json) and func_0x… (unresolved/external-style, absent from the callgraph's callee lists). Both spellings were searched; the callgraph was used where it has edges (FUN_0802eae0 ← 0x0802eb00/0x0802ec10/0x0802eda0; FUN_0802eabc ← five chunk functions) and textual search supplied the edges the callgraph misses (e.g. FUN_0802ea38 → func_0x0802eb00, FUN_08000f90 → func_0x0802ece8). Every caller chain below states which evidence type backs it.
  4. The resulting chunk functions were then validated against the .sav bytes: their header size (0xC), field offsets, record arithmetic (base + 12 + block_size * index), and checksum seed/accumulation all reproduce the file layout exactly (Section 4). Code and bytes corroborate each other; neither was trusted alone.

3.1 Low-level hardware I/O driver (SRAM, byte-wide)

All SRAM traffic funnels through three functions in the 0x080435xx–0x080436xx runtime region. No Flash command sequence (0x5555/0x2AAA), no EEPROM DMA3 serial bitstream, and no 0x0E000000 literal appear in the decompilation — SRAM base/bus details live behind unresolved _DAT_ pointers, consistent with a library SRAM driver. WAITCNT (0x04000204) handling is visible only as *ptr = *ptr & mask | 3 through an unresolved pointer in each entry point (setting the SRAM wait-state field to 3); the mask/base values are _DAT_-hidden, so the WAITCNT claim is CONFIRMED_STATIC by shape, not by literal.

3.3 ALL traced callers and how each mutates the in-RAM save state before flushing

Only three game-side call sites touch the chunk API in the traced corpus. Each is listed with its caller chain, mapping evidence, and RAM mutation. RAM addresses are _DAT_-unresolved throughout, so mutations are described by buffer/field offsets, not absolute addresses — inventing 0x02… values would be fabrication.

Chain A — boot validation (no RAM mutation; SRAM-only repair)

FUN_0802e928 (main, no callers — entry)
  └─ func_0x0802ea38()                     [textual call in FUN_0802e928]
       ├─ func_0x0802eb00(magic) ×11       [verify each chunk; textual]
       └─ func_0x0802ec10(magic) on failure [rewrite chunk from current RAM; textual]
  • FUN_0802e928 is the traced main function (callgraph: no callers; it calls FUN_08000f90, FUN_08001098, FUN_0802a8cc plus unresolved func_0x… targets including func_0x0802ea38).
  • Mutation semantics: FUN_0802ea38 itself mutates only SRAM (via the writer) and its stack offset table. If a chunk is rewritten, the bytes come from whatever the RAM record buffers hold at that moment — at boot, before any load has populated them, that means default/zero RAM. Hence a corrupted chunk reverts to blank/default content, matching the packet probe's reverted_to_blank_on_mutation / save_rewritten_after_mutation.

Chain B — boot config/record fetch

FUN_0802e928 (main)
  └─ FUN_08000f90()                        [callgraph + textual]
       ├─ func_0x0800adb4()                [textual; see Chain C]
       └─ func_0x0802ece8(magic=_DAT_08001084, index=0, dst=_DAT_08001088)  [textual]
  • After the record read, FUN_08000f90 unpacks the fetched record into the game struct: struct+0x294 = (u16)(dst+4), +0x298 = (u16)(dst+6), +0x29C = dst[1], +0x2A0 = dst[2], +0x2A4 = dst[0], +0x2A8 = dst[3], then passes +0x294/+0x298 to func_0x0803789c/func_0x08037884. So record bytes 0..7 (two bytes, two bytes, then two u16s — or overlapping views thereof) seed live game state at boot.
  • Which chunk? The magic is _DAT_08001084 (unresolved literal). By elimination it must be one of the 11 magics, and the 8-byte field extraction suits a small blob (STAT 4-byte payload is too small for offsets up to +6 unless the destination buffer overlaps the following RAM; OPTS 12-byte payload fits best). Assignment to OPTS is a hypothesis (Section 5), not a confirmation.
  • Mutation semantics: this chain mutates RAM from SRAM (deserialize-on-demand). It does not flush anything itself.

Chain C — 64-byte default-pattern record ensure (write-then-read)

FUN_08000f90()
  └─ FUN_0800adb4()                        [textual from FUN_08000f90; callgraph lists it caller-less
       │                                    because the call uses the func_0x spelling]
       ├─ fill RAM buffer[0..63] = 0x01; buffer[0x3F] = 0x00
       ├─ func_0x0802eef0(magic=_DAT_0800ae18, index=0, src=buffer)   [write record + fix checksum; textual]
       └─ func_0x0802ece8(magic, index=0, dst=buffer)                 [read it back; textual]
            └─ if read-back failed: refill buffer[0..63] = 0x01 (defaults stay in RAM)
  • This function writes SRAM on every boot (via FUN_0802eef0), independent of corruption. That alone explains the probe's save_rewritten_after_mutation: true without invoking the 0x7FFC byte: a mutated image can be rewritten by routine boot traffic, not only by integrity repair.
  • The 64-byte pattern (63×0x01 + terminating 0x00) matches the start of the CARD payload (63×0x01, byte 63 = 0x00, rest zero) byte-for-byte. That makes CARD the leading candidate for _DAT_0800ae18 — still a hypothesis, because the literal is unresolved and FUN_0802eef0 writes block_size bytes (400 for CARD) from a buffer that this function only explicitly initializes for 64 bytes (the remainder would be whatever RAM already holds, zeros in a fresh boot, which also matches).

What is NOT in the traced corpus

  • No traced caller invokes FUN_0802ec10 (whole-chunk write) except the boot repair path, and no traced caller invokes FUN_0802eef0 except Chain C. Season/gameplay stat flushing (e.g. updating BATT/PITC records after a game) must either reuse these same entry points from untraced code or live outside the 364-function trace. The report therefore claims these chains as all traced callers, not all ROM callers.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signatures

Eleven 4-byte ASCII magics, each at its chunk offset, each verified in both samples and each required by code (FUN_0802eb00/FUN_0802ece8/FUN_0802eef0 compare header +0 against the descriptor magic):

STAT @0x0000, BATT @0x0010, PITC @0x308C, WBAT @0x4998, WPIT @0x4CC4, WSLU @0x4FF0, LINE @0x51F0, SEAS @0x723C, SERI @0x7CF8, CARD @0x7D9C, OPTS @0x7F38.

Other ASCII found in the images (0123456789ABCDEFL, the full printable charset at file 0x7052, Miscellaneous, Illegal) lies inside the LINE payload (file 0x51FC..0x723B) and is payload data — likely text/charset tables — not chunk magics. No code in the traced corpus references them as signatures.

4.2 Checksum algorithm (CONFIRMED_VERIFIED)

  • Algorithm: 16-bit additive byte sum (sum16 over payload bytes), seed 0, no complement, no XOR, no CRC.
  • Covered range: the chunk payload only — block_size * block_count bytes starting at chunk_offset + 12. Header bytes are excluded (including the magic and the checksum field itself).
  • Stored: header offset +10, u16_le, 2 bytes.
  • Computation order in code: accumulated block-by-block (acc = FUN_0802eae0(block, block_size, acc) per block), which is arithmetically identical to summing the concatenated payload.

Decompiled proof — FUN_0802eae0 (0x0802eae0), in full:

int FUN_0802eae0(byte *param_1, int param_2, short param_3)
{
  byte bVar1;
  if (0 < param_2) {
    do {
      bVar1 = *param_1;
      param_1 = param_1 + 1;
      param_3 = (ushort)bVar1 + param_3;
      param_2 = param_2 + -1;
    } while (param_2 != 0);
  }
  return (int)param_3;
}

Accumulation back into the short parameter truncates to 16 bits each iteration; the verifier compares the result against the header's short at +10 (if (sVar1 == sStack_1e) in FUN_0802eb00), and the record writer recomputes it after every single-record update (FUN_0802eef0 → FUN_0802eda0 → header rewrite).

  • Empty tables (BATT/PITC/WBAT/WPIT/STAT/SERI) sum to 0x0000 — match, but trivially (all-zero payloads); they confirm the field position, not the algorithm's strength. The algorithm rests on the five non-trivial chunks above.

4.4 The 0x7FFC byte — explicitly NOT verified as a checksum

  • cmp -l between the samples shows exactly one differing byte: file offset 0x7FFC, 0x60 → 0xE0.
  • Both files have byte-identical chunk areas (chunk_area_sha256 equal) and all 22 chunk checksums pass in both. Any deterministic checksum over the chunk area, the whole image (excluding its own byte), or the 0x7F50-bounded content would be identical in both files. Tested candidates (sum8/XOR over 0..0x8000 excl. self, over 0..0x7F50, over the 0xFF tail, sum of chunk checksums =0x9C low byte) — none equals 0x60/0xE0, and none can explain the variation. Conclusion: 0x7FFC is not a content checksum under any standard formula tested. Confidence: the negative result is verified; the byte's purpose is UNKNOWN.
  • The bit-7-only difference (0x60 vs 0xE0, shared low bits 0x60) is consistent with a flag/generation toggle over a constant base, or with unmanaged SRAM residue retained by the emulator. The packet probe's claim that mutating this byte reverted the game to blank (integrity_check_confirmed: true) cannot be reproduced from the traced code — no traced function addresses 0x7FFC — and Chain C shows the game rewrites SRAM at boot regardless. Section 6 includes a discriminating test.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for all payload mutations: after editing payload bytes, recompute the target chunk's checksum as sum(payload_bytes) mod 65536 (Python: sum(data[off+12:off+12+size]) & 0xFFFF) and store it little-endian at chunk_offset + 10. Header mutations (magic/shape) must not be checksum-repaired when the goal is to test the validator. No .ss save states were provided in this workspace (states/ is empty), so every prediction below is phrased for cold-boot reload of a mutated .sav (the packet's own probe method) and can be re-run verbatim if paired states become available. Predictions derive from FUN_0802ea38 (verify-or-rewrite), FUN_0802eb00 (verify), FUN_0802ece8 (header-only record read), and Chain C's every-boot write.
