1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM. The physical format, the EEPROM driver, the slot geometry, the header magic, and the checksum algorithm are proven to a high standard (code plus both binaries, with an arithmetic match on both samples). The semantics of most payload fields are not proven, several absolute RAM addresses cannot be resolved from the trace-guided decompilation, and the fully-valid state of the save was never observed. Those gaps cap the overall grade.

What was proven (verified by both decompiled code and .sav bytes):

  • The save lives on a 512-byte EEPROM (EEPROM 4K). The boot loader selects type 4 via FUN_08049158(4), and only one active region exists: 40 bytes at file offsets 0x00–0x27. The remaining 472 bytes are the EEPROM fill byte 0xFF in both samples.
  • The 40 bytes are five 8-byte EEPROM blocks. Block 0 is a header/magic block. Blocks 1–4 hold a single 32-byte RAM profile struct (struct index 0, stride 0x20).
  • Bytes inside each 8-byte block appear in the .sav file in the reverse of RAM order. This was not assumed from the driver shape; it was proven by the checksum (Section 4): only under per-block byte reversal does the stored checksum match on the non-trivial sample, and only under that reversal do the writer's known constants (+0x19 = 1) land on the changed bytes.
  • The header magic in RAM order is the ascending byte sequence 00 01 02 03 04 05 06 07 (file order 07 06 05 04 03 02 01 00). It is compared at every boot by FUN_08008C38 and written at format time by FUN_08008CA4.
  • The integrity algorithm is an 8-bit additive checksum (sum8) over the first 31 bytes of the RAM struct, stored at RAM +0x1F (file offset 0x20). Writer FUN_0800931C, verifier FUN_080093E4. It matches both samples in RAM order: 0x00/0x00 and 0x03/0x03.
  • The only difference between the two saves is a single commit event: the value at RAM +0x17 changed 0 → 2, the committed flag at RAM +0x19 changed 0 → 1, and the checksum at RAM +0x1F changed 0x00 → 0x03. In file terms those are exactly the three mutated bytes reported in PACKET.md (0x18, 0x26, 0x20).
  • There is no backup copy, no mirror, and no generation/sequence counter. Write reliability is by write-then-verify with up to 3 retries (FUN_08049534), not by redundancy.

What remains open (stated plainly):

  • Absolute RAM addresses. The decompilation resolves code addresses (0x08xxxxxx) but leaves data pointers as unresolved literal-pool placeholders (_DAT_xxxxxxxx, iRam…, puRam…). The profile struct base is returned by FUN_080093DC from one such pointer. All field addressing in this report is therefore struct-relative (+0x00…+0x1F), which is fully proven, rather than absolute (0x02…/0x03…), which is not recoverable from the workspace files.
  • Semantics of almost every payload byte. The code proves who writes and reads several fields and what values they hold, but not what they mean in gameplay terms (for example what the committed value 2 at RAM +0x17 selects).
  • The gate byte at RAM +0x18 is 0 in both samples, so the checksum verifier FUN_080093E4 would return 2 (gate-zero) for both, even though the arithmetic checksum matches. A fully-valid (return 0) save was never observed. See Section 4.3.
  • Three other EEPROM block groups (starting at blocks 5, 9, 13) are addressable by the incremental flusher FUN_08008F74 but were never observed with data. They are not slots or copies on current evidence.
  • Boot/menu entry functions have no static callers in the call graph (dispatch is through unrecovered jumptables), so their trigger conditions are inferred from their bodies.

2. Physical Media, Slot Geometry & Redundancy

2.1 Media

  • Kind: EEPROM, 512 bytes total (EEPROM 4K, i.e. 4 Kbit). The .sav files are exactly 512 bytes, and the boot loader calls FUN_08049158(4) — the EEPROM type-select helper whose decompiled body accepts 4 (and 0x40) and returns 0 on success, 1 otherwise. Argument 4 is consistent with a 4-Kbit device.
  • Bus: serial EEPROM at 0x0D000000, transferred with DMA3. The DMA primitive FUN_080492D0 programs a transfer with count | 0x80000000 and busy-waits on the DMA busy bit; the read/write drivers use it to send a bitstream to 0x0D000000 and to receive 0x44 (68) halfword transfers back. No SRAM (0x0E000000) or Flash command sequence (0x5555/0x2AAA) appears anywhere in the traced code — searches for 0x0d000000-family references hit only the EEPROM driver cluster.
  • Block geometry: 8 bytes (4× u16, 64 bits) per EEPROM block, 64 blocks per 512-byte device. Every high-level read/write moves exactly one block (FUN_08049350 / FUN_08049400 take a block number and a 4-short buffer). The driver guards block < *(ushort *)(descriptor + 4) and takes the address-bit count from *(byte *)(descriptor + 8); the descriptor entry is selected by FUN_080491C8(2, &ptr) before each operation. The descriptor values themselves are not readable from the workspace files, so the 64-block limit and 6 address bits are inferred from the media size and the DMA lengths, not read from a constant. This inference is labelled as such wherever it matters.
  • Fill byte: 0xFF (EEPROM erased state). Both samples are 0xFF from offset 40 to 511. Formatted-but-zero data is 0x00, not 0xFF, and the distinction is load-bearing in Section 2.2.
  • SDK tags: none detected in the ROM (per PACKET.md); nothing in the decompilation contradicts that.

2.2 Slot geometry

There is exactly one logical save slot, occupying the first five EEPROM blocks (40 bytes):

EEPROM blockFile offsetContent (RAM order)Role
00x00–0x0700 01 02 03 04 05 06 07Header / magic
10x08–0x0Fprofile RAM +0x00…+0x07Profile struct, part 1
20x10–0x17profile RAM +0x08…+0x0FProfile struct, part 2
30x18–0x1Fprofile RAM +0x10…+0x17Profile struct, part 3
40x20–0x27profile RAM +0x18…+0x1FProfile struct, part 4 (ends with checksum)
5–630x28–0x1FF0xFF (never written in samples)Unused / potentially other records

The file-to-RAM byte mapping inside each block is a reversal:

file_offset(block b, RAM byte j in block) = b*8 + (7 - j)        j = 0..7
RAM struct byte r (0..31)  ->  file offset = 8 + (r & ~7) + (7 - (r & 7))

So, for example, RAM +0x17 is file offset 0x18, RAM +0x19 is file offset 0x26, and the checksum RAM +0x1F is file offset 0x20. Section 4 proves this mapping.

Evidence for the geometry, from the loader FUN_08008D1C:

  1. It zeroes two 32-byte RAM buffers with FUN_080498B0(..., 0, 0x20).
  2. It reads block 0 separately (FUN_08008C38 → FUN_08049350(0, buf)) as the header.
  3. On success it reads blocks 1, 2, 3, 4 in a loop — FUN_08049350(block, ram_base + (block-1)*8) — filling exactly the 32-byte struct. On header failure it instead formats (Section 3).
  4. The formatter FUN_08008CA4 writes block 0 plus blocks 1–4. That is 5 blocks / 40 bytes, matching the observed active range 0x00–0x27 exactly.

A formatted save explains the samples' appearance: blocks 1–4 are 0x00 (explicitly written zeros from the zeroed RAM buffers), while blocks 5+ stay 0xFF (never written). cap-00 is the formatted/empty profile; cap-01 is the same profile after one commit.

2.3 Redundancy, counters, and selection rule

  • Copies/mirrors: none found. No second slot, no A/B copy, and no code that reads an alternate copy on failure. The recovery strategy on header mismatch is to reformat blocks 0–4 (FUN_08008CA4), discarding the profile — not to fall back to a backup. On checksum/gate failure the consumer (FUN_0801E928) substitutes default values for individual fields; it does not repair or re-read the EEPROM.
  • Generation/sequence counters: none found. No field increments per save, and no code compares two copies by recency. The only monotonic-looking values in the samples are the committed value (0 → 2) and its checksum, both explained by a single commit.
  • Write redundancy: retry, not replication. FUN_08049534 attempts write (FUN_08049400) + verify (FUN_080494DC, read-back and 4-short compare) up to 3 times per block.
  • Selection rule (the only one): at boot, FUN_08008D1C accepts the existing save iff the block-0 header compare (FUN_08008C38) passes; the profile struct is then loaded and separately validated by checksum/gate in FUN_0801E928. If the header fails, the save is reformatted. There is no slot choice to make because there is one slot.

2.4 Relation to the cold-reload probe in PACKET.md

The probe reports an integrity check confirmed at probe offset 0x18, with a visual delta after mutation but no rewrite of the mutated save. Offset 0x18 is the file image of RAM +0x17, which is inside the checksum-covered range. Mutating it without repairing the checksum makes FUN_080093E4 disagree with the stored byte, and FUN_0801E928 then installs defaults — a behavioural/visual delta without any EEPROM rewrite (nothing in the load path writes back on a checksum failure; only a header failure reformats). The observations are consistent with the traced code. The probe's reverted_to_blank_on_mutation: false is also consistent: a checksum failure does not blank the save.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method, and a warning about the graph)

Two evidence sources were cross-checked for every edge:

  1. The combined call graph (static C calls plus runtime direct calls), and
  2. The function bodies in the full decompilation and the save-related extract.

They do not always agree, and the disagreement matters. Calls written in the decompilation as func_0x........ (lower-case) are absent from the graph. For example, the graph lists FUN_080074BC's callees as 0x08003E8C, 0x08004844, 0x0800693C only, yet its body plainly calls func_0x0800931C(0) — the checksum commit. Likewise the graph gives FUN_08008D1C only two callees, while its body also calls the memset, type-select, descriptor-select, block-read, and post-load functions. Every caller claim in this section was therefore taken from the decompiled body text (with the graph as corroboration where it agrees), and each chain below states which source proves it. Any call made only through an unrecovered jumptable or function pointer remains potentially untraced; the near-universal UNRECOVERED_JUMPTABLE tail in these functions is a decompilation artefact of Thumb state-machine code, not evidence about the save logic.

Four relevant functions have no static callers in the graph — FUN_08008D1C (boot loader), FUN_08008F74 (incremental flusher), FUN_0801E928 (post-load applier, called from the loader's body as func_), and FUN_08046B90 (menu handler). They are reached by game-state dispatch. Their roles are inferred from their bodies and from the functions they call, and that inference is labelled.

3.1 Low-level hardware I/O driver (EEPROM serial via DMA3)

All bus traffic goes through one primitive and two block drivers. Addresses are code addresses in ROM (0x08xxxxxx).

FUN_080492D0(src, dst, count) — DMA3 transfer primitive. Saves/clears a control value, programs source and destination, writes count & 0xFFFF | 0x80000000 (enable bit) to the DMA control register via literal-pool pointers, then busy-waits while the busy bit (0x8000 of the upper halfword) is set, and restores the saved control value. Called only by the two block drivers. (Exact register addresses are among the unresolved literal-pool values; the 0x0D000000 EEPROM address is visible directly in its callers.)

FUN_08049350(block, out_ptr) — read one 8-byte block. If block >= *(ushort *)(descriptor + 4) it returns an error value. Otherwise it builds the read command bitstream on the stack: the block address is shifted out MSB-first, one stack halfword per bit, preceded by two 1 bits (start/opcode). It DMAs address_bits + 3 halfwords from the stack to 0x0D000000, then DMAs 0x44 (68) halfwords back from 0x0D000000 into the stack buffer, and reassembles four u16s: each output short is built by shifting left and OR-ing successive received bits, and the output shorts are written from the last short backwards (out + 6, descending). Returns 0 on success. This reassembly is the code-side origin of the per-block byte reversal proven in Section 4.

FUN_08049400(block, data_ptr) — write one 8-byte block. Same range guard. It expands the four input u16s bit-by-bit (MSB-first, descending stack writes), appends the block-address bits, and prefixes a 0/1 start pattern, forming the write bitstream. It DMAs address_bits + 0x43 (67) halfwords to 0x0D000000, arms the completion DMA/interrupt helper FUN_08049204, polls the EEPROM ready bit (0x0D000000 & 1), and tears down with FUN_0804928C.

FUN_08049204(param) / FUN_0804928C() — DMA arm/teardown helpers. FUN_08049204 clears and re-arms a DMA channel, installs its saved register triple (*param, param[1], param[2]), sets a channel bit computed as 8 << type_index, and marks the channel active. FUN_0804928C clears the channel, masks off the same 8 << type_index bit, and restores the saved control value. They are called only from FUN_08049400. Their precise register semantics are limited by unresolved literals; their role (bracket the EEPROM write) is clear from position.

FUN_080494DC(block, expected_ptr) — verify one block. Reads the block back with FUN_08049350 into a 4-short stack buffer and compares all four shorts against the caller's buffer. Returns 0 on match, 0x8000 on mismatch.

FUN_08049534(block, data_ptr) — write with retry. Loops at most 3 times: FUN_08049400 write; if that returns 0, FUN_080494DC verify; stops when verify returns 0. Returns the last status. This is the only "redundancy" in the write path.

Configuration helpers.

  • FUN_08049158(type) — EEPROM type select/identify. type == 4 and type == 0x40 install different globals and return 0; anything else returns 1. The loader calls it with 4 and branches on a zero result.
  • FUN_080491C8(kind, out_ptr) — descriptor select. For kind <= 3 it stores the kind, computes a table entry (kind * 4 + table), and writes the entry's pointer through out_ptr. High-level code always calls it with 2 before a read or write, refreshing the descriptor whose +4 (block-count limit) and +8 (address-bit count) fields the drivers consume.
  • FUN_080498B0(ptr, value, length) — memset (word-optimised byte fill). Used to zero RAM buffers; it never touches the EEPROM. (EEPROM "erase" does not exist as a separate operation: formatted blocks are overwritten with zeros by normal block writes.)

The remaining seed in the extract, FUN_08049648, is a signed division/modulo helper (with the trap stub FUN_08049644). It has no callers in the save cluster and no EEPROM references; it is a compiler/SDK arithmetic routine located near the driver, not part of the save path. It is listed here only to exclude it explicitly.

3.2 Serialization, deserialization & checksum routines

There is no separate serialization layer: the RAM struct is the serialized form, moved block-by-block.

  • Deserialization (load): FUN_08008D1C reads header block 0 (via FUN_08008C38) and profile blocks 1–4 (via FUN_08049350) directly into the RAM buffers. The driver-level bit reassembly performs the byte-order conversion.
  • Serialization (store): FUN_08008CA4 writes all five blocks from the RAM buffers; FUN_08008F74 writes a single 8-byte chunk (one block) from a RAM object. Both end at FUN_08049534 → FUN_08049400.
  • Checksum: FUN_0800931C (recompute-and-store on commit) and FUN_080093E4 (verify), detailed in Section 4. Neither touches the EEPROM; they operate on the RAM struct, and a separate flush persists the result.
  • Header check: FUN_08008C38 (Section 4.1).

3.3 High-level callers, chain by chain

For each caller: what triggers it, what it calls, and how it mutates the in-RAM save struct before any flush. Absolute RAM addresses are unresolvable (Section 1), so mutations are given as struct-relative offsets — that is the granularity the code proves.

(a) Boot loader — FUN_08008D1C (no static caller; state dispatch).

FUN_08008D1C
├─ FUN_080498B0(bufA, 0, 0x20) / FUN_080498B0(bufB, 0, 0x20)   ; zero two 32-byte buffers
├─ FUN_080491C8(2, &desc)                                       ; select EEPROM descriptor
├─ FUN_08049158(4)                                              ; select EEPROM 4K; bail to state 4/return 1 on failure
├─ FUN_08008C38() ─ FUN_08049350(0, header_buf) ─ FUN_080492D0   ; header verify
├─ if header OK:  loop block=1..4: FUN_08049350(block, struct + (block-1)*8)
├─ if header bad: FUN_08008CA4()                                ; reformat (chain c)
└─ FUN_0801E928()                                               ; validate/apply (chain e)

RAM mutations before flush: it creates the RAM image (zero, then fill from EEPROM). It does not modify profile semantics. Its failure branch is destructive by design: a bad header discards the profile and reformats.

(b) Header verifier — FUN_08008C38 (caller: FUN_08008D1C). Selects the descriptor (FUN_080491C8(2, …)), reads block 0 into a buffer, and compares its four shorts against a second buffer (the expected magic image, at an unresolved literal address). Returns 0 on match, 1 on first mismatch. It mutates no save data.

(c) Formatter / whole-profile writer — FUN_08008CA4 (caller: FUN_08008D1C).

FUN_08008CA4
├─ FUN_080491C8(2, &desc)
├─ FUN_08049534(0, header_buf)                                  ; write header block
└─ loop block=1..4: FUN_08049534(block, struct + (block-1)*8)   ; write profile blocks
    └─ FUN_08049400 → FUN_080492D0 / FUN_08049204 / FUN_0804928C
    └─ FUN_080494DC → FUN_08049350                              ; verify read-back

It writes whatever the RAM buffers currently hold. Reached from the loader right after the buffers were zeroed, it produces the formatted default: valid magic, all-zero profile, checksum byte 0x00 (the sum of an all-zero struct), which is exactly cap-00. It is the only whole-profile writer traced.

(d) Incremental single-block flusher — FUN_08008F74 (no static caller; state dispatch). Four flag-selected branches share one shape: select the descriptor, take the branch's byte index idx from its own variable, and write one block —

Branch (flag test order)EEPROM blockRAM source
1st (*_DAT_08008FD0 & idx)idx + 1base1 + idx*8
2ndidx + 5base2 + idx*8
3rdidx + 9base3 + idx*8
4thidx + 13base4 + idx*8

via FUN_08049534(block, ram). After the write it decrements one branch's index variable (or clears two state bytes when it reaches 0), and on a non-zero write result it zeroes two 32-byte RAM buffers with FUN_080498B0(..., 0, 0x20). The idx*8 chunking and the 8-byte block size mean each branch flushes successive 8-byte chunks of a larger RAM object; the block-1 group is the profile struct's group (the loader's 1..4 loop covers the same blocks). The other three groups (blocks 5–8, 9–12, 13–16) belong to RAM objects whose bases are unresolved literals and which hold no data in either sample. This function persists prior RAM mutations; the mutations themselves happen in the commit path (f) or in untraced gameplay code. Its exact per-frame/per-event trigger is not recoverable.

(e) Post-load validator/applier — FUN_0801E928 (caller: FUN_08008D1C, as func_).

FUN_0801E928
├─ base = FUN_080093DC()                                        ; profile struct base pointer
├─ empty16 = (u16@+10 == 0 && u16@+12 == 0 && u16@+14 == 0 && u16@+16 == 0)
├─ status = FUN_080093E4(0)                                     ; checksum/gate verify
├─ if status != 0 or empty16: install defaults 0x8000, 0x80, 0x20, 0x10
│  else: copy stored u16s @+10,+12,+14,+16 to their consumers
└─ byte @+0x15: zero → store 0 via one pointer; non-zero → store the byte via another

FUN_080093DC simply returns the struct base pointer (an unresolved literal value). FUN_0801E928 mutates consumers of the profile (output variables at unresolved addresses), not the profile or the EEPROM. It is the reader that makes a checksum failure observable as "defaults instead of stored values."

(f) Commit path — FUN_08046B90 → FUN_080074BC → FUN_0800931C.

FUN_08046B90 (menu/selection handler; no static caller) gates on the committed flag:

  • If its argument is 0, or FUN_08009424(0) — which returns the byte at struct +0x19 — is 0 (no committed profile), it runs a long menu sequence (display/sound/DMA housekeeping, none of it save-related) and calls FUN_080074BC().
  • Otherwise it calls FUN_08009434(0) — the byte at struct +0x17 — and stores the result as a byte variable. It does not re-commit.

FUN_080074BC (callers: FUN_08046B90 per the graph) performs animation/sound calls and, in its middle, calls func_0x0800931C(0). This call is invisible in the graph (Section 3.0) and was mapped by reading the body.

FUN_0800931C(0) is the only semantic mutator of the profile struct that was fully traced. Gated on a global state byte being 1, it:

  1. writes struct +0x17 from a global/table-derived byte (*(char *)(struct + 0x17) = (char)*(undefined4 *)(table + global_state) — the exact source value's meaning is unresolved),
  2. writes struct +0x19 = 1 (committed flag),
  3. recomputes the sum8 over struct bytes 0…0x1E and stores it at +0x1F,
  4. updates two state bytes (*puVar2 = *(u8)(index + table), *puVar4 = 3, *piVar1 = 3 in the decompiler's naming).

It does not write the EEPROM; persistence happens when a flusher (FUN_08008F74 group 1, or a later format) writes blocks 1–4. The transition cap-00 → cap-01 is precisely the EEPROM image of one execution of step 1–3 with the +0x17 value 2: RAM +0x17: 0→2, +0x19: 0→1, +0x1F: 0x00→0x03.

(g) Field readers — FUN_08009424 / FUN_08009434 (caller: FUN_08046B90). One-line getters: FUN_08009424(i) returns *(u8)(base + i*0x20 + 0x19); FUN_08009434(i) returns *(u8)(base + i*0x20 + 0x17). Only index 0 is ever passed in traced code — another indication of a single profile, not a slot array in use.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Header magic (block 0)

  • File bytes (both samples, identical): 07 06 05 04 03 02 01 00 at offsets 0x00–0x07.
  • RAM bytes (after the driver's reassembly): 00 01 02 03 04 05 06 07.
  • Proof in code: FUN_08008C38 reads block 0 with FUN_08049350(0, buf) and loops over four shorts, returning 1 on the first *(short *)(i*2 + expected) != *(short *)(i*2 + read_buf), else 0. FUN_08008CA4 writes block 0 from its header buffer at format time — so the pattern is both written by the game and required by the game. The expected buffer's address is an unresolved literal (_DAT_08008C8C); the magic bytes themselves are verified in the .sav files and in the writer/verifier structure, but they are not read from a named ROM constant in the workspace.
  • Confidence: CONFIRMED_VERIFIED (present and identical in both binaries; compared at boot; written at format). There is no ASCII magic and no SDK tag.

Note on interpretation: a descending file pattern 07…00 would be an odd hand-chosen magic. Its reversal — a plain ascending 00…07 sequence in RAM — is the natural reading and is corroborated by the independent checksum proof below. The four-short comparison in FUN_08008C38 is agnostic to this interpretation (it compares shorts in RAM order either way).

4.2 Checksum: sum8 over the RAM struct

Exact formula (from FUN_0800931C writer and FUN_080093E4 verifier, which are textually the same loop):

stored  = struct[0x1F]
computed = ( Σ struct[i]  for i = 0x00 .. 0x1E )  mod 256     # 31 bytes, signed-char accumulation
valid_checksum = (computed == stored)
  • Algorithm class: sum8 (additive, modulo 256). No seed, no final XOR/complement, no CRC, no multi-byte endianness — the accumulator is a single char.
  • Covered range: RAM struct bytes +0x00…+0x1E inclusive (the loop runs while uVar < 0x1F). The stored byte at +0x1F is not covered. In file terms the covered bytes are the whole of blocks 1–4 except the checksum byte itself, under the per-block reversal.
  • Stored at: RAM +0x1F, which is file offset 0x20 (the first byte of block 4 in file order, because RAM byte 31 is the first byte of its block in RAM order).
  • Writer: FUN_0800931C recomputes and stores it as the last step of a commit, after updating +0x17 and +0x19, so those new values are included in the sum.
  • Verifier: FUN_080093E4 recomputes the same sum but first applies a gate (Section 4.3).
  • Decompiled proof (paraphrased from ghidra/decompiled.c, FUN_0800931C):
iVar6 = (param_1 & 0xff) * 0x20 + STRUCT_BASE;
if (*GLOBAL_STATE == 1) {
    *(char *)(iVar6 + 0x17) = (char)*(undefined4 *)(TABLE + (int)GLOBAL_STATE_PTR);
    *(undefined1 *)(iVar6 + 0x19) = 1;
    cVar5 = 0; uVar7 = 0;

and FUN_080093E4 recomputes the identical sum, then returns 2 / 0 / 1 as described in Section 4.3.

4.3 The gate byte (+0x18) — an honesty note on "valid"

FUN_080093E4 does not return "valid" on a checksum match alone:

if (*(char *)(struct + 0x18) == '\0')   return 2;
else if (computed == struct[0x1F])      return 0;
else                                    return 1;

In both samples RAM +0x18 (file offset 0x27) is 0x00, so the verifier would return 2 for both — even for cap-01, whose arithmetic checksum matches. Additionally, FUN_0801E928 installs its defaults when the verifier returns non-zero or when all four u16 fields are zero; both samples have all-zero u16s, so defaults are installed for both samples on that second condition as well.

Consequences, stated without smoothing:

  • The checksum algorithm (formula, range, stored offset) is CONFIRMED_VERIFIED: it was derived from two independent decompiled functions and matches arithmetic on both real files.
  • The fully-valid state (return 0 with stored u16s actually consumed) was never observed in the corpus. Either RAM +0x18 is set by a later gameplay path not exercised by these early captures, or its setter is among the untraced dispatch paths. No writer that sets +0x18 non-zero was found.
  • Any fuzzing or tooling that "repairs" this save must set +0x18 as well as the checksum to reach the return 0 state (Section 6 gives the exact procedure).

Counter-test (why the reversal is proven, not assumed): computing the same sum8 directly on file-order bytes of blocks 1–4 for cap-01 gives 0x06 against a file-order stored byte of 0x00 at offset 0x27 — no match under any single-byte stored offset in blocks 1–4. Reversing each block gives stored 0x03 = 2 (at +0x17) + 1 (at +0x19), and simultaneously places the writer's known constant 1 exactly on the changed byte at file 0x26. Three independent constraints (checksum value, +0x19 == 1 constant, +0x17 writer/reader pair) are satisfied by the same transform; alternative transforms tried (full reversal, block-order reversal, per-u16 byte swap, u16-order reversal) satisfy none of them on cap-01. cap-00 is all-zero and matches trivially under every transform, so cap-01 is the discriminating sample.

Other checksums: none. No CRC, no second sum, no counter-based integrity was found in any traced function, and no other function in the save cluster computes over the struct bytes.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test below:

  • Work on a copy of cap-01-future-1.sav (the committed sample) unless stated. Keep an untouched copy for A/B comparison.
  • "Repair the checksum" always means, in RAM order: reverse each 8-byte file block of blocks 1–4, sum bytes 0…30 of the resulting 32-byte struct modulo 256, and write the result to file offset 0x20 (which is RAM +0x1F under the reversal). A helper that does exactly this:
def repair(data: bytearray) -> bytearray:
    struct = b''.join(bytes(data[b*8:(b+1)*8][::-1]) for b in range(1, 5))
    data[0x20] = sum(struct[:31]) & 0xff
    return data
  • To write a RAM-order value into the file, use file_off = 8 + (r & ~7) + (7 - (r & 7)) for RAM offset r.
  • There are no paired .ss save states in states/ for this cohort, so reloads are cold boots of the mutated .sav. Predictions are stated in terms of the traced code paths so that each outcome confirms or falsifies a specific claim. Where a prediction depends on the unproven "fully-valid" state, both branches are given.
  • The destructive test (header mutation) is listed last among the single-purpose tests and must only be run on a disposable copy.

Appendix B. Confidence vocabulary used

Appendix C. Known limitations of the evidence base

  1. Literal-pool data values (_DAT_*, iRam*, puRam*, uRam*) are unresolved throughout the trace-guided decompilation, so absolute RAM addresses, the expected-magic buffer address, the EEPROM descriptor contents, and the source table for the +0x17 value cannot be read from the workspace. Struct-relative addressing is used throughout and is fully supported by the code.
  2. The call graph and the decompiled text disagree where calls are written func_0x…; caller mapping relied on reading bodies. Function-pointer/jumptable dispatch (including whatever invokes FUN_08008D1C, FUN_08008F74, FUN_08046B90) is unrecovered, so trigger conditions for those functions are inferred.
  3. The corpus has two saves captured close together and no save states. Fields that only change later in gameplay (notably the +0x18 gate byte, the four u16s, and blocks 5–16) may have writers and meanings that this corpus cannot reveal; the fuzzing plan in Section 6 is designed to expose them.
