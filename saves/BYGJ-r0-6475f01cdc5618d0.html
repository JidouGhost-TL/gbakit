GBA Save Format Report — Yu-Gi-Oh! Duel Monsters GX - Mezase Duel King! (Japan) (BYGJ)

Clean-room analysis derived only from PACKET.md, saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/save_related_functions.c, and ghidra/callgraph.json in this workspace, plus standard GBA hardware addresses given in the packet. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: LOW (structural/architectural confidence is MEDIUM; integrity-algorithm and field-semantics confidence is LOW).

Proven by both code and .sav bytes (VERIFIED):

  • The cartridge save medium exercised by the traced code is byte-wide SRAM at 0x0E000000. The only traced SRAM flush call site passes that literal address: FUN_080e69bc calls func_0x080f1e1c(_DAT_080e69d8, 0xe000000, _DAT_080e69dc).
  • The on-disk image is exactly 32,768 bytes (SRAM 256K) in both samples. cap-00-future-0.sav is uniformly 0xFF (erased/blank). cap-01-future-1.sav is a populated image whose non-0xFF written region ends at 0x6187; bytes 0x6188..0x7FFF are an untouched 0xFF tail (7,800 bytes).
  • The ASCII byte sequence YUGIOHGX occurs exactly once in the populated save, at file offset 0x384E.
  • Two distinct 16-bit checksum-like accumulators exist in code (FUN_080e68bc, FUN_080e68f4), each with a validator (FUN_080e692c, FUN_080e6954) and an updater (FUN_080e697c, FUN_080e699c). The flush path updates checksum #2 immediately before writing SRAM.
  • An 8-byte compare (FUN_080e0eb8, length 8) and an 8-byte copy (FUN_080e0f10, 8 iterations) exist and are wired into the checksum-validate/update path.

Not proven / open (see §4 and §6):

  • The exact checksum seed, XOR constant, covered byte ranges, and stored offsets are not recoverable from the supplied decompilation: every relevant operand is an unresolved literal-pool symbol (_DAT_080e68e4, _DAT_080e68e8, _DAT_080e68ec, _DAT_080e68f0, _DAT_080e691c, _DAT_080e6920, _DAT_080e6924, _DAT_080e6928, and the base+offset pairs in the validators/updaters). The ROM itself is not in the workspace, so those literal values cannot be read.
  • Consequently no checksum was verified against a sample. All concrete candidate formulas tested in Python (plain sum16, XOR16, CRC-16/CCITT, CRC-32 over the plausible ranges, and the decompiled recurrence with seed 0 brute-forced over all 65,536 XOR constants for the deck-like region) failed to match any plausible stored value. This is reported as a negative result, not papered over.
  • Whether YUGIOHGX at 0x384E is a save magic or a deck/player name is unresolved. Its context (preceded by u16 0x001A, followed by a candidate checksum 0x6CFD, a count 40, and 40 u16 values in a card-ID-like range) looks at least as much like a named deck record as like a file header. It is not at offset 0, so it is not a conventional whole-file magic.
  • No backup/mirror slot, generation counter, or slot-selection rule was found. Only one written copy is evidenced.
  • Almost all gameplay field semantics are UNKNOWN. The field map in §5 is structural (offsets, strides, observed values), not semantic.

2. Physical Media, Slot Geometry & Redundancy

  • Media kind: SRAM, 32 KiB (SRAM 256K per packet; consistent with the 32,768-byte files and with the byte-copy SRAM driver in §3). No Flash command sequence (0x5555/0x2AAA), no EEPROM/DMA3 serial protocol, and no SDK save tag string was found in the traced functions. media.sdk_tags = [].
  • Fill/erased byte: 0xFF, proven by cap-00-future-0.sav (32,768/32,768 bytes 0xFF) and by the untouched tail of cap-01-future-1.sav.
  • Total image size: 32,768 bytes (0x0000..0x7FFF).
  • Written (active) span in the populated sample: 0x0000..0x6187 (24,968 bytes = 0x6188). Evidence: the largest 0xFF run is 0x6188..0x7FFF; byte 0x6187 is 0x00. The SRAM write length operand (_DAT_080e69dc) is unresolved, so 0x6188 is an inference from the byte pattern, confidence HYPOTHESIS for the exact length (the true length could be e.g. 0x6188, or a slightly larger rounded value whose trailing bytes happened to be written as 0x00 up to 0x6187 — but no, trailing written bytes beyond the data are 0x00 only inside 0x6000..0x6187; a write extending past 0x6188 with 0xFF source bytes is indistinguishable. The safe statement: at least 0x6188 bytes are written; 0x6188..0x7FFF carry no information in this sample).
  • Slots/copies: Exactly one slot is evidenced: offset 0, the region above. There is no second copy: the upper half (0x4000..0x7FFF) is not a mirror of the lower half (periodicity check: only 44.3% byte equality at lag 0x4000, explained by shared 0x00/0xFF dominance), and 0x6188..0x7FFF is erased. No duplicate header, no A/B ping-pong structure.
  • Generation/sequence counters: None identified. No monotonic counter field could be isolated with a single populated sample. Candidate small scalars at 0x6148 (0x7B), 0x617C (0x02D3), 0x6184 (0x063C) are uninterpreted (see §5).
  • Selection rule: Unknown / not applicable beyond "the single copy at SRAM offset 0 is read at boot". The boot-time validator (§3) gates the copy on an 8-byte compare plus checksum #1; failure presumably falls back to blank/default state (the packet's cold-reload probe reports reverted_to_blank_boot: false and save_preserved_on_load: true for the populated image, consistent with the populated image passing validation, but that probe is packet metadata, not something re-derived here).
  • Redundancy within the copy: Integrity redundancy only — two 16-bit checksums (§4) and the write-verify-retry loop in the SRAM writer (write, verify, up to 3 attempts, §3). No data redundancy.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM addresses (0x08xxxxxx) as labelled in ghidra/decompiled.c. Two systematic limitations of the supplied decompilation shape everything below and are stated once here:

  1. Unresolved literal pool. Every _DAT_080xxxxxx operand is a literal whose value Ghidra did not recover (the ROM binary is not in the workspace). RAM base addresses, struct offsets, checksum seeds/constants/lengths, and the SRAM write length are therefore unknown numbers, referred to below as "unresolved".
  2. Unrecovered jumptables. Most functions end in (*UNRECOVERED_JUMPTABLE)(...), i.e. the decompiler could not recover the tail jump/return target. Calls written as func_0x08... are direct calls the callgraph sometimes misses; ghidra/callgraph.json and the C text disagree in places (noted per function). Caller mapping below was done by (a) taking callers/callees from ghidra/callgraph.json, and (b) grepping ghidra/decompiled.c for every func_0xADDR / FUN_ADDR call site and attributing it to the enclosing // 080xxxxx function header. Method (b) found callers that the callgraph omits (e.g. all FUN_080e697c callers, since that call is spelled func_0x080e697c).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic / 8-byte signature

  • In the .sav: 59 55 47 49 4F 48 47 58 = ASCII YUGIOHGX at file offset 0x384E, exactly once in cap-01-future-1.sav, absent (all-0xFF) in cap-00-future-0.sav. Verified by Python re.finditer(rb'YUGIOHGX', data) → ['0x384e'].
  • In code: an 8-byte field is compared (FUN_080e0eb8(..., 8) in FUN_080e0ee0) and refreshed (FUN_080e0f10, 8-byte copy in both updaters). The length 8 matches the string length, and the wiring (compare at validation, copy before checksumming) is exactly the shape of a magic-signature mechanism. However, neither the reference string's bytes nor the field's RAM address is recoverable (unresolved literals; no ROM in workspace), so identity between the code's 8-byte field and the file's YUGIOHGX is CONFIRMED_STATIC as a mechanism and unverified as a byte identity.
  • Counter-hypothesis (must be stated): at 0x384E the string is flanked by u16 0x001A (before), u16 0x6CFD and u16 40 (after), then 40 u16 values in 117..1192 with a trailing 0 — a layout indistinguishable from a named 40-card deck record ("name, checksum?, count, cards"). If so, YUGIOHGX is a deck name, not a save magic, and the game's real magic (the code's 8-byte field) lives at some other, unidentified offset and was not spotted because a binary magic need not be ASCII. Both readings are carried through §5; the fuzzing plan (§6) discriminates them.

4.2 Checksum algorithm — what the code actually computes

Both checksum functions have the identical decompiled shape (FUN_080e68bc shown; FUN_080e68f4 differs only in literals):

uVar1 = _DAT_080e68e4;                                   // seed (unresolved)
for (puVar2 = _DAT_080e68e8;                             // start ptr (unresolved)
     puVar2 != (ushort *)((int)_DAT_080e68e8 + _DAT_080e68ec);  // byte length (unresolved)
     puVar2 = puVar2 + 1) {                              // u16 stride
  uVar1 = ((*puVar2 + uVar1) * 0x10000 ^ _DAT_080e68f0) >> 0x10;  // XOR const (unresolved)
}
return uVar1;

Algebra (32-bit unsigned arithmetic): let s_i = (u_i + w_i) mod 2^32. Then (s_i << 16) ^ C shifted right 16 gives u_{i+1} = (s_i mod 2^16) ^ (C >> 16). The low 16 bits of C are shifted out and irrelevant. So each checksum is exactly:

u[0]   = SEED                                   (only its low 16 bits ever matter)
u[i+1] = ((u[i] + w[i]) & 0xFFFF) ^ K           for each little-endian u16 w[i] in the region
result = u[n]                                    (16-bit)

where SEED = _DAT_080e68e4 & 0xFFFF type literals and K = _DAT_080e68f0 >> 16 are unknown (likewise start/length for both regions, and the stored-field offsets in FUN_080e692c/6954/697c/699c, all of the form *(u16 *)(_DAT_base + _DAT_off)). Special cases: if K = 0 this degenerates to plain sum16 of the region plus seed; the XOR-each-step form means for K ≠ 0 it is not a plain sum and cannot be reduced to one.

Storage/validation wiring (proven statically): updater FUN_080e697c stores checksum #1's result to base+off after refreshing the 8-byte field; FUN_080e699c does the same for #2; validators FUN_080e692c/FUN_080e6954 recompute and compare equality against the stored u16. The flush (FUN_080e69bc) validates #1, updates #2, then writes — so #2 is always fresh in the written image, while #1 is maintained incrementally by every mutator in §3.3. This two-checksum split suggests (HYPOTHESIS) two covered sub-regions (e.g. main progression data vs. a second block), refreshed by different code paths.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so every test below is specified as: mutate bytes in a copy of cap-01-future-1.sav, load in an emulator with the matching ROM, and observe (a) boot acceptance vs. blank-boot fallback (= FUN_080e0ee0 gate outcome), (b) title/menu state, (c) the in-RAM struct (watch EWRAM once the base is located by searching RAM for YUGIOHGX after load — that search itself is step 0 and also resolves the RAM base address for all other tests).

Checksum repair procedure (needed by most tests). The exact repair cannot be written until the checksum parameters are known — determining them is itself the first fuzzing goal:

  • Step A (locate stored checksums): flip one byte at a time in a data region (e.g. 0x100), boot, and let the game itself re-save (trigger any §3.3 mutator, e.g. via normal play, then save). Diff the re-saved image against the pre-mutation image: bytes that changed beyond the flipped byte and beyond normal gameplay drift are the stored-checksum fields (and the 8-byte field, if offset ≠ 0x384E). Repeat with a flip in a second, distant region (e.g. 0x5000) to separate checksum #1's field from #2's (the flush updates only #2, mutators update only #1 — a flip that is repaired after a mutator-triggered re-checksum but before any flush belongs to #1's coverage).
  • Step B (solve seed/K/ranges): with the stored offsets known, collect (region, stored) pairs from several self-repaired saves differing in a few known u16s. The recurrence u ← ((u + w) & 0xFFFF) ^ K can then be solved: brute K (65,536) × seed (65,536) is 2^32 in the worst case, but a single-word region perturbation gives K directly from the stored delta; verify the solved (SEED, K, start, length) by predicting the stored value on a validation save. Only then is "repair" = recompute both checksums with the solved parameters and patch the two stored u16s.
  • Step C (validation-gate probe): corrupt one byte without repair → prediction: FUN_080e0ee0 fails → game treats save as invalid (blank/new-game boot, packet probe style reverted_to_blank_boot: true). Corrupt + repair → prediction: save accepted and the corrupted field's effect (below) is observable. This pair is the counterfactual that proves the checksum model.
