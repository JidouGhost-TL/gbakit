All findings below are derived exclusively from the files in this workspace: saves/cap-00-future-0.sav, saves/cap-01-future-1.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and standard public GBA hardware specifications (EEPROM bus at 0x0D000000, DMA3 at 0x040000D4, the two-bit EEPROM READ(11)/WRITE(10) opcodes). 1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What is proven:

  • The EEPROM 4K physical transport (DMA3 serial bitstream read/write/verify/retry driver) is fully traced in decompiled code and matches the standard GBA EEPROM hardware protocol exactly. This part is CONFIRMED_STATIC (code-proven) and partially CONFIRMED_VERIFIED where the 0x0D000000 MMIO address and bit-serial framing are directly visible as literal constants in the decompilation.
  • The 512-byte .sav layout contains a repeated 8-byte constant pattern (00 22 44 55 as a fixed 4-byte tail, preceded by a mutable 4-byte field) at four fixed block offsets (0x00, 0x10, 0xA8, 0x140), plus an unwritten tail region (0x1D8–0x1FF, all 0xFF) and one all-zero spacer block (0x1D0–0x1D7). These spans are CONFIRMED_VERIFIED directly against both .sav samples.
  • A precise byte-for-byte diff between the two save snapshots isolates exactly 7 changed bytes, all confined to the first 12 bytes of the file (offsets 0x00–0x0B).

What remains open / unproven:

  • The high-level "pack game state into RAM struct → call EEPROM writer" function and any checksum/CRC routine are not present in the supplied ghidra/decompiled.c / ghidra/callgraph.json trace. The callgraph shows zero callers for the top-level write-with-retry function (FUN_0803fdec) and for the raw read primitive (FUN_0803fc34) anywhere in the 248-function decompiled set. This is a genuine gap in the evidence, not an assumption — it is called out explicitly rather than filled in with guesses.
  • No arithmetic checksum/CRC formula could be verified against the two .sav samples (see §4). The repeating 4-byte "magic" tail is confirmed invariant, but the leading 4 mutable bytes could not be mathematically tied to any other covered byte range using sum8/xor8/complement formulas across both samples — they are far more likely a sequence/generation counter pair than a checksum, but this is a HYPOTHESIS, not a verified fact.
  • With only 2 .sav samples and 0 paired .ss save states provided in states/, field semantics beyond "this byte range changed / did not change" cannot be confirmed to in-game meaning (no game-visible state was correlated).

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K, confirmed by file size (512 bytes = 64 blocks × 8 bytes), consistent with the GBA 4-Kbit EEPROM part accessed via a 6-bit block address over the serial EEPROM bus at 0x0D000000.
  • SDK save tag: none detected in the ROM (per packet metadata); no ASCII magic strings were found anywhere in either .sav file.
  • Active byte spans (from saves/hexdump_and_diffs.txt, confirmed independently with Python against both raw files):

  • Redundancy / slot interpretation (HYPOTHESIS, MEDIUM confidence): Blocks 0, 2, 21, 40 share an identical 8-byte pattern at the time of sample 0. Between sample 0 and sample 1, only block 0's leading 4 bytes change; blocks 2, 21, and 40 remain byte-identical to sample 0. This is the classic signature of a primary/backup mirrored-slot scheme: block 0 is the "live" copy that is rewritten on each save event, while blocks 2/21/40 are stale backup/mirror copies from an earlier write generation that had not yet been refreshed when sample 1 was captured. We cannot confirm the selection rule (e.g., "newest generation wins") because we only have 2 samples and no evidence of the backups ever being rewritten.
  • Generation/sequence counter (HYPOTHESIS, confirmed arithmetic relationship): The 16-bit little-endian field at offset 0x02 goes from 0xAABB (sample 0) to 0xA9BA (sample 1) — an exact decrease of 257 (0x0101), i.e. both the low byte (0xBB→0xBA) and high byte (0xAA→0xA9) independently decremented by exactly 1. This is consistent with two interleaved 8-bit counters/generation IDs, but the sample size (n=2) is too small to confirm direction, wraparound, or whether it is consumed as a 16-bit value at all.
  • "Dirty"/transaction flag (HYPOTHESIS): The 16-bit LE field at offset 0x00 goes from 0x0308 to 0x0000, i.e. cleared entirely rather than incremented/decremented — consistent with a "pending write" or "dirty" flag that is zeroed once a save transaction is confirmed committed, but unconfirmed against any decompiled logic (no serialization code was present in this trace to verify against).
  • Unused tail region: 0x1D8–0x1FF (last 5 of 64 blocks) are all 0xFF in both samples — i.e. never written since EEPROM erase. No slot or counter data lives there in either sample.

3. Save Writer, Reader & Caller-Chain Architecture

All functions below are from ghidra/decompiled.c / ghidra/save_related_functions.c. The callgraph in ghidra/callgraph.json was walked exhaustively (grep over all 248 entries' callees arrays) to find every caller of every save-related function; results are reported honestly, including the dead ends.

3.1 FUN_0803faf0 — Low-level DMA3 bit-serial I/O primitive

ghidra/decompiled.c:8142

void FUN_0803faf0(undefined4 param_1, undefined4 param_2, uint param_3)
  • Saves and clears an interrupt-enable-like flag at *_DAT_0803fb50 (disable, then restore on exit) — standard "disable IRQs around a DMA transfer" idiom.
  • Programs *_DAT_0803fb60 = param_1 (source), *_DAT_0803fb64 = param_2 (destination), *_DAT_0803fb68 = param_3 & 0xffff | 0x80000000 (bit-count | enable bit) — this three-register-write-then-poll-busy-bit shape is the canonical GBA DMA3 transfer pattern (REG_DMA3SAD/REG_DMA3DAD/REG_DMA3CNT, MMIO base 0x040000D4), confirmed structurally (CONFIRMED_STATIC) though the literal register addresses themselves are not resolved as numeric constants in this decompilation (the _DAT_* globals are symbolic pointers whose backing addresses are not shown), so the DMA3 MMIO identification is high-confidence inference from standard hardware idiom, not a byte-for-byte verified literal.
  • Busy-waits on bit 15 of the control word before returning.
  • Callers: FUN_0803fb70, FUN_0803fc34 (both direct, confirmed via ghidra/callgraph.json).

3.2 FUN_0803fb70 — EEPROM block READ (opcode 11)

ghidra/decompiled.c:8173, labeled [MMIO-SEED]

void FUN_0803fb70(uint param_1, int param_2)
  • param_1 = 6-bit block address (bounds-checked against *(ushort *)(*_DAT_0803fb88 + 4), the EEPROM block count).
  • Serializes the EEPROM READ opcode bits 1,1 followed by the address bits into a local 67-entry stack buffer (auStack_96), MSB-first.
  • Calls FUN_0803faf0(auStack_98, 0xd000000, bits+3) to clock the opcode+address out to the EEPROM serial bus at 0x0D000000 — this literal address is directly visible in the decompiled code (CONFIRMED_VERIFIED as the EEPROM MMIO port per standard GBA hardware spec).
  • Calls FUN_0803faf0(0xd000000, auStack_98, 0x44) to clock 68 bits in from the EEPROM bus (4 dummy bits + 64 data bits = one 8-byte block).
  • Unpacks the 64 received bits into 4×16-bit words written into the output buffer param_2 (big-endian bit order within each word, written from the high word down).
  • Callers: FUN_0803fd94 only (confirmed via callgraph).

3.3 FUN_0803fc34 — EEPROM block WRITE (opcode 10) + busy-poll

ghidra/decompiled.c:8247, labeled [MMIO-SEED]

void FUN_0803fc34(uint param_1, ushort *param_2, char param_3)
  • param_1 = block address, param_2 = pointer to 4×16-bit words (8 bytes) to write, param_3 = retry/blocking mode flag.
  • Serializes WRITE opcode bits 1,0, the 64 data bits from *param_2 (4 words consumed), and the address bits into a stack buffer.
  • Calls FUN_0803faf0(auStack_c4, 0xd000000, bits+0x43) to transmit the full write train (opcode + address + 64 data bits + stop bit) to 0x0D000000.
  • Then busy-polls bit 0 of uRam0d000000 (the EEPROM ready/ready-not-busy status bit) in a timed loop (using a tick source at *_DAT_0803fd20), retrying up to the caller-controlled bound, to wait out the EEPROM's internal write cycle — the standard "wait for EEPROM write-complete" pattern.
  • Callers: none found in the traced callgraph (confirmed by exhaustive grep over all 248 functions' callees lists). It is only reachable through FUN_0803fc20's wrapper (see below), and FUN_0803fc20 itself also has zero callers in this trace.

3.4 FUN_0803fc20 — blocking-write wrapper

ghidra/decompiled.c:8229

void FUN_0803fc20(undefined2 param_1, undefined4 param_2)
  • Trivial wrapper: FUN_0803fc34(param_1, param_2, 1) — always requests blocking/retry mode 1.
  • Callers: FUN_0803fdec only (confirmed via callgraph).

3.5 FUN_0803fd94 — WRITE verification (read-back compare)

ghidra/decompiled.c:8337

void FUN_0803fd94(ushort param_1, short *param_2)
  • Calls FUN_0803fb70(param_1, asStack_14) to read back the 8 bytes just written at block param_1 into a local stack buffer.
  • Compares the 4×16-bit words read back against the caller-supplied expected buffer param_2; returns 0 on an exact match, 0x8000 on the first mismatched word.
  • Callers: FUN_0803fdec only (confirmed via callgraph).

3.6 FUN_0803fdec — top-level WRITE-WITH-VERIFY-AND-RETRY

ghidra/decompiled.c:8375

void FUN_0803fdec(undefined2 param_1, undefined4 param_2, uint param_3)
  • Loops up to 3 times: calls FUN_0803fc20 (blocking EEPROM write of one 8-byte block); if that reports success, calls FUN_0803fd94 (read-back verify); if verify also succeeds, breaks out of the retry loop early.
  • This is the complete top-level "commit one 8-byte EEPROM block, verify it stuck, retry on failure" routine.
  • Callers: none found anywhere in the traced 248-function callgraph (confirmed by exhaustive grep). This is the deepest point reachable from the two [MMIO-SEED] functions supplied in ghidra/save_related_functions.c.

3.7 Caller-chain mapping method and honest gap

The method used: for every one of the 248 addresses as keys in ghidra/callgraph.json, its "callees" array was programmatically scanned for each of the six addresses above; any address whose "callees" list contained one of our targets was recorded as a caller. This is an exhaustive search over the supplied trace, not a sample.

Result: no function in the supplied decompilation calls FUN_0803fdec (top-level save-block committer) or FUN_0803fc34/FUN_0803fc20 (raw write) directly. Several of the low-level functions also contain /* WARNING: Could not recover jumptable */ / UNRECOVERED_JUMPTABLE comments at their tails — these functions return through an indirect jump table that Ghidra could not statically resolve, which is the most likely explanation for why their true callers (a higher-level "save game struct to EEPROM" routine, almost certainly built on a loop over 64 or fewer blocks, with the game's RAM save-state struct at some 0x02xxxxxx/0x03xxxxxx address as source) are invisible to this static/2-hop trace. No such higher-level serializer, no RAM save-struct address, and no checksum/CRC function were found anywhere in the 248-function ghidra/decompiled.c — confirmed by grepping the entire file for 0d000000, EEPROM, checksum, CRC, and crc, all of which return matches only inside the 6 functions already documented above.

This is reported as an open gap, not filled with a guess. Any field map below describing how the game populates the RAM buffer passed to these primitives is therefore necessarily a HYPOTHESIS derived only from the observed .sav byte deltas, never from code that actually proves it.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature (CONFIRMED_VERIFIED against both samples)

  • Bytes: 00 22 44 55
  • Offset within each 8-byte block: +4 to +7
  • Observed at absolute offsets: 0x0004, 0x0014, 0x00AC, 0x0144 (i.e., the trailing half of blocks 0, 2, 21, 40)
  • Invariant across both .sav samples at all four locations (verified below).
  • No decompiled code was found that writes or checks this literal constant (the serializer that would do so is in the unresolved-caller gap from §3.7), so its status is CONFIRMED_VERIFIED only at the byte level (it reliably appears, unchanged, at four fixed locations in actual save data) but NOT CONFIRMED_STATIC (no proof in code that this is read/written by the game as a dedicated magic check, as opposed to being incidental constant game data).

4.2 Checksum / integrity algorithm — NOT CONFIRMED (HYPOTHESIS: none proven; most likely absent or out of trace)

No checksum/CRC function exists anywhere in the supplied ghidra/decompiled.c (confirmed by exhaustive grep, §3.7). To be rigorous anyway, every single-byte and multi-byte sum8, xor8, one's-complement-sum8, and one's-complement-xor8 formula over every contiguous sub-range of the first 16 bytes (the only region that changes between samples) was brute-forced against every other byte position in that same 16-byte window, requiring the formula to hold in both .sav samples simultaneously (a true checksum must still match after the payload changes).

s0 = open('saves/cap-00-future-0.sav','rb').read()[0:16]
s1 = open('saves/cap-01-future-1.sav','rb').read()[0:16]

def sum8(b): return sum(b) & 0xff
def xor8(b):
    v = 0
    for x in b: v ^= x
    return v
formulas = {
    'sum8': sum8, 'xor8': xor8,
    'not_sum8': lambda b: (~sum(b)) & 0xff,
    'not_xor8': lambda b: (~xor8(b)) & 0xff,
}

real_matches = []
for start in range(16):
    for end in range(start + 1, 17):
        for name, fn in formulas.items():
            v0, v1 = fn(s0[start:end]), fn(s1[start:end])
            for pos in range(16):
                if start <= pos < end:
                    continue
                # reject trivial zero-matches-zero coincidences
                if v0 == 0 and v1 == 0:
                    continue
                if s0[pos] == v0 and s1[pos] == v1:
                    real_matches.append((name, start, end, pos))
print("non-trivial checksum candidates:", real_matches)

Output (actually run in this workspace):

non-trivial checksum candidates: []

Conclusion: no sum8/xor8/complement checksum formula over any contiguous byte range in the mutated region of either sample reproduces any other stored byte, once trivial all-zero coincidences are excluded. The field at offset 0x02 (16-bit LE) was initially suspected as sum(bytes[0x04:0x08]) because 0+0x22+0x44+0x55 = 0xBB = s0[2], but this is a false positive: the same sum is 0xBB in sample 1 too (bytes 0x04–0x08 are unchanged), while s1[2] = 0xBA, one less — so the relationship breaks under mutation and is coincidental, not a real checksum. This is called out explicitly rather than reported as a finding.

Honest confidence: UNKNOWN whether any checksum exists at all for this title's EEPROM format. Candidates not ruled out: a checksum computed over bytes outside the 16-byte window examined (impossible to test — the rest of the file is either constant backup copies or unwritten 0xFF/0x00 filler across both samples, so no further mutation evidence exists), or no checksum at all (plausible — some EEPROM-based titles rely purely on the write-verify-retry mechanism in §3.5/3.6 instead of a stored checksum).

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states were supplied in states/ for this release (states/ is empty per the packet). The following plan is written to be executed once such pre/post save-state pairs are captured, per the project's mandatory paired-.ss policy.

  1. Magic-tail dependency probe.
  • Mutation: flip one bit in the 00 22 44 55 tail at 0x0004–0x0007 (e.g. 0x0004: 0x00 → 0x01).
  • No checksum repair needed (none proven in §4.2).
  • Predicted effect if this is a real magic/validity check: save is rejected on load, game falls back to new-game/default state, or the block is treated as corrupt and a backup block (0x10, 0xA8, or 0x140) is used instead. Predicted effect if this is incidental constant data: no observable change.
  • Observable: compare post-boot RAM/VRAM screenshot and any in-RAM save-struct mirror at 0x02xxxxxx/0x03xxxxxx against an unmutated control load.
  1. Backup-slot selection probe.
  • Mutation: corrupt block 0 (0x0000–0x0007) only, leaving blocks 2/21/40 (0x10, 0xA8, 0x140) intact.
  • Predicted effect if the redundancy hypothesis (§2) is correct: game falls back to one of the intact mirror blocks and loads successfully with the older generation's data. If wrong: game treats the save as fully corrupt regardless of the mirrors.
  • This directly tests whether blocks 2/21/40 are genuine redundant backups or merely stale/unused leftover writes.
  1. Generation-counter probe.
  • Mutation: force the 16-bit LE field at 0x0002 to a value larger than its current value (e.g. 0xAABB → 0xFFFF) without touching any mirror block.
  • Predicted effect if this is a monotonic generation/sequence counter consumed by game logic: no visible break (counters are typically write-only bookkeeping) — a null result here would be informative on its own.
  • Predicted effect if this value participates in a not-yet-identified checksum formula, contradicting §4.2's "none found" conclusion: save is rejected/reset on load. This probe is specifically designed to falsify the "no checksum" conclusion from §4.2.
  1. Dirty-flag clear probe.
  • Mutation: set 0x0000–0x0001 back to the "dirty" value 0x0308 observed in sample 0, on an otherwise-current save.
  • Predicted effect if this is a pending-transaction flag: game may attempt a self-repair/re-verify pass on next boot, or silently ignore it (write-once flag, never read). A measurable boot-time delta (extra frames before the title screen settles) would support the "self-repair pass" sub-hypothesis.
  1. Counter-increment field probe (0x0009, 0x000A–0x000B).
  • Mutation: independently toggle each of 0x0009 (±1), 0x000A, 0x000B (clear the 0x80 bit) and reload.
  • Predicted effect: if these are UI-visible counters (e.g., a save count, continue count, or settings flags), a corresponding in-game display (continue screen, options menu) should visibly differ from an unmutated control load of the same base save. Matched-duration A/B comparison against a control load is required to rule out frame-timing noise.

All five probes should be run as matched-duration, fresh-vs-restore pairs: one control load (unmutated .sav) and one mutated load, from the same frame-accurate starting .ss state, with before/after screenshots and a RAM diff of the save-struct mirror region once its RAM address is identified. Until the higher-level serializer/checksum caller (§3.7 gap) is located — e.g. by re-running the trace with the jump-table targets resolved, or by seeding the trace from the EEPROM MMIO write-back address directly — all five predictions above remain falsifiable hypotheses, not accepted semantics, per project policy.
