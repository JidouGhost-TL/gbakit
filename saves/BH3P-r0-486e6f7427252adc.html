  • ROM SHA-256: 486e6f7427252adc53d0506578c6607c0f3156496cb4f38b437540299753ae50

  • Method: Clean-room analysis strictly from saves/*.sav, ghidra/decompiled.c (237 functions), ghidra/callgraph.json, ghidra/save_related_functions.c, and standard GBA hardware specifications. No third-party game-specific sources were used.

1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

Proven (verified by both decompiled code AND .sav bytes)

  • The save medium is EEPROM, 512 bytes total (EEPROM 4Kbit), accessed in 8-byte blocks through a serial DMA3 bitstream driver. Only the first 0x138 (312) bytes are used; the remaining 200 bytes (0x138–0x1FF) are erased 0xFF and are never read or written by any traced code path.
  • The used region is a single linear structure: a 0x78-byte global header at offset 0x00, followed by three independent 0x40-byte slots at offsets 0x78, 0xB8, and 0xF8. There is no backup copy, no mirroring, and no generation/sequence counter used for slot selection.
  • The integrity algorithm is an additive sum16 checksum (FUN_080193b4 at 0x080193b4): each byte is zero-extended to ushort and accumulated into a 16-bit short. Four instances exist and all four verify numerically on both sample saves:
  • Three per-slot checksums stored big-endian at header offsets 0x00, 0x02, 0x04.
  • One header checksum stored big-endian at header offset 0x06, covering header bytes 0x00–0x77 with its own two bytes treated as zero.
  • The 4-byte ASCII magic 1M2A (31 4D 32 41) sits at file offset 0x6C in both saves. A 4-byte signature field is compared byte-by-byte on load (FUN_08019364, 0x08019364) and copied into the struct on factory reset (FUN_08019420, 0x08019420).
  • The full boot/load/validate/reset/flush architecture was traced (Section 3), including the low-level EEPROM DMA driver (0x08037274, 0x080372f4, 0x080373c8, 0x08037558), the block I/O wrappers (0x08021fb4 read, 0x080220c0 write), and the EWRAM heap allocator used for staging buffers (0x0801f474 / 0x0801f550).
  • The pack-provided cold-reload probe independently confirms the integrity design: mutating offset 0x7 (the low byte of the stored header checksum) caused the save to be rejected and rewritten — exactly what FUN_080192c8 + FUN_08019364 + FUN_08019420 predict.

Static-only (proven in code, not directly observable in the two samples)

  • Slot-internal initialization writes (slot index byte, two default u32 copies, cleared sub-regions in FUN_080190d4 / FUN_08019078), most of which are subsequently erased by a memset in the reset path, leaving the near-empty slot images seen in the samples.
  • The header-only flush entry point FUN_080192a0 has no caller in callgraph.json and no textual caller in decompiled.c; it is presumably reached through an unrecovered indirect/tail jump.
  • EEPROM configuration selection via FUN_08021fa4 → FUN_0803722c(4).

Hypotheses / unknowns

  • The semantics of almost all payload bytes. Both samples are near-blank (factory-reset) images: every slot contains exactly one non-zero byte (0x20 marker), and the header contains exactly one gameplay-variable byte (offset 0x68, 0x00 → 0xAB between captures). No progressed save exists in the corpus, so field meanings beyond structure cannot be confirmed.
  • The gameplay caller(s) that mutate the in-RAM struct during play and trigger a flush were not found: the only EEPROM write call sites in the entire decompilation are the header flush (FUN_080192a0) and the factory-reset flush (FUN_08019420). Either slot writes reuse the header-flush path after in-RAM slot edits plus an untraced write, or the relevant call is hidden behind an unrecovered jumptable.
  • Exact RAM mirror addresses are not recoverable from the supplied files: decompiled.c references all save globals through _DAT_080xxxxx literal-pool symbols whose values are not included. Only the EWRAM heap base (0x02000000, visible in the allocator) is known.
  • Several code-side byte offsets diverge from file offsets by small amounts (signature field: code +0x68 vs. file +0x6C; flag bytes: code +0x70/+0x71 vs. file +0x76/+0x77; slot marker: code +0x19 vs. file +0x1E; header-checksum store: code struct offset +0 vs. file +0x06). No single constant shift explains all of them, so each function's _DAT_ base most likely points at a different sub-struct, and/or the EEPROM bitstream staging permutes bytes within 8-byte blocks. File offsets in this report are the ground truth (verified against checksums); code offsets are quoted as-is and flagged where they diverge.

Geometry proof from code: FUN_08019420 memsets a 0x78-byte header, then loops uVar3 = 0..2 over slot pointers computed as uVar3 * 0x40 + slot_base, calling the slot initializer FUN_080190d4 and the slot-checksum storer FUN_080193e0 for each, then flushes 0x138 bytes total (0x78 + 3 × 0x40 = 0x138). Redundancy, counters, selection rule

  • Copies: exactly one. There is no primary/backup pair, no mirrored header, and no A/B generation scheme anywhere in the traced code or the byte layout.
  • Generation/sequence counters: none found. No field increments by one between the two captures; the only changed data byte (0x68) moved 0x00 → 0xAB (+171), which is also exactly the header-checksum delta, i.e. it is payload, not a counter maintained by the save layer.
  • Selection rule: none. All three slots are always loaded, always validated, and (on reset) always re-initialized together. Slot validity is per-slot (own checksum), but a single invalid slot — or a bad header signature/checksum — triggers a full factory reset of everything in FUN_080192c8; there is no per-slot fallback to a backup.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM addresses (0x08xxxxxx). "How mapped" describes the evidence used: direct call in decompiled.c text, callgraph.json edge, size/offset constants, or .sav byte verification. Note that decompiled.c contains many UNRECOVERED_JUMPTABLE tail-calls, so callgraph.json (direct calls only) under-reports edges; textual references in decompiled.c were used to complete the chains, and every discrepancy is noted.

3.1 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3)

FUN_08037274 (0x08037274) — DMA3 transfer primitive

  • Saves/restores an interrupt-enable global, programs three globals with param_1 (source), param_2 (destination), and param_3 & 0xFFFF | 0x80000000 (count with DMA-enable bit), then spins while the control register's 0x8000 busy bit is set. This is the classic GBA DMA3 register block at 0x040000D4 (SAD/DAD/CNT); the literal-pool values are not in the supplied files, so the MMIO addresses themselves are identified by register semantics, not by a printed constant.
  • Callers: FUN_080372f4, FUN_080373c8 (textual). Callees: none.

FUN_080372f4 (0x080372f4) — EEPROM read one 8-byte block

  • Signature: (block_index, dst). Rejects block_index ≥ *(ushort*)(eeprom_info + 4) (block count; 64 for a 512-byte device).
  • Builds the read command bitstream on the stack: start bits plus the block address, one bit per ushort, LSB-first into descending stack slots, using the address-bit width from *(byte*)(eeprom_info + 8).
  • DMAs the command out (FUN_08037274(..., addr_bits + 3)), DMAs the response back (FUN_08037274(..., 0x44) halfwords), then unpacks 64 data bits MSB-first (uVar5 = uVar5 << 1 | bit) into four ushorts stored descending from dst + 6. This descending/bit-reversed unpacking is the likely source of the small code↔file offset divergences noted in Section 1.
  • Callers: FUN_08021fb4 (read path), FUN_08037558 (verify path). Callees: FUN_08037274.

FUN_080373c8 (0x080373c8) — EEPROM write one 8-byte block (via wrapper FUN_080373b4, 0x080373b4)

  • Packs four source ushorts bit-by-bit (descending stack slots), appends the block address bits and start/stop bits, DMAs the bitstream out with length addr_bits + 0x43, then polls the EEPROM/DMA status with a bounded wait (accumulated timeout 0x88) to detect write completion.
  • Callers: FUN_080373b4 ← FUN_080220c0. Callees: FUN_08037274.

FUN_08037558 (0x08037558) — EEPROM verify one block

  • Re-reads the block into a stack buffer via FUN_080372f4 and compares four ushorts against the expected buffer; returns 0 on match, 0x8000 on mismatch.
  • Callers: FUN_08021fb4 (post-read verify), FUN_080220c0 (post-write verify). This read-back-verify is why both I/O wrappers loop over every block twice.

FUN_0803722c (0x0803722c) + FUN_08021fa4 (0x08021fa4) — EEPROM type/size select

  • FUN_08021fa4 calls FUN_0803722c(4); FUN_0803722c selects among three configuration structs by argument (4, 0x40, other), i.e. it installs the EEPROM geometry (block count + address-bit width) used by the read/write drivers. Called once at the start of the load path (FUN_080192c8).

3.2 Block I/O wrappers (staged through the EWRAM heap)

FUN_0801f474 (0x0801f474) / FUN_0801f550 (0x0801f550) — EWRAM heap alloc/free

  • Not save-specific: a first-fit allocator over EWRAM (pointers encoded as (addr − 0x02000000) / 4, explicit + 0x2000000 rebasing). Nine/ten other game functions also call them. The save wrappers use them to stage EEPROM transfers in RAM before byte-copying to/from the save struct.

FUN_08021fb4 (0x08021fb4) — EEPROM read N bytes

  • Signature: (dst, length). Converts length to blocks (length >> 3), traps in an infinite loop if the request exceeds the device block count, disables a DMA/interrupt resource, allocates length + 7 bytes, reads every block with FUN_080372f4, re-verifies every block with FUN_08037558, then byte-copies the staging buffer to dst and frees it. Returns 0 on success.
  • Callers: FUN_080192c8 only (with length = 0x138). Callees: FUN_0801f474, FUN_0801f550, FUN_080372f4, FUN_08037558.

FUN_080220c0 (0x080220c0) — EEPROM write N bytes at an offset

  • Signature: (src, start_offset, length). Converts start/length to block indices (>> 3), allocates and zeroes a staging buffer, byte-copies src in, writes every block with FUN_080373b4 → FUN_080373c8, re-verifies every block with FUN_08037558, frees the buffer. Returns 0 on success.
  • Callers: FUN_080192a0 (header only: offset 0, length 0x78), FUN_08019420 (full image: offset 0, length 0x138). These are the only two EEPROM-write call sites in the whole decompilation (verified by textual search for 080220c0).

3.3 Serialization, checksum, validation & (re)initialization

FUN_080193b4 (0x080193b4) — the checksum primitive (sum16)

short FUN_080193b4(int param_1, uint param_2) {
  short sVar1 = 0; uint uVar2 = 0;
  if ((param_2 & 0xffff) != 0) {
    do {
      sVar1 = sVar1 + (ushort)*(byte *)(param_1 + uVar2);
      uVar2 = uVar2 + 1 & 0xffff;
    } while (uVar2 < (param_2 & 0xffff));
  }
  return sVar1;
}

Plain additive sum of bytes, each zero-extended, accumulated modulo 2^16. No seed, no complement, no final XOR. Callers: FUN_080193e0, FUN_08019404, FUN_08019364, FUN_080192c8.

FUN_08019404 (0x08019404) — recompute & store header checksum

  • Zeroes the stored header-checksum ushort, computes FUN_080193b4(base, 0x78), stores the result back. In file coordinates the stored field is at +0x06 and the covered range is 0x00–0x77 (verified numerically, Section 4); the decompiled pointer is a single _DAT_0801941c base, so the code-side struct offset reads as +0 — see the offset-divergence note in Section 1.
  • Callers: FUN_080192a0, FUN_08019420.

FUN_080193e0 (0x080193e0) — recompute & store one slot checksum

  • Computes FUN_080193b4(slot_ptr, 0x40) and stores it into the header checksum table at (slot_index & 0xFF) * 2 + table_base + 2. In file coordinates the three entries sit at +0x00, +0x02, +0x04 (verified numerically), so the table base used at runtime is two bytes before the header-checksum field's frame; the supplied literal values would be needed to pin the exact RAM expression.
  • Callers: FUN_08019420 only.

FUN_08019364 (0x08019364) — validate header signature + header checksum

  • Compares four bytes at struct offset +0x68 (file: the 1M2A magic at +0x6C; see divergence note) byte-by-byte against a second buffer (_DAT_080193b0, presumably a ROM-resident copy of the signature), setting a failure flag on any mismatch.
  • Then reads the stored header checksum, zeroes it in place, recomputes FUN_080193b4(base, 0x78), and flags failure if different. Returns the flag (1 = invalid) through the tail-jump.
  • Callers: FUN_080192c8 only.

FUN_080192c8 (0x080192c8) — load & validate (the reader entry point)

  • Flow: FUN_08021fa4() (EEPROM config select) → if OK, FUN_08021fb4(save_base, 0x138) (read full used image) → if OK, FUN_08019364() (signature + header checksum) → on failure, FUN_08019420() (factory reset + flush). Then, regardless, it validates each slot: checksum(slot_ptr, 0x3C) compared against the stored ushort table entry (stepping psVar4 one short per slot from the header base, psVar3 by 0x20 shorts = 0x40 bytes per slot from base + 0x78). Any slot mismatch → FUN_08019420() and stop. Any EEPROM read failure → FUN_08019420().
  • Note the length discrepancy: write-side slot checksums are computed over 0x40 bytes (FUN_080193e0) but load-side validation sums only 0x3C bytes. Bytes +0x3C–+0x3F of each slot are therefore covered when stored but not when checked (both sample slots have zeros there, so the samples cannot distinguish the two lengths).
  • Callers: FUN_0801909c only (textual + callgraph). Callees: FUN_08021fa4, FUN_08021fb4, FUN_08019364, FUN_080193b4, FUN_08019420.

FUN_08019420 (0x08019420) — factory reset & full flush (the destructive writer)

  • Memsets the header (0x78 bytes) to zero; copies 4 bytes from _DAT_08019494 into the signature field (code offset +0x68, file +0x6C 1M2A); stores 0xFF into two flag bytes (code +0x70/+0x71, file +0x76/+0x77).
  • For each slot 0..2: memsets the 0x40-byte slot, calls FUN_080190d4(slot, index) (slot initializer), then FUN_080193e0(index, slot) (store slot checksum).
  • Calls FUN_08019404() (store header checksum), then flushes the entire used image: FUN_080220c0(struct_base, 0, 0x138).
  • Callers: FUN_080192c8 only (three sites: EEPROM-read failure, header validation failure, slot validation failure). This is the function that produces blank saves exactly like the two samples — and it is what the pack's mutation probe observed ("reverted to blank", "save rewritten after mutation").

FUN_080192a0 (0x080192a0) — header-only flush

  • FUN_08019404() (refresh header checksum) then FUN_080220c0(header_base, 0, 0x78); returns success == 0 through the tail-jump.
  • Callers: none in callgraph.json, none textual in decompiled.c. How mapped: identified by its body (checksum + 0x78-byte write at offset 0). Its real caller is hidden behind an unrecovered indirect/tail jump; it is the only plausible "settings/global data changed" save path, since it rewrites exactly the header (which contains the slot-checksum table, the mutable byte at 0x68, and the flag bytes) without touching slot blocks.

FUN_080190d4 (0x080190d4) + FUN_08019078 (0x08019078) — slot (re)initializers

  • FUN_080190d4(slot_ptr, slot_index) writes: slot-index byte at code offset +0x18 (*(byte*)((undefined4*)slot + 6)), zeroes the first u32, copies two default u32s from a table (+0x28/+0x2C of _DAT_08019118) into slot offsets +12/+16, memsets slot bytes +28..+59 (param_1 + 7, 0x20 bytes), memsets two unrelated globals (0x70 and 0x20 bytes), then delegates to FUN_08019078.
  • FUN_08019078(slot_ptr) memsets the first 0x3C slot bytes to zero — erasing the index byte and default copies just written — then stores the marker byte 0x20 at code offset +0x19 (file: slot +0x1E, the only non-zero byte in every sample slot), and memsets another 0x20-byte global.
  • Net effect in the reset path: each slot ends as all-zero except the 0x20 marker, matching both samples byte-for-byte. The pre-erase writes in FUN_080190d4 only make sense if FUN_080190d4 is also called from gameplay code with a live slot (where FUN_08019078's memset would be destructive — so more likely FUN_08019078 operates on a sub-struct, or the reset path intentionally reuses a "clear sub-record" helper). No other caller of either function exists in the decompilation besides FUN_08019420, FUN_0801909c, and each other.
  • Callers: FUN_080190d4 ← FUN_08019420, FUN_0801909c; FUN_08019078 ← FUN_080190d4.

FUN_0801909c (0x0801909c) — boot-time save bootstrap

  • Calls FUN_080190d4(working_slot, 0) (initialize a standalone working slot struct), then FUN_080192c8() (load & validate the real save), then copies the two header flag bytes (code offsets +0x70/+0x71, file +0x76/+0x77, both 0xFF in the samples) into two one-byte globals (_DAT_080190c8, _DAT_080190d0) — i.e. two global settings are restored from the header at boot.
  • Callers: FUN_08024c60 (textual + callgraph). Callees: FUN_080190d4, FUN_080192c8.

FUN_08024c60 (0x08024c60) — main initialization (top traced caller)

  • A long boot sequence (display, heap init FUN_0801f5f4, sound, input, etc.) that calls FUN_0801909c() roughly two-thirds through, after which the game proper starts. This is the root of every save-read chain found.

3.4 Complete caller chains

  1. Boot / load: FUN_08024c60 → FUN_0801909c → FUN_080192c8 → FUN_08021fa4 → FUN_0803722c(4); → FUN_08021fb4(base, 0x138) → FUN_080372f4 (per block) → FUN_08037274 (DMA3), FUN_08037558 (verify) → FUN_080372f4; → FUN_08019364 → FUN_080193b4; → per-slot FUN_080193b4. On any failure → chain 2.
  2. Factory reset / blank-save creation: FUN_080192c8 → FUN_08019420 → FUN_080190d4 → FUN_08019078; → FUN_080193e0 → FUN_080193b4; → FUN_08019404 → FUN_080193b4; → FUN_080220c0(base, 0, 0x138) → FUN_080373b4 → FUN_080373c8 → FUN_08037274, FUN_08037558 → FUN_080372f4.
  3. Header flush (settings/global save): (caller unrecovered) → FUN_080192a0 → FUN_08019404 → FUN_080193b4; → FUN_080220c0(base, 0, 0x78) → write/verify chain as in chain 2.
  4. Boot settings restore: FUN_0801909c (after chain 1) copies header flag bytes +0x76/+0x77 (file offsets) into two global bytes. No flush follows; it is a pure reader-side mutation of RAM globals.

4.2 Checksum algorithm (exact)

  • Primitive: FUN_080193b4 (0x080193b4) — sum16: acc = (acc + (ushort)byte) mod 2^16 over each byte in order. No seed, no complement, no XOR-out, no reflection. Equivalent Python: sum(data) & 0xFFFF.
  • Byte order of stored values: big-endian in the file (stored byte pair = [sum >> 8, sum & 0xFF]). The RAM-side stores are native ushort stores; the byte swap is attributed to the EEPROM serial serialization (bits are packed/unpacked MSB-first per ushort in FUN_080372f4/FUN_080373c8). This attribution is static inference; the file-level big-endian fact is verified on all 8 checksum instances (4 per file × 2 files).
  • Instances:

  • Probe corroboration: the pack's mutation probe flipped offset 0x7 — the low byte of the stored header checksum — and observed rejection + blank rewrite, matching this algorithm and validation order exactly.

        print(f" slot{i} cksum stored@0x{i*2:02x} BE=0x{st:04x} sum40=0x{sum(blk)&0xFFFF:04x} sum3c=0x{sum(blk[:0x3c])&0xFFFF:04x}")
    print(f" byte@0x68=0x{d[0x68]:02x} flags@0x76..77={d[0x76]:02x} {d[0x77]:02x} tail_all_ff={all(b==0xFF for b in d[0x138:])}")

Cross-check: the only data difference between the files is byte 0x68 (0x00→0xAB, Δ +171), and the header checksum moves 0x034F→0x03FA (Δ +171) — the exact behavior of an additive sum covering that byte. Slot sums cannot distinguish the 0x40 (write-side) from the 0x3C (load-side) covered length because slot bytes +0x3C–+0x3F are zero in both samples (see Section 6, target F5, for the discriminating test).

Checksum repair recipe (for fuzzing): after mutating any header byte, recompute sum16(header[0x00..0x78]) with bytes 0x06–0x07 zeroed and store big-endian at 0x06. After mutating any slot byte, first recompute that slot's sum16 and store big-endian at header 0x00/0x02/0x04, then recompute the header checksum as above (it covers the table).

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for every target below (except F6): after the mutation, repair checksums in this order — (1) if a slot byte changed, store BE16(sum16(slot_block)) at the slot's header entry (0x00/0x02/0x04); (2) store BE16(sum16(header[0x00..0x78] with bytes 0x06–0x07 zeroed)) at 0x06. Without repair, the prediction for every target inside 0x00–0x137 is identical and already probe-confirmed: load validation fails in FUN_080192c8 and the game factory-resets and rewrites a blank save (observable: save file returns to the cap-00-like blank image, boot behaves as first-run). Predictions below assume repair is applied, so they isolate the field's own effect. No paired .ss save states exist in this workspace (states/ is empty), so each test is: patch .sav → cold-boot the ROM with the patched save → compare boot/UI/RAM behavior against the unpatched blank save.
