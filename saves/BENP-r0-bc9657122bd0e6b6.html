1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM, 8192 bytes total, accessed only through the serial EEPROM driver at 0x0D000000 via DMA3. Geometry is exactly: one 16-byte global header at 0x0000, then 3 slots of 0xAA0 (2720) bytes at 0x0010, 0x0AB0, 0x1550, then a 16-byte unused tail at 0x1FF0 (16 + 3*2720 + 16 = 8192).
  • Global-header magic is the 8 ASCII bytes 4100ABGE at offset 0x00, compared byte-by-byte in FUN_0803ade8.
  • Global-header integrity is a 16-bit additive checksum: the eight file-order big-endian u16 words at 0x00..0x0F sum to 0x0000 in both samples, and the last word (0x0E, file bytes 07 0A) equals the negated sum of the first seven. In code this is FUN_0803ad80 (sum of u16s) with the checksum word stamped as -sum at RAM offset +0xE by FUN_0803ada4/FUN_0803a8b0 (see §4 for the file-vs-RAM byte-order caveat).
  • The EEPROM driver chain, block read/write layer, global-header flush path (settings menu → FUN_0802cd7c → FUN_0803a8b0), and the boot/load path (FUN_0803a91c → per-slot load + checksum-validate) are fully traced in code (§3).
  • Both samples contain no valid game slot: every slot's u16 sum over its 0xAA0 bytes is 0xFAB8 ≠ 0, only each slot's first 16 bytes are non-0xFF (all zero), and the rest is erased 0xFF. The captures show an initialized-but-empty save: global header written, slot headers cleared, no progress data.

Static-only (CONFIRMED_STATIC, code seen, not exercised in samples): slot checksum validation over the full 0xAA0 (FUN_0803acf8), write-verify-retry behaviour, EEPROM presence/type detection, the settings byte pack at global offsets 0x08..0x0D.

Open / unknown: the in-game slot writer and slot checksum stamper (no function in the 337-function corpus writes a full 0xAA0 slot or stamps a slot checksum — only the validator exists); all slot payload field semantics (samples are empty); absolute RAM base addresses; the semantic names of the global settings bytes; why byte 0x0B is 0 in both samples although the only traced global writer sets RAM +0xB = 1 (so that writer demonstrably did not produce these samples, or had not run).

Redundancy & selection:

  • No mirroring, no backup copy of the global header, and no duplicate slot copies. Integrity relies on the additive checksum plus write-verify-retry (§3), not on redundancy.
  • No generation/sequence counter was found in code or samples. The two bytes that changed between samples (0x08, 0x0C) are settings-pack bytes (§5), not a generation counter; their changes cancel in the checksum by arithmetic (-1 and +1 in file-byte terms), which is coincidence, not a designed counter/checksum pair.
  • Slot selection rule (from FUN_0803ac9c + FUN_0803acf8): at load, each slot is read in full and its u16 sum over 0xAA0 bytes is computed; SaveMgr + 0x44 + slot_index is set to sum == 0. A slot is selectable/valid iff that flag is true. An all-zero slot would (vacuously) pass; the samples' slots fail because unwritten 0xFF bytes make the sum 0xFAB8.
  • Global selection rule (from FUN_0803ade8): return 2 if the first 8 bytes ≠ 4100ABGE, 1 if magic matches but the 16-byte u16 sum ≠ 0, 0 if valid. On 2, FUN_0803a91c rewrites the default global header and zeroes the first 16 bytes of every slot. On 1 (in FUN_0803a91c's condition (iVar2 != 0) && (FUN_0803ada4(), iVar2 == 2)), the default header is also rewritten via FUN_0803ada4 before the == 2 test, but slots are not cleared.

3.3 Checksum primitive

0x0803ad80 (FUN_0803ad80(short *p, uint byte_len)): sVar1 = 0; for (i = byte_len >> 1; i > 0; i--) sVar1 += *p++; — a plain u16 (signed-short, modulo-2¹⁶ identical) sum over byte_len/2 words, returned as the function's result through the unrecovered jumptable. It is the only checksum-shaped routine in the corpus: no CRC, XOR-fold, or byte-sum routine exists in any of the 337 functions (full-corpus loop search performed). Callers (func_ refs; callgraph shows none): 0x0803a8b0 (global, len 0x10), 0x0803acf8 (slot, len 0xAA0).

3.6 Caller chains (summary)

  1. Verified EEPROM write: 0x08008fe8 → 0x08045dd8 → {0x08045da0 → 0x08045ba8 → 0x08045a64 (DMA3 → 0x0D000000); 0x08045d08 → 0x08045ae4 → 0x08045a64}.
  2. EEPROM read: 0x08008f80 → 0x08045ae4 → 0x08045a64, bracketed by 0x08009054 (detect, via 0x08045a1c(0x40)) and 0x0800909c (restore).
  3. Global flush: 0x080371b8 (menu confirm) → 0x0802cd7c (pack settings into global[8..13]) → 0x0803a8b0 (stamp checksum at +0xE, compare, → 0x08008fe8 write / 0x08008f80 read), with 0x0803ad80 as the checksum core. Reverse direction: 0x0802cd48 (global → settings), caller untraced.
  4. Boot/load: 0x0803a91c → 0x0803ade8 (global validate) [→ 0x0803ada4 default-write; → 0x0803a990 + 0x08008fe8 slot-header clears] → 0x0803ac9c → per slot {0x0803ad28 load → 0x0803acf8 validate → 0x0802cfdc → 0x0803a9f8 read slot header into record}.
  5. In-game slot save: missing (see §3.5).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • File offset 0x00, 8 bytes: 34 31 30 30 41 42 47 45 = ASCII 4100ABGE. Present identically in both samples.
  • Verified in code: FUN_0803ade8 compares RAM bytes 0..7 against an 8-byte template (_DAT_0803ae30) and returns 2 on mismatch; FUN_0803ada4 copies a 16-byte default template (_DAT_0803ade4) whose first 8 bytes are that magic. The template bytes themselves are not in the workspace, so the code-side verification is CONFIRMED_STATIC for the comparison logic and CONFIRMED_VERIFIED for the byte value (code logic + .sav bytes agree on length, offset, and role).
  • No other magic/signature exists: full-corpus search found no other candidate (the only other 4100 hits are the unrelated address 0x08034100 in FUN_080340c0). No SDK tag (EEPROM_V… etc.) is present — packet §1 agrees.

Checksum algorithm (global header)

  • Code formula (FUN_0803ad80 + stampers FUN_0803ada4/FUN_0803a8b0): sum = Σ u16[i] for i = 0..7 over the 16-byte header (mod 2¹⁶); checksum word at offset 0x0E is stored as word[7] = -Σ word[0..6], so a valid header satisfies Σ word[0..7] == 0. FUN_0803ade8 validates exactly sum == 0. There is no seed, no complement beyond the two's-complement negation, no CRC.
  • Covered range: global header only, 0x00..0x0F, including the magic. Stored at 0x0E..0x0F, size 2.
  • Slot analogue (CONFIRMED_STATIC only): FUN_0803acf8 requires Σ u16 over the full 0xAA0-byte slot == 0. The stamped word's offset inside the slot is unknown (no writer in corpus); by analogy with the global header the last word (slot + 0xA9E) is the natural candidate — that is a HYPOTHESIS.

File-order byte-order caveat (important, stated plainly)

The code sums native (little-endian on GBA) RAM u16s. Applied naively to the .sav file as little-endian words, the samples fail: sum = 0x00FF, stored word 0x0A07 ≠ -sum(first 7) = 0x0908. Applied to the file as big-endian words, they pass exactly (below). The EEPROM pack/unpack code explains a per-word byte swap between RAM and the .sav representation: FUN_08045ba8 serializes each u16 bit-by-bit into a descending stack stream and FUN_08045ae4 rebuilds each u16 MSB-first into descending word slots, so the emulator-visible byte order of each 16-bit word is swapped relative to RAM. Byte-oriented fields (magic, settings bytes) are discussed at file offsets in §5; the one unresolved consequence is whether RAM byte +9 corresponds to file byte 0x08 or 0x09 for the two settings bytes packed in the word at 0x08 (see §5 notes).

  • Cold-reload probe (packet §1): mutating offset 0x8 did not revert the save to blank and did not trigger a rewrite, but produced a visual delta. That is consistent with this report: offset 0x8 is a settings data byte covered by the checksum — a mutated header should fail FUN_0803ade8 (return 1) unless the checksum is repaired… the probe reports integrity_check_confirmed: true yet reverted_to_blank_on_mutation: false. The likely reconciliation is that the mutated value was still loaded as data (the game may only rewrite the global header on the rc == 2 magic path / may tolerate rc == 1 in the traced condition — indeed FUN_0803a91c rewrites the header on any rc != 0 via FUN_0803ada4, which would restore defaults rather than blank the slots; "reverted to blank" was defined on the whole save, and slots were already empty). This probe nuance is not fully resolved by the corpus and is listed in the open questions.

Inter-sample diff (verified): exactly 2 bytes — 0x08: 0x0C → 0x0B (−1) and 0x0C: 0x00 → 0x01 (+1). Both lie inside the checksummed global header; the checksum word at 0x0E is unchanged because the two deltas cancel under either word grouping ((0x08,0x09) word −1 in LE terms / −0x100 in BE terms, exactly offset by the (0x0C,0x0D) word). No slot byte changed.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test: work on a copy of cap-00-future-0.sav; keep the other sample as control; reload from a paired save state / cold-boot the ROM with the mutated .sav; record (a) whether the .sav is rewritten on boot (compare hashes before/after), (b) title/menu behaviour, (c) if a debugger is available, the return of FUN_0803ade8 and the flags at SaveMgr +0x44..0x46. No paired .ss states exist in this workspace (states/ is empty), so predictions are stated for cold-reload; with a real save state they can be tested mid-session identically.

Checksum repair (needed wherever marked): after any mutation inside 0x00..0x0D, recompute the global checksum in file order — w7 = (-(w0+w1+w2+w3+w4+w5+w6)) & 0xFFFF with each wi read as big-endian u16 from the file — and write w7 big-endian at 0x0E. Python: import struct; g=bytearray(d[:16]); w=struct.unpack('>8H',g); g[14:16]=struct.pack('>H', (-sum(w[:7]))&0xFFFF). For slot tests, the stamper offset is unproven, so slot repair is itself the experiment (test the slot+0xA9E hypothesis first: zero the slot, write test payload, set the last word to the negated sum of the rest — in the same BE-file convention — and see if the slot is accepted).

Open questions

  1. Where is the in-game slot writer/serializer and slot checksum stamper? Not in the 337 traced functions (no 0xAA0-length FUN_08008fe8 call, no slot -sum store). Needed: a fuller decompilation or a runtime trace of a real save action.
  2. What are the slot payload fields (slot + 0x10 .. +0xA9D)? Both samples are empty (0xFF); a progressed save is required.
  3. Absolute EWRAM base of the save-manager struct and of the settings object (all _DAT_ literals unresolved in this corpus).
  4. Is the file↔RAM per-word byte swap real (§4), i.e. do RAM bytes +8/+9 map to file bytes 0x09/0x08? Fuzz tests #3/#4 settle it.
  5. Why is file byte 0x0B = 0 although 0x0802cd7c/0x0803a978 set RAM +0xB = 1, and which writer produced the observed 0x08/0x0C inter-sample changes?
  6. Meaning of the 0x200 gate in FUN_08045da0, the EEPROM type word at *(type + 4) / address-bit count at *(type + 8) (expected 1024 blocks / 14 bits for 8 KB), and the two masks in the 0x0802cd7c u16 merge.
  7. Semantics/names of settings bytes +0x2A, +0x2B, +0x2C, +0x2D and the 0x0C bitfield (menu-item identities; fuzz #3–#6, #13).
  8. Exact handling of FUN_0803ade8 return 1 in the full game (packet probe nuance, §4; fuzz #2/#8).
