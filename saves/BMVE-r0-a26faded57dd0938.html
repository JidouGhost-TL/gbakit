1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte-level cross-check):

  • The title uses the GBA EEPROM interface exclusively, accessed through a hand-rolled bit-serial driver that talks to the EEPROM MMIO window at 0x0D000000 via a shared low-level DMA3 bit-transfer primitive. No SRAM/Flash command sequences (0x5555/0x2AAA) exist anywhere in the traced function set.
  • There is a 3-tier call stack: hardware bit-transfer primitive → single 8-byte EEPROM block read/write (with write-verify-retry) → multi-block buffer read/write helpers → three game-level save-I/O entry points (header writer, header reader, two payload writers with inline checksum generation).
  • The save image is logically split into 3 contiguous, explicitly-sized regions that are each written by a single dedicated function: an 8-byte magic/header region, a 144-byte payload region with a trailing 32-bit sum-style checksum word, and a 352-byte payload region with its own trailing 32-bit sum-style checksum word. The checksum math (sum of all preceding 32-bit words in the region, plus two externally-sourced RAM words, stored as the final word of the region) is proven directly from decompiled C in FUN_080296fc and FUN_0802974c.
  • Region boundaries were independently confirmed two ways: (a) the exact byte lengths passed to the write helper (0x90 and 0x160 bytes) match (wordcount+1)*4, placing the checksum word exactly at the last word of each region; (b) the byte read from the actual .sav file at the predicted checksum offset for the second region (0x1F4) is non-zero, structured, 4-byte-aligned data, consistent with a real stored checksum, not filler.

What remains open / unproven:

  • The two "extra" 32-bit addends folded into each checksum (read from *_DAT_08029748/_DAT_0802979c and the next word) live in RAM/ROM data not captured in this decompilation and could not be resolved to concrete values, so the checksum arithmetic could not be closed numerically against the sample file (see §4).
  • No read-side checksum verification / load routine was found anywhere in the 219 traced functions — only the write-and-generate side (FUN_080296fc, FUN_0802974c) and a single header-validity read (FUN_08029654) are present. The function(s) that validate the two payload checksums on load are outside the trace window.
  • Field-level semantics inside the 144-byte and 352-byte payload regions (e.g., the repeating 16-byte records containing 3-letter ASCII tags) are inferred purely from the repeating byte structure of the one real .sav sample, not from any traced code that manipulates individual sub-fields. These are reported as HYPOTHESIS.
  • Only one real .sav sample exists in this workspace (saves/cap-00-future-0.sav); there is no second/mutated sample to differentially confirm which bytes are load-bearing vs. incidental, and no paired .ss save-states exist in states/ for this cohort, so no counterfactual reload test could be executed yet.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

  • 0x0803645c — generic EEPROM bit-serial DMA transfer primitive.

Saves/restores an interrupt-mask-style register (*_DAT_080364bc), programs 3 MMIO-like pointer/length registers (_DAT_080364cc, _DAT_080364d0, _DAT_080364d4) with (param_1, param_2, param_3 | 0x80000000) — the 0x8000_0000 high bit is a classic DMA-enable pattern — then busy-waits on a status half-word (*puRam080364d8) until bit 0x8000 (DMA-busy) clears, before restoring the saved mask. This is the only function in the trace that touches these 3 registers directly, and it has no save-specific knowledge — it is a pure bit-transfer engine, called with the EEPROM data port address 0xD000000 as one operand by every caller below.

  • Callers (from ghidra/callgraph.json): 0x080364dc, 0x080365a0.
  • 0x080364dc — EEPROM block READ (8 bytes / 64 bits).

Builds a bit-serial "READ" command (header bits 1,1 + address bits, MSB-first) into a stack buffer, sends it with FUN_0803645c(buf, 0xD000000, addr_bits+3), then clocks back 0x44 (68) bits with FUN_0803645c(0xD000000, buf, 0x44) and unpacks the last 4×16-bit big-endian-packed words (64 data bits) into the caller's 8-byte output buffer. Returns 0 on success (bounds-checked against *(ushort*)(ptr+4), the EEPROM's address-bit-width table), nonzero (0x8000-class) on out-of-range.

  • Caller: 0x08036700.
  • 0x0803658c / 0x080365a0 — EEPROM block WRITE (8 bytes / 64 bits), raw.

0x080365a0 builds a bit-serial "WRITE" command (header 0,1 + address bits + 64 data bits + stop bit), sends it via FUN_0803645c(..., 0xD000000, addr_bits+0x43), then polls a hardware "ready" bit (uRam0d000000 & 1) with a VBLANK-count-based timeout (*_DAT_0803668c, which wraps at 0xE4≈228, matching GBA scanline count) — i.e. a real-time timeout on the EEPROM's internal write-cycle completion, not a fixed instruction-count spin. 0x0803658c is a 1-line wrapper that always passes param_3=1 (wait-for-completion flag).

  • Caller of 0x0803658c: 0x08036758. 0x080365a0 has no further caller in-trace beyond 0x0803658c.
  • 0x08036700 — write-verify (read-back compare).

Calls the 8-byte reader (0x080364dc) and compares the 4×16-bit words it returns against the caller-supplied data; returns 0x8000 on mismatch, 0 on match.

  • Caller: 0x08036758.
  • 0x08036758 — write-with-retry (3 attempts, write + verify).

Loop (≤3 iterations): attempt the raw write (0x0803658c); if it reports success, additionally verify by read-back (0x08036700); break on first clean write+verify pair; otherwise retry. Returns the last status code.

  • No in-trace caller found directly — it is called indirectly via func_0x08036758 from the next tier (0x080297e0), confirmed by the literal call site in ghidra/decompiled.c:2761.

3.2 Multi-block buffer helpers (bridge between single 8-byte blocks and arbitrary-length game buffers)

  • 0x080297a0 — multi-block EEPROM reader.

FUN_080297a0(byte_offset, dest_buf, byte_length): converts byte_offset to a block index (>>3), then loops ceil(byte_length/8) times calling func_0x080364dc(block_index, dest_buf+8*i), advancing the block index and buffer pointer by 1 block / 8 bytes each iteration. Returns 1 on full success, 0 if any single-block read reports failure. Decompiled source: ghidra/decompiled.c:2705-2738.

  • 0x080297e0 — multi-block EEPROM writer.

FUN_080297e0(src_buf, byte_offset, byte_length): identical loop structure, calling func_0x08036758(block_index, src_buf+8*i) (the write-with-retry primitive) per 8-byte block. Returns 1/0 the same way. Decompiled source: ghidra/decompiled.c:2741-2776.

These two functions are the only bridge in the entire 219-function trace between "EEPROM block I/O" and "game save buffers," and every known game-level save call goes through exactly one of them.

3.3 Game-level save entry points and how each mutates the in-RAM mirror

All three entry points share the same guard pattern: FUN_0802bc70() (zeroes two flag words then calls two subsystem routines — most likely an audio/DMA-timing guard disabling some peripheral so its interrupt/DMA activity cannot collide with the blocking, busy-wait EEPROM bitbang) → do the work → FUN_0802bc90() (sets the same flags back) → on I/O failure, call func_0x08025718(1) (a generic error-signal function taking an error code, 1 = "save I/O failed").

  • 0x08029654 — header/magic READ-and-validate (ghidra/decompiled.c:2555-2581).

Reads 8 bytes from EEPROM offset 0 into a 2-word RAM mirror (piVar1 = _DAT_08029694) via func_0x080297a0(0, piVar1, 8), then compares piVar1[0] against a ROM constant _DAT_080296a0 and piVar1[1] against iRam080296a4. Returns 1 only if the read succeeded and both words match. This is the save-validity/"does a save exist" check. How mapped: located by grepping decompiled.c for the only non-save_related_functions.c call site of func_0x080364dc-family helpers (0x080297a0), then reading the surrounding function body.

  • 0x080296c0 — header/magic WRITE (format/new game) (ghidra/decompiled.c:2604-2624).

Writes two ROM constants (_DAT_080296f4, _DAT_080296f8) into the RAM mirror at _DAT_080296f0, then flushes those 8 bytes to EEPROM offset 0 via func_0x080297e0(mirror, 0, 8). On write failure, signals error 1. This is what stamps the valid-save magic at region A.

  • 0x080296fc — payload region B WRITE + inline checksum (ghidra/decompiled.c:2631-2662).

Sums the first 0x23 (35) 32-bit words of the RAM mirror at _DAT_08029744, adds two further words read from a different pointer (*_DAT_08029748, _DAT_08029748[1]), stores the sum into word index 0x23 (the 36th word) of the same mirror, then flushes all 0x90 (144) bytes — i.e. all 36 words including the freshly-computed checksum — to EEPROM offset 8 via func_0x080297e0(mirror, 8, 0x90). The in-RAM struct is mutated by this function itself (the checksum word) immediately before the flush; the preceding 35 words are assumed already mutated by unseen gameplay code elsewhere in the ROM (outside the 219-function trace).

  • 0x0802974c — payload region C WRITE + inline checksum (ghidra/decompiled.c:2669-2700).

Identical pattern to 0x080296fc but over 0x57 (87) words at _DAT_08029798, checksum stored at word index 0x57 (88th word), two extra addends from *_DAT_0802979c/_DAT_0802979c[1], flushed as 0x160 (352) bytes to EEPROM offset 0x98.

No in-trace reader/verifier exists for regions B or C. Only the write-and-checksum-generate side was captured; the loader that presumably re-sums each region and compares against the stored checksum word is outside this 219-function decompilation window. This is called out explicitly as an open question rather than assumed.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature (Region A)

  • Offset: 0x00–0x07 (8 bytes, two 32-bit little-endian words).
  • Observed bytes (saves/cap-00-future-0.sav): 5f e6 4d 6f 4d 50 f6 05
  • Word 0 (0x00–0x03, LE32): 0x6F4DE65F
  • Word 1 (0x04–0x07, LE32): 0x05F6504D
  • The ASCII substring "MoMP" falls at byte offsets 0x02–0x05, straddling both words — consistent with a packed magic value rather than a pure ASCII tag.
  • Code proof: FUN_08029654 (ghidra/decompiled.c:2555-2581) reads these exact 8 bytes and requires word0 == _DAT_080296a0 && word1 == iRam080296a4 to report "save valid." FUN_080296c0 (ghidra/decompiled.c:2604-2624) writes _DAT_080296f4/_DAT_080296f8 (presumed same pair of ROM constants) to this location.
  • Confidence: CONFIRMED_STATIC. The mechanism (two fixed 32-bit words gating save validity) is proven directly from decompiled C. The literal values _DAT_080296a0/iRam080296a4 live in ROM data not included in ghidra/decompiled.c (which contains code only), so we cannot independently re-derive the constants from the decompilation text — we can only observe that the captured .sav sample (taken from a running, presumably successfully-loaded game) contains the bytes above at this offset, which is circumstantial but not courthouse-proof that these are the required constants.

4.2 Checksum algorithm (Regions B and C)

  • Algorithm: sum32_le, custom variant — "sum of N preceding 32-bit little-endian words, plus two externally-sourced 32-bit words, stored as word N (i.e., the last word of the flushed region)."
  • Region B: covered range 0x08–0x93 (35 words), stored checksum at 0x94–0x97. Code: FUN_080296fc.
  • Region C: covered range 0x98–0x1F3 (87 words), stored checksum at 0x1F4–0x1F7. Code: FUN_0802974c.
  • Endianness: little-endian 32-bit words throughout (matches ARM/THUMB native word load/store used in the decompiled sum loop, which uses plain int pointer increments with no byte-swap).

Python verification against the real .sav sample (saves/cap-00-future-0.sav):

Magic word0            = 0x6f4de65f
Magic word1             = 0x05f6504d

Region B (0x08..0x93, 35 words):
  sum of 35 words (mod 2^32)      = 0x84b85644
  stored checksum word @ 0x94     = 0x00000000
  stored - sum (mod 2^32)         = 0x7b47a9bc   <- would be the 2 unknown RAM addends, IF the stored word were the live checksum

Region C (0x98..0x1F3, 87 words):
  sum of 87 words (mod 2^32)      = 0x8bd457e2
  stored checksum word @ 0x1F4    = 0xa9d969c7   (bytes c7 69 d9 a9, confirmed present at that exact offset in the file)
  stored - sum (mod 2^32)         = 0x1e0511e5   <- would be the 2 unknown RAM addends

Interpretation and honesty check:

  • Region C's stored checksum word is not zero and sits exactly at the offset the code's byte-length arithmetic predicts (0x98 + 0x15C = 0x1F4), which is strong structural (not just coincidental) support for the formula and the offset. The arithmetic cannot be fully closed because *_DAT_0802979c/_DAT_0802979c[1] are RAM values not present in this static capture; the residual 0x1e0511e5 is consistent with — but not proof of — those two addends.
  • Region B's stored checksum word is exactly 0x00000000, which does not trivially equal sum - addends for any sane addend pair unless the two external words happen to cancel the sum exactly. The most likely explanations, in order of plausibility, and none of them provable from this single sample alone:
  1. This particular capture was taken before region B's "real" gameplay data (and its checksum) was ever written — the 0xDB-filled high-score table seen in region B (see §5) looks like an engine-level default/placeholder table, not player-entered data, so the checksum may legitimately be 0 for an all-default table if the two external addends are also 0 at that point.
  2. Our region/word-count boundary for B is off by one word (ruled out as likely, since the 0x90-byte length argument to func_0x080297e0 only has one self-consistent interpretation: 36 words with the last as checksum).
  3. A different, as-yet-untraced function overwrites/clears this specific word after FUN_080296fc runs.
  • Confidence: CONFIRMED_STATIC for the formula and byte offsets (proven in decompiled C, offsets match code-derived arithmetic exactly); not CONFIRMED_VERIFIED, because the numeric checksum cannot be independently closed without the two RAM-resident addends, and Region B's observed value is anomalous and flagged rather than hidden.

4.3 No magic/checksum found for the unused tail

Bytes 0x1F8–0x1FF read back as 0xFF (hardware-erased EEPROM default) in the sample and are never referenced by any offset/length pair passed to func_0x080297a0/func_0x080297e0 in the trace. No signature or checksum applies there.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save-states exist yet for this title in states/ (0 states in this cohort per the packet), so the following are proposed mutation/reload experiments to run once gameplay.ss/matching pre/post .sav pairs are captured, rather than results already obtained:

  1. Magic corruption test — flip one byte inside 0x00–0x07 (e.g. 0x02 from 0x4D→0x00), reload from the paired post-save .ss. Predicted effect: FUN_08029654's comparison fails → game should treat the card as having no valid save and offer a fresh-game/format path (no checksum repair needed since this is a plain equality gate, not an error-correcting field). Falsifiable prediction: if the game instead loads normally, our magic-gate hypothesis for 0x00-0x07 is wrong.
  1. Region-B checksum repair test — mutate one byte inside the first score record (0x1D, the low byte of the "EDA" record's value field, 0x7a→0x00), then recompute and rewrite word 0x94 as sum32(words 0x08..0x93) + X for several candidate X (starting with 0, since the observed stored value in this sample is 0), reload, and observe whether the UI score-table entry changes and whether the title accepts the save at all. This simultaneously (a) tests whether the "EDA" field really is a displayed score and (b) probes whether the title actually validates the Region-B checksum on load (currently unproven — see §3.3 open question) by also running a negative control: mutate the same byte but leave the stored checksum word unmodified, and check whether the title rejects/resets the data where the "repaired" case does not.
  1. Region-C checksum negative control — without touching any data byte, flip one bit in the stored checksum word at 0x1F4 only. Predicted effect, if a loader-side verifier exists outside this trace: region C is treated as corrupt/reset to default. If no observable change occurs, that is direct evidence the checksum is write-only telemetry (e.g. for an external tool) rather than something the game itself checks on load — directly resolving the open question in §3.3.
  1. Unused-tail write probe — attempt to write non-0xFF bytes into 0x1F8–0x1FF from a debugger/cheat-search tool during an active session (not via normal gameplay, since no traced writer ever targets this range) and then save normally; confirm the normal save path still produces 0xFF there afterward (fresh/restore repeat), which would confirm no hidden 4th write call exists outside the 219-function trace.
  1. Secondary-table consistency probe — play two matches with clearly different final scores for two different tracked initials, save after each, and diff the two .sav files across 0x10–0x8F. Predicted effect if the §5 HYPOTHESIS record-table reading is correct: exactly the ranked-record counter/value fields for the affected initials change, and the secondary 0x50-0x8F table's duplicated value tracks the most-recently-written score. A mismatch in which bytes move would falsify the current record-layout hypothesis and should prompt re-deriving the stride/record boundaries from the new diff rather than preserving the current guess.

All mutation tests must be run only against copies of the real .sav/.ss captures, preserving the originals in saves//states/ per standing evidence-retention rules.
