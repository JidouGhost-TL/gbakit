1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + bytes, CONFIRMED_VERIFIED unless noted)

  1. The save medium is EEPROM, 512 bytes total (EEPROM_V122 SDK tag in the packet; both .sav files are exactly 512 bytes). Access is exclusively through the serial EEPROM window at 0x0D000000 driven by DMA3, via exactly two functions recovered in the corpus: the DMA3 primitive FUN_0809b67c at 0x0809b67c and the 8-byte block reader FUN_0809b6fc at 0x0809b6fc (Section 3).
  2. FUN_0809b6fc(block_address, dest) reads one 8-byte EEPROM block: it bit-packs a start/read/address command, DMAs address_bits + 3 halfwords to 0x0D000000, DMAs 0x44 (68) halfwords back, then reassembles 64 data bits into 4 u16s stored in reverse word order at dest+6, dest+4, dest+2, dest+0. This word reversal exactly predicts the .sav byte order: reversing every 8 raw bytes yields the ASCII magic DISNEY SNOWBOARD at logical 0x00..0x0F in both saves (Python output in Section 4).
  3. Save layout (logical): a 32-byte header (16-byte magic + 16 zero bytes), two 64-byte records at logical 0x20 and 0x60 (each: 30 u16_le values + 4 zero bytes), a highly periodic table at logical 0xA0 (15-byte template repeated 9 times verbatim, 10th copy diverging), a walking-bit trailer ending at logical 0x147 with candidate value 0x03F7, a zeroed reserved span 0x148..0x1E7, and three sparse tail blocks at 0x1E8, 0x1F0, 0x1F8 (Section 5).
  4. sav-00-f1317.sav is a mid-write snapshot, not an older complete save: its first 0x60 bytes are byte-identical to sav-01-f1351.sav, and everything from 0x60 on is erased 0xFF. sav-01 (34 frames later, same pre-state bfdd44e905a2e35e) contains the completed layout. There is no primary/backup slot pair, generation counter, or sequence number anywhere in the 512 bytes (Section 2).
  5. The second record's 30 u16_le values are each exactly the first record's value plus a small positive delta (+16..+76, all 30 deltas positive; Python output in Section 5). The two records are related data sets, not copies.

Not proven / open (stated plainly)

  1. No EEPROM write function exists in the provided decompilation. Exhaustive searches (Section 3.4) found exactly one reference to 0x0D000000 (the reader), one DMA3-enable pattern (0x80000000 in FUN_0809b67c), and zero textual or callgraph callers of the reader. The writer, the game-level serializer, and any checksum routine were either not traced into the 387-function corpus or are reached only through indirect calls that the combined static+runtime callgraph does not record. This report does not invent them.
  2. No checksum is verified. Every standard algorithm tested over every plausible range (Section 4.3, including an exhaustive start/end brute force) failed to reproduce any candidate stored value. The only candidate is the unexplained u16_le 0x03F7 at logical 0x140 (raw 0x146..0x147 = 03 F7). It is reported as HYPOTHESIS/UNKNOWN, never as a confirmed checksum.
  3. No caller chain into the save code could be recovered from ghidra/callgraph.json or from textual FUN_/func_0x references in ghidra/decompiled.c: FUN_0809b6fc has callers: [] and FUN_0809b67c has exactly one caller (FUN_0809b6fc). Consequently the RAM mirror address (0x02xxxxxx/0x03xxxxxx) of the save struct is unknown; the reader's destination is a caller-supplied pointer (param_2) whose call site is absent.
  4. Semantic labels for the two 64-byte records, the 15-byte table, and the tail blocks are hypotheses from byte patterns only. Two snapshots (one incomplete) cannot confirm gameplay meaning; Section 6 gives falsifiable tests.

2.3 Redundancy, generation counters, selection rule

  • Mirroring/redundancy: none found. Record 0 and Record 1 are not copies: Record 1 = Record 0 + per-index deltas of +16..+76 on every one of 30 u16_le values (Section 5). The table region repeats a template, which is default data, not a backup of another region.
  • Generation/sequence counters: none found. No monotonically increasing field distinguishes the saves: sav-00 and sav-01 share an identical first 0x60 bytes, and sav-01 only adds regions. The tail value 0x0519 (1305 decimal) is close to but not equal to either frame number (1317/1351) and appears in only one snapshot, so calling it a counter is HYPOTHESIS at best.
  • Selection rule: with one linear layout there is nothing to select. The only validity gate supported by evidence is the header magic (game-side comparison code was not recovered, Section 3.4). Predicted rule, to be falsified by fuzzing (Section 6): magic mismatch ⇒ save treated as absent/blank; magic match ⇒ all regions trusted as-is (no checksum gate is known to exist).
  • Write-order evidence (why sav-00 fill is 0xFF and sav-01 fill is 0x00): sav-00-post (frame 1317) and sav-01-pre are the same emulator state (bfdd44e905a2e35e). Between frames 1317 and 1351 the writer completed blocks 12–40, zeroed blocks 41–60, and wrote tail blocks 61–63. sav-00 therefore froze a format/save burst after block 11. Any analysis treating sav-00 as a complete older save would be wrong; this report uses it only as (a) proof of write order and (b) a second observation of Record 0.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver: DMA3 primitive FUN_0809b67c (0x0809b67c) — CONFIRMED_STATIC (callee-proven), role in reader CONFIRMED_VERIFIED

Signature: void FUN_0809b67c(undefined4 src, undefined4 dst, uint count).

What the decompiled body does, in order (literal-pool targets _DAT_0809b6dc.._DAT_0809b6f8 are unresolved pointer cells in the corpus, identified by access pattern against the known GBA map):

  1. Saves and clears a control cell (*_DAT_0809b6dc), consistent with masking DMA/EEPROM chip-select state before a transfer.
  2. Programs WAITCNT EEPROM timing: *_DAT_0809b6e0 = (*_DAT_0809b6e0 & mask) | *(u16*)(config_base + 6) — i.e. wait-state bits come from offset +6 of the same EEPROM config struct the reader bounds-checks against (3.2). This is the 0x04000204 WAITCNT EEPROM-field update; the exact cell addresses cannot be resolved because _DAT_ values are not in the corpus.
  3. Writes the three DMA3 registers through pointer cells: *_DAT_0809b6ec = src (DMA3SAD, 0x040000D4 family), *_DAT_0809b6f0 = dst (DMA3DAD), *_DAT_0809b6f4 = (count & 0xFFFF) | 0x80000000 (DMA3CNT: count in low 16 bits, enable in bit 31).
  4. Polls *(u16*)(cnt_cell + 2) & 0x8000 until clear (transfer-complete wait on the control halfword), restores the saved control cell, and returns via the (unrecovered) tail jump that terminates every function in this corpus.

The reader calls it in both directions — (stack_buffer, 0x0D000000, n) to clock the command out and (0x0D000000, stack_buffer, 0x44) to clock data in — so this single primitive is the entire hardware layer. There is no SRAM byte-copy loop and no Flash 0x5555/0x2AAA command sequence anywhere in the 387 functions (Section 2.1).

3.2 Serialization reader: EEPROM block read FUN_0809b6fc (0x0809b6fc) — CONFIRMED_VERIFIED

Signature: void FUN_0809b6fc(uint block_address, int dest) (return value is passed through the unrecovered tail jump; uVar3 is preloaded from uRam0809b718 as an error sentinel and zeroed on success).

Step-by-step, cross-checked against the .sav bytes:

  1. block_address &= 0xFFFF; if block_address >= *(u16*)(config + 4) the function returns the sentinel without touching the EEPROM. Offset +4 of the config struct is therefore the block-count limit (64 for a 512-byte part; the literal value is unresolved, so the field role is CONFIRMED_STATIC, the value 64 is inferred from file size).
  2. It builds a serial bitstream in the stack array auStack_96[67] (each u16 holds one serial bit in bit 0): the address bits are emitted first (count = *(byte*)(config + 8), the address-width field), followed by two 1 bits written as *puVar5 = 1; puVar5[-1] = 1 (start + read-opcode prefix of the serial EEPROM protocol).
  3. FUN_0809b67c(auStack_98, 0x0D000000, address_bits + 3) clocks the command out; FUN_0809b67c(0x0D000000, auStack_98, 0x44) clocks 68 halfwords back (64 data bits plus lead-in/dummy bits — the unpacker skips the first 3 bit positions via puVar5 = auStack_96 + 3).
  4. Unpacking: four times, it assembles 16 bits MSB-first (uVar4 = (uVar4 << 1) | (*puVar5 & 1)) and stores to (u16*)(dest + 6), decrementing the destination pointer each iteration: dest+6, dest+4, dest+2, dest+0. This reverse-word-order store is the direct cause of the raw .sav byte order: each raw 8-byte block is the logical block reversed, proven by the magic in Section 4.

One call = one 8-byte block. A full-image load therefore requires 64 calls (or fewer for a partial load); no looping wrapper around this function was recovered (3.4).

3.4 Caller-chain tracing: method and honest result

How callers were mapped (three independent routes, all executed):

  1. ghidra/callgraph.json lookup: 387 nodes / 328 edges. FUN_0809b6fc → callers: [], callees: ["0x0809b67c"]. FUN_0809b67c → callers: ["0x0809b6fc"], callees: [].
  2. Textual reference rebuild: every FUN_080xxxxxx( / func_0x080xxxxxx( occurrence in ghidra/decompiled.c was re-extracted (the corpus mixes both spellings, and the JSON graph misses func_0x-style edges such as the memcpy callers). Result: the string 0809b6fc occurs only at its own definition; 0xd000000 occurs exactly twice, both inside FUN_0809b6fc; 0x80000000-style DMA enable occurs in save context only inside FUN_0809b67c.
  3. Pattern search for a hidden second driver: any function containing a DMA3-style count | 0x80000000 store, an & 0x8000 completion poll, a 64-iteration block loop with stride 8, or a byte-compare loop against a candidate magic string. No second hit survived manual inspection (candidates are listed in 3.3).

Result: the complete recoverable caller chain is

[game-level caller: NOT PRESENT in corpus]  --(indirect / untraced)-->  FUN_0809b6fc (0x0809b6fc, EEPROM read-one-block)
                                                                        └─> FUN_0809b67c (0x0809b67c, DMA3 transfer primitive)
  • Entry caller: none recoverable. FUN_0809b6fc is a graph root. The packet's own seed extraction reached the same result (callers: none in ghidra/save_related_functions.c), corroborating that this is a corpus limitation, not a search miss on one route.
  • Trigger context: unknown from code. From the state metadata, a save write burst runs between frames 1317–1351 (Section 2.3); a save read presumably runs at boot/title, but no boot function in the corpus (0x0800073c, 0x08000908, 0x08000d08, …) references the reader by any route above.
  • How each caller mutates the in-RAM save struct: not applicable — there are no recovered callers. Any table assigning RAM field mutations to named caller functions would be fabricated. What can be stated from the reader itself: whichever caller exists passes dest = RAM_save_block_buffer and block_address = EEPROM block index; the reader writes exactly 8 bytes to dest..dest+7 and nothing else. The RAM base (0x02xxxxxx/0x03xxxxxx) is UNKNOWN.
  • Writer: absent from the corpus by the same three routes. The .sav bytes prove writes happened (mid-write snapshot, Section 2.3), so a writer exists in the ROM, but it is not among the 387 decompiled functions — most plausibly it sits in the un-decompiled gap after the reader (0x0809b7ac..0x0809b920 contains no corpus function) or is reached/called only indirectly. Naming an address for it would be a guess; Section 6 includes the runtime test that would identify it.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature — CONFIRMED_VERIFIED in .sav, code-side comparison UNKNOWN

  • Logical bytes (game order): DISNEY SNOWBOARD (16 ASCII bytes) at logical offset 0x00, followed by 16 zero bytes at 0x10..0x1F.
  • Raw .sav bytes at offset 0x00: 53 20 59 45 4E 53 49 44 44 52 41 4F 42 57 4F 4E (S YENSIDDRAOBWON read naively). Each raw 8-byte block is the logical block reversed — exactly the transform the reader's reverse-word-order unpacking predicts (Section 3.2, step 4). Raw block 0 reversed = DISNEY S; raw block 1 reversed = NOWBOARD.
  • Verified in .sav: yes, in both files (Python output below).
  • Verified in code: no. No function in the corpus compares a 16-byte string; the magic is therefore proven as stored data, and its use as a validity gate is the only sensible interpretation but is labeled HYPOTHESIS for the check, CONFIRMED_VERIFIED for the bytes.
  • Related config evidence (CONFIRMED_STATIC): the reader's config struct has block-limit at +4, WAITCNT bits at +6, address-width at +8 (Section 3). No seed, key, or checksum constant is stored in any recovered save function.

4.2 Decompiled-C proof (reader excerpts, ghidra/save_related_functions.c / ghidra/decompiled.c)

4.3 Checksum hunt: exact method, Python verification output, negative result

Candidate stored values tested (both raw and logical views): the u16_le 0x03F7 trailer at logical 0x140; Record 0/1 trailing u16s (0x35AC, 0x3804, 0x35DA, 0x3832 — these turn out to be ordinary array elements, Section 5, but were tested as candidates anyway); tail-block values (0x0519, 0x9464 byte patterns).

Algorithms tested: sum8, sum16 (byte sum), sum of u16_le words, xor8, xor16, CRC-16/MODBUS, CRC-16/ARC, CRC-16/CCITT (init 0xFFFF, 0x0000, 0x1D0F), CRC-32 (zlib). Ranges tested: every record/table/header span listed below, plus an exhaustive brute force over all block-aligned (8-byte) start/end pairs in both views of both files (2,080 ranges per view).

The 0x03F7 trailer value remains UNKNOWN — possibly a count, a packed bitfield continuation (it directly follows the walking-bit bytes ... Field-map notes

  1. No field could be assigned a RAM mirror or writer function. This is a corpus gap (Section 3.4), not an oversight: the report deliberately leaves those columns empty/UNKNOWN rather than attaching the nearest-looking game function.
  2. Record semantics: the strongest semantic evidence in the whole file is the Record 0→Record 1 delta vector (all 30 deltas in +16..+76). Whatever these u16s measure, Record 1 measures the same 30 things at consistently higher values. Snowboarding-context guesses (race times would usually decrease when improved; scores/counts increase) weakly favor scores, distances, or accumulated counts over best-times — but this is context reasoning, not evidence, and is labeled HYPOTHESIS everywhere.
  3. Update mechanism (inferred from snapshots only): header + Record 0 are written first (present in the frame-1317 freeze), then Record 1, table, trailer, zero-fill, and tail blocks (present by frame 1351). Whether normal gameplay rewrites the whole image or only dirty blocks cannot be decided from two snapshots of one burst.

6. Save Fuzzing & Counterfactual Verification Plan

6.0 Harness and ground rules

  • Base image: use sav-01-f1351.sav (the only complete save) for all mutations. Keep a pristine copy; every mutation is applied to the raw file, remembering that the game reads each 8-byte block reversed — to change a logical value, reverse the target block's bytes after editing, or equivalently edit in logical view and re-reverse every block before booting.
  • Reload points: the paired states bracket the write burst (sav-01-pre frame 1317 = complete-save not yet written; sav-00-post is the identical state; gameplay frame 1553 and final frame 1653 show post-save gameplay). For load-path tests, cold-boot (or reset) with the mutated .sav attached is the cleanest test, since the recovered reader runs on the load path; in-state reload via emulator save-load with a replaced .sav is acceptable if cold boot is unavailable. The packet's cold-reload probe (save_preserved: true, visual_delta_vs_blank_boot: true) is the control: an unmutated sav-01 must reproduce that delta before any mutation result is trusted.
  • Checksum repair: there is no verified checksum to repair (Section 4.3). Steps marked "no repair" must be run as-is. The single exception is target F5, which tests whether repair is needed: run it once unrepaired and once with each candidate recomputation (sum16/xor/CRC variants from Section 4.3 over the table range) — acceptance only in a repaired variant identifies the algorithm; acceptance in all variants kills the checksum hypothesis for that value.
  • Observables, in priority order: (1) does the title/file screen treat the save as present or blank? (2) does any displayed number/list change (profile data, course table, options)? (3) does the game rewrite the .sav on next save, and which blocks change (diff mutated-loaded-then-resaved vs. mutated input — blocks the game rewrites reveal what it parsed vs. ignored)? (4) RAM watch, if available: the first buffer written by reads from 0x0D000000 DMA is the missing RAM mirror (Section 3.4); logging DMA3 dest addresses during boot directly answers the report's biggest open question, and logging DMA3 source addresses during a save identifies the writer's flush loop.

6.2 Counterfactual controls (run before trusting any mutation result)

  1. Blank control: boot with an all-0xFF 512-byte file, and separately all-0x00. Predicted: blank-save behavior in both; whichever the game reformats first (diff the post-boot .sav) reveals the format order and confirms the Section 2.3 write-order reading.
  2. Transplant control: splice sav-01 blocks 0–11 onto an erased file (rest 0xFF) — this reconstructs the sav-00 state from parts. Predicted: identical behavior to real sav-00 on cold boot; if the game accepts header+Record 0 alone, partial-save tolerance is proven and F3/F4 results must be read accordingly.
  3. Block-reversal control: byte-reverse one data block (e.g. raw block at 0x20) without changing its multiset of bytes. Predicted: the corresponding parsed values scramble (reader is order-sensitive as decompiled). If values are unchanged, the emulator's .sav ordering — not the game's — explains the reversal, and the logical-view convention in this report must be inverted (the field contents would still stand, byte-swapped per block).
  4. No-op resave control: load unmutated sav-01, force a save with no gameplay change, diff the result. Blocks that change anyway are volatile (counters/timers — prime suspects: tail blocks); blocks that never change across all tests are candidates for removal from the "written by game" set (possible emulator artifacts).

6.3 What would raise confidence to HIGH

  • F11 identifying the writer + RAM mirror, followed by matching its flush order against Section 2.3's snapshot order.
  • F5 producing a selective checksum acceptance (algorithm + range identified), or F5/F1 jointly proving magic-only integrity.
  • F3/F4/F6 attaching at least one UI-visible meaning to each major region.

Until then, the honest grade remains MEDIUM: the transport layer and on-disk layout are verified; the semantics and the write path are not.
