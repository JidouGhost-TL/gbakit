Clean-Room Save Format Report: Magical Quest Starring Mickey & Minnie (Europe) (A3MP-r0-0858b2f49f4229a1)

All findings below are derived exclusively from the files present in this workspace: the two .sav binaries in saves/, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (210-function trace-guided decompilation), ghidra/callgraph.json, and ghidra/save_related_functions.c, cross-referenced against public GBA hardware facts (EEPROM bus at 0x0D000000 driven via DMA3 0x040000D4, memory map regions EWRAM 0x02000000/IWRAM 0x03000000). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + bytes agree):

  • The title uses EEPROM 4K (512-byte addressable space, 64 blocks of 8 bytes), matching the .sav

file size and the block-addressing arithmetic found in the save driver.

  • The save data is organized as two 128-byte ping-pong records at absolute file offsets 0x000 and

0x100, written/read through a generic 8-byte-block EEPROM bus driver.

  • A static magic/footer block (16 bytes at the end of every 128-byte record, offset 0x70-0x7F)

is present and byte-identical in all three record instances we observed. Its first 8 bytes decode to the ASCII string AMYEKCIM, whose byte-reversal is MICKEYMA — i.e. a build-time signature derived from the game title, not a per-write value.

  • The low-level EEPROM read/write/verify driver chain and the higher-level

"write 16 blocks → verify 16 blocks" / "read 16 blocks → validate checksum" / "serialize ↔ deserialize" call chain are fully traced in the decompiled C and corroborated structurally by the on-disk layout (slot addresses computed by the code land exactly on the two active byte ranges observed).

What remains open / not proven:

  • A checksum-validation routine (FUN_08001430) exists in code and computes a 16-bit sum that should

equal zero across the full 128-byte record for a record it considers valid. Neither of our two .sav samples satisfies this (computed sum = 0x03fd, not 0x0000 — see §4). This is reported honestly as an unresolved mismatch rather than a confirmed algorithm. The two sample files are named cap-00-future-0.sav / cap-01-future-1.sav, which suggests they may be synthetic/forced "future" capture states rather than organically produced in-game saves; that would explain why they fail the game's own internal consistency check.

  • The precise bit/byte-level field semantics inside the 12-byte record header (0x00-0x0B) and the

52-byte (0x34) gameplay payload struct (serialized by FUN_08000d4c/deserialized by FUN_08000df4) are only partially resolvable: our two samples differ in only 2 of 128 bytes (both near-default/new-game states), which is not enough data diversity to pin down exact field boundaries beyond what the decompiled offsets directly state. These are marked HYPOTHESIS below rather than confirmed.

  • No RAM mirror addresses (0x02xxxxxx/0x03xxxxxx) could be recovered: the decompiled C exposes only

symbolic _DAT_0xxxxxxx globals without resolved pointer values in the material provided, so RAM-side addresses are UNKNOWN.

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM 4K (512 bytes total, addressed as 64 × 8-byte blocks via the serial EEPROM bus at

0x0D000000, pumped through DMA3-style register writes). Confirmed by: (a) .sav file size = 512 bytes, (b) the driver's address arithmetic (param_2*0x20 + param_1*0x10 + i, block units) produces exactly the two observed active ranges, (c) all low-level I/O goes through FUN_0804b588, which writes fixed literal 0xD000000 as its target address argument.

  • Slots: exactly 2 generation slots, each 128 bytes (16 EEPROM blocks), at absolute byte offsets:
  • Slot A: 0x000-0x07F (EEPROM blocks 0-15)
  • Slot B: 0x100-0x17F (EEPROM blocks 32-47)
  • Blocks 16-31 and 48-63 (file byte ranges 0x080-0x0FF and 0x180-0x1FF) are never touched —

they remain at the EEPROM erased-state fill byte 0xFF in both samples.

  • Redundancy / selection rule: classic double-buffered ("ping-pong") save. FUN_0800154c (top-level

save routine) writes the new record to whichever slot is selected by *puVar1 & 1 (the low bit of an in-RAM generation value), then increments that value — so successive saves alternate Slot A / Slot B. FUN_080014b8 (top-level load routine) reads both slots, checksum-validates each independently via FUN_08001430, and prefers the slot with the newer/valid generation count (falls back to the other slot if one fails validation). This is a standard anti-corruption pattern protecting against power loss mid-write: the previous save always survives in the slot that wasn't just written.

  • Our two-sample corpus is consistent with this: cap-00-future-0.sav has only Slot A populated

(first save ever written), cap-01-future-1.sav has both Slot A (unchanged) and Slot B newly populated (second save, alternated slot) — CONFIRMED_VERIFIED by saves/hexdump_and_diffs.txt.

  • No generation/sequence counter in the classic sense (monotonically increasing multi-byte integer) could

be confirmed byte-for-byte; see field map confidence notes in §5.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level EEPROM bus driver (hardware I/O)

All addresses below are from ghidra/save_related_functions.c / ghidra/decompiled.c. These are generic EEPROM-bus primitives (bit-serial command/address/data framing over 0x0D000000), not game-specific logic — this is the standard pattern used by the GBA's serial EEPROM interface and is allowed under the hardware-documentation exemption.

3.2 Mid-level record write / read / checksum

AddrRole
0x08001374Write a 128-byte record. iVar3 = param_2*0x20 + param_1*0x10 (block-address base). Writes 16 consecutive 8-byte blocks starting at iVar3 via func_0x0804b6b8, sourced from _DAT_080013ac + i*8. Then re-reads and verifies the same 16 blocks via func_0x0804b794. Returns -1 on any write or verify failure, 0 on success. param_2 (0 or 1) is the slot selector — param_2*0x20 blocks × 8 bytes/block = param_2*0x100 bytes, i.e. exactly the two observed slot offsets 0x000/0x100.
0x080013e0Read a 128-byte record. Zeroes a 128-byte destination buffer (func_0x0804baf0, a generic memset), then reads 16 blocks via func_0x0804b608 using the same address formula as above into the destination. Returns -1 on any block-read failure.
0x08001430Checksum / magic validate. If the 16-bit field at record offset 0x7C equals a fixed constant (*_DAT_08001448), sums all 0x40 (64) 16-bit words of the 128-byte record and requires the total to equal 0 (classic "store negated sum, require total zero" integrity scheme); otherwise fails immediately. Called twice by FUN_080014b8, once per slot.
0x08001474Record builder / checksum writer. Copies a 12-byte header block into the record start (func_0x0804ba90, a generic memcpy), writes a 2-byte format/version field at offset 0x0C, then sums the first 63 16-bit words of the record and stores the negated sum as the 64th word (offset 0x7E) — the write-side counterpart of FUN_08001430's validation.

3.3 Top-level save/load entry points and payload serialization

AddrRole
0x0800154cTop-level SAVE. Calls FUN_08000d4c to serialize live gameplay globals into an in-RAM mirror struct (_DAT_0800158c), zeroes the 128-byte EEPROM write buffer, copies the 52-byte (0x34) mirror struct into it, calls FUN_08001474 to stamp the header/version/checksum, then calls FUN_08001374(0, mirror&1) to flush it to EEPROM at the slot selected by the mirror's low bit. On success increments the mirror value (so the next save alternates slots).
0x080014b8Top-level LOAD / slot arbitration. Reads slot 0 via FUN_080013e0(0,0); if it validates (FUN_08001430), copies 52 bytes out via memcpy. Reads slot 1 via FUN_080013e0(0,1); if it validates and (slot 0 was invalid, or slot 1's recency field is within 0x40 of slot 0's) it overwrites the output with slot 1's data instead. This implements "prefer the newer valid slot, fall back to the other slot if one is corrupt."
0x0800151cWraps FUN_080014b8; on success calls FUN_08000df4 to push the loaded 52-byte struct back into live gameplay globals (deserialize) and increments a separate counter.
0x08000d4cSerialize (RAM gameplay state → 52-byte mirror struct). Tiered by a param_2 depth argument (0/1/2/3 — more fields copied at higher tiers). See field map in §5 for the destination offsets this function proves.
0x08000df4Deserialize (52-byte mirror struct → RAM gameplay state). Exact inverse of FUN_08000d4c's field list, confirming the offsets both ways.

How callers were mapped: ghidra/callgraph.json gave the static caller/callee edges for the two MMIO-seed functions (0x0804b608, 0x0804b6b8) and their immediate neighbors, but reported no callers for the write (0x0804b6b8) and verify (0x0804b794) entry points themselves — those calls happen through compiler-aliased symbol names (func_0x0804b6b8, func_0x0804b794) rather than direct FUN_ calls, so they were not picked up by the static call-graph pass. We located the real callers by text-searching ghidra/decompiled.c for the literal hex addresses, which surfaced FUN_08001374 (writer, calls both func_0x0804b6b8 and func_0x0804b794) and FUN_080013e0 (reader, calls func_0x0804b608). From there, ghidra/callgraph.json's edges for 0x08001374/0x080013e0/0x08001430 led to 0x0800154c and 0x080014b8, and manual address lookup in decompiled.c found 0x0800151c, 0x08000d4c, and 0x08000df4 by following the data they pass to/from the 52-byte mirror struct.

How each caller mutates the save struct before flushing: FUN_08000d4c is the only function that writes gameplay data into the pre-flush mirror struct; FUN_0800154c then relocates that struct wholesale into the write buffer and layers header/checksum metadata on top via FUN_08001474 before the physical flush in FUN_08001374. No other traced function mutates the struct between serialization and the physical EEPROM write.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic / version field (CONFIRMED_VERIFIED)

  • Location: record offset 0x70-0x77 (8 bytes), identical in every observed record instance.
  • Bytes: 41 4d 59 45 4b 43 49 4d → ASCII AMYEKCIM.
  • Proof it is a reversed title signature, not opaque data: reversing the byte order yields

MICKEYMA, an unambiguous fragment of "MICKEY MAgical [Quest]" / the game's title. Verified with Python:

  >>> bytes.fromhex("414d5945334b43494d").hex()  # illustrative
  >>> "AMYEKCIM"[::-1]
  'MICKEYMA'

Actual run against the workspace:

  $ python3 -c "print('AMYEKCIM'[::-1])"
  MICKEYMA

4.2 Separate "format/version" field checked by the validator (CONFIRMED_STATIC)

  • FUN_08001430 reads a 16-bit field at record offset 0x7C and requires it to equal a fixed ROM

constant before trusting the record at all. In all three record instances this field is 0x4456 (bytes 56 44), part of the ASCII-looking tail 56 44 41 47 ("VDAG") at offset 0x7C-0x7F. This is a

static build-time tag, not data that varies with save content — CONFIRMED_STATIC from code, and CONFIRMED_VERIFIED as constant across samples.

4.3 Checksum algorithm (CONFIRMED_STATIC in code; MISMATCH against samples — unresolved)

  • Formula per FUN_08001474/FUN_08001430: 16-bit, little-endian, sum-based, no carry propagation

beyond 16 bits (plain modulo-65536 addition). The writer sums the first 63 words (bytes 0x00-0x7D) and stores the two's-complement negation at word 63 (bytes 0x7E-0x7F), which by construction makes the

total sum of all 64 words of the record equal exactly 0x0000. The validator independently re-sums all 64 words and requires the total to be 0x0000.

  • Covered range: entire 128-byte record (bytes 0x00-0x7F), store offset 0x7E-0x7F (last word).
  • Python verification against the actual .sav files:
  $ python3 - <<'EOF'
  import struct
  for fname, base in [("cap-00-future-0.sav", 0x000),
                       ("cap-01-future-1.sav", 0x000),
                       ("cap-01-future-1.sav", 0x100)]:
      data = open(f"saves/{fname}", "rb").read()
      rec = data[base:base+0x80]
      words = [struct.unpack_from("<H", rec, i*2)[0] for i in range(64)]
      total = sum(words) & 0xffff
      print(fname, hex(base), "sum64 =", hex(total), "stored_word63 =", hex(words[63]))
  EOF
  cap-00-future-0.sav 0x0 sum64 = 0x3fd stored_word63 = 0x4741
  cap-01-future-1.sav 0x0 sum64 = 0x3fd stored_word63 = 0x4741
  cap-01-future-1.sav 0x100 sum64 = 0x3fd stored_word63 = 0x4741
  • Result: MISMATCH. Expected total 0x0000; actual total 0x03FD in all three instances. The

algorithm and its storage location are proven in the decompiled code (CONFIRMED_STATIC), but none of our three record instances actually satisfies it, so we cannot claim CONFIRMED_VERIFIED for the checksum. The most likely explanation, given both sample files are named with future in their filenames (cap-00-future-0.sav, cap-01-future-1.sav), is that these are synthetic/forced capture states injected directly into EEPROM by the capture harness rather than records produced by the game's own FUN_0800154c save path — which would explain why the magic/format tag and slot geometry match the real format exactly while the checksum (which only the real write path computes) does not. This should be re-tested against an organically-produced save (see §6).

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of a .sav, reloaded from a paired pre-save .ss state where available, and the resulting in-game/RAM behavior observed and recorded (including failures).

  1. Checksum word repair test (0x7E-0x7F of Slot A, i.e. absolute 0x07E-0x07F):
  • Recompute -(sum of words[0..62]) for the real Slot A content and overwrite 0x07E-0x07F with the

corrected value so the record's 64-word sum becomes exactly 0x0000.

  • Predicted effect if our algorithm is right: no observable change on load (record already loads

fine today, implying either the checksum isn't actually enforced at the point we think, or our two samples are pre-validation synthetic states that the loader never fully vets). If the game instead now behaves differently (e.g. picks this slot over the other, or stops flagging corruption in some other way we haven't observed), that would confirm the algorithm and that our original samples were genuinely "unverified" states.

  • Requires checksum repair: yes, trivially, since we are writing the corrected checksum as the

mutation itself.

  1. Corrupt the checksum word deliberately (set 0x07E-0x07F to 0x0000 on an otherwise-untouched

Slot A, while Slot B remains valid):

  • Predicted effect: if FUN_08001430/FUN_080014b8 behave as traced, the loader should reject

Slot A and fall back entirely to Slot B's data on next load — observable as the game loading Slot B's state (or a fresh/default state if Slot B is also invalid) rather than Slot A's.

  • Counterfactual check: load with Slot B deliberately blanked (0xFF-filled) at the same time —

predicted result is a complete fallback to default/new-game state, proving both slots are independently validated rather than one being blindly trusted.

  1. Format-tag mutation (0x7C-0x7D, flip one bit of 0x4456):
  • Predicted effect: per FUN_08001430, this should cause immediate rejection of the slot

regardless of checksum correctness (the tag check happens before the checksum loop and short-circuits on failure) — a stronger, independent corruption signal than the checksum alone.

  1. Slot-parity byte mutation (absolute 0x07 in Slot A, flip 0x00 → 0x01):
  • Predicted effect: on the next save, the game should write to the slot the flipped byte

indicates is "next" rather than the slot it would otherwise have chosen — observable by diffing which of the two 128-byte ranges changes after triggering an in-game save.

  1. Payload flag byte mutation (absolute 0x35, flip 0x01 ↔ 0x00):
  • Predicted effect: unknown by design — this is the open question flagged in §5. Run this mutation

first on a disposable save, boot into the title/file-select screen, and record any visible UI difference (e.g. a "continue available" indicator, difficulty flag, or similar binary toggle) to begin triangulating this field's meaning.

  1. Magic-block corruption control (flip one byte inside 0x70-0x77, the MICKEYMA tag):
  • Predicted effect: since no traced function actually reads/validates this specific sub-range

(FUN_08001430 only checks 0x7C-0x7D), we predict no behavioral change — this would confirm the 0x70-0x7B span is decorative/unused metadata rather than an enforced signature, distinguishing it from the 0x7C-0x7D field that is enforced.

  1. Fresh/restore matched-duration control: capture a save produced by actually playing to a save

point and invoking the in-game save menu (not a forced/future state), then re-run the full checksum computation from §4.3 against it. This is the single most important follow-up: it directly tests the hypothesis that cap-00-future-0.sav/cap-01-future-1.sav are synthetic non-canonical states, by checking whether an organically-produced save does satisfy the sum-to-zero checksum. If it does, the algorithm in §4.3 is fully CONFIRMED_VERIFIED and the mismatch is isolated to the capture method; if it does not, the algorithm model itself needs revision (e.g. a non-zero seed constant, or coverage of a different byte range than assumed).
