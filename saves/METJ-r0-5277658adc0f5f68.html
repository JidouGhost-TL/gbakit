Clean-Room Save Format Report — Metroid Fusion (Europe) (En,Fr,De,Es,It) (Beta) (2002-09-11)

Release key: METJ-r0-5277658adc0f5f68

ROM SHA-256: 5277658adc0f5f681065bf11e163b3cbb4b53b3afa6180d35f124419f6fb7883 (as supplied; see PACKET.md)

All findings below are derived exclusively from the files in this workspace: the two real .sav binaries in saves/, the pre-computed hexdump/diff file, and the trace-guided Ghidra decompilation/callgraph in ghidra/. No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (decompiled code + .sav bytes agree, byte-exact Python verification):

  • The cartridge uses a flat 32 KiB battery-backed SRAM at 0x0E000000. No EEPROM (DMA3

0x040000D4) or Flash command-sequence (0x5555/0x2AAA) code paths exist anywhere in the 100-function decompilation — the literal 0xe000000 address appears in exactly 3 places, all of which are plain byte-copy calls, matching the packet's declared SRAM 256K media type.

  • A 128-byte header/config block occupies SRAM offset 0x00–0x7F. It carries a running

one's-complement-pair checksum (sum32 at 0x00, ~sum32 at 0x04) over all 32 words of the block, a two-byte tag "01" at 0x08–0x09, a flag byte at 0x0B, and a fixed 20-byte ASCII build tag "AGBMetroid_USVerE003" at 0x0C–0x1F. The checksum formula was reproduced in Python against both .sav files and matches exactly (see §4).

  • A write-verification ("can this cart actually save?") probe routine exists

(FUN_0807d3d4 @ 0x0807d3d4) that writes 16 bytes to SRAM, reads them back, mutates them, rewrites, and compares — a classic SRAM-presence self-test, independent of the header block.

  • A 16-byte footer at 0x7FF0–0x7FFF contains the ASCII tag "METDSAVE\x00\x00" followed by 6

bytes of 0xFF fill, identical and byte-for-byte unchanged across both captured .sav files.

What remains open / unresolved (flagged explicitly below, not asserted as fact):

  • The exact trigger/caller of the top-level dispatcher FUN_0807cb60 (no caller edge exists in

ghidra/callgraph.json; it is almost certainly reached through an un-recovered jump table from the save/options menu, which is outside this workspace's decompiled set).

  • Whether FUN_0807cc34's second candidate buffer (RAM offset +0x80 words relative to its first

argument) corresponds to a genuine second physical SRAM copy, or to a RAM-resident template used only for repair/compare. No second populated 128-byte block was observed anywhere in either .sav file.

  • The nature of the literal ASCII strings "fSTARTKEYLANGUAGE" / "ENDKEY_LANGUAGE_" found at

SRAM 0x7045–0x7066 in cap-01-future-1.sav only. This text does not appear anywhere in ghidra/decompiled.c, so it cannot be attributed to any traced save-writer. It is flagged as a

HYPOTHESIS, most plausibly explained by the full-SRAM bulk-copy writer (FUN_08000d74, §3) flushing an entire 32 KiB RAM mirror in one 0x8000-byte DMA — if that mirror buffer was not fully re-initialized before the copy, stale developer/debug text already resident in EWRAM (this is a Beta ROM) could leak through at a fixed relative offset without ever being deliberately "written" by a field-level save routine.

  • The purpose of the zero-filled 256-byte block at 0x0100–0x01FF. No decompiled function

references this absolute SRAM offset; it is zero (not 0xFF) in both captures, which is enough to say it is deliberately cleared rather than untouched, but not enough to say by what.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O primitives

No raw SRAM byte-copy loop, Flash bank-select/command sequence, or EEPROM DMA3 bitstream code exists in the decompiled set. All SRAM access instead goes through two generic copy wrappers that happen to be called with the literal SRAM base 0x0E000000 as one argument:

  • func_0x08004dc8(src, dst, len) — generic memory copy, used as the SRAM WRITE primitive

whenever dst == 0xe000000 (seen at decompiled.c:205,222). It is also used elsewhere in the ROM (decompiled.c:239,257,311,331,349) with non-SRAM destinations, confirming it is a general-purpose copier, not an SRAM-specific driver — the save semantics come entirely from the literal 0xe000000 argument at the three seed call sites.

  • func_0x08004c90(src, dst, len) — same shape, used as the SRAM READ primitive when

src == 0xe000000 (decompiled.c:292). Also reused elsewhere with unrelated addresses (decompiled.c:275, copying 0x7f00 bytes — almost certainly a graphics/tilemap buffer, not save-related; excluded from this analysis).

  • func_0x080030a0(mode, fill_or_src, dst, len, align) — a CpuSet/memset-like utility used to

stage the RAM-side mirror buffer immediately before a full 32 KiB flush (decompiled.c:204) and elsewhere for unrelated BSS/VRAM clears (decompiled.c:112-114). It is not SRAM-specific; its role here is purely to prepare the source buffer passed to func_0x08004dc8.

3.3 Serialization / checksum routine

FUN_0807caf4 (0x0807caf4) is the header-block serializer. It:

  1. Writes byte 0x30 ('0') at struct offset 0x08 and 0x31 ('1') at offset 0x09.
  2. Writes one byte from *_DAT_0807cb58 at offset 0x0A, and the constant 1 at offset 0x0B.
  3. Copies 20 bytes from a fixed source (_DAT_0807cb5c) into offsets 0x0C–0x1F — this is the

"AGBMetroid_USVerE003" build tag.

  1. Zeroes the first word (offset 0x00) and sets the second word to 0xFFFFFFFF (offset 0x04) as

checksum placeholders.

  1. Sums all 32 little-endian 32-bit words of the 128-byte block (loop over 8 groups of 4 words) into

uVar3.

  1. Stores uVar3 at offset 0x00 and ~uVar3 at offset 0x04.
  2. Calls FUN_08000dac to flush the finished 128-byte block to SRAM.

This is a sum32 / one's-complement-pair checksum: stored_sum + stored_complement == 0xFFFFFFFF always holds by construction, giving the validator a cheap internal-consistency check independent of recomputing the sum.

3.4 Validator / reader-side integrity check

FUN_0807cc34(param_1) (0x0807cc34) validates a 128-byte candidate block (param_1==0 selects the block at a base pointer; param_1==1 selects base pointer + 0x80 bytes). It:

  1. Recomputes the same 32-word sum and compares it against the stored sum (bit 0x1 of the result

if mismatched).

  1. Compares the 20-byte build tag against a reference string _DAT_0807cca4 byte-by-byte (bit

0x2 if any byte differs).

  1. Checks stored_sum == ~stored_complement (bit 0x4 if the pair is inconsistent).

A return value of 0 means "fully valid." FUN_0807cb60 calls this twice (param_1=0,1) and uses the results to choose which in-RAM candidate becomes the active save state before any further mutation.

3.5 Caller chain — how each caller reaches the hardware

FUN_0807cb60            (0x0807cb60)  — top-level save-menu entry; no static/traced caller
 ├─ func_0x0807d3d4()                 — SRAM presence self-test (write/read/mutate/verify, 16 B)
 ├─ if (*_DAT_0807cbb4 == 0)
 │    └─ FUN_08000e50() → func_0x08004c90(0xe000000, ram_mirror, 0x100)   [READ 256 B]
 ├─ FUN_0807cc34(0)                   — validate candidate slot A
 ├─ FUN_0807cc34(1)                   — validate candidate slot B (RAM +0x80)
 ├─ (branch on validity) mutates in-RAM struct fields at 0x02xxxxxx/0x03xxxxxx
 │    (exact RAM target addresses are opaque _DAT_0807cbbc/_DAT_0807cbb8/etc. in this trace)
 └─ if a save is due:
      ├─ FUN_08000d74()  → func_0x08004dc8(ram_mirror, 0xe000000, 0x8000)  [WRITE full 32 KiB]
      └─ FUN_0807caf4()  — recompute checksum + build tag, then
           └─ FUN_08000dac() → func_0x08004dc8(header, 0xe000000, 0x80)   [WRITE 128 B header]

FUN_0807caf4 is the only traced caller of FUN_08000dac besides FUN_0807cb60 itself (ghidra/callgraph.json: "0x08000dac": {"callers": ["0x0807caf4", "0x0807cb60"]}), i.e. the 128-byte header is only ever written immediately after the checksum is (re)computed — there is no path that writes stale/unchecksummed header bytes.

FUN_0807cb60 has zero recorded callers in ghidra/callgraph.json. The decompiler could not recover the indirect jump table at 0x0807cc2c/0x0807cae4 that reaches it, so the actual trigger (save-menu confirm, auto-save-on-exit, etc.) is outside this workspace's visibility and is left as an open question.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Checksum algorithm

  • Algorithm: sum32 over 32 little-endian 32-bit words (128 bytes), stored as a

sum/one's-complement pair.

  • Covered range: SRAM 0x00–0x7F inclusive (the full header block), including the two

checksum words themselves, which are forced to 0x00000000 and 0xFFFFFFFF respectively before the sum is taken (FUN_0807caf4, steps 4–6 above).

  • Stored offset: sum at 0x00 (4 bytes, LE), complement at 0x04 (4 bytes, LE).
  • Endianness: little-endian (ARM default / matches raw byte order in both .sav files).
  • Decompiled proof: FUN_0807caf4 / ghidra/decompiled.c:2676-2708 (identical copy also in

ghidra/save_related_functions.c:63-109).

4.2 Python verification against the real .sav files

import struct, hashlib
for fn in ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]:
    data = open(fn, "rb").read()
    blk = data[0:0x80]
    stored_sum  = struct.unpack_from("<I", blk, 0)[0]
    stored_comp = struct.unpack_from("<I", blk, 4)[0]
    words = list(struct.unpack_from("<32I", blk, 0))
    words[0], words[1] = 0, 0xFFFFFFFF          # placeholders forced by FUN_0807caf4 before summing
    total = sum(words) & 0xFFFFFFFF
    comp  = (~total) & 0xFFFFFFFF
    print(fn, "sum match:", stored_sum == total, "comp match:", stored_comp == comp)

Actual output (re-run in this workspace):

saves/cap-00-future-0.sav sum match: True comp match: True   (stored_sum=0xb8a9d7be)
saves/cap-01-future-1.sav sum match: True comp match: True   (stored_sum=0xb8a9d7be, identical)

Both samples verify exactly. The checksum is identical across both captures because the checksummed region (0x00–0x7F) did not change between captures — all 39 bytes that differ between cap-00 and cap-01 live at 0x7040–0x7066, entirely outside the checksum's covered range. This also means this checksum provides no integrity coverage whatsoever for the volatile 0x7040 region or the 0x100–0x1FF block — no second checksum routine covering those regions was found anywhere in the 100-function decompilation.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below target the paired pre/post .ss emulator save states that should accompany future capture rounds (per the project's mandatory paired-save-state rule); none currently exist in states/ for this legacy checkpoint cohort, so these are predictions to run, not results.

  1. Checksum-sum corruption (negative control).
  • Mutate 0x00 (one byte, e.g. +1) without touching 0x04.
  • Do not repair.
  • Predicted effect: FUN_0807cc34(0) returns a non-zero validity mask (bit 0x1 set) on next

boot; FUN_0807cb60's slot-selection branch should treat candidate 0 as invalid and fall back to whatever its else branch resolves to. Observable: boot-time save should be rejected (reset-to-default build tag / fresh-file behavior), confirming the checksum is load-bearing.

  1. Checksum-repaired build-tag corruption.
  • Mutate one byte inside 0x0C-0x1F (the "AGBMetroid_USVerE003" tag), then recompute and

rewrite the sum/complement pair at 0x00/0x04 so the checksum passes.

  • Predicted effect: FUN_0807cc34 bit 0x1 clears (checksum now "valid") but bit 0x2 sets

(tag mismatch) — this is the test that distinguishes "checksum algorithm correctly implemented" from "the whole 128-byte block, including the tag, is actually enforced on load."

  1. Complement-consistency-only corruption.
  • Set 0x04 to some value != ~stored_sum while leaving 0x00 and its true sum relationship

intact (i.e., break only the self-consistency check, not the recompute check).

  • Predicted effect: bit 0x4 sets in FUN_0807cc34's result even though the recomputed sum at

0x00 still matches. Confirms the two checks are independent, not derived from the same comparison.

  1. 0x7040 region clear/repeat.
  • From a state where 0x7040-0x7066 is populated (as in cap-01), force it back to all-zero

and reload under the emulator, then step forward the same number of frames as the original capture.

  • Predicted effect, if the HYPOTHESIS in §5 is correct (uninitialized-buffer leak): the region

stays zero indefinitely unless the same full-buffer flush (FUN_08000d74) runs again with a differently-uninitialized mirror — i.e. the content should not be deterministically reproducible gameplay data. If instead this turns out to be a real field, repeated identical play sessions from the same .ss should reproduce the same bytes at 0x7040 every time; any non-reproducibility across repeat runs is strong evidence for the leak hypothesis.

  1. 0x100-0x1FF perturbation.
  • Fill 0x100-0x1FF with a non-zero marker pattern, reload, and observe whether any boot-time

reader (only FUN_08000e50, which reads 0x00-0xFF, was traced touching nearby SRAM) ever reads or re-zeroes this block.

  • Predicted effect: since no traced function references this absolute offset, the marker pattern

should persist unchanged through a boot/save cycle if this analysis is complete; any observed change would prove an untraced writer exists and should prompt re-running the Ghidra trace with a wider function set.

  1. Footer tag corruption.
  • Mutate 0x7FF0 ('M' → any other byte).
  • Predicted effect unknown by design (no writer/reader traced) — this test is purely to discover

whether any boot-time code path depends on this tag at all (e.g. cartridge/region validation), since none was found in the available 100-function decompilation.

Checksum repair helper (for tests 2 & 3 above):

import struct
def repair_checksum(path):
    data = bytearray(open(path, "rb").read())
    words = list(struct.unpack_from("<32I", data, 0))
    words[0], words[1] = 0, 0xFFFFFFFF
    total = sum(words) & 0xFFFFFFFF
    struct.pack_into("<I", data, 0x00, total)
    struct.pack_into("<I", data, 0x04, (~total) & 0xFFFFFFFF)
    open(path, "wb").write(data)
