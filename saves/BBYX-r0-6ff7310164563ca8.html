Barnyard (Europe) (En,Fr,De,Es,It,Nl) — Clean-Room GBA Save Format Report

Release key: BBYX-r0-6ff7310164563ca8. ROM SHA-256: 6ff7310164563ca80d4b4df2da4dd9d638e77237715e141e146ca6503d3ff07f. Game code BBYX, header family BBY, community comm-003.

All findings derive only from this workspace: the two .sav binaries in saves/, the pre-computed hexdumps and diffs, the trace-guided Ghidra decompilation, the pre-extracted save functions, and the call graph, plus standard GBA hardware facts stated in PACKET.md.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is an 8 KiB EEPROM (EEPROM 64K), filled with 0xFF when erased.
  • The EEPROM file image stores every 8-byte block byte-reversed relative to the game's RAM byte order. Reversing each block is required before any field or checksum interpretation. This is proven in §4.
  • There are three game slots at EEPROM offsets 0x0000, 0x0880, and 0x1100, each 0x880 bytes, plus one global/config block at 0x1980.
  • Every block starts with the 8-byte magic bygba20\0 in RAM order. In file order it appears as 00 30 32 61 62 67 79 62, i.e. \0 followed by ASCII 02abgyb.
  • The integrity checksum is a custom rotate-left/add hash with seed 0xAA55A5A5, stored little-endian at header offset +0x0C. It verifies exactly on both supplied global payloads. See §4 for the formula and the Python output.
  • The boot-time caller chain in FUN_0800023c loads or recreates the global block, then loads or repairs all three slots.

Static-only facts (CONFIRMED_STATIC):

  • The same checksum routine covers 0x800 bytes for a game slot, but no occupied slot exists in the samples, so that exact coverage is not byte-verified.
  • A 12-byte secondary mirror check and five small summary-field comparisons exist in the slot loader. No occupied slot sample proves them.
  • Most slot-payload and global-payload field meanings remain unknown. Only offsets, types, defaults, clamps, and mirror relationships are mapped.

Open items are listed in §5 and in the open_questions array of save-format.json.

The slot stride 0x880 is not a guess. The slot loader computes param_1 * 0x880 for the header and param_1 * 0x880 + 0x80 for the 0x800-byte payload. The global offsets 0x1980 and 0x1A00 are literal call arguments. Only 0xE0 of the 0x600 bytes after the global header are read or written. The remaining bytes at 0x1AE0..0x1FFF stay 0xFF in both samples and are treated as reserved/unused.

Redundancy and selection rules:

  • There is no duplicate/backup copy of any slot or of the global block. Each region exists once.
  • There is no generation or sequence counter anywhere in the code or the samples. The header status word is the only selector.
  • Header status at +0x10 (RAM order, u32 LE) drives selection. 0 means empty. 1 means valid. 0xFFFFFFFF (-1) means present-but-invalid in RAM after a failed check.
  • Slot scan order is fixed: slot 0, then 1, then 2. FUN_0800dea4 loads each slot and recreates it as empty when loading fails.
  • The global block has no fallback. If its load fails at boot, FUN_0800023c calls the global factory-reset writer.
  • In both samples all three slots are empty (status 0, payload all 0xFF) and the global block is valid (status 1). The cold-reload probe in PACKET.md §1 mutated offset 0x1988, which is inside the stored-checksum block, and the save reverted to blank. That matches the checksum failure path in §3.

Active (non-0xFF) file spans are identical in both samples except for five bytes. Each header occupies file offsets +0x00..+0x27 with gaps of 0xFF. The global payload is non-blank at 0x1A00..0x1ADF only because its tail is zero-filled; zeros are data here, not fill.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level EEPROM driver (serial DMA3 bitstream)

The hardware layer is the Nintendo-style EEPROM access library. It talks to the EEPROM at 0x0D000000 through DMA3 registers at 0x040000D4.

The bit-level framing explains the file byte reversal. Data bits are shifted out and reassembled MSB-first inside each 8-byte block. The emulator .sav image preserves the serial order, so each block appears byte-reversed against the RAM buffer. §4 proves this with in-game default values.

How each caller mutates the in-RAM structs before flushing:

  • FUN_0800d838 (global factory reset). It zeroes a 0xE0-byte RAM payload with memset, then writes field defaults: u16 at payload +0 from a ROM literal, u16 1 at +2, u32 0xC0 at +4, u32 0x100 at +8, and u32 0 at payload byte offset 0xCC. It copies the magic into the header with strcpy, sets header status (+0x10) to 1, computes the checksum over the payload into header +0x0C, then writes header (0x80 bytes to 0x1980) and payload (0xE0 bytes to 0x1A00).
  • FUN_0800e2a8 (global save). It refreshes two payload dwords from ROM literals (*(payload + 4) and *(payload + 8) through its _DAT pointers), sets header status to 1, copies the magic, recomputes the checksum into header +0x0C, and writes header and payload to 0x1980/0x1A00. It ends with FUN_0800a558(0), an unidentified post-save hook.
  • FUN_0800db98 (slot create/erase). It zeroes the header summary fields (dword at +8, checksum at +0x0C, status at +0x10, bytes at +0x18..+0x1D, byte at +0x20), copies the magic, and writes only the 0x80-byte header to slot * 0x880. The payload region is left untouched (still 0xFF). When the slot index came from a previously playable profile (FUN_0801e7fc returns non-zero), it also refreshes the global block exactly like FUN_0800e2a8 and calls FUN_0800a558(0).
  • FUN_0800d8c4 (global load). It reads header and payload, checks the magic with strcmp, requires status < 2, then compares header +0x0C against FUN_08087c68(payload, 0xE0). On success it clamps payload fields in RAM: the signed u16 at payload +2 to 0..2, a signed u16 (through the psRam0800d974 pointer, payload-adjacent) to 0..5, and two dwords to 0..0x100. It does not write EEPROM on success.
  • FUN_0800dd30 (slot load). It reads the header, checks magic and status. Status 0 returns success immediately (empty slot, no payload read). Status 1 reads the 0x800-byte payload, runs the 12-byte mirror compare (payload + 0x40 vs header + 0x20), compares the five summary fields listed in §5, and compares the payload checksum (0x800 bytes) against header +0x0C. Any mismatch sets status to 0xFFFFFFFF in RAM. It never writes EEPROM.
  • FUN_0800dea4 (slot load-or-repair). It zeroes a 0x180-byte RAM area (0x120 + 3 × 0x80 header slots region) with FUN_0807db48, loads each slot with FUN_0800dd30, and calls FUN_0800db98 for any slot that fails, recreating its header as empty.
  • FUN_0800de34 (slot count). It reads each slot header, counts those whose magic compares equal, and stores the count in a RAM byte. Read-only against EEPROM.
  • FUN_0800023c (boot). It initialises EEPROM (FUN_0808bbb4), counts slots, loads the global block, calls the factory reset on failure, then runs FUN_0800dea4. Later boot code consumes the clamped global fields (for example FUN_0808b788/FUN_0808b994 receive values derived from the global header pointer). No other boot code writes the save regions.

No other function in the decompilation writes EEPROM offsets 0x0000, 0x0880, 0x1100, 0x1980, or 0x1A00. A text search for 0x880 and for the literal offsets confirms the save manager above is the only writer/reader set.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • RAM order (8 bytes): 62 79 67 62 61 32 30 00, ASCII bygba20 plus a NUL terminator.
  • File order (as stored in the .sav): 00 30 32 61 62 67 79 62, i.e. \0 followed by ASCII 02abgyb. This is the ascii_magic_strings value 02abgyb reported in PACKET.md.
  • Location: offset +0 of every 0x80-byte header (slots at 0x0000/0x0880/0x1100, global at 0x1980).
  • Verified in code: yes. Writers copy it with strcpy (FUN_08086af4 → FUN_080929f8); loaders compare it with strcmp (FUN_08086b48 → FUN_0809299c) and require a zero (equal) result.
  • Verified in .sav: yes, present at all four headers in both samples, in file order.

4.2 Block byte-reversal (required pre-processing)

The emulator .sav stores each 8-byte EEPROM block byte-reversed relative to RAM. Proof without any checksum assumption: the factory-reset defaults in FUN_0800d838 (u16 1 at payload +2, u32 0xC0 at +4, u32 0x100 at +8) appear in the samples only after reversing each 8-byte block. For example, file cap-01 payload block 0 is 00 00 00 c0 00 01 00 00 in file order and 00 00 01 00 c0 00 00 00 in RAM order. All offsets in §5 are given in file offsets, with RAM-order interpretation stated where it matters.

4.3 Checksum formula

Decompiled proof, from FUN_08087c68 in decompiled.c:

void FUN_08087c68(byte *param_1, int param_2) {
  uint uVar2 = _DAT_08087c84;              // seed, solved below as 0xAA55A5A5
  for (; param_2 != 0; param_2 = param_2 + -1) {
    if ((uVar2 & 0x80000000) == 0) iVar1 = uVar2 << 1;
    else                          iVar1 = uVar2 * 2 + 1;
    uVar2 = iVar1 + (uint)*param_1;
    param_1 = param_1 + 1;
  }
  return uVar2;
}

The branch is a 32-bit rotate-left by 1: rol32(h,1) in both cases. The exact algorithm is therefore:

  • h = 0xAA55A5A5 (seed; the _DAT_08087c84 literal value, recovered by inversion — see below).
  • For each byte b of the covered range, in RAM byte order: h = rol32(h, 1) + b (mod 2^32).
  • Classification: custom (rotate/add hash; not a sum, XOR, or CRC).
  • Stored as u32 little-endian at header offset +0x0C.
  • Covered ranges: global payload, 0xE0 bytes at EEPROM 0x1A00 (calls in FUN_0800d838, FUN_0800d8c4, FUN_0800e2a8, FUN_0800db98); slot payload, 0x800 bytes at slot * 0x880 + 0x80 (call in FUN_0800dd30). The slot coverage is CONFIRMED_STATIC; the global coverage is CONFIRMED_VERIFIED.

Seed recovery: the loop is invertible (h_prev = ror32(h_next - b)). Running the inversion from each stored checksum over its RAM-order payload yields the identical required seed 0xAA55A5A5 for both files. That cross-file agreement is the seed proof; no other seed fits both samples.

4.4 Python verification output (actual run in this workspace)

Script (run as python3 /tmp/verify_save.py; the same logic is reproduced inline below):

import struct
datas=[open(f'saves/cap-0{i}-future-{i}.sav','rb').read() for i in (0,1)]
def ram(d,s,l):
    out=bytearray()
    for o in range(s,s+l,8): out+=d[o:o+8][::-1]
    return bytes(out)
def ck(data,seed=0xAA55A5A5):
    h=seed
    for b in data: h=((((h<<1)&0xffffffff)|(h>>31))+b)&0xffffffff
    return h
for i,d in enumerate(datas):
    hdr=ram(d,0x1980,0x80); pay=ram(d,0x1a00,0xe0)
    stored=struct.unpack('<I',hdr[12:16])[0]
    print(f"cap-0{i}: stored=0x{stored:08x} computed=0x{ck(pay):08x} match={stored==ck(pay)}")

Observed output:

cap-00: stored=0x0a95a66b computed=0x0a95a66b match=True
cap-01: stored=0xca95a5ab computed=0xca95a5ab match=True

Stored file bytes at 0x1988..0x198B are 0a 95 a6 6b (cap-00) and ca 95 a5 ab (cap-01); after block reversal they are the little-endian dwords above. The five-byte diff between the samples (file offsets 0x1988, 0x198A..0x198B, 0x1A06..0x1A07) maps to RAM payload u16 at +0 changing 0xFFFF → 0x0000 plus the resulting checksum update. Without block reversal, no seed fits both files (checked by exhaustive inversion); with reversal, one seed fits both. The cold-reload probe result in PACKET.md (mutation at 0x1988 reverts the save to blank) is consistent: corrupting a stored-checksum byte makes FUN_0800d8c4 fail and triggers factory reset.

6. Save Fuzzing & Counterfactual Verification Plan

There are no paired .ss save states in this workspace (states/ is empty), so every prediction below is stated for a cold reload of a mutated .sav (the same protocol as the verified probe in PACKET.md). Each mutation lists the checksum repair needed, if any. To repair the global checksum after mutating the global payload: reverse each 8-byte block of file 0x1A00..0x1AE0 into RAM order, run h = 0xAA55A5A5; for b in payload: h = rol32(h,1) + b, store h little-endian at RAM header +0x0C, then re-reverse the header block into file order at 0x1980. To repair a slot checksum, do the same over the 0x800-byte payload at slot * 0x880 + 0x80.
