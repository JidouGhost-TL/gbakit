1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree, CONFIRMED_VERIFIED)

  • Physical media: 512-byte EEPROM (EEPROM 4K), SDK tag EEPROM_V122, accessed as a serial device at 0x0D000000 via DMA3.
  • Raw-to-logical byte mapping: every 8-byte block in the .sav file is the reverse of the game's logical EEPROM byte order. This is proven by the unpacking code in FUN_080279f0 and by the fact that the magic and checksum only verify after this transform.
  • Header magic: logical byte 0 = 0x28 ('('), written by the formatter FUN_080237e0 (0x080237e0) and tested by FUN_08023a24 (0x08023a24).
  • Checksum: 16-bit byte-sum over logical bytes 3..511, stored big-endian at logical bytes 1..2. Computed == stored on both captures (Section 4).
  • Geometry: a 3-byte header followed by five 100-byte sectors (offsets 3, 103, 203, 303, 403) plus 9 unused trailing bytes. The 100-byte size is proven by the literal call FUN_08023a24(100) in FUN_08007f20 and by the sector-1..4 word-21 values 0,1,2,3 in the saves (Section 2).
  • Sector 0 default contents and the blank profile template (sectors 1-4) match the initialisation code byte-for-byte, except three sector-0 words that gameplay had already changed.

Static-only (CONFIRMED_STATIC)

  • Function roles inside the SDK stack (Section 3) where the decompiler dropped arguments or left literal-pool values unresolved, and initialised field values that have no observed mutation yet.

Open / unknown

  • The gameplay meaning of almost every sector field. Both captures are near-initial states: sectors 1-4 are still untouched blank templates, and only sector-0 words 10, 16, 18 changed between the captures.
  • The actual EWRAM/IWRAM addresses of the RAM mirrors (Ghidra did not resolve the literal-pool pointers).
  • No caller that writes a sector during gameplay exists in the traced 140-function corpus. FUN_08007f20 is the only sector-API caller found.

The PACKET cold-reload probe is fully explained by the code: raw .sav offset 0x5 is the checksum low byte (logical byte 2), so mutating it makes FUN_08023a24 reformat the EEPROM to blank (Section 4.3).

2.1 Raw .sav bytes vs logical EEPROM bytes (critical)

FUN_080279f0 (EEPROM read) unpacks the 64 serial bits into 4 u16 values stored descending from buffer+6. The emulator's .sav therefore stores each 8-byte EEPROM block in reverse byte order relative to the game's logical addressing:

logical_byte(i) = raw_sav_byte( (i // 8) * 8 + (7 - (i % 8)) )
raw_sav_byte(j) = logical_byte( (j // 8) * 8 + (7 - (j % 8)) )

All offsets in this report (and in save-format.json) are logical EEPROM offsets unless explicitly marked "raw". Example, first block:

Bytes
Raw .sav 0x00-0x07 (cap-00)01 00 00 00 28 62 14 28
Logical 0x00-0x0728 14 62 28 00 00 00 01 = magic 0x28, checksum 0x1462, sector-0 word 0 = 0x28, word 1 low byte 1

Without this transform the header looks meaningless and the checksum does not verify; with it, everything verifies exactly (Section 4). This also means a .sav editor must reverse each 8-byte block before editing and reverse back afterwards.

There is no second copy of any sector and no mirrored region. The only redundancy is the per-block hardware verify (FUN_08027b7c re-reads and compares each 8-byte block after writing) and the whole-image checksum.

2.3 Selection rule and counters

  • Boot validation order in FUN_08023a24 (ghidra/decompiled.c:3768): sector size must satisfy 1 <= size <= 511; then header block is read; if byte 0 is not 0x28, or the stored checksum does not match FUN_08023830, the EEPROM is reformatted by FUN_080237e0. Any read failure also leads to the format path.
  • FUN_08007f20 (ghidra/decompiled.c:2281) then reads sector 0. If sector-0 word 0 is not 0x28, it initialises sector 0 in RAM and writes sectors 0-4 (Section 3.4). If word 0 is 0x28 and sector-0 word 5 < 4, it loads profile sector word5 + 1 into a second RAM buffer. Word 5 is therefore the active-profile selector (observed 0 in both saves → sector 1).
  • Sector API sentinel: passing sector index 0x400 to FUN_08023928 / FUN_080239c0 means "previous sector + 1", tracked in RAM (_DAT_080239a8 for writes, _DAT_08023a0c for reads). No traced caller uses the sentinel.
  • The profile word at byte offset +84 (word 21) holds 0,1,2,3 in sectors 1-4. Code proves this is written at format time as sector_index - 1 (Section 3.4); it is a stored slot copy, not evidence of a generation counter. No other counter-like field changes monotonically between the captures except sector-0 word 18 (0 → 1), whose role is unknown.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped

Two evidence sources were combined:

  1. ghidra/callgraph.json (140 nodes). It correctly records the SDK-internal edges, e.g. 0x080279f0 → 0x08027970, 0x0802368c → 0x0802366c, 0x08023928 → {0x08023720, 0x08023830}.
  2. Text search of ghidra/decompiled.c for the func_0x… alias spellings. This was essential: the game-level calls in FUN_08007f20 appear as func_0x08023a24(100), func_0x080239c0(…), func_0x08023928(…), which the callgraph does not record (it lists those functions with empty caller lists). Every caller claim below was confirmed by reading the function body at the cited line.

Known decompiler artefacts, flagged wherever they matter:

  • FUN_08023928 is displayed calling FUN_08023720(offset, buffer) with the length argument missing; FUN_080239c0 similarly calls FUN_0802368c(offset, buffer). The length is inferred to be the sector size (100) from FUN_08023a24(100) and the observed strides.
  • FUN_08007f20's first write is displayed as func_0x08023928(piVar1) with no sector argument; the destination is sector 0 by the offset formula and by the observed .sav contents.
  • All _DAT_0802xxxx / _DAT_0800xxxx literal-pool values (RAM pointers, limits such as _DAT_080238a8, the sector-size global) were not resolved to numbers by Ghidra, so RAM addresses and a few limits are stated as unresolved rather than guessed.

3.4 Game-level callers (the only ones in the corpus)

FUN_08007f20 (0x08007f20) — save-system boot/load, ghidra/decompiled.c:2281

No callers in the corpus; presumably reached from main-loop code outside the 140 functions. It is the only caller of FUN_08023a24, FUN_08023928, FUN_080239c0, and FUN_08007e48.

Happy path (valid save) — no RAM mutation, pure deserialisation:

  1. FUN_08023a24(100) — validates header + checksum (may silently reformat if corrupt).
  2. FUN_080239c0(sector0_ram, 0) — loads sector 0 (100 bytes at EEPROM offset 3) verbatim into the global RAM struct (pointer from _DAT_08007fc8; numeric RAM address unresolved).
  3. If sector0.word0 == 0x28 and sector0.word5 < 4: FUN_080239c0(profile_ram, word5 + 1) — loads the active profile sector.

A full-text search of ghidra/decompiled.c finds no other call to the sector API. Therefore the code that (a) changed sector-0 words 10, 16, 18 during play and (b) re-flushed sector 0 via FUN_08023928 is outside the traced corpus (or calls through a pointer the trace did not resolve). This is the single biggest gap in the corpus and the reason field semantics below stay at HYPOTHESIS/UNKNOWN.

4.2 Checksum formula

stored   = (logical[1] << 8) | logical[2]                 // big-endian u16 at offset 1
computed = ( Σ logical[i]  for i = 3 .. 511 ) & 0xFFFF    // byte sum, no seed, no complement

Decompiled proof:

  • FUN_08023830 (decompiled.c:3649): reads offset 3 len 8, sums its first 5 bytes (offsets 3-7); then loops offset = 8, 16, … reading 8 bytes and summing all 8, while offset <= _DAT_080238a8. Returns -1 on any read failure.
  • FUN_08023928 (decompiled.c:3711): after writing a sector, sum = FUN_08023830(); buf[0] = sum >> 8; buf[1] = sum & 0xFF; FUN_08023720(1, buf, 2);
  • FUN_08023a24 compares CONCAT11(byte1, byte2) (i.e. big-endian) against sum & mask.

Notes on precision:

  • The JSON schema's algorithm enum has no sum16_be; save-format.json records sum16_le as the nearest enum value and spells out the real (big-endian storage) formula in formula_detail. The summation itself is byte-wise, so endianness applies only to storage.
  • The exact loop bound _DAT_080238a8 is an unresolved literal. The sum is proven to cover at least offsets 3..502 (the last non-zero byte is at 499); bytes 503-511 are zero in both samples, so ends 503..511 are indistinguishable from the samples alone. The 512-byte EEPROM size and the 64-block format support 511; the fuzzing plan (Section 6, tail target) settles it empirically.
  • There is no per-sector checksum and no CRC/XOR/complement anywhere in the save path (full-corpus search). Integrity is this one global sum — which is why any single-byte corruption anywhere in 3..511 invalidates the whole save.

  • Blank-format prediction: after FUN_080237e0, logical bytes are 28 00 00 …, so the stored checksum would be 0x0000; FUN_08023a24 on such an image computes 0 and passes, after which FUN_08007f20 rebuilds sectors 0-4 because sector-0 word 0 (offset 3) is 0, not 0x28.

6. Save Fuzzing & Counterfactual Verification Plan

General repair procedure for every target marked "checksum repair": transform the .sav (reverse each 8-byte block), edit in logical space, recompute sum(logical[3:512]) & 0xFFFF, store it big-endian at logical 1-2, reverse each block back. Load from the paired save state / cold-boot the mutated .sav and observe UI, RAM (the 100-byte sector structs), and whether the .sav is rewritten.
