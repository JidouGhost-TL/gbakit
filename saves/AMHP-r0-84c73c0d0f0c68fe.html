  • Game code / header family: AMHP / AMH
  • ROM SHA-256: 84c73c0d0f0c68fea530cd7a17afb51b891528c267dc267ec34a64420fde052d
  • Save media (declared): EEPROM 64K (8192-byte .sav container; consistent with 64Kbit = 8KB serial EEPROM)
  • Evidence used: saves/cap-00-future-0.sav, saves/cap-01-future-1.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (87 functions), ghidra/save_related_functions.c (6-function EEPROM-bus seed set), ghidra/callgraph.json.

All findings below were derived exclusively from the four evidence sources listed above plus generic, publicly documented GBA hardware behavior (EEPROM serial protocol over DMA3 at 0x0D000000, DMA3 MMIO at 0x040000D4). No third-party game-specific wiki, decompilation project, or walkthrough was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (HIGH confidence):

  • The low-level EEPROM read/write/verify driver chain (6 functions) is fully decompiled and its control flow matches the textbook GBA 64Kbit-EEPROM serial bitstream protocol (address bits + opcode bits + 64 data bits, driven through DMA3 at 0x0D000000), purely from arithmetic present in the code itself.
  • The .sav container's physical layout: three byte-identical 768-byte redundant records plus one trailing 8-byte flag/state block, verified directly against both sample .sav files.

Open / unresolved (MEDIUM-LOW confidence):

  • No checksum, CRC, or other integrity-verification routine was found anywhere in the 87 decompiled functions. The only functions present besides the EEPROM bus driver are generic runtime helpers (memcpy, memset, strlen, a software integer divide) and an unrelated audio-mixer/sound-engine cluster. Whether any higher-level checksum exists at all is unconfirmed — it may live in code outside this extraction window.
  • The two sample .sav files are byte-identical across the entire 2304-byte redundant-record region, so no checksum formula could be exercised against changing data — only the trailing 8-byte flag block changed (0xFF…FF → 0x00…00). This limits what can be proven about any content checksum to "none was found in the available code," not "none exists."
  • The callers of the two top-level EEPROM entry points (FUN_0806bb40 write, FUN_0806bc24 verify) are not present in the supplied 87-function corpus (callgraph.json lists callers: [] for both). The full trigger chain from gameplay logic down to the save flush is therefore unknown.
  • Byte-level semantics of the two large data tables inside each record (a 120-entry flag/bitmask array and a 30-row numeric table) could not be assigned game-specific meaning from the materials provided, per the clean-room constraint — only their structural shape is documented.

2. Physical Media, Slot Geometry & Redundancy

  • Media: Serial EEPROM, 8192-byte .sav container (consistent with the declared "EEPROM 64K" / 64Kbit device). No SDK save-type tag string was detected in the ROM.
  • Active byte range: 0x0000–0x0907 (2312 bytes); everything from 0x0908 to 0x1FFF is the EEPROM erased-fill value 0xFF (unwritten).
  • Slot geometry — verified by direct byte comparison:
SlotOffset rangeSize
Slot 00x000–0x2FF768 bytes
Slot 10x300–0x5FF768 bytes
Slot 20x600–0x8FF768 bytes
Trailer block0x900–0x9078 bytes

Python comparison (slots[0] == slots[1] == slots[2]) against both .sav files returns True in every case — the three 768-byte slots are byte-for-byte identical in both samples. This is consistent with a triple-redundant mirrored record layout (a common EEPROM corruption-resilience pattern: write the same logical record to three independent 8-byte-block-aligned regions so a reader can majority-vote or fall back if one copy is corrupted).

  • Redundancy role / selection rule: HYPOTHESIS only. No slot-comparison, majority-vote, or "pick newest copy" function was found among the 87 decompiled functions, so the actual selection/repair rule used by the reader is unconfirmed. The only evidence for redundancy is the fact that all three copies are always kept byte-identical.
  • 768 bytes = exactly 96 EEPROM blocks (768 / 8) per slot; 3 slots = 288 blocks; the trailer block is EEPROM block index 288 (0x900 / 8 = 288), i.e. the very next block after the three slots. This block-aligned structure is strong evidence the whole layout was authored around the hardware's native 8-byte EEPROM block size.
  • Trailer / generation-flag block (0x900–0x907): 0xFFFFFFFFFFFFFFFF in cap-00-future-0.sav, 0x0000000000000000 in cap-01-future-1.sav. This is the only byte difference between the two samples anywhere in the active range. Candidate interpretations (all HYPOTHESIS, cannot be disambiguated with only two samples):
  • a one-shot "save has been written at least once" flag (erased 0xFF → written 0x00);
  • the low bytes of a save-generation/write counter that happened to start at 0 on its first flush;
  • a reserved/scratch EEPROM block that is simply zero-filled by the writer's buffer-init path and was never populated before the first flush.

A third sample captured after further save-triggering gameplay would disambiguate flag-vs-counter behavior.

3. Save Writer, Reader & Caller-Chain Architecture

All EEPROM bus access in the supplied corpus is confined to exactly 6 functions in ghidra/save_related_functions.c (also present in ghidra/decompiled.c). No other function among the remaining 81 touches 0x0D000000, 0x0E000000, or DMA3-pattern MMIO; the rest of the corpus is a generic memcpy/memset/strlen/software-divide utility cluster plus an unrelated audio-mixer/sound-channel subsystem.

3.1 FUN_0806ba08(void *src, void *dst, uint ctrl) — raw DMA3 transfer primitive

Low-level helper: saves/restores an interrupt-enable-like flag, programs a DMA source/destination/control triplet (*_DAT_0806ba78 = param_1 (SAD), *_DAT_0806ba7c = param_2 (DAD), *_DAT_0806ba80 = param_3 | 0x80000000 (CNT, enable bit set)), then busy-waits on the CNT high word's bit 0x8000 before returning — the canonical shape of a GBA DMA3-triggered serial transfer to/from EEPROM. It is address-agnostic; both of its callers pass the literal 0x0D000000 (GBA EEPROM I/O port) as one side of the transfer.

  • Callers (from callgraph.json): 0x0806ba88, 0x0806bb40.

3.2 FUN_0806b960 / FUN_0806b9c4 — DMA3 enable/disable helpers

Paired helpers invoked only from FUN_0806bb40: FUN_0806b960 programs a second DMA channel's control register (sets an IRQ-enable-shaped bit pattern, *_DAT_0806b9b0 |= (8 << n)) and stages a second source/length pair before an unresolved tail call; FUN_0806b9c4 clears that same bit pattern and tears the channel back down. Shape is consistent with bracketing a write with "enable the save IRQ/channel" / "disable it again" — classic save-driver bracketing.

  • Callers: both called only from 0x0806bb40.

3.3 FUN_0806ba88(uint block_index, int out_buf) — EEPROM READ, one 8-byte block

Validates block_index against a runtime-loaded block-count limit (*(ushort*)(*_DAT_0806baa0 + 4)), serializes the block address into a bit buffer (width taken from a runtime config byte at (*_DAT_0806bb3c)+8 — either 6 bits for 512-byte EEPROM or 14 bits for 8K EEPROM per generic GBA hardware behavior; the literal bit-width is loaded from a table, not a compile-time constant, so it is not directly readable from this decompilation), issues a read-request transfer via FUN_0806ba08(…, 0xD000000, (bits*0x10000 + 0x30000) >> 0x10) — the length encodes exactly bits + 3 halfword transfers (the address bits plus a 2-bit 11 read-opcode plus a stop bit, per the standard EEPROM serial protocol), then a second FUN_0806ba08(0xD000000, …, 0x44) transfer of exactly 0x44 = 68 halfwords (4 dummy bits + 64 data bits, again matching the standard protocol). The 64 returned data bits are unpacked MSB-first into 4 big-endian-ordered 16-bit words written to out_buf.

  • Callers: 0x0806bc24 only.
  • Role: EEPROM block READ.

3.4 FUN_0806bb40(uint block_index, ushort *data8) — EEPROM WRITE, one 8-byte block

Same block-index validation as 3.3. Serializes the 8 input bytes (data8[0..3], 4 × 16-bit words) MSB-first into a bit buffer, followed by the block address bits, followed by a 2-bit 10 write-opcode and a stop bit — exactly matching the standard EEPROM write-command bitstream. Issues the write via FUN_0806ba08(…, 0xD000000, (bits*0x10000 + 0x430000) >> 0x10), where the encoded length is exactly bits + 67 halfwords (2 opcode bits + 64 data bits + 1 stop bit = 67, plus the address-bit count) — again matching the documented protocol exactly. Brackets the transfer with FUN_0806b960() / busy-waits on the EEPROM ready bit / FUN_0806b9c4().

  • Callers (from callgraph.json): none found in the 87-function corpus. This is a top-level entry point; whatever game-logic code calls it to flush the in-RAM save buffer is outside the supplied extraction window.
  • Role: EEPROM block WRITE.

3.5 FUN_0806bc24(ushort block_index, short *expected8) — WRITE-VERIFY

Calls FUN_0806ba88 (read-back) into a local 8-byte stack buffer, then compares the readback to expected8 16 bits at a time, returning 0x8000 on the first mismatch, 0 if all four words match.

  • Callers (from callgraph.json): none found in the 87-function corpus — also a top-level/unresolved entry point.
  • Role: post-write verification (read-after-write compare), called separately from the write itself.

3.6 Caller-chain gap (explicit open question)

FUN_0806bb40 (write) and FUN_0806bc24 (verify) both show "callers": [] in ghidra/callgraph.json. Nothing in the 87-function corpus mutates a 0x02xxxxxx/0x03xxxxxx in-RAM save-record buffer and then calls either function — that higher-level "serialize record → call write for each of N blocks → call verify" driver is not present in this extraction. We cannot say what gameplay event triggers a flush, nor whether the triple-slot redundancy (Section 2) and the trailer flag (Section 2) are written/updated by one unified routine or several. This is the single largest gap in the traced architecture and should be the next capture-and-extract priority (a wider trace window around an observed save-trigger event).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature (verified in .sav, not traced to a writer function)

Each of the three 768-byte slots begins with the identical 16-byte header:

41 4D 52 45 42 4D 4F 42 D2 00 32 58 41 4D 2D 4E

Read as raw ASCII this is AMREBMOB + \xD2\x00 + 2XAM-N — not directly legible. However, reversing each 8-byte EEPROM-block-sized half independently yields legible text:

  • bytes 0x00–0x07 reversed → BOMBERMA
  • bytes 0x08–0x0F reversed → N-MAX2\x00\xD2

Concatenated: BOMBERMAN-MAX2 followed by two non-ASCII trailer bytes (\x00\xD2 in reversed order; \xD2\x00 in stored order). This matches the release's own title (Bomberman Max 2, per this packet's metadata) and is a direct, reproducible byte-reversal observation against the .sav files — not sourced from any external wiki. The per-8-byte-block reversal is also mechanistically consistent with the bit-serialization order used by FUN_0806bb40/FUN_0806ba88 (Section 3.3/3.4), which packs/unpacks each 8-byte block MSB-first in a way that can present as block-local byte reversal depending on how the caller originally laid the bytes out in RAM.

  • Verified in code: No — no writer of this header exists in the 87-function corpus.
  • Verified in .sav: Yes — byte-identical across all 3 slots, in both sample files.
  • Confidence: CONFIRMED_STATIC (proven against .sav bytes; writer not traced).
  • Open question: meaning of the trailing 2 bytes (0xD2, 0x00) — possibly a version/region tag — is unresolved.

4.2 Checksum / integrity algorithm

No checksum, CRC, or integrity-verification routine was found. Searched explicitly:

  • All 87 decompiled functions were enumerated (see ghidra/decompiled.c function list) — besides the 6-function EEPROM bus driver (Section 3) and the write-verify compare in FUN_0806bc24 (which is a direct byte/word compare, not a checksum), the remaining functions are FUN_0806bf98 (memcpy), FUN_0806bff8 (memset), FUN_0806c04c (strlen-like scan), FUN_0806bcf8 (software integer divide/modulo), and an audio-mixer/sound-channel cluster (0x08069774–0x0806a9a0 etc.) that never touches 0x0D000000/0x0E000000.
  • Python verification was run against both .sav files to test common checksum formulas (sum8, sum16, sum32, xor8, xor16) over the 0x000–0x8FF region:
region0 = b0[0:0x900]; region1 = b1[0:0x900]
print("region0 == region1:", region0 == region1)   # -> True
print("region0 sums:", sums(region0))  # (15, 15375, 15375, 97, 62099)
print("region1 sums:", sums(region1))  # (15, 15375, 15375, 97, 62099)
print("tail0 (0x900-0x907):", b0[0x900:0x908].hex())  # ffffffffffffffff
print("tail1 (0x900-0x907):", b1[0x900:0x908].hex())  # 0000000000000000

Because region0 == region1 exactly, every checksum formula naturally agrees between the two samples — this is not evidence of a working checksum, it is an artifact of the data never changing between captures. No byte range was found whose value tracks a formula computed over changing data, because no data changed except the unconditionally-flipped trailer block. Conclusion: checksum presence/absence is UNPROVEN with the current two-sample corpus; this is listed as UNKNOWN in save-format.json rather than asserting there is no checksum.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a fresh .sav copy, loaded via the paired pre/post .ss save states once available for this release, with no checksum repair step (none was confirmed to exist — see §4.2).

  1. Trailer-block reset. Mutate absolute offset 0x900–0x907 from 0x00×8 back to 0xFF×8 (simulating the never-written state seen in cap-00) while leaving the three slots untouched, then reload. Prediction: if this block is a pure "ever saved" flag, the game should behave identically to a normal load (data is present in all 3 slots regardless); if it gates whether the save is considered valid at all, the game should instead treat the cartridge as blank/new-game. Either outcome directly resolves the §2 trailer-block open question.
  2. Single-slot divergence test. Flip one byte inside the 0x120-row table of slot 0 only (e.g. in-slot offset 0x121, 0x05 → 0x06), leaving slots 1 and 2 (offsets 0x421, 0x721) at their original value, then reload. Prediction: if a majority-vote/repair reader exists (§2 hypothesis), the game should either silently correct slot 0 back to match slots 1/2 on next save, or visibly use the slot-1/2 value; if no such reader exists, the corrupted value in slot 0 should persist or cause a visible anomaly, disproving the redundancy-repair hypothesis.
  3. Magic-header corruption, single slot. Zero out in-slot offset 0x00–0x07 (first half of the magic block) in slot 0 only, reload. Prediction: tests whether any per-slot identity/validity check exists; a validity check would cause the game to ignore/rebuild slot 0 from slot 1 or 2, while no check would leave slot 0 silently corrupted (and FUN_0806bc24's read-after-write verify, if it is ever invoked on load rather than only on write, might flag the mismatch at 0x8000).
  4. Bitmask single-bit flip. Toggle one entry in the 0x30–0x11F array (e.g. in-slot offset 0x31, 0x01 → 0x00) identically in all three slots (to avoid confounding with test 2), reload, and observe for any visible UI/gameplay delta. Prediction: unknown pending event-aligned capture; this test's only goal is to establish whether this array is read at all during boot/load, not what any individual flag means.
  5. Numeric-table magnitude test. Increase one of the four non-zero words in a 0x120-row (e.g. in-slot offset 0x133, word index 2 of row 0, raise by +0x10) identically across all three slots, reload. Prediction: unknown; purely to establish read/consumption of this table, as a prerequisite before attempting any semantic labeling in a future round.

For every test above, record a fresh post-mutation .sav + paired .ss state and re-run the Section 4.2 Python diff script to confirm the only intended bytes changed (no unexpected checksum-repair or redundancy-repair side effects), which would itself be evidence for or against the hypotheses in Sections 2 and 3.6.
