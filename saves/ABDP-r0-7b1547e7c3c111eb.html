1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + both .sav samples agree):

  • The save medium is EEPROM, accessed through a generic bit-serial

DMA3 driver (0x0805efc8–0x0805f2f8) that implements the classic GBA EEPROM protocol: 2-bit read/write opcode + 6-bit block address + 64 data bits, MSB-first.

  • Each 8-byte EEPROM block is stored byte-reversed relative to the

in-RAM buffer the game logic actually reads/writes. This is proven, not assumed: reversing every 8-byte group of the raw .sav file turns a run of otherwise-meaningless bytes into the readable tag B-DASH EX\x00\x00\x00/ABDP-00, and — decisively — makes a 32-bit "sum of bytes" checksum match exactly in cap-01-future-1.sav (and show the EEPROM-erased sentinel 0xFFFFFFFF in the not-yet-written cap-00-future-0.sav).

  • A 24-byte identity/header record (logical offset 0x00–0x17,

EEPROM blocks 0–2) containing an ASCII tag + the literal ROM game code ABDP + a 4-byte checksum, with the checksum algorithm and coverage range verified by Python against both real .sav files.

  • The full write call chain from the generic "write save blob with

dirty-check" routine (FUN_0805d94c) down to the raw EEPROM bit-serial write-with-retry routine (FUN_0805f2f8/FUN_0805f1c4/FUN_0805f2a0), traced via ghidra/callgraph.json.

What remains open / unproven:

  • The actual gameplay-side caller(s) that build the in-RAM save image and

invoke FUN_0805dac4/FUN_0805d94c are not present in the 175-function trace-guided decompilation or the callgraph (both report callers: [] for the top of the chain). We therefore cannot show when in gameplay a save is triggered, only how the bytes get to EEPROM once triggered.

  • Only 2 .sav samples exist, both from the same "future" capture lineage

and differing by one save event. This is enough to prove the checksum algorithm and to locate mutating byte ranges, but not enough to disambiguate the semantic meaning (lives/score/level-select) of most individual fields with certainty — those are flagged HYPOTHESIS.

  • No second copy of either record was observed anywhere in the 512-byte

image, so slot redundancy/mirroring at the file level is not proven to exist (the only redundancy found is a RAM-side read-verify-before-write and write-then-read-back retry loop in the I/O driver itself).

2. Physical Media, Slot Geometry & Redundancy

  • Media: EEPROM, 512 bytes total (4K / 4-kilobit EEPROM — 512 bytes

= 64 bits × 64 words... actually 512 bytes = 64 blocks × 8 bytes). This matches the packet's Observed Save Media: EEPROM 4K and the .sav file size of 512 bytes.

  • Block size: 8 bytes (64 bits) per EEPROM address, addressed by a

6-bit block index (0–63), consistent with the bounds check if (param_1 < *(ushort*)(...+4)) seen in both FUN_0805f114 (read) and FUN_0805f1c4 (write) in ghidra/save_related_functions.c.

  • Byte order correction required: every 8-byte block in the raw file

must be reversed to obtain the logical byte order the game code actually operates on. All offsets in this report (unless explicitly marked "raw file offset") are logical/RAM-order offsets, i.e. after this per-block reversal. See §4 for the verification proof.

  • Records observed (2 of them, far apart in the 512-byte space):
RecordLogical rangeSizeRole (hypothesis unless noted)
Identity/header0x00–0x1724 B (3 blocks)CONFIRMED: ASCII tag + game-code + checksum
Config/progress snippet0x18–0x3732 B (4 blocks)HYPOTHESIS: per-save settings/counters

Blocks 0x38–0x1BF (the bulk of the EEPROM) are 0xFF (erased/unwritten) in both samples. Given FUN_0805dac4 writes blocks 3..N in a loop bounded by *_DAT_0805dc1c (an unresolved global, likely the total block count of a larger logical table — e.g. a high-score/level table with many slots), the simplest reading is that this is a sparse table most of whose entries are still blank, not a second physical save slot.

  • Redundancy: No second on-disk copy of either record was found in

either sample — i.e. no file-level slot mirroring is proven. The I/O driver (FUN_0805d94c → FUN_0805d834) does perform a read-verify before write (reads the existing EEPROM contents, checksums them, and skips the physical write entirely if the new data is byte-identical to what's already stored — an EEPROM wear-reduction optimization), and the low-level writer (FUN_0805f2f8) retries up to 3 times with a write-then-read-back-and-compare check (FUN_0805f1c4 then FUN_0805f2a0) per attempt. Both are RAM-side integrity mechanisms, not on-disk redundancy.

  • Generation/sequence counters: Two 32-bit counters were observed

incrementing by exactly 1 between the two samples: logical 0x1C0 (0→1) and logical 0x1CC (1→2). See §5 for field detail. No explicit "active slot selector" byte was identified; with only one populated stats record there is nothing to select between.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are in ROM (0x08xxxxxx).

3.1 Low-level EEPROM bit-serial driver (generic AGB-style, hardware-level)

These functions implement the standard GBA EEPROM access protocol (serial bitstream clocked through DMA3 at 0x040000D4/MMIO 0xD000000): START bits → opcode (10=write,11=read) → 6-bit block address → 64 data bits → STOP bit, busy-poll on the EEPROM ready line. This is textbook GBA hardware behavior, not game-specific code.

AddrRoleNotes
0x0805f094DMA3 transfer primitiveFUN_0805f094(src, dst, count); busy-waits on a ready flag at *_DAT_0805f100+6-derived pointer before issuing the transfer via an unresolved jump table (BIOS-style indirect dispatch). Called with dst=0xd000000 for sends and src=0xd000000 for receives — i.e. this is the raw "shift N bits in/out of the EEPROM bus" primitive.
0x0805efc8DMA3 arm/trigger helperSets several _DAT_0805f03x globals then falls into an unrecovered jump table; only ever called from 0x0805f1c4 right after a write-command bitstream is queued — consistent with "kick off the DMA and chain to completion handler."
0x0805f050DMA3 disarm/cleanup helperZeroes/clears the same class of globals as 0x0805efc8; only caller is 0x0805f1c4, invoked at the tail of a write, i.e. the matching teardown.
0x0805f114EEPROM block READFUN_0805f114(block_addr, out_buf). Builds a 2 (start bits ‘11’) + N address bits bitstream, sends it via two FUN_0805f094 calls (send request, then clock in 68 response bits = 4 dummy + 64 data), and unpacks the last 4×16-bit words in reverse word order into out_buf. This reverse-word unpacking is the root cause of the byte-reversal documented in §4.
0x0805f1c4EEPROM block WRITEFUN_0805f1c4(block_addr, in_buf). Builds 2 (start bits ‘10’) + 64 data bits (from in_buf, MSB first) + 6 address bits + STOP, sends it via FUN_0805f094, arms DMA via FUN_0805efc8, polls the EEPROM busy bit at 0xD000000, then disarms via FUN_0805f050. Returns a status word.
0x0805f2a0Read-back verifyFUN_0805f2a0(block_addr, expected_buf). Calls FUN_0805f114 to read the block just written, then compares all 4 words against expected_buf; returns 0x8000 on mismatch.
0x0805f2f8Write-with-retry (top of I/O driver)FUN_0805f2f8(block_addr, src_buf). Loop up to 3×: write via 0x0805f1c4; if the write itself didn't fail, verify via 0x0805f2a0; break on success. This is the function game logic actually calls (see §3.3).
0x0805f450, 0x0805f598Compiler-support unsigned/signed division helpersPresent in the "MMIO-seed" extraction only because of address proximity to the EEPROM driver; they have no save-specific behavior (generic long-division runtime routines) and no callers among save code. Not part of the save format.

3.2 Serialization / checksum routines

AddrRole
0x0805d834Read N EEPROM blocks + verify internal checksum, optionally copy out. FUN_0805d834(out_ptr_or_0, block_offset, block_count). Bounds-checks block_count against a max; reads block_count blocks via 0x0805f114 into a scratch buffer; computes sum of bytes[0, block_count*8 - 4) into a local accumulator; compares it against the last 4 bytes of the just-read blob (the on-disk checksum field); copies the blob out to out_ptr if non-null; returns 0 (checksum OK), 0x3000 (checksum mismatch / corrupt), or 0x5000 (block_count out of range).
0x0805d94cBuild + conditionally write a checksummed record. FUN_0805d94c(src_buf, block_offset, block_count). Builds a fixed 20-byte ASCII tag ("<12 bytes>/<4 bytes>-<2 bytes>" pattern — see §4), copies src_buf into a scratch buffer, computes the same "sum of bytes[0,len-4)" checksum and stores it in the last 4 bytes, then calls 0x0805d834 to read what's currently on EEPROM at that location. If the current on-disk checksum is valid and byte-identical to the new data, the write is skipped (dirty-check / EEPROM wear reduction). Otherwise it disables IRQs and writes every block via 0x0805f2f8, then re-enables IRQs.
0x0805d92c / 0x0805dac4Record-level wrappers. 0x0805d92c is a thin arg-count guard around 0x0805d94c. 0x0805dac4 builds the identity record (12+4+2-byte tag → "<12B>/<4B>-<2B>", with the middle 4 and trailing 2 bytes sourced from _DAT_0805db80/_DAT_0805db84), writes it via 0x0805d94c(buf, 0, 3) (3 blocks = 24 bytes = the header record in §4), and on success additionally loops from block 3 up to *_DAT_0805dc1c, writing one 8-byte block at a time directly via 0x0805f2f8 (no per-block checksum) — this is the loop that populates the sparse table mentioned in §2.
0x0805d70cRead/validate counterpart. Builds the same 20-byte tag pattern from live globals, reads the on-disk header via 0x0805d834(0,0,3), byte-compares the live tag against the stored tag and the stored checksum field against a freshly recomputed sum; sets a mismatch flag if either differs. This is almost certainly the boot-time "is this a valid save for this game/revision" check — it is what two different .sav files' identity tags would be checked against.

3.3 Caller chain (traced via ghidra/callgraph.json)

FUN_0805dac4  (no traced caller — game-logic entry point outside the
               175-function trace window; UNKNOWN)
   └─ FUN_0805d94c(header_buf, 0, 3)          // identity record, 24 B
         └─ FUN_0805d834(0, 0, 3)             // read+verify existing header
         └─ FUN_0805f2f8(block, src) × 3      // conditional write, line 6998
                └─ FUN_0805f1c4(block, data)  // raw write
                └─ FUN_0805f2a0(block, data)  // verify
                      └─ FUN_0805f114(block, out) // raw read
   └─ loop block=3..N: FUN_0805f2f8(block, table_src)   // line 7076, no checksum

callgraph.json confirms 0x0805f2f8 has no recorded callers inside the save-cluster (its only callers are the two direct call sites found by grepping decompiled.c, lines 6998 and 7076 — the trace-guided callgraph only captured the hardware-level cluster, not these two mid-level callers, which is why they had to be located by address cross-reference rather than via callgraph.json alone). Likewise 0x0805dac4 and 0x0805d94c's ultimate game-logic caller(s) are not present anywhere in the 175 traced functions — this is the chain's unresolved top and is listed as an open question in §6/§ open_questions.

How each traced caller mutates the in-RAM save image before flushing:

  • FUN_0805d94c (RAM src_buf → EEPROM): the caller is responsible for

having already populated src_buf (an arbitrary RAM buffer, address not resolved — passed as param_1, a 0x02xxxxxx/0x03xxxxxx-range pointer at the real call sites per standard C ABI, but the concrete address wasn't captured in this trace) with block_count*8 bytes of logical data; FUN_0805d94c itself only appends the 4-byte checksum — it does not mutate gameplay fields.

  • FUN_0805dac4 builds its own 20-byte tag directly from four small

global tables (_DAT_0805db7c, _DAT_0805db80, _DAT_0805db84, plus a literal //- separator) — this is the only place that constructs save content rather than just relaying a caller-supplied buffer, which is why the identity tag is reproducible/deterministic (same template every save) while the stats region is caller-supplied and therefore actually mutates between saves.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Byte-order correction (proof)

Raw file bytes (as stored in .sav) must be reversed in 8-byte groups to get the logical/RAM order the code above operates on:

def derev(d):
    return b"".join(d[i:i+8][::-1] for i in range(0, len(d), 8))

Applying this to cap-01-future-1.sav bytes 0x00–0x17 turns

raw:     45 20 48 53 41 44 2d 42 44 42 41 2f 00 00 00 58 00 00 04 1f 30 30 2d 50

into the readable, word-reversed-corrected logical bytes:

logical: 42 2d 44 41 53 48 20 45 58 00 00 00 2f 41 42 44 50 2d 30 30 1f 04 00 00
ascii:   B  -  D  A  S  H     E  X  .  .  .  /  A  B  D  P  -  0  0  .  .  .  .

i.e. "B-DASH EX\x00\x00\x00/ABDP-00" followed by 4 binary bytes — which is exactly the 20-byte tag + 4-byte trailer that FUN_0805d94c/0x0805dac4 build (<12-byte name>/<4-byte code>-<2-byte rev><2 pad> = "B-DASH EX\0\0\0" + "/ABD" wait — see exact field cut in §5). The literal substring /ABDP-00 reproduces the packet's own Game Code / Header Family: ABDP / ABD, confirming the de-reversal is correct (this is simply the ROM's own game code being echoed back by its own save code, not an imported external label).

4.2 Checksum algorithm

  • Name: identity-record checksum (header/tag checksum)
  • Algorithm: sum32_le — unsigned sum of each of the first 20 bytes

of the logical record, zero-extended and accumulated in a 32-bit register (no modulo, no carry folding; values this small — max 20 × 255 = 5100 — never overflow a byte-sum's worth of headroom at this record length).

  • Formula: checksum = sum(bytes[0:20]), stored little-endian at

logical offset 0x14..0x17.

  • Covered range: logical 0x00–0x13 (20 bytes) of the identity record.
  • Decompiled-C proof: FUN_0805d94c:
  *piVar4 = 0;                 // piVar4 = buf + (block_count*8 - 4)
  uVar5 = 0;
  uVar3 = param_3 * 8;          // block_count * 8 = 24 for the header
  if (0 < (int)(uVar3 - 4)) {
      do {
          *piVar4 = *piVar4 + (uint)*(byte *)(uVar5 + iVar1);
          uVar5 = uVar5 + 1 & 0xffff;
      } while ((int)uVar5 < (int)(uVar3 - 4));
  }

and the symmetric read-side check in FUN_0805d834:

  iVar4 = 0;
  if (iVar2 != 4) {
      do {
          iVar4 = iVar4 + (uint)*(byte *)(uVar5 + iVar6);
          uVar5 = uVar5 + 1;
      } while (uVar5 < iVar2 - 4U);
  }
  ...
  if (iVar4 == *(int *)(_DAT_0805d90c + 0x1fc)) { uVar1 = 0; } else { uVar1 = 0x3000; }

4.3 Python verification against real .sav files

import struct

def derev(d):
    return b"".join(d[i:i+8][::-1] for i in range(0, len(d), 8))

for name in ("cap-00-future-0.sav", "cap-01-future-1.sav"):
    raw = open(f"saves/{name}", "rb").read()
    logical = derev(raw)
    hdr = logical[0:0x18]
    computed = sum(hdr[0:20])
    stored = struct.unpack_from("<I", hdr, 20)[0]
    print(name, "computed=", hex(computed), "stored=", hex(stored), "match=", computed == stored)

Actual output:

cap-00-future-0.sav computed=0x13ec stored=0xffffffff match=False
cap-01-future-1.sav computed=0x41f stored=0x41f match=True

Interpretation: in cap-01-future-1.sav the stored checksum matches exactly, confirming the algorithm. In cap-00-future-0.sav the header record is still in its EEPROM-erased state (0xFF fill for all 24 bytes except the first few, with the checksum field reading the erased sentinel 0xFFFFFFFF), i.e. this record had not yet been written in that earlier capture — the mismatch there is expected and consistent with "identity record not yet written," not a broken algorithm.

No other checksum was found. The stats/slot record (0x1C0–0x1FF) is written by FUN_0805dac4's per-block loop using raw FUN_0805f2f8 calls with no trailing checksum field recomputation in that loop — a sum(0x1C0:0x1FB) vs. the trailing 4 bytes at 0x1FC was tested and does

not match in either sample, so that trailing value is treated as a plain data field (see §5), not a checksum, pending more samples.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty for this legacy checkpoint cohort), so the following plan is written to be run once paired pre/post save states become available, per repo policy (mandatory paired .ss captures for every future .sav snapshot).

All mutations below must be applied to the raw file, i.e. re-reverse the logical bytes back into each 8-byte block before writing (raw_block = logical_block[::-1]), and the identity-record checksum at logical 0x14–0x17 must be recomputed as sum(new_bytes[0:20]) and written back (also byte-reversed into its raw block) whenever any byte in 0x00–0x13 is changed, or FUN_0805d70c's boot-time validation will flag the save as corrupt.

Open Questions

  1. What is the concrete game-logic function (not present in this trace)

that calls FUN_0805dac4 / supplies the src_buf to FUN_0805d94c, and under what gameplay trigger (level clear, pause-menu save, death)?

  1. Is the 0x1C0–0x1FF region genuinely a single "current stats" record,

or one live entry in a larger high-score/level table whose other slots (0x38–0x1BF) are simply unused so far?

  1. Does FUN_0805d70c's tag/checksum mismatch actually gate anything

(e.g. force a "no save found" state), or is it only used for logging/ diagnostics? Requires runtime tracing or the fuzzing plan in §6.

  1. What are 0x1D8–0x1EF's actual semantics — are they truly static

level-geometry constants, or merely static so far across 2 samples of the same level?

  1. Why do two independent-looking counters at 0x1C0 and 0x1CC both

increment by exactly 1 per save but start from different values (0 and 1)? More samples are needed to determine if they are independent counters or a single 8-byte value misread as two u32s.
