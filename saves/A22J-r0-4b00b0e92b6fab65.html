1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is byte-addressed SRAM at 0x0E000000, total image size 32768 bytes (256 Kbit), erased/fill byte 0xFF, SDK tag SRAM_V110@4147608 (packet metadata).
  • Exactly one contiguous 8192-byte (0x2000) block is ever transferred, at SRAM offset 0x0000. The only SRAM-address literal in all 147 decompiled functions is the call FUN_08015154(0xe000000, _DAT_0801a818, 0x2000) in FUN_0801a6a8 at decompiled.c:3980. No Flash 0x5555/0x2AAA sequence, no EEPROM/DMA3 (0x040000D4) serial bitstream, and no other 0x0E000000 reference exists in the corpus (grep counts: 5555=0, 2aaa=0, eeprom/flash/dma string hits=0, 0e000000 literal=1 call site).
  • cap-00-future-0.sav is a fully blank image: all 32768 bytes are 0xFF. cap-01-future-1.sav differs in exactly the first 0x2000 bytes and is still all-0xFF from 0x2000 to 0x7FFF. This matches a single 8 KiB transfer and no other written region.
  • The populated block starts with the 16-byte ASCII magic POKEMON_TAKASHI2 at offset 0x00, followed by a mostly zero block: only 22 non-zero bytes exist in the whole 8 KiB (magic 16 bytes, 0x20, 0x24, and 4 bytes at 0x28). 8170 of 8192 bytes are 0x00.
  • No checksum, CRC, sum, or XOR stored anywhere in the populated block matches any standard candidate computed over any tested range (Section 4, with Python output). No checksum-computing loop (CRC table, polynomial, accumulating sum over the save buffer) was found in the decompiled save cluster. The integrity mechanism, if any beyond the magic, is the SRAM read-back verify wrappers FUN_0801cb44/FUN_0801ccbc, not a stored digest.

Static-only (CONFIRMED_STATIC, code seen, byte-level effect not independently observable in the two samples):

  • The boot-time caller chain FUN_08000234 -> FUN_0801a6a8 -> FUN_08015154 -> FUN_0801520c -> FUN_0801cb44/FUN_0801ccbc -> FUN_0801cda4 and the sibling path FUN_080151d0 -> FUN_0801cc1c + FUN_0801ccbc.
  • A descriptor struct of at least 4 words {addr_a, addr_b, length, flag} is used to parameterise the transfer (FUN_08015154, FUN_080151d0, FUN_0801520c all read the same three leading words).

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • Transfer direction of the RAM-copied payload FUN_0801cda4 (its body is an unrecovered jumptable in Ghidra), hence whether FUN_0801520c is the read or the write primitive. Boot context strongly favours read-at-boot (Section 3.4).
  • The exact RAM mirror address of the 8 KiB buffer: it is referenced only as _DAT_0801a818, whose value is not in the workspace files. It is in EWRAM or IWRAM (0x02xxxxxx/0x03xxxxxx); the exact address is UNKNOWN.
  • Semantics of the three non-zero header words at 0x20, 0x24, 0x28.
  • Which gameplay trigger invokes the write path in normal play: no static caller of FUN_080151d0 exists in callgraph.json; it is reachable only through the unrecovered jumptable dispatch used throughout this ROM, so its caller chain cannot be closed from the given files.
  • Packet metadata mentions 6 .sav files in the profile summary, but only 2 are present in saves/; all byte-level claims here rest on those 2. The packet also reports a cold-reload probe in which the populated save was preserved on load (save_preserved_on_load: true, reverted_to_blank_boot: false), which is consistent with, but not proof of, the read-at-boot reading.

Why not HIGH: the populated sample is almost entirely zeros, so most of the 8 KiB field map is unobservable; the write-side caller chain is hidden behind unrecovered jumptables; and the RAM mirror address is unresolved. Why not LOW: media, geometry, magic, transfer size/address, boot chain, and absence of a stored checksum are each supported by at least two independent evidence types.

Geometry notes:

  • SRAM on GBA is an 8-bit bus on a 16/32-bit-addressed window; the SDK (SRAM_V110) therefore moves data byte-by-byte. That is exactly the shape of FUN_0801cc1c (a byte copy loop, Section 3.2) and of the stack-copied payload used by FUN_0801cb44/FUN_0801ccbc (SRAM access routines are conventionally executed from RAM, which is why the code copies a halfword range (_DAT_… ^ 1) .. _DAT_… onto the stack and calls through it — the ^ 1 clears the Thumb bit to get a byte address).
  • There is no erase operation: SRAM needs none, and none exists in the corpus. "Erasure" of a save would be indistinguishable from writing zeros/0xFF over the block; the blank sample is simply a never-written (or fully 0xFF-written) image.
  • WAITCNT-style setup is visible in FUN_0801cb44/FUN_0801ccbc: *_DAT_… = *_DAT_… & (ushort)_DAT_… | 3; before the transfer — a read-modify-write of a hardware register (address unresolved, consistent with 0x04000204 WAITCNT SRAM wait-state bits) performed on every transfer. This is CONFIRMED_STATIC for the pattern, HYPOTHESIS for the register identity.

3.2 Low-level hardware I/O driver

There is exactly one SRAM data path, in two flavours sharing one descriptor:

  1. Descriptor setup — FUN_08015154(addr_a, addr_b, len) writes the three words into a RAM descriptor (*_DAT_080151bc) and sets a halfword flag at descriptor+0xC (*(undefined2 *)(puVar1 + 3) = 1). FUN_080151d0/FUN_0801520c read a descriptor from _DAT_08015200/_DAT_0801523c; whether these are the same RAM struct as _DAT_080151bc cannot be proven from the text (different literal symbols, values unavailable) — HYPOTHESIS: same descriptor, set up once by FUN_08015154 and reused.
  2. Plain byte copy — FUN_0801cc1c(src, dst, count): byte-at-a-time, exactly what an 8-bit SRAM bus needs. Used by FUN_080151d0 as FUN_0801cc1c(desc[1], desc[0], desc[2]), i.e. copy from desc[1] to desc[0]. With the boot call's values (desc[0]=0x0E000000, desc[1]=RAM buffer), that flavour is a write to SRAM (RAM → cartridge).
  3. RAM-copied payload — FUN_0801cb44(a, b, n) / FUN_0801ccbc(a, b, n): both (a) read-modify-write a wait-state register with | 3, (b) copy a small halfword code block from ROM (_DAT_… ^ 1 … _DAT_…) onto the stack, (c) tail-call FUN_0801cda4(a, b, n, stack_code + 1). This is the classic SDK pattern of executing the SRAM byte-access routine from RAM. FUN_0801ccbc returns the payload's result; FUN_0801cb44 discards it. In FUN_0801520c the sequence is FUN_0801cb44(desc[0], desc[1], desc[2]) (move) then result = FUN_0801ccbc(desc[1], desc[0], 0x94) (second pass whose non-zero result is treated as an error and logged with a string label). The constant third argument 0x94 (148) in the second pass is not the transfer length (that is desc[2]=0x2000 in the first pass); what 148 means to the payload — a compare length, a mode, or a mis-decompiled value — is UNKNOWN.

No Flash command sequence (0x5555/0x2AAA writes), no EEPROM DMA3 programming, and no DMA3 register writes (0x040000D4) appear in any of the 147 functions. The media identification as SRAM does not rest on the packet's say-so: it is the only mechanism the code implements, and it is byte-wide.

3.3 Serialization / deserialization & "checksum" routines

There is no serialization layer and no checksum routine in the save path:

  • The transfer is a verbatim byte copy of a fixed 8192-byte RAM block to/from SRAM offset 0. The .sav layout is therefore the RAM struct layout, byte for byte. This is directly visible in the populated sample: a C-style header (16-byte ASCII magic, zero padding, three u32 words) followed by a zeroed body — exactly what a zero-initialised RAM struct flushed verbatim looks like.
  • FUN_08019ee8 is strcpy and FUN_08019f1c is a strcmp (0 if equal). Their presence in FUN_08015154 (after the transfer: if the compare differs, strcpy a string into descriptor+0x10 and set two descriptor words to 1) is consistent with a magic-string check around the transfer — e.g. comparing the block's leading string against an expected POKEMON_TAKASHI2-style constant and recording the outcome in the descriptor. Ghidra dropped the compare's arguments (iVar4 = func_0x08019f1c();), so this is HYPOTHESIS, but it is the only string machinery anywhere near the save path, and the magic is the only string in the save. No arithmetic checksum (sum/XOR/CRC) exists in the cluster; corpus-wide, the only CRC-like candidate would have to hide inside the unrecovered payload FUN_0801cda4, and Section 4 shows no stored value behaves like a digest.
  • Verification after transfer is by re-transfer/compare (FUN_0801ccbc returning a status that both FUN_080151d0 and FUN_0801520c test), i.e. read-back verification, not a stored integrity field. If the payload's second-pass result is a first-mismatch indicator, the "integrity algorithm" is byte-equality of the two copies — again, not a stored checksum.

3.4 Caller chains — how each caller was mapped, and how it mutates the RAM struct before a flush

Mapping method, applied uniformly: (1) start from the single MMIO seed FUN_0801a6a8 in ghidra/save_related_functions.c; (2) take its callers/callees from ghidra/callgraph.json; (3) cross-check every edge against the actual call spelling in ghidra/decompiled.c, because the callgraph systematically misses edges spelled func_0x… (e.g. FUN_08015154's call to FUN_0801520c, and FUN_08000234's call to FUN_0801a6a8, are absent from the JSON but present in the C); (4) walk two hops out from the seed and read every reached body in full. Any caller reachable only through an UNRECOVERED_JUMPTABLE is reported as unclosable rather than guessed.

Direction argument for Chain A: FUN_0801a6a8 runs at boot, from the reset entry FUN_08000234, before any gameplay code. If its 8 KiB transfer wrote SRAM, every boot would overwrite the player's save with whatever the freshly zeroed work RAM contains — and the packet's cold-reload probe (save_preserved_on_load: true) shows the populated save survives a load. The coherent reading is: FUN_0801cb44(desc[0]=SRAM, desc[1]=RAM, len) reads SRAM into the RAM mirror at boot, and FUN_0801ccbc performs the SDK verify pass. Confidence: CONFIRMED_STATIC for the chain and call order; HYPOTHESIS (strong) for read-direction, because the payload body FUN_0801cda4 is unrecovered and the decompiled text alone cannot exclude the reversed convention. How this caller mutates the in-RAM save struct before/after the transfer: before calling FUN_08015154, FUN_0801a6a8 zeroes the head of its work struct (*puVar1=0, bytes at +4,+5, halfword at +6), writes uRam04000000 = 0x1040 (a hardware register store, most plausibly DISPCNT-adjacent init, not a save field), zeroes ~24 scattered bytes at literal-derived offsets in the struct, and zeroes five 4-entry halfword arrays; after the transfer it lets the subsystem initialisers above run. However: the identity of this work struct (_DAT_0801a7e4) with the save RAM mirror (_DAT_0801a818) is not provable from the workspace files — the literal values are absent. The honest statement is: FUN_0801a6a8 provably zeroes a large RAM work struct and provably loads the save; that the zeroed struct is the save mirror (cleared before the load fills it, the standard pattern) is HYPOTHESIS. No other caller is shown by the code to write any specific save field (offsets 0x20/0x24/0x28) before a flush.

Chain B — write path (partially closable):

Who sets the descriptor for this path, who calls it, and what gameplay event triggers it (lesson completion, menu save, auto-save) are all UNKNOWN from the given files: callgraph.json lists no caller, and the ROM's habit of ending nearly every function with an unrecovered jumptable call means the trigger is inside one of those dispatches. The descriptor-setup helper FUN_08015154 is itself only called at boot, which suggests (hypothesis) the descriptor is set up once and both directions reuse it.

Chain C — non-boot callers of the helpers: none. Every save-cluster function's only static caller is in Chain A, except FUN_080151d0 (none) and the generic FUN_08019ee8/FUN_0801cf3c/FUN_0801cf9c, whose other callers are unrelated string/memory utilities. There is no second SRAM entry point hiding elsewhere in the 147 functions: the 0x0E000000 literal occurs exactly once in the corpus.

3.5 How the in-RAM struct is mutated before flushing — summary

  • Proven: at boot the work struct is zeroed at many offsets and defaults are installed (FUN_0801a9a4, called via func_0x0801a9a4() inside FUN_0801a6a8, writes 0x100/0 patterns into a 16-halfword window). A zeroed RAM struct is consistent with the populated .sav being 8170/8192 zero bytes.
  • Proven: the flush, when it happens, is verbatim — no field packing, byte swapping, or encoding step exists between RAM and SRAM in either flavour of the path.
  • Not proven / unknown: any gameplay-side writer of header words 0x20, 0x24, 0x28. No function in the corpus can be tied to those offsets, because without the RAM mirror's base address, struct-relative writes elsewhere in the ROM cannot be matched to save offsets. This is the single biggest open item (Section 6 of the JSON: open_questions).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • Bytes (hex): 50 4f 4b 45 4d 4f 4e 5f 54 41 4b 41 53 48 49 32 = ASCII POKEMON_TAKASHI2, offset 0x00, length 16, no NUL terminator within the field (offset 0x10 onwards is zero padding in the populated sample, so as a C string in RAM it would be NUL-terminated by the following zeros).
  • Verified in .sav: yes — present verbatim in cap-01-future-1.sav, absent (all 0xFF) in the blank cap-00-future-0.sav. The blank image would therefore fail any magic gate, which is the expected "no save" state.
  • Verified in code: partially. The string literal itself does not appear in the decompiled text (Ghidra corpus contains no string literals at all). The code-side evidence is circumstantial but real: the only string compare in the save cluster (FUN_08019f1c, strcmp-like) is invoked by FUN_08015154 immediately after the transfer, with a strcpy fallback into the descriptor on mismatch. verified_in_code is therefore recorded as false in the JSON (argument recovery failed), with the hypothesis noted. Honest classification: magic is CONFIRMED_VERIFIED as a byte pattern in the save; its role as the load-time validity gate is HYPOTHESIS.

Additional ranges tested in the same session (full block, 0x10..0x2000, 0x20..0x2000, 0x2C..0x2000, 0x00..0x28, each with sum16 and CRC32): no candidate equals 0x084A1097, nor does any candidate appear stored at any other offset — there is no other non-zero, non-magic byte in the block that a digest could hide in. Two structural observations clinch the negative:

  1. A digest over a block that is 99.7% zeros would be a near-constant function of the 22 non-zero bytes; the value at 0x28 has its top byte 0x08, the signature of a GBA ROM address (0x08000000 window: 0x084A1097 = ROM offset 0x4A1097), not of an arithmetic checksum. The overwhelmingly likely reading is that the RAM struct at +0x28 holds a pointer into ROM (e.g. to a data table or script) that was incidentally persisted by the verbatim flush. Persisted pointers are a hallmark of raw struct dumps.
  2. The code side agrees: no checksum loop exists in the save cluster, and the post-transfer integrity step is a second transfer pass (FUN_0801ccbc) whose result is treated as a status/error, i.e. read-back verification.

Conclusion: algorithm = none (no stored checksum). Formula, covered range, and stored offset are all "not applicable". Any fuzzing (Section 6) therefore needs no checksum repair — only the magic must remain intact, which is itself a testable hypothesis. Confidence: CONFIRMED_VERIFIED that none of sum8/sum16/sum32/xor8/CRC32 (full-block and tested sub-ranges, with and without the candidate word) is stored at 0x28; HYPOTHESIS that no exotic/custom digest exists elsewhere (it cannot, observably — there is nowhere for it to be stored in this sample — but a custom digest that is only computed and compared in RAM during the unrecovered payload cannot be excluded from the payload's unseen body; if it existed and mattered, corrupted saves would be rejected, which Section 6 tests).

6. Save Fuzzing & Counterfactual Verification Plan

General protocol for every target: copy cap-01-future-1.sav to a scratch image, apply exactly one mutation, load in the emulator from the paired save-state/boot flow, and record (i) whether the game boots to its normal state (compare against the packet's cold-reload baseline: populated save preserved, no revert to blank boot), (ii) any visible UI/lesson-state difference, (iii) whether the game re-writes SRAM (dump .sav after the session and diff — a byte-identical re-dump proves the mutated block was accepted and re-flushed verbatim; a reversion to the original bytes proves an in-RAM source of truth overrode it; a blanking proves rejection). No checksum repair is required for any target (Section 4.2: no stored checksum exists) — if any mutation below is rejected, that falsifies the no-checksum conclusion and the rejecting field must be re-investigated first. No paired .ss states exist in this workspace (states/ is empty), so "reload from the paired save state" means cold-boot reload of the mutated .sav; that limitation is noted, not papered over.
