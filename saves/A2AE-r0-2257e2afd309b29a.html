GBA Save Format Report — Disney Sports - Basketball (USA) (A2AE-r0-2257e2afd309b29a)

Clean-room analysis. Sources used, and only these: PACKET.md, saves/*.sav, saves/hexdump_and_diffs.txt, states/*.identity.json, save-related functions, decompiled.c, and callgraph.json, plus standard GBA hardware addresses given in the packet. No third-party game-specific source was used.

Offset convention (read this first). The emulator .sav file stores each 8-byte EEPROM block in serial order. The one proven reader, FUN_080fc3b8, reassembles each block into RAM in reverse u16 order, so the logical RAM image is the .sav file with every 8-byte block byte-reversed (rev8). All offsets in this report and in save-format.json are logical (RAM-image) offsets unless marked “raw”. For a single byte, raw_offset = (logical & ~7) + (7 - (logical & 7)). The magic (§4) only reads correctly in logical order, which is the proof that this convention is the game's own view.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree, i.e. CONFIRMED_VERIFIED):

  • Media is EEPROM, 512 bytes total in the file (EEPROM 4Kbit per PACKET.md: “EEPROM 4K”, SDK tag EEPROM_V122@1425880). Both .sav files are exactly 512 bytes: sav-00-f1501.sav sha256 86912120bffd5f8662873792d13ac185a43915e413f0fd4717c2757e523cb427, sav-01-f1525.sav sha256 84cd7487b88dbadae7461c3fab2281c15845cf2a1d42f212eda0af3b737a38ba (full hashes recomputed with Python hashlib; the packet/hexdump file only lists truncated prefixes).
  • The only save-bus I/O in the traced corpus is an EEPROM read of one 8-byte block at a time via DMA3 to the EEPROM window 0x0D000000: FUN_080fc3b8 (0x080fc3b8) → FUN_080fc338 (0x080fc338). See §3.
  • Magic at logical 0x00: DISNEY SOCCER (16 bytes, trailing 3 spaces), in both files, after rev8. Raw file bytes are 53 20 59 45 4e 53 49 44 20 20 20 52 45 43 43 4f (S YENSID RECCO). It literally says SOCCER, not Basketball — that is what the bytes contain; the shared comm-009 engine explanation is a hypothesis, not a fact.
  • Layout skeleton (byte-proven, semantics mostly not): header 0x00–0x17 (24 B), five 32-byte records 0x18–0xB7, three 108-byte records 0xB8–0x1FB, trailer 0x1FC–0x1FF. Records 0–3 of the 32-byte group are byte-identical; record 4 diverges in exactly 6 bytes. The second and third 108-byte records are byte-identical in sav-01. See §5.
  • The two snapshots are byte-identical for 0x00–0x14F. Between frame 1501 and 1525 the region 0x150–0x1FF changed from erased 0xFF to written (mostly 0x00, sparse flags). This proves writes are lazy/sequential at 8-byte-block granularity and that no whole-512-byte checksum with an unchanged stored value can cover the tail (see §4).

Not proven (stated plainly, not papered over):

  • No writer, serializer, or checksum routine is present in the traced corpus. FUN_080fc3b8 has zero callers in callgraph.json and no textual caller in decompiled.c. The EEPROM write routine most likely sits in the untraced address gap 0x080fc46C–0x080fc5DC, immediately after the reader. The game's save manager, its RAM mirror base (0x02xxxxxx/0x03xxxxxx), and every field's semantic meaning are therefore unknown, and this report does not invent them.
  • No checksum was verified. The candidate stored u16 at logical 0x10 (0xC78F) was not reproduced by any standard algorithm over any plausible range in either byte order (full negative results in §4). Integrity may be magic-only, custom, or the u16 may not be a checksum at all.
  • Two of the three “MMIO seeds” in save-related functions are false positives (0x0807c9e8 gameplay, 0x080fc8a4 modulo helper). Treating them as save code would be wrong; §3 closes them explicitly.

That inference is labelled HYPOTHESIS wherever it matters.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (proven)

FUN_080fc338 (0x080fc338) — generic DMA3 transfer. Role: read/write engine for the EEPROM serial stream (it is direction-agnostic).

  • Saves a control register (*_DAT_080fc398), clears it, programs DMA3 source (*_DAT_080fc3a8 = param_1) and destination (*_DAT_080fc3ac = param_2), then writes the DMA3 control register (*_DAT_080fc3b0 = (param_3 & 0xffff) | 0x80000000, i.e. count in low 16 bits + enable bit 31) and spins while the busy bit (0x8000 in the upper halfword) is set, then restores the saved register. The _DAT_080fc3xx placeholders are the DMA3 register block (0x040000D4 family per the packet's hardware facts); Ghidra did not resolve them to literal addresses, so the register identification is by pattern (source/destination/control-with-enable + busy poll), which is unambiguous.
  • Callers (from callgraph.json): 0x080fc3b8 only. Callees: none.

FUN_080fc3b8 (0x080fc3b8) — EEPROM read, one 8-byte block. Role: read. This is the sole proven save-bus function in the corpus.

  • param_1 = EEPROM block address, masked to 16 bits and bounds-checked: if (param_1 < *(ushort *)(*_DAT_080fc3d0 + 4)). On failure it returns the sentinel uRam080fc3d4 without touching hardware.
  • It unpacks the address into a serial bit buffer: it writes the address bits (count = *(byte *)(*_DAT_080fc464 + 8)) into a stack array of u16s (one bit per u16, LSB-first extraction of param_1), preceded by two 1 bits (the EEPROM read command/start bits), then calls FUN_080fc338(auStack_98, 0xd000000, addr_bits + 3) — DMA to the EEPROM window 0x0D000000.
  • It then calls FUN_080fc338(0xd000000, auStack_98, 0x44) — DMA from 0x0D000000, 0x44 = 68 halfwords (64 data bits + framing), and reassembles the data MSB-first: four times it folds 16 successive & 1 bits into a u16 (uVar4 = uVar4 << 1 | *puVar5 & 1) and stores the u16s to param_2 + 6, +4, +2, +0 (descending). That descending store is exactly why the logical RAM image is the .sav file with each 8-byte block reversed, and why the magic reads DISNEY SOCCER in RAM order. This is the decompiled-C proof linking code to .sav bytes; no other function in the corpus contains the 0x0D000000 literal (verified by search: the only two 0xd000000 occurrences in decompiled.c are these two calls).
  • Callers: none. callgraph.json records "0x080fc3b8": {"callers": [], "callees": ["0x080fc338"]}, save-related functions likewise lists “callers: none”, and a text search of decompiled.c finds no func_0x080fc3b8 reference. How the caller was mapped: there is none to map — the mapping is negative and was verified three ways (callgraph, seed file, text search). The caller must invoke the reader indirectly (function pointer / SDK dispatch table) or live outside the 591 traced functions. Consequently the RAM destination (param_2) — i.e. the in-RAM save struct base in EWRAM/IWRAM — cannot be named from this corpus, and no 0x02xxxxxx/0x03xxxxxx mirror address is claimed anywhere in §5 or in save-format.json (ram_addr: null throughout).

3.2 EEPROM type/identify helpers (static-only)

FUN_080fc1cc (0x080fc1cc) and FUN_080fc234 (0x080fc234) sit in the same 0x080fc1xx–0x080fc2xx SDK library cluster as the reader. FUN_080fc1cc selects between EEPROM type-table entries for param_1 == 4 and param_1 == 0x40 and returns 1 otherwise; FUN_080fc234 stores a type byte and table pointer for param_1 <= 3 and returns param_1 > 3. These match the shape of Nintendo EEPROM_V122 identify/set-type routines and support the media identification, but every _DAT_ operand is unresolved, both have no traced callers, and neither touches .sav bytes observably. Confidence: CONFIRMED_STATIC for “EEPROM SDK cluster exists”, UNKNOWN for any size mapping. Callees/callers per callgraph: none/none for both.

3.3 The missing writer / serializer / checksum (negative result, with the gap named)

There is no EEPROM write function, no erase function, no serializer, and no checksum function in decompiled.c or save-related functions:

  • Function-address gaps were computed from all 591 // 080xxxxx mode headers. In the EEPROM cluster the only large gap is 0x080fc3b8 → 0x080fc5dc (0x224 bytes). A standard EEPROM_V122 write routine (serial command + data + busy-wait, symmetric to the reader) fits that gap exactly and would start near 0x080fc46C, right where the reader's code ends. This is a hypothesis about location, stated as such; the bytes are not in the corpus, so no writer behaviour (write granularity beyond the observed 8-byte blocks, verify-after-write, busy polling) is claimed.
  • No function in the corpus loops over a save-sized buffer computing a sum/XOR/CRC that could be tied to the .sav image, and §4 shows no stored value matches any standard algorithm anyway. Any checksum routine, if one exists, is in the same untraced caller/gap.
  • There is no SRAM byte-copy loop and no Flash 0x5555/0x2AAA command sequence in the corpus (the only 5555 matches in decompiled.c are the arithmetic constant -0x55555555 in division code at lines 1116–1145). The packet's SRAM/Flash alternatives are therefore excluded, not merely unchosen.

3.4 False-positive seeds — closed, with their real caller sets

Per the packet, save-related functions seeds 3 MMIO candidates. Two do not survive inspection:

  • FUN_0807c9e8 (0x0807c9e8) — gameplay/entity update, not save I/O. It decrements a timer field (param_1[0x17]), calls the RNG-like helpers FUN_08045e48/FUN_08045e80/FUN_08045ec4 and the jumptable stub FUN_08000110, and writes gameplay fields (param_1[4], param_1[0x21], param_1[0x22]). No 0x0D000000, no DMA3 pattern, no EEPROM framing. Its callees per callgraph are 0x08000110, 0x08045e48, 0x08045e80, 0x08045e9c, 0x08045ec4; callers: none. The helpers FUN_08045e48/FUN_08045e80/FUN_08045ec4 (table-indexed value fetch and FUN_08007b0c-based random-range, at 0x08045e48/0x08045e80/0x08045ec4 in decompiled.c) are gameplay utilities that happen to be 2-hop neighbours of the seed; they do not mutate any save struct — they mutate the entity struct pointed to by param_1, whose fields (timers, flags at +0x84/+0x88/+0x8C) have no counterpart in the .sav layout. No caller of FUN_0807c9e8 mutates the in-RAM save struct, because this chain never reaches the save struct. Listing its 2-hop neighbourhood as “save callers” would be an error; the honest caller set for save purposes is empty.
  • FUN_080fc8a4 (0x080fc8a4) — unsigned modulo runtime helper (shift/subtract long division, calls func_0x080fc6ac on divide-by-zero). No I/O at all. Callers: none.

4.2 Checksum — exhaustive negative verification (no formula proven)

Candidate stored field: logical 0x10–0x11, bytes 8f c7 (u16 LE 0xC78F, BE 0x8FC7), identical in both files. It is the only non-trivial, non-record word in the header block (0x12–0x14 are 3f 3f 3f; 0x15–0x17 are zero).

Method (Python, run in this workspace; script logic: rev8 reconstruction, then for every 8-byte-aligned (start, end) with start ∈ [0, 0x160), end ∈ (start, 0x208], in both raw and rev8 domains, on both files, compute sum8, sum16 (byte sum), sum16/sum32 LE-word sums, their complements/negations, xor8, xor16 LE, CRC-16 Modbus/CCITT-false/XMODEM/Kermit, CRC-32 and its complement, Adler-32, and position-weighted sums; compare against every stored u16/u32 outside the covered range): 2827 raw hits, all spurious (small values like 0x10/0x3f occurring inside record data). Filtering to plausible integrity fields — stored at header 0x10–0x17 or trailer 0x120–0x12F, covered length ≥ 0x80, computed value > 0xFF — leaves zero credible matches. A targeted search for exactly 0xC78F/0x8FC7/0x3870/0x7038 also found only contrived sub-ranges (e.g. Adler-low over raw 0x4C–0x1C0), which is the signature of chance, not of a checksum.

Representative computed-vs-stored output (the verification the packet asks for; stored = 0xc78f in both files):

Two structural facts bound what the truth can be:

  1. Both files share the same candidate stored value (0xC78F) and the same bytes over 0x00–0x14F, but differ over 0x150–0x1FF (0xFF vs written). Any checksum covering any byte at ≥ 0x150 with stored field at 0x10 would have to change between the files; it does not. So either the covered range excludes the tail, or there is no such checksum.
  2. The dense 6 bytes at 0x124/0x190 (fd 7e bf df ef 03) are identical in two different records with different neighbouring data — a checksum of preceding data cannot be identical in both places, so that pattern is data (a bitmask), not integrity.

Conclusion for §4: formula, covered range, and stored offset are unknown (algorithm: unknown in save-format.json, with the candidate field recorded and match: false verification entries — reporting a guessed sum/CRC here would be fabrication). Decompiled-C proof for a checksum does not exist in the corpus; the likely home of any such routine is the untraced gap in §3.3. Fuzzing (§6) is designed to settle empirically whether the u16 at 0x10 gates loading at all.

6. Save Fuzzing & Counterfactual Verification Plan

Reload protocol for every target: write the mutated 512-byte image as the emulator save, cold-boot (or reload the paired pre-save state — sav-00-pre.ss f1482 for the first image, the f1501 state for the second — and play forward through the save trigger), then observe three channels: (a) title/menu UI (save present vs “no save”/reinitialise), (b) the RAM mirror once its base is located by watching FUN_080fc3b8's param_2 in a debugger (this also closes the report's main open question), (c) whether the game rewrites the .sav, and if so which 8-byte blocks change. Checksum repair: since no algorithm is verified (§4.2), step 0 of the plan is to learn whether repair is needed at all — targets below marked “repair unknown” must first be run without repair; only if the save is rejected does repair become the research question (then: brute-force the writer gap 0x080fc46C–0x080fc5DC by emulation, or accept/reject-test each candidate field). Open questions (carried into save-format.json)

  2. What lives in the untraced gap 0x080fc46C–0x080fc5DC? (Presumed EEPROM write/verify; serializer and any checksum likely there or in the untraced caller.)
  3. Is the u16 at logical 0x10 a checksum, an ID, or data? (Fuzz target 2 settles whether it gates loading.)
  4. What do the five 32 B and three 108 B records mean? (Only template-vs-divergent structure is proven.)
