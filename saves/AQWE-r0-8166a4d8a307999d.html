1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is 32 KiB SRAM (SRAM 256K), fill byte 0xFF. One single save, no slot/copy redundancy, no generation counter.
  • Header is the 14-byte ASCII magic GBGforAGB 0.9. at 0x00–0x0D, written and re-verified on load.
  • Bytes 0x0E/0x0F are a duplicated guard byte, not a data checksum. Every transactional write stores the same fresh byte at 0x0E (before the payload) and 0x0F (after it); load validation only checks byte[0x0E] == byte[0x0F]. This fully explains the packet probe at offset 0xE (mutation → mismatch → erase/reinitialise) and why the byte changed 0x88 → 0xB4 while the payload byte-sum changed only by +3.
  • The live payload is one contiguous 264-byte region 0x328–0x42F, split by code into sub-blocks A (0x328, 36 B), B (0x34C, 28 B), C (0x368, 32 B), D (0x388, 156 B), plus inferred E (8 B) and F (4 B). Factory defaults visible in the code (A.u32[0]=1, D.byte[4]=1) match both samples byte-for-byte.
  • The low-level path is byte-copy SRAM with write-verify-retry (×3). No Flash 0x5555/0x2AAA sequence and no EEPROM-over-DMA3 bitstream exist anywhere in the corpus.

Static-only (CONFIRMED_STATIC) or inferred (HYPOTHESIS/UNKNOWN) — the reasons confidence is not HIGH:

  • The guard byte is generated by an LCG (FUN_08043830) whose multiplier/seed are unresolved _DAT_ constants in this Ghidra export, so its exact value cannot be recomputed from a .sav. Only its equality role is proven.
  • Sub-block E/F SRAM offsets (0x424/0x42C) are inferred from contiguity plus a stack-layout argument, not read from a literal.
  • Block C (0x368) changed between samples but has no writer in the 168-function trace-guided corpus. The corpus is a subset of the ROM; several readers (records at 0x10, 0xC0, 0x2000) likewise have no traced writer and are all-0xFF in both samples.
  • No fixed EWRAM/IWRAM save-struct mirror could be proven. Every traced caller mutates a stack copy of a block and flushes the whole block. Any claim of a 0x02xxxxxx/0x03xxxxxx base address would be guessing; this report says so wherever the field table asks for a RAM address.
  • Both samples are near-factory state (3 flag bytes differ). Multi-byte scores/counters inside A/C/D, if any, are indistinguishable from padding on this evidence.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (method)

ghidra/callgraph.json and the C text disagree in a systematic way, and both were used, with the disagreement stated rather than hidden:

  1. Most save functions end in (*UNRECOVERED_JUMPTABLE)(...) — a Ghidra tail-call artefact. In callgraph.json those functions show "callees": [] (e.g. 0x0803f2c0, 0x0803fd90, 0x0803fdd0), even though the C body visibly calls the next layer. For those edges the textual references (func_0x0803fdd0(...), FUN_0803f2c0(...)) in decompiled.c are authoritative and are cited by line number.
  2. Where callgraph.json does record edges (non-tail calls), they were cross-checked against the C text. Example: 0x080438bc → [0x0801798c, 0x0803f668, 0x0803f67c, 0x0803fd20, 0x080436bc] matches decompiled.c:3969-3977 exactly; 0x080432c8 → [0x0803f30c, 0x0803fd20, …] matches decompiled.c:3804-3815.
  3. Second arguments of the read/write wrappers are frequently lost to the same jumptable artefact (func_0x0803f6d4(&stack0x000000c8); shows only the context). Buffer identities were therefore recovered from the few call sites where both arguments survive (e.g. decompiled.c:351-354, 3973-3975) and from stack-layout arithmetic in FUN_08003df8 (Section 3.4).
  4. param_1 of every wrapper is an opaque 8-byte save-context handle created on the stack and primed by FUN_0803fd20 (once-flag, decompiled.c:2415-2419). It is not a proven EWRAM/IWRAM struct address. Consequently "how each caller mutates the in-RAM save struct" is answered honestly below in terms of the stack copies that the code actually mutates; no caller in the corpus writes a fixed 0x02xxxxxx/0x03xxxxxx save struct before flushing.

3.3 Serialization, transaction wrapper, and integrity routines

FUN_0803f2c0(ctx, sram_offset, src, len) — the transactional writer (decompiled.c:2075-2091). Every payload flush in the game goes through it:

func_0x08043830();                    // advance LCG, result in extraout_var
auStack_18[0] = extraout_var;         // guard byte (low byte of LCG return)
func_0x0803fd90(param_1, 0xe, auStack_18, 1);   // guard copy 1 BEFORE payload
func_0x0803fd90(param_1, param_2, param_3, param_4); // payload
func_0x0803fd90(param_1, 0xf, auStack_18, 1);   // guard copy 2 AFTER payload

FUN_08043830() — guard-byte generator, not a checksum (decompiled.c:3927-3935): state = state * *_DAT_08043844 + 1; *state_ptr = state; return state >> 16; — a linear congruential generator. The multiplier and state seed are unresolved _DAT_ constants in this export, so the byte sequence cannot be recomputed here (open question, Section 6 of the JSON).

FUN_0803f00c(ctx) — boot validation (decompiled.c:1929-1956): reads 16 bytes at offset 0 via FUN_0803fdd0, byte-compares the first 14 against the magic (_DAT_0803f070), then applies the guard test on stack bytes cStack_a (sav 0x0E) and cStack_9 (sav 0x0F): if E != F the match counter is zeroed and, since it is then != 0xE, FUN_0803f074 formats the chip. One unexplained legacy branch — (cStack_a != '2') || (cStack_9 != '\0') — bypasses the equality test when E=='2' (0x32) and F==0; neither sample uses it, and it is recorded as an open question rather than interpreted.

FUN_0803f074(ctx) — format / factory-initialise (decompiled.c:1963-2070): calls FUN_0803fd50 (erase all 32 KiB), writes the magic via FUN_0803f2c0(ctx, 0, magic, 0x0E), reads it back and compares; on match it writes defaults for every sub-block (A: u32[0]=1; B: zeroed; C: zeroed; D: byte[4]=1; E: zeroed; F: via FUN_0803f720) and returns 1. On magic-verify failure it calls func_0x080b0e50(0, …) (error) and returns 0. This is exactly the "reverted to blank / save rewritten" behaviour in the packet probe.

3.4 All traced callers and how each mutates the save before flushing

(a) FUN_08003df8 — progression/unlock evaluation; caller FUN_0800621a (decompiled.c:258-1177; callgraph caller 0x0800621a, decompiled.c:1193-1194). This is the largest save caller. On entry (guarded by *_DAT_0800409c == 0) it primes the context and reads four blocks into stack buffers (decompiled.c:350-354): D via FUN_0803f6e8, E via FUN_0803f70c (dest &stack0x0000009c), A via FUN_0803f6a0 (dest &stack0x000000a4), F via FUN_0803f734 (dest &stack0x000000d0). The stack layout is self-proving and independently confirms block sizes/order: D occupies stack 0x00–0x9B (0x9C bytes), E sits at 0x9C (8 bytes, ends 0xA4), A at 0xA4 (0x24 bytes, ends exactly at the context 0xC8), F at 0xD0 (4 bytes). It then computes iVar6 = FUN_080437d0() (the 0xC0-record score total, decompiled.c:355) and walks threshold branches: as the total passes successive thresholds it sets flag bytes in the stack copies (stack byte 0x4B of D at decompiled.c:742; E bytes _3_/_2_/_1_ at lines 774/804/834/864; A words via puRam… pointers at lines 891–1080; A counter values 1..14 at lines 1086–1151; F bytes _1_/_2_ plus 0x30/0x31 at lines 1158–1164) and flushes each dirtied block once through FUN_0803f6d4 (line 388 also on the '+' branch, line 743), FUN_0803f6f8, FUN_0803f68c, or FUN_0803f720. Character tests ('\a', '*', '\t', '\n', '/') in these branches are byte values of the D/E stack copies, i.e. this function consumes flags it also sets — the exact gameplay identity of each flag is UNKNOWN (the byte constants are unlabelled in the export). This caller is the only traced non-init writer of blocks A, D, E, F.

(b) FUN_080438bc(code) — mark-one-flag; no callgraph caller (reached via jumptable) (decompiled.c:3958-3986). If *_DAT_08043910 == 0: idx = FUN_080436bc(code) (linear search of a 25-entry u16 table, returns −1 if absent, decompiled.c:3837-3845); if 0 ≤ idx < 0x19 it reads B (FUN_0803f67c) into a 28-byte stack buffer, sets byte[idx] = 1, writes B back (FUN_0803f668), then calls FUN_0801798c(0, code) (sound/UI). This is the concrete producer of the observed cap-01 change at 0x35D (B+0x11) if code maps to index 17 — index-to-item naming is impossible without the table contents (UNKNOWN).

(c) FUN_080437d0 / FUN_0803f390 / FUN_08043744 — score tally (reader only). Described in 3.3; mutates nothing, flushes nothing. Its return value drives caller (a).

(d) FUN_080432c8 — boot/init path (decompiled.c:3795-3821; callgraph callees include 0x0803f30c, 0x0803fd20). Primes the context, calls FUN_0803f30c(ctx, *_DAT_080432f8, &uStack_10) for one 8-byte record at 0x10+idx*8; if the read reports empty it clears a RAM flag (*puRam08043330 = 0), else sets a RAM bool from record byte cStack_f. It also issues display/sound configuration calls (FUN_08016c68, FUN_08016ab8, FUN_08017924) which are not save writes. It never flushes — the record's writer is outside the corpus.

(e) FUN_0803f074 (format) and FUN_0803f00c (validate) — described in 3.3. FUN_0803f00c has no caller in either the callgraph or a textual grep; like several functions here it is presumably reached through a function-pointer table outside the 168 traced functions. The same applies to FUN_0803f748 and to the read wrappers FUN_0803f6c4 (block C) — which is precisely why block C's writer remains unknown: its read wrapper exists but no traced caller invokes either C wrapper except the formatter.

Callers explicitly ruled out: FUN_08043244/FUN_080951cc (callgraph neighbours via FUN_08016c68/FUN_08016ab8) touch only display/sound state; FUN_080c09d8, FUN_080c0688, FUN_08095234 mutate game-object structs in RAM and never call a save wrapper (verified by grep for 0803f over all 6117 lines — the complete hit list is the functions named above plus the formatter).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

GBGforAGB 0.9. — 14 bytes, hex 47 42 47 66 6F 72 41 47 42 20 30 2E 39 2E, at SRAM offset 0x00.

  • In code: written by FUN_0803f074 via FUN_0803f2c0(ctx, 0, _DAT_0803f0d8, 0x0E) (decompiled.c:1986) and byte-compared after read-back in both FUN_0803f074 (decompiled.c:1989-1994) and FUN_0803f00c (decompiled.c:1940-1944). verified_in_code = true.
  • In .sav: present verbatim at 0x00–0x0D in both samples. verified_in_sav = true.

4.2 The integrity mechanism — duplicated guard byte (exact formula)

There is no checksum over the payload data in the traced code. The integrity algorithm is a write-transaction guard:

generate:  s = LCG(s)  where  LCG(s) = (s * MULT + 1) >> 16,  guard = LCG(s) & 0xFF
           (FUN_08043830, decompiled.c:3932-3934; MULT and the seed/state are
            unresolved _DAT_08043844 / _DAT_08043840 constants in this export)
write:     SRAM[0x0E] = guard ; SRAM[offset .. offset+len-1] = payload ; SRAM[0x0F] = guard
           (FUN_0803f2c0, decompiled.c:2082-2086)
validate:  accept iff SRAM[0x00..0x0D] == "GBGforAGB 0.9." and SRAM[0x0E] == SRAM[0x0F]
           (FUN_0803f00c, decompiled.c:1940-1951; legacy exception when
            SRAM[0x0E]=='2' and SRAM[0x0F]==0, untested on real samples)
on fail:   erase all 32768 bytes to 0xFF and write factory defaults (FUN_0803f074)

Algorithm name for the JSON schema: custom. Covered range in the transactional sense is the whole formatted save (0x00–0x42F); the stored bytes are at 0x0E and 0x0F (1 byte each, identical). A torn write (power loss between the payload and the second guard write) leaves 0x0E != 0x0F and is detected at next boot — this is a completion sentinel, and it detects no payload corruption that leaves the pair equal. That limitation is stated, not smoothed over: mutating any payload byte while leaving 0x0E == 0x0F will pass validation (see fuzzing target F2 in Section 6).

Because the LCG constants are not in this export, the guard value itself cannot be recomputed from the .sav bytes, and this report does not pretend otherwise. What can be — and was — verified on the real binaries is (a) the pair equality on both samples, (b) the falsification of every conventional checksum hypothesis, and (c) the consistency of the observed guard change with "fresh pseudo-random byte per transaction" rather than with any function of the payload.

Reading of the two apparent "matches": crc32_lo == 0x88 on cap-00 and sum8 == 0xB4 on cap-01 each hold for one file and fail on the other (0x07 ≠ 0xB4; 0xB1 ≠ 0x88). With two samples, a single-byte coincidence on one file is expected by chance (1/256 per candidate per file, and 42 candidate×file pairs were tested). Both hypotheses are therefore falsified as general algorithms, and no tested conventional checksum matches both files. The only invariant holding on both samples — and the only check present in the code — is byte[0x0E] == byte[0x0F]: 0x88==0x88 ✓, 0xB4==0xB4 ✓. verified_on_samples in the JSON records exactly this, with computed equality_check values, not an invented recomputation of the LCG byte.

Corroboration with the packet: the probe mutated offset 0x0E (one side of the pair) and the save "reverted to blank / was rewritten" — the precise prediction of the equality check plus FUN_0803f074. The packet's "candidate checksum span 0xE–0xF" is thus resolved: it is a 1-byte guard stored twice, not a 16-bit checksum.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for every target below: there is no data checksum to repair. The only repair ever needed is keeping sav[0x0E] == sav[0x0F]; any mutation that leaves the pair equal needs no other fix, and any mutation of one guard byte alone is repaired by copying it to the other offset. No paired .ss save states were supplied in this workspace (states/ is empty, per PACKET.md), so predictions are stated as observable boot/UI/RAM outcomes on cold reload; where a save state becomes available, the same mutations should be applied to the .sav and reloaded from the state.
