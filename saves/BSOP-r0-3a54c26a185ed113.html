1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (structure and integrity: HIGH; per-field gameplay semantics: LOW).

Proven by both decompiled code AND .sav bytes (verified):

  • Media is byte-addressed SRAM at 0x0E000000, 32 KiB (SRAM 256K) image. No SDK save tag string was detected in the ROM (PACKET.md §1), and none is present in the save data.
  • Save geometry: 3 slots × 4 redundant copies × 1440-byte (0x5A0) blocks. Slot stride 0x1680, copy stride 0x5A0. Used range 0x0000–0x437F; 0x4380–0x7FFF is never touched by traced code and is 0xFF in both samples.
  • Magic: single byte 0x2A ('*') at block offset 0x00; slot index byte at 0x01.
  • Checksum: stored u16_le at block offset 0x59C = bitwise NOT of the 16-bit sum of all u16_le words in [0x00, 0x59C). Verified in Python on 12/12 copies in cap-01-future-1.sav (Section 4).
  • Writer FUN_080090f0 (0x080090f0), reader FUN_0800917c (0x0800917c), default-init FUN_08008fe8 (0x08008fe8), save-all coordinator FUN_0803411c (0x0803411c), and its sole traced caller FUN_08034d58 (0x08034d58) form the complete save chain in the corpus.

Static-only (code seen, bytes consistent but not independently proving semantics): the default-init constant writes of FUN_08008fe8 and the mask/record writes of FUN_08008e98 / FUN_08008ee8 / FUN_08008f44 match nonzero bytes in the save, but what those fields mean in gameplay is not established.

Open / unknown: the exact RAM mirror base address; the meaning of nearly every payload field; why all 3 slots carry (near-)identical payload in the only non-blank sample. The corpus contains exactly one non-blank save, and it is a near-default state — only initialisation constants are nonzero — so progression-dependent fields cannot be named honestly. cap-00-future-0.sav is a blank, fully 0xFF-erased image (SHA-256 2d864c0b789a43214eee8524d3182075125e5ca2cd527f3582ec87ffd94076bc); cap-01-future-1.sav (SHA-256 ebc25d65a826a3392c3130d71682ea612dc90b50b4a3ac0fc5751f1a6e23166b) differs from it in 17,256 bytes, which is exactly the 0xFF → 0x00 zeroing of the used range plus the default constants below. There are no paired .ss save states (states/ is empty), so no load-behaviour prediction in Section 6 has been executed; the PACKET.md cold-reload probe only confirms a non-blank save is retained and recognised on boot.

Redundancy & selection rule. Each slot stores four byte-identical copies of the same 1,440-byte block (verified: all 4 copies byte-identical within each slot in cap-01). The reader FUN_0800917c(slot) walks copies in order +0x000 → +0x10E0, reads each into the RAM buffer (FUN_0805e8d8), and accepts the first copy satisfying all of: byte 0x00 == '*' (0x2A), stored checksum at +0x59C equals ~sum16 over [0, 0x59C), and byte 0x01 < 3. There is no generation/sequence counter anywhere in the block (the only cross-slot differences in cap-01 are byte 0x01 and the checksum high byte), so "newest copy wins" does not exist: it is purely first-valid wins, and copies are written in the same order they are read, so a torn write of copy 0 leaves copies 1–3 as fallbacks. If all four copies fail, FUN_0800917c calls FUN_08008fe8() to reinitialise RAM defaults; the caller FUN_0803411c then immediately rewrites the slot from that (repaired or defaulted) RAM buffer, so corruption is silently healed to defaults on the next save-all rather than reported.

Slot independence caveat. FUN_0803411c rewrites all three slots from the same RAM buffer on every invocation (load/repair each slot, store one clamped byte, flush each slot). In cap-01 the three slots are byte-identical except byte 0x01 (slot index, written by the writer from its param_1) and the resulting checksum. Either this capture saved the same state three times, or the "slots" are not independent player profiles in the way the geometry suggests. This is an open question (Section 6, and open_questions in the JSON).

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are ROM 0x08xxxxxx (Thumb). "How mapped" states the evidence used: direct call in ghidra/decompiled.c, edge in ghidra/callgraph.json, or byte-pattern match against saves/cap-01-future-1.sav.

The checksum offset (_DAT_08009178 / _DAT_080091ec) is a literal-pool value Ghidra did not resolve in the text; it is recovered as 0x59C from the .sav bytes (Section 4), which also pins the covered range to [0x00, 0x59C) and leaves 0x59E–0x59F as uncovered trailing pad inside the flushed 0x5A0 block.

Default init — FUN_08008fe8(void) (sole caller: FUN_0800917c on total copy failure):

  • Zero-clears the full block: FUN_080007d0(iVar3, 0x5A0) and a second buffer FUN_080007d0(puVar1, 0xB0). The 0xB0 clear plus the constant pattern below place puVar1 at save offset 0x4EC (0x4EC + 0xB0 = 0x59C, exactly the checksum offset) — this is an inference from the bytes, marked CONFIRMED_STATIC, because the pointer literals themselves are unresolved.
  • Clamps a byte (if (4 < bVar2) bVar2 = 0;) and writes defaults, including puVar1[0x2F]=2, [0x30]=2, [0x31]=1, [0x32]=1, [0x39]=1, puVar1[0..2]=0x78 (120), puVar1[3..4]=0x50 (80), a u32 value 1000 at puVar1+0x2C (u16-indexed, byte +0x58), 0xFF sentinel bytes, bit-OR writes (|= 8 at block +0x12/+0x1C, |= 2 at two tail offsets), and a second 1000 via an unresolved DAT offset. Every one of these constants that can be offset-mapped appears verbatim in cap-01 (Section 5).
  • Finishes by calling FUN_08008f44(0x12), FUN_08008e98(0), FUN_08008ee8(1, 1), each of which mutates one RAM field and then calls the derived-state recompute FUN_08008b08.

Derived-state recompute — FUN_08008b08(void) (callers: FUN_08008e98, FUN_08008ee8, FUN_08008f44; callee FUN_0800898c): reads a 5-byte-record array at RAM block +0x7E indexed by byte +0x92, calls FUN_0800898c(record, byte+0x4F, byte+0x9F, &u16[5], &u16[6], tmp) (table lookups with 0xFF = empty), clamps a derived u16 at +0x02 to 0xF0, zeroes cached u16s at +0x20..+0x2C (indices 0x10–0x16), sets bitfields from the 5 record bytes, and conditionally copies fields to a second struct (+0x6A, +0x6D, +0xA8 of a pointer at +0x4E8). This is gameplay-state derivation over the RAM mirror, not an SRAM routine; in cap-01 all its inputs and outputs are zero, so its exact save-offset footprint beyond the setters below is HYPOTHESIS.

Field setters (each stores one value, then calls FUN_08008b08):

  • FUN_08008e98(param): stores param at *(base + DAT) (unresolved), masks byte at block +0x540 with & 0xF3 | 2, and if bit 29 of the u32 at +0x510 is clear, zeroes bytes +0x97, +0x98. The +0x540 write is why save byte 0x540 is 0x02.
  • FUN_08008ee8(idx, val): writes val into the 5-byte record at +0x7E + byte[0x92]*5 + idx, masks byte +0x54 with & 0xF3 | 2, conditionally zeroes two bytes at an unresolved offset (guarded by bit 29 of u32 at +0x24).
  • FUN_08008f44(param): stores param - 0x12 (or -1 if param == 0) at *(base + DAT) (unresolved). Init passes 0x12, storing 0.

3.3 All callers traced, and how each mutates the RAM struct before flushing

Caller chain 1 (the only save entry point): FUN_08034d58 → FUN_0803411c → {FUN_0800917c, FUN_080090f0}.

  • FUN_0803411c(int param) (caller: FUN_08034d58 only, per callgraph.json): clamps param to [0, 4], then for slot = 0..2: calls FUN_0800917c(slot) (load/repair into RAM), stores the clamped byte to a single RAM byte *_DAT_0803414c (exact offset unresolved — it is stored once per slot with the same value, so in cap-01 it cannot be isolated; candidates are any byte that is equal across slots), then calls FUN_080090f0(slot) to flush. Net effect: every save-all rewrites all 3 slots (12 copies) from the current RAM buffer, refreshing magic, slot byte, and checksum each time. It does not itself mutate gameplay fields beyond that one byte.
  • FUN_08034d58(void) (no callers in callgraph.json; a top-level/state handler exiting through an unrecovered jumptable): most of its body is non-save work (palette/OAM-style writes via FUN_0800b080/FUN_0800b1a8, a u16 interpolation). The save-relevant branch, mapped by reading its decompilation directly: if a status byte has bit 0x20, it increments a counter byte and selects value 0; else if bit 0x10, it decrements and selects 1 (calling func_0x0805d618(0) — likely a sound/UI call — in both cases); the selected byte is clamped (> 0x80 → 2, > 2 → 0). Then, only if bit 0x01 of a second status byte is set, it calls func_0x0805d618(1), FUN_0803411c(clamped_byte), writes the same byte to *(DAT + 0x74), and calls FUN_080098f0(...). If bit 0x01 is clear but bit 0x02 is set and a byte at +0x51 is nonzero, it instead calls func_0x0805d618(2) and FUN_080098f0(other_arg) without saving. So FUN_08034d58 is the user-facing trigger (a settings/profile-style screen handler, statically inferred from the +/- adjust + confirm-to-save structure); the byte it adjusts in [0, 2] is the value FUN_0803411c stores per slot. Its semantic identity (difficulty? language? profile?) is unknown — in cap-01 all slots carry identical payload, so its save offset could not be isolated.
  • FUN_080098f0(int param) (caller: FUN_08034d58 only): after the save, writes param into a 0x14-byte-stride RAM table entry (*entry = param; *(entry+8) = 0xFFFFFFFF) if the entry is nonzero. This is downstream bookkeeping in RAM, not SRAM; its exact role is unresolved and it does not touch the .sav image directly.

Caller chain 2 (repair path): FUN_0800917c → FUN_08008fe8 → {FUN_080007d0, FUN_08008f44, FUN_08008e98, FUN_08008ee8} → FUN_08008b08 → FUN_0800898c. Mapped from callgraph.json edges (0x0800917c → 0x08008fe8; 0x08008fe8 → 0x080007d0/0x08008e98/0x08008ee8/0x08008f44; each setter → 0x08008b08 → 0x0800898c) and confirmed in the decompiled bodies. This chain mutates the RAM struct by total reinitialisation (Section 3.2), and only runs when a slot has no valid copy.

Caller chain 3 (normal load path): FUN_0800917c → FUN_0805e8d8. On success the RAM buffer simply becomes the stored block (the read is directly into the buffer the writer later flushes); no field-by-field deserialisation exists — the on-SRAM block is the RAM struct image, byte for byte. That is why every field offset in Section 5 is simultaneously a save offset and (base-relative) RAM offset.

Unresolved pointer caveat (applies to all of §3). Ghidra left every literal-pool pointer as _DAT_08009xxx with no resolved value in decompiled.c, so the RAM mirror's absolute base (0x02xxxxxx EWRAM vs 0x03xxxxxx IWRAM) cannot be stated from this corpus and is null in the JSON. Relative offsets within the 0x5A0 block are proven by the writer/reader loops and the .sav bytes; the tail sub-struct base +0x4EC is proven to CONFIRMED_STATIC by five independent constant matches (Section 5), not by a resolved pointer.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic. One byte: offset 0x00, value 0x2A, ASCII '*'. Verified in code (FUN_080090f0 stores 0x2A; FUN_0800917c compares (char)*ptr == '*') and in bytes (all 12 copies in cap-01; absent in blank cap-00). There is no multi-byte or ASCII-string signature, and no SDK tag.

Checksum — exact formula.

covered range : block bytes [0x000, 0x59C)   (716 u16_le words)
stored at     : block offset 0x59C, u16_le, 2 bytes (inside the 0x5A0 block; 0x59E-0x59F are uncovered pad)
algorithm     : sum16_le with bitwise complement ("~sum")
formula       : stored = (~( Σ u16_le[i]  for i in [0,0x59C) )) & 0xFFFF
equivalently  : (Σ + stored) & 0xFFFF == 0xFFFF

Decompiled proof (FUN_080090f0, identical loop in FUN_0800917c): accumulate uVar2 = uVar2 + *psVar5 over short* from buffer base to base + _DAT_08009178, then store ~uVar2 at that offset. (Signed vs unsigned accumulation is irrelevant modulo 2^16.) The unresolved _DAT value 0x59C was recovered by testing every even length against the real bytes — the unique length where stored == ~sum holds for all three slots is 0x59C (the trivial 0x59E "match" is just sum + stored == 0xFFFF restated and is not the loop bound, since the writer stores the checksum at the loop bound).

Additional validity gate (not part of the checksum): reader also requires byte 0x01 < 3. The writer sets byte 0x01 to the slot number, so this doubles as a slot-sanity check.

6. Save Fuzzing & Counterfactual Verification Plan

Method for every target: mutate a copy of cap-01-future-1.sav, repair the checksum where stated (stored = (~Σ u16_le[0,0x59C)) & 0xFFFF, u16_le at 0x59C, applied per mutated copy — repairing copy 0 alone suffices to load, since the reader stops at the first valid copy; repairing all 4 prevents the fallback copies from masking the mutation), reload cold (per the PACKET.md probe protocol), and observe gameplay/UI plus, where possible, the RAM mirror.
