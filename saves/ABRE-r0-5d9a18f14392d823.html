1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both code and .sav bytes (verified):

  • Media is byte-wide SRAM at 0x0E000000, total dumped size 32 KiB (256 Kbit), fill byte 0xFF.
  • Three slot geometries carved out of SRAM: slot 0 at 0x0000 size 0x100, slot 1 at 0x0400 size 0x100, slot 2 at 0x0800 size 0x300 (FUN_08005970 offset table + FUN_08005958 size table in decompiled.c).
  • An 8-byte magic BLEN0911 at slot offset 0x00, compared byte-by-byte by FUN_080059c8 against a ROM-resident string (_DAT_080059e0) in decompiled.c.
  • A 16-bit additive byte checksum: stored little-endian at slot offset 0x08, covering bytes 0x10, slot_size), computed by FUN_08005990 and read back by FUN_080059c0 (*(u16*)(buf+8)) in [decompiled.c. Recomputed in Python against the real .sav: slot 0 stored 0x70a1 == computed 0x70a1 (see §4 for full output). Alternative covered ranges ([0,0x100), [0,8), [8,0x100)) were falsified.
  • Reader/validator FUN_08005b64 returns status 0 = valid & populated, 1 = empty (*(u32*)(buf+0x10)==0), 2 = invalid (magic mismatch, buf[0x0A]==0, or checksum mismatch). Only slot 0 in the sample is populated; slots 1 and 2 are fully erased (0xFF).

Static-only (code present, no second sample to confirm on bytes):

  • The dispatcher FUN_08005bc8(op, slot) in decompiled.c: op=3 → validated read (FUN_08005b64), op=1 → func_0x08005a64(slot, 0), op=4 → func_0x08005a64(slot, 1), op=2 → func_0x08005af8(slot). The op=1/4 pair (flag 0/1) and op=2 are almost certainly write and erase/init, but their bodies were not recovered — 0x08005a64 and 0x08005af8 lie in the un-decompiled gap between FUN_08005a14 (0x08005a14) and FUN_08005b64 (0x08005b64), appear only as func_0x… call targets, and have no entry in ghidra/callgraph.json. Their exact roles are therefore labelled HYPOTHESIS, never verified.
  • The only recovered caller of the dispatcher is the boot/init routine FUN_0803d6bc, and it only ever calls op=3 (read/validate). No recovered caller invokes a write/erase op; write callers most likely reach the dispatcher through the many UNRECOVERED_JUMPTABLE indirect calls, so the write-side caller chain cannot be closed from this corpus.

Unknown / open:

  • Semantics of the payload bytes at slot offsets 0x10–0xFF beyond the first dword. Only one populated sample exists, with most payload bytes 0x00/0xFF, so no field inside the payload can be named responsibly.
  • Absolute RAM mirror addresses. The reader copies SRAM into a freshly heap-allocated buffer (FUN_080050d8 → allocator FUN_08005038, freed by FUN_08005174 → FUN_080050fc); there is no fixed 0x02xxxxxx/0x03000000 save struct recoverable from the decompilation, because every _DAT_0803d7xx/_DAT_080050xx global is an unresolved literal-pool pointer. All ram_addr values are therefore null in save-format.json.
  • Whether slot 2 (0x300 B) is a third game file, a larger profile, or a different record type. Its size alone distinguishes it; nothing else in the corpus does.
  • Generation/sequence counters: none exist. There is no counter, timestamp, or backup copy anywhere in the code path or the bytes (see §2).

Redundancy & selection:

  • No mirroring, no backup copy, no generation counter. Each slot occurs exactly once. The gaps 0x0100–0x0400, 0x0500–0x0800, and 0x0B00–0x8000 are erased padding, not copies — the reader never touches them (its copy length is exactly the slot size).
  • Selection rule: slots are independent records addressed directly by index. At boot, FUN_0803d6bc validates all three in order (FUN_08005bc8(3,0), (3,1), (3,2)) and records the outcomes in globals; it does not pick a "newest" copy, because there is no sequence field to compare. Validation status per slot: 0 valid/populated, 1 empty, 2 invalid/erased — an erased slot fails the magic test first and therefore reports 2, not 1, a distinction that matters for fuzzing (§6).
  • Slot 2 being 3× larger is the only structural asymmetry. With all three slots probed identically at boot, the most economical reading is three save files where the third holds a larger record, but that is a HYPOTHESIS; the corpus contains no second populated slot to test it against.

3.3 The unrecovered write side

FUN_08005bc8 proves a writer exists: op=1 and op=4 call the same target 0x08005a64 with a distinguishing flag (0/1), and op=2 calls 0x08005af8. By symmetry with the reader (which is op=3, sitting between them), the natural reading is:

  • 0x08005a64(slot, flag) — write/serialize: build the slot image in a bounce buffer (magic, buf[0x0A]=1-style valid byte, payload), compute FUN_08005990-equivalent sum into +8, copy RAM→SRAM. The flag likely selects full write vs. header-only/checksum-refresh. Hypothesis only — the body is absent.
  • 0x08005af8(slot) — erase/init a slot (fill with 0xFF or write an empty header). Hypothesis only.

Supporting circumstantial evidence from the bytes: in slot 0, offsets 0x20–0x8F are still 0xFF while 0x00–0x1F and 0x90–0xFF are written, and the checksum covers the 0xFF region too. That pattern is consistent with a writer that assembles the image in a RAM buffer that was not fully initialised (or writes the slot in two pieces) and then checksums whatever the buffer held. It is not consistent with a writer that zeroes the whole slot first. This observation is recorded as evidence, not as a proven mechanism.

The SRAM copy primitive itself (0x08005940 → 0x0805e6a4 → 0x08061968) is direction-agnostic (src, dst, len); the same primitive would serve the write direction with arguments swapped. Only the read instantiation survives in the recovered code.

3.4 Reader status semantics (FUN_08005b64)

buf = alloc(size(slot));
read_sram(slot, buf);                       // 0x08005a14
status = magic_ok ? 0 : 2;                  // via (int)(-m|m)>>31 & 2 on 0x080059c8 result
if (buf[0x0A] == 0) status = 2;
if (stored_u16(buf+8) != computed_sum(buf)) status = 2;   // compared as (stored-computed)<<16 != 0
if (*(u32*)(buf+0x10) == 0) status = 1;     // empty overrides invalid
free(buf);
return status;

Order matters: an erased slot (0xFF…) fails magic → 2; a slot with a valid header but zeroed payload dword reports 1 even if its checksum also fails, because the empty test runs last.

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Bytes (slot offset 0x00, 8 bytes): 42 4C 45 4E 30 39 31 31 = ASCII BLEN0911.
  • Code proof: FUN_080059c8 loops iVar2 from 0 to 7 comparing *(char*)(buf+iVar2) against *(char*)(iVar2 + _DAT_080059e0), returning 1 at the first mismatch and 0 after all 8 match (decompiled.c). The literal value of _DAT_080059e0 (a ROM string pointer) cannot be read from the decompilation alone; identifying it as BLEN0911 rests on the .sav, whose slot 0 the reader-side logic accepts and whose checksum verifies (below). The 0911 suffix is plausibly a format version, but with a single sample that reading is a hypothesis.
  • Byte proof: slot 0 of sav-00-f1162.sav begins 42 4c 45 4e 30 39 31 31 (saves/hexdump_and_diffs.txt and direct scan).

Checksum

  • Algorithm: 16-bit additive sum of unsigned bytes. Accumulator is a short (sVar1 = sVar1 + (ushort)*pbVar3), i.e. arithmetic modulo 65536. No XOR, CRC, complement, seed, or final negation.
  • Covered range: slot-relative bytes 0x10, size) — from pbVar3 = (byte*)(param_2 + 0x10) with count FUN_08005958(slot) - 0x10 ([decompiled.c). The header (0x00–0x0F) is excluded, so the magic and the stored checksum itself never feed back into the sum.
  • Stored location: slot offset 0x08, u16_le, read by FUN_080059c0 as *(undefined2*)(param_2 + 8) on the little-endian ARM target.
  • Formula: stored == (Σ buf[i] for i in [0x10, size)) & 0xFFFF.

Checksum-repair recipe used by every fuzzing target below: after mutating any byte in [slot+0x10, slot+size), recompute (Σ bytes) & 0xFFFF over that range and store it little-endian at slot+0x08. Header mutations (+0x00..+0x0F) never need repair, because the header is outside the covered range.

7. Open Questions

  1. Bodies of 0x08005a64 (write, flag 0/1) and 0x08005af8 (op 2): what exactly do the flag and op 2 select — full write vs. header refresh, and erase vs. initialise-empty-header?
  2. Which gameplay routines call FUN_08005bc8 with ops 1/2/4, and what RAM state do they serialise? Unrecoverable from this corpus (indirect jumptable calls); needs a runtime call trace or a fuller decompilation.
  3. Absolute RAM addresses behind _DAT_0803d76c–_DAT_0803d850 and the allocator globals: resolvable only with the ROM literal pool, which is not in the workspace.
  4. Meaning of payload bytes — especially slot+0xB3..0xB8 (03 03 00 03 FF 08) and the purpose of the 0xFF payload gap at slot+0x20..0x8F. Needs either more populated samples at different game progress or the T6 fuzzing campaign.
  5. Purpose of slot 2's triple size (0x300): third file, different record type, or shared/global data? The boot code probes it identically and caches (status==0) separately (*_DAT_0803d7a0), hinting at a distinct role.
  6. Is 0911 in the magic a version that other builds check differently, and is byte +0x0B (currently 0x00, never tested) a sub-version? Single-sample corpus cannot answer either.
  7. Exact behaviour of the copy engine FUN_0805e6a4/0x08061968 (WAITCNT handling for SRAM reads): inferred as a RAM-executed byte copy from structure, not from a recovered loop body.
