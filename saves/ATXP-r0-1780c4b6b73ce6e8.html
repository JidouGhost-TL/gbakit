1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven to a high standard (code and both .sav binaries agree):

  • The save lives on a 512-byte EEPROM (EEPROM_V122) and occupies exactly one 208-byte logical slot (EEPROM blocks 0–25, 8 bytes each). The remaining 304 bytes are 0xFF unused space in both captures, not a backup slot.
  • The integrity system is fully solved and verified on both samples: a byte-sum over the logical payload, stored twice (plain and XOR-masked with 0xDEADBEEF), plus a length field stored twice (plain and XOR-masked with 0x44890100). Every stored value was recomputed from the .sav bytes and matches exactly (§4, with runnable Python output). This explains the packet's cold-reload probe at physical 0x2 and its candidate checksum spans 0x2–0x3 / 0x6–0x7.
  • The serializer/deserializer field map is fully triangulated: FUN_08010c94 (write), FUN_08010a70 (read), and FUN_08010980 (default init) all operate on the same struct offsets (+0x54…+0x114) and the same logical buffer offsets (0x10…0xCF). After undoing the per-block reversal, cap-00 reproduces the FUN_08010980 defaults byte-for-byte across all 192 payload bytes (192/192), and cap-01 differs only in the two mutated header-checksum bytes-worth of fields plus the +0x54/+0x58 pair (§4.3, §5).
  • The EEPROM driver chain is fully traced from the high-level caller FUN_080115f0 down to DMA3 transfers to 0x0D000000, including 3-attempt write-verify per block (§3).

What keeps the overall rating at MEDIUM rather than HIGH:

  • The gameplay semantics of the 21 payload fields are unknown. Their offsets, sizes, types, writers, readers, defaults, and observed values are proven, but no decompiled code in the corpus names what struct+0x70 = 6 etc. mean in tennis terms. Two blob fields (108 B and 32 B) are copied as opaque byte blocks.
  • The absolute RAM base address of the save struct, and the exact identities of most gameplay (non-save) mutators of the struct, are not recoverable: several calls go through unrecovered jumptables (UNRECOVERED_JUMPTABLE warnings throughout), callgraph edges using the func_0x… spelling were not recorded as callees, and FUN_08010980/FUN_080115f0 have no direct callers in callgraph.json.
  • The 0x44890100 length-mask constant and 0xDEADBEEF sum-mask constant are derived from the .sav bytes and the XOR structure proven in code; the literal-pool values they correspond to (_DAT_08010f7c, _DAT_08010f80, _DAT_08010b28, uRam08010b3c) are not numerically resolved in the Ghidra C output (see §4.2 for why the assignment is nonetheless forced).

Everything labelled HYPOTHESIS/UNKNOWN below is a hypothesis/unknown, not a finding.

Slots, copies, mirroring

  • One slot only. EEPROM block addresses 0–25 hold the single logical save. There is no second copy at 0xD0 or anywhere else: bytes 0xD0–0x1FF are uniformly 0xFF in both captures, and the reader (FUN_08010a70) only ever reads starting at EEPROM address 0, for exactly (len+7)>>3 blocks, where len comes from the header at blocks 0–1.
  • No generation/sequence counter was found. The header contains a length and a byte-sum, each stored twice (see §4). Nothing in the header increments monotonically between the two captures except through the payload change itself. The payload pair struct+0x54/+0x58 changed from (-1, 0) to (0, 1) between captures, which is arithmetically a +1 step of a little-endian u64 at logical 0x10 (0x00000000_FFFFFFFF → 0x00000001_00000000); whether that pair is one u64 counter or two related u32 fields is a HYPOTHESIS (the serializer copies them as two separate 4-byte fields).
  • Redundancy is within the header, not across slots (details in §4):
  1. Sum stored plain and XOR-masked (0xDEADBEEF).
  2. Length stored plain and XOR-masked (0x44890100).
  3. Reader validates the length pair before trusting the length to size its read loop, then validates the sum pair after reading the payload.
  4. Writer verifies every 8-byte block by read-back compare, retrying each block write up to 3 times (FUN_0802dd18 → FUN_0802dbe4 + FUN_0802dcc0).
  • Selection rule: trivial — at load time the game reads blocks 0–1, checks length ^ mask == stored length-mask partner (FUN_08010a70, see §3.3), reads the rest of the slot, checks sum ^ mask == stored sum-mask partner, and only then deserializes. On any failure the load returns failure and the caller (FUN_080115f0, param2==0 branch) falls through to FUN_08010c94, which (re)writes the slot from the current RAM struct (normally the FUN_08010980 defaults) — i.e. a corrupt/blank save is re-initialized in place rather than falling back to a backup copy. This matches the packet probe: mutating physical 0x2 (inside the physical image of the masked sum) breaks the XOR pair, reverted_to_blank_on_mutation: true, save_rewritten_after_mutation: true.

SDK geometry notes

FUN_08010a70/FUN_08010c94 address EEPROM one 8-byte block at a time (block index in param_1, masked to 16 bits, range-checked against *(ushort *)(eeprom_params+4) in the drivers). The drivers read the EEPROM address-bit count from *(byte *)(eeprom_params+8); FUN_08010980 selects EEPROM type index 2 via FUN_0802d9b0(2, …) and calls FUN_0802d948(4) during save-system init. The exact numeric address-bit count for type 2 is not resolved in the decompilation (it lives behind _DAT_ pointers), so this report does not assert 6 vs 14 address bits; the observed 512-byte file and 26 used blocks are consistent with the packet's EEPROM 4K classification.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

Three sources were cross-checked for every edge claimed below:

  1. ghidra/callgraph.json direct callers/callees arrays;
  2. the actual call expressions in ghidra/decompiled.c — necessary because many save-path calls are spelled func_0x0802dd18(...), func_0x080231c4(...), etc., and those edges are absent from callgraph.json (e.g. it lists callees: [] for FUN_08010c94 even though the body calls func_0x0802dd18 in a loop). Where the two disagree, the decompiled body wins and the discrepancy is noted;
  3. field-offset triangulation: a function is only claimed to touch the save struct if it reads/writes the same struct-relative offsets (+0x54…+0x114) that the serializer uses, which is how the otherwise-orphaned FUN_08010980 was identified as the default initializer.

Unrecovered jumptables ((*UNRECOVERED_JUMPTABLE)()) terminate most of these functions in the Ghidra output. Those are the functions' normal returns/epilogues as mis-recovered by the trace-guided decompilation; callers were therefore taken from return-value usage at call sites, not from the jumptable noise.

3.1 Low-level hardware I/O driver (EEPROM serial bitstream over DMA3)

All EEPROM traffic funnels through one DMA helper. There is no SRAM (0x0E000000) byte-copy and no Flash 0x5555/0x2AAA command sequence anywhere in the save path; the only 0x0E000000-region hit in the corpus is unrelated division code (see FUN_0802e884 note below).

3.2 Serializer / writer: FUN_08010c94 @ 0x08010c94

Signature: FUN_08010c94(char *save_struct) -> status (1 = written, 0 = not). Sole direct caller in the corpus: FUN_080115f0 (§3.4).

Behaviour, in order (all offsets are struct-relative / logical-buffer-relative):

  1. Gate: does nothing unless save_struct[0] == '\0' (byte 0 is a live-state flag, set to 1 by FUN_080115f0 after a successful create; see §3.4).
  2. Serializes the struct fields into a RAM staging buffer (base _DAT_08010f74, an unresolved pointer) starting at logical offset 0x10, in this exact order, accumulating a running byte-sum of every payload byte written (iVar8/uStack_28: sum += (uint)*pbVar6 in each copy loop):

+0x54:4, +0x58:4, +0x5C:4, +0x60:1, +0x61:1, +0x64:4, +0x68:4, +0x6C:1, +0x6D:1, +0x70:4, +0x74:4, +0x78:2, +0x7A:2, +0x7C:2, +0x7E:1, +0x7F:1, +0x80:0x6C, +0xEC:0x20, +0x10C:4, +0x110:4, +0x114:4. These land at logical offsets 0x10, 0x14, 0x18, 0x1C, 0x1D, 0x1E, 0x22, 0x26, 0x27, 0x28, 0x2C, 0x30, 0x32, 0x34, 0x36, 0x37, 0x38, 0xA4, 0xC4, 0xC8, 0xCC respectively — the field map in §5. The final write offset is the total length, 0xD0 for this struct version.

  1. Builds the 16-byte logical header at buffer 0x00 from three u32 LE values (sum, length), each stored plain and XOR-masked (mask constants proven in §4):
  • buf[0x00..0x03] = sum (LE)
  • buf[0x04..0x07] = sum ^ 0xDEADBEEF (the code XORs with _DAT_08010f80 after copying the plain value out)
  • buf[0x08..0x0B] = length (LE)
  • buf[0x0C..0x0F] = length ^ 0x44890100 (uStack_20 = uStack_24 ^ _DAT_08010f7c, copied out last)
  1. Flushes: acquires the guard FUN_080231c4 (sets param+1 flag, calls FUN_0802a630), then for each block i in 0 .. (length+7)>>3 - 1 (26 blocks) calls FUN_0802dd18(i, buffer + 8*i); on any block failure releases the guard with FUN_080231dc and returns 0. On full success releases the guard and returns 1.

How it mutates the in-RAM struct before flushing: it does not — FUN_08010c94 is read-only w.r.t. the save struct (it only reads +0x54…+0x114 and the +0 gate byte). All mutation happens in its callers/initializers (§3.4, §3.5). This is worth stating plainly because it means every gameplay write to the struct that wants persistence must be followed (eventually) by a call path that reaches FUN_08010c94; in this corpus the only such caller is FUN_080115f0.

3.3 Reader / deserializer: FUN_08010a70 @ 0x08010a70

Signature: FUN_08010a70(char *save_struct) -> status (1 = loaded, 0 = rejected). Sole direct caller: FUN_080115f0.

Behaviour:

  1. Gate: save_struct[0] == '\0' required.
  2. Acquires the guard (FUN_080231c4), reads EEPROM block 0 and block 1 with FUN_0802db34 into two staging buffers. Any read error → release guard, return 0.
  3. Takes length = *(u32 *)block1_buffer (logical header offset 0x08). Validates the length pair: (length ^ _DAT_08010b28) == *(u32 *)(block1_buffer+4) — i.e. the second header-in-block-1 value must be the masked length. (Constant assignment in §4.2.)
  4. Reads the remaining blocks 2 .. (length+7)>>3 - 1 into the staging buffer (8 bytes per block) in logical order. Note the reader never reverses bytes within a block in RAM; the reversal in §4.3 is a property of how the emulator dumps EEPROM cells to the .sav file, not something the game does.
  5. Validates the sum pair: computes sum = Σ staging[0x10 .. length-1] bytewise, checks (sum ^ uRam08010b3c) == *(u32 *)staging (the masked-sum partner at logical offset 4 relative to the plain sum at offset 0; the code compares against the header word reached through puRam08010b40).
  6. On success, deserializes with the memcpy helper FUN_080322ac (word-at-a-time copy with byte tail; decompiled.c:6997) into exactly the offsets the writer read from:

buf+0x10→struct+0x54:4, +0x14→+0x58:4, +0x18→+0x5C:4, buf+0x1C→+0x60:1, +0x1D→+0x61:1, +0x1E→+0x64:4, +0x22→+0x68:4, buf+0x26→+0x6C:1, +0x27→+0x6D:1, +0x28→+0x70:4, +0x2C→+0x74:4, +0x30→+0x78:2, +0x32→+0x7A:2, +0x34→+0x7C:2, buf+0x36→+0x7E:1, +0x37→+0x7F:1, +0x38→+0x80:0x6C, +0xA4→+0xEC:0x20, +0xC4→+0x10C:4, +0xC8→+0x110:4, +0xCC→+0x114:4.

  1. Post-load struct processing (still inside FUN_08010a70): calls func_0x08025370(*(struct+0x64)) with the just-loaded +0x64 value (0x1000 in both captures), and if *(int *)(struct+0x54) != -1 calls FUN_08010fc8 (a 3-word struct filler: *p = idx; p[1] = table1[idx]; p[2] = table2[idx], decompiled.c at 0x08010fc8) — consistent with +0x54 being an index/ID where -1 means "none", though the exact call argument list is jumptable-truncated in the output, so this semantic is a HYPOTHESIS (see §5).
  2. Releases the guard (FUN_080231dc) on every exit path.

The guard pair FUN_080231c4/FUN_080231dc (0x080231c4/0x080231dc) set/clear a byte flag at param+1 and call FUN_0802a630/FUN_0802a678 respectively; they bracket all EEPROM access in both reader and writer and behave like a media lock/interrupt guard. Their deeper meaning is CONFIRMED_STATIC as bracketing, UNKNOWN beyond that.

3.4 Top-level caller: FUN_080115f0 @ 0x080115f0 and the boot chain

FUN_080115f0(param_1, param_2) is the only function in the corpus that calls either the reader or the writer (both edges are present in callgraph.json: callees: [0x08010a70, 0x08010c94]). It has no callers in callgraph.json; like many state handlers in this ROM it is reached through an indexed dispatch — FUN_08000280 (0x08000280, the entry function) ends its init by dispatching through (**(code **)(*_DAT_080002fc * 4 + _DAT_08000300))(), an index into a function table, after calling func_0x0802ddcc() (a once-only init that runs FUN_0802dd80 → FUN_080232f4; those two are init-list machinery, not EEPROM functions, despite the numerically adjacent addresses). The dispatch table contents are not resolved in the provided files, so the edge FUN_08000280 → … → FUN_080115f0 is CONFIRMED_STATIC that a table dispatch exists, HYPOTHESIS for the exact slot that reaches FUN_080115f0.

The save-relevant branch is param_2 == '\0':

pcVar1 = _DAT_080116e4;                       // the global save-struct pointer
if ((*pcVar1 == '\0') && (FUN_08010a70(pcVar1) == /*fail*/)) {
    if (FUN_08010c94(pcVar1) == /*fail*/) { /* nothing */ }
    else { *(param_1+0x3f8) = 0; *pcVar1 = '\x01'; }
}

(Return-value polarity at these two call sites is rendered confusingly by the unrecovered-jumptable returns in the Ghidra output; the control flow — try load; if load does not succeed, (re)write from RAM; mark struct live with byte0 = 1 — is unambiguous from the branch structure and from the reader/writer gate checks on byte 0.)

How FUN_080115f0 mutates the in-RAM save struct: in the param_2 == 0 branch it does not write any serialized field (+0x54…+0x114) itself. After the load-or-create step it reads serialized fields to set up live game state — copies struct+0x68 to two globals, indexes tables by *(struct+0x70) and *(struct+0x74), derives booleans from struct+0x6C/+0x6D (-((byte)^1)>>0x1F) — and writes only non-serialized fields of the other struct it owns (param_1+0x3F8, +0x3FC, +0x50, …). The param_2 != 0 branch is a different scene/tick mode (timer at param_1+0x50, calls to audio/reset helpers incl. func_0x0802d92c(0xff)) and touches no save code. In other words, within this corpus the only flush trigger is "load failed at profile/scene entry", which (re)creates the save from whatever the RAM struct already holds.

3.5 Default initializer: FUN_08010980 @ 0x08010980

No callers in callgraph.json and no textual caller in decompiled.c (reached via a jumptable/table dispatch, like FUN_080115f0). It is nevertheless certainly the save-struct initializer, because it writes exactly the serialized field set and nothing else in that range:

  • Zeroes +0x00…+0x28 in dwords, sets +0x3C = 0xFFFFFFFF, +0x40 = 0, +0x44 = 1, +0x45 = 1, +0x48 = 6, +0x4C = 2, +0x50 = 3 (these offsets < 0x54 are not serialized; they belong to the live struct's other sub-structure and are listed here only to show the function's scope);
  • serialized-range defaults: +0x54 = 0xFFFFFFFF, +0x58 = 0, +0x5C = 0, +0x60 = 0, +0x61 = 1, +0x64 = 0x1000, +0x68 = 0, +0x6C = 1, +0x6D = 1, +0x70 = 6, +0x74 = 2, a small zeroing loop over +0x78…, +0x7E = 1, +0x7F = 1, +0x80…+0x8B = 0 (byte loop), +0x8C = 0, +0x90 = 0, +0x94 = 0xFFFFFFFF, +0x10C = 0, +0x110 = 0, +0x114 = 0;
  • finishes with the save-media init calls func_0x0802d948(4) and func_0x0802d9b0(2, _DAT_08010a68) (EEPROM type 2 select).

Decoded defaults are the baseline used to validate the field map in §5: after the §4.3 un-reversal, both captures match these defaults everywhere except the fields they mutated.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 There is no fixed magic string

Packet summary ascii_magic_strings: [] is correct, and there is also no fixed multi-byte magic in the logical header: logical bytes 0x00–0x07 differ between the two captures. 0xDEAD at physical 0x00–0x01, which the hexdump invites you to read as a magic, is an artefact: those two bytes are the high half of the masked sum (0xDEADB6FA / 0xDEADBAF5), whose high half is 0xDEAD precisely because the mask is 0xDEADBEEF and the sums (0x815, 0x41A) are small. The integrity design uses XOR-masked redundancy instead of a magic.

4.2 The algorithm (proven from code, constants forced by the bytes)

From FUN_08010c94 (writer) and FUN_08010a70 (reader), in logical (RAM-buffer) terms:

length  = total serialized size = 0xD0 (208)               ; uStack_24 in writer
sum     = Σ byte[i]  for i in [0x10, length)               ; accumulated as u32 while copying payload
header (all u32 LE in the logical buffer):
  buf[0x00] = sum
  buf[0x04] = sum    ^ MASK_SUM        ; code: uStack_28 ^= _DAT_08010f80 after plain copy-out
  buf[0x08] = length
  buf[0x0C] = length ^ MASK_LEN        ; code: uStack_20 = uStack_24 ^ _DAT_08010f7c

The code proves the structure (plain + XOR-masked pairs, covered range [0x10, length), accumulation as unsigned bytes into a u32). The Ghidra output does not numerically resolve _DAT_08010f80, _DAT_08010f7c, _DAT_08010b28, or uRam08010b3c, so the two mask constants were recovered from the .sav bytes — and they are forced, not fitted, because each must satisfy two independent files and a consistency cross-check:

  • MASK_SUM: from §4.3's un-reversed headers, buf[0x04] ^ buf[0x00] = 0xDEADB6FA ^ 0x00000815 = 0xDEADBEEF (cap-00) and 0xDEADBAF5 ^ 0x0000041A = 0xDEADBEEF (cap-01). Same mask, both files.
  • MASK_LEN: buf[0x0C] ^ buf[0x08] = 0x448901D0 ^ 0x000000D0 = 0x44890100, identical in both files (the header's second block is byte-identical between captures, as it must be — neither length nor mask changed).

Reader validation order matters for fuzzing (§6): the length pair is checked first (from blocks 0–1 alone, before the payload is read), then the full payload is read, then the sum pair is checked; deserialization happens only if both pass.

Covered range, precisely: logical [0x10, 0xD0) — 192 bytes, i.e. every serialized payload byte and not the 16 header bytes. The stored "sum" is a plain unsigned byte-sum kept in a u32 (0x815/0x41A on these samples — far from u32 overflow, and also equal to the u16 truncation, which is why physical .sav analysis first spots it as a big-endian-looking u16 at physical 0x6–0x7, §4.3).

4.3 The physical .sav transform (why the header looks big-endian)

The game never reverses bytes; the reader reads blocks into RAM in logical order. The reversal appears between the logical buffer and the emulator's .sav dump: within each 8-byte EEPROM block, the file stores the bytes in reverse order. This was not assumed — it was tested by serializing the FUN_08010980 defaults through the §3.3 offset map into a candidate logical payload and comparing transforms of the physical file against it:

Transform applied to each 8-byte block of cap-00Payload bytes matching the FUN_08010980 defaults
identity160/192
swap 4-byte halves176/192
reverse whole block192/192
reverse each half162/192
reverse u16 order184/192

Under whole-block reversal, cap-00 is the exact default save, and cap-01 matches on 187/192 bytes — the 5 differing logical bytes are exactly the checksum bytes plus the +0x54/+0x58 payload pair (logical diff offsets 0x00, 0x01, 0x04, 0x05 in the header block, and 0x10–0x14). In physical bytes this is the packet's 9-byte diff (0x2, 0x3, 0x6, 0x7, 0x13–0x17): header fields swap physical positions under reversal, e.g. the logical masked-sum at 0x04–0x07 appears at physical 0x00–0x03 (hence physical byte 0x2 in the probe), and the logical plain sum at 0x00–0x03 appears at physical 0x04–0x07 with its two significant bytes at physical 0x6–0x7 reading big-endian (0x0815, 0x041A). The packet's "candidate checksum spans" 0x2–0x3 and 0x6–0x7 are the significant halves of these two masked/plain images respectively; its "mutated ranges" are the same fields plus the reversed image of logical 0x10–0x14.

A corollary useful for tooling: the byte sum is invariant under the block reversal (it is a permutation within the covered set), so the checksum can be verified directly on the physical file as sum(sav[0x10:0xD0]) (§4.4 does exactly this), but individual field bytes must be un-reversed before they are interpreted.

4.4 Python verification against the real .sav files (actual output)

Script (/tmp/verify_save.py, run in this workspace; kept inline here for reproducibility):

import struct, glob, hashlib

          f"sav[2:4] BE={struct.unpack('>H',sav[2:4])[0]:#06x} "

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save-states were provided for this cohort (packet §2: 0 states), so every test below is phrased as: mutate the .sav, cold-boot, and observe (a) whether the file is rewritten/preserved, (b) the loaded RAM struct (watch struct+0x54…+0x114 via the global pointer used by FUN_080115f0), and (c) any UI/profile change. All offsets below are physical .sav offsets unless marked logical.

6.1 Checksum repair recipe (required for every payload mutation that should be accepted)

sav = bytearray(open('cap.sav','rb').read())
buf = bytearray(b''.join(sav[i:i+8][::-1] for i in range(0, 512, 8)))  # to logical
# ... edit buf at LOGICAL offsets (see §5) ...
length = struct.unpack('<I', buf[8:12])[0]          # normally 0xD0; keep unless testing length
s = sum(buf[0x10:length]) & 0xFFFFFFFF
struct.pack_into('<I', buf, 0, s)
struct.pack_into('<I', buf, 4, s ^ 0xDEADBEEF)
struct.pack_into('<I', buf, 12, length ^ 0x44890100)
out = b''.join(buf[i:i+8][::-1] for i in range(0, 512, 8))              # back to physical
open('cap.sav','wb').write(out)

Header-only edits (no repair) are the control condition: the reader must reject, and FUN_080115f0 must rewrite a default save (file returns to the cap-00 byte pattern, struct shows defaults). Any mutation that is accepted without repair falsifies §4.
