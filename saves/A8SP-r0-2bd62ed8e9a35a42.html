1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and the real .sav bytes (CONFIRMED_VERIFIED):

  • The save lives on a 512-byte EEPROM (EEPROM 4K = 4 Kbit). Only the first 208 bytes (0x00–0xCF) are ever transferred; bytes 0xD0–0x1FF are unused 0xFF fill in both samples.
  • The transfer unit is one 8-byte EEPROM block. The game-level flush/load loops run exactly 26 iterations (0x1A), and 26 × 8 = 208 bytes.
  • A 16-byte header beginning with the 8-byte magic eV SPMID is copied from a ROM template at 0x0802A220 on first-boot/default initialisation and is compared byte-for-byte on load.
  • The integrity byte at file offset 0xCF (207) is an 8-bit additive checksum: sum8 over file bytes 0x00–0xC7 (0–199). It matches both samples exactly, and the only gameplay-mutated byte between the two captures (0xC5, +1) moves the stored checksum by exactly +1 (0x23 → 0x24). See §4 for the Python output.
  • On integrity/magic failure the game discards the loaded image, rebuilds defaults in RAM, and rewrites EEPROM. This is both the static behaviour of FUN_0802A084 and the behaviour recorded by the PACKET probe (mutation at 0xC5 reverted the save to blank and the save was rewritten after mutation).

Static-only (CONFIRMED_STATIC, code seen, not directly observable in the two .sav files):

  • The full writer/reader/dispatch/sanitiser chain in §3, including the EEPROM serial DMA3 bitstream drivers at 0x083AB730 (read), 0x083AB7E0 (write), and 0x083AB8BC (verify).
  • The in-RAM sanitiser layout used by FUN_0802A2E4 (per-record flag/id/name/score clamping). Its byte offsets do not line up 1:1 with the file record layout; see the open question in §5.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • The exact EWRAM address of the RAM mirror. The decompiled C references it only through ROM literal-pool pointers (e.g. the pointer stored at ROM 0x0802A254); the literal values are not present in the decompiled text, so no 0x02xxxxxx address can be honestly quoted.
  • Which concrete function computes the sum8. No explicit 200-byte sum loop was found in the 104-function corpus; the computation is most likely inside the indirect EEPROM block thunks (0x083ABAA0 / 0x083ABAAC, whose targets Ghidra did not recover) or in the unrecovered register value (unaff_r9) stored at RAM+200 by FUN_0802A4A8.
  • Semantics of several tail fields (0xC5 counter/progress byte, 0xCE = 0x0F, the 0xFFFFFFFF dword at 0xC8), and of record sub-fields beyond score/name.
  • Gameplay-time flush callers. Within the traced corpus the only caller of the load/init entry is the boot/game-init path; any mid-game flush caller is outside the 104 trace-guided functions or reached indirectly.

The two samples are near-identical (2 differing bytes), so field semantics that need varied gameplay data cannot be confirmed from bytes alone. That is the main reason the overall rating is MEDIUM rather than HIGH, despite the checksum, magic, geometry, and driver chain being verified.

Notes on geometry:

  • EEPROM block addressing in FUN_083AB730 / FUN_083AB7E0 takes a block index masked to 16 bits and range-checked against a size field in the EEPROM parameter block (*(ushort *)(*DAT + 4)), consistent with a 64-block (512-byte) device. The address-bit count is read from *(byte *)(*DAT + 8); for a 512-byte EEPROM that is 6 address bits, giving a read-command length of 6 + 3 bits and a write-command length of 6 + 0x43 bits as coded.
  • There is no erase operation in the save path (EEPROM needs none; blocks are overwritten in place). No SRAM (0x0E000000) or Flash (0x5555/0x2AAA) sequence appears anywhere in the save-related functions; the Flash/SRAM hypotheses from the packet template do not apply to this title.

3. Save Writer, Reader & Caller-Chain Architecture

Addressing note: functions at 0x080xxxxx are ARM code in the main ROM image; functions at 0x083Axxxx are Thumb code in a later ROM region containing the EEPROM/DMA support library. The save RAM mirror is referenced only via literal-pool pointers (pointer values stored at ROM addresses such as 0x0802A254, 0x0802A258, 0x0802A414, 0x0802A498, 0x0802A4A4, 0x0802A4F0). All of these almost certainly hold the same EWRAM base, but the decompiled text does not contain the literal values, so the mirror is cited below as "save RAM mirror (via ROM literal at …)" rather than by a fabricated 0x02xxxxxx address.

3.1 Low-level hardware I/O drivers

FUN_083AB6B0 — DMA3 transfer primitive (EEPROM serial bus)

  • Role: write. Generic DMA3 setup used exclusively by the EEPROM read/write drivers in this corpus.
  • Behaviour: saves and clears the DMA/interrupt control words reached through its literal pool, programs DMA source (param_1), destination (param_2), and count/control (param_3 & 0xFFFF | 0x80000000, i.e. DMA enable), then busy-waits while the DMA control high bit (0x8000 in the upper halfword) is set, and restores the saved control word.
  • Callers (from ghidra/callgraph.json): 0x083AB730, 0x083AB7E0. No other callers.
  • Mapped by: it is the only function that writes a DMA channel with one endpoint equal to the constant 0x0D000000 (EEPROM serial data address on GBA, accessed only via DMA).

FUN_083AB730 — EEPROM read one block (8 bytes)

  • Role: read. Signature as decompiled: FUN_083AB730(uint block_index, int out_buffer).
  • Behaviour: masks the block index to 16 bits; if it is within the EEPROM size, builds the read command bitstream on the stack (address bits shifted out MSB-first, preceded by the two start bits 1, 1), DMAs the command to 0x0D000000 via FUN_083AB6B0 (length = address-bits + 3), then DMAs 0x44 (68) halfword-bits back from 0x0D000000, and unpacks 64 data bits MSB-first into four u16 words stored descending from out_buffer + 6. Returns 0 on success (via the unrecovered jumptable tail).
  • Callers: 0x083AB8BC (verify). The game-level read thunk 0x083ABAAC is expected to reach this function (or its library entry) indirectly; see §3.3.
  • Save relevance: this is the only EEPROM read-bitstream builder in the corpus. Each call yields exactly 8 bytes = 1 block.

FUN_083AB7E0 — EEPROM write one block (8 bytes)

  • Role: write. Signature: FUN_083AB7E0(uint block_index, ushort *in_buffer).
  • Behaviour: packs four u16 words (8 bytes) bit-by-bit together with the block address and start/stop bits into a stack bitstream, DMAs it to 0x0D000000 via FUN_083AB6B0 (length = address-bits + 0x43), arms the DMA-completion interrupt helper FUN_083AB5E4, polls the EEPROM busy line (uRam0D000000 & 1) together with the completion flag, then tears down via FUN_083AB66C. Returns 0 on success, a non-zero library value on busy/timeout.
  • Callers: none direct in the corpus; reached indirectly through the game-level write thunk 0x083ABAA0 (see §3.3).
  • Save relevance: the only EEPROM write-bitstream builder in the corpus.

FUN_083AB8BC — EEPROM verify one block

  • Role: read + compare. Signature: FUN_083AB8BC(ushort block_index, short *expected).
  • Behaviour: reads the block into a stack buffer via FUN_083AB730, compares four u16 words against expected, returns 0 on match and 0x8000 on the first mismatch.
  • Callers: none direct in the corpus. It is part of the same library cluster; whether the game-level thunks use verify-after-write could not be confirmed (the thunk bodies are indirect jumps, §3.3).

FUN_083AB5E4 / FUN_083AB66C — DMA interrupt arm / disarm helpers

  • Role: support for FUN_083AB7E0. FUN_083AB5E4 copies the pending DMA request into the active slot, sets the channel enable bit (8 << shift), stores the first data words, and marks the channel active. FUN_083AB66C clears the active request and the enable bit. Neither touches save data directly.

Generic DMA helpers that are NOT the save path — FUN_08000B84, FUN_08000BA8

  • These ARM functions program DMA3 registers 0x040000D4–0x040000DE directly (0x8400 = 32-bit, 0x8000 = 16-bit control) and appear in ghidra/save_related_functions.c only because the seed extractor keyed on DMA MMIO. Their callers (0x08018BD0, 0x08029EA0, 0x080E8428) use them for bulk memory/VRAM-style transfers (e.g. FUN_08018BD0 issues transfers of 8, 0x158, and 18×0xE words after setting palette register 0x05000100). They never reference 0x0D000000. They are documented here to prevent misattribution: the EEPROM save path does not go through them, except that FUN_080E8428 (below) is called by the save dispatcher for a still-unclear auxiliary transfer.

3.2 Game-level EEPROM block thunks

FUN_083ABAA0 — write-block thunk (indirect)

  • Role: write (inferred). Body is a single indirect jump through a pointer stored after the code ((*pcRam083ABAA8)()); Ghidra did not recover the target.
  • Callers: FUN_0802A4A8, which calls it once per block index 0..25 and aborts the flush on the first non-zero return.
  • Mapping reasoning: it is called in a 26-iteration loop immediately after FUN_0802A4A8 stores a dword at save-RAM+200, i.e. in flush position; its sibling FUN_083ABAAC occupies the symmetric position in the load loop. The pair are adjacent entries (12 bytes apart) in the same indirect-jump table region (0x083ABA28–0x083ABAD0) as other library veneers. Confidence: role CONFIRMED_STATIC for "per-block EEPROM transfer used by the flush loop"; exact target and any byte-order/checksum work inside it UNKNOWN.

FUN_083ABAAC — read-block thunk (indirect)

  • Role: read (inferred). Same indirect-jump form ((*pcRam083ABAB4)()).
  • Callers: FUN_0802A4F4, once per block index 0..25, aborting on first non-zero return.
  • Mapping reasoning: symmetric to FUN_083ABAA0; called by the load path before the post-transfer delay FUN_0802A558.

3.3 Serialisation, load, flush, and sanitising

FUN_0802A4A8 — flush save RAM to EEPROM (writer)

  • Role: write.
  • Behaviour: calls the busy-delay FUN_0802A558; stores an unrecovered 32-bit register value (unaff_r9) at save-RAM+200 (the first trailer dword, file offset 0xC8); then loops block indices 0..25 (0x1A) calling FUN_083ABAA0(i), returning early on the first non-zero result.
  • How mapped: the store at +200 happens before any block is written, so that dword is part of the flushed image (block 25 covers bytes 200–207). The unaff_r9 value cannot be recovered from the decompiled text; in the samples the corresponding file dword is 0xFFFFFFFF. Whether unaff_r9 is an integrity value, a validity flag, or a caller-supplied field is an open question (§6). It is not the sum8 checksum: the verified checksum is a single byte at offset 207, and sum8 of the payload is 0x23/0x24, not 0xFFFFFFFF.
  • Callers: FUN_0802A41C (write branch).

FUN_0802A4F4 — load EEPROM into save RAM (reader)

  • Role: read.
  • Behaviour: loops block indices 0..25 calling FUN_083ABAAC(i), returning early on the first non-zero result; after a full pass it calls the busy-delay FUN_0802A558.
  • Callers: FUN_0802A41C (read branch).

FUN_0802A558 — short busy delay

  • Role: support. Counts down from 200 doing nothing. Called by FUN_0802A084 after a successful header compare, at the start of FUN_0802A4A8, and at the end of FUN_0802A4F4. It is a timing guard around EEPROM operations, not a checksum.

FUN_0802A2E4 — sanitise / clamp the in-RAM save struct

  • Role: serialize-preparation (runs before every load/flush dispatch).
  • Behaviour on the struct reached via the literal at ROM 0x0802A414:
  • u16 at +0x10: keeps the low 14 bits ((x << 0x12) >> 0x12).
  • u16 at +0x12: masks with 0x1F.
  • u16 at +100 (0x64): masks with 0x1F.
  • Then 10 records of 8 bytes starting at +0x14, per record:
  • byte +0: ANDed with a mask that is 1 for the first record and thereafter the previous record's invalid-name count (in practice 0 for valid names) — i.e. it clears transient flag bits.
  • byte +1: if signed value is < 0 or > 12 (0x0C), set to 0. This is a small id/category field (0–12).
  • bytes +2, +3, +4: each must lie in 0x20–0x82 (printable name characters). If any is outside, bytes +2..+4 are replaced with the three ROM default bytes at 0x0802A40C–0x0802A40E and byte +5 is set to 0.
  • u16 at +6 (score): if bit 15 is set, the record's score bytes are set to 200 (pb[6] = 200, pb[7] = 0); otherwise the score is clamped down to a maximum read from the literal at ROM 0x0802A418 if it exceeds it.
  • Callers: FUN_0802A41C only (per ghidra/callgraph.json).
  • Important mapping caveat: this in-RAM record layout — [+0 flag][+1 id 0..12][+2..+4 name][+5 zero][+6 score u16] — is rotated by one byte relative to the file record layout observed in the .sav ([+0 zero][+1 score u16][+3..+5 name][+6 id/flag u16], see §5). The EEPROM block thunks therefore very likely perform a per-block byte rotation/repacking, or the sanitiser works on a decoded copy of the struct. This is flagged as an open question; the file layout in §5 is stated from the bytes, the RAM layout here from the code, and no stronger equivalence is claimed.

FUN_0802A41C — load/flush dispatcher

  • Role: deserialize + serialize dispatch.
  • Behaviour:
  1. If its 6th (stack) argument equals 1, copies a u16 from save-RAM+0x1C (via literal 0x0802A498) to save-RAM+0x10 (via literal 0x0802A49C).
  2. Calls the sanitiser FUN_0802A2E4.
  3. Calls FUN_080E8428 (auxiliary DMA queue walker; see below).
  4. Branches on its 5th argument: in the read branch it calls FUN_0802A4F4; if that transfer indicates failure, it zeroes 200 bytes of the save RAM mirror (50 × u32, via literal 0x0802A4A4) and returns. In the write branch (arg5 == 0) it calls FUN_0802A4A8 and returns its result.
  • Decompiler caveat: Ghidra reuses the same boolean (bVar5 = param_5 == 0) for the post-read failure test, producing a visibly dead branch. The "clear 200 bytes on load failure" reading follows from the zeroing loop's size (200 = the sanitised payload core) and from FUN_0802A084's reliance on the return value; the exact condition register is not recoverable from the decompiled text. This is stated as CONFIRMED_STATIC for the structure, with the caveat recorded.
  • FUN_080E8428 (called in step 3): walks two 8-byte-stride entries in a struct reached via literal 0x080E84FC; when an entry's u16 at +6 is below its u16 at +0xE it sets a pending flag and issues three 4-word transfers via the generic DMA helper FUN_08000BA8. Its save-specific purpose (likely flushing a pending DMA/graphics queue before EEPROM timing starts) could not be determined from the corpus. It does not read or write save fields that could be identified.
  • Callers: FUN_0802A084 (twice: once for the initial load attempt, once to flush defaults after a rebuild).

FUN_0802A084 — load-or-initialise (top-level save entry)

  • Role: deserialize with fallback to defaults; also the default-image builder.
  • Behaviour:
  1. Remembers the current u16 at save-RAM+0xC0 if called with arg5 == 1 (uVar9 = *(u16 *)(mirror + 0xC0)), else uses 1.
  2. Calls the dispatcher FUN_0802A41C (load attempt, arguments inherited from its own caller).
  3. If the load returned 0: compares the first 8 bytes of the mirror against the ROM template at 0x0802A220 (the eV SPMID magic). On mismatch it goes to the rebuild step. On match it delays (FUN_0802A558) and then checks the 32-bit word at mirror+200 against the last compared template byte (bVar2); if equal, it returns with the loaded save accepted.
  4. Rebuild (LAB_0802A110): zeroes 200 bytes of the mirror; copies 16 bytes from the ROM template at 0x0802A220 to offset 0; copies 3 eight-byte records from a ROM default table (via literal 0x0802A25C) to offset 0x14; then writes 7 further records replicated from a single 4-byte ROM template (via literal 0x0802A260): record bytes 0–2 are the template's first byte repeated, bytes 3–5 are template bytes 1–3, and the u16 at +6 is the template's first u16. Finally stores uVar9 at mirror+0xC0, stores (arg5 == 1) at mirror+0xC2, and calls FUN_0802A41C again to flush the rebuilt image to EEPROM.
  • Decompiler caveat on step 3: as transcribed, the acceptance test compares the dword at +200 (0xFFFFFFFF in both samples) with the 8th magic byte (0x44, 'D'), which can never be equal for the observed valid saves. Since both samples are accepted in practice (PACKET: save_preserved_on_load: true), the decompiled condition must be mis-recovered — most plausibly bVar2 actually holds a computed integrity byte (the sum8 at file offset 207) whose register Ghidra folded into the magic-compare variable, and/or the compared field is the trailer byte rather than the dword. The report therefore treats "an integrity value in the trailer (offset 200–207) is checked on load, and failure triggers rebuild+rewrite" as verified (code structure + PACKET probe), while the exact compared width/offset in code remains UNKNOWN. The byte-level algorithm itself is verified independently in §4.
  • Callers: FUN_080158F8 only, within the corpus.

4.2 Checksum algorithm

  • Name: save sum8 checksum.
  • Formula: checksum = ( Σ byte[i] for i = 0 .. 199 ) mod 256, i.e. an 8-bit additive sum over file offsets 0x00–0xC7 inclusive.
  • Stored at: file offset 0xCF (207), size 1 byte. It is the last byte of the 8-byte trailer block (offsets 200–207); the preceding trailer bytes are FF FF FF FF 00 00 0F.
  • Covered range rationale: 200 bytes is exactly the core that FUN_0802A084 zeroes on rebuild and FUN_0802A41C clears on load failure, and it excludes the trailer that carries the checksum itself. No contiguous-range alternative fits both samples except ranges that differ only by leading/trailing zero bytes (e.g. starting at 58–63, where the intervening bytes are zero); the 0–199 range is the only one that also matches the code's 200-byte core.
  • Code proof status: the load path checks a trailer integrity value and rebuilds+rewrites on failure (FUN_0802A084, §3.3), and the PACKET probe confirms an integrity check exists (mutation at 0xC5 → blank + rewrite). The exact sum loop was not isolated in the decompiled corpus (likely inside the indirect block thunks or the unrecovered unaff_r9 path), so the algorithm is verified from bytes + probe, while its function attribution remains a hypothesis. Formula confidence: CONFIRMED_VERIFIED. Attribution confidence: HYPOTHESIS.

The inter-sample delta is a controlled natural experiment: byte 0xC5 (inside the covered range) increased by 1 and the stored checksum increased by exactly 1, which falsifies XOR/CRC-style alternatives for this byte (an XOR checksum would have changed by 0x01 only for this specific value pair, but the contiguous-range XOR search found no covering range matching both samples other than the trivial single-byte range at 207 itself; CRC16/CRC32 candidates do not fit a 1-byte stored value).

Record-table anomaly notes (honest limits): with records at file 0x14 (per the rebuild code), record 0's name field reads \0YR and record 9's reads P\0\0, while records 1–8 show clean descending scores (250, 200, 150, 0…) and three-letter names (NEL, OMD, EMD, PMD×5). Two readings are possible: (a) the table really starts at 0x14 and records 0/9 are special/empty entries whose name bytes are partially zero; or (b) the table starts at 0x1C, record 0 at 0x14 is a separate 8-byte field, and the last replicated records at 0x5C/0x64 have single-character names by design. The code (destination +0x14, 3+7 records; sanitiser 10 records at RAM +0x14) supports (a) for geometry, so (a) is used in the table and in save-format.json, with the anomaly explicitly retained rather than smoothed over.

RAM-layout summary from FUN_0802A2E4 (for editors who patch RAM instead of the file): mirror fields at RAM +0x10 (u16, low 14 bits kept), +0x12 (u16 & 0x1F), +0x64 (u16 & 0x1F), records at RAM +0x14 with [+0 flag][+1 id 0..12][+2..+4 name][+5 zero][+6 score u16_le], u16 at RAM +0xC0 (preserved/clamped 1–5 by consumers), u16 at RAM +0xC2, dword at RAM +200. Because of the one-byte rotation between this layout and the file record layout, RAM patching should be verified against a subsequent flush before being trusted.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for every payload mutation below (offsets < 0xC8): after editing, recompute byte[0xCF] = sum(bytes[0x00..0xC7]) & 0xFF in Python and write it back, unless the experiment's purpose is to test the integrity check itself. All predictions assume reloading through the normal boot path (FUN_080158F8 → FUN_0802A084), since no paired .ss save-states were provided in states/ (0 states in this cohort); if save-states become available, the same mutations should be applied to the .sav before loading the state, and RAM predictions checked against the save mirror once its EWRAM address is resolved (open question Q1).

7. Open Questions

  1. Exact EWRAM address of the save mirror (literal-pool values at ROM 0x0802A254 etc. are not in the decompiled text). Needed for RAM watchpoints and for verifying the RAM/file layout relationship live.
  2. Targets of the indirect block thunks FUN_083ABAA0 / FUN_083ABAAC: do they call FUN_083AB7E0 / FUN_083AB730 directly, do they use verify (FUN_083AB8BC), and do they perform the suspected one-byte record rotation and/or the sum8 computation?
  3. Which code computes the sum8 at file offset 0xCF, and what exactly does FUN_0802A4A8 store at +200 (unaff_r9)? Is the 0xFFFFFFFF dword a validity marker, and what does the load acceptance check in FUN_0802A084 actually compare (Ghidra's transcription cannot be literal, §3.3)?
  4. Semantics of file offsets 0xC4, 0xC5 (counter/progress candidate), 0xC6, 0xC7 (constant 1), 0xCC, and 0xCE (constant 0x0F); and of the record u16 at file +6 (values 257, 2, 0…).
  5. Whether the u16 at 0xC0 is the language selector (1–5 clamp in FUN_080158F8) or another 5-valued option.
  6. Record-table anomaly: records 0 and 9 name fields (\0YR, P\0\0) versus the clean records 1–8 — special entries, or a table start at 0x1C with a separate field at 0x14?
  7. Which gameplay/options/high-score functions (outside the 104-function trace corpus) mutate the mirror and trigger the write branch of FUN_0802A41C mid-game?
  8. Purpose of FUN_080E8428 in the dispatcher (auxiliary DMA queue?) and of the first dispatcher step that copies mirror+0x1C to mirror+0x10 when its 6th argument is 1.
