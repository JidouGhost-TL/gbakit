GBA Save Format Report — Hamtaro - Rainbow Rescue (USA) (Proto) (2003-07-29)

Release key A84E-r0-2e3a8e3962c9d5fb. Game code A84E. ROM SHA-256 2e3a8e3962c9d5fb0b7df6eff828995c9630a04d659945f797985e1a77fe053f.

All findings below derive only from the workspace corpus: saves/sav-00-f990.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (191 functions), ghidra/save_related_functions.c, ghidra/callgraph.json, plus standard GBA hardware addresses from the packet. No third-party game-specific source was used.

Key evidence files: PACKET.md, sav-00-f990.sav, hexdump_and_diffs.txt, save_related_functions.c, decompiled.c, callgraph.json.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven to a high standard (code and .sav bytes agree):

  • The medium is SRAM. The only save I/O in the traced corpus addresses 0x0E000000 (GBA SRAM base) with length 0x4000. No Flash command sequence (0x5555/0x2AAA), no EEPROM/DMA3 (0x0D000000, 0x040000D4), and no other save bus appears anywhere in ghidra/decompiled.c.
  • The .sav file is 32768 bytes and consists of two byte-identical 0x4000-byte (16384-byte) halves. Python data[:0x4000] == data[0x4000:] is True, with 0 differing bytes.
  • A 32-bit little-endian additive checksum is verified on both halves. It is the sum, modulo 2^32, of all 4095 u32le words at copy offsets 0x0000..0x3FFB, stored as u32le at copy offset 0x3FFC. Computed 0x2FB796B5 equals stored 0x2FB796B5 (b5 96 b7 2f) in both copies. See Section 4 for the full verification output and the falsified alternatives.
  • A 40-byte (0x28) signature region exists in the save and matches the exact length passed to the SRAM verify routine in the loader. It decodes as Shift-JIS title text. See Section 4.
  • The traced save architecture is a boot-time validate-or-repair path, not a demonstrated gameplay save path. FUN_0809dbe4 verifies signature and checksum, and rewrites the entire 0x4000 region from an in-RAM template when validation fails.

What remains open, and why confidence is not HIGH:

  • Only one .sav sample is available. It is dominated by default/sentinel patterns (999, 0xFFFF, 0xFF, 2, zero). Few, if any, fields can be tied to specific gameplay progress.
  • Ghidra did not resolve literal-pool values. Every _DAT_0809xxxx / uRam0809xxxx operand is a placeholder. The exact RAM mirror base of the save struct (the template source passed to the writer) is therefore not recoverable from this corpus.
  • Symmetrically, the on-save offset of the signature and of the 4-byte status word read by the loader cannot be proven from code alone. The signature offset is inferred from the unique 40-byte text region in the save (strong, but labelled accordingly).
  • No traced function other than the repair path ever flushes the save struct. How gameplay progress would normally be written back is not in the traced corpus (191 functions, trace-guided, not the whole ROM). Claiming gameplay writers for individual fields would be fabrication.
  • The origin of the second identical half is unexplained by traced code, which only ever addresses SRAM base 0x0E000000 for 0x4000 bytes. Backup copy, emulator/hardware mirroring, and untraced code are all still possible.
  • There is no distinguishable generation/sequence counter. Both halves are identical, so no selection rule can be observed.

Static-only sub-confidences: checksum HIGH, signature HIGH-on-bytes/MEDIUM-on-offset, field semantics LOW, slot selection LOW.

Redundancy assessment:

  • The duplication is real in the file: two complete, independently checksummed copies (each carries its own valid trailing checksum word, and both checksums pass in isolation).
  • Traced code gives no writer for the second copy and no reader that ever touches it. Three hypotheses remain, none proven:
  1. Backup copy written by code outside the 191 traced functions.
  2. Mirroring: a 16 KiB physical/imaged SRAM mirrored across the 32 KiB window by the cartridge or emulator, so one 0x4000 write appears twice.
  3. Imaging artefact: the capture tool duplicated the 16 KiB image into a 32 KiB .sav file.
  • The fuzzing plan in Section 6 includes a discriminator test (corrupt copy 1 only) for exactly this question.
  • Internal to one copy, there is no A/B sub-slotting: the checksum, signature, and all field regions occur exactly once per copy, and the loader validates the single base image as a whole. On failure it does not fall back to a second in-copy image; it rewrites the whole 0x4000 bytes from the RAM template.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (method)

Two independent routes were used and cross-checked:

  1. ghidra/callgraph.json callers/callees arrays (static C + runtime direct calls).
  2. Full-text search of ghidra/decompiled.c for both spellings of every call, FUN_0809dea0(...) and func_0x0809dea0(...).

Route 2 is essential: Ghidra emitted many direct calls as func_0x… placeholders, and callgraph.json records no callees for exactly the save-core functions (0x0809dbe4, 0x0809dea0, 0x0809e00c, 0x08168490, 0x081684f4, 0x08168564 all show empty callees/callers there). Every caller/callee claim below was confirmed in the decompiled bodies. Literal-pool operands (_DAT_…, uRam…) are unresolved in this corpus, so no RAM address is invented anywhere below; where an address matters it is marked unresolved.

3.2 Low-level hardware I/O drivers (SRAM primitives, 0x081684xx library cluster)

All three primitives first program a wait-state register with the pattern *reg = *reg & mask | 3 (SRAM wait bits set to the slowest setting, consistent with byte-wise SRAM access), then execute a small routine copied onto the stack (source copied halfword-by-halfword from a ^ 1 Thumb address) via the trampoline func_0x0816860c(a, b, len, stack_code + 1). Executing the access loop from RAM while wait states change is the classic SRAM-library shape, matching the SRAM_V112 tag.

  • FUN_08168490 (0x08168490) — SRAM read / generic copy-in. Signature as used: (src, dst, len). Evidence: in the checksum verifier it is called as func_0x08168490(0x0E000000 + chunk, buffer, 0x400); in the loader as func_0x08168490(unresolved_addr, &stack_word, 4); in the writer as func_0x08168490(ram_src, buffer, 0x100). Callers (textual, exhaustive): 0x0809dbe4, 0x0809dea0, 0x0809e00c. No others in 191 functions.
  • FUN_081684f4 (0x081684f4) — SRAM byte write. Its body is an explicit byte loop, while (len-- != -1) *dst++ = *src++;, after the same wait-state setup. Byte-at-a-time store is mandatory for GBA SRAM. Sole caller: 0x0809e00c, as func_0x081684f4(buffer, sram_dst, 0x100).
  • FUN_08168564 (0x08168564) — SRAM verify/compare. Same stub-copy shape as FUN_08168490 but returns the trampoline result (int). Sole caller: 0x0809dbe4, twice, both times with length 0x28 (40). A zero return is treated as "region matches".

Explicitly excluded drivers (searched across all 191 bodies, zero hits): Flash unlock/command writes (0x5555, 0x2AAA), Flash/EEPROM base 0x0D000000, DMA3 registers (0x040000D4). FUN_081686d4 (in the pre-extracted seed file) contains the constant 0xE0000000 only as a sign/rotate mask inside a software division routine; it is not an SRAM driver and is a false positive of address-pattern seeding. Likewise the | 3 in FUN_08090354 modifies a game object's byte field (param_1 + _DAT_…), not WAITCNT.

3.3 Checksum verifier — FUN_0809dea0 (0x0809dea0)

Role: read + checksum. Sole caller: 0x0809dbe4 (textual; callgraph lists no callers because the call is a func_ placeholder).

Behaviour, from the body in save_related_functions.c:

  1. Allocates a 0x400-byte scratch buffer via FUN_08082d74(0x400, 1, …) (heap allocator wrapper, §3.6).
  2. Loops over the SRAM image in 16 chunks of 0x400 bytes: source starts at 0x0E000000, advances +0x400, budget starts at 0x4000 and is decremented by an unresolved literal (consistent with -0x400) until zero. Each chunk is read with FUN_08168490(sram_ptr, buffer, 0x400).
  3. Accumulates a 32-bit sum (iVar3 = iVar3 + word) over the chunk's u32 words. The Ghidra rendering of the unrolled inner loop is partially garbled (a rotating iVar4 guard on each unrolled lane), but the accumulated quantity is the plain sum of u32le words; this is proven independently by the .sav verification in Section 4, which reproduces the stored word exactly. The garbled guard is a decompiler artefact to be aware of, not a different algorithm: any per-lane skipping would not reproduce the stored value.
  4. Frees the buffer via FUN_08082d5c and reads a stored 4-byte word with FUN_08168490(unresolved_addr, &stack_word, 4). The unresolved address is, by elimination, the trailing word of the image (SRAM base + 0x3FFC): that is the only word whose value equals the computed sum in the real file.
  5. Returns the boolean computed == stored (returned through the usual unrecovered-jumptable tail).

3.4 Whole-image SRAM writer — FUN_0809e00c (0x0809e00c)

Role: write / serialize. Sole caller: 0x0809dbe4, as func_0x0809e00c(unresolved_ram_src, 0x0E000000, 0x4000).

Behaviour: allocates a 0x100-byte staging buffer (FUN_08082d74(0x100, 1, …)); for each 0x100-byte page of the 0x4000 length it copies RAM→buffer with FUN_08168490(src, buffer, 0x100) then buffer→SRAM with the byte writer FUN_081684f4(buffer, dst, 0x100), advancing both pointers; frees with FUN_08082d68. This is a complete-image flush: there is no partial/field-level SRAM write anywhere in the corpus.

3.5 Validate-or-repair loader — FUN_0809dbe4 (0x0809dbe4)

Role: deserialize-side validation + conditional serialize. Sole caller: 0x08112284 (confirmed in both callgraph and body text).

Behaviour:

  1. iVar1 = FUN_08168564(unresolved_a, unresolved_b, 0x28) — verify a 40-byte region (signature, Section 4).
  2. ok = FUN_0809dea0() — checksum over the whole 0x4000 image.
  3. If the image does not fully validate (iVar1 != 0 or checksum false), or a separately read 4-byte status word (FUN_08168490(unresolved, &stack, 4)) differs from an unresolved RAM-side expected word, it repairs: FUN_0809e00c(unresolved_ram_template, 0x0E000000, 0x4000) rewrites the entire image from the in-RAM template struct.
  4. After repair it re-verifies the 40-byte region and the checksum, then reads a 4-byte word (FUN_08168490(unresolved, &stack, 4), or an unresolved RAM word on the other branch) and returns that word as its result.
  5. On the already-valid path it returns the word read in step 3's comparison without rewriting.

Interpretation limits: because the literal pool is unresolved, the RAM template base, the signature's SRAM offset as seen by code, the status word's offset, and the numeric return values cannot be read off the code. The returned word behaves as a small status/mode value at its sole caller (next section). It is not proven to be any specific field in the field map; candidate on-save words are listed in Section 5 with UNKNOWN writer attribution.

3.6 Sole traced caller — FUN_08112284 (0x08112284), and what it mutates

Callgraph and textual search agree: FUN_08112284 is the only caller of FUN_0809dbe4, and nothing in the corpus calls FUN_08112284 (it is reached through an unrecovered jumptable/function-pointer dispatch, like most scene constructors here).

What it does around the save call (all mutations are to its own heap/scene object at param_1, not to the save struct):

  • Constructs the object: FUN_08082f74(param_1, param_2) (list-node init), stores a vtable-like pointer at param_1 + 0x18, copies data from 0x06000000 (VRAM) via the SWI wrapper func_0x08168420, allocates sub-objects via FUN_08082d84 + FUN_0808a138 (stored at +0x1C) and FUN_08082d84 + FUN_080b716c (stored at +0x50), zeroes fields +0x28..+0x4C, stores param_4 at +0x74.
  • Calls uVar5 = FUN_0809dbe4().
  • Branches on the returned status word against one unresolved constant (_DAT_08112358): equal → sets *(u16*)(param_1+0x78) = 2 and *(u8*)(param_1+0x7A) = 1; zero (and not greater than the constant) → sets *(u16*)(param_1+0x78) = 1 and *(u8*)(param_1+0x7A) = 0; anything else → error path: disposes the object (func_0x081123d8(param_1, 3)), builds a replacement via FUN_08082d84(0x30, …) + func_0x0809e2bc(...), and returns early.
  • On success it also zeroes +0x7B..+0x84, picks FUN_080829f8(2, 0x3C, 0) when *(int*)(param_1+0x74) == 0xD else FUN_080829f8(2, 0x1E, 0), then initialises display lists in FUN_08111f88(param_1).

So the loader's result selects between (at least) two operating modes and an error scene. That is consistent with "save absent/fresh" vs "save present" vs "save corrupt", but the exact mapping of return values to modes is not provable here (the compared constant and the loader's returned word are both unresolved). This caller does not mutate the in-RAM save struct at all in the traced body; it consumes only the validation result.

3.7 Heap helpers on the save path (not save functions)

FUN_08082d74 and FUN_08082d84 are wrappers over the allocator FUN_08082cac; FUN_08082d5c and FUN_08082d68 are wrappers over the free routine FUN_08082c10. FUN_08082cac walks a block list, splits blocks, and returns block + 0x10; FUN_08082c10 merges/returns blocks and validates block sizes against 0x80000. These are generic heap services. They have many callers across the game (e.g. FUN_08082d74 is called from 0x08090354, 0x08110bcc, 0x081111d8, 0x08111f88, and many more; FUN_08082d5c likewise). Only three uses are on the save path: the 0x400 checksum buffer and the 0x100 writer buffer, plus their frees. The remaining callers (sprite/object/scene constructors such as FUN_08111f88, which allocates the 0x1E-entry tables it fills with constants 0x1000..0x1107 etc.) allocate ordinary game objects and never touch SRAM. Listing them as "save callers" would be wrong; they are included here only to close the seed file's caller lists.

3.8 Caller-chain summary

  • Load/validate chain (the only entrance): [scene dispatch] → 0x08112284 → 0x0809dbe4 → {0x08168564 (verify 0x28), 0x0809dea0 (checksum) → 0x08168490 (read) + 0x08082d74/0x08082d5c (alloc/free)}.
  • Repair chain (only writer): 0x0809dbe4 → 0x0809e00c → {0x08168490 (RAM→buffer), 0x081684f4 (buffer→SRAM byte write), 0x08082d74/0x08082d68 (alloc/free)}, writing all 0x4000 bytes from the unresolved RAM template base to 0x0E000000.
  • No other caller of any SRAM primitive exists in the 191 traced functions. In particular there is no traced "gameplay progress → mutate RAM save struct → flush" chain. Either that path lives in untraced code, or progress is only ever persisted via this validate/repair image. The corpus cannot distinguish these; both are stated as open questions.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Checksum (CONFIRMED_VERIFIED)

  • Algorithm: sum32_le — unsigned 32-bit wrapping sum of little-endian u32 words. No seed, no complement, no final XOR.
  • Covered range: copy offsets 0x0000..0x3FFB inclusive (4095 words). The leading 0x0000..0x1BFF are all zero in this sample, so the sum also equals the sum over 0x1C00..0x3FFB; the code-side loop covers the full 0x4000 image in 16 × 0x400-byte chunks, with the stored word itself excluded from the accumulated quantity (as the match proves).
  • Stored: copy offset 0x3FFC, 4 bytes, little-endian. File offsets 0x3FFC (copy 0) and 0x7FFC (copy 1).
  • Code proof: FUN_0809dea0 (§3.3) accumulates iVar3 += word over every chunk read from 0x0E000000, then compares against a 4-byte word read back from the image; FUN_0809dbe4 treats a false result as "rewrite the image".
  • Python verification (run in this workspace against the real file):
file: saves/sav-00-f990.sav  size=32768  sha256=8bba8b570bb9cce6b6e31cd90d329fc7614fb134d632af4d746a18fc6d06c127

Reproduction snippet:

import struct
data = open('saves/sav-00-f990.sav','rb').read()
for base in (0x0000, 0x4000):
    seg = data[base:base+0x4000]
    stored = struct.unpack_from('<I', seg, 0x3FFC)[0]
    computed = sum(struct.unpack_from('<4095I', seg, 0)) & 0xFFFFFFFF

# -> 0x0 0x2fb796b5 0x2fb796b5 True ; 0x4000 0x2fb796b5 0x2fb796b5 True

Falsified alternatives (same file, copy 0): including the stored word in the sum gives 0x5F6F2D6A (no match); CRC-32 of 0x0000..0x3FFB gives 0xB7EE5B0A (no match); XOR of u32le words gives 0x0E06350D; sum of u16le gives 0x012EC5BD; byte sum gives 0x00061498. The additive u32le sum excluding the stored word is the unique match among standard candidates, and the chance of an accidental 32-bit hit in both copies is negligible.

Endianness note: the stored bytes b5 96 b7 2f read as big-endian would be 0xB596B72F, which the sum does not produce; little-endian is correct.

4.2 Magic signature (bytes CONFIRMED_VERIFIED, code link CONFIRMED_STATIC)

  • Location: copy offset 0x3A04, length 0x28 (40) bytes. File offsets 0x3A04 (copy 0) and 0x7A04 (copy 1), identical in both.
  • Bytes (hex): 82c682c182c682b1836e838091be98598253814682c982b682a282eb91e58d73906982c582bf82e3
  • Decoding (Shift-JIS / CP932): とっとこハム太郎４：にじいろ大行進でちゅ — the Japanese title string ("Tottoko Hamtaro 4: Nijiiro Daikoushin Dechu"). It is the only text-like run in the file; an ASCII scan ([\x20-\x7e]{4,}) finds nothing.
  • Code link: FUN_0809dbe4 calls the SRAM verify routine FUN_08168564(a, b, 0x28) before and after any repair, and a non-zero (mismatch) result triggers the whole-image rewrite. The length 0x28 matches this region exactly, and this is the only 40-byte non-trivial, non-sentinel region in the image, which makes it the overwhelmingly likely verified region. The caveat: the verify operands are unresolved literal-pool placeholders, so the code side cannot be tied to offset 0x3A04 by address. Confidence is therefore CONFIRMED_STATIC for the code link (not CONFIRMED_VERIFIED), while the bytes themselves and their presence in both copies are verified.
  • Either operand order is possible from the corpus (SRAM region vs RAM/ROM expected string, or SRAM vs the RAM template's copy of the same field). Functionally it does not matter: corruption of these 40 bytes in SRAM is exactly what the loader detects and repairs.
  • No other magic was found: no ASCII signature, no 0xFF-framed header magic, and the image start (0x0000..0x0027) is all zero, ruling out a header-string check at offset 0.

Notes on the map:

  • Every payload field above is duplicated at +0x4000 in copy 1 with identical bytes, including its own checksum at 0x7FFC. The map describes one logical image of 0x4000 bytes.
  • Because the single sample is template-dominated, most "fields" are delimited structurally (sentinel runs, exact strides, zero gaps), not semantically. A second save with real progress would likely split several bytes rows into meaningful sub-fields; conversely some rows above (notably 0x1C64 records and the 0x32EB byte) may merge into neighbours.
  • No field has a proven RAM mirror address, a proven field-specific writer, or proven gameplay semantics in this corpus. Those columns are honestly null/unknown rather than guessed.

6. Save Fuzzing & Counterfactual Verification Plan

General repair rule for every mutation that must survive loading: after editing payload bytes, recompute the checksum for each affected copy — stored = sum(u32le words at copy 0x0000..0x3FFB) mod 2^32, written u32le at copy 0x3FFC (and 0x7FFC for copy 1) — in both copies unless the test deliberately desynchronises them. Keep the 40-byte signature intact unless the test targets it. Reload protocol: use states/sav-00-pre.ss (frame 1) as the cold-boot entry so the loader at 0x08112284/0x0809dbe4 actually runs against the mutated .sav, and states/sav-00-post.ss / states/gameplay.ss (frame 990, identical hashes) as the known-good reference behaviour; states/final.ss (frame 2427) gives a longer-run observation window. Observe: (a) whether the save survives or is silently reset to template, (b) title/menu/UI differences versus the blank-boot and known-good boots named in the packet's cold-reload probe, (c) any RAM-visible change if the harness exposes memory.

Open questions carried forward

  1. What is the RAM base (EWRAM/IWRAM) of the save template struct — i.e. the resolved value of the writer's source operand in FUN_0809dbe4/FUN_0809e00c?
  2. Which on-save u32 does FUN_0809dbe4 read and return (candidates 0x1C20, 0x2C18, 0x2C1C), what are its valid values, and what modes do they select at 0x08112284?
  3. Who writes copy 1 at file 0x4000, if anyone — real backup, hardware/emulator mirroring, or imaging artefact? (Fuzzing test 3 discriminates.)
  4. Where is the normal gameplay save path? No traced function mutates and flushes progress; an untraced writer or an untraced caller of the known writer must exist if progress persists outside the repair flow.
  5. What are the gameplay semantics of the delimited structures (34×120-byte sentinel records, 0xFF runs, 48 pairs, 56 stride-4 bytes, 123×12-byte records)? A second, progress-bearing .sav sample is the cheapest way to answer this.
  6. Does the game ever address SRAM beyond 0x4000 in untraced code (second slot, settings region), or is the upper half permanently outside the game's own view?
