Key transform used throughout (proven in §4): the .sav file does not byte-match the RAM mirror. Each 8-byte EEPROM block appears in the file with its bytes reversed within the block, because the EEPROM read/write bitstreams (FUN_080459d0 / FUN_08045a94) reverse word order and pack bits MSB-first. Thus RAM[i] = sav[(i//8)*8 + 7 - (i%8)], file offsets in this report are .sav offsets unless prefixed "RAM".

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (verified, code + both .sav files):

  • Media is EEPROM 4K (512 B, 64 blocks of 8 B), filled with 0xFF.
  • Geometry is a single 24-byte global header at 0x00 plus three independent 160-byte slots at 0x18, 0xB8, 0x158, plus one never-addressed tail block at 0x1F8.
  • Header magic, header integrity algorithm, and the exact reason the two samples differ (one flag byte + compensating checksum) are fully proven and recomputed in Python in §4.
  • The complete low-level EEPROM-over-DMA3 I/O stack and every recovered caller of it are traced in §3.
  • All three slots in both samples are empty/invalid: they contain only an 8-byte boot-time stamp over erased 0xFF, and their checksums do not validate — which is itself verified against the validator code.

Still open (why not HIGH):

  • No populated profile exists in the corpus, so the 160-byte slot payload layout (progress, levels, currency, …) is unmapped — UNKNOWN, not guessed.
  • No full-slot (160-byte) writer was recovered; only header writes and the 8-byte slot stamp reach the EEPROM write API in the 291-function export.
  • The absolute RAM address of the save-manager struct is hidden behind unresolved Ghidra _DAT_ placeholders, so ram_addr is honestly null in save-format.json.
  • Entry callers of the init and settings-flush functions are dispatched through unrecovered jumptables (callgraph.json lists no callers for them).

  • Fill byte 0xFF everywhere outside the active ranges listed in saves/hexdump_and_diffs.txt (31 B header area, 6 B at 0xB8, 5 B at 0x158 — the last-block stamps; see §5).
  • Address arithmetic proof: FUN_080387c4 loads a slot with FUN_08008b64((slot*0x14+3)*8, 0xA0, buf), i.e. byte offsets 0x18 / 0xB8 / 0x158 with stride 0xA0; FUN_080383a4 stamps first blocks starting at iVar5 = 0x18, incrementing 0xA0. Integrity comes only from the per-region sum (§4). If the header fails validation at boot, FUN_080383a4 recreates it from a ROM template (FUN_08038830) and re-stamps the slots — destructive repair, not failover.
  • Selection rule: a slot is usable iff FUN_0803880c(slot, 0xA0) == 0 (FUN_08038798 stores this as a bool at manager +0x34+slot). The header is usable iff that sum is 0 and the first 8 RAM bytes match the template (FUN_08038348). There is no "newest wins" logic; slots are independent.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O (EEPROM serial via DMA3)

  • FUN_08045950(src, dst, count) — DMA3 driver. It saves bus/IRQ state, writes the DMA3 register block at 0x040000D4 (source, destination, CNT = count | 0x80000000), polls the busy bit (CNT & 0x8000), then restores state. Both EEPROM directions funnel through it with the EEPROM port 0x0D000000 as one endpoint (callers: FUN_080459d0, FUN_08045a94).
  • FUN_080459d0(block, buf) — EEPROM read of one 8-byte block. It rejects block >= *(u16*)(eeprom_desc+4), builds a bitstream of start bits 1,1 followed by the block address MSB-first (width *(u8*)(desc+8)), DMAs addr_bits+3 units to 0x0D000000, DMA-reads 0x44 units back, and extracts 64 data bits into 4 u16s stored in reverse word order. This reversal is exactly why each 8-byte block is byte-reversed between RAM and .sav (see §4).
  • FUN_08045a94(block, buf, wait_flag) — EEPROM write of one 8-byte block. It expands the 4 u16s and the address into a write bitstream, DMAs addr_bits + 0x43 units to 0x0D000000, then polls the EEPROM ready bit (0x0D000000 & 1) against a timer-derived timeout (0x88 ticks).
  • FUN_08045a80(block, buf) — write wrapper calling FUN_08045a94(block, buf, 1).
  • FUN_08045bf4(block, buf) — verify: re-reads the block via FUN_080459d0 and compares 4 s16s; returns 0 on match, 0x8000 on mismatch.
  • FUN_08045908(type) — EEPROM type/config select. Called with 4 by FUN_08008c44; it installs the descriptor whose +4/+8 fields bound block numbers and give the address-bit width. (Descriptor constants themselves are static-only; 64-block geometry is corroborated by the 512-byte media and max block 62 actually addressed.)
  • FUN_08008c44 / FUN_08008c8c — session open/close: save and restore the bus/WAITCNT state around EEPROM access; open gates every transfer on FUN_08045908(4) == 0. Note FUN_08045ea8 in the seed file is an unrelated integer-division helper (it calls func_0x08045d5c on divide-by-zero) and plays no save role.

3.2 Block API

  • FUN_08008b64(byte_addr, len, buf) — read API. addr>>3 and len>>3 give the block count; per block it retries FUN_080459d0 up to 3 times, advancing buf += 8, block++. Returns 1 on success.
  • FUN_08008bcc(byte_addr, len, buf) — write API. Per block: FUN_08045a80 write + FUN_08045bf4 verify, up to 3 retries. Returns 1 on success.
  • Exhaustive grep of ghidra/decompiled.c shows the only FUN_08008bcc call sites are the header writes in FUN_080382dc/FUN_08038830 (24 B at 0) and the slot stamps in FUN_080383a4 (8 B each) — a negative result that matters for §5: no 160-byte slot write exists in this export.

3.3 Checksum routine

  • FUN_0803880c(short *p, u32 len) — returns the s16-truncated sum of len>>1 little-endian s16s. Validity everywhere is "sum == 0"; writers store the negated partial sum in the last word (details in §4).

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

  • File bytes at 0x00–0x07: 31 45 41 42 47 4F 49 42 = ASCII "1EABGOIB" in both samples.
  • After the proven per-block reversal, the RAM magic is "BIOGBAE1" (42 49 4F 47 42 41 45 31).
  • Code proof: FUN_08038348 compares the first 8 RAM bytes after EEPROM read against a template, byte by byte (decompiled.c:6630–6640), and FUN_08038830 installs the header from that template. verified_in_code = true, verified_in_sav = true.

4.2 The block-reversal transform (why file ≠ RAM)

Two independent proofs:

  1. Code: FUN_080459d0 stores the four reconstructed u16s of a block in descending address order (puVar6 = buf+6, decrementing), and FUN_08045a94 builds its write bitstream in the mirrored order. A RAM block [b0..b7] therefore appears on the wire/file as [b7..b0].
  2. Bytes: FUN_080383a4 stamps each empty slot by zeroing a 160-byte buffer, setting buffer[slot]=0xFF (cumulatively, reusing the same buffer), and writing the first 8 bytes. Predicted RAM stamps are FF 00…, FF FF 00…, FF FF FF 00…; the file shows exactly their reversals (00…00 FF, 00… FF FF, 00… FF FF FF) at 0x18, 0xB8, 0x158. No other transform fits all three slots simultaneously.

4.3 Exact checksum algorithm

From FUN_0803880c (decompiled.c:6814–6832), FUN_080382dc (6584–6586) and FUN_08038830 (6850–6858):

sum = 0 (s16, truncated each add)
for i in 0 .. (len/2 - 1):  sum = (s16)(sum + le_s16(p + 2*i))
valid  <=>  sum == 0
writer:  last_word = (u16)(-sum_of_all_words_with_last_word_zeroed)
  • Header: len 0x18, 12 words, stored word = index 11 at RAM 0x16. In file terms the stored numeric value appears as big-endian u16 at 0x10 (RAM low byte 0xD0 sits at file 0x11, high byte at 0x10), so equivalently: sum of the twelve u16_be at file 0x00..0x17 ≡ 0 (mod 65536).
  • Slots: same routine over 0xA0 bytes / 80 words (FUN_08038798). The stored-word position for a full slot write is presumed to be the last word by header analogy — the writer itself was not recovered, so this is static-only.
  • No CRC, XOR fold, seed, or complement beyond the two's-complement negation exists in the traced code.

4.4 Python verification against the real .sav files (actual output)

Script (run in this workspace):

import struct, hashlib, pathlib
def ram(d):
    out = bytearray()
    for i in range(0, len(d), 8): out += d[i:i+8][::-1]
    return bytes(out)
for fn in sorted(pathlib.Path('saves').glob('*.sav')):
    d = fn.read_bytes(); r = ram(d)
    print(fn.name, len(d), hashlib.sha256(d).hexdigest()[:16])
    for name, seg in [('header', r[:0x18]), ('slot0', r[0x18:0xB8]),
                      ('slot1', r[0xB8:0x158]), ('slot2', r[0x158:0x1F8])]:
        ws = struct.unpack(f'<{len(seg)//2}H', seg)
        print(f"  {name}: sum={sum(ws)&0xFFFF:#06x} stored_last={ws[-1]:#06x} "
              f"neg(sum_excl_last)={(-sum(ws[:-1]))&0xFFFF:#06x} valid={sum(ws)&0xFFFF==0}")

  • The inter-sample diff is exactly 2 bytes: file 0x0C (00→01, i.e. RAM byte 11 0→1, the flag forced by FUN_08020a58) and file 0x10 (F6→F5, the checksum high byte, 0xF6D0→0xF5D0). 6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss states ship in this corpus (states/ is empty), so predictions are stated for cold-reload from a mutated .sav (the PACKET probe already validated the reload path at 0x0C). Checksum repair for the header always means: recompute RAM word11 = (-sum of RAM u16_le words 0..10) & 0xFFFF, write its low byte to file 0x11 and high byte to file 0x10. For a slot: make the 80 RAM u16_le sum to 0 by adjusting the last word (file position: last word of the slot's final 8-byte block, block-reversed), unless testing whether the checksum word lives elsewhere.
