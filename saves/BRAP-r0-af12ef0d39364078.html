Clean-Room Save Format Report — Racing Gears Advance (Europe) (En,Fr,De,Es,It) [BRAP]

Release key: BRAP-r0-af12ef0d39364078 · ROM SHA-256: af12ef0d393640784705d261139262345c7d2a65c523d65c9ad604fc36f54923

All findings below were derived exclusively from the files in this workspace: ghidra/decompiled.c (187 trace-guided decompiled functions), ghidra/save_related_functions.c (seed extract), ghidra/callgraph.json, and the two real .sav binaries in saves/, cross-referenced against public GBA hardware behavior (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM/IWRAM). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_VERIFIED / CONFIRMED_STATIC):

  • The save medium is EEPROM, 512 bytes, organized as 64 fixed 8-byte records — confirmed both by the

decompiled low-level driver (loop bound 0x40, stride 8) and by the real .sav file size (512 bytes).

  • The complete hardware I/O call chain from the DMA3 bit-serial driver up through a dirty-bitmap-gated

"save all / load all" API, including a write-then-read-back-verify-with-retry loop.

  • A bit-packed field arena (FUN_080220fc/FUN_080221b0, "SetBits"/"GetBits") sits on top of the raw

512-byte EEPROM mirror and transparently marks the owning 8-byte EEPROM record dirty whenever a field inside it is written — this is the mechanism that turns individual field writes into partial EEPROM flushes.

  • A 4-byte ASCII magic signature "dNoB" (bytes 64 4E 6F 42) at file offset 0x04 is read, compared

against a fixed constant, and re-written by a "reset all slots" routine — confirmed present in both the decompiled boot-check code and the real .sav bytes.

  • A repeating 40-byte slot table of 12 entries starting at file offset 0x14, each entry beginning with a

4-byte field that a dedicated routine (FUN_0801ccb8) explicitly initializes to the sentinel value 0xFFFFFFFF — confirmed structurally (offsets match exactly) and confirmed in the real .sav (all 12 fields read back as 0xFFFFFFFF, i.e. still "unpopulated").

Open / not proven (HYPOTHESIS / UNKNOWN):

  • The exact checksum algorithm and its exact covered byte range. Code exists (FUN_0801c224 verify,

FUN_0801c278 recompute) that reads a stored 32-bit value and compares it to an XOR-fold (FUN_080221f0) of a derived bit range, and the bit-offset arithmetic for the per-slot case matches the 12-slot table exactly — but the arithmetic for the global case depends on two unresolved linker constants (_DAT_08022224, _DAT_08022224's pair), so the precise covered range could not be pinned down, and a brute-force Python XOR-fold search against the one available non-blank .sav did not reproduce the value stored at the candidate global-checksum offset (see §4). This is reported as a negative result, not a confirmed algorithm.

  • The real-world meaning of individual fields (what the 12-entry table represents — most likely a

best-times/leaderboard table given the genre and the "0xFFFFFFFF = empty slot" convention, but this is a plausibility judgment, not a proven fact) and of the small header fields at 0x08–0x13.

  • Only two .sav samples exist in the workspace, one of which (cap-00) is a fully blank/erased EEPROM

(all 0xFF). A single non-blank sample is not enough to statistically confirm field boundaries by byte-variance; all field boundaries below come from the decompiled code, with the .sav used only to check consistency, not to independently discover them.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses below are as recovered by Ghidra from the trace-guided decompilation (Thumb code, 0x08xxxxxx region). Caller edges were obtained two ways: (a) ghidra/callgraph.json, and (b) manual grep of ghidra/decompiled.c for literal call-site text, because the callgraph only captures a subset of edges — calls written in the decompilation as func_0x....() (likely PLT-style thunks/veneers in the trace capture) are

not present as edges in callgraph.json even though the call is visible in the C text. This discrepancy is noted so the gap is not mistaken for "no callers".

3.1 Hardware I/O driver layer

  • 0x0802ee18 — DmaEepromXfer(dst_or_src_ptr, port, count).

IME-guarded (disables/restores the IRQ-enable-register-adjacent flag at the start/end), programs a DMA3-style transfer (writes param_1/param_2 into two consecutive MMIO-adjacent globals, writes param_3 | 0x80000000 into a third — the classic "enable" bit pattern for a GBA DMA control word), then busy-waits on a status register bit (& 0x8000) before returning via a tail-call jump table Ghidra could not fully recover. Callers (per callgraph.json and text): 0x0802ee98, 0x0802ef5c (2-hop).

  • 0x0802ee98 — EepromReadRecord(index, dst8bytes).

Builds a 2-bit read opcode ("11") + address bitstream (width taken from a config byte at *_DAT_0802ef44 + 8, consistent with 6 address bits for 64 records = 2^6), sends it to 0x0D000000 via FUN_0802ee18(cmd_buf, 0x0D000000, N+3), then clocks 68 bits back from 0x0D000000 into a stack buffer via FUN_0802ee18(0x0D000000, cmd_buf, 0x44), discards the 4 leading dummy bits, and packs the remaining 64 bits MSB-first into 4×16-bit words written to dst8bytes. This is the per-record EEPROM read. Caller: 0x0802f0bc (per callgraph.json); also called directly 64× from 0x080220b4 as func_0x0802ee98(record_index, dest_in_ram) (text-only edge, not in callgraph.json).

  • 0x0802ef5c, wrapped by 0x0802ef48 — EepromWriteRecord(index, src8bytes, retry_frames=1).

Builds a write opcode ("0","1") + 64 data bits (from src8bytes) + address bits + terminator, sends the whole thing in one FUN_0802ee18(cmd_buf, 0x0D000000, N+0x43) DMA burst, then polls EEPROM-busy bit 0 at 0x0D000000 with a scanline-count (VCOUNT-style, wraps at 0xE4 = 228, the GBA's scanline count per frame) software timeout of 0x88 units, returning an error code (uRam0802f084) on timeout. param_3 (always 1 from the wrapper) enables one extra timeout-cycle retry inside the function itself. Callers: 0x0802ef48 only, in turn called from 0x08022078 (text-only edge).

  • 0x0802f0bc — EepromVerifyRecord(index, expected8bytes).

Calls FUN_0802ee98(index, local_buf) (i.e. performs a fresh read-back) and then compares the 4×16-bit words of local_buf against expected8bytes; returns 0x8000 on the first mismatch, else 0. This is the read-back half of a write-verify pair, not an independent reader.

  • 0x0802edd0(mode) — EEPROM geometry/backend selector. mode==4 selects the function-pointer set used

by the rest of this layer (consistent with the 512-byte/64-record geometry actually exercised); mode==0x40 and the default branch select other (unused by the traced call sites) backends.

3.2 Record-level write-verify-retry and bulk save/load orchestration

  • 0x08022078 — WriteRecordVerified(index, src8bytes). `for (attempt = 0; attempt < 3; attempt++) { if

(!EepromWrite(index, src) && !EepromVerify(index, src)) return success; } return failure; — i.e. write, then independently read back and compare, retrying the whole write+verify pair up to 3 times before giving up. Caller: 0x08022268`.

  • **0x08022268 — SaveAll() (top-level save entry, no traced caller — invoked from untraced game/menu

logic). Calls FUN_08021fd8() (pre-save guard, see below), then for each of the 64 records checks bit index of the 64-bit dirty bitmap at ram_mirror_base + 0x200; if set, calls WriteRecordVerified(index, ram_mirror_base + index*8). After the loop it zeroes both dirty-bitmap words**, then calls FUN_0802202c() (post-save housekeeping).

  • 0x080220b4 — LoadAll(). Calls FUN_08021fd8(), then unconditionally reads all 64 records

(EepromReadRecord(i, ram_mirror_base + i*8) for i in 0..63) with no verify/retry (a plain read, unlike the save path), then zeroes the 2-word region at a second global (_DAT_080220f8, likely a scratch pointer reused for the dirty bitmap after a fresh load), then calls FUN_0802202c(). Caller: 0x080222c8.

  • 0x080222c8 — Load() (top-level load entry, no traced caller). Calls func_0x0802edd0(4) (select

the 512-byte EEPROM geometry) then LoadAll().

  • 0x08021fd8 — pre-save/-load guard. Checks bit 0x10 of a status word at a known RAM struct offset

0x224; if clear, writes 0 to a "busy" byte at offset 0x208 of a related struct; if set, writes 1 to that byte, copies one byte from offset 0x0 to offset 0x60, and calls func_0x080240c4() (an un-traced, presumably audio/VBlank-sync routine). This gates re-entrant saves/loads, it is not part of the data format itself.

  • 0x0802202c — post-save/-load housekeeping. Clears a pending/queue pointer, copies one word between two

globals, and conditionally fires two callbacks (func_0x08023e58(2), func_0x08023cd0(byte)) that look like sound-effect triggers (constant 2 = SFX id) gated on a per-struct flag at offset 0x208. Not a checksum or integrity routine despite running on every save/load.

3.3 Bit-packed field arena (the layer the game logic actually touches)

  • 0x080221b0 — GetBits(bit_offset, bit_count). Generic ≤32-bit little-endian bit-field reader out of

the RAM mirror, handling the case where the field straddles a 32-bit word boundary.

  • 0x080220fc — SetBits(bit_offset, bit_count, value). The write counterpart. After writing, it

compares the new word value to the old one; only if the word actually changed does it set the corresponding dirty bit ((bit_offset >> 11)-th word, (bit_offset >> 6) & 0x1f-th bit) in the 64-bit dirty bitmap at mirror_base + 0x200. Because each dirty bit is one 32-bit mirror word apart by (bit_offset>>6) and the EEPROM record stride is 8 bytes = 64 bits = exactly the granularity this indexing scheme divides the buffer into, one dirty bit ⇔ one EEPROM record, which is how a single SetBits() call anywhere in the game ends up flushing exactly the right 8-byte EEPROM record on the next SaveAll().

  • 0x080221f0 — XorFoldWords(bit_offset, range_param). XORs together every 32-bit mirror word from the

one containing bit_offset through an end word computed as ((range_param * 0x800 + GLOBAL_CONST) >> 0x10) - start_word + 1 words later. This is the only arithmetic/accumulator routine found in the traced code that touches multiple mirror words at once, and is the strongest candidate for "the checksum function" (see §4).

  • 0x0802222c — ResetBuffer(). Calls func_0x0802e938(stack_byte, base, len) (an un-traced

zero/clear helper — signature matches a memset-style call) against the whole mirror, then sets both 64-bit dirty-bitmap words to 0xFFFFFFFF (mark every record dirty, forcing a full 64-record flush on the next SaveAll()). This is the "format/new game" primitive.

3.4 Integrity check & "new game" callers (how the in-RAM struct gets mutated before a flush)

  • 0x0801cd14 — BootCheck() (no traced caller — this is effectively main()'s save-subsystem init).
  1. Load() — pulls all 64 EEPROM records into the RAM mirror.
  2. GetBits(0, 0x20) (the 4-byte field at RAM-mirror-relative bit 0) is compared against a fixed constant

_DAT_0801cd50; on mismatch, calls ResetAllSlots() (0x0801ccb8, below) — i.e. this is the magic signature check.

  1. VerifyChecksum(0, 0) (0x0801c224, global case) is checked; if it fails, applies default settings

(0x0801c3e0) and clears an additional pointer/flag pair; otherwise proceeds to two un-traced continuation routines (func_0x0801c350, func_0x0801c45c), presumably "continue with loaded save".

  • 0x0801ccb8 — ResetAllSlots(). Calls ResetBuffer() (mark-all-dirty + zero-clear), then

SetBits(0, 0x20, GLOBAL_MAGIC_CONST) (re-writes the magic signature), SetBits(0x40, 0x20, 0xFFFFFFFF) (invalidates the global checksum field), then loops 12 times writing SetBits(0x80 + n*0x140, 0x20, 0xFFFFFFFF) for n = 0..11 — invalidating all 12 per-slot checksum fields of the slot table described in §5. This is the clean-room-confirmed "format new save" routine.

  • 0x0801c224(is_slot, slot_or_0) — VerifyChecksum. If is_slot==0: reads the stored 32-bit value at

bit 0x40 and compares it to XorFoldWords(0x60, 0x73). If is_slot!=0: reads the stored value at bit 0x80 + slot*0x140 (exactly the per-slot sentinel field from §3.3/§5) and compares it to XorFoldWords((0x80 + slot*0x140) | 0x20, (0x80 + slot*0x140) + 0x140) — i.e. "does this slot's checksum equal the XOR-fold of the 36 bytes immediately following it". Callers: 0x0801cc40, 0x0801cd14.

  • 0x0801c278(is_slot, slot_or_0) — RecomputeChecksum. Mirror image of the above: computes the same

XorFoldWords(...) and SetBits()s it back into the same stored-checksum field. Callers: 0x0801c2c0, 0x0801c434 (both settings-mutation routines that end with "recompute the global checksum after changing a setting field").

  • **0x0801cc40(out_ptr5bytes) — scans all 12 slots, keeping the minimum of some per-slot byte for each of 5

categories, but only for slots whose VerifyChecksum(1, n) passes.** This is consistent with (but does not prove) a "best of N records across slots" leaderboard-style scan; no traced caller.

  • 0x0801c3e0 — writes 8 fixed default values into the settings region (SetBits-adjacent direct byte/word

stores at mirror offsets 0x1ae, +2, 0x1b0, 0x1b4, 0x1b6, 0x1b8, 0x1ba) used by the difficulty/ settings logic in 0x0801c2c0/0x0801c3e0's own call site. Caller: 0x0801cd14 (checksum-fail path only).

4. Magic Signature & Checksum / Integrity — Python Verification

Magic signature — CONFIRMED_VERIFIED.

offset=0x04, size=4, ascii="dNoB" (bytes 64 4E 6F 42)
>>> d1 = open('saves/cap-01-future-1.sav','rb').read()
>>> d1[4:8].hex(), d1[4:8]
('644e6f42', b'dNoB')

Matches FUN_0801cd14's GetBits(0, 0x20) boot-time comparison and FUN_0801ccb8's re-write of the same field. cap-00-future-0.sav is fully blank (all 0xFF, no magic present yet), confirming this field is written by game code, not present at EEPROM erase state.

Checksum — mechanism CONFIRMED_STATIC, exact field/range NOT verified (negative result below).

The per-slot checksum location formula from FUN_0801c224/FUN_0801ccb8 is internally self-consistent and was checked directly against the real .sav:

>>> import struct
>>> d1 = open('saves/cap-01-future-1.sav','rb').read()
>>> word = lambda d,o: struct.unpack_from('<I', d, o)[0]
>>> for n in range(12):
...     off = 0x14 + n*0x28   # bit (0x80+n*0x140) from base = file offset 4
...     print(n, hex(off), hex(word(d1, off)))
0 0x14 0xffffffff
1 0x3c 0xffffffff
2 0x64 0xffffffff
3 0x8c 0xffffffff
4 0xb4 0xffffffff
5 0xdc 0xffffffff
6 0x104 0xffffffff
7 0x12c 0xffffffff
8 0x154 0xffffffff
9 0x17c 0xffffffff
10 0x1a4 0xffffffff
11 0x1cc 0xffffffff

All 12 fields read back exactly 0xFFFFFFFF — the literal sentinel ResetAllSlots() writes. This confirms the offset/stride arithmetic (0x14 + n*0x28 for n=0..11) but, because the value is the untouched reset-sentinel rather than a computed value, it does not confirm the XOR-fold formula itself (a correct and an incorrect implementation of XorFoldWords would both leave this field at 0xFFFFFFFF if the slot was never subsequently populated by gameplay).

Attempting to confirm the global checksum field (bit 0x40 → file offset 0x0C) failed:

>>> word(d1, 0x0c), word(d1, 0x08)
(0xaab40000, 0xaab40000)   # identical — looks like a mirrored stat, not a checksum
>>> acc = 0
>>> for off in range(0x10, 0x200, 4): acc ^= word(d1, off)
>>> hex(acc)
'0x0'
>>> acc == word(d1, 0x0c)
False

No contiguous word-aligned XOR-fold starting at file offset 0x10 reproduces the value stored at 0x0C, and the value at 0x0C is bit-for-bit identical to the preceding word at 0x08, which is much more consistent with a mirrored/duplicated data field (common GBA integrity pattern: store a value twice and compare copies, rather than checksum it) than with an XOR-fold checksum. The exact second operand of XorFoldWords(0x60, 0x73) could not be resolved from the decompiled text because it depends on an unresolved external constant (_DAT_08022224), so this is reported as HYPOTHESIS for the mechanism and UNKNOWN for the exact covered range — not CONFIRMED_VERIFIED.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below are to be applied to a copy of a .sav loaded from a paired pre-save .ss state (per project retention rules, every .sav capture should have paired sav-XX-pre.ss/sav-XX-post.ss), then reloaded from the matching post-mutation state to observe the effect, with the original bytes always preserved.

  1. Magic-field corruption (offset 0x04, 4 bytes). Flip any bit in 64 4E 6F 42. Prediction:

BootCheck (0x0801cd14) fails the GetBits(0,0x20) == CONST check and calls ResetAllSlots() — expect a full factory-reset on next boot (magic restored to "dNoB", all 12 slot-checksum fields reset to 0xFFFFFFFF, dirty bitmap forced to 0xFFFFFFFF, and a full 64-record EEPROM flush on the next SaveAll). No checksum repair is needed for this test since the reset path rewrites the field itself.

  1. Global "checksum" field corruption (offset 0x0C, 4 bytes) without touching 0x08. Set 0x0C-0x0F to

a value that differs from 0x08-0x0B. Prediction A (mirrored-stat hypothesis): if some other gameplay system reads/validates 0x08/0x0C as redundant copies, expect visibly wrong stat display or a silent fallback to the 0x08 copy. Prediction B (checksum hypothesis): if VerifyChecksum(0,0) actually gates on this field, expect BootCheck to take the "defaults" branch (0x0801c3e0) without a full slot reset. Distinguishing A vs B is the actual point of this test — it directly resolves the open question in §4. No repair needed; this test's job is to observe which branch fires.

  1. Per-slot checksum corruption (any of the 12 offsets 0x14+n*0x28, currently 0xFFFFFFFF). Set to any

value other than 0xFFFFFFFF while leaving the 36-byte body all-zero. Prediction: VerifyChecksum(1,n) should now read the stored (non-sentinel) value and compare it against XorFoldWords of an all-zero 36-byte body, i.e. against 0x00000000. Unless the injected value happens to be 0, this should fail verification, which per 0x0801cc40's scan should cause that slot to be excluded from whatever best-of-N computation it feeds. This test confirms/refutes both the checksum algorithm and the leaderboard hypothesis simultaneously. Repair: to make the slot appear valid, set the field to 0x00000000 (XOR-fold of an all-zero range is 0) and observe whether it is then accepted — a clean, falsifiable repair-and-retest.

  1. Populate one slot body then corrupt its checksum. Requires actual in-game play to populate a slot (the

workspace has no second non-blank sample to derive the real algorithm from directly), then: (a) dump the .sav, (b) compute XorFoldWords-equivalent over the 36-byte body in Python using several candidate algorithms (plain 32-bit-word XOR fold; byte-sum; XOR fold with a different end-word count derived from reversing the (range_param*0x800+C)>>0x10 formula for a few plausible C), (c) check which candidate matches the stored field — this is the concrete follow-up that would finally convert §4's HYPOTHESIS to CONFIRMED_VERIFIED. (d) Then corrupt one byte of the body and confirm the game now flags/ignores the slot.

  1. Dirty-bitmap bypass test. From a save with at least one dirty record pending, hard-power-cycle (or

reset-state) before SaveAll runs, then reload. Prediction: because SetBits only marks dirty records, and SaveAll only flushes dirty records, any field change made since the last successful SaveAll that never reached a SaveAll call should be lost on reload — this validates the dirty-bitmap-gated partial-write model in §3.3 is actually load-bearing and not just a write-amplification optimization that always ends up flushing everything anyway.

  1. Write-verify-retry exhaustion. Not practically fuzzable from .sav bytes alone (it is a runtime EEPROM

timing/retry behavior, not a stored-data property) — flagged here as an open question requiring an emulator-level EEPROM-busy-bit injection fault, out of scope for pure .sav byte fuzzing.
