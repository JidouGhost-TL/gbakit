All findings derive only from this workspace: saves/*.sav, saves/hexdump_and_diffs.txt, ghidra/decompiled.c (91 functions), ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware addresses. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + .sav bytes agree):

  • The save medium is SRAM: the only full save writer flushes EWRAM 0x02000000 to 0x0E000000 (SRAM base) in FUN_0802b904 in decompiled.c. No Flash 0x5555/0x2AAA command sequence, no EEPROM/DMA3 (0x040000D4) serial path, and no SDK save tag exists in the corpus.
  • There is one save image, 11,272 bytes (0x2C08), at SRAM offset 0. No slot, mirror, or backup copy exists. Bytes 0x2C08–0x7FFF of the 32 KiB file are untouched 0xFF in both samples.
  • The populated sample cap-01-future-1.sav is, byte for byte, the output of the factory-initialisation writer FUN_0802b904: header flag, 0x6D empty-text sentinels, and all three record tables match its loops exactly (Section 5).
  • There is no checksum (sum/XOR/CRC/complement) over save data anywhere in the corpus, and brute-force computation finds no stored checksum in the .sav (Section 4). Integrity is a 20-byte header compare plus field-range validation on load, and a write-with-verify retry (×3) on store.
  • cap-00-future-0.sav is not a save: all 32,768 bytes are 0xFF (erased SRAM). The corpus therefore contains exactly one populated sample, in factory-fresh state.

Open / static-only:

  • Ghidra did not resolve many literal-pool _DAT_*/uRam* globals to constants. The absolute SRAM offsets of the validator's u16/u32 fields and of the 0–5 saved index are therefore UNKNOWN, not guessed (Section 5, last two rows).
  • The exact flush-length literal (_DAT_0802badc) is unresolved; 0x2C08 is proven by the 0xFF boundary in the .sav, not by the literal.
  • Three validator/helper functions (FUN_0802be98, FUN_08026254, FUN_08032a7c) are called but not among the 91 decompiled functions.
  • Semantics of the three tables (what game entity each record is) cannot be determined from one factory-fresh sample with no gameplay-mutated counterpart. Field names below are structural.
  • states/ is empty and the PACKET cold-reload probe errored (No bounded save payload), so no reload behaviour was observed. Section 6 is a plan, not results.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

All SRAM access goes through three small drivers. Each first sets a WAITCNT-style register (*_DAT = *_DAT & mask | 3, the SRAM wait-state setting) — Ghidra renders the register as an unresolved _DAT_* global in every case.

Negative results, checked explicitly: no function writes the Flash unlock addresses 0x0E005555/0x0E002AAA; no function programs DMA3 (0x040000D4) toward 0x0D000000 (EEPROM); FUN_08032aac/FUN_08032b88 are signed divide/remainder helpers — FUN_08032b88 is mis-seeded as an MMIO candidate in save_related_functions.c and is not a checksum or save function.

3.2 The writer: FUN_0802b904 (factory init + only full flush)

Read line-by-line at decompiled.c:1246. It has no callers in callgraph.json; like most top-level functions here it is reached through an UNRECOVERED_JUMPTABLE dispatch (most plausibly the FUN_0802f7a4 state machine), so its trigger is inferred, not proven: first boot / save initialisation.

Sequence, with the in-RAM struct at 0x02000000 (EWRAM), SRAM offsets identical to RAM offsets:

  1. FUN_080328b4(&zero, 0x02000000, _DAT_0802baa8) — CpuSet-clear the whole struct (length literal unresolved).
  2. *(u8*)0x0200000A = 1; bytes 0x02000014–0x0200001B = 0x6D (8×, written descending); *(u8*)0x0200001C = 0xFF.
  3. Table A: 50 records, stride 0x18, base _DAT_0802baac + 0x02000000 (= file 0x66C). Per record: +0..7 = 0x6D, +8 = 0xFF, +9 = 0, +0xB..0x14 = 0xFF; then +0.. overwritten by a 0xFF-terminated ROM string (source stride 0x14, max 9 chars, stop at 0xFF).
  4. Table B: 50 records, stride 0x20. Per record, from a ROM table (stride 4 words): word0 → u32 in RAM, word1 → string copied by FUN_08029140 to 0x02000C00 + i*0x20, word2 → u32, word3 → string to 0x02000C10 + i*0x20.
  5. Table C: 32 records, stride 0x78, base _DAT_0802bac0 + 0x02000000 (= file 0x1368). Per record: u32 = 0xFFFFFFFF, u16 = 0, 14 bytes 0x6D, one 0xFF byte, 64 bytes 0x6D, one 0xFF byte.
  6. One final u32 = 0 at an unresolved offset in the tail region.
  7. FUN_08032a38(0x02000000, 0x0E000000, _DAT_0802badc) — the single flush to SRAM, with verify-retry.

Every byte pattern above was matched against cap-01 (Section 5). cap-01 contains no mutation beyond this function's output that any other corpus function could have produced — there is no other full-save writer. Later saves of mutated state, if the game makes them, must reuse FUN_08032a38 from code outside the trace-guided 91-function corpus, or re-enter this function; that is an open question, stated as such.

3.3 The validator / load gate: FUN_0802b7ec

At decompiled.c:1181. Also pre-extracted in save_related_functions.c — note that file's seed set (3 functions) misses most of the chain below; the full corpus was used instead.

  1. FUN_08032900(_DAT_0802b884, buf, 0x18) reads 24 bytes; the first 20 bytes are compared byte-by-byte against a ROM template at _DAT_0802b888. Any mismatch → return 1.
  2. Unrecovered FUN_0802be98(buf2) fills a second buffer; checks: two bytes < 0x32 (50), and seven successive bytes classified by unrecovered FUN_08026254 must return exactly 0, 3, 4, 5, 6, 7, 8. Failure → return 2.
  3. Reads a u16 (must be < 0x2F, i.e. ≤ 46 — consistent with a Table A index into 50 records), then a u32 at uRam0802b8b4; if the u32 is negative or above iRam0802b8d8, it is clamped to 0/the max and written back with FUN_08032a38(&val, base, 4). This is the only in-place SRAM patch outside the factory flush.
  4. All pass → return 0.

3.4 Reader: FUN_0802bf6c

At decompiled.c:1366: reads a u16 via FUN_08032900(_DAT_0802bf94, buf, 2); if > 5 the local copy is set to 0; returns the value. A saved index with 6 legal values. Its SRAM offset is unresolved (UNKNOWN).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

No ASCII magic exists (PACKET: ascii_magic_strings: []; confirmed by Python scan — the only repeated non-zero strings are 0x6D/0xFF sentinel runs and encoded, non-ASCII table text).

The one candidate signature is the 20-byte header block at offset 0, compared byte-by-byte against a ROM template by FUN_0802b7ec (decompiled.c:1202):

offset 0x00, 20 bytes in cap-01: 00 00 00 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00 00 00

Honesty note: the ROM template bytes (_DAT_0802b888) are not in the workspace, so it cannot be proven that the template equals these 20 bytes — only that (a) the code compares 20 bytes read from SRAM against ROM, and (b) these are the 20 bytes a factory-written, presumably valid save carries. verified_in_code is therefore false in the JSON for the signature itself; the compare's existence is CONFIRMED_STATIC.

Checksum: none — with Python verification

No loop in the corpus sums, XORs, CRCs, or complements save bytes. The PACKET "candidate checksum spans" are Table A +9 = 0x00 record bytes (Section 5), each sitting between a 0xFF terminator and 0xFF padding — structural, not arithmetic.

Integrity actually used:

  1. Write-verify-retry — FUN_08032a38: write (FUN_08032964), verify (FUN_080329d4), up to 3 attempts, return verify status (decompiled.c:2731).
  2. Load validation — 20-byte header compare + range checks (FUN_0802b7ec, Section 3.3).

Python verification run against the real files (this session, python3 over saves/*.sav):

stored-value search: none of the above values (as u16_le/u32_le) occurs anywhere in either file → match=false for every candidate

Conclusion: any tool that "repairs the checksum" after editing this save is repairing something that does not exist. Edits need no integrity fix-up; the only gates are the header compare and the validator's range checks.

6. Save Fuzzing & Counterfactual Verification Plan

Prerequisite: no paired .ss states exist in this workspace, so step 0 is to create one: boot the ROM with cap-01 loaded, save an emulator state at a stable menu, and use "reload state + replace .sav" as the harness for every case below. No case requires checksum repair — there is no checksum (Section 4). Restore the original .sav after each case.
