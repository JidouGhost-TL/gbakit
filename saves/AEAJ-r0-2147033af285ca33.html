1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (code + bytes, or code with an unambiguous hardware constant):

  • The save medium is byte-wide SRAM at 0x0E000000, written and read as one 32,768-byte (0x8000) image. This is literal in FUN_08000f54 and FUN_08000e90 in decompiled.c.
  • The only low-level SRAM write primitive in the traced corpus is FUN_080e30f8(src, dst, len), a byte copy that first touches a WAITCNT-style register. The only traced SRAM writer is FUN_08000f54; the only traced SRAM reader/validator is FUN_08000e90.
  • The integrity algorithm in code is an 8-bit additive sum (FUN_08000c4c), recomputed/stored by FUN_08000c64, read back by FUN_08000c38, and checked in FUN_08000e90. No CRC, XOR-fold, complement, Flash 0x5555/0x2AAA command sequence, or EEPROM/DMA3 serial protocol exists in the traced save path.
  • cap-00-future-0.sav is an erased image: all 32,768 bytes are 0xFF (SHA-256 2d864c0b789a43214eee8524d3182075125e5ca2cd527f3582ec87ffd94076bc). cap-01-future-1.sav is the sole populated image (SHA-256 0e85437812fc7acf3dc0fbf31278ca0ba0682a3ee6fb7cc0fb7f718bb64630ab).

Static-only:

  • Exact RAM mirror base, exact covered length, exact stored-checksum offset, and exact magic offset/value, because Ghidra rendered every literal-pool load as an unresolved _DAT_08000xxx / iRam… / puRam… symbol. The decompilation gives the address of the literal in ROM, not the value stored there. No ROM binary is in the workspace, so those values cannot be recovered from the provided text.
  • The internal backup-copy and dword-magic check inside FUN_08000e90: the operations are visible, their offsets operands are not.

Hypotheses / unknowns (single populated sample):

  • A candidate checksum storage byte at file offset 0x7D58: sum8(cap-01[0:0x3DA4]) == 0x69 == cap-01[0x7D58], and 0x69 occurs nowhere else in that file. This is a real single-sample match, not a proof. Any covered end in [0x3DA4, 0x7D50) gives the same sum because the intervening bytes are all zero.
  • A candidate magic/version dword at 0x7D50: little-endian 0x01111702 (02 17 11 01). Code proves a dword equality check exists on load; it does not prove this dword is that check.
  • Most semantic field names. Structural boundaries (notably 200 × 60 = 0x2EE0) are mapped; what a record means in gameplay is not.

What remains open is listed in section 6 and in save-format.json:open_questions. With only one non-blank sample, no field that requires a value change between two valid saves can be confirmed.

Redundancy, precisely: FUN_08000e90, after a successful sum check and dword check, and only when its argument is 1, copies uRam08000f4c halfwords from (RAM base + iRam08000f50) to RAM base, then calls FUN_08000c64 to recompute the RAM checksum. That is an in-RAM restore-from-a-second-region operation (source region, word count, and base are all unresolved literals). It cannot be mapped to a second SRAM slot: the SRAM read that precedes it copies the whole image once, and the .sav contains no duplicated populated payload. Therefore no backup slot, mirror, or A/B selection rule is claimed. Treating the zero gaps as a backup copy would be fabrication.

There is also no erase driver for SRAM (SRAM needs none). FUN_08000c04 erases only the RAM mirror: it stores a base pointer, calls FUN_080e3184, zeroes _DAT_08000c34 halfwords at _DAT_08000c30, then tail-calls FUN_08000fb0 (defaults). It writes nothing to 0x0E000000.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped

Two sources were cross-checked for every edge:

  1. ghidra/callgraph.json: direct FUN_ edges. Example (verified in Python): 0x08000c4c: callers [0x08000c64, 0x08000e90]; 0x08000f54: callers [0x08029ac8]; 0x08000e90: callers [0x0801da54]; 0x08000fb0: callers [0x0801da54, 0x08029ac8].
  2. Textual func_0x… calls in ghidra/decompiled.c. Ghidra could not recover most indirect jump tables (UNRECOVERED_JUMPTABLE), so calls emitted as func_0x08000c04(), func_0x0801da54(0), func_0x080e3268(...), etc. are absent from callgraph.json callees. Every chain below states which source proves each edge. This distinction matters: FUN_08000628 (boot) has graph callees only [0x080005a8, 0x080005f4], yet its body textually calls func_0x08000c04() and func_0x0801da54(0).

The 152-function trace is trace-guided; a function never executed during tracing may be missing entirely. "Only writer/reader" therefore means "only in this corpus", not "only in the ROM".

3.1 Low-level hardware I/O

Byte-at-a-time copy, as SRAM requires. In the writer it is invoked as FUN_080e30f8(RAM_image, 0x0E000000, 0x8000). No Flash unlock writes to 0x5555/0x2AAA, no EEPROM address 0x0D000000, and no DMA3 registers (0x040000D4) appear anywhere in the save path; those media are excluded by the code, not just by the packet label.

FUN_080e3268 at 0x080E3268 — unresolved transfer/verify helper

Body is a single unrecovered jump table, so its implementation is unknown. Its two call sites fix its contract only partially:

  • Reader: func_0x080e3268(0x0E000000, RAM_dst, len_uVar2, *_DAT_08000ef0) — SRAM → RAM.
  • Writer: iVar2 = func_0x080e3268(RAM_src, 0x0E000000, 0x8000, *_DAT_08000fa4) — after the write copy; return 0 breaks the retry loop, i.e. a verify/compare-style result.

Honest reading: a copy/verify routine whose direction follows argument order and whose 4th argument (a dereferenced literal) may be a mode/wait parameter. It is not claimed to be DMA, memcpy, or a checksum. Graph: no callers/callees recorded (all uses are func_ indirect calls).

How mapped: by caller (only FUN_08000fb0), by element counts/strides matching observed .sav boundaries (200×0x3C = 0x2EE0, 200×2 = 400 at 0x3C14, 30 u16 entries, 5×0x12), not by resolved addresses.

Return contract (inferred from the sole caller, which tests < 0): 0 = valid; -1 = sum never matched in 2 attempts; -2 = sum matched but dword check failed. 3.4 Caller chains

Chain A — boot → load (textual edges; graph-invisible)

FUN_08000628 (entry; graph callers []) → func_0x08000c04() → FUN_08000fb0 (defaults, via its tail jump) and, later in boot, func_0x0801da54(0). Boot first zeroes display/OAM/palette RAM (FUN_080005a8, FUN_08000580), calls func_0x08000c04() (clear RAM mirror + defaults), sets *_DAT_080006dc = 0x100, calls FUN_080005f4 (subsystem init, which itself calls func_0x08000bf8() etc.), sets *_DAT_080006e0 = 0x1740, then func_0x0801da54(0). Note the apparent double-initialisation: the RAM mirror is defaulted by FUN_08000c04/FUN_08000fb0 before FUN_0801da54 attempts the SRAM load, and FUN_0801da54 defaults it again if the load fails. The 0 argument in the textual call vs. the void Ghidra signature is a jumptable-call artefact; the load call inside FUN_0801da54 passes literal 1.

RAM fields updated on this chain: entire mirror (defaults, then SRAM image if valid, then the restore copy + recomputed checksum inside FUN_08000e90(1)), plus the flag bits in Chain B. Nothing is written to SRAM on boot unless Chain C runs in the same session.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Algorithm (proven in code)

sum8(p, end):  c = 0 (char); for (p < end) c = (c + *p) & 0xFF; return c
store:         *(u8 *)(base + store_off) = sum8(base, base + length)     [FUN_08000c64]
read stored:   *(u8 *)(base' + off')                                       [FUN_08000c38]
validate:      (sum8(RAM, RAM + len2) - stored) & 0xFF == 0, up to 2 tries [FUN_08000e90]
then:          *(s32 *)(obj + magic_off) == magic_const, else return -2
  • Formula: plain unsigned 8-bit additive sum, no seed, no final complement/XOR, no endianness (byte stream). Signedness of char is irrelevant modulo 256.
  • Covered range: [base, base+length) in RAM mirror order. length, store_off, base, base', off', magic_off, magic_const are all unresolved literal-pool values. The packet's required "exact covered byte range / stored offset" therefore cannot be honestly supplied from code alone. What follows is the byte-side test.
  • No other checksum exists in the save path. In particular, the ~sum16 in FUN_08000998 is not called by any save function (graph: no save caller) and is excluded.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so every test below is: mutate cap-01-future-1.sav copy → boot in an emulator with that .sav → observe load success/failure (title continues vs. defaults/new-save behaviour, per Chain B), plus RAM-mirror inspection if a debugger is available. Step 0 is mandatory before all others.

  1. Acquire a second valid sample first. Play briefly from the cap-01 state and trigger any flush; if no in-game action ever rewrites the .sav, that itself falsifies "progress is persisted by an untraced writer" and supports "only new-game writes". With two valid samples, re-run: sum8 over candidate ranges, diff all bytes (real fields change; magic/checksum-covered boundaries reveal themselves), and check whether byte 0x7D58 tracks sum8[0:0x3DA4]. Do not fuzz "predicted gameplay effects" beyond load-accept/reject until this exists.
  2. Checksum candidate falsification. Flip one byte at 0x0000 (05→06) without repair. Prediction (hypothesis): FUN_08000e90 returns -1 after 2 tries → FUN_08000fb0 defaults → new-save/title-default behaviour, if 0x0000 is inside the covered range. Then repair: recompute s = sum(d[0:0x3DA4]) & 0xFF, write s at 0x7D58, repeat. Prediction: load is accepted again iff covered range/store hypothesis is right. If unrepaired load is still accepted, 0x0000 is outside the covered range (falsifies covered-start 0); if repaired load is rejected, store 0x7D58 or range is wrong. Also flip a byte at 0x3DA3 and at 0x5000 (zero gap) separately: the gap flip changes the full-image sum but not the candidate sum — acceptance after the gap flip (no repair) supports candidate range ending ≤ 0x3DA4-ish; rejection supports a longer covered range.
  3. Candidate magic. Zero the dword at 0x7D50 (with checksum repaired per step 1, to isolate variables — note 0x7D50 is outside candidate covered range [0,0x3DA4), so no repair should be needed; needing one would refute the range). Prediction: load rejected via the -2 path (defaults), while a control mutation of a zero byte at 0x7D54 (repaired if needed) is accepted. If zeroing 0x7D50 is accepted, it is not the checked dword.
  4. Record array. In record 0, flip byte 0x0006 (14→15), repair checksum, reload. Prediction: accepted load; exactly one collection/entry-like UI element or stat differs (identify by screenshot diff). Corrupt record 20's first byte (0x04B0, currently the first zero record) to 0x01 + repair: prediction: a 21st entry appears or nothing changes (padding) — distinguishes "20 of 200 used" from fixed 20.
  5. 0xFFFF entry table. Write 0x0000 at 0x3C14 (first u16 entry), repair, reload. Prediction: if this is an empty-slot table, one previously-empty slot/entry becomes present (or load crashes — record it); no change implies display-only padding.
  6. u16 index/flag array. Change entry 20 at 0x2FD0 from 0x8000 to 0x0014, repair, reload. Prediction per FUN_08000fb0 step 5 semantics: the entry moves between the "indexed" and "0x8000-flagged" classes — observable as list ordering/availability change.
  7. Name records. Replace the text at 0x30D4 with same-length different Shift-JIS (83 58… → another valid pair sequence), keeping the FF FF record markers, repair, reload. Prediction: the corresponding label/name in UI changes verbatim, proving text (not graphics) semantics.
  8. Candidate counter. Change u16 at 0x3A78 from 1500 to 1501, repair, reload. Prediction: exactly one numeric display (score/money/count) increments; if instead load is rejected, 0x3A78 is inside a differently-covered region — informative failure.
  9. Flag at 0x3140. Change u32 at 0x3140 from 1 to 0, repair, reload. Prediction (per FUN_08000fb0 literal-offset write): a single boolean-like unlock/first-time flag toggles.
  10. Sparse tail clusters. Mutate 0x39C4 (06→07), 0x3A44, and 0x3BB2 one at a time, each repaired. Prediction: small settings/UI changes; a rejection on any of them (despite repair) indicates the candidate checksum range is wrong and must be re-derived from step 0 data.
  11. Blank-image control. Boot with cap-00 (all FF). Prediction from Chain B: load fails, defaults are built in RAM, game behaves as no-save. If it instead loads as valid, the entire reader model is wrong — stop and re-derive.
