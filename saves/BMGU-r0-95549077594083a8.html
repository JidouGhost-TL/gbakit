Release key: BMGU-r0-95549077594083a8 | Game code: BMGU / BMG | ROM SHA-256: 95549077594083a84cfe10c93bcc0be1599390d23cf0987dfb226cbb0987f757

All findings below are derived exclusively from this workspace: saves/cap-00-future-0.sav (the only .sav binary present), saves/hexdump_and_diffs.txt, ghidra/decompiled.c, ghidra/save_related_functions.c, and ghidra/callgraph.json, plus standard public GBA hardware addressing (SRAM/Flash 0x0E000000, EEPROM 0x0D000000/DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). 1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_VERIFIED — both decompiled code and real .sav bytes agree):

  • The save media is battery-backed SRAM, 32,768 bytes (256 Kbit), accessed as flat byte-addressable memory at 0x0E000000. No Flash bank-switch command bytes (0x5555/0x2AAA) and no EEPROM DMA3 serial-bitstream pattern appear anywhere in the 205 decompiled functions — this rules out Flash and EEPROM.
  • A generic, reusable block format: every save "slot" consists of a 4-byte header [u16 size][u16 checksum] immediately followed by size bytes of payload, both written and read through one pair of shared driver functions (FUN_08017fc0/writer, FUN_08017ec4/reader).
  • The checksum algorithm: a 16-bit truncating running sum of the payload's little-endian 16-bit words. Verified byte-for-byte against all 8 header+payload blocks present in saves/cap-00-future-0.sav (1 signature block + 1 main 1240-byte block + 7 x 120-byte record blocks) — every stored checksum matches the recomputed value exactly (see §4).
  • A 16-byte ASCII format-integrity signature "MarioGolfGBABUD\0" at file offset 0x0004, compared by the top-level format-check routine FUN_080181c8 against a ROM-resident reference string to decide whether the whole 32KB chip must be erased and reformatted.

Open / unresolved (HYPOTHESIS or UNKNOWN):

  • The exact numeric slot-ID-to-SRAM-offset table is stored in ROM and not present in this workspace, so slot IDs referenced in code (0x00, 0x41, and ~20 derived course-record IDs) are matched to observed file offsets by structural/size inference only, not by reading the table itself.
  • Semantic meaning of most payload bytes (what a "record" actually represents — course best score, par table, unlock flags, etc.) is inferred from byte patterns and numeric coincidences (e.g. 18/72 suggesting holes/par) but not proven by any decompiled code that names these fields.
  • Only one .sav sample is available, so no before/after gameplay diff could be performed; the sample's data appears to be an unplayed/default template state (large repeating sentinel-pattern arrays), not live gameplay.
  • states/ is empty — no paired .ss save states exist in this workspace, so no live RAM-to-SRAM flush could be traced dynamically; everything below is static-code + static-byte analysis only.

2. Physical Media, Slot Geometry & Redundancy

  • Media: SRAM, 32,768 bytes total (0x8000), background/fill byte 0x00.
  • Addressing: All save I/O terminates in two primitive loops, FUN_0801e27c (plain byte copy) and FUN_0801e2ec (byte copy used as a read-back/verify pass), both built on simple pointer increments — the classic GBA SRAM access pattern (one byte at a time, 8-bit bus). No 0x5555/0x2AAA Flash command sequence and no DMA3 (0x040000D4) 16-bit-serial EEPROM transfer pattern were found anywhere in ghidra/decompiled.c or ghidra/save_related_functions.c.
  • Write-verify-retry: FUN_0801e350 calls the write loop then the read-back loop and retries up to 3 times until they match — a defensive write that tolerates transient SRAM write failures.
  • Slots observed in saves/cap-00-future-0.sav:

Bytes 0x00E0-0x0EFF (between slot 0x00's payload end and slot 0x41's header) are entirely 0x00 in this sample — either genuinely unused padding or additional slots whose headers are themselves zero/uninitialized (a decoded size of 0 is explicitly treated as an error by the reader, see §3).

  • Redundancy / mirroring: FUN_080180e4 writes every block twice — once at the plain slot ID and once at (slot ID | 0x100) — and FUN_0801811c reads both plain and |0x100 copies, re-writing the plain copy if both reads succeed. This strongly implies a second mirror copy of at least the slot 0x00/slot 0x41 blocks exists somewhere else in the 32KB SRAM space (selected via the 0x100 flag passed into the ROM-resident slot table lookup FUN_08017ea0). This workspace's single .sav sample does not let us locate that mirror's absolute offset, because the base-address literal it resolves to (_DAT_08017fb8-class ROM constant) is abstracted away by the decompiler. Confidence: CONFIRMED_STATIC for "a mirror exists", UNKNOWN for its location.
  • Selection rule / generation counters: No explicit "active slot index" or incrementing generation/sequence counter field was identified. Slot selection appears to be purely by fixed slot ID (hardcoded per call site), not a rotating/ping-pong scheme as seen in some other GBA titles.

AddressRoleHow mapped
0x08017ea0Slot-ID → SRAM-offset lookup. 0x08017fc0Block serializer / writer. Resolves offset via 0x08017ea0, bounds-checks the free space in the slot's region, computes the sum16 checksum over the caller-supplied payload, packs `size(checksum << 16) into a 4-byte header, and writes header then payload via 0x0801e350`.

All traced callers and how they mutate save state

  • 0x080180e4 (caller of 0x08017fc0) — calls the writer twice per logical block: once with the plain slot ID and once with slot ID | 0x100. This is the redundancy/mirroring wrapper described in §2. Its only caller in this workspace is 0x080181c8.
  • 0x0801811c (caller of both 0x08017ec4 and 0x08017fc0) — reads the plain slot, then reads the |0x100 mirror; if both reads succeed it re-writes the plain slot via 0x08017fc0 — a resync/repair step that keeps the primary copy fresh whenever a mirror read succeeds. Called by 0x080181c8 (format-check path) and by 0x080c9554 (see below).
  • 0x08018180 (caller of the allocator, not of the block writer directly) — fills eight 0x1000-byte buffers via an indirect function pointer (consistent with a memset-style fill, likely to 0xFF or 0x00) and writes each one directly through 0x0801e350 at offsets 0x0000, 0x1000, ..., 0x7000 — i.e. erases the entire 32KB SRAM chip in 8 passes. Only caller: 0x080181c8.
  • 0x080181c8 — the format/integrity-repair entry point. Logic traced directly from the decompiled source:
  1. Allocate 220 bytes, read slot 0x00 into it via 0x0801811c(0, buf, 0xdc).
  2. If the read succeeded, compare the first 16 bytes of the payload against a ROM-resident 16-byte reference string (_DAT_080182f0).
  3. If the read failed or the 16-byte compare fails, call 0x08018180 (full-chip erase), then:
  • Rebuild slot 0x00: copy the 16-byte reference signature into a fresh 220-byte buffer and write it via 0x080180e4(0, buf, 0xdc).
  • Rebuild slot 0x41: allocate 1240 bytes, call an unexplored helper func_0x080c01c0() to populate it, write via 0x080180e4(0x41, buf, 0x4d8).
  • Rebuild up to 20 course-record slots of 120 bytes each: a nested loop (2 outer x 2 mid x 5 inner iterations) calls func_0x080c01c8(buf, idx, mid, outer) to populate a shared 1240-byte scratch buffer, then 0x080180e4(slot_id, buf, 0x78) with slot_id = outer*10 + mid*5 + inner + 9, writing a 120-byte sub-window of the buffer each time.
  1. Finally calls 0x0801811c(0, 0, 0xdc) to re-validate slot 0x00 after the rebuild.
  • This single function is responsible for writing every block offset identified in §2. Its only caller in this workspace is 0x080c9554.
  • 0x080c9554 — the highest traced entry point into the save subsystem. Calls 0x080181c8 (format check/repair-if-needed) then 0x0801811c(5, ..., size) to read slot 0x05, and copies bytes from the result into an engine-global struct (iRam080c95e8), subsequently writing derived single-byte flags (offsets +0xda, +0xdb, +0xff of that struct) that feed into a call gated on func_0x08200068(...) — consistent with applying loaded sound/options settings on boot or save-select, rather than being the point where gameplay progress is committed. No caller of 0x080c9554 exists within the 205 traced functions, so the actual trigger (boot, title screen, save-select menu, or an explicit "Save" confirmation) is UNKNOWN.
  • 0x081a7978 → 0x08017d68 → 0x08017a5c → 0x080179e4 — a separate chain that builds an in-IWRAM scorecard/record staging struct at iRam03000064, comparing the live course ID (iRam080000ac) against up to 8 ROM-resident reference course IDs to select which "best value" to copy in, and updating fields at struct offsets +0x00, +0x02, +0x0a, +0x0b, +0x10, +0x18, +0x1e, +0x28. 0x08017d68 also calls 0x08015f0c, which inserts a (course_id, value) pair into an 18-entry (0x18) lookup table. None of the functions in this chain, as traced in this workspace, call the SRAM writer (0x08017fc0) directly — the link from this in-RAM staging struct to an actual SRAM flush is not proven here; it may occur in a function outside the 205 sampled, or the flush may be driven generically by 0x080181c8's per-record rebuild reading this same staging data indirectly through func_0x080c01c8 (unresolved external symbol).

4. Magic Signatures & Checksum / Integrity Algorithm

Signature

  • Offset: 0x0004 (payload offset 4 within slot 0x00, i.e. file offset 4 relative to the slot-0 header at file offset 0).
  • Bytes: 4d 61 72 69 6f 47 6f 6c 66 47 42 41 42 55 44 00
  • ASCII: MarioGolfGBABUD\0
  • Proof: FUN_080181c8 decompiled source performs a 16-iteration byte compare (do { if (*(char*)(iVar1+iVar4) != *(char*)(_DAT_080182f0+iVar4)) unaff_r9 = 1; iVar4++; } while (iVar4 < 0x10);) directly on the just-read slot-0 payload.

Checksum algorithm

  • Formula: 16-bit truncating running sum of the payload interpreted as little-endian 16-bit words:
  acc = 0
  for each 16-bit little-endian word w in payload:
      acc = (acc + w) & 0xFFFF
  stored_checksum == acc  =>  valid

(If the payload length is odd, the trailing single byte is added as its own value — not exercised by any block in the current sample, all of which have even sizes.)

  • Endianness: little-endian throughout (both the header fields and the word-wise checksum input).
  • Covered range: the block's payload only (header_offset + 4 through header_offset + 4 + size), not the header itself.
  • Stored offset: header bytes [2:4] (upper 16 bits of the packed 32-bit header value size | (checksum << 16)).
  • Decompiled proof (reader, FUN_08017ec4):
  func_0x0801e218(iVar4, &uStack_24, 4);           // read 4-byte header into uStack_24
  uVar2 = uStack_24 & 0xffff;                       // size
  ...
  func_0x0801e218(iVar4 + 4, param_2, param_3);     // read payload
  uVar3 = param_3 + 1 >> 1;                          // word count
  uVar7 = 0;
  do {
      uVar7 = (int)((*param_2 + uVar7) * 0x10000) >> 0x10;  // (word + acc) truncated to 16 bits
      param_2 = param_2 + 1;
  } while (++uVar2 < uVar3);
  if ((uVar7 & 0xffff) == uStack_24 >> 0x10) goto LAB_08017f0e;   // compare to stored checksum
  • Decompiled proof (writer, FUN_08017fc0):
  uVar4 = (param_3 + 1) / 2;         // word count
  iVar6 = 0;
  do {
      iVar6 = iVar6 + (uint)*puVar3;  // plain sum (mod-2^32 int add)
      puVar3 = puVar3 + 1;
  } while (++uVar2 < uVar4);
  uStack_18 = iVar6 << 0x10 | param_3;   // pack: low16=size, high16=checksum (low16 of sum)
  func_0x0801e350(&uStack_18, iVar5, 4);       // write header
  func_0x0801e350(param_2, iVar5 + 4, param_3); // write payload

Python verification against the real .sav file

Script run against saves/cap-00-future-0.sav:

data = open('saves/cap-00-future-0.sav','rb').read()

def sum16(buf):
    s = 0
    n = (len(buf) + 1) // 2
    for i in range(n):
        w = buf[i*2] | (buf[i*2+1] << 8) if i*2+1 < len(buf) else buf[i*2]
        s = (s + w) & 0xffff
    return s

def check_slot(off):
    size = data[off] | (data[off+1] << 8)
    chk  = data[off+2] | (data[off+3] << 8)
    body = data[off+4 : off+4+size]
    return size, chk, sum16(body)

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace, so the mutations below are specified as offset-exact byte edits to saves/cap-00-future-0.sav together with the predicted observable effect after reloading that file in an emulator and capturing a fresh pre/post .ss pair (per the standing paired-save-state requirement):

  1. Global format-gate test. Zero out slot0_block_size at offset 0x0000 (dc 00 → 00 00) without fixing the checksum. Predicted: 0x08017ec4's uVar2 == 0 guard fails the read; 0x080181c8 should take its erase+reformat branch, performing a full 8x0x1000 SRAM wipe and rewriting slots 0x00, 0x41, and all 7+ course-record blocks back to the exact default pattern documented in §5. Verify by diffing the post-load .ss-derived SRAM image against the original file.
  2. Signature-vs-checksum isolation test. Flip one byte of the "MarioGolfGBABUD" signature at offset 0x0004 without touching the checksum at 0x0002 (now stale). Predicted: same erase+reformat branch as (1), since both the checksum compare and the signature compare should independently fail.
  3. Signature-only isolation test. Flip the same byte at 0x0004 but recompute and rewrite the checksum at 0x0002 so it matches the mutated payload. Predicted: if the engine's format gate is driven purely by the 16-byte signature compare (as the decompiled 0x080181c8 source suggests), the erase+reformat branch should still fire even though the generic checksum now validates — this isolates the signature check as an independent gate from the generic block checksum.
  4. Template-field semantic test. In slot_0x41_record_array_8b (offset 0x0FD4), change the hypothesized "holes" field of the first 8-byte record from 12 00 (18) to 63 00 (99), then repair the slot's checksum at 0x0F02. Predicted: if any code path (outside this workspace's 205-function sample) treats this value as a loop bound, an out-of-range value should produce an observable effect (menu glitch, crash, or silently clamped default) when the relevant course-select/record screen is opened — falsifying or confirming the "holes-per-course" hypothesis.
  5. Local-vs-global corruption test. Zero the size field of course_record_0 at offset 0x13E0 only, leaving its checksum stale. Predicted: 0x08017ec4's uVar2 == 0 guard fails for this one record only; since this slot is not part of 0x080181c8's slot-0 signature gate, expect a localized reset of only this 120-byte record (if/when read) rather than the global 32KB erase seen in test (1) — distinguishing the two integrity-failure handling paths documented in §3.

All mutation targets above are also encoded machine-readably in save-format.json under fuzzing_targets.
