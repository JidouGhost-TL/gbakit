All findings below are derived exclusively from the files in this workspace: saves/*.sav (raw bytes), saves/hexdump_and_diffs.txt (precomputed diffs), ghidra/decompiled.c (43 trace-guided decompiled functions), ghidra/callgraph.json, and ghidra/save_related_functions.c, plus standard, publicly documented GBA hardware addressing (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000, WAITCNT 0x04000204). No game-specific third-party research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM, and it is not uniform across layers:

  • HIGH confidence on the physical media and low-level I/O driver: the

traced code is a textbook GBA EEPROM 64Kbit (8KB) serial driver built on the DMA3 MMIO registers, and its behavior is fully consistent with the two .sav samples (erased-state file vs. a file with exactly two 8-byte-aligned active regions).

  • LOW confidence on the save-record semantics: the decompiled function

set (43 functions, scoped by the trace/seed tool to the save bus) contains only the low-level 8-byte EEPROM block read/write/verify primitives. It does

not contain the higher-level game code that decides when to save,

which block address to target, or how the checksum/magic footer is computed. Only one non-blank .sav sample exists, so no field hypothesis below could be confirmed by cross-sample statistics — only by matching byte-grid alignment to the hardware block size.

  • A 4-byte value 13 37 C0 DE at save offset 0x0004 is almost certainly a

magic/sentinel constant (it is not random — see §4), but it was not found as a literal anywhere in ghidra/decompiled.c, so it is .sav-verified but not code-verified.

  • A footer value 2E BC 66 D6 at offset 0x1FFC (inside the EEPROM's last

block, address 0x3FF) could not be reproduced by any of sum8/sum16/ sum32/xor8/crc32/two's-complement-sum32 over the candidate header region. It is left as HYPOTHESIS/UNKNOWN rather than claimed as a confirmed checksum — see the Python verification run in §4.

What is proven: EEPROM 64Kbit media, 1024×8-byte block grid, a generic DMA3-based 8-byte block read/write/verify driver (4 functions), and that exactly two blocks (block 0x000 and block 0x3FF) are touched by the single captured save event.

What remains open: the caller(s) that trigger a save, the meaning of every byte in block 0 beyond the candidate magic, the algorithm (if any) behind the block-0x3FF footer bytes, and whether any of blocks 0x001– 0x3FE are ever used (no sample shows them non-blank).

Slots/copies: Two distinct, non-adjacent regions are written by the one captured save event:

  • slot_0 / primary record — EEPROM blocks 0x000–0x007 (byte offsets

0x0000–0x003F, 64 bytes). Contains the only non-zero content in that range: a 4-byte magic candidate at +0x0004 (see §4); the remaining 56 bytes are all 0x00.

  • footer block 0x3FF — the chip's last addressable block (byte offsets

0x1FF8–0x1FFF). The first 4 bytes of this block equal the erased fill value 0xFFFFFFFF (so it is ambiguous whether they were deliberately rewritten to 0xFF or left untouched — a single 8-byte DMA3 write would write both halves together, so 0xFFFFFFFF as a written value is possible but not distinguishable from "never touched" with this evidence). The last 4 bytes hold 2E BC 66 D6.

Redundancy / mirroring: No evidence of a true mirrored backup copy. The 64-byte primary block and the 8-byte footer block differ in size and content structure, so the footer is more likely a distinct generation counter/metadata slot than a byte-for-byte backup of the primary record.

Selection rule: none observed — only one save slot/record was exercised in the available captures, so no slot-selection or rotation logic can be confirmed or ruled out.

3. Save Writer, Reader & Caller-Chain Architecture

All four traced save-bus functions are generic EEPROM driver primitives (matching standard documented GBA EEPROM-via-DMA3 behavior), not game-specific save logic. Source: ghidra/decompiled.c lines noted below; cross-checked against ghidra/callgraph.json and ghidra/save_related_functions.c.

3.1 0x0805cf48 — DMA3 transfer primitive (shared by both directions)

void FUN_0805cf48(undefined4 param_1, undefined4 param_2, uint param_3)
  • Saves/clears the IME interrupt-master-enable mirror (*_DAT_0805cfa8),

programs what are, by address pattern and bit usage, DMA3 SAD/DAD/CNT registers (*_DAT_0805cfb8 = param_1 [src], *_DAT_0805cfbc = param_2 [dst], *_DAT_0805cfc0 = param_3 & 0xffff | 0x80000000 [count | DMA-enable bit]), then polls bit 0x8000 of the CNT_H half-word until it clears — the documented DMA3-busy/enable-bit idiom — before restoring IME.

  • Called by both FUN_0805cfc8 (read) and FUN_0805d08c (write) to shuttle

serialized bitstreams to/from 0x0D000000 (EEPROM data port). This is the lowest-level MMIO hardware I/O driver in the traced set.

3.2 0x0805cfc8 — EEPROM 8-byte block READ

void FUN_0805cfc8(uint param_1 /*block addr*/, int param_2 /*out: 4x u16*/)
  • Builds an address-request bitstream in a 134-byte stack buffer: two

leading "1,1" request bits followed by the block address serialized MSB-first over a runtime-configured bit width (*(byte*)(*_DAT_0805d074+8), consistent with the EEPROM protocol's configurable 6-bit vs 14-bit addressing).

  • FUN_0805cf48(stackbuf, 0x0D000000, N+3) clocks the request bitstream out

to the EEPROM.

  • FUN_0805cf48(0x0D000000, stackbuf, 0x44) clocks 68 (0x44) response bits

back in from the EEPROM.

  • Unpacks those response bits into 4×16-bit words (MSB-first bit order,

written out in reverse word order into param_2[3..0]) — i.e. it deserializes one 8-byte EEPROM block into a caller-supplied buffer.

  • Caller: 0x0805d1ec (verify-read, confirmed via callgraph.json).

3.3 0x0805d1ec — EEPROM block READ + VERIFY

void FUN_0805d1ec(ushort param_1 /*block addr*/, short *param_2 /*expected 4x u16*/)
  • Calls FUN_0805cfc8(param_1, local_buf) to read 8 bytes back from the

given block, then compares all 4 words against the caller-supplied param_2 buffer; returns 0x8000 (fail flag) on first mismatch, 0 if all 4 words match. This is a classic "verify after write" routine.

  • Callers: none found in the traced 43-function set (confirmed by

callgraph.json: "0x0805d1ec": {"callers": []} and by grep across all of ghidra/decompiled.c for the symbol — no hit outside its own definition). This is an open gap: the code that decides to verify a save, and what "expected" data it checks, is outside our visibility.

3.4 0x0805d08c — EEPROM 8-byte block WRITE

void FUN_0805d08c(uint param_1 /*block addr*/, ushort *param_2 /*4x u16 payload*/, char param_3 /*blocking flag*/)
  • Serializes a write-request bitstream: leading request bits, the 4×16-bit

payload word-by-word (MSB-first), then the block address (same configurable bit width as the read path), then FUN_0805cf48(stackbuf, 0x0D000000, N+0x43) clocks the whole write bitstream out.

  • Afterward it busy-waits on bit 0 of 0x0D000000 (EEPROM write-ready flag)

using the hardware VCOUNT register (*_DAT_0805d178, compared against 0xE4 = 228, the GBA's total-scanlines-per-frame constant — i.e. this is a frame-boundary-aware wrap handler) with a timeout accumulator capped at 0x88 (136) scanline-ticks. param_3 selects whether the function retries indefinitely (!= 0, blocking) or bails after one timeout window (== 0).

  • **Caller found by manual source inspection (not present in

callgraph.json's edge list — see note below):** 0x0805d078.

3.5 0x0805d078 — blocking-write wrapper (caller-graph gap)

void FUN_0805d078(undefined2 param_1, undefined4 param_2)
{
  uVar1 = func_0x0805d08c(param_1, param_2, 1);   // forces blocking mode
  ...
}
  • A thin 1-line wrapper around FUN_0805d08c that hardcodes param_3 = 1

(always block/retry until the EEPROM reports write-complete).

  • Methodology note: ghidra/callgraph.json lists both "0x0805d078" and

"0x0805d08c" with empty callers/callees arrays — it missed this edge. We found it only by grep-ing ghidra/decompiled.c for func_0x0805d08c. This means callgraph.json (built from "static C + runtime direct-calls.json" per its header comment) is not fully complete, and any caller-chain claim in this report that relies solely on the JSON should be treated as a lower bound, not an exhaustive list.

  • Caller of 0x0805d078: none found anywhere in ghidra/decompiled.c

(verified by grep across the whole file). The actual game-logic entry point that decides when to persist a save and what block address/ payload to pass is not present in this trace — it is an explicit unknown, not something we can infer from clean-room evidence here.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Candidate magic signature

  • Offset: 0x0004 (bytes 4–7 of EEPROM block 0x000)
  • Bytes: 13 37 C0 DE
  • Verified in .sav: YES — present in cap-01-future-1.sav, absent (all

0xFF, i.e. erased) in cap-00-future-0.sav.

  • Verified in code: NO — grep -i "1337\|c0de" across

ghidra/decompiled.c and ghidra/save_related_functions.c returns no hits. The comparison/write of this literal happens in code outside the traced function set.

  • Confidence: HYPOTHESIS (strong structural evidence — it is the only

non-zero, non-boundary data in an otherwise all-zero 64-byte record, and its value is distinctive/non-random-looking — but not code-confirmed).

4.2 Footer bytes at 0x1FFC–0x1FFF

  • Bytes: 2E BC 66 D6 (as u32 LE = 0xD666BC2E, BE = 0x2EBC66D6)
  • Located in EEPROM block 0x3FF (the chip's last block), whose first 4

bytes (0x1FF8–0x1FFB) read back as FF FF FF FF — identical to the erased fill, so it is undetermined whether that half was actively rewritten to 0xFF or never touched (an 8-byte block write would cover both halves atomically either way).

We explicitly reject the temptation to claim a formula "probably" fits — none of the standard sum/xor/crc32 trials matched, and there is only one non-blank sample to test against, so even a coincidental match would not be verifiable. 6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav, loaded as .sav, paired with fresh gameplay.ss/final.ss save states per the project's capture-retention rules, and bounded to the existing ≤8 screenshot / ≤4 save-state caps per job.

  1. Magic-byte corruption — flip offset 0x0004 from 13 to 00 (or any

other byte), reload. Predicted: if 13 37 C0 DE is actually checked as a validity magic, the game should treat the save as absent/corrupt and fall back to a "new game" boot path (mirroring the observed all-0xFF cap-00 boot behavior). If nothing changes, the magic hypothesis in §4.1 is falsified.

  1. Reserved-region mutation — write non-zero bytes into 0x0008–0x003F

(currently all-zero) without touching the magic at 0x0004. Predicted: if this region is genuinely a zeroed/default game-state payload, the title screen or save-select UI should visibly reflect different stored state (e.g. non-default selection); if the magic alone gates load validity, no visible change is expected. This distinguishes "payload field" from "padding."

  1. Footer corruption at 0x1FFC–0x1FFF — flip one byte (e.g. 2E→2F)

and reload with no other changes. Predicted: if this is a checksum or integrity field consumed on load, the game should reject/reset the save (same signature as test 1); if it is an unchecked ID/counter, there should be no observable difference. Record which outcome occurs — this is the cheapest way to promote/demote the footer's confidence level without needing the missing caller code.

  1. Footer-only vs whole-block-1023 write test — since

0x1FF8–0x1FFB reads back as the erased value, write a distinguishable non-erased value there (e.g. AA AA AA AA) and observe whether the game ever overwrites it back to FF FF FF FF on a subsequent save. Predicted: if the game always writes the full 8-byte block together, a forced save event should restore FF FF FF FF there (proving it's an actively managed field); persistence of AA AA AA AA across saves would mean that half of the block is never touched by the traced write path.

  1. Blank-slot soak test — from the erased cap-00 state, step through

enough gameplay/menu actions to trigger at least one additional save event, and diff the result against both existing samples. Predicted: this should reveal whether blocks 0x008–0x3FE are ever used (currently unexercised in all available captures) and whether 0x0000-0x0003 ever becomes non-zero, which would start to explain its purpose.

  1. Repeated save-count check — perform two consecutive, distinct save

events and diff all three resulting .sav files. Predicted: this is the only way to gain the second non-blank data point needed before any checksum/counter formula in §4 could be promoted beyond HYPOTHESIS — a single sample is structurally insufficient for statistical confirmation, regardless of which formula is tried.

All of the above are genuine open counterfactuals — none of them assumes an answer in advance, and each has a concrete observable (visual delta, save rejection/reset, or byte-level recurrence) that can falsify the corresponding hypothesis in this report.
