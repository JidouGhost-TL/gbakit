1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both decompiled code and real .sav bytes (CONFIRMED_VERIFIED):

  • The save is a 32,768-byte SRAM image, fill byte 0xFF, with three non-0xFF spans:

0x0000–0x0063 (100 B), 0x7038–0x70BF (136 B), 0x70F8–0x711F (40 B). 276 non-fill bytes in each sample.

  • A 100-byte header block at file offset 0x0000 starts with the ASCII magic AGB-FE7\0,

is validated by FUN_080a1370 (string compare + u32 @ +8 compare + u16 @ +0xC compare + checksum compare), and is created by FUN_080a142c / written by FUN_080a13f0.

  • One checksum algorithm is used by every save block: FUN_080a1344, a 16-bit

(sum16 + xor16) mod 2^16 over little-endian u16 words. It verifies non-trivially on the header block (computed 0xa990 = stored 0xa990 at +0x60, both samples) and on the 20-byte block at 0x70F8 (computed 0x0800 = stored 0x0800 at +0x10 in cap-01-future-1.sav, where the payload is non-zero; 0x0000=0x0000 in cap-00-future-0.sav).

  • The only two bytes that differ between the two samples (0x7103: 0x00→0x04,

0x7109: 0x00→0x08) are exactly one payload-bit set plus its checksum-byte update in that 20-byte block: set bit 90 (u32 word 2, bit 26) of a 128-bit bit array. This matches the only traced in-game writer of that block type, FUN_080a24b8, called from FUN_08003e04.

Static-only (CONFIRMED_STATIC — code is unambiguous, .sav bytes are all-zero so they cannot independently confirm it):

  • Four further block types exist with the same checksum: a second 100-byte block

(FUN_080a1f28/FUN_080a1f84), a 36-byte block (FUN_080a1e50/FUN_080a1ea8), and two 20-byte bit-array blocks (FUN_080a23fc/FUN_080a2454, FUN_080a2520/FUN_080a2578). Their sizes sum with the header to exactly the 276 active bytes (100+100+36+20+20), which strongly constrains, but does not by itself prove, their file offsets.

  • The low-level SRAM byte-copy / write-with-verify / read path

(FUN_080c1000, FUN_080c1124, trampoline func_0x080c11a4, wrapper FUN_080a12a0).

Open / hypothesis (HYPOTHESIS / UNKNOWN):

  • Exact file offsets of the second 100-byte block, the 36-byte block, and which of the two

20-byte blocks sits at 0x70F8 vs 0x710C (sizes fit two orders; zero payloads cannot discriminate — see §2).

  • The 36-byte block's checksum length anomaly (writer and validator both pass 0x24,

i.e. the stored word at +0x22 is inside the summed range — see §4).

  • No fixed EWRAM/IWRAM mirror address (0x02xxxxxx/0x03xxxxxx) can be named for any

field: all traced buffers are stack buffers and all _DAT_ pointer values are unresolved.

  • FUN_080a1558 (seven 16-byte records) and FUN_080a01f0 (100-byte read, then a

0x8000-byte read, five-way branch on u32 @ +8) use the same read trampoline but cannot be placed in the .sav layout from the available evidence.

  • Negative result: the two "MMIO seed" functions in ghidra/save_related_functions.c,

FUN_080c126c and FUN_080c1424, are not save functions at all. They are signed divide/remainder library routines (shift-and-subtract loops, func_0x080c1268() trap on divisor 0, no memory-mapped I/O anywhere in their bodies). The seed extraction is a false positive; the real save cluster is at 0x080a12xx–0x080a25xx plus 0x080c1000/0x080c1124/0x080c11a4, found by following FUN_080a1344 and its callers.

  • Negative result: no Flash command sequence (0x5555/0x2AAA writes), no EEPROM DMA3

pattern (0x040000D4), and no literal 0x0E000000/0x04000204 appears anywhere in ghidra/decompiled.c (full-text search, 0 hits each). The traced save path is SRAM-style byte copy with read-back verification, consistent with the SRAM 256K media in PACKET.md.

Slot geometry. There are no save "slots" in the usual multi-slot sense and no backup copies: the string AGB-FE7 occurs exactly once in each file (Python search at 0x0 only), no block is duplicated at a second offset, and no generation/sequence counter changes between samples (the whole header block is byte-identical between samples; u32 @ +8 = 0x00030115 is a constant compared against a ROM constant by FUN_080a1370, not a counter). Why these offsets are only HYPOTHESIS: every block's SRAM destination is computed from unresolved _DAT_ values (e.g. writer FUN_080a1f84 calls FUN_080a12a0(param_1, *_DAT_080a1fac + _DAT_080a1fb0, 100)), so no code-visible offset exists in the workspace. The assignment above is the smallest layout consistent with the samples: 100+36 = 136 = the 0x7038 span and 20+20 = 40 = the 0x70F8 span, with every block zero-filled by its creator (so an all-0x00 span is exactly what a freshly created B/C/D/E looks like, and an 0xFF byte inside a block's span would have contradicted it). Two orders fit each span (B-then-C or C-then-B starting at 0x7038; D/E in either order at 0x70F8), and all-zero payloads give no checksum discrimination (0 over any range = stored 0). Boot validation order in FUN_08000a20 is A, C, B, D, E — which is not assumed to be file order and is noted here only to show it cannot settle the question either.

Selection rule / redundancy: none. There is no primary/backup pair and no "pick newest" logic in any traced function. Each block is independently validated at boot by FUN_08000a20; a block that fails validation is recreated to its default in place (zero-filled, or the fixed header template for block A) and rewritten. The cold-reload probe in PACKET.md (probe_offset_hex 0x7103, integrity_check_confirmed: true, save_rewritten_after_mutation: true, reverted_to_blank_on_mutation: false) is consistent with this: mutating a payload byte of the 0x70F8 block breaks its FUN_080a1344 checksum, and the boot path rewrites (recreates) the block rather than blanking the whole save.

Erase behaviour: FUN_080a1308 fills a 64-byte stack buffer with 0xFFFFFFFF and writes it in 0x40-byte chunks via FUN_080a12a0(auStack_50, *piVar1 + iVar4 * 0x40, 0x40) for iVar4 = 0.._DAT_080a1340 (base and count unresolved). It is called by the header creator FUN_080a142c before writing a fresh header, and by every branch of FUN_080a01f0. Its exact span is UNKNOWN.

3. Save Writer, Reader & Caller-Chain Architecture

How callers were mapped. Three independent routes were cross-checked: (1) literal text search of ghidra/decompiled.c for func_0x08… / FUN_08… call sites — the most complete route, because most functions end in an UNRECOVERED_JUMPTABLE tail jump that makes Ghidra's recovered call graph drop edges; (2) ghidra/callgraph.json callers/ callees (291 nodes) — corroborates many edges but is missing e.g. all FUN_08000a20 → creator edges that are plainly visible in the C text, so absence in the callgraph was never treated as evidence of absence; (3) argument-shape analysis at each call site (buffer, length, stored-offset arithmetic) matched against the .sav layout. Where callgraph and C text disagree, the C text is quoted and the disagreement is noted.

3.2 Serialization, validation, and checksum routines

One pattern is repeated for every block: a validator reads the block into a stack buffer with func_0x080c11a4, recomputes FUN_080a1344 over a block-specific length, and compares against the stored u16; a writer recomputes and stores the checksum, then flushes the whole block with FUN_080a12a0 → FUN_080c1124 (write + verify, 3 retries); a creator zero-fills a stack buffer with CpuFastSet, sets any fixed fields, and calls the writer. There is no separate serialisation step — the stack buffer is the on-media layout (fields are accessed at the same param_1 + offset in validators, creators, and writers).

3.3 Caller chains (every traced caller, and how each mutates the in-RAM struct)

RAM-mirror note applying to every chain below: the "in-RAM save struct" in all traced code is a caller-owned stack buffer (auStack_*), not a fixed 0x02xxxxxx/ 0x03xxxxxx structure. Creators/writers mutate that buffer, then FUN_080a12a0 flushes it to SRAM. No traced function writes a persistent EWRAM/IWRAM mirror of a save block; any such mirror would be reached only through unresolved _DAT_ values. ram_addr is therefore null in save-format.json for all fields, with the stack buffer named in the evidence instead.

Chain 1 — boot validation / auto-repair (FUN_08000a20, no traced caller; entry point).

cVar1 = func_0x080a1370(0, …); if (cVar1 == '\0') func_0x080a142c();  // A: validate, else create header
cVar1 = func_0x080a1e50(0);    if (cVar1 == '\0') func_0x080a1508();  // C: validate, else zero-create
cVar1 = func_0x080a1f28(0);    if (cVar1 == '\0') func_0x080a1fb4();  // B: validate, else zero-create
cVar1 = func_0x080a23fc(0);    if (cVar1 == '\0') func_0x080a23d0();  // D: validate, else zero-create
cVar1 = func_0x080a2520(0);    if (cVar1 == '\0') func_0x080a24f4();  // E: validate, else zero-create

Each validator first gates on FUN_080a1290() (SRAM-present flag from FUN_080a121c). Mutation of the in-RAM struct: none on success (validators only read into a scratch buffer); on failure the paired creator builds a fresh default buffer (header template for A, all-zero for B/C/D/E) and the writer stamps its checksum at +0x60/+0x60/ +0x22/+0x10/+0x10 respectively before flushing. This chain, executed at boot, fully explains the observed .sav initialisation: an AGB-FE7 header at 0x0 and zeroed blocks elsewhere, on an otherwise 0xFF image. It also explains the PACKET.md probe result at 0x7103 (block rewritten after mutation, save not blanked).

Chain 2 — header display / status (FUN_080a0fe8 → FUN_080a1370, FUN_080a1558, FUN_080a2f50). FUN_080a0fe8 (no traced caller; text-output heavy via FUN_08004f38, a debug/status print routine) validates A into auStack_84; on success it formats the u32 @ +8 with FUN_080a0f9c (renders a value as hex-digit pairs separated by /), then loops iVar5 = 0..6 calling FUN_080a1558(auStack_20, iVar5) (the seven 16-byte records) and prints a fallback string when a record fails its ID check, then prints FUN_080a2f50()'s result and four 1-digit values from untraced helpers (func_0x080a18e0/18e4/191c/19e8, not in the decompiled set). It mutates no save struct — read-only chain. Confidence: CONFIRMED_STATIC for structure; the exact on-screen meaning of each printed value is UNKNOWN (string contents live in unresolved _DAT_s).

Chain 3 — counted-array reader (FUN_080a2f50 → FUN_080a1370 → FUN_080a2f34; caller FUN_08012438). FUN_080a2f50 validates A into auStack_68 and returns FUN_080a2f34(auStack_68), the count (0–12) of non-zero bytes in A's +0x14..+0x1F array, or 0 if A is invalid. FUN_08012438 combines that count with FUN_080123e8()'s result (Chain 5) into a 0–10 rank/grade value (iVar1 < 2 split, then thresholds 4/10/0x13/0x1b on iVar2). Read-only; mutates nothing. This is the only traced semantic reader of a header field beyond validation, and it pins +0x14 as a 12-entry byte array whose entries are counted as booleans.

Chain 4 — bit-set writer, the mutated block (FUN_08003804 → FUN_0800375c → FUN_080036f0 → FUN_08003e04 → FUN_080a24b8 → FUN_080a2454 → FUN_080a12a0). FUN_08003804(p1,p2,p3) forwards to FUN_0800375c, which (guard conditions on unresolved RAM state) calls FUN_080036f0(param_1, param_3). FUN_080036f0 sets bytes +6 = 1, +7 = 0 and a short @ +4 on an unrelated RAM object (_DAT_08003750), then calls func_0x08003e04(param_1, param_2). FUN_08003e04:

if ((int)param_1 < 0x80) { func_0x08003e88(param_1); func_0x080a24b8(0, param_1); }

(FUN_08003e88 is a sound/effect side path: values 0x5a, 0x5c, 0x5f select FUN_08003e6c(8), others FUN_08003e5c() → FUN_08003e6c(7).) Then the save mutation:

// FUN_080a24b8(buf, idx): if buf==NULL, validate D into a stack buffer first;
*(uint *)(param_1 + ((int)param_2 >> 5) * 4) |= 1 << (param_2 & 0x1f);
FUN_080a2454(param_1);   // restamp checksum @ +0x10, write 20 B to SRAM

So this chain sets bit param_1 (must be < 0x80, i.e. one of 128 bits in the 16-byte payload) in block D's bit array and immediately rewrites the whole 20-byte block with a fresh checksum. This is the writer that produced the observed sample diff: between cap-00 and cap-01 exactly one bit flips — word 2 (+8), bit 26 → global bit 2*32 + 26 = 90 = 0x5A (note 0x5a is also one of FUN_08003e88's special cases) — byte 0x70F8+0x0B = 0x7103 goes 0x00→0x04 (the byte holding bit 90, value 1 << 2), and the checksum byte at 0x70F8+0x11 = 0x7109 goes 0x00→0x08 because the stored u16 @ +0x10 becomes 0x0800 (§4). Callgraph corroboration: callgraph.json lists FUN_080a24b8 callees 0x080a23fc, 0x080a2454; the FUN_08003e04 → FUN_080a24b8 edge is visible in C text but the callgraph lists no callers for 0x08003e04 (its caller 0x080036f0 is recorded with empty callees) — a recorded example of callgraph incompleteness, resolved in favour of the C text.

Chain 5 — sub-record dispatch (FUN_080123e8 → FUN_080a34ac/FUN_080a3dd0 → FUN_080a1558). FUN_080a34ac(idx) and the near-identical FUN_080a3dd0(idx) (no traced caller for the latter) gate on FUN_080a1290() and return FUN_080a1558(0, idx). Checksum algorithm (exact)

Decompiled proof — FUN_080a1344 at 0x080a1344, complete body:

void FUN_080a1344(ushort *param_1, int param_2)
{
  short sVar1;
  ushort uVar2;
  sVar1 = 0;
  uVar2 = 0;
  param_2 = param_2 / 2;
  if (0 < param_2) {
    do {
      sVar1 = sVar1 + *param_1;
      uVar2 = uVar2 ^ *param_1;
      param_1 = param_1 + 1;
      param_2 = param_2 + -1;
    } while (param_2 != 0);
  }
  (*UNRECOVERED_JUMPTABLE)(sVar1 + uVar2);   /* return (sum16 + xor16) */
}

Formula: for u16_le words w[0..n-1] over the covered byte range, sum = Σ w[i] mod 2^16, x = w[0] ^ w[1] ^ … ^ w[n-1],

stored checksum = (sum + x) mod 2^16, stored as u16_le. No seed, no complement, no byte swap; endianness is the GBA's native little-endian u16 load. (sVar1 is a signed short, but addition mod 2^16 is identical; the validator compares as *(short *)(buf + stored_off), the writer stores as undefined2 — same 16 bits.) Schema name: custom (a sum16+xor16 composite, not a plain sum16_le/xor16_le/CRC).
