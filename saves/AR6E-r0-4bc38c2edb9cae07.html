GBA Save Format Report — Tom Clancy's Rainbow Six - Rogue Spear (USA) (En,Fr,De,Es,It) (AR6E)

Clean-room analysis derived only from saves/*.sav, ghidra/decompiled.c (255 functions), ghidra/save_related_functions.c, and ghidra/callgraph.json in this workspace, plus standard GBA hardware addresses. No third-party game data was used.

1. Executive Summary & Overall Confidence

Overall confidence: HIGH for media, layout, magic, and checksum; MEDIUM/LOW for gameplay semantics of individual fields.

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is EEPROM 4 Kbit = 512 bytes, SDK tag EEPROM_V122, accessed serially via DMA3 to 0x0D000000.
  • The .sav dump stores every 8-byte EEPROM block byte-reversed relative to the logical (RAM) byte stream. Reversing each block yields magic ROGUES02, little-endian fields, and checksums that validate on both captures, for all 5 profile slots and the global record. The reversal is consistent with the driver code, which assembles/disassembles the serial bitstream MSB-first with descending buffer pointers (FUN_0803a7f8, FUN_0803a8a8).
  • Integrity is a 16-bit byte-sum (sum8 accumulated in s16), computed by FUN_0803a2a0. No CRC/XOR was found.
  • Layout: magic block (8 B) + 5 profile slots × 28 B at logical 0x08..0x93 + one global record (24 B) at logical 0x94..0xAB; the rest is unused.

Open: exact gameplay meaning of each u32 field (all slots in both captures hold factory defaults, so no differentiated progress is observable), absolute RAM base addresses (Ghidra _DAT_080xxxxx placeholders were not resolved to values in the provided decompilation), and the unrecovered indirect callers of the boot-time loaders.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level EEPROM hardware driver (SDK, EEPROM_V122)

AddrRoleNotes
0x0803a778DMA3 transferPrograms DMA3 registers (src/dst/count param3 & 0xFFFF \| 0x80000000 = enable), spins on busy bit 0x8000. One endpoint is 0x0D000000 (EEPROM serial bus). Callers: 0x0803a7f8, 0x0803a8a8 (callgraph).
0x0803a7f8EEPROM read one 8-byte blockBuilds MSB-first address bitstream (address bits from config +8, block-count bound from config +4), DMA-out address, DMA-in 0x44 bits, reassembles 4×u16 MSB-first into the caller buffer via a descending pointer — the origin of the per-block byte reversal in dumps. Returns 0 on success.
0x0803a8a8EEPROM write one 8-byte blockExpands 4×u16 + address LSB-first-into-bit-array, DMA-out addr_bits + 0x43 bits to 0x0D000000, then polls uRam0d000000 & 1 and *_DAT_0803a97c for write completion; bracketed by helpers 0x0803a6ac (bus setup) and 0x0803a734 (bus teardown).
0x0803a984VerifyReads block back via 0x0803a7f8 and compares 4×s16; returns 0x8000 on mismatch.
0x0803a9dcWrite+verify with retryUp to 3 attempts of 0x0803a8a8 + 0x0803a984. This is the write path's only redundancy.
0x0803a6ac / 0x0803a734Bus enable/disable helpersToggle 8 << pin bit in a control register; save/restore DMA/bus state. Callees of 0x0803a8a8 only.
0x0803a60c / 0x0803a674EEPROM type/config selectUsed by FUN_0800c468 (detect/identify EEPROM, argument 4), which reads the config word and reports validity in param_1[2..3]. CONFIRMED_STATIC.

There is no SRAM (0x0E000000) or Flash (0x5555/0x2AAA) code in the save path; all persistence goes through the EEPROM driver above.

3.4 How callers were mapped (method & limits)

  • ghidra/callgraph.json only records direct FUN_ edges; most game→SDK calls appear in the C as func_0x080… (unrecovered indirect/thunk calls) and are absent from the graph (e.g. it lists 0x0803a9dc with no callers, while the C shows it called from FUN_0800c3c4). Caller chains below therefore combine callgraph edges with textual func_0x… reference search in ghidra/decompiled.c. Every chain link below was read in the function body, not inferred from names.
  • No textual or graph caller was found for 0x080198a8, 0x0802e5e0, 0x0802e678, or 0x0800c33c; they are presumed reached via function-pointer tables / boot glue whose jump tables Ghidra did not recover (UNRECOVERED_JUMPTABLE warnings throughout). Marked CONFIRMED_STATIC for behaviour, UNKNOWN for trigger context.

Caller chains (entry → flush):

  1. Boot load-all: 0x080198a8 → 0x08019d10 → 0x0803a1b8 → 0x0800c4ac → 0x0800c50c → 0x0803a7f8 → 0x0803a778 (DMA3). RAM mutation: checksum-gated default replacement (7×u32 ROM defaults) on failure; then conditional 0x08019d98+0x08019d6c re-save for empty slots.
  2. Slot save: (gameplay caller unrecovered) → 0x08019d6c → checksum store at RAM slot+0x18 → 0x0803a1f8 → 0x0800c4c4 → 0x0800c3c4 → 0x0803a9dc (write+verify ×≤3) → 0x0803a8a8 → 0x0803a778.
  3. Global load: (caller unrecovered) → 0x0802e5e0 → 0x0803a238 → read chain as (1). RAM mutation: default reset on invalid/zero, no write-back.
  4. Global save: (caller unrecovered, presumably options/menu exit) → 0x0802e678 → zeroes RAM global+0x04, stores checksum at +0x16 → 0x0803a26c → write chain as (2).
  5. Format/validate: (caller unrecovered) → 0x0800c33c → magic memcmp; on mismatch zero-fills device and rewrites magic. This is the only path that writes block 0; game code never rewrites the magic afterwards.

RAM mirror addresses: the decompilation references all RAM structs only through unresolved _DAT_080xxxxx constants (values live in ROM literal pools not included in the workspace), so absolute 0x02xxxxxx/0x03xxxxxx bases are honestly UNKNOWN. What is proven is the relative layout: slot array base with 28-byte stride (5 entries, +0x00..+0x8B), followed in the same struct by derived fields at +0x8C..+0xA3 (0x08019dd8); the global record is a separate 24-byte struct (base _DAT_0802e620).

4. Magic Signatures & Checksum / Integrity Algorithm

Magic

  • Logical (RAM/EEPROM) bytes at offset 0x00: 52 4F 47 55 45 53 30 32 = ASCII ROGUES02 (plausibly "Rogue Spear 02"). In the raw .sav dump the block appears reversed: 32 30 53 45 55 47 4F 52 = 20SEUGOR, matching the ascii_magic_strings in PACKET.md.
  • Verified in code: FUN_0800c33c reads 8 bytes at offset 0 and memcmps against the caller-supplied expected string, zero-formatting the device on mismatch. The expected string literal itself is passed by an unrecovered caller, so the code-side string is CONFIRMED_STATIC by structure; the byte value is CONFIRMED_VERIFIED by the .sav data under the reversal transform that simultaneously validates every checksum (below) — a coincidence probability that is negligible.
  • Raw↔logical offset mapping (within each 8-byte block B): logical = B + (7 - (raw - B)). E.g. raw 0x93→logical 0x94, raw 0x9B→logical 0x9C, raw 0xAD→logical 0xAA.

Checksum

  • Algorithm: sum16 of unsigned bytes — FUN_0803a2a0: s16 acc=0; for i<len: acc += (u8)buf[i]; return acc; No seed, no complement, no XOR, no CRC. Stored as u16 in RAM byte order (little-endian); in raw dumps it appears inside its reversed block.
  • Per-slot: covers logical slot+0x00 .. slot+0x17 (24 bytes), stored at slot+0x18 (u16_le), bytes slot+0x1A..0x1B unused (00 00 observed). Computed on save by FUN_08019d6c, verified on load by FUN_08019d10 via FUN_08019e94.
  • Global: covers logical 0x94 .. 0xA9 (22 bytes), stored at 0xAA (u16_le). Computed on save by FUN_0802e678, verified on load by FUN_0802e5e0.
  • There is no whole-image checksum and no checksum over the magic block.

Python verification (run in this workspace)

import struct
def logical(d): return b''.join(d[i:i+8][::-1] for i in range(0, len(d), 8))
for fn in ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]:
    L = logical(open(fn, "rb").read())
    assert L[:8] == b"ROGUES02"
    for s in range(5):
        seg = L[8+s*28 : 8+s*28+28]
        assert (sum(seg[:24]) & 0xFFFF) == struct.unpack_from("<H", seg, 24)[0]
    g = L[0x94:0x94+24]
    assert (sum(g[:22]) & 0xFFFF) == struct.unpack_from("<H", g, 22)[0]

EEPROM byte-level geometry for tooling: to edit a logical offset L, write raw offset (L & ~7) + (7 - (L & 7)) in the .sav dump (and read symmetrically). Equivalently, reverse each 8-byte block, edit logically, reverse back.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss states exist in this cohort (states/ is empty), so predictions are stated for reload in an emulator with the mutated .sav attached. Repair procedure for any data mutation: recompute the affected record's u16_le sum (slot: sum of 24 data bytes → +0x18; global: sum of 22 data bytes → +0x16) in logical space, then re-apply per-block reversal. Mutations below are given in logical offsets.

#MutationChecksum repairPredicted observable effect
1Global +0x00 (logical 0x94): 1 → 0Yes (global)On boot, FUN_0802e5e0 treats record as blank → RAM defaults (w0=w1=w2=1, w4=0); EEPROM unchanged until next global save. Tests the zero-sentinel rule independently of checksum.
2Slot0 +0x10 (logical 0x18): 0 → 1 (set one flag bit)Yes (slot0)Slot loads normally; FUN_08019dd8 aggregate +0x9C gains the bit. Observe menu/unlock UI for profile 1. Identifies flag semantics.

5Magic byte logical 0x00: R → XN/A (no checksum covers it)Next boot's validate-or-format (FUN_0800c33c) zero-fills the whole EEPROM and rewrites ROGUES02; all profiles lost. Strongest integrity test — do on a copy.
6Global +0x04 persisted as 0xDEADBEEF (hand-edited .sav)Yes (global)Loads fine (no rule against non-zero), but the next global save stores 0 again (FUN_0802e678 zeroes it). Confirmed by re-dumping after one options save. Tests the transient-field hypothesis.
7Write garbage into logical 0x0AC..0x1F7NoNo effect on load (no traced reader). Any observed effect would falsify the layout and reveal an unmapped record.
8Truncate/blank last block 0x1F8 from FF×8 to 00×8NoPredicted no effect (never addressed). Distinguishes emulator fill behaviour from game behaviour.

General counterfactual: any single-byte data corruption with checksum repair must load silently with only that field changed; any corruption without repair must revert exactly one record (slot or global) to defaults — never the whole save (except magic corruption, #5). Deviation from this pattern indicates an unmapped integrity mechanism.
