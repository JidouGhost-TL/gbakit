1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • The save medium is a 512-byte EEPROM (EEPROM 4K, 64 × 8-byte blocks) accessed serially through DMA3 to 0x0D000000, not SRAM (0x0E000000) and not Flash sector commands (0x5555/0x2AAA).
  • The 512 bytes are partitioned, without remainder, into three 152-byte (0x98) game slots and one 56-byte (0x38) global/config block at 0x1C8.
  • Every block header carries the 8-byte RAM magic game002\0 (bytes 67 61 6D 65 30 30 32 00). In the raw .sav, each 8-byte EEPROM block is byte-reversed, so the magic appears as 00 32 30 30 65 6D 61 67 — read naïvely as \0 + 200emag.
  • The integrity algorithm is Bob Jenkins' lookup2 hash (the 9-step mix with shifts 13/8/13/12/16/5/3/10/15), initialised a = b = 0x9E3779B9, c = 0x805, returning final c, stored as a little-endian u32 at header offset +12 and computed over the payload only. It reproduces the stored value in both sample files exactly, for the 32-byte global payload (see §4 for the full Python verification output).
  • All three game slots in both samples are empty (header status 0, payload never written, payload region still 0xFF). The global block is occupied (status 1) and holds four clamped scalar fields.
  • The transition between the two samples is fully explained in code: the global payload field at +0 is a signed/clamped field with stored value -1 (0xFFFF) in cap-00; the loader clamps it to 0; the next global save rewrites the header+payload and the Jenkins hash changes accordingly. The only changed .sav bytes are the stored hash (physical 0x1D0..0x1D3) and the physical image of that clamped field (0x1E6..0x1E7).

Proven by code only (CONFIRMED_STATIC):

  • The slot payload integrity path (identical Jenkins hash, but over 0x80 bytes), slot-header repair-on-load, valid-slot counting, the factory-default global writer, and the settings-save writer.

Still open (HYPOTHESIS / UNKNOWN):

  • The gameplay serializer that fills a 128-byte slot payload and writes it at slot*0x98 + 0x18 does not occur in the 266 decompiled functions. No caller in the corpus writes slot payloads. Therefore the internal field layout of a populated game slot is unknown.
  • The exact EWRAM/IWRAM addresses of the RAM mirrors are not recoverable: the decompilation references them only through unresolved literal-pool symbols (_DAT_08033cf0, _DAT_08034010, uRam08033f20, …), whose pointed-to values are not present in the workspace.
  • The top-level callers of FUN_08033ca0, FUN_08033f24, FUN_08033f8c, FUN_0803440c and FUN_0803447c are not recoverable. Every such function ends in an UNRECOVERED_JUMPTABLE; their callers were reached through indirect/vtable dispatch that the corpus does not resolve, and callgraph.json lists them with callers: [].
  • The gameplay meanings of global fields +0/+2/+4/+8 are only constrained by their clamp ranges (see §5); names such as "language", "volume" are hypotheses, not proof.

Why not HIGH: the game's main per-slot payload format — the largest part of a real player's save — has no valid sample and no writer in the corpus. Everything around it (media, geometry, magic, hash, global block, driver stack) is verified.

2.3 Redundancy, mirroring, generation counters, selection rule

  • No mirroring / backup copies. Each slot and the global block occur exactly once. No code reads a second copy, compares copies, or falls back. This is visible both in the address constants above and in the .sav images (each header occurs once per region; there is no duplicate global block).
  • No generation / sequence counter. Header fields at +8 and +20 are constants in the samples (0x00000000 for initialised slots, 0xFFFFFFFF sentinel in the global header) and are not incremented by any writer. FUN_0803440c/FUN_0803447c do not touch them, and FUN_08033f8c resets them to 0. If freshness arbitration were needed, it is not implemented here.
  • Validation status word instead of redundancy. Header +16 is a state value, not a counter: 0 = never written / empty slot, 1 = payload present and (for loads) hash-checked, 0xFFFFFFFF = invalid (magic mismatch, hash mismatch, or out-of-range status ≥ 2, subject to the FUN_080344dc flag discussed in §3.4).
  • Selection rule (as coded).
  • FUN_08033f8c loads the three slot headers (through FUN_08033e98) into a zeroed 0x48-byte RAM array; any slot that fails validation is re-initialised in RAM and its 24-byte header alone is rewritten to EEPROM (empty-slot repair).
  • FUN_08033f24 counts slots whose EEPROM header reads back and whose magic strcmp succeeds — note it does not check status or payload hash, so a header-valid but corrupt-payload slot counts as "present" here while FUN_08033e98 would reject it.
  • The single global block is taken as-is; on hash success its payload fields are clamped in RAM (§3.4, §5). There is no alternative global copy to select.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 How callers were mapped (method)

Two sources were combined, because either alone is incomplete:

  1. callgraph.json provides reliable direct edges for the low-level driver stack (e.g. 0x080565b0 → {0x080563e4, 0x08056558}, 0x08056334 → 0x080562b4).
  2. A text search over decompiled.c for func_0x0803e5fc, func_0x0803e6b4, func_0x08052468, func_0x08052414, func_0x08052f20 recovers the high-level edges the callgraph misses. The callgraph lists 0x0803e5fc/0x0803e6b4 with no callees at all, yet their bodies plainly call FUN_08056334/FUN_080565b0; conversely almost every function terminates in an UNRECOVERED_JUMPTABLE, so callers reached only via function pointers (including all callers of the §3.4 entry points) cannot be enumerated from this corpus and are reported as unknown rather than guessed.

Wrapper functions at 0x08052414 (strcpy → FUN_08058298), 0x08052468 (strcmp → FUN_0805823c) appear in the decompilation with void prototypes and no visible arguments; their argument use below is reconstructed from the call sites and from the verified magic bytes, and their identity as string copy/compare is read from their callees' bodies.

All offsets in this report are logical EEPROM/RAM offsets unless called "physical .sav".

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • RAM/logical bytes (8 bytes, at header +0 in every slot and in the global block): 67 61 6D 65 30 30 32 00 = ASCII game002 + NUL.
  • Physical .sav bytes at each header start: 00 32 30 30 65 6D 61 67 (the 8-byte block reversed; naïve ASCII scan sees \0 + 200emag, which is the string reported in PACKET.md).
  • Verified in code: writers copy this string with FUN_08052414 (strcpy → FUN_08058298); readers compare with FUN_08052468 (strcmp → FUN_0805823c) and treat equality (0) as valid. Call sites: FUN_08033ca0, FUN_08033e98, FUN_08033f24, FUN_08033f8c, FUN_0803440c, FUN_0803447c.
  • Verified in .sav: present at logical offsets 0x000, 0x098, 0x130, 0x1C8 in both files after per-block reversal (raw bytes above before reversal).

4.2 Checksum algorithm

  • Algorithm: Bob Jenkins lookup2 (predecessor of hashlittle; not CRC, not a byte sum). Family is custom in JSON terms, described here exactly.
  • Function: FUN_08052f20(byte *data, uint length) in decompiled.c. The sibling string hash FUN_08052d9c uses the identical mix.
  • State and constants: a = b = 0x9E3779B9 (the Jenkins golden-ratio constant, loaded from the same literal _DAT_08052fd8 for both), c = 0x805 (literal _DAT_08052fdc; the value 0x805 was recovered by exhaustive search over c with a=b=0x9E3779B9 and then independently confirmed on the second sample, which played no part in the search — a chance match on both files is ~2⁻⁶⁴). Returns final c as u32.
  • Main loop (while ≥ 12 bytes remain): a += LE32(data+0); b += LE32(data+4); c += LE32(data+8); mix(a,b,c), where all arithmetic is mod 2³² and mix is exactly, in order:
a -= b; a -= c; a ^= c >> 13;
b -= c; b -= a; b ^= a << 8;
c -= a; c -= b; c ^= b >> 13;
a -= b; a -= c; a ^= c >> 12;
b -= c; b -= a; b ^= a << 16;
c -= a; c -= b; c ^= b >> 5;
a -= b; a -= c; a ^= c >> 3;
b -= c; b -= a; b ^= a << 10;
c -= a; c -= b; c ^= b >> 15;

This transliteration was machine-checked against the decompiled step sequence (shifts 13, 8, 13, 12, 16, 5, 3, 10, 15) — the decompiled body performs the same operations with b/c pre-incremented by their data words, which is algebraically identical.

  • Tail: c += length; then the remaining r bytes (r = length mod 12) are folded in as zero-padded little-endian words with Jenkins' fall-through masking (r ≥ 9: masked third word into c; r ≥ 5: masked second word into b; r ≥ 1: masked first word into a; r = 8 adds both full words into a/b only), followed by one final mix. For both verified global payloads r = 8 and the two tail words are zero, so the tail contribution is provably inert there; for a 0x80-byte slot payload r = 8 also, but the tail words will generally be non-zero.
  • Covered range: payload only — global: the 32 RAM bytes at logical 0x1E0..0x1FF; slot (static): the 128 RAM bytes at slot*0x98+0x18 .. +0x98. The header (including the magic) is not covered.
  • Stored location: logical header +12, u32 little-endian in RAM. Because the containing 8-byte block (header+8..+15) is reversed in the physical file, the stored hash appears in the .sav at physical 0x1D0..0x1D3 (global) as a big-endian-looking byte sequence (B6 EE 6A 07 in cap-00) whose little-endian RAM value is 0xB6EE6A07. The cold-reload probe in PACKET.md mutated physical 0x1D0 and the save was rejected and rewritten — consistent with this being the first (most significant) byte of the stored hash.
  • Decompiled proof (writers): FUN_0803440c: uVar2 = func_0x08052f20(puVar1, 0x20); *(undefined4 *)(param_1 + 0xc) = uVar2; — FUN_0803447c identical. (Readers): FUN_08033ca0: iVar4 = func_0x08052f20(iVar5, 0x20); if (*(int *)(param_1 + 0xc) == iVar4) { …clamp… }; FUN_08033e98: iVar3 = func_0x08052f20(uVar1, 0x80); if (*(int *)(param_2 + 0xc) != iVar3) *(u32 *)(param_2 + 0x10) = 0xFFFFFFFF;
  • Alternatives excluded by test, not assertion: CRC-32 (zlib.crc32), Jenkins one-at-a-time (JOAAT), FNV-1/1a, MurmurHash2/3, SuperFastHash, and 32-bit word sums over the raw, block-reversed, word-swapped, and bit-reversed payload representations, plus lookup2 with c ∈ {0, 1, 0x9E3779B9, 0xDEADBEEF, 0xFFFFFFFF, …} — none matches either sample. Only the formula above matches both.

5. Complete Field Map Table

Conventions: "Offset" is the logical EEPROM/RAM offset (the address the game passes to FUN_0803e5fc/FUN_0803e6b4). To obtain the physical .sav byte for a logical byte inside an 8-byte block, reverse the block: physical = block_base + 7 - (logical - block_base). Multi-byte fields are little-endian in RAM; in the physical file their bytes consequently appear reversed within each block. "RAM Mirror Addr" is unknown throughout: RAM buffers are referenced only by unresolved literal-pool symbols (e.g. _DAT_08033cf0 global payload, _DAT_08034010 slot-header array, uRam08033f20 shared slot-payload buffer), and the pointed-to 0x02xxxxxx/0x03xxxxxx values are not present in the workspace corpus. Writers/Readers use the function addresses of §3.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this workspace (states/ is empty), so the following are concrete, ready-to-run tests for when a state paired with either .sav is available. General repair procedure for any payload mutation: (1) decode the .sav to the RAM image by reversing every 8-byte block; (2) edit the RAM field; (3) recompute JenkinsLookup2(payload) per §4.2 over the full payload (0x20 global / 0x80 slot); (4) store the result little-endian at RAM header +12; (5) re-encode by reversing every 8-byte block again; (6) boot the paired state / cold-reload. Mutating the raw file without steps (3)–(5) is itself the negative control.
