Clean-Room Save Format Report: Harry Potter and the Order of the Phoenix (USA, Europe) (En,Fr,De,Es,It,Nl,Da)

Release key: BJXE-r0-34391a3e3c7e2956 | Game code: BJXE / header family BJX | Community: comm-006

All findings below are derived exclusively from ghidra/decompiled.c, ghidra/save_related_functions.c, ghidra/callgraph.json, the two .sav binaries in saves/, and standard public GBA hardware specifications (SRAM/Flash 0x0E000000, EEPROM 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). No third-party game-specific documentation was consulted.

1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

What was proven (decompiled C logic is internally consistent AND matches observed .sav byte deltas):

  • The title uses EEPROM 4K (512 bytes), addressed as 64 fixed 8-byte blocks, consistent with the SDK tag EEPROM_V124@16381608 and the Observed Save Media: EEPROM 4K metadata.
  • A single low-level DMA3 bitstream transfer primitive (FUN_0805b570) underlies both an EEPROM block-read primitive (FUN_0805b5f0) and an EEPROM block-write primitive (FUN_0805b6b4), matching the canonical GBA EEPROM serial protocol (2-bit opcode + 6-bit block address + 64-bit data, clocked through the DMA3 backdoor at 0x0D000000).
  • The save-flush entry point (FUN_080177fc, called from FUN_0802933c) writes a 1-byte "dirty" marker (0xFE) to the last EEPROM block (block 63, file offset 0x1FA) before rewriting the whole 512-byte buffer, then flips that byte to a "clean" value (0xAE) in RAM and performs a full write-and-read-back-verify pass over all 64 blocks. This matches the exact byte values observed at offset 0x1FA in saves/cap-01-future-1.sav (ae).
  • Every block write is immediately followed by a read-back + compare (FUN_0805b814), i.e. this title verifies every EEPROM write before considering the save successful.

What remains open / not provable from the available files:

  • The exact algorithm of the 2-byte value written at file offset 0x1FE-0x1FF (candidate "checksum/sequence" field) could not be empirically confirmed. The function that computes it (FUN_0800d1dc) is called with two arguments (0x1fc, a RAM pointer) but Ghidra's recovered body for that address is a trivial 1-argument decrement loop with an explicit /* WARNING: Globals starting with '_' overlap smaller symbols at the same address */ annotation — a strong signal that the true function at this address was not correctly recovered. No simple sum8/sum16/xor8/xor16 formula over any tested byte range reproduced the observed stored value 0x0505 (see §4). Treat as HYPOTHESIS, not verified.
  • The origin of bytes at file offset 0x1F8-0x1F9 (fd a8 in the mutated sample) is UNKNOWN — these are not written by any function reachable from the traced save-flush chain in this workspace; they are presumably ordinary in-RAM save-state fields (e.g. a counter/stat) mutated by gameplay code outside the 97-function trace-guided extraction.
  • Only 2 of the 6 .sav snapshots referenced in the packet's corpus metadata (total_sav_files: 6) are present in this workspace, and only one of those two (cap-01-future-1.sav) contains non-blank bytes. This single non-blank sample is insufficient to statistically confirm a checksum formula; it only lets us confirm that a value is written, not how it is computed.
  • The true caller of the save-trigger wrapper FUN_0802933c (e.g. a menu "Save Game" handler or autosave hook) is not present in the 97-function extraction, so the in-game trigger condition is unproven, only inferred.

Write-ordering / crash-safety pattern (CONFIRMED_STATIC): block 63 (the footer block containing the dirty/clean marker and the candidate checksum) is written to EEPROM twice per save: once early with the dirty marker 0xFE (a standalone FUN_0805b6a0(63, ...) write immediately after setting the marker byte in RAM), and once more as the last iteration of the main 0..63 write loop, by which point the marker byte in RAM has been flipped to 0xAE and the checksum field has been populated. This means a power-loss during the bulk rewrite would leave the on-EEPROM marker at 0xFE ("dirty"/mid-write"), while a completed save leaves it at 0xAE ("clean"). This is a basic torn-write detector, not a two-copy redundancy scheme.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

  • FUN_0805b570 (0x0805b570) — Generic DMA3 block-transfer primitive. Writes param_1→DMA3 source-address register, param_2→DMA3 destination-address register, and param_3 | 0x80000000→DMA3 control register (start bit set), then busy-waits on the controller-busy bit before restoring the saved IRQ-enable/interrupt-mask state it captured on entry. Behaviorally matches the standard GBA DMA3 register triad (DMA3SAD/DMA3DAD/DMA3CNT, MMIO base 0x040000D4) driving a transfer to/from the EEPROM backdoor address 0x0D000000 passed in by its two callers. No callers outside the EEPROM read/write primitives (FUN_0805b5f0, FUN_0805b6b4) were found.
  • FUN_0805b5f0 (0x0805b5f0) — EEPROM block READ primitive. Signature (uint blockIndex, int destBuffer). Packs a 2-bit read opcode + 6-bit block address into a local bit buffer, clocks it out to 0x0D000000 via FUN_0805b570, then performs a second FUN_0805b570 transfer that reads 68 bits back from 0x0D000000 into the same local buffer. Unpacks the trailing 64 bits into 4×16-bit words written into destBuffer[3..0] (descending). Returns non-zero only when the requested block index is out of range.
  • FUN_0805b6b4 (0x0805b6b4) — EEPROM block WRITE primitive. Signature (uint blockIndex, ushort *srcData, char waitFlag). Packs srcData[0..3] (8 bytes) followed by the 6-bit block address and a 2-bit write opcode into a local bit buffer, clocks the whole buffer out to 0x0D000000 in a single FUN_0805b570 transfer, then busy-polls bit 0 of 0x0D000000 (the EEPROM "ready" status bit) in a timing loop bounded by a wraparound counter (0x88 ticks), optionally retrying once if waitFlag is set. Returns a non-zero status via UNRECOVERED_JUMPTABLE dispatch if the poll times out.
  • FUN_0805b6a0 (0x0805b6a0) — thin wrapper: FUN_0805b6b4(blockIndex, buffer, /*waitFlag=*/1). This is the "write block and wait for completion" entry point actually called by the save-flush routine.
  • FUN_0805b814 (0x0805b814) — write-verify (read-back compare). Signature (ushort blockIndex, short *expectedData). Calls FUN_0805b5f0(blockIndex, localStackBuffer) to read the block that was just written, then compares the 4×16-bit words of localStackBuffer against expectedData word-by-word. Returns 0x8000 on any mismatch, else 0.

3.2 Save flush controller (serialization entry point)

FUN_080177fc (0x080177fc) — the save-writer. Traced call chain and RAM mutation, in execution order:

  1. func_0x0805a840() — opaque helper (likely interrupt/IRQ mask save or audio-engine pause); body not in this extraction.
  2. Sets *_DAT_08017868 = 0 (clears a caller-visible status/error flag).
  3. ramBase = _DAT_0801786c (base address of the in-RAM 512-byte save mirror, presumably in EWRAM 0x02xxxxxx or IWRAM 0x03xxxxxx — exact segment not resolvable from symbolic _DAT_ names alone).
  4. *(ramBase + 0x1fa) = 0xFE — dirty marker set in RAM.
  5. func_0x0805b6a0(63, ramBase + 0x1f8) — immediately flushes block 63 (the footer block, still carrying the dirty marker) to EEPROM. This is how a crash mid-save can be detected on next boot.
  6. *(ramBase + 0x1fa) = 0xAE — marker flipped to "clean" in RAM (not yet re-flushed).
  7. checksumOrSeq = FUN_0800d1dc(0x1fc, ramBase) — candidate checksum/sequence computation (unverified, see §4); result stored at *(uint16*)(ramBase + 0x1fe).
  8. Main loop, blockIndex = 0 .. totalBlocks-1 (bound read from a struct field, consistent with 64):

a. func_0x0805b6a0(blockIndex, ramBase + blockIndex*8) — write block. b. On failure: set error flag, call func_0x08033024(errorCode) (UI/sound notification stub, body not in this extraction), return status 1. c. func_0x0805b814(blockIndex, ramBase + blockIndex*8) — read back and verify the just-written block. d. On mismatch: set error flag, call func_0x08033024(errorCode), return status 2.

  1. On full success: func_0x0805d3c0(dst, src, 0x200) — a 512-byte memcpy-style copy (shadow/snapshot buffer, exact purpose unresolved), sets a "save complete" flag, calls func_0x08033024(successCode) (UI notification), returns status 0.

Caller: FUN_0802933c (0x0802933c) — if (FUN_080177fc() != 0) func_0x08002bc0(); i.e. a thin "call the save routine, dispatch to the generic error handler on any non-zero status" wrapper. No caller of FUN_0802933c was found inside the traced 97-function set — the actual in-game trigger (menu "Save" selection, autosave checkpoint, etc.) lies outside this extraction and cannot be proven from available files; it is inferred only from the function's role.

3.3 Boot-time read/validate path

FUN_08017788 (0x08017788) — iterates blockIndex = 0 .. totalBlocks-1, calling func_0x0805b5f0(blockIndex, ramDest) (read primitive) for each block, advancing the destination pointer by 8 bytes per iteration, and checking for a non-zero read-primitive status (out-of-range index) to detect a save region that is smaller/absent/unformatted. On failure, sets a flag and calls func_0x08033024(errorCode). This is the most plausible boot-time "does a valid EEPROM save exist" scan, but its own caller was likewise not present in the extraction.

3.4 Functions in ghidra/save_related_functions.c not otherwise covered

  • FUN_0805b9b0 / FUN_0805bb40 — FUN_0805bb40 is a 32-bit unsigned restoring division/remainder helper used by two callers (0x0805bac8, 0x0805bb40 itself per the callgraph) and falls back to a no-op FUN_0805b9b0() when the divisor is zero. This is a generic arithmetic library routine (division is a hard op with no assembly instruction on ARM7/ARMv4T, and compilers commonly emit it), not save-format-specific; it was pulled in by the MMIO-seed search only because of address proximity, not because it touches 0x0D000000/0x0E000000/DMA3.

4. Magic Signatures & Checksum / Integrity Algorithm

No ASCII magic string or fixed multi-byte signature constant was found anywhere in the traced save path (consistent with the packet's ascii_magic_strings: []). The only "signature-like" byte is the single-byte dirty/clean state marker described above — it is a 2-value state flag, not a format-identifying magic number, so it is reported separately from the checksums block in save-format.json.

Candidate checksum verification attempt

The call site is uVar3 = FUN_0800d1dc(0x1fc, ramBase); *(uint16 *)(ramBase + 0x1fe) = uVar3;, i.e. the function is invoked with what looks like a length (0x1fc = 508) and a data pointer (ramBase, i.e. bytes 0x000-0x1FB of the 512-byte buffer — everything except the marker-adjacent tail and the checksum field itself). However, the decompiled body of FUN_0800d1dc at that address is:

void FUN_0800d1dc(int param_1)
{
  do { param_1 = param_1 + -1; } while (param_1 != 0);
  (*UNRECOVERED_JUMPTABLE)();
}

This is a single-argument busy/delay loop with no second argument and no return value threaded through — inconsistent with being called with two arguments and its result being stored. Ghidra's own annotation at this address (Globals starting with '_' overlap smaller symbols at the same address) indicates a known symbol-overlap problem, meaning this decompiled body is very likely not the function that actually executes at the call site in FUN_080177fc. We treat the "508-byte range → 2-byte result" relationship as plausible (CONFIRMED_STATIC: something is computed and stored there) but the exact algorithm as UNKNOWN, and we could not derive it independently.

To be rigorous, the following Python check was run against the only non-blank sample (saves/cap-01-future-1.sav) to see whether any simple formula over any plausible byte range reproduces the stored value 0x0505:

import sys
data = open("saves/cap-01-future-1.sav", "rb").read()
assert len(data) == 512

def test(rng_end, label):
    chunk = data[0:rng_end]
    s8  = sum(chunk) & 0xff
    s16 = sum(chunk) & 0xffff
    x8  = 0
    for b in chunk: x8 ^= b
    x16 = 0
    for i in range(0, len(chunk) - 1, 2):
        x16 ^= chunk[i] | (chunk[i+1] << 8)
    print(label, "sum8=%02x sum16=%04x xor8=%02x xor16=%04x" % (s8, s16, x8, x16))

for end in [0x1f8, 0x1fa, 0x1fb, 0x1fc, 0x1fd]:
    test(end, f"range[0:{hex(end)}]")

stored = data[0x1fe] | (data[0x1ff] << 8)
print("stored u16 LE @0x1fe =", hex(stored))

Actual output:

range[0:0x1fa] sum8=ad sum16=f7ad xor8=55 xor16=a8fd
range[0:0x1fb] sum8=5b sum16=f85b xor8=fb xor16=a8fd

None of sum8/sum16/xor8/xor16 over any tested range match 0x0505. FUN_0800d1a0 (0x0800d1a0, adjacent in the same source region) implements a genuine table-driven CRC-style engine (table[(crc^byte)&0xff] ^ (crc>>8), the classic reflected-CRC inner loop), but its 256-entry table (_DAT_0800d1d8) lives in ROM data not present in this workspace, so a CRC hypothesis cannot be tested either. **Conclusion: the 0x1FE-0x1FF field is confirmed to be a computed, non-constant value written once per save, but its exact algorithm is UNKNOWN given the files available.** Do not trust any single formula for this field without ROM-table or multi-sample evidence.

No checksum covering the entire 512-byte buffer was found; the EEPROM write-verify-by-readback (FUN_0805b814) performs integrity checking per-block at write time instead of via a stored whole-buffer checksum, which is consistent with the packet's cold-reload probe showing integrity_check_confirmed: false and reverted_to_blank_on_mutation: false — i.e. this title does not appear to validate/reject the save on load based on the candidate checksum field; it plausibly only uses it to validate as part of the write-time cycle. This is itself a hypothesis pending a direct load-path trace (FUN_08017788 does not reference offset 0x1FE at all in the extracted code).

6. Save Fuzzing & Counterfactual Verification Plan

No .ss emulator save states were provided in this workspace (states/ is empty — "legacy checkpoint cohort", per packet). The following mutations should be queued for the next capture round that includes paired .ss states (per standing project policy, every .sav mutation test must be paired with pre/post .ss states):

  1. Marker-byte corruption test (offset 0x1FA, size 1): Starting from a save with marker 0xAE (clean), overwrite with 0xFE (dirty) without touching anything else, then reload. Prediction: if FUN_08017788's boot scan or another unrecovered loader branches on this byte, the game should treat the save as "incomplete"/corrupt (reset to new-game state, show a corrupted-save message, or silently ignore the stale marker — any of these outcomes is informative). No checksum repair needed since this field is not itself checksum-protected by any mechanism found in this trace.
  2. Checksum-field corruption test (offset 0x1FE-0x1FF, size 2): Flip both bytes (e.g. 05 05 → 00 00) while leaving everything else (including the 0xAE marker) intact, then reload. Prediction: if this field is actually load-validated somewhere outside the traced code, the save should be rejected/reset; if (as the write-time-only hypothesis in §4 suggests) it is never checked on load, the save should load identically with no observable difference. This test is the most direct way to falsify or confirm the "write-only, not load-validated" hypothesis.
  3. Payload-region probe (offset 0x000, size 1, then widen): Flip a single byte from 0xFF to 0x00 in the otherwise-blank 0x000-0x1F7 region on a fresh save, reload, and diff the post-load in-RAM mirror at the same symbolic offset (ramBase+0x000) against pre-load. Prediction: since this entire region was 0xFF in both available samples, any observable in-game effect (even "no effect, overwritten back to 0xFF") will be the first real evidence of what lives in this region. Checksum repair is required only if test 2 confirms load-time validation; otherwise no repair is needed since the field (if any) covering this byte is unverified.
  4. Block-boundary write-verify stress test: Using a debugger/trace harness (not a byte edit), force func_0x0805b6a0 to report success while func_0x0805b814's read-back genuinely differs for one block index in the middle of the 0-63 loop (e.g. by corrupting EEPROM externally between the write and the verify read). Prediction: FUN_080177fc should abort with status 2 and invoke func_0x08033024 with the mismatch error code, never reaching the final func_0x0805d3c0/success-flag step — this validates the write-verify caller chain described in §3.2 end-to-end.
  5. Dual-flush ordering probe: Interrupt emulation between step 5 and step 8's final (block-63) write in FUN_080177fc (i.e. between the early dirty-marker flush and the loop's last iteration). Prediction: EEPROM block 63 should read back 0xFE at offset 0x1FA if interrupted before the loop's final iteration, and 0xAE if interrupted after — directly testing the crash-safety ordering claimed in §2.

All fuzzing must preserve the two original .sav files unmodified in saves/; mutated copies should be written to new files, and every mutation test must capture paired pre/post .ss emulator save states per current project retention policy.
