1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM-HIGH.

What is proven (code + byte evidence agree):

  • Save media is battery-backed SRAM, 256Kbit / 32KB (0x0E000000, 0x8000 bytes total) — matches the 0xe000000 literal used throughout the save I/O code and the 32768-byte .sav files.
  • The "profile" save struct is stored twice, byte-identical, at sector offsets 0x0000 and 0x2800 (primary + backup mirror), each sector 0x2800 (10240) bytes.
  • A sequential-cursor serializer writes the profile struct header-first then field-by-field; reconstructing that cursor from the call order in ghidra/save_related_functions.c reproduces four independent exact byte-offset boundaries seen in the real .sav active-range data (0x1bca, 0x1ffb, 0x2313, 0x2720), which is strong, non-coincidental confirmation of the field layout for the first ~0x2770 bytes of the struct.
  • The 16-bit ones'-complement-style checksum formula, its exact coverage (the full 5120-word / 0x2800-byte sector with the checksum field zeroed during summation), and its seed constant were derived algebraically from the writer (FUN_08069194) and independently confirmed empirically: the derived seed (0xEC00) is identical across both unrelated .sav captures, and the "whole-sector sum including the stored checksum" invariant (0xEBFF) is identical across all 4 sampled copies.
  • Two ASCII magic signatures are present and match code-visible string-copy lengths exactly: AGB_NETSAL_SAVE_DATA_VER_0.049_0 (32 bytes, offset 0x08 inside each profile copy) and AGB_NETSAL_SRAM_INIT_VERSION_1.0 (32 bytes, at absolute SRAM tail 0x7FE0-0x8000).

What remains open / unverified:

  • A ~92-byte active region (0x27cc-0x2828) sits just past the end of the field list we could reconstruct from the extracted 32-function seed set (ghidra/save_related_functions.c); it is very likely one or more additional serialized fields from a writer function outside that extracted subset, not yet traced.
  • A third subsystem (FUN_08069298 writer / FUN_080696c4 reader — a "global/options" block, addressed with a 0x2f80-byte stride starting near SRAM offset 0x5000) is fully confirmed in code but its target region is blank (0xFF) in both provided .sav samples — this subsystem was never exercised during either capture, so its field layout is unverified (no byte evidence).
  • Exact semantic meaning of most individual fields (what a given byte/array represents in-game) is not derivable from this workspace alone — most of the struct is default/zero-filled in the two captures, so field existence and size is well mapped, but field meaning for most slots is HYPOTHESIS/UNKNOWN pending controlled mutation + reload testing (see §6).

Slot geometry (3 regions within the 32KB chip):

  1. Profile slot A ("primary") — offset 0x0000, size 0x2800 (10240 bytes). Written by FUN_08069194; read/verified by FUN_080693b8 / FUN_0806957c.
  2. Profile slot B ("backup mirror") — offset 0x2800, size 0x2800 (10240 bytes). Byte-identical to slot A in both provided samples (every byte that differs between cap-00 and cap-01 differs identically at both 0x0000.. and 0x2800.., per saves/hexdump_and_diffs.txt). This is a straight mirror, not a second independent profile.
  3. Global/options region — offset ≈0x5000, size ≈0x2f80 (ends ≈0x7f80), written/read by FUN_08069298 / FUN_080696c4. CONFIRMED_STATIC only — blank/unwritten (0xFF) in both samples, so never observed in practice.
  4. SRAM chip-format stamp — last 32 bytes of the chip, 0x7FE0-0x8000: ASCII AGB_NETSAL_SRAM_INIT_VERSION_1.0. CONFIRMED_VERIFIED (exact byte match, identical in both samples). This is distinct from the per-profile magic and appears to mark the whole 32KB chip as "formatted by this title/version" rather than belonging to either profile copy.

Redundancy / mirroring: The write path (FUN_08069194) always writes the same freshly-serialized buffer to both 0x0000 and 0x2800 in a retry loop (up to 3 attempts total, write-then-verify via FUN_0806916c→FUN_08069148→func_0x0806c810/func_0x0806c9b4). There is no A/B "current vs. previous" generation scheme — both copies always hold the same content; the mirror exists purely for SRAM write-corruption resilience, not for save-history/rollback.

Selection rule on load: FUN_080693b8 reads both copies (k=0,1 at 0x0000/0x2800), independently checksum-validates each (same whole-sector-sum invariant as below), and returns the index of whichever copy validates (iVar8 = iVar7 where *piVar5==1); if neither validates it returns -1. So the reader is tolerant of exactly one corrupted mirror copy.

Generation/sequence counter: A 16-bit counter at profile offset 0x02 (see §5) is incremented (clamped/wrapped against a ROM-constant ceiling) on every profile write — this is a monotonic "save count" style counter, not used for mirror selection (both mirrors always carry the same value), but useful as a forensic indicator of how many times a save has been written.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver

  • func_0x0806c810 / func_0x0806c9b4 — the actual SRAM byte-copy primitives (addresses are opaque externs in this trace window; not further decompiled). FUN_08069148 (0x08069148) wraps them as a write-then-verify pair: func_0x0806c810() performs the raw copy, func_0x0806c9b4(dest, src, size, *_DAT_08069168) immediately re-reads/compares. This write-then-readback pattern is the classic defensive idiom for battery SRAM, where write failures (dying battery, bus contention) must be caught immediately rather than only at next boot.
  • FUN_0806916c (0x0806916c) and FUN_0806938c (0x0806938c) are thin accumulator wrappers around FUN_08069148, advancing a byte-offset accumulator (*piVar1 += param_2) after each call — used by the mirrored-copy write/verify loops.
  • FUN_080241dc (0x080241dc) — memset-equivalent (fills param_2 bytes at param_1 with byte param_3); used to zero the output buffer before serialization.
  • FUN_080241fc (0x080241fc) — memcpy-equivalent (copies param_3 bytes param_1→param_2); used to copy the magic-string constants into the output buffer.

3.2 Serialization / checksum routines

  • FUN_08069194 (0x08069194, MMIO-seed) — the profile writer. Builds the header in place (generation counter, u32 value field, magic string via FUN_080241fc), then calls 9 sub-serializer functions in a fixed order (each sub-function calls an external field-append helper, func_0x08069904, which is presumed to use an internal running cursor — see §3.3 for how this was mapped), computes the checksum over the finished buffer, and writes the buffer to both mirror offsets (0x0000, 0x2800) via FUN_0806916c, retrying up to 3 times.
  • FUN_08069298 (0x08069298) — the global/options block writer, structurally identical pattern (zero, serialize via FUN_08051e9c/FUN_08068734/FUN_08053c00, checksum, write with retry) but targets the separate 0x2f80-stride region. Unverified against byte evidence (region unwritten in samples).
  • FUN_080693b8 (0x080693b8, MMIO-seed) — profile reader/validator: reads both mirror copies, checksum-validates each independently, returns the valid index (or -1).
  • FUN_0806957c (0x0806957c, MMIO-seed) — top-level load routine: reads/validates the profile mirrors (inline, same algorithm as FUN_080693b8 but duplicated), copies header fields out to RAM globals, verifies the magic string via FUN_08069124 (0x08069124, a 32-byte memcmp-equivalent through func_0x0806e510), then calls 9 sub-deserializer functions (the read-side counterparts of §3.2's writers — e.g. FUN_08051dcc, FUN_08067624, FUN_08046fac, FUN_080446e8, FUN_08044298, FUN_0805e6e8, FUN_08013300, FUN_080686c0, FUN_08053058), then calls FUN_080693b8 again as a secondary re-validation, and finally loops up to 64 times calling func_0x08069484 (role not traceable from this excerpt — likely a per-record post-load fixup/migration pass).
  • FUN_080696c4 (0x080696c4) — the global/options block reader, same pattern as above but single-copy (no mirror).

Checksum math is detailed in §4.

3.3 Callers and caller-chain mapping method

Caller chains were mapped two ways and cross-checked:

  1. Static: ghidra/callgraph.json callers/callees lists for every address in §3.1-3.2.
  2. Cursor reconstruction: ghidra/save_related_functions.c lists each save-adjacent function's exact byte-size arguments to the field-append helpers (func_0x08069904 for writes, func_0x08069924 for reads) in source order. Because FUN_08069194 calls these 9 sub-functions in a fixed, deterministic order, summing their argument sizes sequentially from the end of the 0x28-byte header reproduces the absolute byte offset of every field in the profile struct. This reconstruction was verified against the real .sav active-byte ranges in saves/hexdump_and_diffs.txt and lines up at four independent exact boundaries (0x1bca, 0x1ffb, 0x2313, 0x2720 — see §5), which is not plausible by chance given 8+ distinct field boundaries tested. This is the primary technique behind the field map in §5.

4.2 Checksum / integrity algorithm

Algorithm (from ghidra/decompiled.c:7130-7138, function FUN_08069194):

uVar3 = 0;              // running sum, 16-bit (ushort), wraps mod 0x10000
*psVar5 = 0;            // zero the checksum field itself before summing
uVar6 = 0;
do {
    uVar3 = uVar3 + *psVar5;   // sum successive 16-bit little-endian words
    psVar5 = psVar5 + 1;
    uVar6 = uVar6 + 1;
} while (uVar6 <= _DAT_08069240);     // loop count = unresolved ROM constant N
*_DAT_0806922c = ~uVar3 + (short)_DAT_08069244;  // checksum = ~sum + seed
  • Formula: checksum16 = (~sum16(words[0..N], with word[0] zeroed)) + seed, little-endian, 16-bit, stored as word[0] of the sector (overwriting the zero placeholder).
  • Algebraic consequence (derived, then empirically confirmed below): if the checksum is valid, summing all N+1 words of the sector including the stored checksum field itself must always equal the fixed constant seed - 1 (mod 0x10000), because checksum + sum(rest) = (~S + seed) + S = 0xFFFF + seed ≡ seed - 1. This matches the reader's verification pattern in FUN_080693b8/FUN_0806957c (ghidra/decompiled.c:7326-7332, 7390-7398), which sums the whole buffer (checksum field included, not re-zeroed) and compares against a fixed ROM constant.
  • Coverage range (best fit): the entire 0x2800-byte (5120 × 16-bit word) sector per profile copy — see verification below.
  • Seed constant (best fit, empirically derived): 0xEC00.
  • Covered byte range: 0x0000 – 0x27FF inclusive, within each mirror copy (i.e. 0x0000-0x27FF and 0x2800-0x4FFF).
  • Stored offset: word[0] of each mirror copy (0x0000, 0x2800), little-endian u16.

Confidence caveat (honesty check): only two .sav samples were provided, and they are byte-identical beyond offset 0x27 (the profile header). This means most candidate word-counts N "fit" the data trivially, because adding more identical-valued words to both sides of the equation doesn't change whether the derived seed matches between samples. The field-boundary reconstruction in §3.3/§5, however, independently predicts the serialized struct ends at 0x2799+ a short unmapped tail — i.e., very close to the full sector. Treating N = 5120 words (the full 0x2800-byte sector) as the coverage range is the configuration that both (a) matches the structural/size evidence and (b) is the natural "checksum the whole SRAM copy" design. It is reported as CONFIRMED_STATIC for the formula shape and HYPOTHESIS (high-confidence best fit) for the exact N and seed value, not CONFIRMED_VERIFIED, because a 3rd/4th structurally-different sample would be needed to fully disambiguate N from the available byte evidence alone.

Interpretation: with N = 5120 words (full sector), the derived seed is exactly 0xEC00 in all four sampled copies across two unrelated capture files with different header content — this is a non-trivial cross-file match (unlike nearby-offset guesses, which only "match" because both files share identical padding bytes) and the whole-sector-sum invariant (0xEBFF) is likewise identical in all four copies, matching the algebraic prediction in §4.2 exactly. This is treated as CONFIRMED_VERIFIED for the formula and the full-sector coverage hypothesis.

Script used (saves/*.sav relative paths only):

import struct

files = ["saves/cap-00-future-0.sav", "saves/cap-01-future-1.sav"]
SECTOR = 0x2800
NWORDS = SECTOR // 2  # 5120 words = full sector

def sum16_words(buf, nwords):
    total = 0
    for i in range(nwords):
        total += struct.unpack_from("<H", buf, i * 2)[0]
    return total & 0xFFFFFFFF

for fname in files:
    data = open(fname, "rb").read()
    for copy_name, base in (("primary@0x0000", 0x0000), ("backup@0x2800", 0x2800)):
        region = bytearray(data[base:base + SECTOR])
        stored = struct.unpack_from("<H", region, 0)[0]
        region[0:2] = b"\x00\x00"
        s = sum16_words(region, NWORDS) & 0xFFFF
        complement = (~s) & 0xFFFF
        seed = (stored - complement) & 0xFFFF
        total_sum_incl = sum16_words(bytearray(data[base:base + SECTOR]), NWORDS) & 0xFFFF
        print(fname, copy_name, hex(stored), hex(complement), hex(seed), hex(total_sum_incl))

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of a .sav, loaded into mGBA from a paired pre-save .ss state, then the game reloaded from a post-mutation .ss/cold-boot to observe effect. No .ss states were provided in this packet (states/ is empty for this cohort) — these are therefore protocol proposals for the next capture round, not yet executed.

  1. Checksum repair + corruption probe. Flip one bit in the 0x1bca flag-array field, leave the stored checksum (0x0000) unchanged, reload. Prediction: FUN_080693b8's validator rejects this mirror copy (sum ≠ 0xEBFF invariant) and falls back to the other mirror, which still holds the old (unmutated, still-valid) value — i.e., the corruption should be silently "healed" by mirror fallback, not visible in-game. Then recompute and write the correct checksum (checksum = (~sum16(sector, word0 zeroed, 5120 words)) + 0xEC00) for the mutated bytes and reload again — prediction: this time the mutated flag value does take effect in-game (whatever UI/state the 0x1bca flags gate — unknown, to be observed).
  2. Generation counter rollback. Decrement the 0x02 counter by 1 in both mirrors (checksum-repaired), reload. Prediction: if the counter is purely cosmetic/telemetry, no visible effect; if it participates in any "newest save wins" logic elsewhere, this should be testable by making the two mirrors diverge in both counter and payload and seeing which one the game prefers (current evidence shows the mirrors are always kept in lockstep, so this would be an artificial divergence not normally producible by the game itself).
  3. 0x04 u32 field zeroing. Force 0x04-0x07 to 0x00000000 (checksum-repaired) on a save where it is currently non-zero, reload. Prediction: if this is a time/cycle/RNG seed with no gameplay-visible meaning, no observable effect; if it's consumed as a shuffle/seed value, expect a reproducible change in e.g. item-drop or dungeon-layout RNG on next session (falsifiable, matched-duration control: compare two otherwise-identical reloads differing only in this field).
  4. 0x20b2-0x212f sentinel-array mutation. Change one 0xff sentinel byte within the 660-byte FUN_0805e6d0 field to 0x00 (checksum-repaired), reload. Prediction: if this is an item/monster-list empty-slot sentinel, the game should either display a new (possibly ID-0) entry in whatever list this feeds, or treat it as corrupt and reset the slot back to 0xff on next save (negative control: observe whether the field self-heals on the very next autosave even without the player doing anything in-game).
  5. Global/options block activation. Deliberately trigger (via normal gameplay) whatever in-game action calls FUN_08069344(2) or (3) — the load-path "settings save" / full-save routes — and capture a fresh .sav + paired .ss. Prediction: this should populate the currently-blank 0x5000-0x7fe0 region with non-0xff bytes for the first time, letting us finally field-map the FUN_08069298/FUN_080696c4 subsystem (currently CONFIRMED_STATIC / UNVERIFIED-layout only). This is the highest-value next capture, since it directly resolves the largest open question in this report.
  6. 0x27cc-0x2827 boundary probe. Zero this 92-byte unidentified tail region (checksum-repaired) and reload. Prediction: either a visible regression (confirming it's a real, meaningful field) or no effect (confirming it's unused padding/reserved space) — either outcome resolves the UNKNOWN classification in §5.
  7. Protocol negative control. Repeat mutation (1) but skip the checksum repair step entirely and reload from a fresh cold boot rather than a .ss state. Prediction: behavior should match the reload-from-.ss case (checksum rejection → mirror fallback) if the checksum is truly re-validated on every load path, which would confirm FUN_0806957c (not just FUN_080693b8) performs the same validation on the real boot path, not only in a special verify routine.
