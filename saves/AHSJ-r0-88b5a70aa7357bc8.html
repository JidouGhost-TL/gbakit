Clean-room derivation only: workspace .sav bytes, ghidra/decompiled.c (372 functions), ghidra/save_related_functions.c, ghidra/callgraph.json, and standard GBA hardware addresses. No third-party game-specific source was used.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM

Proven by both code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is 32 KiB SRAM. The only explicit save-bus address in the decompilation is

0x0E000000 (SRAM base) in FUN_08041208. No Flash 0x5555/0x2AAA command sequence, no EEPROM 0x0D000000, and no DMA3 (0x040000D4) save path appears anywhere in ghidra/decompiled.c (negative grep over all 13,606 lines).

  • One integrity algorithm, used by every checksummed structure in the game:

FUN_0800a890 = 16-bit byte-sum XOR 0xFF (see §4).

  • Two complete on-disk blocks verify exactly against both .sav files with that formula:

the 12-byte hC02 block at file offset 0x7DBC (covered 0x0A, stored at 0x7DC6) and the 220-byte lg02 block at 0x7EA0 (covered 0xDA, stored at 0x7F7A). A full-file scan for this relation finds no other non-overlapping hits.

  • The only two bytes that differ between cap-00-future-0.sav and cap-01-future-1.sav

are 0x7DC4 (0x01 -> 0x81, the 5th payload byte of hC02) and 0x7DC6 (0xF1 -> 0x71, its checksum low byte). Payload and checksum move together exactly as FUN_0800a890 predicts. This is also the probe offset 0x7DC4 in PACKET.md §1, whose cold-reload probe reported integrity_check_confirmed: true, reverted_to_blank_on_mutation: true — consistent with the erase-on-fail path in §3.

Static-only (CONFIRMED_STATIC — in code, but the literal that would pin it to a file offset is an unrecovered _DAT_08041xxx literal-pool value and no .sav checksum can confirm it):

  • FUN_08041208 checks seven headered regions at boot, including an explicit 4-byte header

check at SRAM base 0x0E000000 (= file offset 0x0000), four further magic-only regions, one region initialised via FUN_080413f8, and one large region with a checksum field at +0x6F0. Exactly six 4-byte magics besides lg02 exist in the saves (hE01, hP03, hS02 x2, hM02, eM02), matching those six non-lg02 regions in count.

  • FUN_0804390c / FUN_08043964 validate 48-byte (0x30) records with a 2-byte magic and

a checksum at +0x2E, read in caller-supplied index order. No such record validates in either save, so their SRAM base cannot be located from the saves.

Hypotheses / unknowns (HYPOTHESIS / UNKNOWN):

  • Which of hP03/hS02/hM02/eM02/hS02 corresponds to which FUN_08041208 region (and hence

each region's exact length), the large +0x6F0-checksum region's file offset, the SRAM bases of the 0x30-byte records, all in-RAM mirror addresses (_DAT_*/puRam* pointer values are not recovered in the decompilation), the writers of the magic-only blocks, and the functions 0x08043718 / 0x08043808 (called, not present in the decompilation).

  • There are no save "slots" in the usual sense, no backup copy, and no generation counter

anywhere in the traced code (§2). Do not assume redundancy that is not there.

3. Save Writer, Reader & Caller-Chain Architecture

Mapping method (read this before trusting any caller claim)

  • ghidra/callgraph.json (372 nodes) records only direct FUN_→FUN_ edges. Many save

calls in ghidra/decompiled.c are written func_0x0804xxxx(...) (unrecovered jumptable aliases), so the callgraph lists e.g. FUN_08041208, FUN_08041444, FUN_080415a0 with callers: [] even where the text calls them. Every caller claim below was therefore made by (a) textual grep for both FUN_080xxxxx and func_0x080xxxxx spellings in ghidra/decompiled.c, and (b) cross-checking the callgraph edge where one exists. Disagreements are noted explicitly.

  • _DAT_08041xxx / puRam* symbols are literal-pool / pointer globals whose values the

decompilation does not recover. So a function's SRAM/RAM addresses can only be pinned to a file offset when a .sav checksum uniquely confirms it (§4 scan), or when the address is an explicit constant (0x0E000000).

  • SRAM file offset = SRAM address − 0x0E000000. The .sav is a raw SRAM dump.

Boot / validation orchestrator — FUN_08041208 (called from FUN_0800358c)

Caller mapping: textual func_0x08041208() at FUN_0800358c; callgraph lists no callers (jumptable alias). FUN_0800358c itself runs FUN_08000268() (which runs FUN_08002eec, the hC02 validator), then func_0x08036a24(), then FUN_08041208.

FUN_08041208 performs, in order (RAM buffer = _DAT_0804138c throughout; all SRAM source addresses are _DAT_08041388.._DAT_080413c8 literals, unrecovered except as noted):

  1. Large checksummed region — read len=_DAT_08041398 from SRAM _DAT_08041388 into RAM.

Saved checksum = *(s16*)(RAM+0x6F0); zero it; require magic (_DAT_0804139c, 4 B, FUN_0800a8c0) and FUN_0800a890(RAM, _DAT_080413a0) == saved. On any failure: zero-fill the whole SRAM region (FUN_080415b0(SRAM, len)) and rewrite only the 4-byte magic. Note: it does not recompute/write a checksum, so a region erased here will fail its checksum again next boot until some other writer (not traced) populates it.

  1. Magic-only region B — read 4 B from _DAT_08041390; if magic (_DAT_080413a4) differs:

FUN_080415b0(region, _DAT_080413a8), rewrite magic.

  1. Magic-only region C — read 4 B from _DAT_08041394; if magic (_DAT_080413ac) differs:

FUN_080415b0(region, 0xD8), rewrite magic. (Region size 216 B is the only explicit magic-only size beside step 6/FUN_080413f8.)

  1. Magic-only region D — read 4 B from _DAT_080413b0; if magic (_DAT_080413b4) differs:

FUN_080415b0(region, _DAT_080413b8), rewrite magic.

  1. SRAM-base region E — read 4 B from the explicit constant 0x0E000000

(file offset 0x0000, magic hE01 in the saves); if magic (_DAT_080413bc) differs: FUN_080415b0(0x0E000000, _DAT_080413c0), rewrite magic at offset 0.

  1. Region F — read 4 B from _DAT_080413c4; if it differs from _DAT_080413ac (the same

magic variable as region C — code reuses uVar2), call FUN_080413f8.

  1. lg02 region G (re-validated in RAM) — read 0xDC bytes from _DAT_080413c8 into the

same RAM buffer; saved checksum = *(s16*)(RAM+0xDA), zeroed before recompute over 0xDA bytes; require magic (_DAT_080413cc) and checksum. On failure call FUN_08041444 to rebuild and rewrite the whole 0xDC block.

How it mutates the in-RAM struct before flushing: it doesn't build gameplay data. Steps 1–6 only erase + stamp a 4-byte magic; step 7 delegates construction to FUN_08041444. The RAM buffer at _DAT_0804138c is a scratch validation buffer, reused for both the large region (step 1, checksum at +0x6F0) and the lg02 region (step 7, checksum at +0xDA) — the two must not be conflated; they are different SRAM regions loaded into the same buffer.

FUN_080413f8 — region-F initialiser (called only from FUN_08041208 step 6)

Zero-fill 0xD8 bytes at _DAT_08041438, write its 4-byte magic (_DAT_0804143c), then loop a RAM byte counter *_DAT_08041440 from 0 to 3: call func_0x08043690() and, if it returns non-zero, func_0x08043808(). Neither 0x08043718 (called inside FUN_08043690) nor 0x08043808 is present in ghidra/decompiled.c, so what they write for each of the 4 iterations is UNKNOWN — the loop count (4) matches the "for each of up to 4 entries" pattern of FUN_0804097c/FUN_080409f0 in §3 (0x30-record users), so FUN_08043808 is hypothesised to be the missing 0x30-record writer/serialiser (see open questions).

FUN_08041444 — lg02 builder/writer (called only from FUN_08041208 step 7)

  1. Zero the 0xDC-byte RAM block (FUN_0800320c(RAM, 0, 0xDC)), copy the 4-byte magic from

_DAT_080414a8 to RAM+0.

  1. Read a large SRAM region into a second RAM buffer:

FUN_08041620(_DAT_080414ac, _DAT_080414a0, _DAT_080414b0) (source address/length are unrecovered literals).

  1. Gather: for i in 0..0xD4 (213 iterations),

RAM[4+i] = srcRAM[4 + i*0x14 + 0xE] — i.e. byte +0x12 of each successive 20-byte (0x14) record, strided by 0x14. This is a compaction of one flag/status byte per 20-byte record into the lg02 payload. In both saves every gathered byte is 0x00, so the source records are all in their empty state; which SRAM region they live in cannot be identified from the saves.

  1. *(u16*)(RAM+0xDA) = FUN_0800a890(RAM, 0xDA); write all 0xDC bytes to SRAM

_DAT_080414b4 via FUN_080415a0. File offset 0x7EA0 for this destination is

inferred verified: it is the only offset in either save where a 0xDC/0xDA magic+checksum structure validates (§4).

FUN_08002eec / FUN_08002e84 — hC02 12-byte block (boot, from FUN_08000268)

  • FUN_08002eec (reader/validator): FUN_08041620(stack, _DAT_08002f4c, 0xC); saved checksum

= stack s16 at +0x0A, zeroed; require magic (_DAT_08002f50, 4 B) and FUN_0800a890(stack, 10). On failure: set five RAM globals to 0,0,0,0,1 (*_DAT_08002f8c/_f90/_f94/_f98 = 0, *_DAT_08002f9c = 1) and call FUN_08002e84. On success: copy the 5 payload bytes (stack +4..+8) into five 1-byte RAM globals (*puRam08002f54, _f58, _f5c, _f60, _f64 — pointer values unrecovered, so the RAM mirror addresses are UNKNOWN).

  • FUN_08002e84 (writer): build the 12 bytes on the stack — magic from _DAT_08002ed0 (4 B),

then the same five RAM bytes (*_DAT_08002ed4/_ed8/_edc/_ee0/_ee4), checksum FUN_0800a890(buf, 10) stored at +0x0A — and write 12 bytes to SRAM _DAT_08002ee8 via FUN_080415a0. SRAM address inferred verified as file offset 0x7DBC (§4).

  • Caller chain: FUN_0800358c -> FUN_08000268 -> FUN_08002eec -> (on failure) FUN_08002e84.

This runs before FUN_08041208. Note FUN_08002e84 is the only traced writer that flushes live RAM values into a checksummed .sav block; the mutation at 0x7DC4 is the 5th of those bytes (stack +8).

0x30-byte record validators — FUN_0804390c, FUN_08043964, FUN_08043c78

  • FUN_0804390c(buf, idx): FUN_08041620(buf, idx*0x30 + _DAT_0804395c, 0x30); saved checksum

  • FUN_08043964(buf, idx): identical, with base _DAT_080439b4 and magic _DAT_080439b8.

Two distinct SRAM bases for the same record format — two arrays, or one array read through two contexts; UNKNOWN.

  • FUN_08043c78(idx): wraps FUN_08043964 on buffer _DAT_08043ca0; additionally requires

*(u16*)(buf+2) < 4 for a non-zero result... (it zeroes the result when the word at +2 is >= 4). Callers (textual): FUN_0804097c and FUN_080409f0.

  • Caller chains into gameplay-side checks (callgraph + textual):

FUN_08043470 -> FUN_0804097c (returns first-valid-index scan over idx 0..3), FUN_08043470 -> FUN_080409f0 (counts valid records over idx 0..3, returns count > 2), FUN_08043470 -> FUN_08040bb8 -> FUN_08040d1c(n) -> FUN_08040d74(i). FUN_08043690 -> FUN_0804390c(buf=_DAT_080436b4, idx=*_DAT_080436b8) and, on success, func_0x08043718(buf) (not decompiled). FUN_080413f8 loops FUN_08043690 4 times.

  • No writer for these records is in the decompilation (candidates: 0x08043718,

0x08043808). In both saves no 0x30 record validates (full scan, §4), consistent with all records being zero/empty (an all-zero record gives computed 0x00FF vs stored 0).

Other traced save-adjacent functions (explicitly not .sav writers)

  • FUN_08040d74(idx): sets a RAM index byte (*_DAT_08040da4 = idx), calls

func_0x0804bbe0(), then reads 2 bytes from SRAM at *(byte*)_DAT_08040da8 + _DAT_08040dac and returns byte0 & 1. This is a 1-bit flag read from a dynamically-indexed SRAM location. Its base/stride literals are unrecovered, so it cannot be placed in the file; it proves at least one more SRAM-resident flag array exists beyond the headered regions.

  • FUN_0803d2a4: computes FUN_0800a890 over a RAM structure (_DAT_0803d2e4, lengths

0x18E and 0x19A) and stores two 1-byte results into that same RAM structure. Caller: FUN_08036a40 (textual func_0x0803d2a4()), after it writes a batch of default values to RAM globals. This is an internal RAM-struct integrity/default-init routine; no SRAM call occurs in it. Do not map it to a .sav offset.

4. Magic Signatures & Checksum / Integrity Algorithm

Algorithm (exact)

// FUN_0800a890(byte *p, int len)  -- ghidra/decompiled.c:4646
ushort acc = 0;
while (len-- != -1) { acc = (ushort)(acc + *p++); }   // sum modulo 65536
return acc ^ 0xff;                                     // XOR low byte only
  • Name for the JSON schema: sum16_le-family, recorded as custom with the formula below,

because the XOR is with 0x00FF (not 0xFFFF): result = (sum(bytes) & 0xFFFF) ^ 0xFF.

  • Stored as a little-endian u16 at covered_start + covered_len; the stored field is

zeroed before recomputation at every call site (FUN_08041208 steps 1/7, FUN_08002eec, FUN_0804390c/64), so the covered range is exactly [start, start+len).

  • Magic compare is FUN_0800a8c0(p, rom_magic, 4) (2 for 0x30 records). The ROM magic

literals themselves (_DAT_0804139c etc.) are not recovered as bytes in the decompilation; the ASCII values below are read from the .sav files. Linking a specific literal to a specific ASCII string is therefore code+save inference, flagged per-field in §5.

Python verification against the real saves (executed in this workspace)

import struct, pathlib, hashlib
def cksum(b): return (sum(b) & 0xffff) ^ 0xff   # FUN_0800a890
for p in sorted(pathlib.Path("saves").glob("*.sav")):
    d = p.read_bytes()
    print(p.name, len(d), hashlib.sha256(d).hexdigest()[:16])
    for name, st, cov in [("hC02-block",0x7DBC,10),("lg02-block",0x7EA0,0xDA)]:
        stored = struct.unpack_from("<H", d, st+cov)[0]
        print(name, hex(st), hex(cov), "stored", hex(stored),

In particular there is

no valid +0x6F0-checksum block and no valid standalone 0x30-record anywhere in either save — those structures are currently blank/empty or off-SRAM, and their offsets remain open (§1, §6).

Why the cap-to-cap diff is a checksum proof, not a coincidence

0x7DC4 is hC02+8, the 5th payload byte. Changing it 0x01 -> 0x81 raises the byte sum by 0x80; the stored value changes 0x01F1 -> 0x0171, i.e. exactly ((sum+0x80) & 0xFFFF) ^ 0xFF on the low byte (0xF1 -> 0x71, high byte 0x01 unchanged because the XOR touches only the low byte and no carry crosses bit 8). Both files satisfy the formula with their own byte. A random 2-byte co-change would not do this.

6. Save Fuzzing & Counterfactual Verification Plan

General rules for every test: work on a copy of cap-00-future-0.sav; change only the listed bytes; where "checksum repair" is required, recompute stored_u16le = (sum(covered_bytes) & 0xFFFF) ^ 0xFF with the stored field treated as its existing bytes inside the covered range excluded (covered range ends at the stored field), exactly as in §4; reload and observe (a) whether the file is rewritten/reverted on boot — compare the .sav on disk after boot, byte for byte — and (b) the RAM-side effect if a debugger/watchpoint on the listed reader is available. There are no paired .ss states in this workspace (states/ is empty), so predictions are stated as boot/file effects; a reverted file is itself the observable. Predictions marked "by code" follow the traced functions; anything beyond that is labelled a hypothesis.

Checksum-repair recipe (for tests 3, 4, 7, 8, 12), verified against both saves in §4:

import struct
def repair(d: bytearray, start: int, covered: int):
    stored_at = start + covered
    d[stored_at:stored_at+2] = struct.pack("<H", (sum(d[start:start+covered]) & 0xFFFF) ^ 0xFF)
# hC02: repair(d, 0x7DBC, 10)   lg02: repair(d, 0x7EA0, 0xDA)
