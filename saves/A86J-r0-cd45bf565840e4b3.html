1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM (on-disk layout: HIGH; field semantics and RAM addressing: LOW–MEDIUM).

Proven by both decompiled code and .sav bytes (CONFIRMED_VERIFIED):

  • Media is Flash 512Kbit (64 KiB), SDK tag FLASH512_V131, fill/erased byte 0xFF.
  • The save image is a ring of 10 rotating 4 KiB (0x1000) sectors at file offsets

0x0000, 0x1000, …, 0x9000; the remaining 0xA000–0xFFFF is never used by this format.

  • Every sector starts with the 8-byte ASCII magic SONIC_PB and a **64-bit

little-endian sequence counter** at +0x08. The loader picks the valid sector with the largest sequence; the writer writes sector (sequence − 1) mod 10. This is directly observed: cap-00 contains only sector 0 (seq 1); cap-01 adds sector 1 (seq 2), byte-identical except byte 0x08.

  • The only integrity check is a 16-bit byte-sum of the first 4 bytes only

('S'+'O'+'N'+'I' = 0x0139), stored big-endian at sector offset 0xFFE. It matches on all 3 valid copies in the corpus; a full-block sum does not match. This is a near-constant magic-derived check word, not a payload CRC: sequence, configuration and all high-score bytes are outside its coverage.

  • Default/factory contents (magic, seq = 1, field 0x14 = 100, seven config

u16s, three byte arrays, u16s at 0xCC/0xCE/0xD0, and four factory high-score tables of 20 entries each: scores 1 000 000 000 down to 50 000 000 in steps of 50 000 000 with 3-letter names) are fully reconstructed from FUN_080494cc/FUN_08030e8c and match the samples byte for byte.

Static-only (CONFIRMED_STATIC): the writer/reader call chains, the pending-update flag at +0x11, the deferred save in FUN_08049d50, and the RAM-mirror staging performed by the loader.

Open / unknown: the exact RAM mirror address of the save struct (Ghidra emits unresolved _DAT_08049xxx pointer constants, so no 0x02xxxxxx/0x03xxxxxx address is honestly assignable — every ram_addr in save-format.json is therefore null); the meanings of most header fields; the exact opcodes behind two RAM-driver thunks; whether ring sectors 2–9 are populated in longer play (only sectors 0–1 observed).

There is no separate backup/global-config slot: all 10 sectors are identical-format generations of the same 0x1000 struct. The PACKET profile's "active range 0x0–0x1FFF" is simply sectors 0–1 of this ring in cap-01.

One caveat on the selection rule: the loader's max-sequence comparison is (seq_high != 0) || (best_low < seq_low), which can mishandle high-word/wrap cases. This is noted as an open question and a fuzzing target (Section 6).

3.3 ALL traced caller chains

How callers were mapped. Direct func_0x…/FUN_… call sites in ghidra/decompiled.c were extracted and cross-checked against ghidra/callgraph.json (129 nodes). Where Ghidra ends a function with an UNRECOVERED_JUMPTABLE indirect jump, the callee is reported as static/hypothesis rather than verified. RAM-struct mutations are read from the assignment statements in each caller's body; file offsets equal struct offsets because the whole 0x1000 struct is flushed verbatim.

  1. Boot → Load. FUN_08006ef4 (boot/init main) calls FUN_08048dd0 at

decompiled.c line 2477, after early hardware init. FUN_08048dd0 first calls FUN_08048d98, which zeroes the RAM save buffer and identifies the chip (FUN_08060424 → FUN_0805ff48).

  1. Load scan. FUN_08048dd0 calls `FUN_0806019c(sector, 0, ram_buf,

0x1000) for sectors 0–9. Per sector it compares the first 8 bytes against SONIC_PB, then requires FUN_0804971c() to equal the big-endian word at +0xFFE. Valid sectors compete on the 64-bit sequence at +0x08`; the winner is re-read into the RAM struct.

  1. Load staging (how the loader mutates RAM). `(global) = (struct +

0x14); byte-copies +0x30..0x35 (6 B), +0x36..0x39 (4 B) and +0x3A..0x49 (16 B) to three RAM arrays; stages the four score tables from struct +0x22C to the RAM working table +0x1E0 via FUN_0805feb8 (20 entries × 4 tables); copies u16 +0xCC → RAM +0x80, +0xCE → RAM +0x82, and one further u16 (hypothesised +0xD2) → RAM +0x6E0; calls FUN_0803a09c (config mirror) and finally FUN_08049d50` (flush any pending update).

  1. No valid sector → factory init. FUN_08048dd0 calls

FUN_080492e8, which prepares sectors 0–9, builds the default struct with FUN_080494cc, and writes sector 0. (Also reached directly when flash identification in FUN_08048d98 fails, after a FUN_080494cc build in RAM only.)

  1. Explicit save. FUN_080498f4 (jumptable entry, no static caller)

mirrors RAM +0x6E0 → +0x72C and, if its global flag is set, calls FUN_08049644 (SaveGame).

  1. Deferred save. FUN_08049d50 — called from LoadSave and as a

standalone jumptable entry — is the only caller besides 0x080498f4 of SaveGame: it writes a freshly computed value (FUN_0805dbdc(), semantics untraced) into struct +0x14, clears the pending flag +0x11, and flushes.

No other function in the 129-function decompilation writes the save struct: a search for the struct-relative offsets 0x22C/0x1E0/0x6E0/ 0x72C across ghidra/decompiled.c returns only the functions above.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic

SONIC_PB (hex 53 4F 4E 49 43 5F 50 42) at sector offset 0x00, written by FUN_080494cc (8-byte copy into struct +0) and compared byte-by-byte (first 8 bytes) by FUN_08048dd0 for every candidate sector. verified_in_code = true, verified_in_sav = true (present in all three valid copies; the PACKET profile's 9SONIC_PB string is this magic preceded by the preceding byte in ROM, not a file signature).

4.2 Checksum — exact algorithm

Decompiled proof, FUN_0804971c (decompiled.c lines 3616–3632):

short FUN_0804971c(void) {
  byte *pbVar3 = (byte *)*_DAT_0804973c;   // save-struct base
  short sVar1 = 0; ushort uVar2 = 0;
  do { sVar1 = sVar1 + (ushort)*pbVar3; pbVar3 = pbVar3 + 1; uVar2 = uVar2 + 1; }
  while (uVar2 < 4);
  return sVar1;
}
  • Formula: s = (b[0] + b[1] + b[2] + b[3]) & 0xFFFF — a plain byte

sum over covered range [0x000, 0x004) only, no seed, no complement, no XOR/CRC.

  • Storage: big-endian split by both writers — FUN_080494cc and

FUN_08049644 store (s >> 8) at one _DAT-relative offset and (s & 0xFF) at the next; the only location in the samples matching that hi/lo pattern is sector offset 0xFFE (hi) / 0xFFF (lo). The loader reconstructs it as CONCAT11(byte@0xFFE, byte@0xFFF).

  • Because b[0..3] is the constant SONI, the stored value is the

constant 0x0139 (0x53+0x4F+0x4E+0x49 = 313) for every valid save this game can produce. It is a magic-derived check word, not an integrity check over the payload.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist in this corpus (states/ is empty), so every test below is a .sav-only reload test: mutate a copy of cap-01-future-1.sav (which has two valid generations), boot the ROM with it, and observe (a) which generation's data the game presents, (b) whether a new sector appears in the .sav after boot/save, and (c) score/config screens. Checksum repair rule (only needed for mutations inside [0x000,0x004)): recompute s = sum(b[0:4]) & 0xFFFF, write s>>8 at sector+0xFFE and s&0xFF at sector+0xFFF. All other mutations below are predicted to need no repair — that prediction is itself the sharpest test of the Section 4 coverage conclusion.
