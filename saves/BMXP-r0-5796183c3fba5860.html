Clean-Room Save Format Report — Metroid: Zero Mission (Europe, Beta) [BMXP-r0-5796183c3fba5860]

All findings below are derived exclusively from this workspace: the two real .sav binaries in saves/, the trace-guided Ghidra decompilation in ghidra/decompiled.c (339 functions), ghidra/callgraph.json, and ghidra/save_related_functions.c, cross-checked against standard public GBA hardware facts (SRAM @ 0x0E000000, EEPROM @ 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What was proven (code + byte-level verification):

  • Save medium is SRAM, 32,768 bytes (0x8000), accessed via byte-copy MMIO at 0x0E000000.
  • There is a 64-byte "global header" record, present in **two byte-identical mirrored

copies** in both .sav samples (offset 0x0000 and offset 0x6D40).

  • The header's checksum algorithm is fully reverse-engineered and verified: a 32-bit additive

sum over the record's 16 u32 words (with the checksum word itself zeroed and the complement word forced to 0xFFFFFFFF during the sum), stored in word 0, with word 1 holding the bitwise one's-complement of word 0. Python verification against both real .sav files shows an

exact match in all four observed instances (primary+mirror × 2 files).

  • The low-level write path is a classic "write, re-read, compare, retry up to 3×" SRAM

flush routine (FUN_0800546c write / FUN_080054dc verify / FUN_08005540 retry-driver).

  • Code proves a redundant per-record voting/repair scheme (3 header-slot candidates checked

by FUN_08075c7c, reconciled by FUN_08075b28) and a separate, larger 3-slot game-save system (FUN_08076b48/FUN_08076d18/FUN_08076dc8) using 0x1220-byte (4,640-byte) per-slot records with their own A/B-copy voting state machine.

What remains open / unverified:

  • Neither .sav sample contains any populated 0x1220-byte game-save slot — both files are

effectively still near-boot/blank saves, so the game-save-slot layout is code-confirmed but byte-unconfirmed.

  • A 34-byte ASCII block (SELECTSAVENUM_00 / ENDDATA_SEL_SAVE) at 0x6D80-0x6DA6 and a

16-byte ZEROSAVE footer tag at 0x7F70-0x7F7F appear only in the second capture and changed together in one write event, but no writer function for either region was found among the 339 decompiled functions available in this workspace. Their leading numeric fields (0x6D80: 1e 00 d6 9e 29 61; 0x7F78: c0 42 00 00 02 08 f2 3b) were tested against sum8/ sum16/sum32/xor8/xor32/CRC32 (standard and inverted) over every plausible byte range in the file — no algorithmic match was found, so these are reported as UNKNOWN raw observations, not verified checksums.

  • Only 2 of the reportedly 6 captured .sav snapshots (per PACKET.md corpus metadata) were

provided to this workspace; slot-selection/rotation behavior across more saves is unverified.

  • The third header "slot" referenced by FUN_08075c7c(param_1==2) was not located at a distinct

SRAM offset in either sample — it may be RAM-resident only, or at an SRAM offset never exercised by these two captures.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (byte-copy SRAM, write-verify-retry)

  • FUN_0800546c(dst, src, len) (0x0800546c) — raw byte-copy loop, destination written

byte-by-byte (*param_2 = *param_1; param_1++; param_2++;), guarded by a WAITCNT-style mask write (*_DAT_080054a4 = *_DAT_080054a4 & mask | 3) immediately before the copy — i.e. the "set SRAM wait-state bits" step GBA SRAM access requires. Role: write.

  • FUN_080054dc(dst, src, len) (0x080054dc) — re-applies the same wait-state mask, then

calls func_0x08091358(...) (unresolved; signature matches a byte-compare/memcmp) to verify the just-written bytes. Role: verify.

  • FUN_08005540(src, dst, len) (0x08005540) — driver: loops up to 3 times calling

FUN_0800546c then FUN_080054dc; breaks early on a clean verify, otherwise retries.

Role: write-with-retry (classic SRAM reliability pattern — write once, verify, retry on mismatch up to 3×). Called directly from FUN_08076aa8 with destination _DAT_08076b0c/length 0x10 as a self-test ("write known pattern, verify, read back, rotate"), and indirectly from FUN_08000e14.

  • FUN_08000e14(uVar1) (0x08000e14, flagged [MMIO-SEED]) — calls

func_0x080034c4(3, src, buf, 0x8000, 0x10) (RAM→RAM staging DMA of the entire 32 KB save image), then, only if (*_DAT_08000e54 == '\0'), calls FUN_08005540(uVar1, 0xe000000, 0x8000) — the literal flush of the full 32,768-byte save image to SRAM base 0x0E000000. This is the single confirmed top-level "commit all of SRAM" routine. Caller: FUN_08075b28.

3.2 Serialization / checksum routines

  • FUN_08075a94 (0x08075a94) — the global-header writer/serializer. Builds the

64-byte header record in place (field-by-field, see §5), zeroes the checksum word and forces the complement word to 0xFFFFFFFF, sums all 16 words of the record, stores the sum as the checksum (word 0) and its bitwise complement as word 1, then calls FUN_08000e58(0) to schedule/flush slot 0. Caller: FUN_08075b28.

  • FUN_08075c7c(param_1) (0x08075c7c) — the global-header validator/reader. Selects

one of three candidate header pointers by param_1 (0/1/2), re-computes the same 16-word sum, and returns a 3-bit error mask: bit 0 = checksum mismatch, bit 1 = version-string mismatch (byte-for-byte compare of the 20-byte string field against a reference buffer), bit 2 = complement-word mismatch (word0 != ~word1). No direct callers found in the traced callgraph (likely invoked via an unresolved func_0x... thunk from FUN_08075b28, which calls func_0x08075c7c(0/1/2) three times at its entry).

  • FUN_08075b28 (0x08075b28) — the header reconciliation orchestrator. Calls

func_0x08075c7c(0), (1), (2) to get validity of all three header candidates, then branches on which combination is valid/invalid to decide which candidate(s) to copy over which (using FUN_080033f4, the RAM→RAM DMA-style copy, 0x40-byte granularity), schedules an SRAM flush via FUN_08000e58(0/1/2), and finally — only on the "repair performed" branch — calls FUN_08000e14 (commit to real SRAM) followed by FUN_08075a94 (recompute checksum / rewrite header). No callers found in the traced callgraph (top of the traced chain; likely called from an untraced boot/save-menu routine).

  • FUN_08076b48 / FUN_08076d18 / FUN_08076dc8 — the directly analogous game-save-slot

triage: FUN_08076dc8(0/1) checks copy-A/copy-B validity per slot (same 2-state pattern as the header check), FUN_08076d18 sets a per-slot status byte (0=A valid,1=B valid,2=both valid, 3=neither), and FUN_08076b48 iterates all 3 slots and, depending on status, copies 0x1220-byte blocks between the two redundant copy regions (+0x80 base, offsets iRam08076bfc/iRam08076c2c/_DAT_08076ce4) via FUN_080033f4/FUN_080034c4, then triggers FUN_08000e58(3) and/or FUN_08000e58(4) to schedule the SRAM flush. No external callers found in the traced callgraph — this subsystem is present in the ROM but not exercised by either provided .sav sample (no slot data is non-0xFF).

  • FUN_08000e58(id) (0x08000e58) — task dispatcher. If a mode flag (*_DAT_08000e78)

is clear, dispatches through a 17-entry (id 0-0x10) function-pointer jump table (not individually resolved in this decompilation). If the flag is set, id==0xE triggers a direct 0x8000-byte (32 KB, i.e. the whole save image) RAM-to-RAM copy, and id==0xF triggers a direct 0x1220-byte (one game-save-slot-sized) copy with an index-scaled destination offset. Called from FUN_08075a44, FUN_08075a94, FUN_08075b28, FUN_08076b48, FUN_08077188, FUN_08077548, FUN_080777b4, FUN_08078a30 — i.e. every traced save-subsystem function funnels through this one dispatcher, consistent with it being the generic "schedule a save commit" primitive referenced throughout.

  • FUN_08075a44 (0x08075a44) — boot/entry sequencer: retries func_0x08076aa8() (the

SRAM self-test, §3.1) up to 3 times while a status byte is non-zero, then retries FUN_08000e58(0xE)/FUN_08000e58(0x10) up to 3 times, then calls func_0x08075b28() (header reconciliation), then the slot-reconciliation chain (func_0x08076b48, func_0x08077220, func_0x080777b4, func_0x08077548). This reads as the save-system boot/mount sequence: self-test SRAM → reconcile header → reconcile game-save slots.

4.2 Checksum algorithm — global header record (CONFIRMED_VERIFIED)

Formula (exact, derived from FUN_08075a94 lines building the record, reproduced verbatim):

record = 16 little-endian u32 words (64 bytes total), word[0] and word[1] are the checksum pair.
Before summing: word[0] := 0 ; word[1] := 0xFFFFFFFF   (placeholders, per decompiled code)
checksum        = (word[0] + word[1] + word[2] + ... + word[15]) mod 2^32
stored word[0]  = checksum
stored word[1]  = ~checksum  (bitwise NOT, i.e. one's complement)

Equivalently, since the placeholders contribute 0 + 0xFFFFFFFF = -1 mod 2^32:

checksum = (sum(word[2..15]) - 1) mod 2^32

The validator FUN_08075c7c independently re-derives this: it sums all 16 words of the

current (already-finalized) record — which trivially reproduces stored word[0] because word[0] + word[1] == -1 by construction — and separately checks word[0] == ~word[1] (error bit 2) plus a byte-exact match of the 20-byte version string (error bit 1).

Exact covered byte range: entire 64-byte record, offsets +0x00 through +0x3F relative to the record base (which is 0x0000 for the primary copy and 0x6D40 for the mirror copy in the provided .sav files).

Stored offsets: checksum at +0x00 (4 bytes, LE); complement at +0x04 (4 bytes, LE).

Python verification against the real .sav files (script run in this workspace):

import struct
for fname in ['saves/cap-00-future-0.sav', 'saves/cap-01-future-1.sav']:
    d = open(fname, 'rb').read()
    for base in (0x0000, 0x6d40):
        words = [struct.unpack_from('<I', d, base + 4*i)[0] for i in range(16)]
        w0, w1 = words[0], words[1]
        computed = (0xFFFFFFFF + sum(words[2:])) & 0xFFFFFFFF
        assert computed == w0
        assert w1 == (~w0 & 0xFFFFFFFF)

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be applied to a copy of cap-01-future-1.sav (the only sample with non-trivial written data), loaded via a fresh boot + load cycle, with before/after screenshots and a .ss save-state pair bracketing the reload (per the project's mandatory paired-save-state rule). Predictions are stated as falsifiable, observable outcomes.

  1. Checksum-rejection probe (no repair).
  • Mutation: flip one bit in 0x0000 (primary checksum word) and the identical bit in

0x6D40 (mirror checksum word) simultaneously, so both header candidates fail the checksum check identically.

  • Checksum repair: none performed (intentionally break both copies).
  • Prediction: FUN_08075c7c should return a non-zero error mask for both slot 0 and slot 1

candidates; FUN_08075b28's "all invalid" fallback branch (building a fresh default record on auStack_20) should fire, and the loaded game should show a reset/default header state (e.g., the save-counter field +0x0A reset or the version string path re-stamped) rather than a hard crash — falsifiable: if the emulator instead hangs or silently preserves the corrupted header, the "fresh default repair" branch inference is wrong.

  1. Single-copy corruption + repair verification.
  • Mutation: corrupt only the primary copy at 0x0000-0x003F (e.g., zero all 64 bytes),

leaving the mirror at 0x6D40 intact and valid.

  • Checksum repair: none (test the self-healing path itself).
  • Prediction: on next save-system "mount" pass (FUN_08075a44 → FUN_08075b28), the intact

mirror at 0x6D40 should be copied back over the corrupted primary at 0x0000, and a post-boot read of 0x0000-0x003F should exactly equal the pre-mutation mirror bytes. Counterfactual: if the primary stays corrupted/zeroed after a boot cycle, the 3-way repair hypothesis in §3.2 is falsified for this title/version.

  1. Version-string tamper (error bit 1 isolation).
  • Mutation: change one character of "ZeroMissionEURver005" at 0x001C (e.g., '5'→'6' at

0x002F) in both header copies, then recompute and write a correct checksum for the mutated bytes (so only the string-compare check, not the checksum check, should fail).

  • Checksum repair: yes — recompute per §4.2 formula and write to both +0x00/+0x04.
  • Prediction: FUN_08075c7c should still set error bit 1 (version mismatch) even though the

checksum now matches, since the validator's string-compare is checked independently of the checksum. This isolates whether the version string is actually enforced at runtime or merely cosmetic/unused.

  1. Save-generation counter increment probe.
  • Mutation: set +0x0A (both copies) to 0xFFFE just before a save-triggering action,

with a correctly recomputed checksum.

  • Checksum repair: yes.
  • Prediction: after one more save event, the field should read 0xFFFF then wrap to 0x0000

on the save after that (standard u16 overflow), with no checksum failure — confirms the "+=1 on every header write" semantics inferred from FUN_08075a94.

  1. Footer/slot-label probe (unknown-writer region).
  • Mutation: zero out the entire 0x6D80-0x6DA6 block and 0x7F70-0x7F7F block in

cap-01-future-1.sav (reverting them to the cap-00 "unwritten" state), leaving the header untouched.

  • Checksum repair: none required (these regions are not part of the verified header

checksum's covered range).

  • Prediction: since no writer for these regions was identified in this workspace's

decompilation, the predicted in-game effect is unknown. If the save-slot-select screen renders incorrectly, errors, or silently regenerates the labels on next boot, that is strong evidence these are a live-but-untraced UI label cache; if nothing visibly changes, they may be cosmetic/debug remnants not read at runtime. This test exists specifically to resolve the UNKNOWN entries in §5.

  1. Full-SRAM-mirror stress test.
  • Mutation: corrupt bytes throughout the untouched 0xFF filler region (e.g., 0x1000-0x1010)

that are outside every currently-identified active range.

  • Checksum repair: none (none of the identified structures cover this range).
  • Prediction: if the game ignores this region entirely (no crash, no visible change, and the

bytes remain corrupted after a save/reload cycle rather than being restored), this confirms the region is genuinely unused padding rather than an undiscovered field — a negative control for the whole field map.
