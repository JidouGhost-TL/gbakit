1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven to a high standard (code + both .sav binaries agree, byte-for-byte):

  • Physical media is EEPROM, 8192 bytes (64 Kbit), accessed as 1024 blocks of 8 bytes through the serial EEPROM window at 0x0D000000 via DMA3. No SRAM (0x0E000000) or Flash command sequence (0x5555/0x2AAA) save path exists in the traced corpus.
  • Layout is 3 independent save slots of 640 bytes each (0x000, 0x280, 0x500), each split into a 32-byte header + 608-byte payload, plus one global/config block at 0x780 (32-byte header + 16-byte data at 0x7A0). Bytes 0x7B0–0x1FFF are unused and are 0xFF in both samples.
  • The EEPROM driver stores each 8-byte block byte-reversed relative to the RAM buffer. This transform was not assumed: it was derived from the driver bit assembly and then proven against known default values (Section 4.3).
  • The integrity algorithm is a custom rotate-left-1-and-add hash (h = ROL32(h,1) + byte, seed 0xAA55A5A5) implemented in FUN_0806f1c0. The seed is not printed in the decompilation (it is an unresolved literal-pool value _DAT_0806f1dc); it was recovered by inverting the hash from the stored values and then verified forward on 8 independent regions (3 slots + 1 global, × 2 files). Every one matches. See the verbatim Python output in Section 4.4.
  • All three slots in both captures are identical blank/default slots (created by the new-game initialiser). The only difference between the two captures is 5 bytes, all inside the global block: its data field at RAM +0x00 changed 0xFFFF → 0x0000, and its header checksum at file 0x788 was recomputed accordingly. This is exactly the mutation span flagged in PACKET.md (0x788–0x78A, 0x7A6–0x7A7), and it confirms the global checksum covers the 16-byte global data block and nothing else.
  • Boot behaviour on a corrupt global checksum is corroborated by the packet probe: mutating file offset 0x788 (the first stored-checksum byte of the global header) caused the save to be treated as blank and rewritten. That matches the code path in FUN_080192d8 / FUN_080002f4 (Section 3.4).

What keeps the overall rating at MEDIUM rather than HIGH:

  • The payload unpacker 0x08019a50 (called by the slot loader after a successful checksum) has no body in the corpus — it is a func_0x08019a50 call site only, with no FUN_08019a50 definition among the 298 functions. The pack direction (FUN_08019958) is fully mapped, so payload field positions are known, but the reverse assignment into live game state cannot be quoted line-by-line.
  • The global-save writer FUN_08019c80 has no caller in the corpus, and the ordinary in-game slot-save trigger (the menu/save-point code that would call FUN_0801969c during play) is likewise absent: in the traced set FUN_0801969c is only reached from the blank-slot creator FUN_08019b5c. The trace-guided 298-function corpus simply did not execute those paths. Their absence is reported, not filled in.
  • Absolute RAM mirror addresses are not recoverable from the supplied decompilation. Every RAM pointer is an unresolved Ghidra placeholder (_DAT_08019xxxx, psRam…, uRam…); the literal-pool values were not exported. Fields are therefore mapped by buffer-relative offset (header +0x0C, payload +0x26, game-struct +0x20, …), which is exact, instead of by a fabricated 0x02xxxxxx/0x03xxxxxx address.
  • The gameplay semantics (names/meanings) of most payload fields are unknown. Positions, types, writers, default values and observed values are mapped; labels such as health/level/progress are not guessed. Both samples contain only default-state slots, so no non-default field value has ever been observed in a .sav.

Confidence vocabulary used in the field table: CONFIRMED_VERIFIED = code and .sav bytes both prove it; CONFIRMED_STATIC = decompiled code proves it, no .sav observation distinguishes it; HYPOTHESIS = plausible inference, explicitly flagged; UNKNOWN = position known (or region present) but meaning/writer unresolved.

There is no second save technology in the corpus: no byte-copy loop targeting 0x0E000000 (SRAM) and no Flash unlock sequence (0x5555/0x2AAA writes) is associated with any save caller. The two other seed functions in ghidra/save_related_functions.c, FUN_0807a964 and FUN_0807aaac, are false positives — they are signed/unsigned modulo helpers (they call the division-by-zero trap func_0x0807a92c) and never touch the EEPROM window. They are excluded from the save path.

At boot, FUN_080002f4 calls func_0x08072abc(), which sets the EEPROM-ready flag (*_DAT_08072abc… = 1 via *_DAT_08072acc) and calls FUN_08072b30 → FUN_0807a460(0x40), selecting the 0x40 EEPROM-type parameter block. The driver reads two fields from that block: a u16 at +4 used as the exclusive upper bound for block indices (capacity in 8-byte blocks) and a u8 at +8 used as the serial address-bit count (read command length = bits+3, write command length = bits+0x43). The numeric contents of the selected block are not in the exported decompilation, so the bit count is not quoted; the capacity it must describe is fixed by the 8192-byte image (1024 blocks). The public read/write wrappers FUN_08072ae8 / FUN_08072b0c refuse to run (return -1) while the ready flag is zero.

Slot stride and split are not inferred from the hexdump alone; they are the literal constants in the code:

  • Slot base = slot_index * 0x280, header length 0x20, payload length 0x260 — used identically in the saver FUN_0801969c (func_0x08072b0c(param_1 * 0x280, …, 0x20) then … + 0x20, …, 0x260), the loader FUN_08019754 (same offsets via func_0x08072ae8), the blank-slot creator FUN_08019b5c, and the slot prober FUN_080197d0.
  • Global header at 0x780 (length 0x20) and global data at 0x7A0 (length 0x10) — used in FUN_080192d8, FUN_08019c1c, FUN_08019c80.
  • In RAM the four 32-byte headers (3 slots + global) sit consecutively in one descriptor array inside the boot/global struct: slot descriptors at struct +0xCC, +0xEC, +0x10C, and the global header buffer at struct +0x12C (= decimal 300, the pointer passed to FUN_080192d8 and FUN_08019c1c from FUN_080002f4). Per-slot status words live separately at struct +0xDC, +0xFC, +0x11C and are not stored in the EEPROM image.

2.3 Redundancy, counters, selection rule

  • No mirroring and no backup copy exists. Each slot is written exactly once per save (header block(s), then payload blocks); there is no A/B ping-pong region, no second copy of the global block, and no cross-slot duplication in code or in the image. The fact that all three slots are byte-identical in both captures is because all three hold the same default state, not because they mirror each other.
  • Generation/sequence counter: header RAM +0x08 (u32) is a per-save counter. FUN_0801969c updates it on every slot save (increment-style update with an ASCII-digit-flavoured overflow path involving ':'/0x3A — see the honesty note in Section 5), FUN_08019b5c resets it to 0 for a blank slot, and FUN_080197d0 treats values < 0x65 (101) on a distinct fast path. Observed value in every slot of both samples: 0. The global header leaves this field at 0xFFFFFFFF (it is never initialised for the global block; only its checksum word is written).
  • Validity flag: header RAM +0x10 (u32). FUN_0801969c sets it to 1 while saving a real slot; FUN_08019b5c writes the slot once through that path and then rewrites it with +0x08 = 0 and +0x10 = 0, so a blank slot on disk carries flag 0. Observed: 0 in all slots (all blank). The global header again leaves it 0xFFFFFFFF.
  • Selection rule (boot): FUN_08019848 zeroes the three RAM descriptors (0x60 bytes), probes each slot with FUN_080197d0, and records a status per slot: -1 if the header read or the full load/checksum fails, otherwise 0 or 1 depending on a string comparison of the header buffer (func_0x0806e918, body absent from the corpus) and a word at descriptor +0x14. FUN_080002f4 then (a) if the global load failed and all three slots report -1, creates the global defaults (FUN_08019c1c) and three blank slots (FUN_08019b5c ×3); (b) independently, re-creates any individual slot whose status, read as unsigned, is > 1 — in practice the -1 (invalid) case, since the only other values assigned are 0 and 1. There is no "pick newest by counter" arbitration between slots anywhere in the corpus; the player-facing choice among slots is outside the traced code.

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method, read this first)

Two evidence sources were cross-checked for every edge, because neither is complete alone:

  1. ghidra/callgraph.json (298 nodes) records only a subset of edges. Example of its blind spot: it lists 0x0807a81c (the verified EEPROM write) with no callers at all, and lists 0x08072b44's callees as only 0x0806ae84, 0x08072924, 0x08072930.
  2. Textual call sites in ghidra/decompiled.c. Ghidra emits two spellings: FUN_080xxxxx for the defining/calling-convention-recovered form and func_0x080xxxxx for calls through the unrecovered tail-jump. Searching for func_0x0807a81c finds the real call inside FUN_08072bf0 (line 8698) that the JSON graph missed. Every caller claim below was produced by enumerating both spellings, attributing each call site to its enclosing // 080xxxxxx function header, and then confirming the edge against the JSON graph where the graph does contain it. Edges found only textually are marked "(textual; absent from callgraph.json)".

A second systematic caveat: many FUN_ bodies end in (*UNRECOVERED_JUMPTABLE)(…) — Ghidra could not recover the Thumb tail-branch, so return values and later arguments are often missing from the printed prototypes (e.g. FUN_08072b0c prints one parameter but is called with four). Argument roles below are therefore taken from the call sites, which preserve all four registers, not from the broken prototypes.

_DAT_/psRam/uRam symbols are unresolved literal-pool placeholders. Where a function's behaviour depends on such a value (checksum seed, EEPROM type block, string constants), that dependence is stated and the value is either recovered from the .sav bytes (seed) or left explicitly unknown.

3.3 Caller chains (end-to-end)

Chain A — factory init / blank-slot creation (fully traced, matches both samples byte-for-byte): FUN_080002f4 (boot) → FUN_08019848 (probe; all slots invalid on a blank/corrupt EEPROM) + FUN_080192d8 returns -1 → FUN_08019c1c (global defaults) and FUN_08019b5c(slot, desc) → FUN_080194e0 (game defaults) → FUN_08019958 (pack) → FUN_0801969c (counter/flag/checksum) → FUN_08072b0c → FUN_08072bf0 → FUN_0807a81c → FUN_0807a7e4 → FUN_0807a5ec → FUN_0807a4a8 (DMA3 → 0x0D000000), with verify via FUN_0807a74c → FUN_0807a528. FUN_08019b5c then rewrites header+payload with counter/flag zeroed. RAM fields mutated before flush: the entire game struct (defaults), the payload buffer (pack), header +0x08/+0x0C/+0x10. This chain provably produces the observed image: default payload values (§4.3), header counter 0, flag 0, checksum 0xF5E045D3.

Chain B — normal slot save (partially traced): … (in-game trigger absent from corpus) … → FUN_0801969c(slot, header) → pack (FUN_08019958, which snapshots the current game struct fields listed in §5 into the payload buffer) → header counter update, +0x10 = 1, checksum → gated EEPROM write (same tail as Chain A). 3.4 What the boot code does with a bad checksum (ties to the packet probe)

FUN_080192d8 returns -1 if the global header checksum does not match the 16 data bytes. FUN_080002f4 responds as in §2.3: full factory-init only if every slot is also invalid; otherwise each invalid slot is individually re-blanked. The packet's cold-reload probe (single-byte mutation at file 0x788, i.e. inside the stored global checksum; save observed rewritten and boot observed blank) is consistent with this code: the mutated global block can no longer validate. The probe's stronger claim ("reverted to blank") involves UI behaviour outside the traced functions and is recorded as probe metadata, not as a code-proven fact.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signatures

There is no magic signature. No ASCII string, no constant byte pattern, and no SDK tag is stored in the save image: both samples contain no printable run in the active ranges (PACKET.md: ascii_magic_strings: []), and no save function in the corpus compares any payload/header byte against a constant signature. Validity is established solely by (a) the EEPROM read succeeding, (b) the header checksum matching the covered block, and (c) boot-time range clamps. The nearest things to magic, listed to prevent misidentification:

  • Header bytes that are 0xFF (slot header RAM +0x01…+0x07, +0x18…+0x1F; almost the entire global header) are uninitialised/stale buffer contents, not a signature — the writers never set them (slot headers) or never clear them (global header). An emulator or tool must not validate them.
  • The checksum seed 0xAA55A5A5 (§4.2) is a ROM-side constant. It never appears in the .sav.
  • FUN_08019848 string-compares the header buffer against an unresolved constant (func_0x0806e918(iVar4, uRam08019894)). Because neither the string nor the compare body is in the corpus, this is recorded as an open question (§6 of the JSON / report §5 notes), not as a magic: in both samples header RAM byte +0 is 0x00 for slots (empty-string-like) and 0xFF for the global header, and all three slots validate as blank.

4.2 Checksum formula (exact)

Decompiled proof, FUN_0806f1c0 (ghidra/decompiled.c, function header at // 0806f1c0):

void FUN_0806f1c0(byte *param_1, int param_2)
{
  uVar2 = _DAT_0806f1dc;                 /* seed: literal-pool, unresolved in export */
  for (; param_2 != 0; param_2 = param_2 + -1) {
    if ((uVar2 & 0x80000000) == 0) {
      iVar1 = uVar2 << 1;
    } else {
      iVar1 = uVar2 * 2 + 1;
    }
    uVar2 = iVar1 + (uint)*param_1;
    param_1 = param_1 + 1;
  }
  (*UNRECOVERED_JUMPTABLE)(uVar2);       /* returns uVar2 */
}

Restated exactly, over unsigned 32-bit arithmetic:

h ← SEED
for each byte b in covered_range (in RAM-buffer order, increasing offset):
    h ← ROL32(h, 1) + b        (mod 2^32)
stored ← h  as u32 little-endian at header RAM +0x0C

The if/else is precisely a rotate-left by 1: h*2+1 when the top bit is set re-inserts it at bit 0; plain h<<1 otherwise. It is not a CRC (no polynomial/table), not a plain sum (the rotate makes it position-sensitive), and not byte-swapped: the addition uses the byte value zero-extended, and the stored word is little-endian in the RAM buffer (its file bytes are then subject to §4.3).

  • Seed recovery: _DAT_0806f1dc is not exported, so the seed was recovered algebraically. The step h' = ROL(h,1) + b is invertible (h = ROR(h' − b, 1)), so running the stored value backwards through the known covered bytes yields the required seed for each region. All eight regions (3 slots + global, both files) independently yield 0xAA55A5A5 — an unmistakably deliberate constant (AA 55 A5 A5) — and the forward check with that seed then matches every stored value (§4.4). Confidence: CONFIRMED_VERIFIED.
  • Instances: the identical function/instance pattern is used twice: (1) slot checksum — covers the 608-byte RAM payload, stored at slot-header RAM +0x0C; (2) global checksum — covers the 16-byte RAM global data, stored at global-header RAM +0x0C. Call sites: FUN_0801969c/FUN_08019754/FUN_08019b5c for slots (length 0x260), FUN_080192d8/FUN_08019c1c/FUN_08019c80 for global (length 0x10). There is no other checksum, CRC, or integrity field anywhere in the save path.

4.3 The EEPROM byte-order transform (prerequisite for any verification)

The checksum and every multi-byte field are defined over the RAM buffer, but the .sav does not store the RAM buffer linearly. Within each 8-byte block, the file bytes are the reverse of the RAM bytes:

file[block*8 + i] = ram[block*8 + (7 − i)]      for i in 0..7

(The transform is an involution: applying it again restores the RAM image.)

Why this happens, from the driver: FUN_0807a528 reassembles the 64 serial bits into four u16s stored backwards from dst+6, and FUN_0807a5ec serialises with the complementary stack-reversed bit order; the emulator's EEPROM image records the serial block in wire order. The mechanism detail matters less than the empirical proof, which is independent of it:

  • Global data defaults (FUN_08019c1c) in RAM little-endian are SS SS 01 00 C0 00 00 00 | 00 01 00 00 00 00 00 00 (u16@+2=1, u32@+4=0xC0, u32@+8=0x100). Reversing each 8-byte block gives 00 00 00 C0 00 01 SS SS | 00 00 00 00 00 00 01 00. The files contain exactly 00 00 00 C0 00 01 FF FF | 00 00 00 00 00 00 01 00 (cap-00) and … 00 01 00 00 | … (cap-01) — matching with SS SS = FF FF then 00 00. No linear or halfword-swapped interpretation matches.
  • Slot payload defaults: pack places u16 250 at payload RAM +0x02 and 0xFF bytes at +0x04…+0x07. RAM block 0 is therefore 00 00 FA 00 FF FF FF FF; reversed, the file must start (at payload file offset) FF FF FF FF 00 FA 00 00. Both files do (file 0x20: ff ff ff ff 00 fa 00 00). Likewise payload RAM +0x26 = 10, +0x2C = 200, +0x2E = 7, +0x30 = 120, +0x32 = 5 appear in the file at the reversed positions 0x41=0x0A, 0x4B=0xC8, 0x49=0x07, 0x57=0x78, 0x55=0x05 — all confirmed.
  • A checksum computed over the raw file bytes without applying this transform does not match (0x3096329B vs stored 0xF5E045D3 for slot 0, both files). Any tool that checksums the raw .sav will wrongly condemn every valid save.

Consequences for offsets: a RAM offset r inside an 8-byte block starting at B appears at file offset B + (7 − (r − B)). In particular the stored checksum (RAM header +0x0C, block 0x08–0x0F, position 4 within its block) appears at file header offset 0x08 — which is why the packet probe's sensitive byte is file 0x788 (global header 0x780 + 8), and why a naive reading of the header at file +0x0C finds 0x00000000/0xFFFFFFFF instead of a checksum.

Notes on the table:

  1. Slot-header file offsets are given for slot 0. Because of the §4.3 reversal, the file positions of the counter, checksum and flag inside each 32-byte header are: counter RAM +0x08 ↔ file bytes 0x0B,0x0A,0x09,0x08 within the block (value 0 in samples, so indistinguishable), checksum RAM +0x0C ↔ file +0x08…+0x0B in file order F5 E0 45 D3, flag RAM +0x10 ↔ file +0x17…+0x10 reversed block (value 0). Tools should operate on the un-reversed RAM image and re-reverse on write (§6 gives the exact procedure); patching "file offset 0x0C" directly corrupts the header.
  2. The payload byte-copy group (+0x18…+0x22) is transcribed in code order in the FUN_08019958 row text; the decompiled assignments interleave byte and halfword stores to the same buffer, and the table rows for +0x18 and +0x1F–+0x21 together enumerate each destination byte exactly once. Any byte in +0x18…+0x22 not explicitly listed takes the value stated in its row group (all observed 0).
  3. Game-struct default offsets that are not packed (e.g. G+0x4E=4, G+0x64=1, G+0x6C=0xC0, G+0x70=0x3F, the G+0x168… arrays cleared in FUN_080194e0) never reach the EEPROM. They are live-state initialisation only and are deliberately absent from the field map; a tool must not expect them at any file offset.
  4. No field in either sample takes a non-default value except global data +0x00. Every "Observed Values" entry is therefore simultaneously the default value; the table says so where FUN_080194e0/FUN_08019c1c proves the default.

6. Save Fuzzing & Counterfactual Verification Plan

Corpus limitation, stated plainly: states/ is empty for this packet (0 paired save states), so the plan below is written against the .sav files plus a fresh emulator boot (as in the packet's cold-reload probe), not against a supplied .ss. Each test: mutate the .sav, boot/reload, and record (a) whether the slot/global still validates, (b) the observable UI/game effect, (c) the RAM payload/header after load if a debugger is available. Predictions marked [code] follow directly from §3; predictions marked [probe] extrapolate the packet probe; anything else is a genuine open prediction to be measured, not asserted.

Mandatory checksum-repair procedure (needed by every test that must still validate): work on the RAM image, never on raw file bytes.

1. ram = unreverse_each_8byte_block(sav_bytes)          # §4.3 transform
2. edit ram at RAM offsets (header/payload/global as in §5)
3. if payload edited: ram[slot_hdr+0x0C .. +0x10] = LE32( rol_add_checksum(ram[slot_payload .. +0x260], seed=0xAA55A5A5) )
   if global data edited: ram[global_hdr+0x0C ..] = LE32( rol_add_checksum(ram[0x7A0 .. +0x10], seed=0xAA55A5A5) )
   (file offsets for the RAM image are the linear ones: slot s payload RAM starts at s*0x280+0x20 in the un-reversed image)
4. sav_bytes = unreverse_each_8byte_block(ram)          # same operation, it is an involution
5. write sav_bytes (8192 bytes, tail beyond 0x7B0 left as 0xFF)

Tests that intentionally break integrity skip step 3. A repair is proven correct before booting by re-running the §4.4 verifier on the mutated file (all match=True required).
