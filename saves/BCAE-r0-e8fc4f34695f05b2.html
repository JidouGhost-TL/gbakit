Save Format Report — Cars (USA, Europe) [BCAE-r0-e8fc4f34695f05b2]

Clean-room derivation strictly from saves/, ghidra/decompiled.c, ghidra/callgraph.json, ghidra/save_related_functions.c, and generic GBA hardware specs (EEPROM bus at 0x0D000000 via DMA3, EWRAM 0x02000000, IWRAM 0x03000000). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

Proven (CONFIRMED_STATIC, backed by decompiled code and/or exact byte matches against the real .sav):

  • The save medium is GBA EEPROM, 512 bytes (4Kbit), accessed through the standard

DMA3 serial bitstream protocol at 0x0D000000.

  • A complete, 4-layer I/O stack was traced end-to-end: low-level DMA3 bit transceiver →

low-level EEPROM sector read/write → verify-after-write helper → mid-level multi-sector EepromRead/EepromWrite → slot-level load/save entry points.

  • A 200-byte payload region (offsets 0x00-0xC7) is checksummed with a simple unsigned

byte-sum, and that payload ends in a 4-byte ASCII magic trailer, CARS, at offset 0xC4-0xC7 — this magic is byte-for-byte present in the real .sav.

  • A 148-byte block (offsets 0x00-0x93, 37 little-endian dwords) consists entirely of

0/1 values, consistent with a boolean unlock/progress flag array.

Open / not fully reconciled (HYPOTHESIS):

  • The exact on-disk storage offset of the 2-byte checksum. The traced write call site

computes a target EEPROM sector of slot*0x1b + 0x1a (byte offset 0xD0-0xD1 for slot 0), but a byte-sum of the first 200 bytes (0x0150) matches, big-endian, bytes found at offset 0xD6-0xD7 in the real sample instead. The algorithm is proven; its persisted location is only a verified numeric coincidence pending a second sample.

  • The semantics of a 12-dword structured block at offsets 0x94-0xC3 (candidate

time/score records) — no code in the traced function set individually writes these sub-fields.

  • Whether a second save slot and/or a global-config tail region genuinely exist in the

remaining 296 bytes of the 512-byte EEPROM (only slot 0 is non-blank in the single available sample).

  • The function that actually assembles the in-RAM 200-byte payload (including writing the

literal CARS bytes) is not among the 321 functions captured in ghidra/decompiled.c — only its downstream write (FUN_08016198 → FUN_0802ad98 → EEPROM) was traced.

Only one .sav file (cap-00-future-0.sav, 512 bytes) was available in saves/, and it has only one non-blank region. All cross-sample claims are therefore necessarily limited; this is called out per-field in Section 5.

3. Save Writer, Reader & Caller-Chain Architecture

All addresses are GBA ROM addresses (0x08xxxxxx), consistent with the packet's game code BCAE.

3.1 Low-level hardware I/O driver (EEPROM serial DMA3 bitstream)

  • FUN_08037918 (ghidra/save_related_functions.c:9) — shared DMA3 bit-serial

transceiver. Saves/restores an interrupt-related register (*_DAT_08037978), programs DMA source/dest/control (*_DAT_08037988, *_DAT_0803798c, *_DAT_08037990 with the enable bit 0x80000000 set), then busy-waits on the DMA "busy" status bit (uVar2 & 0x8000) until the transfer completes. This is the generic primitive used by both the sector reader and the sector writer; direction is determined purely by the caller's buffer/bit-count arguments, not by anything internal to this function.

Callers: 0x08037998 (reader), 0x08037a5c (writer) — confirmed via ghidra/callgraph.json.

  • FUN_08037998 (EEPROM sector READ, ghidra/save_related_functions.c:40) —

encodes a read command (1,1 leading bits) + sector address bits into a local stack buffer, transmits it via FUN_08037918, then issues a second FUN_08037918 call requesting 0x44 = 68 bits back (4 lead/dummy bits + 64 data bits), and decodes 4× 16-bit big-endian-ordered words from the received bitstream into the destination buffer (param_2). One call transfers exactly one 8-byte sector.

Callers: 0x08037bbc, 0x0802ae48 (both confirmed via ghidra/callgraph.json and direct call-site grep of ghidra/decompiled.c).

  • FUN_08037a5c (EEPROM sector WRITE, ghidra/save_related_functions.c:98) —

encodes a write command + sector address + the 64 data bits taken from the source buffer (param_2) into a stack bit-buffer, transmits it in a single FUN_08037918 call, then busy-waits on a value read through _DAT_08037b48 (almost certainly REG_VCOUNT, 0x04000006, given the ~136-scanline delta threshold 0x88 used as the wait condition — this matches the well-known ~10 ms EEPROM internal write-commit latency) before returning. param_3 selects "retry forever" vs. "wait once."

Callers: 0x08037a48 only.

  • FUN_08037a48 — thin wrapper: FUN_08037a5c(param_1, param_2, 1), forcing the

retry-forever wait variant. Callers: 0x0802ad98.

  • FUN_08037bbc (write-verification helper) — re-reads the sector just written via

FUN_08037998 into a local 8-byte buffer and compares it word-by-word against the caller-supplied buffer, returning 0 on match or 0x8000 on mismatch.

Callers: 0x0802ad98, 0x0802ae48.

  • FUN_08037ea4 (flagged as an MMIO seed by the extraction tool, ghidra/save_related_functions.c:226)

— on inspection this is a generic unsigned 32-bit division/remainder compiler runtime routine (classic shift-and-subtract long division with a param_2==0 → divide-by-zero trap). It has no EEPROM/DMA I/O and no callers in the 321-function trace except a single arithmetic use at ghidra/decompiled.c:9030. This is a false-positive seed, not part of the save I/O chain, and is excluded from the rest of this report.

3.2 Mid-level sector-sequence I/O (serialization boundary)

  • FUN_0802ad98 (EepromWrite(sector, src_buf, byte_count),

ghidra/decompiled.c:4693) — for every full 8-byte chunk of byte_count, writes directly via FUN_08037a48 then verifies via FUN_08037bbc; for a trailing partial chunk, performs read-modify-write: reads the existing sector with FUN_08037998, overwrites only the first N remaining bytes with new data, writes the merged sector back via FUN_08037a48+FUN_08037bbc. This preserves any bytes in the tail sector that are not part of the requested write — directly explaining why a 2-byte write to a sector does not necessarily overwrite the other 6 bytes of that sector.

Callers: 0x08016198 only.

  • FUN_0802ae48 (EepromRead(sector, dest_buf, byte_count),

ghidra/decompiled.c:4756) — mirror of FUN_0802ad98 for reads (direct full-sector reads via FUN_08037998+FUN_08037bbc verify; partial tail read into a temp buffer with the needed leading bytes copied to dest_buf). Callers: 0x080160b4 only.

3.3 Slot-level load/save entry points & caller chains

  • FUN_080160b4 (slot LOAD, ghidra/decompiled.c:462) — computes

sector_base = (slot & 0xff) * 0x1b, reads 200 bytes into a RAM buffer (_DAT_08016144) and a 2-byte trailer into a second RAM buffer (_DAT_08016148), both via FUN_0802ae48 at sector_base and sector_base + 0x1a respectively. If either read fails or its internal verify (FUN_08037bbc, embedded inside FUN_0802ae48) fails, it falls back to calling FUN_08016198(slot) to rebuild/repair the slot. This function has no caller anywhere in the 321 traced functions — it is the top of the traced save call graph; the actual gameplay/menu event that triggers a load was not captured by this trace.

  • FUN_08016198 (slot WRITE / validate, ghidra/decompiled.c:525) — has two

branches:

  1. RAM-cache-valid branch: if a cache-validity marker matches

(*(int*)(cache_base+0xc0) == _DAT_08016234), it recomputes the 200-byte checksum straight from the already-resident RAM buffer, cross-checks it against a cached expected value (*piRam080162ac) and a structural sanity scan over 16 twelve-byte records (small-value range checks on bytes within each record), all with no EEPROM I/O — this is a fast re-validation path for data already loaded this session.

  1. Cold/uncached branch: rebuilds the slot payload in RAM then writes it to EEPROM:

200 bytes via FUN_0802ad98(sector_base, buf, 200), and, if that succeeds, a 2-byte trailer via FUN_0802ad98(sector_base + 0x1a, &checksum, 2).

Callers: FUN_080160b4 (line 495), invoked specifically when the load+verify in the cold branch of FUN_080160b4 fails — i.e., this is the corruption-repair / first-boot format path, not a routine "save game" trigger reachable from this trace.

How each caller mutates the in-RAM struct: Only the shape of the mutation is provable from this trace — FUN_08016198's cold branch populates the 200-byte RAM buffer (_DAT_08016230/_DAT_08016144) and the checksum variable (*piRam080162ac) before any EEPROM write, but the function(s) that set individual bits/fields inside that 200-byte buffer (e.g., which code sets an unlock flag to 1, or writes the literal CARS bytes) are not present among the 321 functions in ghidra/decompiled.c. This is reported as an explicit evidentiary gap rather than guessed at.

4.2 Checksum algorithm

Algorithm: unsigned byte-wise sum (sum16, no masking beyond natural 16-bit wrap), covering bytes 0x00-0xC7 (200 bytes) — proven directly in FUN_08016198 (ghidra/decompiled.c:548-551):

uVar8 = 0;
do {
  iStack_20 = iStack_20 + (uint)*(byte *)(_DAT_08016230 + uVar8);
  uVar8 = uVar8 + 1;
} while (uVar8 < 200);

Covered range: 0x00-0xC7 inclusive (200 bytes), which includes the CARS magic trailer at its tail (0xC4-0xC7).

Stored offset (as implied by the traced EEPROM-write call site in FUN_08016198): sector_base + 0x1a = sector 26 for slot 0 = byte offset 0xD0-0xD1 (2 bytes).

Python verification against saves/cap-00-future-0.sav:

>>> data = open('saves/cap-00-future-0.sav','rb').read()
>>> seg = data[0x00:0xc8]                      # 200 bytes
>>> computed = sum(seg) & 0xffff
>>> hex(computed)
'0x150'
>>> data[0xd0:0xd2].hex()                       # offset implied by the traced write call site
'ffff'                                           # NOT a match — this region is blank in the sample
>>> data[0xd6:0xd8].hex()                        # offset where a non-blank value actually exists
'0150'
>>> int.from_bytes(data[0xd6:0xd8], 'big') == computed
True

Interpretation (honest confidence call): the algorithm (byte-sum of the first 200 bytes) is CONFIRMED_STATIC — it is directly decompiled and matches an exact big-endian 16-bit value found elsewhere in the real save file. The storage offset is not reconciled: the traced write call site addresses 0xD0-0xD1, which is blank/0xFF in the sample, while the exact numeric match sits at 0xD6-0xD7 instead. With only one non-blank sample available, this discrepancy cannot be resolved from static analysis alone — it is reported as HYPOTHESIS in save-format.json, not CONFIRMED_VERIFIED. A second sample (ideally with a deliberately mutated unlock flag, paired with pre/post .ss states) would let us confirm whether the checksum moves with the data at 0xD6-0xD7, or whether this is a coincidental match and the true checksum/trailer field lives at 0xD0-0xD1 but was never populated in this particular capture.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations below should be performed on a copy of saves/cap-00-future-0.sav, loaded into the emulator from a paired pre-mutation .ss state at the save/load-slot screen, with a post-mutation .ss state captured immediately after the game attempts to read the slot.

  1. Magic corruption probe (falsifies magic's role in validation)
  • Mutation: flip offset 0xC4-0xC7 ("CARS" → e.g. "XARS").
  • Requires checksum repair: yes (if 0xD6-0xD7 is the real checksum location, it must

be recomputed to reflect the new byte sum to isolate the magic's own effect).

  • Predicted effect: game treats the slot as invalid and falls back to

FUN_08016198's default-write/repair path (observable as a reset/blank save or "new game" prompt rather than resumed progress).

  1. Checksum-location probe (resolves the Section 4.2 open question directly)
  • Mutation A: flip 0xD6-0xD7 only, leave 0x00-0xC7 untouched.
  • Mutation B (separate test): flip 0xD0-0xD1 only (currently 0xFF 0xFF), leave

everything else untouched.

  • Requires checksum repair: no (that is the point of this probe).
  • Predicted effect: whichever mutation causes the game to detect corruption and run the

repair path identifies the true checksum-storage offset; if neither triggers any observable change, the checksum validation for this title may only run from the RAM-cache path during the session and never re-validate against this on-disk trailer after a fresh cold load.

  1. Boolean flag toggling (maps individual unlock/progress bits)
  • Mutation: flip one u32 dword at a time across 0x00-0x93 (0↔1), with full

checksum repair at 0xD6-0xD7 (and/or 0xD0-0xD1, per probe 2's outcome) after each flip.

  • Predicted effect: each flip should toggle exactly one discrete unlock/progress

indicator in-game (car/track/mode availability) with no other visible change; a flip that crashes or corrupts unrelated UI would indicate the dword is not a simple boolean despite only ever observing 0/1 in this sample.

  1. Structured-record zeroing (tests 0x94-0xC3 hypothesis)
  • Mutation: zero all 48 bytes at 0x94-0xC3, with checksum repair.
  • Predicted effect: if these are time/score-style records, expect a reset-to-default

display (e.g., blank best times) rather than a crash; a crash or garbled display would indicate the block encodes indices/pointers rather than flat counters.

  1. Tail-region write probe (tests whether 0xD8-0x1FF is truly unused)
  • Mutation: write non-0xFF bytes into 0xD8-0x1FF with no other changes, no

checksum repair (that region is outside the proven 200-byte checksum coverage).

  • Predicted effect: if genuinely unused by the game's code, no behavior change should

be observed on load; any crash, UI corruption, or appearance of a "second slot" would indicate an untraced consumer of that region exists and should be captured in a future trace-guided decompilation pass.

  1. Fresh vs. restore repeat (matched-duration control, per standing experiment

guidance)

  • Run A: boot from a blank/erased EEPROM and capture the slot at the moment

FUN_08016198's cold branch first writes it.

  • Run B: boot from the existing cap-00-future-0.sav and let the RAM-cache-valid branch

run instead.

  • Predicted effect: Run A should show the checksum/trailer bytes being written for the

first time (directly confirming the true storage offset via a RAM/EEPROM write trace rather than static inference); Run B should show no EEPROM writes at all unless a flag is deliberately changed in-game, isolating when writes actually occur.
