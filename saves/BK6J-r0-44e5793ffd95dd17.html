Clean-Room Save Format Report — Kouchuu Ouja Mushiking: Greatest Champion e no Michi (Japan) [BK6J]

1. Executive Summary & Overall Confidence

Overall Confidence: LOW

This workspace's trace-guided Ghidra corpus (ghidra/decompiled.c, 99 functions; ghidra/callgraph.json; ghidra/save_related_functions.c) does not contain any function that touches a GBA save-media hardware region (SRAM/Flash at 0x0E000000, EEPROM access via DMA3 0x040000D4, or the EEPROM bus window 0x0D000000). A full-text search of ghidra/decompiled.c for SRAM, EEPROM, FLASH, 0x0E00, 0x0D00, and 0x040000D4 returns zero matches. The single function flagged [MMIO-SEED] in ghidra/save_related_functions.c (FUN_08377664, with its callee FUN_08377660) is, on inspection, a generic software long-division/modulo runtime routine (classic restoring binary-division algorithm with a divide-by-zero trap callee) — it performs no memory-mapped I/O whatsoever and has no callers in ghidra/callgraph.json ("callers": []). A near-identical sibling, FUN_083775cc, is the signed-division variant of the same compiler runtime cluster (0x083755e2–0x08377664). This strongly indicates the trace-seeding heuristic that produced save_related_functions.c mis-tagged a compiler runtime helper as save-I/O-related; it is not evidence of a save driver.

What was proven (from the real .sav bytes directly, independent of the Ghidra corpus):

  • The capture saves/cap-00-future-0.sav is exactly 32,768 bytes (0x8000), consistent with a 32 KB battery-backed SRAM/FRAM part, and matches the declared SDK tag SRAM_V113@8901780 in the packet metadata (CONFIRMED_STATIC via size + SDK tag correlation — not proven by decompiled code).
  • Bytes 0x0000–0x0009 hold the ASCII literal MUSHI_VER9 — almost certainly a save-format/version signature written by the game's own save code.
  • Six other 4-byte little-endian fields exist, at a constant stride of 0x328 (808) bytes, starting at offset 0x330: 0x330, 0x658, 0x980, 0xca8, 0xfd0, 0x12f8. Every other byte in the 32 KB image is 0x00.
  • These six 4-byte values, read as IEEE-754 float32, form a monotonically increasing arithmetic progression with an exactly constant raw-bit delta of 643168 between consecutive entries (verified below in Python). This is a strong, reproducible structural signal, but its semantic meaning (per-slot timestamp, tick counter, generation/sequence stamp, or test-harness artifact) is unknown — no decompiled code was available to confirm which field this is or what writes it.

What remains open: No save writer, reader, serializer, or checksum routine was identified anywhere in the provided decompiled corpus. No checksum/CRC field was found in the .sav file (every byte outside the 7 ranges above is zero, so there is nothing to validate a checksum formula against). No RAM mirror address (0x02xxxxxx/0x03xxxxxx) could be tied to any field because no save-write call site exists in the corpus. All layout conclusions below come exclusively from direct analysis of the .sav bytes, not from code.

3. Save Writer, Reader & Caller-Chain Architecture

No save-specific writer, reader, serializer, or checksum function was identified in ghidra/decompiled.c or ghidra/callgraph.json.

Methodology used to search (all negative):

  1. Text search of ghidra/decompiled.c for SRAM, EEPROM, FLASH, flash, sram, eeprom, the literal MMIO addresses 0x0E000000/0x0D000000/0x040000D4, and the DMA3 control address — zero hits.
  2. Inspection of the single seed function flagged in ghidra/save_related_functions.c:
  • FUN_08377664 ([MMIO-SEED], "callers: none") — body is a 32-bit unsigned software division/remainder routine (shift-and-subtract restoring division, classic compiler-runtime __udivsi3-style implementation). It calls FUN_08377660 only when param_2 == 0 (divide-by-zero trap: FUN_08377660 is a one-instruction return; stub). No MMIO, no SRAM/Flash bus access, no struct field writes.
  • ghidra/callgraph.json["0x08377664"] confirms "callers": [] — this function is unreferenced by anything else in the traced corpus, i.e. the trace that produced this packet never actually observed a call into it from game code. It should not be treated as a real "save bus" entry point.
  • The adjacent FUN_083775cc (signed division/modulo, same code-shape, also 0 callers/0 callees per the callgraph) and the whole 0x083755e2–0x08377664 address cluster is consistent with a compiler math-runtime block (likely AGBSDK math library), not game-specific save logic.
  1. Full scan of all 99 decompiled functions' addresses/signatures in ghidra/decompiled.c for anything resembling a serialization loop (bulk byte copy against a save-sized buffer, 0x5555/0x2AAA Flash command-sequence constants, or a DMA3 EEPROM bit-serial loop) — none found. The 99 functions in this corpus are dominated by sound-engine/graphics/VBlank-handler style code (e.g. FUN_08000470, FUN_08000640 manipulate joypad/IRQ flag words; the 0x0807xxxx–0x0808xxxx block looks like audio-mixer/DMA-channel control; 0x08375xxx-0x08377xxx is the math/runtime cluster described above).

Conclusion: the trace that seeded this packet did not capture the actual save-write code path (whatever triggered the capture of cap-00-future-0.sav did not pass through any function present in this 99-function corpus). No caller chain, no RAM-mirror struct, and no field-level writer/reader mapping can be produced from code evidence for this release. This must not be conflated with "no save writer exists" — it only means this specific trace-guided corpus does not include it. A fresh, broader Ghidra pass (whole-ROM, not trace-seeded) or a trace that specifically brackets the save/write menu action would be required to locate the real I/O driver.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature — CONFIRMED_VERIFIED (bytes only; not tied to code)

  • Offset 0x0000, size 10 bytes, ASCII "MUSHI_VER9" (4d 55 53 48 49 5f 56 45 52 39), followed by zero padding to at least offset 0x0010.
  • verified_in_sav: true (read directly from saves/cap-00-future-0.sav).
  • verified_in_code: false — no function in ghidra/decompiled.c constructs or compares this literal (it is pure data; the decompiled corpus contains no .rodata/string-literal cross-references and no function in the available trace touches these bytes).

4.2 Checksum / integrity field — UNKNOWN (none found)

No byte range in the 32 KB image is populated besides the 7 ranges listed in §2. Since every candidate "record" consists of exactly one non-zero 4-byte value and otherwise all-zero padding, there is no second field anywhere that could serve as a stored checksum/CRC over that record to test a formula against. No checksum algorithm, therefore, could be derived or verified from this capture.

4.3 Verification performed against the real .sav bytes

The following Python was run directly against saves/cap-00-future-0.sav to independently re-derive the active byte ranges (not trusting the pre-computed saves/hexdump_and_diffs.txt, which — note for the record — omits the hexdump line for the 7th range at 0x12f8 even though it lists "Active ranges (7)"; the script below recovers all 7 directly from the binary):

import struct, hashlib

data = open("saves/cap-00-future-0.sav", "rb").read()
assert len(data) == 32768
assert hashlib.sha256(data).hexdigest() == (
    "f0ca7b45b8663b198fdbfbfe20d956a88771e60cb245191fe543d7517941a819"
)

nonzero = [i for i, b in enumerate(data) if b != 0]
ranges, start, prev = [], nonzero[0], nonzero[0]
for i in nonzero[1:]:
    if i != prev + 1:
        ranges.append((start, prev))
        start = i
    prev = i
ranges.append((start, prev))

for s, e in ranges:
    print(hex(s), hex(e), data[s:e+1])

Interpreting the six 4-byte fields as little-endian IEEE-754 float32 and as raw little-endian uint32, and checking the deltas between consecutive records:

vals = [
    (0x330, b'J\xd9\xc7<'), (0x658, b'\xaa\xa9\xd1<'), (0x980, b'\nz\xdb<'),
    (0xca8, b'jJ\xe5<'),    (0xfd0, b'\xca\x1a\xef<'), (0x12f8, b'*\xeb\xf8<'),
]
u32s = [struct.unpack('<I', b)[0] for _, b in vals]
f32s = [struct.unpack('<f', b)[0] for _, b in vals]
print("float32:", f32s)
print("uint32 :", u32s)
print("deltas :", [u32s[i+1] - u32s[i] for i in range(len(u32s)-1)])

Finding (CONFIRMED_VERIFIED, bytes-only): the raw-uint32 delta between every consecutive record's 4-byte field is exactly 643168, with zero deviation across all 5 gaps. This is too precise to be coincidental zero/garbage data; it is a genuine structural property of this save image. As float32 it reads as a smoothly, monotonically increasing value in the ~0.024–0.030 range per record. No code evidence ties this to a semantic meaning (elapsed time, frame/tick counter, per-slot generation stamp, or an artifact of however cap-00-future-0.sav was produced by the capture harness) — flagged as a HYPOTHESIS field in §5, not a confirmed semantic field.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss emulator save states are present in this workspace (states/ is empty) — the mutations below are proposed for the next capture round, once gameplay.ss / final.ss / paired pre/post .ss states exist for this release, per the paired-state capture requirement.

  1. Header-signature mutation. Flip one byte of "MUSHI_VER9" at offset 0x0000 (e.g. 0x39→0x38, "VER9"→"VER8"). Reload from the corresponding pre-save .ss. Prediction: if this is a true format/version gate, the game will treat the save as invalid/corrupt (reset to new-game, show a corrupt-save prompt, or silently reinitialize); if it's cosmetic/unchecked, no observable difference. Either outcome narrows confidence on whether the header string is actually validated by a reader.
  1. Record-field zeroing. Zero out the 0x0330 4-byte field only (leave the other five records untouched) and reload. Prediction: if this field drives slot selection/ordering (e.g. "most recent" by progression value), the game should now treat another record as newest/primary, or show record 0 as blank/default. If nothing changes, the field is either purely cosmetic, unread at this point in the game, or the selection logic depends on a different field not yet identified.
  1. Constant-delta continuation probe. Compute the next value in the arithmetic progression (u32 = 1022946090 + 643168 = 1023589258, little-endian bytes 8a4bfd3c) and write it at a new record position at 0x12F8 + 0x328 = 0x1620, leaving all 32,516 trailing zero bytes otherwise untouched. Reload. Prediction: if the format supports more than 6 records and simply reads "the furthest non-zero/highest-value record," a 7th slot should now appear active in-game; if the format hard-caps at 6 records, this write should be ignored or treated as out-of-bounds/corrupt.
  1. Full-record zero vs. full-record fill (0xFF) at one slot. Separately test zeroing an entire 808-byte record (including its float field) and filling an entire record with 0xFF. Prediction: distinguishes "zero = empty/unused slot" (expected, matches the observed fill byte) from "0xFF = empty/unused slot" (common alternate convention for Flash-backed saves) — this directly tests the fill_byte assumption in save-format.json.
  1. Checksum-repair rehearsal (blocked). Not currently runnable: no checksum/CRC field was identified anywhere in the capture (§4.2), so there is no repair step to script yet. This item should be revisited once a broader (non-trace-seeded) Ghidra pass locates the actual save writer, or once a second .sav capture at a different play state reveals a field whose value changes in a way consistent with a checksum over the rest of the record.
  1. Primary follow-up before further fuzzing: re-run Ghidra decompilation on the full ROM (or re-seed the trace specifically around the in-game save/write-to-cartridge menu action) to recover the actual SRAM/Flash/EEPROM I/O driver and its callers — all of §3 is currently empty because this corpus's trace never captured that code path. Fuzzing byte offsets without first confirming which function reads them back risks drawing conclusions from in-game UI side effects that could have multiple explanations.

Aggregate screenshot/state budget for any follow-up capture round: ≤8 screenshots, ≤4 save states per job, per standing operational guardrails.
