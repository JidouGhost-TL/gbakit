Save Format Report — Super Bubble Pop (Europe) (AVZP-r0-112e947f0f677167)

Clean-room analysis derived exclusively from this workspace's saves/*.sav binaries, ghidra/decompiled.c (36 trace-guided functions), ghidra/callgraph.json, and ghidra/save_related_functions.c, plus standard public GBA hardware facts (EEPROM at 0x0D000000 via DMA3 0x040000D4, EWRAM 0x02000000, IWRAM 0x03000000). No third-party game-specific source was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + .sav bytes agree):

  • Save media is a 512-byte (4Kbit) EEPROM device, accessed 8 bytes per block, through a

bit-serial DMA3 protocol.

  • The game only ever reads/writes the **first 48 of the 64 available 8-byte EEPROM

blocks** (384 bytes / 0x180), leaving the remaining 128 bytes (0x180–0x1FF) permanently at the erased fill value (0xFF) in both captured snapshots.

  • The payload begins with an 8-byte, two-word signature pair whose second word reads as

ASCII SPBS (full ASCII window across the file is <PSPBS).

  • The low-level EEPROM 8-byte block-read primitive (FUN_080177b4) and its DMA3

trigger helper (FUN_08017734) are fully decompiled and match the textbook GBA software EEPROM-read bitstream shape (serialize block address as 1-bit stream, DMA it out to 0x0D000000, DMA 68 response bits back in, unpack 4×16-bit words).

  • The high-level load entry point FUN_08000214 and save entry point FUN_080003f0

are fully decompiled and show a symmetric allocate → clear → device-select → 48×8-byte block I/O → validate-two-magic-words → copy-out-subfields pipeline (load), and the mirrored pack-fields → write-48-blocks pipeline (save).

What remains open / unproven:

  • The link between the high-level loop in FUN_08000214/FUN_080003f0 (which calls

through unresolved function pointers pcRam080003cc/pcRam080005d4 etc.) and the decompiled raw driver FUN_080177b4 is a behavioral match, not a static call-graph edge — ghidra/callgraph.json shows no direct caller recorded for 0x080177b4. This is flagged explicitly everywhere it matters below.

  • No checksum/CRC routine over the 360-byte body was found anywhere in the 36 provided

functions. The only integrity gate visible in code is a two-word magic compare; one of the two comparison values is produced by an unresolved indirect call (pcRam080003d4/pcRam080005d0), so we cannot prove from static code alone whether that word is a fixed constant, a device/region ID, or something checksum-like. Python verification (below) found no simple sum/xor/CRC over the body that reproduces any stored field, which is consistent with "no body checksum exists."

  • The semantic meaning of the 360-byte record table (field-by-field) is a

data-pattern hypothesis only — it was not derived from any external game guide or decomp, purely from repeated structural analysis of the two .sav snapshots, and must be treated as unverified until corroborated by a controlled save-mutation + reload experiment (Section 6).

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Low-level hardware I/O driver (CONFIRMED_STATIC from decompiled code)

FUN_080177b4 (0x080177b4, thumb) — EEPROM 8-byte block read primitive. Marked [MMIO-SEED] in ghidra/save_related_functions.c (no direct callers recorded in the trace-guided callgraph).

param_1 = block address (masked to 16 bits)
if (param_1 < <max_block_count>) {
    // serialize block address into a 1-bit-per-ushort stream in auStack_96[],
    // preceded by two "1" start bits
    FUN_08017734(auStack_98, 0x0D000000, <bitcount>+3);   // DMA OUT: send read command+address
    FUN_08017734(0x0D000000, auStack_98, 0x44);            // DMA IN: read back 68 response bits
    // unpack 4 × 16-bit big-endian-ordered words (1 bit at a time) into param_2[0..7]
}

This is the canonical GBA software EEPROM-read bitstream: write a start-bit + 1-bit read-opcode + N address bits to the EEPROM MMIO window at 0x0D000000, then clock in a 4-bit dummy preamble + 64 data bits (68 total, matching the 0x44 = 68 passed to the second FUN_08017734 call), producing one 8-byte (4×u16) block in param_2.

FUN_08017734 (0x08017734, thumb) — generic DMA3 transfer trigger. Sets up source/dest/count+control through RAM-mirrored MMIO pointers and busy-polls a status word before returning; functionally equivalent to a DMA3 (0x040000D4-class) blocking transfer helper. Called twice by FUN_080177b4 (once to send the read request, once to receive the response), and is the only function in the provided decompilation that drives the EEPROM bus directly.

No raw EEPROM write-block primitive is present anywhere in the 36 decompiled functions. This is an open question (Section 7) — the write path almost certainly exists as a twin of FUN_080177b4 but was not captured by this trace-guided extraction.

3.2 High-level load / save entry points (CONFIRMED_STATIC)

FUN_08000214(int param_1) — load/restore entry point.

  1. Lazily allocates a 384-byte (0x180) heap buffer (*piRam080003b0) via

pcRam080003ec(0x180, uRam080003e8, 0x276) and zero-fills it with FUN_080001f0.

  1. pcRam080003b4(4) — device select/init call (param 4, plausibly an EEPROM save-type

ID).

  1. pcRam080003c8(3, uRam080003c4) — secondary open/enable call.
  2. Loop uVar6 = 0..0x30: pcRam080003cc(uVar6, iVar4) reads one 8-byte block into the

buffer at iVar4, iVar4 += 8 each iteration. This loop is behaviorally identical to what FUN_080177b4 expects to be called with (block index, 8-byte destination), but the callgraph does not statically resolve pcRam080003cc to 0x080177b4 — the link is a HYPOTHESIS, not a confirmed call edge.

  1. Validates the loaded buffer: piVar7[0] == iRam080003d0 (first magic word vs. a

data-segment constant) and piVar7[1] == (*pcRam080003d4)() (second magic word vs. the return value of an unresolved indirect call).

  1. On success, copies out sub-fields: 1 byte at offset 8, 5 bytes at offset 9, 8 bytes

at offset 0xE, and 360 bytes (0x168) at offset 0x18 — into separate destination globals (puRam080003d8, uVar3, uRam080003e0, *puRam080003e4). These four copy lengths (1+5+8+360 = 374, plus the 8 header bytes already consumed = 382 bytes) line up almost exactly with the 382 changed bytes observed between the two .sav snapshots (the 2 untouched bytes are the offset-0x10 gap, which sits between the 5-byte and 8-byte copies — see Section 5).

  1. On any failure, calls an error-handler function pointer (pcRam080003bc).

FUN_080003f0(int param_1) — save entry point, the mirror image of the above: allocates/zeroes the same 384-byte buffer, writes the fixed fields back in (byte at offset 8, 5 bytes at offset 9, 8 bytes at offset 0xE, 360 bytes at offset 0x18), stores a magic word via uRam080005c0 at offset 0 and a second, dynamically-produced word via pcRam080005d0() at offset 4, then loops uVar6 = 0..0x30 calling pcRam080005d4(uVar6, iVar2) (write block) with a fallback/retry call to pcRam080005d8(uVar6, iVar2) on failure, advancing by 8 bytes per block — the exact write-side twin of the read loop in FUN_08000214.

3.3 Caller chains

ghidra/callgraph.json records no callers for FUN_08000214, FUN_080003f0, or FUN_080177b4 among the 36 extracted functions — all three are reached only through function-pointer tables that this trace-guided extraction did not resolve. This means the "who triggers a save/load" question is UNKNOWN from the evidence in this workspace; we can only state what happens once these entry points run, not what gameplay event invokes them.

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

Offsets 0x00–0x07 of the active payload, both as raw bytes and as the two 32-bit words compared in FUN_08000214:

offset  00 01 02 03 04 05 06 07
bytes   00 00 3c 50 53 50 42 53
ascii   .  .  <  P  S  P  B  S
  • Word A (offset 0x00, 4 bytes, LE): 0x503C0000 — compared in code against

iRam080003d0 (a data constant whose literal value is not resolvable from the provided decompilation; it is UNKNOWN statically, but CONFIRMED_VERIFIED as present/matching in the one successful .sav sample).

  • Word B (offset 0x04, 4 bytes, LE): 0x53425053, which reads as ASCII "SPBS" in

byte order — compared in code against the return value of an unresolved indirect call (*pcRam080003d4)(). Given the symmetric structure (word A is a plain stored constant, word B's write-side counterpart in FUN_080003f0 is also a function-call result pcRam080005d0()), the most parsimonious reading is that this is a fixed signature accessor, not a variable checksum — but this is a HYPOTHESIS, since we cannot see inside the indirect call.

4.2 Checksum / integrity algorithm

No sum/XOR/CRC/complement checksum routine exists anywhere in the 36 decompiled functions. The only integrity gate on load is the two-magic-word compare described above. Python verification against the body (offsets 0x18–0x17F, 360 bytes) of the one populated sample confirms no simple candidate reproduces any stored value elsewhere in the file (there is no "stored checksum field" to match against, since none was located):

$ python3 - <<'EOF'
body = open('saves/cap-01-future-1.sav','rb').read()[0x18:0x180]
sum8  = sum(body) & 0xff        # -> 0x52
xor8  = 0
for b in body: xor8 ^= b        # -> 0x9a
EOF

Output: sum8(body) = 0x52, xor8(body) = 0x9a — neither value appears stored anywhere in the 512-byte file. Conclusion: integrity is magic-word-only; confidence CONFIRMED_STATIC that no body checksum exists in this trace-guided decompilation, with the caveat that an undiscovered function outside the 36 extracted could still implement one (see open questions).

5.1 Structural hypothesis for the 360-byte record table (0x18–0x17F)

Byte-pattern analysis (no external source) shows this span tiles into three 120-byte segments (0x18–0x8F, 0x90–0x107, 0x108–0x17F), each internally divided into ten 12-byte slots. Supporting evidence: the byte value 0x28 recurs at absolute offsets 0x25, 0x9D, 0x115 — exactly 120 bytes apart — and each 120-byte segment contains a monotonically-descending counter sequence 0x28, 0x24, 0x20, 0x1C, 0x18, 0x14, 0x10, 0x0C, 0x08, 0x04 (step -4, 10 values) in the second byte of alternating 4-byte words.

Within each 12-byte slot, the first 4-byte word frequently decodes as a clean

big-endian u32 round number when read as 00 XX XX XX/00 0X XX XX (e.g. 00 04 93 e0 = 300,000; 00 0f 42 40 = 1,000,000; 00 03 a9 80 = 240,000), and the following 8 bytes decode as two space-padded 3/4-character ASCII tags (" US", " MD", "CIR", "CMS", "BOB", "KIM", "ZEJ", "MOT", "NOJ", "DOR", "WMR", "VEK", "TLD", "W R", "RQ"). This is consistent with a score/leaderboard-style table with big-endian numeric fields and 2–3 character player/region tags, repeated across three parallel tables (plausibly three difficulty tiers or game modes) — this entire paragraph is a data-driven HYPOTHESIS, not a verified field map, and must not be treated as accepted semantics. Confidence: HYPOTHESIS.

7. Open Questions

  1. The true caller(s) that invoke FUN_08000214 (load) and FUN_080003f0 (save) are

unresolved function pointers outside the 36 extracted functions — triggering gameplay events are unknown.

  1. The raw EEPROM write-block primitive (twin of FUN_080177b4) was not present in

this extraction; its address and exact bitstream shape are unknown.

  1. The literal expected value of magic word A (iRam080003d0) and the exact semantics

of the indirect-call-derived magic word B are unknown — we only know they must equal the stored header words 0x503C0000/0x53425053 for a load to succeed.

  1. The internal field typing of the 360-byte record table (Section 5.1) is an

unverified structural hypothesis pending the fuzzing plan in Section 6.

  1. Only one populated .sav snapshot was available, so no second-save-event diff

exists to confirm which header sub-fields (the 0x08, 0x09–0x0D, 0x0E–0x15 spans) actually vary between distinct game states versus being fixed constants for this particular save slot's content.
