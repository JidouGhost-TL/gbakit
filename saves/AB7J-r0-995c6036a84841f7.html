1. Executive Summary & Overall Confidence

Overall confidence: MEDIUM.

What is proven (code + byte evidence agree):

  • The save medium is plain byte-addressable SRAM at 0x0E000000, written with simple byte-copy

loops guarded by a SRAM wait-state register write (*_DAT_0802cbe0 |= 3). There is no Flash command sequence (0x5555/0x2AAA) and no EEPROM DMA3 bitstream (0x040000D4) anywhere in the 246-function decompiled corpus — this independently confirms the PACKET's SRAM 256K media classification from the code side.

  • There are exactly two low-level "record save" primitives, FUN_08022b24 (fire-and-forget,

unverified write) and FUN_08022b88 (checksummed, write-with-verify-and-retry×3). Both funnel through a shared 8-bit additive checksum routine, FUN_08022ae0.

  • The one non-blank 110-byte record actually present in saves/cap-01-future-1.sav

(offsets 0x301c–0x3089) is a FUN_08022b88-style record: a 28-byte (0x1c) header immediately followed by an 82-byte (0x52) payload, and its stored checksum byte

verifies exactly against a from-scratch Python recomputation of the documented algorithm (see §4). This is the strongest result in this report.

  • The call site that produced this exact record, FUN_0801df08, is identified and traced:

it zero-fills an 82-byte RAM payload buffer, then calls FUN_08022b88(slot=1, fresh=0, buf, 0x52) — matching the observed header length, payload length, and all-zero payload bytes byte-for-byte.

What remains open / unresolved:

  • Neither FUN_08022b24 nor FUN_08022b88 (nor their only identified callers, FUN_08007ab4

and FUN_0801df08) has any caller in the static call graph (callgraph.json lists "callers": [] for all four). Every one of them is reached only through an "UNRECOVERED_JUMPTABLE"/indirect-call site that Ghidra could not statically resolve. This means we have not identified the in-game trigger (menu action, autosave timer, state-machine dispatch) that invokes a save. This is a real, acknowledged gap, not an oversight. from a fresh/default template buffer during normal gameplay.

  • We only have two .sav snapshots (one fully blank, one with a single populated record), so

slot/redundancy structure, the meaning of most header fields, and the behavior of the param_2 != 0 ("reuse existing record") code path in FUN_08022b88 are all unverified by byte evidence — they are static-code-only or pure hypothesis, and are labeled as such below.

  • No ASCII magic string exists anywhere in either .sav file (confirmed by direct byte scan);

the PACKET's ascii_magic_strings: [] is independently confirmed.

3. Save Writer, Reader & Caller-Chain Architecture

3.1 Checksum primitive — FUN_08022ae0 (0x08022ae0)

void FUN_08022ae0(int param_1,int param_2,uint param_3)
{
  char cVar1 = '\0';
  uint uVar2 = 0;
  do {                                   // sum first 0x1c (28) bytes of header @ param_1
    cVar1 = cVar1 + *(char *)(param_1 + uVar2);
    uVar2 = (uVar2 + 1) & 0xffff;
  } while (uVar2 < 0x1c);
  uVar2 = 0;
  if ((param_3 & 0xffff) != 0) {         // then sum param_3 bytes of payload @ param_2
    do {
      cVar1 = cVar1 + *(char *)(param_2 + uVar2);
      uVar2 = (uVar2 + 1) & 0xffff;
    } while (uVar2 < (param_3 & 0xffff));
  }
  (*UNRECOVERED_JUMPTABLE)(cVar1);        // returns cVar1 (8-bit wraparound sum) via indirect return thunk
}

Callers (from callgraph.json): 0x08022b24, 0x08022b88 — the two writer primitives below. No other function calls this routine. Role: checksum (unsigned 8-bit additive sum, header then payload, wraparound on overflow).

3.2 Writer A (unverified, "fast") — FUN_08022b24 (0x08022b24)

void FUN_08022b24(uint param_1,undefined4 param_2,undefined2 param_3)
{
  uVar1 = _DAT_08022b74;                                     // ROM/RAM header template pointer
  iVar3 = *(int *)((param_1 & 0xff) * 4 + _DAT_08022b70);    // slot-id -> SRAM base offset
  func_0x0802cb44(iVar3 + 0xe000000, _DAT_08022b74, 0x1c);   // raw-copy 28B header -> SRAM[iVar3]
  func_0x0802cb44(iVar3 + _DAT_08022b78, param_2, param_3);  // raw-copy payload -> SRAM[iVar3+headerSize]
  cVar2 = FUN_08022ae0(uVar1, param_2, param_3);             // checksum computed but NOT stored anywhere observed
  (*UNRECOVERED_JUMPTABLE)(cVar2 == -1);                      // only used as a boolean "all-0xFF?" status flag
}
  • Only identified caller: FUN_08007ab4 (0x08007ab4), which calls

func_0x08022b24(0, 0x2000000, 0x3000) — slot 0, source = EWRAM 0x02000000, size 0x3000 (12,288 bytes). This is a bulk raw mirror of a large EWRAM buffer straight into SRAM, with no checksum persisted.

  • How mapped: found by grep-ing decompiled.c for literal references to

08022b24/08022b88 (the two save-write addresses); this was the only call site found for the first symbol.

  • How it mutates RAM before flushing: FUN_08007ab4 itself does no mutation — it is a thin

wrapper that only forwards a pre-existing EWRAM buffer. Nothing in the traced corpus shows who populates that EWRAM region; that producer is outside the 246-function trace set.

  • Byte evidence: NONE. Neither .sav file shows any write consistent with a 12,288-byte

bulk SRAM write (the entire file outside the 110-byte window is untouched 0xFF). This path is CONFIRMED_STATIC only — plausibly unexercised during the captured session, or its destination table entry (_DAT_08022b70[0]) points somewhere we have not sampled.

  • FUN_08007ab4 itself has no caller anywhere in callgraph.json — it is only reachable via

an unresolved indirect/jumptable dispatch.

3.3 Writer B (checksummed, verified, retried) — FUN_08022b88 (0x08022b88)

void FUN_08022b88(uint param_1,int param_2,undefined4 param_3,undefined2 param_4)
{
  puVar1 = _DAT_08022bf4;                 // fixed global 28-byte header staging buffer
  *_DAT_08022bf4 = 0;                      // zero header bytes [0..3]
  puVar1[0x17] = 0;                        // zero the checksum byte before computing it
  if (param_2 == 0) {                      // "fresh record" flag
    func_0x0802e77c(puVar1 + 1, _DAT_08022bf8, 0x16);   // memcpy 22B ROM default template -> header[1..22]
  }
  bVar2 = FUN_08022ae0(puVar1, param_3, param_4);        // checksum(header[0..27] w/ byte23==0, payload)
  puVar1[0x17] = ~bVar2;                                 // store ONE'S COMPLEMENT at header byte offset 0x17 (23)
  iVar5 = *(int *)((param_1 & 0xff) * 4 + _DAT_08022bfc); // slot-id -> SRAM base offset (separate table from Writer A)
  cVar3 = func_0x0802cc7c(puVar1, iVar5 + 0xe000000, 0x1c);                 // write+verify+retry(x3) header
  if (cVar3 == 0 && (cVar3 = func_0x0802cc7c(param_3, iVar5 + _DAT_08022c00, param_4), cVar3 == 0))
    uVar4 = 1; else uVar4 = 0;             // uVar4 = overall success flag
  (*UNRECOVERED_JUMPTABLE)(uVar4);
}
  • Only identified caller: FUN_0801df08 (0x0801df08):
  void FUN_0801df08(void)
  {
    uVar1 = _DAT_0801df28;                       // RAM payload buffer pointer
    func_0x0802e864(_DAT_0801df28, 0, 0x52);     // memset(buf, 0, 82) — zero-fill the payload
    func_0x08022b88(1, 0, uVar1, 0x52);          // slot=1, fresh=0 (use template), payload=buf, size=82
  }
  • How mapped: same literal-reference grep as above; this was the only call site found for

08022b88.

  • How it mutates RAM before flushing: FUN_0801df08 zero-fills the 82-byte payload buffer

at _DAT_0801df28 with FUN_0802e864 (a memset-style primitive — word-at-a-time when 4-byte aligned, byte fallback otherwise) immediately before invoking the writer. It does not otherwise populate the buffer in this traced path, i.e. this call site always saves an

all-zero payload together with the ROM default template header.

  • Byte evidence — exact match: this is the call that produced the real 110-byte record in

saves/cap-01-future-1.sav. See §4 for the full verification. The payload bytes 0x3038–0x3089 are all 0x00, matching the memset(buf,0,0x52) call exactly; the header length (28 bytes, 0x301c–0x3037) matches the 0x1c constant used by FUN_08022b88.

  • FUN_0801df08 itself has no caller in callgraph.json — same jumptable-dispatch gap as

FUN_08007ab4.

4. Magic Signatures & Checksum / Integrity Algorithm — Python-Verified

No ASCII/binary magic signature exists. A full-file byte scan of both .sav files found no fixed marker string; the only "magic-like" bytes are the checksum below and two template constants (0x301c, 0x401c) that read back as little-endian u16s but are not validated as pointers against any other part of the file (see §2).

Algorithm: sum8 with one's-complement storage.

  • Covered range: 28-byte header (with the checksum byte itself treated as 0 during the sum)

plus the full variable-length payload that follows it.

  • Formula: stored_byte = (~(sum(header_bytes_with_csum_byte_zeroed) + sum(payload_bytes))) & 0xFF
  • Equivalently, as an integrity check on a loaded record: `(sum(header_bytes_as_stored) +

sum(payload_bytes)) & 0xFF == 0xFF` for any valid record.

  • Stored offset: header-relative 0x17 (decimal 23), i.e. absolute file offset record_base + 0x17.
  • Endianness: not applicable (byte-wise sum, no multi-byte checksum field).
  • Decompiled-C proof: FUN_08022ae0 (checksum computation, §3.1) + puVar1[0x17] = ~bVar2;

in FUN_08022b88 (storage, §3.3).

Python verification against the real saves/cap-01-future-1.sav:

$ python3 - <<'EOF'
data = open('saves/cap-01-future-1.sav','rb').read()
base = 0x301c
HEADER_LEN, PAYLOAD_LEN, CSUM_REL = 0x1c, 0x52, 0x17

header  = bytearray(data[base:base+HEADER_LEN])
payload = data[base+HEADER_LEN:base+HEADER_LEN+PAYLOAD_LEN]
stored  = header[CSUM_REL]

header[CSUM_REL] = 0
computed_sum  = (sum(header) + sum(payload)) & 0xff
computed_csum = (~computed_sum) & 0xff

print("stored checksum byte  @0x3033:", hex(stored))          # -> 0x15
print("computed one's-complement csum:", hex(computed_csum))  # -> 0x15
print("MATCH:", computed_csum == stored)                      # -> True
print("sanity total (incl. stored byte) mod 256:",
      hex((sum(data[base:base+HEADER_LEN]) + sum(payload)) & 0xff))  # -> 0xff
EOF
stored checksum byte  @0x3033: 0x15
computed one's-complement csum: 0x15
MATCH: True
sanity total (incl. stored byte) mod 256: 0xff

Result: CONFIRMED_VERIFIED. The checksum algorithm derived purely from the decompiled C (FUN_08022ae0 + FUN_08022b88) exactly reproduces the stored byte in the real .sav file, and the "total sum ≡ 0xFF" invariant holds, which is the expected signature of a zero-the-checksum-byte / sum / one's-complement scheme.
