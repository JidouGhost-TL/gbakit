1. Executive Summary & Overall Confidence

Overall Confidence: MEDIUM

Proven (code + .sav bytes agree)

  • The save medium is EEPROM, 512 bytes total (marketed as "EEPROM 4K" = 4 Kbit), organised as 64 blocks of 8 bytes. The low-level driver (FUN_0804246c read / FUN_08042530 write) transfers exactly 4× u16 (64 bit) per block over DMA3 to 0x0D000000, matching the 512 B .sav files byte-for-byte in size.
  • The .sav file stores every 8-byte EEPROM block byte-reversed relative to the in-RAM image. Reversing each block turns the raw .sav header 2100TBOR into the RAM magic ROBT0012 and simultaneously makes the header checksum validate (see §4). This transform is independently motivated by the driver code, which assembles/disassembles each 64-bit block MSB-first into descending u16 slots (FUN_0804246c, FUN_08042530).
  • Layout: one 32-byte global header (EEPROM blocks 0–3, .sav 0x00–0x1F) followed by three independent 160-byte save slots (blocks 4–23, 24–43, 44–63; .sav 0x20–0xBF, 0xC0–0x15F, 0x160–0x1FF). Block arithmetic is explicit in code: slot load is FUN_0802fa34(slot*0x14 + 4, 0x14, buf) (FUN_0802f91c), i.e. start block 4 + 20·slot, count 20 blocks = 0xA0 bytes.
  • Header integrity is a 16-bit additive checksum: the sum (mod 2¹⁶) of all sixteen u16_le words of the RAM header must be 0; the last word (RAM offset 0x1E) is stored as the two's-complement negation of the sum of the first fifteen. Verified on both samples (§4): stored 0xF8EE / 0xF86E, computed identical, sum 0x0000.
  • Header validation (FUN_0802f56c) additionally requires the 8-byte magic match. On failure at boot, FUN_0802f5c8 recreates a blank header from a ROM template (FUN_0802f9f4) and blanks the first 24 bytes of each slot — exactly the state both samples are in (24 zero bytes + 0xFF tail per slot).
  • The only header byte observed to change between the two captures is RAM offset 0x08 (.sav offset 0x0F): 0x00 → 0x80, with the checksum compensating by −0x80. This is the language/flags byte: low 7 bits are consumed as a language index (FUN_0802f5c8 → FUN_08039120(byte & 0x7F)), and FUN_0802f618 rewrites it as (old & 0x80) | (lang & 0x7F) | 0x80 before FUN_0802f968 flushes the header. The observed change sets bit 7 while the language stays 0.

Static-only (code proves it, no sample exercises it)

  • Per-slot integrity uses the same additive u16 checksum over the full 160 bytes (FUN_0802f8ec → FUN_0802f9d0(buf, 0xA0), valid iff sum == 0). Both samples contain only empty/invalid slots (sum 0xFFBC ≠ 0), so no valid slot payload could be field-mapped.
  • Slot-list construction (FUN_0802f898), header flush-on-change (FUN_0802f968), and the language-change entry (FUN_08020ca0) are fully traced in code but produce no distinct bytes in this corpus beyond the header byte above.

Open / unknown

  • No valid (populated) save slot exists in the corpus. All in-slot gameplay fields (progress, level, timers, inventory, etc.) are therefore UNKNOWN. Both captures are post-initialisation blank saves differing only in the header flags byte.
  • The gameplay slot-writer was not present in the trace-guided decompilation. Writes of a full 20-block slot (FUN_0802fa90(start, 0x14, buf)) never occur in the 294 functions; only header writes (4 blocks) and blank-slot prefix writes (3 blocks) do. The slot save path (recompute checksum at slot +0x9E, then write 20 blocks) is a symmetric inference, marked HYPOTHESIS.
  • Absolute RAM addresses of the save struct are not recoverable from the C dump. Ghidra emits literal-pool symbols (_DAT_0802f59c, …) whose values (the 0x02xxxxxx/0x03xxxxxx targets) are not included in decompiled.c. Struct-relative offsets (+0x08, +0x20, +0x24 + 0x18·i, +0x6C, +0x7C) are known; the base is not. All ram_addr entries are therefore null with the offset documented in the evidence text.
  • Caller edges above the save-manager roots are missing: FUN_0802f5c8 and FUN_08020ca0 have no callers in callgraph.json. They are reached through unrecovered jump tables / function-pointer state machines (UNRECOVERED_JUMPTABLE tail calls terminate nearly every function in this dump), so the menu/boot trigger context is inferred, not proven.

Redundancy, counters, selection rule

  • No mirroring / backup copy exists. There is exactly one header and one copy of each slot. The three slots are three independent saves, not redundant copies of one save: they are loaded and validated individually (FUN_0802f898 loops slot = 0..2).
  • No generation/sequence counter was found. No field in the header increments across the two captures except the flags byte at RAM +0x08 (bit 7 set, value change +0x80 exactly compensated by the checksum). Header words at RAM +0x0A..+0x1D are constant (FF FF 00 00 01 1E 00, then zeros) and match a fixed ROM template copied by FUN_0802f9f4 (FUN_08024610(dst, template, 0x20)), i.e. constants, not counters.
  • Selection rule (header): at boot FUN_0802f5c8 calls FUN_0802f56c, which reads blocks 0–3, requires (a) 16-word sum == 0 and (b) first 8 bytes equal to the template magic. If either fails, the header is recreated blank and all slot prefixes are blanked. There is no fallback copy to select.
  • Selection rule (slots): each slot is read into a freshly zeroed 0xA0 staging buffer (FUN_0802f91c) and validated by FUN_0802f8ec (full-buffer u16 sum == 0). Invalid slots have their 24-byte menu/cache entry zeroed (FUN_080245a4(entry, 0, 0x18)) and are presented as empty; valid slots set struct+0x7C = staging buffer, struct+0x80 = 0 and are parsed by func_0x08016604(entry) (not in this decompilation). Validity results are cached as booleans at struct+0x6C + 4·slot.
  • Observed state: both samples have a valid header and zero valid slots — consistent with a freshly initialised EEPROM photographed before any gameplay save, plus one language/flags confirmation (capture 01).

3. Save Writer, Reader & Caller-Chain Architecture

3.0 How callers were mapped (method)

Two evidence channels were combined, because neither is complete alone:

  1. ghidra/callgraph.json (294 nodes) records direct FUN_xxxxxxxx edges. It proves e.g. FUN_0802f5c8 → {FUN_0802443c, FUN_0802f56c} and FUN_0804246c → FUN_080423ec, FUN_08042690 → FUN_0804246c.
  2. Text references in ghidra/decompiled.c (func_0x080xxxxx(...) calls) capture edges the callgraph missed because the callee is a separate thumb candidate or the call crosses an unrecovered jump table. Every FUN_/func_ reference was extracted programmatically and cross-checked against the callgraph. Example: the callgraph lists FUN_0802fa34 with no callees, but its body calls func_0x0802fafc, func_0x0804246c, func_0x0802fb30 — those edges come from the text channel.

Nearly every function ends in (*UNRECOVERED_JUMPTABLE)(...) — Ghidra's rendering of a thumb tail-branch through a computed table. Edges that pass through those tables (including whoever calls the roots FUN_0802f5c8 and FUN_08020ca0) are not recoverable from this corpus and are reported as [root — caller not in corpus].

4. Magic Signatures & Checksum / Integrity Algorithm

4.1 Magic signature

  • RAM form (authoritative): ASCII ROBT0012 = bytes 52 4F 42 54 30 30 31 32 at RAM header offset 0x00–0x07.
  • .sav form (as stored): bytes 32 31 30 30 54 42 4F 52 (ASCII 2100TBOR) at .sav offset 0x00–0x07 — the per-block byte reversal of the RAM form.
  • Verified in code: FUN_0802f56c reads blocks 0–3 (FUN_0802fa34(0, 4, buf)), then byte-compares the first 8 bytes against the template bytes (iRam0802f5c0 vs iRam0802f5c4 loop, iVar2 < 8); FUN_0802f9f4 copies the 32-byte template containing this magic from ROM (FUN_08024610(dst, template, 0x20)) when recreating a blank header.
  • Verified in .sav: present verbatim at offset 0x00 in both samples.

4.2 Checksum algorithm (header — CONFIRMED_VERIFIED)

  • Algorithm: sum16_le (additive, mod 2^16; signed/unsigned equivalent). The header is treated as sixteen u16_le words in RAM byte order. The stored word is the two's-complement negation of the sum of the other fifteen, so the sum of all sixteen is 0.
  • Formula: stored = (0 - sum(words[0..14])) & 0xFFFF, equivalently sum(words[0..15]) == 0 (mod 65536).
  • Covered range: RAM header bytes 0x00–0x1D (words 0–14); stored at RAM offset 0x1E (word 15), size 2 bytes. In .sav coordinates the stored word's bytes land at offsets 0x18–0x19 (F8 EE / F8 6E) because of the block reversal.
  • Decompiled proof: FUN_0802f56c sums 16 words and requires sVar1 == 0 before the magic compare. FUN_0802f968: *(u16*)(hdr+0x1e) = 0; sVar1 = FUN_0802f9d0(hdr, 0x20); *(short*)(hdr+0x1e) = -sVar1;. FUN_0802f9f4: sums 16 words then _DAT_0802fa2c[0xf] = -sVar1 (word index 0xF = byte offset 0x1E). FUN_0802f9d0(buf, len) sums len>>1 shorts.

4.4 Slot checksum (CONFIRMED_STATIC, unverified on samples)

  • Same FUN_0802f9d0 core over the full slot: sum of u16_le over RAM slot 0..0xA0 must be 0. Code proof is validation-only: FUN_0802f8ec(i): valid = (FUN_0802f9d0(staging, 0xA0) == 0), cached at struct+0x6C+4*i, called from FUN_0802f898 after each FUN_0802f91c load.
  • By symmetry with the header, the stored word is inferred at RAM slot offset 0x9E (last word) as -sum(words[0..78]) — HYPOTHESIS for the stored offset (the writer is absent from the corpus; only the sum == 0 check is proven).
  • On both samples every slot sums to 0xFFBC != 0 (24 zero bytes + 136 0xFF bytes), i.e. all slots correctly classify as empty/invalid — consistent with the blanking written by FUN_0802f5c8. No sample validates, so the slot checksum is not byte-verified.

4.5 Negative results (what the integrity check is not)

  • Raw (non-reversed) .sav header sums to 0x02FD != 0; byte-sum (sum8) gives 0xFD. No CRC/XOR code path exists in the save cluster (the only checksum code is additive FUN_0802f9d0). The block-reversal decode is required and sufficient.
  • No second header copy, no per-block ECC, and no sequence counter participates in integrity.

6. Save Fuzzing & Counterfactual Verification Plan

All mutations are on copies of saves/cap-01-retained-3.sav (valid header, language byte 0x80). "Repair" means: decode blocks (reverse each 8 bytes), recompute the affected checksum in RAM order, re-encode. Reload with the mutated .sav, observe title/language menu, slot list, and the RAM staging buffer (heap allocation from FUN_0802443c(0xa0)).

Open questions

  1. What gameplay fields occupy a populated 160-byte slot (no valid slot exists in this corpus)?
  2. Where is the gameplay slot writer (absent from the 294 trace-guided functions), and does it store the slot checksum at RAM +0x9E?
  3. What is the absolute RAM base of the save struct (literal-pool values are not in the C dump), and what does func_0x08016604 parse from a valid slot?
  4. What does bit 7 of header byte +0x08 signify beyond being forced on by FUN_0802f618 (e.g. "language confirmed" vs "save initialised")?
  5. Who calls the roots FUN_0802f5c8 (boot) and FUN_08020ca0 (language change) through the unrecovered jump tables, and in what menu/boot state?
  6. Are header bytes RAM +0x09..+0x0F (FF FF 00 00 01 1E 00) pure template constants, or does any non-traced code path read them individually?
