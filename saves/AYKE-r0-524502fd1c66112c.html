1. Executive Summary & Overall Confidence

Overall Confidence: LOW

This is substantially a negative result and is reported as such, per the clean-room honesty rule.

  • The trace-guided Ghidra corpus for this title (ghidra/decompiled.c, 47 functions; ghidra/save_related_functions.c, 0 MMIO seeds) contains zero functions that reference any GBA backup-media hardware: no SRAM/Flash byte-copy loops, no Flash 0x5555/0x2AAA command-sequence writes, no EEPROM/DMA3 (0x040000D4) bit-serial transfer code, and no 0x0D000000/0x0E000000 address literals of any kind. A full-text scan of the decompilation for these patterns, checksum keywords, and the strings save/Save returned no matches.
  • The only two functions in the callgraph with no recorded callers (0x08006a48, 0x0800d862) are large dispatcher-style routines; the one portion inspected in detail (0x08006a48) calls FUN_08001e88(0x5000000, ...), i.e. it targets Palette RAM (0x05000000), not SRAM/Flash/EEPROM — consistent with a menu/UI cursor-navigation routine, not a save writer.
  • saves/cap-00-future-0.sav (65536 bytes) is almost entirely filled with 0xFF. Exactly two 4096-byte windows deviate from the fill byte: 0x5000-0x5FFF and 0x7000-0x7FFF.
  • The 0x7000-0x7FFF window was proven, byte-for-byte, to be a verbatim copy of this game's own GBA cartridge ROM header (entry branch, internal title KARNAAJ, game code AYKE, maker code, fixed 0x96 byte, and a header complement-checksum byte that independently verifies against the standard public GBA header-checksum formula — see §4). This is not evidence of a genuine save record; it is evidence that this byte range of the capture is contaminated with ROM-mirrored/open-bus content.
  • The 0x5000-0x5FFF window contains only 19 non-0xFF, non-zero-adjacent bytes at its very start, followed by 4077 zero bytes. No decompiled function could be tied to writing or reading this range.

What was proven: the exact byte layout of the one .sav sample provided, and that the 0x7000 window is a ROM-header mirror (independently checksum-verified).

What remains open: whether this title has any real battery-backed save at all; the true backup-media type/size (unknown is carried forward from the packet, uncontradicted); the meaning (if any) of the 19-byte fragment at 0x5000; and therefore all writer/reader/checksum/field claims below 0x5000 are UNKNOWN or HYPOTHESIS, not CONFIRMED.

2. Physical Media, Slot Geometry & Redundancy

  • Capture file size: 65536 bytes (64 KiB). This is the size of the provided .sav capture buffer; it is not independently confirmed as the true cartridge backup-media capacity, because no save driver code was found to corroborate a specific media type (SRAM 32 KiB, Flash 64 KiB/128 KiB, or EEPROM 512 B/8 KiB all remain structurally possible for a 64 KiB capture window — the tool may simply allocate a fixed 64 KiB buffer regardless of actual chip).
  • Background fill byte: 0xFF (57402 of 65536 bytes), consistent with an erased Flash/SRAM bus or a pulled-up/open data bus — observed, not proven to be deliberate erase-state.
  • Active byte spans (non-fill): exactly two, both 4096 bytes and 4096-aligned:
  • 0x5000-0x5FFF (4096 B)
  • 0x7000-0x7FFF (4096 B)
  • Slots/copies: No slot or redundancy structure can be confirmed. The two 4KB-aligned active windows are superficially consistent with 4KB Flash sector granularity, but this is purely geometric coincidence absent any Flash command-sequence code — classified HYPOTHESIS, not CONFIRMED.
  • Generation/sequence counters, mirroring, selection rule: none identified. No second .sav sample or paired .ss save state was available in this workspace (states/ is empty) to test for a mirrored/backup copy or a selection rule.

3. Save Writer, Reader & Caller-Chain Architecture

No save-related I/O driver, serialization, or checksum function was identified in the decompiled corpus.

Evidence for this negative result:

  • ghidra/save_related_functions.c explicitly reports 0 MMIO seeds and 0 total functions after expanding 2-hop callers / 1-hop callees — i.e., the trace-guided extraction pass that seeds from known save-hardware MMIO addresses found nothing to seed from in this title's traced execution.
  • A full-text search of all 47 functions in ghidra/decompiled.c for SRAM/Flash/EEPROM address literals (0x0E000000/0x0D000000/0x040000D4 region forms), Flash unlock bytes (0x5555/0x2AAA), and the substrings checksum/save/Save/sector/erase/flash/bank/verify returned zero matches.
  • ghidra/callgraph.json contains 47 function nodes. The two root (caller-less) dispatcher functions are 0x08006a48 and 0x0800d862; both call a large, overlapping fan-out of small helper functions (0x08001c9c, 0x08001e88, 0x0800268c, 0x08002794, 0x080027b0…0x08002894, 0x08003794, 0x08004228). Manual inspection of 0x08006a48 (ghidra/decompiled.c:491-575) shows it is a bounded list-navigation loop (clamps an index param_3 between 0 and param_2-1, calls FUN_08001e88(0x5000000, puVar12, 0x100) which targets Palette RAM 0x05000000, and calls func_0x08014e4c/FUN_08002894 to build a 0x200-byte buffer) — i.e., a menu-cursor/UI routine, not a save writer. No evidence ties 0x0800d862 or any of their shared callees to backup media either.

Because no writer, reader, or caller chain touching 0x0D000000/0x0E000000 exists anywhere in the provided trace, the io_driver_functions and caller_chains sections of save-format.json are both empty arrays. This is reported as a finding in its own right rather than papered over: either this title's save I/O was never exercised during the trace that seeded this packet, or this title has little/no save-driver code to find. Both are plausible given SDK Save Tags in ROM: none detected and Observed Save Media: unknown in the packet metadata.

4. Magic Signatures & Checksum / Integrity Algorithm

No save-specific magic signature or checksum routine was found in code. The only verifiable magic/checksum structure in the .sav file is the standard GBA cartridge ROM header, which is present — unexpectedly — inside the capture's 0x7000-0x7FFF window, confirming that window is ROM-mirror contamination rather than save data.

Verified ROM-header mirror at .sav offset 0x7000

Relative to the start of this window (.sav offset 0x7000 = window offset 0x00), the bytes match the public, fixed-format GBA cartridge header byte-for-byte:

Window offsetFieldBytesDecoded
0x00ARM entry branch2e 00 00 eaB instruction (standard GBA reset-vector branch opcode)

Python verification (standard public GBA header-checksum formula — sum = Σ(-byte) over [0xA0..0xBC], checksum = (sum - 0x19) & 0xFF; this is public GBA hardware documentation, not game-specific third-party research):

blk = data[0x7000:0x8000]
s = 0
for b in blk[0xA0:0xBD]:
    s = (s - b) & 0xFF
chk = (s - 0x19) & 0xFF
# chk == 0xbe == blk[0xBD]  ->  True

Computed 0xBE == stored 0xBE → match confirmed. Since 0x7000 in the .sav file also equals the known GBA ROM-image offset 0x0 (i.e. the entry point and header always live at ROM offset 0x0/0xA0), this proves the .sav capture's 0x7000-0x7FFF window is literally a copy of the first 4KB of this cartridge's own ROM image, not a save record authored by any traced game function.

Conclusion: no save-integrity checksum algorithm could be identified or verified, because no save data distinct from this ROM-mirror artifact was found to carry one. checksums in save-format.json is therefore an empty array rather than a speculative entry.

Unverified fragment at .sav offset 0x5000

The only other non-fill bytes in the file are 19 bytes at the very start of the 0x5000-0x5FFF window, followed entirely by zero padding to 0x5FFF:

offset  0x5000: 65 54 a1 cb 04 03 01 01 01 00 88 13 00 01 00 00 00 00 01

No magic ASCII, no recognizable GBA structure, and no matching literal in ghidra/decompiled.c (checked, e.g., the little-endian u16 0x1388 = 5000 decimal formed by bytes at relative offset 0x0A-0x0B — not referenced anywhere in the decompiled corpus). Classified UNKNOWN.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states were provided (states/ is empty for this release), which blocks any reload-based counterfactual verification right now. Per standing capture requirements, any further harness run against this title must record paired sav-XX-pre.ss / sav-XX-post.ss states (plus gameplay.ss/final.ss) alongside any new .sav snapshot before fuzzing conclusions can be trusted. Until such states exist, the following is a plan, not an executed experiment:

  1. Falsify the "ROM-mirror artifact" hypothesis for 0x7000.
  • Mutation: overwrite one byte inside 0x70A0-0x70AC (the mirrored title string) with a different ASCII byte; leave the rest of the file untouched.
  • No checksum repair needed (no save checksum was found to cover this region; the only checksum present, at 0x70BD, is the ROM header's own and is not regenerated by game code as far as traced).
  • Predicted effect if the hypothesis is correct: no observable change in-game, because this byte range is never read by any traced save-reader (there is none) — the game should load and behave identically regardless of this byte's value. An observed gameplay/UI change would falsify the "pure artifact" hypothesis and should trigger re-opening the search for a hidden reader.
  1. Determine whether 0x5000's 19-byte fragment is live save data.
  • Mutation A: zero out all 19 non-zero bytes at 0x5000-0x5012.
  • Mutation B: flip only the 88 13 (little-endian 0x1388 = 5000) field at relative offset 0x0A-0x0B to 0x00 0x00.
  • No checksum repair attempted (none identified covering this range).
  • Predicted effect if this is a real save field: a fresh load from this .sav should show a different value somewhere observable (e.g. a reset high score, unlocked-content flag, or settings default) versus an unmodified control load. Matched-duration fresh-vs-restore comparison required — load both the original and mutated file from an identical cold-boot state and diff the resulting RAM (0x02000000/0x03000000) snapshot after an identical number of frames, to rule out confounds from differing play duration.
  • Predicted effect if this is also an artifact (e.g. open-bus noise never read by the game): no observable difference, matching §1/§3's overall finding that no save-reader code exists in the traced corpus.
  1. Protocol negative control. Load the original, unmodified .sav twice from identical cold-boot states and diff the resulting RAM state after identical frame counts, to establish the baseline noise floor (timers, RNG, uninitialized stack/heap bytes) before attributing any difference in experiments 1-2 to the mutated save bytes rather than normal nondeterminism.
  2. Save-or-no-save disambiguation. Run the title with the save-media backing store (SRAM/Flash/EEPROM, whichever the emulator defaults to) disabled or forced to constant 0xFF, and compare observable high-score/options/unlock state against a run with the actual cap-00-future-0.sav loaded. If no difference is observed across repeats, this would support the open hypothesis that this title has no functioning or exercised battery-backed save path in the traced build.

All four items require fresh trace capture with paired .ss states before they can move from "planned" to "executed/falsified or confirmed" status, per the mandatory pre/post save-state capture rule.
