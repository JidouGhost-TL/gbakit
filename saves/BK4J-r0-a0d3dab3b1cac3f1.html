Save Format Report: Croket! 4 - Bank no Mori no Mamorigami (Japan) [BK4J]

Release key: BK4J-r0-a0d3dab3b1cac3f1 · ROM SHA-256: a0d3dab3b1cac3f1ae1e79d1e1bc7628c272c0f673f63cf6160c61fd931a6f44

All findings below are derived strictly from this workspace: ghidra/decompiled.c (191 functions), ghidra/callgraph.json, ghidra/save_related_functions.c, and saves/cap-00-future-0.sav (the only .sav binary present), cross-checked with a fresh byte-level Python pass over the raw file (not just the pre-computed hexdump excerpt). No third-party game-specific research was consulted.

1. Executive Summary & Overall Confidence

Overall confidence: LOW.

What is proven (code + bytes agree):

  • The save region is partitioned into fixed 128-byte (0x80) slots, computed in code by FUN_0806db08 as 0x0E000000 + (index & 0xFF) * 0x80. The 32768-byte (0x8000) .sav file divides exactly into 256 such slots, and this is independently confirmed by the raw bytes: the last byte of every one of the 254 "blank" slots is the identical sentinel 0x41, recurring at every 0x80 boundary exactly as the address arithmetic predicts.
  • A narrow read-only path exists for slot 0 only: FUN_0806d824 deserializes one 3-byte record (u8 flag + u16 little-endian value) from slot 0 at base + record_index*3 + 1, and the on-disk bytes at that exact offset match the format perfectly (record 0 = 01 06 00 → flag=1, value=6; records 1-36 = 00 FF FF → flag=0, value=0xFFFF, a clear "empty" sentinel).
  • FUN_0806d71c / FUN_08072a20 consume records 1 and 2 as a self-test/comparator that feeds into bit-flag clears in a large in-RAM struct (consumers FUN_08088e68, FUN_08089044).

What remains open (not provable from this capture):

  • No save WRITE path was present anywhere in the traced decompilation. Across all 191 decompiled functions, the string 0x0e00/0xe000000 (or any Flash/EEPROM hardware address) appears exactly once, inside FUN_0806db08 itself. No function in this capture performs a store to that address range, no Flash command sequence (0x5555/0x2AAA/0xAA/0x55 unlock bytes) appears anywhere, and no EEPROM DMA3 (0x040000D4) bitstream code appears anywhere. The actual writer/flush/checksum routine that produced this .sav file was not captured by the trace that seeded this packet.
  • The checksum/trailer byte at the end of each slot (0x9E for slot 0, 0xF6 for slot 1, 0x41 for all 254 blank slots) could not be reproduced by any of sum8, xor8, 2's-complement-sum, or CRC32 over any tested byte range, using the single .sav sample available. With only one real sample and no paired pre/post save-states (the states/ directory is empty for this cohort), a checksum formula cannot be confirmed or falsified — this is marked UNKNOWN, not guessed.
  • Slot 1's content (A0 00 00 00 00 1F ..., trailer 0xF6) is not reached by any function in the trace — nothing in ghidra/decompiled.c ever calls the slot-address function with an index other than literal 0. Slot 1's structure and the leading unmapped byte at slot 0 offset 0x00 (0xC0) are therefore pure byte observations with no code corroboration and are reported as UNKNOWN.
  • Media kind is inferred, not proven: the direct pointer dereference in FUN_0806d824 (*pbVar3, no command-byte protocol) is inconsistent with Flash (which requires 0x5555/0x2AAA unlock sequences) and with EEPROM (serial, DMA3-driven, mapped at 0x0D000000), and is consistent with plain memory-mapped SRAM at 0x0E000000. The ROM's own SDK save tag, SRAM_F_V103@14961228, independently corroborates "SRAM" naming. This is treated as CONFIRMED_STATIC for "media behaves like directly-addressed SRAM," not as proof of the physical chip.

2. Physical Media, Slot Geometry & Redundancy

  • Total capture size: 32768 bytes (0x8000), file saves/cap-00-future-0.sav.
  • SDK save tag (from ROM metadata, packet-supplied): SRAM_F_V103@14961228.
  • Background fill byte: 0x00 (confirmed by direct read of the file; 254/256 slots are all-zero apart from their trailer byte).
  • Slot size: 128 bytes (0x80), derived directly from FUN_0806db08's arithmetic: (index & 0xFF) * 0x80 + 0x0E000000.
  • Slot count: 256 (0x8000 / 0x80), which exactly matches the file size — the hardware-addressable capacity and the capture size agree exactly, which is strong corroborating evidence for the slot size.
  • Slots actually populated in this sample: only slot 0 and slot 1 have non-zero body content. Slots 2-255 are entirely zero-filled except for a constant trailer byte 0x41.
  • Redundancy / mirroring: none observed. Slot 0 and slot 1 have structurally different first bytes and different trailer values, so they are not mirrors of each other. There is no evidence of a primary/backup pair, generation counter, or rotating-slot scheme in the traced code — the only "index" parameter ever passed to the slot-address function is the literal constant 0.
  • Selection rule: not determined. Only slot 0 is read by any traced function; whatever selects/writes slot 1 is outside this capture.

3. Save Writer, Reader & Caller-Chain Architecture

Low-level hardware I/O driver

FUN_0806db08 (0x0806db08) — the only function in the entire 191-function capture that references a save-hardware address.

int FUN_0806db08(uint param_1)
{
  return (param_1 & 0xff) * 0x80 + 0xe000000;
}

Role: slot-index → absolute address translator for the SRAM window at 0x0E000000. It is a pure address calculator; it performs no I/O itself (no load/store), which is why ghidra/save_related_functions.c correctly flags it as an "MMIO-seed" candidate rather than a full driver.

Note on the callgraph: ghidra/callgraph.json lists "0x0806db08": {"callers": [], "callees": []}, i.e. no recorded caller. This is contradicted by the decompiled source itself — FUN_0806d824 (line ~335 of ghidra/decompiled.c) contains an explicit call iVar2 = func_0x0806db08(0);. The static C is treated as ground truth here; the callgraph's caller/callee edges for this address are incomplete and should not be trusted in isolation.

No store-side driver (SRAM byte-copy write, Flash command sequence, or EEPROM DMA3 bitstream) exists anywhere in ghidra/decompiled.c. This was confirmed by grepping the full 7370-line decompilation for every hardware-save address and command pattern listed in the clean-room rules (0x0e00, 0x0d00, 0xe000000, 0xd000000, 5555, 2aaa, 0x40000d4, DMA3); the only hit in the entire file is the single line quoted above.

Reader / deserializer chain for slot 0's record table

FUN_0806d824 (0x0806d824), callers: [0x0806d71c] (per ghidra/decompiled.c; callgraph.json agrees here).

void FUN_0806d824(int param_1,ushort param_2)
{
  byte bVar1;
  int iVar2;
  byte *pbVar3;
  iVar2 = func_0x0806db08(0);
  pbVar3 = (byte *)(iVar2 + (uint)param_2 * 3 + 1);
  *(ushort *)(param_1 + 2) = param_2;
  *(ushort *)(param_1 + 6) = (ushort)*pbVar3;
  bVar1 = pbVar3[1];
  *(ushort *)(param_1 + 4) = (ushort)bVar1;      // dead store, overwritten next line
  *(ushort *)(param_1 + 4) = CONCAT11(pbVar3[2],bVar1);
  ...
}

How mapped: param_2 is a record index. pbVar3 is always computed from slot 0's base (FUN_0806db08(0) — the literal 0, never any other slot). Each record is 3 bytes, starting at slot-relative offset param_2*3 + 1 (i.e. offset 0x00 of the slot is skipped — it is never read by this function). The function writes three fields into a caller-supplied 8-byte-ish output struct at param_1:

  • param_1+2 (u16): the record index itself (echoed from the input, not read from the file).
  • param_1+6 (u16, zero-extended from a u8): the record's flag byte, pbVar3[0].
  • param_1+4 (u16, little-endian): the record's value, built from CONCAT11(pbVar3[2], pbVar3[1]) = (pbVar3[2]<<8) | pbVar3[1].

This was verified byte-for-byte against saves/cap-00-future-0.sav (see §4/§5) — record 0 is 01 06 00 (flag=1, value=6); records 1-36 are uniformly 00 FF FF (flag=0, value=0xFFFF).

FUN_0806d71c (0x0806d71c), callers: [0x08072a20].

void FUN_0806d71c(undefined2 param_1)
{
  uint uVar1;
  undefined1 auStack_18 [4];
  ushort uStack_14;
  short sStack_12;
  uVar1 = 0;
  if (((*_DAT_0806d75c & 1) == 0) && (func_0x0806d824(auStack_18,param_1), sStack_12 != 0)) {
    uVar1 = (-(uStack_14 ^ uRam0806d760) | uStack_14 ^ uRam0806d760) >> 0x1f;
  }
  ...(*UNRECOVERED_JUMPTABLE)(uVar1);
}

Role: a comparator/self-test, not a writer. It gates on a device/status byte (*_DAT_0806d75c & 1 == 0), reads one record via FUN_0806d824, and — if the record's value field is non-zero — compares the record's flag byte against a global in-RAM reference byte uRam0806d760 using the classic branch-free "is-nonzero" idiom (-(v)|v)>>31. It returns 1 if the stored flag differs from the expected in-RAM value, 0 otherwise. This is a verification primitive, never a mutation of RAM or SRAM.

FUN_08072a20 (0x08072a20), callers: [0x08088e68, 0x08089044].

void FUN_08072a20(void)
{
  uVar2 = FUN_0806d71c(1);
  iVar3 = -((int)(-(uVar2 & 0xffff) | uVar2 & 0xffff) >> 0x1f);
  sVar1 = FUN_0806d71c(2);
  if (sVar1 != 0) { iVar3 = iVar3 + 1; }
  (*UNRECOVERED_JUMPTABLE)(iVar3);
}

Combines the comparator result for records 1 and 2 into a 0/1/2 mismatch count. This is the entry point the two big RAM-struct builders call.

FUN_08072b38 (0x08072b38), callers: [0x08088e68, 0x08089044] — a second, unrelated bit-test (-(*_DAT_08072b48 & param_1) >> 0x1f) against a different global flag; it never touches the SRAM/slot path at all. It is listed here because the two consumer functions call it alongside the slot-0 self-test.

Callers that mutate the in-RAM save/profile struct based on the self-test

FUN_08088e68 and FUN_08089044 (both large state-machine-style functions, 0x08088e68/0x08089044) build and update a large in-RAM structure (observed field offsets up to at least +0x1A0 from a base pointer *_DAT_0808902c) covering sub-ranges +0x20, +0x3C, +0x100..0x104, +0x110, +0x11C, +0x128, +0x140, +0x180 (an 0xF-entry array), +0x198, +0x1A0. Relevant excerpt from FUN_08088e68:

sVar3 = FUN_08072a20();
if (sVar3 == 0) {
  **(byte **)(*_DAT_0808902c + 0x1a0) = **(byte **)(*_DAT_0808902c + 0x1a0) & 0x7f;
}
sVar3 = FUN_08072b38(1);
if (sVar3 == 0) {
  **(byte **)(*_DAT_0808902c + 0x198) = **(byte **)(*_DAT_0808902c + 0x198) & 0x7f;
}

How mapped: when the slot-0 self-test (FUN_08072a20) reports no mismatch (0), bit 7 (0x80) of the byte at RAM struct offset +0x1A0 is cleared. Independently, when the unrelated flag test (FUN_08072b38) reports 0, bit 7 of the byte at +0x198 is cleared. Both are read-driven RAM mutations (clearing a flag bit based on what was read from slot 0 / a global flag); neither writes anything back to SRAM. FUN_08089044 repeats the identical two-call pattern. These are the only two call sites in the entire capture that consume the slot-0 read path; no caller above them (into these two functions) was present in the trace, so the ultimate trigger (e.g., title-screen boot vs. save-select menu) is unknown.

Gap: no writer/flush function was captured

The clean-room rule requires documenting "ALL callers" and the write path — honestly, none exists in this trace. ghidra/save_related_functions.c itself states only "1 MMIO seeds, 1 total" were extracted, consistent with this: the trace that produced this packet seeded from the hardware-address literal and expanded 2 hops of callers / 1 hop of callees, and that expansion simply never encountered a store to the SRAM window. This is reported as an open gap rather than filled with speculation.

Checksum / trailer-byte algorithm: UNKNOWN

Every 128-byte slot ends in a single byte that differs between "blank" and "used" slots:

slot 0 (used):   trailer = 0x9E
slot 1 (used):   trailer = 0xF6
slots 2-255:     trailer = 0x41   (all 254 of them, identical, over all-zero bodies)

Python verification was run against the real file (not just the pre-computed hexdump excerpt) for every candidate algorithm the clean-room hardware rules make plausible:

None of sum8, xor8, or crc32 (full or truncated to one byte) over the slot body reproduce the observed trailer byte for either used slot, and no simple additive/complement relationship (trailer - sum, trailer + sum, 0x41 - sum) was constant across the two used slots either. Conclusion: the trailer byte's algorithm cannot be determined from this single .sav sample. It is marked UNKNOWN rather than guessed. Confirming it requires either (a) the actual checksum-computation function, which is not present anywhere in this 191-function trace, or (b) multiple .sav samples with deliberately varied slot-0 content so the trailer's dependence on specific bytes can be isolated differentially — exactly the kind of counterfactual listed in §6.

6. Save Fuzzing & Counterfactual Verification Plan

No paired .ss save states exist for this cohort (states/ is empty, as stated in the packet). The following plan is therefore a set of concrete, falsifiable predictions to run once paired pre/post save-states become available, per the standing instructions requiring paired .ss capture for every future .sav snapshot.

  1. Record 0 flag mutation — flip offset 0x0001 from 01 → 00.
  • Requires checksum repair: UNKNOWN whether the trailer at 0x007F must change (formula not proven in §4); run both with the original trailer and with several candidate trailers to probe acceptance.
  • Predicted effect: if FUN_08072a20's consumer path (FUN_08088e68/FUN_08089044) runs on next boot/load, bit 7 of the in-RAM byte at struct offset +0x1A0 (mirrored from *_DAT_0808902c) should flip state relative to an unmutated control, since FUN_0806d71c(1)'s comparison against uRam0806d760 will change outcome. Observable via RAM-watch on that struct offset in a live emulator trace, or via any UI element ("NEW"/unlock-style indicator) gated on that bit.
  • Matched-duration control: run an identical boot sequence with the unmutated file to establish the baseline bit state first.
  1. Record 0 value mutation — change offset 0x0002-0x0003 from 06 00 to 00 00 (making the value field exactly zero).
  • Predicted effect: per FUN_0806d71c, the gating condition sStack_12 != 0 becomes false, so the comparator short-circuits and always returns 0 (no mismatch) regardless of the flag byte — this is a sharp, falsifiable prediction distinguishing "value acts as a presence gate" from "value is cosmetic."
  • Counterfactual: also test value 0x0001 (nonzero but different) to confirm the gate is a non-zero test, not an exact-match test.
  1. Records 1/2 sentinel mutation — change offsets 0x0004 and 0x0007 (the two sentinel records FUN_08072a20 actually consumes) from 00 FF FF to 01 FF FF.
  • Predicted effect: FUN_08072a20's returned mismatch count should increase by 1 or 2 (from the baseline of whatever it currently evaluates to, given uRam0806d760's runtime value is unknown without a live trace) — run with RAM-watch on uRam0806d760 and the function's return value simultaneously to pin down its baseline.
  1. Trailer byte mutation (checksum-repair negative control) — flip only 0x007F (slot 0 trailer) while leaving the rest of slot 0 untouched, across several values including 0x00 and 0xFF.
  • Predicted effect: unknown by design — this is the counterfactual that will reveal whether any validator (necessarily untraced in this capture) rejects/corrects the save, which would prove a checksum exists even though its formula is not yet known. A fresh-boot (cold reload) vs. in-session reload comparison should be run as a matched pair, since SDK-level validators often only run at cold boot.
  1. Slot 1 content mutation (open-question probe) — mutate offset 0x0080 (A0 → 00 and → FF) and separately 0x0085 (1F → 00).
  • Predicted effect: unknown — no traced code reads slot 1 at all, so any observable effect here would itself be a discovery (it would prove an untraced function does read slot 1), while no observable effect would be consistent with slot 1 being dead/unused data from an earlier build or an unrelated subsystem.
  • Protocol negative: include an unmutated control run in the same batch to rule out unrelated non-determinism.
  1. Fresh vs. restore repeat — for every mutation above, run both (a) a fresh game boot with the mutated .sav already present, and (b) a mid-session save-reload with the same mutated bytes, to separate cold-boot validation behavior from in-session read behavior, since FUN_0806d71c's device-ready gate (*_DAT_0806d75c & 1) suggests a hardware-status check that may behave differently across boot phases.

All mutation/observation pairs above must preserve the required sav-XX-pre.ss + sav-XX-post.ss + .identity.json sidecars, plus gameplay.ss and final.ss, per the standing per-.sav paired save-state requirement, and must stay within the bounded (≤8 screenshot / ≤4 save-state) capture retention policy.

Open Questions

  • No save WRITE/flush/checksum-computation function exists anywhere in this 191-function trace; where is it, and does it live in a different code region not reached by the 2-hop/1-hop seed expansion?
  • What produces and writes slot 1 (0x0080-0x00FF)? No traced function ever calls the slot-address function with index 1.
  • What is the trailer-byte algorithm (0x9E/0xF6/0x41)? Unconfirmed with a single sample; needs differential samples.
  • What does slot 0 offset 0x0000 (0xC0) mean? Never dereferenced by any traced function.
  • Is ver0000006 at 0x0075-0x007E genuinely an SDK version tag correlated with the ROM's SRAM_F_V103@14961228 tag, or coincidental? No code reads this span in the capture.
  • What is the real-world semantic meaning of record 0's value field (6)? Structure is proven; meaning is not.
  • Does the 256-slot capacity ever get used beyond slots 0-1 in later-game saves (e.g., more save files, more unlocks)? Not observable from a single capture.
